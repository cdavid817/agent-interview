### 1. Claude Code 的启动流程如何隐藏冷启动延迟？这套「触发 + 等待」两段式设计有什么约束？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

延迟隐藏的手段不是把阻塞调用变快，而是把它挪进主线程本来就在忙的时间窗。

1. 进程加载主模块要花掉数百毫秒解析编译，这段窗口里已经并行触发 MDM 配置读取与 macOS 钥匙串预取。钥匙串是同步阻塞调用，单次约 65 毫秒、两次约 130 毫秒，同步读会被直接感知，挪进编译窗口就被吞掉。
2. 初始化阶段就对 API 域名预连，把约 100–200 毫秒的 TCP 与 TLS 握手同配置加载、worktree 创建重叠，首次查询时连接已就绪。
3. CLAUDE.md 读取、git 状态快照等非关键预取推迟到首帧之后——首帧是用户心理上的「已启动」信号，这一段优化的是感知延迟而非总耗时。

约束在于初始化函数必须写成「触发」和「等待」两个，而不是调用即拿结果。代价有三：调用点必须成对出现，漏掉等待就读到半成品状态；预取里的异常推迟到等待点才暴露，栈信息离现场很远；等待点只是大概率已完成而非保证，仍要能承受真等待。验证靠在启动路径上打点，比较各阶段耗时、首帧耗时与首字节延迟，而不是只看进程总时长。

**相关知识点：** 冷启动延迟、并行预取、预连接、感知性能、两段式初始化、启动打点。

### 2. 三阶段引导中哪些时序约束一旦打乱就会造成难以复现的间歇性故障？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

引导顺序里混着两类约束：性能上的「越早越好」和正确性上的「必须在此之前」。后者被打乱不会立刻报错，只会偶发。源码分析点出四条：

1. 额外 CA 证书必须在任何 TLS 连接（含对 API 域名的预连）之前应用，否则预连会因证书校验失败。
2. 设置工作目录必须早于所有依赖它的代码，worktree 创建、git 操作与 CLAUDE.md 发现都读这个隐式全局量。
3. 在项目信任建立之前只允许应用「安全」的那一部分环境变量，防止未信任的项目配置注入危险变量。
4. 遥测 sink 的初始化必须早于第一条启动事件，否则事件只会入队而不会上报。

难复现的原因是失败面都依赖外部条件：证书问题只在自签根证书的企业网络里出现；工作目录问题只在从子目录启动或带 worktree 时暴露；sink 问题根本不影响功能，只表现为某类事件上报率莫名偏低，要对着监控看漏报才发现。这也是引导期全局状态文件顶部写着「不要再往这里加状态」的原因——正确性由初始化顺序保证，而顺序在代码里没有任何强制表达。

验证靠给每个阶段打点并断言前后关系，冒烟测试覆盖自签证书与子目录启动，并把启动事件上报率当指标监控。

**相关知识点：** 引导时序、隐式全局状态、信任门槛、遥测 sink、启动冒烟测试、事件上报率。

### 3. queryLoop 作为异步生成器需要维护哪些不变量？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

难点不在单轮流程，而在流式接收、工具并发执行、错误恢复三者交织时仍要让消息历史满足 API 的一致性要求。可归为三条：

1. **配对完整。** 每个产出的 tool_use 最终都要有 id 对应的 tool_result，缺一个下一轮请求就被拒。中断、流式回退、错误兜底三条路径各自负责补合成。
2. **引用稳定。** 增量事件到达时，用量与停止原因是就地改写已有消息对象而非替换成新对象。因为这条助手消息已经进了可变消息数组，可能正被界面渲染、被 transcript 落盘、被其他子系统持有，替换对象会让持旧引用的地方读到过时数据。代价是放弃「消息不可变」，换取多方并发读取下的一致性——这里引用稳定比不可变更值钱。
3. **恢复不自激。** 跨迭代状态在每轮结束时整体交棒给下一轮，其中带着几个计数与标志位：「本轮是否已尝试过响应式压缩」防止压缩后仍超长时无限重压，最大输出 token 的恢复次数也有上限（不超过三次）。它们熔断的是「恢复路径本身又触发了它要恢复的那个错误」这类自激循环。

三条都不适合只用单测覆盖：配对靠出口断言两侧 id 集合相等；引用稳定靠对同一对象的多方读取做一致性断言；自激靠注入持续超长的上下文，观察重试次数是否被计数器封顶、错误率是否收敛。

**相关知识点：** 异步生成器、消息历史一致性、引用稳定性、可变状态交棒、熔断计数器、不变量断言。

### 4. 为什么 tool_use 与 tool_result 的配对不变量在错误恢复路径上最容易被破坏？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

因为正常路径上 tool_result 是执行的副产品，自然生成；而恢复路径恰好被触发在「tool_use 已经产出、执行却不会完成」的夹缝里。

硬约束是每个 tool_use 块必须在后续消息中被 id 匹配的 tool_result 回填，缺一个整轮请求就报 400。而助手消息一旦流出去、被 transcript 落盘就不能当作没发生过，所以三条恢复路径都得显式补齐孤儿：中断时把已入队未完成的工具收口成标记为中断的合成结果；流式退回非流式、要丢弃已产出助手消息时给孤儿补合成；错误兜底返回模型错误前也先补合成。

两点判断。一是**补合成必须携带语义**：中断和失败对模型是不同信号，若都写成无差别的错误文本，模型会把「没跑」当成「跑了但失败」，去改参数重试一件没执行过的事。二是**这条不变量跨越持久化边界**，检查点得放在「消息即将进入下一轮请求」的出口而非工具执行内部——放在内部就漏掉了尚未启动就被取消的那批。

验证靠出口断言两侧 id 集合相等，并用混沌测试随机注入中断与流式回退，统计 400 错误率与补合成触发次数。

**相关知识点：** 工具配对不变量、孤儿补合成、中断语义、持久化边界、混沌注入、协议级错误率。

### 5. 流式工具执行中的「兄弟取消」要解决什么并发正确性问题？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

流式执行的前提是「模型还在输出，工具已经在跑」，这带来串行实现没有的问题：同一批里先失败的那个，可能已经把环境改成后面几个工具的假设不再成立的样子。

1. 触发条件不对称：只有 Bash 工具报错才会取消同批兄弟，Read、WebFetch 这类失败只影响自己。依据是失败相关性——Bash 报错往往意味着环境出了问题（磁盘满、权限不足、依赖缺失），后续命令大概率一起失败或产出误导性结果；而某个文件不存在、某个 URL 不可达是局部的。
2. 每个工具有自己的取消控制器，另有一个兄弟控制器专做批次级取消。取消不等于可以不给结果，被取消的工具仍要产出合成结果，否则留下孤儿。
3. 源码分析自己把这条定性为启发式而非定理：Bash 失败也可能只是「某个命令不存在」这种局部问题，取消兄弟就成了误杀。选择保守，是因为多跑一条注定失败的命令的代价高于少跑一条本可成功的。

配套约束是顺序保持：结果按 tool_use 在模型输出里出现的顺序回填而非完成顺序。这既维持对话可读性，也让缓存前缀稳定。

划不划算看三个数：误杀率（被取消的兄弟里事后判定本可成功的比例）、批次耗时相对串行的下降幅度、缓存命中率有没有稳住。

**相关知识点：** 流式工具执行、兄弟取消、失败相关性、取消传播、顺序保持、缓存前缀稳定性。

### 6. Claude Code 的工具并发模型如何决定哪些工具可以并行执行？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

判定权在工具自己手上：每个工具声明一个「并发安全」谓词，且它接收本次输入，所以同一工具的不同调用可以有不同答案。最典型的是 Bash——它的并发安全性直接等同于本次命令是否只读，于是两条只读命令能并行，写操作必须独占。

这不是机械的只读判定，而是一份语义契约，要求两件事同时成立：没有副作用或副作用彼此隔离；不依赖也不修改其他工具可能读取的共享可变状态。声明错了不会立刻报错，只会变成偶发的结果错乱，这是最大的风险敞口。

调度有两条路径。流式路径在模型还在输出时就把工具入队执行，并发安全的互相并行、非并发安全的独占；非流式路径把同一批调用按连续段分桶，连续的并发安全段并发跑（默认并发上限 10），其余串行。收益是「读五个文件」的耗时从五者之和降到接近最慢的那个。

代价落在共享上下文上：并发安全工具对执行上下文的修改不立即生效，要推迟到批次结束再处理。源码分析在这里说法不齐：多处正文说延迟应用能避免相互覆盖、修改都留得住，只有一条代码注释说这类修改可能丢失。稳妥的结论是：并发安全工具不要依赖自己的上下文修改被同批其他工具看到，只做读取。

验证靠两个抓手：把「声明为并发安全的工具是否真的只读」做成静态检查加回放测试；盯批次结果一致性与耗时下降幅度，一致性掉了说明有声明在撒谎。

**相关知识点：** 并发安全谓词、语义契约、分桶调度、并发上限、上下文修改延迟应用、回放一致性测试。

### 7. 权限模型的分层决策链由哪几层构成？每一层能否单独否决？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

它不是一条规则链，而是一个决策栈，每层的触发条件与否决权都不同。

一次调用依次过这几道闸：整工具 deny、整工具 ask（沙箱可自动放行时例外）、工具自身权限检查、强制交互的工具、内容级 ask、安全检查，之后才轮到绕过模式与 allow 规则，全不命中则默认转询问。

否决权是不对称的，这是整套设计的核心：

1. deny 规则单独否决且不被任何 allow 覆盖，工具自身权限检查返回 deny 同样直接生效。钩子返回 allow 只意味着「不阻止」，后面仍要跑基于规则的检查；返回 deny 才直接拒。理由是钩子可能来自插件、可能被改过，自动化决策不该凌驾于安全策略之上。
2. 安全检查能单独把结论抬成询问并免疫绕过模式。它盯写 `.git`、`.claude`、`.vscode` 与 shell 启动配置这几类路径：它们有提权效应，一次修改就影响之后所有操作。
3. 绕过权限模式排在这些之后才生效，免除的只是「本来要问的」，免不掉前面那几道闸。

审计靠每个决策都带判别式的「决策理由」——规则、模式、钩子、沙箱放行、分类器、安全检查等十余种。要监控的是各理由的占比漂移：分类器理由突然上升，通常意味着规则被误删。

**相关知识点：** 分层决策栈、强制交互否决点、拒绝优先、安全检查免疫、绕过模式边界、决策理由审计。

### 8. 权限规则字符串如何解析？文件系统 glob 匹配有哪些易错边界？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

规则统一写成「工具名」或「工具名(内容)」，内容的语义由各工具自己解释：Bash 当命令、文件工具当路径模式、网页抓取当域名。

解析上有两个坑：右括号要求是最后一个未转义的且必须落在串尾，否则整串**降级成纯工具名而非报错**；反转义必须先还原括号再还原反斜杠，顺序反了会双重转义。

文件模式的易错边界更多：

1. **以斜杠开头不是文件系统根**，而是「该规则所属来源的设置根目录」——用户设置里的 `/x` 与项目设置里的 `/x` 指向不同地方。以 `~` 开头才是主目录，且要做 Unicode 规范化。
2. 匹配走 gitignore 语义的库，模式尾部的 `/**` 会被剥掉：那个库把一个路径视为同时匹配它自身与它内部。
3. macOS 上 `/tmp` 与 `/private/tmp` 是同一处，判定要同时看原始形式与符号链接解析后的形式。
4. 通配符转正则有一条特例：模式以「空格加单个星号」结尾且这是唯一未转义通配符时，`git *` 也匹配裸 `git`，以对齐旧前缀语法。

这类代码只能靠表驱动验证：把每条边界写成「规则 + 路径 + 期望判定」的三元组跑覆盖率，并对 deny 规则做变异测试，盯漏判率。

**相关知识点：** 规则字符串解析、转义顺序、来源相对根、gitignore 语义匹配、符号链接归一化、表驱动测试。

### 9. BashTool 为什么要做 AST 级子命令拆分？只做字符串黑名单会漏掉什么？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

黑名单匹配字面，语法解析匹配语义，两者的差距就是绕过面。加引号、注释、转义之后字面不同而语义等价；`git$(echo status)` 看着像 git 命令实则是命令替换。归一化之后规则才匹配得住真实意图。

只做字符串黑名单会漏掉三类：

1. **复合命令藏毒。** `&&`、`;`、`|` 串起来的命令要拆成子命令逐个匹配，否则「安全命令 && 危险命令」整体绕过了对后者的检查。
2. **前缀伪装。** 环境变量前缀能改变命令行为，剥离因此分两套：allow 用保守剥离，只剥确定安全的变量与包装器，绝不剥 PATH、动态链接器这类能劫持可执行文件的变量；deny 和 ask 用激进剥离，默认剥掉全部前导变量，另有一份可选黑名单挡住劫持类变量——拦截必须穿透伪装。
3. **组合才危险的逃逸。** 单条子命令看着无害，组合起来才有问题：既切目录又有重定向就抬成询问，防先切进配置目录再往里写；切目录后跟 git 同样抬成询问，防恶意仓库靠自带钩子在你执行 git 时拿到执行权。含变量的重定向与进程替换则不必组合，单独出现就抬询问，后者限非 AST 路径。

配套的非对称设计是：allow 的前缀规则**不匹配**复合命令，deny 与 ask 却必须能匹配其中任意子串。便利策略保守，安全策略激进。

代价是解析可能失败或被判为过于复杂，此时退回询问而非放行。验证靠红队语料回归：维护等价变形与绕过样本，盯漏判率与解析不可用率。

**相关知识点：** 语法树解析、子命令拆分、环境变量剥离、非对称匹配策略、解析降级回退、红队语料回归。

### 10. auto 模式的 AI 分类器如何工作？预批准域名机制的风险边界在哪里？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

分类器只在「规则判定为询问」这一个点介入，目标是减少中断而非放宽策略。它前面还有几道快速通道：不可被分类器覆盖的那类安全检查（敏感文件路径不算在内）与要求人工交互的工具维持原询问，只读与元数据工具走白名单放行，写入类工具则由「接受编辑」模式重跑权限检查提前放行。

三处设计值得注意：

1. **输入刻意裁剪。** 送进分类器的对话只保留用户文本与助手的工具调用，**排除助手的自然语言输出**——否则模型能靠自己写的话给自己的动作背书，形成自证循环。
2. **双阶段换延迟。** 第一阶段输出上限压到几十到几百个 token 并带停止序列，绝大多数安全动作在这里判完，只有可疑的才进第二阶段做深度分析。这是拿准确率的边际收益换 P95 延迟。
3. **出错时选择保守。** 分类器不可用由一个默认开着的门控直接拒绝，对话过长则回退正常询问——两种都不放行。另有连续拒绝与总拒绝上限，超限回退人工批准，避免误判引发「拒绝风暴」。

预批准域名是另一条路径：约八十个文档与代码站点在网页抓取的权限检查末尾直接放行，匹配时强制路径段边界以防前缀欺骗。风险边界有两条：**它只覆盖网页抓取工具的 GET 请求，Bash 里的 curl 与沙箱网络限制都不继承这份名单**；它降低的只是询问频率，取回的内容仍是不可信数据。

可测口径是自动批准率、误放率与误拒率、第一阶段命中比例与成本增量。

**相关知识点：** 权限分类器、快速通道白名单、输入裁剪防自证、双阶段分类、失败保守回退、预批准域名边界。

### 11. 工具结果落盘与延迟加载如何降低上下文占用？代价是什么？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

结果侧有三道闸，按代价从低到高排：

1. **单结果落盘。** 每个工具有自己的结果字符数阈值，超过就把完整内容写进结果目录，模型只收到一段带标记的预览。Read 的阈值被设成无穷大：它的结果一旦落盘，模型会想去读那个文件，又触发落盘，形成自引用循环。
2. **批量预算。** 即使每个结果都没超阈值，累积仍可能过量，预处理管道里还有一道工具结果预算按优先级裁剪。
3. **缓存层删除。** 服务端缓存还有效时，用缓存编辑接口只在发往 API 的请求里删掉旧工具结果，本地历史保持完整；缓存已过期就直接把旧内容替换成占位符——已无前缀可保。判据是「此刻缓存还值不值得保」。

延迟加载走的是另一侧：声明为延迟的工具其 schema 不随系统提示发出，模型靠关键词搜索按需发现。

代价集中在三处。预览有损，模型可能基于不完整的头尾做判断；本地历史与实际发送内容出现分叉，调试时看到的 transcript 不等于模型看到的东西；延迟加载则让模型可能调用一个 schema 没发出去的工具，校验失败后靠提示引导它先搜索，多花一轮往返。可量化口径是落盘触发率、缓存读与缓存创建的 token 比例、延迟加载引入的额外轮次占比。

**相关知识点：** 结果落盘阈值、自引用循环、工具结果预算、缓存编辑删除、历史与请求分叉、延迟加载往返成本。

### 12. 大结果格式化策略如何在信息完整性与 Token 成本之间取舍？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

每个工具都要实现一个把内部输出映射成 API 结果块的函数，这是结果回填的主收口点，绝大多数增删都发生在这里——也意味着 Token 主要花在这里。

往结果上追加内容的口子有好几个：用户批准工具调用时附带的反馈与图片块接在结果之后；工具还能返回额外消息（例如 PDF 文档块、图片元数据）；工具成功后的钩子可以注入附件，MCP 工具走单独路径，钩子能直接改写它的输出再回填。文件读取的映射还会给文本加行号，并附一段网络安全提醒，较新的模型被豁免这段。

取舍就在这些追加项上：行号让后续编辑能精确定位、减少整文件重写，但每一行都在花钱；提醒文本对能力足够的模型是纯冗余，所以按模型豁免；超阈值只给预览最省，代价是信息有损。

**判断标准不是「省了多少 Token」而是「省下的部分有没有被真正用到」**：拆出结果里各部分的 Token 占比，对照删掉它之后的任务完成率与重试次数变化。钩子这一层还要单独看耗时——它在结果回填的关键路径上，源码里对超过两秒的阶段单独打慢日志。

**相关知识点：** 结果映射收口、追加内容成本、行号定位、按模型豁免、钩子改写输出、关键路径耗时。

### 13. Claude Code 的成本与 Token 追踪在哪些层面埋点？如何归因到具体调用？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

埋点分三层，语义各不相同，混用就会算错账。

1. **单消息层。** 增量事件到达时按条累计用量，规则是「只用大于零的值覆盖」——增量事件可能带零值字段，直接覆盖会把已拿到的真实数字抹成零。覆盖的字段含输入、输出、缓存读、缓存创建、服务端工具用量等。
2. **跨消息层。** 另有一个求和累加器把多条消息的用量加起来形成本次查询总量。**同一份数据两种语义：单消息用覆盖，跨消息用求和**，写反了不报错，只会让账目慢慢偏。
3. **会话层。** 按模型算出美元成本后先按模型分桶，再写进全局状态，同时更新带 fast mode 标签的指标计数器，顾问类调用的用量递归计入。进程退出时把会话成本落盘，恢复会话时读回来。

归因靠查询链：每次查询携带链路 ID 与深度，父子查询因此能串起来，子代理与嵌套调用的花费不会变成无主账。返回给调用方的结果消息同时带总用量、总成本与分模型用量。

预算侧有两道熔断：每轮检查会话美元上限，超限直接终止查询并给出专门的错误类型；另有走 API 侧的任务预算，在压缩时维护剩余额度。

**相关知识点：** 分层用量埋点、覆盖与求和语义、按模型分桶、查询链归因、预算熔断、成本落盘恢复。

### 14. Claude Code 的错误处理与重试恢复分为哪几类？哪些错误不应重试？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

按「哪一层能修好它」分层，每层的重试预算独立，除无人值守模式持续重试外都有上限。

**传输层**只退避重试限流与过载这两类瞬时错误，过载有明确的次数上限（三次）；模型过载还可能抛出专门的异常触发切换备用模型。这里有一条容易被忽略的取舍：**非前台来源的查询遇到过载直接放弃**，因为后台任务多等的价值不如把配额让给用户可见的请求。

**循环层**有五条恢复路径：流式执行失败退回非流式，给已产出的助手消息立墓碑、清状态、重建执行器；切备用模型前要剥掉思考签名块，因为签名跨模型不兼容；上下文超长先折叠再走响应式压缩；输出 token 触顶先升级配额、再注入恢复消息，最多三次；中断与错误兜底则负责补齐工具结果配对。

关键机制是**「暂扣」**：上下文超长、输出触顶、媒体过大这几类错误不立刻抛给上层，先留给恢复路径，恢复成功用户根本看不到错误。

不该重试的有三类：用户中断，它是一个决定而不是故障；错误兜底认定的模型错误，此时直接返回不再循环；以及任何已耗尽计数器的恢复路径，继续重试只会自激。可测口径是各路径的触发次数与恢复成功率、重试带来的耗时增量，以及重试消耗的 Token 占总量比例。

**相关知识点：** 分层重试、指数退避、模型回退、暂扣机制、恢复计数上限、前台与后台差异化放弃。

### 15. 系统提示词的组装、缓存与 API 注入如何配合？改动哪一部分会击穿缓存？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

它不是一段字符串，而是三条并行取来的东西按不同通道注入：系统提示走 API 的 system 字段；CLAUDE.md 与当前日期组成的用户上下文作为**前置用户消息**注入对话，不是系统提示；git 状态快照拼到系统提示尾部。工具则完全不进提示字符串，作为独立的工具数组发送，schema 转换结果按工具名做会话级缓存。

缓存的结构由一个「动态边界」标记切开：标记之前是静态段，可以走跨组织的全局缓存范围；标记之后是用户与会话专属内容，只能按会话缓存。动态段有十来个，注册顺序即输出顺序，其中只有 MCP 指令段被标为不缓存——因为 MCP 服务器会在轮次之间连接与断开。框架强制这类段落必须填写理由，等于把「击穿缓存」变成一个需要解释的动作。

击穿点因此有三处：改动静态段会波及全局缓存范围；新增不缓存段落会让它每轮重算；工具集合变化会改变工具数组。缓存段本身则缓存到清空会话或压缩为止。

最值得学的是**日期的处理**：记忆段刻意不随日期失效，当前日期通过附件传给模型，而用户上下文消息故意保留过期值——否则缓存前缀每天必失效一次。验证看用量里的缓存读与缓存创建比例，以及首字节延迟。

**相关知识点：** 三通道注入、动态边界、全局与会话缓存范围、不缓存段的强制理由、故意保留过期值、缓存读写比。

### 16. thinking config 的决策依据是什么？fast mode 优化的是哪一段延迟？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

thinking 是三态配置：自适应、固定预算、关闭。决策只看两件事——本次要不要思考，以及模型支不支持自适应。支持的（较新的模型族）交给模型自己决定思考多少；不支持的给固定预算，取「输出上限减一」与该模型思考上限中的较小值。**减一是为了至少留一个 token 给真正的输出**，否则思考可能占满整个输出预算导致无输出。

另有两个开关：一个环境变量可完全关闭思考；长时间空闲后会置上一个粘滞的清除标记，把旧思考清掉，判断是空闲之后回来大概率不需要之前的思考上下文，清除动作可以交给 API 侧的上下文管理执行。

fast mode 优化的是**同一个大模型的输出速度**，而不是降级到小模型换速度。它靠一个 beta 头启用，用户可用命令切换。所以它省的是生成阶段的墙钟时间，不省 Token 也不改变模型能力——成本计数器专门带了 fast mode 标签，正是为了把它的用量与成本单独摘出来评估划不划算。

**相关知识点：** 自适应思考、思考预算上限、空闲清除粘滞、上下文管理、fast mode、按标签拆分成本。

### 17. 配置系统的来源合并顺序与 schema 校验如何设计？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

关键不在「有几个来源」，而在**同一套来源上并存着三种合并语义**：

1. 大部分设置是后来者覆盖：项目本地覆盖项目，项目覆盖用户。
2. 策略相关设置是先到者胜：企业受管策略一旦存在，其他来源改不动它。
3. 权限规则是累积合并：allow、deny、ask 从所有来源累加而不是覆盖。

第三条最容易踩：你不能靠在本地设置里补一条 allow 去「盖掉」项目里的 deny——规则只会加进同一个池子，而池子里 deny 优先。三种语义对应三种意图：普通设置用户该能改，安全策略企业该能锁死，权限规则宁可多几条也不能漏。注意这里说的是合并优先级，与来源的信任等级方向相反：项目设置在合并上盖过用户设置，信任级别却低于它。

项目设置是信任边界：它可提交进版本库，克隆一个恶意仓库就等于拿到了它的配置。防线包括首次打开项目的信任确认、把自动记忆目录的来源排除在外、三档策略门控（全禁钩子、只允许受管钩子、只允许插件自定义），以及 MCP 服务器、钩子与 Bash 权限在信任前不生效。

校验侧用 Zod：工具入参在调用前跑一次解析，失败返回结构化校验错误，并对延迟加载的工具额外提示「先去搜索它」。工具 schema 还按特性开关条件删字段，避免把不可用能力暴露给模型。验证靠合并结果的快照测试与配置迁移后的回归覆盖率。

**相关知识点：** 三种合并语义、先到者胜、权限规则累积、项目配置信任边界、策略门控分档、schema 校验与条件字段。

### 18. 历史会话持久化与 worktree 隔离如何配合？并行会话的状态边界在哪里？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

持久化选行式 JSON 是因为两个诉求：新消息直接追加不必重写整份文件，读取时可以只取尾部一小段。会话标题与标签就靠只读尾部约 16KB 的窗口提取——**这个优化引入了隐藏耦合**：压缩替换了消息历史之后，元数据可能被挤出尾窗，所以压缩流程必须重新追加一次会话元数据。

状态边界有三层，互不等价：

1. **transcript 只增不减**（读取有 50MB 上限），压缩只改变进入上下文的内容而不改档案。所以「压缩掉了」不等于「记录没了」，排查历史行为要看 transcript 而非当前上下文。
2. **子代理的输出走独立文件**，放在按会话分的子目录里，旁挂一份记录代理类型与 worktree 路径的元数据，既不污染主 transcript 又保住可追溯性。
3. **worktree 是文件系统级隔离**，目录名取代理 ID 前八位以保持路径简短。派生子代理继承父的上下文，而父上下文里的路径属于主工作区，所以要注入一段路径翻译提示，否则子代理会照着父上下文的路径去找，而它们在 worktree 里可能不存在或内容不同。

两处破口要留意：worktree 配置里的共享目录用符号链接实现，被共享的那部分并不隔离；结束时无改动的 worktree 删除、有改动的保留，因此「保留下来的 worktree 数量」本身就是可监控信号——它近似指示有多少个子代理留下了待审查的改动。

**相关知识点：** 行式追加存储、尾窗元数据、压缩与档案分层、子代理独立 transcript、worktree 路径翻译、共享目录破口。

### 19. 自动压缩链在什么条件下触发？它由哪几级组成？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

触发点是算出来的，不是一个固定百分比。

先定窗口：默认二十万 token，带长上下文标记或对应 beta 头则是一百万；环境变量覆盖排在这条优先级链的最前，模型自报的输入上限也在链上。再扣掉留给输出的那部分（最多两万）得到有效窗口，阈值是有效窗口再减一万三千 token 的缓冲。于是有一条不写在配置里的耦合：在两万以内调大输出上限，压缩会来得更早。

分级的原则是**从轻到重**。每轮迭代前，消息先只截取压缩边界之后的部分，再过工具结果预算与历史裁剪，然后是逐步加重的工具结果删除与折叠，最后才轮到要另发一次请求做整体摘要的压缩。越靠前越不损失语义、越不破坏缓存前缀，前面挡不住才升级。

另有三类抑制：压缩自身派生的查询不再触发压缩（否则摘要请求会递归地要求摘要）、折叠与响应式压缩开启时自动压缩让路，避免两套阈值互抢、可整体关掉的开关。

熔断器是最务实的一处：连续失败三次后本会话不再重试。它来自一次真实事故——曾有约一千三百个会话出现五十次以上的连续压缩失败，每天白白消耗约二十五万次 API 调用。宁可让用户手动处理，也不让恢复路径自己变成成本黑洞。

要监控的是触发率、压缩前后的 token 差与连续失败次数；压缩后一轮是否又越过阈值最能说明阈值设得够不够。

**相关知识点：** 有效窗口计算、阈值缓冲、从轻到重管道、递归压缩抑制、压缩熔断器、重触发监控。

### 20. compact 的 prompt 工程如何决定保留什么、丢弃什么？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

它不是等比例缩写，而是按「这类信息被改写之后损失多大」分级。

最高一级是逐字：用户消息是摘要提示里唯一被要求「全部列出」的一类，且要求原样引用——摘要模型有创造性改写的倾向，而用户消息是意图最可靠的来源，改一个词就可能让后续几轮跑偏；关键代码片段同理。次一级是保留要点：涉及的文件、错误与对应修复，后者防的是重新踩同一个坑。最低一级是模型自己的推理，只留结论性概述。

结构上另有一个草稿区：摘要模型先在分析块里按时间顺序过一遍对话再产出正式摘要，而分析块在进入上下文前被整段剥掉——它只用来提高摘要质量，本身不值得占 token。

有界性靠禁工具保证。摘要模型的工具调用全部被拒，约束在提示词首尾各放一遍。前置那一遍来自真实故障：走 fork 路径的摘要为了让缓存 key 一致必须继承父级完整工具集，而某一代模型会忽略尾部指令去尝试调工具；配合单轮上限，被拒的调用产不出文本，只能落进流式回退，这条路径的失败率从万分之一涨到接近百分之三。禁工具与输出 token 上限一起，让压缩成本不随对话长度增长。

压缩前的钩子还可注入聚焦方向，与用户自带指令合并，用户的在前。

可测口径是摘要失败率、压缩后首轮的重复读文件次数与工具重试次数。

**相关知识点：** 分级保留、逐字引用、草稿区剥离、摘要禁用工具、有界成本、聚焦指令注入。

### 21. compact 全流程的关键步骤有哪些？哪一步失败后最难恢复？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

整条流程按「失败之后还剩多少余地」可以切成三段。

**第一段是摘要产出前**，余地最大。摘要请求自身也可能太长，此时按 API 往返分组丢掉最旧的一组或几组重试，丢多少按超出的缺口算，最多三次。按往返而非按单条消息丢，是为了不拆散工具调用与结果的配对——与错误恢复路径上那条不变量同源，只是破坏来源换成了截断。

**第二段是历史替换**，不可逆但会显式报错：摘要顶替掉旧消息后它们不再进入上下文，档案仍在磁盘上，可查但不参与推理。

**第三段最难恢复：替换之后的状态重建。** 当前计划、已激活的技能、延迟加载工具已发出的 schema、后台代理的运行状态都不在消息历史里，却影响模型的后续行为。漏掉一项不报任何错，只表现为模型重新读一遍刚读过的文件、重新激活一次技能、或忘了正在执行的计划。为此边界标记要额外记下压缩前已发现的工具名，好让压缩后继续发送这些 schema。

同段里还有一处反直觉的选择性重置：已读文件状态被清空（压缩后由附件重新填回），技能清单却刻意不重置——重新注入它是纯粹的缓存创建。判据是重建代价，不是数据新旧。

可测口径是压缩后首轮的缓存读与缓存创建比例、重复读文件次数，以及距上次压缩的轮次数——太小说明阈值或摘要质量有问题。

**相关知识点：** 按往返分组截断、不可逆边界、压缩后状态重建、发现工具名续传、选择性重置、重压缩间隔。

### 22. microcompact 的双模式与 API 原生压缩有什么区别？各自适用什么场景？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

两种模式是同一个问题的两个答案：此刻还有没有值得保住的缓存前缀。

有前缀可保时走缓存编辑：本地消息一个字不动，只在发往 API 的请求里挂上删除指令，按数量阈值触发并保留最近若干个工具结果，档案仍能完整回放。缓存已冷时走内容清空：直接把旧结果换成占位文本——前缀反正已失效，再费力保护它没有意义。

冷的判定用时间而非 token：距上一条助手消息超过阈值（默认六十分钟）即认为服务端缓存已过期，这个默认值是照着服务端缓存有效期对齐的。它是一次近似推断，而不是去查询缓存的真实状态。

协同有两条硬规则。一是时间模式优先并短路，因为缓存已冷时缓存编辑毫无收益。二是时间模式触发后必须重置共享状态，否则下一轮的缓存编辑会去删一个已被清空的工具结果——两个模式共用模块级状态，切换时不清理就留下悬空引用。另外它只对主线程查询生效，子代理上下文短，收益抵不上复杂度。

API 原生的上下文管理是另一条分工线：客户端只决定策略（有没有思考块、要不要整体清除），服务端在处理请求时执行，省掉客户端构造编辑块这一层。

可测口径是缓存读与缓存创建的比值、每轮削减的 token 量，以及模式切换后有没有出现编辑失败。

**相关知识点：** 缓存编辑删除、内容清空、缓存冷判定、模式短路、共享状态重置、服务端上下文管理。

### 23. 响应式压缩 partialCompact 与整体压缩相比，优势和风险分别是什么？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

预防式压缩按估算提前动手，响应式压缩是估算失准后的兜底：流式接收时 API 回了上下文过长或媒体过大，错误先被暂扣不上抛，先试一次便宜的折叠排空，不够再走全量摘要。响应式的触发率因此本身就是指标——它高说明预防式那一侧的 token 估算偏差大。

部分压缩的优势在于方向可选。往后摘（保留枢轴之前）留住缓存前缀，命中率保得住；往前摘（保留枢轴之后）留住近期工作上下文，但摘要跑到了前面，缓存必然失效。整体压缩没有这个选择，部分压缩把「省钱」和「保连续性」变成一次显式决策。折叠的实现更克制：读时投影而非改写历史，摘要存在折叠存储而非消息数组里，每次入口重放，因此可撤销、历史完整。

风险有三处。

其一是机制互抢。折叠开启时自动压缩必须让路，否则自动压缩的阈值先命中，把折叠好不容易保住的细粒度整段抹掉；响应式压缩仍留作最后一道兜底。

其二是磁盘上的消息不再连续。边界要记下保留段的头、锚、尾三个标识供加载器重新串接；往前摘还必须把保留段里遗留的旧边界过滤掉，否则加载器从尾向头扫描会先撞上旧边界，把新摘要丢弃。元数据出错的表现是恢复出来的历史缺一段，而不报错。

其三是释放量不会自动被下一级看见：token 计数读的是受保护尾部消息的用量，轻量裁剪释放掉的量在那里看不出来，必须显式透传给下一级阈值检查。

**相关知识点：** 预防式与响应式、错误暂扣、压缩方向选择、读时投影、保留段重链、释放量透传。

### 24. Session Memory 压缩的模板工程要解决什么问题？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

它与一次性摘要的差别在于：会话记忆是一份被反复增量更新的活文档，而非每次重新生成的产物。这带来三个问题。

**一是结构漂移。** 增量更新的前提是结构稳定，于是有一条铁律：节标题与标题下那行斜体说明不能改、不能删、不能加，模型只准改说明行下面的内容。放松这条，按节切分统计 token 的工具就失效，模板的导航价值随之消失。

**二是无限膨胀。** 更新前先按节量一遍 token，单节超过两千就点名提醒压缩，总量超过一万二就追加强制精简指令。一份撑得太大的会话记忆反而当不成摘要。

**三是切多少条消息给它。** 保留区间从上次摘要点向后扩展，同时满足两个下限——至少一万 token、至少五条带文本块的消息——上限四万。下限保证模型还能接着干活，上限保证真的省下东西。区间起点另有一层地板压在最近一次压缩边界上。

切片本身还会破坏 API 的一致性要求：流式输出把一条逻辑消息切成多条物理消息，切片点因此要往前回退，把孤儿工具结果对应的调用与同一条消息 id 下的思考块一并纳入——又一次配对不变量，只是破坏来自切片而非中断。

可测口径是各节 token 分布、压缩后模型能否仍报出当前状态，以及切片后请求的协议级错误率。

**相关知识点：** 活文档更新、结构保留铁律、按节 token 监控、保留区间双下限、切片配对修复、协议一致性。

### 25. compact 的辅助机制与清理恢复负责什么？为什么需要单独设计？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

因为压缩不是纯函数。它动的只是消息数组，可别处有一堆状态是从消息历史推导出来的，不跟着处理就会留下不一致。按目的分三类。

**一是重新注入。** 会话启动钩子以「压缩」这个触发原因再跑一遍，把项目指令等上下文加回；用户上下文的缓存同时失效，因为钩子可能刚改过指令。触发原因被区分成启动、压缩、恢复三种，钩子据此决定要不要做完整初始化。

**二是给监控消音。** 压缩必然击穿缓存前缀、也必然让占用骤降，不告诉下游「这次是预期的」就会有两类误报：缓存断裂告警把正常压缩记成异常，上下文告急提醒在刚压完时还催用户去压缩。所以一边标记压缩已发生供缓存断裂检测使用，一边显式抑制警告。

**三是共享状态的谨慎处理。** 折叠状态是模块级共享的，子代理与主线程共用一份，因此只有主线程的压缩才重置它，否则子代理压一次就误伤主线程。已摘要消息的标识也要清空，旧消息已被裁掉，那个 id 指向的东西不复存在。

配套的是一份上下文构成分解：工具定义、MCP 指令、附件、消息各占多少 token 被拆开，同时供命令行可视化与压缩遥测使用。同一口径既给用户看也给后台看，压缩策略才谈得上可优化。

**相关知识点：** 压缩副作用面、触发原因区分、缓存断裂标记、告警抑制、模块级共享状态、上下文构成分解。

### 26. 记忆系统的召回相关性如何计算？写入互斥为什么必要？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

相关性不是向量相似度，而是一次独立的模型调用。系统扫描记忆文件（最多两百个）的 frontmatter，把每个压成一行清单——类型、文件名、修改时间、描述——交给更便宜的那一档模型挑出最多五个。描述是决定性的一栏，它是唯一进入召回判断的内容摘要，这解释了为什么要求描述写具体。

还有一层用途区分：某个工具正在被使用时，它的参考文档类记忆被跳过（模型已经在用，不需要说明书），坑与警告类则保留（模型可能正撞上）。相关性按用途分，不按主题分。

注入侧另有三道节流：已展示过的不重复选、会话总字节有上限、超大文件按字节截断并注明。

更值得学的是元认知注入：超过一天的记忆会带上「这是某个时间点的观察，引用前先核实」，并明确「记忆说它存在不等于它现在存在」，冲突时以现状为准。这是在承认文件式记忆没有事务一致性，用提示词把验证责任交回模型。

写入互斥的必要在于两条路径分析同一批消息：主代理本轮已直接写过记忆，后台提取就该跳过，否则写出重复甚至矛盾的条目。实现靠游标而非锁——写入方推进游标，提取方见游标已推进就放弃本轮。后台提取另有工具白名单与五轮上限，防它在核实某条事实上钻牛角尖。

可测口径是召回命中率、注入 token 占比与重复记忆比例。

**相关知识点：** 清单式召回、描述驱动相关性、按用途区分、注入节流、新鲜度元认知、游标互斥。

### 27. 团队记忆同步为什么采用乐观锁？发生冲突时如何合并？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

选乐观锁是因为冲突罕见：成员多数时候改的是不同条目，为低频事件付出常态阻塞不划算。拉取用条件请求带上版本标识，服务端按未变、不存在、已更新三种情况分别回应；推送只上传内容哈希与服务端记录不同的那些键。

冲突的处理不是文本三方合并，而是**重算增量**：服务端回版本不匹配时，客户端先探询一次当前各键的哈希，刷新本地记录的服务端校验和，再据此重算还需要上传哪些键，最多重试两次。合并粒度因此是键级——它保证你不会覆盖别人改的其它条目；至于同一个键被两端同时修改时最终留谁，源码分析没有再往下说，实践中应按后写覆盖来预期。

另外三处细节都来自真实部署环境。上传按字节分批、单次控制在两百 KB 以内，是为了绕开网关对请求体大小的限制。上传前跑一遍密钥扫描，命中的文件整个跳过，避免有人把凭据写进记忆后同步给全团队——它是尽力防护而非保证，规则覆盖不到的格式仍会漏。触发用文件监听加两秒去抖合并写事件，另挂一条工具执行后的显式钩子，因为文件监听在某些平台与文件系统上并不可靠。

可测口径是版本冲突率、重试次数、单次推送的字节分布与密钥扫描的拦截数。

**相关知识点：** 乐观锁、增量推送、冲突重算、键级合并粒度、请求体分批、密钥扫描尽力防护。

### 28. 会话恢复时 CLAUDE.md 指令机制如何重新生效？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

恢复的难点不在读回消息记录，而在那些根本不写进记录的东西。

指令按重新生效的方式分两类。全局那一层靠重新加载：会话启动钩子的触发原因里专门有「恢复」一档，钩子据此决定要不要做完整初始化。路径条件那一层不随恢复回来——带路径 glob 的规则与嵌套目录的记忆是在模型读写匹配文件时才加载的，恢复后要等下一次访问才重新触发，匹配走 gitignore 语义。

include 展开则是每次读取都重做，那几道防护因此每次都要重跑：深度上限五层防互相引用成环；只允许文本扩展名，挡住图片与二进制；引用项目目录之外的文件需要显式授权，防恶意的项目指令去 include 系统敏感文件；块级 HTML 注释先剥掉；代码块里的 @ 路径跳过，它是示例不是指令。

不在消息里的还有两样：会话来源记着模式，恢复时按存的模式把环境变量翻回来；成本状态要从落盘处读回，否则预算熔断从零重新计数。会话切换本身是原子的，避免半切换状态被别处读到不一致的会话 ID。

还有一个顺序上的现实：完整记录可能很大，恢复后往往紧接着就要压缩一次。所以恢复的验收标准不是「历史读回来了」，而是压缩之后目标、约束与当前工作仍在。可测口径是恢复后首轮的 token 占用、规则重新加载的触发次数与成本计数的连续性。

**相关知识点：** 分层恢复、路径规则延迟触发、include 深度与扩展名防护、外部引用授权、模式与成本恢复、原子切换。

### 29. 多代理隔离与 forkedAgent 的缓存共享如何兼顾？共享了什么、隔离了什么？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

默认隔离：子代理有自己的消息数组，看不到父对话。fork 是唯一例外，它克隆父的助手消息、补上占位的工具结果再加一段指令，让子代理接着父的上下文往下做。依据是用途——fork 延续父任务（压缩摘要、记忆提取这类），普通子代理委派独立子任务，后者不需要父上下文，给了反而污染。

共享的是缓存前缀：系统提示、工具数组、模型、消息前缀、思考配置这几项字节一致，API 才会命中父对话已建好的缓存。代价是隔离必须让位——fork 不能自己装配工具池，只能原样继承父的精确工具数组；更隐蔽的是它**不能设自己的输出上限**，因为思考预算会取「预算与输出上限减一」中的较小值，改了输出上限就改了思考配置，而它是缓存 key 的一部分。这条耦合藏在两个模块之间。

仍然隔离的有四样：输出走独立文件不进主档案；查询来源被标记，压缩类来源不再触发自动压缩，否则摘要子代理会递归地要求摘要；派生深度靠扫描 fork 模板标签拒绝二次 fork，配合子代理的轮次上限构成双重防护；文件层按需用 worktree 或进程内上下文隔离。任务 ID 取类型前缀加八位随机，让符号链接爆破猜不中。

判断标准是两者的对照：fork 省下的是缓存创建 token，普通子代理换来的是独立工具池与权限边界。

**相关知识点：** 上下文隔离与 fork 例外、缓存 key 字节一致、输出上限隐式耦合、查询来源标记、递归派生防护、任务 ID 防爆破。

### 30. AgentTool 的派生决策树如何决定是否开子代理？内置代理体现了什么设计哲学？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

派生路径由输入参数判定，三路互斥且有先后：给出团队名与成员名走 Swarm，不给子代理类型且 fork 特性开着走 fork，给了子代理类型走普通子代理——顺序是意图强弱的排序，最显式的先判。

同步还是异步是另一条正交决策，来源有好几种：调用方显式要求、代理类型自己声明、协调器模式下 worker 一律异步、fork 统一走异步通知。另有时间兜底——跑满一百二十秒自动转后台，判据是多数只读研究在这个时长内完成。派生前若声明了依赖的 MCP 服务器还要等就绪，最多三十秒。

权限上有个容易踩的非直觉点：worker 的工具池独立装配、权限模式默认接受编辑，**不受父代理工具限制的约束**。父这边被拒的工具子代理未必也被拒——这里说的是代理定义层面的工具限制，最终仍由子代理自己的权限上下文判定；委派不等于自动收窄。

内置代理体现的哲学是：每一个都是「能力、成本、权限」的一次绑定，而不只是一段提示词。只读探索型把禁用编辑工具、用最便宜的模型、不加载项目指令捆在一起，为的是让并行探索便宜到可以随手派；规划型捆的是只读与强制输出关键文件清单；验证型捆的是自动后台与强制给出通过、失败、部分通过的结论，任务是找茬而非确认。一次性的那两类还不附带续派句柄。

可测口径是派生数、异步转化率与单次委派的 token 成本。

**相关知识点：** 三路派生判定、异步决策来源、自动后台阈值、子代理权限不继承限制、能力成本权限绑定、一次性代理。
<a id="cc-131"></a>
### 31. 子代理结果如何回流到主会话？Swarm 的邮箱通信解决什么问题？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

回流的核心矛盾是：协议要求消息角色交替，完成通知只能以用户角色注入，却绝不能被模型当成用户的新指令。折中办法是包成结构化标签，源码注释直白写着「看似 user 消息但不是」——标签降低误读概率，不是消除它。

通知里放什么同样是取舍：任务 ID（据此续派）、完成失败被杀三选一的状态、一段摘要，以及指向完整输出文件的路径；完整结果不进正文，否则子代理省下的上下文又还了回来。用量随通知回流，主代理才能把子代理的花费算进自己那条链的账。

并发上有三处讲究：入队前原子地检查是否已通知过，因为完成、超时、被杀可能同时到达；被杀时倒序取最后一条助手消息文本当部分结果；完成标记先打，让阻塞等待的调用立刻解除，清理收尾放在后面——结果就绪就交付，别让清理挡住等待者。

邮箱解决的是进程边界：进程外的 teammate 是独立进程，没有共享内存，只能靠文件传消息，文件另带持久与可观察两个好处，代价是轮询延迟。它承载的不只是文本，还有关闭协商、计划审批与权限响应。权限那条最关键：teammate 遇到需要询问的操作不自己弹窗，而是发给 leader 统一处理，否则多个 teammate 各弹各的把用户淹掉。

可测口径是通知重复率、部分结果占比与权限请求的响应耗时。

**相关知识点：** 用户角色注入、结构化通知、输出文件外置、用量随通知回流、先标完成后清理、文件邮箱。

### 32. Coordinator 模式的 LLM 编排与确定性编排相比，适用边界在哪里？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

它的立场很极端：不设并发上限。并行靠主代理在一条消息里发出多个派生调用，而不是靠线程池或信号量。理由是能不能并行取决于内容——研究三个互不相干的子系统可以并行，改一组互相依赖的文件必须串行——这个判断要理解任务结构，硬编码规则只能按固定模式近似。工具级并发用的正是那种确定性谓词，代理级并发交给模型，两个层次做了不同选择。

工作流同样是软约束：研究并行、主代理汇总、实现、验证这套四阶段写在提示词里当默认模板，模型可偏离。

放弃的要看清楚：并发上限没有硬保证，同样输入不保证同样的调度，资源分配也没有公平性。唯一保留的硬约束是一个代理同时只能认领一个未完成的共享任务——防贪婪独占，不做调度优化。保留的位置很有信息量：作者判断模型的失效模式是贪婪而非笨拙，它知道怎么拆任务，却不知道该给别人留任务。

worker 之间的共享走文件而非消息，中间结果写进共享草稿目录由别的 worker 自取，好处是异步、无需直连、可观察，代价是没有一致性保证。

边界因此清楚：任务图要看内容才能确定、允许试错的场景适合交给模型编排；依赖已知、要求可重放、要求资源上限有硬保证的场景应该用确定性编排。可测口径是实际并行度、worker 空闲率与相对串行的总耗时。

**相关知识点：** 无硬编码并发、内容感知并行、软约束模板、防独占硬约束、黑板式共享、可重放性取舍。

### 33. Bridge 的 epoch 机制解决什么问题？多会话模式下如何避免串话？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

epoch 是一个单调递增的代际号：注册工作端时领一个，之后每次访问桥接端点都会推进它。它解决互斥——同一会话同一时刻只该有一个活跃工作端。旧工作端因网络问题没能正常断开时，新的一注册代际就变了，旧的后续请求因不匹配被拒，「幽灵工作端」继续操作会话的路被堵死；检测到不匹配就关掉传输退回轮询。

它与序列号正交：代际号回答「谁是当前工作端」，序列号回答「消息有没有丢、有没有重」。事件流每条带递增序号，断线重连时客户端带上最后收到的序号续传，跨传输切换也由同一个序号携带，传输层抖动因此不造成消息缺口。重复投递靠一个容量两千的环形去重集合过滤——这是有界的近似保证，只覆盖最近两千条，更早的重发会漏判。

重连本身分两级：先试原地重连保住会话状态，失败就归档旧会话另开一个，丢掉未保存状态但保证可用，最多重建三次。

多会话（默认容量三十二）的串话分两层看。消息层靠会话标识加去重；文件层由派生模式决定——每会话独立目录、每会话独立 worktree、所有会话共用一个目录，最后一种根本没有文件隔离，是显式取舍而非疏漏。另有超时看门狗清理卡住的会话，否则僵尸会话一直占着容量。

可测口径是代际不匹配次数、续传缺口数、重连成功率与容量占用。

**相关知识点：** 代际号互斥、幽灵工作端、序列号续传、有界去重的近似保证、双级重连、派生模式隔离档次。

### 34. MCP 传输层在超时、失效判定与连接终止上如何取舍？工具包装与 OAuth 刷新各有什么工程陷阱？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

传输侧有三处判断值得记。

**超时按方法分。** 非 GET 请求统一套六十秒上限，GET 不设——在这套协议里 GET 是长生命的事件流，本就该一直挂着。

**失效判定用双信号。** 会话过期要同时看 HTTP 404 与协议层的特定错误码，只看其一会误判。SDK 重连耗尽时不触发关闭回调、在途调用一直悬着，这条也得单独截；终止类连接错误则累计到三次才真正重连。

**关闭时逐级升级信号。** 中断、终止、强杀三级之间各留一小段等待并轮询探测进程，给优雅退出的机会，但保证最终一定被杀。

工具包装里最该警惕的是信任转移：MCP 工具的并发安全性直接取自服务器自报的只读注解。这个谓词本是一份语义契约，声明错了只表现为偶发的结果错乱，这里等于把声明权交给了第三方。工具名带上服务器与工具两段并替换非法字符，为的是可解析且能被权限规则匹配。

OAuth 的复杂度不在标准流程，发现链与 PKCE 照标准做即可。工程量在两类现实：跨进程并发刷新用文件锁串行化，拿到锁后重读一次，剩余有效期够就直接用别人刚刷好的；服务器不守规范则要先归一化，比如用 HTTP 200 返回错误体。最不直觉的是权限升级——收到 403 且提示 scope 不足时不能刷 token，规范禁止用刷新令牌扩权，必须重走完整授权，否则卡在「刷新、403、重试」的死循环里。

可测口径是连接成功率、重连次数、悬挂调用数与刷新锁的等待耗时。

**相关知识点：** 按方法分档超时、双信号失效判定、终止信号升级、注解即并发契约、跨进程刷新锁、权限升级重授权。

### 35. 钩子的配置来源合并、匹配去重与异步执行如何协同？输出协议约定了什么？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

合并只做一次：八路来源（用户、项目、本地、企业策略、插件、技能、代理声明、SDK 会话）在启动时合成一份快照，之后不再变——每执行一个钩子都重合并八处太贵，快照不可变还换来引用稳定。会话期动态注册的内部钩子另走一路，不落盘。

匹配是三层漏斗：先按匹配串筛事件与工具名，再按条件表达式筛，最后去重。条件那一层复用权限规则的语法与解析器，动机是省进程——工具前置钩子每次工具调用都触发，没有条件过滤就等于每读一个文件都起一个 shell；条件还会预编译成匹配函数。信任检查也在这一层：交互模式下未信任的工作区，钩子一律不执行。

输出协议给了钩子相当大的权力：给出权限决策、改写工具入参、注入额外上下文、要求停止后续。但这些输出在权限决策链上并不被对称采信，放行与拒绝的分量不同。

协议本身容错：输出以左花括号开头才按 JSON 校验，否则当纯文本，校验失败也退回纯文本而不报错。钩子是用户代码，输出可能带颜色码，宁可当日志也不要因解析失败中断工具执行。

异步是一条逃生道：首行声明异步后工具不再等它，完成时用特定退出码唤醒模型，走的是和子代理任务通知同一条注入路径。超时按事件分档：工具类默认十分钟，会话结束钩子只有一千五百毫秒——进程要退出了，不能等。

可测口径是钩子耗时分布、进程派生次数、超时率与被条件过滤掉的比例。

**相关知识点：** 启动快照合并、三层匹配漏斗、条件复用权限语法、输出协议容错、异步唤醒、按事件分档超时。
