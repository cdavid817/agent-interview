### 1. Claude Code 的启动流程如何隐藏冷启动延迟？这套「触发 + 等待」两段式设计有什么约束？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

延迟隐藏的手段不是把阻塞调用变快，而是把它挪进主线程本来就在忙的时间窗。

1. 进程加载主模块要花掉数百毫秒解析编译，这段窗口里已经并行触发 MDM 配置读取（派生子进程）与 macOS 钥匙串预取。钥匙串是同步阻塞调用，单次约 65 毫秒、两次约 130 毫秒，同步读会被直接感知，挪进编译窗口就被吞掉。
2. 初始化阶段就对 API 域名预连，把约 100–200 毫秒的 TCP 与 TLS 握手同配置加载、worktree 创建重叠，首次查询时连接已就绪。
3. CLAUDE.md 读取、git 状态快照、模型能力等非关键预取推迟到首帧渲染之后——首帧是用户心理上的「已启动」信号，这一段优化的是感知延迟而非总耗时。无界面的裸模式与测速模式整体跳过它。

约束在于初始化函数必须写成「触发」和「等待」两个，而不是调用即拿结果。代价有三：调用点必须成对出现，漏掉等待就读到半成品状态；预取里的异常推迟到等待点才暴露，栈信息离现场很远；等待点只是大概率已完成而非保证，仍要能承受真等待。验证靠在启动路径上打点，比较各阶段耗时、首帧耗时与首字节延迟，而不是只看进程总时长。

**相关知识点：** 冷启动延迟、并行预取、预连接、感知性能、两段式初始化、启动打点。

### 2. 三阶段引导中哪些时序约束一旦打乱就会造成难以复现的间歇性故障？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

引导顺序里混着两类约束：性能上的「越早越好」和正确性上的「必须在此之前」。后者被打乱不会立刻报错，只会偶发。源码分析点出四条：

1. 额外 CA 证书必须在任何 TLS 连接（含对 API 域名的预连）之前应用，否则预连会因证书校验失败。
2. 设置工作目录必须早于所有依赖它的代码，worktree 创建、git 操作与 CLAUDE.md 发现都读这个隐式全局量。
3. 在项目信任建立之前只允许应用「安全」的那一部分环境变量，防止未信任的项目配置注入危险变量。
4. 遥测 sink 的初始化必须早于第一条启动事件，否则事件只会入队而不会上报。

难复现的原因是这几条的失败面都依赖外部条件：证书问题只在自签根证书的企业网络里出现；工作目录问题只在从子目录启动或带 worktree 时暴露；sink 问题根本不影响功能，只表现为某类事件上报率莫名偏低，要对着监控看漏报才发现。这也是引导期全局状态文件顶部写着「不要再往这里加状态」的原因——正确性由初始化顺序保证，而顺序在代码里没有任何强制表达。

可验证的做法：给每个阶段打点并断言前后关系，冒烟测试覆盖自签证书与子目录启动，把启动事件上报率当指标监控。

**相关知识点：** 引导时序、隐式全局状态、信任门槛、遥测 sink、启动冒烟测试、事件上报率。

### 3. queryLoop 作为异步生成器需要维护哪些不变量？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

难点不在单轮流程，而在流式接收、工具并发执行、错误恢复三者交织时仍要让消息历史满足 API 的一致性要求。可归为三条：

1. **配对完整。** 每个产出的 tool_use 最终都要有 id 对应的 tool_result，缺一个下一轮请求就被拒。中断、流式回退、错误兜底三条路径各自负责补合成。
2. **引用稳定。** 增量事件到达时，用量与停止原因是就地改写已有消息对象而非替换成新对象。因为这条助手消息此时已经进了可变消息数组，可能正被界面渲染、被 transcript 落盘、被其他子系统持有，替换对象会让持旧引用的地方读到过时数据。代价是放弃「消息不可变」的纯粹性，换取多方并发读取下的一致性——在这个系统里引用稳定比不可变更值钱。
3. **恢复不自激。** 跨迭代状态在每轮结束时整体交棒给下一轮，其中带着几个计数与标志位：「本轮是否已尝试过响应式压缩」防止压缩后仍超长时无限重压，最大输出 token 的恢复次数也有上限（不超过三次）。它们熔断的是「恢复路径本身又触发了它要恢复的那个错误」这类自激循环。

三条都不适合只用单测覆盖：配对靠出口断言两侧 id 集合相等；引用稳定靠对同一消息对象的多方读取做一致性断言；自激靠注入持续超长的上下文，观察重试次数是否被计数器封顶、错误率与单任务耗时是否收敛。

**相关知识点：** 异步生成器、消息历史一致性、引用稳定性、可变状态交棒、熔断计数器、不变量断言。

### 4. 为什么 tool_use 与 tool_result 的配对不变量在错误恢复路径上最容易被破坏？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

因为正常路径上 tool_result 是执行的副产品，自然生成；而恢复路径恰好被触发在「tool_use 已经产出、执行却不会完成」的夹缝里。

硬约束是每个 tool_use 块必须在后续消息中被 id 匹配的 tool_result 回填，缺一个整轮请求就报 400。而助手消息一旦流出去、被 transcript 落盘就不能当作没发生过，所以三条恢复路径都得显式补齐孤儿：中断时把已入队未完成的工具收口成标记为中断的合成结果；流式执行退回非流式、要丢弃已产出助手消息时给孤儿补合成；错误兜底路径返回模型错误前也先补合成。

两点判断。一是**补合成必须携带语义**：中断和失败对模型是不同信号，若都写成无差别的错误文本，模型会把「没跑」当成「跑了但失败」，去改参数重试一件其实没执行过的事。二是**这条不变量跨越持久化边界**，检查点得放在「消息即将进入下一轮请求」的出口而不是工具执行内部——放在内部就漏掉了尚未启动就被取消的那批。

验证靠出口断言两侧 id 集合相等，并用混沌测试随机注入中断与流式回退，统计 400 错误率与补合成触发次数。

**相关知识点：** 工具配对不变量、孤儿补合成、中断语义、持久化边界、混沌注入、协议级错误率。

### 5. 流式工具执行中的「兄弟取消」要解决什么并发正确性问题？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

流式执行的前提是「模型还在输出，工具已经在跑」，这带来串行实现没有的问题：同一批里先失败的那个，可能已经把环境改成后面几个工具的假设不再成立的样子。

1. 触发条件不对称：只有 Bash 工具报错才会取消同批兄弟，Read、WebFetch 这类失败只影响自己。依据是失败相关性——Bash 报错往往意味着环境层面出了问题（磁盘满、权限不足、依赖缺失），后续命令大概率一起失败或产出误导性结果；而某个文件不存在、某个 URL 不可达是局部的。
2. 每个工具有自己的取消控制器，另有一个兄弟控制器专做批次级取消。取消不等于可以不给结果，被取消的工具仍要产出合成结果，否则留下孤儿。
3. 源码分析自己把这条定性为启发式而非定理：Bash 失败也可能只是「某个命令不存在」这种局部问题，此时取消兄弟属于误杀。选择保守，是因为多跑一条注定失败的命令的代价高于少跑一条本可成功的。

配套约束是顺序保持：结果按 tool_use 在模型输出里出现的顺序回填而不是按完成顺序。这既维持对话可读性，也让缓存前缀稳定——顺序抖动会让前缀反复失效。

划不划算看三个数：误杀率（被取消的兄弟里事后判定本可成功的比例）、批次端到端耗时相对串行的下降幅度、缓存命中率有没有稳住。

**相关知识点：** 流式工具执行、兄弟取消、失败相关性、取消传播、顺序保持、缓存前缀稳定性。

### 6. Claude Code 的工具并发模型如何决定哪些工具可以并行执行？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

判定权在工具自己手上：每个工具声明一个「并发安全」谓词，且它接收本次输入，所以同一工具的不同调用可以有不同答案。最典型的是 Bash——它的并发安全性直接等同于本次命令是否只读，于是两条只读命令能并行，写操作必须独占。

这不是机械的只读判定，而是一份语义契约，要求两件事同时成立：没有副作用或副作用彼此隔离；不依赖也不修改其他工具可能读取的共享可变状态。声明错了不会立刻报错，只会变成偶发的结果错乱，这是整套设计最大的风险敞口。

调度有两条路径。流式路径在模型还在输出时就把工具入队执行，并发安全的互相并行、非并发安全的独占；非流式路径把同一批调用按连续段分桶，连续的并发安全段并发跑（默认并发上限 10），其余串行。收益是「读五个文件」的端到端耗时从五者之和降到接近最慢的那个。

代价落在共享上下文上：并发安全工具对执行上下文的修改不立即生效，要推迟到批次结束再处理。源码分析在这一点上前后说法不一致，一处说延迟应用能保住全部修改，另一处说这类修改可能丢失。稳妥的结论是：并发安全工具不要依赖自己的上下文修改被同批其他工具看到，只做读取。

验证有两个抓手：把「声明为并发安全的工具是否真的只读」做成静态检查加回放测试；盯住并发批次的结果一致性与批次耗时下降幅度，一致性掉了说明有工具的声明在撒谎。

**相关知识点：** 并发安全谓词、语义契约、分桶调度、并发上限、上下文修改延迟应用、回放一致性测试。

### 7. 权限模型的分层决策链由哪几层构成？每一层能否单独否决？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

它不是一条规则链，而是一个决策栈，每层的信任级别与否决权都不同。

规则按来源分信任等级：企业受管策略最高且用户改不动，用户全局设置与命令行参数次之，项目与本地设置居中，会话级规则临时。关键是**项目设置是唯一会被提交进版本库的那一层**，克隆仓库等于引入了它的规则——所以自动记忆目录的来源刻意排除它，钩子另有「只允许受管钩子」的策略门控。

否决权是不对称的，这是整套设计的核心：

1. deny 规则单独否决且不被任何 allow 覆盖，工具自身权限检查返回 deny 同样直接生效。钩子返回 allow 只意味着「不阻止」，后面仍要跑基于规则的检查；返回 deny 才直接拒。理由是钩子可能来自插件、可能被改过，自动化决策不该凌驾于安全策略之上。
2. 安全检查能单独把结论抬成询问并免疫绕过模式。它盯写 `.git`、`.claude`、`.vscode` 与 shell 启动配置这几类路径：它们有提权效应，一次修改就影响之后所有操作。
3. 绕过权限模式排在这些之后才生效，免除的只是「本来要问的」，免不掉 deny、内容级询问规则与安全检查。

优先级因此是 deny 高于 ask 高于 allow。审计靠每个决策都带判别式的「决策理由」——规则、模式、钩子、沙箱放行、分类器、安全检查等十余种。要监控的是各理由的占比漂移：分类器理由突然上升，通常意味着规则被误删。

**相关知识点：** 分层决策栈、来源信任层级、拒绝优先、安全检查免疫、绕过模式边界、决策理由审计。

### 8. 权限规则字符串如何解析？文件系统 glob 匹配有哪些易错边界？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

规则统一写成「工具名」或「工具名(内容)」，内容的语义由各工具自己解释：Bash 当命令、文件工具当路径模式、网页抓取当域名、MCP 当服务器名或工具名。

解析上有两个坑：右括号要求是最后一个未转义的且必须落在串尾，否则整串**降级成纯工具名而不是报错**；反转义必须先还原括号再还原反斜杠，顺序反了会双重转义。

文件模式的易错边界更多：

1. **以斜杠开头不是文件系统根**，而是「该规则所属来源的设置根目录」——用户设置里的 `/x` 与项目设置里的 `/x` 指向不同地方。以 `~` 开头才是主目录，且要做 Unicode 规范化，防同形不同码点绕过。
2. 匹配走 gitignore 语义的库，模式尾部的 `/**` 会被剥掉：那个库把一个路径视为同时匹配它自身与它内部。
3. macOS 上 `/tmp` 与 `/private/tmp`、`/var` 与 `/private/var` 是同一处，判定要同时看原始形式与符号链接解析后的形式。
4. 通配符转正则有一条特例：模式以「空格加单个星号」结尾且这是唯一未转义通配符时，`git *` 也匹配裸 `git`，以对齐旧前缀语法；多通配符模式不做这个优化。

这类代码只能靠表驱动验证：把每条边界写成「规则 + 输入路径 + 期望判定」的三元组跑覆盖率，并对 deny 规则做变异测试（大小写、符号链接、尾斜杠、Unicode 变体），盯漏判率。

**相关知识点：** 规则字符串解析、转义顺序、来源相对根、gitignore 语义匹配、符号链接归一化、表驱动测试。

### 9. BashTool 为什么要做 AST 级子命令拆分？只做字符串黑名单会漏掉什么？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

黑名单匹配字面，语法解析匹配语义，两者的差距就是绕过面。加引号、加注释、加转义之后字面不同而语义等价；`git$(echo status)` 看着像 git 命令实则是命令替换。归一化之后 `Bash(git *)` 才匹配得住真实意图。

只做字符串黑名单会漏掉三类：

1. **复合命令藏毒。** `&&`、`;`、`|` 串起来的命令要拆成子命令逐个匹配，否则「安全命令 && 危险命令」整体绕过了对后者的检查。
2. **前缀伪装。** 环境变量前缀能改变命令行为，剥离因此分两套：allow 用保守剥离，只剥确定安全的变量与包装器，绝不剥 PATH、动态链接器这类能劫持可执行文件的变量；deny 和 ask 用激进剥离，剥掉所有前导变量——拦截必须穿透伪装。
3. **组合才危险的逃逸。** 单条子命令看着无害，组合起来才有问题：含变量的重定向与进程替换直接抬成询问；既切目录又有重定向也抬成询问，防先切进配置目录再往里写；切目录后跟 git 同样抬成询问，防的是恶意仓库靠自带钩子在你对它执行 git 时拿到执行权。

配套的非对称设计是：allow 的前缀规则**不匹配**复合命令，deny 与 ask 却必须能匹配其中任意子串。便利策略保守，安全策略激进。

代价是解析可能失败或被判为过于复杂，此时退回询问而非放行。验证靠红队语料回归：维护等价变形与绕过样本，盯漏判率、解析不可用率与因保守而多出的询问次数。

**相关知识点：** 语法树解析、子命令拆分、环境变量剥离、非对称匹配策略、影子灰度、红队语料回归。

### 10. auto 模式的 AI 分类器如何工作？预批准域名机制的风险边界在哪里？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

分类器只在「规则判定为询问」这一个点介入，目标是减少中断而非放宽策略。它前面还有几道快速通道：安全检查与要求人工交互的工具维持原询问，只读与元数据工具走白名单直接放行，写入类工具则由「接受编辑」模式重跑一次权限检查提前放行。

三处设计值得注意：

1. **输入刻意裁剪。** 送进分类器的对话只保留用户文本与助手的工具调用，**排除助手的自然语言输出**——否则模型能靠自己写的话给自己的动作背书，形成自证循环。
2. **双阶段换延迟。** 第一阶段输出上限只有几十个 token 并带停止序列，绝大多数安全动作在这里判完，只有可疑的才进第二阶段做几千 token 的深度分析。这是拿准确率的边际收益换 P95 延迟。
3. **不可用时选择保守。** 调用失败默认拒绝而非放行，由一个门控开关控制。另有连续拒绝与总拒绝上限，超限回退人工批准，避免误判引发「拒绝风暴」。

预批准域名是另一条路径：约八十个文档与代码站点在网页抓取的权限检查末尾直接放行，匹配强制路径段边界，`github.com/anthropics` 不会匹配到 `anthropics-evil`。风险边界有两条：**它只覆盖网页抓取工具，Bash 里的 curl 与沙箱网络限制都不继承这份名单**；它降低的只是询问频率，取回的内容仍是不可信数据。

可测口径是自动批准率、误放率与误拒率、第一阶段命中比例与额外 Token 成本。

**相关知识点：** 权限分类器、快速通道白名单、输入裁剪防自证、双阶段分类、失败即拒、预批准域名边界。

### 11. 工具结果落盘与延迟加载如何降低上下文占用？代价是什么？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

结果侧有三道闸，按代价从低到高排：

1. **单结果落盘。** 每个工具有自己的结果字符数阈值，超过就把完整内容写进结果目录，模型只收到一段带标记的预览。Read 工具的阈值被设成无穷大，因为一旦它的结果落盘，模型会想去读那个落盘文件，又触发落盘，形成自引用循环。
2. **批量预算。** 即使每个结果都没超阈值，累积起来仍可能过量，所以预处理管道里还有一道工具结果预算按优先级裁剪。
3. **缓存层删除。** 服务端缓存还有效时，用缓存编辑接口只在发往 API 的请求里删掉旧的工具结果，本地消息历史保持完整；缓存已过期时则直接把旧结果内容替换成一句占位符——反正没有前缀可保了。这两条分支的判据是「此刻缓存还值不值得保」。

延迟加载走的是另一侧：声明为延迟的工具其 schema 不随系统提示发出，模型靠关键词搜索按需发现。

代价集中在三处。预览有损，模型可能基于不完整的头尾做判断；本地历史与实际发送内容出现分叉，调试时看到的 transcript 不等于模型看到的东西，排查要以发送侧为准；延迟加载则让模型可能调用一个 schema 没发出去的工具，校验失败后靠提示引导它先搜索，多花一轮往返。可量化的口径是落盘触发率、缓存读与缓存创建的 token 比例，以及延迟加载引入的额外轮次占比。

**相关知识点：** 结果落盘阈值、自引用循环、工具结果预算、缓存编辑删除、历史与请求分叉、延迟加载往返成本。

### 12. 大结果格式化策略如何在信息完整性与 Token 成本之间取舍？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

每个工具都要实现一个把内部输出映射成 API 结果块的函数，这是唯一的收口点，所有增删都发生在这里——也意味着所有 Token 都花在这里。

往结果上追加内容的口子有好几个：用户批准工具调用时附带的反馈与图片块接在结果之后；工具还能返回额外消息（例如 PDF 文档块、图片元数据）；工具成功后的钩子可以注入附件，MCP 工具走单独路径，钩子能直接改写它的输出再回填。文件读取的映射还会给文本加行号，并附一段网络安全提醒，较新的模型被豁免这段。

取舍就在这些追加项上。行号让后续编辑能精确定位、减少整文件重写，但每一行都在花钱；提醒文本对能力足够的模型是纯冗余，所以按模型豁免；超阈值结果只给预览是最省的一档，代价是信息有损。

**判断标准不是「省了多少 Token」而是「省下的部分有没有被真正用到」**：把结果里各部分的 Token 占比拆出来，对照删掉它之后的任务完成率与重试次数变化。钩子这一层还要单独看耗时——它在工具结果回填的关键路径上，源码里对超过两秒的阶段单独打慢日志。

**相关知识点：** 结果映射收口、追加内容成本、行号定位、按模型豁免、钩子改写输出、关键路径耗时。
