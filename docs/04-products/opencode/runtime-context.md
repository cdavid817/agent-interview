### 1. OpenCode V2 会话运行时由哪些角色组成？一次用户输入的完整流转路径是什么？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

运行时被切成一串小协作者，**每个角色只守一条不变量，路径上的先后顺序本身就是契约**。

1. 角色分工：门面暴露创建、提示、中断、恢复与切换；持久收件箱管准入与晋升；执行路由按会话所在位置取服务层；协调器按会话键排队；运行器跑排空循环；纪元、历史投影、压缩、工具注册表与有界输出存储各管一段；事件存储是真相源，投影器产出物化视图。
2. 路径是：门面写一条持久收件箱行并发布准入事件，再调度建议性唤醒；协调器忙则合并、闲则派生排空纤程；运行器先把遗留的待执行与执行中工具清扫为失败，再初始化纪元、在安全边界晋升提示、调和上下文、解析模型、投影历史、物化工具，最后发起提供者流。
3. 流式事件逐条持久化为步、文本、推理与工具调用；工具结算后发布结果，回合以带文件快照差异的步结束事件收尾，再判断是否延续。
4. 顺序不能调换：初始化必须排在晋升之前，否则会出现「用户消息已可见却跑不出回应」；调和必须排在晋升之后，模型才会先看到用户说了什么、再看到环境变更通知。
5. 最反直觉的取舍是排空不是持久实体：崩溃后不自动续跑，恢复只能从提示、投影历史、提供者尝试与工具状态推理。代价是要用户显式恢复，收益是不必回答「这段输出该重发吗」。可验证的是纪元准备、回合与工具结算三处链路追踪的耗时分位。

**相关知识点：** 会话运行时、持久收件箱、安全提供者回合边界、排空循环、事件溯源、崩溃恢复、链路追踪。

### 2. OpenCode 的「系统上下文代数」指什么？它用哪些运算描述上下文组合？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

叫代数是因为上下文被建模成**有类型来源的集合，加上一组封闭的组合与解释运算**，而不是一次字符串拼接。

1. 一个来源由命名空间形式的稳定键、JSON 编解码器、不可失败的加载器，以及基线、更新、可选移除三个纯渲染函数构成。构造时把值类型隐藏，不同类型的来源才能统一组合。
2. 组合运算按调用方顺序拼接并立即拒绝重复键；注册表在组合前先按键排序再无界并发观察，因此渲染结果与插件的注册先后无关。
3. 解释运算有三个：初始化并发观察全部来源，任一不可观察就带着键列表失败，绝不持久化残缺基线；调和观察一次后返回恰好一个动作——无变更、一条合并的更新文本、需要整体替换、或替换被阻塞；替换在先前已纳入的来源当前不可用时同样阻塞。
4. 编解码器身兼两职：既把值编码进快照，又派生出感知 schema 的等价函数。它比字符串比较精确，键序不同不会误判成变更；解码失败则判为不兼容并转整体替换，避免 schema 演进后发出错误的增量更新。
5. 「暂时不可观察」与「被移除」被刻意分开：前者保留上次生效值、不发消息，后者才渲染撤销文本；没有移除渲染器的来源被摘掉时只能整体重建基线，成本更高。渲染出空文本判为错误而非静默通过。可验证的是同组来源多次渲染的结果一致性、更新消息条数与基线重建频次。

**相关知识点：** 上下文来源、代数组合、确定性渲染、编解码等价、增量更新、优雅降级、快照比较。

### 3. OpenCode 的上下文纪元状态机有哪些状态与迁移条件？纪元切换时什么会失效？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

纪元就是「一段基线保持不变的时期」，一行记录基线文本、上下文快照与基线序列号。状态只有**有纪元与无纪元**两个，复杂度全在迁移条件上。

1. 无纪元到有纪元：初始化并发渲染完整基线，已有行则直接返回，因此幂等。它必须排在输入晋升之前——某个来源不可观察时初始化失败，回合不跑、输入保持待处理可重试。
2. 纪元内自转移：每回合调和一次。无变更就原样复用；有变更则发布一条对话中系统消息，并在同一数据库事务内推进快照，保证消息与快照原子地一起前进；替换被阻塞时降级复用旧基线。
3. 有纪元到新纪元：最新压缩的序列号大于基线序列号时触发整体替换，写入新基线、新快照与新的基线序列号。
4. 有纪元到无纪元：会话移动与回退提交都直接删除纪元行。上下文来源是位置范围的，目的地的工作目录、Git 状态、项目指令与权限都不同，旧基线描述的是别处。纪元行被删但消息与输入不动——执行状态可重置，事实不可丢。
5. 切换时失效三样：作为提供者缓存前缀的基线整体作废，缓存命中率随之下滑；先前的对话中系统消息离开投影给模型的历史，但仍留在消息表里供审计；快照被整体覆盖。模型与 agent 切换刻意不终结纪元，只发一条对话中消息，免得为换个模型付一次全量重渲染。快照解码失败被当作致命错误而非降级，因为不知道上次各来源是什么值时沿用旧基线并不安全。

**相关知识点：** 上下文纪元、提示缓存前缀、状态机迁移、事务内原子推进、基线序列号、位置范围服务、审计保留。

### 4. OpenCode 的持久化提示如何准入与晋升？与一次性提示相比成本差别在哪？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

准入与晋升是两次独立的持久转换：**准入只把输入写进收件箱，晋升才让它成为模型可见的用户消息**，中间隔着一个安全边界。

1. 收件箱行记录消息 ID、准入序列号、编码后的提示、投递模式与晋升序列号；晋升序列号为空即表示尚未对模型可见，两个唯一索引把这两个序号钉死在会话内唯一。
2. 准入先按消息 ID 做一次幂等查找，命中即返回；否则发布准入事件由投影器在事务内写行。这让同一消息 ID 重发成为精确重试，而会话、提示、投递任一不匹配的重用直接失败，不会悄悄多出第二条输入；投影器还挡住「已晋升的消息被退回成待处理」。
3. 晋升发生在回合的安全边界，且先取一次序列号做截止点：只有准入序号不超过截止点的转向提示才晋升，回合进行中新来的留到下一回合，一个回合晋升多少条因此可预测。排队提示则一次只晋升最旧的一条，处理完重新评估延续，保证一个任务答完再开下一个。
4. 晋升会把 agent 的回合配额重置回第一步，但一个边界无论晋升几条都只重置一次，堵住「多发几条就多换步数」的漏洞。
5. 与「收到请求就内联执行」相比，成本是每条输入多一次事件写入与投影；换来的是崩溃重启后未晋升输入仍在、重叠唤醒可合并且置标记极廉价，以及只准入不唤醒的批量喂入。该测重复输入数恒为零、重启后待处理输入保留率与准入到首个回合的延迟。

**相关知识点：** 持久准入、提示晋升、投递语义、截止点快照、幂等重试、回合配额、建议性唤醒。

### 5. OpenCode 的会话执行路由与运行协调器如何决定一次请求由谁执行？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

只有两级判断：**先按会话键在协调器里排队，再按会话所在位置选服务层**。

1. 路由是进程全局的，只从会话 ID 出发：读会话拿到位置，取该位置的服务层，在这层下调用运行器。运行器、目录、模型解析、工具注册表、权限与文件系统都按位置缓存，多工作区因此天然隔离，会话移动只需下次排空换一层，不迁移任何运行器状态。
2. 硬约束是没有任何服务层接收会话 ID——它属于运行时数据，不许进编译期的依赖图。代价是会话相关信息必须显式沿调用参数传，收益是同一套运行器将来把本地层换成远程代理层也不用改代码。
3. 协调器为每个会话键序列化执行、不同会话之间并发，按键维护条目记录完成信号、拥有者纤程、待唤醒标记与停止标记。
4. 两个执行入口语义不同：显式恢复要么加入正在跑的执行并等它结束，要么以强制模式起一个新排空，强制会绕过「没有合格输入」的守卫；建议性唤醒是纯同步设置——忙则只置待唤醒标记，重叠唤醒合并成一次后续排空，闲则创建条目并以非强制模式启动一次排空，并不只是置标记。
5. 中断是独立的停止操作而非入口：先置停止标记、清掉待唤醒标记再打断纤程，并等清理完成才返回，调用方因此能确认「确实停了」而非「信号发出去了」；对空闲、已结算或不由本进程拥有的执行，中断都是空操作。活跃注册表只记进程内前台排空，后台子代理不把父会话算作活跃，进程重启即清空。可观测的是每会话排队等待耗时、唤醒合并率与中断到确认停止的耗时。

**相关知识点：** 执行路由、位置范围服务层、每键序列化、唤醒合并、中断幂等、活动注册表、远程放置预留。

### 6. OpenCode 会话运行器的 Drain 循环解决什么问题？如何避免消息丢失与重复执行？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

排空循环回答「一次唤醒到底要跑几个提供者回合」。它是**双层的**：内层看模型还要不要继续调工具，外层看收件箱里还有没有排队提示。

1. 内层每跑完一个回合就重新检查有没有新的转向提示，有就复活循环；外层在内层耗尽后才晋升一条排队提示，再重新进内层。这正好对应「转向插队、排队等空闲」两种投递语义。
2. 入口有守卫：非强制模式下既无转向也无排队就直接返回，不会白付一次提供者调用。
3. 防重复执行靠三处。每次排空开始先把投影历史里仍待执行或执行中的工具标记为失败，被放弃的副作用从不静默重放；每个回合开头校验会话位置仍是当前这一个，会话被移走就中断退出，避免用旧工作区的服务操作已迁走的会话；工具结算事件携带拥有它的助手消息 ID，因为提供者给的调用 ID 可能跨回合重复。
4. 防消息丢失靠串行发布与无条件刷写：发布用一个许可的信号量串起来，保证增量与结束边界不乱序；刷写挂在收尾钩子上，即使流中途失败，已收到的文本与工具调用仍落盘。
5. 步数耗尽时不再物化工具、把工具选择设为不调用，并追加一条收尾提示，逼模型给最终答案而非无限调工具。压缩过渡用抛缺陷再捕获的方式递归重入，其中溢出补救只允许一次，第二次溢出即终态失败。可测的是每次唤醒的回合数分布、被清扫的遗留工具条数与单回合耗时。

**相关知识点：** 排空循环、延续判定、遗留工具清扫、串行发布、位置守卫、步数上限、递归重入。

### 7. OpenCode 的提供者回合与工具结算如何划分边界？结算失败如何回滚？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

边界是一条固定流水线：**先持久记录调用、再执行、再有界投影、最后才延续**；失败路径的答案则很坦率——基本不回滚，只把失败变成显式终态。

1. 记录先于副作用。调用事件在执行开始前落盘，之后才解析有效注册、解码入参、断言权限、执行、编码出参、投影成模型可见内容。两条法则很硬：解码失败绝不调用工具，编码失败绝不产生成功结算。
2. 注册身份要防漂移。物化时捕获每个被宣传名字的注册身份，结算时比对，不一致即返回过期调用错误——一次调用从不执行「不是它那个回合所宣传的」注册；身份通过后才捕获处理函数，此后移除注册也不影响在途调用。
3. 输出被有界化：文本按行数与字节上限截断并保留首尾，完整正文写进受管文件；有界预览才是持久可重放的记录，受管文件只是有保留期的临时物，结构化结果永不改写。
4. 工具急切启动、并发执行，结果发布却串行；结算区跑在不可中断的掩码内构成完成区——工具一旦成功，有界化与结算发布不会被腰斩，否则模型会以为工具没跑而重试，制造重复副作用。
5. 于是失败被分类而非回滚：预期失败转成模型可见的错误结果让它调整；中断只是取消、不产生结果，未结算工具统一标记失败；受管文件写入失败不把已成功的工具变成失败，只记一条有损输出并给运维发诊断。补丁类工具提交中途失败时保留已应用部分并返回显式的部分应用报告，原子回滚是明确的未完成项。可验证的是重复副作用数与有损输出占比。

**相关知识点：** 工具结算、先记录后执行、注册身份校验、有界输出、受管输出文件、中断安全完成区、部分应用报告。

### 8. OpenCode 的自动压缩与历史投影有什么区别？投影为什么比直接截断更安全？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

两者是写与读的分工：**压缩往历史里追加一条持久检查点，投影则在每次组装请求时按检查点与纪元基线重算该发什么**。

1. 压缩有两条触发路径。预防路径在每个回合前用序列化长度粗估请求 token，超过「上下文窗口减去输出上限与预留头空间中较大者」就先压缩；补救路径只在提供者把请求判为溢出、且助手尚未产生任何持久输出时触发。前者可反复发生，后者只允许一次。
2. 压缩本身是一次独立的、不带工具的摘要调用，输出被约束成固定小节：目标、约束与偏好、进展、关键决策、下一步、关键上下文、相关文件。规则要求小节即使为空也保留、用要点而非散文、原样保留文件路径命令与错误字符串，且不提及摘要过程本身。检查点还附一段 token 有界的近期原文；再次压缩会把上一次的摘要当输入，让摘要随会话演化而非每次重述。
3. 投影不写任何东西。它按最新压缩序号与纪元基线序号筛选：压缩之前的普通消息被检查点取代，基线之前的对话中系统消息已折叠进提供者系统前缀因而丢弃，基线之后的保留。
4. 更安全在三处：完整转录始终留在消息表里，被裁掉的只是发给模型的那一份，审计完整性与上下文效率被拆成两件事；选择器是纯读侧的确定性查询，规则改了重跑即可，不会丢事实；预算用尽时在边界拆分一条消息而非整条丢弃，避免近期上下文被切空。
5. 该盯压缩触发频次、溢出补救成功率、压缩前后的估算 token 降幅，以及基线重建带来的缓存命中率波动。

**相关知识点：** 自动压缩、溢出补救、结构化滚动摘要、历史投影、检查点、审计完整性、token 预算估算。

### 9. OpenCode 的工具系统如何表达权限？非沙箱边界体现在哪里？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

权限被表达成**有序的「动作、资源、效果」规则数组**，动作由工具声明、不与工具名硬绑：写、编辑、打补丁共享同一个动作，一条规则就能同时关掉三个。

1. 授权分两层。物化工具定义时先把「动作命中且资源为全通配的拒绝」对应的工具整体摘掉，模型根本看不到；执行前还要再断言一次。定义过滤只是目录可见性、不是执行授权——权限可能在物化之后被改动。
2. 断言是阻塞式的：需要询问时创建延迟量，在不可中断的区间里等用户回复，免得中断把工具悬在「既没批准也没拒绝」的状态。
3. 批准会级联。选「始终允许」把规则持久化成项目级保存规则，并自动放行同会话中所有资源都被新规则覆盖的待处理请求；拒绝则级联否掉同会话全部待处理并把理由回给模型。取不到 agent 时回落成全部拒绝。
4. 路径是权限的一等公民：相对路径必须落在位置内，绝对路径先规范化，词法在内而规范化后在外的一律判为逃逸，工作区外的目标走强制的外部目录动作。授权绑定发起调用那个回合的 agent，事后切换不改变在途调用的策略。
5. 结构性边界在纵深上没有闭环：shell 以宿主用户的文件系统、进程与网络权限运行，不存在操作系统级沙箱层；对命令参数里绝对路径的扫描只产生建议性警告而非硬边界，受管工具输出目录还开了可读例外。它自我定位为本地开发工具、假设用户信任所运行的东西，该盯外部目录授权触发次数与被拒动作实际执行数恒为零。

**相关知识点：** 权限动作分组、目录可见性过滤、阻塞式断言、保存规则级联、路径逃逸检查、外部目录授权、非沙箱边界。

### 10. OpenCode 的 LLM 包与协议适配器如何屏蔽厂商差异？哪些差异无法屏蔽？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

屏蔽靠两件事：**一套规范请求与统一的流事件词汇**，以及**把路由拆成协议、端点、认证、组帧、传输五个可独立替换的维度**。

1. 两条运行时路径并存：默认路径复用通用 SDK 再把流事件归一化；实验性的原生协议路径直接构造 wire 请求、解析服务端推送帧，只覆盖少数几家且需装对应包，不可用时回落。上层只调一个流接口。
2. 结构化输出被刻意统一成「强制调用一个合成工具」，而非各家原生 JSON 模式——所有厂商都支持工具调用，JSON 模式却各不相同；完成原因同样映射进统一词汇。
3. 屏蔽不掉的第一类是 schema 表达力。各家接受的是 JSON Schema 的不同子集，框架只能逐家清理：移除不支持的特性、处理引用与数组项、把枚举降级为字符串。这是有损的，工具定义在弱支持方精度更低，工具名语法也只能取保守交集。
4. 第二类是缓存与原生延续元数据：以 Anthropic 协议为例，缓存断点数上限为 4，这是尽力优化而非强制约束——候选断点超额时丢弃并告警，预算按工具定义、系统前缀、消息顺序分配。思考签名与加密推理这类原生延续元数据只在同厂商同模型精确续接时保留，换模型即省略，可见推理降级成普通助手文本。
5. 第三类是厂商自执行的工具：结果要求按精确结构原样往返，被排除在通用有界化之外。系统消息形态也随模型而异，不支持原生系统角色时只能包成文本合进用户消息。缓存最值得量化：稳定前缀命中把长会话输入 token 从平方增长压回近线性，该盯缓存命中率与单位任务成本。

**相关知识点：** 协议适配器、路由五维分解、统一事件词汇、合成工具结构化输出、schema 清理、缓存断点预算、原生延续元数据。

### 11. OpenCode 如何统一集成 MCP、LSP、技能、ACP 与自定义命令？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

所谓统一只落在两个入口上：**每个提供者回合组装时的工具集与系统上下文**。其余部分并不同构，五者接入方向差别很大。

1. 收敛进工具集的是内置工具、插件工具、模型上下文协议服务器的工具，以及仅在客户端声明资源能力时合成的资源工具；进系统上下文的不止环境事实、项目指令与技能指引——按权限过滤后的 MCP 服务器指令同样渲染进系统提示，两个入口都收 MCP。工具发给模型前还要过一次插件钩子，可重写描述与 schema。
2. 模型上下文协议是工程量最集中的一条：本地服务器按命令派生子进程，远程服务器先试可流式 HTTP、失败再退回服务端事件流，认证类错误直接中断；握手只声明根目录能力并注册返回项目目录的处理器；调用带超时，收到进度上报时重置计时。
3. 它的失败面被显式建模：连接关闭标记为失败态并广播工具集变更；拆除阶段对标准输入输出型服务器要按父进程递归反查并杀掉整棵进程树，因为服务器常常再派生孙进程，只杀主进程会留下孤儿。工具名按「服务器名加工具名」清洗拼接，既避免同名工具互相覆盖，也满足保守的工具名语法。
4. 其余四者各走各路：语言服务器在主路径上不是工具，而是编辑类工具改完文件后触发的诊断装饰，推拉两路诊断去重并带去抖与总时长封顶（标志门控的实验性 lsp 工具是例外，直接暴露跳转定义、查找引用等能力）；技能只在系统提示里列名称与描述，正文要模型显式调用才加载；代理客户端协议方向相反，由外部宿主驱动 OpenCode；斜杠命令在提示进入会话前完成参数替换。
5. 该测每台外部服务器的连接成功率与调用超时率、拆除后的残留进程数、诊断等待超时占比与首字延迟。

**相关知识点：** 外部能力集成、工具集组装、进程树回收、工具名去重、诊断装饰、按需加载技能、反向驱动协议。

### 12. OpenCode 的可观测性、安全与运维体系覆盖哪些环节？关键指标有哪些？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

三条线不在同一层：**可观测性是横切的调用链标注，安全是认证、权限、路径与供应链上的多道边界，运维集中在生命周期与关闭路径**。

1. 可观测性接的是 OpenTelemetry，装进运行时后按「领域.方法」给关键调用标注跨度，纪元准备、回合与工具结算的延迟与频次因此可见。应用内那个实验开关已被移除，改用进程级标准环境变量，可观测性被当成横切关注而非应用配置；云侧用日志尾随消费者把事件转进分析后端。
2. 安全第一层是认证：服务端走 HTTP 基础认证，桌面边车每次启动生成随机密码、只在进程间传递不落盘，嵌入式同进程信任不设密码但中间件照常运行；终端连接的 WebSocket 用一次性票据换取，免得凭据在 URL 里被日志记下。
3. 第二层是权限与路径边界，第三层是供应链卫生——密钥扫描、安全披露流程与开发期的安全检查技能。诚实的缺口是 shell 不沙箱，派生进程拿宿主用户权限。
4. 运维集中在生命周期：数据库开预写日志并设五秒忙等超时以支持读写并发；工具输出的受管文件按七天保留、每小时清理一次；实例拆除延迟到 HTTP 响应发出之后，否则响应可能被提前关掉的连接打断；强制关闭时逐个套接字给一秒超时兜底。
5. 关键指标落在这些常量上：跨度耗时分位、受管文件清理后的磁盘占用、忙等超时次数、强制关闭后的残留连接与进程数，以及唯一错误号在日志里的可关联率。压缩中间件对流式路径整体跳过——这类响应不能缓冲。

**相关知识点：** OpenTelemetry 跨度、日志尾随、一次性票据、预写日志、受管文件保留、实例拆除顺序、优雅与强制关闭。
