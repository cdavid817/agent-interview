### 1. OpenCode 的设计哲学是什么？它与绑定单一编辑器的 Coding Agent 有哪些取舍差异？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

OpenCode 把自己定位成**可嵌入的编码代理引擎**，而不是某个编辑器的附属插件：同一份领域逻辑既能作独立 HTTP 服务，也能被任意 TypeScript 进程同进程调度。

1. 会话被建模为事件溯源的持久聚合而非内存对象。终端、桌面、网页、IDE 订阅同一条持久事件流，因此支持多客户端共观察、从任意点 fork、跨工作区迁移、崩溃后重放。
2. 核心服务只做「小型有类型容器」，Provider、模型发现、生成行为等策略下沉到插件钩子，换取服务可热重载。
3. 代价是拿不到编辑器原生的选区、补全与语义索引，只能靠 LSP 工具补；多端 UI、多 Provider 适配与协议演进的工程量全部自担。
4. 该问的验证口径：崩溃后会话重放成功率、多端渲染一致率、冷启动耗时与嵌入式调用 P95 延迟。

**相关知识点：** 事件溯源、可嵌入引擎、Coding Agent、容器与插件、热重载、多端一致性。

### 2. OpenCode 的顶层包依赖如何划分？这种划分解决了什么工程问题？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

依赖方向被硬性规定为**Schema 指向 Core 与 Protocol、二者再指向 Server，客户端包只依赖 Schema 与 Protocol、永不依赖 Core 或 Server**。

1. Schema 是零依赖叶节点，只放公共记录与带 brand 的 ID，不得传递加载数据库、ORM、会话执行、Provider 或原生模块。
2. 这不是风格偏好：客户端根入口要打成浏览器安全 bundle，一旦 Schema 间接拉进原生绑定就构建不出来。
3. 分层还换来可嵌入性——嵌入式主机在内存里执行服务端路由器，不监听端口、不走网络，却完整保留路由、中间件、编解码与错误边界，代价是仍付一遍序列化开销。
4. 边界靠可执行测试守护而非文档约定：导入边界测试打包两个入口并断言内容，CI 上任何越界改动立即失败，端点契约另有覆盖率门槛。

**相关知识点：** 包依赖方向、浏览器安全 bundle、导入边界测试、可嵌入性、单一真相源。

### 3. OpenCode 的 CLI 命令体系如何组织？进程启动路径上有哪些关键决策？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

二十余个子命令共享一条主线：**opencode 是一次性进程而非常驻服务，装配成本每次调用重新付一遍，所以启动路径上每一层都必须可跳过、退出路径上必须无条件收尾。**

1. 重模块一律动态导入。命令注册时只声明元信息，服务端与运行时在处理函数真正执行时才解析：查版本不该拉起终端渲染框架，列模型不该建数据库连接。这条直接决定冷启动耗时。
2. 项目实例是可选装配。命令用一个开关声明自己要不要项目上下文，框架负责加载与拆除；列模型、起服务、登录、升级这类命令在裸运行时下跑，完全不构建实例层。
3. 付过的装配不重复付。实例按解析后的目录键控，并发加载合并到同一个占位对象，避免一个目录被同时启两份；拆除时先等加载完成，再并发跑注册过的清理函数并发出销毁事件。
4. 传输同样按需。默认命令有三种形态：非交互脚本化、进程内直连、附加到远程实例。进程内模式根本不监听 TCP，把整个 HTTP 应用跑在进程里、用自定义请求函数路由进去，省掉全部网络往返，却仍保留路由、中间件与编解码边界。
5. 退出必须强制。启动脚本把中断信号转发给子进程并在其退出后用同一信号重新抛出，入口最终无条件退出进程——容器化的 MCP 子进程并不保证响应终止信号。代价是「干净关闭只是尽力而为」，可测口径是首屏耗时与退出后的残留进程数。

**相关知识点：** 惰性加载、一次性进程、实例生命周期、进程内传输、信号转发、强制退出、冷启动延迟。

### 4. OpenCode 的 Schema、Protocol、Server、Client 与 SDK 五层契约各自承担什么职责？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

五层分工是**Schema 定义语义值、Protocol 定义网络形状、Server 是权威真相源、Client 由代码生成、SDK 提供同进程宿主**。

1. Protocol 把 Schema 组合成路径、载荷、信封、错误、游标与流，并规定中间件的摆放位置，具体中间件键由 Server 提供。
2. Server 的具体 API 是唯一权威：改动后必须重跑生成、不许手改生成目录，手工同步的漂移就此消失。
3. 客户端有两种发射器：一种零函数式依赖，只解析响应语法而不做结构校验；另一种保留 brand 与 schema 变换并执行运行时解码。类型安全等级交给消费者选。
4. 两条事件流刻意不同：持久会话流可按序列游标重放，实例级实时流无重放保证。拿 sessionID 过滤实时流冒充持久流可能丢事件。
5. 端点契约测试要求全覆盖，漏测即失败。

**相关知识点：** API 契约分层、代码生成、契约中间表示、运行时校验、序列游标、事件流语义。

### 5. OpenCode 的配置体系如何合并多个来源？来源冲突时按什么规则裁决？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

配置来自八个来源，裁决规则是**普通设置向前读、策略倒序读**，这条不对称是刻意设计。

1. 加载顺序大致为：远程 well-known 配置、全局配置文件、标志文件、从当前目录向上查到 worktree 的项目配置、`.opencode` 目录、内容环境变量、账户与组织配置，最后是设备管理托管配置。
2. 普通设置中更具体的位置胜出，项目覆盖用户全局；策略却按文档倒序评估，让用户全局覆盖仓库，防止不可信仓库静默重启用被用户拒绝的 Provider。本质区别是设置属偏好、策略属安全边界。
3. 严格校验拒绝顶层未知键，把拼错的字段在加载期打回而非留成运行时的神秘行为；写回配置走注释感知补丁，不破坏用户手写格式。
4. 变量展开方便却是注入面，远程来源与多租户部署需要审计。可测口径是配置解析用例覆盖率与非法配置拒绝率。

**相关知识点：** 配置分层、优先级裁决、策略与设置分离、严格校验、注释感知补丁、变量展开。

### 6. OpenCode 的 Provider 与模型目录如何组织？接入新模型需要改动哪些环节？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

模型目录按 Provider 嵌套，因为**模型 ID 只在 Provider 内唯一**，可用性要两级都启用。接入新模型的成本分四层，**落在哪一层取决于它离既有端点协议与选项表有多远**。

1. 零改动层。目录数据来自远程模型清单：五分钟 TTL 缓存、进程间文件锁避免多实例重复抓取、每小时后台刷新，回退编译期快照保证断网可启动。清单新增的模型下次刷新自动出现。
2. 纯配置层。清单里没有、但端点协议已支持的模型（自建网关、OpenAI 兼容端点），只需在配置补一条 Provider 记录：端点地址、SDK 包名、凭据环境变量名、请求头与请求体覆盖。包名缺省走通用兼容适配器，这层因此不必写代码。
3. 改变换表层。模型语义与既有 Provider 不同时，要在请求选项、变体矩阵、Schema 清理三张表里加分支：是否留存、提示缓存键、思考预算、推理档位字段名，还要按模型版本门控——同族不同版本支持的档位并不一致。改动局部但必须补测试；Schema 清理还会丢表达力，各家支持的子集不同，工具定义在弱支持方精度更低。
4. 写新适配器层。端点协议不在既有联合类型里时，要在 LLM 包新增一条路由，覆盖流事件词汇、工具入参增量、结束原因映射、原生延续元数据与错误分类。这是唯一按天计、也唯一需要独立测试套件的一层。
5. 上线看四个数：工具调用成功率、结构化输出解析失败率、缓存命中率折算的单位任务 Token 成本、首字延迟。

**相关知识点：** 模型目录、Provider 适配、请求选项下沉、Schema 清理、协议适配器、缓存与回退、成本与延迟。

### 7. OpenCode 的策略系统解决什么问题？它与工具权限如何分工？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

策略回答「某操作对某命名资源是否允许」，首个消费者是 Provider 使用；权限回答「这次工具调用要不要放行」。**策略是部署治理，权限是运行时授权。**

1. 策略只有允许与拒绝，没有询问；权限多一个询问，用户当场决定并可存为长期规则。
2. 求值是通配匹配后取最后一条命中的语句，没有「更具体优先」这类隐式优先级。要只放行一家就先拒绝全部再允许它：代价是顺序必须写对，好处是按书写顺序可推演结果。
3. 配置正确、凭据有效的 Provider 仍可能被策略拒绝：配置描述端点与选项，策略决定能否使用。
4. 插件不得增删改策略语句，这是安全核心：插件被入侵也无法给自己开全部权限。
5. 权限侧合并取最严格：任一资源拒绝即拒绝，任一需询问即询问。可验证口径是被拒 Provider 的实际调用次数恒为零、规则求值单测通过率。

**相关知识点：** 策略引擎、最后匹配胜出、通配匹配、权限合并、最小权限、插件信任边界。

### 8. OpenCode 的插件生命周期有哪些阶段？插件出错时如何隔离影响？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

插件的关键设计是**注册可重放的变换，而不是直接改目录状态**——目录始终从当前活跃的变换重新物化可见记录。

1. 六个内置插件有固定加载序号（模型清单、环境凭据、账户、Provider、配置、发现），每层看到上一层的结果，顺序确定则结果确定。
2. 阶段依次是：打开位置、构建配置层、求值策略、物化基线目录、后台并发安装外部插件、激活后触发全服务重载。初始构建不算重载；重载只在活跃状态变更后发生并带去抖，一批至多发一次更新事件。
3. 隔离靠可逆性：禁用插件等于关闭它的作用域，终结器注销其变换后重载，不需手写撤销逻辑。
4. 加载第三方代码的护栏包括入口解析强制落在插件目录内以防路径遍历、版本区间门控，以及一键关掉全部外部插件的开关用于二分定位。
5. 该测的是开关插件前后的行为差异、重载耗时、卸载后残留状态数。

**相关知识点：** 插件钩子、可重放变换、加载顺序、热重载去抖、路径遍历防护、故障隔离。

### 9. OpenCode 的存储层与事件系统如何配合？为什么要把事件当作一等公民？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

存储是本地 SQLite，但真正的脊柱是持久事件日志：**状态是事件的衍生物，不是第一性事实**。

1. 提交一条持久事件的流程是：读当前序号、幂等检查（同 ID、类型、序号、数据即空操作）、校验序号严格等于上一条加一、事务内跑投影器与提交钩子、再更新序号表并写事件行。
2. 投影与事件同事务提交，不会出现「事件写了但投影没跟上」的不一致；所有权列强制单写者，两个进程不能同写一个会话。
3. 流式增量刻意不持久化，只有完整值边界才进持久流，因此一个游标恰对应一个聚合序列，断线重连能先重放再追尾。
4. 实例级实时流用有界丢弃队列，订阅者慢就丢事件而非阻塞发布方——实时性与可靠性被拆成两条流。
5. 代价是写路径更复杂，收益是崩溃恢复、重试幂等与跨进程同步复用同一份线格式。验证靠重放一致性测试、提交耗时与订阅溢出率。

**相关知识点：** 事件溯源、单写者全序、幂等提交、事务内投影、游标重放、有界队列。

### 10. OpenCode 的 TUI 如何与会话运行时解耦？渲染压力如何控制？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

终端 UI 是独立包，唯一的后端边界是 SDK：**不许从后端实现模块导入，缺数据只能去补服务器接口**。

1. 它可依赖终端渲染框架与通用展示库，但不得依赖 CLI 宿主包或运行时核心包。公开面只有两个导出函数：启动函数按输入跑起整个 UI 并返回句柄，另一个按解析后配置单独产出终端渲染器。能力开关与存储路径由宿主注入而非全局读取，测试因此能构造确定性环境。
2. 传输有两种：默认在 worker 里承载服务器实例、用 RPC 代理请求与事件流；端口、主机名、局域网发现三者任一被指定即转外部模式，worker 真正监听 TCP。对 UI 两者是同一套客户端。
3. 代价是迭代变慢：任何要用到新后端数据的界面改动都得绕「补服务器接口 → 重跑代码生成 → 再改 UI」一整圈，一处本地调整被放大成跨包、跨生成物的改动。仍坚持是因为不变量写死了「不得要求进程内后端实现」，远程附加一旦丢掉就找不回来。代价靠两个出口封顶：纯展示类功能走 UI 自带的插件运行时与插槽扩展点，不穿透边界；未知工具走通用回退渲染器，后端上新工具不必等 UI 发版。
4. 渲染压力靠三层控制：事件入队后立即或十几毫秒后合并刷新、每次刷新只触发一次渲染、增量只写响应式存储对应字段；单个工具渲染失败不拖垮会话视图。可测口径是每秒渲染次数、首帧耗时，以及「加一个需要新接口的 UI 功能」的端到端交付耗时——后者正是那笔代价的量化。

**相关知识点：** UI 与运行时解耦、SDK 边界、代码生成回路、插槽扩展点、事件批处理、增量渲染、回退渲染器、首帧延迟。

### 11. OpenCode 的桌面端与跨端 UI 复用了哪些层？哪些部分必须分别实现？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

边界只有一条判据：**能用 SDK 契约（一次 HTTP 请求加一条事件流）表达的层全部复用，需要操作系统句柄的才落到宿主**。桌面渲染进程与托管网页跑的是同一个跨端应用包，连构建插件配置都共用一份。

1. 复用层是组件库、会话渲染包（Markdown 流水线、diff 与逐行审查面板，自托管分享站也复用），以及把本地、边车、SSH 三类来源同构成一个连接对象的抽象。事件层一并复用：每台服务器一个客户端加全局 SSE 流，十几毫秒帧合并、定期心跳、亚秒级自动重连与健康轮询。
2. 宿主侧必须各写一份：按发布通道区分应用 ID 让三条通道共存、单实例锁、深链协议、原生菜单、文件选择器、多窗口状态、自动更新器，以及 Windows 上把服务器托管进 WSL 的控制器。渲染进程碰不到这些，只能走预加载脚本暴露的类型化 IPC——IPC 通道清单就是「不可复用层」的准确定义。
3. 最有判断力的是桌面捆绑什么：捆的是 Node 服务器边车而非终端 UI。渲染进程已经是完整的 Web 客户端，缺的只是一个能连的服务器。边车用工具进程派生，靠健康检查轮询确认就绪，认证密码每次启动随机生成、只在进程间传递且不落盘。
4. WSL 说明了这条线怎么划：差异被吸收进宿主，界面层拿到的仍是同一个连接对象。分发则完全无法共用，六平台矩阵各自签名公证，网页端只是同一个包的一次静态构建。可测的是六平台构建通过率、边车就绪耗时、断线重连成功率与帧合并后的每秒渲染次数。

**相关知识点：** 跨端复用、SDK 契约边界、渲染进程与主进程、Sidecar、自动更新、WSL 托管、健康检查。

### 12. OpenCode 的跨工作区会话同步如何保证多设备一致性？写权冲突怎么裁决？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

一致性不靠合并算法，靠两条：**同一时刻只有一个工作区能写某个会话**，以及**按聚合水位增量补齐的可重放事件日志**。冲突被前置成一次显式抢占，而不是事后裁决。

1. 同步粒度是聚合级水位。本地上报「每个聚合我已经收到第几号」，对端只回补缺失那段；重连从上次水位续而不是重传全量。重连指数退避封顶两分钟，每个工作区单独跟踪连接状态。
2. 写权是显式转移的：没有后写者胜出，也没有无冲突数据类型合并。所有权列决定谁能写，跨工作区迁移前先抢占，抢占之后源侧再写直接失败而非静默分叉。代价是抢不到就没有降级路径。
3. 迁移是多步的，每步都可能半成功：抢占所有权 → 复制并应用未提交的工作树差异 → 分批（每批十条）上传事件日志 → 通知对端接管 → 改写会话归属。文件状态与事件历史必须一起搬，只搬历史会让目标端在错误的工作树上继续跑。
4. 读写竞态靠同步栅栏头。变更类调用返回一个栅栏值，对端据此等到同步追平再查询，避免「本地已改、远端还没收到就读到旧值」；另有按聚合轮询等待，五秒超时后放弃。
5. 已知未解的边界是多个嵌入式宿主共享同一份持久存储：执行协调器是进程本地的，两个宿主同时排空同一会话无法互相协调，只能共享协调器或显式隔离存储。该监控每工作区的滞后序号差、重连成功率、迁移端到端耗时与栅栏等待超时率。

**相关知识点：** 水位增量同步、单写者所有权、所有权抢占、跨工作区迁移、同步栅栏、指数退避、凭据存储、去抖合并。

### 13. OpenCode 从 V1 演进到 V2 最关键的架构改变是什么？迁移成本体现在哪里？

> 核验日期：2026-08-17｜来源：[源码分析](references.md)

最关键的改变是三条分离：**持久准入不等于模型执行、基线不等于历史、进程本地不等于持久**。

1. 提示先落进持久收件箱，再由建议性唤醒触发排空，而非收到请求就内联执行；上下文分成不可变基线与投影历史，不必每轮重发全部；排空只是进程本地的临时推进，提示、历史、事件与工具状态才是持久事实。
2. 结构上，数十 KB 的会话单体被拆成输入、执行、协调、运行、纪元、压缩等小协作者，可独立测试与演进。
3. 迁移成本首先是双引擎并存：代码库短期更复杂，桥接层把旧运行时的提示以相同事件发到新流，保两套投影一致。
4. 其次是纪律成本：对等清单逐项标注完成、部分完成或缺失，改变状态的提交必须同步更新清单。
5. 再次是数据成本：新事件 schema 仍属实验性，早期数据库破坏性重置、不承诺兼容；可跟踪清单完成项占比与回归通过率。

**相关知识点：** 渐进式重写、事件桥接、对等清单、上下文纪元、破坏性迁移、回归验证。
