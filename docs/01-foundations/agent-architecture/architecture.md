### 1. 如果让你从 0 到 1 设计一个企业级 Agent，你会如何设计整体架构？（DeepSeek 一面）

**【核心思路】**
分层解耦，自底向上五层：模型接入层、Runtime 核心层、上下文与记忆层、工具能力层、治理层。核心原则：规划与执行分离、状态外置、Runtime 无状态化、工具标准化、全链路可观测。

**【深入拆解】**
- **第一性原理**：LLM 是一个**不确定的概率系统**，工程要做的是用**确定性的 Harness 把它包起来**——控制它的输入（Context）、约束它的输出（结构化/Schema）、兜底它的失败（重试/降级）。分层的本质是**隔离变化**：模型会换、工具会增、业务会变，分层让每层独立演进，避免牵一发动全身。
- **模型接入层何时需要网关**：少量模型和低流量场景可先直连SDK；当多团队、多Provider或统一治理需求出现时，引入网关集中做路由、限流、计量、观测和符合条件的故障降级。网关本身也会增加延迟与故障面，语义缓存只适合可安全复用且有质量校验的请求。
- **Runtime 层——规划与执行为什么分离**：规划需要**强推理模型**（贵、慢），执行可用便宜模型甚至规则；分离后可独立优化、独立扩缩容；Planner 产出的计划**可审计、可人工介入**。
- **上下文与记忆层是核心竞争力**：Context Engineering ≠ 固定模板，而是**动态组装**——按相关性召回、按 Token 预算裁剪、按重要性压缩。短期记忆（对话 buffer）与长期记忆（向量库 + 知识图谱）分治。
- **治理层是企业级的命脉**：Demo 和生产的本质差距就在这层——可观测（每步 Trace 便于复盘）、评测（离线回归 + 在线监控）、安全（注入检测/输出脱敏/权限分级）、成本核算。
- **状态外置的连锁价值**：状态外置 → Runtime 无状态 → 既能水平扩展，又能断点恢复（实例挂了换一台从 Checkpoint 续跑）。

| 层级 | 核心职责 | 为什么需要（失败后果） |
|---|---|---|
| 模型接入层 | 路由/降级/限流/缓存 | 无网关→厂商锁定、无法降级、成本失控 |
| Runtime 核心层 | Agent Loop、规划/执行分离 | 不分离→无法审计、难扩展 |
| 上下文与记忆层 | Context 组装、短/长期记忆 | 组装差→幻觉、Token 爆炸 |
| 工具能力层 | Tool Hub、MCP 标准接入 | 不标准→每个工具重复对接 |
| 治理层 | 可观测/评测/安全/成本 | 缺失→线上黑盒、无法定位、合规风险 |

**相关知识点：** Harness Engineering、Context Engineering、Agent Runtime、Agent Loop、MCP、Tool Hub、Planner、Checkpoint。

### 2. 一个 Agent 系统应该拆分成哪些核心模块？每个模块分别负责什么？（DeepSeek 一面）

**【核心思路】**
按职责拆九模块：意图理解、规划器、执行器、工具层、记忆层、上下文管理、模型网关、安全权限、可观测评测。原则是**高内聚低耦合，按"职责边界"而非"技术栈"拆分**。

**【深入拆解】**
- **意图理解的深水区**：多轮对话里最难的是**指代消解**（"把它删了"里的"它"）与**意图漂移检测**（用户中途改需求）。工程上靠"改写式召回"——用 LLM 把当前轮结合历史改写成独立完整的 query，再做检索与规划。
- **Planner 内部机制**：任务分解有两种策略——**自顶向下**（一次性拆成 DAG，适合结构清晰任务）与**递归/动态分解**（走一步看一步，适合探索性任务）。关键设计是**是否支持 Replan**：计划执行不下去时能否重新规划。
- **Executor 内部机制**：驱动 Agent Loop，核心是三件事——**工具选择**（选哪个工具）、**参数生成**（Function Calling 结构化输出）、**结果解析**（把工具返回喂回上下文）。
- **Memory 的三层认知**：借鉴人类记忆——**工作记忆**（当前对话 buffer）、**情景记忆**（历史事件/会话）、**语义记忆**（沉淀的知识/事实）。三者存储与召回策略不同。
- **模块间通信**：大型系统用**事件驱动/黑板模式**（共享状态）而非硬编码直接调用，便于解耦与异步。
- **为什么要模块化（本质）**：可测试、可替换、可复用、支持团队并行开发——**康威定律**下，模块边界最终会映射团队边界。

| 模块 | 职责 | 内部关键机制 |
|---|---|---|
| 意图理解 | 意图识别、指代消解 | 历史改写、槽位填充 |
| 规划器 Planner | 任务拆解、Replan | DAG 分解/递归分解 |
| 执行器 Executor | Agent Loop 驱动 | 工具选择/参数生成/解析 |
| 工具层 Tool Hub | 能力封装 | Schema 定义、MCP 协议 |
| 记忆层 Memory | 短/长期记忆 | 工作/情景/语义三层 |
| 上下文管理 | Prompt 组装/压缩 | 召回 + 裁剪 + 摘要 |
| 模型网关 | 多模型路由降级 | 负载/成本路由、熔断 |
| 安全权限 | 鉴权/脱敏/防注入 | RBAC、注入检测 |
| 可观测评测 | Trace/打分 | 全链路埋点、Eval |

**相关知识点：** Agent Loop、MCP、Function Calling、Tool Hub、Planner、Executor、Task Decomposition、Replanning。

### 3. 腾讯如果要把大模型能力同时接入不同产品，不同产品之间应该如何划分职责？（腾讯二面）

**【核心思路】**
"**AI 中台 + 业务层**"分工：中台沉淀通用能力（模型网关、Tool Hub、RAG 底座、Prompt 仓库、Eval、安全），业务层负责场景个性（业务 Prompt、编排、领域工具、数据）。原则：**通用 + 稳定 + 规模效应下沉中台，个性 + 多变 + 强耦合留业务层**。

**【深入拆解】**
- **康威定律视角**：架构会映射组织。要做中台，组织上就得有独立的**平台团队**（维护共享能力）和**业务团队**（做场景），职责边界即团队边界。
- **中台边界的判断标准**：问一句"**这个能力是不是多个业务都要、且需要规模效应？**"——是（模型接入、向量库、可观测、成本核算）→ 下沉中台；否（某产品特有的业务规则、快速试错的 Prompt）→ 留业务层。
- **中台的真实陷阱**（有深度的追问点）：过度中台化会导致**响应慢、成为瓶颈、业务不买账**（"既要通用又要贴合我"）。解法是做**薄中台**——只沉淀最稳定的公共底座，把灵活性尽量下放；中台对业务是"**能力供应商**"而非"管控者"。
- **职责契约化**：中台对外暴露稳定的 **API 契约 + SLA**（可用性、延迟承诺）+ **版本兼容策略**（不能随意 breaking change 拖垮所有业务）。
- **共享下的隔离**：多业务共享 RAG/模型时，数据按租户隔离（带权限标签过滤召回）、成本按调用量分摊计费。

| 能力 | 中台（平台层） | 业务层（各产品） |
|---|---|---|
| 模型接入/路由 | ✅ 统一网关 | — |
| Tool Hub/MCP | ✅ 通用工具 | 领域专用工具 |
| RAG | ✅ 引擎 + 隔离机制 | 业务知识库内容 |
| Prompt | ✅ 仓库 + 版本管理 | 业务 Prompt 编写 |
| Agent 编排 | ✅ 引擎 | 场景编排逻辑 |
| 可观测/成本 | ✅ 全链路 + 核算 | 消费侧监控 |
| 迭代节奏 | 慢、稳 | 快、灵活 |

**相关知识点：** MCP、Tool Hub、RAG、检索、Prompt Engineering、权限控制、多租户、可观测性。

### 4. 整个 Agent 是怎么运转的？从用户输入到最终完成任务，中间经历了哪些步骤？（DeepSeek 二面）

**【核心思路】**
Agent 本质是 **Agent Loop（感知→规划→行动→观察的循环）**：输入理解→上下文组装→LLM 决策→工具调用→观察回灌→循环迭代→判定完成→输出。工程上必须加最大步数、超时、错误处理等护栏。

**【深入拆解】**
- **Loop 的本质**：LLM 是"**决策器**"而不是"执行器"。单次调用只能预测一次，**Loop 把"一次预测"变成"多步自主"**——每一步基于最新观察重新决策，这就是 Agent 与普通"一问一答"的根本区别。
- **上下文组装是最关键的一步**：LLM 的决策质量完全取决于"**它看到了什么**"。这一步要拼装 System Prompt（角色/规则）+ 工具描述（能力边界）+ 历史（连续性）+ RAG 召回（外部知识）+ 当前状态，且要在 Token 预算内做取舍。这是 Context Engineering 的战场。
- **工具调用的工程细节**：靠 **Function Calling** 让 LLM 输出结构化调用（工具名 + 参数）；执行器实际执行；**观察结果要裁剪**——工具可能返回巨大内容（如整个文件、长 JSON），直接塞回会撑爆上下文，需摘要/截断/结构化提取。
- **终止条件的设计**（高频追问）：①LLM 主动判定完成（输出 final answer）；②达到**最大步数**（防死循环）；③超时；④连续失败次数超阈值。缺了护栏，Agent 会**无限循环烧钱**或**在错误里越陷越深**。
- **防失控护栏**：检测**重复动作**（同样的工具同样参数反复调 = 卡住了）、危险操作（删数据/发消息）走**人工审批**、Token 预算硬上限。

| 阶段 | 技术实现 | 关键护栏 |
|---|---|---|
| 输入理解 | 意图识别、指代消解 | 输入校验/注入检测 |
| 上下文组装 | Prompt + 工具 + 历史 + RAG | Token 预算、裁剪 |
| LLM 决策 | Function Calling | 结构化输出约束 |
| 工具调用 | Executor 执行 | 权限、超时、幂等 |
| 观察回灌 | 结果摘要/截断 | 防上下文爆炸 |
| 循环/终止 | 迭代判定 | 最大步数、防重复 |

**相关知识点：** Context Engineering、Agent Loop、Function Calling、Tool Calling、Executor、RAG、检索、Prompt Engineering。

### 5. ReAct 加 COT 执行流程和区别（Agent 初级）

**【核心思路】**
CoT指模型通过中间推理改善复杂问题求解，本身不负责获取外部信息或执行动作；ReAct把**决策、Action与Observation**组成循环，使模型能用工具取证并根据结果调整。工程上记录可审计的计划/决策摘要、Action和Observation即可，不要求暴露隐藏思维链。

**【深入拆解】**
- **CoT的作用与边界**：分解复杂问题可能提升数学、逻辑和多跳任务表现，但自然语言推理未必忠实，知识缺失也不能靠“多想”补齐；最终答案仍需外部验证。
- **ReAct的价值**：Action取得搜索、计算或业务系统的真实Observation，再用于下一步决策，可降低只凭模型先验作答的风险。
- **工程循环**：`Decision Summary → Action(tool, args) → Observation → Validate/Continue/Final`。工具参数先校验，返回内容视为不可信数据。
- **局限**：错误观察会污染后续，循环也可能增加Token和副作用；应设置停止条件、重复动作检测、权限、预算和Verifier。

| 范式 | 核心 | 外部交互 | 循环 | 自我纠错 | 适用 |
|---|---|---|---|---|---|
| CoT | 分步推理 | ❌ | ❌ | ❌ | 数学/逻辑推理 |
| ReAct | 推理 + 行动 | ✅ | ✅ | 弱 | 通用 Agent |
| Reflexion | + 自我反思 | ✅ | ✅ | ✅ | 需迭代优化 |
| Plan-Execute | 先规划后执行 | ✅ | 局部 | 中 | 复杂长任务 |
| ToT/LATS | 树搜索多路径 | ✅ | ✅ | ✅ | 高难度决策 |

**相关知识点：** Reflection、ReAct、Chain-of-Thought、权限控制、成本治理、Agent Architecture。

### 6. 为什么企业级 Agent 要采用分层架构？

**【核心思路】**
核心动机是**用分层隔离变化、分离关注点**，从而让"不确定的 LLM"能被"确定的工程"驯服。企业级要的是稳定、可治理、可复用、多团队协作——单体式把模型调用、业务逻辑、工具、Prompt 全糅在一起，任何一处变动都牵一发动全身。

**【深入拆解】**
- **隔离变化频率**：模型层（几个月换代）、能力/工具层（持续新增）、业务层（天天变）**变化速度完全不同**，分层让高频变动不冲击稳定内核。
- **关注点分离**：每层单一职责——网关只管接入、Runtime 只管循环、治理只管安全可观测，便于**独立优化、独立扩展、独立测试**。
- **可复用（中台前提）**：底层能力（模型接入、RAG、Tool Hub）下沉后可被多业务复用，避免重复建设。
- **可治理**：安全、权限、可观测、成本核算需要一个**统一的横切层**，分层才能集中管控。
- **康威定律**：分层边界最终映射团队边界，支持平台团队与业务团队并行开发。

| 维度 | 单体式 | 分层架构 |
|---|---|---|
| 变更影响 | 牵一发动全身 | 局部隔离 |
| 复用性 | 难 | 底层可复用 |
| 可测试 | 耦合难测 | 分层可测 |
| 治理 | 分散 | 集中横切 |
| 团队协作 | 冲突多 | 边界清晰 |

**相关知识点：** Agent Runtime、Tool Hub、RAG、Prompt Engineering、权限控制、可观测性、成本治理、Agent Architecture。

### 7. 单 Agent 与 Multi-Agent 如何选择？

**【核心思路】**
**默认单 Agent（KISS 原则）**，只有在遇到明确瓶颈时才上 Multi-Agent：任务能清晰拆成独立子域、需要不同专业角色分工、需要并行加速、或单 Agent 上下文装不下。Multi-Agent 的协调开销与成本很高，不是越多越好。

**【深入拆解】**
- **为什么默认单 Agent**：简单、可控、便宜、易调试。多数任务单 Agent + 好工具就能解决，过早上 Multi 是过度设计。
- **该上 Multi 的四个信号**：①任务可**清晰解耦**为独立子域（如"研究员 + 写作员 + 审阅员"）；②需要**异构专业角色**（不同 Prompt/工具/模型）；③子任务**可并行**且能显著提速；④单 Agent 的**上下文窗口**装不下所有信息，需要用多 Agent 做**上下文隔离**。
- **Multi 的代价（选择时的成本）**：协调/通信开销、状态一致性难、**错误跨 Agent 传播**、成本和延迟成倍、调试变黑盒。
- **判断法则**：任务**强依赖、串行、共享上下文** → 单 Agent；任务**弱耦合、可并行、需专业分工** → Multi-Agent。

| 场景特征 | 单 Agent | Multi-Agent |
|---|---|---|
| 任务耦合度 | 强依赖/串行 | 弱耦合/可并行 |
| 角色需求 | 单一 | 异构专业分工 |
| 上下文 | 装得下 | 需隔离 |
| 成本/复杂度 | 低 | 高 |
| 调试 | 容易 | 难 |
| 默认选择 | ✅ 优先 | 有明确瓶颈才用 |

**相关知识点：** Multi-Agent、Context Window、Prompt Engineering、成本治理、Agent Architecture。

### 8. Multi-Agent 的优势和缺点是什么？

**【核心思路】**
**优势**：专业分工（关注点分离）、上下文隔离（各自独立窗口）、并行加速、模块化可扩展。**缺点**：协调通信开销大、状态一致性难、错误跨 Agent 级联、成本与延迟成倍、调试困难。适合"可并行的探索/研究类"，不适合"强依赖的串行任务"。

**【深入拆解】**
- **优势详解**：①**关注点分离**——每个 Agent 专注一个子域，Prompt 更聚焦、幻觉更少；②**上下文隔离**——每个 Agent 有独立上下文窗口，绕开单窗口容量上限（这是 Multi 最硬的价值）；③**并行**——独立子任务同时跑，缩短端到端时延；④**模块化**——可独立替换/升级某个 Agent。
- **缺点详解**：①**通信开销**——Agent 间传递信息本身消耗 Token 和延迟；②**一致性难**——多个 Agent 对同一状态的认知易冲突；③**错误级联**——上游 Agent 出错，下游全盘皆错，且更难定位；④**成本/延迟成倍**——每个 Agent 都在调模型；⑤**调试黑盒**——多方交互链路难复现。
- **业界经验**：并行的**研究/检索类**任务（多个子问题独立调研）收益大；**强依赖、需共享上下文**的任务（如连续编辑同一份代码）反而更适合单 Agent，Multi 会因协调成本得不偿失。

| 维度 | 优势 | 对应缺点 |
|---|---|---|
| 分工 | 专业聚焦、少幻觉 | 通信协调开销 |
| 上下文 | 隔离、绕开窗口上限 | 状态一致性难 |
| 执行 | 并行加速 | 错误跨 Agent 级联 |
| 成本 | — | 成倍 Token/延迟 |
| 运维 | 模块化可替换 | 调试黑盒 |

**相关知识点：** Multi-Agent、检索、Context Window、Prompt Engineering、幻觉治理、成本治理、Agent Architecture。

### 9. 企业级 Coding Agent 与通用 Agent 的架构有哪些区别？

**【核心思路】**
**核心差异在"反馈信号"与"环境交互方式"**。Coding Agent 有**编译/测试/运行的确定性反馈**，靠 **Agentic Search 导航代码库 + diff 精确编辑 + 执行闭环**；通用 Agent 反馈模糊，靠 **RAG 召回知识 + 更宽的领域工具 + 多模态**。前者深耕单一环境（代码仓），后者广接多种能力。

**【深入拆解】**
- **反馈信号（最本质区别）**：代码任务有**客观、确定的反馈**——编译报错、测试红绿、运行结果，Agent 可据此**自我纠错闭环**；通用任务（写文案、做决策）反馈**主观模糊**，往往要靠 LLM-as-Judge 或人工。
- **上下文获取**：Coding Agent 用 **Agentic Search**（grep/read 按需探索代码结构）；通用 Agent 更多用 **向量 RAG** 召回外部知识。
- **工具形态**：Coding 工具高度专一（文件、diff、Bash、Git、LSP）；通用 Agent 工具面更宽（搜索、数据库、API、多模态）。
- **任务特性**：Coding 任务**长、多步、可验证**（重构几十步但每步能测）；通用任务多为**较短的问答/生成**。
- **集成**：Coding Agent 深度集成版本控制、IDE、CI；通用 Agent 集成 IM、业务系统。

| 维度 | Coding Agent | 通用 Agent |
|---|---|---|
| 反馈信号 | 确定（编译/测试） | 模糊（需 Judge/人工） |
| 上下文 | Agentic Search 探索代码 | RAG 召回知识 |
| 工具 | 文件/diff/Bash/Git/LSP | 搜索/DB/API/多模态 |
| 任务 | 长、多步、可验证 | 较短、主观 |
| 集成 | VCS/IDE/CI | IM/业务系统 |

**相关知识点：** RAG、检索、评测体系、Coding Agent、Agent Architecture。

### 10. 如果让你设计一个支持百万级用户的企业级 Agent，你会重点优化哪些模块？

**【核心思路】**
重点优化四块：**模型接入层**（语义缓存 + 小模型分流 + KV 复用降成本）、**Context 层**（压缩裁剪降 Token）、**计算层**（无状态化 + 弹性扩缩 + 异步削峰）、**治理层**（限流降级 + 可观测 + 成本核算）。核心命题是**在保证体验的前提下把单位请求成本和尾延迟压下来**。

**【深入拆解】**
- **模型接入层（省钱主战场）**：**语义缓存**吃掉重复/相似请求；**小模型分流**——简单意图/分类走便宜模型，复杂推理才上大模型；**Prompt 前缀/KV Cache 复用**降低重复计算。
- **Context 层**：Token 是主要成本项——做**历史压缩、按相关性裁剪、RAG 精准召回**，避免无脑塞全量上下文。
- **计算层**：**Runtime 无状态化**（状态外置 Redis）以弹性水平扩缩；突发流量用 **MQ 异步削峰 + 优先级队列**。
- **治理层**：**令牌桶限流 + 熔断降级**（过载时降级到缓存/规则/兜底）；**全链路可观测**定位慢点；**成本按租户/业务核算**并持续优化命中率。
- **取舍**：百万级下，**每一分 Token、每一毫秒尾延迟乘以百万都是巨量成本**，优化优先级 = 成本 > 稳定 > 极致效果。

| 模块 | 优化手段 | 收益 |
|---|---|---|
| 模型接入 | 语义缓存/小模型分流/KV 复用 | 降成本 + 提速 |
| Context | 压缩/裁剪/精准 RAG | 降 Token |
| 计算 | 无状态弹性 + MQ 削峰 | 抗并发 |
| 治理 | 限流熔断 + 可观测 + 核算 | 稳定 + 成本可控 |

**相关知识点：** Agent Runtime、RAG、检索、Prompt Engineering、多租户、可观测性、成本治理、KV Cache。

### 11. 意图理解模块如何处理多轮对话中的指代消解和意图漂移？

**【核心思路】**
**指代消解**靠 **Query Rewriting**——用 LLM 结合历史把当前轮改写成"独立完整、无需上下文即可理解"的 query（把"它/这个/上面那个"还原成实体）。**意图漂移**靠**意图跟踪 + 偏离检测 + 主动澄清**——识别当前意图是否偏离会话主线，必要时切换任务或反问确认。

**【深入拆解】**
- **指代消解的工程做法**：不是做传统 NLP 共指模型，而是**用大模型做历史改写**——输入"历史对话 + 当前句"，输出一个自包含的完整 query，再拿去检索/规划。这样"帮我把它也删了"会被还原成"删除刚才创建的订单 X"。
- **意图漂移的三步处理**：①**意图识别/分类**当前轮；②**与会话状态对比**，检测是延续、切换还是漂移；③漂移时**主动澄清**（"你是想换个话题还是继续刚才的？"）或开启新 session，避免用旧上下文污染新意图。
- **多轮的典型坑**：历史过长导致噪声/Token 爆炸（需**摘要式压缩历史**）；隐含指代（省略主语）；话题跳跃后旧上下文误导召回（需**会话切分**）。
- **状态载体**：用**槽位/会话状态（Session State）**跟踪关键实体和当前任务，作为消解和漂移判断的依据。

| 问题 | 表现 | 处理手段 |
|---|---|---|
| 指代消解 | "它/这个"含糊 | LLM 历史改写成独立 query |
| 意图漂移 | 中途换需求 | 意图分类 + 偏离检测 + 澄清 |
| 历史过长 | 噪声/Token 爆 | 摘要压缩历史 |
| 话题跳跃 | 旧上下文污染 | 会话切分/新 session |

**相关知识点：** 检索、成本治理、Query、Rewriting、LLM、Agent Architecture。

### 12. 短期记忆和长期记忆之间如何做数据同步与遗忘策略？

**【核心思路】**
短期记忆是当前会话的工作缓冲（对话 buffer），长期记忆是跨会话的持久沉淀（向量库/知识库）。同步策略是**"提炼式写入"**：会话结束或关键节点，把短期中有价值的信息**摘要、抽取、去重**后固化进长期记忆；召回时再把相关长期记忆**加载回短期上下文**。遗忘靠**分级淘汰**：短期用滑动窗口/摘要压缩，长期按时效/访问频率/重要度打分做衰减与归档。

**【深入拆解】**
- **同步方向**：短期→长期是"沉淀"（提炼摘要写入，不是原文照搬，防噪声）；长期→短期是"召回"（按相关性检索加载）。
- **遗忘策略**：短期记忆超窗口时**摘要压缩老对话**（保留结论丢弃过程）；长期记忆用 **TTL 时效 + LRU 访问频率 + 重要度打分**综合淘汰，过期的降权或归档冷存。
- **防污染**：写入长期前要过滤——错误信息、被评测判失败的结果**不进长期**（呼应 [ARC-003](runtime-harness.md#arc-003)的记忆污染）。
- **一致性**：同一事实的更新要覆盖旧值（如"用户地址变了"），避免新旧矛盾并存。

| 维度 | 短期记忆 | 长期记忆 |
|---|---|---|
| 载体 | 对话 buffer | 向量库/KG |
| 生命周期 | 单会话 | 跨会话持久 |
| 写入 | 实时原文 | 提炼摘要 |
| 遗忘 | 窗口/摘要压缩 | TTL + LRU + 重要度 |

**相关知识点：** Harness Engineering、Agent Runtime、RAG、检索、长期记忆、工作记忆、Memory、评测体系。

### 13. 多个子任务之间存在依赖关系时，编排引擎如何处理死锁或循环依赖？

**【核心思路】**
把子任务建成 **DAG（有向无环图）**，用**拓扑排序**确定执行顺序。**编排时**通过**环检测**（DFS 找回边/Kahn 算法入度归零）在图构建阶段就拒绝循环依赖；**运行时**用**超时 + 依赖等待上限 + 资源加锁顺序统一**防死锁，检测到卡死则**中断 + Replan**打破循环。

**【深入拆解】**
- **循环依赖（编排期）**：任务图必须是 DAG。构建时跑**拓扑排序**，若存在无法归零入度的节点即有环，直接报错或让 Planner 重新拆解。
- **死锁（运行期）**：多任务争抢共享资源可能死锁，用经典手段——**统一加锁顺序**（破坏循环等待）、**超时释放**、**依赖等待上限**。
- **Agent 特有的"软死锁"**：LLM 反复在两个动作间横跳（A 等 B、B 等 A 的语义循环），靠**重复动作检测 + 最大步数**兜底，触发后 **Replan** 换路径。

| 问题 | 阶段 | 手段 |
|---|---|---|
| 循环依赖 | 编排期 | DAG + 拓扑排序 + 环检测 |
| 资源死锁 | 运行期 | 统一锁序 + 超时 + 等待上限 |
| 语义横跳 | 运行期 | 重复检测 + 步数 + Replan |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** Planner、Replanning、DAG、DFS、Kahn、Agent Architecture。

### 14. 如何设计 Prompt Injection 检测机制，是否存在误报问题？

**【核心思路】**
采用**纵深防御**：①输入和外部内容检测；②用角色、来源标签和分隔符帮助模型区分“数据与指令”；③输出和工具调用策略校验；④最小权限、Sandbox与审批限制影响半径。**分隔符是软提示，不是物理或安全隔离边界**。误报不可避免，应分级处置并持续校准。

**【深入拆解】**
- **检测手段**：黑名单规则（快但易绕过）+ **LLM/分类器语义检测**（识别改写变体）+ 已知注入模式库。
- **结构提示**：把不可信输入用清晰边界包裹并声明“以下是数据”，同时保留来源；它能降低混淆但可被绕过，真正的安全边界必须在模型之外执行。
- **纵深防御**：单靠检测不够，**最后防线是权限**——注入即便骗过检测，工具调用的 RBAC（[ARC-022](reliability.md#arc-022)）也能拦住越权操作。
- **误报问题**：安全检测本质是**召回率与误报率的权衡**——查得严则误伤正常请求（如用户正当地说"忽略之前的格式要求"），查得松则漏防。工程上**分级响应**（可疑→加确认而非直接拒绝）+ **人工审核样本回流**持续调优。

| 层次 | 手段 | 局限 |
|---|---|---|
| 输入检测 | 规则 + 语义分类 | 有误报/漏报 |
| 结构隔离 | 分隔符 + 数据声明 | 需模型配合 |
| 输出校验 | 泄露/越权检查 | 事后 |
| 权限兜底 | RBAC 最后防线 | 最可靠 |

**相关知识点：** Tool Calling、检索、Prompt Injection、Prompt Engineering、权限控制、Sandbox、Agent Architecture。

### 15. Replanning 与简单 Retry 的边界如何界定，什么情况下触发哪种策略？

**【核心思路】**
分界线是**"错在哪一层"**。**Retry** 针对**执行层的偶发失败**（超时、限流、网络抖动、工具临时不可用）——计划本身是对的，重试同一步即可。**Replanning** 针对**规划层的方向错误**（工具选错、路径走不通、前提变化、连续多次 Retry 仍失败）——重试无意义，必须让 Planner 重新拆解路径。

**【深入拆解】**
- **触发 Retry**：错误**可恢复且与决策无关**（5xx、Timeout、RateLimit），用**指数退避 + 最大次数**，超限则升级。
- **触发 Replanning**：错误**源于计划本身**（参数反复错、目标不可达、环境变了、Retry 耗尽），需带着失败原因回到 Planner 重规划。
- **中间态——降级**：Replan 和 Retry 之间还有降级（换备用工具/兜底方案）。
- **防振荡**：Replan 也要设次数上限，避免"规划→失败→再规划"无限循环，最终**升级到人工**。

| 策略 | 触发条件 | 动作 | 上限 |
|---|---|---|---|
| Retry | 偶发执行错 | 重试同一步 | 退避 N 次 |
| 降级 | 该路径不稳 | 换备用/兜底 | — |
| Replan | 计划方向错 | 重新拆解 | 有限次→人工 |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** Planner、Replanning、Retry、故障恢复、Agent Architecture。

### 16. 如果是 Multi-Agent 架构，模块之间如何划分职责边界，避免功能重叠？

**【核心思路】**
以**单一职责 + 明确契约**为原则，按**能力域**而非随意拆分，每个 Agent 有清晰的**输入/输出契约和权责范围**；用**编排者/Supervisor 模式**统一调度，避免多个 Agent 抢同一职责；共享状态走**统一黑板/消息协议**，禁止越界直接操作他人领域。

**【深入拆解】**
- **划分原则**：按**正交的能力域**拆（研究/编码/审阅），确保职责不交叉；每个 Agent 定义**接口契约**（我负责什么、输入输出是什么）。
- **避免重叠的手段**：①**Supervisor 编排**——由主 Agent 分派，子 Agent 不自行抢活；②**能力注册表**——明确谁能干什么，路由按注册表分发；③**去重仲裁**——多 Agent 产出冲突时由编排者裁决。
- **通信规范**：统一消息格式/黑板，边界外只读不写。（同簇要点参见 [ARC-034](#arc-034)任务编排）

| 手段 | 做法 | 避免的问题 |
|---|---|---|
| 划分维度 | 按正交能力域拆分 | 职责交叉 |
| 契约 | 每 Agent 定义输入/输出接口 | 边界模糊 |
| 编排 | Supervisor 中心化分派 | 多方抢活 |
| 去重 | 能力注册表 + 冲突仲裁 | 功能重叠 |
| 通信 | 统一黑板/消息协议 | 越界操作 |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** Multi-Agent、任务调度、Supervisor、Agent Architecture。

### 17. Context Engineering 的核心目标是什么？

**【核心思路】**
核心目标是**在有限的上下文窗口内，为模型的每一次决策提供"恰好够用、精准相关、无噪声"的信息**——即 **Right Information, Right Place, Right Time**。既要**信息充分**（该有的都有，避免因缺信息而幻觉），又要**信息精简**（无关的都不要，避免噪声干扰和 Token 浪费）。本质是**信息的动态调度与预算管理**。

**【深入拆解】**
- **三重张力**：**充分 vs 精简**（够用但不冗余）、**相关 vs 全面**、**成本 vs 质量**。
- **要解决的问题**：上下文窗口有限、长上下文的"迷失在中间"、无关信息干扰决策、Token 成本。
- **手段**：精准召回（RAG）、动态裁剪、历史压缩摘要、结构化组织（把重要信息放显著位置）、按需加载。

| 目标 | 含义 | 反面（失败） |
|---|---|---|
| 充分 | 决策所需信息都在 | 缺信息→幻觉 |
| 精简 | 无关信息都不放 | 噪声→干扰/贵 |
| 相关 | 按当前 query 精准召回 | 召回错→跑偏 |
| 及时 | 每轮按当前状态重算 | 静态模板→僵化 |

**相关知识点：** Context Engineering、RAG、检索、Context Window、幻觉治理、成本治理、任务调度、Agent Architecture。

### 18. 动态上下文如何组装？

**【核心思路】**
按"**分层拼装 + 按需召回 + 预算裁剪**"三步动态组装：先铺**固定层**（System Prompt/角色/规则/工具描述），再叠**检索层**（RAG 按当前 query 召回的知识、历史相关片段），最后放**即时层**（当前任务状态、上一步观察结果），全程在 **Token 预算**内按优先级裁剪与压缩。不是静态模板，而是**每一轮根据当前状态重新计算**。

**【深入拆解】**
- **组装顺序（优先级）**：系统指令 > 工具定义 > 当前任务/最新观察 > 召回知识 > 历史（可压缩）。低优先级在超预算时先被裁。
- **动态性**：每一轮依据"当前需要什么"重新召回和拼装，而非固定塞全部。
- **位置策略**：关键信息放开头/结尾（缓解"lost in the middle"）。
- **压缩**：长历史用摘要替代原文，工具大返回做提取。

| 层 | 内容 | 优先级（超预算时） |
|---|---|---|
| 固定层 | System/角色/规则/工具描述 | 高（保留） |
| 即时层 | 当前任务/最新观察 | 高（保留） |
| 检索层 | RAG 召回知识/相关历史 | 中 |
| 历史层 | 早期对话 | 低（先压缩/裁剪） |

**相关知识点：** RAG、检索、Prompt Engineering、成本治理、Agent Architecture。

### 19. 多 Agent 如何进行任务编排？

**【核心思路】**
主流三种编排模式：**Supervisor（主管分派）**——一个编排者 Agent 拆任务、派给子 Agent、汇总结果，最常用、可控；**Sequential/Pipeline（流水线）**——Agent 按固定顺序串行处理；**Network/Group Chat（对等协作）**——Agent 间自由通信讨论。据任务耦合度选型：**结构清晰用 Supervisor，线性流程用 Pipeline，开放探索用 Group Chat**。

**【深入拆解】**
- **Supervisor 模式**：中心化编排，主 Agent 负责规划、分发、监督、聚合，职责边界清晰（呼应 [ARC-026](#arc-026)），是生产首选。
- **Pipeline 模式**：适合确定的多阶段流程（研究→写作→审阅），简单但不灵活。
- **Group Chat/Network**：去中心化，Agent 互相对话协作（AutoGen 风格），灵活但难控、成本高。
- **共性支撑**：统一消息协议、共享状态（黑板）、终止条件与仲裁机制。

| 模式 | 结构 | 特点 | 适用 |
|---|---|---|---|
| Supervisor | 中心化分派 | 可控、职责清 | 多数生产场景 |
| Pipeline | 串行 | 简单、固定 | 线性多阶段 |
| Group Chat | 对等网状 | 灵活、难控 | 开放探索 |

**相关知识点：** AutoGen、Multi-Agent、成本治理、Supervisor、Sequential、Agent Architecture。

### 20. 如何设计 Agent 的状态管理机制？

**【核心思路】**
用**显式状态机 + 状态外置持久化**。定义任务状态（Created→Planning→Running→Waiting→Success/Failed/Paused）及合法转移；每一步执行前后**持久化状态快照**（Checkpoint）到外部存储（Redis/DB），使 Runtime 无状态化。这样既支持**断点恢复**（[ARC-043](runtime-harness.md#arc-043)、[ARC-074](reliability.md#arc-074)），又支持**水平扩展**（任意实例可接管），还便于**审计与可观测**。

**【深入拆解】**
- **状态内容**：当前任务/子任务进度、上下文快照、记忆引用、已执行动作历史、待办队列。
- **状态机**：明确状态集合与转移规则，非法转移拒绝，异常态可回滚或人工介入。
- **外置持久化**：状态不放进程内存，放外部存储，实现无状态 Runtime + 断点续跑。

| 要素 | 设计 |
|---|---|
| 状态集合 | Created/Running/Waiting/Success/Failed/Paused |
| 转移 | 显式规则 + 非法拒绝 |
| 持久化 | Checkpoint 外置 Redis/DB |
| 收益 | 断点恢复 + 水平扩展 + 审计 |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** Harness Engineering、Agent Runtime、状态机、Checkpoint、Memory、可观测性、故障恢复、Agent Architecture。

### 21. 多模型 Router 如何设计？

**【核心思路】**
模型 Router 是模型网关的核心，按**"请求特征 → 路由策略 → 目标模型"**设计。路由维度：**任务复杂度**（简单走小模型，复杂走大模型）、**成本预算**、**能力匹配**（代码/多模态/长文本各选所长）、**负载与延迟**、**可用性**（主模型故障降级到备用）。策略可**规则路由 + 分类器路由**结合，叠加**降级熔断、缓存、限流**。

**【深入拆解】**
- **路由信号**：意图/复杂度分类、上下文长度、模态、SLA 要求、成本档位。
- **核心价值**：**降本**（小模型分流，[ARC-017](#arc-017)）+ **提可用**（多模型互备降级）+ **提质**（能力匹配）。
- **实现**：轻量分类器或规则先判档，再选模型；配额/负载做二次调度。

| 路由维度 | 策略 |
|---|---|
| 复杂度 | 简单→小模型，复杂→大模型 |
| 能力 | 代码/多模态/长文本匹配 |
| 成本 | 按预算档路由 |
| 可用性 | 主故障→备用降级 |

**相关知识点：** 可靠性、成本治理、模型路由、模型网关、任务调度、Agent Architecture。

### 22. 如何避免不同业务团队重复建设知识库？

**【核心思路】**
建**统一 RAG 知识底座（知识中台）**：提供共享的**文档接入、切分、embedding、检索、rerank**能力，各业务只需**上传自己的知识内容**并通过**租户/权限标签隔离**（[ARC-061](platform.md#arc-061)）。公共知识（如公司制度）**沉淀为共享库**多业务复用；业务私有知识**逻辑隔离**。统一管理还便于**质量治理、更新同步、去重**。核心：**平台统一"能力"，业务各自管"内容"**。

**【深入拆解】**
- **能力/内容分离**：平台提供统一的接入、切分、embedding、检索能力；业务只负责上传自己的知识内容。
- **公共 vs 私有**：公司级公共知识建共享库多方复用；业务私有知识按租户/权限标签逻辑隔离（[ARC-061](platform.md#arc-061)）。
- **统一治理红利**：集中做质量审核、更新同步、去重、召回监控，避免各团队各建一套、质量参差。

| 方面 | 平台（能力） | 业务（内容） |
|---|---|---|
| 接入/切分/向量化 | ✅ 统一 | — |
| 检索/rerank | ✅ 统一引擎 | — |
| 知识内容 | — | ✅ 各自上传 |
| 权限/隔离 | ✅ 机制 | 标签配置 |
| 公共知识 | ✅ 共享库 | 复用 |

**相关知识点：** RAG、Embedding、Rerank、检索、权限控制、多租户、Agent Architecture。

### 23. 如何设计统一模型接入层？

**【核心思路】**
统一接入层（模型网关）**屏蔽多厂商差异**，对上提供**统一 API**（统一的请求/响应格式、流式、Function Calling 抽象），对下适配各家模型 SDK。内置**路由、降级熔断、限流、缓存、鉴权、Token 计量、可观测**。价值：业务无需关心底层用哪个模型，**换模型不改业务代码**，并集中做治理与降本（Router 设计参见 [ARC-039](#arc-039)）。

**【深入拆解】**
- **对上统一抽象**：统一 Chat/Completion API、统一流式、统一 Function Calling 格式，屏蔽各厂商 SDK 差异。
- **对下多厂商适配**：适配 OpenAI/Anthropic/开源/私有化模型，新增模型只改网关不动业务。
- **横切能力内置**：路由、降级熔断、限流、缓存、鉴权、Token 计量、可观测集中在网关层做。

| 面向 | 职责 |
|---|---|
| 对上（业务） | 统一 API、换模型不改代码 |
| 对下（模型） | 多厂商/私有化适配 |
| 横切能力 | 路由/降级/限流/缓存/计量/可观测 |
| 收益 | 解耦 + 集中治理 + 降本 |

**相关知识点：** Function Calling、权限控制、可观测性、成本治理、模型路由、模型网关、Agent Architecture。

### 24. 多模型路由策略如何设计？

**【核心思路】**
按**任务复杂度、能力匹配、成本、负载、可用性**多维路由：规则/分类器判档选模型，简单任务分流小模型降本，复杂任务上大模型保质，主模型故障降级备用。叠加缓存与限流（同 [ARC-039](#arc-039)、[ARC-067](platform.md#arc-067)）。

**【深入拆解】**
- **两类路由策略**：**规则路由**（按 token 长度/关键词/场景硬编码，快而透明）+ **分类器路由**（轻量模型判断复杂度，灵活但有开销）。
- **多目标权衡**：质量、成本、延迟、可用性往往冲突，需按业务 SLA 定权重（如客服重延迟、报告重质量）。
- **动态调整**：结合实时负载与配额做二次调度，主模型不可用即降级。

| 策略类型 | 判据 | 特点 |
|---|---|---|
| 规则路由 | token 长度/关键词/场景 | 快、透明、需维护 |
| 分类器路由 | 复杂度模型预测 | 灵活、有开销 |
| 成本路由 | 预算档 | 简单任务→小模型 |
| 故障路由 | 可用性探测 | 主故障→备用降级 |

**历史别名：** `ENG-161`。

**相关知识点：** 可靠性、成本治理、模型路由、任务调度、Agent Architecture。

### 30. Agent 编排层如何管理多轮上下文和任务状态？

**【核心思路】**

**【深入拆解】**

- **任务状态（管得住）**：显式状态机记录进度，Checkpoint 外置持久化支持中断续跑与并发调度（[ARC-036](#arc-036)）。

|---|---|---|
| 多轮上下文 | 组装 + 压缩 + 召回 | 对话连续性 |
| 任务状态 | 状态机 + Checkpoint | 进度可控/可恢复 |
| 并发 | 状态外置 | 多任务调度 |

### 31. 流式输出在高并发场景下如何保证稳定？

**【核心思路】**
用 **SSE/WebSocket** 做流式，稳定性靠：**事件驱动的长连接管理**（连接注册、心跳、空闲超时与资源配额）、**背压处理**（有界缓冲、限速或断开慢消费者）、**断线重连与可选续传**、首Token/整体超时，以及支持长连接的负载均衡。核心是控制每连接资源和慢消费者，而不是把客户端长连接放进普通“连接池”。

**【深入拆解】**
- **连接管理**：使用非阻塞I/O、连接注册表、每租户/实例上限、心跳和超时回收；下游模型HTTP连接可复用，但这与面向客户端的SSE连接管理不同。
- **背压**：客户端消费慢于生成时使用有界队列，超过阈值后降采样、取消上游或断开，禁止无限缓冲。
- **容错**：SSE可用事件ID与持久事件缓冲实现续传；若服务端未保存事件，只能重新请求，不能承诺无损续推。

| 挑战 | 手段 |
|---|---|
| 连接耗尽 | 连接池 + 心跳 + 超时回收 |
| 背压/OOM | 缓冲 + 流控限速 |
| 断线 | 记录位置 + 续传 + 幂等重连 |
| 过载 | 首 Token/整体超时 + 降级非流式/兜底 |
| 高并发 | 网关负载均衡 + keep-alive 调优 |

**相关知识点：** 多租户、成本治理、任务调度、SSE、WebSocket、Agent Architecture。

### 32. 如何防止 Prompt 注入和敏感数据泄露？

**【核心思路】**
**注入防护**（[ARC-023](#arc-023)）：输入检测 + 结构隔离（数据非指令）+ 输出校验 + 权限兜底。**数据泄露防护**：**输入脱敏**（进模型前掩码 PII）、**输出过滤**（拦截泄露系统提示/敏感信息）、**最小权限召回**（RAG 按权限过滤，[ARC-061](platform.md#arc-061)）、**数据不出域**（私有化/合规，[ARC-059](platform.md#arc-059)）、**全程审计**。核心：**输入防注入与脱敏、输出防泄露、权限做兜底、全链路审计**。

**【深入拆解】**
- **注入防护**：输入检测 + 结构隔离（数据非指令）+ 输出校验 + 权限兜底（[ARC-023](#arc-023)四层防御）。
- **泄露防护**：入模型前 PII 脱敏、出模型时过滤敏感信息与系统提示、召回按权限过滤。
- **纵深防御**：单点都可能被绕过，靠"检测 + 隔离 + 脱敏 + 权限 + 审计"多层叠加。

| 威胁 | 防护手段 |
|---|---|
| Prompt 注入 | 检测 + 结构隔离 + 输出校验 + 权限兜底 |
| PII 泄露 | 输入脱敏 + 输出过滤 |
| 越权召回 | 权限标签过滤（[ARC-061](platform.md#arc-061)） |
| 数据出域 | 私有化 + 合规 + 审计 |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** RAG、检索、Prompt Engineering、权限控制、Agent Architecture。

### 33. 线上模型输出异常时如何快速定位根因？

**【核心思路】**
靠**全链路 Trace 回放**（[ARC-042](reliability.md#arc-042)）：定位到具体会话与步骤，检查**当时的完整上下文（喂了什么）、模型输入输出、工具调用与返回、状态**，逐层排查根因——是**上下文组装问题**（召回错/信息缺）、**Prompt/版本变更**、**模型侧波动**、**工具返回异常**还是**参数错误**。配合**变更关联**（最近发布了什么）、**指标告警下钻**、**相似 case 聚类**快速缩小范围。核心：**可复现的 Trace + 变更关联 = 快速归因**。

**【深入拆解】**
- **Trace 回放**：定位到具体会话/步骤，还原当时完整上下文、模型输入输出、工具调用与返回。
- **分层排查**：依次看上下文组装（召回错/缺信息）→ Prompt/版本变更 → 模型波动 → 工具异常 → 参数错误。
- **加速手段**：变更关联（近期发布了什么）、指标告警下钻、相似 case 聚类缩小范围。

| 排查层 | 可能根因 |
|---|---|
| 上下文 | 召回错 / 信息缺失 |
| Prompt | 版本变更引入 |
| 模型 | 侧波动/降级 |
| 工具 | 返回异常/超时 |
| 参数 | 生成错误（[ARC-020](reliability.md#arc-020)） |

**相关知识点：** Tool Calling、检索、Prompt Engineering、可观测性、Agent Architecture。

### 34. 单 Agent 和多 Agent 架构如何选择？

**【核心思路】**
默认单 Agent（简单可控便宜），出现明确瓶颈才上多 Agent：任务可清晰解耦、需异构专业分工、可并行加速、单 Agent 上下文装不下。强依赖/串行/共享上下文用单 Agent；弱耦合/可并行/需分工用多 Agent。核心：**多 Agent 是解决特定瓶颈的手段，不是默认选择**（同 [ARC-013](#arc-013)）。

**【深入拆解】**
- **默认单 Agent**：简单、可控、便宜、易调试，多数任务足够，过早上多 Agent 是过度设计。
- **上多 Agent 的信号**：可清晰解耦、需异构专业分工、可并行提速、单窗口装不下需上下文隔离。
- **代价意识**：多 Agent 有协调开销、错误级联、成本翻倍、调试黑盒（[ARC-014](#arc-014)）。

| 特征 | 单 Agent | 多 Agent |
|---|---|---|
| 耦合 | 强依赖/串行 | 弱耦合/可并行 |
| 角色 | 单一 | 异构分工 |
| 上下文 | 装得下 | 需隔离 |
| 成本 | 低 | 高 |
| 默认 | ✅ | 有瓶颈才用 |

**相关知识点：** Multi-Agent、成本治理、Agent Architecture。
