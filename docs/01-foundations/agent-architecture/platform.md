### ARC-004 · 如果让你从 0 到 1 设计一个面向千万用户的大模型应用平台，你会如何划分整体架构？（腾讯二面）

> 稳定 ID：`ARC-004`｜原题号：4

**【核心思路】**
在 Agent 架构之上，重心从"能力"转向"**规模化稳定 + 成本可控**"。强化：网关限流削峰、Runtime 无状态弹性扩展、多租户隔离、存储分层、灰度与可观测治理。本质是把**确定性工程能力包在不确定的大模型外面**。

**【深入拆解】**
- **限流削峰的具体手段**：网关层**令牌桶限流**保护后端；突发流量用**消息队列（MQ）异步削峰**，把同步请求转排队；设**优先级队列**（付费用户/关键业务优先）；后端过载时**熔断降级**（返回兜底答案或排队提示）。
- **缓存三级策略**（省钱关键）：**精确缓存**（相同 query 直接返回）+ **语义缓存**（向量匹配相似 query）+ **前缀缓存/KV Cache 复用**（相同 System Prompt 复用计算）。缓存命中率直接决定成本。
- **无状态化的实现**：会话状态、任务状态外置到 **Redis/DB**，Runtime 实例本身不存状态，从而可**任意水平扩缩容**，某实例宕机不影响会话（换实例从状态恢复）。
- **多租户隔离三维度**：**计算隔离**（配额/限流按租户）、**数据隔离**（逻辑分库或物理隔离，RAG 知识库带租户标签过滤）、**模型隔离**（大客户专属实例，小客户共享池）。
- **成本核算**：按 Token 计量到租户/业务线，缓存命中优化、小模型分流（简单任务走便宜模型）。
- **高可用**：多活容灾、无单点、**优雅降级**（大模型不可用时降级到规则/缓存/兜底文案，而非直接报错）。
- **流式输出稳定性**：SSE/WebSocket 长连接管理、背压处理、断线重连与续传。

| 维度 | 单 Agent 架构 | 千万级平台架构 |
|---|---|---|
| 首要目标 | 任务正确性 | 规模稳定 + 成本 |
| 流量治理 | 直连模型 | 令牌桶限流 + MQ 削峰 + 熔断 |
| 缓存 | 可选 | 精确 + 语义 + KV 三级 |
| 计算 | 单实例 | 无状态 + 弹性扩缩 |
| 隔离 | 无 | 计算/数据/模型多租户 |
| 可靠性 | 尽力而为 | 多活容灾 + 优雅降级 |
| 成本 | 不敏感 | Token 计量 + 分摊 + 小模型分流 |

**相关知识点：** Agent Runtime、RAG、Prompt Engineering、多租户、可观测性、可靠性、成本治理、KV Cache。

### ARC-045 · 企业级 Agent 平台的 Harness Architecture 一般包含哪些核心模块？

> 稳定 ID：`ARC-045`｜原题号：45

**【核心思路】**
归纳为：**模型网关层、Agent Runtime（Loop/规划/执行）、上下文引擎、记忆系统、工具中心（Tool Hub/MCP）、编排引擎、评测层、安全与权限、可观测、状态与存储**。企业级还叠加**多租户、Prompt 仓库、成本核算、治理**。核心是"**Runtime 内核 + 能力层 + 治理层**"三块（详见 [ARC-001](architecture.md#arc-001)、[ARC-002](architecture.md#arc-002)的分层架构与核心模块）。

**【深入拆解】**
- **内核层**：Agent Loop + Planner + Executor + 上下文引擎 + 状态管理，负责"跑一次任务"。
- **能力层**：模型网关、Tool Hub/MCP、RAG/记忆、编排引擎，为内核提供模型、工具、知识、协作能力。
- **治理层**：评测、安全权限、可观测、成本核算、多租户、Prompt 仓库——是企业级区别于 Demo 的关键。

| 层 | 包含模块 | 定位 |
|---|---|---|
| 内核层 | Loop/Planner/Executor/上下文/状态 | 执行引擎 |
| 能力层 | 模型网关/Tool Hub/RAG/编排 | 能力供给 |
| 治理层 | 评测/安全/可观测/成本/多租户 | 可管可控 |

**相关知识点：** Harness Engineering、Agent Runtime、Agent Loop、MCP、Tool Hub、Planner、Executor、RAG。

### ARC-046 · 为什么采用 AI 中台模式而不是每个业务独立建设 Agent？

> 稳定 ID：`ARC-046`｜原题号：46

**【核心思路】**
核心理由：**避免重复建设、统一治理、规模效应、降本**。各业务独立建设会导致**模型接入/知识库/工具/可观测重复造轮子**、标准不一、安全治理分散、成本高。中台把**通用能力下沉共享**（模型网关、Tool Hub、RAG 底座、Eval），业务只做场景个性，从而**快速复用、统一管控、集中降本**。代价是需做好多租户隔离与稳定性，避免中台成瓶颈（薄中台原则，详见 [ARC-005](architecture.md#arc-005)）。

**【深入拆解】**
- **重复建设的痛**：各业务独立建，模型接入、知识库、可观测、安全全重造，标准不一、成本翻倍、治理分散。
- **中台的收益**：规模效应（一次建设多方复用）、统一治理（安全/成本/合规集中）、快速上线（业务只拼装）。
- **中台的风险与解法**：过度中台化会成瓶颈 → 做**薄中台**，只沉淀最稳定的公共底座，灵活性下放业务。

| 维度 | 各业务独立建设 | AI 中台模式 |
|---|---|---|
| 重复度 | 高（重复造轮子） | 低（复用底座） |
| 成本 | 翻倍 | 集中降本 |
| 治理 | 分散、标准不一 | 统一管控 |
| 上线速度 | 慢 | 快（拼装） |
| 风险 | — | 中台成瓶颈（需薄中台） |

**相关知识点：** Tool Hub、RAG、多租户、可观测性、成本治理、模型网关、Agent Architecture。

### ARC-048 · 多业务共享模型时如何进行资源隔离？

> 稳定 ID：`ARC-048`｜原题号：48

**【核心思路】**
从**计算、配额、数据、性能**四维隔离。**计算/配额**：按租户设 QPS/Token 配额与优先级，防某业务打满影响他人（[ARC-075](#arc-075)）；**数据**：请求上下文、日志、缓存按租户隔离，防串数据；**性能**：关键业务专属资源池/独立实例，普通业务共享池；**故障**：租户级熔断，隔离故障爆炸半径。用**命名空间/租户 ID 贯穿全链路**实现逻辑隔离，高要求场景物理隔离。

**【深入拆解】**
- **隔离级别**：逻辑隔离（共享实例 + 租户标签，省成本）vs 物理隔离（独立资源，强隔离，贵）。
- **QoS**：优先级队列 + 配额限流，保障高价值租户 SLA。

| 维度 | 手段 |
|---|---|
| 配额 | 租户 QPS/Token 限流 + 优先级 |
| 数据 | 租户 ID 贯穿、上下文/缓存隔离 |
| 性能 | 专属池 vs 共享池 |
| 故障 | 租户级熔断 |

**相关知识点：** 多租户、可靠性、成本治理、QPS、Token、Agent Architecture。

### ARC-051 · Agent 平台与业务平台之间如何解耦？

> 稳定 ID：`ARC-051`｜原题号：51

**【核心思路】**
靠**清晰的 API 契约 + SLA + 稳定版本**解耦：Agent 平台对业务是"**能力供应商**"，暴露标准化接口（Agent 编排、工具、RAG、模型调用），业务通过接口消费而不依赖内部实现。平台内部演进不破坏对外契约（版本兼容）。**通用能力在平台、业务逻辑在业务侧**，两者通过契约通信，各自独立迭代（详见 [ARC-005](architecture.md#arc-005)）。

**【深入拆解】**
- **契约解耦**：平台暴露稳定 API（编排、工具、RAG、模型调用），业务只依赖契约不依赖内部实现。
- **版本兼容**：平台内部重构不得破坏对外契约，用版本化 + 灰度保护存量业务（[ARC-052](architecture.md#arc-052)、[ARC-076](#arc-076)）。
- **供需关系**：平台是"能力供应商"（对内），业务是"消费者"，用 SLA 约定可用性与延迟。

| 维度 | 平台侧 | 业务侧 |
|---|---|---|
| 提供 | 稳定 API + SLA | — |
| 依赖 | — | 只依赖契约 |
| 迭代 | 内部自由演进 | 独立快速迭代 |
| 变更约束 | 不破坏契约、版本兼容 | 按契约消费 |

**相关知识点：** RAG、可靠性、灰度发布、API、SLA、Agent Architecture。

### ARC-053 · 如何评估不同业务线 Agent 的效果？

> 稳定 ID：`ARC-053`｜原题号：53

**【核心思路】**
**统一评测框架 + 业务定制指标**：平台提供通用评测能力（成功率、延迟、成本、幻觉率、满意度）和评测流水线，各业务线在此之上定义**场景化指标与评测集**（如客服看解决率、编码看通过率）。用**离线回归 + 在线采样 Judge + 用户反馈**统一采集，横向对比各业务线，纵向防退化（方法参见 [ARC-024](reliability.md#arc-024)、[ARC-027](reliability.md#arc-027)）。

**【深入拆解】**
- **统一 + 定制两层**：平台提供通用指标与评测流水线（成功率/延迟/成本/幻觉率/满意度），业务线定义场景化指标（客服看解决率、编码看通过率）。
- **三路数据源**：离线固定评测集（防退化）+ 在线采样 LLM Judge（真实分布）+ 用户反馈（点赞/投诉）。
- **横纵对比**：横向对比不同业务线水平，纵向监控单业务线版本演进，闭环驱动优化。

| 层 | 指标 | 来源 |
|---|---|---|
| 通用（平台） | 成功率/延迟/成本/幻觉率 | 离线 + 在线 |
| 场景（业务） | 解决率/通过率/转化 | 业务埋点 |
| 体验 | 满意度/NPS/投诉 | 用户反馈 |

**相关知识点：** 幻觉治理、评测体系、成本治理、Judge、Agent Architecture。

### ARC-056 · AI 中台如何进行成本核算和分摊？

> 稳定 ID：`ARC-056`｜原题号：56

**【核心思路】**
建**统一计量 + 按租户/业务分摊**体系。**计量**：全链路埋点采集每请求的**Token 数、模型档位、工具调用、算力占用**，打上租户/业务标签。**核算**：按 Token 单价 + 资源占用折算成本。**分摊**：按业务线用量分账，支持配额与预算告警。**优化**：暴露缓存命中率、小模型分流率等指标驱动降本。核心：**成本可归因到每个业务，可计量、可预算、可优化**。

**【深入拆解】**
- **计量维度**：Token（输入/输出分算）、模型档位、缓存命中、工具/算力。
- **分摊模型**：按实际用量（后付费）或配额包（预付费）。
- **治理**：预算告警、成本看板、降本指标（[ARC-017](architecture.md#arc-017)、[ARC-071](reliability.md#arc-071)）。

| 环节 | 做法 |
|---|---|
| 计量 | 埋点采集 Token/模型档/工具/算力，打租户标签 |
| 核算 | Token 单价 + 资源占用折算成本 |
| 分摊 | 按业务用量分账（预付费配额/后付费账单） |
| 优化 | 缓存命中率、小模型分流率等降本指标 |

**相关知识点：** Tool Calling、多租户、成本治理、Token、Agent Architecture。

### ARC-057 · 如何建设统一 Agent 开发平台？

> 稳定 ID：`ARC-057`｜原题号：57

**【核心思路】**
提供**全生命周期工具链**：可视化/低代码**编排**、**Prompt 仓库**（[ARC-052](architecture.md#arc-052)）、**工具中心**（[ARC-060](architecture.md#arc-060)）、**RAG 知识管理**、**调试与评测**（[ARC-042](reliability.md#arc-042)、[ARC-053](#arc-053)）、**发布与灰度**（[ARC-076](#arc-076)）、**监控运维**。让业务开发者**复用平台能力快速搭 Agent**，平台统一治理、观测、降本。核心：**把 Agent 开发从"各自写代码"变成"平台上装配"**（参见 [ARC-045](#arc-045)、[ARC-051](#arc-051)）。

**【深入拆解】**
- **全生命周期工具链**：编排（可视化/低代码）→ Prompt 仓库 → 工具中心 → RAG 管理 → 调试评测 → 发布灰度 → 监控运维。
- **降低门槛**：业务开发者拖拽/配置即可搭 Agent，复用平台的模型、工具、知识、可观测。
- **统一治理红利**：所有业务 Agent 天然接入平台的安全、评测、成本、监控体系。

| 阶段 | 平台提供 |
|---|---|
| 开发 | 可视化编排 + Prompt 仓库 + 工具中心 |
| 知识 | RAG 知识管理 |
| 验证 | 调试 + 评测流水线 |
| 上线 | 灰度/AB + 回滚 |
| 运维 | 全链路可观测 + 成本核算 |

**相关知识点：** Tool Hub、RAG、Prompt Engineering、可观测性、评测体系、成本治理、灰度发布、Agent Architecture。

### ARC-059 · Agent 平台如何支持私有化部署？

> 稳定 ID：`ARC-059`｜原题号：59

**【核心思路】**
架构上做到**可移植 + 可配置 + 依赖解耦**。**模型层**支持接入私有化/开源模型（vLLM 部署本地模型），不硬依赖公有云 API；**基础设施**容器化（Docker/K8s）一键部署，中间件（向量库、Redis、DB）可替换为客户环境；**配置化**开关功能与外部依赖；**离线能力**（无外网时可运行）；**安全合规**（数据不出域）。核心：**架构无云厂商锁定，模型与依赖可替换，数据本地化**。

**【深入拆解】**
- **模型**：抽象模型网关，公有云/私有化模型可切换。
- **部署**：容器化 + Helm/编排，适配客户 K8s。
- **数据合规**：全部数据本地存储、可审计、满足等保/行业合规。

| 维度 | 可移植设计 |
|---|---|
| 模型 | 抽象网关，公有云/私有化/开源可切换 |
| 部署 | 容器化 + K8s/Helm 一键部署 |
| 中间件 | 向量库/Redis/DB 可替换客户环境 |
| 配置 | 功能与外部依赖开关化 |
| 合规 | 数据不出域 + 离线可运行 + 审计 |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** 模型网关、vLLM、API、Docker、K8s、Agent Architecture。

### ARC-061 · 多业务共享 RAG 平台时如何进行数据隔离？

> 稳定 ID：`ARC-061`｜原题号：61

**【核心思路】**
**租户/权限标签 + 检索过滤**：每条知识 chunk 打上**租户 ID + 权限标签（部门/角色/密级）**，检索时**先按租户强隔离**，再按用户权限过滤召回结果（**行级/文档级过滤**）。高敏感场景**物理分库**。确保**跨租户零泄露**、租户内**按权限可见**，全程审计（参见 [ARC-047](architecture.md#arc-047)、[ARC-055](reliability.md#arc-055)）。

**【深入拆解】**
- **标签先行**：每条 chunk 打租户 ID + 权限标签（部门/角色/密级），是隔离的元数据基础。
- **两级过滤**：检索时先按租户强隔离（跨租户零召回），再按用户权限做行/文档级过滤。
- **分级隔离**：普通业务逻辑隔离（共享库 + 标签），高敏感数据物理分库，全程审计。

| 层次 | 机制 | 强度 |
|---|---|---|
| 租户隔离 | 租户 ID 过滤 | 强（零泄露） |
| 权限过滤 | 标签 + 行/文档级 | 细粒度可见性 |
| 高敏感 | 物理分库 | 最强 |
| 审计 | 召回留痕 | 可追溯 |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** RAG、检索、权限控制、多租户、Agent Architecture。

### ARC-063 · 大规模 Agent 平台如何实现高可用和容灾？

> 稳定 ID：`ARC-063`｜原题号：63

**【核心思路】**
**消除单点 + 冗余 + 降级 + 多活**。**无状态化 Runtime + 状态外置**支持任意实例接管（[ARC-036](architecture.md#arc-036)）；**多副本 + 负载均衡 + 自动扩缩**；**模型多厂商互备**（主故障切备用，[ARC-039](architecture.md#arc-039)）；**依赖故障熔断降级**（大模型不可用→缓存/规则/兜底，[ARC-038](reliability.md#arc-038)）；**多可用区/多活容灾**，异地冗余；**限流削峰**防雪崩（[ARC-066](#arc-066)）。配套健康检查、故障自愈、演练。核心：**任何单一组件挂掉，系统整体仍可用或优雅降级**。

**【深入拆解】**
- **消单点**：无状态化 + 状态外置，任意实例可接管，无有状态单点（[ARC-036](architecture.md#arc-036)）。
- **冗余多活**：多副本 + 负载均衡 + 多可用区/多活容灾，异地冗余抗机房级故障。
- **优雅降级**：模型/依赖故障时降级到缓存/规则/兜底而非报错，限流削峰防雪崩（[ARC-066](#arc-066)）。

| 层面 | 手段 |
|---|---|
| 计算 | 无状态 + 多副本 + 自动扩缩 |
| 模型 | 多厂商互备降级 |
| 依赖 | 熔断 + 降级 + 兜底 |

### ARC-066 · 千万用户并发下，模型调用链路如何做限流和削峰？

> 稳定 ID：`ARC-066`｜原题号：66

**【核心思路】**
**限流**：网关层**令牌桶/漏桶**按租户/用户/全局多级限流，保护后端与模型配额。**削峰**：突发流量转**消息队列异步排队**处理，配**优先级队列**（付费/关键优先）；后端过载**熔断降级**（返回排队提示/兜底）。叠加**缓存**吸收重复请求、**批处理**提吞吐。核心：**把尖峰流量削平成后端可承受的平稳流量**（详见 [ARC-004](#arc-004)）。

**【深入拆解】**
- **限流（挡住）**：令牌桶/漏桶在网关按全局/租户/用户多级限流，保护后端与模型配额。
- **削峰（缓冲）**：突发流量入消息队列异步排队，配优先级队列（付费/关键优先），平滑后端压力。
- **兜底（降级）**：后端过载时熔断降级，返回排队提示/兜底答案，而非雪崩。

| 手段 | 作用 | 位置 |
|---|---|---|
| 令牌桶限流 | 挡住超额请求 | 网关 |
| MQ 异步削峰 | 缓冲尖峰 | 队列 |
| 优先级队列 | 保关键业务 | 队列 |
| 熔断降级 | 防雪崩 | 后端 |
| 缓存/批处理 | 减压/提吞吐 | 全链路 |

**相关知识点：** 多租户、任务调度、Agent Architecture。

### ARC-067 · 如何设计模型网关支持多模型路由和降级？

> 稳定 ID：`ARC-067`｜原题号：67

**【核心思路】**
模型网关统一接入多模型，**路由**按复杂度/能力/成本/负载选模型，**降级**在主模型故障/超时/限流时自动切备用模型或降级方案，配熔断、缓存、限流、Token 计量、可观测。核心是**对业务透明的多模型互备与智能调度**（同 [ARC-039](architecture.md#arc-039)、[ARC-049](architecture.md#arc-049)）。

**【深入拆解】**

| 熔断 | 错误率超阈 | 快速失败 + 半开探测 |
| 透明性 | — | 业务无感知 |

### ARC-076 · 平台如何做灰度发布和 A/B 实验？

> 稳定 ID：`ARC-076`｜原题号：76

**【核心思路】**
建**流量分桶 + 版本路由 + 指标对比**机制。**灰度**：新版本（模型/Prompt/Agent）先放**小流量**，按用户/租户/比例分桶，监控指标不劣化再逐步放量，异常**一键回滚**。**A/B 实验**：并行运行多版本，随机分流，对比**成功率/满意度/成本**等指标做统计显著性检验，择优全量。核心：**变更可控上线、数据驱动决策、异常快速回滚**。

**【深入拆解】**
- **分桶**：按用户 ID hash/租户/比例，保证同用户体验一致。
- **指标**：业务指标 + 系统指标对比，统计显著性。
- **回滚**：Prompt/模型版本化（[ARC-052](architecture.md#arc-052)）支持秒级回退。

| 机制 | 做法 |
|---|---|
| 分桶 | 按用户 ID hash/租户/比例，保证体验一致 |
| 灰度 | 小流量→监控→逐步放量→异常回滚 |
| A/B | 多版本随机分流 + 指标显著性检验 |
| 指标 | 成功率/满意度/成本对比 |
| 回滚 | 版本化支持秒级回退 |

**相关知识点：** Prompt Engineering、多租户、成本治理、灰度发布、Agent Architecture。
