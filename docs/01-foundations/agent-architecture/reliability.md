### 工具调用失败时，系统如何区分是参数错误还是工具本身不可用？

**【核心思路】**
靠**错误分类（Error Taxonomy）+ 来源分层 + 可重试标记**。参数错误通常在本地Schema或服务端业务校验阶段暴露；工具不可用包括连接失败、超时、服务过载和部分5xx。HTTP状态码只能辅助判断，不能用“所有4xx=参数错、所有5xx=可重试”替代语义分类。

**【深入拆解】**
- **判定依据**：调用前做JSON Schema与业务前置校验；调用后读取结构化错误的`category`、`retryable`、`retryAfter`和业务码。可复现性只是补充证据，不能通过盲目换参探测生产接口。
- **常见类别**：400/422可能是参数；401/403是认证/授权；404可能是资源不存在或路径错误；409是冲突；429是限流；5xx中502/503/504常可有限重试，而确定性500也可能持续复现。
- **不同处置**：参数错误只在约束内修正；认证/权限错误停止或刷新凭据；冲突需重新读取状态；429遵守`Retry-After`；瞬时网络/服务错误才做带抖动退避重试，之后降级或熔断。
- **写操作护栏**：只有幂等或带幂等键的调用才能安全自动重试；未知提交状态先查询后置条件，避免重复副作用。

| 维度 | 参数错误 | 工具不可用 |
|---|---|---|
| 典型信号 | Schema/422/业务校验 | 连接失败、503/504、超时 |
| 是否重试 | 修参后才可重试 | 仅可重试类别且有上限 |
| 特殊情况 | 401/403/404/409不是普通参数错 | 500不保证瞬时可恢复 |
| 处置 | 修参、停止或重读状态 | 退避、降级、熔断 |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** Tool Calling、Retry、权限控制、故障恢复、Agent Architecture。

### 权限分级的具体判定依据是什么（操作类型、数据敏感度、用户角色）？

**【核心思路】**
采用**多维度组合判定**：以 **RBAC/ABAC** 为骨架，综合三个维度——**操作类型**（读 < 写 < 删除 < 执行，破坏性越强权限越高）、**数据敏感度**（公开 < 内部 < 机密 < 个人隐私）、**用户角色**（访客 < 普通 < 管理员）。最终权限 = 三者交叉的**最小授权**，高危操作叠加**人工审批**。

**【深入拆解】**
- **操作类型维度**：只读操作低风险可放开；写/删/执行命令/发消息等**不可逆或外发**的操作需高权限 + 确认。
- **数据敏感度维度**：涉及 PII/机密数据的调用要脱敏、审计、限访问范围。
- **用户角色维度**：RBAC 按角色授权；更细的场景用 **ABAC**（按属性动态判定，如"仅本部门数据"）。
- **组合与兜底**：三维交叉取**最小权限原则**；命中高危组合（管理员删机密数据）触发**人工审批 + 全程审计日志**。
- **Agent 特有**：Agent 代表用户行事，需做**权限透传/降权**——Agent 不能拥有超过发起用户的权限。

| 维度 | 分级（低→高风险） | 处置 |
|---|---|---|
| 操作类型 | 读→写→删→执行 | 高危需确认 |
| 数据敏感度 | 公开→内部→机密→PII | 脱敏 + 审计 |
| 用户角色 | 访客→普通→管理员 | RBAC/ABAC |

**相关知识点：** 权限控制、RBAC、ABAC、PII、Agent Architecture。

### 成功/失败判定是基于规则还是引入了 LLM 作为 Judge？

**【核心思路】**
**二者结合、分场景用**。**结构化、可枚举、有明确标准**的结果用**规则判定**（快、稳、零成本，如"是否返回了合法 JSON""测试是否通过"）；**开放式、语义化、无固定答案**的结果用 **LLM-as-Judge**（灵活，能评"回答是否有帮助/准确"）。生产上常**规则先过硬性门槛，LLM Judge 评软性质量**，关键场景再叠加人工抽检。

**【深入拆解】**
- **规则判定**：适合有 ground truth 或可程序化校验的（格式、数值、测试红绿、关键字命中）。优点：确定、便宜、可复现。
- **LLM-as-Judge**：适合语义质量评估（相关性、连贯性、事实性）。优点：灵活贴近人判。缺点：**有成本、有偏差（位置偏好/自我偏好）、不稳定**，需用打分 rubric、pairwise 比较、多次投票降方差。
- **组合范式**：**规则做门禁**（不过直接失败）→ **LLM Judge 做质量分** → 高价值场景**人工兜底**。

| 方式 | 适用 | 优点 | 缺点 |
|---|---|---|---|
| 规则 | 结构化/可校验 | 快/稳/免费 | 不灵活 |
| LLM-as-Judge | 开放/语义 | 灵活近人判 | 有成本/偏差 |
| 人工 | 高价值抽检 | 最准 | 慢/贵 |

**相关知识点：** 评测体系、成本治理、LLM、Judge、JSON、Agent Architecture。

### 如何评估整个 Agent 系统的端到端可靠性（SLA、成功率指标）？

**【核心思路】**
从**业务成功率**和**系统可用性**两条线立指标。业务线：**任务成功率**（端到端完成率）、**首次成功率**、**步骤级正确率**、**幻觉率**、**人工介入率**。系统线：**可用性 SLA**（如 99.9%）、**P95/P99 延迟**、**错误率**、**降级率**。用**离线回归评测集** + **在线监控/采样评测** + **用户反馈**三路交叉验证。

**【深入拆解】**
- **端到端 vs 步骤级**：既看最终任务是否达成（用户视角），也看每步工具调用/决策正确率（定位瓶颈）。
- **可靠性指标体系**：成功率、延迟分位、可用性、降级/熔断触发率、Token 成本/请求。
- **评测方式**：**离线**——固定回归集跑分防退化（结合[ARC-024](#arc-024)规则 + Judge）；**在线**——采样 + LLM Judge + 用户点赞/投诉；**影子/AB**——新版本灰度对比（[ARC-076](platform.md#arc-076)）。
- **SLA 落地**：定义可用性目标、告警阈值、错误预算。

| 类别 | 指标 |
|---|---|
| 业务可靠性 | 任务成功率/首次成功率/幻觉率/人工介入率 |
| 系统可靠性 | 可用性 SLA/P95-P99 延迟/错误率/降级率 |
| 评测方式 | 离线回归 + 在线采样 + AB + 用户反馈 |

**相关知识点：** Tool Calling、可靠性、幻觉治理、评测体系、成本治理、灰度发布、Agent Architecture。

<a id="arc-038"></a>
### Tool Calling 如何做失败重试和降级？

**【核心思路】**
流程：**先归因**（[ARC-020](#arc-020)：参数错→LLM 改参重试；工具不可用→按下述容错）→ **指数退避 Retry**（带抖动、最大次数）→ 仍失败则**降级**（切换备用工具/降级方案/返回兜底）→ 反复失败触发**熔断**（暂时摘除该工具，避免雪崩）并**上报/Replan**。全程**幂等性保障**（重试不产生副作用）。

**【深入拆解】**
- **重试**：仅对**可重试错误**（超时/5xx/限流）退避重试；参数错不盲目重试。
- **降级**：主工具挂了用备用（如主搜索引擎→备用）、或返回缓存/兜底答案。
- **熔断**：错误率超阈值打开熔断器，快速失败保护系统，半开探测恢复。
- **幂等**：写操作重试要保证不重复执行（幂等键）。

| 阶段 | 触发条件 | 动作 |
|---|---|---|
| 归因 | 参数错 / 工具不可用（[ARC-020](#arc-020)） | 分流处置 |
| 重试 | 可重试错（超时/5xx/限流） | 指数退避 + 幂等 |
| 降级 | 重试无效 | 切备用工具/兜底 |
| 熔断 | 错误率超阈 | 摘除工具 + 上报/Replan |

**相关知识点：** Tool Calling、Replanning、Retry、故障恢复、Agent Architecture。

### 如何实现 Agent 全链路可观测与调试？

**【核心思路】**
建立 **Tracing + Metrics + Logging** 三支柱并增加Agent语义。每次会话生成Trace，记录经过脱敏的输入版本、**可审计的决策摘要**、工具调用与参数摘要、观察结果、Token、耗时和状态转移。用OpenTelemetry或Agent观测平台做步骤级回放。目标是复现外部行为与证据链，不是采集隐藏思维链。

**【深入拆解】**
- **Trace（最关键）**：以会话为根Span，每步为子Span，串起计划/决策摘要、Action、Observation和状态变化，说明“基于哪些外部证据做了什么”。
- **Metrics**：成功率、延迟分位、Token/成本、工具调用分布、错误/降级率。
- **Logging**：结构化日志按数据等级保存；Prompt/Response原文只有在合法、必要且脱敏后才采集，并设置访问与保留期限。
- **调试**：步骤级回放、断点、对比不同运行、prompt diff。

| 支柱 | 内容 | 工具 |
|---|---|---|
| Tracing | 步骤级决策链 | OTel/LangSmith/Langfuse |
| Metrics | 成功率/延迟/成本 | Prometheus/Grafana |
| Logging | 结构化 + 脱敏原文 | ELK |

**相关知识点：** Tool Calling、Chain-of-Thought、Prompt Engineering、可观测性、成本治理、Agent Architecture。

### 多业务场景下如何实现权限隔离？

**【核心思路】**
**租户 + RBAC/ABAC 双层**：租户级隔离数据与资源边界（跨租户绝不可见），租户内用 RBAC/ABAC 控制用户对功能/数据的访问。Agent 调用时**透传发起者身份**，RAG 召回按**权限标签过滤**（[ARC-069](#arc-069)），工具调用按角色鉴权。全链路**租户 ID + 用户身份**贯穿，审计留痕（参见 [ARC-022](#arc-022)、[ARC-048](platform.md#arc-048)）。

**【深入拆解】**
- **租户层（强隔离）**：跨租户数据绝不可见，租户 ID 贯穿请求、存储、缓存、日志。
- **用户层（细粒度）**：租户内用 RBAC/ABAC 控制功能与数据访问，Agent 权限不超过发起用户。
- **落地关键**：身份透传 + RAG 召回按权限标签过滤 + 工具按角色鉴权 + 全程审计。

| 层次 | 隔离机制 | 粒度 |
|---|---|---|
| 租户级 | 命名空间/租户 ID 贯穿 | 强隔离、不可见 |
| 用户级 | RBAC/ABAC | 功能/数据可见性 |
| 召回级 | 权限标签过滤 | 行/文档级 |
| 审计 | 全链路留痕 | 可追溯 |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** Tool Calling、RAG、检索、权限控制、多租户、Agent Architecture。

### RAG 知识库如何支持实时更新和权限隔离？

**【核心思路】**
**实时更新**：增量索引 pipeline——文档变更触发**增量 embedding + 索引更新**（近实时），配版本管理与失效清理，避免全量重建；热数据可加缓存。**权限隔离**：chunk 带**租户 + 权限标签**，检索时**元数据过滤 + 行级权限**控制召回可见性（[ARC-055](#arc-055)）。核心：**知识新鲜可控 + 召回按权限可见**（参见 [ARC-061](platform.md#arc-061)）。

**【深入拆解】**
- **实时更新**：文档变更触发增量 embedding + 索引更新（近实时），配版本管理与失效清理，避免全量重建。
- **权限隔离**：chunk 带租户/权限标签，检索时元数据 + 行级过滤，只召回有权访问的内容。
- **工程权衡**：实时性 vs 索引成本——热数据近实时 + 缓存，冷数据批量更新。

| 能力 | 手段 |
|---|---|
| 实时更新 | 增量索引 + 版本 + 失效清理 |
| 权限隔离 | 租户/权限标签 + 检索过滤 |
| 性能 | 热数据缓存 + 冷数据批更 |

**相关知识点：** RAG、Embedding、检索、权限控制、多租户、成本治理、Agent Architecture。

### 长任务失败后如何实现断点续跑？

**【核心思路】**
前提是**状态外置 + Checkpoint**：任务拆成可跟踪子步骤，每步完成**持久化进度与上下文快照**；失败后从**最近成功的 Checkpoint 恢复**，重放剩余步骤（写操作要**幂等**防重复副作用）。配合**失败归因**（[ARC-020](#arc-020)）决定续跑/重试/Replan。核心：**把长任务变成可从任意断点恢复的分步过程**（参见 [ARC-036](architecture.md#arc-036)、[ARC-043](runtime-harness.md#arc-043)）。

**【深入拆解】**
- **前提**：状态外置 + 每步 Checkpoint（进度 + 上下文快照），否则无从恢复。
- **恢复**：从最近成功检查点重放剩余步骤，已完成的不重做。
- **幂等关键**：写操作（下单/发消息）必须幂等，否则重放产生重复副作用；用幂等键去重。
- **归因决策**：恢复前先归因——环境错→续跑重试，计划错→Replan（[ARC-020](#arc-020)、[ARC-025](architecture.md#arc-025)）。

| 环节 | 做法 |
|---|---|
| 前提 | 状态外置 + 分步 Checkpoint |
| 恢复 | 从最近检查点重放剩余步 |
| 幂等 | 写操作幂等键去重 |
| 归因 | 续跑/重试/Replan 分流 |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** Harness Engineering、Agent Runtime、Checkpoint、Replanning、Retry、故障恢复、Agent Architecture。

### 企业知识库权限如何和 Agent 结合？

**【核心思路】**
Agent 召回知识时**透传发起用户身份**，RAG 检索**按用户权限标签过滤**（行级/文档级），**只返回该用户有权访问的知识**，绝不越权召回。工具/数据访问同样按角色鉴权（[ARC-022](#arc-022)）。即"**Agent 的可见范围 = 发起用户的权限范围**"，全程审计。核心：**权限透传 + 召回过滤 + 最小权限 + 审计**（参见 [ARC-055](#arc-055)、[ARC-061](platform.md#arc-061)）。

**【深入拆解】**
- **权限透传**：Agent 代表用户行事，调用时透传发起者身份，不能拥有超过用户的权限。
- **召回过滤**：RAG 检索按用户权限标签做行/文档级过滤，只返回有权访问的知识（[ARC-061](platform.md#arc-061)）。
- **全程审计**：谁在什么时候访问了什么知识全部留痕，满足合规审查。

| 环节 | 机制 |
|---|---|
| 身份 | 透传发起用户 |
| 召回 | 权限标签过滤（行/文档级） |
| 工具/数据 | 按角色鉴权（[ARC-022](#arc-022)） |
| 边界 | Agent 可见 = 用户权限 |
| 审计 | 访问留痕 |

**验证指标：** 端到端任务成功率、P95 延迟、单任务成本、人工接管率和故障恢复率。

**相关知识点：** RAG、检索、权限控制、Agent Architecture。

### 如何评估 Agent 最终任务完成质量？

**【核心思路】**
**多维度评判**：**完成度**（是否达成目标）、**正确性**（结果对不对）、**过程合理性**（步骤是否高效无冗余）、**用户满意度**。方法：**规则校验硬指标**（有 ground truth 的）+ **LLM-as-Judge 评语义质量**（开放式）+ **人工抽检高价值场景**。用固定评测集离线跑分 + 在线采样评估。核心：**结果 + 过程 + 体验多维，规则与 Judge 结合**（参见 [ARC-024](#arc-024)、[ARC-027](#arc-027)）。

**【深入拆解】**
- **多维评判**：完成度（达成目标）、正确性（结果对）、过程合理性（步骤高效无冗余）、用户满意度。
- **方法组合**：有 ground truth 的用规则校验，开放式质量用 LLM-as-Judge，高价值场景人工抽检（[ARC-024](#arc-024)）。
- **离线 + 在线**：固定评测集防退化，在线采样反映真实分布。

| 维度 | 评判方式 |
|---|---|
| 完成度/正确性 | 规则校验（有标准答案） |
| 语义质量 | LLM-as-Judge |
| 过程合理性 | Trace 分析步骤 |
| 满意度 | 用户反馈 |
| 高价值 | 人工抽检 |

**相关知识点：** 可观测性、评测体系、ground、truth、LLM-as-Judge、Agent Architecture。

### 如何控制 Agent 调用成本和 Token 消耗？

**【核心思路】**
杠杆：**缓存复用、小模型分流、Context 压缩裁剪、精准 RAG 召回、减少无效循环步骤（护栏防死循环）、批处理、成本计量治理**。Agent 特有——**控制 Loop 步数**（每步都烧 Token）、**裁剪工具大返回**。核心：**少调用、少 Token、用对模型、控步数**（同 [ARC-017](architecture.md#arc-017)、[ARC-032](#arc-032)、[ARC-071](#arc-071)）。

**【深入拆解】**
- **通用杠杆**：缓存复用、小模型分流、Context 压缩、精准 RAG、批处理（[ARC-071](#arc-071)）。
- **Agent 特有杠杆**：控制 Loop 步数——每步都要调模型烧 Token，护栏防死循环/无效循环；裁剪工具大返回防上下文膨胀。
- **治理**：Token 计量到会话/任务，暴露单任务平均步数、平均成本等指标持续优化。

| 杠杆 | 手段 | 归属 |
|---|---|---|
| 缓存/分流/压缩 | 复用 + 小模型 + 精准召回 | 通用 |
| 控步数 | 护栏防死循环/无效循环 | Agent 特有 |
| 裁剪返回 | 工具大返回摘要 | Agent 特有 |
| 计量治理 | 单任务步数/成本监控 | 治理 |

**相关知识点：** RAG、检索、成本治理、Token、Context、Agent Architecture。

### 如何实现 Agent 全链路可观测和问题定位？

**【核心思路】**
建 **Trace + Metrics + Logging** 三支柱，会话级 Trace 记录每步（上下文/决策/工具/观察/Token/耗时/状态），支持**步骤级回放下钻**；配指标告警与变更关联，快速归因。核心：**让多步黑盒决策可复现、可回放、可归因**（同 [ARC-042](#arc-042)、[ARC-077](architecture.md#arc-077)）。

**【深入拆解】**
- **三支柱**：Trace（步骤级决策链，最关键）+ Metrics（成功率/延迟/成本）+ Logging（结构化脱敏原文）。
- **Agent 语义化**：Trace要能还原每一步的计划/决策摘要、工具调用、外部证据与状态变化，而非通用请求日志；隐藏思维链不作为审计依据。
- **快速定位**：告警下钻 + 变更关联 + 相似 case 聚类，从现象到根因（[ARC-077](architecture.md#arc-077)）。

| 支柱 | 内容 | 用途 |
|---|---|---|
| Tracing | 步骤级决策链 | 回放归因 |
| Metrics | 成功率/延迟/成本 | 告警趋势 |
| Logging | 脱敏原文 | 复盘取证 |
