# 第一部分 · 核心问题（9 题）

## （一）架构设计与模块边界

#### 1、如果让你从 0 到 1 设计一个企业级 Agent，你会如何设计整体架构？（DeepSeek 一面）
**【核心思路】**
分层解耦，自底向上五层：模型接入层、Runtime 核心层、上下文与记忆层、工具能力层、治理层。核心原则：规划与执行分离、状态外置、Runtime 无状态化、工具标准化、全链路可观测。

**【深入拆解】**
- **第一性原理**：LLM 是一个**不确定的概率系统**，工程要做的是用**确定性的 Harness 把它包起来**——控制它的输入（Context）、约束它的输出（结构化/Schema）、兜底它的失败（重试/降级）。分层的本质是**隔离变化**：模型会换、工具会增、业务会变，分层让每层独立演进，避免牵一发动全身。
- **模型接入层何时需要网关**：少量模型和低流量场景可先直连SDK；当多团队、多Provider或统一治理需求出现时，引入网关集中做路由、限流、计量、观测和符合条件的故障降级。网关本身也会增加延迟与故障面，语义缓存只适合可安全复用且有质量校验的请求。
- **Runtime 层——规划与执行为什么分离**：规划需要**强推理模型**（贵、慢），执行可用便宜模型甚至规则；分离后可独立优化、独立扩缩容；Planner 产出的计划**可审计、可人工介入**。
- **上下文与记忆层是核心竞争力**：Context Engineering ≠ 固定模板，而是**动态组装**——按相关性召回、按 Token 预算裁剪、按重要性压缩。短期记忆（对话 buffer）与长期记忆（向量库 + 知识图谱）分治。
- **治理层是企业级的命脉**：Demo 和生产的本质差距就在这层——可观测（每步 Trace 便于复盘）、评测（离线回归 + 在线监控）、安全（注入检测/输出脱敏/权限分级）、成本核算。
- **状态外置的连锁价值**：状态外置 → Runtime 无状态 → 既能水平扩展，又能断点恢复（实例挂了换一台从 Checkpoint 续跑）。

| 层级 | 核心职责 | 为什么需要（失败后果） |
|---|---|---|
| 模型接入层 | 路由/降级/限流/缓存 | 无网关→厂商锁定、无法降级、成本失控 |
| Runtime 核心层 | Agent Loop、规划/执行分离 | 不分离→无法审计、难扩展 |
| 上下文与记忆层 | Context 组装、短/长期记忆 | 组装差→幻觉、Token 爆炸 |
| 工具能力层 | Tool Hub、MCP 标准接入 | 不标准→每个工具重复对接 |
| 治理层 | 可观测/评测/安全/成本 | 缺失→线上黑盒、无法定位、合规风险 |

#### 2、一个 Agent 系统应该拆分成哪些核心模块？每个模块分别负责什么？（DeepSeek 一面）
**【核心思路】**
按职责拆九模块：意图理解、规划器、执行器、工具层、记忆层、上下文管理、模型网关、安全权限、可观测评测。原则是**高内聚低耦合，按"职责边界"而非"技术栈"拆分**。

**【深入拆解】**
- **意图理解的深水区**：多轮对话里最难的是**指代消解**（"把它删了"里的"它"）与**意图漂移检测**（用户中途改需求）。工程上靠"改写式召回"——用 LLM 把当前轮结合历史改写成独立完整的 query，再做检索与规划。
- **Planner 内部机制**：任务分解有两种策略——**自顶向下**（一次性拆成 DAG，适合结构清晰任务）与**递归/动态分解**（走一步看一步，适合探索性任务）。关键设计是**是否支持 Replan**：计划执行不下去时能否重新规划。
- **Executor 内部机制**：驱动 Agent Loop，核心是三件事——**工具选择**（选哪个工具）、**参数生成**（Function Calling 结构化输出）、**结果解析**（把工具返回喂回上下文）。
- **Memory 的三层认知**：借鉴人类记忆——**工作记忆**（当前对话 buffer）、**情景记忆**（历史事件/会话）、**语义记忆**（沉淀的知识/事实）。三者存储与召回策略不同。
- **模块间通信**：大型系统用**事件驱动/黑板模式**（共享状态）而非硬编码直接调用，便于解耦与异步。
- **为什么要模块化（本质）**：可测试、可替换、可复用、支持团队并行开发——**康威定律**下，模块边界最终会映射团队边界。

| 模块 | 职责 | 内部关键机制 |
|---|---|---|
| 意图理解 | 意图识别、指代消解 | 历史改写、槽位填充 |
| 规划器 Planner | 任务拆解、Replan | DAG 分解/递归分解 |
| 执行器 Executor | Agent Loop 驱动 | 工具选择/参数生成/解析 |
| 工具层 Tool Hub | 能力封装 | Schema 定义、MCP 协议 |
| 记忆层 Memory | 短/长期记忆 | 工作/情景/语义三层 |
| 上下文管理 | Prompt 组装/压缩 | 召回 + 裁剪 + 摘要 |
| 模型网关 | 多模型路由降级 | 负载/成本路由、熔断 |
| 安全权限 | 鉴权/脱敏/防注入 | RBAC、注入检测 |
| 可观测评测 | Trace/打分 | 全链路埋点、Eval |

#### 3、一个企业级 Agent 系统应该拆分成哪些核心模块？规划器、执行器、工具层及记忆层和评测层如何协作？（腾讯二面）
**【核心思路】**
五大件（规划器/执行器/工具层/记忆层/评测层）构成一条**闭环**：规划器拆任务 → 执行器驱动 Loop 调工具 → 结果入记忆并回灌 → 评测层打分 → 失败触发 Replanning。本质是"大脑—手脚—工具—记忆—考官"的分工。

**【深入拆解】**
- **三条流看清协作**：①**控制流**——谁触发谁（规划器→执行器→工具，评测器可回弹到规划器）；②**数据流**——结果传递（工具结果→记忆→上下文→下一轮 Prompt）；③**状态流**——任务状态机流转（Pending→Running→Success/Failed/NeedReplan）。
- **规划器与执行器的交互协议**：计划下发（子任务 + 依赖）、进度回报（每步结果）、异常上报（哪步失败、为什么）。这套协议是 Multi-Agent 的基础。
- **评测层的双重角色**：**过程评测**（每步做 Guard，比如工具参数校验、结果合理性）+ **结果评测**（终点做 Judge，判断任务是否真完成）。选型上，**结构化/可枚举结果用规则**（快、便宜、稳定），**开放式/语义结果用 LLM-as-Judge**（灵活但有成本和偏差）。
- **Replan vs Retry 的边界**（高频追问）：**计划本身错了**（工具选错、路径走不通）→ Replanning；**执行偶发失败**（超时、限流、网络抖动）→ Retry。误判会导致要么无脑重试撞墙，要么频繁重规划浪费成本。
- **记忆污染问题**：错误的中间结果一旦写入记忆，会**误导后续所有决策**。需给记忆打**可信度/来源标记**，评测失败的结果不进长期记忆。

| 层 | 输入 | 输出 | 反馈对象 | 关键机制 |
|---|---|---|---|---|
| 规划器 | 目标 + 记忆 + 评测反馈 | 子任务 DAG | → 执行器 | 分解/Replan |
| 执行器 | 子任务 + 上下文 | 工具调用 | → 工具层/记忆 | Agent Loop |
| 工具层 | 参数 | 执行结果 | → 执行器 | 幂等/超时 |
| 记忆层 | 每步结果 | 历史/上下文 | → 规划/执行 | 可信度标记 |
| 评测层 | 中间/最终结果 | 分数 + 反馈 | → 规划器 | 规则 + LLM Judge |

#### 4、如果让你从 0 到 1 设计一个面向千万用户的大模型应用平台，你会如何划分整体架构？（腾讯二面）
**【核心思路】**
在 Agent 架构之上，重心从"能力"转向"**规模化稳定 + 成本可控**"。强化：网关限流削峰、Runtime 无状态弹性扩展、多租户隔离、存储分层、灰度与可观测治理。本质是把**确定性工程能力包在不确定的大模型外面**。

**【深入拆解】**
- **限流削峰的具体手段**：网关层**令牌桶限流**保护后端；突发流量用**消息队列（MQ）异步削峰**，把同步请求转排队；设**优先级队列**（付费用户/关键业务优先）；后端过载时**熔断降级**（返回兜底答案或排队提示）。
- **缓存三级策略**（省钱关键）：**精确缓存**（相同 query 直接返回）+ **语义缓存**（向量匹配相似 query）+ **前缀缓存/KV Cache 复用**（相同 System Prompt 复用计算）。缓存命中率直接决定成本。
- **无状态化的实现**：会话状态、任务状态外置到 **Redis/DB**，Runtime 实例本身不存状态，从而可**任意水平扩缩容**，某实例宕机不影响会话（换实例从状态恢复）。
- **多租户隔离三维度**：**计算隔离**（配额/限流按租户）、**数据隔离**（逻辑分库或物理隔离，RAG 知识库带租户标签过滤）、**模型隔离**（大客户专属实例，小客户共享池）。
- **成本核算**：按 Token 计量到租户/业务线，缓存命中优化、小模型分流（简单任务走便宜模型）。
- **高可用**：多活容灾、无单点、**优雅降级**（大模型不可用时降级到规则/缓存/兜底文案，而非直接报错）。
- **流式输出稳定性**：SSE/WebSocket 长连接管理、背压处理、断线重连与续传。

| 维度 | 单 Agent 架构 | 千万级平台架构 |
|---|---|---|
| 首要目标 | 任务正确性 | 规模稳定 + 成本 |
| 流量治理 | 直连模型 | 令牌桶限流 + MQ 削峰 + 熔断 |
| 缓存 | 可选 | 精确 + 语义 + KV 三级 |
| 计算 | 单实例 | 无状态 + 弹性扩缩 |
| 隔离 | 无 | 计算/数据/模型多租户 |
| 可靠性 | 尽力而为 | 多活容灾 + 优雅降级 |
| 成本 | 不敏感 | Token 计量 + 分摊 + 小模型分流 |

#### 5、腾讯如果要把大模型能力同时接入不同产品，不同产品之间应该如何划分职责？（腾讯二面）
**【核心思路】**
"**AI 中台 + 业务层**"分工：中台沉淀通用能力（模型网关、Tool Hub、RAG 底座、Prompt 仓库、Eval、安全），业务层负责场景个性（业务 Prompt、编排、领域工具、数据）。原则：**通用 + 稳定 + 规模效应下沉中台，个性 + 多变 + 强耦合留业务层**。

**【深入拆解】**
- **康威定律视角**：架构会映射组织。要做中台，组织上就得有独立的**平台团队**（维护共享能力）和**业务团队**（做场景），职责边界即团队边界。
- **中台边界的判断标准**：问一句"**这个能力是不是多个业务都要、且需要规模效应？**"——是（模型接入、向量库、可观测、成本核算）→ 下沉中台；否（某产品特有的业务规则、快速试错的 Prompt）→ 留业务层。
- **中台的真实陷阱**（有深度的追问点）：过度中台化会导致**响应慢、成为瓶颈、业务不买账**（"既要通用又要贴合我"）。解法是做**薄中台**——只沉淀最稳定的公共底座，把灵活性尽量下放；中台对业务是"**能力供应商**"而非"管控者"。
- **职责契约化**：中台对外暴露稳定的 **API 契约 + SLA**（可用性、延迟承诺）+ **版本兼容策略**（不能随意 breaking change 拖垮所有业务）。
- **共享下的隔离**：多业务共享 RAG/模型时，数据按租户隔离（带权限标签过滤召回）、成本按调用量分摊计费。

| 能力 | 中台（平台层） | 业务层（各产品） |
|---|---|---|
| 模型接入/路由 | ✅ 统一网关 | — |
| Tool Hub/MCP | ✅ 通用工具 | 领域专用工具 |
| RAG | ✅ 引擎 + 隔离机制 | 业务知识库内容 |
| Prompt | ✅ 仓库 + 版本管理 | 业务 Prompt 编写 |
| Agent 编排 | ✅ 引擎 | 场景编排逻辑 |
| 可观测/成本 | ✅ 全链路 + 核算 | 消费侧监控 |
| 迭代节奏 | 慢、稳 | 快、灵活 |

## （二）Agent 运行链路

#### 6、整个 Agent 是怎么运转的？从用户输入到最终完成任务，中间经历了哪些步骤？（DeepSeek 二面）
**【核心思路】**
Agent 本质是 **Agent Loop（感知→规划→行动→观察的循环）**：输入理解→上下文组装→LLM 决策→工具调用→观察回灌→循环迭代→判定完成→输出。工程上必须加最大步数、超时、错误处理等护栏。

**【深入拆解】**
- **Loop 的本质**：LLM 是"**决策器**"而不是"执行器"。单次调用只能预测一次，**Loop 把"一次预测"变成"多步自主"**——每一步基于最新观察重新决策，这就是 Agent 与普通"一问一答"的根本区别。
- **上下文组装是最关键的一步**：LLM 的决策质量完全取决于"**它看到了什么**"。这一步要拼装 System Prompt（角色/规则）+ 工具描述（能力边界）+ 历史（连续性）+ RAG 召回（外部知识）+ 当前状态，且要在 Token 预算内做取舍。这是 Context Engineering 的战场。
- **工具调用的工程细节**：靠 **Function Calling** 让 LLM 输出结构化调用（工具名 + 参数）；执行器实际执行；**观察结果要裁剪**——工具可能返回巨大内容（如整个文件、长 JSON），直接塞回会撑爆上下文，需摘要/截断/结构化提取。
- **终止条件的设计**（高频追问）：①LLM 主动判定完成（输出 final answer）；②达到**最大步数**（防死循环）；③超时；④连续失败次数超阈值。缺了护栏，Agent 会**无限循环烧钱**或**在错误里越陷越深**。
- **防失控护栏**：检测**重复动作**（同样的工具同样参数反复调 = 卡住了）、危险操作（删数据/发消息）走**人工审批**、Token 预算硬上限。

| 阶段 | 技术实现 | 关键护栏 |
|---|---|---|
| 输入理解 | 意图识别、指代消解 | 输入校验/注入检测 |
| 上下文组装 | Prompt + 工具 + 历史 + RAG | Token 预算、裁剪 |
| LLM 决策 | Function Calling | 结构化输出约束 |
| 工具调用 | Executor 执行 | 权限、超时、幂等 |
| 观察回灌 | 结果摘要/截断 | 防上下文爆炸 |
| 循环/终止 | 迭代判定 | 最大步数、防重复 |

#### 7、ReAct 加 COT 执行流程和区别（Agent 初级）
**【核心思路】**
CoT指模型通过中间推理改善复杂问题求解，本身不负责获取外部信息或执行动作；ReAct把**决策、Action与Observation**组成循环，使模型能用工具取证并根据结果调整。工程上记录可审计的计划/决策摘要、Action和Observation即可，不要求暴露隐藏思维链。

**【深入拆解】**
- **CoT的作用与边界**：分解复杂问题可能提升数学、逻辑和多跳任务表现，但自然语言推理未必忠实，知识缺失也不能靠“多想”补齐；最终答案仍需外部验证。
- **ReAct的价值**：Action取得搜索、计算或业务系统的真实Observation，再用于下一步决策，可降低只凭模型先验作答的风险。
- **工程循环**：`Decision Summary → Action(tool, args) → Observation → Validate/Continue/Final`。工具参数先校验，返回内容视为不可信数据。
- **局限**：错误观察会污染后续，循环也可能增加Token和副作用；应设置停止条件、重复动作检测、权限、预算和Verifier。

| 范式 | 核心 | 外部交互 | 循环 | 自我纠错 | 适用 |
|---|---|---|---|---|---|
| CoT | 分步推理 | ❌ | ❌ | ❌ | 数学/逻辑推理 |
| ReAct | 推理 + 行动 | ✅ | ✅ | 弱 | 通用 Agent |
| Reflexion | + 自我反思 | ✅ | ✅ | ✅ | 需迭代优化 |
| Plan-Execute | 先规划后执行 | ✅ | 局部 | 中 | 复杂长任务 |
| ToT/LATS | 树搜索多路径 | ✅ | ✅ | ✅ | 高难度决策 |

## （三）框架选型

#### 8、为什么没用 LangChain、Spring AI 这些 Agent 开发框架？（豆包一面）
**【核心思路】**
不是否定框架，而是依据**控制需求、团队能力和维护成本**选型。原型或标准Agent可优先使用成熟框架；只有当现有抽象无法满足关键的状态、Context、性能或治理需求时，才下沉到LangGraph等低层Runtime或自研薄Harness。

**【深入拆解】**
- **先做能力验证**：当前LangChain高层Agent构建在LangGraph上，可获得中间件、持久化、人在环路和耐久执行能力；Spring AI更适合已有Spring技术栈的统一模型与工具集成。不能基于旧版本印象直接判定“不支持”。
- **下沉条件**：需要自定义状态迁移、严格恢复语义、特殊调度、极细Context控制或框架无法满足的性能/SLA时，才考虑直接使用低层API或自研。
- **客观评估**：在真实任务上比较完成率、Trace可解释性、P95、升级兼容、依赖风险和总维护成本；框架开销要用Profile证明，不能凭抽象层数量推断。
- **复用边界**：模型SDK、向量库、解析、Tracing等成熟组件优先复用；自研部分保持最薄，并用契约封装以便替换。
- **版本治理**：锁定依赖、阅读迁移指南、做回归与灰度。选择框架不免除安全、评测和运维责任。

| 维度 | 用框架 | 自研 Harness |
|---|---|---|
| 上手速度 | 快（原型友好） | 慢 |
| Context 控制 | 取决于抽象层，可下沉定制 | 可完全定制 |
| 可调试/可观测 | 有现成集成，仍需验证覆盖 | 自行建设 |
| 稳定性 | 受框架迭代影响 | 自主可控 |
| 性能/依赖 | 需实测和版本治理 | 代码少但维护责任大 |
| 适用 | 标准能力、快速交付 | 明确差异化且框架不满足 |

#### 9、LangChain 和 LangGraph 的区别以及各自适用场景（Agent 初级）
**【核心思路】**
当前 LangChain 是构建 Agent 和 LLM 应用的**高层框架**，其 `create_agent` 本身构建在 LangGraph 之上；LangGraph 是面向长运行、有状态工作流的**低层编排 Runtime**。区别不是“LangChain 只能线性、LangGraph 才能做 Agent”，而是**抽象层级与控制粒度**。

**【深入拆解】**
- **LangChain**：提供模型、工具、中间件、消息和预构建 Agent 等高层接口，适合希望快速构建标准工具调用 Agent 的团队；它可通过底层 LangGraph 获得持久化、流式、人在环路和耐久执行能力。
- **LangGraph**：直接暴露 State、Node、Edge、Reducer、Checkpoint 和 Interrupt，适合需要自定义循环、分支、恢复、并行和多 Agent 协调的复杂流程。
- **简单流程**：普通 RAG、固定转换仍可用 Runnable/LCEL 或普通代码，不必为了“图”而增加状态复杂度。
- **选型**：优先用 LangChain 高层 Agent；只有需要精确控制状态迁移、执行顺序或恢复语义时再下沉 LangGraph。二者可以同时使用，不是互斥替代关系。

| 维度 | LangChain | LangGraph |
|---|---|---|
| 定位 | 高层 Agent/LLM 应用框架 | 低层状态化编排 Runtime |
| 控制粒度 | 预构建抽象与中间件 | 显式 State、Node、Edge |
| 耐久执行 | Agent 可继承 LangGraph 能力 | 直接配置 Checkpoint/Interrupt |
| 适用 | 快速构建标准 Agent | 深度定制复杂长流程 |

**官方资料：** [LangChain Overview](https://docs.langchain.com/oss/python/langchain/overview)、[LangGraph Overview](https://docs.langchain.com/oss/python/langgraph/overview)。

# 第二部分 · 扩展问题 · 架构与模块边界（78 题）

#### 10、为什么企业级 Agent 要采用分层架构？
**【核心思路】**
核心动机是**用分层隔离变化、分离关注点**，从而让"不确定的 LLM"能被"确定的工程"驯服。企业级要的是稳定、可治理、可复用、多团队协作——单体式把模型调用、业务逻辑、工具、Prompt 全糅在一起，任何一处变动都牵一发动全身。

**【深入拆解】**
- **隔离变化频率**：模型层（几个月换代）、能力/工具层（持续新增）、业务层（天天变）**变化速度完全不同**，分层让高频变动不冲击稳定内核。
- **关注点分离**：每层单一职责——网关只管接入、Runtime 只管循环、治理只管安全可观测，便于**独立优化、独立扩展、独立测试**。
- **可复用（中台前提）**：底层能力（模型接入、RAG、Tool Hub）下沉后可被多业务复用，避免重复建设。
- **可治理**：安全、权限、可观测、成本核算需要一个**统一的横切层**，分层才能集中管控。
- **康威定律**：分层边界最终映射团队边界，支持平台团队与业务团队并行开发。

| 维度 | 单体式 | 分层架构 |
|---|---|---|
| 变更影响 | 牵一发动全身 | 局部隔离 |
| 复用性 | 难 | 底层可复用 |
| 可测试 | 耦合难测 | 分层可测 |
| 治理 | 分散 | 集中横切 |
| 团队协作 | 冲突多 | 边界清晰 |

#### 11、Agent Runtime 包含哪些核心模块？
**【核心思路】**
Runtime 是"**运行时**"，负责一次 Agent 执行的**完整生命周期调度**。核心模块：Agent Loop 调度器、上下文管理器、工具执行器、记忆管理、状态管理、模型客户端（LLM Client）。它是 Platform（平台）中真正"跑起来"的引擎内核。

**【深入拆解】**
- **Agent Loop 调度器**：Runtime 的心脏，驱动"决策→行动→观察"循环，控制步数、终止、错误处理。
- **上下文管理器**：每一轮组装喂给模型的 Context（拼装、召回、裁剪、压缩），决定模型"看到什么"。
- **工具执行器**：解析 LLM 的 tool_call，实际执行工具，处理超时/重试/结果裁剪。
- **记忆管理**：短期（对话 buffer）+ 长期（向量库）读写。
- **状态管理**：任务状态机（Pending/Running/Success/Failed），状态外置以支持断点恢复。
- **模型客户端**：与模型网关对接，处理流式、Function Calling、Token 计数。
- **辨析**：Runtime（单次执行引擎）≠ Platform（含网关、多租户、治理的完整平台）；Runtime 是 Platform 的核心子集。

| 模块 | 职责 | 类比 |
|---|---|---|
| Agent Loop 调度器 | 驱动决策循环 | CPU |
| 上下文管理器 | 组装 Context | 内存/工作台 |
| 工具执行器 | 执行 tool_call | IO 设备 |
| 记忆管理 | 短/长期记忆 | 硬盘 |
| 状态管理 | 任务状态机 | 寄存器 |
| 模型客户端 | 对接 LLM | 网卡 |

#### 12、Runtime 与 Workflow Engine 有什么区别？
**【核心思路】**
**核心区别是"谁决定执行路径"**：Workflow Engine 的路径由**人预先定义**（固定 DAG，确定性、可预测）；Agent Runtime 的路径由 **LLM 运行时动态决策**（走一步看一步，灵活、自主）。前者适合标准化流程，后者适合开放式任务，二者常结合使用。

**【深入拆解】**
- **控制权归属**：Workflow 是"**编排者写死流程，引擎照着执行**"；Runtime 是"**LLM 当场决定下一步做什么**"。这是确定性与自主性的根本分野。
- **可预测性 vs 灵活性**：Workflow 结果稳定、可测试、易审计，但遇到预期外情况就走不下去；Agent 能应对开放场景，但**行为不完全可预测**，需护栏兜底。
- **最佳实践是二者结合**：用 **Workflow 编排确定的大流程骨架**，在其中"不确定的节点"嵌入 **Agent** 处理（如"审批"节点用规则、"内容生成/理解"节点用 Agent）。这兼顾可控与智能。
- **成本/延迟**：Workflow 每步确定、无额外 LLM 调用；Agent 每步都要调用模型，慢且贵——**能用 Workflow 就别用 Agent**。

| 维度 | Workflow Engine | Agent Runtime |
|---|---|---|
| 路径决定者 | 人（预定义 DAG） | LLM（动态） |
| 可预测性 | 高 | 低（需护栏） |
| 灵活性 | 低 | 高 |
| 成本/延迟 | 低 | 高（每步调模型） |
| 适用 | 标准化流程 | 开放式任务 |
| 结合方式 | 骨架编排 | 嵌入不确定节点 |

#### 13、单 Agent 与 Multi-Agent 如何选择？
**【核心思路】**
**默认单 Agent（KISS 原则）**，只有在遇到明确瓶颈时才上 Multi-Agent：任务能清晰拆成独立子域、需要不同专业角色分工、需要并行加速、或单 Agent 上下文装不下。Multi-Agent 的协调开销与成本很高，不是越多越好。

**【深入拆解】**
- **为什么默认单 Agent**：简单、可控、便宜、易调试。多数任务单 Agent + 好工具就能解决，过早上 Multi 是过度设计。
- **该上 Multi 的四个信号**：①任务可**清晰解耦**为独立子域（如"研究员 + 写作员 + 审阅员"）；②需要**异构专业角色**（不同 Prompt/工具/模型）；③子任务**可并行**且能显著提速；④单 Agent 的**上下文窗口**装不下所有信息，需要用多 Agent 做**上下文隔离**。
- **Multi 的代价（选择时的成本）**：协调/通信开销、状态一致性难、**错误跨 Agent 传播**、成本和延迟成倍、调试变黑盒。
- **判断法则**：任务**强依赖、串行、共享上下文** → 单 Agent；任务**弱耦合、可并行、需专业分工** → Multi-Agent。

| 场景特征 | 单 Agent | Multi-Agent |
|---|---|---|
| 任务耦合度 | 强依赖/串行 | 弱耦合/可并行 |
| 角色需求 | 单一 | 异构专业分工 |
| 上下文 | 装得下 | 需隔离 |
| 成本/复杂度 | 低 | 高 |
| 调试 | 容易 | 难 |
| 默认选择 | ✅ 优先 | 有明确瓶颈才用 |

#### 14、Multi-Agent 的优势和缺点是什么？
**【核心思路】**
**优势**：专业分工（关注点分离）、上下文隔离（各自独立窗口）、并行加速、模块化可扩展。**缺点**：协调通信开销大、状态一致性难、错误跨 Agent 级联、成本与延迟成倍、调试困难。适合"可并行的探索/研究类"，不适合"强依赖的串行任务"。

**【深入拆解】**
- **优势详解**：①**关注点分离**——每个 Agent 专注一个子域，Prompt 更聚焦、幻觉更少；②**上下文隔离**——每个 Agent 有独立上下文窗口，绕开单窗口容量上限（这是 Multi 最硬的价值）；③**并行**——独立子任务同时跑，缩短端到端时延；④**模块化**——可独立替换/升级某个 Agent。
- **缺点详解**：①**通信开销**——Agent 间传递信息本身消耗 Token 和延迟；②**一致性难**——多个 Agent 对同一状态的认知易冲突；③**错误级联**——上游 Agent 出错，下游全盘皆错，且更难定位；④**成本/延迟成倍**——每个 Agent 都在调模型；⑤**调试黑盒**——多方交互链路难复现。
- **业界经验**：并行的**研究/检索类**任务（多个子问题独立调研）收益大；**强依赖、需共享上下文**的任务（如连续编辑同一份代码）反而更适合单 Agent，Multi 会因协调成本得不偿失。

| 维度 | 优势 | 对应缺点 |
|---|---|---|
| 分工 | 专业聚焦、少幻觉 | 通信协调开销 |
| 上下文 | 隔离、绕开窗口上限 | 状态一致性难 |
| 执行 | 并行加速 | 错误跨 Agent 级联 |
| 成本 | — | 成倍 Token/延迟 |
| 运维 | 模块化可替换 | 调试黑盒 |

#### 15、LangGraph、AutoGen、CrewAI 等框架分别适合哪些场景？
**【核心思路】**
**LangGraph**：底层状态机图，精细控制、生产级，适合需要复杂控制流/断点/人在环路的严肃 Agent。**AutoGen**（微软）：**对话驱动**的多 Agent（Group Chat），适合研究型、探索型的多角色协作。**CrewAI**：**角色化流程**（Role/Task/Crew）抽象，上手快，适合快速搭建结构清晰的分工流水线。

**【深入拆解】**
- **LangGraph**：把 Agent 建成显式状态图，控制粒度最细，支持循环/条件/Checkpoint/人工介入。**灵活但要写更多代码**，适合对稳定性和可控性要求高的生产系统。
- **AutoGen**：核心抽象是"**会话中的多个 Agent 互相对话**"（如 UserProxy + Assistant + GroupChatManager）。适合让多个角色**自由讨论/协作**解决开放问题，研究气质强，编排相对松散。
- **CrewAI**：核心抽象是 **Crew（团队）+ Agent（角色）+ Task（任务）+ Process（流程）**，声明式定义"谁干什么、按什么顺序"。**上手最快、心智模型直观**，但灵活性和底层控制不如 LangGraph。
- **选型**：要**精细控制/生产可靠** → LangGraph；要**多角色自由协作/研究** → AutoGen；要**快速搭建清晰分工的业务流水线** → CrewAI。

| 框架 | 核心抽象 | 控制粒度 | 上手 | 最适场景 |
|---|---|---|---|---|
| LangGraph | 状态机图 | 细（底层） | 中 | 生产级复杂 Agent |
| AutoGen | 多 Agent 对话 | 中 | 中 | 研究/多角色协作 |
| CrewAI | Role/Task/Crew | 粗（高层） | 快 | 快速搭分工流水线 |

#### 16、企业级 Coding Agent 与通用 Agent 的架构有哪些区别？
**【核心思路】**
**核心差异在"反馈信号"与"环境交互方式"**。Coding Agent 有**编译/测试/运行的确定性反馈**，靠 **Agentic Search 导航代码库 + diff 精确编辑 + 执行闭环**；通用 Agent 反馈模糊，靠 **RAG 召回知识 + 更宽的领域工具 + 多模态**。前者深耕单一环境（代码仓），后者广接多种能力。

**【深入拆解】**
- **反馈信号（最本质区别）**：代码任务有**客观、确定的反馈**——编译报错、测试红绿、运行结果，Agent 可据此**自我纠错闭环**；通用任务（写文案、做决策）反馈**主观模糊**，往往要靠 LLM-as-Judge 或人工。
- **上下文获取**：Coding Agent 用 **Agentic Search**（grep/read 按需探索代码结构）；通用 Agent 更多用 **向量 RAG** 召回外部知识。
- **工具形态**：Coding 工具高度专一（文件、diff、Bash、Git、LSP）；通用 Agent 工具面更宽（搜索、数据库、API、多模态）。
- **任务特性**：Coding 任务**长、多步、可验证**（重构几十步但每步能测）；通用任务多为**较短的问答/生成**。
- **集成**：Coding Agent 深度集成版本控制、IDE、CI；通用 Agent 集成 IM、业务系统。

| 维度 | Coding Agent | 通用 Agent |
|---|---|---|
| 反馈信号 | 确定（编译/测试） | 模糊（需 Judge/人工） |
| 上下文 | Agentic Search 探索代码 | RAG 召回知识 |
| 工具 | 文件/diff/Bash/Git/LSP | 搜索/DB/API/多模态 |
| 任务 | 长、多步、可验证 | 较短、主观 |
| 集成 | VCS/IDE/CI | IM/业务系统 |

#### 17、如果让你设计一个支持百万级用户的企业级 Agent，你会重点优化哪些模块？
**【核心思路】**
重点优化四块：**模型接入层**（语义缓存 + 小模型分流 + KV 复用降成本）、**Context 层**（压缩裁剪降 Token）、**计算层**（无状态化 + 弹性扩缩 + 异步削峰）、**治理层**（限流降级 + 可观测 + 成本核算）。核心命题是**在保证体验的前提下把单位请求成本和尾延迟压下来**。

**【深入拆解】**
- **模型接入层（省钱主战场）**：**语义缓存**吃掉重复/相似请求；**小模型分流**——简单意图/分类走便宜模型，复杂推理才上大模型；**Prompt 前缀/KV Cache 复用**降低重复计算。
- **Context 层**：Token 是主要成本项——做**历史压缩、按相关性裁剪、RAG 精准召回**，避免无脑塞全量上下文。
- **计算层**：**Runtime 无状态化**（状态外置 Redis）以弹性水平扩缩；突发流量用 **MQ 异步削峰 + 优先级队列**。
- **治理层**：**令牌桶限流 + 熔断降级**（过载时降级到缓存/规则/兜底）；**全链路可观测**定位慢点；**成本按租户/业务核算**并持续优化命中率。
- **取舍**：百万级下，**每一分 Token、每一毫秒尾延迟乘以百万都是巨量成本**，优化优先级 = 成本 > 稳定 > 极致效果。

| 模块 | 优化手段 | 收益 |
|---|---|---|
| 模型接入 | 语义缓存/小模型分流/KV 复用 | 降成本 + 提速 |
| Context | 压缩/裁剪/精准 RAG | 降 Token |
| 计算 | 无状态弹性 + MQ 削峰 | 抗并发 |
| 治理 | 限流熔断 + 可观测 + 核算 | 稳定 + 成本可控 |

#### 18、意图理解模块如何处理多轮对话中的指代消解和意图漂移？
**【核心思路】**
**指代消解**靠 **Query Rewriting**——用 LLM 结合历史把当前轮改写成"独立完整、无需上下文即可理解"的 query（把"它/这个/上面那个"还原成实体）。**意图漂移**靠**意图跟踪 + 偏离检测 + 主动澄清**——识别当前意图是否偏离会话主线，必要时切换任务或反问确认。

**【深入拆解】**
- **指代消解的工程做法**：不是做传统 NLP 共指模型，而是**用大模型做历史改写**——输入"历史对话 + 当前句"，输出一个自包含的完整 query，再拿去检索/规划。这样"帮我把它也删了"会被还原成"删除刚才创建的订单 X"。
- **意图漂移的三步处理**：①**意图识别/分类**当前轮；②**与会话状态对比**，检测是延续、切换还是漂移；③漂移时**主动澄清**（"你是想换个话题还是继续刚才的？"）或开启新 session，避免用旧上下文污染新意图。
- **多轮的典型坑**：历史过长导致噪声/Token 爆炸（需**摘要式压缩历史**）；隐含指代（省略主语）；话题跳跃后旧上下文误导召回（需**会话切分**）。
- **状态载体**：用**槽位/会话状态（Session State）**跟踪关键实体和当前任务，作为消解和漂移判断的依据。

| 问题 | 表现 | 处理手段 |
|---|---|---|
| 指代消解 | "它/这个"含糊 | LLM 历史改写成独立 query |
| 意图漂移 | 中途换需求 | 意图分类 + 偏离检测 + 澄清 |
| 历史过长 | 噪声/Token 爆 | 摘要压缩历史 |
| 话题跳跃 | 旧上下文污染 | 会话切分/新 session |

#### 19、短期记忆和长期记忆之间如何做数据同步与遗忘策略？
**【核心思路】**
短期记忆是当前会话的工作缓冲（对话 buffer），长期记忆是跨会话的持久沉淀（向量库/知识库）。同步策略是**"提炼式写入"**：会话结束或关键节点，把短期中有价值的信息**摘要、抽取、去重**后固化进长期记忆；召回时再把相关长期记忆**加载回短期上下文**。遗忘靠**分级淘汰**：短期用滑动窗口/摘要压缩，长期按时效/访问频率/重要度打分做衰减与归档。

**【深入拆解】**
- **同步方向**：短期→长期是"沉淀"（提炼摘要写入，不是原文照搬，防噪声）；长期→短期是"召回"（按相关性检索加载）。
- **遗忘策略**：短期记忆超窗口时**摘要压缩老对话**（保留结论丢弃过程）；长期记忆用 **TTL 时效 + LRU 访问频率 + 重要度打分**综合淘汰，过期的降权或归档冷存。
- **防污染**：写入长期前要过滤——错误信息、被评测判失败的结果**不进长期**（呼应全文第 3 题的记忆污染）。
- **一致性**：同一事实的更新要覆盖旧值（如"用户地址变了"），避免新旧矛盾并存。

| 维度 | 短期记忆 | 长期记忆 |
|---|---|---|
| 载体 | 对话 buffer | 向量库/KG |
| 生命周期 | 单会话 | 跨会话持久 |
| 写入 | 实时原文 | 提炼摘要 |
| 遗忘 | 窗口/摘要压缩 | TTL + LRU + 重要度 |

#### 20、工具调用失败时，系统如何区分是参数错误还是工具本身不可用？
**【核心思路】**
靠**错误分类（Error Taxonomy）+ 来源分层 + 可重试标记**。参数错误通常在本地Schema或服务端业务校验阶段暴露；工具不可用包括连接失败、超时、服务过载和部分5xx。HTTP状态码只能辅助判断，不能用“所有4xx=参数错、所有5xx=可重试”替代语义分类。

**【深入拆解】**
- **判定依据**：调用前做JSON Schema与业务前置校验；调用后读取结构化错误的`category`、`retryable`、`retryAfter`和业务码。可复现性只是补充证据，不能通过盲目换参探测生产接口。
- **常见类别**：400/422可能是参数；401/403是认证/授权；404可能是资源不存在或路径错误；409是冲突；429是限流；5xx中502/503/504常可有限重试，而确定性500也可能持续复现。
- **不同处置**：参数错误只在约束内修正；认证/权限错误停止或刷新凭据；冲突需重新读取状态；429遵守`Retry-After`；瞬时网络/服务错误才做带抖动退避重试，之后降级或熔断。
- **写操作护栏**：只有幂等或带幂等键的调用才能安全自动重试；未知提交状态先查询后置条件，避免重复副作用。

| 维度 | 参数错误 | 工具不可用 |
|---|---|---|
| 典型信号 | Schema/422/业务校验 | 连接失败、503/504、超时 |
| 是否重试 | 修参后才可重试 | 仅可重试类别且有上限 |
| 特殊情况 | 401/403/404/409不是普通参数错 | 500不保证瞬时可恢复 |
| 处置 | 修参、停止或重读状态 | 退避、降级、熔断 |

#### 21、多个子任务之间存在依赖关系时，编排引擎如何处理死锁或循环依赖？
**【核心思路】**
把子任务建成 **DAG（有向无环图）**，用**拓扑排序**确定执行顺序。**编排时**通过**环检测**（DFS 找回边/Kahn 算法入度归零）在图构建阶段就拒绝循环依赖；**运行时**用**超时 + 依赖等待上限 + 资源加锁顺序统一**防死锁，检测到卡死则**中断 + Replan**打破循环。

**【深入拆解】**
- **循环依赖（编排期）**：任务图必须是 DAG。构建时跑**拓扑排序**，若存在无法归零入度的节点即有环，直接报错或让 Planner 重新拆解。
- **死锁（运行期）**：多任务争抢共享资源可能死锁，用经典手段——**统一加锁顺序**（破坏循环等待）、**超时释放**、**依赖等待上限**。
- **Agent 特有的"软死锁"**：LLM 反复在两个动作间横跳（A 等 B、B 等 A 的语义循环），靠**重复动作检测 + 最大步数**兜底，触发后 **Replan** 换路径。

| 问题 | 阶段 | 手段 |
|---|---|---|
| 循环依赖 | 编排期 | DAG + 拓扑排序 + 环检测 |
| 资源死锁 | 运行期 | 统一锁序 + 超时 + 等待上限 |
| 语义横跳 | 运行期 | 重复检测 + 步数 + Replan |

#### 22、权限分级的具体判定依据是什么（操作类型、数据敏感度、用户角色）？
**【核心思路】**
采用**多维度组合判定**：以 **RBAC/ABAC** 为骨架，综合三个维度——**操作类型**（读 < 写 < 删除 < 执行，破坏性越强权限越高）、**数据敏感度**（公开 < 内部 < 机密 < 个人隐私）、**用户角色**（访客 < 普通 < 管理员）。最终权限 = 三者交叉的**最小授权**，高危操作叠加**人工审批**。

**【深入拆解】**
- **操作类型维度**：只读操作低风险可放开；写/删/执行命令/发消息等**不可逆或外发**的操作需高权限 + 确认。
- **数据敏感度维度**：涉及 PII/机密数据的调用要脱敏、审计、限访问范围。
- **用户角色维度**：RBAC 按角色授权；更细的场景用 **ABAC**（按属性动态判定，如"仅本部门数据"）。
- **组合与兜底**：三维交叉取**最小权限原则**；命中高危组合（管理员删机密数据）触发**人工审批 + 全程审计日志**。
- **Agent 特有**：Agent 代表用户行事，需做**权限透传/降权**——Agent 不能拥有超过发起用户的权限。

| 维度 | 分级（低→高风险） | 处置 |
|---|---|---|
| 操作类型 | 读→写→删→执行 | 高危需确认 |
| 数据敏感度 | 公开→内部→机密→PII | 脱敏 + 审计 |
| 用户角色 | 访客→普通→管理员 | RBAC/ABAC |

#### 23、如何设计 Prompt Injection 检测机制，是否存在误报问题？
**【核心思路】**
采用**纵深防御**：①输入和外部内容检测；②用角色、来源标签和分隔符帮助模型区分“数据与指令”；③输出和工具调用策略校验；④最小权限、Sandbox与审批限制影响半径。**分隔符是软提示，不是物理或安全隔离边界**。误报不可避免，应分级处置并持续校准。

**【深入拆解】**
- **检测手段**：黑名单规则（快但易绕过）+ **LLM/分类器语义检测**（识别改写变体）+ 已知注入模式库。
- **结构提示**：把不可信输入用清晰边界包裹并声明“以下是数据”，同时保留来源；它能降低混淆但可被绕过，真正的安全边界必须在模型之外执行。
- **纵深防御**：单靠检测不够，**最后防线是权限**——注入即便骗过检测，工具调用的 RBAC（全文第 22 题）也能拦住越权操作。
- **误报问题**：安全检测本质是**召回率与误报率的权衡**——查得严则误伤正常请求（如用户正当地说"忽略之前的格式要求"），查得松则漏防。工程上**分级响应**（可疑→加确认而非直接拒绝）+ **人工审核样本回流**持续调优。

| 层次 | 手段 | 局限 |
|---|---|---|
| 输入检测 | 规则 + 语义分类 | 有误报/漏报 |
| 结构隔离 | 分隔符 + 数据声明 | 需模型配合 |
| 输出校验 | 泄露/越权检查 | 事后 |
| 权限兜底 | RBAC 最后防线 | 最可靠 |

#### 24、成功/失败判定是基于规则还是引入了 LLM 作为 Judge？
**【核心思路】**
**二者结合、分场景用**。**结构化、可枚举、有明确标准**的结果用**规则判定**（快、稳、零成本，如"是否返回了合法 JSON""测试是否通过"）；**开放式、语义化、无固定答案**的结果用 **LLM-as-Judge**（灵活，能评"回答是否有帮助/准确"）。生产上常**规则先过硬性门槛，LLM Judge 评软性质量**，关键场景再叠加人工抽检。

**【深入拆解】**
- **规则判定**：适合有 ground truth 或可程序化校验的（格式、数值、测试红绿、关键字命中）。优点：确定、便宜、可复现。
- **LLM-as-Judge**：适合语义质量评估（相关性、连贯性、事实性）。优点：灵活贴近人判。缺点：**有成本、有偏差（位置偏好/自我偏好）、不稳定**，需用打分 rubric、pairwise 比较、多次投票降方差。
- **组合范式**：**规则做门禁**（不过直接失败）→ **LLM Judge 做质量分** → 高价值场景**人工兜底**。

| 方式 | 适用 | 优点 | 缺点 |
|---|---|---|---|
| 规则 | 结构化/可校验 | 快/稳/免费 | 不灵活 |
| LLM-as-Judge | 开放/语义 | 灵活近人判 | 有成本/偏差 |
| 人工 | 高价值抽检 | 最准 | 慢/贵 |

#### 25、Replanning 与简单 Retry 的边界如何界定，什么情况下触发哪种策略？
**【核心思路】**
分界线是**"错在哪一层"**。**Retry** 针对**执行层的偶发失败**（超时、限流、网络抖动、工具临时不可用）——计划本身是对的，重试同一步即可。**Replanning** 针对**规划层的方向错误**（工具选错、路径走不通、前提变化、连续多次 Retry 仍失败）——重试无意义，必须让 Planner 重新拆解路径。

**【深入拆解】**
- **触发 Retry**：错误**可恢复且与决策无关**（5xx、Timeout、RateLimit），用**指数退避 + 最大次数**，超限则升级。
- **触发 Replanning**：错误**源于计划本身**（参数反复错、目标不可达、环境变了、Retry 耗尽），需带着失败原因回到 Planner 重规划。
- **中间态——降级**：Replan 和 Retry 之间还有降级（换备用工具/兜底方案）。
- **防振荡**：Replan 也要设次数上限，避免"规划→失败→再规划"无限循环，最终**升级到人工**。

| 策略 | 触发条件 | 动作 | 上限 |
|---|---|---|---|
| Retry | 偶发执行错 | 重试同一步 | 退避 N 次 |
| 降级 | 该路径不稳 | 换备用/兜底 | — |
| Replan | 计划方向错 | 重新拆解 | 有限次→人工 |

#### 26、如果是 Multi-Agent 架构，模块之间如何划分职责边界，避免功能重叠？
**【核心思路】**
以**单一职责 + 明确契约**为原则，按**能力域**而非随意拆分，每个 Agent 有清晰的**输入/输出契约和权责范围**；用**编排者/Supervisor 模式**统一调度，避免多个 Agent 抢同一职责；共享状态走**统一黑板/消息协议**，禁止越界直接操作他人领域。

**【深入拆解】**
- **划分原则**：按**正交的能力域**拆（研究/编码/审阅），确保职责不交叉；每个 Agent 定义**接口契约**（我负责什么、输入输出是什么）。
- **避免重叠的手段**：①**Supervisor 编排**——由主 Agent 分派，子 Agent 不自行抢活；②**能力注册表**——明确谁能干什么，路由按注册表分发；③**去重仲裁**——多 Agent 产出冲突时由编排者裁决。
- **通信规范**：统一消息格式/黑板，边界外只读不写。（同簇要点见全文第 34 题任务编排）

| 手段 | 做法 | 避免的问题 |
|---|---|---|
| 划分维度 | 按正交能力域拆分 | 职责交叉 |
| 契约 | 每 Agent 定义输入/输出接口 | 边界模糊 |
| 编排 | Supervisor 中心化分派 | 多方抢活 |
| 去重 | 能力注册表 + 冲突仲裁 | 功能重叠 |
| 通信 | 统一黑板/消息协议 | 越界操作 |

#### 27、如何评估整个 Agent 系统的端到端可靠性（SLA、成功率指标）？
**【核心思路】**
从**业务成功率**和**系统可用性**两条线立指标。业务线：**任务成功率**（端到端完成率）、**首次成功率**、**步骤级正确率**、**幻觉率**、**人工介入率**。系统线：**可用性 SLA**（如 99.9%）、**P95/P99 延迟**、**错误率**、**降级率**。用**离线回归评测集** + **在线监控/采样评测** + **用户反馈**三路交叉验证。

**【深入拆解】**
- **端到端 vs 步骤级**：既看最终任务是否达成（用户视角），也看每步工具调用/决策正确率（定位瓶颈）。
- **可靠性指标体系**：成功率、延迟分位、可用性、降级/熔断触发率、Token 成本/请求。
- **评测方式**：**离线**——固定回归集跑分防退化（结合全文第 24 题规则 + Judge）；**在线**——采样 + LLM Judge + 用户点赞/投诉；**影子/AB**——新版本灰度对比（全文第 76 题）。
- **SLA 落地**：定义可用性目标、告警阈值、错误预算。

| 类别 | 指标 |
|---|---|
| 业务可靠性 | 任务成功率/首次成功率/幻觉率/人工介入率 |
| 系统可靠性 | 可用性 SLA/P95-P99 延迟/错误率/降级率 |
| 评测方式 | 离线回归 + 在线采样 + AB + 用户反馈 |

#### 28、Harness Engineering 与 Prompt Engineering 有什么区别？
**【核心思路】**
**Prompt Engineering 优化"对模型说什么"**（单次输入的措辞、示例、格式），是**点**上的技巧；**Harness Engineering 优化"模型周围的整套工程系统"**（Agent Loop、上下文动态组装、工具、记忆、状态、护栏、可观测），是**面**上的架构。一句话：**Prompt 是喂给模型的一句话，Harness 是承载模型自主运行的整个骨架**。Agent 时代，Harness 决定上限。

**【深入拆解】**
- **作用对象**：Prompt Eng 作用于**单次调用的文本**；Harness Eng 作用于**多次调用组成的系统**（循环、状态流转、外部交互）。
- **稳定性来源**：Prompt 调得再好也是概率输出、不稳定；Harness 用**结构化约束、校验重试、护栏**把不确定性工程化为可靠系统。
- **可维护性**：Prompt 是散点、难版本化治理；Harness 是可测试、可观测、可复用的工程体系。
- **关系**：Harness ⊃ Prompt——Prompt 是 Harness 里"上下文组装"环节的一部分，而非全部。

| 维度 | Prompt Engineering | Harness Engineering |
|---|---|---|
| 粒度 | 单次输入 | 整个系统 |
| 关注 | 措辞/示例/格式 | Loop/上下文/工具/记忆/护栏 |
| 稳定性 | 概率、不稳 | 工程化、可靠 |
| 范围 | 点 | 面（含 Prompt） |

#### 29、为什么 Agent 更强调 Harness 而不是 Prompt？
**【核心思路】**
因为 Agent 是**多步自主系统**，单靠一句好 Prompt 无法保证几十步都不出错——真正决定成败的是**模型周围的工程**：上下文喂什么、工具怎么调、失败怎么兜底、状态怎么恢复、行为怎么约束。**Prompt 决定单步表现的下限，Harness 决定整个任务的上限**；模型能力越强，边际收益越从"调 Prompt"转移到"建 Harness"。

**【深入拆解】**
- **多步放大效应**：单步 95% 正确，20 步连乘就崩；Harness 的校验/重试/护栏把每步"托住"。
- **模型趋同**：底座模型越来越强且趋同，差异化竞争力从 Prompt 技巧转向 **Context 工程与系统设计**。
- **可控性/合规**：企业级要的稳定、安全、可观测，只能由 Harness 提供，Prompt 给不了。

| 视角 | Prompt Engineering | Harness Engineering |
|---|---|---|
| 单步表现 | 决定下限 | — |
| 多步任务 | 连乘误差易崩 | 校验/重试逐步托住 |
| 差异化 | 模型趋同后收益递减 | 系统设计是护城河 |
| 企业诉求 | 无法保障 | 稳定/安全/可观测 |

#### 30、Context Engineering 的核心目标是什么？
**【核心思路】**
核心目标是**在有限的上下文窗口内，为模型的每一次决策提供"恰好够用、精准相关、无噪声"的信息**——即 **Right Information, Right Place, Right Time**。既要**信息充分**（该有的都有，避免因缺信息而幻觉），又要**信息精简**（无关的都不要，避免噪声干扰和 Token 浪费）。本质是**信息的动态调度与预算管理**。

**【深入拆解】**
- **三重张力**：**充分 vs 精简**（够用但不冗余）、**相关 vs 全面**、**成本 vs 质量**。
- **要解决的问题**：上下文窗口有限、长上下文的"迷失在中间"、无关信息干扰决策、Token 成本。
- **手段**：精准召回（RAG）、动态裁剪、历史压缩摘要、结构化组织（把重要信息放显著位置）、按需加载。

| 目标 | 含义 | 反面（失败） |
|---|---|---|
| 充分 | 决策所需信息都在 | 缺信息→幻觉 |
| 精简 | 无关信息都不放 | 噪声→干扰/贵 |
| 相关 | 按当前 query 精准召回 | 召回错→跑偏 |
| 及时 | 每轮按当前状态重算 | 静态模板→僵化 |

#### 31、动态上下文如何组装？
**【核心思路】**
按"**分层拼装 + 按需召回 + 预算裁剪**"三步动态组装：先铺**固定层**（System Prompt/角色/规则/工具描述），再叠**检索层**（RAG 按当前 query 召回的知识、历史相关片段），最后放**即时层**（当前任务状态、上一步观察结果），全程在 **Token 预算**内按优先级裁剪与压缩。不是静态模板，而是**每一轮根据当前状态重新计算**。

**【深入拆解】**
- **组装顺序（优先级）**：系统指令 > 工具定义 > 当前任务/最新观察 > 召回知识 > 历史（可压缩）。低优先级在超预算时先被裁。
- **动态性**：每一轮依据"当前需要什么"重新召回和拼装，而非固定塞全部。
- **位置策略**：关键信息放开头/结尾（缓解"lost in the middle"）。
- **压缩**：长历史用摘要替代原文，工具大返回做提取。

| 层 | 内容 | 优先级（超预算时） |
|---|---|---|
| 固定层 | System/角色/规则/工具描述 | 高（保留） |
| 即时层 | 当前任务/最新观察 | 高（保留） |
| 检索层 | RAG 召回知识/相关历史 | 中 |
| 历史层 | 早期对话 | 低（先压缩/裁剪） |

#### 32、如何控制 Context Window 和 Token 成本？
**【核心思路】**
核心手段：**历史摘要压缩、精准 RAG 召回替代全量塞入、工具返回裁剪提取、Prompt 前缀/KV Cache 复用、语义缓存命中免调用、小模型分流简单任务、设 Token 预算硬上限并按优先级裁剪**。原则：**只放决策必需的信息**。（详见全文第 17 题成本优化、全文第 30/31 题 Context 工程）

**【深入拆解】**
- **输入侧（减少塞入）**：用精准 RAG 召回替代全量文档、工具大返回做摘要/结构化提取，只保留决策相关片段。
- **历史侧（压缩存量）**：滑动窗口 + 长对话摘要，保留结论丢弃过程。
- **复用侧（少算重复）**：相同 System Prompt 走 **KV/前缀缓存**，相似 query 走**语义缓存**直接命中。
- **模型侧（用对模型）**：简单任务分流小模型，复杂任务才上大模型（全文第 39 题 Router）。
- **预算侧（硬约束）**：设 Token 预算上限，超限按优先级裁剪（低优先级历史先裁，全文第 31 题）。
- **Agent 特有**：控制 Loop 步数（每步都烧 Token）、防死循环护栏。

| 手段 | 作用 | 归属 |
|---|---|---|
| 精准 RAG / 裁剪 | 减少输入 Token | 输入侧 |
| 历史摘要压缩 | 控制上下文增长 | 历史侧 |
| KV/语义缓存 | 免/省重复计算 | 复用侧 |
| 小模型分流 | 降单价 | 模型侧 |
| 预算 + 优先级裁剪 | 兜底硬约束 | 预算侧 |

#### 33、RAG 在 Harness 中承担什么角色？
**【核心思路】**
RAG 在 Harness 中是**"外部知识的动态供给器"**，为 Context Engineering 提供**按需召回的相关知识**，解决模型**知识过时、不含私域数据、易幻觉**的问题。它把企业知识库/文档/记忆变成可检索的外部记忆，在每轮上下文组装时**按当前 query 精准注入**，是长期记忆召回和事实性保障的关键环节。

**【深入拆解】**
- **承担的职责**：注入私域/实时知识、作为长期记忆的召回通道、用事实抑制幻觉（全文第 41 题）、缩小需要塞进上下文的信息量（全文第 32 题）。
- **Coding Agent 的例外**：编码场景更多用 **Agentic Search**（grep/read）而非向量 RAG（全文第 16 题），因为代码结构化、精确匹配优于语义匹配。
- **关键工程**：召回质量（chunk 切分、embedding、rerank）、权限过滤（全文第 61/69 题）、实时更新。

| 职责 | 说明 |
|---|---|
| 知识供给 | 注入私域/实时/长尾知识 |
| 记忆召回 | 长期记忆的检索通道（全文第 37 题） |
| 抑制幻觉 | 用外部事实兜底（全文第 41 题） |
| 降 Token | 按需召回替代全量塞入（全文第 32 题） |
| Coding 例外 | 代码用 Agentic Search 而非向量 RAG（全文第 16 题） |

#### 34、多 Agent 如何进行任务编排？
**【核心思路】**
主流三种编排模式：**Supervisor（主管分派）**——一个编排者 Agent 拆任务、派给子 Agent、汇总结果，最常用、可控；**Sequential/Pipeline（流水线）**——Agent 按固定顺序串行处理；**Network/Group Chat（对等协作）**——Agent 间自由通信讨论。据任务耦合度选型：**结构清晰用 Supervisor，线性流程用 Pipeline，开放探索用 Group Chat**。

**【深入拆解】**
- **Supervisor 模式**：中心化编排，主 Agent 负责规划、分发、监督、聚合，职责边界清晰（呼应全文第 26 题），是生产首选。
- **Pipeline 模式**：适合确定的多阶段流程（研究→写作→审阅），简单但不灵活。
- **Group Chat/Network**：去中心化，Agent 互相对话协作（AutoGen 风格），灵活但难控、成本高。
- **共性支撑**：统一消息协议、共享状态（黑板）、终止条件与仲裁机制。

| 模式 | 结构 | 特点 | 适用 |
|---|---|---|---|
| Supervisor | 中心化分派 | 可控、职责清 | 多数生产场景 |
| Pipeline | 串行 | 简单、固定 | 线性多阶段 |
| Group Chat | 对等网状 | 灵活、难控 | 开放探索 |

#### 35、MCP 在 Harness Engineering 中如何接入？
**【核心思路】**
MCP（Model Context Protocol）是**工具/数据源的标准化接入协议**，在 Harness 中扮演"**通用工具适配层**"。Agent 作为 **MCP Client**，外部能力（数据库、文件系统、API、第三方服务）封装为 **MCP Server**，双方通过标准协议通信。接入即"**即插即用**"：新工具只要实现 MCP Server，Agent 无需改代码即可发现并调用，实现 Agent 与工具的解耦。

**【深入拆解】**
- **解决的问题**：传统每接一个工具都要定制适配，**N 个 Agent × M 个工具 = N×M 对接**；MCP 标准化后变成 **N+M**。
- **接入流程**：Harness 内置 MCP Client → 连接/发现 MCP Server → 拉取工具 Schema 注入上下文（作为可用工具描述）→ LLM 决策调用 → Client 转发给 Server 执行。
- **工程要点**：Server 权限与鉴权（全文第 86 题）、工具描述质量（影响 LLM 选择）、超时/错误处理、Server 生命周期管理。
- **关联**：是 Tool Hub（全文第 60 题）的标准化实现方式。

| 环节 | 说明 |
|---|---|
| 角色 | Agent = MCP Client，工具 = MCP Server |
| 核心价值 | 对接复杂度 N×M → N+M |
| 接入流程 | 发现 Server → 拉 Schema → LLM 决策 → Client 转发执行 |
| 工程要点 | Server 鉴权、工具描述质量、超时、生命周期 |

#### 36、如何设计 Agent 的状态管理机制？
**【核心思路】**
用**显式状态机 + 状态外置持久化**。定义任务状态（Created→Planning→Running→Waiting→Success/Failed/Paused）及合法转移；每一步执行前后**持久化状态快照**（Checkpoint）到外部存储（Redis/DB），使 Runtime 无状态化。这样既支持**断点恢复**（全文第 43/74 题），又支持**水平扩展**（任意实例可接管），还便于**审计与可观测**。

**【深入拆解】**
- **状态内容**：当前任务/子任务进度、上下文快照、记忆引用、已执行动作历史、待办队列。
- **状态机**：明确状态集合与转移规则，非法转移拒绝，异常态可回滚或人工介入。
- **外置持久化**：状态不放进程内存，放外部存储，实现无状态 Runtime + 断点续跑。

| 要素 | 设计 |
|---|---|
| 状态集合 | Created/Running/Waiting/Success/Failed/Paused |
| 转移 | 显式规则 + 非法拒绝 |
| 持久化 | Checkpoint 外置 Redis/DB |
| 收益 | 断点恢复 + 水平扩展 + 审计 |

#### 37、长期记忆如何存储、召回和更新？
**【核心思路】**
**存储**：结构化事实入 KV/DB，非结构化知识做 embedding 入**向量库**，关系型知识入**知识图谱**。**召回**：向量语义检索 + 关键词/元数据过滤 + rerank，按相关性注入上下文。**更新**：新信息**提炼后写入**，同一事实**覆盖更新**（防新旧矛盾），失效知识按 TTL/重要度**衰减归档**。核心是"写入要提炼、召回要精准、更新要一致"（详见全文第 19 题）。

**【深入拆解】**
- **存储分型**：不同知识用不同载体——事实/画像入 KV/DB（精确查），文档/经验入向量库（语义查），实体关系入知识图谱（关联查）。
- **召回三段式**：**向量语义召回**（找相关）→ **元数据/权限过滤**（去无关、控可见，全文第 61 题）→ **rerank 精排**（提准确率），再按 Token 预算注入。
- **更新的一致性难点**：新信息要**提炼摘要**再写（防噪声）；同一事实要**覆盖而非追加**（防新旧矛盾并存）；过期低价值知识按 **TTL + 重要度**衰减归档。
- **写入门禁**：错误/未验证结果不进长期记忆，防污染（全文第 82 题）。

| 环节 | 手段 | 关键点 |
|---|---|---|
| 存储 | KV/DB + 向量库 + 知识图谱 | 按知识类型分型 |
| 召回 | 语义检索 + 过滤 + rerank | 精准 + 权限可见 |
| 更新 | 提炼写入 + 覆盖 + 衰减归档 | 一致性、防矛盾 |

#### 38、Tool Calling 如何做失败重试和降级？
**【核心思路】**
流程：**先归因**（全文第 20 题：参数错→LLM 改参重试；工具不可用→按下述容错）→ **指数退避 Retry**（带抖动、最大次数）→ 仍失败则**降级**（切换备用工具/降级方案/返回兜底）→ 反复失败触发**熔断**（暂时摘除该工具，避免雪崩）并**上报/Replan**。全程**幂等性保障**（重试不产生副作用）。

**【深入拆解】**
- **重试**：仅对**可重试错误**（超时/5xx/限流）退避重试；参数错不盲目重试。
- **降级**：主工具挂了用备用（如主搜索引擎→备用）、或返回缓存/兜底答案。
- **熔断**：错误率超阈值打开熔断器，快速失败保护系统，半开探测恢复。
- **幂等**：写操作重试要保证不重复执行（幂等键）。

| 阶段 | 触发条件 | 动作 |
|---|---|---|
| 归因 | 参数错 / 工具不可用（全文第 20 题） | 分流处置 |
| 重试 | 可重试错（超时/5xx/限流） | 指数退避 + 幂等 |
| 降级 | 重试无效 | 切备用工具/兜底 |
| 熔断 | 错误率超阈 | 摘除工具 + 上报/Replan |

#### 39、多模型 Router 如何设计？
**【核心思路】**
模型 Router 是模型网关的核心，按**"请求特征 → 路由策略 → 目标模型"**设计。路由维度：**任务复杂度**（简单走小模型，复杂走大模型）、**成本预算**、**能力匹配**（代码/多模态/长文本各选所长）、**负载与延迟**、**可用性**（主模型故障降级到备用）。策略可**规则路由 + 分类器路由**结合，叠加**降级熔断、缓存、限流**。

**【深入拆解】**
- **路由信号**：意图/复杂度分类、上下文长度、模态、SLA 要求、成本档位。
- **核心价值**：**降本**（小模型分流，全文第 17 题）+ **提可用**（多模型互备降级）+ **提质**（能力匹配）。
- **实现**：轻量分类器或规则先判档，再选模型；配额/负载做二次调度。

| 路由维度 | 策略 |
|---|---|
| 复杂度 | 简单→小模型，复杂→大模型 |
| 能力 | 代码/多模态/长文本匹配 |
| 成本 | 按预算档路由 |
| 可用性 | 主故障→备用降级 |

#### 40、如何评估 Harness Engineering 的效果？
**【核心思路】**
评估 Harness 效果看**系统级增益**：同一模型下，加了 Harness 后**任务成功率↑、幻觉率↓、稳定性↑、成本↓、可恢复性↑**。方法：固定评测集做**AB 对比**（有无某 Harness 组件），观察端到端成功率、步骤正确率、Token 成本、人工介入率、故障恢复率的变化。核心命题：**Harness 是否让"同一个模型"表现得更可靠、更省、更稳**（指标体系参全文第 27 题）。

**【深入拆解】**
- **控制变量**：**固定模型**，只增删/替换某个 Harness 组件（如上下文压缩、重试、评测层），对比前后指标，隔离出该组件的净增益。
- **看系统级而非单点**：不是评单次输出好坏，而是评**整条链路**的成功率、稳定性、成本、可恢复性。
- **典型收益信号**：成功率↑、幻觉率↓、Token 成本↓、故障自恢复率↑、人工介入率↓。
- **方法**：离线固定评测集回归 + 在线 AB/影子对比（全文第 76 题）。

| 维度 | 无 Harness（裸模型） | 加 Harness |
|---|---|---|
| 任务成功率 | 低、波动 | 高、稳定 |
| 幻觉/错误 | 高 | 校验/RAG 抑制 |
| 失败恢复 | 无 | 重试/降级/断点续跑 |
| 成本 | 不可控 | 缓存/分流可控 |
| 可观测 | 黑盒 | 全链路 Trace |

#### 41、如何降低 Agent 幻觉和错误调用工具的问题？
**【核心思路】**
多管齐下：①**用 RAG/工具提供事实依据**（让答案有据可查，全文第 33 题）；②**结构化输出 + Schema 校验**约束工具调用参数（全文第 20 题）；③**清晰的工具描述**降低选错工具概率；④**ReAct 的观察闭环**用真实结果纠偏；⑤**评测/Judge 兜底**拦截可疑输出（全文第 24 题）；⑥**引用溯源**要求模型标注依据；⑦**降低不确定时鼓励"我不知道"**而非编造。

**【深入拆解】**
- **幻觉根因**：模型在无依据时"自信编造"。对策是**给依据（RAG/工具）+ 要溯源 + 允许拒答**。
- **错误工具调用根因**：工具描述模糊、参数生成错、选择过多。对策是**精简工具集、清晰 Schema、校验重试、few-shot 示例**。
- **系统兜底**：输出校验、Judge、人工审核高危场景。

| 问题 | 根因 | 对策 |
|---|---|---|
| 事实幻觉 | 无依据自信编造 | RAG/工具给依据 + 溯源 + 允许拒答 |
| 选错工具 | 描述模糊/工具过多 | 精简工具集 + 清晰 Schema + 示例 |
| 参数错误 | 结构化生成出错 | Schema 校验 + 修正重试（全文第 20 题） |
| 兜底拦截 | — | 输出校验 + LLM Judge + 人工审高危 |

#### 42、如何实现 Agent 全链路可观测与调试？
**【核心思路】**
建立 **Tracing + Metrics + Logging** 三支柱并增加Agent语义。每次会话生成Trace，记录经过脱敏的输入版本、**可审计的决策摘要**、工具调用与参数摘要、观察结果、Token、耗时和状态转移。用OpenTelemetry或Agent观测平台做步骤级回放。目标是复现外部行为与证据链，不是采集隐藏思维链。

**【深入拆解】**
- **Trace（最关键）**：以会话为根Span，每步为子Span，串起计划/决策摘要、Action、Observation和状态变化，说明“基于哪些外部证据做了什么”。
- **Metrics**：成功率、延迟分位、Token/成本、工具调用分布、错误/降级率。
- **Logging**：结构化日志按数据等级保存；Prompt/Response原文只有在合法、必要且脱敏后才采集，并设置访问与保留期限。
- **调试**：步骤级回放、断点、对比不同运行、prompt diff。

| 支柱 | 内容 | 工具 |
|---|---|---|
| Tracing | 步骤级决策链 | OTel/LangSmith/Langfuse |
| Metrics | 成功率/延迟/成本 | Prometheus/Grafana |
| Logging | 结构化 + 脱敏原文 | ELK |

#### 43、Harness Engineering 如何支持长任务、多轮任务和断点恢复？
**【核心思路】**
靠**状态外置 + Checkpoint + 上下文压缩 + 任务拆解**。长任务用 **Planner 拆成可跟踪的子任务/TODO** 逐步推进；每步**持久化状态快照**（全文第 36 题），中断后从最近 Checkpoint **续跑**；多轮/长历史用**摘要压缩**控制上下文（全文第 31 题）；关键节点可**人工介入**后继续。核心是把"一次长执行"变成"可暂停、可恢复、可续跑的分步过程"。

**【深入拆解】**
- **任务拆解**：显式 TODO 列表，完成一项存一项，天然支持断点。
- **Checkpoint**：状态 + 上下文 + 进度外置持久化，实例宕机可换机恢复。
- **上下文管理**：长任务上下文必然超窗，靠摘要压缩 + 按需召回（全文第 30 题）。

| 机制 | 作用 | 关联 |
|---|---|---|
| 任务拆解 | TODO 显式化，逐项可存 | 全文第 44 题 |
| Checkpoint | 状态 + 上下文外置持久化 | 全文第 36 题 |
| 上下文压缩 | 长历史摘要防超窗 | 全文第 31 题 |
| 人工介入 | 关键节点暂停/审批后续跑 | 全文第 74 题 |

#### 44、如何结合 Reflection、ReAct、Plan-and-Execute 等模式构建执行框架？
**【核心思路】**
分层组合：**顶层用 Plan-and-Execute** 做全局规划（拆解 TODO，减少漂移、省 Token）；**每个子任务内用 ReAct** 循环（推理-行动-观察，处理不确定）；**失败或质量不达标时用 Reflection** 自我反思纠错后重试。即"**Plan 定方向、ReAct 干活、Reflection 纠错**"的三层执行框架，兼顾全局可控与局部灵活。

**【深入拆解】**
- **为什么组合**：单 ReAct 易漂移/循环；单 Plan 不够灵活应对意外；Reflection 补纠错。三者互补。
- **组合结构**：Plan（全局 DAG/TODO）→ 每节点 ReAct 执行 → 节点失败 Reflect 后 Retry/Replan（全文第 25 题）。
- **进阶**：高难决策可引入 ToT/LATS 树搜索。

| 层次 | 模式 | 职责 |
|---|---|---|
| 顶层 | Plan-and-Execute | 全局规划、定方向、减漂移 |
| 中层 | ReAct | 子任务内推理-行动-观察 |
| 纠错 | Reflection | 失败后自我反思再重试 |
| 进阶 | ToT/LATS | 高难任务多路径树搜索 |

#### 45、企业级 Agent 平台的 Harness Architecture 一般包含哪些核心模块？
**【核心思路】**
归纳为：**模型网关层、Agent Runtime（Loop/规划/执行）、上下文引擎、记忆系统、工具中心（Tool Hub/MCP）、编排引擎、评测层、安全与权限、可观测、状态与存储**。企业级还叠加**多租户、Prompt 仓库、成本核算、治理**。核心是"**Runtime 内核 + 能力层 + 治理层**"三块（详见全文第 1/2 题的分层架构与核心模块）。

**【深入拆解】**
- **内核层**：Agent Loop + Planner + Executor + 上下文引擎 + 状态管理，负责"跑一次任务"。
- **能力层**：模型网关、Tool Hub/MCP、RAG/记忆、编排引擎，为内核提供模型、工具、知识、协作能力。
- **治理层**：评测、安全权限、可观测、成本核算、多租户、Prompt 仓库——是企业级区别于 Demo 的关键。

| 内核层 | Loop/Planner/Executor/上下文/状态 | 执行引擎 |
| 能力层 | 模型网关/Tool Hub/RAG/编排 | 能力供给 |
| 治理层 | 评测/安全/可观测/成本/多租户 | 可管可控 |

#### 46、为什么采用 AI 中台模式而不是每个业务独立建设 Agent？
**【核心思路】**
核心理由：**避免重复建设、统一治理、规模效应、降本**。各业务独立建设会导致**模型接入/知识库/工具/可观测重复造轮子**、标准不一、安全治理分散、成本高。中台把**通用能力下沉共享**（模型网关、Tool Hub、RAG 底座、Eval），业务只做场景个性，从而**快速复用、统一管控、集中降本**。代价是需做好多租户隔离与稳定性，避免中台成瓶颈（薄中台原则，详见全文第 5 题）。

**【深入拆解】**
- **重复建设的痛**：各业务独立建，模型接入、知识库、可观测、安全全重造，标准不一、成本翻倍、治理分散。
- **中台的收益**：规模效应（一次建设多方复用）、统一治理（安全/成本/合规集中）、快速上线（业务只拼装）。
- **中台的风险与解法**：过度中台化会成瓶颈 → 做**薄中台**，只沉淀最稳定的公共底座，灵活性下放业务。

| 维度 | 各业务独立建设 | AI 中台模式 |
|---|---|---|
| 重复度 | 高（重复造轮子） | 低（复用底座） |
| 成本 | 翻倍 | 集中降本 |
| 治理 | 分散、标准不一 | 统一管控 |
| 上线速度 | 慢 | 快（拼装） |
| 风险 | — | 中台成瓶颈（需薄中台） |

#### 47、如何避免不同业务团队重复建设知识库？
**【核心思路】**
建**统一 RAG 知识底座（知识中台）**：提供共享的**文档接入、切分、embedding、检索、rerank**能力，各业务只需**上传自己的知识内容**并通过**租户/权限标签隔离**（全文第 61 题）。公共知识（如公司制度）**沉淀为共享库**多业务复用；业务私有知识**逻辑隔离**。统一管理还便于**质量治理、更新同步、去重**。核心：**平台统一"能力"，业务各自管"内容"**。

**【深入拆解】**
- **能力/内容分离**：平台提供统一的接入、切分、embedding、检索能力；业务只负责上传自己的知识内容。
- **公共 vs 私有**：公司级公共知识建共享库多方复用；业务私有知识按租户/权限标签逻辑隔离（全文第 61 题）。
- **统一治理红利**：集中做质量审核、更新同步、去重、召回监控，避免各团队各建一套、质量参差。

| 方面 | 平台（能力） | 业务（内容） |
|---|---|---|
| 接入/切分/向量化 | ✅ 统一 | — |
| 检索/rerank | ✅ 统一引擎 | — |
| 知识内容 | — | ✅ 各自上传 |
| 权限/隔离 | ✅ 机制 | 标签配置 |
| 公共知识 | ✅ 共享库 | 复用 |

#### 48、多业务共享模型时如何进行资源隔离？
**【核心思路】**
从**计算、配额、数据、性能**四维隔离。**计算/配额**：按租户设 QPS/Token 配额与优先级，防某业务打满影响他人（全文第 75 题）；**数据**：请求上下文、日志、缓存按租户隔离，防串数据；**性能**：关键业务专属资源池/独立实例，普通业务共享池；**故障**：租户级熔断，隔离故障爆炸半径。用**命名空间/租户 ID 贯穿全链路**实现逻辑隔离，高要求场景物理隔离。

**【深入拆解】**
- **隔离级别**：逻辑隔离（共享实例 + 租户标签，省成本）vs 物理隔离（独立资源，强隔离，贵）。
- **QoS**：优先级队列 + 配额限流，保障高价值租户 SLA。

| 维度 | 手段 |
|---|---|
| 配额 | 租户 QPS/Token 限流 + 优先级 |
| 数据 | 租户 ID 贯穿、上下文/缓存隔离 |
| 性能 | 专属池 vs 共享池 |
| 故障 | 租户级熔断 |

#### 49、如何设计统一模型接入层？
**【核心思路】**
统一接入层（模型网关）**屏蔽多厂商差异**，对上提供**统一 API**（统一的请求/响应格式、流式、Function Calling 抽象），对下适配各家模型 SDK。内置**路由、降级熔断、限流、缓存、鉴权、Token 计量、可观测**。价值：业务无需关心底层用哪个模型，**换模型不改业务代码**，并集中做治理与降本（Router 设计参全文第 39 题）。

**【深入拆解】**
- **对上统一抽象**：统一 Chat/Completion API、统一流式、统一 Function Calling 格式，屏蔽各厂商 SDK 差异。
- **对下多厂商适配**：适配 OpenAI/Anthropic/开源/私有化模型，新增模型只改网关不动业务。
- **横切能力内置**：路由、降级熔断、限流、缓存、鉴权、Token 计量、可观测集中在网关层做。

| 面向 | 职责 |
|---|---|
| 对上（业务） | 统一 API、换模型不改代码 |
| 对下（模型） | 多厂商/私有化适配 |
| 横切能力 | 路由/降级/限流/缓存/计量/可观测 |
| 收益 | 解耦 + 集中治理 + 降本 |

#### 50、多模型路由策略如何设计？
**【核心思路】**
按**任务复杂度、能力匹配、成本、负载、可用性**多维路由：规则/分类器判档选模型，简单任务分流小模型降本，复杂任务上大模型保质，主模型故障降级备用。叠加缓存与限流（同全文第 39/67 题）。

**【深入拆解】**
- **两类路由策略**：**规则路由**（按 token 长度/关键词/场景硬编码，快而透明）+ **分类器路由**（轻量模型判断复杂度，灵活但有开销）。
- **多目标权衡**：质量、成本、延迟、可用性往往冲突，需按业务 SLA 定权重（如客服重延迟、报告重质量）。
- **动态调整**：结合实时负载与配额做二次调度，主模型不可用即降级。

| 策略类型 | 判据 | 特点 |
|---|---|---|
| 规则路由 | token 长度/关键词/场景 | 快、透明、需维护 |
| 分类器路由 | 复杂度模型预测 | 灵活、有开销 |
| 成本路由 | 预算档 | 简单任务→小模型 |
| 故障路由 | 可用性探测 | 主故障→备用降级 |

#### 51、Agent 平台与业务平台之间如何解耦？
**【核心思路】**
靠**清晰的 API 契约 + SLA + 稳定版本**解耦：Agent 平台对业务是"**能力供应商**"，暴露标准化接口（Agent 编排、工具、RAG、模型调用），业务通过接口消费而不依赖内部实现。平台内部演进不破坏对外契约（版本兼容）。**通用能力在平台、业务逻辑在业务侧**，两者通过契约通信，各自独立迭代（详见全文第 5 题）。

**【深入拆解】**
- **契约解耦**：平台暴露稳定 API（编排、工具、RAG、模型调用），业务只依赖契约不依赖内部实现。
- **版本兼容**：平台内部重构不得破坏对外契约，用版本化 + 灰度保护存量业务（全文第 52/76 题）。
- **供需关系**：平台是"能力供应商"（对内），业务是"消费者"，用 SLA 约定可用性与延迟。

| 维度 | 平台侧 | 业务侧 |
|---|---|---|
| 提供 | 稳定 API + SLA | — |
| 依赖 | — | 只依赖契约 |
| 迭代 | 内部自由演进 | 独立快速迭代 |
| 变更约束 | 不破坏契约、版本兼容 | 按契约消费 |

#### 52、Prompt 仓库如何进行版本管理？
**【核心思路】**
把 Prompt 当**代码/配置资产**治理：**版本化存储**（Git 或专用 PromptOps 平台）、**语义化版本号**、**变更评审**、**环境隔离**（dev/staging/prod）、**灰度发布 + 回滚**、**效果追踪**（每版本关联评测分与线上指标）。支持**模板参数化、A/B 版本对比**（全文第 76 题）。核心：**Prompt 变更可追溯、可回滚、可评测**，而非散落在代码里裸改。

**【深入拆解】**
- **要素**：版本号、变更记录、作者、评审、关联评测结果。
- **发布**：灰度上线新版 Prompt，指标不劣化再全量，异常一键回滚。
- **协作**：Prompt 与代码解耦，非工程人员也可维护（配合评测门禁）。

| 要素 | 做法 |
|---|---|
| 存储 | Git / PromptOps 平台版本化 |

| 发布 | 环境隔离 + 灰度 + 一键回滚 |
| 追踪 | 每版本关联评测分与线上指标 |
| 协作 | 与代码解耦，非工程人员可维护 |

#### 53、如何评估不同业务线 Agent 的效果？
**【核心思路】**
**统一评测框架 + 业务定制指标**：平台提供通用评测能力（成功率、延迟、成本、幻觉率、满意度）和评测流水线，各业务线在此之上定义**场景化指标与评测集**（如客服看解决率、编码看通过率）。用**离线回归 + 在线采样 Judge + 用户反馈**统一采集，横向对比各业务线，纵向防退化（方法参全文第 24/27 题）。

#### 54、如何统一管理多个业务知识库？
**【核心思路】**

#### 55、多业务场景下如何实现权限隔离？
**【核心思路】**
**租户 + RBAC/ABAC 双层**：租户级隔离数据与资源边界（跨租户绝不可见），租户内用 RBAC/ABAC 控制用户对功能/数据的访问。Agent 调用时**透传发起者身份**，RAG 召回按**权限标签过滤**（全文第 69 题），工具调用按角色鉴权。全链路**租户 ID + 用户身份**贯穿，审计留痕（参全文第 22/48 题）。

**【深入拆解】**
- **租户层（强隔离）**：跨租户数据绝不可见，租户 ID 贯穿请求、存储、缓存、日志。
- **用户层（细粒度）**：租户内用 RBAC/ABAC 控制功能与数据访问，Agent 权限不超过发起用户。
- **落地关键**：身份透传 + RAG 召回按权限标签过滤 + 工具按角色鉴权 + 全程审计。

| 层次 | 隔离机制 | 粒度 |
|---|---|---|
| 租户级 | 命名空间/租户 ID 贯穿 | 强隔离、不可见 |
| 用户级 | RBAC/ABAC | 功能/数据可见性 |
| 召回级 | 权限标签过滤 | 行/文档级 |
| 审计 | 全链路留痕 | 可追溯 |

#### 56、AI 中台如何进行成本核算和分摊？
**【核心思路】**
建**统一计量 + 按租户/业务分摊**体系。**计量**：全链路埋点采集每请求的**Token 数、模型档位、工具调用、算力占用**，打上租户/业务标签。**核算**：按 Token 单价 + 资源占用折算成本。**分摊**：按业务线用量分账，支持配额与预算告警。**优化**：暴露缓存命中率、小模型分流率等指标驱动降本。核心：**成本可归因到每个业务，可计量、可预算、可优化**。

**【深入拆解】**
- **计量维度**：Token（输入/输出分算）、模型档位、缓存命中、工具/算力。
- **分摊模型**：按实际用量（后付费）或配额包（预付费）。

#### 61、多业务共享 RAG 平台时如何进行数据隔离？
**【核心思路】**
**租户/权限标签 + 检索过滤**：每条知识 chunk 打上**租户 ID + 权限标签（部门/角色/密级）**，检索时**先按租户强隔离**，再按用户权限过滤召回结果（**行级/文档级过滤**）。高敏感场景**物理分库**。确保**跨租户零泄露**、租户内**按权限可见**，全程审计（参全文第 47/55 题）。

**【深入拆解】**
- **标签先行**：每条 chunk 打租户 ID + 权限标签（部门/角色/密级），是隔离的元数据基础。
- **两级过滤**：检索时先按租户强隔离（跨租户零召回），再按用户权限做行/文档级过滤。
- **分级隔离**：普通业务逻辑隔离（共享库 + 标签），高敏感数据物理分库，全程审计。

| 层次 | 机制 | 强度 |
|---|---|---|
| 租户隔离 | 租户 ID 过滤 | 强（零泄露） |
| 权限过滤 | 标签 + 行/文档级 | 细粒度可见性 |
| 高敏感 | 物理分库 | 最强 |
| 审计 | 召回留痕 | 可追溯 |

#### 66、千万用户并发下，模型调用链路如何做限流和削峰？
**【核心思路】**
**限流**：网关层**令牌桶/漏桶**按租户/用户/全局多级限流，保护后端与模型配额。**削峰**：突发流量转**消息队列异步排队**处理，配**优先级队列**（付费/关键优先）；后端过载**熔断降级**（返回排队提示/兜底）。叠加**缓存**吸收重复请求、**批处理**提吞吐。核心：**把尖峰流量削平成后端可承受的平稳流量**（详见全文第 4 题）。

**【深入拆解】**
- **限流（挡住）**：令牌桶/漏桶在网关按全局/租户/用户多级限流，保护后端与模型配额。

- **兜底（降级）**：后端过载时熔断降级，返回排队提示/兜底答案，而非雪崩。

| 手段 | 作用 | 位置 |
|---|---|---|
| 令牌桶限流 | 挡住超额请求 | 网关 |
| MQ 异步削峰 | 缓冲尖峰 | 队列 |
| 优先级队列 | 保关键业务 | 队列 |
| 熔断降级 | 防雪崩 | 后端 |
| 缓存/批处理 | 减压/提吞吐 | 全链路 |

| 采集方式 | 离线 + 在线 + 反馈 + AB | 综合闭环 |

#### 71、如何控制大模型调用成本？
**【核心思路】**
核心杠杆：**缓存**（语义 + 精确 + KV 复用免/省调用）、**小模型分流**（简单任务走便宜模型）、**Context 压缩**（裁剪历史/精准召回降 Token）、**批处理**提效、**成本计量与预算治理**驱动持续优化。原则：**不必要的调用不发、不必要的 Token 不塞、能用小模型不用大模型**（同全文第 17/32/56 题）。

**【深入拆解】**
- **少调用**：语义缓存命中相似 query 直接返回、批处理合并请求，减少实际模型调用次数。
- **少 Token**：Context 压缩 + 精准 RAG + 工具返回裁剪，把每次输入输出的 Token 压到最低。
- **用对模型**：小模型分流简单任务、KV 复用重复前缀，同等效果下降单价。

| 杠杆 | 手段 | 收益 |
|---|---|---|
| 少调用 | 语义缓存 + 批处理 | 减调用次数 |
| 少 Token | 压缩 + 精准召回 + 裁剪 | 降单次成本 |
| 用对模型 | 小模型分流 + KV 复用 | 降单价 |
| 治理 | 计量 + 预算告警 | 持续优化 |

#### 72、流式输出在高并发场景下如何保证稳定？
**【核心思路】**
用 **SSE/WebSocket** 做流式，稳定性靠：**事件驱动的长连接管理**（连接注册、心跳、空闲超时与资源配额）、**背压处理**（有界缓冲、限速或断开慢消费者）、**断线重连与可选续传**、首Token/整体超时，以及支持长连接的负载均衡。核心是控制每连接资源和慢消费者，而不是把客户端长连接放进普通“连接池”。

**【深入拆解】**
- **连接管理**：使用非阻塞I/O、连接注册表、每租户/实例上限、心跳和超时回收；下游模型HTTP连接可复用，但这与面向客户端的SSE连接管理不同。
- **背压**：客户端消费慢于生成时使用有界队列，超过阈值后降采样、取消上游或断开，禁止无限缓冲。
- **容错**：SSE可用事件ID与持久事件缓冲实现续传；若服务端未保存事件，只能重新请求，不能承诺无损续推。

| 挑战 | 手段 |
|---|---|
| 连接耗尽 | 连接池 + 心跳 + 超时回收 |
| 背压/OOM | 缓冲 + 流控限速 |
| 断线 | 记录位置 + 续传 + 幂等重连 |
| 过载 | 首 Token/整体超时 + 降级非流式/兜底 |
| 高并发 | 网关负载均衡 + keep-alive 调优 |

#### 73、如何防止 Prompt 注入和敏感数据泄露？

#### 74、长任务失败后如何实现断点续跑？
**【核心思路】**
前提是**状态外置 + Checkpoint**：任务拆成可跟踪子步骤，每步完成**持久化进度与上下文快照**；失败后从**最近成功的 Checkpoint 恢复**，重放剩余步骤（写操作要**幂等**防重复副作用）。配合**失败归因**（全文第 20 题）决定续跑/重试/Replan。核心：**把长任务变成可从任意断点恢复的分步过程**（参全文第 36/43 题）。

**【深入拆解】**
- **前提**：状态外置 + 每步 Checkpoint（进度 + 上下文快照），否则无从恢复。
- **恢复**：从最近成功检查点重放剩余步骤，已完成的不重做。
- **幂等关键**：写操作（下单/发消息）必须幂等，否则重放产生重复副作用；用幂等键去重。
- **归因决策**：恢复前先归因——环境错→续跑重试，计划错→Replan（全文第 20/25 题）。

| 环节 | 做法 |
|---|---|
| 前提 | 状态外置 + 分步 Checkpoint |
| 恢复 | 从最近检查点重放剩余步 |
| 幂等 | 写操作幂等键去重 |
| 归因 | 续跑/重试/Replan 分流 |

#### 76、平台如何做灰度发布和 A/B 实验？
**【核心思路】**
建**流量分桶 + 版本路由 + 指标对比**机制。**灰度**：新版本（模型/Prompt/Agent）先放**小流量**，按用户/租户/比例分桶，监控指标不劣化再逐步放量，异常**一键回滚**。**A/B 实验**：并行运行多版本，随机分流，对比**成功率/满意度/成本**等指标做统计显著性检验，择优全量。核心：**变更可控上线、数据驱动决策、异常快速回滚**。

**【深入拆解】**
- **分桶**：按用户 ID hash/租户/比例，保证同用户体验一致。
- **指标**：业务指标 + 系统指标对比，统计显著性。
- **回滚**：Prompt/模型版本化（全文第 52 题）支持秒级回退。

| 机制 | 做法 |
|---|---|
| 分桶 | 按用户 ID hash/租户/比例，保证体验一致 |
| 灰度 | 小流量→监控→逐步放量→异常回滚 |
| A/B | 多版本随机分流 + 指标显著性检验 |
| 指标 | 成功率/满意度/成本对比 |
| 回滚 | 版本化支持秒级回退 |

#### 77、线上模型输出异常时如何快速定位根因？
**【核心思路】**
靠**全链路 Trace 回放**（全文第 42 题）：定位到具体会话与步骤，检查**当时的完整上下文（喂了什么）、模型输入输出、工具调用与返回、状态**，逐层排查根因——是**上下文组装问题**（召回错/信息缺）、**Prompt/版本变更**、**模型侧波动**、**工具返回异常**还是**参数错误**。配合**变更关联**（最近发布了什么）、**指标告警下钻**、**相似 case 聚类**快速缩小范围。核心：**可复现的 Trace + 变更关联 = 快速归因**。

**【深入拆解】**
- **Trace 回放**：定位到具体会话/步骤，还原当时完整上下文、模型输入输出、工具调用与返回。
- **分层排查**：依次看上下文组装（召回错/缺信息）→ Prompt/版本变更 → 模型波动 → 工具异常 → 参数错误。
- **加速手段**：变更关联（近期发布了什么）、指标告警下钻、相似 case 聚类缩小范围。

| 排查层 | 可能根因 |
|---|---|
| 上下文 | 召回错 / 信息缺失 |
| Prompt | 版本变更引入 |
| 模型 | 侧波动/降级 |
| 工具 | 返回异常/超时 |
| 参数 | 生成错误（全文第 20 题） |

#### 78、规划器和执行器为什么要拆开？
**【核心思路】**
核心理由：**关注点分离 + 独立优化 + 可控可审计**。规划是"**决定做什么**"（需强推理、全局视野、慢而贵），执行是"**具体怎么做**"（工具调用、可用小模型/规则、快而多）。拆开后：①各自用**最合适的模型/策略**（规划用大模型，执行分流）；②计划**可审计、可人工介入**；③**独立扩展**（执行可并行水平扩展）；④**失败可分层处理**（Replan vs Retry，全文第 25 题）。合在一起则职责混乱、难优化、难控制。

**【深入拆解】**
- **用对模型**：规划需强推理（大模型、慢、贵），执行是工具调用（可用小模型/规则、快），分离后各取所需。
- **可审计可介入**：Planner 产出显式计划，可人工审查、修改、批准，而非黑盒一把梭。
- **独立扩展与容错**：执行可并行水平扩展；失败按层处理——执行偶发错 Retry，计划错 Replan（全文第 25 题）。

| 维度 | 规划器 | 执行器 |
|---|---|---|
| 职责 | 决定做什么 | 具体怎么做 |
| 特性 | 强推理/全局/慢贵 | 工具调用/快/可并行 |
| 模型 | 大模型 | 小模型/规则 |
| 收益 | 可审计/可介入 | 可扩展/可容错 |

#### 79、单 Agent 和多 Agent 架构如何选择？
**【核心思路】**
默认单 Agent（简单可控便宜），出现明确瓶颈才上多 Agent：任务可清晰解耦、需异构专业分工、可并行加速、单 Agent 上下文装不下。强依赖/串行/共享上下文用单 Agent；弱耦合/可并行/需分工用多 Agent。核心：**多 Agent 是解决特定瓶颈的手段，不是默认选择**（同全文第 13 题）。

**【深入拆解】**
- **默认单 Agent**：简单、可控、便宜、易调试，多数任务足够，过早上多 Agent 是过度设计。
- **上多 Agent 的信号**：可清晰解耦、需异构专业分工、可并行提速、单窗口装不下需上下文隔离。
- **代价意识**：多 Agent 有协调开销、错误级联、成本翻倍、调试黑盒（全文第 14 题）。

| 特征 | 单 Agent | 多 Agent |
|---|---|---|
| 耦合 | 强依赖/串行 | 弱耦合/可并行 |
| 角色 | 单一 | 异构分工 |
| 上下文 | 装得下 | 需隔离 |
| 成本 | 低 | 高 |
| 默认 | ✅ | 有瓶颈才用 |

#### 80、如何设计 Agent 的任务状态机？

定义**状态集合**（Created→Planning→Running→Waiting/Paused→Success/Failed）与**合法转移规则**，非法转移拒绝；每次转移**持久化快照**支持恢复；异常态可**回滚/Replan/人工介入**。状态机让 Agent 执行**可跟踪、可恢复、可审计、可并发调度**。核心：**用显式状态机把不确定的执行过程约束成可管理的确定流转**（同全文第 36 题）。

**【深入拆解】**
- **状态集合**：Created→Planning→Running→Waiting/Paused→Success/Failed，覆盖全生命周期。
- **转移规则**：定义合法转移，非法转移拒绝；异常态可回滚/Replan/人工介入。
- **持久化**：每次转移存快照，支撑断点恢复与并发调度（全文第 36/74 题）。

| 要素 | 设计 |

| 异常 | 回滚/Replan/人工 |
| 持久化 | 每步快照 → 恢复/审计 |

#### 81、工具调用失败时如何重试和降级？
**【核心思路】**
先**归因**（全文第 20 题：参数错→LLM 改参；工具不可用→容错）→**退避 Retry**（可重试错、带上限、幂等）→**降级**（备用工具/兜底）→**熔断 + 上报/Replan**。核心：**归因决定策略，重试幂等，降级兜底，熔断防雪崩**（同全文第 38 题）。

**【深入拆解】**
- **归因先行**：先判是参数错还是工具不可用（全文第 20 题），错因不同处置不同。
- **分级容错**：可重试错 → 退避重试（幂等）；重试无效 → 降级（备用/兜底）；持续失败 → 熔断 + 上报/Replan。
- **幂等与防雪崩**：写操作幂等防重复副作用；熔断快速失败保护整体。

| 策略 | 触发 | 动作 |
|---|---|---|
| 重试 | 偶发可恢复错 | 退避 + 幂等 |
| 降级 | 重试无效 | 备用工具/兜底 |
| 熔断 | 错误率超阈 | 摘除 + 快速失败 |
| Replan | 计划方向错 | 重新规划（全文第 25 题） |

#### 82、记忆层如何避免信息污染？

- **冲突消解 + 清洗**：同一事实覆盖更新防新旧矛盾；定期淘汰过期/低可信/矛盾记忆。

| 防护 | 手段 |
|---|---|
| 写入把关 | 验证通过才入库 |
| 溯源标记 | 置信度/来源标签 |
| 冲突消解 | 覆盖更新防矛盾 |
| 定期清洗 | 淘汰过期/低可信 |
| 隔离 | 租户/会话防串 |

#### 83、企业知识库权限如何和 Agent 结合？
**【核心思路】**
Agent 召回知识时**透传发起用户身份**，RAG 检索**按用户权限标签过滤**（行级/文档级），**只返回该用户有权访问的知识**，绝不越权召回。工具/数据访问同样按角色鉴权（全文第 22 题）。即"**Agent 的可见范围 = 发起用户的权限范围**"，全程审计。核心：**权限透传 + 召回过滤 + 最小权限 + 审计**（参全文第 55/61 题）。

**【深入拆解】**
- **权限透传**：Agent 代表用户行事，调用时透传发起者身份，不能拥有超过用户的权限。
- **召回过滤**：RAG 检索按用户权限标签做行/文档级过滤，只返回有权访问的知识（全文第 61 题）。
- **全程审计**：谁在什么时候访问了什么知识全部留痕，满足合规审查。

| 环节 | 机制 |
|---|---|
| 身份 | 透传发起用户 |
| 召回 | 权限标签过滤（行/文档级） |
| 工具/数据 | 按角色鉴权（全文第 22 题） |
| 边界 | Agent 可见 = 用户权限 |
| 审计 | 访问留痕 |

#### 84、如何评估 Agent 最终任务完成质量？
**【核心思路】**
**多维度评判**：**完成度**（是否达成目标）、**正确性**（结果对不对）、**过程合理性**（步骤是否高效无冗余）、**用户满意度**。方法：**规则校验硬指标**（有 ground truth 的）+ **LLM-as-Judge 评语义质量**（开放式）+ **人工抽检高价值场景**。用固定评测集离线跑分 + 在线采样评估。核心：**结果 + 过程 + 体验多维，规则与 Judge 结合**（参全文第 24/27 题）。

**【深入拆解】**
- **多维评判**：完成度（达成目标）、正确性（结果对）、过程合理性（步骤高效无冗余）、用户满意度。
- **方法组合**：有 ground truth 的用规则校验，开放式质量用 LLM-as-Judge，高价值场景人工抽检（全文第 24 题）。
- **离线 + 在线**：固定评测集防退化，在线采样反映真实分布。

| 维度 | 评判方式 |
|---|---|

#### 85、如何控制 Agent 调用成本和 Token 消耗？
**【核心思路】**
杠杆：**缓存复用、小模型分流、Context 压缩裁剪、精准 RAG 召回、减少无效循环步骤（护栏防死循环）、批处理、成本计量治理**。Agent 特有——**控制 Loop 步数**（每步都烧 Token）、**裁剪工具大返回**。核心：**少调用、少 Token、用对模型、控步数**（同全文第 17/32/71 题）。

**【深入拆解】**
- **通用杠杆**：缓存复用、小模型分流、Context 压缩、精准 RAG、批处理（全文第 71 题）。
- **Agent 特有杠杆**：控制 Loop 步数——每步都要调模型烧 Token，护栏防死循环/无效循环；裁剪工具大返回防上下文膨胀。
- **治理**：Token 计量到会话/任务，暴露单任务平均步数、平均成本等指标持续优化。

| 杠杆 | 手段 | 归属 |
|---|---|---|
| 缓存/分流/压缩 | 复用 + 小模型 + 精准召回 | 通用 |
| 控步数 | 护栏防死循环/无效循环 | Agent 特有 |
| 裁剪返回 | 工具大返回摘要 | Agent 特有 |
| 计量治理 | 单任务步数/成本监控 | 治理 |

#### 86、如何保证工具调用的安全性？
**【核心思路】**
多层保障：**权限校验**（工具调用按角色/租户鉴权，最小权限）、**参数校验与沙箱**（Schema 校验 + 危险操作沙箱隔离执行，如代码/命令在容器内跑）、**危险操作审批**（写/删/外发走人工确认）、**注入防护**（防被诱导调用危险工具，全文第 23 题）、**审计留痕 + 限流**（防滥用）。核心：**鉴权 + 校验 + 沙箱 + 审批 + 审计**五道防线。

**【深入拆解】**
- **沙箱**：Bash/代码执行等在隔离环境运行，限制文件/网络/系统访问。
- **审批**：不可逆/高危操作人工确认，Agent 不能自主执行。
- **最小权限**：Agent 权限不超过发起用户（全文第 22 题）。

| 防线 | 手段 |
|---|---|
| 鉴权 | 按角色/租户，最小权限 |
| 校验 | 参数 Schema 校验 |
| 沙箱 | 命令/代码隔离容器执行 |
| 审批 | 危险/不可逆操作人工确认 |
| 审计 | 调用留痕 + 限流防滥用 |

#### 87、如何实现 Agent 全链路可观测和问题定位？
**【核心思路】**
建 **Trace + Metrics + Logging** 三支柱，会话级 Trace 记录每步（上下文/决策/工具/观察/Token/耗时/状态），支持**步骤级回放下钻**；配指标告警与变更关联，快速归因。核心：**让多步黑盒决策可复现、可回放、可归因**（同全文第 42/77 题）。

**【深入拆解】**
- **三支柱**：Trace（步骤级决策链，最关键）+ Metrics（成功率/延迟/成本）+ Logging（结构化脱敏原文）。
- **Agent 语义化**：Trace要能还原每一步的计划/决策摘要、工具调用、外部证据与状态变化，而非通用请求日志；隐藏思维链不作为审计依据。
- **快速定位**：告警下钻 + 变更关联 + 相似 case 聚类，从现象到根因（全文第 77 题）。

| 支柱 | 内容 | 用途 |
|---|---|---|
| Tracing | 步骤级决策链 | 回放归因 |
| Metrics | 成功率/延迟/成本 | 告警趋势 |
| Logging | 脱敏原文 | 复盘取证 |
