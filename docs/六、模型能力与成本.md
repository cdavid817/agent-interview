# 六、模型能力与成本

> 本章共 **160** 题，覆盖多模型路由、Fallback、缓存、Token 与成本治理、模型评测、微调、流式输出和容量规划。
>
> 成本题应以“单位成功任务成本”为核心，不能只优化单次调用价格；模型能力和价格、上下文上限等易变化信息应按具体版本核验。

#### 1、模型API异常如何熔断和切换？（豆包二面）
模型API容错应形成**“分类—重试—熔断—兼容切换—校验”**闭环。不能遇到失败立即换模型，而要判断是否受理、能否恢复及备用模型是否满足能力与安全要求。

1. 异常分为参数或鉴权、限流、网络与临时`5xx`、持续故障、空响应或格式错误。参数、权限和策略拒绝不重试；限流遵循`Retry-After`；瞬时错误在幂等前提下退避重试。
2. 按供应商、模型和区域统计错误率、超时率与慢调用率，达到样本和阈值后Open快速失败；冷却后Half-Open小流量探测，稳定成功再渐进恢复。
3. 备用路由校验上下文、结构化输出、Tool Calling、地域、合规和价格。切换使用统一Schema并重算Token；生成内容不保证逐字一致，只保证验收标准一致。
4. 流式输出中断后禁止直接拼接另一模型，应从检查点重生成或说明降级。Agent保存计划、工具结果与幂等状态，避免整链重跑。
5. 记录熔断原因、候选、切换、质量和成本，防止备用链循环。

| 异常 | 自动重试 | 处理 |
|---|---|---|
| 参数、鉴权、策略拒绝 | 否 | 修正或终止 |
| 限流、瞬时网络、临时5xx | 有界 | 退避与抖动 |
| 持续故障 | 否 | 熔断并切换 |
| 内容不合格 | 条件式 | 校验、重生成或降级 |

**相关知识点：** 错误分类、Retry-After、指数退避、重试预算、熔断状态机、Half-Open、能力画像、流式恢复、幂等。

#### 2、多模型调度策略怎么设计？（豆包二面）
多模型调度采用**“硬过滤、能力召回、效用排序、执行升级、反馈校准”**。目标不是总选最强模型，而是在质量与安全达标后降低时延和成本。

1. 模型画像包含推理、代码、中文、视觉、结构化输出和Tool Calling分数，以及上下文、区域、数据策略、价格、配额、P95和健康度。
2. 请求提取任务类型、复杂度、长度、模态、SLA、预算和数据等级。先过滤能力不足、地域不合规、权限不符或已熔断模型。
3. 计算`效用=质量收益−时延−成本−风险`。规则控制安全边界，分类器判断复杂度，Bandit只在安全候选中探索；高风险请求禁止探索。
4. 默认用满足阈值的最小模型；低置信、格式失败、工具参数错误或用户重试时升级。降级仅选能力兼容模型并重算上下文与预算。
5. 记录候选、过滤原因、分数和策略版本；以成功率、升级率、P95、单位成功成本和误路由率校准，并经Shadow、灰度和回滚发布。

| 层次 | 方法 | 作用 |
|---|---|---|
| 硬过滤 | 规则与Policy | 安全、合规、可执行 |
| 复杂度判断 | 分类器/小模型 | 选择能力档位 |
| 候选排序 | 效用函数/Bandit | 优化质量成本时延 |
| 运行升级 | 校验与置信门控 | 兜住困难任务 |

**相关知识点：** Model Router、能力画像、效用函数、级联推理、Bandit、硬约束、升级策略、Shadow、严重误路由率。

#### 3、小模型和大模型如何分工？（豆包二面）
小模型与大模型应按**任务复杂度、风险和可验证性**分工：小模型负责高频、边界清晰、可程序校验的工作，大模型负责开放推理、复杂规划和高价值异常；通过级联升级而非固定绑定，在质量达标前提下控制成本。

1. 小模型适合意图分类、实体抽取、查询改写、内容路由、格式转换、简单摘要、规则补全和候选初筛。这类任务输入输出Schema明确、评测稳定，失败可由校验器快速发现，并可通过蒸馏或微调提高领域表现。
2. 大模型适合跨领域综合、长链规划、复杂代码、模糊需求、冲突仲裁和长尾任务。高风险场景仍需证据、规则、工具校验和人工门禁。
3. 典型流水线是“小模型分类与召回→规则过滤→小模型尝试→验证器判定→必要时升级大模型”。升级信号包括低置信、输入分布外、结构化输出失败、工具参数错误、多轮无进展和用户明确要求高质量。
4. 两类模型使用统一请求与结果契约，但Prompt、上下文窗口、Token预算和工具能力分别适配。切换时传递结构化状态与证据，避免把全部对话重复发送。
5. 以任务成功率而非模型单次准确率评估分工，重点监控升级率、误升级、漏升级、P95时延、单位成功成本和大模型调用占比。

| 维度 | 小模型 | 大模型 |
|---|---|---|
| 优势 | 低成本、低时延、高吞吐 | 复杂推理与长尾能力 |
| 任务 | 分类、抽取、改写、初筛 | 规划、综合、仲裁 |
| 风险 | 能力不足、漏升级 | 成本高、时延与幻觉 |

**相关知识点：** 模型级联、能力分层、蒸馏、领域微调、验证器、置信门控、分布外检测、单位成功成本。

#### 4、Prompt Cache 如何设计？
Prompt Cache复用**相同输入前缀的模型计算结果**，用于减少重复Prefill，不等同于缓存最终回答。核心是稳定前缀、严格缓存键和安全失效。

1. 将系统指令、工具Schema和稳定示例放在前部，用户内容和随机字段放在后部；前缀越长、复用越高，收益越大。
2. 键包含供应商、模型版本、Tokenizer、模板、工具Schema、前缀摘要、策略和租户。任何影响Token或行为的变化都须换键，禁止跨权限域复用。
3. 缓存值可为服务侧KV或网关引用。设置TTL、容量、LRU和版本失效；敏感前缀应加密并最小留存。
4. 请求先计算前缀及Token边界；命中则复用，未命中完成Prefill后按长度与复用阈值写入。首次并发用Singleflight防击穿。
5. 监控命中率、命中Token、节省时延与费用、驱逐和误命中。低复用短Prompt不宜缓存。

| 缓存 | 命中依据 | 缓存对象 |
|---|---|---|
| Prompt Cache | 精确前缀/Token序列 | Prefill计算 |
| Semantic Cache | 语义相似请求 | 最终结果 |
| Response Cache | 完全相同请求 | 最终响应 |

**相关知识点：** Prefill、前缀缓存、KV Cache、缓存键、Singleflight、TTL、LRU、缓存击穿、租户隔离、版本失效。

#### 5、如何降低 Token 消耗？
降低Token应从**输入、输出、执行、复用和模型路由**共同治理，并以任务成功率为边界。盲目裁剪会导致重试或模型升级，反而提高成本。

1. 输入侧移除重复指令、无用Schema、日志和无关检索片段；静态内容用引用或Prompt Cache。长对话采用滑窗、分层摘要和结构化状态，并保留事实来源。
2. RAG按步骤检索，以元数据过滤、动态Top-K和Rerank只注入相关证据。Chunk需兼顾完整性与噪声，并去除重复片段。
3. 输出设置Schema、长度、停止条件和`max_tokens`，避免复述、冗长解释与无界代码；机器消费结果优先字段化输出。
4. Agent设置步骤、工具、Reflection、重试和总预算，并检测无进展循环。小模型完成分类与压缩，大模型处理困难节点；升级只传结构化状态。
5. 使用Prompt/Response/Semantic Cache复用，但键须含模型、模板、数据、工具和权限版本。监控缓存命中、重试放大及单位成功Token。

| 层面 | 主要方法 | 风险 |
|---|---|---|
| 输入 | 裁剪、摘要、RAG | 信息丢失 |
| 输出 | Schema、长度和停止条件 | 表达不足 |
| 执行 | 预算、去循环、模型级联 | 过早终止 |
| 复用 | Prompt/语义缓存 | 过期与越权 |

**相关知识点：** Context压缩、动态Top-K、Rerank、Token预算、模型级联、Prompt Cache、Semantic Cache、单位成功Token。

#### 6、Reflection会增加多少Token成本？
Reflection没有固定增幅，取决于**轮数、上下文、Critic长度和是否重写**。一次“生成—评审—重写”会增加输入与输出；每轮重传完整轨迹时，成本会随上下文累积。

1. 可按`总Token=初次生成+Σ(反思输入+输出+修订输入+输出)`核算。反思需携带目标、候选、证据和Rubric，完整重传是主要增量。
2. 规则或小模型自检成本最低；同模型Reflection增加调用；独立大模型Critic加完整重写成本最高，但可降低严重错误与返工。
3. 应看单位成功任务Token。若反思明显提高成功率，增量可能小于重试与人工成本；若任务可程序验证而反思只重复措辞，则收益为负。
4. 仅在低置信、高风险或校验失败时触发；Critic接收最小证据包，输出结构化问题，仅重写失败片段，并限制轮数和预算。
5. 在线记录无反思基线、触发率、每轮Token、修复成功率和净质量增益，通过A/B按任务类型确定是否开启。

| 方式 | Token增量 | 适用 |
|---|---|---|
| 规则/小模型检查 | 低 | 格式与确定性约束 |
| 同模型Reflection | 中 | 一般复杂生成 |
| 独立Critic+重写 | 高 | 高价值高风险任务 |

**相关知识点：** Reflection、Critic、Token成本分解、触发率、局部重写、评审预算、单位成功Token、A/B测试。

#### 7、如何控制反思带来的延迟？
控制Reflection延迟的核心是**按风险触发、缩小范围、并行校验和设置硬Deadline**。所有请求串行“生成—反思—重写”会显著增加总时延。

1. 门控器按风险、置信度、格式、证据覆盖和历史失败率决定是否反思。低风险且校验通过则返回，高风险或低置信才进入Critic。
2. 生成时并行运行Schema、引用、代码测试和安全规则；确定性校验足够时不调用LLM Critic。独立评审可并行，只等待必要结果。
3. Critic只接收目标、候选输出、关键证据和Rubric，不重传完整对话；要求返回结构化问题位置、级别与修复建议。修订只重写失败段落或工具参数，避免整篇重新生成。
4. 为反思设置首轮和总Deadline、最大轮数、Token及费用预算。接近SLA时可切换小模型Critic、减少检查项或异步执行非关键评审；高风险门禁不可因超时静默绕过，应暂停或人工接管。
5. 可先流式输出草稿，但涉及金融、生产操作等场景必须评审后再提交副作用。用P50/P95增量时延、触发率、修复率和单位质量增益评估策略。

| 策略 | 时延收益 | 风险 |
|---|---|---|
| 条件触发 | 避免无效反思 | 漏检 |
| 并行校验 | 缩短关键路径 | 资源增加 |
| 局部修订 | 减少生成时间 | 上下文衔接 |
| 异步评审 | 不阻塞主响应 | 不适合强门禁 |

**相关知识点：** Reflection Gate、关键路径、并行校验、局部重写、Deadline、SLA、异步评审、质量门禁。

#### 8、什么场景适合关闭Reflection？
适合关闭Reflection的任务具有**低风险、边界清晰、结果可确定性验证、时延敏感且反思增益很低**等特征。关闭不等于取消质量控制，而是用规则、Schema、测试或业务系统校验替代概率性的自我评审。

1. 意图分类、字段抽取、固定格式转换、简单查询改写等任务，若有严格Schema、枚举和范围校验，Reflection通常只会重复确认；模型一次通过即可交付。
2. 结果完全由权威工具产生，例如数据库查询、计算器、库存接口或编译器输出，LLM只负责组装调用时，应校验参数和工具结果，而不是让模型重新猜测事实。
3. 实时补全、搜索联想等低延迟场景，若错误可撤销且用户能纠正，可关闭同步Reflection，改为异步抽检。
4. 输入输出很短、任务分布稳定、离线评测与线上监控显示反思修复率长期接近零，且新增成本和P95明显高于质量收益时，应关闭。判断必须按任务类型切片，不能用全局平均。
5. 达到硬Token或费用预算时可以关闭非关键反思，但高风险操作、不可逆副作用、证据冲突、低置信和分布外输入不应因预算静默绕过门禁；应暂停、降级为只读或转人工。

| 场景 | 是否关闭 | 替代控制 |
|---|---|---|
| 确定性可验证 | 是 | Schema、规则、测试 |
| 极低延迟低风险 | 条件式 | 异步抽检 |
| 高风险不可逆 | 否 | Critic与人工门禁 |
| 低置信/分布外 | 否 | 升级模型或澄清 |

**相关知识点：** Reflection Gate、确定性校验、异步抽检、分布外检测、风险分级、质量增益、预算门禁。

#### 9、如何设计轻量级Reflection机制？
轻量Reflection应采用**确定性检查优先、最小输入、结构化缺陷和局部修复**，在一次短调用中发现高价值错误，避免完整重写。

1. 按任务定义Rubric，仅保留Schema、引用、数值、参数和硬约束等可行动项。能程序验证的交给规则、测试或数据库，不交给LLM。
2. 仅在低置信、格式失败、证据不足或抽检时触发。Critic可用小模型，输入只含目标、候选、关键证据与Rubric。
3. 输出固定为`pass、issues[]、severity、location、evidence、patch`。无Blocking问题直接通过；否则只修订对应字段或参数，禁止整篇重写。
4. 设置单轮、短`max_tokens`、Deadline和费用上限。修订仍失败则升级模型或人工，而非循环；用指纹避免重复评审。
5. 对比无反思基线，监控触发率、误报率、修复成功率、增量P95和单位修复成本，以A/B迭代Rubric与阈值。

| 维度 | 轻量Reflection | 完整Reflection |
|---|---|---|
| 输入 | 最小证据包 | 完整上下文 |
| 输出 | 结构化缺陷/Patch | 长篇评审与重写 |
| 轮数 | 通常一轮 | 可能多轮 |
| 适用 | 常规质量检查 | 复杂高价值任务 |

**相关知识点：** Rubric、确定性校验、最小证据包、结构化Critic、局部Patch、循环控制、质量基线、A/B。

#### 10、Reflection和Self-Consistency如何结合使用？
Self-Consistency以**多条推理路径降低偶然性**，Reflection负责**检查并修复候选缺陷**；应先生成少量候选并聚合，只对低置信或高风险结果反思。

1. 复杂任务用不同种子、温度或视角生成`k`个候选；工具和副作用必须在沙箱或只读模式，禁止多路径写生产资源。
2. 先用Schema、测试、计算和引用回查淘汰无效项；离散答案多数表决，连续值稳健统计，开放生成按证据与约束评分。
3. 一致性高且验证通过时直接采用，避免Reflection；候选分歧大、最高分与第二名差距小、证据冲突或任务风险高时，将聚合结果、少数关键候选和证据交给Critic。
4. Critic分析事实、假设、计算或约束分歧，并输出局部修复或补证要求。仍无法消解则升级模型、调用工具或转人工。
5. 设置候选数、并行度、Reflection轮数、Token和Deadline预算。通过`质量增益/(新增候选成本+评审成本)`评估组合，只在高不确定性、高价值任务启用。

| 机制 | 主要作用 | 局限 |
|---|---|---|
| Self-Consistency | 降低单路径随机错误 | 成本随候选数增加 |
| Reflection | 定位并修复缺陷 | 可能自评偏差 |
| 确定性验证 | 提供客观门禁 | 覆盖范围有限 |

**相关知识点：** Self-Consistency、多样性采样、多数表决、稳健聚合、Reflection、分歧门控、确定性验证、预算控制。

#### 11、如何设计Agent自动反思与自修复机制？
自动反思与自修复应构建**“执行—验证—归因—修复—再验证”**有界闭环，由验证器和状态机控制，LLM只提出诊断与修复方案。

1. 每个节点声明Schema、前后置条件、幂等键、错误分类和补偿。执行后先运行规则、测试、引用回查和状态查询，再决定是否触发Critic。
2. Critic接收目标、计划版本、失败步骤、证据和副作用状态，完成错误分类并给出结构化Patch，不允许直接操作生产资源。
3. 参数或局部内容错误可原位修补；知识缺失重新检索；计划假设失效由Planner生成新版本；瞬时错误有限重试；权限错误终止或审批；结果未知先查询，禁止重放非幂等副作用。
4. 修复在沙箱或事务边界执行，只重做受影响节点。每轮后重验；状态指纹重复即判定停滞，达到轮数、Token或时间上限后转人工。
5. 全链记录原计划、错误归因、Patch、验证证据与状态变化。用自动修复率、误修复率、回归率、平均恢复时间和单位修复成本评估，策略通过离线回放和灰度发布。

| 错误类型 | 自动动作 | 限制 |
|---|---|---|
| 参数/局部输出 | Patch后重验 | 不扩大范围 |
| 计划错误 | 版本化重规划 | 复用已完成节点 |
| 瞬时故障 | 有界重试 | 幂等与预算 |
| 权限/状态未知 | 审批或查询 | 禁止绕过与盲重试 |

**相关知识点：** Reflection、验证器、失败归因、版本化重规划、状态指纹、幂等、补偿、沙箱、MTTR。

#### 12、如何利用LLM-as-a-Judge进行失败归因？
LLM-as-a-Judge适合做**轨迹语义分类和证据归纳**，但不能作为唯一事实裁判。应先用确定性信号定界，再按Taxonomy输出结构化归因，并以人工样本校准。

1. 建立失败分类：需求、计划、路由、检索、工具参数/执行、模型生成、验证、权限和依赖，并允许`unknown`及主次原因。
2. 证据包含目标、计划、模型与Prompt版本、文档ID、工具状态、节点状态、验收结果和Trace。敏感信息脱敏，不能只给最终答案。
3. 固定Rubric，返回`primary_cause、secondary_causes、evidence_refs、confidence、owner`。引用须指向轨迹事件；无证据则降置信或输出unknown。
4. HTTP错误、Schema失败和超时由规则标注，Judge只分析语义。可用多Judge检查一致性，但需防同源偏差；高风险样本转人工。
5. 用黄金集评估Precision、Recall、混淆矩阵、校准误差和版本稳定性。Judge变更先离线回放与Shadow；归因用于改进，不能自动放宽安全策略。

| 信号 | 首选归因方式 |
|---|---|
| 状态码、超时、Schema | 规则 |
| 需求、计划、语义错误 | LLM Judge |
| 高风险争议 | 人工复核 |

**相关知识点：** LLM-as-a-Judge、失败Taxonomy、Rubric、证据引用、置信校准、混淆矩阵、同源偏差、Shadow。

#### 13、如何判断一个任务应该走大模型还是小模型？
判断应基于**复杂度、风险、模态、上下文、可验证性和SLA**，采用硬过滤加级联升级，而不是依赖关键词或用户身份。默认选择能达到质量阈值的最小模型，困难或高风险任务再升级。

1. 请求特征包括指令数量、约束冲突、推理步骤、输入长度、代码/数学信号、所需工具、模态、数据等级、输出Schema、P95目标与预算。轻量分类器结合历史标注预测复杂度与小模型成功概率。
2. 安全、地域、上下文和能力属于硬约束：小模型不支持视觉、工具、所需窗口或合规部署时直接排除。高风险操作即使使用大模型，也必须有规则、证据和人工门禁，模型大小不替代安全控制。
3. 高成功概率、结构化、可程序校验、低风险、短上下文任务走小模型；跨领域综合、模糊需求、长链规划、复杂代码、低样本长尾和证据冲突优先大模型。
4. 边界任务使用小模型先行，Schema失败、低置信、检索证据不足、工具参数错误、多轮无进展或用户重试触发大模型。升级只传结构化状态与关键证据，减少重复Token。
5. 用离线能力曲线确定阈值，线上记录小模型一次成功率、升级率、漏升级、误升级、P95和单位成功成本。策略通过Shadow和灰度校准，并按任务类型分别设置。

| 条件 | 小模型 | 大模型 |
|---|---|---|
| 复杂度 | 低、规则稳定 | 高、开放推理 |
| 验证 | 程序可验 | 语义评审为主 |
| 风险 | 低且可逆 | 高价值但仍需门禁 |
| 长尾 | 常见分布 | 分布外与冲突 |

**相关知识点：** 复杂度分类、成功概率、硬约束、级联升级、分布外、置信门控、漏升级、单位成功成本。

#### 14、模型路由策略是规则驱动还是模型驱动？
生产系统应采用**规则硬过滤、模型软判断、运行时校验升级**的混合路由。规则负责安全合规，分类器或LLM理解语义与复杂度，单一方式均有缺口。

1. 规则依据租户、数据等级、地域、模态、上下文、Tool能力、预算、SLA和熔断状态判断，低延迟且可审计；缺点是难覆盖同义表达与复杂组合。
2. 模型路由通过轻量分类器、Embedding检索或LLM读取请求，预测任务类型、难度和候选模型成功概率，语义泛化更强；但存在误分类、漂移、额外成本和不可解释性，不能决定数据是否允许出域。
3. 混合流程先用Policy排除不合规、能力不足和不可用模型，再让模型在安全候选中排序；最高分低于阈值或前两名差距过小时，选择保守模型、澄清或小模型试运行。
4. 执行结果由Schema、事实证据、工具状态和业务规则验证，失败触发升级，而非让Router一次决定最终质量。高风险请求固定路由或人工审批，禁止Bandit自由探索。
5. 以路由准确率、严重误路由率、升级率、SLA和单位成功成本评估。策略、特征和模型版本必须记录，新版本通过离线回放、Shadow、灰度与回滚发布。

| 维度 | 规则路由 | 模型路由 |
|---|---|---|
| 确定性/审计 | 强 | 较弱 |
| 语义泛化 | 弱 | 强 |
| 延迟成本 | 低 | 较高 |
| 适用 | 安全与硬约束 | 复杂度与语义排序 |

**相关知识点：** 混合路由、Policy、分类器、Embedding Router、置信门控、Bandit、严重误路由、Shadow。

#### 15、如何自动判断一个任务的复杂度等级？
任务复杂度应由**可观测特征、分类器和执行反馈**共同判断，输出概率而非绝对标签。复杂度不等于文本长度，短问题也可能需要深推理。

1. 特征包括约束数量、冲突、预计步骤、Token、跨文档依赖、代码/数学信号、模态、工具、Schema、领域稀有度、风险和可验证性。
2. 先用规则识别确定边界，例如视觉任务、超长上下文、生产写操作或特定工具要求；其余请求由轻量分类器、Embedding近邻或小型Router模型预测`P(simple/medium/complex)`。训练标签来自人工标注与历史任务结果，而非模型自评。
3. 标签定义应可执行：简单任务由小模型一次完成且可校验；中等任务需要检索、少量工具或有限推理；复杂任务涉及多阶段规划、冲突证据、跨领域、分布外或高风险。
4. 预测不确定时用小模型试运行，依据Schema、置信、工具参数和验证结果动态升级。将重试、步骤、Token与最终结果回写以校准分类器。
5. 评估使用各等级Precision/Recall、严重低估率、升级率、校准误差、SLA和单位成功成本。低估高风险任务的代价通常高于误升，因此阈值应按风险分层。

| 等级 | 典型特征 | 默认策略 |
|---|---|---|
| 简单 | 单目标、可校验 | 小模型 |
| 中等 | 检索/工具/有限推理 | 中档或级联 |
| 复杂 | 多阶段、冲突、长尾 | 大模型与验证 |

**相关知识点：** 复杂度分类、特征工程、置信校准、试运行升级、概念漂移、严重低估率、成本敏感分类。

#### 16、模型路由层如何实现实时决策？
实时路由应采用**本地特征、内存策略、低延迟评分和原子快照**，避免每次请求访问远端系统或大型LLM，实现毫秒级、可降级决策。

1. 请求提取任务、Token、模态、SLA、预算、数据等级、租户和能力；模型健康、P95、配额及价格由后台更新本地缓存，在线只读快照。
2. Policy Engine先用编译规则或决策表完成权限、地域、上下文、功能、预算和熔断硬过滤。若候选为空，立即返回澄清、私有模型、排队或明确失败，禁止绕过安全条件。
3. 对候选使用线性效用、GBDT或小型分类器预测成功概率与成本；复杂语义可调用轻量Router模型，但须设置严格Deadline，超时回退到规则默认。高风险流量不参与在线探索。
4. 选择结果与备用序列交给Executor。低置信、Schema失败、限流或慢调用时按策略升级；以Singleflight、连接池和批量遥测降开销。
5. 策略通过控制面发布不可变版本，数据面原子切换并保留旧版回滚。每次记录特征摘要、过滤、分数、版本和耗时，监控路由P99、缓存陈旧、候选为空率、误路由与单位成功成本。

| 在线阶段 | 延迟控制 |
|---|---|
| 特征 | 本地解析、预计算 |
| 策略 | 编译规则、内存快照 |
| 排序 | 轻量模型/效用函数 |
| 状态 | 异步刷新、版本化 |

**相关知识点：** 路由数据面、控制面、Policy Engine、配置快照、GBDT、Singleflight、原子发布、路由P99。

#### 17、如何设计模型能力评估体系？
模型能力评估应是**按任务、版本和约束切片的多维体系**，不能以单一Benchmark替代。需覆盖质量、时延、成本、安全和部署边界。

1. 按业务建立评测集，覆盖推理、代码、抽取、视觉、RAG忠实度、结构化输出和Tool Calling，并加入长尾、对抗及分布外样本。指标包括成功率、Pass@k、格式率和人工Rubric。
2. 服务维度测量TTFT、TPS、P95/P99、并发、可用率和错误；成本记录输入、输出、缓存单价及单位成功任务成本。
3. 边界记录上下文、模态、工具/JSON、地域、数据留存、部署和配额。安全评测覆盖提示注入、越权、隐私泄露和拒答质量。
4. 离线评测使用相同Prompt、工具Mock、采样参数和硬件条件，多次运行估计方差；模型版本、Tokenizer和模板必须固定。在线通过Shadow、Canary和A/B观察真实分布，并防用户选择偏差。
5. 画像按版本更新，保存样本结果、置信区间和退化告警。Router只用具备统计显著性和新鲜度的特征，高风险场景看最差切片。

| 评估维度 | 代表指标 |
|---|---|
| 质量 | 任务成功率、Pass@k、忠实度 |
| 性能 | TTFT、TPS、P95、并发 |
| 经济 | 单价、单位成功成本 |
| 安全与边界 | 越权率、地域、留存、功能 |

**相关知识点：** 能力评估、业务评测集、Pass@k、TTFT、TPS、置信区间、Shadow、Canary、分布外评测。

#### 18、小模型升级到大模型的触发条件有哪些？
升级应由**能力缺口、运行失败、不确定性和业务风险**触发，并设置去抖、预算和次数。不能仅凭模型自报低置信升级。

1. 调用前硬触发包括不支持模态、上下文、Tool Calling、结构化输出、语言或安全部署；跨域、多阶段、复杂代码、分布外或高风险任务可直接用大模型。
2. 运行时触发包括Schema/JSON多次失败、工具参数非法、引用缺失、确定性测试不通过、检索证据冲突、答案与权威数据不一致、无进展循环或达到小模型重试上限。
3. 不确定性应使用校准概率、候选分差、Self-Consistency分歧或历史成功率，而非单个Logprob。低置信且高影响时优先升级。
4. 用户重试、明确要求高质量、付费等级或严格SLA可以影响效用权重，但不得覆盖数据地域、权限和预算硬约束。升级前检查大模型是否在剩余Deadline与预算内可完成。
5. 升级只传目标、失败节点、关键证据、已完成工具结果和验收标准，保留TaskID与幂等键。相同错误不得来回升降；记录触发器、修复结果和额外成本，评估漏升级、误升级与单位质量增益。

| 触发类别 | 示例 |
|---|---|
| 能力缺口 | 模态、上下文、工具不支持 |
| 验证失败 | Schema、测试、事实冲突 |
| 不确定性 | 校准置信低、候选分歧 |
| 风险与价值 | 高影响、严格质量要求 |

**相关知识点：** 模型升级、硬触发、置信校准、分布外检测、验证器、升级去抖、漏升级、误升级。

#### 19、如何衡量模型升级带来的ROI？
模型升级ROI应比较**增量业务收益与增量总成本**，而非只看Benchmark。升级会增加Token、P95和评审成本，只有产生可归因净收益才值得上线。

1. 建立基线，按任务、用户价值、风险和长度统计成功率、返工、人工接管、转化、事故损失、P95和单位成功成本，以切片定位提升。
2. 新模型先经黄金集、历史回放和Shadow，再做稳定分桶A/B。除模型外保持Prompt、RAG、Tool和采样参数一致，并报告置信区间。
3. 增量收益包括成功率提高带来的收入、人工节省、返工下降和风险损失减少；增量成本包括输入输出Token、缓存变化、推理基础设施、延迟导致的流失、迁移适配、评测及运维。
4. 可用`ROI=(增量收益−增量成本)/增量成本`，同时计算每增加一个成功任务的边际成本。若提升仅集中于少量复杂请求，应采用路由按需升级，而非全量替换。
5. 设置质量、安全、P95和预算护栏；严重错误可否决平均正ROI。上线后监控漂移、价格与升级占比，达到阈值自动降级。

| 维度 | 代表量 |
|---|---|
| 质量收益 | 增量成功率、返工下降 |
| 业务收益 | 转化、留存、人工节省 |
| 直接成本 | Token、算力、缓存 |
| 间接成本 | 时延、迁移、运维、风险 |

**相关知识点：** ROI、TCO、增量收益、单位成功成本、边际成本、稳定分桶、Shadow、护栏指标、置信区间。

#### 20、如何设计模型降级和熔断机制？
模型熔断负责**隔离不健康依赖**，降级负责提供有限服务；两者须与限流、重试预算和备用矩阵协同，避免重试风暴。

1. 按供应商、模型、区域和租户隔离统计窗口，以错误率、超时率、慢调用、连续失败和最小样本触发。参数、鉴权及策略拒绝单独告警。
2. Closed状态正常放行；超过阈值进入Open并快速失败；冷却后进入Half-Open，仅允许受控少量探测。探测请求应低风险、可幂等且覆盖真实功能，连续成功后逐步恢复，失败则重新Open。
3. 降级链按同能力备用、较弱模型加功能裁剪、缓存/模板、异步排队、人工或明确失败排列。备用模型须满足上下文、模态、Tool、Schema、地域和数据安全；高风险写操作能力不足时必须暂停。
4. 请求在熔断前只进行有限退避重试，并共享端到端Retry Budget；切换保留TaskID、幂等键和结构化状态，限制最大跳数，防止模型A、B之间循环。流式中断不得无标记拼接。
5. 监控熔断频率、Open时长、Half-Open成功率、降级质量、SLA和切换振荡；阈值经故障演练校准，配置可回滚。

| 机制 | 触发依据 | 作用 |
|---|---|---|
| 限流 | 流量/配额 | 控制入口 |
| 熔断 | 健康指标 | 隔离故障 |
| 降级 | 主能力不可用 | 保留有限服务 |
| 备用切换 | 兼容且健康 | 恢复完整能力 |

**相关知识点：** 熔断状态机、Half-Open、慢调用率、Retry Budget、能力兼容矩阵、功能裁剪、切换振荡。

#### 21、模型故障时如何实现无感切换？
“无感”指**业务目标和接口契约连续**，而非逐字一致。实现依赖统一Gateway、兼容备用、幂等状态和结果校验；副作用或流式内容须显式处理。

1. 统一Message、Tool、JSON Schema、流事件和错误协议以隔离厂商差异。Adapter不静默删除参数；Registry维护上下文、模态、工具、安全与地域矩阵。
2. 请求生成TaskID、幂等键和Deadline，保存模板版本、结构化上下文、工具结果与完成步骤。备用复用幂等键，避免重复副作用。
3. 建连或首Token前失败可直接切换；流式输出后不能拼接另一模型Token，应从稳定检查点重生成，由客户端按Sequence替换版本。
4. 切换时重算Tokenizer、上下文、`max_tokens`和工具能力；超限则受控裁剪。备用结果仍须通过Schema、事实、后置条件和安全校验。
5. 以Shadow验证主备差异，Canary演练切换。监控成功率、TTFT、质量差、重复副作用和Token放大；恢复后渐进切回。

| 故障阶段 | 切换策略 |
|---|---|
| 调用前/首Token前 | 直接调用兼容备用 |
| 流式输出中 | 检查点重生成并版本替换 |
| 工具副作用后 | 状态查询、幂等续作 |
| 能力不兼容 | 功能降级或人工 |

**相关知识点：** 统一Gateway、能力兼容矩阵、幂等键、Sequence、检查点、Tokenizer差异、Shadow、渐进切回。

#### 22、如何避免模型频繁升级导致成本失控？
避免频繁升级需要**校准阈值、设置迟滞和次数、复用状态并实施预算门禁**。升级应是有证据的能力提升，而非模型间来回震荡。

1. 优先使用Schema、测试、事实冲突和工具错误等客观信号，模型置信须校准并结合风险。单次轻微失败不升级，可要求多个信号越阈值。
2. 使用Hysteresis：升级阈值高于保持当前模型的阈值；同一Task升级后锁定能力档位一定时间或步骤，禁止自动降回再升。设置最大升级层数和每任务切换次数，命中后人工或明确失败。
3. 升级只重做失败节点，传递目标、关键证据、工具结果和验收标准，不重发完整对话或重跑成功副作用。相同输入与策略的升级结果可短期缓存，防用户重试重复消耗。
4. 执行前估算升级后的剩余Token、费用和Deadline，软预算触发摘要、短输出或中档模型，硬预算要求审批或终止。高风险任务不能为了省钱绕过必要门禁，但可提前直接选择合适模型，避免先小后大双重成本。
5. 监控升级率、连续升级、误升级、升级修复率、增量Token和单位质量增益，按任务切片调整阈值。新触发器先离线回放和Shadow，防分布变化造成全量升级。

| 控制 | 作用 |
|---|---|
| 迟滞/冷却 | 防止档位震荡 |
| 最大升级次数 | 限制最坏成本 |
| 局部续作 | 避免重复上下文与副作用 |
| 预算门禁 | 阻止费用越界 |

**相关知识点：** Hysteresis、置信校准、升级锁定、局部续作、预算门禁、误升级、增量Token、Shadow。

#### 23、Prompt压缩有哪些常见方案？
Prompt压缩应删除**冗余、低相关和可外部引用的信息**，保护目标、硬约束、权限、事实与输出契约。不能简单截断，须保留来源并验证。

1. 规则压缩包括指令去重、合并示例、删除日志噪声和使用Schema；工具说明按需加载，不把全部Tool注入。该方法确定且便宜。
2. Extractive选择关键句、实体、约束和证据，适合高风险材料，但可能不连贯。Abstractive更短却可能遗漏或幻觉，须保留来源与未决项。
3. RAG只召回相关Chunk，并结合元数据、动态Top-K和Rerank；长对话使用滑窗、阶段摘要、结构化状态和长期Memory分层。
4. Token级压缩可用小模型按目标保留信息，也可将大对象外置，仅传URI、摘要和权限令牌。Prompt Cache不减Token，但可降低重复Prefill。
5. 建立不可压缩字段清单，压缩后执行Schema、事实、引用及任务回归；以压缩率、召回率、质量差和重试放大评估。

| 方法 | 优势 | 风险 |
|---|---|---|
| 规则去重 | 确定、低成本 | 覆盖有限 |
| 抽取式 | 事实保真 | 连贯性较弱 |
| 生成式摘要 | 压缩率高 | 遗漏与幻觉 |
| RAG按需注入 | 动态相关 | 召回失败 |

**相关知识点：** Prompt压缩、Extractive、Abstractive、动态Top-K、Rerank、结构化状态、Prompt Cache、压缩回归。

#### 24、Context裁剪如何避免关键信息丢失？
Context裁剪应采用**信息分级、依赖感知、来源保留和裁后校验**，而非只留最近N轮。目标、约束、权限、事实、未决项和计划依赖须固定保护。

1. 将上下文拆为策略、目标、状态、证据、历史、工具轨迹和噪声，并记录来源、版本、时间、敏感级别和关联节点。先删重复、过期及无依赖内容。
2. 使用Dependency-aware裁剪，从当前节点反向遍历输入、约束和证据形成最小闭包。工具大结果外置，只保留摘要、关键字段、哈希和URI。
3. 长对话按阶段生成结构化Summary，含决策、事实、偏好、失败与待办；数字、否定和权限应保留原文片段或确定性字段。
4. RAG召回采用元数据过滤、动态Top-K和Rerank，并保留一定多样性，防相似片段挤掉反例。预算不足时优先缩短低价值证据，而不是截断每段开头。
5. 裁剪后检查计划输入、引用可达、硬约束和摘要一致性，并用成功率、关键事实召回、引用缺失、重试及Token节省评估。

| 优先级 | 内容 | 策略 |
|---|---|---|
| 必保留 | 目标、约束、权限、当前状态 | 固定保护 |
| 高 | 当前证据与依赖 | 按引用闭包 |
| 中 | 历史决策 | 结构化摘要 |
| 低 | 重复日志、无关闲聊 | 删除 |

**相关知识点：** Context裁剪、依赖闭包、结构化Summary、RAG、动态Top-K、来源引用、完整性校验、Token预算。

#### 25、Semantic Cache如何设计？
Semantic Cache按**请求语义等价性**复用已验证结果，但风险高于精确缓存。核心是规范化表示、分层召回、任务阈值、版本权限隔离和新鲜度校验。

1. 写入项含规范化请求、Embedding、任务、约束、响应、模型/Prompt/知识版本、租户、权限、TTL、质量分和证据。仅缓存通过验证的低风险结果。
2. 先按租户、任务、语言、数据域、权限和版本硬过滤，再向量召回；以Cross-Encoder或规则比较实体、数值、时间、否定词和格式，避免条件错配。
3. 阈值按任务校准：FAQ可宽松，价格、库存、权限和法律结果应高阈值、短TTL或禁用。命中后重验版本、资源与权限，过期则回源。
4. 写入前执行安全、来源和质量门禁；键值加密、租户隔离，删除同步失效。热点Key用Singleflight防击穿，以LRU/LFU管理容量。
5. 监控召回命中、可用命中、误命中、节省Token、陈旧率和质量差；先用Shadow评估，再逐任务灰度。

| 缓存 | 匹配方式 | 主要对象 |
|---|---|---|
| Prompt Cache | 精确前缀 | Prefill计算 |
| Response Cache | 精确请求键 | 最终响应 |
| Semantic Cache | 语义相似+约束 | 最终响应 |

**相关知识点：** Semantic Cache、Embedding、Cross-Encoder、TTL、版本失效、缓存投毒、Singleflight、误命中、租户隔离。

#### 26、RAG与大上下文模型如何取舍？
RAG与大上下文是**检索筛选与阅读容量**的组合。知识规模大、更新频繁、需权限和引用时优先RAG；材料有限且需全局关系时可用大上下文。

1. RAG分块、索引并召回少量证据，Token低、更新快、可做权限和引用；风险是Chunk边界、查询、Top-K和Rerank造成漏召回。
2. 大上下文可读取完整材料并保留跨段关系；但Attention、KV Cache、费用和时延上升，且“放得下”不等于能有效利用，还存在上下文污染。
3. 选型依据包括语料总量、单次相关比例、更新频率、权限粒度、跨文档推理、SLA和预算。相关内容比例低时RAG更优；几份文档整体比较或需全局结构时大上下文更合适。
4. 常采用Hybrid：先用元数据和混合检索缩小候选，再将相关章节放入窗口；关键问题增加Rerank、引用回查和缺失检测。
5. 使用端到端任务成功率、证据Recall、忠实度、P95、Token和单位成功成本比较，评测必须包含跨段、反例、更新和权限样本。

| 维度 | RAG | 大上下文 |
|---|---|---|
| 成本 | 按需注入，较低 | 随长度增长 |
| 更新/权限 | 灵活 | 需重新组装输入 |
| 全局关系 | 受召回限制 | 较有优势 |
| 主要风险 | 漏召回 | 污染与利用不足 |

**相关知识点：** RAG、大上下文、Hybrid检索、Rerank、证据Recall、Lost-in-the-Middle、KV Cache、忠实度。

#### 27、如何建立模型质量评分体系？
模型质量评分应是**任务级、多维、可校准且带安全门槛**的体系，不能把能力压成无解释总分。排序、发布与路由须检查关键切片和严重错误。

1. 按业务任务建立黄金集，覆盖常见、长尾、对抗、分布外和高风险样本，并记录语言、长度、领域、工具和风险标签。训练/调参与最终测试隔离，防止Prompt或模型针对测试集过拟合。
2. 指标分为正确性、完整性、忠实度、格式、工具成功、安全和用户价值。确定答案使用Exact Match、F1、Pass@k和单元测试；开放生成使用清晰Rubric的人工或Judge评分，并要求证据引用。
3. 每个任务先归一化维度，再按业务价值配置权重；安全越权、严重事实错误等采用硬门槛而非被平均分抵消。报告均值、分位数、置信区间及最差关键切片。
4. LLM Judge需用人工标注集校准偏差、顺序效应和自家模型偏好，可采用盲评、交换顺序及多Judge一致性。线上信号如点赞和重试受选择偏差影响，只作为补充。
5. 评分与模型、Prompt、RAG、Tool和策略版本绑定，定期回归并监控漂移。最终结合P95和单位成功成本形成路由效用，但质量原始分和经济分应分别保留。

| 层次 | 指标示例 |
|---|---|
| 结果质量 | 准确率、F1、Pass@k |
| 过程质量 | Tool成功、引用覆盖 |
| 安全 | 越权率、严重错误率 |
| 业务 | 完成率、人工接管率 |

**相关知识点：** 黄金集、Rubric、Pass@k、LLM Judge、置信区间、关键切片、安全门槛、评测漂移。

#### 28、如何实现在线A/B测试与灰度发布？
在线A/B与灰度发布应以**用户或会话稳定分桶、端到端任务指标和安全护栏**为核心。不能在同一会话中随机切换模型，否则上下文和用户行为会污染因果判断；灰度用于控制风险，A/B用于估计效果。

1. 先定义假设、主指标、护栏指标和最小可检测效应。主指标可为任务成功率、一次解决率或业务转化；护栏包括严重错误、安全事件、P95、Token、单位成功成本和用户投诉。
2. 随机化单元选择用户、会话或租户，并通过哈希稳定分桶；控制Prompt、工具、RAG数据、参数和UI一致，只改变模型或明确策略。跨用户网络效应明显时采用集群随机化。
3. 上线前做离线黄金集和Shadow；再按内部用户、白名单租户、1%、5%、20%逐级Canary。每级设置观察窗口和自动回滚阈值，高风险请求固定到已验证版本。
4. 样本量按基线、显著性、统计功效和MDE估算，覆盖峰谷及主要任务切片。避免提前窥视随意停止；多指标和多版本比较需控制多重检验。
5. 分析总体及语言、任务、长度、风险与用户层级切片，报告置信区间。胜出版本仍需渐进放量，保留一键回滚和长期Holdout，监控新奇效应与模型漂移。

| 阶段 | 用户影响 | 目标 |
|---|---|---|
| 离线/Shadow | 无 | 质量与兼容 |
| Canary | 少量 | 风险控制 |
| A/B | 有 | 因果评估 |
| 全量+Holdout | 大 | 长期收益监控 |

**相关知识点：** 稳定分桶、MDE、统计功效、Shadow、Canary、Holdout、护栏指标、多重检验、自动回滚。

#### 29、企业级模型网关需要具备哪些能力？
企业级Gateway是**统一协议、路由、安全、可靠执行、成本和审计**入口，不只是API代理；它将模型差异和企业治理从Agent解耦。

1. 接入层统一Message、Tool、JSON、流事件和错误，通过Adapter连接商业、开源及私有模型；Registry维护版本、上下文、模态、地域、价格和健康。
2. 路由先按数据、权限、地域、功能和预算过滤，再按质量、P95、成本与健康排序，支持模型级联、备用、Shadow和灰度，并生成Decision Record。
3. 安全层集成IAM、RBAC/ABAC、短期凭据、DLP、脱敏、Egress白名单和租户隔离；机密数据只进批准模型，日志最小留存。
4. 执行层统一Deadline、取消、限流、重试预算、熔断、降级、缓存和背压。任务携带TaskID与幂等键，防副作用重复。
5. 治理层记录Token、费用、TTFT、P95、错误、缓存和质量，按租户/Agent/任务归因并告警；Trace、配置版本和策略回放支持审计。

| 能力域 | 核心功能 |
|---|---|
| 接入 | Adapter、统一协议、Registry |
| 决策 | 路由、级联、实验 |
| 安全 | IAM、DLP、Policy、隔离 |
| 运行 | 限流、熔断、缓存、流式 |
| 治理 | 计费、观测、审计 |

**相关知识点：** Model Gateway、Model Registry、ABAC、DLP、智能路由、重试预算、Decision Record、AI FinOps。

#### 30、哪些模型 API 错误可以重试，哪些不能重试？
是否重试取决于**错误是否瞬时、请求幂等性、剩余Deadline和服务端状态**，不能只看HTTP码；超时可能发生在建连前或副作用之后。

1. 可重试项包括连接重置、网络瞬断、部分`500/502/503/504`、过载和限流。遵循`Retry-After`，使用退避、抖动和端到端Retry Budget。
2. `400`参数错误、`401`凭据无效、`403`权限或策略拒绝、能力不存在及安全拒绝不可原样重试；应修正、授权、换合法能力或终止。`404`需看一致性语义。
3. `429`在配额可恢复且Deadline允许时重试；额度耗尽则切换批准备用或失败。超时须区分连接、首Token、Chunk空闲和总时长，并查询状态。
4. 只读生成通常可重试，但流式输出须按Sequence去重；Tool Calling或写操作必须带业务幂等键。状态未知且不可查询时转人工。
5. 重试前检查熔断、健康和预算；持续故障进入降级。监控各阶段重试成功率、放大倍数、额外Token和重复副作用。

| 错误 | 默认重试 | 处理 |
|---|---|---|
| 网络、临时5xx | 是，有界 | 退避与抖动 |
| 429 | 条件式 | Retry-After/备用 |
| 参数、权限、策略 | 否 | 修正或终止 |
| 超时状态未知 | 先核验 | 续作、补偿或人工 |

**相关知识点：** 错误分类、Retry-After、指数退避、Jitter、Retry Budget、幂等、状态核验、重试放大。

#### 31、熔断阈值应该如何设置？
熔断阈值应依据**历史基线、SLO、最小样本和错误类型**设置，不能直接照搬固定“50%错误率”。阈值过敏会频繁切换，过钝会拖垮连接池并放大重试；应按模型、区域和调用类型独立配置。

1. 使用滚动时间窗或计数窗，至少同时观察失败率、超时率、慢调用比例、连续失败和请求量。只有达到最小调用数后才按比例触发，低流量时可用连续失败或贝叶斯置信方法防小样本误判。
2. 错误分类需加权：连接拒绝、`5xx`和超时反映供应商健康；参数、鉴权、内容策略和业务校验错误不应计入同一熔断器，否则客户端Bug会错误隔离健康模型。
3. 慢调用阈值由P95/P99 SLO与端到端Deadline决定，例如单模型耗尽大部分剩余时间即视为失败。高成本请求还可按单位时间Token浪费或队列饱和触发容量熔断。
4. Open冷却时间采用指数增加并设上限；Half-Open只放少量、低风险、幂等且有代表性的探测请求。按探测成功率和延迟连续满足窗口后渐进恢复，失败立即回Open。
5. 初始阈值从历史分布和故障演练得到，再监控误熔断率、故障发现时间、Open时长、探测成功和切换振荡。配置版本化，按峰谷自适应但限制变化幅度。

| 参数 | 作用 |
|---|---|
| 最小样本 | 防低流量误判 |
| 错误/超时率 | 检测不可用 |
| 慢调用率 | 防资源被拖死 |
| 冷却与探测量 | 控制恢复节奏 |

**相关知识点：** 滚动窗口、最小样本、慢调用率、SLO、Half-Open、指数冷却、误熔断、切换振荡。

#### 32、熔断、限流、降级有什么区别？
三者分别解决**流量过载、依赖故障和能力不可用后的连续性**：限流控制请求量，熔断隔离故障依赖，降级定义有限服务，不能互相替代。

1. 限流基于QPS、Token、并发或配额，健康时也会触发。常用令牌桶、滑动窗口和有界队列；请求可排队、返回`429`或按优先级丢弃。
2. 熔断基于错误率、超时率和慢调用比例，发现特定模型、区域或供应商不健康后快速失败，避免线程、连接和重试继续消耗。它具有Closed、Open、Half-Open状态，并通过探测恢复。
3. 降级是业务策略，如切备用、用较弱模型、缩短输出、关闭Reflection、返回缓存或人工接管。必须声明质量边界；高风险能力不足时停止。
4. 典型顺序是入口限流与背压，调用前检查熔断，失败在Retry Budget内重试，持续故障触发熔断，再执行降级链。备用模型本身也有独立限流与熔断，防故障流量全部压垮备用。
5. 监控限流拒绝率、熔断Open时间、降级比例、SLA、质量差与用户重试，并按租户和任务类型切片。触发原因和策略版本必须写入Decision Record。

| 机制 | 触发依据 | 核心目标 |
|---|---|---|
| 限流 | 流量、配额、并发 | 防过载 |
| 熔断 | 错误、超时、慢调用 | 隔离故障 |
| 降级 | 完整能力不可用 | 保留有限服务 |

**相关知识点：** 令牌桶、滑动窗口、熔断状态机、Half-Open、降级链、背压、Retry Budget、备用容量。

#### 33、半开状态下如何做探测流量？
Half-Open探测应**小流量、低风险、有代表性、可幂等**，用于验证依赖稳定恢复，而非立即恢复全部业务；过少易误判，过多会再次压垮服务。

1. 冷却后只放固定并发或总请求数，由独立信号量控制；其余请求走备用、排队或快速失败，防止实例同时放量。
2. 探测请求应覆盖真实模型版本、区域、认证、短文本、流式首Token和关键Tool/JSON能力，但优先选择低成本、无副作用或具备幂等键的流量。禁止用生产高风险写操作作为健康探针。
3. 判断不仅看HTTP成功，还要检查TTFT、完整响应、Schema、空内容、Token速率和错误类别。设置探测专用Deadline，慢成功仍可视为未达到SLO；参数或权限错误不计入服务恢复失败。
4. 达到最小样本且成功率、慢调用率连续满足多个窗口后，按5%→20%→50%→100%渐进放量；任一阶段再次超过阈值立即Open，并指数增加冷却时间。使用随机抖动避免集群实例同时探测。
5. 多副本状态可集中协调或按区域共享，防重复探测。监控探测量、成功率、恢复耗时、再次Open及额外Token，并以故障演练校准。

| 探测要素 | 设计要求 |
|---|---|
| 流量 | 小并发、独立配额 |
| 请求 | 代表性、低风险、幂等 |
| 判定 | 成功率+时延+内容质量 |
| 恢复 | 多阶段渐进放量 |

**相关知识点：** Half-Open、最小样本、探测信号量、渐进恢复、Jitter、慢调用率、SLO、再次熔断。

#### 34、多模型切换时如何保证回答质量一致？
多模型无法逐字一致，应通过**统一契约、能力兼容、Prompt校准和结果验收**保证语义及质量下限。切换前须验证候选。

1. 定义模型无关的Schema、必含字段、引用、语气、长度、安全和后置条件。Prompt使用统一语义模板，Adapter针对Chat Template、Tool和采样参数适配。
2. Registry维护任务成功率、格式率、Tool准确率、上下文、模态和安全能力，构建兼容矩阵。备用模型通过关键门槛后才能接管。
3. 用同一黄金集、RAG快照、工具Mock和验收器做主备配对评测，关注语义、事实、引用、拒答和严重错误，而非文本相似度；再以Shadow监控漂移。
4. 切换时传递结构化任务状态、事实与证据版本，重新计算Tokenizer和上下文预算；温度等参数按模型校准。输出经过Schema、事实、工具后置条件和安全校验，失败可升级、重生成或转人工。
5. 风格差异可用后处理模板规范化，但不得改写事实。记录切换模型、质量差、用户重试和单位成功成本；质量不等价时标记降级。

| 一致性层 | 保障机制 |
|---|---|
| 契约 | Schema、字段、验收标准 |
| 能力 | 画像与兼容矩阵 |
| 行为 | 配对评测、参数校准 |
| 结果 | 事实、安全与后置校验 |

**相关知识点：** 语义一致性、模型兼容矩阵、配对评测、Prompt适配、Tokenizer迁移、结果验证、降级标记。

#### 35、模型切换后上下文如何迁移？
上下文迁移应以**模型无关的结构化状态为权威源**，由目标Adapter重新模板化和Tokenize；Token ID、KV Cache及隐藏状态不能直接复制。

1. Context Store保存策略、目标、约束、事实、证据、工具结果、计划、未决项和输出契约，并带来源、权限与版本。完整对话不是唯一状态。
2. 切换前检查上下文、模态、Tool/JSON和数据策略。按目标Tokenizer重算长度；超限时保护目标、权限、状态与证据，对历史摘要或按需召回。
3. Adapter按目标Chat Template重建角色、工具Schema、多模态Part和参数。不支持的并行工具或结构化模式须串行化、增加验证或拒绝，不能丢字段。
4. 工具结果和副作用以TaskID、StepID及幂等键传递，目标模型只续作未完成节点。流式迁移从稳定边界重生成，不拼接不同模型Token。
5. 迁移后校验Schema、事实、引用、权限和后置条件，记录源/目标模型、摘要版本、丢弃内容及Token变化，并以配对回放测试。

| 可迁移 | 不可直接迁移 |
|---|---|
| 文本、结构化状态、证据URI | Token ID |
| Tool结果、计划与幂等状态 | KV Cache/隐藏状态 |
| 业务版本和权限 | 模型专用控制Token |

**相关知识点：** Context Store、Chat Template、Tokenizer、结构化状态、KV Cache、上下文压缩、幂等续作、Sequence。

#### 36、如果主模型和备用模型能力差异很大怎么办？
能力差异大时不能承诺等价切换，应设计**分级降级、任务拆解、增强验证和可见状态**。备用只执行能力内子任务；高风险越界应排队、人工或失败。

1. 用同一评测集建立主备差距矩阵，覆盖上下文、模态、推理、代码、Tool/JSON、安全、P95和成本，并定义最低质量。未评测场景不自动切换。
2. 将任务拆为可验证节点：备用小模型可做分类、检索、抽取和格式化，复杂规划或最终仲裁延后；通过RAG、计算器、规则、专用Tool和模板补足知识与确定性能力，但工具不能弥补模型无法正确规划的缺口。
3. 降级时缩短上下文、减少非关键输出、关闭复杂Reflection或改为只读建议，并加强Schema、事实、单元测试和人工审批。生产写入、资金、权限等任务若达不到门槛必须停止。
4. 返回结果标记`degraded_level`、缺失能力和待完成步骤，避免用户误以为完整成功。可异步排队等待主模型恢复，保存TaskID、结构化状态与幂等键后续续作。
5. 监控降级任务成功率、质量差、用户重试、人工量、额外Token和积压。若备用长期不足，应增加中间档模型、私有专用模型或重新设计产品SLA，而非依赖应急链。

| 差异程度 | 策略 |
|---|---|
| 小 | 等价备用切换 |
| 中 | 功能裁剪+强校验 |
| 大 | 仅处理可验证子任务 |
| 高风险不达标 | 排队、人工或拒绝 |

**相关知识点：** 能力差距矩阵、功能降级、任务拆解、增强验证、Degraded状态、异步续作、质量门槛。

#### 37、如何避免重试导致请求风暴？
避免请求风暴要实施**端到端重试预算、退避抖动、熔断、并发隔离和负载丢弃**。各层独立重试会乘法放大调用量，消耗Token与备用容量。

1. 只重试瞬时且幂等错误，参数、鉴权、策略拒绝和业务失败终止。超时状态未知时先查询；Tool副作用使用业务幂等键。
2. 根请求创建Retry Budget并下传，网关、Agent和SDK共享次数、时间或额外流量比例，禁止每层独立重试；接近Deadline时停止。
3. 使用指数退避、Full Jitter并尊重`Retry-After`，设置最大次数和总时长。热点请求以Singleflight合并，异步任务进入有界队列。
4. 错误率和慢调用率升高时快速熔断，入口按租户和优先级限流，依赖使用独立线程池/信号量舱壁。队列满时实施Load Shedding，保留高价值请求；备用模型预留容量并有自身限流。
5. 监控请求放大比、重试成功率、重试Token、队列、熔断和备用饱和度。故障演练覆盖宕机、`429`与慢响应，删除低收益策略。

| 机制 | 防护目标 |
|---|---|
| Retry Budget | 限制总放大 |
| Backoff+Jitter | 打散重试时间 |
| 熔断 | 停止调用故障依赖 |
| 舱壁/限流 | 限制故障半径 |
| Load Shedding | 过载时保核心流量 |

**相关知识点：** 重试风暴、Retry Budget、Full Jitter、Singleflight、熔断、舱壁、Load Shedding、幂等。

#### 38、如何统计单个Agent任务的真实成本？
Agent任务成本应按**端到端执行图和全部资源**归集，不能只看主模型Token。应计入模型、检索、Tool、沙箱、存储、重试、Reflection与人工，并以TaskID贯穿。

1. Gateway记录输入、输出、缓存、推理Token、模型版本和单价；Span携带TaskID、AgentID、StepID、Tenant和CostCenter，取消也记录用量。
2. 工具按API、数据库、搜索、浏览器、沙箱CPU/内存/时长和出网计费；共享资源按规则分摊，固定与边际成本分开。
3. 重试、降级、备用切换、Judge和Reflection作为独立步骤计入，缓存命中记录避免的成本。人工审批和返工按工时费率折算，但与直接云费用分别展示。
4. 状态机汇聚Span，处理迟到事件与重复账单，以供应商账单校准Token估算。输出直接、分摊、总成本及单位成功成本；失败也计费。
5. 按任务类型、版本、用户和结果质量分析P50/P95成本、预算偏差与成本瀑布，定位上下文、输出、重试或工具浪费，并设置软硬预算告警。

| 成本类别 | 示例 |
|---|---|
| 模型 | Token、缓存、推理 |
| 工具与计算 | API、沙箱、数据库 |
| 编排 | 重试、Reflection、Judge |
| 人工与共享 | 审批、运维、固定资源 |

**相关知识点：** TaskID、成本归因、CostCenter、成本瀑布、直接/分摊成本、单位成功成本、账单校准、预算告警。

#### 39、多模型环境下如何进行统一评测？
多模型统一评测应使用**相同任务契约、受控条件和端到端指标**，同时保留能力边界。统一不是单一总分，而是在可比样本、Prompt、工具和预算下分层评估。

1. 建立版本化数据集，覆盖常见、长尾、对抗、分布外和高风险样本，按语言、长度、领域、模态和风险标注。不支持项记为能力缺口，不能跳过。
2. 统一Adapter固定消息语义、工具Mock、RAG快照、Schema和验收标准；采样、最大输出与重试一致。记录模型版本、Tokenizer、模板和区域。
3. 确定任务用Exact Match、F1、Pass@k、测试和工具成功率；开放任务用人工Rubric或校准Judge。另统计TTFT、P95、错误率及单位成功成本。
4. 模型输出具有随机性，应重复运行并报告均值、方差和置信区间；使用配对样本比较降低噪声。安全严重错误、越权工具和数据泄漏采用硬门槛，不被平均质量分抵消。
5. 离线后进行Shadow、Canary和稳定分桶A/B，观察真实分布与漂移。结果按任务写入能力画像，并审计数据污染和过拟合。

| 评测层 | 代表指标 |
|---|---|
| 任务质量 | 成功率、F1、Pass@k |
| 工程性能 | TTFT、TPS、P95 |
| 经济性 | Token、单位成功成本 |
| 安全 | 越权、泄漏、严重错误 |

**相关知识点：** 统一评测、任务契约、配对实验、置信区间、能力缺口、Judge校准、Shadow、数据污染。

#### 40、如何实现质量、时延、成本三目标优化？
三目标优化应先定义**质量安全底线、时延SLA和预算约束**，再寻找Pareto最优，而非随意加权。权重须按任务价值和风险配置。

1. 建立模型画像，记录任务成功概率、严重错误率、TTFT、TPS、P95、Token和单位成功成本。请求侧提取复杂度、模态、风险、SLA及预算。
2. 先按安全、地域、能力、质量、时延和硬预算过滤。候选用`效用=质量收益−λ1×时延−λ2×成本−风险罚分`排序，或从Pareto前沿选点。
3. 使用小模型级联：简单任务低成本完成，校验失败、低置信或高风险时升级；异步后台任务可选择慢而便宜的模型，实时交互优先低TTFT。输出长度、RAG Top-K和Reflection也作为决策变量。
4. 在线系统按健康、排队、配额和价格调整，并用迟滞防频繁切换。高风险请求禁止Bandit自由探索，新策略先Shadow和Canary。
5. 评估端到端任务成功率、SLA违约、P95成本和单位成功成本，并绘制质量—时延—成本前沿。若某方案成本更高、质量更低且更慢，则被支配应淘汰；阈值随业务价值和分布漂移定期校准。

| 场景 | 优先目标 | 典型策略 |
|---|---|---|
| 实时低风险 | 时延/成本 | 小模型、短输出 |
| 后台批处理 | 成本 | 批量、高性价比模型 |
| 高价值高风险 | 质量/安全 | 大模型、验证与审批 |

**相关知识点：** 多目标优化、Pareto前沿、效用函数、级联推理、SLA、单位成功成本、迟滞、Bandit。

#### 41、如果预算固定，如何设计最优模型资源分配策略？
固定预算下应最大化**风险约束后的业务价值或成功任务数**，而非平均分配Token。资源优先投向高边际收益且不可替代的任务，并保留故障储备。

1. 按任务、用户、风险、复杂度、SLA和可验证性分层，估计不同模型的成功率、成本与价值。以`价值密度=(收益−风险损失)/成本`排序，安全和质量为硬约束。
2. 低风险高频任务用小模型，复杂、高价值或不可逆任务预留大模型；检索、Judge和工具成本一并计入。组织、租户、Agent及任务设独立预算。
3. 在线采用级联与Admission Control，小模型失败才升级；预算燃烧过快时缩短输出、降低Reflection、延后后台任务或拒绝低价值请求，但不绕过高风险门禁。
4. 可用整数规划、Knapsack或Contextual Bandit分配，但只在安全范围探索。为突发、价格变化和故障保留Reserve，不将预算用满。
5. 按小时/日滚动预测并再平衡，监控燃烧率、单位成功成本、拒绝率和升级率，以影子模拟验证新策略。

| 预算层 | 控制对象 |
|---|---|
| 组织/租户 | 总额与公平性 |
| 任务类型 | 业务价值优先级 |
| 单任务 | 最大Token、步骤和升级 |
| 储备 | 突发与故障切换 |

**相关知识点：** 资源分配、价值密度、Knapsack、Admission Control、预算燃烧率、级联、Reserve、Contextual Bandit。

#### 42、千万级用户场景下如何进行模型容量规划？
容量规划应将**用户规模转换为流量、Token吞吐、并发和GPU/供应商配额**，并为峰值和故障留冗余。DAU、请求频率、峰值与长度才决定负载。

1. 按地区、场景和模型估算`QPS=活跃用户×人均请求/时间窗×峰值系数`；流式并发约为QPS乘连接时长。另统计输入/输出Token/s、TTFT和长度分布。
2. 自部署需基准测试不同批量、上下文和硬件下的Prefill、Decode TPS、显存及KV Cache，结合P95和利用率算实例数；商业API规划RPM/TPM与区域配额。
3. Router将流量分到不同模型，实时与批处理分池；设置租户、模型和优先级限流、有界队列、Admission Control及背压，并为高价值流量留容量。
4. 扩缩容观察队列、Token吞吐、KV Cache、GPU利用率和TTFT；预热模型与连接，以预测扩容应对峰值，并按单区域故障配置N+1。
5. 压测覆盖长短请求、慢客户端、重试风暴和降级。滚动更新预测，监控容量余量、拒绝率、排队P95及故障后的SLA。

| 容量对象 | 核心指标 |
|---|---|
| 请求入口 | QPS、峰值、并发 |
| 模型计算 | Prefill Token/s、Decode TPS |
| 显存 | 权重、KV Cache、批量 |
| 外部供应商 | RPM、TPM、区域配额 |

**相关知识点：** 容量规划、Little定律、Prefill、Decode、KV Cache、Admission Control、N+1、预测扩容、混合压测。

#### 43、如何构建自动化模型路由闭环优化系统？
闭环路由应形成**采集—归因—训练—评测—Shadow/灰度—监控—回滚**，自动化用于提出和验证策略，不能依据未验证反馈直接修改生产Policy。

1. 记录请求画像、候选、硬过滤、路由分数、策略版本、实际模型、Token、时延、重试和结果，并以TaskID关联反馈、工具状态与人工验收。
2. 标签优先使用业务成功、单元测试、Schema、权威事实和人工审核；点赞、停留和模型自评仅作弱信号。LLM Judge需经黄金集校准，并防同源偏差、奖励黑客和选择偏差。
3. 离线训练成功概率、复杂度或排序模型，目标可采用质量、时延、成本和风险的约束优化。训练数据按时间切分，加入困难负样本与分布外样本，比较旧策略的反事实回放。
4. 新策略先离线门禁和Shadow，随后Canary与稳定分桶A/B；高风险流量固定策略，Bandit仅在合规候选中探索，并设置探索比例、预算和严重错误熔断。
5. 监控路由准确率、漏升级、单位成功成本、P95、候选为空、漂移和策略振荡。越阈值即原子回滚；模型、特征、数据与Policy须版本化。

| 闭环阶段 | 主要防护 |
|---|---|
| 数据/标签 | 权威结果、去偏与脱敏 |
| 训练 | 时间切分、约束目标 |
| 发布 | Shadow、Canary、A/B |
| 在线 | 护栏、漂移、自动回滚 |

**相关知识点：** 闭环学习、反事实评估、奖励黑客、Contextual Bandit、数据漂移、策略版本、Shadow、自动回滚。

#### 44、开源模型与商业模型混合部署如何设计？
混合部署应以**统一Gateway、能力画像和数据Policy**纳管开源与商业模型。开源侧提供数据主权和定制，商业侧补充前沿能力与弹性，按任务分工。

1. 自部署侧管理推理服务、GPU调度、模型仓库、量化和SLA；商业侧以Adapter管理认证、区域、配额、留存与价格。统一Message、Tool、流式和错误契约。
2. Registry记录推理、代码、视觉、上下文、JSON/Tool、P95、成本和数据策略。路由先分级：机密数据只走本地/VPC，普通数据在合规候选中排序。
3. 开源小模型承担分类、抽取、RAG和高频任务，商业强模型处理复杂推理与长尾，校验失败再升级。商业故障回退本地，本地不足则排队或合规外溢。
4. 两侧用相同评测集与契约测试，但Prompt、Tokenizer和Tool须分别适配。上线经回放、Shadow和Canary，不能假设参数等价。
5. 记录Token、GPU时长、能耗、账单、运维与折旧，比较单位成功成本；同时监控许可证、模型投毒、泄漏和供应商锁定。

| 维度 | 开源自部署 | 商业模型 |
|---|---|---|
| 数据控制 | 强 | 依赖供应商策略 |
| 弹性/前沿能力 | 自建、迭代较慢 | 通常较强 |
| 成本结构 | 固定容量与运维 | 按量计费 |
| 定制 | 高 | 有限 |

**相关知识点：** 混合部署、Model Gateway、数据主权、GPU TCO、能力路由、许可证、供应链安全、供应商锁定。

#### 45、MCP、Tool Calling、Agent场景下如何进行模型路由？
此类路由必须评估**模型理解和执行工具契约的可靠性**，不能只看对话质量。Router应将MCP、Tool Calling和Agent需求转换为硬能力及风险。

1. 请求画像含Tool数量、Schema、并行调用、MCP Resource、计划深度、上下文、模态、数据等级、副作用和SLA；单工具与多阶段写操作分档。
2. Registry记录Tool Calling、严格JSON、并行工具、长上下文、多模态和指令遵循分数，以及Schema一次通过率。不支持功能、地域或安全部署时硬过滤。
3. 低风险工具选择、参数抽取和摘要由小模型完成；跨工具规划、依赖、冲突和高价值任务用强模型。执行后由Schema、Policy与业务服务校验。
4. 工具过多时按权限、任务和语义召回Top-K，再注入精简Schema；MCP不可信内容与指令隔离。参数失败、计划停滞或验证失败时升级，只传结构化状态。
5. 记录模型、候选工具、过滤原因、计划版本和副作用。评测工具选择、参数通过率、完成率、越权率、循环率及单位成功成本。

| 场景 | 模型重点能力 |
|---|---|
| MCP资源读取 | 长上下文、引用与安全 |
| 单Tool Calling | Schema与参数准确 |
| 多工具Agent | 规划、状态与恢复 |
| 高风险写入 | 强模型+Policy/人工门禁 |

**相关知识点：** MCP、Tool Calling、Schema一次通过率、Tool Retrieval、Policy、提示注入隔离、模型升级、任务完成率。

#### 46、如何设计企业级统一模型接入层（Model Gateway）？
企业级Gateway是**统一协议、路由、安全、可靠执行、成本和审计**入口，不只是API代理；它将模型差异和企业治理从Agent解耦。

1. 接入层统一Message、Tool、JSON、流事件和错误，通过Adapter连接商业、开源及私有模型；Registry维护版本、上下文、模态、地域、价格和健康。
2. 路由先按数据、权限、地域、功能和预算过滤，再按质量、P95、成本与健康排序，支持模型级联、备用、Shadow和灰度，并生成Decision Record。
3. 安全层集成IAM、RBAC/ABAC、短期凭据、DLP、脱敏、Egress白名单和租户隔离；机密数据只进批准模型，日志最小留存。
4. 执行层统一Deadline、取消、限流、重试预算、熔断、降级、缓存和背压。任务携带TaskID与幂等键，防副作用重复。
5. 治理层记录Token、费用、TTFT、P95、错误、缓存和质量，按租户/Agent/任务归因并告警；Trace、配置版本和策略回放支持审计。

| 能力域 | 核心功能 |
|---|---|
| 接入 | Adapter、统一协议、Registry |
| 决策 | 路由、级联、实验 |
| 安全 | IAM、DLP、Policy、隔离 |
| 运行 | 限流、熔断、缓存、流式 |
| 治理 | 计费、观测、审计 |

**相关知识点：** Model Gateway、Model Registry、ABAC、DLP、智能路由、重试预算、Decision Record、AI FinOps。

#### 47、如何处理模型调用失败和超时？
模型失败处理应遵循**Deadline贯穿、错误分类、有界重试、状态核验和熔断降级**。超时不等于未执行；流式或Agent可能已产生副作用，须先核验再重放。

1. 设置建连、首Token、Chunk空闲和端到端Deadline，并下传剩余时间。客户端取消时立即终止模型和工具任务，释放连接与队列。
2. 参数、鉴权、策略和能力错误不重试；限流遵循`Retry-After`；连接失败、瞬时`5xx`和部分超时在幂等时采用退避、抖动与重试预算。
3. 流式失败时保存Sequence和检查点，不拼接备用模型内容。可从安全边界重生成、标记部分结果，或用Last-Event-ID恢复缓存事件。
4. 错误率、超时率或慢调用越阈值后熔断；Half-Open只放少量探测。切换前校验上下文、Tool、Schema、地域及安全，并限制次数。
5. Agent保存计划、工具结果和幂等键，已完成节点不重做；非幂等状态未知时先查询或人工核对。监控时延、重试放大、熔断与降级质量。

| 错误 | 重试策略 | 后续动作 |
|---|---|---|
| 参数/鉴权/策略 | 不重试 | 修正或终止 |
| 限流/瞬时5xx | 有界退避 | 同模型或备用 |
| 超时状态未知 | 先核验 | 续作、补偿或人工 |
| 持续故障 | 不重试 | 熔断降级 |

**相关知识点：** Deadline、TTFT、Retry-After、指数退避、重试预算、熔断、Half-Open、流式检查点、幂等。

#### 48、如何评估不同模型的能力画像？
模型能力画像应是**按任务、版本和约束切片的多维数据产品**，不能用单一Benchmark替代。画像覆盖质量、时延、成本、安全和部署边界。

1. 按业务建立评测集，覆盖推理、代码、抽取、视觉、RAG忠实度、结构化输出和Tool Calling，并加入长尾、对抗及分布外样本。指标包括成功率、Pass@k、格式率和人工Rubric。
2. 服务维度测量TTFT、TPS、P95/P99、并发、可用率和错误；成本记录输入、输出、缓存单价及单位成功任务成本。
3. 边界记录上下文、模态、工具/JSON、地域、数据留存、部署和配额。安全评测覆盖提示注入、越权、隐私泄露和拒答质量。
4. 离线评测使用相同Prompt、工具Mock、采样参数和硬件条件，多次运行估计方差；模型版本、Tokenizer和模板必须固定。在线通过Shadow、Canary和A/B观察真实分布，并防用户选择偏差。
5. 画像按版本更新，保存样本结果、置信区间和退化告警。Router只用具备统计显著性和新鲜度的特征，高风险场景看最差切片。

| 画像维度 | 代表指标 |
|---|---|
| 质量 | 任务成功率、Pass@k、忠实度 |
| 性能 | TTFT、TPS、P95、并发 |
| 经济 | 单价、单位成功成本 |
| 安全与边界 | 越权率、地域、留存、功能 |

**相关知识点：** 能力画像、业务评测集、Pass@k、TTFT、TPS、置信区间、Shadow、Canary、分布外评测。

#### 49、如何控制大模型调用成本？
大模型成本应通过**计量归因、预算门禁、模型分层、上下文治理和复用**控制，核心是单位成功任务成本而非Token单价，并同时观察质量与重试。

1. Gateway记录输入、输出、缓存、推理Token、模型版本与单价，关联租户、Agent、Task和步骤；将重试、Reflection、Judge、检索和工具计入成本。
2. 设置组织、租户、Agent和任务多级预算。执行前估算Token与费用；软阈值触发小模型、短输出或关闭非关键步骤，硬阈值暂停、审批或终止。
3. 小模型完成分类、抽取、压缩和路由，大模型只处理复杂节点。低置信、校验失败或高风险再升级，并传结构化状态避免重发轨迹。
4. Prompt去重并缓存稳定前缀；长对话用摘要、RAG和分层Memory；输出设Schema、长度与停止条件。Semantic Cache仅复用低风险且权限一致的结果。
5. 检测循环、无进展调用和重试风暴，设置步骤、Token、时间及费用上限。通过成本瀑布和A/B验证，监控P95成本与预算超限率。

| 手段 | 主要收益 | 风险 |
|---|---|---|
| 模型级联 | 减少大模型占比 | 漏升级 |
| Context治理 | 降输入Token | 信息丢失 |
| 缓存复用 | 避免重复计算 | 过期、越权 |
| 预算门禁 | 防止失控 | 任务提前终止 |

**相关知识点：** AI FinOps、Token计量、预算门禁、模型级联、Context压缩、Prompt Cache、Semantic Cache、成本瀑布。

#### 50、敏感数据如何保证不被发送到外部模型？
“不得外发”应实现为**数据分级、出站策略、确定性检测和网络阻断**，不能依赖Prompt保密。安全边界位于模型调用前，并覆盖输入、RAG、Memory、工具和日志。

1. 建立分类标签，对个人信息、密钥、财务、代码、合同等标记Owner、租户、地域与允许模型。分类来源包括数据目录、字段标签和DLP扫描。
2. Gateway Policy按主体、数据等级、模型部署、留存、地域和用途做ABAC决策。机密数据只进本地/VPC；未分类或策略不明时默认拒绝。
3. 序列化前执行字段过滤、密钥检测、正则、NER和文件扫描。假名化只替换任务不需要的敏感值；模型须理解原值时必须切私有模型。
4. 出站仅允许Gateway访问批准端点，使用mTLS、短期凭据和白名单；Agent与沙箱无直接外网权限。供应商配置禁训练、最小留存和区域绑定。
5. 日志、Trace、缓存和错误同样脱敏并隔离；审计记录策略版本、命中规则和发送摘要，并以泄漏与绕过测试持续验证。

| 控制层 | 机制 | 作用 |
|---|---|---|
| 数据 | 分类、标签、DLP | 识别敏感内容 |
| 策略 | ABAC、默认拒绝 | 决定可否外发 |
| 网络 | Egress白名单、mTLS | 阻断绕过 |
| 运行后 | 脱敏日志、审计 | 防二次泄漏 |

**相关知识点：** 数据分级、DLP、ABAC、Policy Engine、假名化、Egress控制、mTLS、默认拒绝、审计。

#### 51、如何设计模型降级和兜底策略？
模型降级应是**按能力兼容矩阵验证的有序策略**，在故障、容量或预算受限时保留可接受服务。每级须声明质量边界、可见状态和退出条件。

1. 记录上下文、模态、Tool Calling、结构化输出、地域、安全、价格和P95，构建主备兼容矩阵。缺关键能力、数据不准出域或上下文不足者排除。
2. 熔断、配额耗尽、SLA将违约、预算不足和维护触发降级。参数、鉴权、策略拒绝不能靠换模型掩盖；瞬时故障先有限重试。
3. 推荐顺序是同档同能力备用模型、较弱模型加缩减非关键功能、缓存或已验证模板、异步排队、人工接管或明确失败。高风险写操作在能力不足时应暂停，禁止以低质量模型继续执行。
4. 切换时通过统一Schema转换消息和工具，重新计算Token，传递TaskID、结构化状态、证据和幂等键。流式已输出内容不能无标记拼接，必要时从检查点重启并告知用户。
5. 降级结果继续经过Schema、事实和业务后置条件校验，并标记`degraded_level`。监控降级率、成功率、质量差异、用户重试、额外Token和恢复时间；主模型恢复后渐进切回，避免抖动。

| 层级 | 兜底方式 | 质量定位 |
|---|---|---|
| L0 | 同能力备用 | 基本等价 |
| L1 | 较弱模型+功能裁剪 | 可接受下降 |
| L2 | 缓存/模板/异步 | 有限服务 |
| L3 | 人工或明确失败 | 安全优先 |

**相关知识点：** 能力兼容矩阵、熔断、降级链、功能裁剪、检查点、幂等、Degraded状态、渐进恢复。

#### 52、如何支持多厂商模型统一接入？
多厂商接入应通过**统一协议、Adapter、能力注册表和公共执行治理**实现。统一不抹平差异；不支持功能须在能力协商时暴露，禁止静默改语义。

1. 定义Vendor-neutral请求，包括Message、Part、Tool Schema、结构化输出、采样、流事件、用量和错误；响应统一为增量、工具调用和Token。
2. Adapter负责认证、参数映射、Chat Template、工具格式、流式Chunk、取消和错误转换。`vendor_options`承载特有功能，但业务层不得依赖未治理字段。
3. Registry记录版本、上下文、模态、JSON/Tool、地域、留存、单价、配额和健康度。调用前协商能力；不支持并行Tool时须拒绝或显式串行化。
4. Executor统一实施Deadline、限流、重试、熔断、缓存、预算、DLP和Trace。凭据由密钥系统按租户注入，Agent不持有；出站只准批准端点。
5. 契约测试覆盖工具、Unicode、长上下文、流式中断和Token统计。新模型经回放、Shadow及灰度，评测成功率、P95、成本和安全。

| 层次 | 职责 |
|---|---|
| 统一协议 | 稳定业务契约 |
| Adapter | 厂商格式转换 |
| Registry | 能力、版本和策略 |
| Executor | 可靠性、安全与观测 |

**相关知识点：** Model Gateway、Adapter、能力协商、Vendor-neutral Schema、契约测试、密钥注入、DLP、Shadow。

#### 53、如何做模型效果的A/B实验？
模型A/B实验应以**用户或会话稳定分桶、端到端指标和安全护栏**为核心。不能只看点赞或Judge分数，也不能在同一会话随机切换模型。

1. 先定义假设、主指标、护栏指标和最小可检测效应。主指标可为任务成功率、一次解决率或业务转化；护栏包括严重错误、安全事件、P95、Token、单位成功成本和用户投诉。
2. 随机化单元通常选择用户、会话或租户，并通过哈希稳定分桶；控制Prompt、工具、RAG数据、参数和UI一致，只改变模型或明确的策略变量。跨用户网络效应明显时应采用集群随机化。
3. 上线前做离线黄金集和Shadow，确认功能与安全底线；再小流量Canary，最终进入A/B。高风险请求可排除实验或固定到已验证模型，禁止为探索突破Policy。
4. 样本量按基线、显著性、统计功效和最小效应估算，实验覆盖工作日、峰谷和主要任务切片。避免提前窥视后随意停实验；多指标和多版本比较需控制多重检验。
5. 分析总体及语言、任务、长度、风险和用户切片，报告置信区间。记录版本与采样参数并考虑重复测量，胜出后仍须渐进发布。

| 方法 | 是否影响用户 | 主要用途 |
|---|---|---|
| 离线评测 | 否 | 基础质量与回归 |
| Shadow | 否 | 真实分布对比 |
| Canary | 少量 | 安全与兼容 |
| A/B | 是 | 因果评估业务效果 |

**相关知识点：** 稳定分桶、随机化单元、MDE、统计功效、护栏指标、Shadow、Canary、多重检验、置信区间。

#### 54、如何记录一次请求为什么选择了某个模型？
每次路由应生成**不可变的Model Decision Record**，记录请求特征、硬过滤、候选评分、策略版本和运行变化，使决策可审计、可重放；不能保存完整敏感Prompt。

1. 生成DecisionID并关联TraceID、TaskID、租户和时间；保存任务、复杂度、Token区间、模态、SLA、预算、数据等级、地域及能力。文本只存脱敏摘要或哈希。
2. 每个候选记录ModelID、版本、画像版本、硬约束结果及拒绝原因，如数据越界、上下文不足、工具不兼容、配额或熔断。硬过滤与软分数分开。
3. 排序记录质量预测、P95、预估费用、健康度、风险和最终效用，连同权重、阈值、Router模型版本及随机实验桶。若规则优先级覆盖模型评分，也要记录命中规则ID。
4. 执行阶段补充实际模型、重试、升级、降级、备用、缓存、Token、时延、校验和最终状态，以判断初始选择是否合理。
5. 记录写入追加式审计存储并设访问控制与保留期。回放固定策略、画像和模型版本，并支持候选为空、模型升级等查询。

| 字段组 | 关键内容 |
|---|---|
| 请求画像 | 复杂度、SLA、预算、安全 |
| 候选过滤 | 模型、通过状态、原因 |
| 排序决策 | 分数、权重、阈值、策略版本 |
| 执行结果 | 切换、Token、质量、时延 |

**相关知识点：** Decision Record、TraceID、模型画像版本、硬过滤、效用分数、策略回放、追加式审计、成本归因。

#### 55、多模型路由策略具体如何设计？规则路由和LLM路由如何选择？
生产系统应采用**规则硬过滤、模型软判断、运行时校验升级**的混合路由。规则负责安全合规，分类器或LLM理解语义与复杂度，单一方式均有缺口。

1. 规则依据租户、数据等级、地域、模态、上下文、Tool能力、预算、SLA和熔断状态判断，低延迟且可审计；缺点是难覆盖同义表达与复杂组合。
2. 模型路由通过轻量分类器、Embedding检索或LLM读取请求，预测任务类型、难度和候选模型成功概率，语义泛化更强；但存在误分类、漂移、额外成本和不可解释性，不能决定数据是否允许出域。
3. 混合流程先用Policy排除不合规、能力不足和不可用模型，再让模型在安全候选中排序；最高分低于阈值或前两名差距过小时，选择保守模型、澄清或小模型试运行。
4. 执行结果由Schema、事实证据、工具状态和业务规则验证，失败触发升级，而非让Router一次决定最终质量。高风险请求固定路由或人工审批，禁止Bandit自由探索。
5. 以路由准确率、严重误路由率、升级率、SLA和单位成功成本评估。策略、特征和模型版本必须记录，新版本通过离线回放、Shadow、灰度与回滚发布。

| 维度 | 规则路由 | 模型路由 |
|---|---|---|
| 确定性/审计 | 强 | 较弱 |
| 语义泛化 | 弱 | 强 |
| 延迟成本 | 低 | 较高 |
| 适用 | 安全与硬约束 | 复杂度与语义排序 |

**相关知识点：** 混合路由、Policy、分类器、Embedding Router、置信门控、Bandit、严重误路由、Shadow。

#### 56、如何设计统一模型接入层，根据任务难度响应速度，成本和数据安全自动选择不同模型？（腾讯二面）
统一接入层把厂商差异收敛为**标准契约、策略决策和可靠执行**。先做安全与能力硬过滤，再优化质量、时延和成本；数据安全具有否决权。

1. Adapter统一Message、Tool、结构化输出、流式事件、Token和错误码，映射厂商参数；不支持的特性显式拒绝，禁止静默降级。
2. Registry保存版本、上下文、模态、工具、区域、数据策略、价格、配额、P95和能力画像；请求提取类型、复杂度、SLA、预算和敏感等级。
3. Policy先做数据分级，机密数据只进批准模型，敏感字段脱敏；再过滤能力不足、配额耗尽和熔断项。Router按质量、时延、成本与健康度排序。
4. Executor负责Deadline、限流、重试、熔断、缓存和计费。低复杂度走小模型，校验失败或置信不足时升级，并保留TaskID与结构化状态。
5. 记录特征摘要、过滤原因、候选分数和策略版本，通过Shadow、A/B与灰度验证。

| 层次 | 核心职责 |
|---|---|
| Adapter | 统一协议与错误 |
| Registry/Router | 能力画像与候选排序 |
| Policy | 数据、权限与合规硬约束 |
| Executor | 可靠调用、计费与观测 |

**相关知识点：** Model Gateway、Adapter、Model Registry、Policy Engine、效用路由、数据分级、熔断、用量计费、Shadow。

#### 57、模型效果最好但成本无法商业化，低成本模型又无法满足质量要求，应该如何设计多模型路由和降级方案？（腾讯二面）
应把问题从“二选一”改为**按任务价值分层、低成本模型先行、验证失败再升级**的级联系统，并以单位成功成本而非单次调用价格衡量商业可行性。高价模型只覆盖真正影响结果的少量困难步骤。

1. 按业务价值、复杂度、风险和可验证性划分S0—S3档：分类、改写等确定任务使用小模型；一般生成由中档模型处理；复杂推理、高价值写入和长尾异常使用大模型或人工门禁。
2. 小模型输出必须经过结构化Schema、规则、检索证据、工具结果和领域验证器。低置信、格式失败、事实冲突、多轮无进展、用户重试或高风险操作触发升级；不可验证且后果严重的任务不得以低价模型直接交付。
3. 大模型只接收失败节点、结构化状态、关键证据和验收标准，完成局部修复或评审，减少重复上下文，并将优质结果用于蒸馏。
4. 降级用于容量或故障场景，顺序是同能力低价模型、缩短输出或减少非关键功能、异步处理、人工接管；不能把明显能力不足的模型伪装成正常结果。降级状态应向用户或下游显式标记。
5. 通过任务成功率、升级率、漏升级率、P95、单位成功成本、付费转化和事故成本计算ROI，并用Shadow与灰度调整阈值。

| 层级 | 默认模型 | 保护机制 |
|---|---|---|
| 简单可验证 | 小模型 | 规则与Schema |
| 中等生成 | 中档模型 | 证据和质量评分 |
| 复杂高价值 | 大模型 | 工具校验与评审 |
| 不可接受风险 | 人工/拒绝 | 强门禁 |

**相关知识点：** 模型级联、单位成功成本、价值分层、置信门控、局部升级、蒸馏、显式降级、ROI。

#### 58、混合模型调度路由系统：根据任务复杂度、时延要求、成本预算、数据安全等级自动路由不同模型（Agent高级）
混合路由应实现**约束满足与多目标优化分离**：安全、能力和预算先硬过滤，质量、时延与成本再排序；运行中由校验器决定升级。

1. 请求画像包含类型、复杂度、Token、模态、工具、P95、预算、数据等级和地域。复杂度由规则、分类器和历史任务判断，并输出校准置信度。
2. 模型画像包含能力、上下文、功能、位置、留存、单价、配额、延迟和健康度。Policy剔除数据越界、能力不足、预算超限或熔断项；脱敏失败须走私有模型。
3. 用Pareto前沿或效用函数排序。严格SLA优先低延迟，后台任务选择高性价比模型，高风险任务提高质量权重。
4. 小模型先行，校验失败、置信不足、工具错误或无进展时升级；只传关键状态。故障时按兼容矩阵降级并控制重试预算。
5. 记录特征、过滤原因、候选分数与策略版本，以成功率、漏升级、单位成功成本和SLA违约率优化，并经Shadow、灰度发布。

| 阶段 | 主要机制 | 输出 |
|---|---|---|
| 画像 | 复杂度与安全分类 | 请求特征 |
| 硬过滤 | Policy与能力约束 | 可执行候选 |
| 排序 | Pareto/效用函数 | 首选与备用 |
| 运行门控 | 校验与升级 | 最终模型 |

**相关知识点：** 多目标优化、Pareto前沿、Policy、请求画像、模型画像、Cascade、置信校准、兼容矩阵、Shadow。

#### 59、模型调用成本管控体系：Token用量统计、多模型分级降级、缓存复用、提示词精简、记忆压缩、批量合并请求等组合降本方案（Agent高级）
成本治理应做到**可计量、可预算、可归因、可优化、可门禁**。核心指标是单位成功任务成本；低价模型若导致重试和升级，实际可能更贵。

1. 网关记录输入、缓存命中、输出和推理Token，按模型版本计费，并关联Tenant、Agent、Task、Step和CostCenter；流式取消也记录已用量。
2. 设置组织、租户、Agent和任务预算，执行前估算、运行中扣减；软阈值缩短输出、关闭非关键Reflection或换小模型，硬阈值暂停或终止。
3. 小模型先行，大模型只处理困难节点。Prompt去除重复规则；对话用滑动窗口、摘要和RAG按需注入，关键事实保留来源版本。
4. Prompt Cache复用稳定前缀，Semantic Cache复用低风险等价结果；键包含模型、模板、数据和权限版本并按租户隔离。仅批量合并独立同配置请求。
5. 分析上下文、输出、重试、Reflection和无效工具占比，用A/B验证优化对成功率的影响，避免表面降本。

| 杠杆 | 主要收益 | 风险 |
|---|---|---|
| 路由与级联 | 降低高价模型占比 | 漏升级 |
| 压缩与RAG | 减少输入Token | 关键信息丢失 |
| 缓存 | 避免重复推理 | 过期与越权 |
| 批处理 | 提高吞吐 | 增加等待时延 |

**相关知识点：** FinOps、Token计量、成本中心、预算门禁、Prompt Cache、Semantic Cache、记忆压缩、批处理、单位成功成本。

#### 60、什么是微调，业务场景里什么情况下才需要做微调（Agent初级）
微调是在预训练模型上用领域样本优化参数，使模型学习**特定行为、风格、格式或任务映射**。动态知识优先RAG，流程与权限由Tool、Workflow和Policy解决。

1. 常见方式有SFT、LoRA/Adapter和DPO。SFT学习理想输出，LoRA降低训练与存储成本，DPO调整偏好；都依赖高质量代表性数据。
2. 适合信号是Prompt稳定但输出仍波动、有大量重复任务和标签、领域映射难靠少量示例表达、希望小模型逼近大模型，或工具调用模式需稳定。
3. 数据少且噪声高、事实频繁更新、检索缺失、规则变化或无法建立独立评测集时不适合。微调不会自动解决幻觉和权限。
4. 流程是基线、清洗脱敏、数据划分、训练、离线评测、安全红队、Shadow和灰度；训练与测试按用户或时间隔离，防止泄漏。
5. 以成功增益、稳定性、推理成本和维护成本计算ROI；Prompt或RAG已达标时无需微调。

| 方法 | 主要解决 | 不适合解决 |
|---|---|---|
| Prompt | 少量规则与示例 | 大规模稳定行为迁移 |
| RAG | 动态事实与私有知识 | 固定风格和模型行为 |
| 微调 | 行为、格式、领域映射 | 实时知识更新 |

**相关知识点：** SFT、LoRA、Adapter、DPO、数据泄漏、独立评测集、RAG、蒸馏、Shadow、微调ROI。

#### 61、在QPS达到1000以上的场景中，SSE流式连接如何实现心跳检测，超时释放和资源复用？（腾讯一面）
高并发SSE应采用**异步I/O、分层超时、心跳和取消传播**，不能每连接占一个线程。并发数近似为QPS乘以平均连接时长，不能只看QPS。

1. 网关用事件循环或异步Servlet，生成与写出通过有界队列解耦。连接只保存轻量状态，线程、HTTP连接与缓冲区使用受控池；禁止无界队列。
2. 定期发送SSE注释心跳`: ping\n\n`，间隔小于各层空闲超时。心跳只保活和检测写失败，业务进度用`event/id/data`事件。
3. 设置建连、首Token、Chunk空闲、总时长和写阻塞超时。失败时原子关会话、取消模型与工具，释放队列、订阅和租约；清理须幂等。
4. 通过队列水位检测慢客户端，先合并Chunk或降频，超过上限则断开并按Last-Event-ID恢复。
5. 限制全局、租户和用户连接数，监控活跃连接、建连率、心跳失败、断开原因、缓冲水位、连接寿命和资源回收延迟。

| 方案 | 资源特征 | 适用性 |
|---|---|---|
| 阻塞线程/连接 | 线程占用高 | 不适合大规模长连接 |
| 异步事件循环 | 少量线程承载多连接 | 推荐 |
| 无界缓冲 | 易内存雪崩 | 禁止 |
| 有界队列+背压 | 可控降载 | 推荐 |

**相关知识点：** SSE、非阻塞I/O、Little定律、应用心跳、分层超时、取消传播、背压、Last-Event-ID、连接配额。

#### 62、流式输出同时适配小程序，APP和PC端时，如何解决Markdown兼容，内容乱序和页面渲染卡顿问题？（腾讯一面）
多端流式输出应把**协议、增量解析和平台渲染**解耦：服务端发送带序号的语义Chunk，客户端解析为统一IR，再由各端Adapter渲染，禁止逐Token刷新富文本。

1. 协议包含`stream_id、seq、type、delta、version、finish_reason`。客户端按Seq重排、重复丢弃；发现缺口后请求补段或快照，不能按到达顺序拼接。
2. Markdown解析器维护文本、代码块、列表、表格和链接状态。未闭合结构暂存，只渲染确认边界；后续Chunk局部更新AST，结束时全量校验。
3. 定义跨端Markdown子集和平台无关IR，各端实现Renderer。小程序不支持的表格或嵌套降级为卡片/纯文本；禁用原始HTML并校验链接图片。
4. UI按时间窗合并Chunk并逐帧批量更新；长内容用虚拟列表，代码高亮放Worker且只处理闭合代码块，避免全文重排。
5. 监控首字时延、Seq缺口、重排等待、渲染次数和丢帧率，低性能设备增大批次。

| 问题 | 核心机制 |
|---|---|
| Markdown不完整 | 增量状态机与局部AST |
| 内容乱序 | Seq、重排缓冲、快照 |
| 多端差异 | 统一IR与Renderer Adapter |
| 页面卡顿 | 批量刷新、虚拟列表、Worker |

**相关知识点：** 流式Chunk协议、Sequence、增量Markdown、AST/IR、平台适配、批量渲染、虚拟列表、Web Worker、XSS防护。

#### 63、为什么需要 Model Router？
Model Router把**任务需求映射到合适的模型档位**。单一模型难同时兼顾质量、时延、成本、安全和可用性；全走最强模型成本高，全走小模型长尾质量差。

1. 请求的复杂度、模态、风险、SLA和预算不同；模型在代码、推理、视觉、Tool Calling、上下文和地域合规上也不同，Router显式建模这些差异。
2. 路由先执行能力、安全和权限硬过滤，再按预测质量、P95时延、价格、配额与健康度排序。数据不得出域、模型不支持工具或上下文不足等条件必须直接否决，不能只降低分数。
3. Router支持小模型先行与运行时升级：低复杂度请求使用低成本模型，校验失败、低置信、工具调用错误或用户重试时升级大模型；供应商故障时按兼容矩阵切换备用。
4. 它还是统一治理点，可集中实施限流、预算、缓存、熔断、审计和用量归因，并记录“为什么选这个模型”，使线上决策可解释、可回放。
5. Router自身会增加分类误差和时延，因此简单稳定场景可用规则，高语义复杂度再使用分类器或轻量LLM；新策略应通过离线评测、Shadow和灰度验证。

| 无Router的问题 | Router提供的能力 |
|---|---|
| 高价模型全量调用 | 成本分层与级联 |
| 单模型能力盲区 | 能力匹配与升级 |
| 厂商故障 | 熔断和备用切换 |
| 数据越界 | 安全硬过滤 |

**相关知识点：** Model Router、能力画像、硬约束、模型级联、兼容矩阵、成本治理、路由解释、Shadow。

#### 64、多模型如何协同工作？
多模型协同围绕**分工、契约、验证和汇聚**设计，常见形态是级联、专家流水线、并行集成和生成—评审；收益必须超过额外Token、时延与冲突成本。

1. 级联让小模型先处理，失败或低置信时升级，适合成本敏感任务；专家流水线按分类、检索、代码、视觉等能力分步处理。
2. 并行集成让多个模型独立生成，再按规则、可信度或Judge融合；同源模型可能共模错误，高风险结果仍需工具或人工验证。
3. 生成—评审模式由一个模型产出，另一个按Rubric检查事实、格式和安全。Critic默认只读，输出结构化问题与证据，并限制迭代轮数，防止反复修改导致成本失控。
4. 模型以统一Schema交换目标、证据、状态和验收标准，不传完整对话。Supervisor维护TaskID、版本、预算、Deadline与幂等状态。
5. 汇聚时优先确定性校验，其次权威来源，再考虑加权投票；不能按语言流畅度选择结果。评测关注端到端成功率、冲突率、增量收益、P95与单位成功成本。

| 协同方式 | 优势 | 主要代价 |
|---|---|---|
| 级联 | 成本低 | 可能漏升级 |
| 专家流水线 | 专业分工 | 状态与依赖复杂 |
| 并行集成 | 稳健性 | 调用成本高 |
| 生成—评审 | 质量门禁 | 时延与迭代成本 |

**相关知识点：** 模型级联、专家模型、Ensemble、LLM-as-a-Judge、共模错误、Supervisor、结构化契约、单位成功成本。

#### 65、大模型和小模型如何分工？
小模型与大模型应按**任务复杂度、风险和可验证性**分工：小模型负责高频、边界清晰、可程序校验的工作，大模型负责开放推理、复杂规划和高价值异常；通过级联升级而非固定绑定，在质量达标前提下控制成本。

1. 小模型适合意图分类、实体抽取、查询改写、内容路由、格式转换、简单摘要、规则补全和候选初筛。这类任务输入输出Schema明确、评测稳定，失败可由校验器快速发现，并可通过蒸馏或微调提高领域表现。
2. 大模型适合跨领域综合、长链规划、复杂代码、模糊需求、冲突仲裁和长尾任务。高风险场景仍需证据、规则、工具校验和人工门禁。
3. 典型流水线是“小模型分类与召回→规则过滤→小模型尝试→验证器判定→必要时升级大模型”。升级信号包括低置信、输入分布外、结构化输出失败、工具参数错误、多轮无进展和用户明确要求高质量。
4. 两类模型使用统一请求与结果契约，但Prompt、上下文窗口、Token预算和工具能力分别适配。切换时传递结构化状态与证据，避免把全部对话重复发送。
5. 以任务成功率而非模型单次准确率评估分工，重点监控升级率、误升级、漏升级、P95时延、单位成功成本和大模型调用占比。

| 维度 | 小模型 | 大模型 |
|---|---|---|
| 优势 | 低成本、低时延、高吞吐 | 复杂推理与长尾能力 |
| 任务 | 分类、抽取、改写、初筛 | 规划、综合、仲裁 |
| 风险 | 能力不足、漏升级 | 成本高、时延与幻觉 |

**相关知识点：** 模型级联、能力分层、蒸馏、领域微调、验证器、置信门控、分布外检测、单位成功成本。

#### 66、如何处理模型返回内容为空或格式不合法？
应将模型输出视为**不可信的外部数据**，通过“协议约束、分层校验、有限修复、受控重试、确定性兜底”处理。空内容还需区分安全拦截、截断、超时和模型真实返回空值。

1. 请求侧使用结构化输出、JSON Schema或函数调用声明字段、类型、枚举及必填项；提示词禁止附加解释，并设置最大输出Token，降低截断和自由格式概率。
2. 接收侧先校验HTTP状态、finish reason和流是否完整，再执行语法、Schema、语义及业务规则四层校验。移除Markdown围栏应采用确定性规则，禁止宽松解析吞掉非法字段。
3. 可修复错误仅限尾逗号、围栏或轻微转义等无歧义问题；缺失关键字段、类型冲突和事实约束失败应携带精简错误信息重试。重试使用同一幂等键、次数上限与退避，并记录原始响应。
4. 多次失败后切换模型、改用更严格的Tool Calling，或返回可识别的降级结果；涉及写操作时，必须在执行副作用前完成校验。禁止模型自行补造审批、金额等关键字段。
5. 监控空响应率、Schema失败率、修复成功率、截断率、重试成本和供应商分布，以请求ID关联原始输出、校验错误与最终动作。

| 异常 | 处理 |
|---|---|
| 空响应/截断 | 检查原因后重试或切换 |
| 轻微语法错误 | 确定性修复后复验 |
| Schema/业务错误 | 约束重试或安全失败 |

**相关知识点：** Structured Output、JSON Schema、Tool Calling、finish reason、语义校验、幂等、降级。

#### 67、Agent 执行到一半模型失败，如何恢复任务？
Agent中途失败应采用**持久化状态机、检查点、幂等工具和可恢复执行**，从最后一个已确认状态继续，并避免重复产生外部副作用。

1. 将任务拆为有稳定Step ID的规划、模型决策、工具执行、验证和提交阶段。每步记录输入摘要、模型版本、输出、工具参数、状态、重试次数、预算与Deadline，状态变更通过事务或事件日志持久化。
2. 检查点只能落在一致性边界：模型仅生成计划时可安全重算；工具写入后必须保存调用幂等键、外部回执和结果哈希，再标记完成。恢复时先查询外部系统确认执行状态，禁止盲目重放支付、发送、删除等动作。
3. 将错误分为瞬时、永久、上下文过长和策略拒绝。瞬时错误在Deadline及重试预算内退避；模型不可用时按兼容矩阵切换，并把状态、证据和未完成步骤迁移给备用模型。
4. 对非幂等操作采用Prepare/Commit、补偿事务或人工确认。若工具Schema或权限已变化，应使旧检查点失效并从安全边界重新规划。
5. 恢复后校验后置条件，监控恢复成功率、重复副作用率、回退步数、恢复时延及额外Token。超过预算或风险阈值时转人工并保留审计链。

| 状态 | 恢复方式 |
|---|---|
| 模型调用前失败 | 从检查点重算 |
| 幂等工具状态未知 | 查询后决定重放 |
| 非幂等写入已发生 | 补偿或人工处理 |

**相关知识点：** Durable Execution、状态机、Checkpoint、幂等键、事件溯源、Saga、Prepare/Commit、恢复点。

#### 68、如何设计模型调用的监控指标？
模型监控应覆盖**流量、可靠性、时延、质量、成本、安全与依赖健康**，并按模型、版本、供应商、租户、场景和路由切片；仅观察HTTP成功率无法反映“返回成功但答案不可用”。

1. 流量层记录请求量、并发、队列、上下文长度、流式连接数和取消率。可靠性层统计超时、`429`、`5xx`、空响应、Schema失败、重试、熔断与切换率。
2. 时延拆分排队、网关、首Token时间TTFT、生成时间、工具时间和端到端耗时，分别观察P50/P95/P99；流式场景增加Token间隔与卡顿次数，避免均值掩盖长尾。
3. 质量指标包括任务成功率、格式通过率、事实正确性、引用有效率、工具成功率、用户重试率和人工接管率。离线基准、抽样评审与线上反馈共同使用，不能把点赞率作为唯一标准。
4. 成本按输入、输出、缓存命中、推理Token、重试和工具费用归因到Task/Agent/租户，核心指标为**单位成功任务成本**，同时监控预算消耗速度。
5. 安全层统计越权、敏感数据拦截、策略拒绝和注入命中。Trace关联路由原因、Prompt版本、响应和工具链；告警基于SLO、错误预算和多窗口 burn rate。

| 维度 | 代表指标 |
|---|---|
| 可靠性 | 成功率、超时、重试、降级 |
| 性能 | TTFT、P95、Token间隔 |
| 质量 | 任务成功率、事实/格式通过率 |
| 成本 | 单位成功任务成本、预算速度 |

**相关知识点：** RED、USE、SLO、错误预算、TTFT、Trace、LLM可观测性、Burn Rate、成本归因。

#### 69、如何区分模型异常、网络异常和业务异常？
应建立**分层错误分类与统一错误信封**，依据证据判定故障层级。分类结果必须驱动不同的重试、熔断、降级和用户提示策略。

1. 网络异常发生在DNS、连接、TLS、代理或传输层，表现为连接拒绝、握手失败、超时、流中断；记录阶段耗时和目标节点。请求状态未知时，写操作必须先查询或依靠幂等键。
2. 模型异常包括`429`、`5xx`、过载、空响应、异常finish reason、截断、Schema不合规及能力退化。HTTP 200仍需验证内容、格式和任务后置条件。
3. 业务异常是输入、权限、额度或领域规则不满足，例如参数非法、无库存；通常不可重试。安全拒绝应单列，防止切换到宽松模型绕过控制。
4. 网关使用标准字段记录layer、category、code、retryable、providerCode、requestId和cause chain。错误映射保留原始码，未知异常归为Unknown并采样调查，不能默认可重试。
5. Trace串联客户端、网关、模型和工具，结合供应商状态、对照和重放定位。统计分类准确率、未知率、重试收益和误熔断率。

| 类型 | 主要证据 | 默认动作 |
|---|---|---|
| 网络 | DNS/TLS/连接/传输失败 | 有界重试 |
| 模型 | 状态码、finish reason、内容校验 | 重试、切换或降级 |
| 业务 | 领域错误码与规则 | 修正输入或终止 |

**相关知识点：** 错误分类、Error Envelope、Cause Chain、幂等、Trace、可重试性、后置条件、安全拒绝。

#### 70、如何做多供应商模型路由？
多供应商路由应以**统一契约、硬约束过滤、动态评分、故障隔离和可回放决策**为核心，目标不是平均分流，而是在满足安全与质量底线后优化时延、成本和可用性。

1. 接入层定义统一的消息、流式事件、Tool Calling、结构化输出、用量和错误模型；适配器保留供应商原始字段。建立能力矩阵，标注模态、上下文、工具、地域、数据保留、价格、限额及版本兼容性。
2. 路由先按数据驻留、敏感级别、租户授权、所需能力和上下文长度执行硬过滤，任何不合规候选直接排除；再根据预测质量、P95时延、单位成本、实时健康度和剩余配额计算分数。
3. 稳定场景使用规则和加权评分，高语义分类可由轻量模型辅助。低复杂度任务小模型先行，格式失败、低置信或验证未通过时升级；厂商故障按场景化备用链切换，不能假设模型完全等价。
4. 为每家供应商设置独立连接池、限流器、重试预算和熔断器，防止故障扩散。切换只迁移标准化任务状态、证据和未完成步骤；非幂等工具通过业务幂等键防重放。
5. 记录候选集、过滤原因、特征快照、策略版本和最终选择。离线回放、Shadow及灰度评估任务成功率、P95、切换率和单位成功成本，并设置单厂商流量上限。

| 层次 | 核心职责 |
|---|---|
| 适配层 | 协议、错误与用量统一 |
| 策略层 | 约束过滤与动态评分 |
| 韧性层 | 限流、熔断、备用切换 |
| 治理层 | 审计、预算、评测与回放 |

**相关知识点：** Model Gateway、能力矩阵、数据驻留、动态路由、故障域、模型级联、Shadow、决策日志。

#### 71、模型降级会不会影响用户体验？
模型降级会影响能力上限，但不必等同于体验恶化；通过**按场景降级、能力契约、结果校验和透明反馈**，可把故障转化为“功能受限但结果可信”。关键是守住安全和正确性底线。

1. 先定义场景SLO和最低可接受能力，包括格式、事实、工具、上下文、语言及安全要求。备用模型不满足硬约束时不得承接，可改为检索答案、规则流程、只读模式、排队稍后处理或人工接管。
2. 降级顺序应优先减少非核心能力：关闭Reflection和多候选，降低上下文与输出长度，缩小工具集，再切换低档模型。高风险写操作、金融医疗建议和权限决策不可仅为可用性而降低校验标准。
3. 使用统一Schema、系统指令和回归集缩小模型差异；切换后执行事实、格式和业务后置条件验证。能力差距较大时，限制任务范围并避免复杂多步计划。
4. 对用户说明“当前使用简化模式”、受限能力及可选操作，保留已完成状态，避免无提示的风格、精度和功能突变。恢复主模型后不应自动重复已产生副作用的步骤。
5. 监控降级率、降级成功率、用户重试/放弃率、质量差值、P95和单位成功成本；按租户与任务风险灰度验证降级链。

| 降级方式 | 体验影响 | 适用条件 |
|---|---|---|
| 减少反思/候选 | 轻微 | 低风险任务 |
| 切换小模型 | 质量可能下降 | 能力契约满足 |
| 规则/只读模式 | 功能受限 | 结果可确定 |
| 人工接管 | 时延增加 | 高风险任务 |

**相关知识点：** Graceful Degradation、能力契约、SLO、功能降级、质量门禁、用户透明度、故障恢复。

#### 72、如何控制熔断和切换带来的 Token 成本？
控制成本的核心是让熔断与切换共享**端到端Token预算、有限重试和最小状态迁移**。备用模型不应成为无上限的第二次完整执行；每次切换都必须基于预期成功收益和剩余预算。

1. 根任务创建总预算，拆分输入、输出、重试和备用额度，并向调用传播。路由前估算迁移上下文与备用模型价格；若超过余额，采用摘要降级、规则结果或人工处理。
2. 熔断器尽早阻止无效调用，并与重试预算联动。单层统一重试，使用指数退避与抖动，禁止网关、SDK和Agent各自重试；接近Deadline时不再尝试备用。
3. 首次请求尽量采用可复用的前缀缓存。切换时仅传目标、约束、证据、已完成步骤和未决问题，不复制完整对话、失败输出和重复工具结果；长内容使用引用或摘要。
4. 按兼容矩阵选择能完成当前剩余步骤的最低成本模型；低风险任务可关闭Reflection、多候选和冗长解释。流式响应已产生可用内容时，优先续写或明确终止，避免从头生成。
5. 记录原始、重试、迁移、备用Token及最终状态，以**单位恢复成功成本**评估策略。对高切换率、低恢复收益和重复前缀告警，并用演练校准阈值。

| 成本来源 | 控制方式 |
|---|---|
| 无效重试 | 共享预算、熔断与退避 |
| 上下文重传 | 结构化检查点、摘要与引用 |
| 高价备用 | 能力匹配、最低可用档位 |
| 重复生成 | 续写、缓存与幂等恢复 |

**相关知识点：** Token Budget、Retry Budget、熔断、上下文迁移、Prompt Cache、单位恢复成本、Deadline。

#### 73、Context Window越来越大，为什么仍然要控制Token成本？
更大的Context Window只提高容量上限，不意味上下文免费或全部有效。Token同时影响**费用、首Token时延、吞吐、显存、计算和答案质量**；冗余内容还会稀释关键信号。

1. API通常按输入和输出Token计费，长对话每轮重发历史使累计成本持续增长。Agent的工具结果、反思和重试进一步放大消耗，高QPS下尤其明显。
2. Attention的Prefill计算随序列长度增长；即使FlashAttention改善访存，长输入仍增加TTFT、GPU占用和批处理难度。KV Cache随上下文增长，压缩并发容量。
3. “上下文中存在”不等于模型能稳定使用。无关记录、重复证据和冲突旧信息会造成Lost in the Middle、注意力稀释与上下文污染。
4. 保留系统约束、当前目标、关键事实、未完成状态和证据；历史采用分层摘要，工具大结果保存引用，知识通过RAG按需召回，并利用前缀缓存。
5. 设置请求、会话、Agent步骤和租户预算，监控输入输出比、缓存命中、单位成功任务Token、TTFT及KV容量。压缩必须以任务成功率回归验证。

| 长上下文代价 | 直接影响 |
|---|---|
| 输入计费 | 单次及累计费用上升 |
| Prefill与KV增长 | 时延、显存、并发恶化 |
| 信息冗余冲突 | 召回与推理质量下降 |

**相关知识点：** Context Window、Prefill、KV Cache、TTFT、Lost in the Middle、RAG、上下文压缩、Prompt Cache。

#### 74、长对话场景如何进行上下文压缩？
长对话压缩应采用**保真分层、结构化状态与按需召回**，不是简单截断或一次性摘要。目标是在Token预算内保留影响后续决策的信息，并允许关键原文追溯。

1. 将上下文分为规则、工作状态、历史摘要和外部记忆层。系统规则、安全约束、当前目标及工具Schema固定保留；实体、决策、待办、约束和证据以结构化字段维护。
2. 对较旧轮次做滚动摘要，按主题形成层级摘要，并记录来源消息ID、时间、置信度与版本。数值、否定、权限、承诺和未解决冲突应原样或结构化保留，禁止让摘要模型自行补全事实。
3. 工具返回、文档和代码等大对象存入外部存储，只在上下文保留内容哈希、引用、关键片段与访问权限；当前问题到来时使用关键词、向量和时间衰减混合召回，再经Rerank控制Top-K。
4. 触发条件可基于Token水位、主题切换或阶段完成。压缩后执行一致性检查：比较关键槽位、未完成任务和引用是否丢失；高风险字段通过规则校验，必要时保留原文窗口。
5. 监控压缩率、召回命中、事实丢失率、冲突率、任务成功率与节省Token。摘要需可回滚；事实变更时更新状态并使旧摘要失效。

| 方法 | 优势 | 风险 |
|---|---|---|
| 滑动窗口 | 简单、低延迟 | 早期关键信息丢失 |
| 滚动摘要 | 压缩率高 | 摘要漂移 |
| 结构化状态 | 决策信息稳定 | Schema维护成本 |
| 外部记忆召回 | 容量大 | 召回错误 |

**相关知识点：** 分层记忆、Conversation Summary、滑动窗口、结构化状态、RAG、Rerank、摘要漂移、可追溯性。

#### 75、Conversation Summary如何设计？
Conversation Summary应是**可验证、可增量更新、可追溯的会话状态**，而非自由散文。它必须区分事实、偏好、决策、待办和临时推测，并保留来源。

1. Schema至少包含当前目标、参与实体、稳定偏好、关键事实、约束、已完成动作、待办、冲突、证据引用和更新时间。事实附source message ID、时间与置信度；模型推断单独标记，不能写成用户明确陈述。
2. 采用增量合并：新消息先抽取变更，再由规则处理新增、修改、撤销和过期。用户最新明确更正优先，但安全与系统约束不可被覆盖；冲突未解决前并列保存。
3. 数字、日期、否定、权限、承诺、工具回执和高风险条件尽量结构化或引用原文。大段文档只存摘要、哈希和定位信息，需要时按权限回取，避免在每轮反复注入。
4. 摘要在Token阈值、主题结束或任务检查点触发，使用固定模板与低随机性生成。更新后校验必填字段、实体一致性、待办数量和引用有效性；关键字段可由规则或第二模型复核。
5. 摘要需版本化、可回滚并设TTL，隐私字段按策略脱敏和删除。通过任务成功率、事实遗漏率、矛盾率、压缩比和召回率评估，不能仅看文本相似度。

| 内容类型 | 保存方式 |
|---|---|
| 目标、约束、待办 | 结构化字段 |
| 用户原始事实 | 字段加消息引用 |
| 模型推断 | 明确标记置信度 |
| 大文档/工具结果 | 摘要、哈希与外部引用 |

**相关知识点：** Conversation Summary、Schema、增量合并、事实溯源、摘要漂移、版本化、TTL、隐私治理。

#### 76、长期记忆召回过多会带来什么问题？
长期记忆召回过多会造成**成本上升、首Token变慢、信号稀释、事实冲突和隐私暴露**。目标不是召回数量，而是对当前任务有效且可信的最小证据集。

1. 大量记忆占用Context Window和KV Cache，降低并发并增加输入费用；无关片段会产生Lost in the Middle，使模型忽略当前指令或真正关键证据。
2. 不同时间的偏好、身份和业务状态可能冲突。缺少时间、来源和有效期时，模型会把旧事实当成现状；推断被误存为事实还会形成记忆污染。
3. 召回内容属于不可信输入，历史文档中的指令可能触发Prompt Injection。跨租户、跨项目或权限已撤销的记忆被召回，会形成严重的数据越权。
4. 检索先按租户、权限、任务类型、时间和状态硬过滤，再混合召回；结合Rerank、阈值、去重和MMR控制Top-K，并保留来源、时间、置信度及TTL。
5. Prompt中将记忆标记为“参考数据而非指令”，冲突时优先当前用户明确输入和权威系统。监控召回精确率、有效使用率、冲突率、注入命中、每任务记忆Token及质量增益；无增益片段应停止注入。

| 过量召回问题 | 控制措施 |
|---|---|
| 无关信息稀释 | 阈值、Rerank、Top-K |
| 新旧事实冲突 | 时间、版本、TTL |
| 重复与单一视角 | 去重、MMR |
| 越权与注入 | 权限过滤、数据/指令隔离 |

**相关知识点：** 长期记忆、Rerank、MMR、Top-K、记忆污染、Lost in the Middle、TTL、Prompt Injection。

#### 77、如何避免上下文污染？
避免上下文污染要把信息视为**带来源、权限、时效和可信度的数据**，通过写入治理、检索隔离、冲突处理与执行前校验，阻止错误或恶意内容影响决策。

1. 明确指令层级，系统策略与开发约束只来自受控配置；用户文本、网页、文档、工具结果和记忆均标记为数据，使用边界标签隔离，禁止其中的自然语言指令改变权限或工具策略。
2. 记忆写入前执行事实/推断分类、敏感检查、去重和质量门禁。仅保存稳定信息，记录主体、来源、时间、置信度、租户、权限、TTL和版本；模型猜测不得升级为事实。
3. 召回前按租户、项目、ACL和有效期硬过滤，再以阈值、Rerank、Top-K和去重限量。旧事实与当前输入冲突时，优先权威且更新的来源，并显式呈现冲突。
4. 摘要采用结构化Schema和增量合并，关键数字、否定、承诺及工具回执保留引用。用户更正时建立撤销记录，使相关摘要、Embedding和缓存同步失效，避免陈旧副本回流。
5. 工具执行前验证参数、权限和后置条件，高风险动作要求规则或人工确认。监控污染命中、冲突率、过期与越权召回、纠正时间，并支持追溯删除。

| 污染来源 | 主要防护 |
|---|---|
| 恶意文档指令 | 指令/数据隔离 |
| 错误模型推断 | 事实标签与写入门禁 |
| 过期或冲突记忆 | 版本、TTL、来源优先级 |
| 跨域数据 | ACL与租户硬隔离 |

**相关知识点：** Context Pollution、Prompt Injection、Provenance、ACL、TTL、记忆写入门禁、缓存失效、后置条件。

#### 78、RAG为什么能够降低Token成本？
RAG通过**按需注入少量相关证据**，替代把全部知识库或长文档送入模型，可降低输入Token及Prefill、KV Cache成本；但检索与Rerank也有费用，设计不当可能增本。

1. 文档离线切分并建立索引，请求时只召回相关Top-K片段，形成“最小充分证据集”。变化知识无需写入Prompt或重新微调，更新索引即可生效。
2. 检索结果可去重、压缩和引用化：大结果存于外部，只注入关键行、摘要与定位。多轮复用检索缓存，稳定前缀利用Prompt Cache，避免重复计费。
3. 收益取决于语料规模、查询选择性和精度。Chunk过大、Top-K过高、重叠过多会填满上下文；低质召回还会引发重试和升级，抵消节省。
4. 采用元数据硬过滤、混合检索、Rerank、动态Top-K和上下文去重，在召回率与Token间优化。简单事实可由检索结果或模板直接回答，复杂综合再调用大模型。
5. 评估应比较端到端任务成功率、每次查询的检索与模型总成本、输入Token、TTFT、重试率和**单位成功任务成本**，而非只统计向量库命中率。

| 方案 | 输入规模 | 主要代价 |
|---|---|---|
| 全量长上下文 | 大且重复 | 模型Token与时延 |
| RAG按需注入 | 小且相关 | 检索、Rerank成本 |
| 微调注入知识 | 推理输入较小 | 训练、更新与遗忘风险 |

**相关知识点：** RAG、Top-K、Chunk、Hybrid Search、Rerank、Prompt Cache、动态检索、单位成功成本。

#### 79、Chunk大小如何影响成本和效果？
Chunk大小决定**语义完整性、召回粒度、索引规模和注入Token**。不存在通用最优值：过小会割裂证据并增加索引开销，过大则混入噪声、降低区分度并推高成本。

1. 小Chunk适合条款、FAQ和字段事实，定位精确、注入Token少；但标题、指代可能丢失，答案跨片段时需要更高Top-K，Embedding条目也会增加。
2. 大Chunk能保留段落、表格和代码关系，适合跨句推理；但一个向量代表多个主题，局部事实相似度被稀释，并把无关文本送入模型。
3. 应优先按文档结构、语义边界和内容类型切分，而非固定字符数。保留标题与层级元数据；代码按函数/类、表格按完整表或行组切分。适量Overlap用于跨边界语义，但需在索引和注入阶段去重。
4. 可采用父子Chunk：小片段负责检索，命中后返回包含必要上下文的父段；或先召回大段再做句级压缩。根据问题复杂度动态选择Top-K和父段范围。
5. 用真实问答集评测Chunk长度、Overlap和Top-K，观察Recall@K、证据完整率、正确率、输入Token、时延和单位成功成本，并按文档类型配置。

| 大小 | 优势 | 主要风险 |
|---|---|---|
| 小Chunk | 精准、注入少 | 语义割裂、条目多 |
| 大Chunk | 上下文完整 | 噪声与Token高 |
| 父子Chunk | 兼顾定位与完整性 | 实现复杂 |

**相关知识点：** Semantic Chunking、Overlap、父子检索、Recall@K、上下文压缩、Embedding、动态Top-K。

#### 80、Top-K应该如何选择？
Top-K应按**召回充分性、上下文预算、查询类型和Rerank能力**动态选择。K过小会漏证据，过大则引入噪声、冲突和Token；最优点以任务成功率确定。

1. 用离线集绘制Recall@K、Precision@K、正确率和输入Token曲线，选择边际收益下降前的区间。单跳问题需较小K，多跳与跨文档综合需更大候选集。
2. 分离“候选K”和“注入K”：先取较大候选集保证召回，再经Cross-Encoder或轻量模型Rerank、去重、权限过滤和阈值，只注入少量高质片段。
3. 动态策略根据查询长度、实体数量、意图、多跳复杂度、分数分布、Chunk大小和剩余Token预算调整。若头部结果分数高且断层明显，可提前停止；分数接近或证据覆盖不足时扩大检索。
4. 采用MMR平衡相关性与多样性，避免多个近重复Chunk占满名额。父子检索中，小Chunk命中后合并同一父段，需去重重叠部分；强制保留引用来源和关键反例。
5. 监控证据使用率、无答案率、重试率、输入Token、P95和单位成功成本，按知识库和问题类型配置。高风险场景还需证据完整性校验。

| 策略 | 适用场景 | 代价 |
|---|---|---|
| 固定K | 分布稳定、简单系统 | 难适配复杂度 |
| 阈值截断 | 分数可校准 | 可能结果过少 |
| 动态K | 查询差异大 | 策略更复杂 |

**相关知识点：** Recall@K、Precision@K、Rerank、MMR、动态Top-K、分数校准、证据覆盖、Token Budget。

#### 81、Rerank带来的收益是否值得增加额外成本？
Rerank是否值得取决于它能否提高**证据精度、任务成功率并减少无关Token**。候选多、语义相近或高价值任务通常值得；简单FAQ和首条稳定命中时可跳过。

1. 向量或BM25负责高召回初筛，Reranker用Query—Document联合特征精排，能处理否定、关系和时间语义。它把大候选集压缩为小注入集，降低上下文噪声。
2. 成本包括调用费、时延、算力和复杂度；收益包括正确率提升、重试减少、小模型可用率提高、Token下降。应比较**单位成功任务总成本**。
3. 离线消融比较不同候选K、模型大小的Recall、NDCG、证据完整率和正确率；线上灰度观察P95、无答案率、重试率和Token，计算增量收益。
4. 采用条件触发降低成本：头部相似度断层明显、规则精确命中或低风险FAQ直接跳过；分数接近、多跳、高风险或候选重复时开启。可用轻量Cross-Encoder批量排序，并缓存标准查询结果。
5. 若排序指标提升却未改善任务质量，瓶颈可能在切分、召回或生成，应停止增配。必须先做权限过滤，避免越权内容进入候选。

| 场景 | 建议 |
|---|---|
| FAQ精确命中 | 通常跳过 |
| 候选相似、语义细粒度 | 启用 |
| 多跳或高风险 | 启用并校验证据 |
| 极低时延链路 | 条件触发或轻量模型 |

**相关知识点：** Rerank、Cross-Encoder、NDCG、消融实验、条件路由、检索缓存、单位成功成本。

#### 82、混合检索相比纯向量检索有什么优势？
混合检索将**稀疏关键词与稠密语义召回**结合，既保留精确词项、编号和专名，又覆盖同义表达和改写，在异构知识库中更稳健。

1. BM25擅长型号、错误码、人名、缩写和罕见词，结果可解释；向量检索擅长同义词、改写和概念相关性。纯向量可能优先语义相近但实体错误的片段。
2. 两路先获取候选，再用RRF、归一化加权或学习排序融合。分数尺度不同，不能直接相加未经校准的BM25分数与余弦相似度；融合后去重和Rerank。
3. 查询可动态分流：含编号、引号短语和强实体时提高关键词权重；描述性、模糊或跨语言查询提高向量权重。元数据、ACL、租户、时间和文档状态属于硬过滤，应在候选进入LLM前执行。
4. 混合检索增加索引、延迟和调参成本，可通过并行召回、有界候选、缓存及条件跳过控制。若查询均为精确键，稀疏检索可能足够。
5. 使用真实问题集比较Recall@K、MRR、NDCG、关键证据覆盖率、答案正确率、P95和单位成功成本，并按查询类型做消融，证明增益来自融合而非更大的候选数。

| 方式 | 擅长 | 主要弱点 |
|---|---|---|
| 关键词检索 | 精确实体、编号、罕见词 | 同义改写弱 |
| 向量检索 | 语义相似、自然表达 | 精确词可能失真 |
| 混合检索 | 兼顾精确与语义 | 系统与调参更复杂 |

**相关知识点：** BM25、Dense Retrieval、RRF、分数校准、Hybrid Search、Rerank、ACL过滤、消融评测。

#### 83、如何判断一个任务应该使用大模型还是小模型？
模型选择应依据**能力底线、任务复杂度、风险、可验证性和预算**。先以硬约束排除不适用模型，再选择满足质量SLO的最低成本档位，并允许运行时升级。

1. 特征包括模态、语言、上下文长度、Tool Calling需求、领域、歧义度、步骤数、跨文档关系、代码复杂度和输出约束。数据驻留、敏感级别、权限及模型能力属于硬约束，不能用成本权重抵消。
2. 小模型适合分类、抽取、改写、格式化、FAQ和规则明确且可程序验证的任务；大模型适合开放推理、复杂规划、长尾异常、跨领域综合与冲突仲裁。高风险任务即使使用大模型，也需证据和确定性校验。
3. 路由可采用“规则/轻量分类器预测复杂度→小模型尝试→验证器检查→必要时升级”的级联。升级信号包括低置信、分布外、Schema失败、证据不足、工具参数错误、多轮无进展和用户明确要求。
4. 分类器用离线标注校准，输出成功概率。决策函数比较模型的预测质量、P95、价格、健康度和升级成本；小模型失败的重试成本也要计入。
5. 记录特征、候选、路由原因和结果，通过Shadow、灰度及回放评估漏升级率、误升级率、成功率、P95和单位成功成本。

| 维度 | 倾向小模型 | 倾向大模型 |
|---|---|---|
| 任务边界 | 明确、结构化 | 开放、模糊 |
| 推理复杂度 | 单步、局部 | 多步、跨域 |
| 可验证性 | 规则可校验 | 需综合判断 |
| 长尾风险 | 低 | 高 |

**相关知识点：** Model Router、复杂度分类、模型级联、置信校准、OOD检测、质量SLO、单位成功成本。

#### 84、Model Router通常如何设计？
Model Router通常设计为**能力过滤、策略决策、执行适配、反馈优化**四层。先满足安全与能力硬约束，再优化质量、时延、成本和健康度，并保证选择可解释、可回放。

1. 模型画像包含模态、语言、上下文、Tool Calling、领域质量、价格、配额、地域和版本；请求侧提取任务类型、复杂度、风险、SLA、预算及数据等级。
2. 候选生成阶段先做硬过滤：数据不得出域、上下文不足、工具不兼容或租户未授权时直接排除。候选排序可从规则和加权评分起步，复杂场景使用分类器或学习排序预测成功概率。
3. 评分考虑质量、时延、成本、实时错误率、队列、限额和切换代价。低风险任务小模型先行，验证失败、低置信或分布外时升级；故障按兼容矩阵切换。
4. 执行层统一消息、流式事件、错误、用量和Tool Schema，为不同模型维护Prompt模板、Token预算、限流与熔断。路由服务需低延迟、高可用，并在策略服务异常时使用安全的静态默认规则。
5. 日志记录候选、过滤原因、特征、分数和策略版本。离线评测、Shadow、灰度及反事实回放优化成功率、P95、升级率和单位成功成本。

| 层次 | 职责 |
|---|---|
| 能力层 | 模型与请求画像 |
| 决策层 | 硬过滤、评分、级联 |
| 执行层 | 适配、限流、熔断 |
| 反馈层 | 评测、回放、策略更新 |

**相关知识点：** Model Router、能力画像、硬约束、Learning to Rank、模型级联、Shadow、反事实评估、决策日志。

#### 85、多模型协同架构如何实现？
多模型协同围绕**任务分解、标准契约、状态编排、结果验证和预算控制**实现。仅当专业分工或验证收益超过额外Token、时延和冲突成本时启用。

1. 编排器将任务拆为带Step ID、输入、依赖、验收标准和Deadline的DAG。按能力画像把分类、检索、代码、视觉、生成与评审分配给模型，简单步骤优先用小模型。
2. 模型间通过统一Schema交换目标、证据、结构化结果、置信度和未决问题。状态由编排器持久化并版本控制，工具调用使用幂等键，避免重复副作用。
3. 常见模式包括级联、专家流水线、并行候选和生成—评审。并行结果先经规则、权威数据和后置条件验证，再按证据质量融合；不能仅因语言流畅或多数投票就选择答案。
4. 为根任务设置Token、调用次数、并发和Deadline预算，并向子调用传播。限制并行宽度和评审轮数，支持取消慢分支、Early Exit、缓存与Singleflight；高风险冲突转人工。
5. Trace记录模型版本、Prompt、输入摘要、路由原因和合并过程。评测成功率、分工增益、冲突率、P95和单位成功成本；删除无边际收益的角色。

| 模式 | 适用场景 | 主要代价 |
|---|---|---|
| 级联 | 难度分层 | 漏升级 |
| 专家流水线 | 能力互补 | 依赖与状态复杂 |
| 并行候选 | 高不确定任务 | 成本高 |
| 生成—评审 | 质量门禁 | 时延增加 |

**相关知识点：** DAG编排、Supervisor、模型级联、Ensemble、LLM-as-a-Judge、结构化契约、幂等、Early Exit。

#### 86、Agent为什么会出现Token爆炸问题？
Agent的Token爆炸来自**多轮、上下文重复、工具大结果、并行、反思重试和缺少终止条件**的乘法效应。治理必须覆盖任务图，而非只限制单次输出。

1. ReAct每步都会重发历史；对话、系统Prompt、工具Schema和检索片段随轮次增长。工具返回日志或代码原文时，后续每轮重复计入Token。
2. Reflection、Self-Consistency和多Agent会产生多个候选与评审轮次；从头重试、切换时复制完整上下文进一步放大。规划不清会形成调用循环。
3. 根任务设置Token、调用、步骤、并发、重试和Deadline预算并向下传播；软阈值时关闭反思、缩小Top-K，硬阈值立即终止或转人工。
4. 上下文保留目标、约束、事实、状态和证据；旧历史摘要，大结果外部存储并按需引用。稳定前缀缓存，相同请求去重与Singleflight。
5. 每步声明信息增益与验收条件；无新证据、状态重复或连续失败时Early Exit。监控任务Token、每步增量、重复率、工具占比和单位成功成本。

| 放大源 | 控制方式 |
|---|---|
| 历史重复 | 摘要、引用、前缀缓存 |
| 反思与分支 | 条件触发、限制轮数 |
| 工具大结果 | 外部存储、字段裁剪 |
| 无限循环 | 状态检测、预算、Early Exit |

**相关知识点：** Token Explosion、ReAct、Reflection、Self-Consistency、预算传播、Singleflight、Early Exit、上下文压缩。

#### 87、ReAct模式如何控制推理成本？
ReAct成本控制是把“思考—行动—观察”变成**有预算、有状态、有停止条件的闭环**，仅在外部信息有价值时调用工具，避免重传完整轨迹。

1. 先生成短计划和验收标准，为根任务设置Token、步骤、工具、重试和Deadline预算。每步检查余额；简单问答、确定性计算或缓存命中时直接回答。
2. 工具目录按权限和任务裁剪，Schema精简。模型说明缺失信息，路由器再决定调用；相同参数使用缓存、幂等键和Singleflight，优先批量接口。
3. Observation只保留状态码、关键字段、引用和摘要，大结果存外部。上下文维护目标、约束、状态和未决问题，旧轨迹滚动压缩。
4. 验证器判断Schema、事实、权限和后置条件；通过即Early Exit。无新证据、状态重复、工具连续失败或信息增益低时终止，必要时升级或转人工。
5. Reflection仅在高风险、低置信或验证失败时触发且限一轮；低价值步骤用小模型。监控步数、工具、推理Token、重复率和单位成功成本。

| 控制点 | 机制 |
|---|---|
| 进入ReAct前 | 难度判断、缓存、短计划 |
| 循环中 | 预算、裁剪、摘要、去重 |
| 结束时 | 验证器、Early Exit |
| 异常时 | 有限重试、升级或人工 |

**相关知识点：** ReAct、Token Budget、工具路由、Singleflight、Observation压缩、信息增益、Early Exit、验证器。

#### 88、Reflection机制什么时候开启最合适？
Reflection适合在**错误代价高、结果可评审、首次输出不确定且可修正**时条件开启；不应成为固定步骤，否则增加Token和时延，还可能把正确答案改坏。

1. 触发信号包括Schema或单测失败、证据不足、工具后置条件未满足、低置信、候选冲突、复杂代码/规划及高风险输出。已通过确定性验证时直接结束。
2. 简单分类、抽取、FAQ、低价值高QPS任务，以及结果无法获得新证据、接近Deadline或预算不足时应关闭。安全策略拒绝、权限不足和确定性业务错误不能靠Reflection绕过。
3. 反思Prompt基于Rubric，只检查事实、约束、遗漏、工具参数和验收条件，输出结构化问题与建议；Critic默认只读，与执行权限隔离。
4. 通常限制一轮“评审—修订”，只有新增证据或校验结果变化才允许第二轮。高价值任务可让独立模型评审，普通任务使用小模型或规则验证器；若连续输出状态相同则Early Exit。
5. 通过A/B和消融测量首次成功率、反思后净提升、正确改错率、误改率、额外Token、P95和单位成功成本。只有增量质量收益超过成本与误改风险的场景，才纳入触发策略。

| 场景 | 是否开启 |
|---|---|
| 验证失败且可修正 | 开启 |
| 高风险复杂任务 | 条件开启 |
| 已通过确定性校验 | 关闭 |
| 权限/策略拒绝 | 关闭并终止 |

**相关知识点：** Reflection、Critic、Rubric、验证器、条件触发、Early Exit、误改率、消融实验。

#### 89、如何限制Agent无限循环调用工具？
限制无限循环需要**硬预算、状态机、重复检测、进展判定和工具治理**。Prompt约束不可靠，编排层必须拥有最终中止权。

1. 根任务设置步骤、工具次数、Token、重试和Deadline；预算向子Agent传播，不能在嵌套调用中重置。软阈值时缩小工具集，硬阈值立即停止或转人工。
2. 工具调用生成指纹，包括工具名、关键参数、资源版本和状态。相同指纹且状态未变时复用缓存或拒绝；写操作使用幂等键，防止重复副作用。
3. 状态机定义合法转移与每步后置条件。Agent调用前必须声明预期获得的信息和成功判据，调用后计算新证据、已解决约束或状态差异；连续若干步信息增益为零、状态回到历史节点或错误码重复即触发断路。
4. 错误分为可重试、需改参和永久失败；永久错误、权限拒绝及参数校验失败不得无条件重试。工具返回结构化错误与修复提示，重试采用共享预算和退避。
5. 记录Trace、状态哈希、循环原因和终止动作，监控步数、P99、重复调用率、无进展率和单位成功成本。回放样本以修正规划器。

| 防线 | 作用 |
|---|---|
| 硬预算 | 限制最坏资源消耗 |
| 调用指纹 | 识别重复请求 |
| 进展检测 | 识别无效变参循环 |
| 状态机 | 限制非法转移 |

**相关知识点：** Loop Detection、状态机、调用指纹、信息增益、幂等、Retry Budget、Circuit Breaker、Deadline。

#### 90、Prompt Cache和Semantic Cache有什么区别？
两者都降低计算，但层级不同：**Prompt Cache复用相同前缀计算，Semantic Cache复用语义相近请求的结果**。前者仍生成新答案，后者可能返回历史答案，风险更高。

1. Prompt Cache基于模型、版本和Token化前缀，命中后跳过部分Prefill，仍由模型生成。系统Prompt、工具Schema和固定知识前置且顺序稳定时命中率高。
2. Semantic Cache对查询生成Embedding，检索相似历史请求，超过阈值后复用结果。它覆盖措辞变化，但时间、权限、租户和上下文差异会导致误命中。
3. Prompt Cache随模型版本、前缀Token或工具变化失效；Semantic Cache还需把知识版本、权限、时间窗和安全策略纳入Key，并设置TTL。
4. 高风险任务只复用检索结果；写操作、实时价格和账户状态禁止语义答案缓存。两者均需租户隔离和审计。
5. 监控命中率、节省Token、P95、陈旧率、错误命中率和单位成功成本。语义阈值通过标注集校准，并支持回源。

| 维度 | Prompt Cache | Semantic Cache |
|---|---|---|
| 复用对象 | 前缀计算 | 答案或中间结果 |
| 命中依据 | Token前缀一致 | 语义相似 |
| 主要收益 | 降Prefill成本 | 省完整模型调用 |
| 核心风险 | 命中率低 | 错误或陈旧复用 |

**相关知识点：** Prefix Cache、Prefill、Semantic Cache、Embedding、Cache Key、TTL、缓存污染、租户隔离。

#### 91、如何提高缓存命中率？
提高命中率要稳定**等价请求表示、缓存键和失效边界**，同时保证权限与时效。宽松匹配产生的错误复用会降低质量并造成泄露。

1. Prompt Cache把系统指令、工具Schema、示例和共享知识放在前缀，保持字段顺序、工具排列和参数稳定；用户变量、时间戳和请求ID放到尾部。按模型版本建Key。
2. 精确缓存规范化Unicode、大小写、空白和无语义参数，但不能删除影响权限、语言、时间或业务语义的字段。相同工具请求使用参数指纹和Singleflight。
3. Semantic Cache用意图、实体、租户、权限、知识版本和时间窗构成复合Key，再由Embedding判断。按场景校准阈值；高风险、实时状态和写操作不复用答案。
4. 对热点请求预热，对长尾不盲目缓存；TTL依据数据变化速度设置，并通过事件驱动失效同步知识、摘要和权限变更。缓存空值与失败需短TTL，防止故障结果长期扩散。
5. 监控各类命中率、可缓存率、错误命中、陈旧率、节省Token、P95和驱逐原因。用未命中日志发现Key碎片化，以单位成功成本和质量回归约束。

| 命中障碍 | 优化 |
|---|---|
| Prompt前缀抖动 | 稳定模板与字段顺序 |
| 等价参数不同 | 安全规范化 |
| 知识频繁变化 | 版本Key与事件失效 |
| 并发相同请求 | Singleflight |

**相关知识点：** Cache Key、Prompt Cache、Semantic Cache、规范化、Singleflight、TTL、预热、缓存失效。

#### 92、企业级Agent如何实现Token预算管理？
企业级Token预算采用**分层配额、预算传播、实时核算和策略化降级**，覆盖输入输出、重试、反思、检索及多Agent，防止局部合理而总成本失控。

1. 预算按组织、租户、项目、Agent、任务和步骤分层，区分周期财务配额与单任务上限。根任务创建Budget Context，记录Token、金额、调用、Deadline及保留额度，并向下传播。
2. 调用前按价格、输入和最大输出预占额度；流式按实际用量扣减，结束后对账并释放差额。重试、切换和子Agent不得重置预算。
3. 软阈值触发压缩、降低Top-K、关闭Reflection、选择小模型或缩短输出；硬阈值停止非核心步骤、返回部分结果或转人工。安全与审计额度应预留。
4. 设置优先级和价值密度，高价值任务使用受控共享池，低优先级排队或降级；超额需审批。异常租户限流隔离，防止抢占预算。
5. 成本账本按Task ID记录模型、Prompt版本、缓存、重试和工具费用，监控预算消耗速度、预测超支、单位成功成本及闲置额度。定期以质量回归和业务价值校准配额。

| 层级 | 管理对象 |
|---|---|
| 财务配额 | 租户、项目的周期总额 |
| 任务预算 | Token、金额、步骤与Deadline |
| 运行时门控 | 预占、扣减、软硬阈值 |
| 策略降级 | 压缩、缓存、小模型、终止 |

**相关知识点：** Token Budget、Budget Context、配额、预占核算、成本账本、预算传播、价值密度、单位成功成本。

#### 93、如何统计每个Agent的Token消耗？
统计应建立**任务—Agent—步骤—模型调用**成本账本，统一厂商口径，并将重试、缓存、反思和共享调用归因；仅汇总总Token无法解释来源。

1. 任务生成Task ID，子Agent携带Parent ID、Step ID和Trace ID。网关记录租户、Agent、模型版本、Prompt版本、输入、输出、推理、缓存Token及厂商请求ID。
2. 以厂商最终usage为计费事实；流式在结束事件汇总，中断时用已接收用量或Tokenizer估算并标记。各厂商用量映射为统一Schema并保留原始字段。
3. 重试、降级和切换标记attempt与reason，计入触发Agent。共享检索、Judge或子Agent按独占、均摊或业务权重分配，规则固定以防重复。
4. 输入Token拆分系统Prompt、历史、记忆、RAG、工具Schema与结果。成本按调用时价格计算，保留币种和价格版本；定期与厂商账单对账。
5. 展示每Agent总量、每成功任务Token、P95、重试占比、缓存节省、异常增长和预算达成率。明细需脱敏并限制访问。

| 归因层级 | 关键字段 |
|---|---|
| 任务 | Task ID、租户、业务结果 |
| Agent/步骤 | Parent、Step、角色 |
| 模型调用 | 模型、attempt、usage |
| 财务 | 价格版本、金额、账单差异 |

**相关知识点：** Cost Ledger、Trace ID、Token Usage、成本归因、流式计量、价格版本、账单对账。

#### 94、如何设计成本监控和告警体系？
成本监控应形成**计量—归因—预算—预测—告警—处置**闭环，并把费用与任务成功率关联。总账无法定位是流量、模型、重试还是上下文膨胀造成。

1. 网关采集输入、输出、推理、缓存Token，模型、价格、重试、路由、工具费和业务结果；以Task ID关联租户、Agent和步骤。定期对账，区分估算值与最终值。
2. 指标包括总成本、每成功任务成本、Token/QPS、输入输出比、重试成本、缓存节省、大模型占比及预算速度。按租户、场景、模型和Prompt版本切片。
3. 预算支持日/月配额、单任务上限和Forecast。告警采用静态阈值、同比异常、单位成本突增和多窗口Burn Rate组合，区分预警、严重与阻断级；短时流量峰值不能造成告警风暴。
4. 告警携带影响范围、贡献模型、最近变更和推荐动作。自动处置可限流、关闭Reflection、降低Top-K、切换小模型；高风险变更需审批且可回滚。
5. 仪表盘同时展示质量、P95和成本，避免只降费导致成功率下降。通过演练验证超预算、价格变更、重试风暴和用量缺失；复盘误报、漏报及节省金额，持续调整阈值。

| 告警类型 | 示例 |
|---|---|
| 预算 | 消耗速度将提前耗尽 |
| 单位成本 | 每成功任务成本突增 |
| 结构异常 | 重试或大模型占比激增 |
| 计量异常 | 用量缺失、账单偏差 |

**相关知识点：** FinOps、成本归因、Cost Ledger、Forecast、Burn Rate、单位成功成本、预算告警、自动降级。

#### 95、如何在效果、时延和成本之间进行权衡？
三者权衡先定义**不可突破的质量与安全底线**，再在满足SLO的方案中优化时延和单位成功成本。不能用加权分数掩盖硬约束，也没有统一最优模型。

1. 质量指标包括成功率、事实/格式通过率、工具后置条件和安全违规率；时延观察TTFT、P95/P99；成本采用每成功任务总成本，包含重试、检索和工具。
2. 对模型、Prompt、RAG参数和Agent策略做离线与灰度，绘制质量—时延—成本Pareto前沿。三维均被支配的配置淘汰，业务再按价值选择。
3. 路由先按数据、能力和质量底线过滤，再按复杂度、风险、SLA及预算选择。简单任务用小模型，验证失败时升级；高价值任务可用Reflection或Rerank。
4. 降本手段包括稳定前缀缓存、上下文压缩、动态Top-K、工具结果引用和批量调用；降时延包括并行独立步骤、流式输出、Early Exit和容量预热。并行与重试会增本，必须受预算控制。
5. 日志记录特征、策略版本和结果，监控漏升级、误升级、P95、质量与单位成本。需求或价格变化时重新评测。

| 优化方式 | 可能收益 | 主要代价 |
|---|---|---|
| 小模型/短上下文 | 降成本与时延 | 质量上限下降 |
| Rerank/Reflection | 提升质量 | 增时延与成本 |
| 并行调用 | 降尾延迟或提稳健性 | 成本上升 |
| 缓存 | 三者可能同时改善 | 陈旧与误命中风险 |

**相关知识点：** Pareto Front、SLO、单位成功成本、模型路由、质量门禁、灰度实验、Early Exit、价值密度。

#### 96、多Agent架构下如何控制整体Token开销？
多Agent成本治理以**统一预算、角色最小化、结构化通信和边际收益门控**为核心。若各Agent独立扩展上下文、重试和反思，开销会乘法增长。

1. Supervisor为根任务创建Token、金额、调用、步骤和Deadline预算并向下传播；子任务只能消费分配额度，不得重置预算。预留汇总、验证与恢复额度。
2. 仅保留有可测增益的角色，按DAG激活；分类、抽取和校验用小模型，复杂规划与仲裁用大模型。避免通用Agent重复分析。
3. Agent间通过Schema交换目标、证据、结果、置信度和未决问题，不广播完整对话。大结果存外部按需读取；稳定前缀、检索及工具结果使用缓存。
4. 限制并行宽度、候选数、反思轮数和重试次数。聚合器根据证据覆盖和状态变化执行Early Exit，取消慢分支；相同子任务使用指纹去重与Singleflight，工具写操作采用幂等键。
5. 账本按Agent、步骤、模型记录输入输出、缓存、重试和共享成本，监控成功率、增量收益、每Agent Token及单位成功成本。收益不足角色下线。

| 放大点 | 控制机制 |
|---|---|
| 子Agent无限扩张 | DAG与按需激活 |
| 上下文广播 | 结构化状态与引用 |
| 并行候选 | 宽度限制、Early Exit |
| 重试反思 | 共享预算与条件触发 |

**相关知识点：** Multi-Agent、Supervisor、预算传播、DAG、结构化通信、Singleflight、Early Exit、成本归因。

#### 97、除了Token成本，还需要关注哪些AI系统成本指标？
AI系统应按**端到端任务总拥有成本**核算。除Token外，还包括算力、存储、检索、网络、工具、运维、人工审核及失败重试，并应与成功结果关联。

1. 推理设施关注GPU/CPU利用率、显存、KV Cache、实例小时、峰值预留、空闲率和有效TPS；API模式还需记录并发套餐、最低消费及多模态计费。
2. 数据链路包括Embedding更新、向量库查询、Rerank、对象存储、日志、缓存、跨区流量及保留。知识频繁更新时，索引重建和缓存失效可能成为主要成本。
3. Agent链路统计工具API、沙箱、数据库、队列、SSE、重试、降级、并行、Reflection与人工接管。失败任务消耗的所有资源都应计入。
4. 生命周期成本包括数据标注、离线评测、微调训练、模型部署、红队、安全审计、许可证和工程维护；还需考虑供应商锁定、容量冗余和迁移成本。
5. 核心指标采用每成功任务成本、转化成本、毛利率、质量调整成本和成本方差，并按租户、场景、模型归因。同步展示质量与P95，防止隐性成本上升。

| 成本域 | 代表指标 |
|---|---|
| 推理 | GPU小时、KV占用、有效TPS |
| 数据/RAG | Embedding、向量查询、存储 |
| Agent执行 | 工具、重试、连接、人工接管 |
| 生命周期 | 评测、微调、安全与运维 |

**相关知识点：** TCO、FinOps、GPU利用率、KV Cache、RAG成本、人工接管、单位成功成本、质量调整成本。

#### 98、模型路由策略是规则驱动还是模型驱动？
企业路由宜采用**规则管硬约束、模型做语义判断、评分器做多目标优化**的混合方案。纯规则难覆盖长尾，纯模型存在成本和随机性。

1. 数据驻留、敏感级别、租户权限、上下文上限、模态与工具兼容、预算硬限额属于确定性条件，应由规则直接过滤，任何模型评分都不能绕过。
2. 任务意图、复杂度、歧义、推理深度和领域识别可由轻量分类器或小模型判断。输出应是经过校准的类别或成功概率，不直接自由生成模型名称；低置信和分布外请求进入保守默认链。
3. 在合法候选中，评分器综合预测质量、P95、价格、实时健康度、配额和切换代价。低风险任务可小模型先行，Schema失败、证据不足或验证未通过时升级。
4. 高频场景优先规则或分类器；语义复杂时再用LLM路由，并设置超时、缓存与静态兜底。路由模型不得接收无必要的敏感数据。
5. 记录特征、规则命中、模型分数、候选和策略版本，通过离线回放、Shadow和灰度比较路由准确率、漏升级、误升级、额外时延及单位成功成本，防止反馈回路偏差。

| 方式 | 优势 | 局限 |
|---|---|---|
| 规则驱动 | 快、稳定、可审计 | 长尾维护困难 |
| 模型驱动 | 语义泛化强 | 成本、随机性 |
| 混合驱动 | 安全与灵活兼顾 | 工程复杂 |

**相关知识点：** Rule Engine、LLM Router、硬约束、置信校准、OOD、模型级联、Shadow、决策可解释性。

#### 99、如何处理模型调用失败和超时？
应通过**分层超时、错误分类、受控重试、熔断隔离、幂等恢复和降级**处理。策略服从根请求Deadline与重试预算，避免发起必然超时的调用。

1. 设置连接、首Token、Token间隔、单次及端到端超时，并向下游传播Deadline。客户端取消后中止模型流、释放连接与配额，防止继续计费。
2. `429`、部分`5xx`、网络抖动可在幂等前提下重试；参数、鉴权、策略、上下文超限和业务错误不重试。状态未知的写操作先查询结果。
3. 重试采用指数退避、Full Jitter、最大次数和总时长，并尊重`Retry-After`。网关统一重试，禁止SDK、Agent和业务层叠加；所有尝试共享同一Retry Budget和Token预算。
4. 按模型和供应商设置独立熔断、限流与连接池。错误率或慢调用率超阈值时快速失败，半开仅放探测；备用模型必须满足兼容要求。
5. 降级可缩短上下文、关闭Reflection、改用小模型、规则答案或人工接管。记录attempt、错误层、耗时、Token和结果，监控单位恢复成本。

| 故障 | 处理 |
|---|---|
| 瞬时网络/过载 | 有界退避重试 |
| 参数/权限/策略错误 | 直接失败并修正 |
| 持续供应商故障 | 熔断并兼容切换 |
| 状态未知写操作 | 查询、幂等或补偿 |

**相关知识点：** Deadline、Retry Budget、Full Jitter、熔断、半开探测、幂等、取消传播、Graceful Degradation。

#### 100、如何评估不同模型的能力画像？
能力画像是**按任务、风险和运行条件分层的版本化数据资产**，不能用总分代表模型。它包含质量、时延、成本、稳定性和合规属性，供路由使用。

1. 静态维度包括模态、语言、上下文、Tool Calling、结构化输出、地域、数据保留、价格和配额。任务维度覆盖分类、抽取、RAG、推理、代码、规划及领域知识。
2. 评测集由公共基准、真实脱敏、长尾失败和对抗样本组成，按难度、语言、场景、风险分桶。指标采用成功率、事实正确率、Schema通过率、工具后置条件和违规率。
3. 性能画像记录TTFT、TPS、P50/P95/P99、超时和最大稳定并发；成本画像记录输入输出价格、缓存折扣、每成功任务Token与金额。可靠性还需统计空响应、限流、版本漂移和降级兼容性。
4. 固定Prompt与参数重复评测，给出均值、方差和置信区间；由规则、人工和盲化LLM Judge联合评审并校准偏差。全部资产版本化。
5. 新模型先离线，再Shadow和灰度；线上反馈需防选择偏差。画像按时间更新，路由只使用满足样本量和新鲜度的数据。

| 画像域 | 代表内容 |
|---|---|
| 能力 | 任务、模态、工具、领域 |
| 质量安全 | 成功率、事实、违规率 |
| 性能可靠性 | TTFT、P95、错误率 |
| 经济性 | 单位成功成本、配额 |

**相关知识点：** Capability Profile、分桶评测、置信区间、LLM-as-a-Judge、Shadow、版本漂移、单位成功成本。

#### 101、如何控制大模型调用成本？
控制成本应以**单位成功任务成本**为目标，从减少调用、压缩上下文、模型分级、缓存和预算门控入手，不能只压低单Token价格而牺牲成功率。

1. 网关记录输入、输出、推理、缓存、重试及工具成本，按租户、Agent、场景归因。根任务设置Token、金额、步骤、调用和Deadline预算，调用前预占。
2. 采用规则/分类器与小模型级联：分类、抽取、改写用小模型，复杂推理用大模型；低置信、验证失败或分布外时升级。先满足安全和质量硬约束。
3. Prompt删除重复说明，历史滚动摘要，大结果外部引用，RAG动态Top-K只注入必要证据。稳定前缀用Prompt Cache，低风险问答可用Semantic Cache。
4. Reflection、多Agent和重试按风险触发，限制轮数与宽度。相同请求用Singleflight；软预算时关闭非核心步骤，硬预算时返回部分结果或转人工。
5. 通过A/B与回归评估措施，监控缓存命中、升级率、重试Token、重复率、P95和单位成功成本。异常关联Prompt或路由版本并可回滚。

| 手段 | 主要收益 | 风险 |
|---|---|---|
| 小模型级联 | 降单次成本 | 漏升级 |
| 上下文压缩 | 降输入Token | 信息丢失 |
| 缓存 | 避免重复计算 | 陈旧误命中 |
| 条件反思 | 控制推理分支 | 质量增益不足 |

**相关知识点：** FinOps、模型级联、Token Budget、Prompt Cache、Semantic Cache、RAG、Singleflight、单位成功成本。

#### 102、敏感数据如何保证不被发送到外部模型？
必须采用**默认拒绝、数据分级、出口强制检查与审计**，不能依赖Prompt保密。策略位于统一网关，Agent、SDK或备用路由均不得绕过。

1. 建立数据目录与分级，识别PII、凭证、商业秘密及租户内容，并映射允许的模型、地域、用途和保留策略。无法分类时按更高敏感级处理。
2. 网关发送前执行DLP、字段白名单、脱敏、令牌化或聚合；Prompt、RAG、记忆、附件和工具结果均检查。密钥及原始身份字段禁止进入上下文。
3. 路由先做数据驻留和供应商授权硬过滤；敏感任务进入私有部署、专属实例或本地小模型。若无合规候选，应拒绝、只运行确定性规则或人工处理，不能因主模型故障切换到不合规外部模型。
4. 使用网络出口白名单、私有链路、服务身份、最小权限和短期凭证，阻断应用直连公共API。配置供应商零保留/不训练条款、加密、区域和审计，但合同承诺不能替代技术控制。
5. 日志只存哈希、分类标签和脱敏摘要，记录策略版本、路由原因与主体。用诱饵数据、红队和流量审计验证，监控DLP命中、绕过与越域路由。

| 防线 | 作用 |
|---|---|
| 数据分级 | 确定允许用途与地域 |
| DLP/脱敏 | 出口前移除敏感字段 |
| 硬路由约束 | 仅选择合规模型 |
| 网络与审计 | 阻断绕过并可追责 |

**相关知识点：** Data Classification、DLP、Tokenization、Data Residency、Egress Control、零保留、最小权限、审计。

#### 103、如何设计模型降级和兜底策略？
降级设计应遵循**能力逐级收缩、质量与安全底线不降、状态可恢复、用户可感知**。目标是在故障或预算不足时提供可信的有限服务，而不是用低能力模型伪装成完整成功。

1. 按场景定义能力契约，包括模态、上下文、Tool Calling、结构化输出、事实和安全要求。备用模型不满足硬约束时不得切换，可选择只读、规则或人工。
2. 建立有序降级链：先关闭多候选与Reflection、压缩上下文和输出；再切换同能力低价/低延迟模型；随后退化为RAG摘录、模板或部分结果。支付、删除、审批等高风险写操作不能降低校验标准。
3. 触发依据包括错误率、慢调用率、配额、预算和质量监控。按模型与供应商独立熔断，半开小流量探测；所有重试与切换共享Deadline、Retry Budget和Token预算。
4. 模型间迁移结构化目标、约束、证据、已完成步骤及工具回执，不复制完整历史。工具使用幂等键，恢复主模型后不得重放已提交副作用。输出经Schema、事实和后置条件验证。
5. 对用户说明简化模式、能力限制和选项。监控降级率、成功率、质量差值、恢复时间、重复副作用率和单位恢复成本，并通过演练和灰度验证。

| 层级 | 兜底方式 |
|---|---|
| L1 | 关闭非核心推理 |
| L2 | 兼容备用模型 |
| L3 | RAG、规则、模板或只读 |
| L4 | 排队、人工或安全失败 |

**相关知识点：** Graceful Degradation、能力契约、熔断、半开探测、幂等、状态迁移、质量门禁、故障演练。

#### 104、如何支持多厂商模型统一接入？
应建设**Model Gateway与厂商适配器**，统一协议、能力、错误、计量和治理，并保留特性扩展。统一接入不等于模型等价，路由仍依据兼容矩阵。

1. 标准Schema覆盖消息、多模态、流式事件、Tool Calling、结构化输出、停止原因和usage。适配器负责字段转换、鉴权及流协议，并保留原始响应用于诊断。
2. 能力注册表记录模型版本、上下文、模态、工具、JSON约束、地域、数据保留、价格和限制。路由前做能力协商，不支持的功能明确失败。
3. 厂商状态码映射为统一错误信封，包含layer、code、retryable和原始码。网关集中实施Deadline、重试预算、限流、熔断、取消及备用切换。
4. 路由先做权限、数据驻留和能力过滤，再综合质量、P95、成本、健康与配额。各模型维护独立Prompt和兼容测试，切换只迁移结构化状态。
5. Trace记录模型、路由原因、Token和原始请求ID；成本账本定期对账。契约测试、回放、Shadow和灰度验证版本变化，策略支持回滚。

| 层次 | 职责 |
|---|---|
| 标准契约 | 请求、响应、流、错误、用量 |
| 适配器 | 厂商协议与鉴权转换 |
| 治理层 | 路由、限流、熔断、预算 |
| 验证层 | 契约测试、回放与灰度 |

**相关知识点：** Model Gateway、Adapter、Capability Registry、Error Envelope、协议归一化、契约测试、兼容矩阵。

#### 105、如何做模型效果的A/B实验？
模型A/B实验应验证**任务价值与安全性**，而非只比较回答偏好。实验必须稳定随机、隔离版本差异、预先定义指标和停止规则，并把质量、时延、成本共同纳入。

1. 明确假设与实验单元，通常按用户、租户或会话哈希固定分桶，避免同一对话跨组造成上下文污染。设置互斥实验层，记录模型、Prompt、RAG、工具、路由和价格版本，防止多个变量同时变化。
2. 主指标采用任务成功率、业务转化或人工通过率；护栏指标包括事实错误、安全违规、Schema/工具失败、P95/P99和单位成功成本。点赞等主观信号只能作为辅助。
3. 上线前用离线基准、回放和Shadow排除明显回归，再从低风险小流量灰度。样本量、最小可检测效应、显著性与实验周期预先计算；不要因短期波动反复窥视并提前结束。
4. 生成模型存在随机性，需固定可控参数并保留多次采样分布。LLM Judge应盲化顺序、使用Rubric并以人工样本校准；高风险失败触发自动止损，不能等统计显著才停止。
5. 分析总体效果及任务难度、语言、租户、长尾场景分层结果，检查新奇效应和选择偏差。实验结束形成可回放数据集与决策记录，胜者仍需分阶段放量并持续监控漂移。

| 阶段 | 目的 |
|---|---|
| 离线/回放 | 快速排除回归 |
| Shadow | 验证真实流量但不影响用户 |
| 小流量A/B | 估计因果增量 |
| 灰度放量 | 控制上线风险 |

**相关知识点：** A/B Testing、稳定分桶、MDE、护栏指标、LLM-as-a-Judge、Shadow、统计显著性、自动止损。

#### 106、如何记录一次请求为什么选择了某个模型？
每次路由应生成**可审计、可回放的决策日志**，记录请求特征、候选、硬过滤原因、评分和策略版本，而非事后猜测。

1. Trace ID关联请求、Agent任务和模型调用；记录任务类型、复杂度、风险、SLA、预算、上下文、模态、工具、数据等级和权限。敏感原文只存摘要或哈希。
2. 保存完整候选集及每个候选的能力匹配结果。数据驻留、权限、上下文不足、工具不兼容等硬约束需记录稳定Reason Code，明确为何被排除，不能只显示最终模型。
3. 对候选记录预测质量、P95、价格、健康、配额、缓存和切换代价，以及归一化分数、权重、置信度和排序。规则、画像与价格表均带版本。
4. 记录是否触发小模型先行、升级、重试、熔断或降级，以及最终任务成功、Token、时延和成本。这样可区分“路由判断错误”与“模型执行异常”，并进行反事实评估。
5. 日志采用结构化Schema、访问控制和保留策略，支持查询与回放。监控未知原因率、低置信路由、策略漂移和解释一致性；用户侧只展示必要说明。

| 日志域 | 关键内容 |
|---|---|
| 请求特征 | 任务、风险、SLA、预算 |
| 候选过滤 | 模型、硬约束、Reason Code |
| 排序决策 | 特征、分数、策略版本 |
| 执行结果 | 升降级、质量、时延、成本 |

**相关知识点：** Decision Log、Reason Code、Feature Snapshot、策略版本、Trace、反事实评估、审计、数据脱敏。

#### 107、多模型路由策略具体如何设计？规则路由和LLM路由如何选择？
宜采用**规则硬过滤、轻量模型分类、评分器排序、运行时级联**。规则与LLM不是二选一：安全与能力边界确定性执行，难枚举的任务语义交给模型。

1. 构建模型能力矩阵和请求画像，维度包括模态、上下文、工具、领域、质量、P95、价格、地域、数据保留和配额。先按权限、数据驻留、能力及预算上限过滤，任何不合规候选直接排除。
2. 稳定、可枚举、高QPS场景使用规则；语义复杂、长尾多、规则冲突频繁时使用分类器或轻量LLM预测任务类型、复杂度和成功概率。
3. LLM路由输出结构化标签与置信度，不自由生成模型名；低置信、分布外或超时采用安全默认规则。候选评分综合预测质量、时延、成本、健康度和切换代价，并支持按场景配置权重。
4. 简单任务小模型先行，Schema失败、证据不足、工具错误或验证未通过时升级。实时错误率、队列和限额触发熔断与备用切换，所有尝试共享Deadline和预算。
5. 日志记录规则、特征、候选分数和版本；通过回放、Shadow、灰度比较成功率、漏升级、路由开销和单位成功成本，将稳定决策蒸馏为分类器。

| 路由方式 | 适用场景 | 主要风险 |
|---|---|---|
| 规则 | 硬约束、稳定高频 | 长尾维护困难 |
| 分类器 | 标签稳定、规模大 | 需训练与校准 |
| LLM | 语义复杂、冷启动 | 成本与随机性 |

**相关知识点：** Hybrid Router、能力矩阵、硬过滤、置信校准、OOD、模型级联、Shadow、蒸馏。

#### 108、如何自动判断一个任务的复杂度等级？
复杂度是**任务所需能力与资源的可观测需求**，不能只看输入长度。可结合规则、轻量分类器和运行反馈，输出校准后的等级或成功概率。

1. 特征包括意图、模态、上下文、约束、歧义、步骤、跨文档关系、工具、领域、风险和Schema。长文本可能只需抽取，短问题也可能需要高难推理。
2. 先用规则识别确定性边界，例如超长上下文、视觉输入、强工具需求和高风险任务；其余使用小模型或分类器预测简单、中等、复杂，或各候选模型完成成功概率，并给出置信度。
3. 训练标签来自人工分级与“最小可成功模型”：对同一任务用不同模型运行并经验证器评测，找到满足质量SLO的最低档位。需按领域、语言和长尾样本分层，防止标签只代表主流流量。
4. 运行时将低置信、分布外、Schema失败、证据不足和无进展作为升级信号；成功并通过后置验证则Early Exit。安全约束独立于复杂度。
5. 用混淆矩阵、校准误差、漏升级率、误升级率、P95与单位成功成本评估；Shadow和回放更新模型。分布漂移或样本不足时回退保守规则。

| 复杂度信号 | 说明 |
|---|---|
| 结构复杂度 | 约束、步骤、依赖数量 |
| 认知复杂度 | 推理、歧义、跨域程度 |
| 执行复杂度 | 工具、状态与副作用 |
| 风险复杂度 | 错误代价与审计要求 |

**相关知识点：** Task Complexity、成功概率、最小可成功模型、置信校准、OOD、模型级联、概念漂移。

#### 109、模型路由层如何实现实时决策？
实时路由应结合**静态能力策略**与**动态健康、配额、队列**，快速过滤和排序；路由自身须低延迟、高可用并有安全默认项。

1. 离线维护能力画像、质量、价格、地域和兼容矩阵，发布为内存快照；请求到达后提取任务、风险、SLA、预算、模态和工具特征。
2. 先执行权限、数据驻留、能力、上下文和预算过滤。随后读取本地实时指标，包括错误率、TTFT/P95、队列、限额与熔断状态，避免查询远端系统。
3. 对候选计算预测成功率、时延和成本的综合分数，或使用预训练的轻量Learning-to-Rank模型。高语义复杂度才调用小型路由模型，并设置极短Deadline；低置信时使用保守规则。
4. 以一致性哈希实现会话稳定与A/B分桶，并保留少量探索流量。决策后执行模型级联与备用切换；所有尝试共享任务预算。
5. 动态指标采用滑动窗口、滞回与最短驻留时间，避免反复切换。记录特征、候选、分数、策略版本和结果，通过Shadow、回放和反馈更新策略。

| 数据类型 | 更新频率 | 用途 |
|---|---|---|
| 能力/合规 | 版本发布 | 硬过滤 |
| 质量/价格 | 周期更新 | 基础评分 |
| 健康/队列 | 秒级或更快 | 实时排序与熔断 |
| 请求特征 | 每请求 | 个性化决策 |

**相关知识点：** Online Routing、内存快照、Learning to Rank、一致性哈希、滞回、会话粘性、Shadow、决策日志。

#### 110、如何设计模型能力评估体系？
评估体系应具备**分层任务集、可验证指标、统计置信和线上闭环**，同时衡量质量、安全、时延与成本。公开榜单或平均分不足以支撑路由。

1. 按场景建立能力树，覆盖理解、抽取、RAG、推理、代码、规划、Tool Calling和多模态；再按难度、语言、风险和上下文分桶。
2. 数据集组合公开基准、脱敏样本、历史失败、边界和对抗样本，隔离训练/调参/测试并检查污染；答案、Rubric、来源和版本可追溯。
3. 优先使用测试、Schema、事实来源和工具后置条件；开放答案由盲化人工与校准后的LLM Judge评审，并报告成功率和置信区间。
4. 同时测量TTFT、TPS、P95/P99、超时、并发稳定性、输入输出Token及单位成功成本。固定Prompt、参数和环境重复运行，避免把随机波动误判为模型差异。
5. 新模型经过离线评测、回放、Shadow、灰度和监控。线上失败回流，画像随模型、Prompt和知识版本更新；晋级须通过质量与安全门槛。

| 层次 | 目的 |
|---|---|
| 能力分桶 | 定位擅长与短板 |
| 质量安全 | 验证可用与合规 |
| 性能成本 | 判断生产经济性 |
| 线上闭环 | 监控漂移与真实价值 |

**相关知识点：** Evaluation Harness、能力树、Rubric、LLM-as-a-Judge、置信区间、Shadow、数据污染、单位成功成本。

#### 111、小模型升级到大模型的触发条件有哪些？
升级应由**能力不足或风险上升的可观测信号**触发，而非重试即升级。条件包括调用前预测和执行反馈，并受Deadline与预算约束。

1. 调用前触发包括能力缺失、上下文超限、多步推理、跨域、高歧义、分布外和高风险。数据安全与地域不兼容属于硬过滤。
2. 小模型低置信、类别概率接近、Schema失败、证据不足、事实或单测失败时升级。置信度须经标注集校准，不能相信模型口头声明。
3. 工具反复错误、步骤无进展、计划冲突或用户纠错时，可升级重规划；已完成副作用通过幂等状态传递，禁止重放。
4. 升级前估算剩余上下文、输出与大模型价格，检查Token预算和Deadline；若无法在限制内完成，应返回部分结果、排队或人工接管。安全拒绝、权限不足和确定性业务失败不得通过升级绕过。
5. 监控升级率、漏升级、误升级、大模型增量成功率、额外P95和单位成功成本。通过离线回放、Shadow和A/B调整阈值，并对不同任务、租户与风险等级分别配置。

| 信号阶段 | 代表触发 |
|---|---|
| 调用前 | 能力缺口、复杂度、高风险 |
| 输出后 | 低置信、Schema/事实失败 |
| 执行中 | 工具循环、计划无进展 |
| 用户反馈 | 明确纠错或高质量诉求 |

**相关知识点：** Model Escalation、置信校准、OOD、验证器、信息增益、预算门控、漏升级、误升级。

#### 112、如何衡量模型升级带来的ROI？
模型升级ROI应衡量**增量业务价值减去增量总成本**，而非只看基准分或Token单价。质量收益只有转化为成功任务、收入或风险降低才有价值。

1. 同一请求比较小模型、全量大模型和条件升级，固定Prompt、RAG、工具与版本。主指标采用成功率、转化率、一次解决率或人工节省时间。
2. 收益包括减少错误退款、提高转化、降低人工、缩短周期和避免风险损失。安全与合规指标作为硬护栏，不宜随意折算抵消。
3. 增量成本包含大模型输入输出、迁移上下文、额外P95、重试、评审、基础设施和供应商配额；小模型失败后再升级的双重调用也必须计入。核心公式可写为ROI=(增量价值-增量成本)/增量成本。
4. 通过随机A/B或Shadow回放估计因果增量，并按任务难度、风险、租户和长尾分层。计算升级后净成功增量、每挽救一个失败任务成本和置信区间，避免总体均值掩盖局部负收益。
5. 设置准入阈值；质量增益下降、价格上调、升级率异常或单位成功成本超标时回滚，并定期校准触发条件。

| 指标 | 含义 |
|---|---|
| 净成功增量 | 升级新增成功任务数 |
| 增量总成本 | 模型、时延、重试、运维 |
| 挽救成本 | 每修复一个失败任务的成本 |
| ROI | 净增量价值/增量成本 |

**相关知识点：** ROI、增量分析、因果A/B、单位成功成本、机会成本、置信区间、分层评估。

#### 113、如何设计模型降级和熔断机制？
模型韧性应把**熔断、重试、降级和恢复探测**设计为统一状态机：熔断隔离故障依赖，降级提供受限服务，并共享Deadline与预算。

1. 按供应商、模型、区域和错误类型建立熔断器，统计错误率、慢调用率、最小请求数和连续失败。参数、鉴权错误不计入依赖故障。
2. Closed状态正常调用；指标超阈值进入Open并快速失败；冷却后进入Half-Open，仅放少量、低风险、受限并发的探测。连续成功达到门槛才恢复，失败立即重新Open，并采用递增冷却。
3. 降级可关闭Reflection、压缩上下文、切换模型、返回RAG摘录或模板、排队及人工接管。数据驻留、工具能力和安全底线不可降。
4. 可重试错误使用指数退避与Full Jitter，所有层共享Retry Budget，避免重试风暴。切换时传递结构化任务状态和工具回执；写操作使用幂等键，恢复后不得重放。
5. 监控熔断次数、Open时长、半开成功率、降级质量差值、用户放弃率、重复副作用与单位恢复成本。通过故障注入验证阈值，配置版本化且可回滚。

| 机制 | 目标 |
|---|---|
| 重试 | 恢复瞬时失败 |
| 熔断 | 隔离持续故障 |
| 降级 | 保留最小服务 |
| 半开探测 | 安全判断恢复 |

**相关知识点：** Circuit Breaker、Half-Open、Retry Budget、Full Jitter、Graceful Degradation、幂等、故障注入。

#### 114、模型故障时如何实现无感切换？
无感切换依赖**统一协议、能力兼容、结构化状态、幂等和备用链**。备用模型不满足安全或质量底线时，应明确降级。

1. Gateway统一消息、流事件、Tool Calling和错误；能力矩阵验证上下文、模态、工具、数据驻留和质量。备用模型定期Shadow预热。
2. 超时、错误率、配额或熔断触发切换。仅切换可重试且幂等的请求；所有尝试共享Deadline、重试和Token预算。
3. 状态Schema含目标、约束、证据、已完成步骤、工具回执和未决项。切换只传最小状态，并使用模型专属Prompt适配器。
4. Tool调用使用幂等键并查询未知状态。流式输出前可直接切换；输出后从序列号和检查点续写，无法保证一致时终止，避免拼接矛盾答案。
5. 切换后验证Schema、事实和后置条件，持续监控成功率、质量差、重复副作用、恢复时延与额外Token，并以离线回放和故障演练验证主备链的可靠性。

| 阶段 | 切换策略 |
|---|---|
| 首Token前 | 直接调用兼容备用 |
| 流式中 | 从检查点续写或受控终止 |
| 工具状态未知 | 查询与幂等恢复 |
| 无兼容备用 | 降级、排队或人工 |

**相关知识点：** Failover、Model Gateway、兼容矩阵、状态迁移、幂等、流式续传、Shadow、故障演练。

#### 115、如何避免模型频繁升级导致成本失控？
应通过**校准触发、升级预算、滞回和增量收益评估**控制升级。只有大模型预计能显著提高成功概率且预算充足时才执行。

1. 升级信号限定为Schema/单测失败、证据不足、低置信、分布外和无进展；参数、权限、安全拒绝及确定性业务错误不升级。阈值用标注集校准。
2. 每个根任务设置升级次数、额外Token、金额和Deadline上限，子Agent共享同一预算。升级前估算迁移上下文与大模型费用并预占额度；余额不足时返回部分结果、排队或人工接管。
3. 使用滞回与最短驻留：一旦升级，在当前阶段保持模型档位；降回小模型需满足更严格条件，避免阈值附近来回切换。相同失败状态和相同输入指纹禁止重复升级。
4. 优先通过确定性验证器、Prompt修正、上下文裁剪或一次有界重试解决可恢复问题；小模型可先承担分类、检索和格式化，仅把复杂剩余步骤交给大模型，避免从头重算。
5. 监控升级率、误升级率、升级后净成功率、重复迁移Token、P95和每挽救任务成本。按任务类型做A/B和反事实回放，若某触发器边际收益低则降低权重或关闭。

| 控制点 | 机制 |
|---|---|
| 触发前 | 校准置信与错误分类 |
| 决策时 | 预算预占与收益预测 |
| 运行中 | 滞回、去重、阶段粘性 |
| 事后 | 净成功率与ROI回放 |

**相关知识点：** Escalation Budget、Hysteresis、置信校准、状态指纹、预算预占、反事实评估、单位挽救成本。

#### 116、Prompt压缩有哪些常见方案？
Prompt压缩应遵循**去冗余、结构化、摘要与选择性召回**，并以任务成功率验证。安全约束、目标、事实和工具契约不能丢失。

1. 删除重复说明和冗余示例，合并规则，以Schema、枚举和引用ID代替长描述；稳定内容置于前缀利用Prompt Cache。
2. 历史采用滑窗与滚动摘要，保留最近交互、更正、未完成事项和关键实体。摘要应结构化并附来源；数字、否定和权限尽量保留原文。
3. RAG以元数据、动态Top-K、Rerank和去重注入最小证据集；文档、日志和工具大结果存外部，上下文只留摘要与引用。
4. 可用小模型做句子选择、相关摘要或Prompt蒸馏，将长指令转为经回归测试的短模板。压缩输出须检查关键槽位、引用和安全规则。
5. 按Token水位、主题切换或阶段完成触发，并设置分区预算。监控压缩率、事实遗漏、TTFT、任务成功率和单位成功成本。

| 方案 | 适用内容 | 风险 |
|---|---|---|
| 去重/模板化 | 系统指令、示例 | 语义过度合并 |
| 滚动摘要 | 长对话历史 | 摘要漂移 |
| 检索与Rerank | 知识文档 | 关键证据漏召回 |
| 外部引用 | 工具大结果 | 引用失效 |

**相关知识点：** Prompt Compression、滚动摘要、Prompt Distillation、RAG、动态Top-K、Prompt Cache、保真评测。

#### 117、Context裁剪如何避免关键信息丢失？
Context裁剪应采用**信息分层、关键槽位保护、来源追溯和裁后校验**，不能简单删除最早消息。应保留影响当前决策的信息。

1. 内容分为不可裁剪、工作状态、可摘要历史和外部引用。系统规则、目标、权限、用户更正、未完成任务、工具Schema及后置条件固定保留。
2. 将实体、数字、否定、偏好、决策、工具回执和证据抽取为结构化状态，记录来源ID、时间与版本。模型推测和用户事实分开，冲突时并列保存。
3. 旧对话使用按主题的滚动摘要，文档和工具大结果存外部，只保留摘要、哈希和定位引用；当前问题到来时通过混合检索、Rerank和动态Top-K按需补回。
4. 裁剪前计算Token预算和内容优先级，采用最近性、相关性、权威性、风险及未决状态综合评分。不能只依赖向量相似度，高风险字段使用规则白名单保护。
5. 裁剪后比较关键槽位、待办、引用和约束，执行一致性与任务回归；缺失则扩大窗口或取回原文。监控遗漏率、压缩率和任务成功率，并支持回滚。

| 内容 | 处理 |
|---|---|
| 安全规则/当前目标 | 固定保留 |
| 关键事实/状态 | 结构化保护 |
| 旧对话 | 分层摘要 |
| 大文档/工具结果 | 外部引用、按需召回 |

**相关知识点：** Context Pruning、关键槽位、滚动摘要、Provenance、动态召回、摘要漂移、回归验证。

#### 118、Semantic Cache如何设计？
Semantic Cache应以**业务等价而非文本相似**为标准，通过复合键、阈值、权限、版本和时效治理复用结果。写操作和实时高风险数据不缓存最终答案。

1. 请求先规范化Unicode、空白和无语义参数，再提取意图与实体并生成Embedding。Key包含租户、权限、任务类型、语言、知识版本、Prompt/模型版本和时间窗。
2. 在硬条件分区内做向量检索，候选再经实体、否定、数值、时间和权限校验；必要时用Cross-Encoder判断等价。阈值按场景标注集校准。
3. 缓存项保存问题、答案、证据、质量分、时间、TTL与数据版本。返回前检查证据；低置信或版本不一致时回源，也可只复用检索结果。
4. 数据、权限、安全策略和Prompt更新通过事件主动失效，并用TTL兜底。租户分区、加密、访问控制和审计防止泄露，负缓存使用短TTL。
5. 精确Key优先、语义匹配其次；热点预热，并发请求用Singleflight。监控命中率、错误命中、陈旧率、节省Token、P95和质量差值。

| 命中阶段 | 作用 |
|---|---|
| 硬条件分区 | 隔离租户、权限、版本 |
| 向量召回 | 找语义相近候选 |
| 业务校验 | 排除实体、时间等不等价 |
| TTL/事件失效 | 控制陈旧结果 |

**相关知识点：** Semantic Cache、Embedding、复合Cache Key、阈值校准、Cross-Encoder、TTL、事件失效、Singleflight。

#### 119、RAG与大上下文模型如何取舍？
两者不是替代关系：**RAG从动态知识中选择证据，大上下文对已选材料整体理解**。应按语料规模、更新、证据定位、隐私、时延和成本选择，常组合使用。

1. RAG适合知识库远大于窗口、频繁更新、需权限过滤与引用的场景。它减少Token，但依赖切分、召回和Rerank，可能漏证据或破坏跨段关系。
2. 大上下文适合材料已知、规模可控且需跨章节综合的任务。它保留全局关系，但成本、TTFT和KV Cache随长度增长，并有Lost in the Middle。
3. 先判断能否确定材料：不能则先检索；能且不超预算，可用长上下文。高精度任务可先RAG筛选，再注入相邻父段或完整候选文档。
4. RAG按租户、ACL和时效过滤，使用混合检索、动态Top-K与Rerank；长上下文需目录、位置标记和分层摘要。两者都要控制Prompt Injection。
5. 比较证据Recall、正确率、引用有效率、TTFT、输入Token和单位成功成本，并按单跳、多跳与全局综合分桶，不能只比较窗口上限。

| 维度 | RAG | 大上下文 |
|---|---|---|
| 知识规模 | 可扩展到库级 | 受窗口限制 |
| 更新与权限 | 易过滤和更新 | 需重组输入 |
| 全局关系 | 可能被切分破坏 | 更完整 |
| 成本 | 检索费+少量Token | 大量输入Token |

**相关知识点：** RAG、Long Context、Lost in the Middle、父子检索、Rerank、ACL、Prompt Injection、单位成功成本。

#### 120、如何建立模型质量评分体系？
质量评分应采用**场景分层、多指标门槛、统计置信与版本化聚合**，避免用单一总分掩盖安全或关键能力缺陷。评分服务于路由、准入和回归，因此必须与真实任务成功相关。

1. 按任务、难度、语言、领域、风险和上下文长度分桶，指标包括任务成功率、事实正确率、引用有效率、Schema通过率、工具后置条件、完整性及安全违规率。
2. 可确定的结果优先使用规则、单元测试和权威数据；开放答案由盲化人工和经校准的LLM Judge按Rubric评审。报告均值、方差、样本量和置信区间，不能把小样本差异当成提升。
3. 设置安全、合规和关键任务最低门槛，未通过即淘汰；通过后再按业务价值为质量维度加权。总体分同时保留分桶明细，防止高频简单题掩盖长尾失败。
4. 线上质量结合用户重试、人工接管、业务转化和工具成功，但需校正选择偏差、延迟反馈及曝光差异。离线基准、Shadow和A/B共同校准线上评分。
5. 模型、Prompt、RAG、Judge和数据集均版本化，设置漂移监控与回归阈值。评分更新采用时间衰减和最低样本量，记录变更原因，路由只消费已发布的稳定版本。

| 评分层 | 作用 |
|---|---|
| 硬门槛 | 安全、合规、关键能力准入 |
| 分桶指标 | 描述不同场景真实能力 |
| 加权总分 | 候选排序与运营概览 |
| 线上反馈 | 验证真实任务价值 |

**相关知识点：** Quality Score、Rubric、置信区间、硬门槛、LLM-as-a-Judge、选择偏差、版本漂移。

#### 121、如何实现在线A/B测试与灰度发布？
应建立**稳定分桶、配置版本化、护栏监控、自动止损和逐级放量**的一体化发布链路，使效果验证与风险控制使用同一套流量和观测体系。

1. 按用户、租户或会话ID一致性哈希分桶，保证同一上下文不跨组；实验层互斥，模型、Prompt、RAG、工具和路由策略分别版本化，避免多个变量同时改变。
2. 新版本先离线回归与Shadow，再按内部用户、低风险租户、1%、5%、20%、50%逐级灰度。每阶段设置最小观察时间和样本量，晋级由审批或策略引擎执行。
3. 主指标采用任务成功率或业务转化，护栏包含安全违规、事实错误、Schema/工具失败、P95/P99、超时和单位成功成本。高风险失败立即停止，不等待统计显著。
4. 发布控制面维护流量比例、白名单、地域、租户和回滚版本；数据面读取本地配置快照，控制面异常时保持最后安全版本。流式长任务在会话内保持版本粘性。
5. 日志记录分桶、策略版本、请求特征和结果，使用显著性、置信区间与分层分析判断增量。发现回归时自动切回稳定版本，并保留失败样本用于后续回放。

| 阶段 | 主要目标 |
|---|---|
| Shadow | 验证兼容与真实分布 |
| 小流量 | 发现安全和性能问题 |
| 分级放量 | 验证统计增益与容量 |
| 全量/回滚 | 稳定运营与快速止损 |

**相关知识点：** A/B Testing、灰度发布、一致性哈希、会话粘性、护栏指标、自动止损、配置快照、回滚。

#### 122、企业级模型网关需要具备哪些能力？
企业级模型网关是**统一接入、路由、安全、韧性、成本和审计**的策略执行点，而非HTTP转发。所有Agent和应用经由网关，避免治理旁路。

1. 接入层统一消息、多模态、流事件、Tool Calling、结构化输出、错误与usage，通过适配器连接厂商；注册表记录模型、上下文、地域、价格和限制。
2. 路由先按权限、数据驻留、安全、模态和工具能力过滤，再综合质量、P95、价格、健康与配额排序；支持模型级联、A/B、Shadow和备用切换。
3. 韧性层实施分层超时、取消传播、限流、并发、Retry Budget、熔断、半开探测和负载丢弃。写操作使用幂等键，防止重复副作用。
4. 安全层提供认证、授权、DLP、脱敏、出口控制、密钥、内容安全、注入防护及审计。Prompt、RAG、工具结果和日志按租户隔离。
5. FinOps记录输入输出、缓存、重试和工具成本，支持配额、预占、告警与对账；Trace保存路由原因和调用链。配置版本化并可回滚。

| 能力域 | 核心职责 |
|---|---|
| 接入与路由 | 协议统一、能力匹配 |
| 韧性 | 超时、限流、重试、熔断 |
| 安全 | 身份、DLP、隔离、审计 |
| FinOps/观测 | 计量、预算、Trace、告警 |

**相关知识点：** Model Gateway、Adapter、Capability Registry、Retry Budget、DLP、FinOps、配置快照、决策日志。

#### 123、如何统计单个Agent任务的真实成本？
真实成本应按**根任务全链路成本账本**计算，覆盖成功与失败的资源，而非只统计最后一次模型usage。核心口径是任务从接收到终态的总成本。

1. 任务生成Task ID，所有子Agent、模型、工具、检索与人工环节携带Trace ID、Step ID和attempt。网关采集输入、输出、推理、缓存Token和厂商请求ID。
2. 模型费用按调用时价格核算，包含重试、切换、Reflection、Judge和并行分支；流式中断使用Tokenizer估算并标记，后续与账单对账。
3. RAG计入Embedding、向量查询、Rerank、存储和流量；工具计入API、沙箱、数据库与队列；自部署按GPU实例小时和利用率分摊。
4. 共享子任务、缓存和基础设施按固定规则采用独占、均摊或业务权重归因，避免重复或漏计。人工审核、补偿、失败重跑和SSE连接等也应进入任务TCO。
5. 账本关联成功、部分成功或失败状态，输出总成本、步骤占比、Token构成、重试浪费和人工成本。监控单位成功成本与异常分支，校准分摊规则。

| 成本域 | 组成 |
|---|---|
| 模型 | Token、重试、反思、切换 |
| 数据 | Embedding、检索、存储、流量 |
| 执行 | 工具、沙箱、队列、连接 |
| 人工/共享 | 审核、补偿、基础设施分摊 |

**相关知识点：** TCO、Cost Ledger、Task ID、成本归因、价格版本、账单对账、共享成本分摊、单位成功成本。

#### 124、多模型环境下如何进行统一评测？
统一评测需要**公共任务契约、特性适配、盲化评分和同口径成本性能测量**。统一的是任务与验收，不是强迫模型使用相同Prompt。

1. 定义模型无关的输入、工具、Schema、证据和后置条件；按任务、难度、语言、风险、模态和上下文分桶。模型可使用登记的专属Prompt。
2. 数据集结合公共基准、生产脱敏、历史失败和对抗样本，固定版本并检查污染。模型、Prompt、RAG、工具、参数和环境均版本化。
3. 结构化任务用单测、Schema和规则；开放答案采用盲化人工与校准后的LLM Judge，Rubric聚焦事实、完整性、引用和安全。Judge不知模型身份。
4. 同时测量TTFT、TPS、P50/P95/P99、错误率、输入输出/缓存Token与单位成功成本；对随机生成重复采样，报告均值、方差、样本量和置信区间。
5. 新模型依次经过离线、回放、Shadow和A/B灰度。报表保留分桶结果与Pareto前沿，不用总分掩盖短板；失败回流仍需独立验证。

| 统一对象 | 允许差异 |
|---|---|
| 任务输入与验收 | 模型专属Prompt |
| 数据集与版本 | Tokenizer与厂商协议 |
| 质量/安全指标 | 可用能力与工具 |
| 成本性能口径 | 部署形态 |

**相关知识点：** Evaluation Harness、任务契约、Blind Judge、Rubric、置信区间、Pareto Front、Shadow、数据污染。

#### 125、如何实现质量、时延、成本三目标优化？
三目标优化先设置**质量与安全硬约束**，再搜索Pareto最优，并按任务价值动态路由。固定权重会在流量、价格或质量变化后失效。

1. 质量采用成功率、事实/格式通过率、工具后置条件和违规率；时延采用TTFT、P95/P99；成本采用含重试、检索和工具的单位成功成本。指标按场景分桶。
2. 对模型、Prompt、RAG、缓存、Reflection和并行策略做消融与灰度，形成Pareto前沿。三维均被其他方案支配的配置淘汰。
3. 路由先按数据、能力、安全和质量过滤，再根据复杂度、风险、SLA、预算及健康选择方案。简单任务小模型先行，验证失败时升级；高价值任务启用Rerank。
4. 降成本使用缓存、上下文压缩、动态Top-K和结果引用；降时延使用流式、并行、预热和Early Exit。并行与重试必须受预算约束。
5. 日志记录特征、候选、分数和策略版本，监控质量、P95、漏升级与单位成本。多臂老虎机探索设置安全护栏和流量上限。

| 优化手段 | 主要收益 | 主要风险 |
|---|---|---|
| 小模型级联 | 成本与时延下降 | 漏升级 |
| 缓存/压缩 | 三者可能改善 | 陈旧、信息丢失 |
| Rerank/反思 | 质量提升 | 成本与时延增加 |
| 并行 | 降尾延迟 | 资源放大 |

**相关知识点：** Multi-Objective Optimization、Pareto Front、SLO、模型级联、多臂老虎机、Early Exit、单位成功成本。

#### 126、如果预算固定，如何设计最优模型资源分配策略？
固定预算下应最大化**约束内的预期业务价值或成功任务数**，而不是平均分配调用额度。先保障安全与最低质量，再按任务的边际收益、风险和机会成本进行资源配置。

1. 将流量按场景、复杂度、风险、租户SLA和业务价值分桶，估计各模型在每桶的成功概率、P95与总成本。成本需包含小模型失败后升级、重试、检索、工具和人工。
2. 为每个分桶定义最低服务和质量门槛，高风险、合规及核心客户保留容量；剩余预算按“升级带来的增量价值/增量成本”从高到低分配，直到边际收益相等或预算耗尽。
3. 采用小模型级联：简单任务小模型处理，低置信、验证失败或分布外才升级。高价值任务可配置Rerank或Reflection，低价值流量使用缓存、规则答案、排队或更短输出。
4. 建立日/月配额与单任务预算，调用前预占，实时监控消耗速度并动态调节升级阈值、Top-K、并行宽度和模型档位。预留故障恢复、峰值和安全校验额度。
5. 离线用历史流量做背包/线性规划或仿真，线上以安全多臂老虎机小流量探索。评估预算利用率、成功任务数、每成功任务成本、公平性与SLO违约率，防止只服务高价值流量造成租户饥饿。

| 分配原则 | 作用 |
|---|---|
| 最低保障 | 守住安全、质量与SLA |
| 边际ROI排序 | 优先高增量价值 |
| 动态阈值 | 适应流量和价格变化 |
| 预留池 | 应对峰值与故障 |

**相关知识点：** Resource Allocation、边际ROI、Knapsack、模型级联、预算预占、多臂老虎机、公平性、机会成本。

#### 127、千万级用户场景下如何进行模型容量规划？
容量规划应将**业务到达率转换为Token吞吐、并发与显存需求**，按峰值、模型档位和冗余计算。关键是同时在线、请求分布和任务资源消耗。

1. 预测每场景QPS、峰均比、会话时长、Token分布、TTFT/P95、工具等待与取消率；按分钟峰值而非日均设计，并考虑活动和重试放大。
2. API模式核算厂商RPM/TPM、并发和配额；自部署压测每卡Prefill/Decode吞吐、KV Cache、批处理效率与加载时间。按路由比例转换为每档需求。
3. 预留发布、故障、区域切换和预测误差容量，采用N+1或多区域冗余；主备能力与合规必须兼容。备用容量定期压测。
4. 使用无状态网关、队列削峰、连续批处理、优先级、限流和Load Shedding。模型级联、缓存、压缩和输出上限降低峰值Token；高价值请求独立配额。
5. 监控QPS、TPM、并发、队列、GPU、KV、TTFT、P99和拒绝率，做负载、突发、故障及长稳测试。滚动预测并设置扩缩容滞回。

| 规划对象 | 核心指标 |
|---|---|
| 需求 | 峰值QPS、TPM、并发 |
| 模型服务 | Prefill/Decode吞吐、KV |
| 冗余 | 区域、供应商、N+1 |
| 保护 | 队列、限流、负载丢弃 |

**相关知识点：** Capacity Planning、TPM、Continuous Batching、KV Cache、N+1、Load Shedding、自动扩缩容、峰均比。

#### 128、如何构建自动化模型路由闭环优化系统？
闭环系统应形成**观测—归因—离线学习—安全发布—在线反馈**链路，同时把硬约束与可学习策略分离。自动优化不能修改数据安全、权限和最低质量边界。

1. 网关为每次请求记录特征、候选、过滤原因、预测分数、模型/Prompt版本、质量、时延、Token、成本和最终业务结果，形成可回放的Decision Log。
2. 反馈层结合确定性验证、人工抽样、用户行为和LLM Judge生成标签，并校正延迟反馈、选择偏差与缺失结果。失败样本按任务、错误类型和风险分桶进入评测集。
3. 离线训练复杂度分类器、成功概率模型或Learning-to-Rank，目标函数在质量硬门槛下优化P95和单位成功成本。利用历史候选做反事实评估，避免直接上线未经验证的策略。
4. 新策略先离线回放，再Shadow、小流量A/B和逐级灰度；设置安全护栏、最大探索流量、自动止损和稳定回滚版本。多臂老虎机只在合规候选内探索，并防止高价值任务被过度试验。
5. 监控数据/概念漂移、校准误差、漏升级、误升级、策略抖动和反馈回路偏差。模型画像、价格、策略与特征Schema全部版本化；当数据新鲜度或样本量不足时回退规则。

| 闭环阶段 | 输出 |
|---|---|
| 观测 | 决策日志与结果标签 |
| 学习 | 成功概率/排序策略 |
| 验证 | 回放、Shadow、A/B |
| 发布 | 灰度、止损、回滚 |

**相关知识点：** Closed-Loop Routing、Decision Log、Learning to Rank、反事实评估、多臂老虎机、漂移、自动止损。

#### 129、开源模型与商业模型混合部署如何设计？
混合部署以**统一网关、数据分级、能力路由、故障隔离和统一评测**为基础：开源模型承担敏感和稳定任务，商业模型补充复杂推理与多模态。

1. Model Gateway统一消息、流式、Tool Calling、错误与usage；适配层屏蔽框架和厂商差异，注册表记录上下文、工具、模态、价格、地域和许可证。
2. 路由按数据等级、驻留、权限和能力过滤。敏感数据进入本地模型；复杂推理、视觉及长尾选择商业模型。无法合规时安全失败，禁止外发兜底。
3. 开源侧采用推理集群、量化、连续批处理、KV Cache和扩缩容，并核算GPU、运维与闲置TCO；商业侧管理RPM/TPM、配额、零保留和SLA。
4. 两类模型维护独立Prompt、Tokenizer和工具兼容测试，使用统一任务集比较成功率、P95、违规率和单位成功成本。小模型先行，验证失败时在合规候选内升级。
5. 各故障域设置限流、熔断和备用链；日志、记忆和缓存按租户隔离。模型、权重、许可证、Prompt和策略版本化，通过Shadow与灰度验证升级。

| 维度 | 开源自部署 | 商业API |
|---|---|---|
| 控制与隐私 | 强 | 依赖合同与配置 |
| 能力更新 | 自主管理 | 通常更快 |
| 成本结构 | GPU与运维固定成本 | 按量与配额 |
| 运维责任 | 高 | 较低 |

**相关知识点：** Hybrid Deployment、Model Gateway、TCO、数据驻留、量化、Continuous Batching、许可证、故障域。

#### 130、MCP、Tool Calling、Agent场景下如何进行模型路由？
此类路由需考虑**推理能力、工具兼容、执行风险和任务阶段**，不能仅按问答得分选择。模型决定调用意图，执行层决定是否允许。

1. 画像记录Tool Calling、JSON Schema遵循率、MCP资源、上下文、规划和修复能力；工具侧记录权限、幂等、副作用、时延、成本及数据地域。
2. 路由先按授权、数据驻留、工具和上下文过滤。分类、参数抽取用小模型；跨工具规划、长链推理和冲突恢复用大模型；高风险写操作需人工确认。
3. Planner输出带Step ID和验收条件的计划；Executor使用结构化调用稳定的模型；Critic默认只读，仅在验证失败时启用。模型间传递状态和证据。
4. 工具参数经过Schema、权限、规则和注入检查，写操作使用幂等键。失败按可重试性分类；无进展、相同调用指纹或预算耗尽时终止。
5. 监控工具选择、参数通过、后置条件、步骤数、重复调用、Token、P95和单位成功成本。用沙箱回放和Shadow更新模型—工具兼容矩阵。

| 路由对象 | 关键依据 |
|---|---|
| Planner | 复杂度、规划与长上下文能力 |
| Executor | Tool Calling与Schema稳定性 |
| Critic | 风险、验证失败与增量收益 |
| Tool | 权限、副作用、幂等与地域 |

**相关知识点：** MCP、Tool Calling、Planner-Executor、能力矩阵、Schema校验、幂等、Prompt Injection、Loop Detection。

#### 131、如何设计企业级统一模型接入层（Model Gateway）？
Model Gateway应是**高可用数据面与版本化控制面分离**的策略层，集中处理适配、路由、安全、韧性、成本和观测，并禁止业务绕过。

1. 数据面提供消息、多模态、流式、Tool Calling、结构化输出、错误与usage；适配器负责鉴权和转换。注册表维护模型、上下文、工具、地域、价格和限制。
2. 控制面管理模型、路由、Prompt、配额、价格、DLP和熔断阈值，配置经校验、审批、版本化和灰度后发布为快照；故障时使用最后安全版本。
3. 路由先按权限、数据驻留、能力与预算过滤，再按质量、P95、价格、健康和配额排序，支持模型级联、A/B、Shadow与备用切换。
4. 韧性包括分层超时、取消、限流、Retry Budget、熔断、半开和Load Shedding；安全包括认证、授权、DLP、脱敏、出口、租户隔离和审计。
5. Trace记录候选、路由原因、策略版本、Token、时延和工具链；账本支持预算预占、告警与对账。通过契约测试、回放、压测和灰度验证变更。

| 架构面 | 关键职责 |
|---|---|
| 数据面 | 低延迟调用、执行策略 |
| 控制面 | 配置、路由、价格、发布 |
| 适配层 | 厂商协议与能力转换 |
| 治理层 | 安全、FinOps、审计与观测 |

**相关知识点：** Model Gateway、Control/Data Plane、Adapter、Capability Registry、Retry Budget、DLP、FinOps、配置快照。

#### 132、SSE和WebSocket在Agent流式输出场景下如何选型？
服务端持续输出文本优先**SSE；高频双向、二进制或实时协同选择WebSocket**。选型依据通信方向、代理兼容、恢复语义和运维能力。

1. SSE基于HTTP，以`text/event-stream`单向推送，浏览器支持EventSource，易穿透网关、复用认证；事件含id、event、data，并可用Last-Event-ID恢复。
2. WebSocket支持全双工和二进制，适合语音、多人协作、频繁控制或持续上行；但需自定义心跳、重连、序列、鉴权续期、背压和确认。
3. Agent通常由HTTP提交任务，再用SSE接收Token、工具状态和最终事件；停止生成另发HTTP取消，不必仅为此引入WebSocket。
4. SSE并非可靠队列，重连需事件日志、Sequence和TTL；WebSocket也不保证不丢，需ACK、重放与幂等。两者均需取消传播和慢消费者治理。
5. 运维比较连接规模、代理超时、会话粘性、连接内存、移动重连和SDK成熟度。网关对WebSocket支持有限且业务单向时，SSE更简单。

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 服务端到客户端 | 全双工 |
| 协议 | HTTP事件流 | 独立帧协议 |
| 恢复 | Last-Event-ID辅助 | 自定义ACK/重放 |
| 场景 | 文本生成、状态通知 | 语音、协同、频繁交互 |

**相关知识点：** SSE、WebSocket、EventSource、Last-Event-ID、ACK、背压、心跳、取消传播。

#### 133、客户端断开后，后端模型调用如何及时取消？
应建立**端到端取消传播链**：断开触发取消令牌，中止编排器、模型流、工具和下游连接，并回收配额。停止写数据不等于停止模型计费。

1. 网关监听连接关闭、写失败、心跳超时和Stop请求，将Task ID的Cancellation Token置为取消；该Token传给Agent、模型SDK、HTTP客户端与工具。
2. 适配器调用厂商取消接口或关闭流与连接，并丢弃不可复用连接。若厂商不支持取消，停止读取未必停止生成，应设置最大输出和供应商Deadline。
3. Agent在模型步骤、工具和循环边界检查取消。并行分支统一取消并清理；异步任务需区分“后台继续”和“随连接取消”，策略在提交时明确。
4. 写操作不能因取消回滚未知状态：使用幂等键、Prepare/Commit或状态查询确认是否完成；必要时执行补偿。取消后的晚到结果按任务版本丢弃，禁止重新写入已终止会话。
5. 记录取消延迟、成功率、取消后Token、孤儿任务、连接与槽位释放时间。通过断网、代理超时和慢响应演练验证无泄漏。

| 层级 | 取消动作 |
|---|---|
| 网关 | 产生取消信号、释放连接 |
| Agent | 停止状态机与并行分支 |
| 模型 | 取消流/关闭请求 |
| 工具 | 幂等终止、查询或补偿 |

**相关知识点：** Cancellation Token、结构化并发、Deadline传播、流取消、幂等、孤儿任务、补偿事务。

#### 134、如何避免SSE连接占满线程池？
关键是采用**事件驱动非阻塞I/O与异步管道**，使长连接占用状态而非“一连接一线程”。同时对连接、缓冲区和慢消费者设硬上限。

1. 使用Netty、WebFlux、Node.js、Go协程或异步Servlet，读取模型流后由事件循环写SSE；禁止请求线程阻塞等待，也不为每个心跳创建线程。
2. 模型SDK、HTTP客户端和数据依赖应异步或使用隔离的有界池；阻塞依赖使用专用线程池、队列上限与拒绝策略，防止污染公共池。
3. 每连接维护有界发送队列和最大待发字节；慢消费者达到阈值时合并Chunk、暂停上游、降采样或断开，避免内存累积。
4. 心跳由共享时间轮或调度器批量驱动，设置空闲超时、最大连接时长和客户端断开检测。取消信号向模型与工具传播，及时释放连接、并发槽和Token预算。
5. 网关按租户限制连接与新建速率，系统设置全局上限和Load Shedding。监控连接、事件循环延迟、线程队列、连接内存和慢消费者，并长稳压测。

| 模式 | 资源特征 |
|---|---|
| 一连接一线程 | 长时间占线程，扩展性差 |
| 事件驱动I/O | 少量线程管理大量连接 |
| 阻塞依赖隔离池 | 限制故障半径 |
| 有界发送队列 | 防止慢客户端耗尽内存 |

**相关知识点：** Non-blocking I/O、Event Loop、Reactive Streams、背压、Bulkhead、时间轮、Load Shedding、慢消费者。

#### 135、Nginx或网关对SSE有哪些特殊配置？
SSE网关配置核心是**关闭缓冲、合理读取超时、保持流式并感知断开**。面向短请求的缓存、压缩和超时会导致事件积压或误断。

1. 响应设置`text/event-stream`、`Cache-Control: no-cache`和`X-Accel-Buffering: no`；Nginx配置`proxy_buffering off`，避免批量延迟发送。
2. 使用HTTP/1.1或正确支持流的HTTP/2，不缓存响应体。压缩可能增加缓冲和延迟，通常关闭或验证后使用。
3. `proxy_read_timeout`大于最大静默间隔但不无限；服务端定期发送注释心跳。分别设置连接总时长、空闲和首事件超时。
4. 禁止重试已输出的流；首事件前可按幂等策略切换。传递`Last-Event-ID`、Request ID和取消信号，断开后关闭上游请求。
5. 调整worker连接、文件描述符、keepalive及租户连接/新建速率；使用任务ID恢复或会话粘性。监控连接、499、超时、心跳和内存。

| 配置点 | 目的 |
|---|---|
| 关闭proxy buffering | 事件立即下发 |
| 延长read timeout+心跳 | 避免静默误断 |
| 禁用流中重试 | 防止重复事件 |
| 连接/FD限额 | 防止资源耗尽 |

**相关知识点：** proxy_buffering、X-Accel-Buffering、text/event-stream、心跳、499、Last-Event-ID、文件描述符。

#### 136、SSE流式输出如何做限流和背压？
SSE需控制**入口速率、活动连接、上游生成和每连接积压**。限流保护总量，背压处理生产者快于消费者，两者不能替代。

1. 按租户、用户、IP和模型设置新建QPS、活动连接、任务并发与Token预算，采用令牌桶和全局上限；超限返回`429`及`Retry-After`，或Load Shedding。
2. 每连接维护有界队列与最大待发字节，写入前检查可写状态。软阈值时合并Token、降低事件频率；硬阈值时暂停上游或断开慢消费者。
3. 若支持暂停读取，Reactive Streams通过request(n)传播需求；若不能减速，应限制输出、将结果写入可恢复日志并关闭连接，禁止无界缓存。
4. 事件带递增Sequence，断线后使用Last-Event-ID从短期日志重放。重放也受速率和窗口限制，过期则返回快照或任务最终结果，避免历史事件瞬间压垮客户端。
5. 监控新建/活动连接、租户占比、队列、写阻塞、Chunk合并、断开、消费速率与取消后Token。压测覆盖慢网、重连和突发。

| 机制 | 控制对象 |
|---|---|
| 令牌桶/配额 | 新建连接与任务流量 |
| 有界队列 | 单连接内存 |
| 上游暂停 | 生产速率 |
| 合并/丢弃 | 非关键事件 |

**相关知识点：** Rate Limiting、Backpressure、Reactive Streams、Token Bucket、慢消费者、Load Shedding、Last-Event-ID。

#### 137、多租户场景下如何限制单租户连接数？
应实施**租户配额、分布式计数、连接租约和公平调度**，防止单租户占满SSE连接、内存及模型并发。限制覆盖新建速率和存量连接。

1. 按租户套餐和优先级配置最大活动连接、新建速率、任务并发、Token/分钟和队列；用户/IP设次级上限，平台保留全局阈值。
2. 单实例用原子计数，多实例使用Redis或租约服务。建立连接时原子获取Permit，断开、超时和异常均释放；租约带TTL与心跳，崩溃后自动回收。
3. 采用令牌桶控制连接建立突发，信号量控制活动连接。超过上限返回`429`、`Retry-After`和当前配额信息；高价值任务可进入有界优先队列，但不能无限等待占用资源。
4. 配额Key必须来自已认证租户身份，不信任客户端Header；内部子账号共享父租户总额并可设置子配额。调整配额经审计，防止通过多用户或多区域绕过。
5. 监控租户连接、新建率、租约泄漏、连接时长、慢消费者、拒绝率和模型并发占比。定期对账本地与分布式计数，并做噪声邻居压测。

| 控制器 | 控制对象 |
|---|---|
| 令牌桶 | 新建连接速率 |
| 信号量/Permit | 活动连接数 |
| 租约TTL | 崩溃后的配额回收 |
| 公平队列 | 多租户资源分配 |

**相关知识点：** Multi-Tenancy、Quota、Distributed Semaphore、Lease、Token Bucket、Fair Queuing、Noisy Neighbor。

#### 138、流式输出中途失败如何设计重试和补偿？
流式中途失败不能从头重试，应基于**事件序列、检查点、幂等任务和明确终态**恢复。首字节前可重试，已输出后需防止重复、断裂和副作用重放。

1. 事件包含Task ID、Stream ID、递增Sequence、类型和校验；服务端将确认事件写入TTL日志。客户端保存最后Sequence，重连携带Last-Event-ID。
2. 断线后从日志重放缺失事件；任务仍运行则继续订阅，而非新建模型调用。窗口过期时返回快照、已完成文本和终态。
3. 首Token前瞬时错误在Retry Budget内重试或切换；已有文本且无法续写时，以稳定语义边界为检查点，附带已输出摘要续写，并标记恢复段。
4. 工具写操作与流展示分离，使用业务幂等键、状态查询和事务日志；重连只重放事件，不重放工具。未知状态先查询，失败后通过补偿事务或人工处理。
5. 协议定义`error`、`partial`、`completed`和`cancelled`终态，客户端不得把部分输出当成功。监控重连、重复/缺失、恢复时延、续写质量和额外Token。

| 失败位置 | 策略 |
|---|---|
| 首Token前 | 有界重试或切换 |
| 传输断开 | Sequence日志重放 |
| 模型生成中断 | 检查点续写或部分终止 |
| 工具状态未知 | 查询、幂等与补偿 |

**相关知识点：** Event Log、Sequence、Last-Event-ID、Checkpoint、幂等、Saga、部分结果、Retry Budget。

#### 139、如何监控SSE连接泄漏？
连接泄漏判定应基于**连接注册表、生命周期闭环和资源核对**。仅看活动连接无法区分真实长会话与失去客户端的孤儿连接。

1. 注册表记录Connection ID、Task ID、租户、实例、建立时间、最后心跳、状态、发送队列与上游ID；打开、完成、取消、超时和异常都产生事件。
2. 指标包括活动连接、新建/关闭速率、P99存活时间、空闲连接、写失败、心跳超时、连接内存、文件描述符、事件循环延迟及模型调用数。
3. 通过不变量发现泄漏：活动连接应近似累计打开减累计关闭；SSE连接、任务运行数、并发Permit和模型流数量应在合理比例。任务已终态但连接仍活跃、客户端断开后上游仍计费均属于异常。
4. 使用空闲超时、最大时长、共享心跳和租约TTL回收；写失败时传播取消并释放Permit。Reaper扫描注册表，对超阈值连接校验后关闭。
5. Trace串联代理`499`、关闭事件和取消结果，按实例与租户告警。长稳压测覆盖拔线、半开TCP、代理重启和进程崩溃。

| 异常信号 | 可能泄漏 |
|---|---|
| 打开数长期大于关闭数 | 生命周期未闭环 |
| 任务终态但连接活跃 | 应用未清理 |
| FD/内存持续升高 | 连接或缓冲未释放 |
| 断开后模型仍生成 | 取消未传播 |

**相关知识点：** Connection Registry、Lease、Reaper、心跳、半开连接、499、Cancellation、资源不变量。

#### 140、QPS继续提升到1万时架构如何演进？
QPS到1万时应演进为**无状态接入、异步任务、事件驱动流网关、分层限流和多区域治理**。重点是拆开短请求、长连接与模型计算资源。

1. API Gateway负责鉴权、配额、规范化与任务创建；任务写入持久队列并返回Task ID。SSE网关负责订阅与下发，采用非阻塞I/O并独立扩展。
2. Agent Worker按类型与优先级消费，模型网关负责路由、批处理、缓存、限流、熔断和预算。工具、RAG和模型使用独立连接池与舱壁。
3. 状态外置到任务库、事件日志和对象存储；事件带Sequence，支持断线重放。热点查询用多级缓存与Singleflight，大结果只存引用。
4. 按租户、区域、模型实施QPS、连接、TPM和并发配额，队列满时Load Shedding。容量按峰值QPS、Token吞吐、KV Cache和N+1计算。
5. 监控排队、TTFT、P99、连接、事件循环、TPM、拒绝率和单位成功成本。通过阶梯、突发、长稳及故障压测确定拐点，扩缩容采用滞回。

| 层次 | 演进重点 |
|---|---|
| 接入 | 无状态网关、分层限流 |
| 执行 | 队列、Worker、优先级 |
| 流式 | 独立SSE网关、事件日志 |
| 模型 | 路由、批处理、缓存、熔断 |

**相关知识点：** 异步任务、Event-Driven、SSE Gateway、Continuous Batching、Bulkhead、Load Shedding、N+1、容量规划。

#### 141、SSE如何和Agent任务状态机结合？
SSE应作为**任务状态机事件的只读投影**，而非任务容器。客户端断开不破坏持久状态，重连后按Sequence恢复同一任务。

1. 状态机定义排队、规划、工具、生成、等待、完成、失败和取消等合法状态，每次转移以Task ID和版本号原子持久化。
2. 状态与输出写入Outbox或事件日志，事件包含Stream ID、Sequence、state、stepId、payload和版本。发布器送至SSE网关，避免提交后事件丢失。
3. 客户端通过HTTP创建任务，再订阅事件；SSE只传进度、Token、工具状态、确认请求与终态。建立连接和重连时重验权限。
4. 断开后任务按策略继续或取消；重连携带Last-Event-ID，从日志重放并继续订阅。日志过期时返回快照与结果，不能重执行。
5. Stop作为状态机命令，通过Cancellation Token向模型和工具传播；写操作用幂等键。监控非法转移、事件延迟、重复/缺失和重连率。

| 状态机职责 | SSE职责 |
|---|---|
| 持久化任务真相 | 投影状态与输出 |
| 校验状态转移 | 按Sequence传输 |
| 管理取消与恢复 | 断线重放 |
| 执行业务副作用 | 不直接修改任务状态 |

**相关知识点：** State Machine、Event Sourcing、Transactional Outbox、SSE、Sequence、Last-Event-ID、Cancellation、幂等。

#### 142、高并发下SSE连接资源如何管理？
高并发SSE管理围绕**非阻塞连接、分层配额、有界缓冲、生命周期回收和隔离**展开。连接、模型任务和Token吞吐必须分别治理。

1. SSE网关采用事件循环和异步I/O，无状态扩展；每连接只保存认证、订阅ID、Sequence和小型发送队列，任务状态与日志外置。
2. 按区域、租户、用户设置活动连接、新建速率、连接时长、任务并发和TPM。建立时获取Permit，各结束路径释放；租约TTL处理崩溃回收。
3. 每连接队列和待发字节有硬上限，软阈值时合并Chunk、降低进度事件频率，硬阈值时暂停上游或断开慢消费者。禁止把完整模型输出长期积压在网关内存。
4. 共享时间轮发送心跳并扫描空闲连接，配置首事件、空闲和最大时长；客户端断开时传播Cancellation，释放模型流、工具和并发槽。重连通过Sequence日志恢复。
5. 连接按租户和优先级分片，以舱壁隔离噪声邻居；全局水位过高时Load Shedding。监控连接、FD、内存、事件循环、队列和孤儿任务。

| 资源 | 管理方式 |
|---|---|
| 连接/FD | 配额、Permit、租约 |
| 内存 | 有界发送队列 |
| CPU线程 | 事件驱动I/O |
| 上游模型 | 并发与TPM独立限制 |

**相关知识点：** Event Loop、Distributed Semaphore、Lease、时间轮、Backpressure、Bulkhead、Load Shedding、孤儿任务。

#### 143、百万级在线用户场景下流式网关如何扩容设计？
百万在线需采用**区域无状态流网关、连接任务解耦、分片事件总线和分层保护**。扩容依据连接、事件吞吐、带宽与内存，而非只看QPS。

1. 全局负载均衡就近接入区域，区域LB分发到事件驱动SSE节点。节点仅保留连接上下文和有界缓冲，任务状态、日志与订阅外置。
2. 按Task ID或Tenant ID分区，Agent输出进入消息总线，SSE节点只消费所需分区。重连可落任意节点，通过Last-Event-ID和日志恢复。
3. 容量模型计算每节点连接、FD、内存、带宽、心跳和事件循环延迟，并预留N+1和故障容量。扩缩容使用连接、待发字节和带宽并采用滞回。
4. 按租户实施新建速率、活动连接、TPM和并发配额；慢消费者使用有界队列、Chunk合并和断开策略。全局过载时按优先级Load Shedding，核心流量使用独立故障域。
5. 多区域事件复制只保存恢复窗口，避免全量广播。监控连接、重连风暴、事件滞后、带宽、FD、P99和单位连接成本，通过断区与长稳压测验证。

| 层次 | 扩容重点 |
|---|---|
| 全球/区域 | 就近接入与故障隔离 |
| 网关节点 | 无状态、事件驱动 |
| 事件层 | 分区、日志、重放 |
| 保护层 | 配额、背压、Load Shedding |

**相关知识点：** Global Load Balancing、SSE Gateway、Event Bus、分区、N+1、自动扩缩容、重连风暴、多区域容灾。

#### 144、Markdown增量解析具体如何实现状态机？
Markdown增量解析采用**词法缓冲、块状态机、稳定前缀和局部重解析**，不能每个Token重解析全文。未闭合结构保留暂态，稳定块才固化。

1. Chunk按Sequence排序并追加缓冲，处理UTF-8半字符、`\r\n`和转义。词法层识别换行、反引号、列表、表格和HTML，但不判断不完整标记。
2. 块状态包括段落、标题、列表、引用、围栏代码、表格、HTML和空闲；行结束或围栏闭合触发转移。行内处理强调、链接、代码和转义，并维护定界符栈。
3. 解析器维护最后稳定边界：已闭合块提交为AST；开放块仅在临时节点更新。新Chunk从最近检查点重解析，避免全量DOM替换。
4. 代码围栏未闭合时按代码显示，表格在分隔行前按段落处理；结构确认后只替换受影响节点。流结束执行EOF规则。
5. AST节点使用稳定ID，渲染层Keyed Diff并按动画帧批量更新。测试覆盖任意切分、嵌套列表、跨Chunk定界符和乱序，确保与全量解析一致。

| 层级 | 状态/职责 |
|---|---|
| 传输层 | Sequence与字符边界 |
| 词法层 | 标记与定界符 |
| 块解析 | 段落、列表、代码、表格 |
| 渲染层 | AST局部Diff与批量更新 |

**相关知识点：** Incremental Parsing、Lexer、AST、Delimiter Stack、Checkpoint、Stable Prefix、Keyed Diff、EOF规则。

#### 145、代码块未闭合时如何保证渲染正确？
未闭合代码块是**合法的流式暂态**，解析器保持围栏状态并安全临时渲染，不能自动补闭合后写入AST，也不能把代码误解析为Markdown或HTML。

1. 块状态机识别三个以上反引号或波浪线、围栏长度、缩进和语言标识，进入`OPEN_FENCE`状态；只有同类且长度不短于起始围栏的独立结束行才关闭。
2. 跨Chunk保留围栏状态、未完成行和UTF-8字符缓冲。收到的内容按纯文本节点追加并HTML转义，禁止解释其中标签、链接或脚本；语言标识经过白名单规范化。
3. 渲染树区分稳定AST与临时尾节点。已闭合块保持稳定ID不重绘，开放代码块只更新其Text节点；视觉上可显示“生成中”光标，但不要通过插入虚假结束围栏改变源文本。
4. 语法高亮采用增量Tokenizer或对当前代码块节流重算，避免每个Token重跑全文。高亮失败时回退为转义后的纯文本，内容正确性优先于颜色。
5. 流正常结束仍未闭合时，按Markdown EOF规则将其作为代码块展示并标记不完整；若协议报错，则保留部分内容和错误状态。测试需覆盖围栏跨Chunk、内部反引号、更长围栏、嵌套文本及断线重放。

| 状态 | 渲染策略 |
|---|---|
| 围栏刚出现 | 创建临时代码节点 |
| 内容流入 | 纯文本转义后追加 |
| 合法围栏闭合 | 固化AST并高亮 |
| EOF未闭合 | 保留代码并标记不完整 |

**相关知识点：** Fenced Code Block、增量解析、AST、HTML Escape、稳定节点、增量高亮、EOF规则。

#### 146、流式输出为什么容易产生页面抖动？
页面抖动源于**高频DOM更新、尺寸变化、全量重解析和滚动锚点不稳**。Token到达远快于适宜渲染频率，逐Token更新会反复布局与绘制。

1. 每Token修改会产生大量更新；Markdown若重建整棵AST/DOM，会导致节点变化、代码高亮和表格列宽重算，引发Reflow与Repaint。
2. 图片、代码块、字体和异步组件加载后高度改变；未闭合列表、表格或强调语法会让解析器回溯，造成已显示结构重排。
3. 接收层缓冲Token，按字符、标点或时间窗口合并Chunk，在`requestAnimationFrame`内提交。增量解析只更新尾节点，稳定AST使用固定Key。
4. 只有用户接近底部时自动跟随，上滑后停止并显示“回到底部”。不在每次更新调用`scrollIntoView`；图片预设宽高，代码块稳定高度。
5. 长文本使用虚拟列表；语法高亮和公式节流到块闭合或空闲阶段。监控Commit、长任务、CLS、丢帧率和绘制延迟。

| 抖动来源 | 优化 |
|---|---|
| 逐Token更新 | Chunk缓冲、帧内批量 |
| 全量Markdown解析 | 增量AST与稳定Key |
| 内容高度后变 | 尺寸占位 |
| 强制自动滚动 | 底部锚点与用户意图检测 |

**相关知识点：** Reflow、Repaint、CLS、requestAnimationFrame、增量DOM、稳定Key、虚拟列表、滚动锚定。

#### 147、如何设计Chunk协议格式？
Chunk协议应是**版本化、可排序、可恢复的结构化协议**。客户端必须识别重复、缺失、终态和部分失败。

1. 信封包含版本、`taskId`、`streamId`、`seq`、`eventType`、时间；payload按类型定义，禁止字段语义变化。
2. 类型包括`start`、`delta`、`tool`、`state`、`usage`、`error`、`complete`和`heartbeat`。delta声明追加、替换或快照语义。
3. `seq`在单Stream内递增，客户端按序应用并丢弃重复；间隙请求重放。SSE的`id`使用Sequence，重连通过Last-Event-ID恢复。
4. `error`包含错误码、retryable、partial、message；`complete`携带状态、内容哈希与usage。终态后不再发业务事件，晚到消息丢弃。
5. 设置Chunk最大字节、UTF-8边界和JSON规范，大对象传引用与哈希。Schema以可选字段扩展，测试覆盖乱序、重复、丢失。

| 字段/事件 | 作用 |
|---|---|
| taskId/streamId | 标识任务与流实例 |
| seq/id | 排序、去重、恢复 |
| eventType | 区分内容、状态与控制 |
| schemaVersion | 协议演进 |
| complete/error | 明确终态 |

**相关知识点：** Protocol Envelope、Sequence、Idempotency、Last-Event-ID、Schema Evolution、内容哈希、契约测试。

#### 148、Sequence丢失时如何补偿？
Sequence丢失应采用**检测缺口、暂停应用、范围重放、幂等去重和快照兜底**。不能先渲染后续事件再插入缺失内容，否则状态会错乱。

1. Stream从确定起点递增，客户端保存`lastAppliedSeq`。收到`seq <= last`时去重；收到`seq > last+1`时记录缺口并暂停应用。
2. 客户端请求缺口范围重放，或SSE重连携带Last-Event-ID。服务端从TTL日志返回原始事件，重放与实时流通过同一排序缓冲合并。
3. 事件应用必须幂等，delta明确追加/替换语义，状态事件带版本。客户端在连续Sequence恢复后提交渲染；重复事件不执行副作用。
4. 若事件日志过期或校验失败，服务端返回某个`baseSeq`对应的完整快照、内容哈希和当前终态，客户端原子替换本地投影，再从`baseSeq+1`继续。不能为恢复而重新执行Agent任务。
5. 设置最大乱序窗口和重放次数，超阈值终止流。监控缺口率、重复率、重放率、快照回退率和恢复时延，并测试丢包、乱序和断线。

| 情况 | 补偿 |
|---|---|
| 重复Sequence | 幂等丢弃 |
| 小范围缺口 | 日志范围重放 |
| 暂时乱序 | 有界排序缓冲 |
| 日志已过期 | 快照+后续增量 |

**相关知识点：** Sequence Gap、Replay Log、Last-Event-ID、Idempotency、Snapshot、排序缓冲、内容哈希。

#### 149、WebSocket断线重连如何保证消息不丢失？
WebSocket仅提供连接内有序帧，断线后不保证可靠；需通过**Sequence、ACK、持久日志、会话恢复和幂等消费**实现至少一次传递且效果不重复。

1. 会话分配Session ID，每条消息包含Message ID、Sequence、方向、类型和版本。两端分别保存最后连续应用和确认的Sequence。
2. 发送方先写Outbox或日志再推送；接收方成功后累计ACK。未确认消息保留到TTL，重连携带Session ID、恢复Token和最后ACK请求重放。
3. 客户端维护排序缓冲，重复Message ID丢弃，缺口请求重放。业务用幂等键或Inbox，避免重放副作用；ACK与业务提交语义需明确。
4. 恢复Token短期有效并绑定用户和会话；重连重鉴权。日志过期时返回快照和`baseSeq`，客户端原子替换，不能跳过消息。
5. 心跳检测半开连接，重连采用退避与抖动，防止恢复风暴。监控未ACK积压、重放、重复/缺失、恢复时延和幂等冲突。

| 机制 | 作用 |
|---|---|
| Sequence | 排序与缺口检测 |
| ACK | 确认连续消费位置 |
| 持久日志 | 断线后重放 |
| 幂等键/Inbox | 防止业务效果重复 |
| 快照 | 日志过期兜底 |

**相关知识点：** WebSocket、ACK、Sequence、Outbox/Inbox、At-Least-Once、幂等、Session Resume、重连风暴。

#### 150、Last Event ID机制底层原理是什么？
Last-Event-ID是SSE的**客户端消费位置提示**：服务端发送`id`，浏览器记录最近ID；重连时以`Last-Event-ID`带回。它不自动保存或重放事件。

1. SSE事件由字段行组成，空行结束；`id: 123`更新EventSource内部缓冲，随后分发`message`或自定义事件。无`id`时不更新。
2. 连接异常时EventSource按`retry`间隔重连，并把最近ID放入请求头。自定义客户端可显式传游标，但浏览器原生API不能任意设置该头。
3. 服务端把ID映射到事件日志Sequence，从`last+1`重放后切换实时流；日志按Task/Stream隔离，防止不同流混淆。
4. 传输可能重复，客户端应用需幂等并检测缺口。ID表示浏览器最后接收，不代表业务已完成渲染，高可靠场景还需显式ACK。
5. 日志过期或ID未知时，返回快照、`baseSeq`与终态，不能静默跳过。监控重连、游标落后、重复、缺口和重放时延。

| 组件 | 职责 |
|---|---|
| SSE `id`字段 | 标记事件游标 |
| EventSource | 保存ID并随重连发送 |
| 服务端日志 | 按ID重放 |
| 客户端幂等层 | 处理重复与缺口 |

**相关知识点：** SSE、EventSource、Last-Event-ID、Sequence、Replay Log、At-Least-Once、ACK、Snapshot。

#### 151、流式输出如何支持停止生成（Stop Generate）？
停止生成应作为**幂等任务取消命令**贯穿客户端、网关、Agent、模型和工具，而非只关闭SSE。系统需区分停止展示、取消模型和撤销业务动作。

1. 客户端发送带Task ID、版本和幂等键的取消请求；服务端鉴权后原子转为`cancelling`。重复取消返回当前状态。
2. 编排器触发Cancellation Token并取消分支；适配器调用厂商取消API或关闭流与连接，释放Permit。若不支持取消，设置最大输出和Deadline。
3. SSE发送`cancel_requested`和`cancelled`，携带最后Sequence、内容哈希和usage。客户端保留已确认文本并标记部分结果，不能显示为正常完成。
4. 对工具读操作可直接取消；写操作需查询状态，使用幂等键、Prepare/Commit或补偿事务。取消不等于数据库回滚，已提交副作用必须明确告知并按策略补偿。
5. 以状态版本CAS解决完成与取消竞态，晚到Token或工具结果丢弃。监控取消延迟、取消后Token、孤儿任务、重复副作用和取消成功率。

| 层级 | Stop动作 |
|---|---|
| 客户端 | 发幂等取消命令 |
| Agent | 终止状态机与分支 |
| 模型 | 取消请求/关闭流 |
| 工具 | 查询、幂等或补偿 |

**相关知识点：** Cancellation Token、CAS、幂等、结构化并发、取消传播、Saga、竞态、部分结果。

#### 152、如何实现边输出边语法高亮？
边输出边高亮以**围栏状态、增量词法状态和节流渲染**实现，避免每Token重解析代码。未闭合时优先保证文本正确，高亮失败可降级。

1. Markdown状态机识别围栏、语言和结束；进入代码状态后，Chunk均按代码文本处理，不解析HTML或Markdown，直到合法闭合。
2. 高亮器维护Lexer状态，如字符串、注释和模板字面量。新Chunk从上次状态继续Tokenize，只生成新增节点；不支持增量则节流重算开放块。
3. 接收层按字符、换行或时间合并Chunk，在`requestAnimationFrame`内提交。稳定代码行使用固定Key，只更新未完成行，减少DOM抖动。
4. 语言标识使用白名单，未知语言回退纯文本；源码先HTML转义，禁止未净化HTML。Worker解析大代码块，主线程应用样式。
5. 围栏闭合时完整校验并固化AST；EOF未闭合则保留代码并标记。监控耗时、长任务、丢帧及增量与全量差异，测试跨Chunk状态。

| 阶段 | 策略 |
|---|---|
| 围栏识别 | 进入代码块状态 |
| Chunk到达 | 延续Lexer状态 |
| 帧内渲染 | 批量更新尾部节点 |
| 闭合/EOF | 全量校验或安全降级 |

**相关知识点：** Incremental Lexer、Fenced Code、requestAnimationFrame、Web Worker、HTML Escape、稳定Key、节流。

#### 153、长文本场景下虚拟列表如何设计？
长文本虚拟化以**块级节点、动态高度、滚动锚定和增量追加**为核心，只渲染视口附近内容。不能按Token虚拟化，否则破坏Markdown结构。

1. 以段落、标题、列表、代码块、表格或消息为Item并分配稳定ID。流式尾块单独维护，闭合后固化；代码和表格不可任意拆分。
2. 使用高度缓存与Fenwick Tree计算Item偏移；未测量项用类型均值估算，挂载后通过ResizeObserver更新高度并校正位置。
3. 渲染视口前后一定Overscan，快速滚动时适当增大。节点卸载后保留高度、解析状态和交互状态；重新挂载使用稳定Key，避免代码高亮、折叠和选择状态丢失。
4. 流式追加时若用户接近底部，以底部锚点保持自动跟随；用户上滑后锁定当前可见Item及像素偏移，新内容只显示提示。高度变化时补偿`scrollTop`，避免页面跳动。
5. 搜索、复制不能只依赖已挂载DOM，可基于完整文本定位并临时挂载。监控DOM节点、测量耗时、丢帧、布局偏移和内存，并测试图片加载。

| 设计点 | 作用 |
|---|---|
| 块级Item | 保持Markdown语义 |
| 高度索引 | 快速计算滚动位置 |
| Overscan | 减少快速滚动白屏 |
| 锚定补偿 | 防止追加与测量抖动 |

**相关知识点：** Virtual List、Dynamic Height、Fenwick Tree、ResizeObserver、Overscan、Scroll Anchoring、稳定Key。

#### 154、Token级刷新和Chunk级刷新如何取舍？
系统通常采用**后端细粒度接收、前端Chunk级刷新**。Token级更即时，但增加协议帧、Markdown解析和DOM绘制；Chunk级更平衡延迟与效率。

1. Token级适合低生成速率、纯文本终端或打字感场景；在浏览器和移动端，每秒数十Token会触发过多Commit、Reflow和高亮，造成掉帧。
2. Chunk按字节、Token、换行或时间聚合。首Chunk尽快发送以降低TTFT，后续按时间或Token批量；代码换行和Markdown块边界可提前刷新。
3. 自适应策略根据TPS、RTT、设备、页面可见性和队列调整。客户端慢时扩大Chunk并降低进度频率；结束、工具和错误事件立即flush。
4. Chunk保持UTF-8边界、Sequence和追加语义；聚合不能跨控制事件。前端在`requestAnimationFrame`内更新尾节点，不重建全文。
5. A/B比较首可见内容、P95、每秒事件、长任务、丢帧、带宽和中止率。最优值依设备和内容而异，应配置化。

| 策略 | 优势 | 代价 |
|---|---|---|
| Token级 | 即时感强 | 帧数与渲染开销高 |
| 固定Chunk | 简单稳定 | 场景适应性弱 |
| 自适应Chunk | 体验与性能平衡 | 控制逻辑复杂 |

**相关知识点：** Chunk Coalescing、TTFT、TPS、requestAnimationFrame、Backpressure、Adaptive Batching、Flush。

#### 155、小程序环境下Markdown渲染有哪些限制？
小程序Markdown受**组件、包体、性能、样式隔离和安全能力**限制，不能照搬浏览器DOM解析器。应采用受控语法子集、结构化节点与分块更新。

1. 小程序通常没有完整DOM、`innerHTML`和扩展API，第三方库可能依赖不支持对象；需用纯JavaScript解析器，将AST映射为原生组件。
2. `setData`或跨线程同步有大小与频率成本，逐Token更新会卡顿。应合并Chunk，仅更新尾块，稳定节点不重复传输；长内容使用虚拟列表。
3. 代码高亮、数学公式、复杂表格、脚注和HTML嵌入会显著增加包体与CPU。采用语法白名单和按需分包，未知结构回退纯文本；表格在窄屏使用横向滚动或卡片化。
4. 禁止渲染原始HTML和内联脚本，链接、图片与协议必须白名单校验；远程图片受域名、HTTPS和下载限制，并应设置尺寸占位。用户内容始终进行转义，防止注入。
5. 不同平台、基础库和字体有差异，应建立统一AST协议与Renderer，做真机矩阵测试。监控解析时间、`setData`大小、丢帧、内存和节点上限。

| 限制 | 设计措施 |
|---|---|
| 无完整DOM | AST映射原生组件 |
| 数据同步昂贵 | Chunk合并、局部更新 |
| 包体/CPU受限 | 语法子集、按需分包 |
| 窄屏与安全 | 表格适配、白名单与转义 |

**相关知识点：** 小程序Renderer、AST、setData、分包、虚拟列表、HTML Escape、域名白名单、真机测试。

#### 156、多端统一渲染引擎如何设计？
多端渲染采用**统一协议与AST、独立解析核心、平台专属Renderer**。统一的是语义与行为，不是共享DOM代码或像素样式。

1. 服务端输出含Sequence、事件类型和Markdown增量的协议；客户端核心负责排序、去重、增量解析、白名单和净化，生成稳定ID的AST。
2. AST定义段落、标题、列表、代码、表格、图片、引用和工具卡片，不含Web标签。Web、App和小程序分别映射到DOM或原生组件。
3. 建立Capability Matrix：不支持的表格、公式、HTML或交互使用横向滚动、图片、卡片或纯文本降级。协议保留原文和fallback。
4. 主题、字体、间距和颜色通过Design Token统一；复制、链接、代码展开和图片预览由适配器实现。外链、图片与HTML做白名单和转义。
5. 增量渲染只更新尾节点，长文本用虚拟列表；Golden Test确保各端AST一致，Renderer做截图、真机和性能测试。监控错误、降级率和端间差异。

| 层次 | 统一内容 | 平台差异 |
|---|---|---|
| 协议 | Chunk、Sequence、版本 | 传输SDK |
| 语义 | 规范AST | 节点到组件映射 |
| 视觉 | Design Token | 字体与布局能力 |
| 交互 | 行为契约 | 原生实现 |

**相关知识点：** Canonical AST、Renderer Adapter、Capability Matrix、Design Token、Progressive Enhancement、Golden Test。

#### 157、Agent输出包含图片、表格、代码时如何增量渲染？
应将输出建模为**类型化内容块事件流**，由增量解析器生成稳定AST，再由组件局部更新。图片、表格和代码闭合条件不同，不能均按文本追加。

1. Chunk包含Sequence、blockId、blockType、op与payload，操作区分`open`、`append`、`patch`、`close`和`error`。客户端按序幂等应用；缺口先重放。
2. 解析器维护块状态。代码围栏打开后按转义文本追加，闭合时固化并高亮；表格确认前按段落暂态展示，确认后只更新当前行与列。
3. 图片事件先渲染固定宽高占位、加载状态和替代文本，URL需域名、协议、权限与内容安全检查；加载成功原子替换资源，失败保留可重试卡片，避免高度突变。
4. 每个块使用稳定ID，已闭合块不重解析，开放尾块在`requestAnimationFrame`内批量更新。大代码高亮放Worker，宽表格横向滚动，长内容使用块级虚拟列表。
5. 流结束执行EOF规则，未闭合块保留内容并标记；终态携带AST或内容哈希。测试覆盖任意切分、乱序、图片失败、表格变化和围栏中断。

| 内容块 | 增量策略 |
|---|---|
| 图片 | 尺寸占位、异步替换 |
| 表格 | 行/单元格模型局部更新 |
| 代码 | 围栏状态、增量词法 |
| 普通文本 | 尾节点批量追加 |

**相关知识点：** Typed Block、Incremental AST、Stable ID、占位布局、增量高亮、虚拟列表、Sequence。

#### 158、流式输出过程中如何统计TPS和延迟指标？
应以Trace拆分**排队、首Token、生成、传输和渲染**，并明确TPS口径。总Token除以总时长会混入Prefill和网络等待。

1. 记录请求、调度、首Token、每Chunk、末Token、客户端首绘和终态时间，使用单调时钟；跨服务通过Trace关联，不相减未同步时钟。
2. TTFT为请求到首Token，可拆为队列、网关、Prefill和网络；端到端首显用客户端首绘。生成TPS为输出Token数除以Decode区间。
3. Chunk可能含多个Token，应使用usage或目标Tokenizer统计，不能把事件数当Token数。流中计算滑动TPS、ITL及停顿，结束后汇总。
4. 分别报告模型、网关和客户端TPS，差异可定位网络或背压。按模型、输入/输出长度、并发、地区和缓存分桶，观察分位数。
5. 监控TTFT、TPOT、ITL、总时延、取消、慢Chunk、事件队列和渲染延迟；采样保留时间线但不记录敏感文本。

| 指标 | 定义 |
|---|---|
| TTFT | 请求到首Token |
| TPS | Decode阶段每秒输出Token |
| TPOT | 平均每个输出Token时间 |
| ITL | 相邻Token/Chunk间隔 |

**相关知识点：** TTFT、TPS、TPOT、ITL、Monotonic Clock、Distributed Tracing、滑动窗口、分位数。

#### 159、如何设计流式输出的缓存层？
流式缓存应区分**事件日志、完成结果和请求去重**。它不是整页缓存；必须支持Sequence重放、终态一致、权限隔离和过期回源。

1. 进行中任务按Task ID/Stream ID写有序日志，事件含Sequence、类型、版本和哈希，设置短TTL与字节上限。重连依据Last-Event-ID重放。
2. 完成后生成不可变快照，保存文本/AST、状态、usage、证据版本和哈希；热点可用Redis/CDN，但Key包含租户、权限、任务、模型/Prompt和知识版本。
3. 相同幂等请求使用Singleflight，只启动一个任务，其余订阅同一流；语义相似请求仅在低风险且业务等价时复用，写操作禁止共享。
4. 数据、权限、Prompt、安全策略或知识变化时事件失效，TTL兜底。未完成、失败和取消分别标记，失败负缓存短TTL，部分结果不能冒充完成。
5. 不保存无限流，超过窗口后压缩快照并裁剪旧事件；敏感内容加密分区。监控重放/结果命中、Singleflight、陈旧率、存储和节省Token。

| 缓存类型 | 用途 |
|---|---|
| 事件日志 | 断线重放 |
| 结果快照 | 完成结果快速读取 |
| Singleflight | 并发相同任务去重 |
| 语义缓存 | 低风险等价请求复用 |

**相关知识点：** Event Log、Snapshot、Singleflight、Semantic Cache、Sequence、TTL、事件失效、租户隔离。

#### 160、如何实现流式输出的可观测体系？
流式可观测以**任务、流、连接生命周期和Trace**为核心，关联模型、网关与客户端。HTTP 200只表示连接建立，不代表流完成。

1. 统一Trace ID、Task ID、Stream ID、Connection ID和Sequence；Span覆盖排队、Prefill/Decode、工具、事件、网关、重放与首绘。不记录敏感正文。
2. 指标包括连接、关闭、心跳、重连、缺口/重复、队列、慢消费者、FD和内存；性能包括TTFT、TPS、TPOT、ITL、首绘和P95/P99。
3. 区分首Token前失败、流中失败、部分结果、取消和完成，统计重放、孤儿任务、取消后Token及重复副作用。成本关联重试、缓存和恢复Token。
4. 日志记录模型/Prompt/协议版本、路由、Sequence、错误码和终态；RUM上报首绘、丢帧、解析错误和网络类型，并与Trace关联。
5. SLO覆盖首Token、成功终态、重连和停顿；告警使用Burn Rate和资源水位，按租户/区域/模型切片。演练断网、乱序、慢客户端和模型超时。

| 信号 | 关注内容 |
|---|---|
| Metrics | 连接、时延、TPS、错误、成本 |
| Traces | 端到端阶段耗时与因果链 |
| Logs | 事件、版本、Sequence、终态 |
| RUM | 客户端首绘、卡顿、解析错误 |

**相关知识点：** Observability、Distributed Tracing、RUM、TTFT、ITL、SLO、Burn Rate、结构化日志。
