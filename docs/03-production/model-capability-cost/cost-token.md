# Token 与成本治理

<a id="model-003"></a>
### 1. 小模型和大模型如何分工？（豆包二面）

小模型与大模型应按**任务复杂度、风险和可验证性**分工：小模型负责高频、边界清晰、可程序校验的工作，大模型负责开放推理、复杂规划和高价值异常；通过级联升级而非固定绑定，在质量达标前提下控制成本。

1. 针对“小模型和大模型如何分工”，小模型适合意图分类、实体抽取、查询改写、内容路由、格式转换、简单摘要、规则补全和候选初筛。这类任务输入输出Schema明确、评测稳定，失败可由校验器快速发现，并可通过蒸馏或微调提高领域表现。
2. 大模型适合跨领域综合、长链规划、复杂代码、模糊需求、冲突仲裁和长尾任务。高风险场景仍需证据、规则、工具校验和人工门禁。
3. 典型流水线是“小模型分类与召回→规则过滤→小模型尝试→验证器判定→必要时升级大模型”。升级信号包括低置信、输入分布外、结构化输出失败、工具参数错误、多轮无进展和用户明确要求高质量。
4. 两类模型使用统一请求与结果契约，但Prompt、上下文窗口、Token预算和工具能力分别适配。切换时传递结构化状态与证据，避免把全部对话重复发送。
5. 以任务成功率而非模型单次准确率评估分工，重点监控升级率、误升级、漏升级、P95时延、单位成功成本和大模型调用占比。

| 维度 | 小模型 | 大模型 |
|---|---|---|
| 优势 | 低成本、低时延、高吞吐 | 复杂推理与长尾能力 |
| 任务 | 分类、抽取、改写、初筛 | 规划、综合、仲裁 |
| 风险 | 能力不足、漏升级 | 成本高、时延与幻觉 |

**相关知识点：** 模型级联、能力分层、蒸馏、领域微调、验证器、置信门控、分布外检测、单位成功成本。

### 2. 如何降低 Token 消耗？

降低Token应从**输入、输出、执行、复用和模型路由**共同治理，并以任务成功率为边界。盲目裁剪会导致重试或模型升级，反而提高成本。

1. 输入侧移除重复指令、无用Schema、日志和无关检索片段；静态内容用引用或Prompt Cache。长对话采用滑窗、分层摘要和结构化状态，并保留事实来源。
2. RAG按步骤检索，以元数据过滤、动态Top-K和Rerank只注入相关证据。Chunk需兼顾完整性与噪声，并去除重复片段。
3. 输出设置Schema、长度、停止条件和`max_tokens`，避免复述、冗长解释与无界代码；机器消费结果优先字段化输出。
4. Agent设置步骤、工具、Reflection、重试和总预算，并检测无进展循环。小模型完成分类与压缩，大模型处理困难节点；升级只传结构化状态。
5. 使用Prompt/Response/Semantic Cache复用，但键须含模型、模板、数据、工具和权限版本。监控缓存命中、重试放大及单位成功Token。

| 层面 | 主要方法 | 风险 |
|---|---|---|
| 输入 | 裁剪、摘要、RAG | 信息丢失 |
| 输出 | Schema、长度和停止条件 | 表达不足 |
| 执行 | 预算、去循环、模型级联 | 过早终止 |
| 复用 | Prompt/语义缓存 | 过期与越权 |

**相关知识点：** Context压缩、动态Top-K、Rerank、Token预算、模型级联、Prompt Cache、Semantic Cache、单位成功Token。

### 3. Reflection会增加多少Token成本？

Reflection没有固定增幅，取决于**轮数、上下文、Critic长度和是否重写**。一次“生成—评审—重写”会增加输入与输出；每轮重传完整轨迹时，成本会随上下文累积。

1. 可按`总Token=初次生成+Σ(反思输入+输出+修订输入+输出)`核算。反思需携带目标、候选、证据和Rubric，完整重传是主要增量。
2. 规则或小模型自检成本最低；同模型Reflection增加调用；独立大模型Critic加完整重写成本最高，但可降低严重错误与返工。
3. 应看单位成功任务Token。若反思明显提高成功率，增量可能小于重试与人工成本；若任务可程序验证而反思只重复措辞，则收益为负。
4. 仅在低置信、高风险或校验失败时触发；Critic接收最小证据包，输出结构化问题，仅重写失败片段，并限制轮数和预算。
5. 在线记录无反思基线、触发率、每轮Token、修复成功率和净质量增益，通过A/B按任务类型确定是否开启。

| 方式 | Token增量 | 适用 |
|---|---|---|
| 规则/小模型检查 | 低 | 格式与确定性约束 |
| 同模型Reflection | 中 | 一般复杂生成 |
| 独立Critic+重写 | 高 | 高价值高风险任务 |

**相关知识点：** Reflection、Critic、Token成本分解、触发率、局部重写、评审预算、单位成功Token、A/B测试。

### 4. 什么场景适合关闭Reflection？

适合关闭Reflection的任务具有**低风险、边界清晰、结果可确定性验证、时延敏感且反思增益很低**等特征。关闭不等于取消质量控制，而是用规则、Schema、测试或业务系统校验替代概率性的自我评审。

1. 意图分类、字段抽取、固定格式转换、简单查询改写等任务，若有严格Schema、枚举和范围校验，Reflection通常只会重复确认；模型一次通过即可交付。
2. 结果完全由权威工具产生，例如数据库查询、计算器、库存接口或编译器输出，LLM只负责组装调用时，应校验参数和工具结果，而不是让模型重新猜测事实。
3. 实时补全、搜索联想等低延迟场景，若错误可撤销且用户能纠正，可关闭同步Reflection，改为异步抽检。
4. 输入输出很短、任务分布稳定、离线评测与线上监控显示反思修复率长期接近零，且新增成本和P95明显高于质量收益时，应关闭。判断必须按任务类型切片，不能用全局平均。
5. 达到硬Token或费用预算时可以关闭非关键反思，但高风险操作、不可逆副作用、证据冲突、低置信和分布外输入不应因预算静默绕过门禁；应暂停、降级为只读或转人工。

| 场景 | 是否关闭 | 替代控制 |
|---|---|---|
| 确定性可验证 | 是 | Schema、规则、测试 |
| 极低延迟低风险 | 条件式 | 异步抽检 |
| 高风险不可逆 | 否 | Critic与人工门禁 |
| 低置信/分布外 | 否 | 升级模型或澄清 |

**相关知识点：** Reflection Gate、确定性校验、异步抽检、分布外检测、风险分级、质量增益、预算门禁。

### 5. Reflection和Self-Consistency如何结合使用？

Self-Consistency以**多条推理路径降低偶然性**，Reflection负责**检查并修复候选缺陷**；应先生成少量候选并聚合，只对低置信或高风险结果反思。

1. 复杂任务用不同种子、温度或视角生成`k`个候选；工具和副作用必须在沙箱或只读模式，禁止多路径写生产资源。
2. 先用Schema、测试、计算和引用回查淘汰无效项；离散答案多数表决，连续值稳健统计，开放生成按证据与约束评分。
3. 一致性高且验证通过时直接采用，避免Reflection；候选分歧大、最高分与第二名差距小、证据冲突或任务风险高时，将聚合结果、少数关键候选和证据交给Critic。
4. Critic分析事实、假设、计算或约束分歧，并输出局部修复或补证要求。仍无法消解则升级模型、调用工具或转人工。
5. 设置候选数、并行度、Reflection轮数、Token和Deadline预算。通过`质量增益/(新增候选成本+评审成本)`评估组合，只在高不确定性、高价值任务启用。

| 机制 | 主要作用 | 局限 |
|---|---|---|
| Self-Consistency | 降低单路径随机错误 | 成本随候选数增加 |
| Reflection | 定位并修复缺陷 | 可能自评偏差 |
| 确定性验证 | 提供客观门禁 | 覆盖范围有限 |

**相关知识点：** Self-Consistency、多样性采样、多数表决、稳健聚合、Reflection、分歧门控、确定性验证、预算控制。

### 6. 如何判断一个任务应该走大模型还是小模型？

判断应基于**复杂度、风险、模态、上下文、可验证性和SLA**，采用硬过滤加级联升级，而不是依赖关键词或用户身份。默认选择能达到质量阈值的最小模型，困难或高风险任务再升级。

1. 请求特征包括指令数量、约束冲突、推理步骤、输入长度、代码/数学信号、所需工具、模态、数据等级、输出Schema、P95目标与预算。轻量分类器结合历史标注预测复杂度与小模型成功概率。
2. 安全、地域、上下文和能力属于硬约束：小模型不支持视觉、工具、所需窗口或合规部署时直接排除。高风险操作即使使用大模型，也必须有规则、证据和人工门禁，模型大小不替代安全控制。
3. 高成功概率、结构化、可程序校验、低风险、短上下文任务走小模型；跨领域综合、模糊需求、长链规划、复杂代码、低样本长尾和证据冲突优先大模型。
4. 边界任务使用小模型先行，Schema失败、低置信、检索证据不足、工具参数错误、多轮无进展或用户重试触发大模型。升级只传结构化状态与关键证据，减少重复Token。
5. 用离线能力曲线确定阈值，线上记录小模型一次成功率、升级率、漏升级、误升级、P95和单位成功成本。策略通过Shadow和灰度校准，并按任务类型分别设置。

| 条件 | 小模型 | 大模型 |
|---|---|---|
| 复杂度 | 低、规则稳定 | 高、开放推理 |
| 验证 | 程序可验 | 语义评审为主 |
| 风险 | 低且可逆 | 高价值但仍需门禁 |
| 长尾 | 常见分布 | 分布外与冲突 |

**历史别名：** `MODEL-083`。

**相关知识点：** 复杂度分类、成功概率、硬约束、级联升级、分布外、置信门控、漏升级、单位成功成本。

### 7. 如何自动判断一个任务的复杂度等级？

任务复杂度应由**可观测特征、分类器和执行反馈**共同判断，输出概率而非绝对标签。复杂度不等于文本长度，短问题也可能需要深推理。

1. 特征包括约束数量、冲突、预计步骤、Token、跨文档依赖、代码/数学信号、模态、工具、Schema、领域稀有度、风险和可验证性。
2. 先用规则识别确定边界，例如视觉任务、超长上下文、生产写操作或特定工具要求；其余请求由轻量分类器、Embedding近邻或小型Router模型预测`P(simple/medium/complex)`。训练标签来自人工标注与历史任务结果，而非模型自评。
3. 标签定义应可执行：简单任务由小模型一次完成且可校验；中等任务需要检索、少量工具或有限推理；复杂任务涉及多阶段规划、冲突证据、跨领域、分布外或高风险。
4. 预测不确定时用小模型试运行，依据Schema、置信、工具参数和验证结果动态升级。将重试、步骤、Token与最终结果回写以校准分类器。
5. 评估使用各等级Precision/Recall、严重低估率、升级率、校准误差、SLA和单位成功成本。低估高风险任务的代价通常高于误升，因此阈值应按风险分层。

| 等级 | 典型特征 | 默认策略 |
|---|---|---|
| 简单 | 单目标、可校验 | 小模型 |
| 中等 | 检索/工具/有限推理 | 中档或级联 |
| 复杂 | 多阶段、冲突、长尾 | 大模型与验证 |

**历史别名：** `MODEL-108`。

**相关知识点：** 复杂度分类、特征工程、置信校准、试运行升级、概念漂移、严重低估率、成本敏感分类。

### 8. 如何衡量模型升级带来的ROI？

模型升级ROI应比较**增量业务收益与增量总成本**，而非只看Benchmark。升级会增加Token、P95和评审成本，只有产生可归因净收益才值得上线。

1. 建立基线，按任务、用户价值、风险和长度统计成功率、返工、人工接管、转化、事故损失、P95和单位成功成本，以切片定位提升。
2. 新模型先经黄金集、历史回放和Shadow，再做稳定分桶A/B。除模型外保持Prompt、RAG、Tool和采样参数一致，并报告置信区间。
3. 增量收益包括成功率提高带来的收入、人工节省、返工下降和风险损失减少；增量成本包括输入输出Token、缓存变化、推理基础设施、延迟导致的流失、迁移适配、评测及运维。
4. 可用`ROI=(增量收益−增量成本)/增量成本`，同时计算每增加一个成功任务的边际成本。若提升仅集中于少量复杂请求，应采用路由按需升级，而非全量替换。
5. 设置质量、安全、P95和预算护栏；严重错误可否决平均正ROI。上线后监控漂移、价格与升级占比，达到阈值自动降级。

| 维度 | 代表量 |
|---|---|
| 质量收益 | 增量成功率、返工下降 |
| 业务收益 | 转化、留存、人工节省 |
| 直接成本 | Token、算力、缓存 |
| 间接成本 | 时延、迁移、运维、风险 |

**历史别名：** `MODEL-112`。

**相关知识点：** ROI、TCO、增量收益、单位成功成本、边际成本、稳定分桶、Shadow、护栏指标、置信区间。

### 9. 如何避免模型频繁升级导致成本失控？

避免频繁升级需要**校准阈值、设置迟滞和次数、复用状态并实施预算门禁**。升级应是有证据的能力提升，而非模型间来回震荡。

1. 优先使用Schema、测试、事实冲突和工具错误等客观信号，模型置信须校准并结合风险。单次轻微失败不升级，可要求多个信号越阈值。
2. 使用Hysteresis：升级阈值高于保持当前模型的阈值；同一Task升级后锁定能力档位一定时间或步骤，禁止自动降回再升。设置最大升级层数和每任务切换次数，命中后人工或明确失败。
3. 升级只重做失败节点，传递目标、关键证据、工具结果和验收标准，不重发完整对话或重跑成功副作用。相同输入与策略的升级结果可短期缓存，防用户重试重复消耗。
4. 执行前估算升级后的剩余Token、费用和Deadline，软预算触发摘要、短输出或中档模型，硬预算要求审批或终止。高风险任务不能为了省钱绕过必要门禁，但可提前直接选择合适模型，避免先小后大双重成本。
5. 监控升级率、连续升级、误升级、升级修复率、增量Token和单位质量增益，按任务切片调整阈值。新触发器先离线回放和Shadow，防分布变化造成全量升级。

| 控制 | 作用 |
|---|---|
| 迟滞/冷却 | 防止档位震荡 |
| 最大升级次数 | 限制最坏成本 |
| 局部续作 | 避免重复上下文与副作用 |
| 预算门禁 | 阻止费用越界 |

**历史别名：** `MODEL-115`。

**相关知识点：** Hysteresis、置信校准、升级锁定、局部续作、预算门禁、误升级、增量Token、Shadow。
<a id="model-024"></a>
### 10. Context裁剪如何避免关键信息丢失？

Context裁剪应采用**信息分级、依赖感知、来源保留和裁后校验**，而非只留最近N轮。目标、约束、权限、事实、未决项和计划依赖须固定保护。

1. 将上下文拆为策略、目标、状态、证据、历史、工具轨迹和噪声，并记录来源、版本、时间、敏感级别和关联节点。先删重复、过期及无依赖内容。
2. 使用Dependency-aware裁剪，从当前节点反向遍历输入、约束和证据形成最小闭包。工具大结果外置，只保留摘要、关键字段、哈希和URI。
3. 长对话按阶段生成结构化Summary，含决策、事实、偏好、失败与待办；数字、否定和权限应保留原文片段或确定性字段。
4. RAG召回采用元数据过滤、动态Top-K和Rerank，并保留一定多样性，防相似片段挤掉反例。预算不足时优先缩短低价值证据，而不是截断每段开头。
5. 裁剪后检查计划输入、引用可达、硬约束和摘要一致性，并用成功率、关键事实召回、引用缺失、重试及Token节省评估。

| 优先级 | 内容 | 策略 |
|---|---|---|
| 必保留 | 目标、约束、权限、当前状态 | 固定保护 |
| 高 | 当前证据与依赖 | 按引用闭包 |
| 中 | 历史决策 | 结构化摘要 |
| 低 | 重复日志、无关闲聊 | 删除 |

**历史别名：** `MODEL-117`。

**相关知识点：** Context裁剪、依赖闭包、结构化Summary、RAG、动态Top-K、来源引用、完整性校验、Token预算。

### 11. 如何统计单个Agent任务的真实成本？

Agent任务成本应按**端到端执行图和全部资源**归集，不能只看主模型Token。应计入模型、检索、Tool、沙箱、存储、重试、Reflection与人工，并以TaskID贯穿。

1. Gateway记录输入、输出、缓存、推理Token、模型版本和单价；Span携带TaskID、AgentID、StepID、Tenant和CostCenter，取消也记录用量。
2. 工具按API、数据库、搜索、浏览器、沙箱CPU/内存/时长和出网计费；共享资源按规则分摊，固定与边际成本分开。
3. 重试、降级、备用切换、Judge和Reflection作为独立步骤计入，缓存命中记录避免的成本。人工审批和返工按工时费率折算，但与直接云费用分别展示。
4. 状态机汇聚Span，处理迟到事件与重复账单，以供应商账单校准Token估算。输出直接、分摊、总成本及单位成功成本；失败也计费。
5. 按任务类型、版本、用户和结果质量分析P50/P95成本、预算偏差与成本瀑布，定位上下文、输出、重试或工具浪费，并设置软硬预算告警。

| 成本类别 | 示例 |
|---|---|
| 模型 | Token、缓存、推理 |
| 工具与计算 | API、沙箱、数据库 |
| 编排 | 重试、Reflection、Judge |
| 人工与共享 | 审批、运维、固定资源 |

**历史别名：** `MODEL-123`。

**相关知识点：** TaskID、成本归因、CostCenter、成本瀑布、直接/分摊成本、单位成功成本、账单校准、预算告警。

### 12. 如何实现质量、时延、成本三目标优化？

三目标优化应先定义**质量安全底线、时延SLA和预算约束**，再寻找Pareto最优，而非随意加权。权重须按任务价值和风险配置。

1. 建立模型画像，记录任务成功概率、严重错误率、TTFT、TPS、P95、Token和单位成功成本。请求侧提取复杂度、模态、风险、SLA及预算。
2. 先按安全、地域、能力、质量、时延和硬预算过滤。候选用`效用=质量收益−λ1×时延−λ2×成本−风险罚分`排序，或从Pareto前沿选点。
3. 使用小模型级联：简单任务低成本完成，校验失败、低置信或高风险时升级；异步后台任务可选择慢而便宜的模型，实时交互优先低TTFT。输出长度、RAG Top-K和Reflection也作为决策变量。
4. 在线系统按健康、排队、配额和价格调整，并用迟滞防频繁切换。高风险请求禁止Bandit自由探索，新策略先Shadow和Canary。
5. 评估端到端任务成功率、SLA违约、P95成本和单位成功成本，并绘制质量—时延—成本前沿。若某方案成本更高、质量更低且更慢，则被支配应淘汰；阈值随业务价值和分布漂移定期校准。

| 场景 | 优先目标 | 典型策略 |
|---|---|---|
| 实时低风险 | 时延/成本 | 小模型、短输出 |
| 后台批处理 | 成本 | 批量、高性价比模型 |
| 高价值高风险 | 质量/安全 | 大模型、验证与审批 |

**历史别名：** `MODEL-125`。

**相关知识点：** 多目标优化、Pareto前沿、效用函数、级联推理、SLA、单位成功成本、迟滞、Bandit。

### 13. 如何记录一次请求为什么选择了某个模型？

每次路由应生成**不可变的Model Decision Record**，记录请求特征、硬过滤、候选评分、策略版本和运行变化，使决策可审计、可重放；不能保存完整敏感Prompt。

1. 生成DecisionID并关联TraceID、TaskID、租户和时间；保存任务、复杂度、Token区间、模态、SLA、预算、数据等级、地域及能力。文本只存脱敏摘要或哈希。
2. 每个候选记录ModelID、版本、画像版本、硬约束结果及拒绝原因，如数据越界、上下文不足、工具不兼容、配额或熔断。硬过滤与软分数分开。
3. 排序记录质量预测、P95、预估费用、健康度、风险和最终效用，连同权重、阈值、Router模型版本及随机实验桶。若规则优先级覆盖模型评分，也要记录命中规则ID。
4. 执行阶段补充实际模型、重试、升级、降级、备用、缓存、Token、时延、校验和最终状态，以判断初始选择是否合理。
5. 记录写入追加式审计存储并设访问控制与保留期。回放固定策略、画像和模型版本，并支持候选为空、模型升级等查询。

| 字段组 | 关键内容 |
|---|---|
| 请求画像 | 复杂度、SLA、预算、安全 |
| 候选过滤 | 模型、通过状态、原因 |
| 排序决策 | 分数、权重、阈值、策略版本 |
| 执行结果 | 切换、Token、质量、时延 |

**历史别名：** `MODEL-106`。

**相关知识点：** Decision Record、TraceID、模型画像版本、硬过滤、效用分数、策略回放、追加式审计、成本归因。

### 14. 在QPS达到1000以上的场景中，SSE流式连接如何实现心跳检测，超时释放和资源复用？（腾讯一面）

高并发SSE应采用**异步I/O、分层超时、心跳和取消传播**，不能每连接占一个线程。并发数近似为QPS乘以平均连接时长，不能只看QPS。

1. 网关用事件循环或异步Servlet，生成与写出通过有界队列解耦。连接只保存轻量状态，线程、HTTP连接与缓冲区使用受控池；禁止无界队列。
2. 定期发送SSE注释心跳`: ping\n\n`，间隔小于各层空闲超时。心跳只保活和检测写失败，业务进度用`event/id/data`事件。
3. 设置建连、首Token、Chunk空闲、总时长和写阻塞超时。失败时原子关会话、取消模型与工具，释放队列、订阅和租约；清理须幂等。
4. 通过队列水位检测慢客户端，先合并Chunk或降频，超过上限则断开并按Last-Event-ID恢复。
5. 限制全局、租户和用户连接数，监控活跃连接、建连率、心跳失败、断开原因、缓冲水位、连接寿命和资源回收延迟。

| 方案 | 资源特征 | 适用性 |
|---|---|---|
| 阻塞线程/连接 | 线程占用高 | 不适合大规模长连接 |
| 异步事件循环 | 少量线程承载多连接 | 推荐 |
| 无界缓冲 | 易内存雪崩 | 禁止 |
| 有界队列+背压 | 可控降载 | 推荐 |

**相关知识点：** SSE、非阻塞I/O、Little定律、应用心跳、分层超时、取消传播、背压、Last-Event-ID、连接配额。

### 15. 大模型和小模型如何分工？

小模型与大模型应按**任务复杂度、风险和可验证性**分工：小模型负责高频、边界清晰、可程序校验的工作，大模型负责开放推理、复杂规划和高价值异常；通过级联升级而非固定绑定，在质量达标前提下控制成本。

1. 针对“大模型和小模型如何分工”，小模型适合意图分类、实体抽取、查询改写、内容路由、格式转换、简单摘要、规则补全和候选初筛。这类任务输入输出Schema明确、评测稳定，失败可由校验器快速发现，并可通过蒸馏或微调提高领域表现。
2. 大模型适合跨领域综合、长链规划、复杂代码、模糊需求、冲突仲裁和长尾任务。高风险场景仍需证据、规则、工具校验和人工门禁。
3. 典型流水线是“小模型分类与召回→规则过滤→小模型尝试→验证器判定→必要时升级大模型”。升级信号包括低置信、输入分布外、结构化输出失败、工具参数错误、多轮无进展和用户明确要求高质量。
4. 两类模型使用统一请求与结果契约，但Prompt、上下文窗口、Token预算和工具能力分别适配。切换时传递结构化状态与证据，避免把全部对话重复发送。
5. 以任务成功率而非模型单次准确率评估分工，重点监控升级率、误升级、漏升级、P95时延、单位成功成本和大模型调用占比。

| 维度 | 小模型 | 大模型 |
|---|---|---|
| 优势 | 低成本、低时延、高吞吐 | 复杂推理与长尾能力 |
| 任务 | 分类、抽取、改写、初筛 | 规划、综合、仲裁 |
| 风险 | 能力不足、漏升级 | 成本高、时延与幻觉 |

**相关知识点：** 模型级联、能力分层、蒸馏、领域微调、验证器、置信门控、分布外检测、单位成功成本。

### 16. 如何设计模型调用的监控指标？

模型监控应覆盖**流量、可靠性、时延、质量、成本、安全与依赖健康**，并按模型、版本、供应商、租户、场景和路由切片；仅观察HTTP成功率无法反映“返回成功但答案不可用”。

1. 流量层记录请求量、并发、队列、上下文长度、流式连接数和取消率。可靠性层统计超时、`429`、`5xx`、空响应、Schema失败、重试、熔断与切换率。
2. 时延拆分排队、网关、首Token时间TTFT、生成时间、工具时间和端到端耗时，分别观察P50/P95/P99；流式场景增加Token间隔与卡顿次数，避免均值掩盖长尾。
3. 质量指标包括任务成功率、格式通过率、事实正确性、引用有效率、工具成功率、用户重试率和人工接管率。离线基准、抽样评审与线上反馈共同使用，不能把点赞率作为唯一标准。
4. 成本按输入、输出、缓存命中、推理Token、重试和工具费用归因到Task/Agent/租户，核心指标为**单位成功任务成本**，同时监控预算消耗速度。
5. 安全层统计越权、敏感数据拦截、策略拒绝和注入命中。Trace关联路由原因、Prompt版本、响应和工具链；告警基于SLO、错误预算和多窗口 burn rate。

| 维度 | 代表指标 |
|---|---|
| 可靠性 | 成功率、超时、重试、降级 |
| 性能 | TTFT、P95、Token间隔 |
| 质量 | 任务成功率、事实/格式通过率 |
| 成本 | 单位成功任务成本、预算速度 |

**相关知识点：** RED、USE、SLO、错误预算、TTFT、Trace、LLM可观测性、Burn Rate、成本归因。

### 17. Context Window越来越大，为什么仍然要控制Token成本？

更大的Context Window只提高容量上限，不意味上下文免费或全部有效。Token同时影响**费用、首Token时延、吞吐、显存、计算和答案质量**；冗余内容还会稀释关键信号。

1. API通常按输入和输出Token计费，长对话每轮重发历史使累计成本持续增长。Agent的工具结果、反思和重试进一步放大消耗，高QPS下尤其明显。
2. Attention的Prefill计算随序列长度增长；即使FlashAttention改善访存，长输入仍增加TTFT、GPU占用和批处理难度。KV Cache随上下文增长，压缩并发容量。
3. “上下文中存在”不等于模型能稳定使用。无关记录、重复证据和冲突旧信息会造成Lost in the Middle、注意力稀释与上下文污染。
4. 保留系统约束、当前目标、关键事实、未完成状态和证据；历史采用分层摘要，工具大结果保存引用，知识通过RAG按需召回，并利用前缀缓存。
5. 设置请求、会话、Agent步骤和租户预算，监控输入输出比、缓存命中、单位成功任务Token、TTFT及KV容量。压缩必须以任务成功率回归验证。

| 长上下文代价 | 直接影响 |
|---|---|
| 输入计费 | 单次及累计费用上升 |
| Prefill与KV增长 | 时延、显存、并发恶化 |
| 信息冗余冲突 | 召回与推理质量下降 |

**相关知识点：** Context Window、Prefill、KV Cache、TTFT、Lost in the Middle、RAG、上下文压缩、Prompt Cache。
<a id="model-078"></a>
### 18. RAG为什么能够降低Token成本？

RAG通过**按需注入少量相关证据**，替代把全部知识库或长文档送入模型，可降低输入Token及Prefill、KV Cache成本；但检索与Rerank也有费用，设计不当可能增本。

1. 文档离线切分并建立索引，请求时只召回相关Top-K片段，形成“最小充分证据集”。变化知识无需写入Prompt或重新微调，更新索引即可生效。
2. 检索结果可去重、压缩和引用化：大结果存于外部，只注入关键行、摘要与定位。多轮复用检索缓存，稳定前缀利用Prompt Cache，避免重复计费。
3. 收益取决于语料规模、查询选择性和精度。Chunk过大、Top-K过高、重叠过多会填满上下文；低质召回还会引发重试和升级，抵消节省。
4. 采用元数据硬过滤、混合检索、Rerank、动态Top-K和上下文去重，在召回率与Token间优化。简单事实可由检索结果或模板直接回答，复杂综合再调用大模型。
5. 评估应比较端到端任务成功率、每次查询的检索与模型总成本、输入Token、TTFT、重试率和**单位成功任务成本**，而非只统计向量库命中率。

| 方案 | 输入规模 | 主要代价 |
|---|---|---|
| 全量长上下文 | 大且重复 | 模型Token与时延 |
| RAG按需注入 | 小且相关 | 检索、Rerank成本 |
| 微调注入知识 | 推理输入较小 | 训练、更新与遗忘风险 |

**相关知识点：** RAG、Top-K、Chunk、Hybrid Search、Rerank、Prompt Cache、动态检索、单位成功成本。
<a id="model-079"></a>
### 19. Chunk大小如何影响成本和效果？

Chunk大小决定**语义完整性、召回粒度、索引规模和注入Token**。不存在通用最优值：过小会割裂证据并增加索引开销，过大则混入噪声、降低区分度并推高成本。

1. 小Chunk适合条款、FAQ和字段事实，定位精确、注入Token少；但标题、指代可能丢失，答案跨片段时需要更高Top-K，Embedding条目也会增加。
2. 大Chunk能保留段落、表格和代码关系，适合跨句推理；但一个向量代表多个主题，局部事实相似度被稀释，并把无关文本送入模型。
3. 应优先按文档结构、语义边界和内容类型切分，而非固定字符数。保留标题与层级元数据；代码按函数/类、表格按完整表或行组切分。适量Overlap用于跨边界语义，但需在索引和注入阶段去重。
4. 可采用父子Chunk：小片段负责检索，命中后返回包含必要上下文的父段；或先召回大段再做句级压缩。根据问题复杂度动态选择Top-K和父段范围。
5. 用真实问答集评测Chunk长度、Overlap和Top-K，观察Recall@K、证据完整率、正确率、输入Token、时延和单位成功成本，并按文档类型配置。

| 大小 | 优势 | 主要风险 |
|---|---|---|
| 小Chunk | 精准、注入少 | 语义割裂、条目多 |
| 大Chunk | 上下文完整 | 噪声与Token高 |
| 父子Chunk | 兼顾定位与完整性 | 实现复杂 |

**相关知识点：** Semantic Chunking、Overlap、父子检索、Recall@K、上下文压缩、Embedding、动态Top-K。
<a id="model-080"></a>
### 20. Top-K应该如何选择？

Top-K应按**召回充分性、上下文预算、查询类型和Rerank能力**动态选择。K过小会漏证据，过大则引入噪声、冲突和Token；最优点以任务成功率确定。

1. 用离线集绘制Recall@K、Precision@K、正确率和输入Token曲线，选择边际收益下降前的区间。单跳问题需较小K，多跳与跨文档综合需更大候选集。
2. 分离“候选K”和“注入K”：先取较大候选集保证召回，再经Cross-Encoder或轻量模型Rerank、去重、权限过滤和阈值，只注入少量高质片段。
3. 动态策略根据查询长度、实体数量、意图、多跳复杂度、分数分布、Chunk大小和剩余Token预算调整。若头部结果分数高且断层明显，可提前停止；分数接近或证据覆盖不足时扩大检索。
4. 采用MMR平衡相关性与多样性，避免多个近重复Chunk占满名额。父子检索中，小Chunk命中后合并同一父段，需去重重叠部分；强制保留引用来源和关键反例。
5. 监控证据使用率、无答案率、重试率、输入Token、P95和单位成功成本，按知识库和问题类型配置。高风险场景还需证据完整性校验。

| 策略 | 适用场景 | 代价 |
|---|---|---|
| 固定K | 分布稳定、简单系统 | 难适配复杂度 |
| 阈值截断 | 分数可校准 | 可能结果过少 |
| 动态K | 查询差异大 | 策略更复杂 |

**相关知识点：** Recall@K、Precision@K、Rerank、MMR、动态Top-K、分数校准、证据覆盖、Token Budget。

### 21. Agent为什么会出现Token爆炸问题？

Agent的Token爆炸来自**多轮、上下文重复、工具大结果、并行、反思重试和缺少终止条件**的乘法效应。治理必须覆盖任务图，而非只限制单次输出。

1. ReAct每步都会重发历史；对话、系统Prompt、工具Schema和检索片段随轮次增长。工具返回日志或代码原文时，后续每轮重复计入Token。
2. Reflection、Self-Consistency和多Agent会产生多个候选与评审轮次；从头重试、切换时复制完整上下文进一步放大。规划不清会形成调用循环。
3. 根任务设置Token、调用、步骤、并发、重试和Deadline预算并向下传播；软阈值时关闭反思、缩小Top-K，硬阈值立即终止或转人工。
4. 上下文保留目标、约束、事实、状态和证据；旧历史摘要，大结果外部存储并按需引用。稳定前缀缓存，相同请求去重与Singleflight。
5. 每步声明信息增益与验收条件；无新证据、状态重复或连续失败时Early Exit。监控任务Token、每步增量、重复率、工具占比和单位成功成本。

| 放大源 | 控制方式 |
|---|---|
| 历史重复 | 摘要、引用、前缀缓存 |
| 反思与分支 | 条件触发、限制轮数 |
| 工具大结果 | 外部存储、字段裁剪 |
| 无限循环 | 状态检测、预算、Early Exit |

**相关知识点：** Token Explosion、ReAct、Reflection、Self-Consistency、预算传播、Singleflight、Early Exit、上下文压缩。
<a id="model-092"></a>
### 22. 企业级Agent如何实现Token预算管理？

企业级Token预算采用**分层配额、预算传播、实时核算和策略化降级**，覆盖输入输出、重试、反思、检索及多Agent，防止局部合理而总成本失控。

1. 预算按组织、租户、项目、Agent、任务和步骤分层，区分周期财务配额与单任务上限。根任务创建Budget Context，记录Token、金额、调用、Deadline及保留额度，并向下传播。
2. 调用前按价格、输入和最大输出预占额度；流式按实际用量扣减，结束后对账并释放差额。重试、切换和子Agent不得重置预算。
3. 软阈值触发压缩、降低Top-K、关闭Reflection、选择小模型或缩短输出；硬阈值停止非核心步骤、返回部分结果或转人工。安全与审计额度应预留。
4. 设置优先级和价值密度，高价值任务使用受控共享池，低优先级排队或降级；超额需审批。异常租户限流隔离，防止抢占预算。
5. 成本账本按Task ID记录模型、Prompt版本、缓存、重试和工具费用，监控预算消耗速度、预测超支、单位成功成本及闲置额度。定期以质量回归和业务价值校准配额。

| 层级 | 管理对象 |
|---|---|
| 财务配额 | 租户、项目的周期总额 |
| 任务预算 | Token、金额、步骤与Deadline |
| 运行时门控 | 预占、扣减、软硬阈值 |
| 策略降级 | 压缩、缓存、小模型、终止 |

**相关知识点：** Token Budget、Budget Context、配额、预占核算、成本账本、预算传播、价值密度、单位成功成本。
<a id="model-093"></a>
### 23. 如何统计每个Agent的Token消耗？

统计应建立**任务—Agent—步骤—模型调用**成本账本，统一厂商口径，并将重试、缓存、反思和共享调用归因；仅汇总总Token无法解释来源。

1. 任务生成Task ID，子Agent携带Parent ID、Step ID和Trace ID。网关记录租户、Agent、模型版本、Prompt版本、输入、输出、推理、缓存Token及厂商请求ID。
2. 以厂商最终usage为计费事实；流式在结束事件汇总，中断时用已接收用量或Tokenizer估算并标记。各厂商用量映射为统一Schema并保留原始字段。
3. 重试、降级和切换标记attempt与reason，计入触发Agent。共享检索、Judge或子Agent按独占、均摊或业务权重分配，规则固定以防重复。
4. 输入Token拆分系统Prompt、历史、记忆、RAG、工具Schema与结果。成本按调用时价格计算，保留币种和价格版本；定期与厂商账单对账。
5. 展示每Agent总量、每成功任务Token、P95、重试占比、缓存节省、异常增长和预算达成率。明细需脱敏并限制访问。

| 归因层级 | 关键字段 |
|---|---|
| 任务 | Task ID、租户、业务结果 |
| Agent/步骤 | Parent、Step、角色 |
| 模型调用 | 模型、attempt、usage |
| 财务 | 价格版本、金额、账单差异 |

**相关知识点：** Cost Ledger、Trace ID、Token Usage、成本归因、流式计量、价格版本、账单对账。
<a id="model-094"></a>
### 24. 如何设计成本监控和告警体系？

成本监控应形成**计量—归因—预算—预测—告警—处置**闭环，并把费用与任务成功率关联。总账无法定位是流量、模型、重试还是上下文膨胀造成。

1. 网关采集输入、输出、推理、缓存Token，模型、价格、重试、路由、工具费和业务结果；以Task ID关联租户、Agent和步骤。定期对账，区分估算值与最终值。
2. 指标包括总成本、每成功任务成本、Token/QPS、输入输出比、重试成本、缓存节省、大模型占比及预算速度。按租户、场景、模型和Prompt版本切片。
3. 预算支持日/月配额、单任务上限和Forecast。告警采用静态阈值、同比异常、单位成本突增和多窗口Burn Rate组合，区分预警、严重与阻断级；短时流量峰值不能造成告警风暴。
4. 告警携带影响范围、贡献模型、最近变更和推荐动作。自动处置可限流、关闭Reflection、降低Top-K、切换小模型；高风险变更需审批且可回滚。
5. 仪表盘同时展示质量、P95和成本，避免只降费导致成功率下降。通过演练验证超预算、价格变更、重试风暴和用量缺失；复盘误报、漏报及节省金额，持续调整阈值。

| 告警类型 | 示例 |
|---|---|
| 预算 | 消耗速度将提前耗尽 |
| 单位成本 | 每成功任务成本突增 |
| 结构异常 | 重试或大模型占比激增 |
| 计量异常 | 用量缺失、账单偏差 |

**相关知识点：** FinOps、成本归因、Cost Ledger、Forecast、Burn Rate、单位成功成本、预算告警、自动降级。
<a id="model-096"></a>
### 25. 多Agent架构下如何控制整体Token开销？

多Agent成本治理以**统一预算、角色最小化、结构化通信和边际收益门控**为核心。若各Agent独立扩展上下文、重试和反思，开销会乘法增长。

1. Supervisor为根任务创建Token、金额、调用、步骤和Deadline预算并向下传播；子任务只能消费分配额度，不得重置预算。预留汇总、验证与恢复额度。
2. 仅保留有可测增益的角色，按DAG激活；分类、抽取和校验用小模型，复杂规划与仲裁用大模型。避免通用Agent重复分析。
3. Agent间通过Schema交换目标、证据、结果、置信度和未决问题，不广播完整对话。大结果存外部按需读取；稳定前缀、检索及工具结果使用缓存。
4. 限制并行宽度、候选数、反思轮数和重试次数。聚合器根据证据覆盖和状态变化执行Early Exit，取消慢分支；相同子任务使用指纹去重与Singleflight，工具写操作采用幂等键。
5. 账本按Agent、步骤、模型记录输入输出、缓存、重试和共享成本，监控成功率、增量收益、每Agent Token及单位成功成本。收益不足角色下线。

| 放大点 | 控制机制 |
|---|---|
| 子Agent无限扩张 | DAG与按需激活 |
| 上下文广播 | 结构化状态与引用 |
| 并行候选 | 宽度限制、Early Exit |
| 重试反思 | 共享预算与条件触发 |

**相关知识点：** Multi-Agent、Supervisor、预算传播、DAG、结构化通信、Singleflight、Early Exit、成本归因。
<a id="model-097"></a>
### 26. 除了Token成本，还需要关注哪些AI系统成本指标？

AI系统应按**端到端任务总拥有成本**核算。除Token外，还包括算力、存储、检索、网络、工具、运维、人工审核及失败重试，并应与成功结果关联。

1. 推理设施关注GPU/CPU利用率、显存、KV Cache、实例小时、峰值预留、空闲率和有效TPS；API模式还需记录并发套餐、最低消费及多模态计费。
2. 数据链路包括Embedding更新、向量库查询、Rerank、对象存储、日志、缓存、跨区流量及保留。知识频繁更新时，索引重建和缓存失效可能成为主要成本。
3. Agent链路统计工具API、沙箱、数据库、队列、SSE、重试、降级、并行、Reflection与人工接管。失败任务消耗的所有资源都应计入。
4. 生命周期成本包括数据标注、离线评测、微调训练、模型部署、红队、安全审计、许可证和工程维护；还需考虑供应商锁定、容量冗余和迁移成本。
5. 核心指标采用每成功任务成本、转化成本、毛利率、质量调整成本和成本方差，并按租户、场景、模型归因。同步展示质量与P95，防止隐性成本上升。

| 成本域 | 代表指标 |
|---|---|
| 推理 | GPU小时、KV占用、有效TPS |
| 数据/RAG | Embedding、向量查询、存储 |
| Agent执行 | 工具、重试、连接、人工接管 |
| 生命周期 | 评测、微调、安全与运维 |

**相关知识点：** TCO、FinOps、GPU利用率、KV Cache、RAG成本、人工接管、单位成功成本、质量调整成本。

### 27. 如何评估不同模型的能力画像？

能力画像是**按任务、风险和运行条件分层的版本化数据资产**，不能用总分代表模型。它包含质量、时延、成本、稳定性和合规属性，供路由使用。

1. 静态维度包括模态、语言、上下文、Tool Calling、结构化输出、地域、数据保留、价格和配额。任务维度覆盖分类、抽取、RAG、推理、代码、规划及领域知识。
2. 评测集由公共基准、真实脱敏、长尾失败和对抗样本组成，按难度、语言、场景、风险分桶。指标采用成功率、事实正确率、Schema通过率、工具后置条件和违规率。
3. 性能画像记录TTFT、TPS、P50/P95/P99、超时和最大稳定并发；成本画像记录输入输出价格、缓存折扣、每成功任务Token与金额。可靠性还需统计空响应、限流、版本漂移和降级兼容性。
4. 固定Prompt与参数重复评测，给出均值、方差和置信区间；由规则、人工和盲化LLM Judge联合评审并校准偏差。全部资产版本化。
5. 新模型先离线，再Shadow和灰度；线上反馈需防选择偏差。画像按时间更新，路由只使用满足样本量和新鲜度的数据。

| 画像域 | 代表内容 |
|---|---|
| 能力 | 任务、模态、工具、领域 |
| 质量安全 | 成功率、事实、违规率 |
| 性能可靠性 | TTFT、P95、错误率 |
| 经济性 | 单位成功成本、配额 |

**历史别名：** `MODEL-048`。

**相关知识点：** Capability Profile、分桶评测、置信区间、LLM-as-a-Judge、Shadow、版本漂移、单位成功成本。

### 28. 如何控制大模型调用成本？

控制成本应以**单位成功任务成本**为目标，从减少调用、压缩上下文、模型分级、缓存和预算门控入手，不能只压低单Token价格而牺牲成功率。

1. 网关记录输入、输出、推理、缓存、重试及工具成本，按租户、Agent、场景归因。根任务设置Token、金额、步骤、调用和Deadline预算，调用前预占。
2. 采用规则/分类器与小模型级联：分类、抽取、改写用小模型，复杂推理用大模型；低置信、验证失败或分布外时升级。先满足安全和质量硬约束。
3. Prompt删除重复说明，历史滚动摘要，大结果外部引用，RAG动态Top-K只注入必要证据。稳定前缀用Prompt Cache，低风险问答可用Semantic Cache。
4. Reflection、多Agent和重试按风险触发，限制轮数与宽度。相同请求用Singleflight；软预算时关闭非核心步骤，硬预算时返回部分结果或转人工。
5. 通过A/B与回归评估措施，监控缓存命中、升级率、重试Token、重复率、P95和单位成功成本。异常关联Prompt或路由版本并可回滚。

| 手段 | 主要收益 | 风险 |
|---|---|---|
| 小模型级联 | 降单次成本 | 漏升级 |
| 上下文压缩 | 降输入Token | 信息丢失 |
| 缓存 | 避免重复计算 | 陈旧误命中 |
| 条件反思 | 控制推理分支 | 质量增益不足 |

**历史别名：** `ARC-071`、`MODEL-049`。

**相关知识点：** FinOps、模型级联、Token Budget、Prompt Cache、Semantic Cache、RAG、Singleflight、单位成功成本。

### 29. 敏感数据如何保证不被发送到外部模型？

必须采用**默认拒绝、数据分级、出口强制检查与审计**，不能依赖Prompt保密。策略位于统一网关，Agent、SDK或备用路由均不得绕过。

1. 建立数据目录与分级，识别PII、凭证、商业秘密及租户内容，并映射允许的模型、地域、用途和保留策略。无法分类时按更高敏感级处理。
2. 网关发送前执行DLP、字段白名单、脱敏、令牌化或聚合；Prompt、RAG、记忆、附件和工具结果均检查。密钥及原始身份字段禁止进入上下文。
3. 路由先做数据驻留和供应商授权硬过滤；敏感任务进入私有部署、专属实例或本地小模型。若无合规候选，应拒绝、只运行确定性规则或人工处理，不能因主模型故障切换到不合规外部模型。
4. 使用网络出口白名单、私有链路、服务身份、最小权限和短期凭证，阻断应用直连公共API。配置供应商零保留/不训练条款、加密、区域和审计，但合同承诺不能替代技术控制。
5. 日志只存哈希、分类标签和脱敏摘要，记录策略版本、路由原因与主体。用诱饵数据、红队和流量审计验证，监控DLP命中、绕过与越域路由。

| 防线 | 作用 |
|---|---|
| 数据分级 | 确定允许用途与地域 |
| DLP/脱敏 | 出口前移除敏感字段 |
| 硬路由约束 | 仅选择合规模型 |
| 网络与审计 | 阻断绕过并可追责 |

**历史别名：** `MODEL-050`。

**相关知识点：** Data Classification、DLP、Tokenization、Data Residency、Egress Control、零保留、最小权限、审计。

### 30. RAG与大上下文模型如何取舍？

两者不是替代关系：**RAG从动态知识中选择证据，大上下文对已选材料整体理解**。应按语料规模、更新、证据定位、隐私、时延和成本选择，常组合使用。

1. RAG适合知识库远大于窗口、频繁更新、需权限过滤与引用的场景。它减少Token，但依赖切分、召回和Rerank，可能漏证据或破坏跨段关系。
2. 大上下文适合材料已知、规模可控且需跨章节综合的任务。它保留全局关系，但成本、TTFT和KV Cache随长度增长，并有Lost in the Middle。
3. 先判断能否确定材料：不能则先检索；能且不超预算，可用长上下文。高精度任务可先RAG筛选，再注入相邻父段或完整候选文档。
4. RAG按租户、ACL和时效过滤，使用混合检索、动态Top-K与Rerank；长上下文需目录、位置标记和分层摘要。两者都要控制Prompt Injection。
5. 比较证据Recall、正确率、引用有效率、TTFT、输入Token和单位成功成本，并按单跳、多跳与全局综合分桶，不能只比较窗口上限。

| 维度 | RAG | 大上下文 |
|---|---|---|
| 知识规模 | 可扩展到库级 | 受窗口限制 |
| 更新与权限 | 易过滤和更新 | 需重组输入 |
| 全局关系 | 可能被切分破坏 | 更完整 |
| 成本 | 检索费+少量Token | 大量输入Token |

**历史别名：** `MODEL-026`。

**相关知识点：** RAG、Long Context、Lost in the Middle、父子检索、Rerank、ACL、Prompt Injection、单位成功成本。

### 31. 如果预算固定，如何设计最优模型资源分配策略？

固定预算下应最大化**约束内的预期业务价值或成功任务数**，而不是平均分配调用额度。先保障安全与最低质量，再按任务的边际收益、风险和机会成本进行资源配置。

1. 将流量按场景、复杂度、风险、租户SLA和业务价值分桶，估计各模型在每桶的成功概率、P95与总成本。成本需包含小模型失败后升级、重试、检索、工具和人工。
2. 为每个分桶定义最低服务和质量门槛，高风险、合规及核心客户保留容量；剩余预算按“升级带来的增量价值/增量成本”从高到低分配，直到边际收益相等或预算耗尽。
3. 采用小模型级联：简单任务小模型处理，低置信、验证失败或分布外才升级。高价值任务可配置Rerank或Reflection，低价值流量使用缓存、规则答案、排队或更短输出。
4. 建立日/月配额与单任务预算，调用前预占，实时监控消耗速度并动态调节升级阈值、Top-K、并行宽度和模型档位。预留故障恢复、峰值和安全校验额度。
5. 离线用历史流量做背包/线性规划或仿真，线上以安全多臂老虎机小流量探索。评估预算利用率、成功任务数、每成功任务成本、公平性与SLO违约率，防止只服务高价值流量造成租户饥饿。

| 分配原则 | 作用 |
|---|---|
| 最低保障 | 守住安全、质量与SLA |
| 边际ROI排序 | 优先高增量价值 |
| 动态阈值 | 适应流量和价格变化 |
| 预留池 | 应对峰值与故障 |

**历史别名：** `MODEL-041`。

**相关知识点：** Resource Allocation、边际ROI、Knapsack、模型级联、预算预占、多臂老虎机、公平性、机会成本。

### 32. 客户端断开后，后端模型调用如何及时取消？

应建立**端到端取消传播链**：断开触发取消令牌，中止编排器、模型流、工具和下游连接，并回收配额。停止写数据不等于停止模型计费。

1. 网关监听连接关闭、写失败、心跳超时和Stop请求，将Task ID的Cancellation Token置为取消；该Token传给Agent、模型SDK、HTTP客户端与工具。
2. 适配器调用厂商取消接口或关闭流与连接，并丢弃不可复用连接。若厂商不支持取消，停止读取未必停止生成，应设置最大输出和供应商Deadline。
3. Agent在模型步骤、工具和循环边界检查取消。并行分支统一取消并清理；异步任务需区分“后台继续”和“随连接取消”，策略在提交时明确。
4. 写操作不能因取消回滚未知状态：使用幂等键、Prepare/Commit或状态查询确认是否完成；必要时执行补偿。取消后的晚到结果按任务版本丢弃，禁止重新写入已终止会话。
5. 记录取消延迟、成功率、取消后Token、孤儿任务、连接与槽位释放时间。通过断网、代理超时和慢响应演练验证无泄漏。

| 层级 | 取消动作 |
|---|---|
| 网关 | 产生取消信号、释放连接 |
| Agent | 停止状态机与并行分支 |
| 模型 | 取消流/关闭请求 |
| 工具 | 幂等终止、查询或补偿 |

**相关知识点：** Cancellation Token、结构化并发、Deadline传播、流取消、幂等、孤儿任务、补偿事务。

### 33. SSE流式输出如何做限流和背压？

SSE需控制**入口速率、活动连接、上游生成和每连接积压**。限流保护总量，背压处理生产者快于消费者，两者不能替代。

1. 按租户、用户、IP和模型设置新建QPS、活动连接、任务并发与Token预算，采用令牌桶和全局上限；超限返回`429`及`Retry-After`，或Load Shedding。
2. 每连接维护有界队列与最大待发字节，写入前检查可写状态。软阈值时合并Token、降低事件频率；硬阈值时暂停上游或断开慢消费者。
3. 若支持暂停读取，Reactive Streams通过request(n)传播需求；若不能减速，应限制输出、将结果写入可恢复日志并关闭连接，禁止无界缓存。
4. 事件带递增Sequence，断线后使用Last-Event-ID从短期日志重放。重放也受速率和窗口限制，过期则返回快照或任务最终结果，避免历史事件瞬间压垮客户端。
5. 监控新建/活动连接、租户占比、队列、写阻塞、Chunk合并、断开、消费速率与取消后Token。压测覆盖慢网、重连和突发。

| 机制 | 控制对象 |
|---|---|
| 令牌桶/配额 | 新建连接与任务流量 |
| 有界队列 | 单连接内存 |
| 上游暂停 | 生产速率 |
| 合并/丢弃 | 非关键事件 |

**相关知识点：** Rate Limiting、Backpressure、Reactive Streams、Token Bucket、慢消费者、Load Shedding、Last-Event-ID。

### 34. 多租户场景下如何限制单租户连接数？

应实施**租户配额、分布式计数、连接租约和公平调度**，防止单租户占满SSE连接、内存及模型并发。限制覆盖新建速率和存量连接。

1. 按租户套餐和优先级配置最大活动连接、新建速率、任务并发、Token/分钟和队列；用户/IP设次级上限，平台保留全局阈值。
2. 单实例用原子计数，多实例使用Redis或租约服务。建立连接时原子获取Permit，断开、超时和异常均释放；租约带TTL与心跳，崩溃后自动回收。
3. 采用令牌桶控制连接建立突发，信号量控制活动连接。超过上限返回`429`、`Retry-After`和当前配额信息；高价值任务可进入有界优先队列，但不能无限等待占用资源。
4. 配额Key必须来自已认证租户身份，不信任客户端Header；内部子账号共享父租户总额并可设置子配额。调整配额经审计，防止通过多用户或多区域绕过。
5. 监控租户连接、新建率、租约泄漏、连接时长、慢消费者、拒绝率和模型并发占比。定期对账本地与分布式计数，并做噪声邻居压测。

| 控制器 | 控制对象 |
|---|---|
| 令牌桶 | 新建连接速率 |
| 信号量/Permit | 活动连接数 |
| 租约TTL | 崩溃后的配额回收 |
| 公平队列 | 多租户资源分配 |

**相关知识点：** Multi-Tenancy、Quota、Distributed Semaphore、Lease、Token Bucket、Fair Queuing、Noisy Neighbor。

### 35. 流式输出如何支持停止生成（Stop Generate）？

停止生成应作为**幂等任务取消命令**贯穿客户端、网关、Agent、模型和工具，而非只关闭SSE。系统需区分停止展示、取消模型和撤销业务动作。

1. 客户端发送带Task ID、版本和幂等键的取消请求；服务端鉴权后原子转为`cancelling`。重复取消返回当前状态。
2. 编排器触发Cancellation Token并取消分支；适配器调用厂商取消API或关闭流与连接，释放Permit。若不支持取消，设置最大输出和Deadline。
3. SSE发送`cancel_requested`和`cancelled`，携带最后Sequence、内容哈希和usage。客户端保留已确认文本并标记部分结果，不能显示为正常完成。
4. 对工具读操作可直接取消；写操作需查询状态，使用幂等键、Prepare/Commit或补偿事务。取消不等于数据库回滚，已提交副作用必须明确告知并按策略补偿。
5. 以状态版本CAS解决完成与取消竞态，晚到Token或工具结果丢弃。监控取消延迟、取消后Token、孤儿任务、重复副作用和取消成功率。

| 层级 | Stop动作 |
|---|---|
| 客户端 | 发幂等取消命令 |
| Agent | 终止状态机与分支 |
| 模型 | 取消请求/关闭流 |
| 工具 | 查询、幂等或补偿 |

**相关知识点：** Cancellation Token、CAS、幂等、结构化并发、取消传播、Saga、竞态、部分结果。

### 36. Token级刷新和Chunk级刷新如何取舍？

系统通常采用**后端细粒度接收、前端Chunk级刷新**。Token级更即时，但增加协议帧、Markdown解析和DOM绘制；Chunk级更平衡延迟与效率。

1. Token级适合低生成速率、纯文本终端或打字感场景；在浏览器和移动端，每秒数十Token会触发过多Commit、Reflow和高亮，造成掉帧。
2. Chunk按字节、Token、换行或时间聚合。首Chunk尽快发送以降低TTFT，后续按时间或Token批量；代码换行和Markdown块边界可提前刷新。
3. 自适应策略根据TPS、RTT、设备、页面可见性和队列调整。客户端慢时扩大Chunk并降低进度频率；结束、工具和错误事件立即flush。
4. Chunk保持UTF-8边界、Sequence和追加语义；聚合不能跨控制事件。前端在`requestAnimationFrame`内更新尾节点，不重建全文。
5. A/B比较首可见内容、P95、每秒事件、长任务、丢帧、带宽和中止率。最优值依设备和内容而异，应配置化。

| 策略 | 优势 | 代价 |
|---|---|---|
| Token级 | 即时感强 | 帧数与渲染开销高 |
| 固定Chunk | 简单稳定 | 场景适应性弱 |
| 自适应Chunk | 体验与性能平衡 | 控制逻辑复杂 |

**相关知识点：** Chunk Coalescing、TTFT、TPS、requestAnimationFrame、Backpressure、Adaptive Batching、Flush。

### 37. 多端统一渲染引擎如何设计？

多端渲染采用**统一协议与AST、独立解析核心、平台专属Renderer**。统一的是语义与行为，不是共享DOM代码或像素样式。

1. 服务端输出含Sequence、事件类型和Markdown增量的协议；客户端核心负责排序、去重、增量解析、白名单和净化，生成稳定ID的AST。
2. AST定义段落、标题、列表、代码、表格、图片、引用和工具卡片，不含Web标签。Web、App和小程序分别映射到DOM或原生组件。
3. 建立Capability Matrix：不支持的表格、公式、HTML或交互使用横向滚动、图片、卡片或纯文本降级。协议保留原文和fallback。
4. 主题、字体、间距和颜色通过Design Token统一；复制、链接、代码展开和图片预览由适配器实现。外链、图片与HTML做白名单和转义。
5. 增量渲染只更新尾节点，长文本用虚拟列表；Golden Test确保各端AST一致，Renderer做截图、真机和性能测试。监控错误、降级率和端间差异。

| 层次 | 统一内容 | 平台差异 |
|---|---|---|
| 协议 | Chunk、Sequence、版本 | 传输SDK |
| 语义 | 规范AST | 节点到组件映射 |
| 视觉 | Design Token | 字体与布局能力 |
| 交互 | 行为契约 | 原生实现 |

**相关知识点：** Canonical AST、Renderer Adapter、Capability Matrix、Design Token、Progressive Enhancement、Golden Test。
