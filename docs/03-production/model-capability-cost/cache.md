### 1. Prompt Cache 如何设计？

Prompt Cache复用**相同输入前缀的模型计算结果**，用于减少重复Prefill，不等同于缓存最终回答。核心是稳定前缀、严格缓存键和安全失效。

1. 将系统指令、工具Schema和稳定示例放在前部，用户内容和随机字段放在后部；前缀越长、复用越高，收益越大。
2. 键包含供应商、模型版本、Tokenizer、模板、工具Schema、前缀摘要、策略和租户。任何影响Token或行为的变化都须换键，禁止跨权限域复用。
3. 缓存值可为服务侧KV或网关引用。设置TTL、容量、LRU和版本失效；敏感前缀应加密并最小留存。
4. 请求先计算前缀及Token边界；命中则复用，未命中完成Prefill后按长度与复用阈值写入。首次并发用Singleflight防击穿。
5. 监控命中率、命中Token、节省时延与费用、驱逐和误命中。低复用短Prompt不宜缓存。

| 缓存 | 命中依据 | 缓存对象 |
|---|---|---|
| Prompt Cache | 精确前缀/Token序列 | Prefill计算 |
| Semantic Cache | 语义相似请求 | 最终结果 |
| Response Cache | 完全相同请求 | 最终响应 |

**历史别名：** `CTX-187`。

**相关知识点：** Prefill、前缀缓存、KV Cache、缓存键、Singleflight、TTL、LRU、缓存击穿、租户隔离、版本失效。

### 2. Prompt压缩有哪些常见方案？

Prompt压缩应删除**冗余、低相关和可外部引用的信息**，保护目标、硬约束、权限、事实与输出契约。不能简单截断，须保留来源并验证。

1. 规则压缩包括指令去重、合并示例、删除日志噪声和使用Schema；工具说明按需加载，不把全部Tool注入。该方法确定且便宜。
2. Extractive选择关键句、实体、约束和证据，适合高风险材料，但可能不连贯。Abstractive更短却可能遗漏或幻觉，须保留来源与未决项。
3. RAG只召回相关Chunk，并结合元数据、动态Top-K和Rerank；长对话使用滑窗、阶段摘要、结构化状态和长期Memory分层。
4. Token级压缩可用小模型按目标保留信息，也可将大对象外置，仅传URI、摘要和权限令牌。Prompt Cache不减Token，但可降低重复Prefill。
5. 建立不可压缩字段清单，压缩后执行Schema、事实、引用及任务回归；以压缩率、召回率、质量差和重试放大评估。

| 方法 | 优势 | 风险 |
|---|---|---|
| 规则去重 | 确定、低成本 | 覆盖有限 |
| 抽取式 | 事实保真 | 连贯性较弱 |
| 生成式摘要 | 压缩率高 | 遗漏与幻觉 |
| RAG按需注入 | 动态相关 | 召回失败 |

**历史别名：** `MODEL-116`。

**相关知识点：** Prompt压缩、Extractive、Abstractive、动态Top-K、Rerank、结构化状态、Prompt Cache、压缩回归。

### 3. 千万级用户场景下如何进行模型容量规划？

容量规划应将**用户规模转换为流量、Token吞吐、并发和GPU/供应商配额**，并为峰值和故障留冗余。DAU、请求频率、峰值与长度才决定负载。

1. 按地区、场景和模型估算`QPS=活跃用户×人均请求/时间窗×峰值系数`；流式并发约为QPS乘连接时长。另统计输入/输出Token/s、TTFT和长度分布。
2. 自部署需基准测试不同批量、上下文和硬件下的Prefill、Decode TPS、显存及KV Cache，结合P95和利用率算实例数；商业API规划RPM/TPM与区域配额。
3. Router将流量分到不同模型，实时与批处理分池；设置租户、模型和优先级限流、有界队列、Admission Control及背压，并为高价值流量留容量。
4. 扩缩容观察队列、Token吞吐、KV Cache、GPU利用率和TTFT；预热模型与连接，以预测扩容应对峰值，并按单区域故障配置N+1。
5. 压测覆盖长短请求、慢客户端、重试风暴和降级。滚动更新预测，监控容量余量、拒绝率、排队P95及故障后的SLA。

| 容量对象 | 核心指标 |
|---|---|
| 请求入口 | QPS、峰值、并发 |
| 模型计算 | Prefill Token/s、Decode TPS |
| 显存 | 权重、KV Cache、批量 |
| 外部供应商 | RPM、TPM、区域配额 |

**历史别名：** `MODEL-127`。

**相关知识点：** 容量规划、Little定律、Prefill、Decode、KV Cache、Admission Control、N+1、预测扩容、混合压测。

### 4. 如何避免上下文污染？

避免上下文污染要把信息视为**带来源、权限、时效和可信度的数据**，通过写入治理、检索隔离、冲突处理与执行前校验，阻止错误或恶意内容影响决策。

1. 明确指令层级，系统策略与开发约束只来自受控配置；用户文本、网页、文档、工具结果和记忆均标记为数据，使用边界标签隔离，禁止其中的自然语言指令改变权限或工具策略。
2. 记忆写入前执行事实/推断分类、敏感检查、去重和质量门禁。仅保存稳定信息，记录主体、来源、时间、置信度、租户、权限、TTL和版本；模型猜测不得升级为事实。
3. 召回前按租户、项目、ACL和有效期硬过滤，再以阈值、Rerank、Top-K和去重限量。旧事实与当前输入冲突时，优先权威且更新的来源，并显式呈现冲突。
4. 摘要采用结构化Schema和增量合并，关键数字、否定、承诺及工具回执保留引用。用户更正时建立撤销记录，使相关摘要、Embedding和缓存同步失效，避免陈旧副本回流。
5. 工具执行前验证参数、权限和后置条件，高风险动作要求规则或人工确认。监控污染命中、冲突率、过期与越权召回、纠正时间，并支持追溯删除。

| 污染来源 | 主要防护 |
|---|---|
| 恶意文档指令 | 指令/数据隔离 |
| 错误模型推断 | 事实标签与写入门禁 |
| 过期或冲突记忆 | 版本、TTL、来源优先级 |
| 跨域数据 | ACL与租户硬隔离 |

**相关知识点：** Context Pollution、Prompt Injection、Provenance、ACL、TTL、记忆写入门禁、缓存失效、后置条件。

### 5. Prompt Cache和Semantic Cache有什么区别？

两者都降低计算，但层级不同：**Prompt Cache复用相同前缀计算，Semantic Cache复用语义相近请求的结果**。前者仍生成新答案，后者可能返回历史答案，风险更高。

1. Prompt Cache基于模型、版本和Token化前缀，命中后跳过部分Prefill，仍由模型生成。系统Prompt、工具Schema和固定知识前置且顺序稳定时命中率高。
2. Semantic Cache对查询生成Embedding，检索相似历史请求，超过阈值后复用结果。它覆盖措辞变化，但时间、权限、租户和上下文差异会导致误命中。
3. Prompt Cache随模型版本、前缀Token或工具变化失效；Semantic Cache还需把知识版本、权限、时间窗和安全策略纳入Key，并设置TTL。
4. 高风险任务只复用检索结果；写操作、实时价格和账户状态禁止语义答案缓存。两者均需租户隔离和审计。
5. 监控命中率、节省Token、P95、陈旧率、错误命中率和单位成功成本。语义阈值通过标注集校准，并支持回源。

| 维度 | Prompt Cache | Semantic Cache |
|---|---|---|
| 复用对象 | 前缀计算 | 答案或中间结果 |
| 命中依据 | Token前缀一致 | 语义相似 |
| 主要收益 | 降Prefill成本 | 省完整模型调用 |
| 核心风险 | 命中率低 | 错误或陈旧复用 |

**相关知识点：** Prefix Cache、Prefill、Semantic Cache、Embedding、Cache Key、TTL、缓存污染、租户隔离。

### 6. 如何提高缓存命中率？

提高命中率要稳定**等价请求表示、缓存键和失效边界**，同时保证权限与时效。宽松匹配产生的错误复用会降低质量并造成泄露。

1. Prompt Cache把系统指令、工具Schema、示例和共享知识放在前缀，保持字段顺序、工具排列和参数稳定；用户变量、时间戳和请求ID放到尾部。按模型版本建Key。
2. 精确缓存规范化Unicode、大小写、空白和无语义参数，但不能删除影响权限、语言、时间或业务语义的字段。相同工具请求使用参数指纹和Singleflight。
3. Semantic Cache用意图、实体、租户、权限、知识版本和时间窗构成复合Key，再由Embedding判断。按场景校准阈值；高风险、实时状态和写操作不复用答案。
4. 对热点请求预热，对长尾不盲目缓存；TTL依据数据变化速度设置，并通过事件驱动失效同步知识、摘要和权限变更。缓存空值与失败需短TTL，防止故障结果长期扩散。
5. 监控各类命中率、可缓存率、错误命中、陈旧率、节省Token、P95和驱逐原因。用未命中日志发现Key碎片化，以单位成功成本和质量回归约束。

| 命中障碍 | 优化 |
|---|---|
| Prompt前缀抖动 | 稳定模板与字段顺序 |
| 等价参数不同 | 安全规范化 |
| 知识频繁变化 | 版本Key与事件失效 |
| 并发相同请求 | Singleflight |

**相关知识点：** Cache Key、Prompt Cache、Semantic Cache、规范化、Singleflight、TTL、预热、缓存失效。

### 7. Semantic Cache如何设计？

Semantic Cache应以**业务等价而非文本相似**为标准，通过复合键、阈值、权限、版本和时效治理复用结果。写操作和实时高风险数据不缓存最终答案。

1. 请求先规范化Unicode、空白和无语义参数，再提取意图与实体并生成Embedding。Key包含租户、权限、任务类型、语言、知识版本、Prompt/模型版本和时间窗。
2. 在硬条件分区内做向量检索，候选再经实体、否定、数值、时间和权限校验；必要时用Cross-Encoder判断等价。阈值按场景标注集校准。
3. 缓存项保存问题、答案、证据、质量分、时间、TTL与数据版本。返回前检查证据；低置信或版本不一致时回源，也可只复用检索结果。
4. 数据、权限、安全策略和Prompt更新通过事件主动失效，并用TTL兜底。租户分区、加密、访问控制和审计防止泄露，负缓存使用短TTL。
5. 精确Key优先、语义匹配其次；热点预热，并发请求用Singleflight。监控命中率、错误命中、陈旧率、节省Token、P95和质量差值。

| 命中阶段 | 作用 |
|---|---|
| 硬条件分区 | 隔离租户、权限、版本 |
| 向量召回 | 找语义相近候选 |
| 业务校验 | 排除实体、时间等不等价 |
| TTL/事件失效 | 控制陈旧结果 |

**历史别名：** `CTX-188`、`MODEL-025`。

**相关知识点：** Semantic Cache、Embedding、复合Cache Key、阈值校准、Cross-Encoder、TTL、事件失效、Singleflight。

### 8. 如何设计流式输出的缓存层？

流式缓存应区分**事件日志、完成结果和请求去重**。它不是整页缓存；必须支持Sequence重放、终态一致、权限隔离和过期回源。

1. 进行中任务按Task ID/Stream ID写有序日志，事件含Sequence、类型、版本和哈希，设置短TTL与字节上限。重连依据Last-Event-ID重放。
2. 完成后生成不可变快照，保存文本/AST、状态、usage、证据版本和哈希；热点可用Redis/CDN，但Key包含租户、权限、任务、模型/Prompt和知识版本。
3. 相同幂等请求使用Singleflight，只启动一个任务，其余订阅同一流；语义相似请求仅在低风险且业务等价时复用，写操作禁止共享。
4. 数据、权限、Prompt、安全策略或知识变化时事件失效，TTL兜底。未完成、失败和取消分别标记，失败负缓存短TTL，部分结果不能冒充完成。
5. 不保存无限流，超过窗口后压缩快照并裁剪旧事件；敏感内容加密分区。监控重放/结果命中、Singleflight、陈旧率、存储和节省Token。

| 缓存类型 | 用途 |
|---|---|
| 事件日志 | 断线重放 |
| 结果快照 | 完成结果快速读取 |
| Singleflight | 并发相同任务去重 |
| 语义缓存 | 低风险等价请求复用 |

**相关知识点：** Event Log、Snapshot、Singleflight、Semantic Cache、Sequence、TTL、事件失效、租户隔离。
