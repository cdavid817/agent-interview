### ENG-006 · 做代码理解的时候，AST、调用关系这些信息是怎么用起来的？（百度Agent）

> 稳定 ID：`ENG-006`｜原题号：6

AST与调用关系把代码变成**可查询的符号、结构和依赖图**：AST描述组成，Call Graph描述行为传播，共同指导检索与影响分析。

1. 解析AST，抽取函数、类、接口、变量、类型、Import、控制流与源码范围，生成SymbolID；索引保存定义、引用、签名和Commit版本。
2. 命中符号后按AST范围提取完整函数、所属类、字段和必要Import；结构切分避免语句中间截断，并可过滤测试、生成代码和配置。
3. Call Graph通过调用表达式、类型解析和符号绑定建立Caller—Callee边，结合继承、接口、重载及依赖注入推导目标；LSP补充定义与引用。
4. Agent从入口沿图扩展有限跳数：定位缺陷时追上游调用与下游副作用，修改接口时寻找引用、实现和测试；边权融合静态置信、Trace与Git共变。
5. 动态派发、反射和代理无法仅靠静态分析确定，应保留候选边，并用配置、框架规则和运行时覆盖校准，不把不确定关系当事实。

最终只把关键签名、代码片段、路径与边证据加入上下文。效果以Symbol定位率、边Precision/Recall、影响召回和Token节省衡量。

**相关知识点：** AST、SymbolID、结构感知切分、Call Graph、符号绑定、LSP、动态派发、运行时Trace、Change Impact Analysis。

### ENG-007 · 代码上下文检索系统应该怎么设计？如何结合向量检索、关键词检索、AST分析和调用链分析？（DeepSeek一面）

> 稳定 ID：`ENG-007`｜原题号：7

代码检索应采用**多路召回、结构扩展、统一重排和预算化组装**：关键词保证精确命中，向量补充语义，AST与调用图提供依赖证据。

1. 按Commit构建全文、Symbol/AST、Embedding和Call Graph索引，保存路径、语言、模块、签名、权限及源码范围；摘要用于导航。
2. Planner提取符号、路径、错误码和接口。BM25负责名称、字符串和日志；Embedding负责意图语义；AST负责定义、引用、继承和结构。
3. 多路结果用RRF融合，再由Code Reranker结合查询、代码、路径、符号类型、新鲜度和权限排序；重复Symbol先合并。
4. 对Top候选沿Call Graph扩展Caller、Callee、实现和测试，限制跳数、方向与Token；边置信度用LSP、运行时Trace、配置及Git共变校准。
5. Context Builder按Repo Map、签名、片段、调用链和测试组装，保留来源与Commit，执行去重和裁剪；Executor需要时再检索。

系统按Commit Diff增量更新，哈希驱动缓存失效。评估Recall@K、MRR、NDCG、上下文Precision和影响召回，监控延迟与过期率。

**相关知识点：** BM25、Embedding、AST Index、Call Graph、RRF、Code Reranker、Context Builder、增量索引、Hybrid Search。

### ENG-008 · 单测生成里，哪些代码不适合生成单测？怎么识别并过滤？（百度Agent）

> 稳定 ID：`ENG-008`｜原题号：8

不适合生成单测的通常是**不可隔离、行为非确定、价值低或应由其他测试层验证**的代码；过滤是把预算用于可验证业务逻辑。

1. 纯数据模型、Getter/Setter、常量、自动生成、序列化样板和无分支转发若无自定义约束，测试只会重复实现；可用AST复杂度与生成标记识别。
2. UI像素、动画、音视频、硬件、GPU及并发时序难由单测稳定表达，应转为快照、视觉、仿真、性能或集成测试；识别依赖API和环境。
3. 强依赖真实数据库、网络、文件系统、第三方服务或全局状态，且缺少依赖注入边界的代码，不应让模型强行Mock内部细节；先重构接口，或在容器化环境执行组件测试。
4. 非确定算法、随机、机器学习推理和异步竞态若没有可控种子、Clock或Scheduler，应先建立可控性；否则生成的断言容易Flaky或只断言“非空”。
5. 已废弃、不可达、实验、迁移脚本、日志包装及已充分覆盖且近期无变更的代码，可按风险、变更频率和覆盖增量降权。

过滤器结合AST、依赖图、注解、Git变更、覆盖和Flaky标签，输出“不生成、需重构、转其他测试、可生成”及原因。高风险代码应升级人工设计。

**相关知识点：** 测试金字塔、可测试性、依赖注入、AST复杂度、Flaky Test、组件测试、视觉测试、风险驱动测试、覆盖增量。

### ENG-020 · 多模态模型处理图片时最终输入形式是什么？

> 稳定 ID：`ENG-020`｜原题号：20

图片进入模型后，最终不是原始字节，也不必先转成文字，而是被视觉编码器转换为**可与文本Token共同计算的视觉Token序列**。

1. 先解码图片，进行颜色、尺寸、归一化和方向校正；高分辨率图切成Tile并保留缩略图、坐标和缩放信息，避免细节丢失。
2. ViT把图片划分Patch，每个Patch经投影和位置编码形成Embedding；其他架构也可输出多尺度特征，但最终都得到带空间位置的视觉特征。
3. Projector、Adapter或Q-Former把特征映射到LLM维度，并经池化或查询Token压缩；视觉Token与文本Token拼接，或由Cross-Attention读取。
4. OCR、检测和版面分析产生的文字、Bounding Box与标签可作为结构化Token，但不能完全替代视觉特征；图表、公式和空间关系仍依赖视觉表示。
5. 推理时模型利用视觉Token、文本、历史和Tool结果生成下一Token。视觉Token数量影响显存、时延和成本，多图输入需按预算路由。

工程上保存原图Artifact、预处理参数、编码器版本、Tile坐标和Token预算，以便复现；用于检索时另生成全局或区域向量。

**相关知识点：** Vision Transformer、Patch、视觉Token、Projector、Q-Former、Cross-Attention、Tile、位置编码、多模态Embedding。

### ENG-053 · Embedding检索和BM25检索分别适用于哪些场景？为什么企业通常采用Hybrid Search？

> 稳定 ID：`ENG-053`｜原题号：53

BM25擅长**精确词项匹配**，Embedding擅长**语义召回**；两者错误模式互补，Hybrid Search可提高召回稳定性。

| 维度 | BM25 | Embedding |
|---|---|---|
| 核心依据 | 词频统计 | 向量距离 |
| 优势场景 | 类名、错误码、API | 意图、同义表达 |
| 主要短板 | 同义改写弱 | 标识符、数字易失真 |

1. “NullPointerException”“PaymentService”“ERR_1042”具有强词法信号，BM25可解释、更新快；Embedding可能召回拼写相近但无关的符号。
2. “订单取消后如何退库存”与实现中的“release reservation”词面不同，Embedding能映射意图；但效果依赖切块、模型和领域，近邻不等于调用相关。
3. Hybrid并行执行两路召回，保留各自Top K，使用RRF、加权归一化或学习排序融合；再结合路径、Symbol、AST、调用图、新鲜度与权限Rerank。
4. 查询可动态调权：包含标识符、路径和数字时提高BM25权重；自然语言、模糊需求提高向量权重。去重时避免同一文件挤占候选。
5. 离线用Recall@K、MRR、NDCG分层评估；线上观察定位成功率、首个有效结果位置、延迟和成本，融合方案须在同一候选预算下比较。

**相关知识点：** BM25、Embedding、词法检索、语义检索、RRF、Rerank、查询路由、Recall@K、MRR、NDCG。

### ENG-055 · 什么是Symbol Index？与全文索引有什么区别？

> 稳定 ID：`ENG-055`｜原题号：55

Symbol Index以**语义实体及其关系**为单元，覆盖类、函数、变量、接口及定义、引用、继承和实现；全文索引以词项和位置为核心。

| 维度 | Symbol Index | 全文索引 |
|---|---|---|
| 数据来源 | AST、LSP | 文本分词 |
| 主要查询 | 定义、引用、实现、重命名 | 关键词、错误码、注释 |
| 语义能力 | 区分作用域、同名符号 | 通常不理解语言语义 |

1. Symbol记录稳定ID、名称、全限定名、类型、签名、文件、范围、可见性和Commit，并建立defines、references、imports、extends等边，用于导航与影响分析。
2. 全文索引使用倒排表与BM25，建立简单、查询快，适合日志、字符串、配置键、注释和不完整标识符；但同名方法可能被混合。
3. Symbol Index能回答“哪个实现覆盖接口”“调用引用哪个重载”，但依赖解析；宏、反射、动态语言和条件编译会造成缺边，失败时需要降级。
4. 精确导航优先Symbol，未知名称和文本线索优先全文，再结合Embedding处理语义描述，利用调用图、路径和权限Rerank。
5. 增量更新依据Git Diff重解析受影响文件，维护跨文件引用；快照绑定分支与Commit，避免读取旧定义修改新代码。

**验证指标：** 任务完成率、测试通过率、变更接受率、交付周期和单位任务成本。

**相关知识点：** Symbol、全限定名、AST、LSP、倒排索引、BM25、作用域、定义引用、增量索引、语义检索。

### ENG-057 · AST为什么比正则表达式更适合代码理解？

> 稳定 ID：`ENG-057`｜原题号：57

AST将源码转换为**具有语法层级和节点类型的结构**，能表达作用域、声明、调用和控制流；正则只匹配字符模式，适合简单文本筛选，不适合承担通用代码理解。

| 维度 | AST | 正则表达式 |
|---|---|---|
| 处理对象 | 语法节点与层级 | 字符序列 |
| 可区分内容 | 代码、注释、字符串、作用域 | 依赖文本形态 |
| 适用任务 | 符号提取、重构、依赖分析 | 日志、固定格式与粗筛 |

1. 同一调用可跨行、嵌套泛型、包含注释或不同空白；正则容易漏召回或误匹配字符串中的伪代码。AST依据语言文法解析，格式变化不会改变节点语义。
2. AST能识别函数定义、参数、返回类型、Import、继承、注解、调用表达式和控制结构，并保留源码范围，支持按函数切块、定义—引用索引和最小范围修改。
3. 安全修改需要确保插入位置、括号层级和语法合法。基于AST执行结构化变换后可重新打印并校验；正则替换可能误改同名文本、破坏缩进或匹配到其他作用域。
4. AST也不是完整语义：名称绑定、重载解析、类型推断和跨文件引用通常需要编译器或LSP；调用可达性还需CFG、调用图或运行时Trace。
5. 对语法不完整、模板语言、宏和动态生成代码，解析器可能失败，应采用容错Parser、局部解析和文本降级。工程上常先用正则快速缩小候选，再用AST确认与修改。

**验证指标：** 任务完成率、测试通过率、变更接受率、交付周期和单位任务成本。

**相关知识点：** AST、Parser、语法树、作用域、结构化变换、名称绑定、LSP、CFG、容错解析、文本降级。

### ENG-064 · Repository Summary、Module Summary和File Summary分别如何生成和维护？

> 稳定 ID：`ENG-064`｜原题号：64

三层摘要应形成**可追溯的层级索引**，由底层向上聚合，而非独立生成；每条摘要绑定Commit、来源Symbol和版本。

| 层级 | 核心内容 | 主要用途 |
|---|---|---|
| File | 职责、Symbol、依赖、副作用 | 选文件 |
| Module | 边界、接口、数据流、依赖 | 跨文件规划 |
| Repository | 架构、入口、技术栈、目录 | 初始导航 |

1. File Summary基于AST、LSP，提取签名、Import、调用、配置、I/O、副作用、异常及测试；LLM归纳语义，事实保留路径、行号和Symbol引用。
2. Module Summary从文件摘要、构建清单和模块图聚合，描述职责、API、核心实体、上下游、扩展点和约束；先确定性聚合，再由模型压缩。
3. Repository Summary从模块摘要、目录、依赖、README、CI和部署清单生成，突出边界、入口、架构、运行方式与风险，不堆叠文件细节。
4. 内容哈希和Git Diff触发增量维护：文件变化重建File Summary，并沿DAG标记上层摘要；新版本原子切换，旧版本用于审计。
5. 固定摘要Schema，包含事实、推断、证据和置信度；抽样与源码校验，监控覆盖率、陈旧率和一致性。低置信或修改时回读原文。

**相关知识点：** 分层摘要、确定性聚合、摘要DAG、内容哈希、增量更新、来源追踪、摘要陈旧率、事实一致性。

### ENG-076 · 向量语义检索相比传统关键词检索定位代码有哪些劣势，如何优化？

> 稳定 ID：`ENG-076`｜原题号：76

向量检索能理解意图，但定位代码时存在**标识符弱、结构缺失、可解释性低和索引成本高**等问题，应作为Hybrid Search的一路召回。

1. 类名、错误码、版本号、路径和短变量具有离散词法意义，Embedding可能把相近但错误的Symbol排前。含标识符、引号和数字时提高BM25与Symbol权重。
2. 向量距离只表示片段相似，不表达定义—引用、调用、继承、作用域和数据流；需以AST、LSP、Call Graph和构建依赖校验候选。
3. 切块过大稀释语义，过小丢失签名；应按函数、类、接口和配置切块，附路径、签名、语言、模块、Commit，并分别索引代码、注释和摘要。
4. 通用Embedding对内部术语、混合语言和新框架可能失配。可选Code Embedding模型，用企业标注对做对比学习并加入难负样本；升级须版本化回归。
5. ANN会牺牲召回并受索引新鲜度影响；调节HNSW和Top K，使用RRF融合，再以Cross-encoder、路径、图距离、新鲜度和权限Rerank。

结果须保留分数、来源和版本，不能把相似度当概率。按查询类型评估Recall@K、MRR、NDCG、无关上下文率、P95和成本，确认未损害精确定位。

**相关知识点：** Code Embedding、Hybrid Search、语义切块、Symbol Index、RRF、Cross-encoder、难负样本、HNSW、索引新鲜度。

### ENG-078 · 如何解决几十万行代码下 Agent 上下文窗口长度受限的问题？

> 稳定 ID：`ENG-078`｜原题号：78

应把仓库转化为**可索引、可摘要、可恢复的外部记忆**，使每轮只注入当前步骤的最小充分上下文，而非无限扩窗。

1. 建立路径/BM25、Embedding、Symbol、AST、Call Graph、构建依赖和Git索引；按Repo、模块、文件、函数生成分层摘要，绑定分支与Commit。
2. 提取标识符、错误码、意图和验收条件，多路召回后以RRF融合，结合路径、图距离、新鲜度、权限和频次Rerank；先读高置信候选，再沿定义、引用、调用和测试扩展。
3. 上下文分级：待修改代码、契约、断言和错误现场保留原文；稳定依赖保留签名或摘要；日志去重聚类，大Artifact外置并保存句柄与来源。
4. 使用工作记忆与Checkpoint，将轨迹压缩为目标、事实、修改、失败、未决问题和下一步；关键决策保留文件、行号及Trace引用，避免摘要幻觉。
5. Planner把长任务拆为可验证子任务，独立检索与验证；编译、LSP诊断和测试触发局部重检索。设置Token、候选、图深度、轮数和停止条件。

缓存Repo Map、查询向量和已读文件，索引按Git Diff更新。观察完成率、Recall@K、无关上下文率、压缩一致性、Token、P95和成功成本。

**相关知识点：** 外部记忆、分层索引、渐进式检索、上下文分级、Checkpoint、动态重检索、Token预算、最小充分上下文。

### ENG-083 · 企业项目存在大量重复工具代码，Agent 如何区分通用代码和业务核心代码？

> 稳定 ID：`ENG-083`｜原题号：83

区分不能只看目录或命名，应综合**调用位置、数据语义、变更模式、运行重要性和所有权**并保留置信度；通用代码也可能位于关键链路。

1. 通用代码通常跨模块复用、与领域实体弱相关，如序列化、日期、重试、日志和集合操作；业务核心代码承载规则、状态转换、权限、金额和领域不变量。
2. 构建Symbol与调用图，统计入度、调用模块、入口距离和数据流。调用者分散的节点偏通用；位于入口到数据库/外部动作路径、处理领域实体的节点偏核心。
3. 工具代码常跨业务共变少、Owner属于平台团队；核心代码与需求PR、领域测试和业务文件共变。克隆检测识别重复片段，但语法相似不代表语义相同。
4. 融合Trace、SLO、频次、故障影响、敏感标签和CODEOWNERS，建立“通用性分”和“业务关键度分”，避免把高频基础库误判为低风险。
5. 检索时对工具片段设置Hub惩罚、去重和每簇上限，优先返回接口摘要；仅当调用、错误栈或数据流穿过时展开。业务规则、契约与测试保留原文。

分类需可解释并绑定Commit，变化后更新。低置信节点由Owner或测试验证，不能据此自动删除、合并代码；重构需独立影响分析与审批。

**相关知识点：** 领域代码、基础设施代码、调用图、数据流、Git共变、代码克隆检测、Hub惩罚、业务关键度、Code Ownership。

### ENG-088 · 索引如何随代码库的增量提交（commit）实时更新，避免索引过期？

> 稳定 ID：`ENG-088`｜原题号：88

### ENG-092 · 为什么不能只使用向量检索？

> 稳定 ID：`ENG-092`｜原题号：92

向量检索只解决**语义相似召回**，不能表达精确词项、代码结构、权限与版本约束；单独使用会造成标识符和调用定位错误。

1. 类名、错误码、路径、数字、版本和短变量具有离散含义，Embedding可能混淆相近表达，无法像BM25或Symbol Index稳定命中精确Token。
2. 向量相似不等于程序相关。描述相似的函数可能无调用，真正依赖可能词面不同。定义—引用、继承、调用、数据流与构建依赖需AST、LSP和图索引。
3. Embedding依赖切块、模型、语言和领域；长Chunk稀释目标，短Chunk丢失签名。内部术语、混合语言及生成代码容易产生分布外误差。
4. ANN近似搜索会引入召回损失；向量分数没有统一概率含义，难设跨查询阈值，解释和故障定位也弱。
5. 权限、租户、分支、Commit、新鲜度和生成物过滤是确定性约束，必须在元数据层执行，不能依赖向量隐式学习。

企业应采用Hybrid Search：BM25负责词法，Embedding负责意图，Symbol/AST/Graph负责关系，RRF融合后结合路径、调用距离、新鲜度和权限Rerank。按查询类型评估Recall@K、MRR、NDCG、无关上下文率、P95和成本。

**相关知识点：** 向量检索、BM25、Symbol Index、AST、Graph Search、ANN、语义切块、RRF、元数据过滤、Hybrid Search。

### ENG-095 · AST相比普通文本检索有哪些优势？

> 稳定 ID：`ENG-095`｜原题号：95

4. 各通道并行Top-K，以RRF统一尺度，再按命中、语义分、结构、图距离、新鲜度和路径Rerank；硬条件用于过滤。
5. Context Builder去重选择Repo Map、签名、代码、依赖和测试，形成最小充分证据；Planner按覆盖率决定执行或再检索。

设置超时、候选上限与降级，保存来源和分数。评测Recall@K、MRR、NDCG、Context Precision、P95及完成率，并做消融。

**相关知识点：** Code RAG、混合召回、Symbol Index、AST、Call Graph、RRF、Rerank、Context Builder、查询改写、消融实验。

### ENG-118 · AST分析和Embedding检索如何结合？

> 稳定 ID：`ENG-118`｜原题号：118

两者形成**Embedding扩大语义候选、AST提供结构边界与硬约束、图关系补全上下文**的组合，避免语法角色错误。

1. Parser生成AST，按函数、类和声明切块，提取Symbol、节点类型、签名、作用域、定义引用及调用边；代码、注释和摘要分别生成Embedding。
2. 查询解析为自然语言意图与结构条件，例如语言、节点类型、注解、调用某API或继承某接口。业务描述优先向量召回，精确结构条件进入AST过滤或图查询。
3. 向量返回Top-K后，以AST校验类型、签名和作用域，沿定义、调用者、实现与测试扩展；也可AST先筛选再向量排序。
4. 分数包含cosine、Symbol、AST匹配、图距离、路径和新鲜度；硬约束不以软加分代替，Cross-Encoder重排Top-N。
5. 增量更新由Git Diff触发，只重解析变化文件、重算变化节点Embedding及受影响边；Parser失败时降级文本块，并标记低置信度，不能假装结构信息完整。

评测按语义查询、结构查询和跨文件查询切片，比较单独Embedding、单独AST与融合方案的Recall@K、MRR、结构准确率、Token和完成率。

**相关知识点：** AST切块、Code Embedding、结构过滤、定义引用、图扩展、Cross-Encoder、增量解析、低置信降级、消融评测。

### ENG-142 · 大规模代码库下，如何做增量式单测质量评估而非全量重跑？

> 稳定 ID：`ENG-142`｜原题号：142

增量评估以**变更影响分析和证据缓存**选择最小必要测试集，并用周期性全量运行校准漏选风险。

1. 从Git Diff提取变化文件和Symbol，结合静态调用图、构建依赖、覆盖映射及历史运行关系计算受影响测试。
2. 对公共接口、配置、Schema、依赖升级和动态调用扩大影响闭包；图信息缺失或置信度低时回退到模块或全量测试。
3. 缓存键包含测试、代码/依赖Hash、环境和种子；只有所有输入未变且无副作用依赖时复用结果。
4. 优先运行目标单测，再运行受影响模块、契约和关键路径；按风险和历史失败概率排序并并行分片。
5. 周期性全量运行与随机哨兵测试用于估计漏选率，发现漏选即更新依赖和覆盖图。

报告测试选择Precision/Recall、漏检回归、节省时长、缓存命中率和P95，而非只报告“少跑了多少测试”。

**相关知识点：** Test Impact Analysis、调用图、覆盖映射、增量测试、缓存键、哨兵测试、漏选率。

### ENG-159 · 长视频分析如何优化成本？
