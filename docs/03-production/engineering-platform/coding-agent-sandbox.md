### 1. 把仓库送进沙箱有哪些方式？完整 clone、工作树快照与只读挂载如何取舍？

三种方式的差别不在快慢，而在**沙箱是否拥有独立的对象库、以及构建往源码树写回时会污染谁**。

1. 完整 clone 语义最干净：沙箱有自己的对象库与引用日志，追溯行级历史、二分定位、与目标分支求合并基点都成立；代价是每个任务一份对象副本，大仓库的准备耗时与磁盘随并发线性增长。可先在宿主维护一个定期同步的裸镜像，再从本地路径 clone，把网络往返换成本地拷贝。
2. 从本地镜像派生工作树快照最省时间，因为对象库共享、只写一份工作目录；但共享意味着沙箱对版本控制目录的写入会波及其他任务，且分支占用是全局的——同一个分支不能同时在两个工作树里检出。
3. 只读挂载宿主检出目录再叠一层可写覆盖，准备近似零耗时；但构建会往源码树里生成文件（编译产物、缓存、代码生成结果），这些写入落在覆盖层，导出变更时必须显式排除，否则改两行会变成上千文件的差异。
4. 三者的失败模式不同：完整 clone 卡在资源，工作树快照卡在并发耦合，只读挂载卡在"宿主检出被谁改过"——它是一份跨任务共享的可变状态，一旦某个任务绕过覆盖层写了进去，后续任务的基线就不再可信。

选型按"任务是否需要历史"乘"构建是否写源码树"两维决定；执行外部贡献者代码时一律用独立 clone，不共享对象库。可采集的验证指标是准备阶段 P95 耗时、每任务磁盘占用，以及导出差异中被判定为构建产物的文件占比——最后一项持续偏高说明挂载方式与忽略规则没有配对。

**相关知识点：** 裸镜像预热、对象库共享、工作树快照、只读挂载叠加覆盖、合并基点可用性、构建产物排除。

### 2. 多个 Coding Agent 并行修改同一仓库时，如何用 Git worktree 做工作区隔离？

worktree 的隔离粒度是**工作目录与索引，而不是引用和对象库**；并行是否安全取决于有没有把共享的那一半也划清。

1. 每个任务分配独立工作树并直接切到分离头指针，而不是先建分支再检出：分支一旦在某个工作树里被检出，其他工作树就无法再检出同一分支，任务重试或复用时会撞上这条约束；分离头指针把"任务基于哪个提交"与"分支归谁"解耦。
2. 索引与头指针是每工作树独立的，所以并行暂存和提交互不干扰；但引用命名空间、暂存区栈与钩子是共享的——多个 Agent 同时写同名临时引用或用暂存区栈传状态，就会互相覆盖。约定用带任务标识前缀的引用名，并禁止把暂存区栈当跨步骤存储。
3. 共享对象库省的是磁盘而不是构建时间：工作目录各自独立，依赖目录与编译产物这类未跟踪内容每个工作树都要重新生成，这往往才是准备阶段的大头。要么给依赖目录单独挂只读缓存，要么接受首次构建慢。
4. 回收必须显式做：直接删目录会留下悬空的工作树登记项，之后创建同名工作树会失败；任务结束应按顺序移除工作树、清理任务引用，并定期执行清理命令收敛残留。

worktree 适合同一仓库、同一基线、互不冲突的并行改动；跨基线或需要不同子模块状态时，独立 clone 更省心。监控并行度、工作树创建失败率与残留工作树数量，并用"两个任务同时跑时各自的测试通过率是否与单跑一致"作为隔离真正成立的回归检查。

**相关知识点：** 分离头指针、每工作树索引、共享引用命名空间、未跟踪内容重建、工作树登记项回收、并行一致性回归。

### 3. 超大仓库如何用稀疏检出与浅克隆压缩沙箱准备时间？

两者压缩的是不同维度——**浅克隆砍历史深度，稀疏检出砍工作目录宽度**；砍错维度会直接破坏编码任务依赖的操作。

1. 浅克隆省的是对象传输，代价是历史不完整：与目标分支求合并基点、行级历史追溯、按历史定位引入缺陷的提交都会失败或给出错误答案。Coding Agent 恰恰高频用这些操作解释"这行为什么是这样"，所以浅克隆更适合只跑构建与测试的验证型沙箱，不适合探索型任务。
2. 按需拉取文件内容的部分克隆更贴合编码场景：提交图完整，合并基点与历史遍历仍然成立，只有真正被读的文件才拉取。风险是访问模式一旦发散——例如跨历史全量检索——惰性拉取的往返次数会让总耗时超过一次完整克隆。
3. 稀疏检出按目录锥形裁剪工作目录，只有落在选定路径下的文件才写盘，对多语言巨型仓库收益最大；但构建系统看到的是一棵残缺的树，依赖分析可能把缺失目录当成被删除，或因找不到被引用的模块而失败。裁剪范围必须由构建图推出来，不能凭任务描述猜。
4. 两种裁剪都会让"Agent 找不到东西"这个失败信号变得含混：究竟是没检索到，还是文件根本没落盘。要在沙箱里暴露裁剪清单，让读取被裁掉的路径直接报出明确错误，而不是静默返回不存在。

先测量准备阶段耗时的构成再决定裁什么，多数超大仓库的瓶颈在工作目录写盘与依赖安装，而不是对象传输。用准备耗时 P95、按需拉取往返次数、构建首次成功率三项一起看，任何一项因裁剪明显恶化就说明裁过了头。

**相关知识点：** 浅克隆、部分克隆、惰性拉取往返、稀疏检出锥形模式、构建图推导裁剪范围、缺失路径显式报错。

### 4. 子模块、Git LFS 和生成物目录在沙箱里应该如何处理？

这三类内容的共同点是**都不在主仓库的对象里，却决定构建能不能跑通**；沙箱要为每一类明确取还是不取，默认全取和默认全不取都会出事。

1. 子模块是一个指向具体提交的指针，初始化时要按各自的地址再拉一次，凭证与协议不一定与主仓库相同——只发了主仓库令牌而子模块用另一套地址，是准备阶段典型的静默失败。按任务是否触及子模块决定是否初始化，不触及就保持指针原样。
2. 未初始化的子模块最危险的地方不在构建失败，而在提交：Agent 一次全量暂存可能把指针改成空值或改回旧提交，产出人类评审时极难看懂的变更。导出前应单独校验指针类条目是否被非预期修改。
3. LFS 内容在检出时由过滤器按需下载。全量拉取会让准备耗时被少数二进制文件支配；跳过下载则工作目录里留下指针文件，读它的构建步骤会拿到一段文本而不是二进制，报错信息通常和真实原因毫无关系。折中是默认跳过、按路径选择性拉取，并让读到指针文件的失败带上明确提示。
4. 生成物目录靠忽略规则排除在版本控制外，但忽略不等于隔离：Agent 仍能读写，构建也会往里写。它们应由缓存机制承载而不是随工作区走，并在导出变更时按忽略规则过滤，否则一次依赖安装就能把补丁撑到无法审阅。

把这三类外部内容做成准备阶段的显式清单，每项记录取或不取及原因，失败时能直接定位。监控子模块初始化失败率、LFS 下载在准备耗时中的占比，以及导出补丁中被过滤掉的文件数——最后一项突然升高通常意味着忽略规则与构建行为脱节了。

**相关知识点：** 子模块指针条目、凭证与协议不一致、LFS 过滤器与指针文件、选择性拉取、忽略规则过滤补丁。

### 5. 沙箱工作区的生命周期如何定义？何时可以复用、何时必须销毁重建？

把工作区当成**带显式缓存键的缓存**而不是长期存在的开发机；复用的前提是能证明状态，证明不了就销毁。

1. 缓存键至少包含仓库、基线提交、工具链镜像摘要与依赖锁文件哈希，任一变化即视为未命中。凭"目录还在就接着用"的复用方式会把上一个任务的环境变更悄悄带进下一个任务，而失败现场往往在几十个任务之后才暴露。
2. 常见的复用判据是"版本控制状态干净"，但这个信号覆盖不到真正的污染源：被忽略的目录、全局包缓存、临时目录、上个任务装的系统包、残留的后台进程、被改过的环境变量。它能证明源码树干净，不能证明环境干净。
3. 必须销毁重建的情形要写成硬规则：执行过外部不可信代码且有过出网、注入过凭证、工具链或基础镜像更新、发生过越权或破坏性操作、任务以未知状态失败。这几类的共同点是"污染是否发生"无法低成本判定，此时销毁比排查便宜。
4. 销毁工作区与保留缓存要分开：真正贵的是依赖安装与编译，而它们可以放进内容寻址的只读缓存跨任务共享。工作区一次性、缓存长期只读，是兼顾干净与速度的常见切分。

复用是性能优化而非默认语义，出现任何歧义都应向销毁一侧倾斜。验证方式是定期抽样对照——同一任务分别在复用工作区与全新工作区各跑一遍，比较首次测试通过率与构建耗时；通过率出现系统性差异就说明复用池已被污染，此时应整体清空而不是逐个排查。

**相关知识点：** 工作区缓存键、锁文件哈希、状态可证明性、强制销毁规则、内容寻址只读缓存、复用对照抽样。

### 6. 编码任务的沙箱该选进程隔离、容器还是 microVM？决策依据是什么？

决策依据不是"哪个更安全"，而是**即将执行的代码是谁写的，以及这个仓库的构建对文件访问和系统调用有多敏感**。

1. 编码负载的特征很特别：构建与测试是大量进程创建、海量小文件读写和密集路径查询。隔离层的开销不会均匀摊在算力上，而是精确落在最痛的地方——同样的资源配额，隔离方式不同，整套测试耗时可能差一个量级。
2. 进程级隔离（独立用户、资源限制、命名空间）文件访问性能最接近原生，适合第一方仓库：本来就要执行它的测试，等于已经信任这份代码，再叠一层重隔离收益有限。它的问题是边界脆弱，同宿主上不能混跑不同信任级别的任务。
3. 容器是默认选择，但选它的真实理由通常是工具链可复现而非安全——共享内核决定了它挡不住内核层面的问题。对第一方代码配上非特权运行、只读根文件系统与能力裁剪，性价比最高。
4. 用户态内核方案拦截系统调用换取更强边界，而编码负载恰好是系统调用密集型，开销会被放大；microVM 提供独立内核边界，代价是内存需按实例预留，且文件访问要穿过虚拟化存储路径，对大仓库构建不友好。二者更适合执行来源不明的代码，例如外部贡献者提交的变更。

按代码来源分级：第一方仓库与第一方依赖用加固容器；外部提交、来源不明的依赖树或多租户共宿主时升级到独立内核边界，并同时撤销凭证与出网。选型必须用同一个真实仓库跑基准：整套测试耗时相对原生的倍数、冷启动 P95、单节点可并发任务数，三项一起看才有意义。

**相关知识点：** 编码负载特征、小文件读写密集、进程级隔离、独立内核边界、代码来源分级、真实仓库基准对照。

### 7. Agent 需要完整工具链才能跑构建和测试，如何既保持隔离又不每次冷编译？

把环境与缓存分层——**工具链固化进镜像，依赖与编译产物放内容寻址缓存，工作区一次性**；三者的可变性和信任级别都不一样。

1. 工具链进镜像是为了可复现：编译器、运行时、系统库的版本变化会直接改变构建结果，让它们随任务动态安装等于每次执行的环境都不同，排查时无法区分"代码问题"还是"环境漂移"。代价是镜像更新频率受限于发布流程。
2. 依赖缓存挂载进来而不是打进镜像，因为它随仓库锁文件变化，节奏远快于镜像迭代。挂载方式选只读加本地可写覆盖：Agent 读得到已有条目，写入落在任务自己的层里、结束即丢弃，避免一次失败的安装污染全局。
3. 编译缓存的收益远大于依赖缓存，但只在缓存键真正捕获了全部输入时才成立。键里漏了编译器版本、环境变量或目标平台，就会出现"命中了但结果不对"——这类错误比不命中危险得多，因为它以构建成功的形式出现。
4. 预热要按仓库画像做，而不是笼统地热一个大镜像：把最常被执行的少数仓库的依赖树与基础产物预生成为快照，冷门仓库按需构建。命中率提升的边际收益随预热范围扩大迅速下降。

这套分层的隐含前提是构建本身确定；对存在不确定输入的构建，缓存复用会放大不稳定性，应先把构建变确定再谈复用。核心指标是缓存命中率、命中与未命中的耗时差，以及缓存导致的构建结果不一致次数——最后一项必须为零，一旦出现就立即停用相应缓存键。

**相关知识点：** 环境分层、镜像固化工具链、只读缓存加可写覆盖、缓存键输入完整性、假命中、按仓库画像预热。

### 8. 构建缓存跨任务复用会带来哪些污染与投毒风险？如何治理？

跨任务共享缓存等于把**一个任务的产物变成另一个任务的输入**；治理的核心是明确谁有权写缓存，而不是不断加强读取时的校验。

1. 最现实的风险不是攻击而是污染：一次失败的依赖安装留下半成品条目，一次非确定构建写入了带时间戳或本机路径的产物，后续任务读到后失败，且失败现象与真实原因完全脱节，排查成本极高。
2. 投毒路径是缓存键碰撞：如果键没有覆盖全部输入，攻击者只要构造一个键相同、内容不同的条目，就能让后续任何键相同的构建拿到它的产物。这条路径不需要突破沙箱，只需要一次写缓存的机会。
3. 因此写权限必须收紧：Agent 发起的构建默认只读缓存、不回写，条目由受信流水线在受控环境生成并签名。这会牺牲一部分命中率，但把"任意任务都能写全局缓存"这个最大敞口关掉了。
4. 分区同样重要：按仓库、按信任级别、按工具链摘要划分缓存命名空间，让外部提交触发的构建既读不到也写不进第一方分区。共享一个大缓存池省下的空间，通常不值得这份跨租户风险。

缓存是性能设施，不能承担正确性职责——发布用的产物应来自可复现的受控构建，而不是沙箱里恰好读到的缓存。治理效果用三项验证：缓存回写来源分布（应集中在受信流水线）、同一输入在启用与禁用缓存下的构建结果一致性抽检、以及缓存相关故障的平均定位耗时。

**相关知识点：** 产物即输入、缓存键碰撞、只读复用、受信写入方、缓存命名空间分区、构建结果一致性抽检。

### 9. 沙箱如何用可写层承载修改，并干净地导出变更？

可写层负责**回滚**，版本控制负责**导出**；用文件系统层面的差异直接生成补丁，几乎必然把构建产物混进去。

1. 覆盖式可写层的价值在于任意时刻能整体丢弃：底层保持只读基线，写入全部落在上层，任务失败时销毁上层即回到干净状态，比逐个撤销操作可靠得多。代价是修改一个大文件会触发整份拷贝，反复改动大文件的任务写入放大明显。
2. 但把上层内容直接当作"本次变更"是错的：依赖安装结果、编译产物、缓存、编辑器临时文件都在上层，而删除在覆盖式文件系统里是用特殊标记表达的，还需要额外翻译成删除操作。这些细节让文件系统差异既不准确也不易读。
3. 正确的导出路径是让仓库自己回答"改了什么"：在版本控制层生成差异并按忽略规则过滤；新增文件需要显式标记为待加入才会出现在差异里——漏掉这一步正是"Agent 说新建了文件，补丁里却没有"的典型原因。
4. 导出物要能被独立应用与审阅：绑定基线提交，二进制变更单独处理，超出规模阈值时不要硬生成一个巨大补丁，而应停下来报告——多数超大差异不是任务真的很大，而是某条过滤规则失效了。

可写层与版本控制差异各司其职，前者是安全网，后者是交付物。可验证的信号包括补丁能否在干净基线上无冲突应用、补丁中构建产物文件占比，以及丢弃上层后重跑同一任务能否得到一致结果——第三项不成立说明有状态漏到了可写层之外。

**相关知识点：** 覆盖式可写层、写时整份拷贝、删除标记翻译、待加入标记、基线提交绑定、补丁可应用性。
<a id="eng-212"></a>
### 10. 一个仓库同时包含多种语言运行时，沙箱如何避免镜像无限膨胀？

不要试图做一个装齐所有语言的巨型镜像——**镜像里应该只放这个仓库真正需要的运行时**，其余按需组合。

1. 巨型镜像的成本不只是体积：拉取耗时随体积线性增长且发生在每个冷节点上；任何一种语言的补丁都会让整个镜像失效并波及全部任务；包越多，漏洞扫描噪声与需要修补的面越大。它唯一的优点是省掉了"该装什么"的判断。
2. 需要哪些运行时应从仓库本身推导，而不是让任务描述来声明：依赖清单、构建配置与版本声明文件已经写明了语言与版本。推导结果要缓存并随基线失效，否则每次都重新扫描大仓库本身就成了新开销。
3. 组合方式上，把语言运行时做成可挂载的只读层比重建镜像更省：同一个运行时版本被多个仓库共享，节点上只存一份。代价是需要一套按版本寻址的存储与挂载编排，小规模团队未必划算。
4. 承认长尾的存在：极少数仓库需要冷门运行时，为它们保留"启动时从内部源安装"的降级路径，接受更慢的准备耗时，而不是把冷门运行时塞进公共基础镜像去照顾百分之一的场景。

判断做得好不好，看镜像数量与体积是否稳定、按仓库推导出的运行时集合与实际构建所需是否一致（不一致会直接表现为构建失败），以及冷节点镜像拉取的 P95 耗时。推导错误率居高不下说明仓库缺少可靠声明文件，应先补齐声明而不是继续加大镜像。

**相关知识点：** 镜像体积成本、运行时集合推导、版本声明文件、可挂载只读运行时层、按版本寻址、长尾降级路径。
<a id="eng-213"></a>
### 11. 沙箱内安装依赖需要出网，如何避免出网策略变成任意外联通道？

把出网做成**分阶段的能力**而不是沙箱的常驻属性——依赖安装阶段放行且只通向制品源，之后的构建、测试与推理阶段一律断网。

1. 分阶段的理由来自攻击目标：注入与恶意依赖的最终目的通常是把仓库内容或凭证发出去，而这一步需要网络。安装结束即断网，等于把最大的暴露窗口压缩成一个短暂且可审计的阶段。
2. 按域名放行远远不够：加密隧道对代理不透明，允许连到某个主机就等于允许向该主机发送任意字节；而制品源本身允许任何人发布内容，"允许连制品源"并不意味着"只会下载可信内容"。放行清单控制的是连接对端，不是内容。
3. 因此代理要理解协议而不只是转发：只允许制品获取这一类请求，记录每次取了哪个包及其摘要，拒绝方法与路径不符合预期的请求。实现成本更高，但换来一条可审计的依赖获取记录，这也是事后定位投毒的唯一依据。
4. 别忘了旁路：直连的域名解析本身可以携带数据外传，云环境的实例元数据地址会在不需要任何凭证的情况下泄露身份。二者都要在网络层显式拒绝并只保留内部解析器，且不能依赖沙箱内的配置来实现——沙箱里的配置随时可能被改写。

这套设计的边界在于确实需要真实外网的集成测试，对它们应单独开辟受限环境而不是放宽通用沙箱。跟踪各阶段出网请求量（推理阶段应为零）、被拒绝连接的目的地分布，以及依赖获取记录的完整率；推理阶段出现外联尝试要按安全事件处理，而不是当成配置问题。

**相关知识点：** 分阶段出网能力、加密隧道不可见、放行清单局限、协议感知代理、解析请求外传、实例元数据旁路。
<a id="eng-214"></a>
### 12. 私有制品库如何接入沙箱？代理、镜像与直连各有什么风险？

三种接法的真正差别在**命名空间怎么合并、凭证放在哪里**，性能差异是次要的。

1. 拉取式代理把上游与内部包放在同一入口，好处是单一收口点、可缓存、可审计；风险在名称解析优先级——当一个内部包名在上游也存在时，若代理允许回落上游，攻击者只要在公共源发布同名且版本更高的包，就可能让沙箱装到它。内部命名空间必须显式排除上游解析，这条配错，其他防护都没用。
2. 完整镜像换来可复现与可离线，代价是同步策略与自身的安全维护：镜像滞后会让上游的修复进不来，而镜像本身也需要独立的漏洞情报与存储成本。它适合合规要求高、依赖集合稳定的场景。
3. 直连上游最简单，但每个沙箱都要持有上游凭证，失去统一审计点，也无法在依赖进入构建前做任何拦截。它只适合完全公开、不含内部包的场景。
4. 无论哪种接法，凭证的写入位置都是隐患：包管理器的认证配置常被写进工作目录，Agent 一次全量暂存就可能把它提交进仓库。认证信息应放在工作区之外，并把这类文件名纳入导出前的阻断规则。

接入方式按"是否存在内部包"与"能否接受上游滞后"两个问题选择，而无论选哪种，都要求依赖获取有统一记录。可验证的信号是内部包被上游同名包解析的次数（应恒为零，需要用构造用例主动测试）、依赖获取的审计覆盖率，以及提交前凭证文件扫描的命中数。

**相关知识点：** 拉取式代理、名称解析回落上游、同名包覆盖、完整镜像滞后、认证配置落盘、导出前阻断规则。
<a id="eng-215"></a>
### 13. 依赖安装脚本可以执行任意代码，沙箱如何限制这一步的权限？

依赖安装是**沙箱里最该收紧、实际却往往最宽松的一步**——它执行的是第三方代码，却常常与 Agent 共享同一套凭证和网络。

1. 先承认能力边界：多数生态的安装过程本身就设计成可执行代码，例如包声明的生命周期脚本，或从源码分发包构建时执行的构建脚本。关掉它们通常有开关，但会让需要本地编译的包直接失败；现实做法是以关闭为默认，维护一份必须放行的例外清单，并优先使用预编译产物避免触发本地构建。
2. 把安装拆成独立阶段执行，权限与后续阶段不同：不挂载版本控制凭证与云凭证，网络只通向制品源，文件系统只能写依赖目录。这样即使安装脚本被劫持，它也拿不到可用于横向移动的东西。
3. 阶段之间用产物传递而不是共享环境：安装阶段的输出是一棵依赖树，构建阶段以只读方式消费它。安装期间对环境做的任何改动——写配置、改环境变量、留下后台进程——都不会延续到后面。
4. 例外清单要有主人和复核周期，否则它会单调增长直到等同于全开。每次新增都应记录是哪个包、为什么必须、有没有预编译替代。

这些措施防的是安装期的即时危害，防不住依赖在运行期作恶，那属于供应链审查的范围。验证方式包括：安装阶段的出网目的地是否只有制品源、例外清单条目数与增长率，以及关闭脚本执行后构建失败的包分布——最后一项能直接量化例外清单的必要性，而不是靠主观判断。

**相关知识点：** 生命周期脚本、源码分发包构建、预编译产物优先、安装阶段权限收窄、产物传递、例外清单治理。
<a id="eng-216"></a>
### 14. 完全离线的沙箱可行吗？依赖预取与锁文件如何配合？

**构建与测试阶段可以完全离线，依赖解析阶段通常不能**；把这两件事分开，离线就从"做不到"变成默认状态。

1. 离线成立的前提是依赖集合确定，而锁文件正是这份确定性的载体：它固定版本并附带完整性校验值，因此可以提前把全部内容取到本地。没有锁文件、或锁文件与清单已经不一致的仓库，谈不上离线。
2. 锁文件覆盖不到的部分才是离线失败的真正来源：工具链本身、系统包、构建脚本里临时下载的二进制、测试用例访问的外部服务。这些不会出现在任何锁文件里，只能靠实际跑一遍离线构建把它们逼出来。
3. 因此把"离线跑一遍"当成常规检查而不是特殊场景：任何出网尝试都记录并失败，失败清单就是这个仓库的隐藏网络依赖列表。逐条消除后，离线才是可维持的状态而不是一次性成绩。
4. 预取粒度要与缓存键对齐：按锁文件哈希预取整棵依赖树，命中时零网络，未命中时明确降级到需要网络的路径，而不是让部分命中导致半在线半离线的模糊状态——那种状态下的失败最难复现。

Agent 主动新增依赖必然要联网解析，这条路径应显式保留并单独授权，产物是一份待评审的锁文件更新，而不是在沙箱里就地生效。核心指标是离线执行的任务占比、离线失败中归因于隐藏网络依赖的数量，以及锁文件更新从提出到评审通过的耗时。

**相关知识点：** 锁文件确定性、完整性校验值、隐藏网络依赖、离线回归检查、按锁哈希预取、锁文件更新评审。
<a id="eng-217"></a>
### 15. Agent 主动引入新依赖时，如何在沙箱内做供应链审查？

模型提出的依赖要按**与人类提交同等甚至更严的标准**审查，因为它多了一类人类很少犯的错误——凭印象写出一个并不存在的包名。

1. 幻觉包名是这个场景独有的风险：模型可能生成看似合理但从未发布的名称，而攻击者可以抢注这些被反复"想象"出来的名字，等着安装行为自己找上门。防线是先在内部制品源核对包是否真实存在且已被批准，未批准的一律不进构建。
2. 常规的抢注与近似名同样要查：与知名包仅差一个字符、连字符与下划线互换、作用域前缀被去掉，这些在字符串上很像，在信任上完全不同。用与已知包名的编辑距离做候选筛查，命中的强制人工确认。
3. 引入必要性优先于安全属性：先问依赖树里是否已有等价能力、这个包解决的问题是否只需几十行代码。绝大多数被拒绝的新依赖是因为不必要而不是因为不安全，把这一步前置能显著降低后续审查量。
4. 通过审查的包要固定版本与完整性校验值，并纳入常规的漏洞与许可证检查。审批结论绑定到具体版本，升级需要重新过一遍，否则审批就退化成对包名的一次性永久放行。

这套流程会让 Agent 无法在会话内完成"想装就装"，这是有意为之——依赖引入是长期负债，不适合按会话节奏决策。可采集的指标包括新增依赖的提议数与通过率、其中不存在或近似名的命中数，以及从提议到审查完成的耗时；通过率长期接近百分之百通常说明审查已流于形式。

**相关知识点：** 幻觉包名、抢注与近似名、编辑距离筛查、内部批准集、必要性前置、版本绑定审批。
<a id="eng-218"></a>
### 16. 沙箱内的 Git 凭证如何做到只能推特性分支、不能推主干？

这条限制**必须由服务端强制**；沙箱内的任何配置、钩子或包装脚本都在 Agent 可改写的范围内，不构成边界。

1. 令牌的作用域通常只能到仓库与操作类型这一粒度，很难直接表达"只能推某类分支名"。真正生效的约束来自服务端的分支保护与推送规则：拒绝直接推送受保护分支、禁止强制推送、要求经由合并请求，并按引用名模式限制可创建的引用。
2. 容易漏掉的引用不止主干：标签常常触发发布流水线，某些引用命名空间会影响评审展示或元数据。规则应按引用名前缀正向放行任务分支、其余默认拒绝，而不是逐条枚举需要保护的名字——枚举方式永远追不上新增的引用类型。
3. 凭证要与目标主机绑定：沙箱里可以随意添加一个新的远端地址并推到外部，如果凭证会被无差别地送给任何地址，它同时就是一条外传通道。凭证的提供方式应校验请求目标，并配合出网限制，让它只在预期对端可用。
4. 令牌要短时、单任务、可即时吊销，并与"谁批准了这次任务"关联。任务结束即失效，可以把泄漏影响窗口收敛到一次任务的时长，这比事后检测更可靠。

客户端的限制仍有价值，但价值在于减少误操作和给出更清晰的错误提示，不能当作安全控制。应主动用构造用例定期测试：从沙箱尝试推主干、强制推送、推标签、推到外部地址，四项必须全部被拒绝；把它们做成常规回归，任何一项通过都视为线上安全缺陷。

**相关知识点：** 服务端强制、分支保护与推送规则、引用名前缀放行、标签触发发布、凭证绑定目标主机、拒绝用例回归。
<a id="eng-219"></a>
### 17. 制品库与云服务凭证如何注入沙箱而不进入模型上下文？

判断标准很具体——**凭证要能被进程使用，但不能出现在任何会回流到上下文的文本里**；环境变量并不满足这个标准。

1. 环境变量常被误当成隔离手段，实际上沙箱里任何进程都能读到它们，Agent 也随时可以执行一条打印环境的命令，输出会原样进入上下文并被持久化到会话记录。它解决的是"不写进代码"，没解决"不进上下文"。
2. 更彻底的做法是让沙箱根本不持有凭证：请求经由本地代理转发，代理在出口注入认证信息。沙箱里的工具照常工作，但整个环境里不存在可被读出的密钥。代价是每种协议都要有对应的代理支持，覆盖不到的场景仍需回落到注入。
3. 必须注入时，用凭证助手这类按需取值的接口代替常驻变量，并让取值过程不产生可打印输出；文件形式的凭证放在工作区之外，避免被一次全量暂存带进提交。
4. 无论前面做得多好，都要在输出侧兜底：已知凭证值在进入上下文和写入日志前做匹配替换。这一层挡不住派生出来的临时凭据，但成本极低且能覆盖大量意外路径。

这套设计的验证不能靠人工检查配置，要靠主动探测——在沙箱内执行打印环境、读取配置文件、打印进程信息等一组用例，再检查会话记录里是否出现凭证特征。指标是探测用例的拦截率、会话记录扫描的命中数，以及走代理而非注入的请求占比。

**相关知识点：** 环境变量非隔离手段、出口代理注入、凭证助手按需取值、工作区外存放、输出侧匹配替换、主动探测用例。
<a id="eng-220"></a>
### 18. 集成测试需要真实凭证时，如何设计最小权限与短时效令牌？

优先级依次是**换环境、换身份、换时效**——先问能不能不用生产凭证，再谈把权限和有效期收窄。

1. 最有效的一步是把集成测试指向独立的测试租户，用合成数据而不是生产数据。在生产里靠精细权限保护真实数据既难以论证也难以维持，测试一旦需要读取真实记录，权限就会被一次次放宽。
2. 身份上用工作负载联合而不是长期密钥：沙箱出示可验证的身份凭据，换取一次性的短时凭证。密钥不落盘、不进配置，并且天然带上"哪个任务、哪次执行"的上下文，便于审计归因。
3. 有效期要与任务时长匹配：比任务短会让长测试中途失败，而无条件续期又把短时凭证退化回长期能力。折中是允许在任务仍处于活动状态时续期，同时给出绝对上限。
4. 权限范围除操作类型外还要限制资源命名：测试创建的资源统一带前缀，凭证只能操作带该前缀的资源，另有独立清理任务负责回收。有创建权限不等于有删除任意资源的权限，这条分离能挡住相当一部分连锁破坏。

这类凭证的风险随集成测试规模增长，需要定期复核而不是一次配好。可采集的指标包括仍在使用长期密钥的流水线数量（目标为零）、凭证有效期分布、超时未回收的测试资源数，以及测试身份触发的越权拒绝次数——最后一项长期恒为零反而值得怀疑权限是不是给宽了。

**相关知识点：** 独立测试租户、合成数据、工作负载联合、续期绝对上限、资源前缀约束、遗留资源回收。
<a id="eng-221"></a>
### 19. 如何防止密钥经由命令回显、日志和 Trace 泄漏出沙箱？

泄漏路径的共同点是**密钥曾以明文形式出现在某个"顺手记录下来"的地方**；治理要沿着记录链路做，而不只是在代码里避免打印。

1. 对 Coding Agent 而言最独特的一条路径是命令本身：模型构造的命令行会被完整记录进会话，如果它把密钥写成字面量而不是引用变量，密钥就直接进了上下文与审计记录。命令行还会出现在进程列表里，同宿主的其他任务可能读到。
2. 其次是输出侧：调试开关会回显展开后的命令，失败请求的报错常常带上完整地址与查询参数，异常堆栈可能包含请求头。这些都不是应用主动打印的，靠代码审查发现不了，只能在采集链路上过滤。
3. 链路数据同样要治理：跨度属性、请求头、请求体都可能带凭证。正确做法是属性按允许清单上报，而不是默认全采后再删——默认全采意味着新增字段自动泄漏，而删除规则永远滞后于字段新增。
4. 过滤要双管齐下：已知值精确匹配负责确定性，模式匹配负责覆盖未登记的凭证形态。两者都有代价，过度替换会让排查失去必要信息，因此替换后应保留可关联的指纹，让人能判断"是不是同一个值"而不知道值本身。

过滤必须发生在数据进入任何持久存储和回流上下文之前，事后清洗只能减少留存、不能撤回已经扩散的副本。验证靠定期注入诱饵密钥：在沙箱内以各种方式使用它，再到会话记录、日志与链路数据里检索，统计诱饵出现次数与首次出现位置，命中即定位到具体的采集环节。

**相关知识点：** 命令行字面量、进程列表可见性、调试回显、跨度属性允许清单、可关联指纹、诱饵密钥探测。
<a id="eng-222"></a>
### 20. 沙箱凭证泄漏后如何快速定位影响面并完成轮换？

响应速度取决于**事前有没有一份"凭证—签发方—使用方—轮换方式"的台账**；没有台账时，绝大部分时间会耗在确认这把钥匙到底谁在用。

1. 先算暴露窗口，起点是密钥进入任何可留存介质的时刻，而不是被检测到的时刻。会话记录、构建日志、链路数据、缓存的工具输出都是留存介质，起点通常比想象的早很多；用错起点会系统性低估影响面。
2. 影响面用凭证自身的访问记录来算：按凭证标识过滤窗口内的全部调用，看动作、目标资源与来源地址能否与已知任务一一对上。对不上的调用优先处理，而不是先去猜攻击者可能做了什么。
3. 轮换顺序取决于业务耐受度：能立即吊销的立即吊销，不能的先签发新凭证、切换使用方、再吊销旧的。这个顺序必须事前定好并演练过，事发时临时判断往往因为担心中断而拖延吊销。
4. 清理留存副本是最容易被跳过的一步：泄漏值可能已经进了会话记录、评测数据集或日志归档，不清理会让同一次泄漏在后续被反复重新发现，也可能被下游系统再次使用。

这类事件的能力必须靠演练验证，不能靠预案文档。可采集的指标是从检测到吊销完成的耗时、具备自动轮换路径的凭证占比、影响面评估所需时间，以及演练中发现的台账缺项数量——最后一项通常是真实事件里最大的时间黑洞。

**相关知识点：** 凭证台账、暴露窗口起点、按凭证标识回溯调用、吊销顺序预案、留存副本清理、轮换演练。
<a id="eng-223"></a>
### 21. Bash 命令允许清单为什么容易被绕过？管道、命令替换与转义如何处理？

根源是**用字符串匹配去约束一门可编程语言**：匹配器看到的词法单元，和 Shell 真正执行的东西不是一回事。

1. 组合结构直接打破了"一条命令"的假设：分隔符、逻辑连接、管道、命令替换、进程替换都能在一次输入里引出第二条命令，而只看开头那个词的匹配器完全看不见。要处理就必须真正解析语法结构，把每个会被执行的命令逐个取出来判断。
2. 即使解析正确，转义与展开仍会让文本与语义分离：反斜杠、引号、各种编码形式的字面量、变量间接引用、字段分隔符替换，都能拼出同一条命令的不同写法。匹配器在展开前判断，Shell 在展开后执行，这个时间差是结构性的。
3. 更根本的是，清单里放行的很多程序本身就能执行任意代码：解释器带一行脚本参数、构建工具的自定义任务、支持调用外部命令的文本处理工具、允许对每个匹配项执行命令的查找工具。放行了它们，等于放行了整个 Shell。
4. 因此现实定位是：允许清单用于降低误操作和给出可解释的拒绝理由，安全边界放在沙箱、文件系统与网络层。承认这一点之后设计会更诚实——与其把清单越写越复杂，不如假设 Shell 内可执行任意命令，再问"那样最坏会怎样"。

如果确实需要强约束，可行方向是不经 Shell、直接以参数数组执行一组受限工具，代价是失去管道与通配符，而编码任务对它们依赖很深。评估这类机制唯一有意义的方式是红队绕过测试：维护一个持续增长的绕过用例集，把绕过成功率而不是清单条目数当作指标。

**相关知识点：** 语法结构解析、命令替换、展开时间差、可执行任意代码的放行程序、边界下沉、参数数组执行。
<a id="eng-224"></a>
### 22. 如何在沙箱内判定一条命令是否高危？静态规则与模型判定如何配合？

分级的核心维度不是"命令看起来吓不吓人"，而是**影响是否越出沙箱、以及是否可逆**；两者共同决定该自动执行、该拦截还是该问人。

1. 越界优先于危险度：删掉沙箱里的依赖目录看着吓人却完全可逆，重装即可；而把变更强制推送到共享分支写入量很小，却会改写他人的历史。判定应先看作用对象在不在沙箱内，再看操作语义。
2. 可逆性要有具体依据：有没有基线或快照可回到、外部副作用能否补偿、是否会触发下游流水线。凡是说不清如何撤销的操作一律按不可逆处理，而不是凭经验判断"应该没事"。
3. 静态规则负责确定性与可审计：解析后按规则匹配，命中就是命中，能复现、能解释、能进回归测试。它的弱点是只覆盖枚举过的形态，对没见过的写法沉默。
4. 模型判定负责泛化，但它读的是可能被注入的内容、自身可被操纵，因此只能单向使用——允许把静态规则判为低危的提升为高危，不允许把静态高危降级放行。这样即使模型被诱导，最坏结果也只是多问几次人，而不是放过一条危险命令。

判定质量要用标注过的命令语料持续评测，同时看漏判和误判：漏判直接对应事故，误判抬高审批频率并诱发盲目点同意。还要跟踪人工审批的实际否决率——如果人几乎从不否决，说明阈值定低了，这道审批正在消耗信任却不产生价值。

**相关知识点：** 越界优先于危险度、可逆性依据、静态规则确定性、模型单向升级、标注命令语料、否决率信号。
<a id="eng-225"></a>
### 23. 沙箱的只读模式该覆盖哪些操作？它与审批模式如何切换？

只读必须按**副作用**定义而不是按工具名定义，否则最大的漏洞会大大方方留在里面——运行仓库里的代码。

1. 很多"读"操作其实会写：拉取远端会写入版本控制目录，装依赖会写盘，不少分析工具会生成缓存。真正的只读要在文件系统层强制，同时单独给出一小块临时可写空间，因为完全没有可写位置会让大量工具直接崩溃。
2. 最需要堵的是执行：跑构建或测试就是在执行仓库里的代码，而仓库内容可以是任意的。把"跑一下测试看看"当成只读模式的例外，等于取消了这个模式。真要执行，就该切换到有隔离和审批的模式。
3. 只读模式还应撤销凭证并断网，否则读到的敏感信息可以被发出去——只读限制的是写入本地，不是限制信息流出，这两件事经常被混为一谈。
4. 切换必须单向安全：从可写降到只读随时可以，从只读升到可写要重新授权，且触发条件不能来自 Agent 读到的内容。否则一段被注入的文档就能促使会话自己去申请提权。

只读模式的代价是 Agent 无法用执行来验证自己的结论，方案质量会下降，所以它适合审阅、排查与方案设计，不适合交付变更。可采集的信号包括只读会话中被拦截的写入与执行尝试次数、提权申请频率与通过率，以及只读模式下的任务完成率——完成率过低说明边界划得不实用，应重新界定而不是靠例外放行。

**相关知识点：** 按副作用定义只读、临时可写空间、执行即写入、断网与撤销凭证、单向安全切换、提权触发源限制。
<a id="eng-226"></a>
### 24. 审批点应该设在命令级、工具级还是任务级？

三者都不是答案，正确的位置是**效果边界**——沙箱内随便做，任何越出沙箱的效果才需要人来批。

1. 命令级审批的信息质量最高，但一次编码任务往往有几十上百步，人会迅速进入机械点同意的状态。这比不设审批更糟：它没拦住任何东西，却把责任转移给了那个点同意的人。
2. 工具级审批通常最没用："允许执行命令"这样的授权粒度既不说明会做什么，也不说明影响多大，等于用一次点击换取一整类能力。
3. 任务级审批批的是意图而不是效果。Agent 中途完全可能做出符合意图、但你绝不会同意的具体动作，而任务开始时没人能预见它。
4. 效果边界的好处是与编码工作流天然对齐：沙箱内的编辑、构建、测试全部自动进行，把最终差异作为审批对象呈现给人——这正是代码评审已有的习惯。审批要绑定到具体产物（差异内容及其基线），产物变化即失效，避免批准之后被替换。

审批的价值来自人真的看懂了被批的东西，因此要控制单次审批的规模，差异过大就先拆任务。可采集的信号包括审批通过率、从展示到决策的耗时分布（大量秒级决策就是走过场的证据），以及自动放行类别中的事故率。后者非零说明效果边界划错了，应把相应类别移出自动区，而不是把所有操作都加回审批。

**相关知识点：** 效果边界、审批疲劳、责任转移、意图与效果的差距、审批绑定产物、决策耗时分布。
<a id="eng-227"></a>
### 25. Agent 在沙箱内执行了破坏性操作，如何回滚工作区与外部副作用？

工作区的回滚是工程问题，外部副作用的回滚往往**不存在**；所以真正的设计目标是让破坏性操作尽量只发生在沙箱里。

1. 工作区侧不要指望 Agent 自己提交过：由外层在每次工具调用的边界做快照，内容寻址让未改动文件几乎不占额外空间，代价只是元数据。这样任何一步之后都能回到确切状态，而不是依赖记忆去反向操作。
2. 要区分可恢复与不可恢复的破坏：已经提交过的内容通常还能通过引用日志找回，而清除未跟踪与被忽略的文件是直接删盘，快照没覆盖就真的没了。这也正是快照必须包含未跟踪文件的原因。
3. 外部副作用按可逆性分三类：可撤销的（创建的资源、可回滚的写入）、可补偿的（发出的消息可再发一条更正）、不可逆的（已支付、已通知外部、已覆盖他人历史）。每一类事前就要写好对应动作，事后临时想办法通常来不及。
4. 不可逆的那一类只能靠事前拦住——它们正是应该落在审批与出网限制范围内的操作。把"反正能回滚"当作放宽执行权限的理由，是这个话题上最常见的误判。

恢复能力必须演练：定期在沙箱里故意执行破坏性操作，测量恢复所需时间以及恢复后测试是否仍然通过。指标包括工作区恢复耗时、快照覆盖率（是否含未跟踪文件）、有成文补偿方案的副作用类型占比，以及演练中被发现根本无法恢复的场景数量。

**相关知识点：** 调用边界快照、内容寻址存储、引用日志找回、未跟踪文件覆盖、副作用可逆性分类、恢复演练。
<a id="eng-228"></a>
### 26. 仓库里的 README、注释和 Issue 可能带注入指令，如何阻断它们触发命令执行？

难点在于**Coding Agent 的本职就是遵循仓库里的说明**——贡献指南要求提交前跑格式化是完全正当的，所以不能靠"忽略文件里的指令"来防。

1. 分界要落在能力而不是意图上：仓库内容可以影响 Agent 做什么，但不能扩大它能做什么。一段文档要求把某个目录打包发到外部地址，失败原因应该是出网被拒绝，而不是模型判断出这是坏指令。
2. 面向 Agent 的配置文件是最高危的一类，因为工具链本来就设计成会读取并遵循它们。它们应按代码对待：纳入评审、锁定来源，尤其不能从待评审分支、外部贡献者的提交或第三方目录里自动加载。评审外部变更时，被评审的变更本身就可能改写这些文件。
3. 来源要在上下文里结构化地标出，让"用户交代的任务"和"读到的内容"不可混淆。这不是安全边界，但能明显减少无意的混淆，成本也低。
4. 越权动作要求可追溯的依据：当某一步要执行越出沙箱的操作时，要求它能指向用户任务而不是某份被读取的文件；理由来自不可信内容就直接拒绝。

这些措施降低发生概率但不能归零，所以必须假设有一天模型会被说服，并保证那一刻它手上没有可造成损失的能力。验证靠常态化的注入用例集：把诱导指令埋进不同载体，统计诱导成功率以及被哪一层拦下；如果绝大部分拦截发生在模型自身的拒绝上，说明能力层还太宽松。

**相关知识点：** 本职即遵循说明、能力不可被内容扩大、Agent 配置文件即代码、来源结构化标注、依据可追溯、注入用例集分层统计。
<a id="eng-229"></a>
### 27. 依赖包元数据与第三方代码中的注入如何防范？

先做优先级判断——**执行第三方代码的风险远高于阅读它的文本**；如果安装脚本已经跑过，再纠结元数据里的诱导指令就有点本末倒置。

1. 元数据的注入面是那些会被原样送进上下文的自由文本：包描述、说明文档、报错字符串、发行说明。防法很直接——只提取结构化字段（名称、版本、校验值、许可证），自由文本不进上下文或严格截断，需要人判断时给人看。
2. Agent 调试时会读第三方源码，代码注释同样是载体。可行做法是标注这段内容的来源与信任级别、限制单次读入量，并在阅读第三方代码期间不放行任何越界动作——这个阶段本来也不需要它们。
3. 靠检测"指令样式"的过滤召回率很低：诱导可以写得完全像正常文档，例如以诊断为名要求打印某个环境变量。把它当降噪手段可以，当防线不行。
4. 真正的风险排序应当指导投入：优先关掉安装期的代码执行、优先切断出网，其次才是元数据过滤。反过来做的团队往往在过滤规则上投入很多，却对安装脚本毫无限制。

这一层的作用是减少上下文被污染的机会，最终仍要靠能力限制兜底。可采集的指标包括第三方来源内容在上下文中的占比、元数据自由文本的截断率，以及同一套注入用例在"仅阅读"与"允许安装"两种配置下的成功率对比——这个对比能直观说明投入该放在哪一侧。

**相关知识点：** 风险优先级排序、结构化字段提取、自由文本截断、来源与信任级别标注、指令样式检测召回率、配置对比实验。

### 28. CI 日志、测试输出和编译报错回填上下文时会引入什么风险？

这类内容最容易被当成"我们自己系统的输出"而默认可信，实际上它**大量由仓库内容和第三方依赖决定**，是一条外观可信的不可信通道。

1. 内容风险在于任何字符串都可能是攻击面：测试名称、断言消息、依赖打印的提示都可以由提交者控制，而它们出现在"构建失败原因"这种高权重位置，比藏在文档里更容易被采纳。
2. 泄漏风险同样现实：失败用例常常打印请求详情、环境信息或响应体，这些内容一旦回填上下文就进了会话记录并可能被长期留存。回填前必须过一遍与日志相同的脱敏规则，不能因为"只是给模型看"就跳过。
3. 体量风险最常被低估：完整日志动辄数十兆，按尾部截断恰好会丢掉最早的那个根因错误，模型于是围着连锁失败打转。更好的做法是走结构化产物——测试报告与编译诊断都有结构化形式，可以按失败项去重后取前若干条，而不是按字节截断文本。
4. 还有一类行为风险：以日志变绿为目标，模型可能改的是断言或跳过用例而不是缺陷本身。回填时应同时给出用例的判定标准，并在验收侧检查测试文件的改动。

把 CI 输出当作需要清洗和结构化的外部输入，而不是可信的系统消息。可采集的指标包括 CI 输出占上下文 Token 的比例、截断率、根因错误是否落在被送入的片段内（可用已知失败样本回归测试），以及修复变更中测试文件改动的占比——后者异常升高通常是绕过而不是修复。

**相关知识点：** 外观可信通道、提交者可控字符串、失败输出脱敏、结构化诊断产物、失败项去重取样、测试文件改动占比。

### 29. 工具返回值与 MCP Server 响应进入上下文前应做哪些过滤？

外部工具服务是**信任链里的第三方**，它的响应应按不可信输入处理；而且不只是响应，工具描述本身也是会被注入进提示词的内容。

1. 先做结构约束：按声明的模式校验，丢弃未声明字段，限制长度与嵌套深度。校验失败要显式报错而不是把原始内容塞进上下文——后者会让一个坏掉的服务直接变成任意文本注入通道。
2. 清洗控制字符与终端转义序列：这类内容可能在终端界面里制造与实际数据不符的显示效果，让人在审批时看到的和真实内容不一致。对以终端为主界面的编码工具，这是一条容易被忽略的欺骗路径。
3. 工具清单要固定并在变化时重新确认：描述文本会进入提示词，一个服务完全可以在获得批准之后修改自己的描述来改变模型行为。按内容哈希锁定清单、变更时要求重新批准，比只在接入时审一次可靠得多。
4. 来源与信任级别要随内容传递下去，让后续的越界判定能识别"这个建议来自外部服务"；同时限制单次返回在上下文中的占比，避免一个服务的输出淹没任务本身。

过滤越严，与快速演进的第三方服务的兼容性越差，所以模式要有版本并给出兼容窗口。可采集的指标包括模式校验失败率、响应体积分布、工具清单变更次数与重新批准耗时，以及外部来源内容在上下文中的 Token 占比；这几项一起看，能较早发现某个服务在悄悄变化。

**相关知识点：** 第三方信任链、响应模式校验、未声明字段丢弃、终端转义序列清洗、工具清单哈希锁定、模式版本兼容窗口。

### 30. 面向 Coding Agent 的注入防御如何做纵深分层？各层分别拦得住什么？

各层的强度差别很大——**能力层、出网层与人工评审是承重的，提示层与检测层只是降噪**；把投入压在后者是这个话题上最常见的错配。

1. 上下文层（来源标注、体量控制、结构化提取）降低模型被混淆的概率，成本低、收益确定，但对方只要写得足够自然就能穿过去，它拦不住有准备的攻击。
2. 能力层（工具最小化、不持有凭证、按阶段授予权限）是唯一在模型完全被说服后仍然成立的一层：被说服的模型也只能调用它已经拥有的东西。这一层的质量决定了最坏情况有多坏。
3. 出网层直接对着攻击目的：绝大多数注入最终要把数据发出去。默认拒绝、协议感知代理、封堵解析与元数据旁路，能把"注入成功"和"造成损失"这两件事分开。
4. 交付层是变更进入代码库的最后一道：即使前面全被穿透，一个恶意改动仍需通过评审与测试。它的短板是人对大体量差异的审阅质量急剧下降，所以必须配合差异规模上限与必过的检查项。
5. 检测与审计层不阻止任何事，作用是缩短从发生到发现的时间，并在事后提供可追溯的证据链，价值全部体现在响应速度上。

分层的意义在于任何单层失效都不致命，因此评估必须逐层做而不是只看端到端通过率：把上面的层依次关闭，测量每一层单独的拦截能力，才知道哪一层实际在承重。指标包括分层拦截率、注入用例的端到端成功率、从注入发生到被发现的耗时，以及自动放行路径上的事故数。

**相关知识点：** 分层强度不均、上下文层降噪、能力层承重、出网层切断目的、交付层评审、逐层消融评估。
