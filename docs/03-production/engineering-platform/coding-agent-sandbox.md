### 1. 把仓库送进沙箱有哪些方式？完整 clone、工作树快照与只读挂载如何取舍？

三种方式的差别不在快慢，而在**沙箱有没有独立对象库、构建往源码树写回时会污染谁**。

1. 完整 clone 语义最干净：沙箱有独立的对象库与 reflog，`git bisect`、行级追溯与 merge-base 都成立。它的磁盘代价常被高估——从宿主 bare mirror 本地 `git clone`，对象默认是硬链接而非拷贝，随并发线性增长的只有工作目录；代价换成了耦合：源镜像并发 gc 或 repack 会破坏已有克隆，打包窗口必须与克隆窗口错开。
2. 从本地镜像派生 worktree 快照最省时间：对象库共享、只写一份工作目录；但共享意味着沙箱对版本控制目录的写入会波及其他任务，且分支占用是全局的——同一分支不能同时在两个工作树里检出。
3. 只读挂载宿主检出目录再叠一层 overlayfs 可写层，准备近似零耗时；但构建会往源码树里写文件（编译产物、缓存、生成代码），这些写入落在上层，导出时必须显式排除，否则改两行会变成上千文件的差异。
4. 三者的失败模式不同：完整 clone 卡在工作目录写盘与源镜像的 gc 窗口，worktree 快照卡在并发耦合，只读挂载卡在"宿主检出被谁改过"——那是跨任务共享的可变状态，一旦有任务绕过上层写入，后续基线就不再可信。

选型按"任务是否需要历史"乘"构建是否写源码树"两维决定；执行外部贡献者代码一律用独立 clone。指标是准备阶段 P95 耗时、每任务工作目录占用、导出差异中构建产物占比——最后一项偏高说明挂载方式与忽略规则没配对。

**相关知识点：** bare mirror、`git clone` 硬链接、gc 与 repack、merge-base、reflog、overlayfs 可写层。

### 2. 多个 Coding Agent 并行修改同一仓库时，如何用 Git worktree 做工作区隔离？

worktree 的隔离粒度是**工作目录与索引，而不是引用和对象库**；并行是否安全取决于有没有把共享的那一半也划清。

1. 每个任务分配独立工作树并直接切到 detached HEAD，而不是先建分支再检出：分支一旦在某个工作树里被检出，其他工作树就无法再检出同一分支，任务重试或复用时会撞上它；detached HEAD 把"任务基于哪个提交"与"分支归谁"解耦。
2. index 与 HEAD 每工作树独立，所以并行暂存和提交互不干扰；但 refs 命名空间、`git stash` 栈与钩子目录是共享的——多个 Agent 同时写同名临时引用或用 stash 传状态就会互相覆盖。约定用带任务标识前缀的 refs 名，并禁止把 stash 当跨步骤存储。
3. 共享对象库省的是磁盘而不是构建时间：工作目录各自独立，依赖目录与编译产物这类未跟踪内容每个工作树都要重新生成，这往往才是准备阶段的大头。要么给依赖目录挂只读缓存，要么接受首次构建慢。
4. 回收必须显式做：直接删目录会在 `.git/worktrees` 里留下悬空登记项，之后创建同名工作树会失败；任务结束应按顺序移除工作树、清理任务 refs，并定期跑 `git worktree prune` 收敛残留。

worktree 适合同一仓库、同一基线、互不冲突的并行改动；跨基线或需要不同子模块状态时独立 clone 更省心。监控并行度、工作树创建失败率与残留数量，并用"两个任务同时跑时各自的测试通过率是否与单跑一致"作为隔离成立的回归检查。

**相关知识点：** Git Worktree、detached HEAD、refs 命名空间共享、`git stash`、`git worktree prune`。

### 3. 超大仓库如何用稀疏检出与浅克隆压缩沙箱准备时间？

两者压缩的维度不同——**浅克隆砍历史深度，稀疏检出砍工作目录宽度**；砍错维度会破坏编码任务依赖的操作。

1. 浅克隆（shallow clone）省的是对象传输，代价是历史不完整：求 merge-base、行级追溯、用 `git bisect` 定位引入缺陷的提交都会失败或给出错误答案。Coding Agent 高频用这些操作解释"这行为什么是这样"，所以它适合只跑构建与测试的验证型沙箱，不适合探索型任务。
2. 按需拉取文件内容的 partial clone（`blob:none` 过滤）更贴合编码场景：提交图完整，merge-base 与历史遍历仍成立，只有被读的文件才拉取。风险是访问模式一旦发散（例如跨历史全量检索），惰性拉取的往返会让总耗时超过一次完整克隆。
3. 稀疏检出（sparse checkout）按 cone 模式裁剪工作目录，只有选定路径下的文件才写盘，对多语言巨型仓库收益最大；但构建系统看到的是残缺的树，依赖分析会把缺失目录当成被删除，或找不到被引用的模块。裁剪范围必须由构建图推出，不能凭任务描述猜。
4. 两种裁剪都会让"Agent 找不到东西"这个信号变得含混：究竟是没检索到，还是文件根本没落盘。要在沙箱里暴露裁剪清单，让读取被裁掉的路径直接报错，而不是静默返回不存在。

先测量准备阶段耗时的构成再决定裁什么：多数超大仓库的瓶颈在工作目录写盘与依赖安装，不是对象传输。用准备耗时 P95、按需拉取往返次数、构建首次成功率一起看，任一项因裁剪恶化就说明裁过头。

**相关知识点：** shallow clone、partial clone、sparse checkout、git bisect、merge-base。

### 4. 子模块、Git LFS 和生成物目录在沙箱里应该如何处理？

这三类内容都不在主仓库对象里，却**决定构建能不能跑通**；沙箱要逐类明确取或不取，默认全取和全不取都会出事。

1. 子模块在主仓库里只是一条 gitlink，需按 `.gitmodules` 单独初始化。凭证或协议不匹配会显式报错、非零退出，反而好查；真正静默的是**根本没初始化**：目录空着、工作树干净，直到构建后段才抛出与真实原因无关的错误。不触及的任务保持 gitlink 原样，但构建入口要对空目录报错。
2. 提交阶段的风险在另一侧：**已初始化但停在非记录提交、或整个目录被删掉的子模块**。前者让一次全量暂存把 gitlink 换成谁也没想推的新 SHA，后者把它记为删除，两者在补丁里都只是一行 SHA，评审看不出影响。未初始化的空目录反而最安全，全量暂存根本不碰 gitlink。导出前应单独比对 gitlink。
3. Git LFS 内容由 smudge 过滤器在检出时下载：全量拉取让准备耗时被少数大文件支配，跳过下载则留下 LFS 指针文件，构建读到文本而非二进制，报错与真实原因无关。折中是默认跳过、按路径选择性拉取，并让读到指针时明确报错。
4. 生成物目录靠 `.gitignore` 排除在版本控制外，但忽略不等于隔离：Agent 仍能读写，构建也会往里写。它们应由缓存承载、不随工作区走，导出时按同一份规则过滤，否则一次依赖安装就撑爆补丁。

把三类内容做成准备阶段的显式清单，每项记录取或不取及原因。监控子模块初始化失败率、LFS 下载占准备耗时的比例、导出补丁被过滤掉的文件数——最后一项升高说明忽略规则失效。

**相关知识点：** gitlink、`.gitmodules`、Git LFS 指针文件、smudge 过滤器。

### 5. 沙箱工作区的生命周期如何定义？何时可以复用、何时必须销毁重建？

把工作区当成**带显式缓存键的缓存**而不是长期存在的开发机；复用的前提是能证明状态，证明不了就销毁。

1. 缓存键至少包含仓库、基线提交、工具链镜像摘要与 lockfile 哈希，任一变化即视为未命中。凭"目录还在就接着用"的复用方式会把上一个任务的环境变更悄悄带进下一个任务，而失败现场往往在几十个任务之后才暴露。
2. 常见的复用判据是"版本控制状态干净"，但这个信号覆盖不到真正的污染源：被忽略的目录、全局包缓存、临时目录、上个任务装的系统包、残留的后台进程、被改过的环境变量。它能证明源码树干净，不能证明环境干净。
3. 必须销毁重建的情形要写成硬规则：执行过外部不可信代码且有过出网、注入过凭证、工具链或基础镜像更新、发生过越权或破坏性操作、任务以未知状态失败。这几类的共同点是"污染是否发生"无法低成本判定，此时销毁比排查便宜。
4. 销毁工作区不等于销毁缓存，切分标准是这份状态能否被一个键完整描述：依赖包与编译产物按 content-addressable storage 存放，同一个键必然对应同一份字节，可以跨任务长期留存；工作区、后台进程、临时目录与注入的凭证描述不了，只能随任务一起消失。

复用是性能优化而非默认语义，出现任何歧义都应向销毁一侧倾斜。验证方式是定期抽样对照——同一任务分别在复用工作区与全新工作区各跑一遍，比较首次测试通过率与构建耗时；通过率出现系统性差异就说明复用池已被污染，此时应整体清空而不是逐个排查。

**相关知识点：** 工作区缓存键、lockfile 哈希、镜像摘要、content-addressable storage、强制重建规则、复用对照抽样。

### 6. 编码任务的沙箱该选进程隔离、容器还是 microVM？决策依据是什么？

决策依据不是"哪个更安全"，而是**代码是谁写的、这个仓库的构建对文件访问和系统调用有多敏感**。

1. 编码负载的特征很特别：构建与测试是大量进程创建、海量小文件读写与密集路径查询。隔离层的开销不会均匀摊在算力上，而是精确落在最痛的地方——同样配额下，隔离方式不同，整套测试耗时可能差一个量级。
2. 进程级隔离（独立用户、cgroup 配额、Linux namespace）文件访问性能最接近原生，适合第一方仓库：本来就要跑它的测试，等于已经信任这份代码，再叠重隔离收益有限。问题是边界脆弱，同宿主不能混跑不同信任级别的任务。
3. 容器是默认选择，但真实理由通常是工具链可复现而非安全——共享内核决定了它挡不住内核层面的问题。对第一方代码配上非特权运行、只读根文件系统、seccomp 与 capabilities 裁剪，性价比最高。
4. gVisor 这类用户态内核靠拦截系统调用换取更强边界，而编码负载恰是系统调用密集型，开销被放大；Firecracker 这类 microVM 提供独立内核边界，代价是内存按实例预留，文件访问要穿过虚拟化存储路径，对大仓库构建不友好。二者更适合来源不明的代码，例如外部贡献者的提交。

按代码来源分级：第一方仓库与依赖用加固容器；外部提交、来源不明的依赖树或多租户共宿主时升级到独立内核边界，并同时撤销凭证与出网。选型必须用同一个真实仓库跑基准：整套测试耗时相对原生的倍数、冷启动 P95、单节点并发数，三项一起看才有意义。

**相关知识点：** gVisor、Firecracker、microVM、seccomp、Linux capabilities、cgroup、代码来源分级。

### 7. Agent 需要完整工具链才能跑构建和测试，如何既保持隔离又不每次冷编译？

把环境与缓存分层——**工具链固化进镜像，依赖与编译产物进内容寻址缓存，工作区一次性**；三者的可变性与信任级别都不同。

1. 工具链进镜像是为了可复现：编译器、运行时、系统库的版本变化直接改变构建结果，随任务动态安装等于每次的环境都不同，排查时无法区分"代码问题"还是"环境漂移"。代价是镜像更新受限于发布流程。
2. 依赖缓存挂载进来而不打进镜像，因为它随 lockfile 变化，节奏远快于镜像迭代。挂载形态用 overlayfs：全局缓存做 lowerdir 只读，任务的 upperdir 承接全部写入、结束即丢弃。这样 Agent 读得到已有条目，一次中断或损坏的安装只污染自己那一层，不会让下一个任务继承半成品；代价是并行任务各留一份 upperdir，必须随任务回收。
3. 编译缓存的收益很不均：**对编译型语言的仓库**它远大于依赖缓存，而 Node、Python、Ruby 这类仓库的准备耗时由依赖安装主导，编译缓存几乎无收益，该先投依赖缓存。缓存键必须覆盖编译器版本、目标平台与构建参数，漏一项拿到的就是错误产物。
4. 预热要按仓库画像做，而不是笼统热一个大镜像：把最常执行的少数仓库的依赖树与基础产物预生成快照，冷门仓库按需构建。命中率的边际收益随预热范围扩大迅速下降。

这套分层的前提是构建本身确定；对存在不确定输入的构建，缓存复用会放大不稳定性，应先把构建变确定再谈复用。核心指标是缓存命中率、命中与未命中的耗时差、缓存导致的构建结果不一致次数——最后一项必须为零，出现即停用相应缓存键。

**相关知识点：** 镜像固化工具链、overlayfs upperdir、lockfile 哈希、编译缓存键、按仓库画像预热。

### 8. 构建缓存跨任务复用会带来哪些污染与投毒风险？如何治理？

跨任务共享缓存等于把**一个任务的产物变成另一个任务的输入**；治理核心是明确谁有权写缓存，而不是不断加强读取时的校验。

1. 最现实的风险不是攻击而是污染：一次失败的依赖安装留下半成品条目，一次非确定构建写入带时间戳或本机路径的产物，后续任务读到即失败，现象与真实原因脱节，排查成本极高。
2. 投毒走的是缓存键碰撞（cache poisoning）：键是构建输入的摘要，一旦没覆盖全部输入——编译器版本、环境变量、目标平台、构建参数——攻击者只要先写入一个键相同、内容不同的条目，后续所有算出同一个键的构建都会跳过编译直接取走它。这条路径不需要突破沙箱，只需一次写缓存的机会，而且它以"构建成功"的形式出现，读取侧校验看不出异常。
3. 因此治理点在写入方而不在读取方：全局条目只接受受信流水线在受控环境生成的产物，并附带可验证的来源证明——谁、基于哪个提交、在哪个环境构建，消费前校验签名。Agent 发起的构建不获得全局写权限，这牺牲一部分命中率，但关掉了"任意任务都能写全局缓存"这个最大敞口。
4. 分区同样重要：按仓库、信任级别、工具链摘要划分缓存命名空间，让外部提交触发的构建既读不到也写不进第一方分区。共享大缓存池省下的空间不值得这份跨租户风险。

缓存是性能设施，不承担正确性职责——发布产物应来自可复现的受控构建，而不是沙箱里恰好读到的缓存。治理效果用三项验证：缓存回写来源分布（应集中在受信流水线）、同一输入在启用与禁用缓存下的结果一致性抽检、缓存故障的平均定位耗时。

**相关知识点：** cache poisoning、缓存键碰撞、可复现构建、构建来源证明、缓存命名空间分区、supply chain。

### 9. 沙箱如何用可写层承载修改，并干净地导出变更？

可写层负责**回滚**，版本控制负责**导出**；用文件系统差异直接生成补丁，几乎必然把构建产物混进去。

1. overlayfs 这类联合文件系统的价值在于任意时刻能整体丢弃：lowerdir 保持只读基线，写入全部落进 upperdir，任务失败时销毁 upperdir 即回到干净状态，比逐个撤销操作可靠得多。代价是 copy-up——改动一个大文件会先把它整份拷到上层，反复改大文件的任务写入放大明显。
2. 但把 upperdir 内容直接当作"本次变更"是错的：依赖安装结果、编译产物、缓存、编辑器临时文件都在上层，而删除在 overlayfs 里由 whiteout 标记表达，还要额外翻译成删除操作。这让文件系统差异既不准确也不易读。
3. 正确的导出路径是让仓库自己回答"改了什么"：在版本控制层生成差异并按忽略规则过滤；新增文件要用 `git add -N`（intent-to-add）显式标记才会出现在 `git diff` 里——漏掉这一步正是"Agent 说新建了文件，补丁里却没有"的典型原因。
4. 导出物要能被独立应用与审阅：绑定基线提交，二进制变更单独处理，超出规模阈值时不要硬生成巨大补丁，而应停下来报告——多数超大差异不是任务真的大，而是某条过滤规则失效了。

可写层与版本控制差异各司其职，前者是安全网，后者是交付物。可验证的信号包括补丁能否在干净基线上无冲突应用、补丁中构建产物占比、丢弃上层后重跑同一任务能否得到一致结果——第三项不成立说明有状态漏到了可写层之外。

**相关知识点：** overlayfs、lowerdir 与 upperdir、whiteout、copy-up、`git add -N`、基线提交绑定。
<a id="eng-212"></a>
### 10. 一个仓库同时包含多种语言运行时，沙箱如何避免镜像无限膨胀？

不要试图做一个装齐所有语言的巨型镜像——**镜像里应该只放这个仓库真正需要的运行时**，其余按需组合。

1. 巨型镜像的成本不只是体积：拉取耗时随体积线性增长且发生在每个冷节点上；任何一种语言的补丁都会让底层 OCI 镜像层失效并波及全部任务；包越多，CVE 扫描噪声与需要修补的面越大。它唯一的优点是省掉了"该装什么"的判断。
2. 需要哪些运行时应从仓库本身推导，而不是让任务描述来声明：`package.json`、`pyproject.toml`、`go.mod` 这类清单已经写明了语言与版本。推导结果要缓存并随基线失效，否则每次重新扫描大仓库本身就成了新开销。
3. 组合方式上，把语言运行时做成可挂载的只读层比重建镜像更省：同一个运行时版本被多个仓库共享，节点上只存一份。代价是需要一套按摘要寻址的存储与挂载编排，小规模团队未必划算。
4. 承认长尾的存在：极少数仓库需要冷门运行时，为它们保留"启动时从内部源安装"的降级路径，接受更慢的准备耗时，而不是把冷门运行时塞进公共基础镜像去照顾百分之一的场景。

判断做得好不好，看镜像数量与体积是否稳定、按仓库推导出的运行时集合与实际构建所需是否一致（不一致会直接表现为构建失败），以及冷节点镜像拉取的 P95 耗时。推导错误率居高不下说明仓库缺少可靠声明文件，应先补齐声明而不是继续加大镜像。

**相关知识点：** OCI 镜像层、CVE 扫描面、运行时集合推导、版本声明文件、只读运行时挂载层、按摘要寻址、长尾降级路径。
<a id="eng-213"></a>
### 11. 沙箱内安装依赖需要出网，如何避免出网策略变成任意外联通道？

把出网做成**分阶段的能力**而不是沙箱的常驻属性——依赖安装阶段放行且只通向制品源，之后的构建、测试与推理阶段一律断网。

1. 分阶段的理由来自攻击目标：注入与恶意依赖的最终目的通常是把仓库内容或凭证发出去，而这一步需要网络。安装结束即断网，等于把最大的暴露窗口压缩成一个短暂且可审计的阶段。
2. 按域名放行远远不够：TLS 隧道对代理不透明，允许连到某个主机就等于允许向该主机发送任意字节；而制品源本身允许任何人发布内容，"允许连制品源"并不意味着"只会下载可信内容"。放行清单控制的是连接对端，不是内容。
3. 因此代理要理解协议而不只是转发：只允许制品获取这一类请求，记录每次取了哪个包及其摘要，拒绝方法与路径不符合预期的请求。实现成本更高，但换来一条可审计的依赖获取记录，这也是事后定位投毒的唯一依据。
4. 别忘了旁路：DNS 查询本身就能把数据带出去（DNS exfiltration），云环境的实例元数据服务 IMDS 会在不需要任何凭证的情况下泄露身份。二者都要在网络层显式拒绝并只保留内部解析器，且不能依赖沙箱内的配置来实现——沙箱里的配置随时可能被改写。

这套设计的边界在于确实需要真实外网的集成测试，对它们应单独开辟受限环境而不是放宽通用沙箱。跟踪各阶段出网请求量（推理阶段应为零）、被拒绝连接的目的地分布，以及依赖获取记录的完整率；推理阶段出现外联尝试要按安全事件处理，而不是当成配置问题。

**相关知识点：** egress 分阶段授权、TLS 隧道不可见、协议感知代理、DNS exfiltration、IMDS、默认拒绝出网。
<a id="eng-214"></a>
### 12. 私有制品库如何接入沙箱？代理、镜像与直连各有什么风险？

三种接法的真正差别在**命名空间怎么合并、凭证放在哪里**，性能差异是次要的。

1. 拉取式代理（pull-through cache）把上游与内部包放在同一入口，好处是单一收口点、可缓存、可审计；风险在名称解析优先级——内部包名在上游也存在时，若代理允许回落上游，攻击者只要在公共源发布同名且版本更高的包就可能让沙箱装到它，这就是 dependency confusion。内部命名空间必须显式排除上游解析，这条配错其他防护都没用。
2. 完整镜像换来可复现与可离线，代价是同步策略与自身的安全维护：镜像滞后会让上游的修复进不来，而镜像本身也需要独立的漏洞情报与存储成本。它适合合规要求高、依赖集合稳定的场景。
3. 直连上游最简单，但每个沙箱都要持有上游凭证，失去统一审计点，也无法在依赖进入构建前做任何拦截。它只适合完全公开、不含内部包的场景。
4. 无论哪种接法，凭证的写入位置都是隐患：包管理器的认证配置（`.npmrc`、`.pypirc`）常被写进工作目录，Agent 一次全量暂存就可能把它提交进仓库。认证信息应放在工作区之外，并把这类文件名纳入导出前的阻断规则。

接入方式按"是否存在内部包"与"能否接受上游滞后"两个问题选择，而无论选哪种，都要求依赖获取有统一记录。可验证的信号是内部包被上游同名包解析的次数（应恒为零，需要用构造用例主动测试）、依赖获取的审计覆盖率，以及提交前凭证文件扫描的命中数。

**相关知识点：** dependency confusion、pull-through cache、私有命名空间排除上游、镜像滞后、`.npmrc` 落盘、导出前阻断规则。
<a id="eng-215"></a>
### 13. 依赖安装脚本可以执行任意代码，沙箱如何限制这一步的权限？

依赖安装是**沙箱里最该收紧、实际却最宽松的一步**——它执行第三方代码，却常与 Agent 共享凭证和网络。

1. 先承认能力边界：多数生态的安装过程本身就设计成可执行代码，例如 npm 的 lifecycle script，或从 sdist 构建时执行的 `setup.py`。关掉通常有开关（`--ignore-scripts`），但会让需要本地编译的包直接失败；现实做法是以关闭为默认，维护一份必须放行的例外清单，并优先取 wheel 等预编译产物。
2. 安装必须作为独立阶段执行，且权限与后续阶段不同：用独立的低权限用户和独立的 `HOME` 跑——包管理器常把凭证与配置写进 `$HOME`，共用等于把它们摊给第三方脚本；同时不挂载版本控制与云凭证，文件系统只能写依赖目录，网络只通制品源。这样即使安装脚本被劫持，也拿不到可用于横向移动的东西。
3. 阶段之间用产物传递而不是共享环境：安装阶段的输出是一棵依赖树，构建阶段只读消费它。安装期间对环境的任何改动——写配置、改环境变量、留后台进程——都不会延续到后面。
4. 例外清单要有主人和复核周期，否则它会单调增长直到等同于全开。每次新增应记录哪个包、为什么必须、有无预编译替代。

这些措施防的是安装期的即时危害，防不住依赖在运行期作恶，那属于供应链审查范围。验证方式包括：安装阶段的出网目的地是否只有制品源、例外清单条目数与增长率、关闭脚本执行后构建失败的包分布——最后一项能直接量化例外清单的必要性，而非靠主观判断。

**相关知识点：** npm lifecycle script、sdist 与 wheel、`--ignore-scripts`、独立低权限用户、产物传递、例外清单治理。
<a id="eng-216"></a>
### 14. 完全离线的沙箱可行吗？依赖预取与锁文件如何配合？

离线**不是网络策略问题，而是依赖集合的确定性问题**：lockfile 完整且与清单一致，离线就成立；否则再严的网络策略也只是把失败从解析期推迟到执行期。

1. lockfile 固定版本并附带 integrity 校验值，因此整棵依赖树可以在受控环境预取、vendoring 到本地，而校验值保证离线取回的字节与联网时一致——这才是离线可信的基础。锁文件与清单不一致的仓库要先修一致性，否则安装会静默回落到联网解析。
2. lockfile 覆盖不到的部分才是离线失败的真正来源：工具链本身、系统包、构建脚本里临时下载的二进制、测试用例访问的外部服务。这些不会出现在任何锁文件里，只能靠实际跑一遍离线构建把它们逼出来。
3. 因此把"离线跑一遍"当成常规检查而不是特殊场景：任何出网尝试都记录并失败，失败清单就是这个仓库的隐藏网络依赖列表。逐条消除后，离线才是可维持的状态而不是一次性成绩。
4. 预取粒度要与缓存键对齐：按 lockfile 哈希预取整棵依赖树，命中时零网络，未命中时明确降级到需要网络的路径，而不是让部分命中导致半在线半离线的模糊状态——那种状态下的失败最难复现。

Agent 主动新增依赖必然要联网解析，这条路径应显式保留并单独授权，产物是一份待评审的锁文件更新，而不是在沙箱里就地生效。核心指标是离线执行的任务占比、离线失败中归因于隐藏网络依赖的数量，以及锁文件更新从提出到评审通过的耗时。

**相关知识点：** lockfile、integrity 校验值、vendoring 预取、隐藏网络依赖、离线回归检查、锁文件更新评审。
<a id="eng-217"></a>
### 15. Agent 主动引入新依赖时，如何在沙箱内做供应链审查？

模型提出的依赖要按**与人类提交同等甚至更严的标准**审查，因为它多了一类人类很少犯的错误——凭印象写出一个并不存在的包名。

1. 幻觉包名是这个场景独有的风险：模型可能生成看似合理但从未发布的名称，攻击者只要抢注这些被反复"想象"出来的名字（业界称 slopsquatting），就能等着安装行为自己找上门。防线是先在内部制品源核对包是否真实存在且已被批准，未批准的一律不进构建。
2. 常规的 typosquatting 同样要查：与知名包仅差一个字符、连字符与下划线互换、作用域前缀被去掉，这些在字符串上很像，在信任上完全不同。用与已知包名的 Levenshtein 距离做候选筛查，命中的强制人工确认。
3. 引入必要性优先于安全属性：先问依赖树里是否已有等价能力、这个包解决的问题是否只需几十行代码。绝大多数被拒绝的新依赖是因为不必要而不是因为不安全，把这一步前置能显著降低后续审查量。
4. 通过审查的包要固定版本与 integrity 校验值，登记进 SBOM，并纳入常规的漏洞与许可证检查。审批结论绑定到具体版本，升级需要重新过一遍，否则审批就退化成对包名的一次性永久放行。

这套流程会让 Agent 无法在会话内完成"想装就装"，这是有意为之——依赖引入是长期负债，不适合按会话节奏决策。可采集的指标包括新增依赖的提议数与通过率、其中不存在或近似名的命中数，以及从提议到审查完成的耗时；通过率长期接近百分之百通常说明审查已流于形式。

**相关知识点：** typosquatting、slopsquatting、幻觉包名、Levenshtein 距离筛查、SBOM、版本绑定审批。
<a id="eng-218"></a>
### 16. 沙箱内的 Git 凭证如何做到只能推特性分支、不能推主干？

这条限制**必须由服务端强制**；沙箱内的 Git 配置、client-side hook 或包装脚本都在 Agent 可改写的范围内，不构成边界。

1. 令牌的作用域通常只能到仓库与操作类型这一粒度，很难直接表达"只能推某类分支名"。真正生效的约束来自服务端的 branch protection 与 push rules：拒绝直接推送受保护分支、禁止强制推送、要求经由合并请求，按 refs 名模式限制可创建的引用，必要时用 pre-receive hook 兜底。
2. 容易漏掉的引用不止主干：`refs/tags` 常常触发发布流水线，某些 refs 命名空间会影响评审展示或元数据。规则应按 refs 前缀正向放行任务分支、其余默认拒绝，而不是逐条枚举需要保护的名字——枚举永远追不上新增的引用类型。
3. 凭证要与目标主机绑定：沙箱里可以随意添加一个新的远端地址并推到外部，如果凭证会被无差别地送给任何地址，它同时就是一条外传通道。凭证的提供方式应校验请求目标，并配合出网限制，让它只在预期对端可用。
4. 令牌要短时、单任务、可即时吊销，并与"谁批准了这次任务"关联。任务结束即失效，可以把泄漏影响窗口收敛到一次任务的时长，这比事后检测更可靠。

客户端的限制仍有价值，但价值在于减少误操作和给出更清晰的错误提示，不能当作安全控制。应主动用构造用例定期测试：从沙箱尝试推主干、强制推送、推标签、推到外部地址，四项必须全部被拒绝；把它们做成常规回归，任何一项通过都视为线上安全缺陷。

**相关知识点：** branch protection、push rules、pre-receive hook、refs 前缀放行、短时令牌吊销、拒绝用例回归。
<a id="eng-219"></a>
### 17. 制品库与云服务凭证如何注入沙箱而不进入模型上下文？

判断标准很具体——**凭证要能被进程使用，但不能出现在任何会回流到上下文的文本里**；环境变量并不满足这个标准。

1. 环境变量常被误当成隔离手段，实际上沙箱里任何进程都能读到它们，Agent 也随时可以执行一条打印环境的命令，输出会原样进入上下文并被持久化到会话记录。它解决的是"不写进代码"，没解决"不进上下文"。
2. 更彻底的做法是让沙箱根本不持有凭证：请求经由 egress proxy 转发，由它在出口注入认证信息。沙箱里的工具照常工作，但整个环境里不存在可被读出的密钥。代价是每种协议都要有对应的代理支持，覆盖不到的场景仍需回落到注入。
3. 必须注入时，用 Git credential helper 这类按需取值的接口代替常驻变量，并让取值过程不产生可打印输出；文件形式的凭证放在工作区之外，避免被一次全量暂存带进提交。
4. 这件事最终能不能成立，取决于**回流通道枚举得全不全**：命令的标准输出与错误输出、文件读取工具、异常堆栈、构建日志、Trace 与会话记录，每一条都会把沙箱内的文本带回模型。要逐条确认凭证不会出现在其中——漏掉任何一条，前三步都白做。

这套设计的验证不能靠人工检查配置，要靠可读性探测：在沙箱内执行打印环境、读取包管理器配置、查看进程环境与命令行等一组用例，看能不能把明文取出来。指标是沙箱内可读出的明文凭证形态数量（目标为零）、走代理而非注入的请求占比，以及必须落盘注入的例外数与复核周期。

**相关知识点：** egress proxy 凭证注入、Git credential helper、环境变量可读面、工作区外凭证文件、上下文回流通道、可读性探测。
<a id="eng-220"></a>
### 18. 集成测试需要真实凭证时，如何设计最小权限与短时效令牌？

优先级依次是**换环境、换身份、换时效**——先问能不能不用生产凭证，再谈把权限和有效期收窄。

1. 最有效的一步是把集成测试指向独立的测试租户，用合成数据而不是生产数据。在生产里靠精细权限保护真实数据既难以论证也难以维持，测试一旦需要读取真实记录，权限就会被一次次放宽。
2. 身份上用 workload identity federation 而不是长期密钥：沙箱出示可验证的 OIDC 身份令牌，向 STS 换取一次性短时凭证。密钥不落盘、不进配置，并且天然带上"哪个任务、哪次执行"的上下文，便于审计归因。
3. 有效期要与任务时长匹配：比任务短会让长测试中途失败，而无条件续期又把短时凭证退化回长期能力。折中是允许在任务仍处于活动状态时续期，同时给出绝对上限。
4. 权限范围除操作类型外还要限制资源命名：测试创建的资源统一带前缀，凭证只能操作带该前缀的资源，另有独立清理任务负责回收。有创建权限不等于有删除任意资源的权限，这条分离能挡住相当一部分连锁破坏。

这类凭证的风险随集成测试规模增长，需要定期复核而不是一次配好。可采集的指标包括仍在使用长期密钥的流水线数量（目标为零）、凭证有效期分布、超时未回收的测试资源数，以及测试身份触发的越权拒绝次数——最后一项长期恒为零反而值得怀疑权限是不是给宽了。

**相关知识点：** 独立测试租户、合成数据、workload identity federation、OIDC 身份令牌、资源前缀约束、遗留资源回收。
<a id="eng-221"></a>
### 19. 如何防止密钥经由命令回显、日志和 Trace 泄漏出沙箱？

泄漏路径的共同点是**密钥曾以明文形式出现在某个"顺手记录下来"的地方**；治理要沿着记录链路做，而不只是在代码里避免打印。

1. 对 Coding Agent 而言最独特的一条路径是命令本身：模型构造的命令行会被完整记录进会话，如果它把密钥写成字面量而不是引用变量，密钥就直接进了上下文与审计记录。命令行还会出现在进程表里（`ps` 可见），同宿主的其他任务可能读到。
2. 其次是输出侧：`set -x` 这类调试开关会回显展开后的命令，失败请求的报错常常带上完整地址与查询参数，异常堆栈可能包含请求头。这些都不是应用主动打印的，靠代码审查发现不了，只能在采集链路上过滤。
3. 链路数据同样要治理：OpenTelemetry 的 Span 属性、请求头、请求体都可能带凭证。正确做法是属性按 allowlist 上报，而不是默认全采后再删——默认全采意味着新增字段自动泄漏，而删除规则永远滞后于字段新增。
4. 过滤要双管齐下：已知值精确匹配负责确定性，模式匹配负责覆盖未登记的凭证形态。两者都有代价，过度替换会让排查失去必要信息，因此替换后应保留可关联的指纹，让人能判断"是不是同一个值"而不知道值本身。

过滤必须发生在数据进入任何持久存储和回流上下文之前，事后清洗只能减少留存、不能撤回已经扩散的副本。验证靠定期注入 canary token：在沙箱内以各种方式使用这枚诱饵密钥，再到会话记录、日志与链路数据里检索，统计诱饵出现次数与首次出现位置，命中即定位到具体的采集环节。

**相关知识点：** canary token、Span 属性 allowlist、进程表命令行可见、`set -x` 回显、脱敏指纹、采集侧过滤。
<a id="eng-222"></a>
### 20. 沙箱凭证泄漏后如何快速定位影响面并完成轮换？

响应速度取决于**事前有没有一份"凭证—签发方—使用方—轮换方式"的台账**；没有台账时，绝大部分时间会耗在确认这把钥匙到底谁在用。

1. 先算暴露窗口，起点是密钥进入任何可留存介质的时刻，而不是被检测到的时刻。会话记录、构建日志、链路数据、缓存的工具输出都是留存介质，起点通常比想象的早很多；用错起点会系统性低估影响面。
2. 影响面用凭证自身的访问记录来算：按凭证标识过滤窗口内的全部调用，看动作、目标资源与来源地址能否与已知任务一一对上。对不上的调用优先处理，而不是先去猜攻击者可能做了什么。
3. 轮换顺序取决于业务耐受度：能立即吊销的立即吊销，不能的先签发新凭证、切换使用方、再吊销旧的。这个顺序必须事前定好并演练过，事发时临时判断往往因为担心中断而拖延吊销。
4. 清理留存副本是最容易被跳过的一步：泄漏值可能已经进了会话记录、评测数据集或日志归档，不清理会让同一次泄漏在后续被反复重新发现，也可能被下游系统再次使用。

这类事件的能力必须靠演练验证，不能靠预案文档。可采集的指标是从检测到吊销完成的耗时、具备自动轮换路径的凭证占比、影响面评估所需时间，以及演练中发现的台账缺项数量——最后一项通常是真实事件里最大的时间黑洞。

**相关知识点：** 凭证台账、暴露窗口起点、凭证访问日志回溯、吊销顺序预案、留存副本清理、轮换演练。

### 21. Bash 命令允许清单为什么容易被绕过？管道、命令替换与转义如何处理？

根源是**用字符串匹配去约束一门可编程语言**：匹配器看到的词法单元，和 Shell 真正执行的东西不是一回事。

1. 组合结构直接打破了"一条命令"的假设：分隔符、逻辑连接、管道、command substitution、进程替换都能在一次输入里引出第二条命令，而只看开头那个词的匹配器完全看不见。要处理就必须真正解析出语法树，把每个会被执行的命令逐个取出来判断。
2. 即使解析正确，转义与展开仍会让文本与语义分离：反斜杠、引号、各种编码形式的字面量、变量间接引用、`IFS` 替换，都能拼出同一条命令的不同写法。匹配器在展开前判断，Shell 在展开后执行，这个时间差是结构性的。
3. 更根本的是，清单放行的很多程序本身就能执行任意代码：解释器带一行脚本参数、构建工具的自定义任务、支持调用外部命令的文本处理工具、允许对每个匹配项执行命令的查找工具——这类 LOLBin 放行了，等于放行了整个 Shell。
4. 因此现实定位是：允许清单用于降低误操作、给出可解释的拒绝理由，安全边界放在沙箱、文件系统与网络层。承认这点设计会更诚实——与其把清单越写越复杂，不如假设 Shell 内可执行任意命令，再问"那样最坏会怎样"。

如果确实需要强约束，可行方向是不经 Shell、直接以 `execve` 参数数组执行一组受限工具，代价是失去管道与通配符，而编码任务对它们依赖很深。评估这类机制唯一有意义的方式是红队绕过测试：维护持续增长的绕过用例集，把绕过成功率而非清单条目数当作指标。

**相关知识点：** shell 语法树解析、command substitution、参数展开与 IFS、LOLBin、execve 参数数组、绕过用例集。

### 22. 如何在沙箱内判定一条命令是否高危？静态规则与模型判定如何配合？

分级的核心维度不是"命令看起来吓不吓人"，而是**影响是否越出沙箱、以及是否可逆**；两者共同决定该自动执行、该拦截还是该问人。

1. 越界优先于危险度：删掉沙箱里的依赖目录看着吓人却完全可逆，重装即可；而把变更强制推送到共享分支写入量很小，却会改写他人的历史。判定应先看作用对象在不在沙箱内，再看操作语义。
2. 可逆性要有具体依据：有没有基线或快照可回到、外部副作用能否补偿、是否会触发下游流水线。凡是说不清如何撤销的操作一律按不可逆处理，而不是凭经验判断"应该没事"。
3. 静态规则负责确定性与可审计：解析后按规则匹配，命中就是命中，能复现、能解释、能进回归测试。它的弱点是只覆盖枚举过的形态，对没见过的写法沉默。
4. 模型判定负责泛化，但它读的是可能被注入的内容、自身可被操纵，因此只能单向使用——允许把静态规则判为低危的提升为高危，不允许把静态高危降级放行。这是典型的 fail-safe 取向：即使模型被诱导，最坏结果也只是多问几次人，而不是放过一条危险命令。

判定质量要用标注过的命令语料持续评测，同时看漏判和误判：漏判直接对应事故，误判抬高审批频率并诱发盲目点同意。还要跟踪人工审批的实际否决率——如果人几乎从不否决，说明阈值定低了，这道审批正在消耗信任却不产生价值。

**相关知识点：** 作用域越界判定、可逆性分级、静态规则匹配、fail-safe 单向升级、标注命令语料、审批否决率。

### 23. 沙箱的只读模式该覆盖哪些操作？它与审批模式如何切换？

只读必须按**副作用**定义而不是按工具名定义，否则最大的漏洞会大大方方留在里面——运行仓库里的代码。

1. 很多"读"操作其实会写：拉取远端会写入版本控制目录，装依赖会写盘，不少分析工具会生成缓存。真正的只读要靠只读挂载在文件系统层强制，同时单独给一小块 tmpfs 临时可写空间，因为完全没有可写位置会让大量工具直接崩溃。
2. 最需要堵的是执行：跑构建或测试就是在执行仓库里的代码，而仓库内容可以是任意的。把"跑一下测试看看"当成只读模式的例外，等于取消了这个模式。真要执行，就该切换到有隔离和审批的模式。
3. 只读模式还应撤销凭证并断网，否则读到的敏感信息可以被发出去——只读限制的是写入本地，不是限制信息流出，这两件事经常被混为一谈。
4. 切换必须单向安全：从可写降到只读随时可以，从只读升到可写要重新授权，且触发条件不能来自 Agent 读到的内容。否则一段被注入的文档就能促使会话自己去申请提权。

只读模式的代价是 Agent 无法用执行来验证自己的结论，方案质量会下降，所以它适合审阅、排查与方案设计，不适合交付变更。可采集的信号包括只读会话中被拦截的写入与执行尝试次数、提权申请频率与通过率，以及只读模式下的任务完成率——完成率过低说明边界划得不实用，应重新界定而不是靠例外放行。

**相关知识点：** 只读挂载、tmpfs 可写空间、按副作用定义的只读边界、断网与凭证撤销、提权重新授权、提权触发源限制。
<a id="eng-226"></a>
### 24. 审批点应该设在命令级、工具级还是任务级？

三者都不是答案，正确的位置是**效果边界**——沙箱内随便做，任何越出沙箱的效果才需要人来批。

1. 命令级审批的信息质量最高，但一次编码任务往往有几十上百步，人会迅速进入机械点同意的状态。这比不设审批更糟：它没拦住任何东西，却把责任转移给了那个点同意的人。
2. 工具级审批通常最没用："允许执行命令"这样的授权粒度既不说明会做什么，也不说明影响多大，等于用一次点击换取一整类能力。
3. 任务级审批批的是意图而不是效果。Agent 中途完全可能做出符合意图、但你绝不会同意的具体动作，而任务开始时没人能预见它。
4. 效果边界的好处是与编码工作流天然对齐：沙箱内的编辑、构建、测试全部自动进行，把最终 diff 作为审批对象呈现给人——这正是代码评审已有的习惯，也是 Human-in-the-loop 在编码场景最自然的落点。审批要绑定到具体产物（diff 内容及其基线的哈希），产物变化即失效，避免批准之后被替换。

审批的价值来自人真的看懂了被批的东西，因此要控制单次审批的规模，差异过大就先拆任务。可采集的信号包括审批通过率、从展示到决策的耗时分布（大量秒级决策就是走过场的证据），以及自动放行类别中的事故率。后者非零说明效果边界划错了，应把相应类别移出自动区，而不是把所有操作都加回审批。

**相关知识点：** 效果边界、审批疲劳、Human-in-the-loop、diff 级审批、审批绑定产物哈希、决策耗时分布。
<a id="eng-227"></a>
### 25. Agent 在沙箱内执行了破坏性操作，如何回滚工作区与外部副作用？

工作区的回滚是工程问题，外部副作用的回滚往往**不存在**；所以真正的设计目标是让破坏性操作尽量只发生在沙箱里。

1. 工作区侧不要指望 Agent 自己提交过：由外层在每次工具调用的边界做快照，content-addressable storage 让未改动文件几乎不占额外空间，代价只是元数据。这样任何一步之后都能回到确切状态，而不是依赖记忆去反向操作。
2. 要区分可恢复与不可恢复的破坏：已经提交过的内容通常还能通过 reflog 找回，而 `git clean -xdf` 清除未跟踪与被忽略的文件是直接删盘，快照没覆盖就真的没了。这也正是快照必须包含未跟踪文件的原因。
3. 外部副作用按可逆性分三类：可撤销的（创建的资源、可回滚的写入）、可补偿的（Saga 式补偿，发出的消息可再发一条更正）、不可逆的（已支付、已通知外部、已覆盖他人历史）。每一类事前就要写好对应动作，事后临时想办法通常来不及。
4. 不可逆的那一类只能靠事前拦住——它们正是应该落在审批与出网限制范围内的操作。把"反正能回滚"当作放宽执行权限的理由，是这个话题上最常见的误判。

恢复能力必须演练：定期在沙箱里故意执行破坏性操作，测量恢复所需时间以及恢复后测试是否仍然通过。指标包括工作区恢复耗时、快照覆盖率（是否含未跟踪文件）、有成文补偿方案的副作用类型占比，以及演练中被发现根本无法恢复的场景数量。

**相关知识点：** 工具调用边界快照、content-addressable storage、reflog、`git clean -xdf`、Saga 补偿、恢复演练。
<a id="eng-228"></a>
### 26. 仓库里的 README、注释和 Issue 可能带注入指令，如何阻断它们触发命令执行？

难点在于**Coding Agent 的本职就是遵循仓库里的说明**——贡献指南要求提交前跑格式化是完全正当的，所以不能靠"忽略文件里的指令"来防。

1. 分界要落在能力而不是意图上：仓库内容可以影响 Agent 做什么，但不能扩大它能做什么。一段文档要求把某个目录打包发到外部地址，失败原因应该是出网被拒绝，而不是模型判断出这是坏指令。
2. 面向 Agent 的配置文件（`AGENTS.md`、`CLAUDE.md`、MCP 配置）是最高危的一类，因为工具链本来就设计成会读取并遵循它们。它们应按代码对待：纳入评审、锁定来源，尤其不能从待评审分支、外部贡献者的提交或第三方目录里自动加载。评审外部变更时，被评审的变更本身就可能改写这些文件。
3. 来源要在上下文里结构化地标出：用户任务、仓库文件、工具返回、第三方内容各带各的标签，并把标签一路传到下游判定。这不是安全边界——读了标签仍可能被说服——但它把"这条指令是谁说的"变成可判定的事实，代价只是一套格式约定，是性价比最高的一层。
4. 越权动作要求可追溯的依据：某一步要执行越出沙箱的操作时，必须能指向用户任务而不是某份被读取的文件；理由来自不可信内容就直接拒绝。

这些措施降低概率但不能归零，所以必须假设有一天模型会被说服，并保证那一刻它手上没有可造成损失的能力。验证靠常态化的注入用例集：把诱导指令埋进不同载体，统计诱导成功率以及被哪一层拦下；如果绝大部分拦截发生在模型自身的拒绝上，说明能力层还太宽松。

**相关知识点：** Prompt Injection、`AGENTS.md`、`CLAUDE.md`、provenance 来源标注、能力边界、注入用例集分层统计。
<a id="eng-229"></a>
### 27. 依赖包元数据与第三方代码中的注入如何防范？

先做优先级判断——**执行第三方代码的风险远高于阅读它的文本**；如果安装脚本已经跑过，再纠结元数据里的诱导指令就有点本末倒置。

1. 元数据的注入面是那些会被原样送进上下文的自由文本：包描述、说明文档、报错字符串、发行说明。防法很直接——只提取结构化字段（名称、版本、校验值、许可证），自由文本不进上下文或严格截断，需要人判断时给人看。
2. Agent 调试时会读第三方源码，代码注释同样是载体。可行做法是给这件事开一个受限的阅读窗口：限制单次读入量、只读不执行，并在窗口期间冻结全部越界动作——出网、写外部资源、提交都不放行。读依赖源码这个阶段本来就不需要它们，冻结的代价接近于零。
3. 靠检测"指令样式"的过滤召回率很低：诱导可以写得完全像正常文档，例如以诊断为名要求打印某个环境变量。把它当降噪手段可以，当防线不行。
4. 真正的风险排序应当指导投入：优先关掉安装期的代码执行、优先切断出网，其次才是元数据过滤。反过来做的团队往往在过滤规则上投入很多，却对安装脚本毫无限制。

这一层的作用是减少上下文被污染的机会，最终仍要靠能力限制兜底。可采集的指标包括第三方来源内容在上下文中的占比、元数据自由文本的截断率，以及同一套注入用例在"仅阅读"与"允许安装"两种配置下的成功率对比——这个对比能直观说明投入该放在哪一侧。

**相关知识点：** supply chain 风险排序、结构化字段提取、自由文本截断、第三方代码阅读窗口、指令样式检测召回率、配置对比实验。
<a id="eng-230"></a>
### 28. CI 日志、测试输出和编译报错回填上下文时会引入什么风险？

这类内容最容易被当成"我们自己系统的输出"而默认可信，实际上它**大量由仓库内容和第三方依赖决定**，是一条外观可信的不可信通道。

1. 内容风险在于任何字符串都可能是攻击面：测试名称、断言消息、依赖打印的提示都可以由提交者控制，而它们出现在"构建失败原因"这种高权重位置，比藏在文档里更容易被采纳。
2. 泄漏风险同样现实：失败用例常常打印请求详情、环境信息或响应体，这些内容一旦回填上下文就进了会话记录并可能被长期留存。回填前必须过一遍与日志相同的脱敏规则，不能因为"只是给模型看"就跳过。
3. 体量风险最常被低估：完整日志动辄数十兆，按尾部截断恰好会丢掉最早的那个根因错误，模型于是围着连锁失败打转。更好的做法是走结构化产物——测试报告有 JUnit XML，静态检查与编译诊断有 SARIF，可以按失败项去重后取前若干条，而不是按字节截断文本。
4. 还有一类行为风险：以日志变绿为目标，模型可能改的是断言或跳过用例而不是缺陷本身。回填时应同时给出用例的判定标准，并在验收侧检查测试文件的改动。

把 CI 输出当作需要清洗和结构化的外部输入，而不是可信的系统消息。可采集的指标包括 CI 输出占上下文 Token 的比例、截断率、根因错误是否落在被送入的片段内（可用已知失败样本回归测试），以及修复变更中测试文件改动的占比——后者异常升高通常是绕过而不是修复。

**相关知识点：** CI 日志回填、提交者可控字符串、失败输出脱敏、JUnit XML、SARIF、失败项去重取样、测试文件改动占比。

### 29. 工具返回值与 MCP Server 响应进入上下文前应做哪些过滤？

外部工具服务是**信任链里的第三方**，它的响应应按不可信输入处理；而且不只是响应，工具描述本身也是会被注入进提示词的内容。

1. 先做结构约束：按声明的 JSON Schema 校验，丢弃未声明字段，限制长度与嵌套深度。校验失败要显式报错而不是把原始内容塞进上下文——后者会让一个坏掉的服务直接变成任意文本注入通道。
2. 清洗控制字符与 ANSI escape 序列：这类内容可以在终端界面里制造与实际数据不符的显示效果，让人在审批时看到的和真实内容不一致。对以终端为主界面的编码工具，ANSI escape injection 是一条容易被忽略的欺骗路径。
3. 工具清单要固定并在变化时重新确认：描述文本会进入提示词，一个服务完全可以在获得批准之后修改自己的描述来改变模型行为。按内容哈希锁定清单、变更时要求重新批准，比只在接入时审一次可靠得多。
4. 响应里不能夹带可执行意图：如果 MCP Server 返回的文本包含"下一步该调哪个工具、传什么参数"的建议，就等于让第三方直接驱动会话。响应只当数据看，工具选择权始终留在编排侧；同时限制单次返回在上下文中的占比，避免一个服务的输出淹没任务本身。

过滤越严，与快速演进的第三方服务的兼容性越差，所以 Schema 要有版本并给出兼容窗口。可采集的指标包括校验失败率、响应体积分布、工具清单变更次数与重新批准耗时，以及外部来源内容在上下文中的 Token 占比；这几项一起看，能较早发现某个服务在悄悄变化。

**相关知识点：** MCP Server 响应、JSON Schema 校验、未声明字段丢弃、ANSI escape injection、工具清单哈希锁定、Schema 版本兼容窗口。

### 30. 面向 Coding Agent 的注入防御如何做纵深分层？各层分别拦得住什么？

各层的强度差别很大——**能力层、出网层与人工评审是承重的，提示层与检测层只是降噪**；把投入压在后者是这个话题上最常见的错配。

1. 上下文层（来源标注、体量控制、结构化提取）降低模型被混淆的概率，成本低、收益确定，但对方只要写得足够自然就能穿过去，它拦不住有准备的攻击。
2. 能力层（工具最小化、不持有凭证、按阶段授予权限）是唯一在模型完全被说服后仍然成立的一层：被说服的模型也只能调用它已经拥有的东西。这一层的质量决定了最坏情况有多坏。
3. 出网层直接对着攻击目的：绝大多数注入最终要把数据发出去。默认拒绝、协议感知代理、封堵 DNS 与 IMDS 旁路，能把"注入成功"和"造成损失"这两件事分开。
4. 交付层是变更进入代码库的最后一道：即使前面全被穿透，一个恶意改动仍需通过评审与测试。它的短板是人对大体量差异的审阅质量急剧下降，所以必须配合差异规模上限与必过的检查项。
5. 检测与审计层不阻止任何事，作用是缩短从发生到发现的时间，并在事后提供可追溯的证据链，价值全部体现在响应速度上。

分层的意义在于任何单层失效都不致命，因此评估必须逐层做而不是只看端到端通过率：把上面的层依次关闭，测量每一层单独的拦截能力，才知道哪一层实际在承重。指标包括分层拦截率、注入用例的端到端成功率、从注入发生到被发现的耗时，以及自动放行路径上的事故数。

**相关知识点：** 纵深防御、上下文层降噪、能力层最小权限、egress 默认拒绝、交付层评审、逐层消融评估。
