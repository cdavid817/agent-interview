### ENG-001 · Prompt如何评估和优化？（豆包一面）

> 稳定 ID：`ENG-001`｜原题号：1

Prompt评估与优化应建立**目标—基线—归因—改动—回归—线上验证**闭环，不能依赖少量样例或主观感受。

1. 将成功拆成指令遵循、事实正确、格式合法、工具参数准确、引用忠实和安全拒绝等指标，并设置延迟、Token成本与人工介入护栏；开放任务使用Rubric。
2. 建立版本化数据集，包含黄金样本、生产回放、历史失败、长尾与对抗输入，按场景、难度和风险分层；开发集与隐藏测试集隔离，防止针对样例过拟合。
3. 固定模型、温度、知识库、工具和预算，新旧Prompt对相同输入进行配对运行。确定性任务优先使用Schema、单元测试和业务终态评分，语义任务采用经人工校准的LLM-as-a-Judge与盲审抽检。
4. 基于失败Trace区分需求不清、上下文缺失、指令冲突、示例偏差、格式不稳和模型能力不足；每次只调整职责边界、约束、示例或输出结构中的少数因素，保留修改假设。
5. 报告总体及分层指标、效应量、置信区间、退化样本和成本变化；通过回归门禁后，再以Shadow或A/B Test验证真实完成率，护栏越界立即回滚。

线上失败经脱敏后回流评测集，Prompt模板、变量、渲染结果和Judge版本均留痕。**有效优化必须带来可复现的净业务收益**。

**相关知识点：** Prompt Benchmark、Rubric、配对评测、LLM-as-a-Judge、回归测试、A/B Test、护栏指标、数据泄漏、版本管理。

### ENG-002 · 代码Agent项目的提示词模板是怎么设计和迭代的（百度Agent）

> 稳定 ID：`ENG-002`｜原题号：2

Coding Agent提示词应按**系统契约、动态上下文、工具协议和验证闭环**分层，使模型明确目标、边界、证据及完成条件。

1. System层固定角色、安全边界、工作区、工具规则和停止条件；项目层加载仓库规范、构建命令与架构约束；任务层描述需求、验收和修改范围。
2. 动态模板只注入当前步骤所需的Repo Map、符号、调用链、测试、Diff和错误日志，并标记来源；用户文本、代码注释与检索内容不能覆盖系统规则。
3. 工具使用严格Schema，规定先检索再修改、读取最新版本、最小Diff、写后测试和重试预算；输出包含计划、证据、修改、验证及风险。
4. 依据Trace和Failure Taxonomy，将失败归为定位、上下文、规划、生成、工具、测试或安全；每次针对明确失败簇做最小改动。
5. 使用真实任务、历史失败、跨文件和对抗样本配对回归，评估定位Recall、补丁正确率、测试、安全、Token与时延；通过后再Canary。

模板、变量Schema、Few-shot、项目规则和渲染结果均版本化。**提示词表达策略，目录权限、分支保护和危险命令拦截由系统强制**。

**相关知识点：** System Prompt、动态上下文、Repo Map、Tool Schema、最小Diff、Failure Taxonomy、Prompt版本、回归测试、Canary。

### ENG-003 · System Prompt为什么比User Prompt权限更高？（百度Agent）

> 稳定 ID：`ENG-003`｜原题号：3

System Prompt优先级更高，是因为平台需要**不可被普通用户覆盖的行为契约**，用于定义职责、安全边界和工具规则；User Prompt表达本次目标。

| 层级 | 主要来源 | 典型职责 |
|---|---|---|
| System | 平台 | 身份、安全边界 |
| Developer | 开发者 | 工作流、工具策略 |
| User | 用户 | 任务目标、输入 |

1. 若用户能覆盖系统规则，任何人都可用“忽略之前要求”解除隐私和输出约束，因此冲突时必须遵循更高层指令。
2. 优先级由消息角色和运行时实现，而非文字语气或“管理员”声明。文档、网页、代码注释和Tool返回属于数据，不能改变层级。
3. System Prompt应稳定、简洁且可审计，规定允许行为、信息边界、工具和失败处理；User Prompt提供目标、约束与数据。
4. 高优先级不等于真实权限。Prompt影响模型决策，Tool仍由Policy Engine校验身份、资源、动作与审批；隔离和凭证由系统强制。
5. 应明确冲突处理，并通过直接、间接、多轮和编码混淆注入测试，验证低层内容不能篡改高层契约。

System Prompt解决**指令治理和行为一致性**，IAM解决真实资源授权，两者不可替代。

**相关知识点：** 指令层级、System Prompt、Developer Prompt、User Prompt、Prompt Injection、指令数据隔离、Policy Engine、IAM。

### ENG-004 · 怎么判断一个提示词模板是真的更好了？有没有量化的评估标准？（百度Agent）

> 稳定 ID：`ENG-004`｜原题号：4

提示词是否变好，应以**同一任务分布下相对基线的净收益**判断：主质量指标显著提升、关键分层无回归，且安全、时延和成本护栏仍满足要求。

1. 预定义Rubric。确定性任务使用格式、字段、Tool参数、单元测试或业务终态；开放任务评估正确性、完整性、事实性、引用忠实和指令遵循。
2. 测试集包含黄金样本、生产回放、历史失败、长尾与对抗输入，并按任务、难度和风险分层；开发集与隐藏集隔离。
3. 固定模型、温度、知识库、工具和预算，让基线与候选Prompt在相同输入上配对运行；随机输出需重复采样。确定性规则优先，LLM Judge使用结构化Rubric、隐藏版本、随机顺序并以人工盲审校准。
4. 量化绝对提升、相对提升、效应量和置信区间；完成率可做配对比例检验，评分型指标可用Bootstrap，延迟与成本报告P50/P95。必须列出改善、持平和退化样本，而非只看平均分。
5. 护栏包括安全违规、拒答错误、人工介入、Token、P95延迟和成功成本。离线通过后用Shadow或A/B验证线上完成率与业务价值。

只有提升超过预设最小实际效应并跨周期稳定，才判定有效。模板、变量、渲染结果、数据和Judge版本应留痕，避免口径变化制造虚假提升。

**相关知识点：** 基线、配对评测、Rubric、效应量、置信区间、Bootstrap、护栏指标、A/B Test、最小实际效应。

### ENG-022 · Prompt 的最佳实践有哪些？

> 稳定 ID：`ENG-022`｜原题号：22

Prompt最佳实践是**职责清晰、指令可执行、上下文可信、输出可验证、版本可评测**，目标是减少歧义并让失败可定位。

1. 按System、Developer、User分层：高层固定角色、安全边界、工具和停止条件；用户层描述目标、输入与约束。外部文档和Tool结果放入数据边界。
2. 用目标、背景、输入、约束、步骤、输出Schema、成功标准和失败处理组织模板；表述应具体、可测试，避免模糊词和冲突要求。
3. 只提供所需上下文并标注来源、版本和权限；长材料先检索、去重和压缩。重要要求放在稳定位置，结构化数据用JSON或内容块。
4. Few-shot覆盖代表性、边界和拒绝场景，格式与实际输入一致；数量以新增信息为准，过多会占用Token、引入偏差并稀释指令。
5. 工具调用使用严格Schema、枚举和参数范围，输出由解析器、业务规则或Verifier检查；高风险权限不能依赖Prompt，必须由Policy Engine和沙箱强制。

模板、变量和渲染结果应版本化。每次修改在黄金集、生产回放、长尾与对抗集上配对回归，评估完成率、正确性、安全和成本，再通过Canary验证。

**相关知识点：** 指令层级、结构化Prompt、Few-shot、上下文裁剪、Tool Schema、Verifier、Prompt Injection、版本管理、回归评测。

### ENG-023 · System Prompt 和 User Prompt 的职责如何划分？

> 稳定 ID：`ENG-023`｜原题号：23

System Prompt定义**稳定的行为契约与安全边界**，User Prompt表达**本次任务目标、输入和约束**；二者不应重复或冲突。

| 维度 | System Prompt | User Prompt |
|---|---|---|
| 生命周期 | 应用级、稳定 | 请求级、动态 |
| 内容 | 角色、工具、禁止项 | 目标、数据、验收 |
| 维护者 | 平台开发者 | 用户或业务系统 |

1. System层规定Agent身份、允许任务、数据边界、工具、输出Schema、失败与停止条件；规则应简洁、可审计并版本化。
2. User层提供问题、对象、时间范围、期望产物和验收条件；缺少参数时先澄清，但不能用“忽略之前指令”改变系统策略。
3. 项目规范、领域术语和工作流放Developer或Project层，避免把所有业务规则塞入System或要求用户重复固定规则。
4. RAG文档、网页、代码和Tool返回属于数据，即使含命令也无User或System权限；使用边界标签、来源和可信级别隔离。
5. 冲突按角色优先级处理；真实Tool权限仍由IAM、Policy Engine和沙箱校验，Prompt层级不能替代授权。

通过直接、间接、多轮注入和空输入测试验证划分；评测系统规则稳定性、目标满足率、拒绝准确率和Token开销。

**相关知识点：** System Prompt、User Prompt、Developer Prompt、指令优先级、行为契约、Prompt Injection、数据隔离、Policy Engine。

### ENG-026 · Prompt 是否越长越好？

> 稳定 ID：`ENG-026`｜原题号：26

Prompt不是越长越好，目标是**以最少且充分的信息消除关键歧义**。新增内容若不提高决策质量，只会引入噪声、冲突和成本。

1. 长Prompt挤压用户输入、RAG证据、Tool结果与输出空间；注意力并非均匀分配，重要要求可能被中间材料淹没，出现Lost-in-the-Middle。
2. 重复规则、过多Few-shot、无关背景和历史会稀释系统指令，增加矛盾与位置偏差；模型可能忽略真正成功标准。
3. 长输入提升预填充时延、显存和Token费用，扩大敏感暴露与Prompt Injection；动态上下文未过滤时还会注入过期或越权内容。
4. 保留角色、目标、必要约束、输出Schema、少量边界示例和完成条件；长文档先检索、去重、摘要或分层加载，详细规则按需获取。
5. 复杂任务不靠单个超长Prompt，可拆成Planner、Executor、Verifier，各阶段只获所需上下文，并用状态与证据连接。

通过消融实验比较完成率、安全、P95延迟和成功成本，逐项删除不影响结果的内容。**最优Prompt追求信息密度和可执行性**。

**相关知识点：** 上下文窗口、信息密度、Lost-in-the-Middle、Prompt压缩、渐进式上下文、消融实验、Token成本、Prompt Injection。

### ENG-027 · 如何设计结构化 Prompt？

> 稳定 ID：`ENG-027`｜原题号：27

结构化Prompt应把任务拆成**职责、目标、输入、约束、过程、输出和验收**等区块，使模型与程序可解析，降低歧义和格式漂移。

1. 顶层规定角色、目标、成功标准、允许与禁止行为；目标用可观察动作描述，例如输出三个符合Schema的候选，避免模糊词。
2. 输入区将用户数据、RAG证据和Tool结果放在独立标签中，记录来源、版本与可信级别；这些内容仅供分析，不得覆盖系统规则。
3. 约束区定义语言、范围、Token预算、工具、引用、安全与失败处理；缺少信息时澄清、拒答或返回Unknown，禁止编造字段。
4. 过程区描述必要步骤，如先检索、再比较、后验证；复杂任务拆为Planner、Executor、Verifier，不在模板里嵌套无限分支。
5. 输出区使用JSON Schema、枚举、必填字段和示例，区分展示与机器消费；Tool参数用原生Schema约束，并由解析器和业务规则验证。

模板与变量Schema版本化，防止转义和字段注入。使用正常、边界、缺失、冲突及注入样本回归，评估格式合法率、完成率、安全与Token；不增加无意义层级。

**相关知识点：** Prompt Template、JSON Schema、输入边界、指令数据隔离、Tool Schema、Verifier、模板注入、版本管理。

### ENG-028 · Dynamic Prompt 和 Static Prompt 的区别是什么？

> 稳定 ID：`ENG-028`｜原题号：28

Static Prompt提供**稳定规则与格式**，Dynamic Prompt按用户、任务和证据运行时组装；通常以静态骨架保一致，以动态内容提相关性。

| 维度 | Static Prompt | Dynamic Prompt |
|---|---|---|
| 时机 | 发布时固定 | 请求时组装 |
| 内容 | 角色、政策、Schema | 用户、RAG、Tool、记忆 |
| 风险 | 规则过时 | 注入、漂移、难复现 |

1. 静态部分适合System规则、工作流、工具协议、停止条件和安全边界，便于评审、缓存和回归，但不放频繁变化的业务数据。
2. 动态部分适合租户配置、任务参数、项目规范、Few-shot、知识证据和实时状态；Context Builder按相关性、权限、新鲜度与预算选择。
3. 动态数据带来源、版本、可信级别和ArtifactID；外部文档与Tool结果放入边界，不能改变静态指令；敏感数据先脱敏。
4. 模板引擎校验变量Schema、类型、长度、转义和默认值，防止字段缺失与模板注入；渲染文本、数据快照和选择策略留痕。
5. 分别评测静态规则稳定性和动态检索质量，并对完整渲染结果配对回归，观察完成率、安全、Token和延迟。

动态不等于模型自由改写Prompt，可变内容及选择逻辑仍由受控程序生成、版本化和审计。

**相关知识点：** Static Prompt、Dynamic Prompt、Context Builder、模板引擎、变量Schema、模板注入、Artifact、可复现性、Prompt缓存。

### ENG-034 · 如何构建 Prompt Benchmark 数据集？

> 稳定 ID：`ENG-034`｜原题号：34

Prompt Benchmark应覆盖**真实任务、能力边界、历史失败与安全对抗**，并具有明确Rubric、稳定版本和隐藏测试集。

1. 数据来源组合黄金样本、脱敏生产回放、用户反馈、历史失败、长尾和红队样本；按任务、难度、领域、语言、风险、长度和Tool需求建立矩阵。
2. 样本包含输入、上下文、变量、允许Tool、知识快照、期望行为、证据、输出Schema、Rubric和预算；开放任务允许多个正确答案。
3. 确定性任务使用解析、单元测试、业务终态和规则；语义任务由专家双标，LLM Judge使用Rubric、隐藏版本、随机顺序并经人工校准。
4. 数据集划分开发、回归和隐藏测试集，使用哈希与近重复检测防止泄漏；核心集保持稳定用于纵向趋势，滚动集反映最新生产分布，对抗集独立衡量安全。
5. 记录来源、时间、许可证、隐私、标签、难度和版本，执行PII脱敏、隔离和访问控制；过期知识与失效Tool复审，不删除回归样本。

报告按分层展示样本量、完成率、置信区间、安全、Token和成本。线上失败经人工确认后回流，监控类别和难度漂移，避免Benchmark被刷熟。

**相关知识点：** Benchmark、黄金集、生产回放、覆盖矩阵、Rubric、隐藏测试集、近重复检测、数据泄漏、滚动评测集。

### ENG-038 · 如何进行 Prompt 回归测试？

> 稳定 ID：`ENG-038`｜原题号：38

Prompt回归测试的核心是以**冻结输入、依赖和判分口径比较新旧版本**，证明目标能力改善且既有能力、安全与成本没有不可接受的退化。

1. 建立分层回归集，覆盖核心业务、边界条件、历史缺陷、多轮对话、工具异常和Prompt Injection；样本保存知识快照、Tool版本、期望Schema、证据与Rubric。
2. 在模型参数、随机性、检索索引和沙箱环境中运行基线与候选Prompt。对非确定性任务重复采样，避免将模型波动或外部数据变化归因于Prompt。
3. 确定性输出用解析器、规则、单元测试和业务终态判分；开放输出由经校准的LLM Judge与人工抽检评分。除任务成功率外，还需比较事实性、指令遵循、安全、P95延迟、Token和单次成功成本。
4. 按任务类型、难度、风险和语言切片，报告胜率、退化率、置信区间及显著性。总体均值可能掩盖关键场景下降，高风险样本应设置零容忍或更严格阈值。
5. 将回归测试接入Prompt版本库与CI，变更必须关联原因、实验和审批；未达门禁不得发布。通过后依次进行Shadow、灰度和线上A/B，并配置自动停止与快速回滚。

新增线上失败需脱敏、去重、人工确认后加入历史缺陷集；复核过期知识、失效工具和Judge漂移。这样回归集既保持稳定趋势，也能随真实分布演进。

**相关知识点：** Prompt CI、成对评测、冻结环境、历史缺陷集、回归门禁、置信区间、Shadow、灰度发布、Judge校准。

### ENG-039 · Prompt 修改后如何验证没有副作用？

> 稳定 ID：`ENG-039`｜原题号：39

Prompt修改不存在绝对“零副作用”，可验证的是在**预定义风险边界和统计置信度内没有显著退化**；必须采用差异分析、分层回归和线上渐进验证，而非只检查目标用例。

1. 冻结基线版本及模型、参数、检索索引、Tool、知识快照和随机策略，记录修改意图与预期影响面。对新旧Prompt执行相同输入的成对评测，非确定性任务多次采样。
2. 数据集除目标场景外，应包含核心能力、历史缺陷、边界输入、多语言、长上下文、格式约束、工具失败和安全对抗；额外加入最可能受修改影响的邻近场景。
3. 比较任务成功率、事实性、指令遵循、引用忠实、拒答、工具选择、调用次数、安全违规、延迟、Token及单次成功成本。轨迹Diff还应检查步骤顺序、参数、权限和副作用范围。
4. 按任务、难度、风险、用户群和语言切片，计算赢、平、输比例、置信区间与显著性；总体提升不能抵消高风险场景下降，安全与数据泄漏应采用硬门禁。
5. 离线通过后进行Shadow流量验证，再按小流量灰度和A/B逐步扩大；配置护栏告警、自动熔断、版本回滚及人工复核，避免隐性退化进入全量。

对开放输出采用规则、业务终态、校准后的LLM Judge和盲审组合。上线后持续比较投诉、人工介入和长期留存，因为部分副作用只有在真实多轮交互与分布漂移中出现。

**相关知识点：** 成对评测、影响面分析、轨迹Diff、分层回归、硬门禁、统计显著性、Shadow、灰度发布、自动回滚。
<a id="eng-040"></a>
### ENG-040 · Prompt版本管理如何设计？

> 稳定 ID：`ENG-040`｜原题号：40

Prompt应作为**可测试、可审批、可追溯、可回滚的配置资产**管理，而不是散落在代码中的字符串；版本必须绑定运行依赖与评测证据。

1. 建立Prompt Registry，保存不可变版本、模板正文、变量Schema、适用Agent、模型参数、Tool权限、知识库版本、变更原因和父版本；生产发布使用内容哈希引用，禁止覆盖修改。
2. 模板与环境配置分离，明确System、Developer、User、Few-shot和工具描述的拼装顺序。变量执行类型、必填、转义和敏感字段校验。
3. 采用开发、评审、候选、灰度、生产、废弃等生命周期状态，变更通过Diff审查、Lint、注入扫描、Token预算和回归门禁；高风险Prompt双人审批。
4. 每个版本关联Benchmark结果、线上实验和发布记录，支持流量和时间灰度。日志记录实际版本、模型、检索与Tool版本，保证调用可复现。
5. 回滚只切换已验证的不可变版本，并处理缓存、会话和长任务的版本一致性；Tool协议不兼容时，使用版本化契约。

版本号可采用语义化规则：行为或契约破坏升级主版本，能力增强升级次版本，措辞修复升级补丁版本。定期清理失效候选但保留审计元数据，避免分叉、幽灵版本与未经评测的热修改。

**相关知识点：** Prompt Registry、不可变版本、内容哈希、语义化版本、生命周期、配置分离、回归门禁、灰度发布、可复现性。

### ENG-041 · Prompt A/B实验平台如何实现？

> 稳定 ID：`ENG-041`｜原题号：41

Prompt A/B平台应以**稳定分流、版本隔离、端到端指标和统计决策**为核心，确保观测差异来自Prompt，而不是模型、流量结构或外部依赖变化。

1. 实验前登记假设、主指标、护栏指标、最小可检测效应、样本量、持续时间和停止规则；冻结候选Prompt及模型参数、知识库、Tool、采样策略，先通过离线回归与安全门禁。
2. 分流服务按用户或会话稳定哈希，保证多轮交互始终进入同一实验桶；支持租户、地域、任务和风险分层，排除机器人、内部测试及污染流量，并记录曝光事件。
3. 执行网关从不可变Registry加载版本，严禁同桶热修改。端到端Trace关联实验ID、版本、输入、检索、工具轨迹、结果、Token、延迟、成本和业务终态。
4. 主指标可采用任务完成率、首次通过率或转化率；护栏覆盖幻觉、安全、投诉、人工介入、P95延迟和单次成功成本。开放结果由规则、业务状态、校准Judge及盲审组合判定。
5. 分析采用意向处理口径，报告效应量、置信区间和显著性，必要时使用分层、CUPED或序贯检验；不得因中途波动反复查看并提前宣布胜出。高风险指标越界应自动熔断回滚。

平台还需处理互斥实验、实验碰撞、新奇效应、跨设备身份和网络效应。发布后保留小比例对照或持续监测长期留存，避免短期成功以长期质量下降为代价。

**相关知识点：** 稳定哈希、实验桶、曝光日志、意向处理、最小可检测效应、CUPED、序贯检验、护栏指标、实验碰撞。

### ENG-042 · 如何自动识别失效Prompt？

> 稳定 ID：`ENG-042`｜原题号：42

失效Prompt应定义为在**相同或标准化流量下，关键质量指标持续越过退化阈值**的版本；识别机制必须区分Prompt缺陷、模型变更、知识过期、工具异常和用户分布漂移。

1. 为每个Prompt建立基线画像和SLO，覆盖任务完成率、首次通过率、格式合规、事实性、拒答、工具成功、安全、延迟、Token及单次成功成本，并按任务、语言、难度和租户分层。
2. 在线采集版本、模型、渲染变量、检索结果、工具轨迹、业务终态和反馈。采用滑动窗口、EWMA、控制图或变点检测，对退化、突变及长尾异常告警，避免单点噪声触发。
3. 使用固定哨兵集定时回放新旧版本，冻结模型、Tool与知识快照；若同环境下候选显著退化，才更可能归因于Prompt。外部依赖变化则通过多维归因和对照版本隔离。
4. 自动聚类失败Trace，识别指令冲突、变量缺失、模板截断、格式漂移、检索未利用、工具选择和注入攻击；规则判定与校准后的LLM Judge互补，高风险样本人工复核。
5. 达到阈值后先停止扩量、切回稳定版本并保留证据，再创建缺陷样本进入回归集。失效不能只由低点击或负反馈判定，因为产品入口、流量和用户预期也会改变。

平台需监控评测器漂移与标签延迟，使用置信区间、最小样本量和多重检验校正。通过版本谱系、变更记录和因果实验形成可审计的定位闭环。

**相关知识点：** Prompt SLO、哨兵集、EWMA、控制图、变点检测、失败聚类、归因分析、评测器漂移、自动回滚。

### ENG-043 · Prompt优化效果如何量化？

> 稳定 ID：`ENG-043`｜原题号：43

Prompt优化效果应量化为**单位成本下任务价值的增量**，而不是输出更长、更像人或少数样例得分更高；评价必须同时包含质量、风险、效率和业务结果。

1. 优化前冻结基线Prompt、模型、参数、知识库、Tool和样本版本，预先声明主指标、护栏指标、分层维度、最小可检测效应及停止规则，避免看到结果后更换口径。
2. 离线对同一回归集执行新旧版本成对测试。确定性任务使用单元测试、Schema、规则和业务终态；开放任务使用结构化Rubric、校准后的LLM Judge与人工盲审。
3. 质量指标包括任务完成率、首次通过率、事实性、引用忠实、格式合规和人工介入率；效率指标包括P50/P95延迟、Token、工具调用数、重试率和单次成功成本；安全违规采用硬门禁。
4. 报告绝对提升、相对提升、胜平负比例、置信区间与显著性，并按任务、难度、语言、风险和用户群切片。总体均值提高但关键任务下降，不能认定优化成功。
5. 离线达标后以Shadow排除环境问题，再实施稳定分流A/B，观察真实完成率、转化、留存、投诉和人工处理时长。短期指标改善还需检查新奇效应与长期退化。

可用综合效用分表达取舍：业务收益减去质量损失、风险罚分、延迟和成本，但权重必须由业务和风险等级确定，并同时展示原始指标，避免综合分掩盖严重缺陷。

**相关知识点：** 增量价值、成对评测、护栏指标、最小可检测效应、效应量、置信区间、单次成功成本、综合效用、线上A/B。

### ENG-046 · 如何量化评估Prompt优化效果？

> 稳定 ID：`ENG-046`｜原题号：46

Prompt优化应以**相对基线的增量收益、统计可信度和风险约束**共同判定。单一准确率或主观“回答更好”不能证明优化有效。

| 维度 | 核心指标 | 作用 |
|---|---|---|
| 质量 | 完成率、事实性、首次通过率 | 判断能力增量 |
| 效率 | P95、Token、工具调用、成功成本 | 判断资源代价 |
| 风险 | 幻觉、泄漏、违规、投诉 | 设置发布门禁 |

1. 预先固定基线Prompt、模型、参数、Tool、知识快照和测试集，登记主指标、护栏、最小可检测效应、样本量与停止规则；非确定性输出应重复采样。
2. 对新旧版本执行成对离线评测，确定性任务以业务终态、Schema、规则或单元测试判分，开放任务采用结构化Rubric、校准后的LLM Judge与人工盲审。
3. 计算绝对增量Δ=M新−M旧、相对提升Δ/M旧，并报告胜平负比例、效应量、置信区间和显著性。多指标可构建效用分，但业务收益、风险、延迟与成本权重必须透明。
4. 按任务、难度、语言、风险和用户群切片；若总体提升来自简单样本占比变化，或高风险场景退化，则不能通过。
5. 离线达标后进行Shadow和稳定分桶A/B，验证真实完成率、转化、留存及人工处理时长。同步检查SRM、实验碰撞与新奇效应，护栏越界自动回滚。

最终应报告**每提升一个百分点完成率所增加的成本**及单次成功成本变化，使技术收益能够映射到业务ROI，并在上线后持续监控长期漂移。

**历史别名：** `GOV-128`。

**相关知识点：** 增量评估、效应量、置信区间、效用函数、成对测试、分层分析、单次成功成本、SRM、业务ROI。

### ENG-047 · 企业级 Prompt 管理平台如何设计？

> 稳定 ID：`ENG-047`｜原题号：47

企业级Prompt平台应覆盖**资产管理、协作研发、自动评测、安全治理和运行观测**，使Prompt从个人经验转化为受控的软件交付物。

1. 资产层以Registry保存模板、变量Schema、Few-shot、适用Agent、模型参数、Tool契约和知识库依赖；版本不可变并具备父子谱系、Diff与内容哈希。
2. 研发层提供结构化编辑、变量校验、沙箱调试、样本回放和Token估算；明确System、User、检索上下文及工具描述的拼装优先级，防止环境差异。
3. EvalOps层管理黄金集、历史失败和红队集，组合规则、单元测试、业务终态、校准Judge与人工评审；变更自动回归，比较质量、安全、延迟和单次成功成本。
4. 发布层实行开发、评审、候选、灰度、生产、废弃状态机，支持审批、Shadow、A/B、门禁、熔断与回滚；运行时只能引用已发布版本，禁止热修改。
5. 治理层实现SSO、RBAC/ABAC、租户隔离、密钥托管、PII脱敏、审计和配额。敏感变量不进入明文日志，高风险发布双人审批。

观测层将实验ID、Prompt版本、模型、检索、Tool轨迹、结果和业务终态关联到Trace，支持失败聚类和影响面定位。控制面与推理数据面解耦，并采用缓存和降级版本避免平台故障阻断服务。

**相关知识点：** Prompt Registry、控制面、数据面、版本谱系、EvalOps、RBAC、发布状态机、稳定分流、可观测性、灾备降级。

### ENG-048 · Prompt 日志应该记录哪些内容？

> 稳定 ID：`ENG-048`｜原题号：48

Prompt日志应支持**复现、评测、故障定位、成本归集和合规审计**，但不能把完整敏感上下文无差别落盘。

1. 请求身份记录Trace ID、任务ID、时间、租户、应用、Agent、实验桶、环境和父子关系；用户身份使用不可逆标识，避免记录明文账号。
2. 配置快照记录Prompt模板版本与内容哈希、渲染后Prompt哈希、模型及参数、路由策略、Tool契约、知识库与检索索引版本。只有具备授权时才保存加密正文。
3. 输入输出记录消息角色、Token数、截断位置、结构化输出、引用、拒答及完成原因；RAG还需记录查询改写、召回文档ID、分数、Rerank和证据片段来源。
4. Agent轨迹记录计划、工具名、参数摘要、权限决策、结束时间、返回码、重试、超时、状态转换和最终业务终态。密钥、Cookie、环境变量、PII及Tool敏感结果必须在采集前脱敏。
5. 质量与资源记录判分器版本、Rubric、任务成功、幻觉、安全标签、用户反馈、延迟、缓存命中、Token、模型与工具成本；发布、查询、导出和删除行为进入不可篡改审计日志。

日志采用字段白名单、分级权限、传输与静态加密、租户隔离、保留期限和删除策略。采样不能丢失高风险失败；正文与Trace元数据解耦，并通过受控回放环境复现，兼顾诊断能力与最小化收集原则。

**相关知识点：** Trace ID、配置快照、内容哈希、数据脱敏、字段白名单、审计日志、租户隔离、数据保留、可复现性。

### ENG-049 · 如何分析 Prompt 失败案例？

> 稳定 ID：`ENG-049`｜原题号：49

Prompt失败分析应从**现象复现、责任分层、根因验证到回归固化**形成闭环，避免看到错误输出便改措辞；失败可能来自Prompt，也可能来自上下文、模型、工具或评测器。

1. 保存最小可复现包，包括脱敏输入、会话历史、渲染后Prompt、模型参数、检索证据、Tool轨迹、业务终态及依赖快照；在隔离环境中重放，并多次采样验证稳定复现。
2. 依据预期行为和Rubric定位首个偏离点，将失败分类为指令冲突、变量缺失、上下文截断、检索错误、事实幻觉、格式违规、工具或参数错误、外部依赖失败。
3. 通过消融实验验证根因：只替换Prompt、模型、检索结果、Few-shot或Tool返回中的一个变量，并与基线成对比较。相关性、模型自我解释和成功重试均不能作为因果证据。
4. 评估严重度、频率、可恢复性和业务损失，使用帕累托图优先处理高频高损问题；聚类相似Trace，区分孤例、系统性缺陷及变点。
5. 修复应尽量局部，补充约束、反例、Schema或工具前置条件。随后运行回归、安全测试和成本检查，通过Shadow与灰度验证，防止修复一个案例破坏邻近场景。

确认后的失败样本经脱敏、去重加入历史缺陷集，记录根因、修复版本、责任层和防复发措施。若根因属于Tool、数据或模型，应修复对应层，避免Prompt承担无法可靠解决的问题。

**相关知识点：** 最小可复现包、首个偏离点、错误分类、消融实验、因果归因、失败聚类、帕累托分析、历史缺陷集。
<a id="eng-050"></a>
### ENG-050 · Prompt 优化和模型微调（Fine-tuning）应该如何选择？

> 稳定 ID：`ENG-050`｜原题号：50

应遵循**先诊断、先Prompt与系统工程，后微调**：Prompt适合改变任务说明；微调适合用样本稳定改变行为分布。知识更新通常应交给RAG，而非微调。

| 维度 | Prompt优化 | Fine-tuning |
|---|---|---|
| 变更对象 | 上下文 | 模型权重 |
| 优势 | 快速、易回滚 | 行为稳定 |
| 局限 | 规则易冲突 | 训练成本高 |

1. 任务边界、输出Schema、Few-shot、工具选择、检索利用和安全约束不清时，优先优化Prompt、Tool契约、RAG和验证器；这些问题易解释且迭代快。
2. 当高质量示例充足、行为模式重复，且Prompt过长或仍不稳定时，考虑SFT；典型场景包括固定风格、结构化抽取、领域表达和工具调用习惯。
3. 需要偏好对齐可使用DPO等方法；需要注入频繁变化的事实应使用RAG。微调不能可靠替代权限控制、事实数据库、业务规则和执行后校验。
4. 建立共同Benchmark，比较基线、Prompt、微调及组合方案的完成率、事实性、安全、P95、Token、训练与推理成本、维护周期。
5. 微调需进行脱敏、去重、训练验证隔离和遗忘测试；发布仍须配合System Prompt、工具护栏、灰度和回滚。

工程上常采用“微调固化共性能力，Prompt表达租户与任务差异，RAG提供动态知识”的组合，以总拥有成本和单次成功成本决定是否值得训练。

**相关知识点：** Prompt Engineering、SFT、DPO、RAG、权重更新、灾难性遗忘、数据治理、总拥有成本、组合架构。

### ENG-051 · 什么场景应该优化 Prompt，什么场景应该进行 Fine-tuning？

> 稳定 ID：`ENG-051`｜原题号：51

选择依据是问题发生在哪一层：**任务指令、上下文和流程问题优化Prompt；跨样本持续存在的模型行为偏差才考虑Fine-tuning**。动态知识用RAG，权限约束用护栏。

1. 适合Prompt的场景包括任务目标不清、输出格式不稳、角色边界模糊、Few-shot不足、工具选择错误和检索证据未利用。这类需求变化快、样本少，便于快速回滚。
2. 适合SFT的场景包括大量高质量示例具有稳定模式，模型需要持续输出特定风格、结构化抽取或工具调用序列；Prompt过长、重复示例的Token成本高，且优化后仍波动。
3. 偏好、语气和排序可用DPO；变化的企业事实不应写入权重，而应进入可更新、可引用的知识库。复杂规则由规则引擎和验证器执行。
4. 微调前需证明基座模型具有目标能力，准备许可清晰、脱敏、去重的数据，并建立训练、验证、隐藏测试集；样本不足或标签不一致时可能放大偏差。
5. 使用同一Benchmark比较Prompt、微调与组合方案的任务成功、事实性、安全、延迟、Token、训练成本和维护成本。只有长期收益覆盖数据、训练、部署与监控成本时才训练。

常见企业方案是**微调固化通用行为，Prompt承载任务策略，RAG提供动态知识，Tool执行确定性动作**，各层职责分离比单纯依赖一种技术更稳定。

**相关知识点：** 问题分层、Prompt Engineering、SFT、DPO、RAG、规则引擎、灾难性遗忘、数据质量、TCO。

### ENG-056 · LSP（Language Server Protocol）在Coding Agent中发挥什么作用？

> 稳定 ID：`ENG-056`｜原题号：56

2. 补全、签名帮助、重命名和代码动作可辅助跨文件修改；Diagnostics返回语法、类型和静态检查错误，构成**编辑—诊断—修复**闭环。

**相关知识点：** LSP、Language Server、Definition、References、Call Hierarchy、Diagnostics、Symbol Index、工作区版本、降级策略。

### ENG-073 · 当代码仓库持续变化时，如何实现索引的增量更新？

> 稳定 ID：`ENG-073`｜原题号：73

增量索引以**Git事件和内容哈希驱动子图重建**，通过版本构建与原子切换保证一致快照，不能在生产索引原地半更新。

1. 监听Push、Merge或文件事件，获取base/head Commit与Git Diff；识别新增、修改、删除、重命名，用内容哈希跳过重复内容。
2. 对变更文件重新分块、解析AST、提取Symbol和Embedding；未变化块复用向量。重命名保持Symbol谱系，删除项写墓碑，防止旧块召回。
3. 依据定义—引用、Import、继承、调用和模块依赖计算影响闭包，只重算邻边、上层摘要及受类型变化影响的文件；接口变化扩大范围，注释变化只更新文本与向量。
4. 更新生成独立版本，绑定仓库、分支、Commit、解析器和Embedding版本。校验文档、边、悬空引用与抽样查询后原子切换；失败保留旧版本。
5. 高频提交使用事件合并、去抖、批量Embedding和优先队列；查询可叠加实时小索引，再由后台合并主索引。租户隔离配额，避免大仓阻塞。

监控索引滞后、吞吐、解析失败、墓碑比例、版本不一致和Recall@K；定期全量校验。Agent会话固定索引版本，防止中途看到混合Commit。

**相关知识点：** Git Diff、内容哈希、影响闭包、墓碑、事件去抖、索引版本、原子切换、实时小索引、一致性校验。

### ENG-081 · 多分支、多版本并行开发场景，Agent 如何保证代码上下文匹配准确性？

> 稳定 ID：`ENG-081`｜原题号：81

### ENG-098 · 静态调用链与运行时调用链有什么区别？

> 稳定 ID：`ENG-098`｜原题号：98

静态调用链回答**代码中可能发生什么**，运行时调用链回答**某次或某类流量实际发生了什么**。前者偏高召回，后者偏高精度，二者不能互相替代。

| 维度 | 静态调用链 | 运行时调用链 |
|---|---|---|
| 数据来源 | 源码、类型、配置 | 插桩、Profiler、APM Trace |
| 覆盖范围 | 未执行路径也可分析 | 仅覆盖观测流量 |
| 主要误差 | 多态候选多、动态边缺失 | 冷门路径缺失、采样偏差 |

1. 静态链通过AST、编译器、LSP、类层次或指针分析生成，不必运行系统，适合影响分析、安全扫描和测试选择；但反射、动态代理、依赖注入、配置路由与动态语言会造成缺边或过度扩张。
2. 运行时链记录真实接收者、调用顺序、耗时、异常和频次，能跨进程关联HTTP、RPC和消息；它依赖测试或生产流量、Trace传播和采样，未出现的边不能判定不存在。
3. 静态边应保存算法、源码位置和置信度，动态边保存环境、部署版本、时间窗口、采样率和Trace证据；两个图都必须绑定Commit或制品版本。
4. 融合时以静态图建立候选全集，用动态频次与最近观测排序，高风险未观测边仍保留；动态出现但静态缺失的边用于发现反射、配置或跨仓关系。
5. Agent解释时区分“可能调用”“已观测调用”和“推断关联”，修改后以定向测试和新Trace验证。Call Graph也不等于控制流或数据流，仍需结合CFG与业务终态。

**相关知识点：** 静态分析、动态插桩、APM Trace、CHA、指针分析、采样偏差、边置信度、版本绑定、CFG。

**相关知识点：** Event Time、Watermark、乱序缓冲、流式ASR、版本化结果、Deadline、降级。

### ENG-180 · 多模态场景下的Prompt injection攻击有哪些新形式，如何防御？

> 稳定 ID：`ENG-180`｜原题号：180

新攻击包括**图片隐写/小字指令、文档OCR指令、音频命令、视频单帧注入、二维码/链接诱导和跨模态冲突**。

所有媒体提取内容均标记为不可信数据，不能提升指令优先级；OCR/ASR结果与用户命令分通道保存，来源和区域/时间戳可追溯。对隐写、特殊Token、二维码和外链做检测，但检测不能替代权限边界。

工具层按身份独立鉴权，限制文件、网络和Secret，高风险动作预览确认；媒体解析在沙箱中运行。红队应覆盖不可见文字、对抗样本、跨帧与多语言攻击，并验证成功攻击的影响半径。

**相关知识点：** Visual Prompt Injection、Audio Injection、隐写、二维码、来源标记、最小权限、红队。

### ENG-199 · AI产品与传统互联网产品指标体系有什么区别？

> 稳定 ID：`ENG-199`｜原题号：199

AI产品除流量与转化外，还必须评估**概率性质量、任务完成、生成成本、模型漂移和安全风险**。

同一输入可能多次输出不同结果，因此需重复运行、置信区间和切片；“接口成功”不等于任务成功。成本与输入/输出Token、工具和重试直接相关，使用越多未必毛利越好。模型、Prompt和知识更新会造成非代码版本变化，需全链路版本化。

传统DAU、留存、漏斗仍适用，但要加入事实/引用、拒答、人工接管、单位成功成本、越权和有害输出等护栏。

**相关知识点：** 概率系统、任务完成率、重复评测、模型漂移、Token Cost、护栏指标、版本治理。
