### Agent的任务是怎么拆分的？拆分粒度是怎么决定的？（百度Agent）

任务拆分应形成**目标明确、依赖可表达、结果可验证、失败可恢复**的DAG；粒度由复杂度、副作用、并行性、验证成本和上下文决定。

1. 将目标标准化为输入、产物、验收、约束和禁止动作；识别澄清、信息获取、规划、执行、验证与交付阶段，缺少关键参数时先澄清。
2. 每个Step只有一个主要意图，具备输入输出Schema、工具、资源、预算、超时、重试和完成条件；步骤以数据、控制与副作用依赖构成DAG。
3. 过粗会使上下文膨胀、失败难归因；过细会增加调用和状态成本。以“可由一次工具或受控推理完成，并能独立验证”为边界。
4. 不相交资源和只读分析可并行；共享文件、数据库写入与发布需串行或加锁。高风险副作用前设Dry Run和门禁，执行后验证终态。
5. 运行中可按新证据重规划，但已完成副作用不能覆盖；生成新Plan Version，保留Attempt与检查点，设置深度、步骤、Token和时间预算。

评估步骤成功率、重试局部性、关键路径、并行度、验证覆盖和完成率。高频失败步骤再拆分，无独立验证价值的步骤合并。

**相关知识点：** Task Decomposition、DAG、Step Schema、粒度控制、关键路径、动态重规划、Verifier、检查点、重试局部性。

### MCP、Tool Calling、RAG返回结果最终如何统一进入LLM？

MCP、Tool Calling和RAG职责不同，进入LLM前应统一成**带类型、来源和版本的消息或Artifact**，由编排器渲染。

1. Tool Calling是模型产生的Tool与参数；MCP提供发现、Schema和协议。网关校验权限和结果后生成ToolResult。
2. RAG完成召回、过滤和Rerank，返回DocumentResult，含SourceID、ChunkID、摘要、分数和Citation；它是证据而非回执。
3. Envelope含type、content、source、version、trustLevel、trace和artifactId。大结果写对象存储，上下文只放摘要。
4. Context Builder按相关性、可信度和预算选择与压缩；RAG放证据区，ToolResult放tool消息，MCP资源转Artifact。
5. Adapter映射为system、user、assistant、tool或多模态块；不支持Tool角色时转为有边界的结构文本。

外部内容均为不可信数据，不能授权调用；Prompt保留Citation，Verifier检查引用和终态，Trace关联检索、调用与裁剪。

**验证指标：** 任务完成率、测试通过率、变更接受率、交付周期和单位任务成本。

**相关知识点：** MCP、Tool Calling、RAG、ToolResult、Context Builder、Envelope、Artifact、Model Adapter、Citation、指令数据隔离。

### Few-shot 示例应该如何设计？

Few-shot的目标是通过**少量高信息密度示例显式传递任务边界、推理模式和输出格式**，不是堆积相似问答。示例质量、覆盖和顺序通常比数量更重要。

1. 先确定示例要解决的问题：格式不稳定、类别边界、工具选择、拒答或复杂推理。规则已能清楚表达时无需示例，避免重复占用上下文。
2. 示例应代表真实输入分布，覆盖典型、边界、易混淆、异常和应拒绝场景；输入结构、字段、语言和输出Schema与生产一致，不能使用与任务无关的演示数据。
3. 每个示例提供明确输入与理想输出，必要时给简短决策依据或可观察步骤，但不暴露敏感内部信息；Tool示例应展示正确参数、错误处理和停止条件，而非只展示成功路径。
4. 保证标签与答案经专家校验，删除歧义、重复和相互冲突的示例。避免类别数量失衡、固定位置偏差和过度文风暗示；可随机顺序评估模型是否依赖表面模式。
5. 静态Few-shot适合稳定规则，动态Few-shot可根据查询从经审核的示例库检索相似且多样的样本；检索需做权限、去重、新鲜度和Token预算控制，不能将用户内容直接变成新示例。

通过消融实验比较Zero-shot与不同示例组合，评估完成率、边界准确率、格式合法率、安全、Token和延迟，并检查关键分层回归。示例库、选择器和模板均需版本化。

**相关知识点：** Few-shot、Zero-shot、示例选择、边界样本、类别平衡、动态Few-shot、示例检索、消融实验、Token预算。

### 为什么 Few-shot 数量过多反而会降低效果？

Few-shot过多会降低效果，根因是**边际信息下降，而上下文竞争、噪声、偏差和成本上升**；模型不会无损归纳所有示例。

1. 上下文窗口有限，示例占用Token会挤压真实输入、RAG证据、工具结果和输出空间；重要指令可能被稀释，长上下文还会出现Lost-in-the-Middle。
2. 重复示例不增加新规则，却放大特定措辞，使模型模仿表面格式而非理解任务；示例分布与线上不同还会造成局部过拟合。
3. 示例之间若存在轻微标签、边界或格式冲突，模型难判断优先级；类别不平衡会形成先验偏置，排序固定还会产生位置与近因效应。
4. 长Prompt增加注意力计算、首Token延迟和费用，也扩大Prompt Injection与敏感数据暴露面；动态示例检索若相关性不足，会把无关信息误当成高权威模式。
5. 复杂任务中，过多完整推理示例可能限制探索，让模型机械复制不适用路径；工具场景还可能诱发错误Tool选择或沿用旧参数。

优化方法是选择少量互补示例，覆盖典型、易混淆、边界和拒绝场景；先去重、统一Schema和标签，再动态检索，并设置多样性和Token预算。通过数量消融比较完成率、安全、延迟与成本，选择收益平台化前的最小集合。

**相关知识点：** 上下文竞争、边际信息、Lost-in-the-Middle、位置偏差、类别不平衡、动态示例检索、消融实验、Token预算。

### CoT 为什么能提升复杂任务效果？

CoT把复杂问题转化为**可衔接的中间状态与局部推理步骤**，降低从输入直达答案的搜索难度，因此对数学、逻辑、多跳和规划任务更有效。

1. 分步表示使模型能够保留中间变量、约束和子目标，减少工作记忆混乱；每一步只解决局部关系，比直接预测最终答案更接近训练语料中的解释与解题模式。
2. 显式步骤提供计算草稿，便于执行分解、条件检查、单位换算和错误回溯；配合Self-Consistency可从多条路径投票，降低单一路径偶然错误。
3. CoT还能为Verifier提供过程证据，在关键步骤调用计算器、检索或规则校验；但自然语言推理并不天然忠实，写得合理不代表真实决策依据，最终仍需外部验证。
4. 简单任务使用长CoT可能增加Token、延迟和错误传播，使模型过度思考；知识缺失、工具不可用或权限问题也不能靠增加推理步骤解决，应按任务难度路由。
5. 工程上可要求“先规划、再执行、后验证”，但不必向用户暴露完整内部推理；更适合保存结构化计划、关键假设、证据引用和可检查中间结果，兼顾可审计与安全。

评估时比较Direct Answer、CoT及工具增强方案在相同模型和预算下的完成率、关键分层、稳定性、Token和时延，并通过步骤扰动或反事实测试检查是否真正利用中间结果。

**相关知识点：** Chain-of-Thought、任务分解、工作记忆、Self-Consistency、Verifier、工具增强推理、过度思考、过程忠实度。

### ReAct 和 CoT 的区别是什么？

CoT侧重**连续推理**，ReAct将推理与Action、Observation交替；需要实时信息或Tool时优先ReAct，封闭推理更适合CoT。

| 维度 | CoT | ReAct |
|---|---|---|
| 循环 | Reason→Answer | Reason→Action→Observation |
| 信息 | 已有上下文 | 动态检索、工具 |
| 风险 | 幻觉、错误累积 | 误用、循环、副作用 |

1. CoT拆成中间步骤，适合数学、逻辑和证据充分的多跳任务；它不能获取缺失事实，错误前提会沿链传播。
2. ReAct每轮选择Search、RAG、API或代码执行，再将Observation反馈模型，适合开放世界、实时数据和执行任务。
3. ReAct需要Tool Schema、权限、幂等、沙箱和审计，并设置步骤、Token和停止条件；Observation不能覆盖系统规则。
4. 二者可组合：Planner用短CoT形成假设，ReAct取证并执行，Verifier检查终态；无需工具的步骤不强制调用。
5. 不把自然语言Thought当审计依据；保存Plan、Action、Observation、证据和摘要，正确性由规则、测试或外部系统验证。

选择应按任务比较完成率、事实性、Tool成功、步骤、延迟、成本和安全，而非固定一种范式。

**相关知识点：** ReAct、Chain-of-Thought、Action、Observation、Tool Schema、停止条件、工具增强推理、Verifier、过程忠实度。

### ToT 相比 CoT 的优势是什么？

ToT的优势是**维护多个候选状态，并通过评估、搜索和回溯选路径**；问题存在早期分叉、局部最优或组合规划时，比单链更稳健。

| 维度 | CoT | ToT |
|---|---|---|
| 搜索结构 | 单条线性链 | 分支树或状态图 |
| 纠错 | 继续或重启 | 评分、剪枝、回溯 |
| 代价 | 较低 | Token和延迟较高 |

1. CoT早期假设错误后可能持续自洽；ToT在关键节点生成多个Thought或Action候选，保留替代方案，降低错误传播。
2. ToT可结合BFS、Beam Search或MCTS，按可行性、约束、收益和风险评分，剪掉重复、无效或超预算分支，适合代码修复与规划。
3. 候选评估不只依赖同一模型，可使用规则、单元测试、检索、Tool、Judge或人工；状态需包含已满足约束、未决问题和累计成本。
4. 简单任务使用树搜索会增加成本，评估器偏差也可能剪掉正确路径；需设置分支数、深度、Beam宽度、Token和停止条件。
5. 先判断是否有高不确定分叉，仅对关键节点启用ToT，其余使用CoT或ReAct；搜索结果由Verifier验证。

选择应比较相同预算下的完成率、路径命中、回溯、延迟与成本，关注复杂任务的边际收益。

**相关知识点：** Tree of Thoughts、Chain-of-Thought、Beam Search、MCTS、状态评分、剪枝、回溯、搜索预算、Verifier。

### Reflection 如何提升 Agent 成功率？

Reflection通过**外部验证、错误归因和受控修复循环**，把一次性失败转为可定位、可重试的局部问题；有效性来自证据反馈。

1. Verifier检查Schema、业务终态、单元测试、引用、安全和预算，生成结构化错误，包括失败类型、证据、严重度和可恢复性。
2. Reflector读取目标、计划、状态与证据，按Failure Taxonomy提出根因、最小修复和验证方式；不得修改成功标准或注入无关历史。
3. 修复包括纠正Tool参数、重新检索、替换证据、调整局部计划或切换Tool；写操作必须有幂等键和终态查询，未知时禁止重放。
4. 设置反思轮数、Token、时间、重试和成本预算，检测相同状态与振荡；连续失败、低置信、高风险或不可逆操作转人工。
5. 记录Attempt、诊断、修改、验证和成本，形成Trace；高频成功修复沉淀为规则，高频误修加入回归集并降低权限。

离线评估修复成功率、误修率、循环数、净完成率和成功成本；线上先Canary。**没有独立Verifier的Reflection可能只把错误解释得更流畅**。

**相关知识点：** Reflection、Verifier、Failure Taxonomy、受控重试、幂等性、振荡检测、检查点、人工接管、故障注入。

### Plan-and-Execute 与 ReAct 如何选择？

Plan-and-Execute适合**目标明确、依赖多、可并行且需全局协调**的长任务；ReAct适合信息不全、环境变化快的任务，常采用混合模式。

| 维度 | Plan-and-Execute | ReAct |
|---|---|---|
| 决策 | 先规划再执行 | 每轮观察后行动 |
| 优势 | 全局一致、可并行 | 适应性强 |
| 风险 | 计划过时 | 局部贪心、循环 |

1. 软件迁移、报告、跨系统流程和多Agent协作具有稳定子目标与DAG，适合先规划；计划定义Step输入输出、工具、预算、验收及副作用顺序。
2. 故障排查、搜索和动态网页操作需根据Observation修正假设，更适合ReAct；必须设置步骤、Token、时间、重复检测与停止条件。
3. 高风险任务优先显式计划，以便在副作用前校验权限、Diff和审批；ReAct每个Action仍需Policy Engine校验。
4. 混合方案由Planner生成里程碑，Executor在Step内使用ReAct；关键假设、资源或目标变化时生成新Plan Version。
5. 简单单工具任务不应完整规划，以降低调用和状态成本；无法可靠规划时也不强行预生成长步骤。

按任务比较完成率、重规划率、循环率、关键路径、并行度、成本和安全，依据数据动态路由。

**相关知识点：** Plan-and-Execute、ReAct、任务DAG、Observation、动态重规划、关键路径、停止条件、Policy Engine、混合编排。

### 如何评估 Agent 的任务完成率？

Agent任务完成率应衡量**业务目标是否在约束内正确达成**，而不是模型是否给出回复或某个工具返回成功；口径、分母和成功证据必须预先固定。

1. 定义有效任务与统计窗口。严格完成率等于结果通过验收、必要副作用成功且满足安全与SLA的任务数除以有效任务数；取消、恶意输入、测试流量和平台事故的处理规则需冻结。
2. 区分自主完成、澄清后完成、审批后完成、人工代办、失败和放弃；人工直接修正结果不能计入自主完成。同步报告首次通过率、重试后通过率与人工介入率。
3. 成功证据优先使用业务系统终态、单元测试、Schema、状态回读和用户确认；开放任务采用结构化Rubric及经人工校准的LLM Judge，保存规则版本、Trace和Artifact。
4. 按任务类型、难度、风险、租户、Agent、模型和Prompt版本分层，报告样本量、置信区间与趋势；总体完成率上升可能只是简单任务占比增加，需要标准化任务分布。
5. 配套护栏包括事实错误、引用忠实、安全违规、用户投诉、P95延迟、Token、单次成功成本和重复副作用，防止无限重试、降级质量或增加人工把指标刷高。

离线集用于快速回归，线上Shadow或A/B用于验证业务流量。定期抽检成功样本与失败分母，监控Judge漂移、标签延迟和任务分布变化，确保指标可审计。

**相关知识点：** 严格完成率、自主完成率、首次通过率、业务终态、分层统计、置信区间、护栏指标、Judge校准、分母漂移。

### 如何量化幻觉率？

幻觉率应定义为**输出中缺乏证据、违背证据或虚构事实的可验证主张占比**，不能简单用整条回答对错替代；企业评测必须同时覆盖主张级、回答级和高风险事件级口径。

1. 先将回答拆成原子主张，标注可验证事实、推断、意见和无需外部验证的表达。对事实主张依据权威知识快照、检索证据、工具终态或业务数据库判定为支持、矛盾、证据不足。
2. 主张级幻觉率为错误与无依据主张数除以全部事实主张数；回答级幻觉率为至少含一个严重幻觉的回答数除以有效回答数。按严重度加权，身份、金额、医疗、安全等错误权重高于非关键描述。
3. RAG场景应报告**事实正确率、引用正确率和引用完整率**：引用存在不等于内容被证据支持；还要检测伪造链接、跨段拼接、知识过期及检索无证据时强行作答。
4. 自动评测可采用NLI、规则、知识库核验和经人工校准的LLM Judge组合。Judge需看到证据和Rubric，使用双盲抽检、多人一致性及置信区间校准，不能让被测模型自判。
5. 指标按领域、难度、是否检索、模型、版本和风险分层，并与拒答率、覆盖率、任务完成率联看；通过大量拒答降低幻觉会损害可用性。

线上抽样真实流量，回放高风险失败，保存证据版本、判定理由和Trace。知识更新后重评历史样本，区分当时可知事实与变化，避免将数据漂移误判为幻觉。

**相关知识点：** 原子主张、事实一致性、Groundedness、引用忠实度、NLI、LLM Judge、严重度加权、拒答率、知识快照。
<a id="eng-037"></a>
### Agent 的自动化评测平台如何设计？

Agent自动化评测平台应建设为**数据集、运行编排、判分、分析和发布门禁一体化系统**，同时复现模型推理、工具副作用和业务终态，而非只比较最终文本。

1. 数据层管理黄金集、历史失败、安全对抗和合成样本，保存任务输入、环境快照、期望行为、Rubric、标签、难度和版本；开发集、回归集和隐藏集隔离。
2. 执行层在可重置沙箱中固定模型、Prompt、Tool、知识库与依赖版本，支持并发、超时、重试和多轮状态回放；外部写操作由Mock、影子环境或事务回滚承接。
3. 判分层组合确定性断言、Schema校验、单元测试、业务终态、规则、人工标注和经校准的LLM Judge，分别评估任务成功、轨迹效率、事实性、安全、延迟、Token与成本。
4. 分析层按任务、难度、风险、租户和版本切片，提供显著性检验、失败聚类、Trace与Artifact下钻，识别模型退化、数据漂移和Judge漂移。
5. 平台接入CI/CD，设置核心成功率不可下降、安全零容忍、成本与P95预算等门禁；高风险变更经过离线评测、Shadow、灰度和线上A/B，支持自动停止与回滚。

平台自身需具备租户隔离、凭据托管、审计、数据脱敏、资源配额和结果可追溯能力。线上失败回流数据集，要去重、防泄漏并冻结知识快照，形成可持续评测闭环。

**相关知识点：** EvalOps、黄金集、环境快照、轨迹评测、LLM Judge、故障注入、显著性检验、发布门禁、Shadow、数据回流。
<a id="eng-060"></a>
### Agent如何处理动态调用、反射和依赖注入导致的调用链分析难题？

动态调用无法仅靠AST精确还原，应采用**静态候选扩张、框架语义解析、运行时观测和置信度建模**，输出“可能边”而非唯一调用目标。

1. 静态阶段提取反射API、字符串类名或方法名、接口调用、工厂、回调、注解、代理和容器获取点；结合常量传播、类型推断、类层次分析及指针分析缩小候选集合。
2. 针对Spring、Guice等依赖注入框架解析Bean定义、注解、Qualifier、条件装配和配置文件，将注入点连接到可能实现；对AOP补充代理、拦截器和目标方法边。
3. 对RPC Stub、路由、消息Topic和插件注册表解析协议或配置，将生产端与消费端、客户端与Handler关联；配置版本必须绑定环境与部署快照。
4. 使用单元测试插桩、Profiler、APM Trace、Service Mesh和覆盖率数据收集实际接收者与调用频次。动态边准确但只覆盖观测流量，不能把“未出现”解释为“不可能”。
5. 图中为边记录静态/动态来源、分析算法、环境、版本、时间和置信度。查询时优先动态高频边，再扩展静态候选，并通过深度、节点预算、环检测和权限控制图膨胀。

修改前应对低置信路径请求更多证据，修改后通过定向测试和运行时Trace验证。静态分析保证召回，动态证据提高精度，两者结合才能在可解释性与完整性之间平衡。

**相关知识点：** 反射、依赖注入、AOP、常量传播、指针分析、CHA、运行时插桩、动态Call Graph、边置信度。
<a id="eng-061"></a>
### Progressive Context Building为什么比一次性加载全部上下文更高效？

Progressive Context Building按任务证据逐步扩展**最小充分上下文**，可降低Token、延迟与噪声，并让Agent根据中间结果修正检索方向；一次性加载容易超窗。

1. 首轮只注入任务、仓库规则、Repo Map和高置信摘要；再通过Symbol、BM25、Embedding、AST和调用图读取定义、引用、配置与测试，而非猜测全部文件。
2. 每次Observation更新工作记忆：保留已确认事实、Commit、证据和未决问题，删除重复内容，将旧轨迹压缩为摘要。重要源码片段保留原文与行号，避免失真。
3. 分阶段设置Token预算、候选数和停止条件。新证据信息增益低、关键依赖闭合或验证满足时停止；编译或测试失败时沿错误链局部补充。
4. 该方式减少注意力稀释与“中间信息遗失”，缓存命中更高，只更新受影响片段；每次读取前校验权限，降低敏感代码与注入文本暴露面。
5. 早期检索错误可能导致遗漏，因此需要多路召回、探索配额、低置信回退和覆盖检查。决策应追溯到证据，不能只依据递归摘要。

效果可用任务完成率、Recall@K、无关上下文占比、Token、检索轮数、P95和单次成功成本评估，并与固定上下文基线做分层实验。

**相关知识点：** 渐进式上下文、最小充分上下文、信息增益、工作记忆、上下文压缩、注意力稀释、停止条件、多路召回。
<a id="eng-062"></a>
### Context Window不足时有哪些上下文压缩策略？

上下文不足时应优先**删除无关与重复信息，再结构化摘要，最后外置可恢复状态**；目标不是最短，而是在Token预算内保留证据、约束和因果链。

1. 相关性裁剪：按任务、Symbol、调用距离、新鲜度和检索分数排序，移除无关文件、生成物、重复日志、已完成工具回显及对话；System约束、安全规则和用户目标不得丢失。
2. 结构化摘要：将轨迹压缩为目标、已确认事实、决策、失败尝试、未决问题和下一步；代码采用Repo、模块、文件、函数分层摘要，并保留路径、Commit和行号引用。
3. 源码压缩：只保留目标函数、相关类型、调用者/被调用者及配置；函数体可折叠为接口与副作用摘要，但正在修改的代码、测试断言和错误现场应保留原文。
4. 工具结果压缩：日志去重、聚类并保留异常栈，表格只保留命中行，检索候选执行去重与Rerank；大Artifact存入外部对象存储，上下文保留句柄和摘要。
5. 分层记忆与滚动窗口：工作记忆保存当前步骤，长期记忆保存稳定项目事实；阶段切换建立Checkpoint，需要时按引用重新检索，避免摘要递归失真。

压缩后执行覆盖检查，确认目标、硬约束、关键证据和未决风险仍存在。通过任务完成率、证据召回、压缩比、Token、延迟及摘要事实一致性评估，并在低置信时回读原文。

**相关知识点：** 相关性裁剪、分层摘要、滚动窗口、外置Artifact、Checkpoint、工作记忆、压缩比、摘要一致性。
<a id="eng-063"></a>
### Agent如何判断哪些代码需要加入上下文，哪些可以忽略？

Agent应以**当前任务的最小证据闭包**选择代码，综合相关性、结构、运行证据、风险和Token预算，不能仅按向量相似度取Top K。

1. 从目标提取实体、动作、错误、约束和验收条件，用路径、BM25、Embedding和Symbol召回入口、定义及测试；修Bug优先栈、调用者和回归测试。
2. 以目标Symbol为种子，沿定义—引用、调用、继承、Import、配置和测试限深扩展。直接调用、接口实现、数据模型及安全校验权重高，无关系证据的片段降权。
3. Reranker综合词法、语义、路径、图距离、Git共变、新鲜度、运行频次和权限；过滤重复片段、生成文件、Vendor、构建产物和无关历史版本。
4. 按“原文、摘要、引用”分级：待修改代码、契约、断言和错误现场保留原文；稳定模块用签名与摘要；大日志、旧轨迹和低置信候选外置。
5. 根据编译、测试、LSP诊断和Observation动态增删。出现未解析Symbol、缺失类型或新错误时补充；关键依赖闭合且验证通过时停止。

记录来源、分数、Commit和理由并做覆盖检查。离线以Recall@K、无关上下文率、完成率和Token评估，避免过度裁剪。

**相关知识点：** 最小证据闭包、Hybrid Search、图扩展、Rerank、上下文分级、动态组装、覆盖检查、无关上下文率。
<a id="eng-065"></a>
### Agent如何利用长期记忆（Long-term Memory）减少重复分析？

长期记忆应保存**跨任务稳定、可验证且可复用的项目知识**，并通过检索按需注入；它不是对话归档，更不能将模型推断直接永久化。

1. 记忆内容包括架构与模块职责、术语、构建测试命令、代码规范、关键Symbol、依赖关系、历史决策、常见故障及已验证修复。临时计划、未证实猜测和敏感凭据不应进入长期层。
2. 每条记忆采用结构化Schema，记录租户/仓库/分支作用域、正文、类型、来源文件或Trace、Commit、置信度、权限、有效期和内容哈希，实现证据追溯与版本隔离。
3. 写入前执行事实校验、去重、冲突检测和密钥扫描；重要记忆由测试、业务终态或人工确认。更新采用新版本覆盖语义而非删除审计历史，代码变化通过Git Diff使关联记忆失效。
4. 新任务先按任务实体、Symbol、语义和图关系检索，结合新鲜度、置信度及权限Rerank；只注入Top K摘要和证据句柄，需要修改时回读当前源码，避免旧记忆污染。
5. 分层管理项目记忆、用户偏好、情景记忆和组织知识，隔离租户与访问控制。对高频稳定事实建立缓存，对低频内容保留外部索引，减少上下文与存储成本。

效果以重复工具调用下降、定位时长、Token、记忆命中后成功率和陈旧记忆误导率评估。定期执行TTL清理、抽样复核和冲突合并，确保“记住”带来的收益高于错误传播风险。

**相关知识点：** 长期记忆、情景记忆、结构化Schema、来源追踪、记忆失效、冲突检测、权限隔离、TTL、检索注入。
<a id="eng-068"></a>
### Git历史、Commit记录和Code Ownership如何帮助代码定位？

Git历史与Ownership提供**时间语义、变更动机和责任边界**，可补足文本、AST无法回答的“为何实现、哪些文件共变、谁了解风险”。

1. `git log`、Blame和Diff能定位代码的引入、修复与重构；提交说明、Issue和PR揭示业务原因、替代方案及限制，避免恢复已否定实现。
2. 历史共变识别同一Commit中常被共同修改的文件或Symbol；即使没有静态调用边，也可能受同一配置、协议或业务流程约束，可用于影响分析。
3. 按错误码、Symbol、路径和提交语义检索历史补丁，比较修改、测试与回滚；旧补丁只能作证据，必须校验当前架构和依赖。
4. CODEOWNERS、Blame贡献度和维护记录可确定评审人、专家及敏感区域。Ownership应结合近期贡献和评审，不能把最后修改者等同于负责人。
5. 排序加入新鲜度、共变、缺陷密度、所有权和任务实体；高风险变更请求Owner审批。索引绑定分支与Commit，重命名时维护Symbol谱系。

历史存在压缩提交、批量格式化、迁移和错误说明等噪声，应过滤机械变更并标注置信度。访问Commit、Issue和作者信息须遵守权限与隐私策略。

**相关知识点：** Git Blame、Commit Diff、历史共变、Symbol谱系、CODEOWNERS、专家推荐、变更动机、影响分析、置信度。
<a id="eng-075"></a>
### 如果代码存在循环依赖或复杂架构，Agent如何避免上下文膨胀并保持推理效率？

面对循环依赖，Agent应将代码关系图压缩为**强连通分量与摘要**，在有限预算内围绕任务路径展开；遍历整个依赖环只会重复加载同类信息。

1. 从目标Symbol构建调用、Import、继承、配置和数据依赖子图，识别强连通分量并将环折叠为超节点；记录入口、出口、公共契约和内部成员。
2. 查询先保留相关入口、出口、待修改Symbol、接口和测试；环内其他实现以签名或模块摘要表示。只有出现未解析类型、错误路径或验证失败时才展开成员。
3. 设置图遍历深度、节点数和Token预算，进行环检测与visited去重；依据图距离、边置信度、运行频次、Git共变和风险排序，低信息增益分支停止扩展。
4. 上下文分为原文、摘要和外部引用：修改代码、契约、断言及错误现场保留原文；稳定依赖折叠；大日志和历史轨迹外置。阶段结束将计划、事实、决策和未决问题写入Checkpoint。
5. 静态图过度保守时结合APM Trace、覆盖率或定向测试确定真实路径，但未观测边仍保留“可能”标签。对复杂架构可按有界上下文、服务或构建目标分解子任务，再由主Agent合并接口级结果。

同时应把循环依赖本身作为架构风险输出，而非在任务中擅自重构。效果通过任务完成率、重复片段率、图展开节点数、Token、P95和漏召回率评估。

**相关知识点：** 强连通分量、Tarjan算法、图折叠、环检测、信息增益、上下文分级、Checkpoint、有界上下文。
<a id="eng-084"></a>
### Repo Map 具体是怎么生成的？如何保证摘要既精简又不丢失关键信息？

Repo Map是**仓库结构与关键符号导航图**，由确定性解析生成骨架，再由模型压缩；精简依赖分层、预算和证据引用。

1. 扫描目录、构建清单、Workspace、CI和部署配置，排除二进制、生成物、Vendor与无权限文件；记录Commit、路径、语言、模块和哈希。
2. 用AST、编译器或LSP提取类、函数、接口、签名、定义/引用、Import、继承和实现，结合调用图、构建依赖、API/IDL与测试形成Repo—Module—File—Symbol图。
3. 计算公共接口、入口、引用度、调用中心性、业务关键度、变更/运行频次和安全敏感度；折叠同类工具、低价值叶子与重复Symbol，保留可展开句柄。
4. 固定Token预算：Repo层保留架构、入口和模块关系；Module层保留职责、API和上下游；File层保留职责与关键Symbol。待修改代码必须回读原文。
5. LLM只归纳职责、数据流和约束，输入为结构化事实；Schema区分事实、推断与未知，保存路径、行号、来源和置信度。检查入口、公共契约和高风险节点覆盖。

Git Diff触发File、Module到Repo摘要增量更新，新版本校验后切换。用Recall@K、事实一致性、关键节点覆盖率、压缩比和Token收益评估。

**相关知识点：** Repo Map、分层摘要、Symbol Graph、中心性、Token预算、来源追踪、覆盖检查、摘要DAG、增量更新。
<a id="eng-085"></a>
### 向量检索和关键词检索的结果如何做排序融合（Re-ranking 策略）？

融合采用**分数校准、合并和任务感知重排**。BM25与向量分数不可直接相加，优先用排名融合建立基线。

| 方法 | 特点 | 适用场景 |
|---|---|---|
| RRF | 按名次融合 | 默认方案 |
| 加权归一化 | 动态调权 | 有校准数据 |
| Learning to Rank | 学习多特征 | 标注充足 |

1. BM25、Embedding、Symbol各取Top K，按chunk hash去重，保留名次、分数和来源。RRF公式为score=Σ1/(k+rank)，常数k降低头部波动。
2. 加权前在同类查询内做Min-Max、Z-score或分位数校准；含类名、路径、数字和错误码时提高词法权重，自然语言提高向量权重。
3. 仅对少量候选用Cross-encoder或LLM Reranker，并加入Symbol命中、路径、AST类型、调用图距离、Git共变、新鲜度、权限和Owner特征。
4. 无权限、错误Commit和生成物先过滤；定义、引用或测试关系可Boost；限制同文件和重复工具占比，保证多样性。
5. 用Recall@K衡量召回，MRR、NDCG评估排序，并观察定位率、P95和成本。按查询类型评测，防止总体指标掩盖标识符退化。

线上用A/B或Interleaving验证任务成功并校正点击偏置。模型、权重和特征版本留痕，索引变化后重新校准。

**相关知识点：** RRF、分数校准、加权融合、Learning to Rank、Cross-encoder、Query Routing、NDCG、Interleaving、去重。
<a id="eng-086"></a>
### 当上下文窗口即将超限时，Compaction 的具体压缩算法是怎样设计的？

Compaction是**受约束的分层选择与摘要算法**：先定硬保留集合，再按信息价值分配Token，生成可追溯Checkpoint；不能直接截断旧消息。

1. 将上下文分为System约束、目标、计划、事实、源码、工具结果、Artifact和对话块，记录Token、来源、相关度、风险、依赖与可外置性。
2. 硬保留安全规则、当前目标、验收条件、待修改源码、契约、失败现场、未决问题和最新状态；文件路径、Commit、行号和Trace句柄一并保留。
3. 其余块计算U=w1·相关性+w2·新鲜度+w3·证据+w4·中心性+w5·风险−w6·冗余−w7·Token，在预算内用贪心或背包近似选择；相似块聚类去重。
4. 日志保留异常与统计，代码保留签名、目标函数和必要类型，轨迹压缩为“动作—结果—原因”；大内容外置，只留哈希、权限、范围和句柄。
5. 生成结构化Checkpoint：目标、事实、决策、修改、失败、风险和下一步。摘要引用来源，并用规则或Judge检查数字、路径、状态和否定词。

压缩后做覆盖与恢复测试，低置信时回读原文。指标包括压缩比、事实保持率、证据召回、完成率、Token和摘要漂移率，并限制递归层数。

**相关知识点：** Compaction、硬保留集、效用函数、背包近似、聚类去重、外置Artifact、Checkpoint、摘要漂移、可恢复性。
<a id="eng-090"></a>
### 如何评估 Agent 定位代码上下文的准确率（如何设计离线评测集）？

离线集把任务绑定到**冻结代码快照与最小证据集**，评估召回、排序、噪声和端到端可用性；只标一个文件会低估跨文件任务。

1. 样本来自Issue/PR、历史Bug、代码问答、线上失败和长尾；覆盖精确Symbol、自然语言、错误栈、跨文件/跨仓、动态调用、多语言和旧索引。
2. 保存repo、Commit、任务、Token预算、难度与类型；标注必需文件、Symbol、行区间、调用路径、配置、测试、关键事实及替代证据，禁止泄漏修复后信息。
3. 两名工程师独立标注并仲裁，用候选池化补充真值；开放任务允许多个最小证据集。记录依据和置信度，复核代码过期与标签漂移。
4. 指标包括File/Symbol/Chunk三级Precision@K、Recall@K、MRR、NDCG、证据完全覆盖率和无关上下文率；在统一Top K与Token下比较方案。
5. 固定Agent基于检索结果完成解释、修改或测试，报告完成率、首次通过、检索轮数、Token和P95，识别“检索分高但上下文不可用”。

数据划分开发、回归和隐藏集，按仓库或时间隔离。报告语言、规模、难度与任务分层结果和置信区间，线上失败去重后回流。

**相关知识点：** 黄金证据集、冻结Commit、候选池化、Precision@K、Recall@K、MRR、NDCG、证据覆盖率、数据泄漏。

### Hybrid Search通常如何融合排序？

Hybrid Search采用**并行召回—去重—融合—精排—规则约束**。BM25与向量分数尺度不同，未经校准不能直接相加。

1. 词法、向量、Symbol或图检索各取Top K，候选携带来源、名次、分数、文档ID、Commit和权限；按chunk hash或Symbol ID去重，保留多路命中。
2. 缺少标注时优先RRF：计算Σ1/(k+rank_i)，只依赖名次，对不同引擎较稳健；k用于降低头部波动。
3. 有校准集时对分数做Min-Max、Z-score、分位数或Platt校准，再按查询动态加权。标识符、路径、错误码提高BM25/Symbol权重，自然语言提高Embedding权重。
4. 只对少量候选用Cross-encoder、Learning to Rank或受控LLM Reranker，特征加入精确命中、路径、AST类型、调用图距离、Git共变、新鲜度和权限。
5. 最后硬过滤并控制多样性：错误租户、Commit、生成物删除，定义或测试关系Boost，限制同文件和重复工具占比。

离线在统一预算下比较Recall@K、MRR、NDCG、无关上下文率、P95和成本；线上用A/B或Interleaving验证任务成功。权重、模型、特征和索引版本留痕。

**相关知识点：** Hybrid Search、RRF、分数校准、动态加权、Cross-encoder、Learning to Rank、多样性、Interleaving、NDCG。
<a id="eng-097"></a>
### 调用链（Call Graph）是如何生成的？

Call Graph通过**解析调用点、解析目标Symbol并建立有向候选边**生成；静态图强调可能调用，动态图记录观测，通常融合两者。

1. 使用编译器前端、AST或LSP提取函数/方法定义、调用表达式、类型、Import、继承和实现关系，为每个Symbol分配绑定Commit、全限定名和签名的ID。
2. 对直接调用执行名称绑定、作用域、重载和参数类型解析；接口、抽象类和虚方法用类层次分析、快速类型分析或指针分析枚举可达实现，并排除不可能接收者。
3. 对反射、依赖注入、工厂、回调、AOP、RPC和消息路由，解析注解、容器配置、IDL、路由表及Topic，建立低置信候选边；环境和配置版本必须留痕。
4. 通过测试插桩、Profiler、APM Trace或字节码Agent采集调用目标、顺序和频次，补全动态边。运行时证据精确但覆盖有限，未观测不能证明边不存在。
5. 图节点保存可见性和权限，边保存caller、callee、源码位置、静态/动态来源、算法与置信度。查询支持上游、下游、限深、环检测和路径排序。

Git Diff触发变更Symbol和受类型、继承影响邻域的重算，新图校验悬空边、覆盖率后原子切换。Call Graph不表示控制流和数据依赖，影响分析仍需结合CFG、数据流、测试与业务终态。

**相关知识点：** Call Graph、名称绑定、CHA、RTA、指针分析、动态插桩、APM Trace、边置信度、CFG、增量图。
<a id="eng-099"></a>
### 如何处理反射、动态代理导致的调用链缺失？

反射与代理导致的缺边应通过**静态候选恢复、框架语义解包和运行时观测补全**处理；输出带置信度的候选，不能伪造唯一目标。

1. 识别Class.forName、Method.invoke、字符串类/方法名、工厂与回调，进行常量传播、字符串分析、类型推断和指针分析，缩小接收者集合。
2. 对Spring、Guice等容器解析Bean、注解、Qualifier、条件装配和配置，将注入点连接到实现；对JDK/CGLIB代理及AOP解析代理—拦截器—目标Bean—方法链。
3. 对RPC Stub、插件、SPI、路由和消息Topic解析IDL、注册表与配置中心，建立客户端—服务端、生产者—消费者边，并绑定环境与版本。
4. 使用单测插桩、字节码Agent、Profiler、APM Trace或Service Mesh采集接收者与频次。动态证据精确但覆盖有限，未观测静态边保留“可能”标签。
5. 图边记录来源、算法、源码位置、配置、环境、Commit和置信度；查询优先已证实边，再展开候选，并设置深度、环检测和节点预算。

通过针对反射参数、代理实现和不同Profile的定向测试提高覆盖，修改后比较新旧Trace。监控动态边补全率、静态/动态一致性、误报和漏报；低置信关键路径需请求更多证据或Owner确认。

**相关知识点：** 反射分析、字符串分析、动态代理、AOP、依赖注入、SPI、运行时插桩、边置信度、Profile。
<a id="eng-104"></a>
### 如何对检索结果进行Rerank？

Rerank在高召回候选上执行**更精确的相关性判断**，目标是在固定Top K与Token内提升首个有效证据位置和上下文纯度。

| 方法 | 优势 | 代价 |
|---|---|---|
| 规则加权 | 快、可解释 | 泛化有限 |
| Cross-encoder | 深度交互 | 计算较高 |
| LLM Reranker | 理解集合关系 | 慢、成本高 |

1. BM25、Embedding、Symbol和Graph召回候选，RRF合并去重；租户、Commit、权限和生成物在精排前硬过滤。
2. 特征包括词法命中、向量分、Symbol类型、路径、AST邻近、调用图距离、Git共变、新鲜度、频次、Owner及任务类型；分数按查询类型校准。
3. Cross-encoder输入查询与Chunk，适合Top 50到Top 10的两阶段排序；训练使用正例及同名、相邻、语义相似但无关的难负例。
4. 跨文件可用Set-wise或LLM重排，判断集合是否覆盖入口、契约、实现和测试；提供Rubric、Schema、超时与回退，不能改写证据。
5. 设置多样性和每文件/模块上限，避免重复片段垄断窗口；定义、引用、测试关系可Boost，高风险证据保留探索配额。

离线报告MRR、NDCG、Recall@K、无关上下文率、P95和成本；线上以定位与任务完成率验证。模型、特征、权重和版本留痕。

**相关知识点：** Rerank、Cross-encoder、Learning to Rank、难负样本、Set-wise Ranking、多样性、MRR、NDCG、分数校准。
<a id="eng-105"></a>
### 上下文窗口有限时如何进行上下文裁剪？

上下文裁剪应遵循**硬约束不删、证据按任务价值排序、可恢复内容外置**，目标是在预算内保留最小充分上下文，而非简单截掉最早消息。

1. 将内容分为System/安全规则、用户目标、计划、事实、源码、工具结果和历史对话，记录Token、来源、Commit、相关性、风险、冗余和可恢复句柄。
2. 硬保留当前目标、验收条件、权限边界、待修改代码、接口契约、测试断言、错误现场、未决问题和最新状态；这些内容不参与普通相关性淘汰。
3. 其余内容按任务实体、Symbol/调用距离、证据强度、信息增益和Token成本评分；相似Chunk去重，同文件只保留最相关范围，旧版本、无关工具回显和已完成轨迹优先删除。
4. 待修改源码保留原文；稳定依赖折叠为签名和摘要；日志保留异常与统计；大Artifact存入外部存储，正文只留哈希、范围、权限和读取句柄。
5. 历史对话压缩成Checkpoint：目标、事实、决策、修改、失败尝试、风险和下一步，并保留行号及Trace引用。压缩后检查证据覆盖，低置信时回读原文。

裁剪应在查询、规划、编辑和验证阶段使用不同预算，并根据编译或测试Observation动态补充。通过任务完成率、关键证据Recall、无关上下文率、压缩比、Token、P95和摘要漂移率评估。

**相关知识点：** 上下文裁剪、硬保留集、信息增益、去重、分层摘要、外置Artifact、Checkpoint、摘要漂移、Token预算。
<a id="eng-106"></a>
### 如何避免向LLM注入无关代码导致Token浪费？

应以**多路高召回、任务感知精排、结构约束和动态停止**控制上下文，使进入LLM的代码都能说明与任务的关系，而不是按相似度机械取Top K。

1. 从任务提取Symbol、错误码、路径和验收条件，先路由仓库、Commit、语言与模块；错误版本、无权限文件、生成物、Vendor和二进制在召回前过滤。
2. BM25、Embedding、Symbol和Graph并行召回，RRF融合后用Cross-encoder Rerank；特征包括精确命中、路径、AST节点、调用图距离、Git共变、新鲜度和频次。
3. 以定义—引用、调用、继承、配置和测试构造最小证据闭包，只保留目标代码、契约、类型和直接上下游；公共工具和高连接Hub设置惩罚与每文件上限。
4. 候选按“原文、摘要、引用”分级：待修改代码与断言保留原文；稳定依赖保留签名或摘要；重复Chunk去重，大日志与Artifact外置。
5. 设置Token、候选数和图深度预算。新证据信息增益低、依赖闭合或验证满足时停止；编译、LSP诊断和测试暴露缺口时再局部检索。

对每个块记录来源、分数和Commit，低置信块与缺失触发覆盖检查。以无关上下文率、Recall@K、完成率、Token、P95和成功成本评估，不能只追求压缩率。

**相关知识点：** 查询路由、Hybrid Search、Rerank、最小证据闭包、Hub惩罚、上下文分级、信息增益、Token预算。
<a id="eng-107"></a>
### Graph RAG与普通Code RAG有什么区别？

Code RAG以**代码Chunk相似性**为主，Graph RAG以**Symbol关系路径**扩展；前者擅长局部语义，后者擅长跨文件依赖，应组合使用。

| 维度 | 普通Code RAG | Graph RAG |
|---|---|---|
| 检索单元 | Chunk、摘要 | Symbol、模块与边 |
| 主要信号 | BM25、Embedding | 调用、引用、依赖路径 |
| 局限 | 关系弱 | 建图贵、动态边缺失 |

1. Code RAG按函数或类切块，用关键词与向量召回并Rerank，适合名称未知、同义描述和局部解释；但语义相似不代表调用相关。
2. Graph RAG从种子Symbol沿定义—引用、calls、imports、extends、配置、测试和数据关系限深遍历，可回答接口影响与入口路径。
3. Graph由AST、LSP、编译器、构建图和Trace生成，边记录来源、Commit、环境和置信度；反射、代理与动态语言会缺边，保守分析则导致膨胀。
4. 先用BM25/Embedding找种子，再图扩展上下游、契约和测试，按语义分、图距离、置信度、新鲜度与权限Rerank，并设置节点与Token预算。
5. 除Recall@K、MRR、NDCG外，还需测路径准确率、证据覆盖、无关上下文率、图查询P95及完成率；向量指标不能证明图关系正确。

**相关知识点：** Code RAG、Graph RAG、Symbol Graph、Call Graph、种子检索、图遍历、边置信度、证据路径、Hybrid Retrieval。
<a id="eng-109"></a>
### 如何利用Git提交历史提升检索效果？

Git历史为检索增加**时间、共变、意图和责任信号**，可发现依赖图外的业务关联；历史只能辅助排序，当前Commit仍是事实基准。

1. 为Commit、文件和Symbol建时间索引，提取作者、说明、Issue/PR、Diff、重命名和父提交；Symbol谱系把旧路径映射到当前实体，避免历史断裂。
2. 统计文件/Symbol共变，构建“经常同改”边。配置、接口、测试与实现即使无调用，也可能因同一需求关联；批量格式化、生成代码和大合并需降权。
3. 查询含错误码、术语或Issue时检索历史提交与补丁，召回相似修复、修改文件和配套测试；旧Patch只作候选，必须校验当前依赖与契约。
4. Rerank加入修改时间、共变、相似Commit、缺陷密度、Blame和CODEOWNERS。修复任务提高缺陷历史权重，新功能更关注当前接口。
5. 提交说明、评审和回滚原因生成带来源摘要；作者邮箱、Issue正文和敏感Diff遵守权限、隐私与保留策略，禁止跨租户索引。

离线回放历史Issue/PR，比较Recall@K、MRR、NDCG和测试推荐；线上监控陈旧历史误导率。索引按Commit更新，过滤机器人与机械变更。

**相关知识点：** Git History、Symbol谱系、共变分析、Commit检索、Blame、CODEOWNERS、时间衰减、历史噪声、来源追踪。
<a id="eng-115"></a>
### 如何利用缓存、预取和热点分析进一步优化代码上下文检索？

核心是**让高价值且版本一致的上下文接近请求路径**。缓存减少计算，预取隐藏I/O，热点分析决定资源投放。

1. L1保存查询计划与Symbol元数据，L2保存Embedding、召回列表和代码块，对象存储保存不可变索引段。键包含tenant、repo、Commit、查询指纹、模型及ACL版本。
2. 空结果和解析失败使用短期负缓存，SingleFlight合并并发；采用LFU/LRU混合淘汰，超大对象按价值准入。
3. Symbol召回后异步预取定义、直接引用、相邻测试和配置。任务须低优先级、可取消，以命中概率×节省延迟−成本决定执行。
4. 滑动统计查询频次、复用距离、仓库活跃度和分片负载，识别热点仓库与Symbol；提前生成摘要、Embedding和图邻接缓存。
5. Git事件精确失效对应块、Symbol、摘要和依赖闭包，未变化内容按hash复用；ACL变化立即失效。

评估命中率、有效预取率、P95/P99、节省Token、额外I/O及新鲜度违规率；命中率高却未降低延迟，表明对象选择不合理。

**相关知识点：** 多级缓存、SingleFlight、LFU/LRU、负缓存、预测预取、热点检测、精确失效、内容寻址、ACL一致性、尾延迟。
<a id="eng-119"></a>
### OpenCode如何解决上下文窗口限制问题？

采用**按需检索、渐进式读取、状态外置、语义压缩和子任务隔离**，把上下文视为有限工作缓存。

1. 首轮加载规则、目录摘要、目标和Git状态，以Grep、LSP、Symbol或外部索引定位；先读签名与命中区间，再按需展开。
2. Context Builder按相关性、依赖距离、新鲜度和Token成本排序去重；日志过滤根因，大对象外置，仅保留路径、hash和摘要。
3. 维护Read Record、Evidence Map和缓存，同一Commit同一区间不重复读取；文件修改后只失效变化块。工具、Plugin与MCP Schema按需加载。
4. 接近阈值时将目标、约束、决定、证据、Diff、测试和待办压缩为Checkpoint；恢复时校验HEAD，漂移则重检索。
5. 独立研究或并行任务交给隔离子Agent，只返回结构化发现与Artifact，不合并其全部历史。设置检索深度、轮次和Token预算，连续无新增证据则停止。

以Context Recall、Precision、重复Token率、恢复正确率、完成率及单位成功成本衡量；摘要丢失约束时应提高保真度。

**相关知识点：** 上下文预算、渐进式读取、Context Builder、Read Record、Artifact Store、语义压缩、Checkpoint、子Agent隔离。
<a id="eng-120"></a>
### Agent如何进行任务拆解与规划？

任务拆解生成**目标明确、依赖可表达、结果可验证、失败可恢复的步骤DAG**；计划是随证据更新的状态。

1. 澄清目标、范围、禁止项、环境、预算与Acceptance Criteria，将未知信息列为假设；不可逆动作单独成节点并审批。
2. 按“探索—定位—修改—验证—交付”拆解，节点定义输入、Artifact、依赖、权限、成本、成功条件和失败分支；粒度应可独立验证。
3. 用依赖关系形成DAG：只读研究和独立模块可并行，公共接口、共享文件及生产写入串行；关键路径优先，非关键任务分配独立子预算。
4. Planner选择前置完成且价值最高的节点，Executor返回观测；新证据或失败时局部重规划，保留已验证节点。
5. 状态记录pending、running、succeeded、failed、blocked、cancelled以及attempt、Evidence和Checkpoint；设置最大轮次、Token、时间与无进展阈值，重复状态触发停止。

以步骤成功率、返工率、冲突、无效调用、关键路径耗时和完成率评估；简单任务可省略长计划，但仍需验收与终止条件。

**相关知识点：** 任务DAG、Acceptance Criteria、关键路径、动态重规划、结构化观测、Checkpoint、风险节点、进展函数、预算控制。
<a id="eng-128"></a>
### 如何实现Git自动回滚机制？

Git回滚应以**不破坏用户工作区、可审计、可幂等恢复**为原则，按任务隔离后再自动化。

1. 任务开始记录repo、branch、HEAD、submodule和工作区状态；若已有未提交变更，优先创建worktree或只保存本轮Patch。
2. 每个验证通过阶段创建独立Commit或可识别Patch作为Checkpoint，保存任务ID和验证证据。
3. 未提交的Agent变更可反向应用本轮Patch；已提交且可能共享的变更使用`git revert`生成新Commit，不重写公共历史。
4. 回滚前核对目标Commit、文件范围和并发变化；冲突时停止人工处理，禁止用破坏性的硬重置覆盖他人修改。
5. 回滚后重跑关键测试并核对工作树，审计记录触发原因、操作者、前后Commit和结果。

数据库、制品和外部副作用不由Git覆盖，必须配套迁移回滚、Feature Flag或补偿事务。

**相关知识点：** Worktree、Patch、Checkpoint Commit、git revert、幂等回滚、补偿事务、审计。

### OpenCode如何实现长期记忆和项目记忆？

应采用**显式项目文件加可检索记忆库**，并把“事实来源与失效”放在召回能力之前；具体内置支持以版本文档为准。

1. 稳定规范、命令和架构决策保存在仓库可审查文件中，与代码一起Review；用户偏好和私有历史存放在隔离空间。
2. 长内容按主题切块，保存repo、branch、Commit、路径、时间、Owner、来源和置信度，使用关键词、向量及元数据过滤召回。
3. 只把用户确认或工具验证的事实写入长期记忆；模型推断、失败结果和临时日志不自动沉淀。
4. Git变更触发关联记忆降权或失效；冲突事实并存时显示来源，由当前代码、测试或Owner裁决。
5. 召回片段按最小权限与Token预算注入，并向用户展示引用，支持查看、编辑、导出和删除。

评估跨会话命中率、陈旧信息率、错误写入率、引用可追溯率和实际任务增益。

**相关知识点：** Project Memory、显式规则文件、Provenance、Commit绑定、混合检索、失效策略、可删除性。

### OpenCode未来向自主软件工程（Autonomous Software Engineering）演进需要哪些关键能力？

演进重点不是增加“自主”时长，而是提升**需求闭环、环境可靠性、验证强度、安全边界和责任可追溯性**。

1. 从Issue中澄清需求、识别歧义并生成可执行验收条件，能在证据不足时主动停下询问。
2. 建立大仓检索、依赖图、跨文件重构、环境构建和可复现沙箱，支持长任务状态与失败恢复。
3. 用编译、测试、形式约束、安全扫描、性能基准和线上Canary构成多层Verifier，降低自评偏差。
4. 多Agent只用于可证明的专业分工和并行，所有交接包含Artifact、版本和验收证据。
5. 权限最小化，高风险写入和发布人在环路；完整记录需求、决策摘要、工具、Diff、审批与结果。
6. 通过真实仓库评测和线上反馈迭代，优化单位成功成本，而非单看Benchmark或代码生成量。

近期更现实的是“可监督的半自主工程”，生产发布与责任归属仍需人类Owner。

**相关知识点：** Autonomous Software Engineering、Acceptance Criteria、Verifier、长任务恢复、Human-in-the-loop、Canary、责任链。

### 如何量化"断言质量"，是否有可落地的评分公式？

断言质量可用多维评分辅助排序，但不能由一个公式完全替代Review。可定义：

`Q = 0.30D + 0.20R + 0.20B + 0.15S + 0.15I - P`

- `D`缺陷辨识力：目标突变杀死率或历史缺陷检出率；
- `R`需求可追溯性：断言与契约/验收条件的关联覆盖；
- `B`边界覆盖：正常、边界、异常和状态转换覆盖；
- `S`稳定性：重复运行通过率及对非语义改动的鲁棒性；
- `I`隔离性：失败能否定位单一行为；
- `P`惩罚：无意义断言、过度Mock、硬编码实现细节和Flaky。

各项归一到0～1，权重应以历史缺陷数据校准，并按单元、集成和契约测试分别设阈值。最终展示原始子指标，避免团队“刷综合分”。

**相关知识点：** Mutation Score、需求追踪、边界覆盖、Flaky Rate、可诊断性、Goodhart定律、权重校准。

### Agent如何保证工具调用成功率？

成功率来自**选对工具、参数正确、依赖可用和结果被验证**四个环节，不能只统计HTTP 200。

使用清晰Schema、枚举和示例降低参数错误，调用前做类型、权限和前置条件校验；执行时设连接/请求超时、幂等键、有限退避重试、熔断和备用能力。参数错误修正，权限错误停止，瞬时错误才重试。

调用后检查业务码和后置状态，媒体处理还要检查文件可读、格式、时长和质量。记录工具选择Top1、参数准确率、业务成功率、重试率、P95和最终任务完成率，并按错误类型治理。

**相关知识点：** Tool Selection、Schema校验、Error Taxonomy、幂等键、退避重试、熔断、后置条件。

### 早期融合与晚期融合各自的适用场景和优劣对比是什么？

早期融合在特征或Token层联合建模，适合需要细粒度跨模态关系的任务；晚期融合先独立处理各模态，再组合结果，适合模块化和异步系统。

| 维度 | 早期融合 | 晚期融合 |
|---|---|---|
| 优势 | 交互充分、细节关系强 | 易替换、易解释、可独立降级 |
| 代价 | 训练/推理成本高、缺失模态敏感 | 可能丢失细粒度联合信息 |
| 场景 | 图文定位、音视频联合理解 | 多路检索、风控、异步业务 |

实际常用混合方案：各模态先专用编码，关键层Cross-Attention，决策层再做校准融合。选型以任务、时延、缺失模态和消融实验为准。

**相关知识点：** Early Fusion、Late Fusion、Cross-Attention、缺失模态、混合融合、消融实验。

### 视觉幻觉产生的根本原因是什么，如何量化评估？

视觉幻觉来自**视觉信号不足或压缩、训练先验压过证据、跨模态对齐误差、解码偏好和问题诱导**。

可按对象存在性、属性、关系、数量、OCR文字和动作分型。构建有区域标注与难负样本的数据集，要求回答关联区域；计算对象幻觉率、Precision/Recall、定位IoU、拒答校准及引用支持率。

评测需包含遮挡、低清、裁剪、反事实图文冲突和不存在对象问题，并按分辨率、语言和场景切片。自动Judge只能辅助，关键集应由人标或专用检测器复核。

**相关知识点：** Object Hallucination、Grounding、IoU、反事实样本、拒答校准、视觉先验。

### Agent任务完成率应该如何定义和计算？

先定义有效任务与验收条件，再计算：

`Strict Completion Rate = 完全满足全部验收条件的任务数 / 有效任务数`

无效请求、用户主动取消和平台环境故障应单列，不能随意从分母删除；Partial Completion用预定义权重计算，不能由模型自报。Judge优先采用业务状态、规则、测试和后置条件，开放任务再用盲审Rubric。

同时报告首次完成率、人工接管率、重规划率、无回归率和置信区间，并按任务类型和难度切片。同一任务多次运行时明确是pass@1还是多次尝试成功率。

**相关知识点：** Strict Success、Partial Completion、Acceptance Criteria、有效任务、pass@1、置信区间、Judge。

### CAC与LTV的合理比例应该是多少？

不存在跨行业通用阈值。常见经验是`LTV/CAC > 3`且回收期可接受，但它只是筛查线，不是定律，必须结合毛利、现金流、流失和增长阶段。

LTV应使用毛利贡献而非收入，可按Cohort估计留存、扩张、推理成本和服务成本；CAC包含营销、销售、人力、折扣和渠道成本，并区分新增与自然用户。AI产品的推理成本随使用增长，若忽略会显著高估LTV。

应同时报告回收期、净收入留存、边际毛利和不同渠道Cohort，并用敏感性分析呈现不确定性。

**相关知识点：** CAC、LTV、Gross Margin、Payback Period、Cohort、NRR、敏感性分析。

### 如何评估RAG系统对业务价值的贡献？

采用**检索—答案—任务—业务**四层指标和可归因实验，不能只看Recall@K。

检索层评Recall、MRR、Context Precision和新鲜度；答案层评事实、引用支持与拒答；任务层评完成率、人工接管和处理时长；业务层评转化、一次解决率、工时或风险。

通过关闭RAG、替换检索器或不同知识版本做随机/影子实验，并按问题类型切片。记录“答案使用了哪些证据”，分析RAG带来的净增益及错误召回造成的损害，再与索引和模型成本结合计算单位价值。

**相关知识点：** RAG Evaluation、Recall@K、Context Precision、引用正确率、消融实验、业务归因、单位价值。

### 企业内部效率型Agent如何量化价值？

以**质量调整后的净节省工时、流程周期和可兑现成本**为主，避免把生成次数当价值。

建立同任务人工基线，统计Agent操作、Review、返工和异常处理时间；按实际采用率和完成率折算净节省。若节省时间未减少支出，也应说明它转化为吞吐、响应速度或更高价值工作的证据。

同时追踪缺陷、合规、员工满意和技能影响，通过对照组或分阶段上线控制任务难度与学习效应。财务价值按可兑现节省、避免损失和平台总成本计算，并给出保守区间。

**相关知识点：** 净节省工时、质量调整、Adoption、可兑现节省、避免损失、对照组、TCO。

### 大模型平台化建设如何评估长期价值？

长期价值体现在**复用、治理、交付速度、规模经济和选择权**，而不只是平台调用量。

衡量新Agent上线周期、公共组件复用率、重复建设减少、统一评测/安全覆盖、故障恢复和供应商切换成本；经济性看单位成功成本随规模的变化及平台团队TCO。

平台若迫使业务绕行、定制周期变长或成为单点，复用数字也可能虚高。应跟踪业务团队满意、旁路系统数量、API稳定性和迁移成本，并用采用前后对照验证。架构选择权和合规能力可作为风险调整价值单列。

**相关知识点：** Platform Engineering、复用率、Time to Market、规模经济、TCO、供应商选择权、平台健康度。
