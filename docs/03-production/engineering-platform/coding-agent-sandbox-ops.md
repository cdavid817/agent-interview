### 1. 沙箱池化如何按仓库预热？命中率与资源浪费如何平衡？

按仓库预热要先回答"热的是哪一层数据"——**节点本地磁盘上的 OCI 镜像层与依赖快照可以低成本长期持有，已启动却空转的实例最贵**，两者的平衡点完全不同。

1. 分层持有：镜像层、按 lockfile 哈希寻址的依赖树快照、代码索引与 bare mirror 都存在节点本地磁盘上，占的是存储而非计算，按周为单位为几十个仓库各留一份是划算的。真正昂贵的是预先启动好、等着接任务的空转实例，它按实例秒计费，只值得给到达率最高的少数仓库准备。
2. 预热谁的排序依据是三项相乘：任务到达率 × 该仓库未命中时的额外耗时 × 数据的可共享程度。只按到达率排，资源会砸给本来就启动很快的小仓库；只按耗时排，一年跑两次的巨型仓库会长期占位。可共享程度这一项常被忽略，而它决定了同一份预热数据能摊给几个仓库。
3. 失效应由事件驱动而不是定时刷新：基线分支推进、lockfile 变化、基础镜像摘要更新各自只作废对应的那一层。把三者混成一个统一的过期时间，结果是新鲜的层被反复丢弃，陈旧的层却还在被命中。
4. 命中要按层统计而不是当成二值判断。一次准备完全可能镜像层命中而依赖快照未命中，只记录整体命中率会掩盖是哪一层在漏，而各层未命中的补救成本相差一个量级。

平衡点可以算，但要注意两侧单位不同：浪费是空转实例数乘空闲时长乘单价，收益是各层命中次数乘该层未命中时的额外耗时。要比较就必须先由业务给出"省下一小时准备时间值多少钱"这个换算系数，平台自己拍一个是没有依据的。要监控分层命中率、空转占比与预热数据的陈旧度分布——陈旧度长尾变厚通常说明失效事件没接全，而不是预热规模不够。

**相关知识点：** OCI 镜像层、lockfile 哈希、bare mirror、预热池、缓存失效事件、分层命中率、空转成本。

### 2. 沙箱冷启动时间由哪些环节构成？各段分别如何优化？

先把冷启动拆成能分别归因的段，否则优化会砸在错的位置——多数团队盯着实例启动那几百毫秒，而**真实 P95 通常被仓库物化和依赖恢复吃掉**。

1. 分段口径要覆盖从任务入队到第一条命令可执行的全程：调度排队、镜像获取、实例启动、仓库物化、依赖与工具链就绪、代码索引与语言服务就绪。每段单独打点，因为它们的优化手段互不通用，有些甚至互相排斥。
2. 镜像获取段的关键是不必等整个镜像落盘。eStargz 这类支持惰性拉取的镜像格式让容器在少数必需文件就位后即可启动，代价是后续首次访问文件时产生随机延迟；对启动后立刻全量读盘的构建负载，它反而可能更慢。
3. 实例启动段对容器已接近下限，继续压缩要靠快照恢复：microVM 从已初始化的内存快照恢复实例，跳过内核与运行时初始化。前提是快照里不含任何租户数据，且要处理同一快照派生出的多个实例共享初始随机状态的问题。
4. 仓库物化与依赖恢复通常是大头，且两者的优化方向相反——前者靠减少写盘（本地镜像派生、sparse checkout），后者靠增加预置数据（依赖快照挂载）。同时推进会让磁盘吞吐成为新瓶颈，应按实测的段耗时占比决定先做哪个。
5. 只报均值会掩盖问题。冷启动耗时通常呈多峰分布，每个峰对应一种"哪几层缓存没命中"的离散状态。按命中组合分桶后各自看 P95，才能定位到具体是哪一层在漏。

优化的终点不是零，而是让冷启动在任务总耗时里的占比降到可忽略——一个要跑二十分钟的任务不值得为省十秒重构存储层。可采集的指标是各段耗时的 P95 与占比、按缓存命中组合分桶的耗时分布，以及冷启动占任务总时长的比例。

**相关知识点：** 冷启动 P95、eStargz、镜像惰性拉取、microVM 快照恢复、sparse checkout、分段埋点。

### 3. 如何按团队与仓库设置沙箱并发与资源配额？

配额要拆成两层：**准入层的并发额度是可等待的软约束，运行层的资源上限是会杀进程的硬约束**，二者由不同机制执行，失败方式也完全不同。

1. 准入层控制"同时能有多少个沙箱在跑"，超出就排队；运行层由 cgroup v2 的 `cpu.max`、`memory.max`、`pids.max`、`io.max` 强制，超出即被限流或直接失败。把两件事混成一个数字，最典型的后果是内存配额按平均用量设置，于是链接或类型检查阶段的内存峰值触发 OOM kill，表现成"测试偶发失败"而不是"配额不足"。
2. 收紧 CPU 与内存的代价不对称：CPU 被限流只是变慢，内存超限直接被杀。所以内存应按观测到的峰值分位数留余量，允许超售的是 CPU；反过来配会同时得到低利用率和高失败率。
3. 层级配额比扁平配额实用：团队总额之下给仓库分配下限与上限，并允许在总额内借用闲置额度。没有借用机制时，每个仓库都会申请自己的峰值需求，加总远超集群容量，实际利用率却很低。
4. 计量单位要贴合负载形态。编码任务是突发型：准备阶段几乎不用 CPU，构建测试阶段打满，之后又长时间等模型返回。按并发实例数配额简单且排队体验可预期，但要为空闲时段付费；按核时计量更公平却难以给出确定的等待时间，因此多数平台按实例数做准入、按核时算成本。

配额是治理工具而不只是技术参数，需要配套的申请、复核与回收流程，否则只增不减。可采集的信号包括各级配额使用率、排队时延 P95、因内存超限被杀的任务占比，以及长期低于配额一半的仓库数量——最后一项直接对应可回收的容量。

**相关知识点：** cgroup v2、`cpu.max`、`memory.max`、`pids.max`、OOM kill、层级配额、准入控制。

### 4. 沙箱集群如何调度长任务与短任务的混合负载？

混合负载的病根不在容量而在**耦合**：只要两类任务共享一条队列和一批节点，短任务的排队时延就会被长任务的时长决定。

1. 最直接的症状是队头阻塞。单一先进先出队列里，一个占满节点的长任务会让后面几十个本来几秒就能跑完的短任务一起等。按预期时长分池能解决它，代价是两个池各自的空闲无法互相填补，总体利用率下降。
2. 时长的先验只能来自历史。同仓库、同任务类型的过往执行时长分位数是可用的估计；任务发起方声明的时长不可用——声明者没有说实话的动机，而且编码任务的时长主要由测试套件决定，发起时它自己也不知道。
3. 估不准时用多级反馈队列更稳妥：所有任务默认按短任务入队，运行超过阈值就降级到长任务队列并让出资源。它不需要预知时长，代价是被降级的任务经历一次调度抖动，因此阈值要落在真实时长分布的谷底而不是取一个整数。
4. 长任务还会阻碍缩容——节点排空要等它上面最长的那个任务结束，最坏情况下的缩容延迟就等于长任务的时长上限。把长任务集中到少数节点上，能让其余节点保持可快速回收的状态，这是分池在成本侧的额外收益，常常比调度公平性更值钱。

分池粒度不宜过细：池子越多，每个池都要留一份安全余量，加总的浪费会超过混跑带来的干扰。评估要分开看两类任务——短任务看排队时延 P95 及其在端到端耗时中的占比，长任务看被中断率与完成率，再加一个节点排空耗时，用来判断分池是否真的改善了缩容。

**相关知识点：** 队头阻塞、多级反馈队列、按时长分池、节点排空、排队时延 P95、任务时长分位数。

### 5. 资源紧张时沙箱如何抢占与驱逐？被驱逐的任务如何恢复？

驱逐与恢复是同一件事的两面——**能不能驱逐，取决于被驱逐者以多大代价恢复**；没有恢复设计的驱逐，等于随机丢弃已经完成的工作。

1. 优先用准入控制而不是驱逐。拒绝一个还没开始的任务，成本是零；杀掉一个跑了二十分钟的任务，已消耗的算力与 Token 全部作废。集群水位接近上限时应先收紧准入，只有内存压力这类无法靠排队缓解的场景才驱逐。
2. 触发信号要用压力而不是用量。cgroup v2 的 PSI 指标反映"进程为等待资源停顿了多久"，比内存占用率更早也更准地预示即将 OOM。等用量打满再动手，内核的 OOM killer 通常已经先杀了，而它的评分主要由内存占用决定，挑中的往往正是最不该杀的那个。
3. 驱逐对象不能只按优先级挑，要综合已投入成本、剩余预期时长与可恢复性。一个刚启动、有检查点的低优任务，比一个即将完成、没有检查点的同优任务更该被驱逐。这意味着"是否可恢复"要作为任务属性显式上报，而不是驱逐那一刻才去猜。
4. 恢复分三档，按代价递增：从头重跑（幂等且成本可接受时最简单）、从检查点续跑（要求状态完整且未过期）、人工接管（前两者都不可行时的兜底）。选择依据是任务已经产生了哪些不可撤销的外部副作用——已推送的分支、已创建的 PR、已发出的通知都不能靠重跑消解，续跑前必须先查询这些副作用的真实状态再决定跳过还是补做。
5. 重试要有预算。驱逐导致重跑、重跑加剧拥塞、拥塞触发更多驱逐，这个正反馈在容量紧张时会把集群拖垮。给每个任务设重试上限，并让重试排在新任务之后而不是插队到前面。

驱逐率长期不为零说明容量规划有缺口，靠驱逐机制掩盖只会推迟问题。可采集的指标包括驱逐率与其中可恢复的占比、重跑产生的重复成本，以及恢复后的任务完成率——恢复后完成率明显低于首次执行，说明检查点没覆盖住某个关键状态。

**相关知识点：** 准入控制、PSI、OOM killer、抢占与驱逐、检查点续跑、幂等键、重试预算。

### 6. 沙箱基础镜像如何随仓库工具链演进？维护责任如何划分？

责任划分不清时，镜像会同时得两种病：安全补丁推不动，仓库需要的新工具链也进不来。解法是**按变更动机分层，每层归属不同的人**。

1. 三层对应三种变更动机。平台层（操作系统、根证书、基础工具、安全加固）由平台团队维护并强制更新，因为它的变更理由是安全而不是功能；语言层（运行时与包管理器版本）由语言方向的维护者按支持窗口滚动；仓库层（项目特有的系统依赖与构建工具）由仓库自己声明，平台只负责让它可被声明。
2. 底层强制、上层自治的边界要落到具体动作上：平台层更新不询问仓库，但必须提前公告并保证向后兼容；上层变更由仓库通过 devcontainer 或等价声明文件提出，平台不审查内容，只审查它是否引入了被禁的能力，例如特权挂载或宿主套接字。
3. 版本要像 lockfile 一样被仓库固定：仓库记录自己使用的镜像摘要而不是可变标签，升级是一次可评审、可回滚的提交。用可变标签的后果是某天构建突然失败却没有任何仓库侧变更，排查会从代码一路查到平台。
4. 强制升级要有过渡期而不是切断。新旧镜像并行一段时间，期间对仍在使用旧镜像的仓库持续告警并给出差异说明；过期后应拒绝调度，而不是静默替换成新镜像——静默替换会让失败原因与真实变更彻底脱节。

这套划分成立的前提是平台层足够薄；平台层一厚，"强制"就会覆盖到仓库真正关心的东西，自治只剩名义。可采集的指标包括安全补丁从发布到全量覆盖的耗时、仍在使用过期镜像的仓库数、镜像升级引发的构建失败次数，以及仓库自助完成的变更占比——最后一项过低，通常说明声明机制不好用，仓库只能来找平台加东西。

**相关知识点：** 基础镜像分层、devcontainer、镜像摘要固定、可变标签、EOL 过渡期、补丁覆盖耗时。

### 7. 一个平台要服务多种语言与版本，镜像矩阵如何收敛？

矩阵规模是几个维度相乘的结果，所以**能砍的只有维度本身，不是每个维度里的取值**——在"多留一个版本"上讨价还价没有意义。

1. 先看清这个乘法：语言 × 主版本 × 系统基线 × CPU 架构 × 变体（含不含浏览器、含不含数据库客户端）。加一个架构就是整体翻倍，而这一维往往只为少数机型引入。真正的收敛动作是砍掉整个维度，比如把变体做成运行时可选，而不是预先组合成一堆标签。
2. 版本维度靠支持窗口治理，这是政策问题不是技术问题：明确同时支持几个主版本、超窗后进入只读的宽限期、宽限期结束不再重建。没有窗口的平台会为了一个未升级的仓库把五年前的版本一直构建下去，而它的重建成本在每次安全补丁时都要重新付一遍。
3. 重建的扇出是矩阵的隐藏成本。底层一个补丁触发全矩阵重建，构建时长、镜像仓库存储与漏洞扫描告警都按矩阵大小放大。因此衡量矩阵规模的正确指标不是标签数量，而是"一次基础层变更需要多久完成全量重建并推到所有节点"。
4. 长尾要有出口，不要硬塞进公共矩阵。允许仓库自建镜像，但要求它基于平台的基线层构建、纳入同一套扫描与签名流程，并明确安全责任随之转移给该仓库。没有这条出口，长尾需求会变成对公共镜像不断加包的压力。

矩阵收敛与启动性能存在冲突：变体外置意味着更多运行时组装，冷启动会变慢，需要用缓存补回来。可采集的信号包括活跃标签数及其增长率、全矩阵重建耗时、每个标签的实际使用量分布，以及自建镜像的漏洞修复及时率——使用量分布的长尾里那些零调用的标签，是最容易直接回收的部分。

**相关知识点：** 镜像矩阵、版本支持窗口、EOL 策略、构建扇出、镜像扫描、基线层、自建镜像责任转移。

### 8. 「沙箱里过、CI 里挂」的环境漂移如何检测与量化？

这类问题难查，是因为两侧都认为自己是对的，而**两个环境的差异从来没有被表示成可比较的东西**。检测的第一步是把环境变成一份可以逐字段 diff 的指纹。

1. 指纹要覆盖真正会改变行为的维度，而不只是版本号：工具链与系统包的名称版本集合、CPU 架构与指令集、可用核数与内存上限、文件系统的大小写敏感性与路径长度限制、时区与 locale、环境变量键集合、网络可达性、运行用户及其权限。同一个探针在两侧各跑一次，输出结构化结果后比对。
2. 排在前列的漂移源往往不是版本不同，而是并发度与资源不同。CI 上核数更多或更少都会改变测试的并行度，从而暴露或掩盖竞态；内存上限不同会让同一个用例在一边被 OOM 杀掉。这两类差异在版本清单里完全看不见。
3. 其次是被当成理所当然的隐式依赖：沙箱能出网而 CI 不能（或反过来）、沙箱里恰好残留了上一次的构建产物、宿主时区让日期断言只在特定时段失败。它们的共同点是在某一侧长期成立，因此从未被写进任何配置文件。
4. 量化口径要能指导投入。漂移率定义为沙箱通过而 CI 失败的任务占比，再按归因分桶：环境差异、真实缺陷、不稳定测试。不分桶的漂移率会把 flaky test 记在环境头上，导致团队长期在修错的东西。

指纹比对能发现差异，但哪些差异重要仍需人判断——主机名不同显然无关，核数不同则可能致命。可采集的指标是漂移率及其分桶构成、指纹差异字段的出现频次排序，以及从提交到 CI 反馈的耗时。差异字段的频次排序稳定之后，就可以把高频字段固化成两侧必须一致的硬约束。

**相关知识点：** 环境指纹、环境探针、locale 与时区、大小写敏感文件系统、并发度差异、flaky test、漂移归因分桶。

### 9. devcontainer、Nix 等既有环境定义能否直接复用为 Agent 沙箱？

可以复用，但要分清它们描述的是**环境**而不是**隔离**：把环境定义直接交给通用运行器执行，等于把仓库里的一段脚本提升到了平台权限下运行。

1. devcontainer 的价值在于仓库已经写好了它，而且它就是开发者本人在用的环境，天然贴合"能跑起来"。风险集中在它为便利而设计的部分：`postCreateCommand` 与 features 会在容器构建与创建阶段执行任意代码；docker-outside-of-docker 一类特性要求挂载宿主的 Docker 套接字，那等价于交出宿主 root。安全的用法是解析它、提取镜像与端口这类结构化信号，而不是原样执行。
2. Nix 在可复现性上明显更强：每个包的存储路径由其全部构建输入的哈希决定，flake 把外部输入锁到具体版本，同一份定义在不同机器上求值出同一个依赖闭包。代价是仓库必须已经 Nix 化，而且首次求值与构建的耗时相当可观，需要共享的二进制缓存来摊薄。
3. 两者都不描述沙箱真正需要的东西：网络策略、凭证注入范围、系统调用限制。这些必须由平台在外层叠加，且平台约束的优先级要高于环境定义——否则仓库可以通过改自己的环境定义来放宽自己的沙箱。
4. 现实做法是分级复用：有 Nix 定义的走 Nix，有 devcontainer 的按结构化字段降级复用，两者都没有的回落到平台推导的默认镜像。走了哪一级必须记进执行记录，否则同一个仓库两次运行拿到不同环境却查不出原因。

复用既有定义能显著提高首次跑通率，但它带来的是仓库口径而非平台口径的环境，与 CI 的一致性要单独验证。可采集的指标包括各分级路径的占比与首次构建成功率，以及环境定义中被平台拒绝的能力申请次数。

**相关知识点：** devcontainer、`postCreateCommand`、devcontainer features、Docker 套接字挂载、Nix flake、依赖闭包、二进制缓存。

### 10. 沙箱环境的可复现性如何保证？哪些不确定性必须消除？

先划清范围：这里说的是**同一份输入在两次执行之间的一致性**，与沙箱和 CI 之间的差异是两个不同的问题。判定标准只有一个——两次独立执行的产物字节是否相同。

1. 必须消除的是会写进产物的不确定性：嵌入的构建时间戳、绝对构建路径、目录遍历顺序、并行构建导致的输入顺序变化、归档文件里的 uid/gid 与 mtime、未固定的随机种子。前两项有通行做法，reproducible-builds 约定的 `SOURCE_DATE_EPOCH` 提供统一的时间基准，构建路径则做归一化处理。与之相对，只出现在日志里的时间戳、进程号与测试执行顺序不进入产物，一并消除的成本很高而收益接近零，这条界线不划清会浪费大量工作。
2. 网络是最隐蔽的一类不确定性。构建期任何未锁定的下载，都让产物取决于"那一刻上游返回了什么"。这不只是版本问题——同一个版本的制品被重新发布过就足以打破复现，所以 integrity 校验值锁定与离线构建才是唯一可靠的答案。
3. 验证要靠实际比对而不是靠约定：在不同路径、不同时间、不同主机上各构建一次，用 diffoscope 这类工具逐层拆包比对，差异点会直接指出哪个环节没归一化。只在流程文档里声明"我们的构建是可复现的"没有任何证据价值。

在有些生态里做到字节级完全可复现代价过高，可以退一步只要求关键产物可复现，其余记录足够的构建元数据以便追溯。可采集的指标是纳入复现检查的产物占比、二次构建的字节一致率，以及每次不一致定位到根因的耗时——一致率长期不足百分之百却无人跟进，等于这项检查根本没有生效。

**相关知识点：** 可复现构建、`SOURCE_DATE_EPOCH`、构建路径归一化、diffoscope、integrity 校验值、归档元数据归一化。

### 11. 长时编码会话的沙箱状态如何保存与恢复？

状态不是一个整体，按"**能不能被重放重建**"分层才知道该存什么。绝大多数进程态不值得保存，真正必须保存的是无法重放的决策历史。

1. 最外层是会话侧状态：任务目标、已完成步骤、读过哪些文件、做过哪些判断与排除。它无法从沙箱里重建，一旦丢失，恢复后的 Agent 会重复已经做过的探索，甚至推翻自己之前的正确结论。这一层最该持久化，而且体积最小。
2. 中间层是工作树改动。用版本控制表达它——落成一次带标记的提交或一份补丁——比保存整个文件系统可靠得多，也天然可读、可审查、可在新沙箱里重放。未跟踪文件必须一并纳入，否则恢复后会缺东西且缺得很隐蔽。
3. 再往里是文件系统层：依赖目录、编译产物、各类缓存。它们能重建，只是慢。是否保存要看重建耗时与快照存储成本的比值，而不是"能存就存"。可写层快照适合这一层，代价是快照与镜像版本绑定，镜像一更新旧快照就不可用。
4. 最内层是进程与内核态。CRIU 这类检查点技术能把内存、文件描述符甚至连接一并冻结，但对编码会话收益很低：恢复一个跑到一半的测试进程，不如让它重跑；而且它对内核版本、运行时与外部连接的假设很强，恢复失败率显著高于前三层。

恢复不是把状态搬回去就完事，还要重新校验环境指纹——镜像或依赖在中断期间更新过，直接续跑会得到与中断前不同的行为。可采集的信号包括各层状态的保存体积与耗时、恢复成功率，以及恢复后首次执行的测试结果与中断前是否一致；不一致率偏高，说明分层里漏掉了某个会影响行为的状态。

**相关知识点：** CRIU、检查点与恢复、overlayfs 快照、未跟踪文件、镜像摘要绑定、会话状态持久化。

### 12. 沙箱任务的检查点该记录什么才能支持断点续跑？

检查点最难的部分不是记录已完成的工作，而是**记录已经发生的外部副作用**——续跑时必须能回答"那条推送到底成功没有"。

1. 定位信息决定恢复到哪里：任务标识与幂等键、基线提交、当前工作树的内容哈希、镜像摘要、依赖锁文件哈希。用分支名或浮动标签定位是不够的，它们在中断期间会移动，恢复时指向的可能已经不是同一份代码。
2. 进度信息决定从哪一步继续：已完成步骤的有序列表、待办队列、每一步的产出摘要。上下文按摘要保存而不是全量对话——全量既占空间，又会在恢复后把已经过时的判断重新带回模型。
3. 外部副作用要用预写方式记录：任何越出沙箱的动作，先写下"打算做什么"，执行后再写结果。崩在写入与执行之间时，恢复方至少知道存在一个状态未知的动作，可以去实际查询而不是盲目重试。缺了这一条，续跑要么重复执行要么整段遗漏，两种都不可接受。
4. 检查点时机应按语义边界而不是固定间隔。一个完整的"编辑—构建—测试"循环结束时才是可续跑的状态；循环中间的快照恢复出来仍要重跑整个循环。按时间切会产生大量根本用不上的检查点。
5. 检查点自身要带格式版本并声明兼容窗口。平台升级后旧检查点的字段含义可能已变，此时明确判定为不可恢复、回退到重跑，比按旧语义解释新字段安全得多。

检查点不是免费的：写入越频繁，正常路径的开销越大，而绝大多数任务根本不会中断。合理做法是只对超过一定时长或成本的任务开启。可采集的指标包括检查点写入耗时占任务总时长的比例、恢复成功率、恢复后仍需重做的步骤占比，以及副作用状态未知的发生次数。

**相关知识点：** 幂等键、write-ahead 记录、检查点格式版本、工作树内容哈希、上下文摘要、断点续跑。

### 13. 后台自主编码任务的沙箱与交互式会话有什么不同要求？

核心差异是**没有人在场**。由此推出的第一条结论不是"给它更多权限让它自己解决问题"，恰恰相反——无人复核时，可造成的最坏后果必须更小。

1. 权限方向常被搞反。交互式会话里人随时能看到并叫停，因此可以承担较宽的能力；后台任务无人看管，越权动作没有即时纠正的机会，权限应当更窄：不注入生产凭证、不允许自动合并、不执行不可逆的外部动作。需要越界时排队等人处理，而不是提前预授权放行。
2. 必须有硬性终止条件。交互式会话由人的耐心兜底，后台任务没有这层兜底，会在一个错误方向上持续消耗。终止条件应包括时长、Token 预算、工具调用次数与无进展轮次，其中"无进展"最难定义也最有效：连续若干轮没有产生新的通过用例、没有新的文件改动，就该停止而不是继续尝试。
3. 中途可见性要主动产出。交互式会话的过程本身就是可见的，后台任务必须把进度、当前假设与遇到的障碍作为事件流发出；否则失败时只剩一个结论，无法判断是任务本身不合理还是执行出了问题。
4. 失败要产出可读的交付物而不是一个异常。后台任务失败时应给出说明：尝试了什么、卡在哪里、需要人补充什么信息。把这份说明当成正式产出，能让大量"跑不通"的任务变成有价值的输入，而不是纯粹的浪费。

后台模式适合边界清晰、验收标准可自动判定的任务；目标模糊或需要产品判断的任务放到后台，只会稳定地产出无人认领的废弃分支。可采集的指标包括后台任务完成率与因预算耗尽终止的占比、无进展轮次的分布，以及产出被人工采纳的比例——采纳率远低于完成率，说明该收紧的是任务筛选标准而不是执行能力。

**相关知识点：** 无人值守执行、Token 预算、停止条件、无进展检测、进度事件流、最小权限。

### 14. 沙箱如何支持「跑起来看效果」：启动服务、访问端口、验证行为？

这条能力的价值是让 Agent 拿到执行证据而不是靠推测，但**"服务起来了"和"功能对了"是两个判断**，混为一谈会产生大量假阳性。

1. 端口不应直接映射到宿主或公网。服务监听沙箱内的回环地址，由平台侧的反向代理按任务身份鉴权后转发，人和 Agent 都从这个代理进。直接映射端口在多租户下会让一个沙箱的调试端口被其他任务扫到，而调试端口通常没有任何鉴权。
2. 就绪判定不能靠固定等待。可靠的顺序是先确认进程仍存活，再确认端口进入监听，最后确认健康检查返回预期。少了第一步，一个启动即崩溃的服务会被当成"还在启动中"，直到超时才暴露，而超时报错与真实原因毫无关系。整个判定必须有上限，超时后要把启动日志作为证据带回。
3. 端口占用是这个场景的高频陷阱：上一次任务残留的进程仍在监听，本次启动其实失败了，探测却显示端口通，Agent 于是对着旧版本做验证并得出错误结论。每个任务用独立的网络命名空间，或在启动前校验监听进程的归属，都能消除它。
4. 长驻进程必须挂在任务的进程组与 cgroup 下，任务结束时整组回收。放任服务进程脱离管理，节点上会逐渐积累占着端口和内存的孤儿进程，症状是后启动的任务莫名其妙地失败，排查时几乎不会想到上一个任务。
5. 最重要的一条：HTTP 状态码为 200 不等于功能正确。验证要落在业务断言上——给定输入得到预期输出、页面出现预期文本、数据库产生预期记录。把状态码当验收标准，是这类"跑起来看效果"最常见的自欺。

这套能力显著提高了 Agent 自证的可信度，但也把不可信代码变成了长驻网络服务，出网限制与凭证隔离必须照常生效。可采集的指标包括服务启动成功率与就绪耗时分布、超时占比、节点上的孤儿进程数，以及带业务断言的验证在全部验证中的占比。

**相关知识点：** 回环地址监听、反向代理、健康检查、就绪探测、进程组与 cgroup 回收、孤儿进程、业务断言验收。

### 15. 需要浏览器或图形环境验证时，沙箱如何提供而不扩大攻击面？

提供方式已经相当成熟，难点全在后半问——**浏览器是一个功能完备的网络客户端兼代码执行器**，把它塞进原有沙箱，等于给已经建好的每一条限制开了一个新入口。

1. 多数验证只需要无头模式，通过 Chrome DevTools Protocol 驱动导航、点击与断言；确实需要真实图形栈的场景再叠一层 Xvfb 虚拟显示，并用 VNC 让人旁观。产出应固化为截图、DOM 快照与控制台日志这类可归档的证据，而不是只留一句"页面正常"。
2. 调试协议端点等同于本机代码执行能力：它能导航到本地文件、把内容下载到任意路径、创建新的浏览器上下文。这个端点必须只监听回环地址、不做端口映射，并且拒绝来自被测页面的连接——否则一个页面就能通过重绑定域名的方式反过来控制它。
3. 浏览器会绕过为包管理器设计的出网策略。它自己解析域名、自己建立 TLS 连接，不理会构建工具的代理配置。必须强制它走同一个 egress proxy 并保留默认拒绝，否则被测页面里的一个资源引用就是一条现成的外联通道。
4. 浏览器自身的多进程沙箱依赖 user namespace 等内核能力，而容器为收紧攻击面常把这些能力禁掉，实践中就用关闭沙箱的方式绕过——结果是渲染进程直接以容器权限解析不可信页面内容，最该被隔离的那一层反而失效了。要么为浏览器保留所需能力，要么把它放进一个独立的、更严的沙箱实例，后者通常更划算。

图形验证应当作为独立的能力域部署，而不是给编码沙箱加装软件包。被访问页面的文本同样进入上下文，是一条与仓库内容同级的注入载体，防御归注入专题。可采集的指标包括图形验证任务的成功率与耗时占比、调试端点的对外可达性检查（应恒为不可达，需主动测试而不是看配置），以及浏览器发起的出网请求中被代理拦截的比例。

**相关知识点：** 无头浏览器、Chrome DevTools Protocol、Xvfb、VNC、DNS rebinding、user namespace、egress proxy、DOM 快照。

### 16. 修改结果如何从沙箱提取为可审查的 patch？

提取的技术路径不难，难的是让产出**值得被人逐行看完**。一个混着格式化、生成文件与文件移动的补丁，通过率高不是因为它正确，而是因为没人读得下去。

1. 语义改动与格式噪声必须分开。Agent 触发一次全局格式化，几行真实修改会淹没在几千行重排里。可行的约束是只允许格式化本次改动触及的文件，或者把格式化单独落成一次提交，让评审可以整段跳过。
2. 重命名与移动要能被识别出来。相似度检测在多数工具链里默认开启，但伴随内容改动的跨目录大规模移动会超出默认的候选数上限，检测被跳过，结果仍然呈现为大量删除加大量新增，评审看到的行数与实际改动量差一个数量级。大规模移动应调高上限或单独成一次提交并说明。
3. 生成文件要标注而不是隐藏。锁文件、序列化的快照测试、由接口定义生成的代码都是真实且必须提交的内容，但不需要被逐行阅读。用 `linguist-generated` 这类属性把它们声明为生成物，评审界面可以默认折叠；直接隐藏或干脆不提交则会破坏可复现性。
4. 补丁要能自证：能在声明的基线上干净应用、应用后测试仍然通过、不包含被忽略规则覆盖的路径。这三项都可自动判定，应该在交给人之前跑完——让评审替机器做机械检查是最贵的用法。
5. 规模要有上限，而且上限要定得低。人对差异的审阅质量随体量迅速下降，超过阈值时正确做法是拆任务，或者先单独合并一次纯机械改动，而不是附一句"辛苦看一下"。

可审查性是产出质量的一部分，不是评审环节要自己消化的成本。可采集的指标包括补丁中格式化与生成文件所占行数比例、单个补丁的净改动行数分布、干净应用成功率，以及评审首轮通过率与人均阅读耗时——阅读耗时随行数增长会很快见顶，那个拐点就是规模上限的经验值。

**相关知识点：** 重命名与复制检测、`linguist-generated`、生成文件折叠、补丁干净应用、净改动行数、评审首轮通过率。

### 17. 沙箱产出如何落地为 PR？分支保护与 CI 触发如何配合？

这条链路最容易踩的坑是静默的：**用流水线自带的默认令牌创建的 PR 不会再触发工作流**——这是平台为防止递归的有意设计，后果是分支保护要求的检查永远处于待定，PR 卡死却没有任何报错。

1. 身份要独立。用专用的应用或机器人账号而不是借用发起人的个人凭证：归因才成立（谁发起、谁执行、谁批准是三件事）、吊销才不影响本人、权限才能单独收窄。独立身份签发的令牌同时也是绕开上述递归抑制的正规方式，检查会正常触发。
2. 触发方式的选择有安全含义。`pull_request_target` 这类在基仓库上下文中运行、能读到仓库密钥的事件，一旦检出并执行 PR 分支的代码就成为被反复利用的提权路径——工作流文件取自基分支，PR 只需改动会被执行的构建脚本或依赖即可。Agent 产出的 PR 应走与外部贡献同级别的触发方式：无密钥、只读令牌；需要密钥的检查放到合并后或由人触发。
3. 分支保护的配置要点是不留例外：要求必需检查通过、要求评审、禁止强制推送，且机器人身份不在任何绕过名单里。同样重要的是它不能自我批准——生成变更与批准变更必须是不同主体，否则整条审批链失去意义。
4. 自动合并可以开，但只在全部必需检查通过且有人评审之后。把自动合并理解成"省掉点击"而不是"省掉评审"，这个区分决定了它是效率工具还是事故来源。

这条链路的失败大多是配置性且静默的，所以要有端到端探针：定期跑一个完整流程，断言每个环节都按预期发生。可采集的指标包括 PR 创建成功率、检查触发率（应为百分之百，低于即为静默故障）、从创建到检查完成的耗时，以及自动合并的变更中事后被回滚的比例。

**相关知识点：** 机器人身份、branch protection、必需状态检查、`pull_request_target`、auto-merge、端到端探针、职责分离。

### 18. 如何在提交前拦截密钥、大文件与生成物？

拦截点选错，整套检测就只是摆设——**客户端钩子跑在沙箱里，而沙箱正是被约束的对象**：它能被跳过、被改写、被绕开。真正的边界只能在服务端。

1. 服务端的 pre-receive hook 或推送规则是唯一不可绕过的位置；客户端检查的价值只剩快速反馈与减少无效往返。两处应共用同一份规则，否则会出现"本地过了服务端挂"的割裂体验，团队最终会去关掉更严的那一侧。
2. 三类目标的检测方式并不通用。密钥靠已知服务商的令牌前缀加高熵串识别，可选地对候选值发起一次只读调用确认是否仍然有效——这能极大降低误报，但它本身是一次外联，必须走受控出口且绝不记录明文。大文件靠对象大小阈值，命中后引导到 Git LFS 而不是直接拒绝。生成物靠路径规则加内容特征，因为同一个文件在不同仓库里可能是生成物，也可能是手写的。
3. 命中密钥后拦住推送只解决了一半。这个值已经存在于沙箱磁盘、会话记录与本地提交历史里，正确顺序是先吊销、再清理，最后才谈重写历史。把重写历史当成解决方案是典型误判：旧对象仍可被直接引用取到，克隆副本与各级缓存也不会跟着变。
4. 豁免要按发现项的内容指纹而不是按路径。测试固件里的假密钥反复触发告警时，人会去关掉整个目录，而那个目录以后新增的真密钥就一并放行了。按具体值的哈希豁免既保留检测能力，又让豁免本身可审计、可设过期。

这类检测的误报会直接转化为对规则的信任流失，所以调优目标不是零漏报，而是让每一条告警都值得看。可采集的指标包括拦截命中数按类型的分布、误报比例与豁免条目增长率、从命中到凭证吊销完成的耗时，以及事后在历史中扫出的漏网数量——漏网数持续不为零时，应先修检测覆盖率再谈流程。

**相关知识点：** pre-receive hook、推送规则、高熵串检测、令牌前缀识别、Git LFS、凭证吊销顺序、按指纹豁免。

### 19. 同一任务多次迭代产生的中间提交如何整理？

中间提交的价值是不对称的：对评审者是噪声，对失败复盘和行为分析却是唯一的证据。所以正确的做法不是"整理掉"，而是**让两种用途各拿一份**。

1. 保留两条链。任务分支上完整记录每一次尝试与回退，用于分析 Agent 在哪一步走错、以及重跑时能从哪里接上；推给评审的是重新组织后的版本。前者的留存期可以很短，但不能在整理的那一刻就直接丢弃。
2. 整理手段按可靠性排序。让 Agent 在产生每次改动时就用 `fixup` 标注它属于哪个逻辑单元、之后由 `autosquash` 自动折叠，比事后让模型重新划分归属可靠得多——事后重组要求它准确判断哪些行属于同一意图，恰恰是它容易出错的地方。全部压成一个提交最省事，代价是丢失 bisect 的定位粒度，对大改动不划算。
3. 提交信息要写动机而不是复述差异。模型倾向于把改了什么再说一遍，而这部分读补丁就能看到；有价值的是为什么改、依据是哪条失败用例或哪项需求。信息里还应带上任务标识与生成方式标注，让后续能按来源统计缺陷分布。
4. 已经推送并进入评审的分支不要重写。评论挂在具体提交上，重写后全部失效，评审要从头再来。此时正确做法是追加提交，等合并时再由平台按策略压缩。

整理的投入要与改动规模匹配：三行的修复压成一个提交就够了，跨十几个文件的重构才值得费力划分逻辑单元。可采集的信号包括每个 PR 的提交数分布、整理前后评审首轮通过率的差异，以及因重写历史导致评审重来的次数——若通过率没有明显改善，说明噪声其实来自补丁内容而不是提交结构，该改的是上一环。

**相关知识点：** fixup 提交、autosquash、squash 合并、交互式变基、bisect 粒度、提交信息规范、生成来源标注。

### 20. 沙箱产出的构建工件如何签名与溯源？

先接受一个不舒服的前提：**Agent 沙箱是一个由被构建方可控的构建环境**，它产出的工件天然拿不到高等级来源证明。签名只能证明"这是我们平台跑出来的"，证明不了"构建过程没有被待构建的代码影响"。

1. 因此发布路径必须分开：沙箱负责产生变更并验证其合理性，进入制品库的工件由独立的受信流水线基于合并后的提交重新构建。这条分离正是 SLSA 这类框架的核心要求——构建平台的完整性不能依赖被构建的项目本身。
2. 证明要绑定内容摘要而不是名称。in-toto 风格的 attestation 由主体（工件的哈希）与断言体（用什么源码、什么构建器、什么参数产生）组成；验证方拿到工件先算哈希再找对应证明。名称与标签都可以被替换，摘要不行。
3. 签名建议走无密钥路径：以工作负载的 OIDC 身份换取短时证书完成签名，签名与身份一并记入可公开查询的透明日志。它避免了长期私钥的保管与轮换问题，并把"某个身份在某时刻签过什么"变成第三方可核对的事实。
4. 物料清单要在构建时生成。构建后扫描只能看到最终产物里残留的痕迹，而构建时能拿到包管理器真实的解析结果，包括最终选定的版本与全部传递依赖，两者的差距在多层依赖的项目里相当可观。
5. 没有验证的签名等于没签。消费侧必须有准入策略：只接受特定签名者、特定构建器、来源提交位于受保护分支的工件，不满足就拒绝部署。策略还要真正运行在拦截模式下——只观察不拦截的策略很容易长期停在观察态，而没人会注意到。

这套机制的成本主要落在改造消费侧，收益却要到发生供应链事件时才显现，因此很容易被排到后面。可采集的指标包括带完整证明的工件占比、准入策略的拒绝次数与其中误拒比例，以及从发现某个依赖有问题到定位出全部受影响工件的耗时——最后一项是这项投入最直接的回报。

**相关知识点：** SLSA、构建平台完整性、in-toto attestation、无密钥签名、透明日志、SBOM、准入策略。

### 21. 沙箱执行记录要留什么，才能回答「谁在什么代码上跑了什么命令」？

这句话里的三个成分各有各的坑，而**最常被记错的是"什么代码"**：记下分支名等于什么都没记，因为分支会移动。

1. "谁"是一条链而不是一个字段：发起的人、批准的人、实际执行时使用的机器身份，以及从机器身份回到人的映射。只记机器人账号，审计时会得到一堆同一主体的记录；只记发起人，又无法区分某个动作是自动执行还是人工确认过的。
2. "什么代码"要用不可变标识：仓库、基线提交的完整哈希、工作树内容的哈希、镜像摘要、依赖锁文件哈希。这几项合起来才能在事后把当时的环境重新搭出来。分支、浮动标签这类可变引用只作为辅助信息记录，不能当定位依据。
3. "什么命令"要记参数数组而不是拼接后的字符串。拼接串丢失了参数边界，含空格或引号的参数事后无法还原成执行时的真实形态，而那正是分析可疑命令时最需要的细节。同时记录工作目录、有效用户、环境变量的键集合（值不记）、退出码、起止时间与输出摘要。
4. 三者要靠一个贯穿全链的任务标识串起来，而且这个标识必须跨系统：写进沙箱记录、写进提交尾部、带进 CI 的运行上下文。缺了它，回答一个问题要在三套系统里按时间戳做模糊匹配，而时间戳在并发场景下根本不足以区分。

记录的完整性比丰富度更重要：字段缺失的记录在调查时会被整条丢弃，等于白采。可采集的指标包括关键字段的完整率、执行记录与提交、CI 运行的关联成功率、按任务标识检索的平均耗时，以及抽样复核中"能否据此还原当时环境"的通过率——这项抽查是唯一能检验记录是否真的够用的方式。

**相关知识点：** 参数数组记录、基线提交哈希、镜像摘要、工作树内容哈希、任务关联标识、提交尾部、字段完整率。

### 22. 沙箱审计数据如何满足合规要求？留存与访问如何控制？

合规对这类数据施加的是**三个方向相反的要求**：留够久、别留太多、还要能按请求删除。把它们当成一件事去做，一定会在某一条上违规。

1. 拆解的关键是把元数据与载荷分开存。谁在什么时间对哪个仓库做了什么，是体积小、不含个人数据、需要长期留存的元数据；命令的完整输出、文件内容、补丁正文则是体积大、可能含个人数据与源码的载荷。前者按合规下限长期保存，后者按最短必要期保存，这也直接呼应数据最小化原则。
2. 不可变与可删除的矛盾用加密切分来解：载荷加密存储，密钥按数据主体或按仓库分片管理，需要删除时销毁密钥即可让密文不可恢复，而承载它的不可变存储不必被改动。这条路径必须事前设计好密钥粒度，事后再拆几乎不可行。
3. 访问控制要比生产数据更严。审计记录里有源码片段、内部主机名与完整命令行，一次越权查询的收益比读一个业务库还大。默认无人可读，调查时通过 break-glass 临时授权开启，全部查询本身留痕并定期复核；含源码的字段再加一道授权。
4. 跨境与数据驻留要求会直接决定架构。源码及其执行记录在不少行业被要求不出境，这意味着审计存储要按区域切分，全局检索只能在元数据层做。这一条留到上线后再补，代价是把已经写入的数据整体搬迁一遍。

合规不是一次性达标，法规与内部政策都会变，所以留存策略要做成可配置而不是硬编码进采集端。可采集的指标包括各类数据的实际留存分布与策略的一致率、超期未清理的数据量、审计查询的授权通过率与复核覆盖率，以及删除请求从受理到完成的耗时。

**相关知识点：** 数据最小化、留存期策略、crypto-shredding、WORM 存储、break-glass 授权、数据驻留、查询留痕。

### 23. 沙箱成本如何归属到团队、仓库与任务？

编码 Agent 的成本结构里，**沙箱算力常常不是大头**——模型推理的开销与它同量级甚至更高，只按实例小时数算会得到一份误导性的账单。

1. 计量口径要覆盖四类：实例的计算与内存时长、镜像与缓存占用的存储、出网与制品拉取流量、每次任务消耗的 Token。四类的驱动因素不同，分摊方式也就不能统一——把预热池的存储成本按任务数摊薄是合理的，按 Token 摊则毫无意义。
2. 归属靠创建时打标签，不能靠事后关联。团队、仓库、任务标识、触发方式（人工发起还是定时批量）必须在实例创建那一刻写入，实例销毁后没有任何补救办法。标签缺失的支出会堆进一个无人认领的池子，而这个池子往往正是增长最快的部分。
3. 共享成本的分摊方式会改变行为。预热池空转、控制面、公共缓存无法直接归属；若按用量摊给各团队，团队就会主动反对预热——它们承担成本却感受不到收益。更合理的做法是把可归因的部分做 chargeback、直接计入团队账单，公共设施留在平台账上只做 showback、供参考而不计费，同时单独给平台侧的空转率定目标。
4. 单位成本的分母要选对。用"每个沙箱小时"会鼓励减少重试，而重试恰恰是提高任务成功率的手段；用"每个被采纳的产出"才与业务价值对齐，代价是这个口径滞后于支出，需要配一个短周期的先行指标。

成本数据的用途是决策而不是问责；口径一旦被用于考核，各方就会开始优化口径本身而不是真实开销。可采集的指标包括标签覆盖率、无法归属支出的占比、各团队的单位产出成本分布，以及预热池空转成本占总成本的比例——最后一项是平台侧最容易独立优化、也最容易被忽略的部分。

**相关知识点：** 成本标签、chargeback 与 showback、Token 成本、单位产出成本、空转率、共享成本分摊。

### 24. 如何从沙箱行为数据中识别异常与滥用？

能把误报压到可用水平的，是**特征的组合而不是单个阈值**：沙箱里的正常构建本来就会打满 CPU、疯狂读写文件、大量拉取网络资源，每一项单看都像异常。

1. 算力盗用的特征组合相当干净：CPU 长时间满载、文件写入量极低、进程数稳定、出网目的地固定且与制品源无关。四项同时成立时几乎没有正常解释；而任取其一，都会淹没在正常构建里。
2. 数据外带看的是形状而不是流量：大范围遍历读取源码与凭证路径之后紧接着出网、压缩后单向上传、以及域名解析请求量异常升高。最后一项对应把数据编码进查询名的 DNS exfiltration，只看连接数会完全漏掉。
3. 能力探测的信号最确定，也最值得自动阻断：访问 IMDS 地址、尝试挂载或变更命名空间、读取其他进程的信息、触发被 seccomp 拒绝的高危系统调用。这类行为在正常编码任务里几乎没有合理理由，可以直接终止并保留现场。
4. 基线必须按仓库与任务类型建立。一个大型单体仓库的正常构建可以占满一台机器一小时，用全局阈值衡量它会天天告警；同样的负载出现在小仓库上则高度可疑。基线还要随仓库自身演进滚动更新，否则新增的重量级测试套件会被长期误判。
5. 产出应是排序过的调查队列而不是一律阻断。绝大多数偏离来自正常的行为变化，自动阻断只留给上面那类确定性极高的信号；其余进入人工调查，并保留回到那次会话输入的链路——Agent 的异常行为可能源于注入而不是发起人的意图，不看输入就会归错责任。

行为检测的价值随覆盖面增长，但采集本身有成本，而且这些数据自身就是敏感资产。可采集的指标包括告警量与调查后的确认率、从行为发生到告警的耗时、自动阻断的误伤次数，以及各类特征组合的独立命中率——某个组合长期零命中，要么威胁不存在，要么采集根本没覆盖到它。

**相关知识点：** 行为基线、特征组合检测、cryptojacking、DNS exfiltration、IMDS、seccomp 拒绝事件、调查队列。

### 25. 沙箱审计日志本身如何防篡改？

先定威胁模型再选机制，否则会做出**看着很密、实际防不住任何具体攻击者**的方案。防沙箱内的执行者、防有权限的运维、防存储层，三者的答案完全不同。

1. 防沙箱内的执行者最容易也最必要：日志不落在被审计的沙箱里，由沙箱外的采集器直接写入，沙箱内的进程不持有任何写审计或删审计的凭证。多数团队真实的威胁模型到此为止，把这一条做扎实的收益远大于后面那些更复杂的机制。
2. 防有权限的内部人要靠链式结构加外部锚定。用哈希链或 Merkle 树把记录串起来，任何删改都会让后续校验失败；但只做链不够——有权限的人可以整条重算。必须定期把根哈希发布到另一个信任域：不同账号下的不可变存储、第三方透明日志或公证服务。锚定频率直接决定了可被无痕篡改的时间窗有多宽。
3. 存储层用对象锁定，但要分清两种模式：治理模式允许具备特定权限的主体解除锁定，适合防误删；合规模式在保留期内任何身份都无法删除，包括账号所有者，代价是写错的数据也删不掉，因此要配更严的写入前校验。把两者混同，会以为自己有不可变性而实际没有。
4. 完整性不只是"已有记录没被改"，还包括"该有的记录没缺"。删掉一段日志和采集链路中断，事后无法区分。因此每个来源要维护单调递增的序号，消费端做缺口检测，缺口本身就是需要调查的事件而不是运维噪声。

防篡改的目的是让证据在事后争议中站得住，所以机制要能向第三方解释清楚；过于自定义的方案在这一点上先天不利。可采集的指标包括链式校验的执行频率与失败次数、根哈希锚定的间隔分布、序号缺口的发生次数与补齐耗时，以及单次完整性验证覆盖的记录比例。

**相关知识点：** 哈希链、Merkle 树、外部锚定、透明日志、对象锁定、治理模式与合规模式、序号缺口检测。

### 26. 如何验证沙箱真的隔离了？有哪些可执行的对抗性测试？

隔离是配置出来的，而配置会漂移，所以验证的形式必须是**每次变更都重跑的回归测试**而不是上线前的一次渗透。判定标准也要写死：动作被拒绝，并且产生了一条对应的审计记录。

1. 文件系统面：尝试读取宿主的根挂载与一号进程的根目录、枚举挂载点、跟随指向沙箱外的符号链接、向只读挂载点写入、访问其他任务的工作目录。这一面的问题多半来自为了方便临时加的挂载，因此每次挂载配置变更都必须重跑。
2. 内核与进程面：跟踪其他进程、创建或加入新的命名空间、执行挂载与切换根目录、加载内核模块、读写内存与内核参数接口。这些用例同时在检验系统调用过滤与 capabilities 裁剪是否按预期生效，而这两项在运行时升级后最容易悄悄回退。
3. 网络与身份面：连接 IMDS 地址、连接宿主网关与集群内部服务、向任意外部地址发起连接、用域名解析携带数据、读取挂载进来的服务账号令牌。这一面最值得投入，因为它同时对应数据外带与横向移动两类后果。
4. 资源面：制造进程爆炸、超额申请内存、写满磁盘、占满网络带宽，期望是只有发起的任务自身失败，同节点其他任务不受影响。资源隔离常被当成性能问题而不是安全问题，因此在配置里往往最先被放松。
5. 用例集本身就是攻击工具，要限制分发范围、只在受控环境执行，并且与被测平台一起做版本管理——一份与当前配置对不上的用例集跑绿了，制造的是虚假信心。

这类测试证明的是"已知边界成立"，不能证明不存在未知路径，因此它与红队演练是互补而非替代关系。可采集的指标包括用例通过率（应恒为百分之百，任何一条失败按线上安全缺陷处理）、被拒绝动作中产生审计记录的比例、用例集相对平台新增能力的更新滞后，以及每次运行时或内核升级后回归的执行耗时。

**相关知识点：** 隔离回归测试、挂载点枚举、符号链接穿越、Linux capabilities、IMDS、服务账号令牌、fork bomb、资源隔离。

### 27. 逃逸演练如何组织？红队应重点攻击哪些面？

演练要先把成功判据定成**具体的资产而不是抽象的权限**——"拿到 root"推导不出损失，"读到另一个租户的源码"或"改写了公共基础镜像"才能直接推出该修什么。

1. 组织上先划范围与停止条件：哪些环境在范围内、哪些数据绝对不能触碰、遇到真实客户数据时立即停止并上报、演练凭证与真实凭证如何区分。缺了停止条件，一次演练本身就可能变成事故。
2. 蓝队是否知情按目的选择。目的是验证防护配置时，双方协作的紫队方式效率最高——攻击方每走一步，防守方同步对照检测是否触发，直接产出一份检测覆盖缺口清单；只有目的是检验响应流程时才需要不知情，而这种演练成本高、频率必须低。
3. 攻击面按真实收益排序，而不是按技术难度。第一位是配置错误：特权容器、挂载宿主目录或容器运行时套接字、过宽的服务账号权限，它们提供的是直达路径。第二位是供应链：往基础镜像、公共缓存或工具链里写入，比攻破内核容易得多，影响面还更大。第三位是控制面：任务提交接口的越权，例如用别人的仓库标识发起任务。第四位是横向移动：沙箱之间、沙箱到 CI、沙箱到制品库。内核与运行时漏洞排在最后——它要求具体版本可利用，而前四类几乎总是存在。
4. 产出必须可执行：每个发现要转成一条进入回归用例集的测试、一条检测规则，或一处默认配置的收紧，并带上责任人与期限。只交一份报告的演练，半年后会发现同样的问题原样还在。

演练频率应与变更速度匹配：架构稳定时一年一次足够，重构隔离层的那个季度必须加做。可采集的指标包括从首次落地到达成目标资产的耗时、每个阶段是否被检测到及其时延、发现项转化为回归用例的比例，以及上一轮发现项在本轮的复现次数——复现说明上次的修复停留在了单点。

**相关知识点：** 红队演练、紫队协作、rules of engagement、关键资产、配置错误、供应链攻击面、控制面越权、横向移动。

### 28. 沙箱平台的 SLO 该怎么定？哪些指标直接影响 Agent 成功率？

沙箱平台的消费者是编排层而不是人，所以传统的接口可用性远远不够：**沙箱起来了但环境不对，在任何可用性口径下都算成功，却是最贵的一类失败**。

1. 服务等级指标要按任务生命周期的关键时刻定义，至少四个：获取沙箱的成功率与排队时延、环境就绪的正确率、执行期的非任务原因中断率、产出可交付率（补丁能在基线上应用）。四者串起来才是编排层真正感知到的可用性，缺一个就会留下一段无人负责的区间。
2. 最有效的测量手段是探针任务：用一个已知必然通过的小仓库任务端到端跑完，把它的通过率当作服务等级指标。它一次覆盖上面四段，也是唯一能发现"环境静默不对"的方式；接口层的健康检查对此完全无感。
3. 第二问要单独回答：并非所有指标都影响任务成功率。冷启动时延主要影响成本与体验，多跑十秒不会改变结论；真正影响成功率的是环境正确性、执行结果的确定性与中断率。环境缺一个工具会让模型把失败当成代码问题，进而做出错误修改，而错误的修改代价远高于一次明确的失败。执行结果不确定则直接破坏 Agent 的验证循环——它无法再用重跑来确认自己改对了。
4. 错误预算的消费方要写清楚。预算被消耗时该停下来的是平台侧的变更（新镜像、新运行时、新调度策略），而不是限制业务使用。这一点不明确，错误预算就只是仪表盘上的一个数字。

指标定得太多会稀释注意力，四个关键指标加一个探针通过率通常够用，其余作为诊断指标而非对外承诺。这套指标本身要定期用真实事故回测：如果某次影响面很大的故障没有让任何一个指标明显恶化，说明覆盖存在缺口，修这个缺口比调整目标值重要得多。

**相关知识点：** SLI、SLO、错误预算、探针任务、排队时延 P95、环境就绪正确率、静默故障。

### 29. 沙箱故障如何降级？降级期间哪些能力必须关闭？

这类平台的降级方向与在线服务相反：**在线服务优先保可用，沙箱平台应优先保正确与安全，牺牲的是吞吐**。一个返回了错误结果的沙箱，危害远大于一个明确拒绝服务的沙箱。

1. 容量类故障降级为排队加分级准入：交互式会话优先于后台批量，已在执行的任务优先于新任务。这一档对正确性无损，是唯一可以放心自动执行的降级。
2. 依赖类故障要有明确的回退目标。基础镜像或制品源不可用时，回退到上一个已知良好的镜像摘要或备用镜像源，而不是让任务自行寻找替代来源——后者会把一次可用性事件变成一次供应链事件。缓存层故障则直通构建，慢但结果仍然正确。
3. 隔离层故障不降级。运行时异常、系统调用过滤加载失败、网络策略下发不成功，正确反应是拒绝调度，而不是以更弱的隔离继续跑。把"先跑起来再说"用在这一档，等于在故障期间取消了平台的全部安全属性。
4. 后半问的清单要事先写死，分成两类。必须关闭的是无人复核的写路径与不可信执行：自动合并与自动推送、外部来源代码的任务、批量后台任务、需要真实凭证的集成测试。绝不能因降级而放宽的是：出网默认拒绝、凭证注入范围、提交前的密钥扫描、审批要求、隔离级别——这五项在压力下最容易被临时放开，事后也最难发现曾被放开过。
5. 一条容易被忽略的强约束：审计管道故障时应停止执行而不是无记录地继续。没有记录的执行在事后无法复盘、无法归因，等于在故障期间自造了一段盲区。

降级要能自动触发也能人工强制，每次进入与退出都留下记录与原因。可采集的指标包括各档降级的触发次数与持续时长、降级期间的任务成功率与拒绝率、被临时放宽的安全约束数量（目标为零），以及从故障发生到进入正确档位的耗时。

**相关知识点：** 分级准入、优雅降级、已知良好版本回退、fail-closed、直通构建、审计管道可用性、安全约束基线。

### 30. 沙箱相关事故的复盘应该沉淀哪些可执行改进？

判断一项改进是否"可执行"只有一个标准——**它有没有验收方式**。写不出"改完之后用什么来证明它生效"的条目，是一句愿望，不是改进项。

1. 第一类沉淀是回归用例。每次事故的触发路径都应变成隔离验证用例集里的一条，此后每次配置与运行时变更都会重跑它。这是所有防复发手段里唯一自动生效的一类，优先级应当最高。
2. 第二类是检测规则，配套要记录的是检测滞后——从事故实际发生到被发现之间的时长。改进目标是把这个时长压短，而不是笼统地"加强监控"。如果发现渠道是用户报障而不是告警，说明这条路径的检测覆盖为零。
3. 第三类是默认值与护栏的收紧，也是最容易做半截的一类。只修出问题的那个仓库或那台节点，等于把同样的事故留给了其余全部对象。正确的问法是"这个配置为什么允许被设成这样"，答案通常指向一个应该被收窄的默认值。
4. 第四类是把预案变成可执行的东西。演练中发现的"需要临时找人执行一串命令"应该变成一个按钮或一条脚本；只停留在文档里的步骤，在真实事件的压力下没人会照着做。
5. 反模式要点名：根因写成"人为失误"就停止追问，实际该问的是为什么这个操作可以在没有防护的情况下完成；以及给每次事故加一道审批，审批数量单调增长之后，所有审批都会退化成走过场。

复盘质量无法在复盘当场评价，只能靠后续验证。可采集的指标包括改进项的按期完成率与带验收方式的比例、同类事故的复发次数、平均检测滞后与止损耗时的趋势，以及改进项中属于默认值收紧的占比——同类复发次数不为零时，前面所有的产出量都不能算成绩。

**相关知识点：** 无指责复盘、行动项跟踪、回归用例集、MTTD、MTTR、默认配置收紧、复发率。
