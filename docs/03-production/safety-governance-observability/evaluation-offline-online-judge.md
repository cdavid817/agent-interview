# 评估基础、离线/在线评估与 LLM-as-a-Judge

> 所属章节：[安全、治理与可观测性](README.md)｜本文件共 **32** 题。

<a id="gov-252"></a>
### 1. 什么是 Agent 评估（Evaluation）？它和传统软件测试有什么区别？

Agent 评估是**用数据集、评分器和指标系统性衡量 Agent 输出与过程质量**的活动；与传统软件测试的区别在于被测对象非确定、正确性多为程度而非布尔值，且需要评估过程（轨迹）而不仅是结果。

1. 传统测试断言确定的输出；评估用分数、通过率与分布描述质量，允许一定波动。
2. 评估维度更多：正确性、相关性、忠实度、安全性、成本、延迟、工具使用是否合理。
3. 评分器包括代码判定、LLM 评委和人工，各自的可靠性都需要验证。
4. 评估既在上线前离线进行，也在生产中持续在线进行，形成闭环。
5. 评估结果用于回归门禁、版本对比与问题归因，而不是一次性验收。

**相关知识点：** Agent 评估、非确定性、程度性正确、轨迹评估、评分器、回归门禁。
<a id="gov-253"></a>
### 2. 为什么大模型应用不能只靠人工抽查，而需要系统化评估？

人工抽查**样本少、主观、不可复现、无法跟上迭代速度**，Prompt、模型或工具的任何一次改动都可能引发难以察觉的回归，只有系统化评估才能量化质量并守住底线。

1. 覆盖：抽查几十条无法覆盖长尾输入，系统化评估集可达数百到数千条并按场景分层。
2. 一致性：固定数据集与评分标准使不同版本、不同时间的分数可比。
3. 速度：自动评估可在 CI 中数分钟完成，支撑每天多次迭代。
4. 归因：按维度与切片统计能定位是检索、Prompt 还是工具导致的下降。
5. 人工不是被取代，而是用于校准评分器、标注黄金集和处理疑难样本。

**相关知识点：** 系统化评估、回归、覆盖率、可复现、切片分析、人工校准。
<a id="gov-254"></a>
### 3. 评估通常关注哪些维度？

常见维度可分为**结果质量、过程质量、安全合规和工程效率**四组，具体指标按任务类型选取，不追求一次评全。

1. 结果维度优先用可验证方式（测试、规则、业务状态）判定，再用 Judge 补充开放式部分。
2. 过程维度依赖轨迹记录，是 Agent 评估与普通问答评估的主要差异。
3. 各维度权重随业务而定，例如金融场景忠实度与安全优先，客服场景相关性与延迟优先。

| 组别 | 维度示例 |
|---|---|
| 结果质量 | 正确性、相关性、完整性、忠实度/引用准确、格式合规 |
| 过程质量 | 工具选择与参数正确率、步数、冗余调用、是否遵循约束 |
| 安全合规 | 有害内容、注入抵抗、隐私泄露、越权操作 |
| 工程效率 | 延迟、Token 与成本、成功率、重试次数 |

**相关知识点：** 正确性、相关性、忠实度、安全性、过程质量、成本与延迟、指标权重。
<a id="gov-255"></a>
### 4. 什么是评估数据集？一条评估样本一般包含哪些字段？

评估数据集是**一组带预期或评分依据的输入样本**；一条样本通常包含输入、上下文、预期输出或验收标准、元数据四部分。

1. 输入：用户问题或任务描述、对话历史、可用工具列表、初始状态。
2. 上下文：应检索到的文档、环境快照、Mock 工具返回，保证可复现。
3. 预期：参考答案、必含/禁含要点、期望的工具调用序列、验收规则或 Rubric。
4. 元数据：场景标签、难度、来源（生产/合成/人工）、创建时间、版本。
5. 样本应可被代码或 Judge 自动判定，并记录预期口径以便统计通过率，避免"看起来对就算对"。

**相关知识点：** 评估数据集、样本 Schema、参考答案、验收标准、Mock 工具、元数据标签。
<a id="gov-256"></a>
### 5. 什么是 Golden Dataset（黄金数据集）？它是如何构建和维护的？

黄金数据集是**经过人工确认、被视为可信标准的高质量评估样本集**，用于回归门禁和评分器校准；它通过多来源采集、专家标注、交叉复核和定期更新来构建与维护。

1. 来源：生产真实请求（脱敏）、失败案例、边界与对抗样本，少量合成数据补足覆盖。
2. 标注：领域专家给出参考答案与验收要点，至少两人复核，分歧样本讨论定稿。
3. 版本化：与代码同库管理，变更记录原因；评估报告注明使用的数据集版本。
4. 维护：定期加入新出现的失败模式，剔除过时或已泄漏到 Prompt 示例中的样本。
5. 规模不求大，求准：几百条高质量样本比几万条噪声样本更能反映真实通过率的变化。

**相关知识点：** Golden Dataset、人工标注、交叉复核、版本化、失败案例回流、数据泄漏。
<a id="gov-257"></a>
### 6. 什么是评估的可复现性？为什么模型输出的随机性会影响评估结果？

可复现性是**同一评估在不同时间重复运行能得到一致结论**；模型采样随机性、依赖服务变化和评委随机性都会让分数抖动，需要用固定配置和多次运行来控制。

1. 固定可控变量：模型版本、temperature（评估时通常设 0 或较低）、seed、Prompt 版本、工具 Mock。
2. 多次运行取均值与置信区间，用 pass@k 或成功率的区间判断差异是否显著，而不是看单次分数。
3. 评委也有随机性：固定评委模型版本与 Prompt，并测量评委自身的一致性。
4. 外部依赖（检索库、API）用快照或录制回放，避免环境漂移。
5. 报告中记录所有配置，任何分数变化先排除配置差异再归因。

**相关知识点：** 可复现性、随机性、temperature、seed、置信区间、pass@k、录制回放。
<a id="gov-258"></a>
### 7. 什么是离线评估？它一般在什么阶段进行？

离线评估是**在非生产环境用固定数据集对系统进行批量评估**，一般在开发迭代、上线前和每次变更后进行，作为发布门禁。

1. 输入来自评估集而不是实时流量，可以反复运行、可以对比历史版本。
2. 适合发现回归、比较候选方案（Prompt A/B、模型替换）、做消融实验。
3. 局限：数据分布可能偏离生产，无法评估真实用户满意度与长期效果。
4. 常与 CI 集成，变更提交后自动运行并阻断低于阈值的合并。
5. 关键输出：各维度得分、按切片的通过率、与基线的差异及显著性。

**相关知识点：** 离线评估、评估集、回归检测、发布门禁、消融实验、分布偏移。
<a id="gov-259"></a>
### 8. 离线评估的基本流程是什么？

基本流程是**准备数据集 → 固定配置运行被测系统 → 用评分器打分 → 汇总指标并与基线对比 → 分析失败样本**。

1. 准备：选择版本化的评估集，确认样本覆盖目标场景，准备工具 Mock 与环境快照。
2. 运行：批量执行，记录每条样本的输出、轨迹、耗时与 Token，保存为可复查的结果文件。
3. 打分：按维度调用代码判定、LLM 评委或人工标注，得到每条样本的分数与理由。
4. 汇总：计算通过率、平均分、分位数，按场景/难度切片，与基线做显著性比较。
5. 分析：抽查失败样本，归类错误类型，把新失败模式回流到评估集。

**相关知识点：** 评估流水线、批量运行、评分器、基线对比、切片统计、失败归类。
<a id="gov-260"></a>
### 9. 什么是回归测试？Prompt 或模型变更后如何做回归评估？

回归测试是**验证变更没有破坏原有能力**；Prompt 或模型变更后，用同一评估集在新旧版本上运行，比较各维度分数与逐样本通过情况。

1. 固定评估集与评分配置，只改变被测版本，确保差异来自变更本身。
2. 不只看总分：逐样本对比找出"原来对、现在错"的样本，这类回归最需要关注。
3. 设定门槛：关键维度不得下降超过阈值，安全类样本必须全部通过。
4. 模型升级要覆盖格式、工具调用、拒答行为等易变项，Prompt 变更要覆盖被改动意图的样本。
5. 结果与版本号、提交记录绑定，失败即阻断发布并记录原因。

**相关知识点：** 回归测试、逐样本对比、门槛阈值、Prompt 版本、模型升级、发布阻断。
<a id="gov-261"></a>
### 10. 离线评估如何处理没有标准答案的开放式任务？

没有标准答案时，把"对不对"改写为**可检查的要点、约束和质量维度**，用 Rubric、参考要点、成对比较或经人工校准的 LLM 评委来评估。

1. 要点清单：定义必须包含、不得包含的信息点，由代码或评委检查覆盖率。
2. Rubric 评分：按相关性、准确性、完整性、表达等维度分级描述，评委按级打分。
3. 成对比较：让评委在两个版本的输出间选优，比绝对打分更稳定。
4. 约束检查：格式、长度、语言、安全等硬约束仍用代码判定。
5. 用人工标注的小样本验证评委与人的一致性，达标后再放大规模。

**相关知识点：** 开放式任务、要点清单、Rubric、成对比较、硬约束、评委一致性。
<a id="gov-262"></a>
### 11. 什么是基线（Baseline）？为什么要和基线对比而不是只看绝对分数？

基线是**当前已知的参照版本或分数**，只有与基线对比才能判断变更是"改善、持平还是退化"；绝对分数受数据集难度与评委偏好影响，本身没有可比性。

1. 常见基线：线上当前版本、上一次发布、简单方案（直接调用模型）或人类水平。
2. 对比要在相同数据集、相同评分器、相同配置下进行。
3. 关注差异的显著性与切片：总分持平但某个场景大幅下降同样是回归。
4. 基线要随发布更新，并保留历史曲线观察长期趋势。
5. 报告写法："相对基线完成率 +3.2 个百分点（95% 置信区间 [1.1, 5.3]）"。

**相关知识点：** Baseline、相对比较、显著性、切片回归、历史趋势、置信区间。
<a id="gov-263"></a>
### 12. 离线评估的数据集应该多大？如何保证覆盖典型场景和边界情况？

规模由**希望检测的最小差异和置信度**决定，通常每个关键场景几十条、总计几百到上千条；覆盖靠场景分层、难度分层和边界样本保证。

1. 统计角度：要稳定检测 3～5 个百分点的通过率变化，每个切片一般需要上百条样本。
2. 分层抽样：按意图类型、用户群、语言、工具组合划分，每层设最低样本数。
3. 边界样本：空输入、超长输入、模糊意图、冲突信息、工具失败、注入攻击。
4. 来源多样：生产日志、历史失败案例、专家构造、合成生成，并标注来源以便分析。
5. 定期用覆盖报告检查各层样本数与失败分布，补齐薄弱切片。

**相关知识点：** 样本规模、最小可检测差异、分层抽样、边界样本、覆盖报告、合成数据。
<a id="gov-264"></a>
### 13. 什么是数据泄漏？评估集与 Few-shot 示例或训练数据重叠会有什么问题？

数据泄漏是**评估样本或其答案已经出现在被测系统的 Prompt、Few-shot 示例、训练或微调数据中**，导致分数虚高，无法反映真实泛化能力。

1. Few-shot 示例若与评估样本相同或高度相似，模型只是在复述而不是解决问题。
2. 微调数据混入评估集会让离线分数远高于线上表现。
3. 检测方法：对评估集与 Prompt/训练集做精确与近似去重（哈希、n-gram、Embedding 相似度）。
4. 治理：评估集单独管理与访问控制，新增示例前先查重。
5. 保留一个从不用于调优的 Holdout 集，用于最终验证。

**相关知识点：** 数据泄漏、Few-shot 污染、去重、Embedding 相似度、Holdout、泛化能力。
<a id="gov-265"></a>
### 14. 如何把离线评估集成到 CI/CD 流水线中？

把评估当作**自动化测试的一部分**：变更触发评估流水线，输出分数与失败样本，低于门槛阻断合并或发布，报告归档以便追溯。

1. 分层执行：提交时跑小规模冒烟集（几分钟），合并前跑完整集，发布前跑全量加安全集。
2. 评估脚本读取版本化数据集与配置，输出机器可读结果（JSON/JUnit），与基线自动比较。
3. 门槛策略：关键维度不得回退、安全样本全部通过、成本与延迟不超预算。
4. 成本控制：缓存未变更样本的结果，评委调用并行化并设预算上限。
5. 报告包含总览、切片、回归样本列表与轨迹链接，便于快速定位。

**相关知识点：** CI/CD、评估流水线、冒烟集、质量门禁、结果缓存、评估报告。
<a id="gov-266"></a>
### 15. 什么是在线评估？它和离线评估有什么区别？

在线评估是**对生产环境真实流量的输出持续评估**；与离线评估相比，它使用真实分布、能反映用户感受，但不可控、无标准答案，且需要控制评估成本与延迟。

1. 数据来源不同：离线是固定集，在线是实时或近实时的流量抽样。
2. 评判方式不同：在线更多依赖用户反馈、业务结果与自动评委，缺少参考答案。
3. 目的不同：离线用于发布前决策，在线用于监控质量漂移、验证真实效果和发现新问题。
4. 风险不同：在线评估不能影响用户体验，评委通常异步执行。
5. 两者闭环：在线发现的失败回流到离线评估集，离线门禁防止再次出现。

**相关知识点：** 在线评估、真实流量、质量漂移、异步评估、用户反馈、闭环。
<a id="gov-267"></a>
### 16. 在线评估常用的信号有哪些？

在线信号分为**显式反馈、隐式行为、业务结果和自动评估**四类，需要组合使用，因为单一信号都有偏差。

1. 显式：点赞/点踩、评分、文字反馈、举报。
2. 隐式：重试或重新提问率、放弃率、复制/采用率、会话时长、追问次数。
3. 业务：任务完成状态、转人工率、工单解决率、转化率、退款或投诉。
4. 自动：LLM 评委抽样打分、规则校验失败率、幻觉检测、安全过滤命中率。
5. 系统：错误率、P95 延迟、Token 成本，作为质量变化的旁证。

**相关知识点：** 显式反馈、隐式反馈、转人工率、采用率、自动评委、信号组合。
<a id="gov-268"></a>
### 17. 什么是隐式反馈和显式反馈？各有什么优缺点？

显式反馈是**用户主动给出的评价**，准确但稀疏且有偏；隐式反馈是**从用户行为推断的信号**，量大但含噪声，需要谨慎解释。

1. 显式反馈率通常只有百分之几，且极端体验的用户更愿意反馈，分布偏向两端。
2. 隐式信号覆盖全部会话，但"重新提问"可能是追问而不是不满，需结合上下文判断。
3. 显式反馈适合校准评委与构建评估集，隐式信号适合监控趋势与做 A/B 实验指标。
4. 两者都可能被误导：点赞可能奖励讨好式回答，采用率可能受界面影响。
5. 实践中用隐式信号看大盘，用显式反馈做定性分析，再用人工抽检验证。

**相关知识点：** 显式反馈、隐式反馈、反馈偏差、噪声信号、趋势监控、人工抽检。
<a id="gov-269"></a>
### 18. 什么是 A/B 测试？如何用它比较两个 Prompt 版本或模型版本？

A/B 测试是**把流量随机分配给不同版本，比较预定义指标的差异并做显著性检验**；用于比较两个 Prompt 或模型版本时，需固定其他变量并提前设定样本量与主指标。

1. 随机分流按用户或会话粒度，保证同一用户体验一致；检查分流是否均衡（SRM）。
2. 主指标选任务完成率或采用率等业务结果，辅以延迟、成本和安全指标做护栏。
3. 按最小可检测差异估算样本量与运行时长，避免提前看结果导致误判。
4. 差异用置信区间和 p 值表达，并按切片检查是否某类用户退化。
5. 上线前先做离线评估和影子测试，A/B 用于验证真实效果，通过后逐步放量。

**相关知识点：** A/B 测试、随机分流、SRM、主指标、护栏指标、显著性、样本量估算。
<a id="gov-270"></a>
### 19. 什么是影子模式（Shadow Mode）？它适合什么场景？

影子模式是**新版本并行接收生产请求但不向用户返回结果**，把其输出与线上版本对比评估；适合高风险变更在真实流量下的零影响验证。

1. 请求复制到影子版本，输出仅记录不展示，用户始终看到线上版本的结果。
2. 对比方式：代码判定差异、LLM 评委成对比较、人工抽查分歧样本。
3. 适用：模型替换、重大 Prompt 改动、新工具接入、成本优化方案。
4. 注意副作用：影子版本的写操作必须 Mock 或走沙箱，避免重复下单、重复发送。
5. 成本翻倍，通常只对抽样流量开启，并设定运行时长与评估指标。

**相关知识点：** Shadow Mode、流量复制、零影响验证、副作用隔离、成对比较、抽样流量。
<a id="gov-271"></a>
### 20. 在线评估中如何对生产流量做采样再打分？

在线打分要**按策略抽样、异步执行、控制成本**：全量记录轨迹，对错误、异常与代表性样本用评委打分，正常流量按比例抽样。

1. 分层抽样：按任务类型、租户、模型版本分层，保证每层有足够样本。
2. 优先级：失败、超时、高成本、用户点踩、新功能流量全量评估。
3. 异步管道：轨迹进入队列，评委在后台批量打分，不影响在线延迟。
4. 成本：限定每日评委调用预算，用小模型初筛、大模型复核。
5. 结果写回指标系统，按版本与切片展示质量趋势并配置告警。

**相关知识点：** 分层抽样、异步评估、优先级采样、评委预算、质量趋势、告警。
<a id="gov-272"></a>
### 21. 在线评估发现质量下降后，一般有哪些处置动作？

处置动作按严重程度分为**告警与确认、回滚或降级、限流或关闭功能、修复与回归验证**四级，并要求记录事件与根因。

1. 确认：排除评委抖动与数据异常，用人工抽查验证下降是真实的。
2. 回滚：Prompt、模型或工具版本回退到上一个稳定版本，需要版本化才能快速执行。
3. 降级：切换到保守策略，如更强模型、缩小工具权限、增加人工审批。
4. 限制：对受影响场景限流或暂停功能，减少爆炸半径。
5. 修复后用离线回归验证，并把该问题的样本加入评估集。

**相关知识点：** 质量告警、回滚、降级、Feature Flag、爆炸半径、事后复盘。
<a id="gov-273"></a>
### 22. 如何把在线评估的结果回流到离线评估集中？

回流是**把在线发现的失败、分歧和代表性样本经脱敏与标注后加入离线评估集**，让离线评估的分布逐渐逼近生产。

1. 采集：用户点踩、评委低分、规则失败、人工接管的会话自动进入候选池。
2. 处理：脱敏、去重、按场景归类，判断是否为新的失败模式。
3. 标注：人工给出正确答案或验收要点，确认后成为评估样本。
4. 版本：新增样本以增量版本发布，评估报告区分新旧样本的表现。
5. 度量指标：跟踪回流样本数量、离线与在线分数的差距，差距缩小说明评估集更有代表性。

**相关知识点：** 样本回流、候选池、脱敏、人工标注、失败模式、分布对齐。
<a id="gov-274"></a>
### 23. 什么是 LLM-as-a-Judge？它解决了什么问题？

LLM-as-a-Judge 是**用大模型按给定标准对输出进行打分或比较**的评估方法，解决了开放式任务无法用规则判定、人工评估又慢又贵的问题。

1. 输入：被评估的输出，可附参考答案、上下文和 Rubric；输出：分数、标签或偏好及理由。
2. 优势：可扩展、成本远低于人工、能理解语义与多维标准。
3. 局限：存在偏差、随机性和领域知识不足，分数需要与人工对齐验证。
4. 不能把评委分数当作业务正确性：可验证的部分仍用测试、规则和业务状态判定。
5. 典型用途：离线批量评估、在线抽样监控、成对比较选版本。

**相关知识点：** LLM-as-a-Judge、开放式评估、评委偏差、人工对齐、可验证优先。
<a id="gov-275"></a>
### 24. LLM-as-a-Judge 常见的打分方式有哪些？

常见方式有**单样本打分、成对比较、多候选排序和分类标签**四种，按需要的输出粒度和稳定性选择。

1. 打分易受评委尺度漂移影响，需要 Rubric 锚定。
2. 成对比较更稳定，但成本随候选数平方增长。
3. 二分类最简单可靠，适合硬性要求。
4. 验证时按方式选择一致性指标：打分看相关系数，成对看一致率，分类看准确率。

| 方式 | 输出 | 适用 |
|---|---|---|
| 单样本打分 | 1～5 分或 0～100 | 监控绝对质量、多维 Rubric |
| 成对比较 | A 优 / B 优 / 平局 | 版本对比、偏好数据 |
| 排序 | 多个候选的顺序 | 选最佳回复、Rerank |
| 分类 | 通过/失败、标签 | 安全审核、格式合规 |

**相关知识点：** Pointwise、Pairwise、Listwise、二分类判定、尺度漂移、偏好数据。
<a id="gov-276"></a>
### 25. 什么是 Pointwise 评估和 Pairwise 评估？各适合什么场景？

Pointwise 是**对单个输出独立打分**，Pairwise 是**对两个输出比较优劣**；前者适合绝对质量监控与多维诊断，后者适合版本选择与偏好收集。

1. Pointwise 可给出每个维度的分数，便于定位短板，但评委对绝对尺度的把握不稳定。
2. Pairwise 只需相对判断，人与模型都更一致，但无法回答"够不够好"。
3. Pairwise 存在位置偏差，需交换顺序评估两次；平局需单独处理。
4. 组合使用：先 Pairwise 选出更优版本，再 Pointwise 检查其是否达到上线标准。
5. 验证方式：与人工标注的一致率（Pointwise 看相关系数，Pairwise 看一致率）。

**相关知识点：** Pointwise、Pairwise、绝对尺度、位置偏差、一致率、相关系数。
<a id="gov-277"></a>
### 26. 用 LLM 做评委时，Prompt 一般需要包含哪些要素？

评委 Prompt 应包含**任务说明、评分标准、输入材料、输出格式与推理要求**，必要时加入示例与边界说明。

1. 任务说明：评委角色、评估对象是什么、目标用户是谁。
2. 评分标准：Rubric 或要点清单，明确各分数等级的含义与优先级。
3. 输入材料：用户问题、上下文/参考答案、被评估输出，用清晰的分隔符标记。
4. 输出格式：先给理由再给分，用 JSON 固定字段（score、reason、flags）便于解析。
5. 边界说明：不评估的内容、遇到不确定时如何处理、防止被输出中的指令劫持；用校准集测试 Prompt 版本。

**相关知识点：** 评委 Prompt、Rubric、输出格式、JSON 输出、理由先行、评委防注入。
<a id="gov-278"></a>
### 27. LLM 评委有哪些常见偏差？

常见偏差包括**位置偏差、长度偏差、自我偏好、风格偏好和参考答案锚定**，需要通过设计和校准减轻。

1. 位置偏差：成对比较中倾向第一个（或最后一个）候选。
2. 长度偏差：更长、更详细的输出得分更高，即使内容冗余。
3. 自我偏好：评委倾向偏爱同系列模型生成的文本。
4. 风格偏差：偏好自信、结构化、礼貌的表达，忽视事实错误。
5. 锚定：给了参考答案后，对合理但不同的答案打低分；缓解方法是交换顺序、Rubric 约束、多评委投票和人工校准，并用一致率验证效果。

**相关知识点：** 位置偏差、长度偏差、自我偏好、风格偏差、参考锚定、评委校准。
<a id="gov-279"></a>
### 28. 如何缓解 LLM 评委的位置偏差？

主要手段是**交换候选顺序重复评估、随机化位置、要求逐项比较后再给结论**，并把不一致的结果记为平局或送人工。

1. 双向评估：A-B 与 B-A 各评一次，两次一致才采纳，否则判平局。
2. 随机化：批量评估时随机分配位置，消除系统性偏向。
3. 匿名化：用中性标签（Response 1/2）替代模型名，避免品牌偏好。
4. 结构化比较：让评委先按维度逐项列出差异，再综合判断。
5. 度量指标：统计位置一致率，低于阈值时调整 Prompt 或更换评委模型。

**相关知识点：** 位置偏差、交换顺序、随机化、匿名化、结构化比较、位置一致率。
<a id="gov-280"></a>
### 29. 为什么建议让 LLM 评委先给出理由再给分？

先写理由再给分能**迫使评委基于具体证据判断**，减少随意打分，提高一致性，并让人工复核能看到评分依据。

1. 生成顺序影响结果：先给分再解释容易变成为分数辩护，先分析再结论更接近真实评估。
2. 理由让分数可审计，人工复核时可快速判断评委是否理解了标准。
3. 理由中暴露的评委错误可用于改进 Rubric 与 Prompt。
4. 输出结构化：reason 字段在前，score 在后，并限制理由长度以控制成本。
5. 验证：比较有无理由时与人工标注的一致率，通常前者更高。

**相关知识点：** 理由先行、Chain-of-Thought 评估、可审计、一致性提升、结构化输出。
<a id="gov-281"></a>
### 30. 如何验证 LLM 评委的可靠性？

用**人工标注的校准集**测量评委与人的一致性，并检查评委自身的稳定性；只有达标的评委才能用于门禁和监控。

1. 构建校准集：几百条带人工分数或偏好标签的样本，覆盖各场景与难度。
2. 一致性指标：分类用准确率与 Cohen's Kappa，打分用 Spearman/Pearson 相关，成对用一致率。
3. 稳定性：同一样本重复评估的方差、交换顺序后的一致率。
4. 分析分歧：评委的系统性偏差（偏长、偏保守）比随机噪声更需要修正。
5. 定期重校准：模型或 Rubric 更新后重新测量，一致性下降则暂停使用。

**相关知识点：** 校准集、Cohen's Kappa、Spearman 相关、一致率、评委稳定性、重校准。
<a id="gov-282"></a>
### 31. 用什么模型做评委比较合适？评委模型是否需要比被评估模型更强？

评委模型不必绝对更强，但**应在评估任务上足够可靠**：判别通常比生成容易，一般选用能力强、稳定且与被评模型不同系的模型，并用校准集验证。

1. 复杂开放任务（推理、代码审查）倾向用更强模型做评委，简单分类任务小模型也可胜任。
2. 使用不同系列的模型可减少自我偏好偏差；多评委投票可进一步降低单一模型的偏差。
3. 成本考虑：小模型初筛、大模型复核，或把大模型评委蒸馏成专用小评委。
4. 评委模型版本要固定并记录，否则分数不可比。
5. 最终依据是校准集上的一致率与稳定性，而不是模型排行榜名次。

**相关知识点：** 评委模型选择、判别难度、自我偏好、多评委投票、评委蒸馏、版本固定。
<a id="gov-283"></a>
### 32. LLM-as-a-Judge 的成本和延迟如何控制？

通过**抽样、分级评委、缓存、批处理和精简输入**控制评估开销，把评委用在最有价值的样本上。

1. 抽样：在线只评估失败、异常与按比例抽样的正常流量，离线对未变更样本复用历史结果。
2. 分级：规则与小模型先过滤明显通过/失败的样本，大模型只评灰区。
3. 缓存：相同输入输出与评委配置的结果直接复用。
4. 批处理与并发：离线评估用批量 API 与并行调用，在线评估异步执行不阻塞用户。
5. 精简：限制理由长度、只传必要上下文、用结构化输出；监控每千次评估的成本与评估滞后时间。

**相关知识点：** 评估抽样、分级评委、结果缓存、批量 API、异步评估、评估成本。
