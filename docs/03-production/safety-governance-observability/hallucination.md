# 幻觉与事实可靠性

> 所属章节：[安全、治理与可观测性](README.md)｜本文件共 **17** 题。

<a id="gov-002"></a>
### 大模型幻觉产生的底层原因，以及基础层面可行的优化手段（Agent初级）

大模型幻觉的根因是**模型按条件概率生成文本，而非查询保证真实的知识库**。训练目标奖励语言连贯性，不天然约束事实、来源与不确定性。

1. 训练数据可能过时、冲突、稀疏或含噪，参数只压缩统计关联，无法逐条保存事实与来源。长尾知识、精确数字和最新事件尤其易被错误补全。
2. 自回归解码逐Token生成，早期错误会累积；高温度增加多样性，也提高偏离可靠答案的概率。贪心解码也不能消除知识不确定性。
3. 指令含糊、前提错误、上下文冲突或要求模型必须作答时，模型倾向迎合用户而非承认未知。对齐训练还可能强化流畅、自信和帮助性，使错误更难被察觉。
4. 基础优化包括提升数据质量、去重去噪、加入拒答与不确定性样本、领域继续训练；推理时降低温度、约束输出、使用Schema并允许回答“证据不足”。
5. 工程上应用RAG或权威工具提供外部事实，要求引用并回查来源；对数字、代码和关键事实采用规则、计算器、单元测试或独立验证器。高风险场景还需人工复核，不能只靠模型自我反思。

| 原因层 | 典型问题 | 基础治理 |
|---|---|---|
| 数据 | 过时、冲突、长尾缺失 | 清洗、更新、领域训练 |
| 生成 | 概率采样、误差累积 | 降温、约束解码 |
| 系统 | 上下文或证据不足 | RAG、工具、验证器 |

**相关知识点：** 自回归生成、最大似然训练、参数知识、Exposure Bias、温度、RAG、校准、拒答、事实核验。
<a id="gov-003"></a>
### 模型产生幻觉的原因是什么？工程上有什么办法降低幻觉？（百度Agent）

幻觉来自**参数知识不完备、证据不足或冲突、概率生成误差和结果缺乏约束**。治理不能只靠“不要编造”，而应建立证据供给、受控生成和外部验收闭环。

1. 定义事实错误、错误归因、虚构实体、数值错误，以及Agent虚构工具、参数和执行结果等类型。不同类型需不同验证器，不能只看总体幻觉率。
2. 输入侧澄清歧义和错误前提，以RAG、数据库或API提供证据；检索结果经过权限、时效、去重和Rerank。证据缺失或冲突时明确未知并补检索。
3. 生成侧使用低温度、Schema、限定候选和引用格式，将答案、证据ID、置信度分开输出。置信度须通过数据校准，不能相信模型自报。
4. 输出侧以规则、计算器、测试、引用回查或第二模型验证；关键事实须映射到原始证据。失败时局部重生成、补检索或转人工。
5. 建立带标准证据的评测集，统计事实准确率、引用精确率/召回率、拒答正确率和严重错误率，并按领域及风险切片。线上记录各版本与验证结果。

| 治理层 | 主要手段 | 局限 |
|---|---|---|
| Prompt约束 | 明确边界与格式 | 不能保证事实 |
| RAG/工具 | 提供外部证据 | 可能漏召回 |
| 验证器 | 拦截可判定错误 | 覆盖有限 |

**相关知识点：** Hallucination Taxonomy、RAG、Grounding、引用回查、置信校准、拒答、事实验证器、严重错误率。

### 如何减少RAG幻觉问题？（千问一面）

减少RAG幻觉要治理**知识源、切分、召回排序、上下文、生成约束和答案核验**。RAG只提供证据，不保证召回正确、模型采纳或引用一致。

1. 数据侧管理来源、版本、时效、权限和删除，清理重复、矛盾及低质量文档。Chunk按语义结构切分，保留标题、时间、实体和父子关系。
2. 使用关键词与向量混合召回，结合元数据、查询改写、动态Top-K和Rerank；多证据任务执行多跳检索。置信低、冲突或覆盖不足时补检索或澄清。
3. 上下文去重并按权威性与时间排序，明确文档边界，隔离不可信指令。Token预算优先保留直接证据及反例，避免相似Chunk稀释信息。
4. Prompt要求只基于证据并返回证据ID，无依据时拒答。生成后拆分Claim，通过引用跨度、蕴含、规则或独立模型核验；数字再与原文比对。
5. 评测检索Recall@K、Rerank、Context Precision、忠实度、引用精确率、拒答正确率及端到端成功率。保存查询、候选、排序、上下文与知识版本。

| 故障层 | 典型幻觉来源 | 主要治理 |
|---|---|---|
| 知识库 | 过期、冲突 | 版本与来源管理 |
| 检索 | 漏召回、错排序 | 混合检索、Rerank |
| 生成 | 忽略证据、错误引用 | Grounding与Claim核验 |

**相关知识点：** Hybrid Retrieval、Chunking、Rerank、Context Precision、Faithfulness、Claim Verification、引用精确率、拒答。

### 大模型幻觉系统性治理：检索校验、结果事实核验、反思校验、多轮自我修正、规则拦截多层防护（Agent高级）

系统性治理应构建**证据供给—受控生成—事实核验—有界修复—风险拦截**的防线。多轮反思只能修复，不能替代外部事实源或确定性验证。

1. 检索层记录查询改写、权限、混合召回、Rerank和知识版本；以Recall@K、Context Precision及冲突率判断质量。证据不足、过期或矛盾时补检索或拒答。
2. 生成层按Claim组织答案，附证据ID、引用跨度和置信状态；事实与推测分栏。数值、日期、实体及工具状态使用Schema。
3. 核验层以规则、数据库、计算器、NLI或独立Judge逐Claim验证。高风险事实要求双来源或权威来源；Judge必须引用证据。
4. 修复层把失败Claim、原因和最小证据包交给模型，仅重写问题片段；限制轮数、Token与Deadline。相同错误、无新证据或置信不升即转人工。
5. 拦截层对禁答、严重事实错误、越权工具和缺失引用实施硬门禁。记录模型、Prompt、知识和策略版本，评估严重幻觉率、引用精确率与修复成功率。

| 防线 | 作用 | 不能替代 |
|---|---|---|
| 检索校验 | 保证证据可用 | 生成核验 |
| 事实核验 | 判断Claim真伪 | 权限策略 |
| 反思修复 | 局部纠错 | 外部证据 |
| 规则拦截 | 守住硬底线 | 语义判断 |

**相关知识点：** Claim-level Verification、NLI、Grounding、Rerank、Reflection、修复预算、Guardrail、严重幻觉率、版本追踪。
<a id="gov-006"></a>
### 在Agent工具调用场景下，大模型幻觉有哪些典型表现，对应的落地优化手段（Agent高级）

工具幻觉会升级为真实副作用，表现为**虚构工具、错误选型、参数臆造、误读结果、伪造成功和重复调用**。模型只提出意图，权限、执行与验收由系统控制。

1. 发现阶段可能调用不存在或无权限的Tool。Registry按租户、任务和权限注入白名单Schema；服务端再校验ToolID与版本，禁止拼接端点。
2. 参数可能缺失、类型错误、实体混淆或臆造。使用严格Schema、枚举、范围和跨字段约束；关键值须来自用户或证据并保存来源，缺失时澄清。
3. 执行可能误写、重复提交或越权。Policy按身份、资源、动作和风险做ABAC；写操作使用幂等键、Dry Run、事务和审批，高风险参数需确认。
4. 模型可能忽略错误码、把空结果当成功或虚构返回。响应应含结构化状态、证据和错误；原始回执不可修改，最终结果须通过后置条件验收。
5. 超时和未知状态先查询再重试。记录计划、Schema、参数来源、Policy决策、请求响应、幂等键及副作用，评估选择准确率、参数通过率和重复副作用率。

| 幻觉类型 | 主要控制 |
|---|---|
| 虚构工具 | Registry白名单与能力协商 |
| 参数臆造 | Schema、来源追踪、澄清 |
| 伪造成功 | 原始回执与后置验收 |
| 重复/越权 | 幂等、Policy与审批 |

**相关知识点：** Tool Registry、JSON Schema、参数来源、ABAC、Dry Run、幂等键、后置条件、未知状态、工具幻觉。

### 幻觉率如何量化评估？

幻觉率应在**可验证Claim级别**定义，而非整段评分。先规定Taxonomy、证据范围、分母和严重度，再结合自动校验、人工与Judge测量。

1. 将输出拆为Claim，标注`supported、contradicted、not_verifiable`。证据限定任务中，未支持Claim属于Grounding幻觉；开放事实需权威来源验证。
2. Claim幻觉率=`错误或计入的无支持Claim/可评估Claim`；答案级幻觉率是含幻觉的答案占比。另报严重幻觉率，防轻微错误稀释关键问题。
3. RAG统计Faithfulness、引用精确率/召回率和拒答正确率；工具任务统计虚构Tool、参数臆造与伪造成功。不同类型分别报告。
4. 评测集覆盖常见、长尾、时效、冲突和无答案样本，并冻结知识快照。规则、数据库和NLI自动评估；开放Claim由人工或校准Judge复核。
5. 报告样本量、置信区间和各版本切片。线上抽样复核高风险Trace，并监控拒答率，防过度拒答美化指标。

| 指标 | 含义 |
|---|---|
| Claim幻觉率 | 错误Claim占可评估Claim比例 |
| 答案级幻觉率 | 含任一幻觉的答案比例 |
| 严重幻觉率 | 高影响错误答案比例 |
| 拒答正确率 | 无证据场景正确拒答比例 |

**历史别名：** `ENG-190`。

**相关知识点：** Atomic Claim、Grounding、Faithfulness、Citation Precision/Recall、严重度加权、Judge校准、Bootstrap、拒答率。
<a id="gov-024"></a>
### 如何降低Agent幻觉和错误调用工具的问题？

应把问题拆为**答案Grounding与工具执行安全**两条链：模型可提出事实和调用意图，但证据、工具、权限、参数、回执和后置条件须由外部系统验证。

1. 输入侧澄清目标、实体、资源和验收；以RAG、数据库或API提供版本化证据。证据缺失、冲突或召回置信低时补检索或询问用户，允许拒答。
2. 生成侧使用低温度、Schema和Claim引用，分开事实、推测和待确认项。输出经引用、规则、计算器、测试或Judge核验；失败只重写问题片段。
3. Tool Registry按任务和权限只注入必要工具，执行器再校验ToolID、版本和能力。参数使用类型、枚举、范围、跨字段约束及来源；关键值缺失时澄清。
4. Policy以RBAC/ABAC检查主体、资源、Action和风险；写入、删除、资金和生产操作要求Dry Run、HITL、幂等及回滚。未知状态先查询。
5. 工具响应使用结构化Envelope，模型不得把错误或空结果写成成功；Validator核验后置条件。记录各版本、参数来源、Policy和回执，评估幻觉率、选Tool准确率、参数通过率及重复调用率。

**历史别名：** `ARC-041`。

**相关知识点：** Grounding、Claim Verification、Tool Registry、参数来源、Policy Engine、ABAC、HITL、幂等、Postcondition、Tool Hallucination。

### 如何追踪上下文构建过程？

上下文追踪应建立**从来源到最终Prompt的逐项血缘**，解释每个片段为何被召回、过滤、排序、截断和引用。

1. 为构建分配ContextBuildID，关联TraceID、StepID、PromptVersion和TokenBudget；用户输入、系统指令、历史、Memory、RAG及Tool结果分别建为Item。
2. Item记录SourceType、SourceID、版本、权限标签、ContentHash、Token数和加密引用。RAG项补充Query、索引版本、召回通道、原始与Rerank分数及Chunk位置。
3. 候选、权限过滤、去重、排序、时效过滤、压缩、截断和选入阶段均生成Event，记录算法版本、阈值、前后排名、Token变化及淘汰原因。
4. 保存Item在最终Prompt中的顺序、Token区间与引用映射。事实错误可据此区分未召回、被过滤、排序过低、被截断或模型未采用。
5. 敏感内容只存Hash、脱敏摘要和受控引用，调试访问须审计。监控Token占比、截断率、无引用率、过期率、权限拒绝率及来源贡献。

回放须固定索引快照、Memory、构建器、权限策略和Token预算；动态数据无法冻结时标注不可复现字段。

**相关知识点：** Context Lineage、ContextBuildID、RAG Trace、Content Hash、Token Budget、索引快照、引用映射、数据脱敏。
<a id="gov-038"></a>
### 如何定位模型幻觉问题？

定位幻觉应以**原子事实和证据链**为单位，先确认与事实冲突，再判断问题在知识供给、上下文、模型还是后处理。

1. 固化输入、Prompt版本、模型参数、上下文快照、RAG候选、Tool回执和输出；将答案拆为Claim，标注Supported、Contradicted、Unverifiable及应拒答。
2. 检查语料是否含正确事实、检索是否召回、Rerank是否排入预算，以及权限、去重或截断是否误删。证据未进入Prompt，属于RAG或Context问题。
3. 若证据已提供，检查模型是否误读、混淆实体、虚构引用或忽视时效；再核查解析、摘要合并、工具映射和缓存是否改变原输出。
4. 固定其余条件，分别替换检索结果、Prompt、模型或参数，比较事实准确率和引用一致性；随机模型应重复采样，以统计差异判断。
5. 分类统计无依据生成、证据冲突、过期事实、引用错配和工具结果臆造，并关联模型、领域、Prompt版本及阶段。

修复后进入回归集，同时验证事实性、拒答率和完成率，避免以过度拒答降低幻觉率；高风险事实需独立核验。

**相关知识点：** Claim-level Evaluation、Groundedness、Faithfulness、RAG归因、Context Snapshot、单变量实验、Failure Taxonomy、回归评测。
<a id="gov-039"></a>
### 如何评估模型输出质量？

模型输出质量应按**任务正确性、事实性、完整性、安全性、格式与成本**评估，以业务验收为主；单一相似度或LLM评分不足以证明可用。

1. 按任务定义Rubric和硬门槛。问答关注事实、引用、覆盖与拒答；结构化输出关注Schema；代码关注测试、静态分析、安全及变更范围；决策关注合规。
2. 金标集覆盖正常、长尾、对抗、时效、缺失信息和高风险样本，划分开发与盲测集，并按领域、难度分层；版本评测使用同一快照，报告总体及切片。
3. 确定性项采用规则、Schema、单元测试和事实库；开放式项采用人工双评与LLM-as-Judge。固定Judge、Prompt和Rubric，随机交换答案顺序，并校准人工一致率。
4. 指标包括Task Success、Claim Precision、Groundedness、Completeness、指令遵循、安全违规率、P95延迟及单成功任务成本。严重安全或事实错误设置门禁，不能由其他高分抵消。
5. 线上结合用户修正、重试、人工接管和真实验收，以A/B Test验证离线提升；监控数据与评分漂移，将失败样本回流。

版本比较应报告置信区间并审查副作用，例如更高拒答虽降低幻觉，却可能损害完成率。

**相关知识点：** Evaluation Rubric、Golden Set、Task Success、Groundedness、LLM-as-Judge、人工一致性、A/B Test、置信区间。
<a id="gov-062"></a>
### 如何自动进行根因分析？

自动根因分析应输出**带证据和置信度的候选**，不能让LLM自由猜测；依据是依赖拓扑、时间顺序、首个异常、版本变更和历史模式。

1. 将Metrics、Logs、Traces、Events、Deployment和Configuration按TaskID、TraceID及时间对齐，构建依赖图与DAG；缺失和断链显式标记。
2. 从用户影响反向遍历关键路径，寻找最早且能解释最多下游症状的节点；比较错误、延迟、饱和、状态停留、重试和质量与历史基线。
3. 关联模型、Prompt、索引、工具、Policy、代码及基础设施变更；利用变点检测、拓扑传播和相似Incident生成候选，排除无依赖的巧合事件。
4. 按时间先行、拓扑覆盖、异常强度、变更相关性和历史准确率评分，输出证据Span、影响及反证。LLM仅汇总证据，不得虚构事实。
5. 对低风险假设执行探针、影子流量或回滚验证；高风险场景人工确认。最终根因进入Failure Taxonomy和案例库。

评估Top-1/Top-3命中率、定位耗时、误归因率和证据完整度；低于置信阈值时返回未知并保留多候选。

**相关知识点：** Dependency Graph、Change Point Detection、Causal Ranking、Failure Taxonomy、Incident Similarity、证据链、LLM摘要、置信度校准。
<a id="gov-093"></a>
### 如何设计企业级Agent评估指标体系？

企业级指标应以**业务价值为北极星，质量、安全、效率和成本为护栏**，并为每项指标定义口径、Owner与用途。

1. 业务层衡量有效完成率、自动化覆盖、满意度、节省时长、收入或风险降低和ROI；高风险任务以业务状态或人工验收确认，不能只用模型自评。
2. 质量层包括目标完成、事实性、Groundedness、完整性、指令遵循、结构、工具选择及结果利用；长任务还评估规划、节点通过和最终验收。
3. 安全层统计越权、Prompt Injection、数据泄露、危险工具误调、审批绕过、重复副作用和审计覆盖；严重事件设置零容忍门禁。
4. 效率与成本层报告P50/P95、Token、Tool费用、重试、缓存、Cost/Success、可用性和Error Budget，避免以低成本掩盖完成率下降。
5. 指标按Tenant、TaskType、风险、难度、模型、Prompt和版本切片，离线金标、红队与线上A/B Test相互校验，并报告置信区间。

平台维护Metric Catalog、Failure Taxonomy和评测集版本；发布门禁预定义主指标、护栏与回滚阈值，盲测集隔离以防过拟合。

**相关知识点：** North Star Metric、Guardrail Metric、Metric Catalog、Task Success、Groundedness、Cost/Success、红队评测、置信区间。

### 如何自动识别任务失败根因？

自动根因识别应采用**确定性信号优先、因果链分析其次、模型辅助归纳最后**的分层方案，输出证据、置信度和可执行建议，而非让LLM凭日志猜测。

1. 先统一Failure Taxonomy与成功终态，将失败划分为输入不清、规划、模型、检索、Tool、权限、状态、验证、资源和外部依赖，并定义互斥的主因、可并列的诱因及判定规则。
2. 通过TaskID和TraceID还原DAG，定位首个异常Span；结合状态机、错误码、超时、重试、策略拒绝、检索分数、Tool返回及Verifier结果，按因果方向排除后续连锁错误。
3. 建立规则与知识库：例如召回为空且索引正常判为知识覆盖，召回相关但答案无引用判为生成忠实度，Tool参数校验失败判为Schema或规划。规则需版本化并保存证据。
4. 对规则无法覆盖的样本，抽取脱敏Trace特征，使用聚类发现新失败簇，再由LLM按Rubric生成候选标签和解释；高风险、低置信度或新类别进入人工复核。
5. 将预测与人工终审对比，监控准确率、召回率、混淆矩阵和拒判率；新确认根因回流规则、分类器和回归集，防止标签漂移。

系统应区分**故障发生点与根因所在点**，并关联部署、Prompt、模型、索引及工具变更。告警按影响任务数和业务风险聚合，避免同一根因产生大量重复事件。

**相关知识点：** Failure Taxonomy、首错定位、因果图、状态机、错误聚类、变更关联、置信度、人工复核、标签漂移、根因分析。
<a id="gov-139"></a>
### Agent失败样本自动分类如何实现？

失败样本分类宜采用**规则、Embedding、LLM与人工复核**的级联架构，优先使用可验证证据，输出标签、置信度和依据。

1. 建立版本化Failure Taxonomy，定义正反例、必需证据、排除条件和责任域；主根因单选，诱因可多选，保留未知类别。
2. 从Trace抽取首个异常Span、状态、错误码、停止原因、检索分数、Tool返回、权限、重试、版本和业务终态；Prompt与日志先脱敏。
3. 高确定性事件由规则判定，例如Schema校验失败、权限拒绝和依赖超时；已知模式可用监督分类器，未知样本通过Embedding聚类发现新失败簇；复杂语义再交给LLM按固定Rubric分类。
4. 高置信结果自动入库，中置信由第二模型或规则验证，低置信、新类别和高风险失败交人工；LLM必须引用Trace证据。
5. 用独立标注集评估Precision、Recall、F1、混淆矩阵、覆盖率与拒判率，并按版本和任务分层。将人工终审回流训练，但保留时间切分，防止训练测试泄漏。

上线后监控标签漂移、Other比例和规则冲突；结果关联工单和回归集。**人工应集中处理高价值的不确定样本**。

**相关知识点：** Failure Taxonomy、规则引擎、级联分类、Embedding聚类、置信度、拒判、混淆矩阵、标签漂移、主动学习。
<a id="gov-147"></a>
### 如何判断问题出在检索还是生成？

判断以**黄金证据替换与上下文消融**为核心：先确认检索是否提供足够证据，再验证模型能否正确使用。

| 观测 | 主要问题 | 证据 |
|---|---|---|
| TopK缺关键文档 | 检索 | Recall低 |
| 有证据但被截断 | 组装 | Prompt无证据 |
| 正确证据输入仍答错 | 生成 | 曲解或幻觉 |

1. 标注相关文档、关键Chunk和可接受答案，记录召回、Rerank、最终上下文、Prompt与输出，避免只看最终答案。
2. 计算Recall@K、MRR或NDCG，检查知识覆盖、Chunk、查询改写、过滤和排序；黄金证据未进入最终上下文，属于检索或拼装问题。
3. Oracle Context将黄金证据直接提供给原模型。若答案恢复，根因在检索；若仍错误，则检查推理、引用、拒答和格式。
4. 保留检索结果并替换更强模型；若恢复，支持生成瓶颈。测试证据顺序、长度和冲突，识别Lost-in-the-Middle。
5. 端到端检查答案正确性、引用忠实度和文档利用率；答案依赖外部知识时，不能误判为检索成功。

归因应区分**知识缺失、召回、重排、上下文组装和生成**，修复样本分别进入组件回归集。

**相关知识点：** Oracle Context、Recall@K、NDCG、上下文消融、Lost-in-the-Middle、引用忠实度、文档利用率、组件归因。
<a id="gov-148"></a>
### RAG链路如何做可观测？

RAG可观测应贯穿**摄取、索引、召回、重排、上下文和引用**，既定位质量问题，也解释答案使用的证据。

1. 摄取侧记录SourceID、文档版本、解析器、Chunk策略、权限、Embedding及索引版本；监控解析失败、空Chunk、重复和索引延迟。
2. 为改写、过滤、混合检索、Rerank和上下文建立Span，记录Query摘要、文档与ChunkID、分数、排名、过滤原因、K值、耗时和Token。
3. 指标包括Recall@K、Precision@K、MRR、NDCG、零结果率、Context Recall、引用忠实度、文档利用率和越权召回率，并按场景分层。
4. 保存最终Chunk顺序、截断和去重，建立答案到Citation再到Source的数据血缘；原文只存受控Artifact引用。
5. 以TaskID、TraceID贯穿RAG与生成，从低质答案下钻候选集，并关联文档、Embedding、索引和Reranker变更。

告警覆盖延迟、零召回突增、分数漂移、过期索引、权限异常及引用缺失；通过黄金Query、回放和Canary持续校验。

**相关知识点：** 数据血缘、索引新鲜度、Recall@K、NDCG、Context Precision、引用忠实度、分数漂移、黄金Query、Trace。
<a id="gov-150"></a>
### 如何评估知识库命中率？

知识库命中率应衡量**可回答查询是否在限定TopK内命中足够的权威证据**，不能把“返回任意文档”视为命中，也不能与答案正确率混为一谈。

1. 构建Query—相关文档或Chunk黄金集，覆盖事实、多跳、时效、权限、歧义和无答案场景；相关性分为关键、辅助与无关，由双人标注并保留多个可接受证据。
2. 基础Hit Rate@K等于至少命中一个相关项的查询数除以可回答查询总数；多证据任务还应计算All-Hit Rate或Recall@K，要求所有关键证据达到阈值。
3. 在线可定义有效命中：召回文档被最终上下文保留，答案实际引用且引用经忠实度验证。分别报告检索命中、上下文命中和答案利用命中，定位重排、截断或生成未使用问题。
4. 对无答案查询计算正确零命中或拒答率，对权限场景计算越权命中率；任何无权文档进入候选集都属于安全缺陷，不应被高总体命中率掩盖。
5. 按领域、任务、语言、文档版本、新鲜度和K值分层，报告样本量、置信区间及趋势；生产日志只能作为弱标签，应通过人工抽检纠正用户点击和模型引用偏差。

评测时固定Chunk、Embedding、索引、过滤和Reranker版本，并保存候选与分数。命中率下降需进一步区分知识缺失、索引未更新、查询改写、过滤、召回和排序问题。

**相关知识点：** Hit Rate@K、Recall@K、All-Hit Rate、有效命中、引用忠实度、无答案评测、越权命中、黄金标注。
