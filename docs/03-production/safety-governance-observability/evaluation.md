### 任务完成率如何评估？（豆包二面）

任务完成率是**在范围、期限和验收标准内达到业务目标的任务占比**，不能用流程结束或模型自报代替。分母、部分完成与取消口径须预先定义。

1. 分母是进入可执行状态的有效任务，排除测试、重复、执行前取消及不可支持输入；执行中取消、超时或资源不足按产品承诺固定口径，不能临时剔除。
2. 各类任务建立验收：问答看事实与引用，工具看后置条件，代码看测试与门禁，工作流看必选节点。优先用规则、数据库和业务回执，开放结果再用Judge。
3. 区分完全成功、部分成功、失败和未知。完成率为`完全成功数/有效任务数`；部分完成另报加权分，不得掩盖关键节点失败。严重错误独立统计。
4. 按任务、复杂度、模型、Prompt、知识、工具和时间切片并报告置信区间，同时关联一次解决率、重试率、人工接管、P95和单位成功成本。
5. 结果通过Trace与TaskID汇聚，迟到回执更新状态并保留历史。抽样审计验收器，以失败Taxonomy区分模型、检索、工具和编排问题。

| 结果状态 | 是否计成功 |
|---|---|
| 全部验收条件满足 | 是 |
| 非关键步骤缺失 | 部分完成，单独报告 |
| 关键条件失败/超时 | 否 |
| 外部状态未知 | 未知，待核验 |

**相关知识点：** Task Success Rate、验收标准、分母治理、部分完成、一次解决率、置信区间、Failure Taxonomy、Baseline。

### 当Agent任务完成率只有70%时，如何判断问题出在模型、Prompt、RAG、工具调用还是流程编排？（腾讯二面）

应基于**统一Trace、分层验收、失败Taxonomy和受控消融**归因，不能凭直觉判断。先定位首个决定性失败节点，再验证是否引发连锁失败。

1. 建立黄金样本和节点验收：计划、Prompt、检索、模型、工具、状态及最终结果均有指标。Trace记录组件版本、输入摘要、候选、回执和错误。
2. RAG问题表现为Gold证据未召回、Rerank淘汰关键Chunk或Context噪声高；测Recall@K、Context Precision和引用覆盖。证据完整但回答错误则偏生成。
3. 固定检索和工具，比较不同模型×Prompt。多模型在同一约束失败说明Prompt或任务定义有误；同Prompt仅弱模型失败说明能力不足，并控制采样随机性。
4. 工具问题分为选错Tool、参数、权限、超时和后置条件失败；编排问题表现为节点遗漏、顺序错误、状态丢失、循环或补偿缺失。确定性错误由规则标注。
5. 对失败样本人工复核，再做回放、Shadow和单变量消融，计算根因占比及修复增量。允许主因、次因和`unknown`，优先修复高占比瓶颈。

| 组件 | 关键证据 |
|---|---|
| RAG | Recall、排序、证据覆盖 |
| 模型/Prompt | 配对替换与格式/事实失败 |
| 工具 | 参数、权限、回执、后置条件 |
| 编排 | DAG顺序、状态、循环与补偿 |

**相关知识点：** Failure Taxonomy、首个失败节点、配对实验、消融、Recall@K、Context Precision、Tool验收、根因占比。

### 如何统计工具成功率和耗时？

工具指标应以**逻辑调用Operation**为主键，同时保留Attempt；否则重试会放大样本，造成成功率和耗时失真。

1. 成功需满足协议、响应Schema、业务状态及下游验收。分别计算传输、业务、解析和端到端有效成功率，不能只以HTTP 200为准。
2. 逻辑成功率为成功Operation除以已完成Operation；首试成功率衡量稳定性，重试后成功率衡量恢复力。Cancelled和超时Unknown单列，并明确是否进入SLO分母。
3. 耗时拆分排队、连接、网络、工具、下游、解析和重试退避；报告P50、P95、P99及直方图，不以平均值掩盖长尾。端到端耗时按Operation计算。
4. 按ToolName、Version、Tenant、Region、Endpoint、任务类型、错误类型和是否重试切片，但Prometheus Label只放低基数字段；TraceID用于下钻高基数明细。
5. 监控调用量、Attempt/Operation、超时、限流、熔断、Unknown积压、重复副作用和单位成功成本。低流量工具设置最小样本与置信区间。

仪表盘呈现SLO、时间窗口和发布标记；告警采用错误预算与多窗口Burn Rate，识别持续退化并抑制噪声。

**相关知识点：** Operation、Attempt、SLO、业务成功率、Latency Histogram、分位数、Error Budget、Burn Rate、指标基数。

### Prometheus需要监控哪些指标？

Prometheus应监控**业务、模型、RAG、Tool、编排、基础设施和观测管道**，遵循低基数；TaskID、UserID等只放Trace或Log。

1. 业务：任务量、成功/失败、端到端延迟、人工接管、重试、验收失败和安全违规；按Agent、TaskType、Version切片。
2. 模型：请求、错误、首Token与总延迟、输入/输出Token、限流、截断、缓存命中和成本；Provider、Model可作受控Label。
3. RAG：QPS、P95、零召回、Rerank耗时、Chunk数、引用率、索引新鲜度和权限过滤；DocumentID不可作Label。
4. Tool与Workflow：Operation成功、Attempt/Operation、超时、熔断、Unknown、队列深度、状态停留、死信和Checkpoint失败。
5. 系统与Telemetry：CPU、内存、GC、连接池、Pod重启，以及Collector队列、丢弃、导出失败和断链率。

计数用Counter，当前量用Gauge，延迟与Token用Histogram；核心SLO基于完成率和延迟，告警采用多窗口Burn Rate，并以Exemplar关联Trace。

**相关知识点：** Prometheus、Counter、Gauge、Histogram、Label Cardinality、RED/USE、SLO、Burn Rate、Exemplar。
<a id="gov-059"></a>
### 如何利用追踪数据持续优化Agent性能与成本？

追踪优化应形成**测量—归因—实验—门禁—回归**闭环，以成功任务为单位约束质量、延迟和成本，不能只压缩Token。

1. 建立Task Success、P50/P95、Token、Tool费用、重试和单成功任务成本基线；按Agent、任务类型、模型、Prompt及版本切片，并标记发布。
2. 用Critical Path分解排队、规划、模型、RAG、Tool、人工等待和重试；通过Span归因Token、缓存、模型价格和外部费用，识别热点。
3. 查找重复规划、无效上下文、低价值Chunk、串行分支、慢Tool、重试风暴和大模型滥用；采用压缩、缓存、Batch、并行、模型路由和Deadline优化。
4. 每项优化只改变一个主要变量，在固定评测集和A/B Test中比较完成率、质量、P95、成本及安全违规；质量门禁未通过不得上线。
5. 发布后按版本监控Burn Rate与漂移，异常自动回滚；失败Trace回流评测集。高价值链路用Tail Sampling，正常链路代表性采样。

优化优先级按节省×流量×成功概率÷风险排序，同时审查长尾和高风险任务，避免平均值掩盖退化。

**相关知识点：** Critical Path、Cost Attribution、Unit Economics、A/B Test、Tail Sampling、模型路由、缓存、回归评测、置信区间。
<a id="gov-063"></a>
### 如何建设Agent运营分析平台？

Agent运营平台应把**使用、质量、效率、成本、风险和用户价值**统一到任务事实模型，以成功任务为核心单位，并可下钻Trace。

1. 建立Task、Step、Model、Tool、Evaluation、Feedback和Cost事实表，维表包含Tenant、Agent、TaskType、Model、Prompt、KnowledgeBase、Tool及Version；统一口径与事件时间。
2. 北极星指标采用有效任务完成率或用户价值，配套活跃、留存、满意度、接管率、完成时间、单成功任务成本和安全事件；明确分母、排除项与Owner。
3. 实时层提供健康、告警与漏斗，离线层提供留存、分群、版本对比、失败归因和成本；TaskID、TraceID支持证据下钻。
4. 仪表盘按管理、产品、运营、算法和工程分层，支持Tenant、渠道、领域、难度及版本切片；禁止只看总体平均值而掩盖长尾。
5. A/B Test预注册主指标、护栏和样本量；上线后监控数据质量、埋点覆盖、迟到事件与指标漂移，防止重复任务或过度拒答刷高指标。

治理上实施数据目录、血缘、口径评审、RBAC、租户隔离、脱敏与留存；优化项关联负责人、预期收益、实验结果和复盘。

**相关知识点：** Metrics Layer、Fact Table、North Star Metric、Funnel、Cohort、A/B Test、数据血缘、指标治理、单位经济性。

### Agent任务成功率和用户满意度有什么区别？

两者分别衡量**客观完成**与**主观体验**，相关但不可替代。任务可能按验收标准成功却因慢、贵或表达不佳而低满意；用户也可能满意于错误但流畅的答案。

| 指标 | 任务成功率 | 用户满意度 |
|---|---|---|
| 依据 | 规则、测试、业务状态 | 评分、反馈、行为 |
| 粒度 | Task/Step验收 | 用户与会话体验 |
| 主要偏差 | 验收覆盖不足 | 选择偏差、情绪和延迟反馈 |

1. 任务成功率＝通过全部必需验收的Task÷可评估Task，验收包括目标、事实、工具副作用、格式和安全门禁；Cancelled、不可评估和部分完成需单列，不能随意排除失败。
2. 满意度可结合CSAT、点赞/点踩、投诉、重复提问、用户改写、留存和人工接管，但应区分显式评分与行为代理，并按用户、场景和任务难度校准。
3. 两者应组成二维矩阵：成功且满意为理想；成功但不满意多为体验问题；失败但满意可能是验收过严或用户未发现错误；失败且不满意优先修复能力。
4. 指标按TaskType、风险、版本和用户分群报告置信区间，并关联Trace抽样复核。高风险任务以成功与安全为硬门禁，不能用满意度抵消事实错误。
5. 优化版本需同时观察成功率、满意度、P95、成本和拒答率，使用A/B Test验证；防止通过降低任务难度、过度拒答或诱导评分刷高指标。

**相关知识点：** Task Success Rate、CSAT、Behavioral Proxy、验收标准、选择偏差、二维分析、A/B Test、护栏指标。
<a id="gov-094"></a>
### Agent评估为什么不能只看任务完成率？

任务完成率只回答**是否到达终点**，无法说明过程是否真实、安全、稳定且经济。单指标优化还会诱导过度拒答或绕过验收，形成Goodhart效应。

1. 流程结束、模型声称完成、工具返回200与业务目标达成并不等价。必须由规则、测试、事实证据、外部状态或人工验收。
2. 相同完成率可能质量不同：答案会遗漏或引用错误，代码可能测试通过却引入漏洞，多步骤任务可能最终正确但产生错误副作用。
3. 安全与治理不能被平均值抵消。越权、敏感数据泄露、Prompt Injection、审批绕过、误删和重复支付即使低频，也应作为硬门禁单独统计。
4. 效率需看P95、Token、Tool费用、重试、人工接管和Cost/Success；依赖无限重试或人工补救的完成不等于高质量自动化。
5. 稳定性与分布同样重要，应按领域、难度、风险、用户群和版本切片，报告置信区间、长尾退化和数据漂移；总体完成率会掩盖关键场景失败。

体系以Task Success为主指标，以事实性、安全、满意度、延迟、成本和接管率为护栏，结合离线金标、红队与A/B Test复核。

**相关知识点：** Goodhart’s Law、Task Success、Guardrail Metric、Side-effect Safety、Cost/Success、切片评估、置信区间、A/B Test。

### LLM-as-Judge有哪些优缺点？

LLM-as-Judge适合**规模化评估开放式输出**，但存在偏差、随机性和攻击面，不能替代确定性测试与业务验收。

| 方面 | 优点 | 局限 |
|---|---|---|
| 覆盖 | 理解语义和风格 | 专业事实可能误判 |
| 效率 | 批量评分 | 有成本和延迟 |
| 一致性 | 固定Rubric较稳定 | 顺序、长度、自偏好 |
| 扩展 | 可输出理由 | 可能事后合理化 |

1. 适合完整性、相关性、指令遵循、文风、成对比较和失败分类；Schema、单元测试、SQL与外部事实优先用确定性Oracle。
2. 偏差包括Position、Verbosity、Self-preference和数据污染；答案还可能通过Prompt Injection操纵Judge，故须作为不可信数据隔离。
3. 固定Judge、版本、温度、Rubric和Schema，随机交换答案顺序，隐藏模型身份，设置校准题与人工金标；高风险样本专家复核。
4. 报告人工一致率、相关系数、分类误差、采样方差及置信区间。Judge升级时在锚点集重新校准。
5. Judge分数仅是证据之一，应与规则、任务成功、反馈、安全门禁和A/B Test组合，不能成为唯一裁决。

**相关知识点：** LLM-as-Judge、Position Bias、Verbosity Bias、Self-preference、Pairwise Evaluation、Rubric、Calibration、Inter-rater Agreement。

### 如何降低大模型评测结果的主观性？

降低主观性依赖**可操作Rubric、确定性证据、盲评校准和统计报告**，使不同评审者获得可重复、可解释的结果。

1. 将质量拆为正确性、Groundedness、完整性、指令遵循、安全和格式；各档给出可观察锚点、正反例及严重错误，禁用模糊描述。
2. 优先采用Schema、单元测试、事实库、Tool回执和业务状态；开放式部分再由人工或Judge评价，严重安全与事实错误设硬门禁。
3. 人工评审采用双盲、随机顺序、统一培训和重叠样本，计算Cohen’s Kappa或Krippendorff’s Alpha；分歧由第三方裁决并更新Rubric。
4. Judge固定模型、版本、Prompt、温度和Schema，隐藏候选来源，随机交换Pairwise顺序，设置锚点题；答案作为不可信数据隔离。
5. 对任务和Judge重复采样，报告样本量、方差、置信区间及分层结果；版本对比使用相同快照与配对检验，不能凭少量样本宣布提升。

以专家金标校准Judge，分析Position、Verbosity和Self-preference偏差；高风险领域保留专家复核，并用线上A/B Test验证。

**相关知识点：** Rubric、Anchor Example、Blind Review、Cohen’s Kappa、Krippendorff’s Alpha、Judge Calibration、配对检验、置信区间。
<a id="gov-098"></a>
### 多模型交叉评测是怎么实现的？

多模型交叉评测通过**候选匿名化、独立Judge、偏差校准和确定性Oracle融合**实现，用于降低单一模型的系统偏见。

1. 固定评测集、Rubric、上下文和参数，候选输出用随机ID匿名；Pairwise比较时交换左右顺序，Judge看不到模型品牌、价格和排名。
2. 选择架构来源不同的Judge，固定版本、温度、Prompt和Schema。候选模型不宜评价自己；无法避免时，Self-preference结果单独标记并降权。
3. Judge输出分维度分数、严重错误、证据和置信度。Schema、测试、事实库或业务状态优先判定，Judge不得推翻硬证据与安全门禁。
4. 聚合可用加权平均、Majority Vote或Bradley-Terry/Elo，权重由专家锚点集准确率确定；分歧超阈值转人工，不强制统一。
5. 报告Judge一致率、专家相关性、Position/Verbosity/Self-preference偏差、采样方差和置信区间；版本变化后重新校准。

输入输出、JudgeVersion、随机顺序和聚合版本须可追溯。高风险领域专家终审，线上A/B Test验证排序与真实价值。

**相关知识点：** Multi-Judge、Blind Evaluation、Pairwise Ranking、Bradley-Terry、Elo、Self-preference、Inter-rater Agreement、Calibration。
<a id="gov-099"></a>
### 自动验收机制如何设计？

自动验收应把目标转化为**可执行、分层、不可被模型修改的Acceptance Contract**，由独立Verifier判定；Agent自评仅作证据。

1. 创建时定义必需目标、约束、允许副作用、数据范围、阈值和严重错误。Contract绑定TaskID，目标变化时生成新版本。
2. 确定性验收采用Schema、规则、测试、SQL、文件Hash、业务状态和Tool回执；开放内容使用Rubric、引用核验或校准后的Judge。
3. 多步骤DAG在关键节点设置局部验收，前置Artifact满足Schema、事实和安全条件才解锁下游；最终再检查端到端目标。
4. Verifier运行在隔离权限域，输入不可通过Prompt Injection改写；安全、越权、重复副作用和数据泄露设硬门禁，不能平均抵消。
5. 结果分为PASSED、PARTIAL、FAILED、UNVERIFIABLE，附规则、证据和可修复性；有限次修复后转人工，随机Judge需多次采样。

验收规则以Golden Set、对抗样本和历史失败回归，监控误收、误拒、不可评估率、耗时及成本；Agent升级不能自动修改Verifier。

**相关知识点：** Acceptance Contract、Independent Verifier、Hard Gate、Schema Validation、Golden Set、LLM-as-Judge、Partial Success、回归测试。
<a id="gov-100"></a>
### 多步骤任务如何计算完成率？

多步骤任务应报告**最终成功、必需节点通过率和加权进度**，不能用已执行步骤数计算；执行完成不等于验收通过。

1. DAG节点标为Required、Optional或Compensating，并定义验收、权重、依赖和严重错误。权重依据业务价值、关键路径或风险预先确定，禁止事后调整。
2. Task Success是二元指标：所有必需目标和硬门禁通过，且关键副作用正确才算成功。安全、权限或不可逆错误可直接判失败。
3. 加权进度＝已验收Required权重÷全部Required权重；Optional单报增益。并行分支按权重聚合，重规划生成新DAGVersion并保留原分母。
4. 部分完成按通过的Criteria或权重计算，但需标记阻塞节点、未完成目标和剩余价值；Skipped仅在策略允许时排除。
5. 重试只统计节点一次，Attempt用于稳定性；执行但验收失败不计完成，补偿节点按最终状态计算，Cancelled和Unverifiable单列。

平台展示Task Success、Weighted Progress、关键路径、首次通过和接管率，并按任务类型切片；验收规则与权重版本化，防止拆小步骤刷高。

**相关知识点：** DAG、Required/Optional、Weighted Progress、Task Success、Acceptance Criteria、Hard Gate、Attempt、Goodhart效应。
<a id="gov-101"></a>
### Agent任务拆解失败如何评估？

拆解质量应评估**目标覆盖、依赖、粒度、可执行、可验收和风险**。最终失败只是结果，还需定位计划中的结构错误。

1. 检查用户目标是否映射到Required节点，识别遗漏、重复、无关步骤和约束丢失；计算Goal Coverage、冗余率与必要步骤召回率。
2. 校验DAG无环、依赖、顺序、并行安全和Schema；缺少前置数据、副作用提前、资源竞争或依赖不满足均为结构错误。
3. 判断节点能否由Agent/Tool执行，权限、预算、Deadline和上下文是否足够；过粗难恢复与验收，过细增加通信和Token成本。
4. 节点须有完成条件、失败路径、重试及补偿；不能验收则不可操作。高风险动作应标注RiskScore、审批与回滚，遗漏门禁是严重失败。
5. 统计首次可执行率、修订、新增节点、依赖错误、死循环、计划归因失败、额外成本和人工改计划率，并按TaskType切片。

通过Trace回放、对抗任务和变异测试建立基线；失败归入Omission、Ordering、Granularity、Feasibility、Acceptance和Safety，修复后同时验证成本。

**相关知识点：** Plan Evaluation、Goal Coverage、DAG Validation、Granularity、Feasibility、Acceptance Criteria、Mutation Testing、Failure Taxonomy。
<a id="gov-102"></a>
### 多Agent协作任务如何评估整体成功率？

整体成功率应以**端到端目标和副作用正确性**为准，不能取Agent成功率平均值；局部完成不代表组合结果正确。

1. 父Task定义Acceptance Contract，将目标映射到Required节点与硬门禁；所有必需目标通过、关键资源正确且无安全违规才成功。
2. 子Agent评估理解、Schema、事实性、Tool和局部验收；父级检查消息、依赖、Artifact兼容、冲突、汇聚和最终一致性。
3. 报告Task Success、节点通过率、首次通过、重规划、协作轮次、消息错误、重复工作、接管、P95和Cost/Success；Attempt不重复计入。
4. Failure Taxonomy区分规划、路由、Agent能力、通信、共享状态、资源冲突、Tool、权限和验收错误；多原因记录主因与贡献因子。
5. 测试覆盖并行、汇聚、消息丢失/重复/乱序、慢Agent、部分失败和恶意Agent；以Fault Injection验证降级、取消、补偿和恢复。

按TaskType、Agent组合、DAG长度、难度和版本切片并报告置信区间；与单Agent或Workflow基线比较，确认质量收益大于协调成本。

**相关知识点：** End-to-end Success、DAG Acceptance、Artifact Compatibility、Failure Taxonomy、Fault Injection、Cost/Success、协作开销、基线对照。
<a id="gov-104"></a>
### Coding Agent最重要的评估指标是什么？

最重要的指标是**经独立验收的任务解决率**：代码是否真正解决任务且未引入安全与回归问题。测试通过或可编译只是子指标。

1. 在干净环境应用Patch，运行预定义公开与隐藏测试并核对Acceptance Criteria；测试不能由被评Agent任意修改，新增测试由独立Verifier检查。
2. 正确性护栏包括构建、单元/集成/E2E、类型、Lint和回归；还需检查边界、并发、错误处理、性能及兼容性，避免对可见测试过拟合。
3. 安全是硬门禁：SAST、依赖漏洞、Secret、License、鉴权、注入、路径越界和危险命令；严重漏洞、误删或越权不能被功能分抵消。
4. 变更质量关注Diff最小性、无关修改、API破坏、可维护性、覆盖Diff、Reviewer接受率和回滚难度；大面积重写风险高于局部修复。
5. 效率包括首次通过、修订、人工接管、P95、Token和Cost/Resolved Task；重试后成功与首试成功分开报告。

评测覆盖真实Issue、跨文件修改、调试、重构、依赖升级和安全修复，按语言与难度切片，并结合缺陷逃逸率和回滚率验证。

**相关知识点：** Task Resolution Rate、Hidden Test、Regression、SAST、Diff Minimality、Defect Escape Rate、Cost/Resolved Task、代码评测。
<a id="gov-106"></a>
### 如何评估代码生成质量？

代码生成质量应以**正确、安全、可维护、变更最小且可交付**为标准，由独立Verifier在沙箱评估；相似度和编译通过不足以代表质量。

1. 在干净仓库应用Patch，运行构建、公开与隐藏测试、集成/E2E及验收；新增测试需验证断言，Mutation Testing发现弱测试。
2. 检查边界、异常、并发、资源释放、性能和兼容性；通过类型、Lint、复杂度及API/Schema契约发现未覆盖缺陷。
3. 执行SAST、依赖漏洞、Secret、License、鉴权、注入、反序列化、路径越界和危险命令检查；严重漏洞或越权设Hard Gate。
4. 评估Diff最小性、无关修改、命名、模块边界、重复、覆盖Diff和回滚难度；大面积重写提高RiskScore并要求Review。
5. 检查Commit原子性、依赖锁、Migration、配置和回滚；统计Task Resolution、首次通过、Reviewer接受、缺陷逃逸及Cost/Resolved Task。

评测覆盖新功能、Bug修复、重构、调试、跨文件、依赖升级和安全修复，按语言、难度与版本切片，以线上缺陷和回滚校准。

**相关知识点：** Task Resolution、Hidden Test、Mutation Testing、Static Analysis、SAST、Diff Minimality、Maintainability、Defect Escape Rate。
<a id="gov-107"></a>
### 如何评估代码修改带来的风险？

代码风险由**影响面、资产敏感度、验证强度、可逆性和运行证据**评估，不能只看修改行数；一行鉴权代码可能更危险。

1. 分析Diff涉及的模块、调用图、API/Schema、配置、依赖、权限、数据流和Migration，识别跨服务、公共库、关键路径及意外变更，计算Blast Radius。
2. 资产按鉴权、支付、加密、PII、生产配置和删除分级。RiskScore综合文件敏感度、外部输入、提权、复杂度、规模和历史缺陷。
3. 验证覆盖构建、单元/集成/E2E、隐藏测试、Mutation Testing、类型、Lint、SAST、依赖漏洞、Secret和性能回归，关注关键路径覆盖。
4. 评估兼容性、Feature Flag、Canary、数据备份、Expand/Contract和回滚。不可逆Migration或外部副作用提高风险，要求专项审批。
5. 高风险变更由CODEOWNERS或双人Review，审批绑定Commit SHA和测试证据；代码变化后旧批准失效。灰度监控SLO和安全，超阈值回滚。

平台记录RiskScore、证据、Reviewer、部署和缺陷，以逃逸率、回滚率和事故校准评分；未知依赖与验证缺口必须单独呈现。

**相关知识点：** Blast Radius、Risk Score、Call Graph、SAST、Mutation Testing、Feature Flag、Canary、CODEOWNERS、缺陷逃逸率。
<a id="gov-108"></a>
### 人工接管率为什么重要？

人工接管率衡量**Agent在风险边界内独立完成任务的能力**，影响自动化价值和成本；但并非越低越好，正确升级也是能力。

1. 指标为发生人工继续、修改、审批外干预或补救的Task÷有效Task，并区分主动请求、策略强制、用户主动、超时和事故补救；预设审批不等于能力失败。
2. 高接管可能源于模型、Prompt、RAG、Tool、计划、权限或验收问题；须按Failure Taxonomy、TaskType、难度、风险、版本和节点切片。
3. 接管时点很重要：早期澄清成本低，执行后补救成本高。统计接管前耗时、Token、重复副作用、人工时长、最终成功及Cost/Success。
4. 低接管也可能源于未识别风险、过度自动执行或用户放弃；须与完成率、安全事件、投诉、缺陷逃逸和满意度联合观察。
5. 优先优化高频可自动化原因，如参数、知识、工具和计划；对法律、财务、生产发布等高风险领域保留HITL，不为指标取消审批。

记录接管原因、节点、人工Diff和结果，衡量Automation Rate、Appropriate Escalation及人工分钟/成功任务，以A/B Test验证成本与安全。

**相关知识点：** Human Takeover Rate、Automation Rate、Appropriate Escalation、Failure Taxonomy、Cost/Success、HITL、护栏指标、A/B Test。
<a id="gov-110"></a>
### 如何通过监控发现Agent能力退化？

能力退化应通过**稳定基线、分层指标、版本关联和统计检测**发现，并区分真实下降与流量、数据、工具或评测变化。

1. 按TaskType、难度、领域和风险建立Baseline，监控Task Success、事实性、工具选择、首次通过、重规划、接管和缺陷逃逸；总体平均值会掩盖局部退化。
2. 同时观察P95、Token、Cost/Success、重试、RAG零召回和Tool错误。完成率不变但成本或接管上升，也可能退化。
3. 标记Model、Prompt、Workflow、Index、Tool、Policy和代码发布，利用变点检测、Control Chart和Burn Rate发现持续偏移；低流量需置信区间。
4. 固定Canary集定时运行并锁定数据版本；线上以Shadow Traffic或A/B Test比较稳定版。固定集正常而线上下降时，检查分布与依赖。
5. 异常Trace按Failure Taxonomy归因，并替换模型、Prompt、RAG或Tool。高风险退化触发降级或回滚，普通波动观察。

还要监控Judge漂移、埋点缺失和口径变化，避免测量退化被误判；确认后的失败样本进入回归集，盲测集保持隔离。

**相关知识点：** Capability Drift、Baseline、Canary Set、Change Point、Control Chart、Shadow Traffic、Failure Taxonomy、Judge Drift。
<a id="gov-115"></a>
### 如何构建Agent评测平台（Evaluation Platform）？

Agent评测平台应形成**数据集—执行—裁判—分析—发布门禁—反馈回流**的闭环，既评估最终答案，也评估规划、检索、工具和安全过程。

1. 数据层统一管理黄金集、生产回放集、对抗集和长尾失败集，保存任务、上下文、参考答案、允许工具、评分规则及数据版本；按能力、行业、风险和难度分层，隔离训练集与测试集。
2. 运行层将Agent、模型、Prompt、知识库和Tool版本封装为可复现实验，支持并发执行、固定随机性、依赖Mock、超时重试和轨迹采集，避免外部波动污染对比。
3. 评分层组合确定性断言、单元测试、规则、语义指标、LLM-as-a-Judge与人工复核；Judge采用结构化Rubric、盲测、顺序随机化和多裁判仲裁，并用人工标注校准。
4. 指标覆盖任务完成率、答案正确性、引用忠实度、Tool成功率、安全违规率、延迟、Token成本及人工介入率；同时按场景分桶，报告均值、分位数、置信区间和显著性。
5. 平台提供版本对比、失败聚类、Trace下钻和根因标签；CI中设置质量、安全与成本门槛，只有无关键回归的版本才能灰度发布。

线上反馈经脱敏、去重和人工确认后回流评测集，防止数据泄漏与指标漂移；**离线评测用于筛选，在线实验用于验证真实业务价值**。

**相关知识点：** 黄金数据集、生产回放、Rubric、LLM-as-a-Judge、显著性检验、分层指标、回归门禁、数据泄漏、评测闭环。
<a id="gov-116"></a>
### 你们线上Agent完成率是多少？

该问题不能只给一个脱离口径的百分比。面试中应先明确统计周期、任务边界与成功定义，再给真实数据；若没有生产数据，应明确说明，**不得虚构完成率**。可按以下方式作答：

1. 主指标为端到端任务完成率，即在统计窗口内，通过业务验收且未被人工代办的有效任务数除以有效任务总数；取消、测试流量、恶意请求和平台事故是否剔除必须预先固化。
2. 同时报告严格完成率与辅助完成率。前者要求结果正确、工具副作用成功且满足SLA；后者允许一次澄清或人工审批，但人工直接修正结果不计自主完成。
3. 除总体值外，必须按任务类型、难度、租户、Agent版本和风险等级分层，并给出样本量、置信区间及最近趋势。总体上升可能只是简单任务占比增加，不能代表能力提升。
4. 配套观察首次通过率、重试后通过率、人工介入率、用户放弃率、安全违规率、P95延迟和单次成功成本，以识别“靠重试、降级或人工堆高”的虚假改善。
5. 成功应由确定性验证器、业务系统终态、用户确认或经校准的Judge共同判定；抽样人工复核误判，并通过Trace审计分子、分母。

示例表达可为：“近30天有效任务N个，严格完成率X%，置信区间为Y，较上版提升Z个百分点；高风险场景仍为主要缺口。”所有数值均应来自可追溯报表。

**相关知识点：** 任务完成率、严格成功、辅助成功、分层统计、置信区间、首次通过率、人工介入率、指标口径、幸存者偏差。
<a id="gov-117"></a>
### 如何持续优化Agent完成率？

持续优化完成率应建立**可度量、可归因、可验证、可回滚**的工程闭环，在不牺牲安全、成本和时延的前提下减少失败。

1. 固化成功口径，按任务类型、难度、版本和风险分层统计完成率、首次通过率、人工介入率及单次成功成本，避免任务结构变化掩盖真实能力。
2. 汇总线上Trace、用户反馈和人工接管样本，建立Failure Taxonomy，将失败归到需求不清、规划、模型、检索、工具、权限、状态、验证或外部依赖；按失败频率乘业务影响排序。
3. 针对根因实施最小改动：输入不清先澄清；规划错误增加约束与Verifier；检索问题优化切分、召回和重排；Tool问题完善Schema、幂等、重试及熔断；高风险任务增加审批。
4. 将每个修复样本加入版本化回归集，使用确定性断言、LLM Judge与人工复核验证；同时检查安全违规、P95延迟和成本，禁止以无限重试或人工兜底换取表面提升。
5. 新版本经过离线门禁、Shadow、Canary和A/B Test逐级放量，按分层指标与置信区间判断收益；异常自动回滚，避免平均值掩盖关键场景退化。

上线后监测数据漂移、知识时效、工具契约和模型版本，定期重校Judge。**每次优化必须对应明确失败簇，并由回归样本证明改进**。

**相关知识点：** Failure Taxonomy、错误预算、回归集、根因分析、分层指标、Shadow、Canary、A/B Test、Verifier、持续评测。
<a id="gov-118"></a>
### Agent能力升级后如何验证效果提升？

能力升级必须通过**同口径基线、配对评测、统计检验和线上业务验证**证明净收益，不能仅凭展示样例或总体平均分判断。

1. 升级前冻结Agent、模型、Prompt、知识库、工具和环境版本，记录基线；明确主指标、护栏指标、最小可接受提升及回滚阈值，防止看到结果后修改标准。
2. 构建版本化评测集，包含黄金样本、生产回放、历史失败、长尾与对抗样本，并按任务类型、难度和风险分层。新旧版本使用相同输入、依赖Mock及执行预算，形成配对结果。
3. 评分组合确定性验证、任务终态、结构化Rubric、经校准的LLM Judge及盲审人工抽样；除完成率外，检查正确性、引用忠实度、安全违规、延迟、Token成本和人工介入。
4. 对完成率差异采用配对比例检验或Bootstrap置信区间，对延迟和成本报告分位数；同时分析改善样本与退化样本，确认收益不是任务构成、随机性或Judge偏差造成。
5. 通过Shadow验证真实流量兼容性，再进行Canary或A/B Test；按用户或任务稳定分流，隔离同期变化，观察足够周期，并设置自动停止和回滚。

只有主指标达到最小实际效应、关键分层无不可接受回归、护栏全部通过，才能确认升级有效。评测记录需保存版本、种子、Trace和产物，确保结果可复现、可审计。

**相关知识点：** 配对评测、基线、最小实际效应、Bootstrap、置信区间、回归测试、Shadow、Canary、护栏指标、可复现性。
<a id="gov-119"></a>
### 如何设计A/B Test评估Agent版本效果？

Agent A/B Test应验证新版本对真实业务的**因果增益**，核心是稳定随机化、口径一致、污染隔离和预设停止规则，而非简单比较两个时间段。

1. 先定义假设、主指标、护栏指标、最小可检测效应、显著性水平、检验功效和实验周期。主指标可用严格任务完成率；护栏应包含安全违规、P95延迟、单次成功成本、投诉和人工介入率。
2. 选择用户、会话或租户作为随机化单元并保持粘性，避免同一上下文跨组；按任务类型、难度和历史活跃度分层随机，检查实验前样本比例及关键特征是否平衡。
3. A组固定基线版本，B组只改变待验证因素；锁定模型、Prompt、知识库和工具依赖，或完整记录差异。共享缓存、记忆、人工坐席和学习数据必须隔离，防止处理干扰。
4. 成功由业务终态、确定性验证或经校准的Judge判定；实验期间监控SRM、数据丢失、外部故障和新奇效应。除总体指标外分析预设分层，禁止事后挑选有利人群。
5. 使用适合比例或连续指标的统计检验，报告效应量和置信区间；除安全紧急停止外，不因短期显著而反复窥视提前结束，可采用序贯检验控制误报。

新版本仅在主指标达到实际收益、护栏无退化且结果跨周期稳定时放量；否则回滚并保留失败Trace。高风险操作宜先Shadow和Canary，再进入受控实验。

**相关知识点：** 随机对照实验、随机化单元、分层随机、SRM、最小可检测效应、检验功效、序贯检验、处理干扰、护栏指标。
<a id="gov-121"></a>
### 企业级Agent上线前需要经过哪些评测流程？

企业级Agent上线前应通过**能力、安全、可靠性、性能成本和合规**五类门禁，并采用离线到线上、低风险到高风险的逐级放量流程。

1. 需求与风险评审：明确允许任务、禁止行为、数据分级、工具权限、成功口径、SLA及责任人；完成威胁建模、隐私影响和供应商风险评估。
2. 离线能力评测：使用黄金集、生产回放、历史失败及长尾集验证任务完成率、事实正确性、RAG忠实度、Tool成功和多轮状态；执行新旧版本配对回归，关键场景不得退化。
3. 安全评测：覆盖Prompt Injection、越权、数据泄露、恶意文件、危险工具、跨租户访问及拒绝绕过；验证最小权限、沙箱、审批、审计和敏感信息脱敏，并进行红队测试。
4. 工程评测：开展单元、集成、契约、故障注入、并发、容量和长稳测试，检查超时、重试、幂等、熔断、降级及灾难恢复；量化P95延迟、吞吐、Token和单次成功成本。
5. 发布验证：在类生产环境完成端到端验收，先Shadow观察真实流量，再Canary小比例放量；设置完成率、安全、延迟和成本阈值，异常自动熔断或回滚。

发布包必须包含模型、Prompt、知识库和Tool版本、评测报告、已知限制、Runbook及回滚方案，并由业务、安全和平台责任人签署。上线后继续A/B或监控漂移，评测不是一次性验收。

**相关知识点：** 发布门禁、威胁建模、红队测试、回归测试、故障注入、契约测试、Shadow、Canary、Runbook、持续评测。
<a id="gov-126"></a>
### Prompt评测体系如何搭建？

Prompt评测体系应把Prompt视为**可版本化、可回归、可灰度的软件资产**，同时检验任务质量、安全性、稳定性、延迟与成本，避免凭少量案例主观选择。

1. 明确Prompt职责和成功Rubric，将指标拆为指令遵循、事实正确、格式合法、引用忠实、Tool参数准确、安全拒绝、Token成本和响应延迟，并设置不可用的硬门槛。
2. 数据集包含标准任务、生产回放、历史失败、边界、多轮和注入样本；保存输入、期望行为、允许工具及版本，隔离开发集与隐藏测试集。
3. 固定模型、采样参数、知识库、工具和执行预算，对候选Prompt进行相同种子或多次重复的配对运行。保存Prompt模板、变量、渲染结果、Trace和输出，确保可复现。
4. 评分优先使用Schema校验、单元测试和业务终态；开放任务采用结构化LLM Judge并辅以人工盲审。Judge需随机候选顺序、隐藏版本，定期用人工标签校准偏差和一致性。
5. 报告总体与场景分桶结果、效应量、置信区间、退化样本及成本变化；通过回归门禁后，先Shadow再A/B验证线上完成率和护栏指标，异常立即回滚。

线上失败经脱敏确认后回流评测集；防止测试集泄漏与模板过拟合。**每次Prompt变更都须绑定假设、评测报告和版本记录**。

**历史别名：** `ENG-044`。

**相关知识点：** Prompt版本管理、Rubric、配对评测、隐藏测试集、确定性评测、LLM Judge、人工盲审、回归门禁、Prompt漂移。
<a id="gov-127"></a>
### Prompt AB Test如何实施？

Prompt A/B Test应在**仅改变Prompt版本**的前提下，以稳定随机流量验证真实业务收益，并用安全、成本和延迟指标约束质量提升。

1. 实验前登记假设、主指标、护栏、最小可检测效应、样本量和停止规则。主指标通常为严格完成率或首次通过率；护栏包含安全违规、事实错误、人工介入、P95延迟及单次成功成本。
2. A组使用当前Prompt，B组使用候选Prompt；固定模型版本、采样参数、知识库、Tool、记忆策略和预算。记录模板版本与最终渲染哈希，防止变量或配置漂移造成混杂。
3. 按用户、会话或任务稳定随机，涉及多轮记忆时必须保持组别粘性；按任务类型、难度和风险分层，并隔离缓存、反馈学习和人工处理，避免跨组污染。
4. 成功优先由业务终态和确定性验证器判定，开放任务使用经人工校准的Judge；Judge隐藏组别并随机候选顺序。持续监控样本比例失衡、日志缺失、外部故障与异常流量。
5. 到达预定样本量后比较效应量和置信区间，同时检查各预设分层及退化样本；除安全紧急情况外，不随意提前停止或事后挑选有利指标。

候选Prompt只有在主指标达到实际收益、全部护栏通过且结果跨周期稳定时才放量；否则回滚。实验产物应保留Prompt、配置、Trace、评分和数据版本，支持复核。

**历史别名：** `ENG-045`。

**相关知识点：** 随机对照实验、粘性分流、混杂变量、最小可检测效应、护栏指标、Judge盲测、SRM、效应量、实验污染。

### RAG召回率与准确率如何评估？

RAG评估应建立**Query—相关Chunk黄金标注**，将“是否找全”和“结果是否相关”分开测，再验证证据能否支持答案。

| 指标 | 计算与含义 | 主要问题 |
|---|---|---|
| Recall@K | 命中相关项数÷全部相关项数 | 是否漏证据 |
| Precision@K | TopK相关项数÷K | 是否有噪声 |
| Hit Rate@K | 至少命中一项的查询占比 | 能否命中 |
| MRR/NDCG | 首个命中及排序质量 | 是否靠前 |

1. 数据集覆盖事实、多跳、时效、权限、歧义及无答案问题；相关性分为关键、辅助和无关，由双人标注，避免单一标准文档造成伪漏召。
2. 固定Chunk、Embedding、索引、查询改写、过滤和Rerank版本，分别记录候选召回与重排指标；按领域、难度和新鲜度分层，报告K曲线与置信区间。
3. 无答案查询计算拒答正确率，权限场景计算越权召回率；端到端评估Context Precision、Context Recall、答案正确性、引用忠实度和文档利用率。
4. 抽检误召与漏召，定位知识缺失、切分、Embedding、过滤、查询改写或Rerank问题。

**召回率高不代表答案正确**；目标是在受控上下文和延迟下提供充分、可信的证据。

**相关知识点：** Recall@K、Precision@K、Hit Rate、MRR、NDCG、Context Recall、Context Precision、黄金标注、无答案评测。
<a id="gov-135"></a>
### 多模型AB Test如何实施？

多模型A/B Test应比较不同模型在同一Agent中的**端到端净效益**，必须控制Prompt、工具、知识库和路由差异，并处理模型价格、限流及输出风格造成的混杂。

1. 实验前定义主指标、护栏、最小可检测效应和停止规则。主指标可为严格任务完成率；护栏包含安全违规、事实错误、人工介入、P95延迟、可用性、Token量及单次成功成本。
2. 统一适配层规范消息、Tool Schema、超时和错误；维护等价Prompt模板，不同模型可做格式适配，但不得引入无关逻辑变化。
3. 离线先在黄金集、生产回放、历史失败和对抗集上进行配对评测，固定知识库快照、工具Mock及预算；随机任务多次运行，记录模型版本、区域、采样参数、Trace和输出。
4. 线上按用户或会话稳定随机，任务类型与难度分层；共享缓存、记忆和反馈学习需隔离。监控SRM、供应商故障、限流、上下文截断与路由回退，回退样本不能错误计入原实验组成功。
5. 成功以业务终态和确定性验证为主，Judge须隐藏模型身份并随机顺序；比较效应量和置信区间，分析关键分层与退化样本，不只比较总体均值。

若质量接近，以“每个成功任务成本”及延迟选择，也可按风险与难度组合路由。高风险场景先Shadow、Canary，安全护栏越界立即停止。

**相关知识点：** 模型适配层、配对评测、稳定随机、SRM、路由回退、每次成功成本、Judge盲测、分层路由、护栏指标。
<a id="gov-136"></a>
### 如何判断模型能力是否达到瓶颈？

判断模型瓶颈应通过**上限实验和错误归因**证明：控制检索、工具、上下文与预算后，更强模型仍显著提升，才说明当前模型是主要限制。

1. 对失败Trace标注输入、规划、推理、RAG、Tool、权限、状态和验证根因。若多数失败源于知识、工具或流程，升级模型收益有限。
2. Oracle实验提供黄金文档、正确Tool结果和计划；若性能恢复，瓶颈在上游，若仍在推理或指令遵循上失败，才支持模型瓶颈判断。
3. 做模型阶梯实验，在相同Prompt、数据、工具、温度和预算下比较不同能力等级模型，采用配对评测并分析效应量。若质量随模型能力持续上升且成本可接受，说明尚有模型空间；若曲线平台化，应优化系统。
4. 对当前模型增加合理的思考预算、自一致性或Verifier，观察边际收益；同时测试上下文压缩、Prompt优化、Rerank和Tool Schema消融，比较每项改动的单位成本收益。
5. 按任务和难度分层，检查错误是否集中于长上下文、多跳推理、专业知识或函数参数，并人工排除Judge偏差。

瓶颈不是永久属性，会随数据与工具变化。最终应依据**提升一个组件后的可实现上限、边际收益和单次成功成本**决定升级模型、优化编排或采用分层路由。

**相关知识点：** Oracle实验、组件消融、模型阶梯、错误归因、能力上限、边际收益、分层评测、单位成功成本、系统瓶颈。
<a id="gov-137"></a>
### Agent任务完成率指标体系如何设计？

任务完成率体系应围绕**业务终态是否正确达成**设计主指标，并用自主程度、安全、效率和成本指标约束，避免重试、人工代办或筛除困难任务造成虚高。

1. 定义有效任务及统计窗口。严格完成率等于结果通过验收、必要副作用成功且满足SLA的任务数除以有效任务数；用户取消、恶意请求、测试流量及平台事故的处理规则需预先冻结。
2. 设置分层漏斗：请求可受理率、计划生成率、关键步骤成功率、首次通过率、重试后通过率、最终完成率。区分自主完成、澄清后完成、审批后完成、人工代办和失败，人工直接修正不能计为自主成功。
3. 成功判定优先采用业务系统终态、确定性断言、回读校验和用户确认，开放任务采用经校准的Judge并抽样人工复核；每次判定保存证据、规则版本和Trace。
4. 配套护栏包括事实错误、安全违规、越权、用户投诉、人工介入、P95延迟、Token成本及单次成功成本；否则可通过无限重试、降级质量或增加人工抬高完成率。
5. 报表按任务类型、难度、租户、风险、Agent及模型版本分层，展示样本量、置信区间和趋势；版本比较应采用相同任务分布或标准化加权。

同时监控分母漂移、标签延迟、Judge漂移与重复任务。核心经营指标可使用**风险调整后的每次成功成本**，但权重和成功价值必须由业务预先确定。

**相关知识点：** 严格完成率、自主完成率、首次通过率、任务漏斗、业务终态、护栏指标、分层统计、置信区间、分母漂移。
<a id="gov-140"></a>
### 如何构建Agent质量评测集？

Agent质量评测集应代表**真实任务分布、关键风险和能力边界**，并提供可执行环境、明确成功标准与版本血缘，而不是只保存问答文本。

1. 数据来源组合业务流程设计的黄金样本、脱敏生产回放、历史失败、用户反馈、专家构造的长尾及安全对抗样本；按任务类型、难度、领域、语言、风险和多轮长度建立覆盖矩阵。
2. 每个样本包含输入、上下文、初始状态、允许与禁止工具、知识快照、期望业务终态、参考证据、评分Rubric、超时和预算。对动态外部依赖使用Mock或录制回放，保证可复现。
3. 开放任务允许多个正确路径，不把单一参考答案当唯一标准；代码、数据库和工具任务优先通过测试、Schema、状态回读及副作用验证，语义质量再使用经校准的Judge和人工盲审。
4. 采用专家双标与仲裁建立金标，记录分歧和不确定性；去重、近重复检测、PII脱敏及许可证检查必须前置，训练集、开发集和隐藏测试集严格隔离。
5. 生产流量变化与Failure Taxonomy驱动增量采样，对高价值、低频和新失败簇提高权重；数据集版本保存来源、时间、标签、知识与工具版本，并设置过期复审。

发布时同时报告总体和分层指标、样本量及置信区间，禁止因修复某版本而删除失败样本。核心集保持稳定用于纵向回归，滚动集反映最新分布，对抗集独立衡量安全。

**相关知识点：** 黄金集、生产回放、覆盖矩阵、业务终态、Rubric、双人标注、隐藏测试集、数据泄漏、滚动评测集。
<a id="gov-141"></a>
### Agent完成率从70%提升到90%的优化路径是什么？

从70%提升到90%应按**失败占比乘业务影响**逐层消除缺陷；先统一口径，否则变化可能只来自分母或人工兜底。

1. 以业务终态定义严格完成率，按任务、难度和风险分层，统计首次通过、人工介入、安全、P95延迟及成功成本；用Trace建立Failure Taxonomy。
2. 优先修复高频确定性问题：需求不清增加澄清；参数错误强化Tool Schema；超时完善幂等重试、熔断和检查点；权限问题通过预检消除。
3. 改善知识链路：补齐高价值知识缺口，优化解析、Chunk、元数据、混合召回和Rerank；分别监控Recall与排序，要求答案携带引用并由忠实度Verifier检查。
4. 改善推理与执行：将复杂任务分解为可验证步骤，增加计划约束、状态机、预算和步骤级Verifier；只在确认模型为瓶颈的任务上升级模型或增加推理预算。
5. 处理长尾：低置信、高风险和不可逆操作引入审批，可恢复任务使用自修复；通过失败聚类发现新模式。

每项改动将样本加入回归集，经离线配对、Shadow、Canary和A/B验证后放量。**90%必须在安全、成本和时延护栏不退化时成立**。

**相关知识点：** 帕累托优化、Failure Taxonomy、严格完成率、RAG诊断、Tool Schema、Verifier、长尾治理、Shadow、Canary。
<a id="gov-146"></a>
### 如何建立Agent持续优化闭环体系？

持续优化闭环应把**线上信号转化为可验证的工程改动，再安全发布并回流新证据**，形成“观测—归因—排序—修复—评测—发布—监控”的循环。

1. 统一成功口径，采集完成率、首次通过率、人工介入、安全违规、延迟和成功成本；以TaskID、TraceID关联Prompt、RAG、Tool及业务终态。
2. 失败样本脱敏、去重并按Failure Taxonomy分类，以频率乘业务影响乘可修复性排序；区分症状与根因，高风险或低置信归因由人工复核。
3. 每项优化建立假设，选择最小作用域方案：澄清、调整Prompt、补齐知识、优化检索、修正Tool、增加Verifier或升级模型。
4. 将问题样本加入版本化回归集，使用确定性断言、业务终态、Judge及人工盲审进行配对评测；主指标提升的同时，安全、成本、时延和关键分层不得退化。
5. 经CI门禁、Shadow、Canary和A/B逐级放量，异常自动停止或回滚；上线后比较预期与真实收益，记录改善、退化和无效改动，并更新知识、规则及Runbook。

设置评测负责人、版本审批和定期复盘，监控任务、Judge、模型与知识漂移。**每个失败都应成为资产，每次改动都应有可复现证据**。

**相关知识点：** 持续评测、Failure Taxonomy、优先级模型、回归集、配对实验、CI门禁、Shadow、Canary、A/B Test、漂移监控。
