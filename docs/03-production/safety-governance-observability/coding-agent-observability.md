### 1. Coding Agent 一次会话该记录哪些事件？与通用 Agent 的 Trace 有何不同？

通用 Agent 的 Trace 记的是「向外部系统发了哪些请求」，编码会话的 Trace 记的是**一份可变工作树如何一步步演变**——观测对象从无状态调用换成了有版本的状态机，这一条决定了后面所有差异。

1. 必记的事件分五类：仓库状态锚点（起始提交的完整哈希、每次写盘后的工作树内容哈希）、读取事件（文件、行区间、这次读取由什么触发）、编辑事件（目标区间与所依据的证据引用）、执行事件（构建与测试命令、退出码、失败用例）、外部事件（PR 创建、CI 结论）。少了状态锚点这一类，其余四类都无法互相校验。
2. 第一个差异是**幂等假设不成立**。通用工具调用大多可以孤立重放，编辑是对可变状态的累积写入，第 N 次编辑的语义依赖前 N−1 次的结果。因此事件必须带会话内单调的序号并支持重建中间状态，只当独立 Span 记录会丢掉顺序这一最关键的信息。
3. 第二个差异是**成功信号发生在会话之外**。工具返回码基本就是通用 Agent 的结果，而编码的真实结果是 CI 通过率、review 是否放行、合并后有没有被回滚，这些在会话结束后数小时到数天才出现。所以会话必须留一个能被后续事件回接的稳定标识，并接受结果标签是延迟到达且可能永远不到。
4. 第三个差异是**载荷天生敏感且大**。通用链路可以只留脱敏摘要，编码排障的价值恰恰在原文——是哪一行、哪个符号。折中是 Span 只存路径、区间与内容哈希，正文进受控存储按哈希寻址，Trace 层保持轻量。
记录密度应由「事后是否真会被用来回答某个具体问题」倒推，而不是能采什么就采什么——逐 Token 事件、每一次补全预览、LSP 的全部往返都不值得进结构化日志。可采集的指标包括编辑事件能追到读取依据的比例、工作树哈希链的连续率、延迟结果标签的回接率与到达时间分布。

**相关知识点：** 工作树内容哈希、事件序列号、写后状态锚点、延迟结果标签、内容寻址引用、结构化日志、Span 载荷外置。

### 2. 编码会话的 Span 层级如何划分：任务、轮次、工具调用还是文件？

文件不应该成为一层 Span，而应该是属性——**Span 树表达控制流，文件是数据维度**。把文件做成层级，一次批量修改三十个文件就会产生三十个彼此没有因果关系的兄弟 Span，瀑布图立刻不可读。

1. 真正稳定的是三层：任务对应根 Span，轮次对应一次模型推理及其后续工具执行，工具调用是叶子。文件、行区间、内容哈希挂在叶子 Span 的属性上。这样的树形与实际的控制流一致，父子关系表达的是「谁触发了谁」而不是「谁涉及了什么」。
2. 文件维度仍然要能查，但走的是 Span 属性索引而不是 Metric 标签。「这个文件被几次会话改过」是典型的高基数分析，放进时序库的标签会直接把基数打爆；放进 Span 属性则只影响追踪存储的索引，代价可控且查询语义更准。
3. 深度的代价是实打实的：树越深，上下文传播、采样决策与存储都变贵，且深层 Span 在人眼看的瀑布图上失去意义。实用约束是让单会话 Span 数落在人能翻完的量级，超出后应把重复的细碎步骤降级为 Span Event 挂在父 Span 上。
4. 值得破例加一层的是计划步骤。当 Agent 显式产出待办列表并逐项推进时，在轮次之上加一层能让归因落到「第三步做错了」而不是「第十七轮做错了」，后者对人几乎没有解释力。代价是这一层的边界由模型输出定义，模型不产计划时它会退化成空壳，需要允许缺省。

检验层级设计好坏的方式很直接：常见的排障问题能不能只靠 Span 树答出来，而不用去翻原始日志。要盯的信号是单会话 Span 数分布、树的最大深度、按文件属性检索的命中耗时，以及降级为 Event 的步骤占比。

**相关知识点：** Span 树深度、Span Attribute、Span Event、高基数标签、Metric Label 基数、计划步骤 Span、瀑布图可读性。

### 3. 一次会话中的「轮次」如何定义才对分析有用？

轮次有三种候选边界，选哪一种**取决于要回答的问题**：按用户消息切是产品口径，按模型调用切是成本口径，而同时支撑效率与质量分析的只有一种——一次模型推理加上它触发的全部工具执行。

1. 按用户消息切，两次人类介入之间算一轮，适合统计人均干预次数；但它在后台自主任务上完全退化，整个任务只有一轮，跨场景对比时这个口径直接失效。按模型调用切与计费和窗口占用天然对齐，是成本分析唯一可靠的分母，缺点是把推理与工具执行切在同一个边界上，延迟归因会被搅在一起。
2. 推荐口径的边界条件比口径本身更容易出错：同一轮内的并行工具调用应算一轮，因为它们基于同一份上下文做出决策；而因输出被截断而续写、因工具报错而自动重试，都不该新起一轮——否则轮次数会被基础设施抖动污染，所有按轮次归一化的指标跟着漂。
3. 轮次编号必须在会话内单调且不因上下文压缩而重置。压缩会重建消息数组，如果编号跟着数组下标走，压缩后轮次号会回退，此后所有时序分析的对齐都是错的，而这种错误不会报错、只会安静地给出反直觉的曲线。

轮次的价值在于当**进展速率的分母**：每轮的净变更行数、每轮成本、首次测试通过用了几轮。这几项比总耗时更能区分「慢但在推进」和「快但在原地转」。可采集的指标是会话轮次分布、每轮净变更行数、首次通过所需轮次的 P50 与 P95，以及重试被误算成新轮次的比例。

**相关知识点：** 轮次边界、并行工具调用、自动重试与续写、上下文压缩、轮次单调编号、每轮净变更、进展速率。

### 4. 交互式会话与后台自主任务的观测模型能统一吗？

能统一一半：**数据模型可以完全共用，指标口径必须分开**。两者在 Span 结构与事件语义上同构，但成功的定义、延迟的意义和采样的经济性互不通用，硬把口径也统一会得到一组谁都不敢用的数字。

1. 可共用的是 Trace 结构、事件语义与标识体系——同一套会话标识、仓库锚点、编辑事件。差别只在根 Span 由谁开启：交互式由用户消息开启，自主任务由调度器开启。为这点差别拆两套 schema，代价是每个下游分析都要写两遍，长期一定会分叉。
2. 第一处不能统一的是**延迟的语义相反**。交互式场景里没人愿意等，TTFT 与首次可见反馈直接决定体验，是必须优化的 SLI；后台任务没有人在等，端到端时长只是成本的代理量，压它反而可能牺牲正确性。
3. 第二处是**结果的判定者不同**。交互式会话的标签常来自用户的即时动作——采纳、拒绝、继续追问、放弃，样本量大但噪声高；自主任务只能靠 CI 与 review 给结论，滞后但可信。混进同一个成功率，指标会随两类流量的配比变化而漂移，而这个漂移看起来完全像质量波动。
4. 统一的具体做法是在 Resource 与 Span 属性上打一个执行模式维度，所有指标默认按它切分，仪表盘干脆不提供未切分的总览。看着只是加一个维度，实际决定了告警阈值能否分别设定——这正是两类流量最容易互相污染的地方。
5. 采样策略也要分：交互式流量大、单条价值低，适合头部采样加尾部保留异常；自主任务量少、单条价值高、失败代价大，应接近全采，为它单独设采样规则是划算的。

统一的边界在于跨模式的横向对比——两类流量的成功率不具可比性，只能各自与自己的历史比。要盯的指标是按执行模式切分的完成率、交互式的 TTFT P95、自主任务的单任务成本与人工接管率，以及两类流量的配比变化本身。

**相关知识点：** 执行模式维度、Resource 属性、TTFT、SLI、头部采样、尾部采样、结果标签来源、指标切分。

### 5. 会话与 PR、Issue、工单如何建立稳定关联？

关联必须**落在 Git 对象本身**，不能只存在观测系统的库里。PR 会被 rebase、squash、cherry-pick，提交哈希随之改变，事后靠时间戳或分支名重新匹配在并发场景下一定会错配，而错配的审计记录比没有记录更危险。

1. 最稳的载体是提交尾部的 trailer，比如一行 `Session-Id`。它随提交消息一起被 cherry-pick 携带，成本极低。代价是 squash 合并时保留哪几条 trailer 取决于平台配置，多个会话的提交被压成一个时会丢掉一部分，因此这条策略必须与合并方式的约定配套，单独上线是不完整的。
2. `git notes` 能在不改写提交的前提下附加元数据，适合事后补挂与写入较大的结构化信息。它的实际障碍不在机制而在传播：notes 默认不随普通推送同步，需要显式推送对应的 refs，团队协作中极易遗漏，于是本地看得到、平台上查不到。
3. 反向关联同样要做——PR 描述里写会话标识、工单上留引用。它们由平台 API 维护，可编辑、可删除，只能当辅助索引，权威副本必须在不可变对象上。把可编辑的一份当权威，等于允许任何人改写审计结论。
4. 数据模型要按多对多设计。一个会话可能产出多个 PR，一个 PR 也可能来自多个会话加上人工修改。假设一对一时最先崩掉的是「Agent 起草、人接手改完」这个最常见的形态，而它恰恰是最需要区分责任的场景。

关联的完整性要主动监控，而不是等出事才发现断了。可采集的指标包括提交的关联覆盖率、rebase 与 squash 之后的关联保持率、会话到 PR 的落地率，以及多对多关系的分布——落地率偏低通常意味着大量会话空跑，那本身就是值得单独看的一类结果。

**相关知识点：** commit trailer、`git notes`、cherry-pick 携带、squash 合并、反向索引、多对多关联、关联覆盖率。

### 6. 代码编辑如何做到可追溯：哪次修改基于哪条证据？

可追溯的关键不是「记录了编辑」，而是**每个编辑事件携带指向具体证据的引用标识**，并且这个引用在证据被挤出上下文之后仍然可解析——否则最需要追溯的长会话恰恰是断链最严重的。

1. 证据类型要能穷举并各自有稳定标识：一次文件读取（路径、区间、读时的内容哈希）、一条 LSP 诊断或一条 SARIF 结果（规则标识与位置）、一次测试失败（用例标识与断言消息）、用户的显式指令、检索命中的片段。类型不穷举，模型就会用自然语言描述来源，那种描述无法被机器校验。
2. 引用要在服务端校验而不是照单全收。让模型在编辑参数里带证据标识数组是可行的，但必须接受它可能编造标识：校验时要求该标识存在于本会话已产生的证据表中，校验失败的编辑仍然执行、但标记为「无证据」。直接拒绝执行会诱导模型胡乱填一个存在的标识来通过检查，反而污染数据。
3. 内容哈希是防证据过期的关键。读取时记下区间哈希，编辑时比对当前内容——若文件在读取之后被别的步骤改过，这条证据已经失效，而这正是大量编辑失败的前因，能在失败之前就报出来。
4. 上下文压缩会让引用悬空。证据表必须独立于上下文窗口持久化，压缩只影响模型看得到什么，不影响追溯链是否完整。代价是证据表随会话线性增长，需要单独的留存策略。
5. 追溯的实际用法是反向的：从一行有问题的代码回到当时依据了什么。所以索引要建在文件加行区间上，而不只是按时间排的事件流——按时间翻在长会话里成本太高。

不是所有编辑都该有证据，格式化、批量重命名、按用户指令的直改本来就没有，强行要求覆盖率百分之百只会逼出编造。可采集的指标是编辑事件的证据引用率、引用校验失败率、悬空引用比例，以及从代码行反查证据的命中率。

**相关知识点：** 证据标识、LSP 诊断、SARIF、内容哈希、证据表持久化、悬空引用、行区间反向索引。

### 7. 编辑失败（patch 打不上、字符串不匹配）如何度量与归因？

度量的第一个决定是选分母：**分母应是模型的编辑意图数，不是工具调用次数**。一次意图重试四次才成功，从工具视角是八成成功率，从任务视角是一次失败加一笔额外开销，两个数字会引导出完全相反的结论。

1. 归因要按可修复的根因切，至少七类：锚点字符串在文件中不存在、锚点出现多次导致定位不唯一、文件在读取之后被改动、行号漂移、空白与缩进不匹配、行尾符与编码差异、上下文行数不足使 unified diff 的 hunk 无法定位。这七类的修复手段分别落在检索、工具设计、并发控制和仓库规范上，合成一个「编辑失败率」没有任何行动价值。
2. 要做出归因，三份数据必须同时在场：模型给出的锚点原文、文件当时的真实内容、读取该区间时记下的内容哈希。缺任何一份都只能得到「失败了」这个结论。存储代价是每次失败要留一小段文件正文，因此规则应是失败才留、成功不留。
3. 必须把**工具形态导致的失败**与模型能力导致的失败分开。同一个模型在整文件重写、字符串替换、unified diff 三种编辑接口下的失败率差异很大，且失败构成不同：diff 形态多为行号与上下文问题，替换形态多为唯一性问题。不按接口切分，工具设计缺陷会被读成模型退化。
4. 重试会让失败在最终结果里消失。多数实现会自动重读文件再试一次，于是外部只看到成功。首次尝试成功率与最终成功率必须分别记录，两者的差就是被重试吃掉的成本，它体现为额外 Token 与额外延迟，而这部分往往比失败本身更贵。

编辑失败率上升不一定是模型的问题：仓库里新增了大量重复代码会让锚点不再唯一，换一套行尾规范会让整批替换失效。可采集的指标包括按根因分类的首次编辑成功率、意图级成功率、重试放大倍数，以及每次失败附带的额外 Token。

**相关知识点：** 锚点唯一性、stale read、行尾符差异、unified diff hunk、首次尝试成功率、意图级分母、重试放大。

### 8. 如何观测「改了又改」的返工模式？

返工本身不是缺陷，**要分辨的是收敛式迭代与震荡**：前者每次修改都在缩小与目标的差距，后者在两个状态之间来回。只统计修改次数会把这两种完全不同的行为压成同一个数字。

1. 基本量是同一位置的重复修改次数，粒度要落在符号区间而不是文件。一个大文件被改五次可能是五处互不相干的修改；同一个函数被改五次几乎一定是返工。把 diff hunk 用语法解析归属到符号上是这套度量的前提，也是它最主要的实现成本——没有这一步，整套指标的信噪比会低到不可用。
2. 震荡的判据可以做到纯机械：某个区间的内容哈希在会话中出现 A→B→A 的回摆。它不需要理解语义，因此可以在线检测并直接作为终止条件的输入信号，而不必等事后分析。
3. 收敛与否只能靠外部信号判断：每次返工之后，失败用例数是否单调下降、诊断条数是否减少。若某区间被反复修改而这两项毫无改善，结论通常不是模型能力不足，而是这段代码没有可跑的验证手段，Agent 缺少能推动它前进的反馈——修复方向是补测试而不是换模型。
4. 触发源要分三类：由新到达的测试失败触发是合理的；由 review 意见触发也合理，但说明前置检查不够；由模型自己重读后改主意触发最可疑，往往是上下文丢失或压缩的后果。三者对应的改进分别是保持现状、加强提交前检查、修上下文管理，混在一起看就只能得出「返工太多」这种无从下手的结论。

把返工压到零是错误目标——那会让 Agent 不敢根据反馈修正自己。衡量它的是符号级重复修改次数分布、内容回摆的发生率、返工后失败用例数的变化方向，以及按触发源分类的返工占比。

**相关知识点：** 符号级 diff 归属、内容哈希回摆、code churn、收敛判据、返工触发源、终止条件信号。

### 9. 最终 diff 与中间编辑序列都要留吗？各自回答什么问题？

两份都要留，但**读者、问题与留存期限完全不同**：最终 diff 是给人和评测系统看的结论，长期保留；中间序列是给排障用的过程，价值随时间衰减极快，用同一套策略管理必然一头浪费、另一头缺数据。

1. 最终 diff 回答「这次会话交付了什么、值不值得合并」。它是评测样本与训练数据的载体，也是唯一能与 CI 结论、review 结果对齐的对象。保存形式应是相对基线提交的差异而不是全量文件内容——前者可以复用仓库已有的对象，后者在多轮会话里会迅速膨胀。
2. 中间序列回答「为什么走到了这个结果」。有几类问题只有它能答：这一行是第几轮引入的、引入时依据的是什么、中间是否曾经正确过又被改坏。这类调查基本发生在事故后的几天内，之后几乎不再被查询。
3. 两者不能互相推导，这是最容易被想当然的地方。最终 diff 无法还原过程；反过来把中间编辑逐条叠加也未必等于最终 diff——中间有回滚、有被覆盖的写入、有绕过编辑工具的操作，比如切分支或直接检出单个文件。假设「序列可折叠成 diff」会在这些场景静默出错，而且不会报错。
4. 因此中间序列必须与仓库状态锚点交替记录，而不只记编辑动作：每次写盘后记一次工作树哈希，任何一段序列都能被验证是否与后续状态一致。这条校验是发现「有操作没被工具记录到」的唯一手段。
5. 留存策略按事件驱动而非固定周期：中间序列默认短期保存，但失败会话、被回滚的 PR、触发过安全告警的会话，其序列跟随事件延长保留，因为它们正是事后一定会被翻的那批。

可采集的指标包括最终 diff 与实际合入内容的一致率、中间序列的调查使用频率、序列折叠后与最终 diff 的偏差率。使用频率长期偏低是缩短留存期的直接依据，而偏差率上升说明有写入路径没被埋点覆盖。

**相关知识点：** 基线提交相对 diff、工作树状态锚点、中间编辑序列、留存分层、事件驱动延长留存、序列折叠一致性。

### 10. 如何把一个有问题的 PR 归因到会话中的某一步？

入口是**出问题的那几行代码，不是会话的时间线**。从头翻一遍会话在长任务里成本高且容易被无关细节带偏；正确顺序是先用 blame 把行定位到引入它的那次修改，再沿证据链向上回溯。

1. 需要一层从「最终文件的行」到「中间编辑事件」的映射，而 `git blame` 给不到这个粒度——一次会话常常只产出一两个提交，blame 只能停在提交级。要在编辑事件里保存 hunk 的行区间，并在后续编辑发生时维护行号偏移，才能把最终的某一行回溯到具体那一步。这层映射是整套归因里唯一需要额外投入的部分，也是决定归因能不能做的分水岭。
2. 定位到编辑步之后要连问三件事：这一步依据的证据是什么、这一步之后有没有验证（跑没跑测试、测试有没有覆盖到这几行）、这一步是否被后续步骤覆盖过。第三问经常被忽略，而「改对了又被后面改坏」是相当高频的形态。
3. 必须区分**引入点与根因**。一段错误代码可能源于读到的是过时文件，也可能源于工单本身就写错了需求。停在「第十二轮改错了」是没有改进价值的结论，必须继续追问那一轮为什么会那样改，否则归因只是换了个说法复述现象。
4. 边界要说清楚：人在 Agent 产出之上又改过时，责任只能靠行的 blame 来源区分；如果 PR 以 squash 方式合入成单个提交，行级归属信息在合并那一刻就丢了，此时只能退回会话级归因。
5. 归因的产出不应止于定位。把「问题行 → 编辑步 → 缺失的验证」这条链沉淀成一条规则，比如某类文件的修改必须伴随某类测试，比单次定位有价值得多，也是唯一能让同类问题不再发生的动作。

可采集的指标是问题行能定位到具体编辑步的比例、从告警到定位的耗时，以及归因结论落在「证据缺失」与「验证缺失」两类上的占比——后者的分布直接指出该补哪一侧的能力。

**相关知识点：** `git blame`、行号偏移映射、hunk 行区间、引入点与根因、squash 合并的行级归属丢失、归因规则沉淀。

### 11. 上下文构建过程该记录什么？窗口占用如何可视化？

该记的不是最终 Prompt 长什么样，而是**每个上下文条目的来源、体积、入选原因，以及被淘汰的候选**。只留最终结果，就永远回答不了那个最常见的问题：该看的文件为什么没进去。

1. 每个条目记五项：来源类型（系统指令、仓库规范文件、检索命中、显式打开的文件、工具返回、历史消息、压缩摘要）、来源标识（路径加区间，或工具调用标识）、Token 数、在装配顺序中的位置、入选或淘汰的原因（预算不足、相关性分数偏低、去重命中）。位置这一项看似冗余，但它决定了缓存前缀能否稳定。
2. 被淘汰的候选比入选的更有诊断价值，全量记正文却太贵。折中是只记淘汰候选的标识与分数、不记正文——这样「文件其实检索到了、只是被预算挤掉」这个高频故障才能被发现，而它在只看最终上下文的视角里完全不可见。
3. 可视化的第一张图是按来源类型的窗口占用堆叠，横轴是轮次。它直接暴露两种常见病态：历史消息随轮次线性膨胀、持续挤压证据空间；系统指令与仓库规范文件占比过高，在长会话里一直消耗预算却只在开头有用。
4. 第二张图是缓存前缀边界的位置。prompt caching 依赖前缀逐字稳定，如果每轮都在靠前的位置插入变动内容，命中率会崩。把「从第几个 Token 开始与上一轮不同」画出来，比盯命中率数字更容易定位是哪个组件破坏了前缀。
5. 不要把这套可视化当成 Token 的精确账本。tokenizer 差异、工具定义的序列化方式都会让本地统计与计费值有偏差，当趋势和占比看是可靠的，拿去对账则会长期对不上且无人能解释差在哪。

窗口占用的目标不是压到最小，而是让证据类条目在预算中的占比保持稳定。可采集的指标包括各来源类型的窗口占比及其轮次趋势、被预算淘汰的候选数、缓存前缀的稳定长度与命中率。

**相关知识点：** 上下文条目来源、淘汰候选记录、窗口占用堆叠、prompt caching 前缀、缓存命中率、tokenizer 偏差。

### 12. 检索质量在线上如何观测？没有标注数据怎么办？

线上确实没有标注，但**结果本身就是延迟到达的标签**：一次会话最终修改过的文件集合，就是一份不需要任何人工投入的事后相关性判定，用它算召回率是可行的，前提是清楚它偏在哪。

1. 主口径是以最终改动的文件集合为相关集，统计检索结果的前 K 个是否覆盖了它们。这是弱标签而非真标签：它只包含「被改的」，不包含「看了之后确认不用改的」，而后者同样是有效检索，会被系统性低估。用它做趋势对比是稳的，用它做绝对水平的判断则会偏低。
2. 第二类信号来自 Agent 的使用行为，形成一条漏斗：检索返回 → 被实际读取 → 被引用为编辑证据 → 所在文件被修改。每一级的转化率指向不同问题——返回到读取偏低说明结果摘要不足以判断相关性，读取到引用偏低说明检索精度差，两者的修复完全不在一处。
3. 反事实探针是唯一能给出因果结论的方法：对小比例流量做交换，把某个候选移出上下文或换成对照，看任务成功率是否变化。代价很实在，它会牺牲这部分流量的成功率，因此比例必须小，且不能用在高风险仓库或对外交付的任务上。
4. 弱标签最大的风险是**幸存者偏差**：只有走到产出 diff 的会话才有标签，而中途放弃的会话恰恰可能是检索失败最严重的一批。必须单独统计无产出会话的检索行为，把它们的缺失当成一个独立指标，而不是从分母里悄悄去掉——去掉之后指标会随着失败率上升反而变好看。
5. 人工标注不是不要，而是要花在小而稳定的集合上：一批有代表性的查询做一次高质量标注，长期作为回归基线。线上弱标签负责发现漂移，标注集负责判断漂移的方向，两者缺一个都会在版本变更时给不出结论。

可采集的指标是以最终改动文件为相关集的 Top-K 召回率、漏斗各级转化率、无产出会话占比，以及反事实实验中的成功率差值。

**相关知识点：** 弱标签、事后 ground truth、Top-K 召回率、检索使用漏斗、反事实探针、幸存者偏差、回归标注集。

### 13. 如何识别「读了大量无关文件」这类上下文浪费？

先把「无关」定义清楚，否则度量必然指错方向——**没被改不等于无关**。读了一个文件后确认它不需要改，这是排除性证据，是有效工作；把它算成浪费，等于把 Agent 优化成不敢核实。

1. 分三档而不是二分：被读且被引用为编辑证据（有效）、被读且明确得出「不需要改」的结论（排除性，有效但成本可优化）、被读之后在整个会话里再未被提及（疑似浪费）。只有第三档是度量目标，前两档要能被识别出来并从分子里排除。
2. 浪费的单位是 Token 而不是文件数。读一个三十行的配置文件和读一个三千行的实现文件，浪费程度差两个数量级。指标应定义为疑似浪费条目占本轮上下文 Token 的比例，按文件个数统计会把小文件的噪声放大到与真正的问题同一量级。
3. 最大的浪费来源往往不是选错文件，而是**读得太整**：只需要一个函数却拉进整个文件。观测必须能区分「文件选错」与「区间选大」，两者的修复手段不同——前者改检索策略，后者改读取工具的默认行为，让它按符号区间返回而不是整文件。
4. 浪费率与成功率的关系不是单调的。适度冗余能提高鲁棒性，把浪费压到零通常伴随成功率下降。所以这个指标必须与成功率联合观察，目标是找拐点而不是取最小值；单独给浪费率定 KPI 会直接导致质量回退。
5. 归因要看是谁塞进来的：检索自动召回、模型主动读取、工具返回体过大。第三类最容易被忽略——一次搜索返回上千行、一次目录列举展开了整棵树，单次占比常常是最大的一项，而它既不是检索的锅也不是模型的锅。

可采集的指标包括疑似浪费 Token 占比、按注入来源分类的构成、读取区间大小的分布，以及浪费率与成功率的联合曲线。曲线的拐点位置才是这套度量真正要交付的结论。

**相关知识点：** 排除性证据、疑似浪费 Token 占比、符号区间读取、注入来源归类、冗余与鲁棒性权衡。

### 14. 上下文压缩发生时该记录什么，才能事后判断压丢了什么？

压缩是**有损且不可逆**的，所以记录的目标不可能是保留正文——那就等于没压。目标是留一份可校验的丢失清单：哪些条目被丢弃、哪些被摘要、摘要后还剩多少。

1. 触发侧要记原因、压缩前后的 Token 数、发生在第几轮。原因这一项最常被省略，但「每次都是逼近窗口上限被动触发」和「按策略提前触发」对应完全不同的调优方向，前者说明预算规划失效，后者说明策略阈值可调。
2. 条目侧记每个被处理条目的去向三态：保留原文、被摘要（附摘要后的 Token 数与压缩比）、被完全丢弃。被丢弃的条目至少要留标识——路径加区间，或工具调用标识。事后最常问的是「那条关键报错是不是被压掉了」，回答它只需要标识，不需要正文，这让记录成本降到可接受。
3. 判断「压丢了什么」真正靠的是后续行为反证：压缩之后 Agent 是否立刻重读了刚被丢弃的文件、是否引用了已不在上下文中的证据标识、是否重复了压缩前已经做过的探索。这三个信号比压缩比本身有用得多，因为压缩比只描述省了多少，不描述省错了什么。
4. 摘要由模型生成，会引入事实错误，而这个错误会被后续所有推理继承且无法察觉。因此摘要要保留生成它的模型标识与提示版本，出问题时才能判断责任在压缩策略还是主链路——否则这类错误会被长期归因到主模型身上。
5. 高价值条目应有豁免清单，并且**豁免结果要显式记录**：用户的原始指令、当前失败的测试输出、正在编辑文件的当前内容。清单里的东西仍然被压掉，本身就该告警，因为这说明豁免规则在某条路径上没生效。

可采集的指标是压缩后的立即重读率、悬空证据引用率、压缩前后的任务成功率差，以及按去向三态统计的条目分布。这几项一起看，才能判断压缩策略是省了成本还是在偷偷损害质量。

**相关知识点：** 压缩触发原因、去向三态、压缩比、悬空证据引用、压缩后重读率、豁免清单、摘要模型标识。

### 15. 如何从 Trace 中识别反复读取同一批文件的低效循环？

判据不是重复次数，而是**两次重复之间有没有发生状态变化**。同一批文件被读三次，如果每次之间都有编辑落盘或新的测试结果到达，那是正常的验证循环；如果之间只有模型输出，就是空转。

1. 把读取序列按文件集合做成签名，用路径集合的哈希在会话内检测重复。用集合签名而不是单个文件，是因为病态循环的特征是整批一起重来；按单文件统计会把正常的反复查看同一个入口文件也算进去。
2. 在两次相同签名之间插入进展检查：这段区间内是否有写盘、是否有新的测试或诊断结果到达、工作树哈希是否变化。三项全否才判定为无进展重复。这是纯机械判定，不需要模型参与，因此可以在线执行而不只是事后分析。
3. 必须排除三种合法重读，否则误报率会高到没人看：上下文压缩之后的重建（应与压缩事件在时间上相邻）、文件被自己改过后的复核（工作树哈希已变）、并行子任务各自读了同一批文件（分属不同 Span 子树）。这三项排除是整个检测能否落地的关键，比检测逻辑本身更需要投入。
4. 检测结果的首要用途是**在线终止**而不是事后统计。这类循环会以线性速度消耗成本且几乎不可能自愈，达到阈值时应触发换策略或交还控制权；事后分析的价值在于校准阈值，而阈值不能全局统一——大型仓库的探索阶段本来就需要多次回看，按仓库和任务类型分别校准才不会顾此失彼。

要注意这套检测只能发现「重复读取」这一种低效形态，反复运行同一条失败命令、反复生成等价补丁属于同类问题但需要各自的签名定义。可采集的指标是无进展重复的发生率与每次消耗的 Token、触发终止后的任务成功率对比，以及人工复核判定为合法重读的误报率。

**相关知识点：** 读取签名、进展检查、工作树哈希变化、无进展重复、在线终止条件、按仓库校准阈值。

### 16. Token 与缓存命中如何埋点才能定位成本异常？

只记总 Token 数定位不了任何异常。必须**按四类分开计量**——未缓存输入、缓存写入、缓存读取、输出。它们单价不同，且各自由完全不同的原因驱动，混成一个数只能告诉你贵了，不能告诉你为什么。

1. 四类的驱动因素互不相同：未缓存输入由上下文中的变动部分决定，缓存写入由前缀被打破的次数决定，缓存读取大致随轮次线性增长，输出由任务的产出量决定。一个成本尖峰只要看四类占比的变化，就能把范围缩小到某一环，这是分类计量最直接的回报。
2. 缓存命中要按前缀边界记，而不是只记一个命中率。要记录本轮请求与上一轮的公共前缀长度、命中的 Token 数，以及是哪个上下文组件导致了前缀断裂——系统指令变了、工具定义变了、还是历史被压缩了。只有最后这一项能直接指向修复动作，命中率数字本身指不到任何人。
3. 埋点必须落在每一次模型请求上，并能向轮次、会话、仓库、团队四级上卷。只在会话级汇总就发现不了「某一轮突然吃掉半个窗口」这种最常见的异常形态，而这种形态在会话总量上可能只表现为一个不起眼的凸起。
4. 计费口径与本地统计必然有偏差，来自 tokenizer 差异、工具定义的序列化方式与服务端计费规则。埋点应把服务端返回的用量字段存为权威值，本地估算只用于请求前的预算控制。两者混用会让成本报表长期对不上账，而且随着时间推移越来越没人能说清差在哪。
5. 高基数要提前掐住：会话标识、文件路径不能进成本 Metric 的标签。成本明细走日志或宽表，Metric 只保留模型、仓库、任务类型、执行模式这类低基数维度，否则时序库的成本会先于模型成本失控。

可采集的指标是四类 Token 的占比与趋势、缓存命中率与前缀断裂次数、单轮 Token 的 P99，以及服务端用量与本地估算的偏差率。

**相关知识点：** Token 分类计量、prompt caching 前缀断裂、服务端用量字段、四级上卷、Metric Label 基数、预算控制。
<a id="gov-208"></a>
### 17. 编码任务的延迟该拆成哪些段？哪一段最值得优化？

拆段的唯一原则是**每段有独立的优化手段**，按这个原则切出来通常是六段；而最值得优化的那一段在多数团队里是验证等待——构建与测试，因为它常占一半以上，且与模型能力完全无关。

1. 六段覆盖从任务受理到产出可提交：环境与仓库准备、上下文构建（检索、读取、装配）、模型推理、工具执行（文件操作与命令）、验证等待（构建、测试、静态检查），以及各段之间的排队。排队必须单列，否则它会被摊进相邻段里，让优化打在错的位置。
2. 模型推理段要再分 TTFT 与输出生成两项，因为优化方向相反：TTFT 靠减少输入与命中缓存，输出耗时主要由输出长度决定，只能靠约束产出形态。把两者合成一个「模型耗时」，会得出「换个更快的模型」这种大概率无效的结论。
3. 验证段之所以通常最值得动，有三个理由：它的时长由测试套件决定，因此改进不会被模型迭代冲掉；它是串行阻塞的，Agent 必须等结果才能继续；可用手段成熟且确定——只跑受影响的测试、增量构建、编译与测试结果缓存。这三点凑齐的段并不多。
4. 但「最值得」要看**关键路径上的可压缩量**而不是绝对时长。某段耗时很长却能与其他段并行，比如提前启动依赖安装或预跑基线测试，它对端到端的贡献就远小于它的绝对值。先画关键路径再排优化顺序，否则很容易把力气花在一个本来就不阻塞的环节上。
5. 交互式与后台任务的答案不同：交互式场景里首次可见反馈的时间最重要，用户对总时长的容忍度反而更高；后台任务只看端到端，且可以用并行换时间。同一份分段数据要按执行模式分别排序，才不会得出互相矛盾的优化建议。

可采集的指标是各段耗时的 P50 与 P95 及其占比、关键路径上各段的贡献、验证段中可并行的比例，以及优化前后端到端 P95 的实际变化。

**相关知识点：** 延迟分段、排队时间单列、TTFT、受影响测试选择、增量构建、构建缓存、关键路径。
<a id="gov-209"></a>
### 18. 单次任务成本如何归因到具体步骤与工具？

难点不在记账而在**大量成本没有直接归属对象**：一个工具返回的长输出，其花费发生在之后每一次模型调用上，而不是这次工具调用上。只按 Span 直接汇总，最贵的东西反而看不见。

1. 直接成本是容易的：每次模型请求的用量按 Span 记录，沿 Span 树向上汇总到轮次与任务；沙箱算力按实例时长记。只要 Span 树建对了，这部分自动成立，不需要额外设计。
2. 间接成本才是重点。工具返回的内容会进入后续所有轮次的上下文，只要没被压缩掉就在每一轮被重复计费。要把这笔账算回产生它的工具头上，需要在上下文条目里保留来源工具调用标识，再把每轮该条目占用的 Token 摊回去。这是让「某个工具输出太长」变得可见的唯一办法，代价是要维护条目级的 Token 归属。
3. 摊派规则要提前定死并保持稳定。同一份数据既可以按「产生它的那一次调用」计，也可以按「每一次被使用」计，两种口径下同一个工具的排名可能完全相反。中途改口径会让历史数据不可比，而成本治理最需要的恰恰是跨版本的纵向对比。
4. 重试与失败步骤的成本必须单独可见，不能并进成功步骤。编辑失败触发的重读与重试往往是成本长尾的主要来源，藏进总数里就永远不会被优化——它在均值上几乎不可见，只在分位数尾部露头。

归因的产出应该是一张排序过的贡献榜，说明哪个工具、哪一步、哪个文件贡献了最多 Token，而不是精确到分的账单；精度要求过高会让实现复杂度暴涨，而决策实际只需要排序。可采集的指标包括按工具与步骤的 Token 贡献排名、间接成本占比、失败与重试成本占比，以及单位成功产出的成本。

**相关知识点：** Span 树成本汇总、间接 Token 成本、条目级 Token 归属、摊派口径稳定性、成本长尾、贡献排名。
<a id="gov-210"></a>
### 19. 模型侧的 TTFT、输出速率与工具等待如何分别观测？

这三项在流式响应里是**交错发生的**，不分开埋点就会互相污染。最典型的错误是把工具执行时间算进模型输出时间，于是得到「模型变慢了」这个既错误又难以证伪的结论。

1. TTFT 的测量起点要选对，而且两个起点都要记。从发出请求起算包含网络与网关排队，从服务端开始处理起算才是模型的真实首 Token 时间。两者的差就是接入层开销，它在高并发时会成为主要矛盾，而这个矛盾与模型无关，混在一个指标里就会一直被误判。
2. 输出速率不能用总输出 Token 除以总耗时。流式响应中途会因工具调用而中断，中间还可能在思考内容与正式输出之间切换。正确做法是在流上给每个片段打时间戳，只统计相邻输出片段之间的间隔，并剔除因工具执行而暂停的区间。
3. 工具等待要按「在等谁」分类：等本地文件操作是毫秒级，等命令执行是秒到分钟，等外部服务不可控，等人审批可能是小时级。全部混进一个「工具耗时」，P95 会被审批等待完全主导，而那根本不是性能问题，优化它也没有任何技术抓手。
4. 一轮内的并行工具调用要同时记各自耗时与整体墙钟时间。只记总和看不出并行度，只记各自耗时又算不出真实等待；两者的差正是并行带来的收益，也是判断该不该继续加并行度的唯一依据。
5. 长会话中这三项都会自然漂移——上下文越长 TTFT 越高，这是可预期的物理现象。必须把 TTFT 与输入 Token 数放在一起看，否则「上下文变长」会被反复误报成「模型变慢」，而每次排查都查不出问题。

可采集的指标是分起点的 TTFT P95、剔除工具暂停后的输出速率、按等待对象分类的工具耗时分布、并行带来的墙钟收益，以及 TTFT 对输入长度的回归关系。最后一项是判断漂移是否正常的基线。

**相关知识点：** TTFT 测量起点、流式片段时间戳、思考内容与输出切换、工具等待分类、并行墙钟时间、输入长度与 TTFT 关系。
<a id="gov-211"></a>
### 20. 成本异常告警如何避免被正常的大任务误触发？

绝对阈值在这里必然失败——**同一平台上单次任务的成本可以差三个数量级**。可用的做法是对成本与产出的比值、以及成本的增长形态告警，而不是对成本本身告警。

1. 归一化的分母必须是事前可观测的量：任务涉及的文件数、仓库规模、任务类型、目标改动范围的估计。用事后才知道的量做分母（比如最终 diff 的行数），告警就只能在任务结束后触发，止损的意义随之消失。
2. 形态比总量更能区分正常与异常。正常的大任务成本随轮次近似线性增长，且伴随净变更持续增加；病态循环的特征是成本继续涨而净变更停滞。把「每单位成本带来的净变更」做成滑动窗口指标，比任何总额阈值都稳健，而且它对任务规模天然不敏感。
3. 分层设置两类规则：会话级设硬上限用于止损，超限即暂停并要求人工确认；队列级看聚合趋势用于发现系统性回归，比如一次提示词变更让所有任务的成本整体上浮。两者的观察窗口相差一个量级，混用会同时得到误报和漏报。
4. 基线必须按仓库与任务类型分组，并随版本变更重置。模型换代、提示词改版、检索策略调整都会整体抬高或压低成本，沿用旧基线会在发布后集中误报，几次之后告警就没人看了。把变更事件接进告警系统做静默或基线重算，是这类告警能长期存活的前提。

少数极端昂贵的任务是真实存在的，不该被当成异常抑制掉；更实用的是给它们单独的审批路径——超过某个量级需要显式授权，而不是先跑再告警。可采集的指标包括告警的确认率与误报率、按仓库归一化后的成本分布、单位净变更成本的时序，以及变更事件之后的告警密度变化。

**相关知识点：** 成本归一化分母、单位净变更成本、滑动窗口、会话级硬上限、基线按仓库分组、变更事件静默。
<a id="gov-212"></a>
### 21. 一次任务跨越 IDE、CI 与代码托管平台，如何端到端串联？

这三段之间**没有活的进程上下文可以传播**：CI 在几分钟后由另一套系统触发，托管平台的回调更是异步的。所以串联不能靠运行时头部直传，只能把标识写进代码制品本身，再在下游把它捞出来。

1. W3C Trace Context 在 IDE 到后端这一段完全适用，`traceparent` 可以直接注入并逐跳传播。但它到「提交代码」这一步就断了——下一段的触发者是 Git 推送事件而不是一次 HTTP 调用，没有任何头部可以携带。承认这个断点，比试图用长连接硬撑一条 Trace 更现实。
2. 跨越断点的载体只能是不可变的代码对象，这带来一个方向性约束：标识只能随代码向前流动，无法从 CI 反向注入回已经结束的会话进程。因此结果的回流必须设计成异步写入，而不是同步回调，链路两端的生命周期从一开始就不重叠。
3. CI 侧拿到标识后应新建一条 Trace，用 Span Link 指回会话 Trace，而不是把 CI 的 Span 强行挂进会话 Trace。理由是时间跨度差得太远——把几小时后的 Span 塞进一条早已结束的 Trace，会让这条 Trace 的采样决策、留存期与查询性能同时失效。
4. 因果关系天然是分叉与汇合的：一个会话可能触发多次 CI 运行（推送一次、修一次、重跑一次），一次 CI 运行也可能覆盖多个会话的提交。Link 的多对多语义可以自然表达这件事，父子关系则表达不了，硬用父子会逼出一个随意选定的「主」运行。

这条链路最容易缺的一环是结果回接——CI 结论、review 结论、合并与回滚事件写回会话的结果表。缺了它，所有会话级成功率就只能依赖会话内的自评，而自评恰恰是最不该信的那个信号。可采集的指标是跨段关联成功率、标识在 rebase 与 squash 之后的存活率，以及结果回接的延迟分布。

**相关知识点：** W3C Trace Context、`traceparent`、Span Link、异步回调、结果回接、多对多因果、Trace 边界切分。
<a id="gov-213"></a>
### 22. IDE 侧埋点有哪些限制？本地数据如何合规上报？

限制几乎全部源于一件事：**IDE 跑在用户自己的机器上**。这意味着网络随时会断、进程随时被杀、遥测随时可以被关掉，而采到的每一个字节都可能是未提交的源码或个人数据。

1. 技术限制有四条互相独立：插件与编辑器共享资源，同步埋点会直接表现为编辑卡顿；内存缓冲会随进程被杀而丢失，必须落盘且设上限；离线时长可以是几天，缓冲策略要按天而不是按分钟设计；用户机器的时钟不可信，事件排序只能按单调序号，时间戳要同时记本地时间与服务端接收时间。
2. 数据限制更严重：IDE 能看到的东西远超服务端——未提交的代码、私有仓库路径、其他项目的文件名。默认只应上报结构化的事件元数据，比如动作类型、文件扩展名、区间长度、耗时；源码正文必须有显式开关且默认关闭，把它做成默认开启的「可关闭」在多数合规框架下站不住。
3. 合规上报的实际做法是本地先脱敏再出网：路径做仓库相对化或哈希，凭证与密钥在离开进程前用模式匹配剔除。要清楚这道过滤一定有漏网，因此不能当作唯一防线，服务端仍需二次检测与可删除的存储设计。
4. 采样必须在本地做而不是服务端做。数据已经离开用户机器再丢弃，只节省了存储、完全不解决合规问题；而合规问题恰恰是这类埋点唯一的硬约束。
5. IDE 数据的分析价值有天然上限：它能可靠回答「用户采纳了多少建议、编辑了什么」，回答不了「这次改动最终有没有被合并」——那要靠托管侧的数据回接。把两边拼起来时要注意身份映射的口径差异，IDE 侧是本机用户，托管侧是账号，映射不准会让所有按人聚合的指标失真。

给用户可见的开关与「查看我上报了什么」的本地能力，在不少合规框架里是硬要求而非加分项。可采集的指标包括本地缓冲丢失率、上报延迟分布、遥测关闭率、密钥模式被拦截的次数，以及身份映射成功率。

**相关知识点：** 本地缓冲落盘、单调序号排序、结构化事件元数据、路径哈希、本地采样、遥测开关、身份映射。
<a id="gov-214"></a>
### 23. CI 中的构建与测试结果如何回接到 Agent 会话？

回接的价值不在于知道红了还是绿了，而在于**把失败精确到用例与代码行，再落到会话中的具体编辑步上**。只回一个状态码，Agent 拿不到任何可执行的信息，人也拿不到。

1. 结果必须来自结构化格式而不是解析控制台文本：测试用 JUnit XML 这类报告拿到用例名、耗时与失败断言，静态检查与安全扫描用 SARIF 拿到规则标识、文件、行区间与严重级别。解析日志文本的方案会在每次工具升级、每次输出格式微调时静默失效，而且失效时表现为「最近没有失败」，极难察觉。
2. 连接键用提交哈希，不能用分支名或时间窗。CI 运行针对的是一个具体提交，会话产出的也是具体提交，两者精确匹配；用分支名会在并发推送时把结果接到错误的会话上，得到的还是一个看起来正常的关联。
3. 回接是异步且可能多次的：同一个提交会被重跑，重跑结果不一致就意味着 flaky。所以结果表要允许同一键存在多条记录并全部保留，覆盖式更新会让不稳定测试永远无法被发现，而它恰恰是长期拖低成功率的主因之一。
4. 要把失败映射回编辑步：用失败用例覆盖到的文件行与本次会话的 diff 行求交集。交集为空是一个强信号——说明失败可能与本次改动无关，是先前就红的、环境问题或 flaky。这类失败不该计入会话的质量指标，否则成功率会被基线噪声长期压低，且压低的幅度还随仓库健康度波动。
5. 回接链路本身要可观测：有多少 CI 运行找不到对应会话、有多少会话等不到结果。后者常因分支被删或 PR 被关而永远悬空，需要超时清理，否则会话状态会无限停留在「等待验证」，把完成率算成永远不满。

可采集的指标是结果回接率与延迟、失败行与会话 diff 的交集命中率、同提交重跑的不一致率，以及悬空等待的会话数。

**相关知识点：** JUnit XML、SARIF、提交哈希连接键、多次重跑记录、flaky 检测、失败行与 diff 交集、悬空超时清理。
<a id="gov-215"></a>
### 24. 子 Agent 与并行任务的 Trace 如何与主会话关联？

关联方式取决于一件事：**它们是否共享同一份工作区**。共享工作区的并行编辑必须落在同一条时间线上才能做写冲突归因；工作区隔离的探索型子 Agent 更适合独立 Trace 加 Span Link。

1. 共享工作区时，最关键的观测对象是「谁在什么时刻写了哪个区间」。两个子 Agent 先后写同一段代码时，后写的会静默覆盖前者，而从各自的视角看都成功了，任何单侧的日志都发现不了。只有把写入事件与工作树哈希的变化序列放在同一条时间线上比对，覆盖才会显形。
2. 工作区隔离时（各自的 worktree 或各自的沙箱），子任务生命周期独立、时间跨度可能很长，塞进一条 Trace 会造成超长 Trace 并让采样与留存策略失效。独立 Trace 加 Link 回指主会话更合适，代价是查询要跨 Trace 拼装，需要在查询层做一层封装，否则排障体验会明显变差。
3. 无论哪种形态，**结果的合并点必须显式建 Span**。子 Agent 各自的结论如何被采纳、冲突如何裁决，是多 Agent 编码最容易出错的一环；没有合并 Span，事后只能看到主 Agent 突然改变方向，无法解释为什么。
4. 编码场景有个特有的传播坑：子 Agent 常在子进程或独立沙箱里运行，进程边界会丢掉内存中的上下文。必须把追踪上下文与会话标识一并注入环境变量或命令行参数，并在子进程侧显式恢复，否则子 Agent 的全部 Span 会成为孤儿，而且这种孤儿在主 Trace 上表现为「什么都没发生」。
5. 成本与配额也要沿这条关联汇总。子 Agent 是成本失控的高发区——派生数量可能不受限，每一个又都带着完整上下文。

可采集的指标是孤儿 Span 比例、写冲突的检出数、合并点 Span 的覆盖率，以及含子 Agent 的会话相对普通会话的成本倍数。

**相关知识点：** 共享工作区写冲突、独立 Trace 与 Span Link、合并点 Span、跨进程上下文注入、孤儿 Span、子 Agent 成本汇总。
<a id="gov-216"></a>
### 25. MCP Server 与外部工具的调用如何纳入同一链路？

难点不在追踪机制本身，而在**这些 Server 常常是你无权修改的第三方进程**。链路完整性因此不能建立在「对端会配合埋点」的假设上，必须由客户端侧的边界 Span 独立成立。

1. 最低保证是客户端侧的调用 Span：工具名、Server 标识、参数摘要与哈希、耗时、返回体大小、错误分类。即使对端完全不埋点，这一层也足以回答「是哪次外部调用拖慢或污染了会话」，而这正是绝大多数排障需要的粒度。
2. 上下文透传能做到什么程度取决于传输形态：基于 HTTP 的连接可以按 W3C Trace Context 注入 `traceparent`，做到调用级关联；本地标准输入输出形态没有 HTTP 头可用，退路是启动时用环境变量传一次会话级标识，或把上下文放进请求的元数据字段——后者要求两端事先约定，第三方 Server 未必实现。承认这个差别，比假装两种形态一致更有用。
3. 编码场景的特殊点在于**外部工具的返回体会变成上下文的一部分**。一个返回上千行的工具，其真正花费发生在后续每一轮模型调用上，而不是这一次调用的耗时里。所以这类 Span 必须记录返回体的 Token 数并接进成本归因，只记耗时会让最贵的工具看起来最便宜。
4. 返回内容同时是注入面。链路上要记录返回体是否经过过滤、过滤规则的版本、是否触发了拦截，这样事后发现异常行为时才能判断可疑内容是从哪一步进来的；不记这几项，注入排查就只能靠猜。

第三方 Server 的能力与行为会随版本变化，因此要记录工具清单的哈希与 schema 版本，否则「上周还好好的」这类问题无从查起。可采集的指标是外部调用的错误率与耗时分布、返回体 Token 在上下文中的占比、schema 版本变更与成功率变化的相关性，以及无法关联到会话的调用比例。

**相关知识点：** 客户端边界 Span、`traceparent` 注入、标准输入输出传输限制、返回体 Token 计量、工具清单哈希、注入过滤记录。

### 26. 会话回放要复现代码状态，如何绑定 Commit 与工作区快照？

绑定基线提交只完成了一半——**Agent 面对的是工作区而不是提交**。未提交的修改、未跟踪的文件、被忽略的本地配置都会影响它的行为，而这些东西不在任何提交里，只绑定提交的回放会稳定地偏离原始执行。

1. 已提交部分用完整的提交哈希绑定，不用分支名也不用短哈希——分支会移动，短哈希在大仓库上会碰撞。同时必须绑定子模块指向的具体提交与 Git LFS 的对象指针：它们在父仓库里只是引用，不携带内容，漏掉之后重建出来的是空壳。
2. 未提交部分需要独立的内容标识。Git 的对象模型本身就是内容寻址的，把当前工作区写成一棵树对象即可得到一个 tree 哈希，它是 Merkle 结构，天然支持逐目录比对差异并复用仓库里已有的对象，比打包整个目录省得多。
3. 被 `.gitignore` 排除的文件是最容易漏的一类：本地环境配置、构建产物、缓存目录。它们进不了树对象，却实实在在影响构建结果。要么显式列出并单独存哈希，要么在回放报告里声明这部分不保证一致——**默默忽略是三种选择里最坏的**，因为它会把不可复现伪装成可复现。
4. 还有几项与代码内容同等重要却常被漏：文件模式位、行尾符配置、文件系统的大小写敏感性、以及仓库的本地配置。它们在同构环境里毫无存在感，跨平台回放时却是首要故障源，且症状是「文件找不到」这种极具误导性的报错。
5. 快照要与时间轴对齐。一次会话中工作区会变化很多次，只存起始快照就无法从中途开始回放。实用做法是在每个轮次边界存一次树哈希，正文靠对象复用，增量成本很低而收益是任意断点可复现。

可采集的指标是快照的完整率（能否成功重建出可构建的工作区）、重建后与记录哈希的一致率，以及被明确声明为不保证一致的部分所占比例。

**相关知识点：** 提交完整哈希、tree 对象哈希、Merkle 结构、子模块指针、Git LFS 指针、`.gitignore` 排除项、文件模式位、行尾符配置。

### 27. 回放需要哪些不可变输入？哪些环节天然不可复现？

输入清单要按能否被固定分成两堆，而**清单一半的价值在于明确声明哪些固定不了**。把不可复现项默认当成可复现，结果是所有回放差异都被读成模型退化，团队会花大量时间追一个不存在的回归。

1. 能固定的输入分四类，且每一类都要用内容哈希而不是名称来固定：模型侧（模型标识、采样参数、系统指令与工具定义的哈希）、代码侧（提交与工作区状态）、检索侧（索引的快照标识与检索参数）、环境侧（容器镜像摘要、依赖锁文件哈希、运行时版本）。
2. 还有一类几乎总被漏掉：**会话依赖的外部可变引用**。工单正文、PR 评论、被读取的远端配置、文档页面，回放时可能早已改动。要么在会话进行中就把它们的内容快照下来，要么明确承认这部分不可复现，没有第三条路。
3. 天然不可复现的第一项是模型采样。即使参数完全相同，服务端的批处理、数值实现与路由差异都会带来不确定性，固定随机种子也不保证逐 Token 一致。因此回放的判等标准必须是行为等价——是否做了同类操作、是否达成同样的验证结果——而不是文本相同。
4. 第二项是并发与时序：并行工具的完成顺序、文件系统事件的到达顺序、超时是否触发，都依赖当时的机器负载。要复现这类问题只能记录当时的实际顺序并在回放时强制按记录调度，代价是它已经不再是自然重放，只能用来验证特定假设。
5. 第三项是外部世界：网络可达性、依赖解析结果、时间与时区、目标系统的当前状态。录制回放可以把它们变成确定的，但录制本身会掩盖「依赖源真的变了」这类真实问题。所以录制模式与真实模式要并存，各自回答不同的问题，不能用一种替代另一种。

可采集的指标包括输入清单的固定率、被标记为不可复现的环节占比、行为等价判定的通过率，以及录制模式与真实模式之间的结果差异率。

**相关知识点：** 内容哈希固定、索引快照标识、镜像摘要、依赖锁文件、采样非确定性、行为等价判等、并发顺序录制、录制回放。

### 28. 回放数据的存储成本如何控制？

编码场景的存储大头与通用链路完全不同：不是日志条数，而是**同一份文件内容在一个会话里被反复装进上下文、又被反复落盘**。所以去重的对象是文件内容，而不是事件记录。

1. 最大的一笔是上下文快照。若每轮都存一份完整的输入内容，一个几十轮的会话就把同一批文件存了几十遍。正确做法是每轮只存条目引用列表——路径、区间、内容哈希、装配顺序——正文按哈希在共享存储里存一份。这一步通常能把这类数据砍掉一个量级。
2. 第二笔是文件内容本身，而它有一个近乎免费的替代品：仓库里已经有的内容不必再存一遍，只存提交哈希与相对差异即可——前提是这些提交长期可达，分支被删或强推之后对象会被回收。真正需要独立存储的只有未提交的修改和被忽略的文件。很多实现直接存全量文件正文，白白浪费了 Git 已经做好的内容寻址与压缩。
3. 第三笔是命令输出——构建日志、测试输出、依赖安装日志，单次可以是几十兆。它们的价值高度集中在失败的那部分：成功的构建日志几乎从不被读。按结果分级留存，失败留全量、成功只留摘要与结构化报告，能砍掉绝大部分体量而几乎不损失可用性。
4. 留存期限应由「这条数据还能回答什么问题」决定，而不是由数据类型决定。中间过程数据的调查窗口通常是天级，而作为评测样本与结果标签的最终差异是月到年级。用同一个过期策略管理这两者，必然一头浪费、另一头在最需要时缺数据。
5. 存源码带来的不只是成本问题，还扩大了泄漏面并引入删除义务。有些数据的正确策略是**根本不采**，而不是采了再压缩——这个判断必须在设计阶段做，事后清理的代价高出一个数量级，而且往往已经无法完全撤销。

任何裁剪都要用抽样回放来验证是否砍过了头。可采集的指标是单会话存储字节数的分布、内容去重率、按数据类别的占比构成，以及抽样回放的成功率。

**相关知识点：** 内容寻址去重、条目引用列表、相对差异存储、按结果分级留存、分类留存期限、抽样回放验证。

### 29. 如何用回放定位「同样的输入这次却失败了」？

这句话里的「同样」几乎从来不成立。**定位的第一步不是回放，而是逐项比对两次运行的输入清单**——绝大多数案例在这一步就结束了，而这一步的成本接近零。

1. 机械比对的项要事先固定：模型标识与采样参数、系统指令与工具定义的哈希、检索索引版本、镜像摘要、依赖锁文件、基线提交与工作区树哈希、外部引用的内容。任何一项不同就先解释它，不要急着归因到模型。这一步不需要重跑，把它放在流程最前面能省掉大部分调查成本。
2. 清单全等时才进入执行轨迹比对，目标是找**首个分歧点**：两次运行从哪一步开始做了不同的事。要找的不是最后失败的那一步——失败点通常离根因很远，从它往回推会经过一长串无关细节。分歧的判定用行为等价，不是文本逐字相同。
3. 分歧点定位后做单变量固定：把该步之前的模型输出全部用录制值回放，只让分歧步真实调用，重复多次观察是否稳定复现。若多次采样中失败率明显低于百分之百，说明这是模型的随机性而非回归，两者的处理完全不同——前者要加约束或加验证，后者要回滚变更。
4. 要单独排除环境侧的非确定：测试本身 flaky、依赖解析拉到了新版本、外部服务当时不可用、并发导致顺序变化。这几项在编码任务里占比不低，且都会伪装成「模型变差了」。判据很干净——把模型输出完全固定后重跑，若仍然失败，那就与模型无关。
5. 结论要落成可回归的样本：把这次的输入清单与失败现象固化成一个回放用例进回归集。不做这一步，同一个问题会以不同表象反复出现，而每次都要从头查一遍。

可采集的指标包括输入差异检出率（有多少案例在第一步就得到解释）、首个分歧点的定位耗时、多次采样下的复现率，以及归因落在模型、环境、数据三类上的占比分布。

**相关知识点：** 输入清单机械比对、首个分歧点、行为等价、单变量固定、多次采样复现率、flaky 排除、回归用例固化。

### 30. 回放能力如何服务于评测集与训练数据构建？

线上会话能直接转成评测样本的比例，远比直觉低。**瓶颈不是数据量而是可自动判定的成功条件**——绝大多数会话没有留下这样的判据，回放能重建过程却给不出对错。

1. 最好的素材是带验证结果的失败到修复对：某次会话把红的测试改绿了，这天然构成一个带 fail-to-pass 判据的样本。筛选时两个方向都要验证——修改前测试确实失败、修改后确实通过。只验一边会混进本来就通过的样本，而这类样本会让评测分数虚高且很难被察觉。
2. 从会话到评测样本必须**剥离答案**：保留初始仓库状态、任务描述与验证脚本，去掉当时的编辑过程与最终差异。剥离不干净就是数据泄漏，模型在评测里能看到答案，分数会持续偏高而没有任何报错提示，往往到线上表现对不上时才被发现。
3. 训练数据的要求比评测更严：它需要过程而不只是结果，且过程中的错误步骤同样有价值，可以作为负样本或偏好数据。但一次成功的会话里包含大量与最终结果无关的探索，全量当正样本会把无效行为一起学进去，反而强化绕路。
4. 合规与所有权是硬约束而非附加项。线上会话里是真实的私有代码，转成评测集或训练数据涉及授权、去标识化与跨租户隔离。这一条决定了相当一部分数据根本不能用，因此可用性标记应在采集阶段就打好，留到构建阶段再筛的代价是重新走一遍全量数据。
5. 评测集会随时间失效：仓库继续演进，旧样本的环境可能已经无法重建、依赖已经下架。样本必须绑定完整的环境标识，并定期做可重建性巡检，否则会在某次评测时突然发现大批样本跑不起来，而此时无法判断是被测系统的问题还是样本的问题。

可采集的指标是可转化为样本的会话占比、样本的环境可重建率、fail-to-pass 双向验证的通过率，以及评测集定期巡检的失败率。

**相关知识点：** fail-to-pass、答案剥离、数据泄漏、过程数据与负样本、数据可用性标记、环境可重建性巡检。
