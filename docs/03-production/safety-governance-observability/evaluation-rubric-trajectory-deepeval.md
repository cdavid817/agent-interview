# 代码判定、G-Eval、Rubric、轨迹评估与 DeepEval

> 所属章节：[安全、治理与可观测性](README.md)｜本文件共 **28** 题。

<a id="gov-284"></a>
### 1. 什么是代码判定（基于规则的评估）？它和 LLM 评委有什么区别？

代码判定是**用确定性程序（规则、断言、测试）判断输出是否符合要求**；与 LLM 评委相比，它快速、廉价、可复现、无偏差，但只能覆盖可形式化的标准。

1. 输出为确定的通过/失败或数值，重复运行结果一致。
2. 适合格式、结构、事实可核对、执行结果可验证的场景。
3. 无法判断语义相关性、表达质量等主观维度，这些交给评委或人工。
4. 规则本身需要测试，避免过严误判或过松漏判。
5. 实践中优先代码判定，剩余部分再用评委，并统计两者覆盖的样本比例。

**相关知识点：** 代码判定、确定性评估、断言、可复现、规则测试、覆盖比例。
<a id="gov-285"></a>
### 2. 哪些评估任务适合用代码判定？

凡是**输出有明确形式或可执行验证**的任务都适合代码判定：格式校验、结构校验、精确/模糊匹配、数值比对、执行测试和业务状态检查。

1. 格式与结构：JSON 可解析、符合 Schema、必填字段存在、长度与语言限制。
2. 匹配：分类标签精确匹配、抽取字段与标准答案比对、正则匹配关键内容。
3. 执行：生成的代码通过单元测试、SQL 能执行且结果集正确、命令返回码正常。
4. 工具调用：调用了正确的工具、参数符合 Schema、调用顺序满足约束。
5. 业务状态：订单已创建、工单已关闭等通过查询系统状态验证，比模型自述更可靠。

**相关知识点：** JSON Schema 校验、精确匹配、正则匹配、单元测试、工具调用校验、业务状态验证。
<a id="gov-286"></a>
### 3. 什么是精确匹配和模糊匹配？各适合什么场景？

精确匹配要求**输出与标准答案完全一致**，适合封闭答案；模糊匹配允许**一定差异**（归一化、部分匹配、相似度阈值），适合表述可变但含义固定的答案。

1. 精确匹配：分类标签、数值、ID、选择题选项，先做大小写、空白、标点归一化。
2. 模糊匹配：包含关键词、编辑距离、Token 重叠率（F1）、Embedding 相似度超过阈值。
3. 模糊匹配的阈值需要用标注样本校准，过低会放过错误答案。
4. 数值与日期应解析后比较，而不是字符串比较；单位换算要处理。
5. 两者都无法处理"意思对但要点不同"的开放答案，需要要点清单或评委补充。

**相关知识点：** Exact Match、模糊匹配、归一化、编辑距离、Token F1、相似度阈值。
<a id="gov-287"></a>
### 4. 如何用单元测试来评估 Coding Agent 生成的代码？

用**预先编写或隐藏的测试用例在沙箱中运行 Agent 生成的代码**，以通过率作为主要指标，并辅以静态检查、复杂度与安全扫描。

1. 测试集：每个任务附带功能测试，包含正常路径与边界用例，Agent 看不到隐藏测试以防过拟合。
2. 沙箱：隔离执行环境，限制网络、时间与资源，防止破坏性操作。
3. 指标：pass@k、全部测试通过率、部分通过率、首次运行通过率。
4. 辅助检查：Lint、类型检查、依赖安全扫描、代码变更范围（是否改了无关文件）。
5. 防作弊：检查代码是否修改或跳过测试、硬编码答案，这类行为应判为失败。

**相关知识点：** 单元测试评估、隐藏测试、沙箱执行、pass@k、静态检查、防作弊。
<a id="gov-288"></a>
### 5. 代码判定的优点和局限分别是什么？

优点是**快、便宜、确定、可解释、可在 CI 中作为硬门禁**；局限是**只能评估可形式化的部分，规则维护成本高，容易被"形式对内容错"的输出骗过**。

1. 优点：毫秒级执行，无模型成本，结果稳定，失败原因明确。
2. 优点：适合作为门禁，规则失败即阻断，不需要人工复核。
3. 局限：语义、风格、有用性无法用规则表达。
4. 局限：规则过严会误伤合理变体，过松会漏判；规则随需求变化需要维护。
5. 局限：输出可能满足所有格式规则但内容错误，需与评委或业务验证结合。

**相关知识点：** 确定性、硬门禁、规则维护、形式正确内容错误、误判与漏判。
<a id="gov-289"></a>
### 6. 什么是混合评估？如何把代码判定和 LLM 评委结合使用？

混合评估是**先用代码判定过滤硬性要求，再用 LLM 评委评估语义质量，最后用人工校准与抽检**的分层策略，兼顾成本、覆盖与可靠性。

1. 第一层代码判定：格式、Schema、安全规则、可执行验证，失败直接判不通过。
2. 第二层评委：对通过硬性检查的样本评估相关性、完整性、忠实度。
3. 第三层人工：评委低置信或分歧样本、随机抽检，用于校准评委。
4. 分数合成：硬性维度一票否决，软性维度加权平均，权重按业务定。
5. 度量：各层覆盖比例、评委与人工一致率、整体评估成本。

**相关知识点：** 混合评估、分层策略、一票否决、加权合成、人工校准、评估成本。

### 7. 什么是 G-Eval？它的基本思想是什么？

G-Eval 是一种**基于大模型的评估框架**（Liu 等，2023），核心思想是让模型根据任务说明与评估标准**自动生成评估步骤**，按步骤打分，并用输出分数的 Token 概率加权得到更细粒度的分数。

1. 输入：任务介绍、评估标准（如连贯性 1～5 分的定义）、待评估文本及上下文。
2. 步骤生成：用 Chain-of-Thought 让模型先写出评估步骤，再依据步骤给分。
3. 打分：填表式输出 1～5 分，并对各分数的概率加权求期望。
4. 原论文在摘要与对话评估上与人工判断的相关性高于传统指标（ROUGE、BERTScore）。
5. DeepEval 等框架内置 G-Eval 实现，可自定义标准或评估步骤。

**相关知识点：** G-Eval、评估步骤生成、Chain-of-Thought、概率加权打分、人工相关性、DeepEval。
<a id="gov-291"></a>
### 8. G-Eval 是如何利用 Chain-of-Thought 自动生成评估步骤的？

G-Eval 把**任务介绍与评估标准作为 Prompt，让模型以 CoT 方式写出具体的检查步骤**，随后评估时把这些步骤附在 Prompt 中执行，使打分依据显式化。

1. 例如评估"连贯性"，模型可能生成：先读原文找主要观点，再检查摘要是否按逻辑组织，最后给 1～5 分。
2. 步骤只需生成一次，可复用于同一标准下的所有样本，成本低。
3. 步骤显式化减少了评委的随意性，也便于人工审核标准是否被正确理解。
4. 步骤质量依赖模型能力与标准描述的清晰度，模糊的标准会得到模糊的步骤。
5. 实践中可人工修订自动生成的步骤后固定下来，并用校准集验证一致率。

**相关知识点：** 自动评估步骤、Chain-of-Thought、标准显式化、步骤复用、人工修订。
<a id="gov-292"></a>
### 9. G-Eval 的打分为什么要用 Token 概率加权？这样做有什么好处？

直接让模型输出整数分数会**集中在少数值上且区分度低**，用各分数 Token 的输出概率加权求期望能得到连续分数，提高细粒度区分与人工相关性。

1. 模型倾向给 3 或 4 这样的"安全分"，导致大量样本得分相同。
2. 取 1～5 各分数的概率 p_i，最终分 = Σ p_i × i，得到如 3.7 这样的连续值。
3. 连续分数更适合排序、阈值调整与相关性分析。
4. 需要 API 提供 logprobs；无法获取时可多次采样取平均近似。
5. 加权分依旧是评委的主观估计，仍需与人工标注校准验证。

**相关知识点：** 概率加权、logprobs、期望分数、区分度、多次采样、人工校准。
<a id="gov-293"></a>
### 10. G-Eval 适合评估哪些类型的任务？

G-Eval 适合**开放式生成任务的多维质量评估**，如摘要、对话、改写、创意写作，也可用于 RAG 回答的相关性与连贯性评估。

1. 摘要：连贯性、一致性（忠实）、流畅性、相关性四个维度。
2. 对话：自然度、上下文一致性、参与度、知识运用。
3. 自定义标准：任何能用自然语言描述的维度，如"是否遵循品牌语气"。
4. 不适合：可用代码判定的格式与事实核对，或需要专业领域知识而模型不具备的任务。
5. 用于 Agent 时可评估最终回复质量，但过程正确性应结合轨迹评估与可验证指标。

**相关知识点：** 摘要评估、对话评估、自定义评估标准、开放式生成、轨迹评估补充。
<a id="gov-294"></a>
### 11. G-Eval 与普通 LLM-as-a-Judge 相比有什么改进和不足？

G-Eval 的改进在于**自动生成评估步骤和概率加权打分**，使评估更结构化、区分度更高；不足是仍继承 LLM 评委的偏差，且依赖 logprobs 与较强模型。

1. 改进：步骤显式化降低随意性，人工相关性在论文实验中优于直接打分。
2. 改进：概率加权得到连续分数，适合细粒度比较。
3. 不足：对 LLM 生成文本存在偏好（自我偏好），可能受长度与风格影响。
4. 不足：需要支持 logprobs 的模型接口，否则退化为多次采样。
5. 选择：需要多维细粒度评分时用 G-Eval，简单通过/失败判定用普通评委或规则更省成本。

**相关知识点：** G-Eval、评估步骤、概率加权、自我偏好、logprobs 依赖、成本权衡。
<a id="gov-295"></a>
### 12. 什么是 Rubric（评分量表）？为什么评估需要 Rubric？

Rubric 是**把评估标准拆成维度和等级、并为每个等级写明可观察描述的评分量表**；它让不同评委（人或模型）对"好"的理解一致，使分数可比、可解释。

1. 没有 Rubric 时，"回答质量 4 分"对每个评委含义不同，分数无法聚合。
2. Rubric 把抽象目标转成具体检查项，减少主观性并便于培训标注员。
3. 对 LLM 评委，Rubric 是 Prompt 的核心部分，直接决定评估一致率。
4. Rubric 也用于产品需求沟通：业务方以等级描述表达期望。
5. 效果验证指标：使用 Rubric 前后的评委间一致性（Kappa）变化。

**相关知识点：** Rubric、评估维度、等级描述、评委一致性、可解释评分、Kappa。
<a id="gov-296"></a>
### 13. 一个好的 Rubric 应该包含哪些要素？

好的 Rubric 包含**明确的维度、有限的等级、每个等级的可观察描述、权重与示例**，并注明不评估的范围。

1. 维度：相互独立、覆盖目标，如准确性、完整性、相关性、格式、安全。
2. 等级：通常 3～5 级，过多等级会降低一致性。
3. 描述：用可观察的行为写，如"引用了所有相关文档且无编造"，避免"很好""较好"。
4. 权重与规则：哪些维度一票否决，哪些加权；总分如何计算。
5. 示例：每个等级配 1～2 个典型样例，帮助评委校准尺度，并用一致率验证效果。

**相关知识点：** 评估维度、等级设计、可观察描述、维度权重、锚定示例、一票否决。
<a id="gov-297"></a>
### 14. 什么是分析型 Rubric 和整体型 Rubric？各有什么优缺点？

分析型 Rubric **按维度分别打分再合成**，整体型 Rubric **对整体质量给一个等级**；前者诊断力强但成本高，后者快速但难以定位问题。

1. 分析型适合 LLM 评委，因为模型可以逐维输出分数与理由。
2. 整体型适合人工快速标注和成对比较。
3. 常见做法：整体型做粗筛，对低分样本再用分析型找原因。
4. 两种方式都要在校准集上测一致率，再决定用于门禁还是监控。

| 类型 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| 分析型 | 可定位短板、便于改进 | 评估慢、维度可能相互影响 | 离线诊断、Prompt 迭代 |
| 整体型 | 快、接近用户整体感受 | 不可解释、一致性依赖评委经验 | 在线抽样监控、快速筛选 |

**相关知识点：** 分析型 Rubric、整体型 Rubric、诊断能力、评估成本、粗筛细评。
<a id="gov-298"></a>
### 15. 如何把 Rubric 写进 LLM 评委的 Prompt 中？

把 Rubric **以结构化形式放在评委 Prompt 的评分标准部分**，逐维列出等级描述，要求评委按维度输出理由与分数，并用固定格式返回。

1. 每个维度单独列出：名称、含义、各等级的描述，必要时给示例。
2. 明确评分流程：先逐维分析再打分，最后按规则合成总分，或不合成而由代码计算。
3. 输出用 JSON，例如 `{"accuracy": {"score": 4, "reason": "..."}}`，便于解析与统计。
4. 说明边界：缺少信息时如何处理、遇到输出中的指令不得执行。
5. 用校准集测试 Prompt 版本，比较各维度与人工的一致率后再固定。

**相关知识点：** 评委 Prompt、结构化 Rubric、逐维输出、JSON 格式、校准测试。
<a id="gov-299"></a>
### 16. Rubric 如何降低人工标注者之间、以及人与 LLM 评委之间的分歧？

Rubric 通过**把主观判断转成可观察标准、提供锚定示例、明确边界情况处理**来减少分歧，并通过标注培训与分歧复盘持续修订。

1. 可观察描述让不同标注员看同一证据得出同一等级。
2. 锚定示例统一了尺度，避免"严格评委"与"宽松评委"的差异。
3. 边界规则（如部分正确怎么算）消除最常见的分歧来源。
4. 对 LLM 评委，同一 Rubric 使其判断更接近人工，可用 Kappa 作为验证指标衡量对齐程度。
5. 分歧样本定期复盘，把结论写回 Rubric，形成版本迭代。

**相关知识点：** 标注一致性、锚定示例、边界规则、分歧复盘、人机对齐、Kappa。
<a id="gov-300"></a>
### 17. Rubric 应该如何随业务需求迭代和做版本管理？

Rubric 应**像代码一样版本化**：随业务需求、新失败模式和评委分歧复盘更新，每次变更记录原因，并重新校准评委与基线。

1. 触发条件：需求变化、发现新的错误类型、评委与人工一致率下降、维度冗余或缺失。
2. 变更流程：提出修改、在校准集上试评、比较一致率等指标、评审后发布新版本。
3. 版本记录：版本号、变更内容、生效时间、影响的评估集与报告。
4. 兼容：Rubric 变更后历史分数不可直接比较，需要重跑基线或标注版本。
5. 与数据集、评委 Prompt 一起纳入配置管理，评估报告注明三者的版本。

**相关知识点：** Rubric 版本化、变更流程、重新校准、基线重跑、配置管理。
<a id="gov-301"></a>
### 18. 什么是轨迹（Trajectory）评估？它和只看最终输出的评估有什么区别？

轨迹评估是**评估 Agent 从输入到输出的完整执行过程**（规划、工具调用、中间结果），而不只是最终答案；它能发现"结果对但过程错"和"过程合理但结果错"的问题。

1. 只看输出无法区分靠猜对与靠正确流程得到的答案，前者在生产中不可复现。
2. 轨迹评估检查工具选择、参数、顺序、步数、是否遵守约束和是否使用了证据。
3. 数据来源是 Trace 或框架记录的事件流，需要结构化存储。
4. 判定方式包括与参考轨迹匹配、规则检查和评委对过程合理性打分。
5. 指标：工具正确率、步数分布、冗余率、约束违反率，与最终正确率一起报告。

**相关知识点：** 轨迹评估、过程质量、参考轨迹、工具正确率、约束违反率、Trace 数据源。
<a id="gov-302"></a>
### 19. 一条 Agent 轨迹通常包含哪些内容？

一条轨迹通常包含**输入与初始状态、每一步的决策摘要、工具调用与返回、中间观察、状态迁移和最终输出**，并附带时间与成本信息。

1. 起点：用户输入、系统约束、可用工具、初始上下文。
2. 步骤：每步的类型（规划、LLM、工具、检索、验证）、决策摘要（而非隐藏思维链原文）、选择理由。
3. 工具：名称、参数、返回值摘要、状态、耗时、重试。
4. 状态：任务状态迁移、检查点、人工介入事件。
5. 终点：最终输出、验证结果、总步数、总 Token 与成本。

**相关知识点：** 轨迹结构、决策摘要、工具调用记录、状态迁移、检查点、Token 成本。
<a id="gov-303"></a>
### 20. 轨迹评估常见的判定方式有哪些？

常见方式有**精确匹配、有序子集匹配、无序集合匹配、单步匹配和评委打分**，严格程度依次递减，按任务是否允许多种合法路径选择。

1. 参数也要比较，工具对但参数错同样算失败。
2. 多条合法路径可提供多个参考轨迹，任一匹配即通过。
3. 报告时同时给出最终正确率与轨迹匹配率两项指标。

| 方式 | 要求 | 适用 |
|---|---|---|
| 精确匹配 | 工具序列与参考完全一致 | 流程固定的任务 |
| 有序匹配 | 参考序列按顺序出现，允许额外步骤 | 允许探索但顺序重要 |
| 集合匹配 | 调用了参考工具集合，不管顺序 | 顺序无关的信息收集 |
| 单步匹配 | 逐步比较每一步是否合理 | 细粒度诊断 |
| 评委打分 | 模型评估过程合理性 | 无参考轨迹的开放任务 |

**相关知识点：** 精确匹配、有序子集匹配、集合匹配、单步匹配、参考轨迹、轨迹匹配率。
<a id="gov-304"></a>
### 21. 如何评估 Agent 是否调用了正确的工具和正确的参数？

把**期望的工具调用（名称与参数）写入评估样本**，运行后从轨迹提取实际调用，逐一比较名称、参数值与顺序，并检查是否有多余或缺失的调用。

1. 期望定义：必须调用的工具、参数的精确值或约束（范围、正则、Schema）。
2. 提取：从 Trace 的 Tool Span 或框架事件中取出调用列表。
3. 比较：名称精确匹配；参数按类型比较，允许等价形式（日期格式、大小写）。
4. 指标：工具选择准确率、参数正确率、多余调用数、缺失调用数。
5. 用 Mock 工具返回固定结果，避免外部数据变化影响判定；DeepEval 的 Tool Correctness 等指标可直接使用。

**相关知识点：** 工具选择准确率、参数校验、Mock 工具、Tool Span、Tool Correctness、多余调用。
<a id="gov-305"></a>
### 22. 如何评估 Agent 的步数、冗余调用和死循环问题？

从轨迹统计**步数、重复调用、无效调用与循环模式**，与参考步数或预算比较，超出即扣分或判失败。

1. 步数：记录总步数与 LLM 调用次数，和参考轨迹或任务预算对比，设分布阈值（如 P95）。
2. 冗余：相同工具相同参数的重复调用、结果未被使用的调用。
3. 循环：连续 N 步重复相同动作、状态无变化、反复重规划。
4. 效率指标：单位成功任务的步数与 Token，作为版本对比维度。
5. 生产中这些指标也用于监控，超限触发自动终止与告警。

**相关知识点：** 步数预算、冗余调用率、循环检测、效率指标、自动终止、Token 成本。
<a id="gov-306"></a>
### 23. 什么是"结果正确但过程错误"？为什么这种情况也需要被评估出来？

指**最终输出恰好正确，但执行过程包含错误决策**，如调用了错误工具、编造了中间结果、忽略了约束；这类成功不可复现且隐藏风险，必须通过轨迹评估识别。

1. 典型情况：模型未调用工具而凭记忆回答、检索失败但答案碰巧正确、违反权限约束但结果无害。
2. 风险：换一个输入同样的过程就会失败；违反约束的行为在生产中可能造成安全事故。
3. 识别：对比参考轨迹、检查证据是否被使用、检查约束违反记录。
4. 评分：结果与过程分开打分，过程失败应影响总体判定。
5. 指标：过程失败但结果正确的比例，用于衡量系统的"侥幸率"。

**相关知识点：** 过程正确性、侥幸成功、证据使用检查、约束违反、分离打分。
<a id="gov-307"></a>
### 24. 如何从生产 Trace 中提取轨迹用于评估？

把生产 Trace 中的**Span 树按时间与父子关系转换为结构化的步骤序列**，补充输入输出引用与验证结果，经脱敏后形成评估样本。

1. 选择：按 TaskID 或 trace_id 取完整 Trace，优先失败、低分、高成本与人工接管的任务。
2. 转换：LLM Span → 模型步骤，Tool Span → 工具调用，检索 Span → 检索步骤，事件 → 状态迁移。
3. 补齐：从 Artifact 存储取回脱敏后的 Prompt、工具返回摘要与最终输出。
4. 标注：人工确认期望结果与期望轨迹，或标记为负样本。
5. 质量检查：断链、缺属性的 Trace 无法转换，需统计转换成功率并反推埋点缺陷。

**相关知识点：** Trace 转轨迹、Span 树、Artifact、脱敏、负样本、转换成功率。
<a id="gov-308"></a>
### 25. 什么是 DeepEval？它主要提供哪些能力？

DeepEval 是一个**开源的 LLM 应用评估框架**，提供测试用例与数据集抽象、数十种内置指标（含 RAG、对话、Agent 与安全类）、LLM 评委实现和 pytest 风格的运行方式，可选接入 Confident AI 平台。

1. 核心对象：LLMTestCase、ConversationalTestCase、EvaluationDataset、Golden。
2. 指标：Answer Relevancy、Faithfulness、Contextual Precision/Recall、Hallucination、Toxicity、Bias、Summarization、G-Eval、Tool Correctness、Task Completion 等。
3. 评委可选：默认使用 OpenAI 模型，也可配置其他厂商或本地模型。
4. 运行：`deepeval test run` 集成 pytest，或在代码中调用 evaluate()；支持并行与结果缓存。
5. 具体指标与 API 随版本变化，使用前以官方文档为准，并在评估报告中记录版本。

**相关知识点：** DeepEval、LLMTestCase、EvaluationDataset、内置指标、Confident AI、pytest 集成。
<a id="gov-309"></a>
### 26. DeepEval 中的 Test Case、Metric、Dataset 分别是什么概念？

Test Case 是**一条待评估样本**，Metric 是**一种评分逻辑**，Dataset 是**Test Case 的集合**；评估即对 Dataset 中每个 Test Case 应用一组 Metric 并汇总。

1. LLMTestCase 字段：input、actual_output、expected_output、context、retrieval_context、tools_called、expected_tools 等。
2. Metric 定义评估维度、阈值与评委模型，输出 score、success 与 reason；可自定义。
3. EvaluationDataset 由 Golden（未运行的期望样本）或 Test Case 组成，可从 CSV/JSON 加载或合成生成。
4. 运行时先用被测系统填充 actual_output，再逐条评估，得到通过率与各指标分布。
5. 三者对应"数据—标准—集合"的分离，便于复用同一数据集评估不同版本。

**相关知识点：** LLMTestCase、Metric、EvaluationDataset、Golden、阈值、通过率。
<a id="gov-310"></a>
### 27. DeepEval 内置了哪些常见指标？

内置指标可分为**RAG 类、生成质量类、安全类、对话类和 Agent 类**，多数以 LLM 评委实现并支持阈值判定。

1. G-Eval 可自定义标准与步骤，是最常用的通用指标。
2. Tool Correctness 基于期望工具列表做确定性比较，不依赖评委。
3. 指标名称与集合随版本更新，以官方文档为准，并在校准集上验证一致率后再使用。

| 类别 | 指标 |
|---|---|
| RAG | Answer Relevancy、Faithfulness、Contextual Precision、Contextual Recall、Contextual Relevancy |
| 生成质量 | G-Eval、Summarization、Hallucination、JSON Correctness |
| 安全 | Toxicity、Bias、PII Leakage（红队测试已拆分为独立的 DeepTeam 项目） |
| 对话 | Conversation Completeness、Role Adherence、Knowledge Retention |
| Agent | Tool Correctness、Task Completion、Argument Correctness |

**相关知识点：** Answer Relevancy、Faithfulness、Contextual Precision、Hallucination、Tool Correctness、G-Eval。
<a id="gov-311"></a>
### 28. DeepEval 如何与 pytest 集成，实现类似单元测试的评估流程？

DeepEval 把**每个 Test Case 当作一个 pytest 测试**：在测试函数中调用 assert_test(test_case, metrics)，用 `deepeval test run` 执行，指标低于阈值即测试失败，从而纳入 CI 门禁。

1. 编写 test_*.py：构造 LLMTestCase（调用被测系统得到 actual_output），指定 Metric 与阈值。
2. 用 @pytest.mark.parametrize 或 EvaluationDataset 迭代多条样本。
3. `deepeval test run test_file.py` 会并行执行、生成报告，可选上传 Confident AI 查看趋势。
4. 与 CI 结合：在流水线中运行，失败阻断合并；用缓存减少重复的评委调用。
5. 注意评估的非确定性：设置合理阈值、必要时重复运行，并记录评委模型版本。

**相关知识点：** assert_test、deepeval test run、pytest 参数化、CI 门禁、阈值、结果缓存。
