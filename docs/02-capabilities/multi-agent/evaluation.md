# 协作效果与评测

> 所属章节：[多 Agent 与协作](README.md)｜本文件共 **5** 题。

<a id="multi-031"></a>
### 1. 相比单体应用，Multi-Agent系统的可观测性（Observability）怎么设计？

Multi-Agent可观测性要在**Logs、Metrics、Traces**上增加任务语义、模型决策、跨Agent因果和成本质量信号，既定位故障，也解释路由、停滞与结果依据。

1. Trace表示用户目标，Span覆盖规划、路由、Agent、LLM、Tool、评审和汇聚；TaskID用于续跑，MessageID关联异步消息。同步与队列均传播W3C Trace Context。
2. 日志记录事件、状态迁移、错误、候选路由和策略决策；Prompt与输出保存脱敏摘要、哈希或受控引用，并执行访问控制与保留期。
3. 指标覆盖资源与队列、P95与错误率、Token与重试、任务完成率和单位成功成本，并按模型、Agent版本、租户和任务类型切片。
4. 错误、高延迟、高成本和高风险Trace全量保留；保存计划、状态和证据版本支持回放，模型重放须固定版本并标注非确定性。
5. 告警关注停滞、重试放大、路由漂移、成本突增和严重误执行。

| 维度 | 单体应用 | Multi-Agent系统 |
|---|---|---|
| 关联范围 | 进程或服务调用 | Agent、消息、Tool和任务 |
| 核心信号 | 时延、错误、资源 | 增加决策、Token、质量 |
| 回放 | 请求与日志 | 计划、状态、证据版本 |

**相关知识点：** OpenTelemetry、W3C Trace Context、Trace、Span、TaskID、语义约定、尾部采样、成本归因、执行回放。

### 2. 如何量化 Multi-Agent 相比单 Agent 的净收益？

**【核心思路】**
多 Agent 不是天然更好——它用**更高的成本、延迟和复杂度**换取**任务质量或覆盖范围**。量化净收益必须做**同任务集的对照实验**：固定评测集，分别用单 Agent 和多 Agent 跑，比较端到端成功率提升幅度与成本延迟增幅。核心判据：**质量增益是否超过协作开销**，否则应退回单 Agent。

**【深入拆解】**
- **对照设计**：同一批任务、同一底座模型，唯一变量是架构（单 vs 多），隔离出协作本身的贡献。
- **收益侧指标**：端到端任务成功率、复杂任务完成率、结果质量评分、覆盖的任务类型数。
- **成本侧指标**：总 Token 消耗（多 Agent 常是单 Agent 的数倍）、端到端 P95 延迟、失败率、运维复杂度。
- **净收益公式思路**：单位成功成本 = 总成本 / 成功任务数。若多 Agent 的单位成功成本更高且成功率提升有限，说明协作是负收益。
- **分任务档位看**：简单任务多 Agent 往往负收益，复杂任务才可能为正——应按任务复杂度分层评估，而非看总平均。

| 维度 | 单 Agent | Multi-Agent |
|---|---|---|
| 成功率 | 基线 | 复杂任务可能↑ |
| Token 成本 | 低 | 数倍增长 |
| P95 延迟 | 低 | 串行协作放大 |
| 单位成功成本 | 基线 | 需低于基线才划算 |

**验证指标：** 端到端任务成功率差值、单位成功成本、总 Token 消耗比、P95 延迟增幅和按复杂度分层的净收益。

**相关知识点：** A/B 实验、单位成功成本、任务成功率、Token 成本、复杂度分层、架构选型。

<a id="multi-036"></a>
### 3. 多 Agent 系统的评测集应该如何设计？

**【核心思路】**
单 Agent 评测只需"输入—输出"对，多 Agent 还要评**协作过程**：任务是否被正确拆分、是否分派给合适角色、Agent 间信息传递是否失真、冲突是否被正确消解。评测集要同时覆盖**结果正确性**和**过程合理性**，并刻意包含会触发协作失败的场景（角色歧义、信息冲突、依赖成环）。

**【深入拆解】**
- **分层评测**：结果层（最终产出对不对）+ 过程层（拆分/分派/传递/消解是否合理）+ 成本层（步数、Token、延迟）。
- **刻意构造协作压力样本**：任务边界模糊（考角色划分）、子任务结论冲突（考消解）、存在循环依赖（考检测）、某 Agent 失败（考容错）。
- **过程标注**：为样本标注"理想拆分方式"和"应由哪个角色处理"，用于评判分派准确率，而非只看最终答案。
- **避免只测 happy path**：多 Agent 的价值和风险都在异常路径，评测集必须有足够比例的失败注入样本。
- **与单 Agent 共用基线**：同一评测集也跑单 Agent，才能算出净收益（[MULTI-035](#multi-035)）。

| 评测层 | 关注 | 样本设计 |
|---|---|---|
| 结果层 | 最终正确性 | 标准答案对比 |
| 过程层 | 拆分/分派/消解 | 标注理想协作路径 |
| 异常层 | 容错/冲突 | 失败注入、结论冲突 |
| 成本层 | 步数/Token | 记录协作开销 |

**验证指标：** 任务分派准确率、拆分合理性评分、冲突消解正确率、异常样本通过率、评测集覆盖的协作失败模式数。

**相关知识点：** 评测集设计、分层评测、失败注入、任务分派、冲突消解、LLM-as-a-Judge。

<a id="multi-037"></a>
### 4. 如何判断某个 Agent 角色是否值得独立拆分？

**【核心思路】**
角色拆分不是越细越好——每多一个 Agent 就多一次模型调用、一次上下文传递、一处失败点。值得拆分的判据是：**该职责有独立的能力要求或独立的演进节奏**，且拆分后带来的质量增益超过通信开销。如果两个角色总是被同时调用、共享几乎全部上下文，说明它们本该是一个 Agent。

**【深入拆解】**
- **该拆的信号**：需要不同模型（如规划用大模型、执行用小模型）、需要不同权限边界、职责独立演进、可并行执行提升吞吐。
- **不该拆的信号**：两者总是顺序成对出现、上下文几乎全量传递、拆分后仅增加一次 LLM 调用却无质量提升。
- **通信开销评估**：每次跨 Agent 传递都要序列化上下文、可能信息失真、增加延迟——拆分收益必须覆盖这部分成本。
- **粒度过细的典型症状**：Agent 数量增长但任务成功率不变、Token 成本线性上升、调试链路变长难定位。
- **验证方法**：合并候选角色做对照实验，若成功率无明显下降则说明拆分无必要（[MULTI-035](#multi-035)）。

| 判据 | 该拆 | 不该拆 |
|---|---|---|
| 能力要求 | 需不同模型/权限 | 完全同质 |
| 调用模式 | 可并行/条件触发 | 总是顺序成对 |
| 上下文 | 只需局部信息 | 需全量传递 |
| 收益 | 质量或吞吐提升 | 仅增加调用次数 |

**验证指标：** 拆分前后任务成功率差值、跨 Agent 通信次数、单任务 Token 增幅、端到端延迟变化和故障定位耗时。

**相关知识点：** 角色设计、职责边界、通信开销、模型分工、架构选型、成本治理。

<a id="multi-038"></a>
### 5. 多 Agent 协作中如何归因某次失败是哪个环节导致的？

**【核心思路】**
多 Agent 失败的难点是**责任扩散**：最终结果错了，但可能错在拆分、分派、某个子 Agent 执行、信息传递失真，或汇聚环节。归因需要**全链路可追溯 + 分环节验证**：每个环节留下输入输出快照，失败后逐段回放比对，定位第一个偏离预期的节点。核心：**把"整体错了"细化到"哪一步开始错"**。

**【深入拆解】**
- **分环节留痕**：拆分结果、分派决策、每个 Agent 的输入输出、传递的消息、汇聚逻辑，全部记录（[MULTI-031](#multi-031)）。
- **首错定位**：沿链路正向比对每步实际输出与预期，第一个偏离点就是根因环节，而非追最后报错处。
- **区分错误类型**：拆分错（子任务本身不对）、分派错（给错角色）、执行错（角色做错）、传递错（信息失真/截断）、汇聚错（合并逻辑问题）。
- **可重放**：固定模型版本与随机种子后重放该链路，确认问题可复现而非偶发（[MULTI-031](#multi-031)）。
- **归因指标化**：统计各环节的错误占比，指导优化优先级——若 60% 失败来自分派，就该先修路由。

| 环节 | 典型错误 | 定位手段 |
|---|---|---|
| 拆分 | 子任务不合理 | 比对理想拆分 |
| 分派 | 给错角色 | 检查路由决策日志 |
| 执行 | 单 Agent 做错 | 单独重跑该 Agent |
| 传递 | 信息失真/截断 | 比对收发消息 |
| 汇聚 | 合并逻辑错 | 检查汇聚输入输出 |

**验证指标：** 失败归因准确率、平均归因耗时、各环节错误占比分布、问题可复现率和修复后回归通过率。

**相关知识点：** 全链路追踪、根因定位、执行回放、Trace、错误分类、可观测性。
