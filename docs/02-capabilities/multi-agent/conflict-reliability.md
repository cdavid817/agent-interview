### 1. 多子Agent输出信息冲突、结论不一致时，构建一套自动校验、权重打分、可信度排序、冲突消解机制（Agent高级）

应建立**“结构化主张—确定性校验—证据评分—相关性校正—分层仲裁—反馈校准”**的闭环。可信度不是模型自报概率，而是由可验证证据、来源质量和历史表现共同计算，并针对任务领域动态调整。

1. 将输出拆成原子主张，每条附来源、引用位置、时间戳、推理链摘要和不确定性。先执行Schema、数值范围、逻辑约束、时间一致性与权限校验；不通过硬规则的结果直接淘汰。
2. 评分可定义为`S=w1×来源权威性+w2×证据覆盖率+w3×历史校准准确率+w4×时效性+w5×跨源一致性−风险罚分`。权重按领域和任务风险配置，禁止把同一底层数据或同源模型的多个回答误当独立证据。
3. 排序前进行相关性与独立性修正，并校准概率；低风险事实可选择最高分，高同质样本可多数表决，连续值可稳健加权融合。若前两名分差小、证据冲突不可验证或操作风险高，应拒绝自动决策。
4. 裁决Agent只能基于证据包复核，不能脱离来源重新猜测；关键任务转人工。最终结果保存采用的主张、被拒绝项、分数分解和证据版本，事后以真实标签更新权重，但设置变化上限防反馈污染。

| 机制 | 适用条件 | 主要风险 |
|---|---|---|
| 多数表决 | 独立同质判断 | 共模错误 |
| 加权融合 | 专家能力不同 | 权重漂移 |
| 最高可信择优 | 权威源明确 | 单源故障 |
| 拒绝与人工仲裁 | 高风险或分差小 | 成本增加 |

**相关知识点：** 原子主张、证据图、概率校准、共模错误、可信度排序、加权融合、拒答门控、裁决Agent、反馈污染。

### 2. 心跳机制的超时阈值怎么设定？误判Agent"假死"怎么处理？

心跳阈值应依据**故障发现目标与网络分布动态设定**。系统要区分进程存活、能够接单和任务推进；心跳正常不代表Agent没有阻塞。

1. 设周期`H`，收集RTT、调度停顿和丢包，阈值取窗口高分位延迟加余量，连续丢失`K`次才进入Suspect。过短误报高，过长发现慢，应按SLO权衡。
2. 波动明显时用滑动窗口或Phi Accrual，把到达间隔转为怀疑度；不同地域和运行时使用独立基线。
3. Suspect先停止派发，通过独立通道探测、检查指标、查询任务与租约。Agent有响应但无进展应标记Stalled，并触发诊断；短暂网络分区可设置宽限期。
4. 确认失联后使租约过期并提升Fencing Token，再重派任务；旧Agent恢复后不能提交旧结果。依靠幂等键和检查点避免双执行。
5. 记录误报率、平均故障发现时间、恢复时间及二次探测成功率，持续校准阈值。

| 检测方式 | 优点 | 局限 |
|---|---|---|
| 固定超时 | 简单、可预测 | 难适应抖动 |
| 分位数自适应 | 贴合历史分布 | 窗口可能滞后 |
| Phi怀疑度 | 连续风险评分 | 参数与解释更复杂 |

**相关知识点：** 心跳、Failure Detector、Phi Accrual、Suspect、Stalled、租约、Fencing Token、故障发现时间、幂等恢复。

### 3. 多Agent之间如果出现循环依赖，怎么检测和避免？

循环依赖要在**设计期检查任务图、运行期检查调用链和等待图**。静态DAG无环不代表运行时不会相互委托或互等，还须限制调用方向、深度和等待时间。

1. 发布前将依赖建成有向图，用DFS、Tarjan强连通分量或Kahn拓扑排序检测；无法覆盖全部节点即拒绝，并输出循环路径。
2. 采用Supervisor→领域Agent→Tool的单向依赖，禁止下层反调上层；反馈通过事件返回，由上层决策。跨域调用经明确接口，避免隐式双向依赖。
3. 消息携带TaskID、调用链和深度。若接收方已在链中或任务指纹重复，应快速失败或重规划；同时限制深度、步骤、Token和Deadline。
4. 对资源等待维护Wait-for Graph。锁按固定顺序获取并设租约；发现环后按优先级、已完成成本和可补偿性选择牺牲者并补偿。
5. 事件驱动仍需幂等和去重，防止A触发B、B再触发A；监控阻断次数、调用深度和无进展轮数。

| 环类型 | 检测对象 | 主要处理 |
|---|---|---|
| 静态依赖环 | DAG | 发布前拒绝 |
| 动态调用环 | 调用链、指纹 | 快速失败与重规划 |
| 资源死锁 | Wait-for Graph | 取消牺牲者并补偿 |
| 事件反馈环 | 事件因果链 | 去重、预算、熔断 |

**相关知识点：** DFS、拓扑排序、Tarjan、强连通分量、Wait-for Graph、调用深度、任务指纹、死锁、租约、补偿。

### 4. 多Agent并发修改同一文件时如何解决冲突？

应**先降低共享写入，再用版本校验和三方合并**。多个Agent不能在同一工作树无约束写文件；应使用独立分支或工作区，由单一集成者合并。

1. Planner按目录、模块、符号或Owner划分范围，尽量修改不同文件；热点文件用租约串行。任务契约声明允许路径，运行时拒绝越界。
2. Agent基于固定Base Commit在独立branch/worktree生成最小Patch，携带Base SHA、文件哈希和意图。禁止整体覆盖或最后写入胜出。
3. 以共同Base执行三方合并。非重叠行自动合并；文本重叠、同一符号变化或重命名冲突交Merge Agent或人工。合并者须审查完整diff和调用关系。
4. 合并后运行格式化、编译、静态分析和测试，并校验各子任务验收条件；关键行为需增加回归测试。
5. 提交采用乐观锁：目标HEAD变化则Rebase并重验。高争用仓库用合并队列串行集成。

| 机制 | 并发度 | 适用场景 |
|---|---|---|
| 文件租约 | 低 | 热点文件、强串行 |
| 独立分支+三方合并 | 高 | 常规代码协作 |
| 模块分片 | 高 | 边界清晰的仓库 |
| 合并队列 | 中 | 受保护主分支 |

**历史别名：** `CC-069`。

**相关知识点：** Git worktree、Base SHA、最小Patch、三方合并、乐观锁、文件租约、合并队列、回归测试、代码Owner。
