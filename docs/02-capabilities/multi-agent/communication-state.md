### MULTI-003 · 多Agent通信和进度同步怎么做？（豆包一面）

> 稳定 ID：`MULTI-003`｜原题号：3

多Agent通信宜采用**“消息承载协作、状态库记录进度、事件传播变化”**的组合方案。消息负责传递任务和结果，权威状态库回答任务当前阶段；若把消息本身当状态，重复、丢失或乱序后便无法可靠恢复。

1. 统一消息信封，至少包含`message_id`、`task_id`、`correlation_id`、发送者、接收者、类型、Schema版本、时间戳和幂等键。大对象存入对象存储，消息只传URI、摘要与短期访问令牌。
2. 定向请求使用RPC或点对点队列；一对多通知使用发布订阅；多个Agent共同完善中间结果可使用黑板。通信方式只解决信息交换，授权、重试和一致性仍由运行时负责。
3. 进度以**持久化状态机**为权威源，例如`Created→Assigned→Running→Validating→Completed/Failed`。Agent通过带版本号的条件更新写入状态，并以本地事务加Outbox保证状态变化和通知事件一致。
4. Supervisor订阅事件获得低延迟更新，断线后按事件序号补拉；心跳与租约判断存活，超时重分派前先执行fencing，防止原Agent恢复后继续写入。

| 模式 | 适用关系 | 主要风险 |
|---|---|---|
| 点对点/RPC | 定向请求与结果 | 级联超时 |
| 发布订阅 | 一对多事件 | 重复、乱序 |
| 黑板 | 共享中间状态 | 并发覆盖、污染 |

**相关知识点：** 消息信封、A2A、发布订阅、黑板模式、状态机、Outbox、幂等消费、事件序号、心跳、租约、fencing、分布式追踪。

### MULTI-005 · A2A通信超时、子Agent服务宕机、工具调用雪崩场景下的熔断、降级、流量隔离、备用Agent兜底策略（Agent高级）

> 稳定 ID：`MULTI-005`｜原题号：5

应按**“入口削峰、资源隔离、依赖熔断、分级降级、备用接管”**建立纵深防线。雪崩并非单个Agent失败，而是慢调用占满执行槽、上游重试放大流量，最终拖垮健康依赖，因此首先保护系统容量。

1. 入口按租户、任务类型和优先级实施令牌桶限流、有界队列与负载丢弃；队列接近上限时返回可重试信号并背压。重试流量受独立**Retry Budget**约束，防止各层叠加重试。
2. 为每个子Agent和Tool设置独立线程池、连接池、信号量与并发配额，以舱壁模式限制故障半径；高风险、高成本任务进入独立工作池，避免侵占核心容量。
3. 熔断器根据错误率、超时率、慢调用比例和最小样本数开启；Open状态快速失败，等待后进入Half-Open，仅放少量探测请求，恢复时必须渐进放量。
4. 降级链预先验证为：等价备用Agent→较弱模型或简化Skill→缓存/部分结果→异步排队→人工接管。切换前校验能力、权限、数据地域和版本，并沿用同一幂等键。
5. 重点监控饱和度、排队时间、重试放大率、熔断状态与降级比例；状态未知的任务先查询或补偿。

| 机制 | 保护对象 | 触发依据 |
|---|---|---|
| 限流与背压 | 系统容量 | 队列、并发 |
| 舱壁隔离 | 健康依赖 | 资源池配额 |
| 熔断 | 故障依赖 | 错误率、慢调用 |
| 备用与降级 | 核心业务 | SLA、兼容性 |

**相关知识点：** 级联故障、Retry Budget、令牌桶、背压、舱壁模式、熔断状态机、负载丢弃、渐进恢复、备用Agent、幂等与补偿。

### MULTI-009 · 多个Agent返回的信息互相矛盾，你会设计怎样的处理逻辑；完整任务状态流转如何设计（Agent中级）

> 稳定 ID：`MULTI-009`｜原题号：9

应将**事实冲突处理**与**任务状态管理**分离：前者判断信息可信度，后者保证任务沿合法路径推进，禁止按语言流畅度选答案或以后写结果覆盖状态。

1. 输出先结构化为“主张—证据—来源—时间—置信度”，执行Schema、逻辑和时效校验。客观事实优先回查权威源或调用独立验证工具。
2. 有权威源时按来源等级和新鲜度；同质独立Agent可多数表决；异质Agent按历史准确率、证据质量和相关度加权。高影响且分差不足阈值时，转裁决Agent或人工确认。
3. 状态使用**有限状态机**：`Created→Planned→Assigned→Running→Validating→Completed`，异常进入`Retrying、WaitingApproval、Failed、Cancelled`。迁移须定义事件、前置条件、超时与补偿。
4. 状态存入权威数据库并使用CAS防并发覆盖；状态与事件通过事务加Outbox提交。恢复从检查点续跑，副作用节点依靠幂等键和补偿，决策关联TaskID与证据版本。

| 冲突场景 | 推荐机制 | 主要限制 |
|---|---|---|
| 权威事实不一致 | 回查原始权威源 | 来源可能过期 |
| 同质独立判断 | 多数表决 | 相关性错误会共振 |
| 异质专家判断 | 可信度加权 | 权重需持续校准 |
| 高风险僵局 | 人工或裁决Agent | 成本与时延增加 |

**相关知识点：** 证据溯源、可信度加权、多数表决、裁决Agent、有限状态机、CAS、Outbox、检查点、幂等与补偿。

### MULTI-011 · Multi-Agent 如何通信？

> 稳定 ID：`MULTI-011`｜原题号：11

Multi-Agent通信用于交换**任务、状态、证据和控制事件**，应按交互方向、实时性和一致性选择点对点、发布订阅或黑板，并以统一契约屏蔽传输差异。可靠执行仍依赖状态机、幂等和权限。

1. 同步RPC适合短请求响应，但受下游时延约束；异步队列适合长任务和削峰；发布订阅适合一对多广播；黑板适合围绕共享状态增量协作。
2. 消息包含MessageID、TaskID、CorrelationID、收发方、类型、Schema版本、幂等键、TraceContext和PayloadRef。载荷结构化并版本化，大文件只传受控引用。
3. 消费端按幂等键去重，状态使用版本号或CAS；业务写入与事件发布采用事务Outbox。乱序消息按序列号处理，过期事件拒绝或补偿。
4. 使用双向认证、短期令牌、消息签名、最小权限和租户隔离；透传TraceID并记录排队、重试和端到端时延。A2A规范跨组织交互，内部传输仍可使用队列。

| 模式 | 适合场景 | 主要代价 |
|---|---|---|
| RPC/点对点 | 定向短交互 | 耦合与级联超时 |
| 发布订阅 | 广播和事件驱动 | 乱序与重复 |
| 黑板 | 协同求解 | 并发争用与污染 |

**相关知识点：** RPC、消息队列、发布订阅、黑板、A2A、消息契约、Outbox、CAS、幂等、死信队列、TraceContext。

### MULTI-012 · 如何避免多个 Agent 死循环？

> 稳定 ID：`MULTI-012`｜原题号：12

避免多Agent死循环必须具备**设计期无环约束、运行时进展检测和硬性资源预算**。仅设置最大轮数无法识别Agent相互委托、措辞变化但状态不变的语义循环。

1. 规划阶段把Agent调用和任务依赖建模为有向图，使用拓扑排序或DFS检测静态环；架构上规定分层单向调用，禁止下层反向调用上层。确需回馈时通过事件返回状态，由Supervisor决定是否重规划。
2. 每次委托携带调用链、深度和任务指纹。指纹由目标、规范化输入、目标资源和关键状态构成；若相同Agent—任务组合再次出现，或调用深度超过阈值，应拒绝派发并记录循环路径。
3. 进展检测不能只看消息文本，而要检查已完成节点、未满足约束、外部状态或证据集合是否变化。连续若干轮无新增事实、无状态推进或相同错误重复出现，进入Stalled状态，只允许有限重规划。
4. 为任务设置最大步骤、墙钟时间、Token、费用、工具调用数和重试预算；预算由根任务向子任务分配，子Agent不得自行扩张。到达软阈值时降级或请求人工，到达硬阈值时取消并执行补偿。
5. 终止协议应区分成功、失败、等待输入和取消；超时后用租约与fencing阻止旧实例继续执行。

| 循环类型 | 检测信号 | 处理 |
|---|---|---|
| 调用环 | 调用链重复 | 阻断并重规划 |
| 状态环 | 指纹重复 | 去重或终止 |
| 语义停滞 | 多轮无进展 | 降级或人工介入 |

**相关知识点：** 有向图环检测、拓扑排序、任务指纹、进展函数、预算控制、终止协议、租约、fencing、补偿。

### MULTI-013 · Shared Memory 如何设计？

> 稳定 ID：`MULTI-013`｜原题号：13

共享内存应是**分层、版本化、最小可见且可追溯的状态服务**，而非无限增长的公共对话；既要共享必要事实，也要防并发覆盖、越权和过期信息污染。

1. 数据分为Agent私有、任务共享、团队共享和长期知识，每条记录包含Owner、TaskID、Schema、版本、来源、TTL和访问策略。状态使用KV或关系库，大对象存对象存储，向量索引只负责语义检索，不能充当权威源。
2. 写入采用事件或补丁。低冲突状态使用CAS/MVCC，高争用区使用短租约或事务，可交换集合采用CRDT。冲突须按字段定义合并、拒绝或仲裁，不能默认后写胜出。
3. 读取使用Snapshot或版本引用，确保推理看到一致视图；Agent只获取必要字段。外部内容标记来源并与指令隔离，写前校验Schema、权限和敏感信息。
4. 生命周期包括TTL、压缩、归档和删除。原始轨迹与稳定知识分离，只有验证事实进入长期层；读写记录审计事件和Trace。

| 并发方式 | 适用场景 | 主要代价 |
|---|---|---|
| CAS/MVCC | 低冲突读多写少 | 冲突重试 |
| 租约/事务 | 高争用关键状态 | 并发降低 |
| CRDT | 可合并分布式数据 | 语义受限 |

**相关知识点：** Shared Memory、黑板模式、MVCC、CAS、CRDT、Snapshot、命名空间、TTL、向量索引、数据血缘、提示注入隔离。

### MULTI-016 · Planner Agent和Executor Agent如何协作？

> 稳定 ID：`MULTI-016`｜原题号：16

Planner与Executor通过**版本化计划、结构化回执和受限重规划**形成闭环：Planner分解目标，Executor可靠执行步骤；二者共享事实状态但不越权，以确定性运行时控制副作用。

1. Planner读取目标、约束和状态，生成含`plan_id`、版本、依赖、Schema、成功判据、预算和风险的DAG；规划只描述目标与可用能力，不持有生产凭据。
2. Executor领取就绪节点，校验参数、权限、预算和幂等后调用Tool。回执区分`Succeeded、RetryableFailed、PermanentFailed、Unknown、NeedInput`，并携带证据与副作用摘要。
3. 只有假设失效、永久错误或验收失败才触发重规划；瞬时故障由Executor有限重试。新计划引用旧版本和已完成节点，禁止重复副作用。
4. 状态库是唯一事实源，计划更新使用CAS；暂停、审批、取消和恢复均通过状态机。Executor不得扩展任务范围，Planner不得绕过Policy。

| 角色 | 核心职责 | 禁止事项 |
|---|---|---|
| Planner | 分解、排序、重规划 | 直接持有凭据执行 |
| Executor | 校验、调用、回报 | 擅自扩大目标 |
| Runtime/Policy | 状态、权限与可靠性 | 依赖模型自我约束 |

**验证指标：** 协作任务完成率、冲突率、通信开销、P95 延迟和单任务成本。

**相关知识点：** Planner-Executor、DAG、计划版本、执行回执、CAS、状态机、幂等、Policy Engine、受限重规划。

### MULTI-019 · 多Agent之间如何共享上下文？

> 稳定 ID：`MULTI-019`｜原题号：19

多Agent不应共享完整对话，而应采用**状态共享、证据引用和按需上下文包**。过量共享会增加Token、泄露范围和提示注入风险，并造成事实版本混乱。

1. Context Store按任务、租户和Agent命名空间保存结构化状态，记录Schema、版本、来源、敏感等级、TTL和Owner。事实用关系库或KV，大文件放对象存储，向量索引只负责召回。
2. Supervisor为子任务构建最小上下文包，包含目标、约束、必要事实、输入引用和输出契约。证据通过URI与摘要引用，使用短期令牌读取，避免复制和漂移。
3. 消息适合少量即时信息，黑板适合增量协作，RAG适合大规模知识召回。摘要须保留来源；关键数值、权限和状态不能只存在摘要中。
4. 并发写入使用CAS、事务或字段合并，读取绑定Snapshot。外部内容与系统指令分区，写前执行权限、Schema、DLP和注入检测。
5. 完成后清理临时上下文，仅将验证事实沉淀为长期记忆；读写关联TaskID与TraceID。

| 方式 | 适合内容 | 主要风险 |
|---|---|---|
| 消息透传 | 小型实时增量 | 重复与膨胀 |
| 共享存储/黑板 | 状态和中间产物 | 并发污染 |
| RAG引用 | 大型知识与证据 | 召回遗漏 |

**相关知识点：** Context Store、命名空间、最小上下文、RAG、黑板、Snapshot、CAS、数据血缘、DLP、提示注入隔离。

### MULTI-020 · 多Agent如何避免重复工作？

> 稳定 ID：`MULTI-020`｜原题号：20

避免重复工作要从**语义去重、唯一所有权、执行幂等和结果复用**四层治理。消息UUID只能识别重投，不能发现不同文本表达的同一子任务。

1. Planner以目标、规范化输入、资源、Skill版本和约束计算Task Fingerprint。注册表对`tenant+fingerprint`设唯一约束；相同任务运行中则订阅，已完成则复用结果。
2. Scheduler通过原子状态或租约授予单一执行权。Agent持有效Lease和Fencing Token才能写结果；重派前提升令牌版本，阻止旧实例提交。
3. 消费端按TaskID和幂等键查执行表，重复消息返回已有状态。副作用须把幂等键传给业务服务，并用唯一索引、事务或CAS保证只生效一次。
4. 结果按输入摘要、数据版本、权限和有效期缓存。复用前重验依赖与授权，防止过期或跨租户复用；中间产物可供其他DAG节点引用。
5. 监控重复派发、去重命中和重复副作用；状态不明时先查询，禁止盲目重试。

| 层次 | 机制 | 防止的问题 |
|---|---|---|
| 规划 | 任务指纹、注册表 | 语义重复任务 |
| 调度 | 租约、Fencing Token | 多Agent并行执行 |
| 业务 | 幂等键、唯一约束 | 重复副作用 |
| 结果 | 版本化缓存 | 重复计算 |

**相关知识点：** Task Fingerprint、任务注册表、租约、Fencing Token、幂等键、唯一约束、CAS、结果缓存、状态核验。

### MULTI-021 · Critic Agent和Executor Agent为什么要分离？

> 稳定 ID：`MULTI-021`｜原题号：21

Critic与Executor分离是为了建立**职责分离、独立证据和质量门禁**。Executor优化完成度与效率，Critic优化正确性和安全性，可降低执行者忽略自身缺陷的自评偏差。

1. Executor调用工具并输出结果、证据、变更清单和风险；Critic只读制品与原始要求，按Rubric检查事实、逻辑、完整性、安全和副作用，不直接修改资源。
2. 独立部署不等于独立判断；相同模型和数据仍会产生共模错误。应加入确定性测试、权威源、不同视角或异构模型，并回查引用。
3. Critic输出问题位置、级别、证据、建议和置信度。Blocking阻止推进，Warning要求修正，Suggestion非阻塞；评审轮数和预算须设上限。
4. 低风险任务可自检或规则校验；高价值、不可逆、合规任务适合独立Critic。效果以检出率、误报率、返工率和净成功率评估。
5. 最终验收由Supervisor执行，Critic只有建议或门禁权限，不能无限否决。

| 维度 | Executor | Critic |
|---|---|---|
| 优化目标 | 完成任务 | 发现缺陷与风险 |
| 权限 | 可执行受控动作 | 默认只读 |
| 产物 | 结果与证据 | 分级问题与判定 |

**相关知识点：** 职责分离、自评偏差、共模错误、Rubric、质量门禁、误报率、异构评审、状态机、评审预算。

### MULTI-022 · Reflection Agent应该独立部署吗？

> 稳定 ID：`MULTI-022`｜原题号：22

Reflection Agent是否独立部署取决于**复用范围、资源模型、隔离要求和时延SLA**。反思只是同一任务内的轻量自检时应内联；需要被多个流程复用、采用不同模型、独立扩缩容或承担质量门禁时，才适合服务化部署。逻辑角色分离不等于必须物理进程分离。

1. 内联方式共享当前上下文，无网络序列化和远程调用开销，适合低风险、低频、短链路反思；但它与Executor共享故障域和资源池，难以独立限流、升级与评估。
2. 独立部署可以选择专用模型和提示，建立只读权限、单独预算、质量指标及版本发布，并被多个Agent复用；代价是上下文传输、隐私扩大、额外时延和运维复杂度。
3. 决策可量化：调用频率高且跨三个以上工作流复用、CPU/GPU资源与执行侧差异明显、需独立审计或故障隔离时，优先独立；P95时延敏感、上下文很大且反思简单时优先内联。
4. 独立服务只接收最小证据包，包括目标、结果、引用、约束和Rubric，不接收无关完整对话；接口必须版本化并支持幂等、超时、限流、熔断和降级。服务不可用时，低风险任务可跳过或规则校验，高风险任务应暂停而非绕过门禁。
5. 可采用同进程独立模块作为过渡，待调用量与收益明确后再拆分。

| 方式 | 优点 | 主要代价 |
|---|---|---|
| 内联 | 低时延、上下文完整 | 耦合、难独立伸缩 |
| 独立服务 | 可复用、可隔离治理 | 网络与运维成本 |

**相关知识点：** 逻辑分离、物理部署、故障域、独立扩缩容、质量门禁、最小上下文、服务降级、P95时延。
<a id="multi-023"></a>
### MULTI-023 · 多Agent互相评审会不会增加成本？

> 稳定 ID：`MULTI-023`｜原题号：23

互相评审必然增加**模型调用、Token、通信和时延**，但应与减少的错误、返工和事故损失比较。应采用风险驱动的选择性评审，禁止全连接式互评。

1. 显性成本包括Token、证据传输、等待和存储；隐性成本包括误报返工、Critic冲突及循环修改。Agent数量为N时，全互评产生近似`O(N²)`交互。
2. 先用Schema、规则、测试、静态分析和小模型筛选；仅高风险写入、低置信、关键节点、模型分歧或抽检调用Critic，低风险结果可自检。
3. 评审深度按风险分级：普通任务单评审，高风险任务异构双评审，极高风险进入人工门禁。Critic只读取最小证据包，缓存相同版本的评审结果，并设置轮数、Token、时间和费用上限。
4. 评价应使用**风险调整后的净收益**：减少的失败损失与返工成本，减去新增推理和时延成本。跟踪缺陷检出率、误报率、评审采纳率、任务成功增益、单位缺陷成本和P95时延。
5. 若Critic与Executor高度同源，应优先增加确定性验证或权威数据，而非简单堆叠相同模型。

| 策略 | 成本 | 适用场景 |
|---|---|---|
| 自检/规则 | 低 | 低风险、可验证 |
| 单独Critic | 中 | 重要通用任务 |
| 异构双评审 | 高 | 高风险决策 |
| 人工门禁 | 很高 | 不可逆或合规操作 |

**相关知识点：** O(N²)通信、风险分级、选择性评审、Critic、误报率、异构评审、评审预算、风险调整收益。

### MULTI-024 · 黑板模式和消息总线模式各自的优缺点是什么？分别适合什么场景？

> 稳定 ID：`MULTI-024`｜原题号：24

黑板以**共享状态**协作，消息总线以**不可变事件**协作；前者便于共同改进中间成果，后者利于异步解耦和扩展。系统可用总线传播事件、黑板保存任务视图。

1. 黑板由共享存储、Agent和控制器组成，适合诊断、规划、联合研究等增量求解。其上下文直观、参与者松耦合；风险是并发争用、状态膨胀、污染传播和热点。
2. 黑板需提供Schema、命名空间、CAS、字段权限、来源与TTL；读取绑定Snapshot，冲突按规则合并或仲裁。
3. 总线通过队列或Topic发布事件，适合事件驱动、一对多通知和流量削峰。其吞吐与扩展性较好，但存在至少一次投递、重复、乱序、积压和追踪困难。
4. 总线需有幂等消费、分区键、死信队列、Schema Registry、Outbox和TraceContext；消息不应成为权威状态。
5. 共同演进解空间选黑板；强调事件传播和独立扩容选总线；强事务由状态机或工作流引擎主导。

| 维度 | 黑板模式 | 消息总线 |
|---|---|---|
| 核心 | 共享可变状态 | 传递不可变事件 |
| 优势 | 协同求解、全局视图 | 异步解耦、扩展性 |
| 风险 | 争用与状态污染 | 重复、乱序、积压 |
| 适用 | 联合推理 | 事件驱动协作 |

**相关知识点：** 黑板模式、发布订阅、事件总线、CAS、Snapshot、Schema Registry、Outbox、死信队列、幂等消费。

### MULTI-025 · 如果两个Agent同时修改同一个共享状态，怎么保证一致性？

> 稳定 ID：`MULTI-025`｜原题号：25

先定义状态需要**强一致还是最终一致**。资金、权限、任务所有权等不可合并状态应串行化，标签、计数或集合可乐观更新或采用CRDT。

1. 写入携带StateID、基线版本、AgentID、TaskID和幂等键。低冲突场景用CAS，仅当当前版本等于基线时提交，否则重读、合并或重试，防止Lost Update。
2. 高冲突状态使用事务、行锁或租约。租约配Fencing Token，存储层拒绝旧令牌，避免暂停Agent恢复后双写；锁需超时并按固定顺序获取。
3. 可交换数据采用字段操作或CRDT。重要字段不能简单使用Last-Write-Wins，否则时钟漂移和覆盖会丢失变更。
4. 复杂冲突比较双方Patch与共同基线，无重叠字段自动合并；相同字段按Owner、权限、优先级或人工仲裁，新版本保留父版本。
5. 状态与事件通过Outbox保持一致，读取绑定Snapshot；审计记录前后值、版本、决策和Trace。

| 机制 | 一致性 | 适用场景 |
|---|---|---|
| CAS/MVCC | 强，冲突重试 | 低争用状态 |
| 锁/租约 | 强，串行写 | 高争用关键状态 |
| CRDT | 最终一致 | 可交换集合或计数 |
| 三方合并 | 业务定义 | 文档与结构化Patch |

**相关知识点：** 强一致、最终一致、CAS、MVCC、租约、Fencing Token、CRDT、三方合并、Lost Update、Outbox、Snapshot。

### MULTI-026 · Task DAG中如果某个节点执行失败，如何决定是重试、跳过还是整体回滚？

> 稳定 ID：`MULTI-026`｜原题号：26

决策应由节点预先声明的**错误类型、关键性、幂等性、下游影响和补偿能力**共同决定，不能在失败后临时让模型自由选择。DAG运行时应把重试、跳过、补偿和人工介入建模为显式状态迁移。

1. 瞬时网络错误、限流或临时`5xx`，且节点只读或具备幂等键时，采用指数退避、抖动和有限次数重试；参数、权限、业务拒绝属于永久错误，修正前不得重试。超时且结果未知时先查询外部状态。
2. 非关键节点、可选增强步骤或存在合法默认值时可跳过，但必须标记`Degraded`并向下游传播缺失字段，防止后续把不完整结果当完整成功。若下游前置条件不再满足，应剪枝相关分支。
3. 关键节点失败且已完成步骤产生副作用时，执行Saga补偿，而不是假设分布式事务可以直接回滚。补偿按逆依赖顺序执行，并具备幂等键、独立重试和失败告警；不可逆操作进入人工处置。
4. 若失败只影响局部分支，可隔离该分支并保留其他成果；若破坏全局不变量、安全策略或最终产物的必要条件，则终止整体任务。检查点记录节点输入、版本、状态与副作用，恢复时避免重复执行。

| 处理方式 | 适用条件 | 前提 |
|---|---|---|
| 重试 | 瞬时可恢复错误 | 幂等、预算内 |
| 跳过 | 非关键或有默认值 | 下游允许降级 |
| 局部终止 | 分支可隔离 | 不破坏全局目标 |
| 补偿回滚 | 关键副作用已发生 | 有Saga补偿 |

**验证指标：** 协作任务完成率、冲突率、通信开销、P95 延迟和单任务成本。

**相关知识点：** DAG失败策略、错误分类、重试预算、幂等、Degraded状态、分支剪枝、Saga、补偿事务、检查点。

### MULTI-028 · 如何设计消息的幂等性，防止重复消费导致任务被执行两次？

> 稳定 ID：`MULTI-028`｜原题号：28

消息系统通常提供**至少一次投递**，须用幂等键、原子状态和业务去重实现“效果只发生一次”。仅在消费后记录消息ID存在崩溃窗口。

1. 幂等键代表业务意图，可由`tenant+operation+object+request_id`构成，在重试、转发和降级时保持不变；Broker的MessageID不能替代业务键。
2. 消费者先原子插入幂等键或将`Pending`迁移为`Running`，唯一约束只允许一个实例执行。已成功返回原结果，执行中等待或查询，失败按类型处理。
3. 业务写入与幂等记录放在同一事务；后续事件使用Transactional Outbox。外部API须接收幂等键；不支持时增加状态查询、唯一约束或补偿。
4. 状态未知先查账，禁止直接重放副作用。记录保存请求摘要和响应，同一键对应不同参数时必须拒绝。
5. TTL覆盖最大重投、任务运行和灾备窗口；关键记录不得过早删除。监控重复、未知状态和补偿失败。

| 层次 | 机制 | 作用 |
|---|---|---|
| 传输层 | MessageID | 识别消息重投 |
| 消费层 | 幂等表、唯一约束 | 单一消费者生效 |
| 业务层 | 业务键、状态机 | 防重复副作用 |
| 事件层 | Outbox | 状态与事件一致 |

**相关知识点：** 至少一次投递、业务幂等键、唯一约束、状态机、Transactional Outbox、查账、补偿、TTL、崩溃窗口。
