### MULTI-002 · 复杂任务如何拆分子任务下发给子Agent，怎么避免任务重复下发、重复执行（Agent中级）

> 稳定 ID：`MULTI-002`｜原题号：2

复杂任务应建模为**具有依赖、输入输出契约和验收条件的任务DAG**，再依据能力、负载和权限分派；重复问题必须建立**调度去重、执行幂等、结果去重**三道防线。

1. Planner识别目标、约束和共享资源，按领域、阶段或可独立验收的产物拆分。节点应包含`task_id`、依赖、输入、输出、截止时间、重试策略和成功判据；粒度过粗无法并行，过细则协调成本过高。
2. Scheduler仅下发前置条件满足的节点，按能力标签、负载和风险选择子Agent。并行节点若写同一资源，应串行化、加租约或采用版本号控制。
3. 下发前以**任务ID+规范化输入哈希+版本**形成唯一键，通过唯一约束或原子状态迁移占用，避免调度实例重复派发。
4. 子Agent先查询执行记录，重复请求直接返回既有结果。幂等键还应传至数据库或外部服务，并以本地事务加Outbox保证业务提交与完成事件一致；超时后先查状态，禁止盲目重放非幂等操作。

| 防线 | 核心机制 | 解决的问题 |
|---|---|---|
| 调度层 | 唯一键、原子占用、租约 | 重复下发 |
| 执行层 | 幂等表、状态机、服务端幂等键 | 重复副作用 |
| 结果层 | 结果缓存、事件去重、版本校验 | 重复汇聚与覆盖 |

消息系统通常采用**至少一次投递**，应在业务层实现可验证的近似Exactly-once效果并保留Trace。

**相关知识点：** DAG、任务契约、拓扑调度、能力路由、幂等键、唯一约束、分布式租约、Outbox、至少一次投递、结果缓存。

### MULTI-004 · A2A多智能体通信场景下，Agent调用超时、接口报错、服务宕机，重试、降级、兜底的完整方案（Agent中级）

> 稳定 ID：`MULTI-004`｜原题号：4

A2A容错应形成**“截止时间—错误分类—有界重试—熔断隔离—降级兜底—状态核验”**闭环。关键是先判断请求是否产生副作用，再选择恢复路径；超时后直接重放可能造成重复任务或重复写入。

1. 调用链传播Deadline，并设置建连、首包、读取和总任务超时。长任务应使用A2A Task，通过查询、订阅流或推送获取状态，不能让同步连接无限等待。
2. 参数、内容类型、协议版本和鉴权错误属于永久错误，修正前不重试；限流、网络抖动、临时`5xx/503`可遵循`Retry-After`，采用指数退避、随机抖动和重试预算；持续不可用则触发熔断。
3. `Send Message`使用稳定`messageId`与业务幂等键。超时后先`Get Task`核验：任务已存在就继续订阅或复用结果，仅在确认未受理时重试；状态不可查询且操作非幂等时，应人工核对或补偿。
4. 熔断后按能力、权限、数据地域和版本路由备用Agent；无等价能力时，依次降级为缓存、缩减任务、异步排队或人工接管。失败上下文、重试次数、状态迁移和Trace必须持久化。

| 错误类型 | 是否重试 | 主要处理 |
|---|---|---|
| 参数、鉴权、版本错误 | 否 | 修正或快速失败 |
| 限流、网络、临时5xx | 有界 | 退避、抖动、预算 |
| 超时且状态未知 | 先查询 | 复用、补偿或核验 |
| 持续宕机 | 否 | 熔断、备用、降级 |

**验证指标：** 协作任务完成率、冲突率、通信开销、P95 延迟和单任务成本。

**相关知识点：** A2A Task生命周期、Deadline、Retry-After、指数退避、重试预算、messageId、幂等、熔断、补偿、备用路由、人工接管。

### MULTI-015 · 多 Agent 如何进行任务分配？

> 稳定 ID：`MULTI-015`｜原题号：15

任务分配采用**“硬约束过滤、软目标评分、租约认领、运行时再平衡”**。最优Agent不是语义最相似者，而是在可执行候选中综合质量、时延、成本与负载最优者。

1. 任务声明Skill、Schema、资源范围、数据地域、风险、优先级、Deadline和预算；Agent目录记录能力、权限、并发、成功率、成本与健康度。强约束缺失时不得派发高风险任务。
2. 先过滤无权限、版本不兼容、不健康和资源不足者，再计算`能力匹配度+质量−时延−成本−负载−风险`，权重按SLA调整并保留选择原因。
3. 稳定流程由中心Scheduler指派；大规模自治系统可用合同网竞标；固定资源亲和可用一致性哈希，故障时重新路由。
4. 分配携带TaskID、幂等键和租约。逾期先fencing旧执行者再重派；抢占任务须保存检查点并释放资源。
5. 通过队列时间、分配命中率、一次成功率、利用率和单位任务成本评估策略，防止某些Agent长期过载或饥饿。

| 分配机制 | 优点 | 适用场景 |
|---|---|---|
| 中心化指派 | 全局可控、易审计 | 稳定企业流程 |
| 合同网竞标 | 弹性、利用局部信息 | 大规模动态协作 |
| 一致性哈希 | 映射稳定、缓存友好 | 分片与数据亲和 |

**相关知识点：** Agent Registry、能力匹配、合同网、负载均衡、优先级调度、一致性哈希、租约、fencing、饥饿、检查点。

### MULTI-017 · Multi-Agent任务如何拆分？

> 稳定 ID：`MULTI-017`｜原题号：17

任务拆分以**可独立执行、可验收、依赖最小和副作用内聚**为边界，产出可调度DAG，不能按文本段落平均切割。子任务应在有限上下文内完成，且失败不污染其他分支。

1. 先明确最终产物、硬约束和验收标准，再采用目标分解：按领域专家、业务阶段、数据分片或产物组件切分。确定性流程用模板或规则，开放目标可由Planner提出候选分解，但必须经过Schema与依赖检查。
2. 每个节点定义TaskID、目标、输入引用、输出Schema、前置条件、允许工具、权限、Deadline、预算、成功判据和失败策略。共享背景通过版本化引用获取，避免在消息中复制完整上下文。
3. 识别数据依赖、控制依赖和共享资源冲突。无依赖节点并行；前一步输出决定后一步输入时串行；分支条件必须使用可验证表达式；多个节点写同一资源时，应合并为一个事务边界或加锁。
4. 粒度以“协调成本低于并行或专业化收益”为准。节点过粗会降低并行度和故障隔离，过细会增加Token、通信、调度与结果拼接成本，可通过历史关键路径和失败率持续调整。
5. 拆分后执行环检测、权限和预算校验；汇聚节点须定义缺失、部分失败与冲突的处理规则。

| 依赖类型 | 调度方式 | 关键控制 |
|---|---|---|
| 无依赖 | 并行 | 并发与预算上限 |
| 数据依赖 | 串行 | Schema和版本 |
| 条件依赖 | 分支 | 可验证条件 |
| 共享写资源 | 串行或合并 | 锁、事务、幂等 |

**相关知识点：** 目标分解、DAG、任务契约、粒度控制、关键路径、并行调度、事务边界、环检测、汇聚策略。
