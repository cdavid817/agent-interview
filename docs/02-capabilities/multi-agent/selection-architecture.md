# 选型与角色架构

> 所属章节：[多 Agent 与协作](README.md)｜本文件共 **6** 题。

<a id="multi-001"></a>
### Agent是单Agent还是多Agent？为什么这么设计？有没有考虑过另一种方案？（百度Agent）

应优先采用**“单Agent起步、按瓶颈演进为多Agent”**的方案。单Agent共享同一上下文和决策闭环，链路短、调试简单，适合目标清晰、工具数量有限、任务以串行为主的场景；多Agent通过规划者、执行者、评审者或领域专家分工，能够实现上下文隔离、并行处理和故障隔离，但会引入通信成本、状态一致性、冲突仲裁及分布式观测问题。

1. 选型应评估**任务可分解性、领域异构度、并行收益、权限边界、上下文压力和可靠性要求**。若子任务存在清晰契约、可独立验收且并行收益大，多Agent更合理；若步骤高度共享上下文、频繁相互依赖，拆分反而会造成信息损失。
2. 设计上可先使用单Agent配合Tool、Skill和显式状态机；当出现工具选择准确率下降、上下文被大量描述挤占、单模型无法覆盖专业领域或串行时延超过SLA时，再拆出专家Agent。
3. 多Agent必须补齐任务ID、消息契约、幂等、超时、重试预算、状态存储和Trace，否则只是把模型问题转化为分布式系统问题。

| 维度 | 单Agent | 多Agent |
|---|---|---|
| 上下文 | 连贯但受窗口限制 | 可分区，但需摘要与同步 |
| 执行 | 编排简单，通常串行 | 可并行，协调开销较高 |
| 故障 | 单点影响完整任务 | 可隔离、重分派或降级 |
| 适用场景 | 边界稳定、中低复杂度 | 跨领域、强并行、强隔离 |

**相关知识点：** 架构演进、任务分解、Supervisor、Planner-Executor、上下文工程、故障隔离、分布式状态、幂等、可观测性。
<a id="multi-006"></a>
### 多Agent主流两种架构：中心化调度、去中心化自治，分别讲实现方式、优缺点、适配什么业务场景（Agent中级）

两种架构的核心差异是**全局决策权放在统一编排器，还是分散给自治Agent**。中心化适合流程可控、合规要求高的业务；去中心化适合节点规模大、拓扑动态且局部信息更重要的场景。

1. 中心化由Supervisor维护任务DAG、全局状态和Agent目录，统一完成分解、路由、重试与结果聚合。优点是决策一致、资源可全局优化、权限和审计入口集中；缺点是主控可能成为性能瓶颈和故障集中点，因此需要多副本、选主、持久化检查点与幂等接管。
2. 去中心化由Agent通过点对点消息、发布订阅、合同网竞标或共享黑板协商任务。其局部自治、横向扩展和故障隔离能力较强，但容易出现重复认领、循环委托、状态分歧和局部最优，必须增加租约、共识或冲突合并机制。
3. 业务流程稳定、强审批、需要完整审计以及中等规模团队协作，优先中心化；跨组织、跨地域、边缘节点或高动态资源调度可采用去中心化。
4. 大型系统更适合**分层中心化**：全局层只管理目标、策略和预算，领域Supervisor负责局部调度，Agent保留有限自治，从而控制跨域通信和故障半径。

| 维度 | 中心化调度 | 去中心化自治 |
|---|---|---|
| 决策 | 全局统一 | 局部协商 |
| 一致性与审计 | 较强、易追踪 | 较弱、需额外协议 |
| 扩展与容错 | 受主控容量影响 | 横向扩展、无单主控 |
| 适用 | 固定流程、强治理 | 高动态、大规模协作 |

**验证指标：** 协作任务完成率、冲突率、通信开销、P95 延迟和单任务成本。

**相关知识点：** Supervisor、合同网、黑板模式、任务DAG、选主、租约、共识、分层架构、联邦架构、故障隔离。

### 对A2A架构是否了解；什么场景下单一Agent无法完成任务，需要引入多Agent协同处理（Agent初级）

A2A是面向**Agent能力发现、任务委托和状态交互**的互操作协议，使远端Agent独立接受任务并返回Message、Task状态和Artifact。引入多Agent应由系统瓶颈驱动，而不是仅因任务复杂。

1. 服务方通过Agent Card声明端点、能力、Skill、输入输出模式和安全方案；调用方按能力选择Agent。短请求可返回Message，长任务使用Task，并通过查询、流式订阅或推送跟踪进展。
2. 工具描述、历史和材料挤占上下文并造成信息丢失时，可按领域拆分；任务横跨法律、财务、代码等专业且需独立评测时，应使用专家Agent。
3. 子任务有清晰依赖和验收标准，并行能缩短关键路径时，多Agent具有性能价值；角色拆分还可实现权限、复核与故障隔离。
4. 若步骤共享大量隐式上下文、频繁往返，或协调成本高于收益，则单Agent配合Tool、Skill和状态机更合适。多Agent必须补齐幂等、超时、状态、Trace与冲突仲裁。

| 维度 | A2A | MCP |
|---|---|---|
| 主要对象 | 自治Agent与任务 | Tool、Resource、Prompt |
| 交互形态 | 委托、状态、Artifact | 能力发现与调用 |
| 生命周期 | 支持长任务状态 | 通常由宿主编排 |

**相关知识点：** Agent Card、Message、Task、Artifact、A2A、MCP、能力发现、上下文隔离、专家Agent、并行执行、权限隔离。
<a id="multi-008"></a>
### 大规模多Agent集群架构：中心化管控、联邦式协同、去中心化自治三种架构的取舍、优缺点、适配业务场景（Agent高级）

三种架构位于**治理强度与自治扩展性**的连续谱上：中心化强调统一控制，去中心化强调局部自治，联邦式通过分域Supervisor取得折中。选型应同时考察规模、跨域边界、一致性要求、故障半径和审计责任，不能只依据Agent数量。

1. 中心化由全局Orchestrator维护目录、DAG、状态和策略，易实现全局最优调度、强审计与统一权限，但控制面存在容量上限；需要分片、主备选举、检查点和幂等接管保障高可用。
2. 联邦式按地域、租户或业务域设局部Supervisor，域内强一致调度，跨域只交换能力、任务摘要和事件。它能限制数据移动和故障扩散，适合大型企业与跨组织协作；难点是身份信任、跨域协议、版本兼容及最终一致性。
3. 去中心化Agent通过发现、竞标、Gossip或共享黑板自治协商，无单一调度瓶颈，适合边缘网络、开放生态和高动态资源；代价是重复执行、循环委托、全局最优性不足及调试困难。
4. 建议采用渐进演进：小规模从中心化开始，规模或组织边界扩大后下沉为联邦式；只有在中心不可达、拓扑极度动态且允许最终一致时才采用高度去中心化。

| 架构 | 控制与一致性 | 扩展性 | 典型场景 |
|---|---|---|---|
| 中心化 | 强 | 中 | 合规流程、中小集群 |
| 联邦式 | 域内强、跨域最终一致 | 高 | 跨地域、跨组织 |
| 去中心化 | 弱或最终一致 | 很高 | 边缘、开放动态网络 |

**验证指标：** 协作任务完成率、冲突率、通信开销、P95 延迟和单任务成本。

**相关知识点：** 控制面、联邦架构、Supervisor、Gossip、合同网、最终一致性、选主、分片、故障域、零信任。

### Supervisor Agent 如何调度多个 Agent？

Supervisor是**控制面编排器而非万能执行者**，负责任务分解、Agent选择、全局状态和异常处理，业务动作由子Agent完成。调度依赖显式契约和确定性运行时。

1. 将目标分解为带依赖、输入输出Schema、优先级、截止时间和验收标准的DAG。前置条件满足的节点进入Ready队列，独立节点并行，共享写资源串行或加租约。
2. Registry记录能力、权限、成本、成功率、并发和健康状态。先做权限与前置条件硬过滤，再按能力、负载、数据位置、时延和成本评分。
3. 派发携带TaskID和幂等键，状态机记录`Ready→Leased→Running→Validating→Completed/Failed`。超时后先fencing旧执行者再重分派，避免双写。
4. 结果经Schema、业务规则和后置条件校验；失败按类型进行有限重试、备用路由、重新规划或人工接管。Deadline和预算向下传播。
5. 记录选择原因、候选评分、状态迁移和Trace，支持审计与容量调整。

| 路由方式 | 优势 | 适用场景 |
|---|---|---|
| 规则过滤 | 确定、可审计 | 权限与强约束 |
| 能力评分 | 综合质量与成本 | 常规动态分派 |
| 合同网竞标 | 自适应资源报价 | 大规模自治系统 |

**相关知识点：** Supervisor、DAG、Agent Registry、能力路由、租约、fencing、状态机、重试预算、结果验证、合同网。

### Supervisor Agent的职责是什么？

Supervisor是多Agent系统的**全局控制面**，负责确保任务被正确分解、分派、推进、验证和终止，而非亲自完成业务步骤；其目标是让协作可观测、可恢复。

1. 任务编排：解析目标，校验DAG，维护依赖、优先级、预算、Deadline与成功标准；开放计划仍须通过确定性检查。
2. 能力路由：维护Registry，按权限、地域、版本和健康度过滤，再综合能力、质量、时延、成本与负载选Agent。
3. 状态协调：维护状态机、租约和检查点，接收回执并驱动结果汇聚；重复、乱序事件执行幂等与版本校验。
4. 异常治理：执行有限重试、fencing后重派、备用切换、重规划、补偿或人工接管，并限制故障半径。
5. 质量安全：校验Schema、证据与后置条件，执行Policy、审批、审计和Trace。自身须多副本与持久化，避免单点。

| 组件 | 主要职责 | 与Supervisor的边界 |
|---|---|---|
| Planner | 生成计划 | 不负责运行态接管 |
| Router | 匹配候选能力 | 不维护全局流程 |
| Executor | 执行具体节点 | 不扩大任务目标 |
| Supervisor | 编排与治理 | 不直接实现业务工具 |

**相关知识点：** 控制面、Supervisor、Planner、Agent Registry、状态机、检查点、租约、fencing、Policy、结果聚合、高可用。
