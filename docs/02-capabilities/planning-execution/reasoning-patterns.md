### 1. 反思机制怎么做？（豆包二面）

**Reflection应被设计为基于验证证据的受控诊断流程，用于发现根因并改变错误策略，而不是让模型机械重答。**

1. 反思可在三个阶段触发：规划后检查遗漏与依赖；步骤失败后分析与Success Criteria的差距；任务结束后复盘成本和失败模式。简单任务已通过客观验证时不触发。

2. Reflector输入包括**原目标、计划、执行轨迹、工具结果、Validator报告、历史尝试和剩余预算**；输出采用结构化Schema，明确错误类型、证据、根因、影响节点、修正动作及置信度，禁止泛化建议。

| 机制 | 核心职责 | 是否修改策略 |
| --- | --- | --- |
| Validation | 判断是否达标 | 否 |
| Retry | 再次执行同一动作 | 否 |
| Reflection | 诊断失败原因 | 提出建议 |
| Replan | 修改执行路径 | 是 |

3. 应优先使用编译、测试、规则或检索作为外部证据，也可由独立Critic复核。Reflection只负责诊断，策略层再按风险、权限和成本选择Repair、Retry或**Local Replan**，不得直接执行高风险动作。

4. 设置最大轮数、Token、时间和费用预算，并对错误指纹及建议去重。连续两轮无新增证据、重复失败方案或触及不可逆操作时停止自动反思。以恢复成功率、额外成本和误修正率评估效果。

**相关知识点：** Reflection、Critic、Validator、Self-Correction、反思预算、Local Replan、终止条件。

### 2. 说下你对Agent的理解，如何通过反思机制提升整体任务执行成功率？（Agent中级）

**Agent是能以目标为中心感知、规划、行动和验证的状态化系统；反思机制以证据驱动纠错并提升失败恢复率。**

1. Agent不只生成文本，还维护目标、计划和状态，主动选择模型、工具或Skill改变环境，并根据观察决定下一动作。其核心是**Planning—Action—Observation—Validation闭环**，而非单次Prompt。

2. Reflection由Validator触发：步骤未满足Success Criteria、结果不确定或成本异常时，将目标、计划、工具结果、错误轨迹和历史尝试交给Critic，输出根因、证据、影响节点、修正建议及置信度。

| 失败类型 | 反思后的动作 | 示例 |
| --- | --- | --- |
| 瞬时故障 | Retry | 网络超时 |
| 动作错误 | Repair | 参数不符合Schema |
| 证据不足 | 补充检索或验证 | 事实无法确认 |
| 路径失效 | Local Replan | 工具能力不匹配 |

3. 代码任务优先使用测试、编译和静态分析，事实任务使用可追溯检索，必要时采用独立Critic。反思只负责诊断，策略层再决定Retry、Repair或**局部重规划**，不得直接执行高风险动作。

4. 设置轮数、Token、时间和成本上限，对错误指纹及建议去重；无新证据或重复失败时转人工。效果统计首次成功率、恢复成功率、误修正率、成本和人工接管率。

**相关知识点：** Agent Loop、Planning、Reflection、Critic、Validator、Local Replan、恢复成功率。

### 3. ReAct 与 Plan-and-Execute 有什么区别？

**ReAct强调基于即时观察的逐步决策，Plan-and-Execute强调全局分解后的受控执行，核心差异在规划时机与状态管理。**

1. ReAct按“推理—动作—观察”循环，每轮决定下一步，能及时吸收搜索结果、工具报错和环境变化，适合探索性强的短任务。但它缺少全局视图，容易重复调用、偏离目标或陷入循环，需要步数上限、重复检测和终止条件。

2. Plan-and-Execute先生成任务列表或DAG，再逐节点执行并验证产物。它适合多阶段、依赖明确、需要并行和审计的任务，可预估成本并设置检查点；缺点是计划可能基于错误假设，环境变化后会产生**计划陈旧**。

| 维度 | ReAct | Plan-and-Execute |
| --- | --- | --- |
| 规划范围 | 当前下一步 | 全局结构 |
| 反馈利用 | 每轮吸收 | 节点后更新 |
| 状态 | 对话轨迹 | 结构化计划 |
| 风险 | 循环、短视 | 计划过时 |
| 场景 | 开放探索 | 长链路、强依赖 |

3. 工程上常采用**分层混合架构**：外层Plan-and-Execute确定里程碑、依赖、预算和风险门控，节点内部用ReAct处理检索、调试等不确定性；节点失败或假设失效时触发局部重规划。

4. 选择取决于复杂度和环境动态性：简单问答直接生成；动态性高、步骤少时偏向ReAct；依赖多且可预见时偏向Plan-and-Execute。评估完成率、调用数、重复率、重规划率、延迟、成本和不可恢复错误率。

**历史别名：** `PLAN-205`。

**相关知识点：** ReAct、Planner、Executor、DAG、Validator、计划陈旧、局部重规划、分层控制。

### 4. Reflection 有什么作用？

**Reflection通过分析执行证据定位失败原因并生成修正策略，使Agent从机械重试转向有依据的自我纠错。**

1. Reflection在验证失败、工具报错或计划停滞时触发。输入包含**目标、计划、执行轨迹、工具结果、Validator报告、历史尝试和预算**；输出应给出错误类型、证据、根因、影响范围、修正动作及置信度，不能只写“重新思考”。

| 机制 | 回答的问题 | 产物 |
| --- | --- | --- |
| Validation | 结果是否达标 | 判定与证据 |
| Retry | 同一动作能否再试 | 新Attempt |
| Reflection | 为什么失败 | 根因与建议 |
| Replan | 应换什么路径 | 新计划版本 |

2. Reflection负责诊断，Retry重新执行相同动作，Replan改变任务路径。瞬时网络错误可退避重试；参数或工具错误应修正动作；目标分解错误则触发**局部重规划**。三者混用会造成无效循环。

3. 反思必须受外部证据约束。代码任务使用测试、编译和日志，事实任务使用可追溯来源，结构化任务使用Schema校验。模型自评分只能作为弱信号，不能替代Validator，否则可能强化偏差。

4. 系统需限制轮数、Token、时间和费用，并对错误指纹与建议去重。连续无新证据、重复方案、置信度下降或涉及不可逆操作时，应停止并转人工。评估修复率、无效循环率、额外成本、误修率和完成率。

**相关知识点：** Reflection、Critic、Validator、Retry、Replan、证据驱动、反思预算、终止条件。

### 5. ReAct模式与Plan-Execute模式分别适用于哪些场景？

**ReAct适合短链路、环境动态且下一步依赖即时观察的任务；Plan-Execute适合长链路、依赖明确且需要全局控制的任务。**

1. ReAct按“推理—动作—观察”循环，根据结果决定下一步，适合检索、故障排查和环境探索。它能吸收新证据，无需完整计划；但易重复或循环，需要步数、预算和终止条件。

| 维度 | ReAct | Plan-Execute |
| --- | --- | --- |
| 决策范围 | 当前下一步 | 全局结构 |
| 环境假设 | 动态、逐步揭示 | 相对可预测 |
| 状态形式 | 轨迹与观察 | DAG与节点状态 |
| 并行能力 | 较弱 | 可显式并行 |
| 风险 | 循环与短视 | 计划陈旧 |
| 典型场景 | 搜索、调试、探索 | 开发、分析、长流程 |

2. Plan-Execute先生成DAG，再执行并验证。它适合复杂开发、研究报告和跨系统流程，可安排依赖、并行、预算、审批和Checkpoint；环境变化时计划可能失效。

3. 选型依据是任务长度、依赖和动态性。短且动态优先ReAct，长且清晰优先Plan-Execute；简单问答无需两者，高风险固定业务优先Workflow。长任务含局部不确定性时采用**外层Plan-Execute、内层ReAct**。

4. 混合模式下，节点失败时局部重规划，保留有效结果，并限制步数与重规划次数。评估完成率、调用数、重复率、计划可执行率、P95延迟、单位成本和不可恢复错误率。

**相关知识点：** ReAct、Plan-Execute、Planner、Executor、Validator、DAG、Workflow、局部重规划。

### 6. Task Planning有哪些常见算法或实现方式？

**Task Planning应依据状态可枚举性、领域知识、环境不确定性和预算选择符号规划、层次规划、工作流或LLM规划。**

1. **经典规划**用STRIPS/PDDL描述状态、目标、动作前置条件与效果，再以A*等搜索动作序列，可验证性强，但存在状态空间爆炸和建模困难。

| 方法 | 核心机制 | 适用场景 | 局限 |
| --- | --- | --- | --- |
| STRIPS/PDDL | 状态空间搜索 | 规则明确的封闭域 | 建模成本高 |
| HTN | 高层任务递归分解 | 专家流程丰富 | 依赖领域模板 |
| Workflow/DAG | 固定节点与依赖 | 稳定业务流程 | 长尾适应弱 |
| ReAct/Plan-and-Execute | 行动反馈循环 | 开放工具环境 | 波动较高 |
| ToT/MCTS | 多候选搜索 | 复杂决策 | 开销大 |

2. **HTN**按方法库逐层分解目标，便于复用业务经验；行为树适合反应式控制；DAG适合包含并行、共享依赖和重试的工程任务。

3. LLM实现包括一次性计划、ReAct边执行边修正、Plan-and-Execute分离规划与执行，以及ToT生成多路径后评分。生产系统多采用混合架构：稳定步骤固化，LLM规划不确定节点，并受Schema、权限和验证器约束。

4. 选型需评估成功率、计划可执行率、搜索节点数、延迟、成本、重规划次数与风险。高风险场景采用强约束和人工门控，动态环境保留局部重规划。

**相关知识点：** STRIPS、PDDL、A*搜索、HTN、行为树、DAG、ReAct、Plan-and-Execute、ToT、MCTS。

### 7. Reflection机制通常在什么阶段使用？

**Reflection通常用于计划提交前、关键节点完成后、验证失败后和任务收尾阶段，其作用是发现偏差并提出可验证的修正。**

1. 计划前反思检查目标覆盖、遗漏约束、不可执行步骤和高风险副作用，可提前阻断错误；执行中不必每步反思，只在里程碑、异常信号或高风险动作前触发，避免增加主链路延迟。

| 机制 | 回答的问题 | 产物 |
| --- | --- | --- |
| Validation | 结果是否达标 | 判定与证据 |
| Retry | 同一动作能否再试 | 新Attempt |
| Reflection | 为什么失败 | 根因与建议 |
| Replan | 应换什么路径 | 新计划版本 |

2. 验证失败后是重要触发点。Reflector接收**目标、计划、执行轨迹、工具结果、Validator报告、历史尝试和剩余预算**，输出错误类型、证据、根因、影响范围和修正建议。代码任务以测试、编译和静态分析为主要证据，不能仅让模型自评。

3. 任务结束时检查交付物完整性、未解决项和副作用，并生成可追溯总结；离线阶段聚合失败轨迹，改进Prompt、规则、Skill或评测集。离线学习不得直接修改线上策略，需经回归测试和灰度发布。

4. Reflection只负责诊断，Retry负责重做，**Replan**负责修改路径。系统限制轮数、Token、时间与费用，对错误指纹和建议去重；没有新证据、重复同一方案或涉及不可逆操作时，应停止自动反思并转人工。

**相关知识点：** Reflection、Critic、Validator、证据驱动、自我修正、反思预算、终止条件。

### 8. Reflection与Replanning有什么区别？

**Reflection基于轨迹诊断根因，Replanning据此改变后续节点、依赖或能力路径；前者产出诊断，后者产出新计划。**

1. Reflection在计划提交前、关键节点后或Validator失败时触发，输入是目标、假设、证据和历史尝试。它可得出参数错误、能力不匹配或前提失效，但不改变任务状态，也不执行修复。

2. Reflector接收**目标、计划、轨迹、工具结果、Validator报告、已尝试方案和预算**，输出错误类型、证据、根因、影响范围、建议及置信度。代码任务采用测试、编译和静态分析，事实任务采用可追溯证据。

| 机制 | 回答的问题 | 产物 |
| --- | --- | --- |
| Validation | 结果是否达标 | 判定与证据 |
| Retry | 同一动作能否再试 | 新Attempt |
| Reflection | 为什么失败 | 根因与建议 |
| Replan | 应换什么路径 | 新计划版本 |

3. Replanning读取诊断、计划版本、有效产物与预算，修改失败节点及受影响下游，再经过依赖、权限和风险校验。若只是网络抖动或参数错误，应Retry或Repair，无需改变计划。

4. 两者形成闭环但保持解耦：Reflector不能扩大权限，Replanner不能在无新证据时反复改路。系统限制反思与重规划次数，检测近似方案；无新信息、涉及不可逆操作或目标冲突时转人工。

**相关知识点：** Reflection、Replanning、Critic、Validator、根因分析、局部重规划、计划版本、终止条件。

### 9. Plan-and-Execute与ReAct各自适用于哪些场景？

**ReAct适合短链、信息逐步显现且路径高度不确定的任务；Plan-and-Execute适合长链、依赖清晰且需要全局控制的任务。**

1. **ReAct**逐轮进行推理、行动和观察，根据工具结果调整下一步，适合故障排查、网页探索等无法预先列出完整路径的场景。缺点是容易局部贪心、重复调用、目标漂移，且难以并行。

| 维度 | ReAct | Plan-and-Execute |
| --- | --- | --- |
| 决策方式 | 逐轮观察后决策 | 先规划后执行 |
| 适用任务 | 短、路径不确定 | 长、依赖较清晰 |
| 全局视角 | 较弱 | 较强 |
| 并行调度 | 难以表达 | 可使用DAG |
| 主要风险 | 局部循环、成本失控 | 计划过时、前提错误 |

2. **Plan-and-Execute**先生成结构化计划，再按节点执行，适合多文件开发、研究报告等具有多个交付物和依赖的任务。它便于预算、权限、并行和节点验证，但初始计划可能因新信息失效。

3. 生产系统通常混合使用：外层Plan-and-Execute控制目标、DAG、预算和审批，不确定节点内部用ReAct探索；结果写回事实层，影响关键前提时触发局部Replan。稳定子流程固化为Workflow。

4. 选型依据步数、依赖密度、环境动态性、风险和可验证性。ReAct需设置最大轮数、重复检测和停止条件；Plan-and-Execute需设置计划版本、前提校验和重规划阈值。

**相关知识点：** ReAct、Plan-and-Execute、Agent Loop、DAG、局部规划、全局规划、动态重规划、Workflow。

### 10. LLM如何判断自己的结果是否正确？

**LLM无法通过主观置信度证明答案正确，可靠判断必须依赖任务契约、外部证据和独立验证。**

1. 将答案拆成可核验主张，为每项指定证据和条件。数学题重新计算，代码题运行测试，事实题检索权威来源，写操作回读真实状态。**确定性验证应优先于语言模型自评**。

2. 模型可反向检查、生成反例、比较独立推理路径或检查约束遗漏，但这些方法共享训练偏差与上下文，可能重复确认同一错误。因此Self-Reflection只能发现部分问题，不能证明正确。

| 方法 | 能发现的问题 | 主要局限 |
| --- | --- | --- |
| Self-Reflection | 明显矛盾、遗漏 | 与原答案错误相关 |
| Self-Consistency | 推理路径不稳定 | 多数一致仍可能错误 |
| LLM Judge | 语义质量与Rubric | 偏好偏差、提示敏感 |
| 外部Validator | 可执行事实与不变量 | 需明确验证接口 |

3. 无唯一答案时，独立Judge按固定Rubric评价正确性、完整性、相关性和安全性，并引用证据；高风险任务使用不同模型、多评审器或人工复核。Judge应看原始材料而非生成摘要。

4. 输出包含PASS、FAIL和UNCERTAIN，并给出失败项、证据、置信度及缺失信息。置信度需用标注集校准，不能采用模型口头概率。证据冲突、过期或验证器不可用时，应标记不确定并补证。

**相关知识点：** Self-Reflection、Self-Consistency、外部验证、LLM-as-a-Judge、Rubric、置信度校准、证据链。
<a id="plan-143"></a>
### 11. ReAct模式如何处理执行失败问题？

**ReAct通过“推理—行动—观察”闭环把执行失败转化为新Observation，再据错误类型决定修参、重试、换工具或终止。**

1. Action执行后，Runtime生成结构化Observation，包括错误码、可重试性、Retry-After、副作用状态和证据，而非仅回填异常。模型据此更新假设与下一动作。

2. 宿主约束恢复策略：瞬时错误可Retry，参数错误应Repair，能力不匹配则换工具，前提失效时Replan；权限、合规和不可逆风险必须停止，**模型不得用新Thought绕过安全策略**。

| Observation | 下一动作 | 计划是否变化 |
| --- | --- | --- |
| 超时、限流、偶发5xx | 退避Retry | 否 |
| 参数校验失败 | 修正Action | 局部调整 |

### 15. MCP 在 Agent 中解决了什么问题？

**MCP标准化AI应用与外部工具、数据和提示的连接，使能力可发现、可协商并跨Host复用。**

1. 没有统一协议时，每个框架都要为数据库或SaaS编写适配器。MCP采用Host—Client—Server架构与JSON-RPC，初始化协商版本和能力，运行时以list、read/get、call等方法交互。

2. Server暴露**Tools、Resources和Prompts**：分别表示动作、URI数据与模板；listChanged和订阅支持动态变化。stdio与Streamable HTTP使本地和远程服务使用同一数据协议。

| --- | --- | --- |
| Function Calling | 模型调用结构 | 服务发现 |
| MCP | 能力发现与交互 | 业务决策 |
| API/SDK | 单服务接口 | 跨生态统一 |
| Workflow | 多步骤顺序 | 协议适配 |

### 21. 如何量化反思效果？

**反思效果应通过“同等预算下是否提高任务成功率”量化，并同时衡量修正收益、额外成本和负面回归。**

1. 建立无反思基线与反思实验组，固定模型、工具、任务集、采样参数和总预算，只改变反思策略。核心指标包括首次成功率、最终成功率、错误修复率和回归率；其中净修正率可定义为“修复失败样本数减去破坏正确样本数”占样本总数的比例。

2. 效果不能只看准确率，还要计算每次成功修正消耗的Token、延迟、工具调用和费用，并观察平均反思轮数。**边际收益应按轮次统计**：若第二、三轮带来的成功率增量快速下降，说明继续反思的经济性不足，应设置提前停止条件。

| 指标 | 计算重点 | 说明 |
| --- | --- | --- |
| 最终成功率增量 | 反思组减基线组 | 衡量总体收益 |
| 错误修复率 | 失败转成功比例 | 衡量纠错能力 |
| 回归率 | 正确转失败比例 | 衡量副作用 |
| 单位修正成本 | 总增量成本除以净修正数 | 衡量经济性 |

3. 评测集按推理、代码、工具调用和长链任务分层，并覆盖可修复与不可修复错误，避免平均分掩盖退化。采用配对实验和置信区间判断提升是否显著，同时审查反思是否真正利用新证据，而非偶然采样得到正确答案。线上再用任务完成率、人工接管率和用户返工率校准离线结果。

**相关知识点：** Reflection、A/B测试、配对实验、净修正率、回归率、边际收益、单位修正成本、置信区间、反思预算、终止条件。
