### PLAN-004 · 任务拆解以后，Agent如何决定先做什么、后做什么？什么时候调用模型，什么时候调用工具？（DeepSeek二面）

> 稳定 ID：`PLAN-004`｜原题号：4

**执行顺序首先服从任务依赖，再综合关键路径、信息增益、风险和资源成本排序；模型负责认知决策，工具负责确定性操作。**

1. Scheduler根据DAG计算入度，只把依赖全部满足的节点放入Ready Queue。无依赖且没有资源冲突的节点可以并行；共享文件、数据库记录或独占资源的节点需要串行或加锁。

2. 就绪节点按**关键路径、截止时间、用户等级、等待时长、失败概率和资源配额**排序。低成本信息收集可提前执行以验证假设；不可逆操作应等待证据、权限和审批齐备。

| 任务特征 | 推荐执行主体 | 典型场景 |
| --- | --- | --- |
| 语义模糊、需要推理 | 模型 | 意图理解、方案取舍 |
| 实时或外部信息 | 工具 | 搜索、数据库查询 |
| 精确且可执行操作 | 工具 | 计算、代码运行、文件写入 |
| 固定规则和格式校验 | 普通代码 | Schema、状态转换 |

3. **Tool Router**依据节点目标、Schema、权限、幂等性、实时性和费用召回候选。模型只生成调用意图和参数，Runtime负责校验、授权与执行，避免模型直接产生副作用。

4. Validator检查业务结果，不能只看HTTP状态。瞬时错误有限重试，参数错误先修正，能力不匹配时更换工具；前提或路径失效时才局部重规划，并记录原因、成本和计划版本。

**相关知识点：** 拓扑调度、Ready Queue、关键路径、优先级调度、Tool Selection、Runtime、Validator。

### PLAN-008 · DAG任务调度完整执行流程（Agent初级）

> 稳定 ID：`PLAN-008`｜原题号：8

**DAG调度通过拓扑关系控制执行顺序，使依赖任务串行推进、独立任务并行运行，并把失败影响限制在相关分支。**

1. Planner将目标拆成节点，声明输入输出、执行器、资源、超时、重试和Success Criteria；再根据数据依赖、控制依赖及资源冲突建立边。提交前执行**环检测、依赖闭包和可达性检查**。

2. Scheduler计算入度，将入度为零且资源满足的节点放入Ready Queue。Worker通过原子更新或租约把节点改为RUNNING并续租；租约支持失联接管，幂等键防止重复副作用。

| 节点状态 | 含义 | 后续动作 |
| --- | --- | --- |
| PENDING | 依赖未满足 | 等待前置节点 |
| READY | 可以执行 | 进入调度队列 |
| RUNNING | Worker执行中 | 心跳、超时监控 |
| SUCCESS/FAILED | 验证完成 | 释放后继或恢复 |

3. Executor完成节点后，Validator按成功标准验收。成功则持久化输出，将后继节点入度减一；失败则根据错误类型进行有限重试、参数修复、补偿或局部Replan。共享资源即使图上无直接依赖，也必须加锁或串行。

4. 当所有终止节点成功时聚合结果并完成任务；关键节点不可恢复失败时停止受影响分支。调度器还需处理取消、超时、优先级老化和动态节点插入，并记录**关键路径、队列等待、节点耗时、重试率和执行Trace**。

**相关知识点：** DAG、拓扑排序、入度、Ready Queue、Worker租约、关键路径、结果聚合。

### PLAN-014 · 高并发任务如何排队和限流？（豆包二面）

> 稳定 ID：`PLAN-014`｜原题号：14

**高并发Agent系统应通过持久化队列削峰、多级限流保护模型与工具，并以公平调度实现租户和任务隔离。**

1. 请求进入后先完成鉴权、配额、幂等和参数检查，再写入持久化队列。队列按租户、任务优先级、模型或工具资源类型分区；在线与离线、长任务与短任务应隔离，避免长任务占满Worker并拖垮交互请求。

2. 限流覆盖全局、租户、用户、模型和工具多个层级，同时约束**RPM、TPM、并发数、队列长度和费用预算**。令牌桶允许有限突发，适合API入口；漏桶平滑输出，适合保护处理速率稳定的下游；Semaphore控制执行并发。

| 机制 | 解决的问题 | 触发后的动作 |
| --- | --- | --- |
| Queue | 瞬时流量削峰 | 排队、异步返回 |
| Rate Limit | 下游容量保护 | 延迟或拒绝 |
| Backpressure | 防止积压扩散 | 收紧入口 |
| Circuit Breaker | 故障服务隔离 | 快速失败或降级 |

3. Scheduler采用加权公平队列，为每个租户设置最大并发和最小资源份额；优先级老化防止低优任务长期饥饿。Worker通过租约和可见性超时接管失败任务，消费端使用幂等键吸收重复投递。

4. 队列积压时按顺序执行批处理、扩容、模型降级、限制新任务和拒绝低优请求。系统监控**排队时长、积压年龄、吞吐量、限流率、下游错误率和租户资源份额**，依据SLO动态调整阈值。

**相关知识点：** 异步队列、多级限流、令牌桶、漏桶、Backpressure、公平调度、租户隔离。

### PLAN-020 · Rule 与 Prompt 如何协同工作？

> 稳定 ID：`PLAN-020`｜原题号：20

**Rule负责确定性边界与强约束，Prompt负责开放语义理解与生成，两者应通过结构化接口组成分层决策链。**

1. 执行前由规则完成权限校验、参数限制、敏感操作拦截和输入规范化；再把目标、上下文、候选动作及输出Schema写入Prompt。模型结果返回后接受规则验证，失败时进入修复、降级或审批，形成**规则前置—模型推理—规则后验**闭环。

| 机制 | 适合处理 | 不适合处理 |
| --- | --- | --- |
| Rule | 合规边界、精确条件、状态机 | 长尾语义、模糊意图 |
| Prompt | 意图理解、推理、内容生成 | 强一致性与安全兜底 |
| 混合链路 | 受控的开放任务 | 无监控的自由执行 |

2. 法律限制、金额上限、工具白名单必须由代码或策略引擎执行，不能只写入Prompt；摘要风格、任务拆解和方案比较适合交给模型。若两者冲突，应以**权限与安全规则优先**并记录原因，禁止自然语言覆盖系统策略。

3. 接口层使用JSON Schema、枚举动作、证据和置信度。规则只消费可验证字段，不解析自由文本；Prompt明确缺失信息、禁止猜测项和失败格式。结构化契约可隔离提示词变化，便于测试和回滚。

4. 评估应覆盖规则覆盖率与误拦截率、Prompt成功率与格式遵从率，以及端到端越权率、回退率、延迟和成本。两者须独立版本化，并通过离线样本、对抗测试和灰度发布验证。

**相关知识点：** 规则引擎、Prompt Engineering、策略优先级、结构化输出、Guardrail、JSON Schema、灰度发布。

### PLAN-021 · Skill Matching 如何实现？

> 稳定 ID：`PLAN-021`｜原题号：21

**Skill Matching应采用“硬约束过滤、语义召回、效果排序、运行时验证”的多阶段架构，而不是仅比较名称相似度。**

1. 每个Skill要有机器可读的能力卡，包含功能描述、适用与禁用场景、输入输出Schema、工具、权限、成本、版本及成功标准。请求被解析成**目标、对象、交付物、约束、风险和上下文**，形成统一Task Spec。

| 阶段 | 核心方法 | 解决的问题 |
| --- | --- | --- |
| 硬过滤 | Schema、权限、环境规则 | 排除不可执行Skill |
| 候选召回 | 关键词与向量检索 | 覆盖语义近似能力 |
| 精排 | LLM或学习排序 | 判断上下文适配度 |
| 验证 | 预条件与结果校验 | 防止匹配正确但执行失败 |

2. 先检查输入类型、权限、工具可用性和禁用条件；再用BM25与向量检索召回候选，兼顾精确术语和语义表达。精排综合语义相关度、参数完整度、历史成功率、延迟、成本及风险，并返回选择理由。能力相似时，优先选择边界更窄、验证更充分的Skill。

3. 最高分低于阈值，或前两名分差小且副作用不同，应请求澄清；低风险任务可受限试运行。需要多个能力时，由Planner构建**Skill依赖图**，明确数据传递、前后置条件和失败补偿。

4. 线上记录候选集、评分、选择、版本和结果，以Top-K召回率、匹配准确率、误调用率、完成率、延迟及成本评估。Skill变更需经过冲突检测、离线回放和灰度发布。

**相关知识点：** 能力注册表、Task Spec、混合检索、学习排序、Schema校验、Skill依赖图、置信度阈值。

### PLAN-034 · Workflow 如何支持并行执行？

> 稳定 ID：`PLAN-034`｜原题号：34

**Workflow通过DAG依赖、就绪队列和资源约束识别可并发节点，并在汇合点统一验证和聚合结果。**

1. 节点声明输入输出、前置条件、资源、副作用和成功标准；边表达数据、控制依赖与资源冲突。构图后执行环和依赖校验，前驱成功且产物持久化后，节点进入**Ready Queue**。无依赖仅表示逻辑可并行。

| 并行模式 | 特点 | 适用场景 |
| --- | --- | --- |
| Fan-out/Fan-in | 分发后统一汇合 | 多源检索、批量分析 |
| Map-Reduce | 并行映射后归并 | 大规模数据处理 |
| 竞速 | 首个合格结果胜出 | 多模型或多工具兜底 |
| 流水线 | 不同阶段重叠执行 | 连续数据处理 |

2. Scheduler按关键路径、优先级、配额和容量分配节点。Worker用租约避免重复领取，外部写操作设置幂等键。写入同一资源的节点须通过锁、资源边或分区串行化；模型和API调用还受并发与速率限制。

3. Fan-in需明确汇合策略：全部成功、达到法定数量、首个合格或超时使用部分结果。聚合前验证分支Schema和质量；关键分支失败时选择重试、取消同级、降级或整体失败。

4. 并行度应自适应：队列积压时扩容Worker，下游限流或错误率上升时降低并发并背压。记录等待、执行、锁竞争和汇合耗时，评估关键路径、并行加速比、资源利用率、重复执行率和成功率。

**相关知识点：** DAG、Ready Queue、Fan-out/Fan-in、Map-Reduce、关键路径、资源锁、背压、结果聚合。

### PLAN-044 · 不同类型任务对应 Agent 资源调度策略差异

> 稳定 ID：`PLAN-044`｜原题号：44

**Agent资源调度应由任务复杂度、时延目标、工具需求、风险和预算共同决定，并采用差异化模型、并发与持久化策略。**

1. Router提取任务类型、步骤数、工具、并行性、副作用及SLA，生成资源档位。简单问答使用小模型；复杂推理升级强模型；长任务启用Planner、状态存储和异步Worker；高风险任务降低并发并审批。

| 任务类型 | 核心资源策略 | 主要目标 |
| --- | --- | --- |
| 简单问答 | 小模型、单次调用、缓存 | 低时延低成本 |
| 检索分析 | 检索并发、重排、证据缓存 | 召回与可信度 |
| 代码修改 | 沙箱、测试Worker、较长上下文 | 正确性与隔离 |
| 复杂开发 | DAG、多Agent、Checkpoint | 吞吐与可恢复 |
| 高风险执行 | 强验证、串行、人工门控 | 安全与审计 |

2. 无依赖只读任务可并行，写同一资源的节点须串行或加锁。Scheduler按优先级、期限、配额和容量分配Worker，并以**背压与速率限制**保护下游。交互任务优先首Token时延，批处理优先吞吐与成本。

3. 模型采用级联：小模型处理高置信度请求，低置信度或高难度任务升级强模型；验证失败时才增加预算。上下文用摘要、检索和缓存控制长度，工具结果复用需校验时效与权限。

4. 按任务类型监控完成率、P95延迟、成本、队列等待、重试率和风险事件。策略经A/B实验校准；错误率或下游延迟上升时降并发、切换模型或降级只读。

**相关知识点：** Model Routing、资源配额、优先级调度、背压、模型级联、DAG、多Agent、成本治理。

### PLAN-062 · 多文件代码修改任务如何进行规划？

> 稳定 ID：`PLAN-062`｜原题号：62

**多文件修改应先建立符号级影响图，再按接口、实现、调用方、测试和文档的依赖顺序形成可验证的文件级计划。**

1. 先读取仓库规范、构建方式和测试入口，复现问题或建立基线。通过关键词、语言服务器、符号索引、引用、调用图和配置链定位文件；除直接命中项，还要检查公共类型、序列化、生成代码及跨模块测试。

| 阶段 | 主要产物 | 验证方式 |
| --- | --- | --- |
| 定位 | 文件、符号与调用关系 | 基线测试、影响面审查 |
| 契约 | 接口、Schema与不变量 | 类型检查、契约测试 |
| 实现 | 最小差异补丁 | 格式化、静态分析 |
| 集成 | 调用方与配置更新 | 单测、集成测试 |
| 验收 | 变更摘要与证据 | 全量回归、Diff审查 |

2. 节点记录目标文件、修改目的、依赖、不变量、验收命令和回滚点，形成**文件级DAG**。先确定接口和数据模型，再改实现与调用方，最后更新测试和文档；写同一文件或公共契约的节点串行，独立模块可并行。

3. 采用最小变更原则，避免顺手重构。每完成节点即运行单测和静态检查，汇合后执行编译、集成与回归测试。失败依据编译错误、测试日志和运行证据修复，不能凭主观反思改动。

4. 依赖升级、数据库迁移、公共API破坏性变更和大范围删除应设置审批、备份及版本恢复点。最终检查未提交差异、生成文件、配置、测试覆盖和向后兼容性，并记录修改文件、验证命令、已知风险和未覆盖项。

**相关知识点：** 符号索引、调用图、影响分析、文件级DAG、契约测试、最小变更、回归测试、Diff审查。

### PLAN-065 · 多Agent系统中的任务分发（Task Dispatch）如何设计？

> 稳定 ID：`PLAN-065`｜原题号：65

**多Agent任务分发应以DAG和任务契约为基础，按照能力、权限、负载、成本与历史效果选择执行者，并由Orchestrator统一治理。**

1. 主Agent把目标拆成可交付、验证和重试的节点，明确依赖与资源冲突。Task Contract包含目标、输入版本、输出Schema、上下文、操作范围、期限、预算和成功标准，防止责任重叠。

| 分发策略 | 适用场景 | 主要风险 |
| --- | --- | --- |
| 能力匹配 | 专业化任务 | 能力描述不准确 |
| 负载均衡 | 同质Worker池 | 忽略任务难度 |
| 竞速执行 | 时延敏感、结果可验证 | 成本放大 |
| 广播协作 | 方案探索 | 冲突与通信膨胀 |
| 固定所有权 | 模块长期维护 | 单点瓶颈 |

2. Orchestrator以Schema、权限和工具过滤，再按相关度、成功率、负载、成本和风险精排。子Agent只获得**最小上下文与权限**；无依赖节点可并行，写同一文件需串行或分支隔离。

3. 状态通过任务存储或消息总线传递，消息包含Task ID、Attempt ID、版本和幂等键。子Agent返回产物、证据、假设和风险，不覆盖他人结果；Orchestrator检查Schema、合并冲突并验证。

4. 失败时选择重试、替换、降级或局部重规划，并限制并发、委派深度、消息量和预算。评估分发准确率、队列等待、并行加速比、冲突率、返工率、Agent利用率、完成率及单位成本。

**相关知识点：** Orchestrator、Task Contract、任务DAG、能力匹配、最小权限、消息总线、结果聚合、委派预算。

### PLAN-073 · Task Tree和DAG任务规划有什么区别？

> 稳定 ID：`PLAN-073`｜原题号：73

**Task Tree强调目标的层级分解，DAG强调任务间的依赖与可调度性；前者适合表达思路，后者更适合作为执行计划。**

1. Tree中除根节点外每个节点通常只有一个父节点，路径表示“整体—部分”的从属关系；DAG允许节点被多个后继共享，边表示数据或控制依赖。因此同一项环境检查在Tree中可能重复出现，在DAG中可作为公共前置节点只执行一次。

2. 针对“Task Tree和DAG任务规划有什么区别”，构图前为节点声明**输入、输出、成功标准、资源和副作用**，再从数据依赖、控制依赖及资源冲突推导边，并执行环检测、依赖闭包和可达性检查。依赖满足的节点进入Ready Queue，Worker通过租约或条件更新领取，避免并发重复执行。

| 维度 | Task Tree | DAG |
| --- | --- | --- |

### PLAN-101 · Agent如何实现串行执行和并行执行？

> 稳定 ID：`PLAN-101`｜原题号：101

**串行与并行执行应由DAG依赖和资源约束决定：有强依赖或写冲突的节点串行，无依赖且资源独立的节点并行。**

1. Planner声明节点输入输出、前置条件、资源读写集和副作用，再生成DAG。Scheduler维护前驱数；入度为零的节点进入**Ready Queue**，形成串行链、并行分支和Fork-Join。

| 模式 | 调度条件 | 典型实现 |
| --- | --- | --- |
| 串行 | 有依赖或写冲突 | await、状态机 |
| 并行 | 输入和资源独立 | Future、任务队列 |
| 限制并行 | 服务存在配额 | Semaphore、令牌桶 |
| 竞速 | 任一候选成功即可 | Promise.any |
| 汇合 | 等待全部或法定数 | Barrier、Join |

2. 并行节点由Worker Pool消费，以租约或CAS保证单次领取，并通过Semaphore限流。I/O任务适合异步并发，CPU任务使用进程池；图上无边也不能忽略数据库锁、文件写入和API配额。

3. 节点成功后持久化产物并原子减少后继入度；Join按all、any或quorum聚合。并行分支隔离上下文，通过版本化产物交换数据，避免共享内存竞态；输出合并使用确定性规则。

4. 关键分支失败可取消同组任务，非关键分支允许降级；超时和取消沿子任务传播，已产生副作用的动作先补偿。监控并行度、队列等待、关键路径、资源利用率和重复执行率，调整限流参数。

**相关知识点：** DAG、拓扑调度、Ready Queue、Fork-Join、Worker Pool、Semaphore、CAS、竞态条件、结构化并发。

> 稳定 ID：`PLAN-105`｜原题号：105

**避免过细拆解的关键是为节点设置最小工作量和独立价值门槛，并用协调成本模型主动合并低风险连续步骤。**

1. 节点只有在能产生可复用产物、形成验证点、隔离风险、支持并行或降低重试范围时才值得独立存在。仅做字段搬运、格式微调或共享同一上下文的连续动作，不应拆成多次调用。

| 判断项 | 保持拆分 | 建议合并 |
| --- | --- | --- |
| 验证 | 可独立验收 | 只能整体判断 |
| 失败 | 错误类型和恢复路径不同 | 必须一起重做 |
| 上下文 | 输入边界清晰 | 大量重复传递 |
| 执行器 | 不同Tool或权限 | 同一Tool连续操作 |
| 风险 | 含独立副作用 | 均为低风险转换 |

3. 采用分层计划：顶层保留业务里程碑，底层将稳定连续动作封装为Skill、批处理Tool或Workflow子流程。对同一数据源的多次读取合并查询，对同一模型的相邻推理合并Prompt，无依赖的小调用则批量或受控并行。

4. 运行时以平均节点耗时、协调耗时占比、上下文重复率、模型调用数、局部重试收益和关键路径监控粒度。若协调成本持续高且失败总是成组出现，应自动提出合并候选，经回放评测确认完成率不下降后再调整模板。

**相关知识点：** 任务粒度、Node Fusion、协调成本、分层规划、复合Skill、批处理、上下文复用、关键路径。

### PLAN-107 · Executor模块通常负责哪些工作？

> 稳定 ID：`PLAN-107`｜原题号：107

4. 执行后保存原始响应、状态码、工具回执、耗时、费用和错误分类，大产物写入对象存储。Executor只报告协议与运行状态，业务成功由Validator判断；需要换路径时将证据交给RePlanner。

### PLAN-113 · 如何设计Agent的任务优先级调度策略？

> 稳定 ID：`PLAN-113`｜原题号：113

**任务优先级应由业务价值、截止时间、关键路径、风险、等待时长和资源成本共同计算，并以公平性与配额约束动态修正。**

1. 先定义服务端优先级类别，如安全告警、人工交互、在线请求和后台批处理；类别内再计算**Priority Score**，组合业务等级、截止时间、下游阻塞数、关键路径、等待时间、重试次数和资源成本。

| 因素 | 提升优先级的条件 | 控制风险 |
| --- | --- | --- |
| 截止时间 | 剩余裕量变小 | 防止虚报紧急 |
| 关键路径 | 阻塞大量后继 | 不忽略资源冲突 |
| 等待时长 | 排队时间持续增加 | Aging防止饥饿 |
| 业务等级 | SLA或风险更高 | 由服务端策略赋值 |
| 资源成本 | 可释放瓶颈 | 防止大任务延期 |

2. Scheduler只在Ready节点中排序，高优任务不能越过依赖。按租户、模型和Tool设置配额、Semaphore与加权公平队列，防止单一客户占满资源；共享锁使用优先级继承，降低优先级反转。

3. 紧急任务到达时可调整队列；只有无副作用、可暂停且有检查点的任务才能抢占。付款、发布或外部写入节点必须到达安全点再暂停，不能为时延破坏一致性。

4. 优先级随等待、资源健康、截止时间和Replan动态重算，并记录原因。监控P50/P95排队时间、SLA违约率、饥饿率、抢占次数、公平性和资源利用率；通过回放和A/B测试校准权重。

**相关知识点：** Priority Queue、Priority Score、Aging、关键路径、加权公平队列、优先级反转、抢占、SLA、资源配额。

### PLAN-118 · Agent如何构建任务DAG？

> 稳定 ID：`PLAN-118`｜原题号：118

**构建任务DAG应先从验收条件反推原子产物，再依据数据、控制、条件和资源依赖连边，最后执行图一致性校验。**

1. Planner将Task Spec拆成单一责任且可验证的节点。节点声明**Node ID、输入、输出Schema、执行器、前置条件、成功标准、资源读写集和副作用**；输入来自用户、环境或上游产物，不能依赖隐式上下文。

| 边类型 | 判定条件 | 示例 |
| --- | --- | --- |
| 数据边 | B消费A的输出 | 编译依赖代码生成 |
| 控制边 | 业务要求先A后B | 审批后发布 |
| 条件边 | A的结果决定B是否启用 | 测试失败才修复 |
| 资源边 | 节点竞争同一可变资源 | 串行修改同一文件 |

2. 自动连边采用生产者—消费者匹配：把输入字段绑定到产物生产者，再补充领域规则、权限与事务约束。共享前置只保留一个节点，多分支在Join节点按all、any或quorum聚合；资源独立的节点可并行。

3. 构图后检查缺失生产者、重复节点、环、不可达节点、依赖闭包、Schema兼容和资源冲突，并以**传递约简**去除冗余边。循环应封装为带退出条件的迭代节点或状态机，不能破坏DAG定义。

4. DAG以Plan Schema持久化。前驱验证成功且产物落盘后，节点进入Ready Queue；新证据或失败触发Replan时，仅替换受影响子图并重算入度，保留有效节点。评估依赖准确率、并行度、关键路径和重复执行率。

**相关知识点：** DAG、Task Spec、生产者—消费者、环检测、拓扑排序、传递约简、Join节点、Ready Queue、关键路径。

### PLAN-119 · 如何识别任务之间的依赖关系？

> 稳定 ID：`PLAN-119`｜原题号：119

**任务依赖应通过输入输出匹配、业务前置条件、条件分支和资源读写冲突共同识别，而不是依据自然语言中的先后顺序猜测。**

1. 为任务建立**Task Contract**：目标、输入及来源、输出Schema、前置条件、资源读写集、权限和副作用。若B的必需输入由A产生，则A→B是数据依赖；若规则要求A通过后才能执行B，则是控制依赖。

| 识别信号 | 依赖类型 | 例子 |
| --- | --- | --- |
| 输出匹配输入 | 数据依赖 | 报告依赖查询 |
| 审批前置条件 | 控制依赖 | 审批后发布 |
| 结果决定节点启用 | 条件依赖 | 失败才修复 |
| 资源读写冲突 | 资源依赖 | 修改同一文件 |
| 外部事件或人工响应 | 事件依赖 | 等待回调 |

2. 静态识别用Schema和生产者—消费者映射连边，再用领域规则补充事务、权限与合规顺序。代码任务读取符号、调用图和构建依赖；数据任务分析血缘和读写集。LLM补充开放语义，结果仍需规则校验。

3. 对候选边记录来源与置信度。硬依赖加入DAG；低置信且影响顺序的关系通过只读检查或澄清确认。构图后检查缺失生产者、环、不可达节点、Schema不兼容和资源冲突，并以传递约简去除冗余边。

4. 运行时通过工具结果、Validator和事件发现新依赖，例如“等待审批”。此时生成新版本，仅更新受影响子图并重算Ready节点。用依赖准确率、漏边率、误串行率、关键路径和冲突率评估质量。

**相关知识点：** Task Contract、数据依赖、控制依赖、资源依赖、生产者—消费者、数据血缘、环检测、传递约简。

### PLAN-122 · 如何实现任务优先级计算？

> 稳定 ID：`PLAN-122`｜原题号：122

**任务优先级应先确定服务等级，再对截止时间、关键路径、业务价值、等待时长、风险和成本归一化加权。**

1. 优先级不能由LLM自由打分。安全告警、人工交互、在线请求和后台任务先由服务端分层；只有Ready节点参与排序。用户表达紧急程度，但不能提升租户等级或绕过权限。

| 因子 | 一种计算方式 | 作用 |
| --- | --- | --- |
| Deadline | 1−剩余裕量/上限 | 越近超时越高 |
| Critical Path | 下游最长路径/全图最长路径 | 解除瓶颈 |
| Business Value | 服务等级映射0—1 | 业务价值 |
| Aging | 等待时间/上限 | 防止饥饿 |
| Risk | 损失或影响范围归一化 | 风险处置 |
| Cost | 资源占用归一化 | 控制昂贵任务 |

2. 可定义**Score=w₁D+w₂C+w₃V+w₄A+w₅R−w₆Cost**，因子截断并归一化，权重按领域配置。分数相同时按截止时间、入队时间和Task ID排序，保证可解释且重放一致。

3. 动态因素随环境重算：等待增加Aging，工具降级改变Cost，Replan改变关键路径，SLA裕量缩小。为防队列抖动，设置最小重排间隔、滞后区间和批量更新；共享锁采用优先级继承。

4. 权重通过回放和A/B测试校准，在SLA违约、等待、资源利用率和公平性间优化。记录分数分解与排序原因，监控饥饿率、抢占率、P95排队时长和误判率，禁止在线自学习直接改权重。

**相关知识点：** Priority Score、归一化、Deadline Slack、关键路径、Aging、优先级继承、加权公平、SLA。

### PLAN-123 · Agent如何支持并行任务执行？

> 稳定 ID：`PLAN-123`｜原题号：123

**Agent并行执行应建立在DAG依赖、资源隔离和受控并发之上，仅并行输入独立且不会产生写冲突的任务。**

1. Planner声明节点输入输出、资源读写集、副作用和依赖。Scheduler通过入度识别Ready节点，形成Fork-Join；存在数据依赖、控制依赖或共享可变资源的节点必须串行，不能凭语义不同就并行。

| 并行模式 | 适用场景 | 汇合策略 |
| --- | --- | --- |
| 全部并行 | 独立检索或分析 | all成功后继续 |
| 竞速执行 | 等价候选路径 | any成功即取消其余 |
| 法定数量 | 多评审器或数据源 | quorum达标 |
| 流水线 | 阶段重叠处理批次 | 按批次提交 |

2. Ready节点进入队列，由**Worker Pool**异步消费。按租户、模型、Tool和API设置Semaphore、令牌桶及费用预算；I/O任务用异步并发，CPU任务用进程池，队列积压时启用背压。

3. 分支使用局部上下文和独立Attempt，通过版本化产物交换数据。写同一文件、数据库行或外部资源时使用锁、版本检查或单写者；结果由确定性Reducer合并，解决重复、顺序和冲突。

4. 关键分支失败可取消同组任务，非关键分支可降级；有副作用的任务需到达安全点并补偿。监控并行度、关键路径、队列等待、资源利用率、冲突率和重复执行率；协调成本过高时降低并发或合并节点。

**相关知识点：** DAG、Fork-Join、Worker Pool、Semaphore、背压、上下文隔离、乐观锁、Reducer、结构化并发。

### PLAN-124 · 什么是关键路径（Critical Path）？

> 稳定 ID：`PLAN-124`｜原题号：124

**关键路径是任务依赖网络中累计工期最长的起止路径，它决定项目在当前约束下能够完成的最早时间。**

1. 将任务表示为DAG，节点记录持续时间，边表示前置依赖。采用前向计算得到最早开始与最早完成时间，后向计算得到最晚开始与最晚完成时间；**总时差为零的连续任务构成关键路径**。项目最短工期等于该路径各节点耗时之和，任一关键节点延期都会直接推迟整体完成时间。

2. 非关键任务具有可用时差，短期延迟未必影响总工期；但任务耗时、依赖关系或资源供给变化后，关键路径可能转移，因此它不是一次计算后永久固定的静态标签。

| 概念 | 判定依据 | 管理重点 |
| --- | --- | --- |
| 关键路径 | DAG中最长依赖链 | 缩短端到端工期 |
| 瓶颈 | 吞吐受限的资源或环节 | 提升系统处理能力 |
| 关键链 | 依赖叠加资源约束 | 设置项目与接驳缓冲 |

3. Agent调度中，应给关键节点优先分配模型、工具配额和Worker，提前预取输入，并将可拆节点并行化；优化非关键节点只有在耗尽时差或即将转为关键节点时才会改善总时延。若要压缩工期，可采用**赶工**增加资源，或采用**快速跟进**重叠原本串行的阶段，但需评估成本、返工和并发冲突。

4. 运行时根据真实耗时持续重算关键路径，并监控关键节点延迟、剩余时差、路径切换和预计完工时间。存在多条等长路径时均应视为关键路径；资源互斥明显时，还需结合资源约束调度，不能仅依赖理想DAG。

**相关知识点：** DAG、关键路径法、前向计算、后向计算、总时差、赶工、快速跟进、瓶颈、关键链。

### PLAN-152 · Agent执行过程中如何实现人工审批和人工接管？

> 稳定 ID：`PLAN-152`｜原题号：152

**人工审批用于授权某个待执行动作，人工接管用于转移任务控制权，两者都应由持久化状态机和工具网关强制执行。**

1. Planner为节点声明Approval Policy。删除、付款、发布、权限变更等动作执行前进入WAITING_APPROVAL并写Checkpoint；调度器停止该节点及下游，独立分支可继续。

2. 审批界面展示**目标、工具、参数、资源、副作用、可逆性及证据**。Approval Token绑定task_id、node_id、参数哈希、审批人和有效期；参数或计划版本变化即失效。

| 模式 | 控制权 | 典型结果 |
| --- | --- | --- |
| Approve | 仍由Agent执行 | 按已批准参数继续 |
| Reject | Agent停止该动作 | Replan或安全终止 |
| Takeover | 转移给人工 | Agent只提供上下文 |
| Return | 交还Agent | 从新Checkpoint恢复 |

3. 接管时切为HUMAN_CONTROLLED，撤销Agent的Lease和令牌，阻止迟到提交。系统提供计划、轨迹、产物、失败证据和未完成项；人工操作仍需权限、幂等和审计。

4. 人工完成后写入决策、回执和Checkpoint，再结束或交还Agent。审批超时按策略暂停、降级或取消，不得默认同意。请求、参数Diff、审批人和结果进入审计日志，并监控等待时长、拒绝率和接管率。

**相关知识点：** Human-in-the-Loop、Approval Token、参数哈希、状态机、Lease、人工接管、最小权限、审计日志。

### PLAN-153 · 如何设计Agent的状态机？

> 稳定 ID：`PLAN-153`｜原题号：153

**Agent状态机应把任务生命周期、节点执行和人工门控显式建模，使每次迁移可校验、可持久化、可恢复。**

1. 采用两层状态机：任务层包含CREATED、RUNNING、PAUSED及终态；节点层包含PENDING、READY、RUNNING、WAITING及终态。终态不可逆，依赖满足后才能进入READY。

2. 迁移定义**Source、Event、Guard、Action、Target**。节点仅在Validator通过且回执保存后转为SUCCEEDED；权限、预算或版本不满足时由Guard拒绝，模型不能改状态。

| 状态类型 | 典型状态 | 核心语义 |
| --- | --- | --- |
| 活动态 | RUNNING | 可继续推进 |
| 等待态 | PAUSED、WAITING | 等待事件 |
| 终态 | COMPLETED、FAILED | 不再迁移 |
| 不确定态 | UNKNOWN | 查询状态 |

3. 状态、Plan Version、Attempt、产物、幂等键、Lease和预算持久化；迁移与Outbox同事务提交，用CAS防双写。Event Log记录事实，Checkpoint用于恢复。

4. 超时、取消、审批、Retry和Replan建模为事件。恢复时加载快照、回放并核对副作用；迟到结果按版本和Fencing Token拒绝。检查不可达状态、非法环、终态外迁和死锁，测试重复消息与并发迁移。

**历史别名：** `PLAN-258`。

**相关知识点：** 有限状态机、层次状态机、Guard、Event、CAS、Outbox、Event Sourcing、Fencing Token。

### PLAN-232 · 企业级 Agent 如何实现高并发、高可用与可扩展架构？

> 稳定 ID：`PLAN-232`｜原题号：232

**企业级Agent应采用无状态控制面、持久化任务状态、异步队列和按资源隔离的Worker池，实现水平扩展与故障接管。**

1. API Gateway完成鉴权、配额与幂等检查后创建Task，Planner和Scheduler保持无状态，Plan、Checkpoint与Lease写入共享存储；消息队列解耦调度和执行。Worker崩溃后由可见性超时或心跳失效触发其他实例从快照接管。

2. 入口完成鉴权、配额和幂等检查后再入队；调度按**租户、优先级、截止时间、任务长度和资源类型**分层。在线与离线、长任务与短任务、GPU与外部API任务应隔离，Worker使用租约、心跳和可见性超时支持故障接管。

| 机制 | 目标 | 关键指标 |
| --- | --- | --- |
| 消息队列 | 削峰与解耦 | 积压量、等待时间 |
| 限流 | 保护下游 | RPM、TPM、并发 |
| 公平调度 | 租户隔离 | 资源份额 |
| 弹性扩缩容 | 匹配供需 | 利用率、扩容延迟 |

3. 限流同时约束RPM、TPM、并发数和费用，覆盖全局、租户、用户、模型及工具。队列积压时依次采用批处理、扩容、模型降级、限制新任务和拒绝低**优先级**请求；公平队列与优先级老化用于避免资源垄断和任务饥饿。

**相关知识点：** 异步队列、背压、多级限流、令牌桶、公平调度、租户隔离、弹性扩缩容。

### PLAN-275 · Kafka、RabbitMQ、Redis Stream分别适用于什么场景？

> 稳定 ID：`PLAN-275`｜原题号：275

**Kafka适合高吞吐、可回放的事件流，RabbitMQ适合复杂路由与可靠任务分发，Redis Stream适合已有Redis体系中的轻量低延迟消息场景。**

1. Kafka以提交日志、Partition和Consumer Group提供高吞吐、分区内有序、长期保留和历史重放，适用于日志、数据管道及海量Agent轨迹。其复杂路由不直观，顺序与扩展性受分区键影响。

2. RabbitMQ以Exchange、Binding、Routing Key和Ack支持灵活路由、优先级及死信，适合命令队列与复杂分发。Redis Stream接入简单、延迟低，适合中小规模实时任务，但容量、长期留存和故障语义需谨慎规划。

| 中间件 | 核心优势 | 典型选择 |
| --- | --- | --- |
| Kafka | 吞吐、留存、回放 | 事件流与大规模轨迹 |
| RabbitMQ | 路由、确认、任务语义 | 复杂工作队列 |
| Redis Stream | 轻量、低延迟 | 小中规模实时消费 |

3. 选型应量化吞吐、尾延迟、保留期、重放、路由复杂度、顺序范围和运维能力。**三者都不能替代业务幂等与状态持久化**：生产端仍需Outbox，消费端仍需确认、去重、有限重试和DLQ，并监控积压年龄、延迟与重复率。

**相关知识点：** Kafka Partition、Consumer Group、RabbitMQ Exchange、Routing Key、Redis Stream、Outbox、消息确认、死信队列。

### PLAN-281 · 如何防止某个租户占满全部资源？

> 稳定 ID：`PLAN-281`｜原题号：281

**防止单租户占满资源需要在准入、排队、调度和执行四层实施配额与隔离，并以加权公平调度保障最低份额和可控突发。**

1. 为每个租户配置RPM、TPM、并发任务数、在途Step、GPU时间、外部工具调用和费用预算；入口按租户令牌桶执行准入，超限请求排队或返回Retry-After。配额应包含硬上限与可借用的突发额度，避免空闲资源长期浪费。

2. 使用租户独立逻辑队列或分层队列，由加权公平队列、Deficit Round Robin等算法分配执行槽；长短任务和在线离线任务进一步隔离。**优先级只能在租户份额内生效**，不能让高优先级标签成为突破全局公平性的通道。

| 机制 | 主要作用 | 边界 |
| --- | --- | --- |
| 租户配额 | 限制最大消耗 | 需覆盖多种资源 |
| 公平队列 | 保证调度份额 | 需处理任务成本差异 |
| 资源池隔离 | 限制故障扩散 | 资源利用率可能下降 |
| 突发借用 | 利用空闲容量 | 高负载时必须回收 |

3. 执行层按租户设置连接池、信号量和熔断器，必要时为关键租户建立专用资源池；共享缓存、向量库和日志也应带租户维度，防止隐性争用。监控资源份额、排队P95、拒绝率、借用量和SLO违约，发现异常流量自动收紧配额，但策略调整必须审计、灰度并允许回滚。

**相关知识点：** 多租户隔离、Noisy Neighbor、租户配额、加权公平队列、Deficit Round Robin、令牌桶、资源池隔离、突发借用、熔断。

### PLAN-282 · 优先级队列如何实现？

> 稳定 ID：`PLAN-282`｜原题号：282

**优先级队列应把业务优先级、截止时间和等待时长组合为可比较的调度键，并通过优先级老化与租户配额避免低优先级任务永久饥饿。**

1. 单机可用二叉堆实现入队和出队O(log n)，调度键可按“有效优先级、截止时间、创建时间、Task ID”排序，最后一项保证稳定性。优先级必须由服务端根据任务类型、SLA和用户等级计算，不能直接信任客户端传入值。

2. 分布式场景可使用多个物理优先级队列，调度器按权重轮询；也可在数据库或有序集合中存储Score并原子领取。任务状态、优先级和版本需持久化，Worker通过租约执行。**调整优先级必须采用CAS并记录审计，避免任务同时存在于新旧队列**。

| 实现 | 优势 | 主要限制 |
| --- | --- | --- |
| 二叉堆 | 单机操作高效 | 不直接支持分布式 |
| 多物理队列 | 简单、隔离明确 | 跨队列公平较难 |
| 有序集合 | 动态Score方便 | 需保证领取原子性 |
| 数据库条件领取 | 状态一致、易审计 | 高吞吐下压力较大 |

3. 有效优先级可随等待时间逐步提升，或为各等级保留最小服务份额；再叠加租户加权公平，防止高等级租户垄断。正在执行的任务通常不强制抢占，有安全Checkpoint的长任务才允许协作式抢占。监控各等级排队P95、最大等待时间、饥饿率、抢占次数和SLA违约率，并用突发高优先级流量压测。

**相关知识点：** 优先级队列、二叉堆、有序集合、调度键、优先级老化、任务饥饿、CAS、租约、加权公平、协作式抢占。

### PLAN-285 · 如何实现公平调度（Fair Scheduling）？

> 稳定 ID：`PLAN-285`｜原题号：285

**公平调度不是让所有任务获得相同次数，而是依据租户权重和任务资源成本分配可解释的长期份额，同时保证最低服务与防饥饿。**

1. 先定义公平主体与计量单位：主体可以是租户、团队或优先级，成本不能只按任务数计算，应估算Token、GPU秒、工具调用、并发连接与费用。为每个主体设置权重、最小保障、硬上限和可借用份额，并把未使用容量临时借给活跃队列。

2. 任务成本近似相同时可用加权轮询；成本差异明显时用Deficit Round Robin累积信用并按成本扣减，或用Weighted Fair Queuing近似虚拟完成时间。多资源场景可依据主导资源份额调度。**优先级应在公平份额内部生效，不能绕过租户上限**。

| 算法 | 适用条件 | 特点 |
| --- | --- | --- |
| 加权轮询 | 任务成本接近 | 简单但不感知大小 |
| DRR | 可估算任务成本 | 高效、支持变长任务 |
| WFQ | 需精细份额 | 公平性好、计算更复杂 |
| 主导资源公平 | 多维资源 | 平衡不同资源瓶颈 |

3. 实际消耗与估算偏差应在任务完成后回补信用；长任务通过时间片和Checkpoint避免一次占槽过久，等待任务通过老化获得进展。监控每主体实际份额与目标份额偏差、最大等待时间、SLO和资源利用率，并在单租户洪峰、任务大小悬殊及资源稀缺场景下验证公平性。

**相关知识点：** 公平调度、加权轮询、Deficit Round Robin、Weighted Fair Queuing、主导资源公平、资源成本、信用回补、优先级老化。

### PLAN-290 · 队列消息丢失如何处理？

> 稳定 ID：`PLAN-290`｜原题号：290

**生产端用Outbox或事务消息保证业务提交与发消息一致，Broker启用持久化和副本，消费端在业务提交后ACK。**

1. 丢失可能发生在业务提交后未发送、Broker未持久化、节点故障丢副本，以及消费者先ACK后业务提交。应为每段建立交付状态和消息ID，不能把“客户端调用成功”当作端到端送达。

2. 生产者在同一数据库事务中写业务数据与Outbox，由Relay重试投递并保存Broker确认；Broker开启持久化、多副本及符合风险要求的确认级别。消费者在业务事务成功后再提交Offset或ACK，并按Event ID去重。**可靠投递通常以可能重复换取不丢失**。

| 环节 | 主要措施 | 防范问题 |
| --- | --- | --- |
| 业务到生产者 | 事务Outbox | 提交后未发消息 |
| 生产者到Broker | 确认、重试、幂等生产 | 网络与发送失败 |
| Broker存储 | 持久化、多副本 | 节点故障 |
| 消费者 | 提交后ACK、Inbox | 先确认后处理 |

3. 定期以Outbox、Broker Offset、消费水位和业务结果对账，发现缺口后按原Event ID补发；超过重试上限进入隔离队列并告警。设置足够保留期与受控重放权限。通过断网、Broker宕机、ACK丢失和消费者崩溃等故障注入，验证最终到达且副作用不重复。

**相关知识点：** 消息丢失、事务发件箱、Broker确认、持久化副本、Event ID、Inbox、消费确认、Offset、至少一次投递、对账、受控重放。

### PLAN-295 · GPU资源不足时如何调度任务？

> 稳定 ID：`PLAN-295`｜原题号：295

**GPU调度应依据显存、模型驻留、预计Token和优先级进行装箱，结合连续批处理、模型副本伸缩和队列隔离。**

1. 调度器维护每张GPU的型号、显存、算力、健康度、已驻留模型和KV Cache占用；任务声明模型、上下文长度、最大输出、延迟SLO和预计显存。先做能力匹配，再按最少剩余显存、数据局部性与模型驻留选择节点，避免仅按GPU数量分配。

2. 在线短请求使用预热模型池和连续批处理，批任务进入独立队列并填充低峰容量；大模型可采用张量或流水线并行。**频繁加载、卸载模型会造成显存碎片和冷启动抖动**，应设置驻留窗口、切换成本和每模型最小副本。

| 策略 | 主要收益 | 风险 |
| --- | --- | --- |
| 连续批处理 | 提高吞吐 | 单请求延迟可能增加 |
| 模型驻留 | 降低冷启动 | 占用显存 |
| 量化或小模型路由 | 降低资源需求 | 可能损失质量 |
| 安全抢占 | 保障高优任务 | 需可恢复边界 |

3. 容量不足时依次提高安全批大小、扩展副本、延迟离线任务、路由到已评测的量化或小模型，最后拒绝低优请求；高风险任务不能未经验证降级。长任务在Checkpoint边界协作式抢占，防止GPU长期独占。监控显存利用率、Token吞吐、队列年龄、批等待、冷启动和OOM率，据此校准装箱与扩缩容。

**相关知识点：** GPU调度、显存装箱、模型驻留、KV Cache、连续批处理、张量并行、量化、协作式抢占、OOM、模型冷启动。
