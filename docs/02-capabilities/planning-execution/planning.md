### PLAN-016 · 为什么大模型调用经常使用异步编程？（千问一面）

> 稳定 ID：`PLAN-016`｜原题号：16

**大模型调用属于高延迟、强限流的网络I/O，异步编程可以在等待期间释放执行线程，提高系统并发与资源利用率。**

1. 单次推理通常持续数秒甚至更久，大部分时间消耗在网络传输、排队和模型生成。如果每个请求独占线程，高并发下会产生线程堆积、上下文切换和内存浪费；事件循环可在I/O等待时调度其他任务。

2. 异步特别适合**流式输出、多Agent协作、DAG并行分支、批量评测和模型—工具交替调用**。无依赖请求可通过gather并行，有依赖步骤仍须按DAG推进；异步只提升吞吐和等待利用率，不会缩短单次推理时间。

| 执行方式 | 优势 | 适用场景 |
| --- | --- | --- |
| 同步阻塞 | 实现简单 | 低并发短任务 |
| 异步I/O | 连接并发高 | 在线模型调用 |
| 任务队列 | 可削峰、跨进程 | 长任务与离线任务 |
| Batch | 单位吞吐高 | 批量推理与评测 |

3. **异步不等于无限并发**。Runtime应使用Semaphore、连接池和令牌桶同时限制并发数、RPM和TPM；遇到429或暂时性5xx时采用带抖动的指数退避，并通过背压阻止请求持续涌入。

4. 还需处理超时、取消传播、部分成功、响应乱序和流式断线。每次请求携带Task ID与Step ID，确保结果写回正确节点；用户取消后应中止下游调用，避免任务已经无效却继续产生Token费用。

**相关知识点：** 异步I/O、事件循环、Semaphore、RPM、TPM、指数退避、流式输出、取消传播。

### PLAN-029 · Runtime 如何支持流式输出？

> 稳定 ID：`PLAN-029`｜原题号：29

**Runtime支持流式输出的关键是把增量内容建模为有类型、有顺序、可恢复的事件流，而不是直接转发模型Token。**

1. Runtime定义start、delta、tool_call、progress、error和done等事件。每条包含Task ID、Attempt ID、类型、单调序号、时间戳及负载Schema；客户端按序组装，并以**done事件**确认结束。

| 传输方式 | 优势 | 适用场景 |
| --- | --- | --- |
| SSE | 简单、自动重连 | 服务端单向推送 |
| WebSocket | 全双工、低延迟 | 双向交互与控制 |
| HTTP分块 | 协议开销低 | 简单Token流 |
| 消息队列 | 可持久化、可回放 | 后台长任务 |

2. 模型Token、工具进度和状态先进入事件总线，再由网关转换为SSE或WebSocket。生产与消费速度不一致时实施**背压**：限制缓冲区、合并Token、降低刷新频率，超限则暂停读取或断开慢消费者。

3. Runtime持久化游标或关键事件，客户端重连时提交Last-Event-ID，从下一序号续传。传输可能重复投递，消费端须按事件ID去重；历史过期时返回快照。断线只终止订阅，不应取消后台任务。

4. 错误事件区分可重试、不可重试和部分成功，且只允许一个终态。敏感参数和内部推理不得直接输出，应脱敏并按权限过滤。评估首Token时延、乱序率、重连恢复率、缓冲峰值和完整流成功率。

**相关知识点：** SSE、WebSocket、事件序号、Last-Event-ID、背压、断线续传、事件去重、内容脱敏。

### PLAN-038 · 规则引擎和 LLM 分类器各自优缺点，如何融合使用

> 稳定 ID：`PLAN-038`｜原题号：38

**规则引擎适合确定性边界，LLM分类器适合开放语义；最佳方案是规则先过滤与兜底、LLM处理中间不确定区域。**

1. 规则基于字段和逻辑条件，稳定、低延迟且可审计，适合权限、合规和固定命令；但规则增长后容易冲突，也难覆盖指代和长尾意图。LLM能理解复杂语义、多意图和少样本标签，但延迟、费用、随机性更高。

| 维度 | 规则引擎 | LLM分类器 |
| --- | --- | --- |
| 确定性 | 高 | 较低 |
| 语义泛化 | 弱 | 强 |
| 延迟与成本 | 低 | 较高 |
| 可解释性 | 条件可追溯 | 需输出证据 |
| 维护方式 | 人工编写与测试 | Prompt、样本和模型版本 |

2. 融合采用**规则硬过滤—LLM分类—规则后验校验**。前置规则处理名单、格式、权限和风险；未命中部分由LLM输出候选标签、证据与字段；后置规则检查兼容性、必填参数和风险。冲突时安全与权限规则优先。

3. 置信度应基于验证集校准，并结合规则强度、候选分差和历史先验。高置信度自动路由，中置信度复核，低置信度且标签副作用不同时澄清；低风险任务可记录假设后继续。

4. 规则、Prompt、标签体系和阈值分别版本化，线上记录输入、规则命中、候选标签、最终路由与结果。评估宏平均F1、误拦截率、长尾召回率、校准误差、澄清率和端到端完成率，并将LLM稳定识别的高频模式沉淀为规则。

**相关知识点：** 规则引擎、LLM分类器、级联分类、置信度校准、多标签分类、Guardrail、灰度发布。

### PLAN-052 · 如何提高任务分类的准确率？

> 稳定 ID：`PLAN-052`｜原题号：52

**提高任务分类准确率的优先级应是优化标签与数据，其次改进上下文表示和模型，最后通过校准与反馈闭环稳定线上效果。**

1. 先治理标签：确保边界可判定、正反例充分、父子标签一致，并允许多标签和Unknown类。对高频混淆标签合并、拆分或重写；多人标注并以Kappa检验一致性。标注者无法稳定区分时，升级模型无效。

| 优化层面 | 主要措施 | 解决问题 |
| --- | --- | --- |
| 标签 | 边界、正反例、Unknown | 降低概念重叠 |
| 数据 | 长尾采样、难例、去噪 | 提升覆盖与质量 |
| 特征 | Task State、指代与槽位 | 减少上下文误判 |
| 模型 | 级联、微调、检索示例 | 提高语义能力 |
| 决策 | 校准、阈值与澄清 | 控制误路由风险 |

2. 数据覆盖多意图、否定、指代、任务切换、模糊输入和对抗表达，并处理类别不均衡。通过**主动学习**优先标注分差小、模型分歧大和损失高的样本；合成数据须人工抽检，不能替代真实分布。

3. 将请求解析为目标、对象、动作、交付物、约束和副作用，并结合Task State，而非拼接全部历史。规则处理确定性格式，轻量分类器召回高频意图，LLM负责长尾精排；输出Top-K标签、证据和缺失字段。

4. 在验证集校准置信度，并按错误成本设置阈值。低置信度且候选副作用不同时澄清。离线评估Macro-F1、长尾召回和ECE，线上监控误路由率、澄清有效率及完成率；通过灰度发布和失败样本回流迭代。

**相关知识点：** 标签治理、主动学习、类别不均衡、Task State、Top-K分类、置信度校准、数据漂移、灰度发布。

### PLAN-053 · 分类置信度（Confidence Score）如何计算？

> 稳定 ID：`PLAN-053`｜原题号：53

**分类置信度应表示“预测正确的经验概率”，必须由可观测信号融合并在独立验证集上校准，不能直接采用LLM自报分数。**

1. 单标签分类器将logit经Softmax得到概率，并结合候选分差和预测熵；多标签任务对各标签使用Sigmoid。LLM场景可加入采样一致率、检索相似度、证据完整度及规则强度。

| 方法 | 适用情况 | 特点 |
| --- | --- | --- |
| Temperature Scaling | 有logit | 简单且保持排序 |
| Platt Scaling | 二分类 | 学习逻辑映射 |
| Isotonic Regression | 非线性关系 | 灵活但易过拟合 |
| Conformal Prediction | 需覆盖率保证 | 输出候选集合 |

2. 可训练轻量校准器，输入原始分数、候选分差、熵、规则一致性、相似度和先验，输出**校准后置信度**。只能使用推理时可得特征，禁止真实标签或后验结果泄漏。

3. 通过Reliability Diagram、ECE、Brier Score和NLL评估校准，并检查分组误差。准确率高不代表校准好：若预测0.9的样本仅70%正确，该分数就不能可靠路由。

4. 阈值按错误成本设置：高风险写操作要求高置信度，中间区间复核或澄清，低风险只读任务可降低阈值。线上记录分数、校准版本和结果，定期重校准；标签或模型变更后须重新拟合。

**相关知识点：** Softmax、Sigmoid、预测熵、Temperature Scaling、Brier Score、ECE、Conformal Prediction、成本敏感阈值。

### PLAN-077 · Agent如何选择合适的Tool或Skill？

> 稳定 ID：`PLAN-077`｜原题号：77

**Tool或Skill的选择应采用“硬约束过滤、语义召回、多目标排序、参数校验、执行反馈”的分层决策，而非让模型凭名称猜测。**

1. 将任务节点规范化为目标、输入输出Schema、权限、风险、时延和成本预算，再查询**能力注册表**。权限不足、参数不兼容、服务不可用或副作用超出授权的候选在排序前剔除，避免相似度掩盖不可执行性。

| 对象 | 能力粒度 | 适用情况 |
| --- | --- | --- |
| Tool | 单次原子操作 | 查询、读写、调用接口 |
| Skill | 指令、知识和脚本的封装 | 可复用专业任务 |
| Workflow | 固定状态与异常分支 | 稳定业务流程 |

2. 使用规则、向量检索或分类器召回Top-K，再综合匹配度、历史成功率、延迟、价格、稳定性和合规性排序。高风险任务优先可审计、可回滚的能力，实时任务优先低延迟，不能只看相似度。

3. 选择后做**Schema Binding**：将任务字段映射到调用参数，检查必填项、类型、来源和输出能否满足下游。候选得分接近且结果差异显著时澄清；低风险场景可选择低成本者试运行，并保留备选。

4. 执行结果反哺路由器，但“调用成功”不等于“任务成功”，应由节点Validator判定产物质量。记录候选集、选择理由、能力版本、参数摘要、耗时、成本和失败类型；超时或可恢复错误按策略切换备选，权限错误不得降级绕过。

**相关知识点：** Tool Routing、Skill Registry、硬约束过滤、Top-K召回、多目标排序、Schema Binding、能力降级、Validator。

### PLAN-082 · RAG在任务理解阶段起什么作用？

> 稳定 ID：`PLAN-082`｜原题号：82

**RAG在任务理解阶段负责引入与当前请求相关的外部事实，使Agent能够消解术语、识别实体、补全约束并生成有依据的Task Spec。**

1. 用户常以内部简称、字段或特定版本描述任务，模型参数中未必包含这些信息。RAG检索业务词典、接口Schema、代码符号和操作规范，把对象、规则和可用能力转化为证据，减少猜测。

| 机制 | 提供的信息 | 适用变化 |
| --- | --- | --- |
| RAG | 当前外部文档和结构化数据 | 知识频繁更新 |
| Memory | 用户与会话历史 | 个体上下文变化 |
| Fine-tuning | 稳定行为模式和表达 | 低频离线更新 |

2. 检索查询从请求中抽取**实体、领域、版本、时间、权限和任务阶段**，采用关键词、向量与元数据过滤混合召回，再经重排、去重和时效筛选。代码场景还应使用路径、符号索引和调用关系；仅凭向量相似度容易召回版本错误的材料。

3. 检索结果需验证来源、时间、适用范围和一致性。证据冲突时，优先权威且版本匹配的来源，并把冲突标为未决问题；权限不足的文档不得进入模型上下文。

4. RAG产物应进入Task Spec的证据字段，支持后续规划与审计，而非无差别拼接到Prompt。评估需区分检索和任务两层：Recall@K、重排质量、证据覆盖率、引用正确率，以及意图识别准确率、澄清率和最终完成率。

**相关知识点：** RAG、Task Spec、实体链接、Hybrid Search、Metadata Filter、重排、知识时效性、证据溯源、Fine-tuning。

### PLAN-083 · Agent如何进行上下文检索和上下文压缩？

> 稳定 ID：`PLAN-083`｜原题号：83

**上下文管理应先按任务阶段检索最相关证据，再按信息价值压缩，并始终保留来源、约束和可恢复的原始引用。**

1. 检索器从子任务抽取实体、动作、版本、时间、路径和权限，生成关键词、语义及结构化查询。混合召回后，以相关性、时效、权威性和权限重排；代码任务还结合符号索引、调用图和最近变更，避免只按相似度取片段。

2. 检索粒度与任务匹配：定位定义时返回符号片段，分析调用链时扩展相邻节点，理解长文时先召回章节再定位段落。使用**逐级扩展**而非加载全文，并给证据附来源ID、版本和位置，便于回查。

| 压缩方式 | 优势 | 风险 |
| --- | --- | --- |
| 抽取式 | 保留原文、可核验 | 压缩率有限 |
| 摘要式 | 压缩率高 | 可能遗漏或改写事实 |
| 结构化 | 适合目标、约束和状态 | 需预定义Schema |
| 外置化 | 大结果仅传句柄 | 依赖存储可用性 |

3. 压缩时按“系统约束与权限＞用户目标＞已验证事实＞未决问题＞辅助材料”分配Token预算。对话保留决策和纠正，不保留寒暄；工具结果保留状态、字段和异常；长材料生成摘要时必须关联原文句柄，关键数字与否定条件尽量抽取而非改写。

4. 当计划阶段变化或证据过期时重新检索，不能永久复用旧摘要。评估同时覆盖Recall@K、重排质量、压缩后事实保真率、证据覆盖率、Token节省率和最终任务成功率；发现答案依据不足时应回查原文而不是继续压缩。

**相关知识点：** Hybrid Search、Query Rewriting、重排、上下文窗口、抽取式压缩、摘要式压缩、Token预算、证据溯源。

### PLAN-087 · 多Agent系统中任务拆解如何进行协作？

> 稳定 ID：`PLAN-087`｜原题号：87

**多Agent协作应由Orchestrator按能力和依赖分派原子任务，通过结构化契约交换产物，并治理状态、权限与冲突。**

1. Planner将目标拆成可验证的DAG节点，仅当专业化、上下文隔离或并行收益大于通信成本时才委派。强依赖任务拓扑执行，输入独立且无资源冲突的任务并行；高耦合小任务由单Agent完成。

2. Orchestrator依据DAG、能力、负载、权限、成本和历史成功率分配任务。委派必须声明**目标、输入、输出Schema、上下文边界、截止时间和成功标准**，子Agent只获得最小权限与信息。

| 模式 | 优势 | 主要风险 |
| --- | --- | --- |
| 单Agent | 状态集中、控制简单 | 专业性与并行有限 |
| 主管-执行者 | 职责清晰、易治理 | 主管可能成为瓶颈 |
| 对等协作 | 灵活、容错较好 | 冲突与通信成本高 |
| 黑板模式 | 共享信息充分 | 一致性复杂 |

3. 针对“多Agent系统中任务拆解如何进行协作”，通信宜通过任务存储或消息总线传递结构化结果；无依赖节点并行，有依赖节点拓扑推进。冲突结果由规则、独立Judge或人工裁决。子Agent失败先在本节点**重试**或替换执行者，并设置委派深度、消息预算与全局截止时间。

4. 共享状态采用单一事实源，Agent通过版本号或乐观锁提交结果，禁止依赖私有对话中的隐式信息。Orchestrator记录分派理由、执行轨迹和产物血缘；权限不得因再次委派而扩大，并防止循环委派、重复执行和消息风暴。

**相关知识点：** Orchestrator、Task Dispatch、能力标签、共享状态、结果聚合、委派预算。

### PLAN-088 · Coding Agent的任务拆解流程与普通Agent有什么不同？

> 稳定 ID：`PLAN-088`｜原题号：88

**Coding Agent的任务拆解以代码依赖、可执行验证和最小差异为核心，比普通Agent更强调仓库事实、变更顺序与回归风险。**

1. 普通Agent可按业务目标或交付物拆分；Coding Agent先读取仓库规范，检索符号、调用链、配置和测试，确认问题可复现后再规划。不能凭需求猜测文件位置，也不能按文件数量分配子任务。

2. 典型链路是读取仓库约束、搜索符号与调用关系、复现问题、建立文件级计划、修改、测试和审查。多文件任务应按**接口、实现、调用方、测试和文档**建立依赖，共享接口修改串行推进，互不相关的分析与测试才可并行。

| 维度 | 普通Agent | Coding Agent |
| --- | --- | --- |
| 事实来源 | 文档、接口和对话 | 代码、历史和运行结果 |
| 拆分依据 | 业务步骤与交付物 | 符号、依赖和测试边界 |
| 成功证据 | 业务规则或用户确认 | 编译、测试、静态分析 |
| 主要风险 | 流程或内容错误 | 回归、兼容性和数据破坏 |

3. 修改节点需声明目标符号、不变量、预期差异和验证命令。执行顺序是复现、确认测试、修改实现、运行局部测试、再扩大回归范围；失败反思必须基于编译错误、测试、静态分析和运行日志，而非模型自评。

4. Coding Agent还要保护用户改动，审查Diff并区分任务内外变更。依赖升级、数据迁移、公共接口修改和大范围删除等高风险项应建立**版本恢复点**并经过审批；最终交付需列出修改文件、测试证据和剩余风险。

**相关知识点：** 代码检索、符号索引、调用图、多文件规划、最小变更、测试驱动、差异审查。

### PLAN-110 · 多Agent协作时如何进行任务拆分与分配？

> 稳定 ID：`PLAN-110`｜原题号：110

**多Agent任务拆分应按可独立验证的产物和依赖形成DAG，再由Orchestrator基于能力、权限、负载和成本进行约束匹配。**

1. 拆分边界不是角色名称，而是输入输出契约。子任务应具有单一目标、产物、上下文边界、成功标准和失败责任；高耦合且共享隐式状态的工作不宜分给不同Agent，无依赖且专业性明显的节点才适合并行。

2. Orchestrator依据DAG、能力、负载、权限、成本和历史成功率分配任务。委派声明**目标、输入、输出Schema、上下文边界、截止时间和成功标准**，子Agent只获得最小权限与信息。

| 模式 | 优势 | 主要风险 |
| --- | --- | --- |
| 单Agent | 状态集中、控制简单 | 专业性与并行有限 |
| 主管-执行者 | 职责清晰、易治理 | 主管可能成为瓶颈 |
| 对等协作 | 灵活、容错较好 | 冲突与通信成本高 |
| 黑板模式 | 共享信息充分 | 一致性复杂 |

3. 先剔除能力缺失、权限不足、环境不兼容或数据不可见的Agent；再按匹配度、成功率、负载、延迟和费用排序。关键任务可指定主执行者与备选者，但不得让多个Agent无协调地写同一资源。

4. 通信通过任务存储传递结构化产物，引用单一事实源而非复制对话。结果由Validator验收，冲突用规则、独立Judge或人工裁决；失败先局部**重试**或重新分配。限制委派深度、消息预算和截止时间，防止循环委派与通信风暴。

**相关知识点：** Orchestrator、Task Dispatch、能力标签、共享状态、结果聚合、委派预算。

### PLAN-126 · Tool Selection具体如何实现？

4. 宿主校验白名单和参数后执行，以Validator判断结果。记录状态、错误、耗时、费用和反馈，更新成功率先验、排序权重及工具描述；离线评估Top-K召回率和选择准确率，线上监控任务成功率、误调用率及单位成功成本。

### PLAN-129 · 如何降低Agent的工具调用成本？

> 稳定 ID：`PLAN-129`｜原题号：129

**降低工具调用成本的核心是减少无效调用，并在成功率、时延、费用和结果新鲜度之间进行全链路优化。**

1. 单任务成本应覆盖决策Token、工具计费、网络等待、重试及失败补偿，不能只统计API单价。记录各工具费用、P95时延、成功率和结果价值，以**单位成功任务成本**为主要指标。

2. 调用前以意图分类和选择阈值判断外部能力需求；仅向模型暴露Top-K候选与精简Schema，减少Token和误选。已有信息或本地计算结果直接复用；高成本工具增加预算门控，低价值任务采用轻量模型。

| 手段 | 降本来源 | 主要风险 |
| --- | --- | --- |
| 语义缓存 | 避免重复查询 | 数据过期或错配 |
| 批量调用 | 摊薄请求开销 | 单批延迟上升 |
| 并行调用 | 缩短总时延 | 不一定降低计费 |
| 结果裁剪 | 减少回填Token | 丢失必要证据 |

3. 按规范化参数设计缓存键，并设置TTL、版本和权限隔离；合并相同请求，批量接口优先于多次单项调用。仅并行必要的独立任务，竞速模式取得合格结果后取消其余请求；大结果先过滤、聚合和压缩再回填。

4. 仅对瞬时错误限次退避重试，参数、权限及业务错误不得盲目重试。监控调用量、缓存命中率、重复率、失败率和单位成功成本，以真实轨迹优化阈值。降本必须受正确率与新鲜度SLO约束，不能以少调用换取错误答案。

**相关知识点：** 成本模型、Tool Selection、语义缓存、请求合并、批处理、结果裁剪、指数退避、单位成功成本。

### PLAN-180 · 哪些场景必须引入人工干预？

> 稳定 ID：`PLAN-180`｜原题号：180

**不可逆、高影响、越权风险或证据不足的决策必须引入人工干预，模型只能提出建议，不能替代责任主体完成授权。**

1. 强制介入场景包括资金支付、生产发布、数据删除、敏感信息披露、权限提升、法律与医疗等高责任判断，以及自动恢复多次失败。目标含义不清且不同解释会产生重大差异时，也应先澄清再执行。

2. 针对“哪些场景必须引入人工干预”，风险评分综合**资源敏感度、操作范围、可逆性、数据级别、异常行为和用户授权**。低风险且明确授权的操作可Allow；高影响、不可逆或信息不足的操作进入Ask；越权、违规或禁止行为必须Deny。模型可以建议，但不能成为授权主体。

| 模式 | 适用条件 | 系统动作 |
| --- | --- | --- |
| Allow | 低风险且已授权 | 执行并记录 |
| Ask | 高影响或信息不足 | 请求明确审批 |
| Deny | 越权或违反政策 | 拒绝并说明 |
| Sandbox | 允许试验但需隔离 | 限制资源和网络 |

3. 针对“哪些场景必须引入人工干预”，工具网关采用最小**权限**、短期令牌、参数白名单和沙箱隔离。审批界面应显示具体对象、范围和副作用；长任务恢复或权限变更后，高风险步骤必须重新校验。所有策略版本、判定证据、审批人和执行结果进入不可篡改审计日志。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** Allow/Ask/Deny、最小权限、动态风险评分、工具网关、审批、审计日志。

### PLAN-183 · 如何设计任务回放的数据结构？

> 稳定 ID：`PLAN-183`｜原题号：183

**任务回放应采用追加写事件流加周期快照的数据结构，同时保存版本、因果关系和外部证据，才能确定性重建历史状态。**

1. Task表保存task_id、租户、目标、当前状态和版本；Event表保存event_id、task_id、sequence、type、timestamp、actor、payload_ref、causation_id和correlation_id。sequence在单任务内严格递增，事件只追加不覆盖，以还原真实发生顺序。

2. Snapshot表记录截至某个sequence的**Plan版本、节点状态、上下文摘要、待执行队列、预算和Schema版本**。模型输入输出、工具结果及文件等大对象存对象存储，事件仅保存URI、内容哈希和保留策略，避免日志无限膨胀。

| 数据结构 | 核心字段 | 用途 |
| --- | --- | --- |
| Task | 状态、版本 | 当前视图 |
| Event | 序号、类型、因果ID | 历史事实 |
| Snapshot | 序号、状态快照 | 加速重建 |
| Artifact | URI、哈希、版本 | 保存大对象 |

3. 回放时加载目标sequence之前最近的Snapshot，再按序应用后续事件；Reducer必须幂等，并校验序号连续性、哈希和Schema迁移。缺失或损坏事件应立即停止，不能猜测补全。敏感字段加密并按租户授权访问。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** Event Sourcing、Snapshot、Reducer、Sequence、因果ID、Artifact、Schema演进、确定性回放。

### PLAN-188 · OpenHands如何实现Plan-Execute循环？

> 稳定 ID：`PLAN-188`｜原题号：188

**OpenHands以Action—Observation循环执行任务；显式Plan不是固定阶段，而是可定制的Agent策略。**

1. Conversation管理生命周期、状态与工作区；无状态Agent读取事件历史，调用LLM产生动作，校验执行后把结果写回。未完成则触发下一step，返回最终响应后转为Finished。

2. Plan可作为消息、Agent状态或任务列表保存，并依据新Observation修改；Execute是读取、编辑、运行与验证闭环。**规划属于Agent层，持久化和调度属于Conversation层**。

| 组件 | 职责 | 循环中的作用 |
| --- | --- | --- |
| Agent | 推理与选动作 | Plan、Action |
| Conversation | 状态与生命周期 | 调度下一step |

### PLAN-270 · 分布式锁有哪些实现方案？

> 稳定 ID：`PLAN-270`｜原题号：270

**常见方案包括数据库悲观锁或租约、Redis SET NX加过期时间、ZooKeeper/etcd临时节点。**

2. ZooKeeper临时顺序节点和etcd租约、事务与Revision适合强一致协调、主节点选举和公平排队，代价是运维复杂。条件写也可实现轻量租约。**选型必须基于故障模型、一致性要求、持锁时间和延迟**。

| etcd租约 | 强一致、Revision可用 | 集群成本较高 |

**令牌桶按速率补充令牌并允许消费历史积累，因此可以承接有限突发；漏桶按近似固定速率排出请求，更强调平滑。**

1. 令牌桶维护容量B和补充速率R，请求按成本消耗令牌；空闲期间令牌最多积累到B，因此可在短时间内放行突发流量，长期平均速率仍受R约束。请求无令牌时可拒绝或等待，适合模型API的RPM、TPM及租户配额控制。

2. 漏桶把请求放入有限队列，以固定或近似固定速率流出；入口突发被排队平滑，队列满时丢弃或拒绝。它适合吞吐稳定、不能承受瞬时峰值的数据库、第三方工具或设备。**令牌桶限制平均速率并容许突发，漏桶塑造稳定输出速率**。

| 维度 | 令牌桶 | 漏桶 |
| --- | --- | --- |
| 突发能力 | 允许有限突发 | 平滑输出 |
| 核心参数 | 桶容量、补充速率 | 队列容量、泄漏速率 |
| 满载处理 | 无令牌则等待或拒绝 | 队列满则丢弃或拒绝 |
| 典型用途 | API限流、配额 | 流量整形、保护下游 |

3. Agent系统常组合两者：入口令牌桶允许合理突发，下游队列以漏桶节奏执行。分布式实现需原子更新余额与时间戳，处理时钟偏差，并按请求Token数或预计费用加权扣减，而非一请求一令牌。参数应依据下游容量、允许突发和排队SLO设置，同时监控拒绝率、等待时间、桶利用率及租户公平性。

**相关知识点：** 令牌桶、漏桶、限流、流量整形、突发容量、RPM、TPM、加权请求、原子更新、排队SLO、租户配额。

### PLAN-279 · 如何设计多级限流体系？

> 稳定 ID：`PLAN-279`｜原题号：279

**多级限流应从全局容量逐层下钻到租户、用户、模型、工具和任务，任何一级超限都触发明确的排队、降级或拒绝策略。**

1. 全局层保护系统CPU、GPU、连接池和总预算；租户层依据套餐与权重隔离资源，防止单租户挤占；用户或API Key层控制滥用；模型与工具层遵守供应商RPM、TPM、并发及费用限制；任务层限制子任务扇出、反思轮次和在途调用。

2. 入口用令牌桶处理速率与突发，执行层用信号量限制并发，队列用容量和最大等待时间形成背压，预算层按Token或预计费用加权扣减。**限流键、窗口、配额、优先级和豁免规则必须集中配置并版本化**，避免各服务策略矛盾。

| 层级 | 保护对象 | 典型指标 |
| --- | --- | --- |
| 全局 | 平台总容量 | CPU、GPU、总并发 |
| 租户/用户 | 公平性与套餐 | 请求率、资源份额 |
| 模型/工具 | 下游配额 | RPM、TPM、并发 |
| 任务 | 单任务成本 | 扇出、Token、费用 |

3. 超限响应区分短暂与持续过载：短暂峰值排队并返回Retry-After，长期过载则批处理、模型降级、暂停低优先级或拒绝请求；高风险任务不能通过降级绕过安全校验。分布式计数需原子更新并处理时钟偏差与故障降级。监控各层命中率、拒绝率、等待时长和配额利用率，定期压测校准阈值。

**相关知识点：** 多级限流、令牌桶、信号量、背压、RPM、TPM、加权配额、租户隔离、Retry-After、分布式计数、过载保护。

### PLAN-280 · 限流阈值如何动态调整？

> 稳定 ID：`PLAN-280`｜原题号：280

**限流阈值应由容量上限、实时负载和业务SLO共同驱动，采用缓慢上调、快速下调及上下界约束，避免固定阈值失效或控制振荡。**

1. 先通过压测得到各模型、工具和资源池的安全基线，包括最大稳定吞吐、并发、P95延迟与错误率，再按租户配额和供应商限制设置硬上限。动态控制器持续观察排队时间、最老任务年龄、超时率、错误率、CPU/GPU及下游429响应。

2. 当延迟和错误低于目标且存在余量时小步提高并发；一旦出现429、超时或队列年龄越界，按比例快速收缩，并尊重Retry-After。**使用EWMA平滑指标、迟滞区间、冷却时间和每次最大变更幅度**，防止短时噪声导致阈值频繁抖动。

| 策略 | 优点 | 风险 |
| --- | --- | --- |
| 固定阈值 | 简单可预测 | 难适应负载变化 |
| AIMD | 稳定、实现简单 | 收敛速度有限 |
| 延迟反馈控制 | 贴近SLO | 易受噪声影响 |
| 预测式调整 | 可提前扩缩 | 依赖预测准确度 |

3. 阈值按全局、租户、模型和工具分别计算，同时受预算与公平份额约束；扩容尚未就绪前不能提前放宽入口。策略变更需版本化、灰度发布并保留快速回滚，异常时降至保守静态阈值。评估关注SLO违约率、资源利用率、拒绝率、队列时长和控制器振荡次数，而非只追求吞吐最大化。

**相关知识点：** 自适应限流、AIMD、EWMA、反馈控制、迟滞、冷却时间、Retry-After、并发限制、SLO、策略灰度、控制振荡。
<a id="plan-286"></a>
### PLAN-286 · 模型TPS、RPM、TPM分别代表什么？

> 稳定 ID：`PLAN-286`｜原题号：286

**RPM表示每分钟请求数，TPM表示每分钟处理Token数；模型TPS通常表示每秒生成或处理Token的吞吐。**

1. RPM统计一分钟窗口内接收的请求数量，与每个请求大小无关；大量短请求通常先触达RPM上限。TPM统计同一窗口内输入与输出Token量，供应商可能分别限制或合并计算；少量超长上下文也可能快速耗尽TPM。

2. TPS在推理性能语境中多指每秒生成Token数，有时也指输入输出合计吞吐，必须确认口径；单请求TPS反映生成速度，系统TPS反映所有并发请求总吞吐。**TPS不是请求成功率，也不能替代首Token延迟TTFT和端到端延迟**。

| 指标 | 计量对象 | 主要用途 |
| --- | --- | --- |
| RPM | 每分钟请求数 | 控制请求频率 |
| TPM | 每分钟Token数 | 控制计算与配额 |
| TPS | 每秒Token吞吐 | 衡量推理速度 |
| TTFT | 首Token等待时间 | 衡量交互响应性 |

3. Agent调度需同时预算请求数、预计输入Token、最大输出Token、并发和费用：小请求合批可缓解RPM，压缩上下文可缓解TPM，提高并发可能增加系统TPS却恶化单请求延迟。指标应区分配额上限、实际消耗和性能观测，并按模型、租户及时间窗统计；收到429时依据具体限额与Retry-After退避。

**相关知识点：** RPM、TPM、TPS、Token、TTFT、端到端延迟、并发、动态批处理、上下文压缩、Rate Limit、Retry-After。

### PLAN-299 · 如何判断两个自然语言请求属于同一个任务？

> 稳定 ID：`PLAN-299`｜原题号：299

**判断两个自然语言请求是否属于同一任务，应比较结构化业务意图、作用对象、关键约束和时间范围，不能仅依赖文本相似度。**

1. 先将请求解析为Intent Schema：tenant、actor、action、object、parameters、desiredState、deadline和sideEffect。对实体、时间、金额、单位和默认值规范化；关键字段一致或满足业务等价规则时，才进入同任务候选。

2. 文本Embedding和语义模型可用于召回候选，再由规则或LLM分类器逐字段判断蕴含、冲突与补充关系。**“表达相似”不等于“业务相同”**：修改同一文件但目标分支不同、给同一人发邮件但模板版本不同，都可能是独立任务。

| 关系 | 判定特征 | 处理方式 |
| --- | --- | --- |
| 同一任务重试 | 意图、对象、参数一致 | 复用taskKey |
| 同一任务补充 | 核心目标相同，新增约束 | 更新任务版本 |
| 相关但独立 | 主题相同，副作用不同 | 新建任务并关联 |
| 冲突请求 | 目标状态互斥 | 阻止合并并确认 |

3. 风险越高，自动合并阈值越严格；支付、删除、发信要求确定性业务键，不能只靠模型。分类器输出匹配字段、冲突字段和置信度，低置信度转人工。用同义改写、参数差异、时效变化和对抗样本评估误合并率与漏合并率，并优先降低误合并。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** 语义去重、Intent Schema、实体解析、参数规范化、Embedding召回、NLI、taskKey、任务版本、误合并率、漏合并率。

### PLAN-305 · 多个用户共享同一个任务结果时，权限如何隔离？

> 稳定 ID：`PLAN-305`｜原题号：305

**共享计算结果必须把计算去重与数据授权分开：底层结果可按规范化任务键复用，但返回前重新执行租户、用户和字段级权限过滤。**

1. taskKey只判断计算是否等价，不能作为访问凭证。共享前先确认输入数据、模型输出和中间Artifact是否允许跨用户或跨租户复用；含用户私有数据、个性化上下文、密钥或不可脱敏内容时，必须把安全域纳入缓存键或完全禁止共享。

2. 共享存储保存内容哈希、数据分类、来源、Owner、租户边界和访问策略；返回时根据当前用户、用途、资源与权限版本重新鉴权，再做行级、字段级脱敏。**缓存命中只复用计算，不复用首个请求者的身份、令牌或授权判定**。

| 隔离方式 | 适用对象 | 关键要求 |
| --- | --- | --- |
| 租户级缓存 | 企业私有结果 | 键中包含tenantId |
| 用户级缓存 | 个性化结果 | 键中包含userId |
| 共享公共缓存 | 公共只读结果 | 无私有输入且可复用 |
| 共享计算、私有视图 | 同源不同权限 | 返回时重新过滤 |

3. Artifact使用每租户密钥加密或独立命名空间，下载链接短期有效且绑定调用者；日志、Embedding和缓存元数据同样按租户隔离。权限撤销或数据版本变化时使相关缓存失效，不能依赖TTL慢慢过期。审计记录谁因何taskKey访问了哪个版本，并用越权、撤权后访问和缓存投毒测试验证。

**相关知识点：** 多租户隔离、taskKey、缓存键、ABAC、行列级权限、字段脱敏、Artifact Store、加密隔离、权限版本、缓存失效、审计日志。
<a id="plan-306"></a>
### PLAN-306 · 任务结果缓存多久合适？

> 稳定 ID：`PLAN-306`｜原题号：306

**TTL应由数据新鲜度、结果复用概率、计算成本、权限敏感度和错误影响共同决定，而不是统一配置。**

1. 先定义业务允许的最大陈旧时间：库存、权限、告警等实时状态使用秒级TTL或不缓存；基于固定文档与模型版本的分析可缓存小时至天；不可变构建产物可长期缓存。TTL不能超过源数据更新周期、授权有效期和合规保留边界。

2. 缓存键包含租户或用户安全域、规范化输入、数据版本、模型、Prompt、工具Schema和策略版本；任一影响语义的版本变化都应失效。**权限撤销、源数据更新和错误结果修复应采用事件驱动失效，不能只等待TTL到期**。

| 结果类型 | TTL策略 | 主要失效信号 |
| --- | --- | --- |
| 实时业务状态 | 秒级或禁用 | 数据变更事件 |
| 版本化分析 | 小时至天 | 输入或版本变化 |
| 公共稳定知识 | 较长TTL | 内容发布事件 |
| 权限敏感结果 | 短TTL、隔离 | 授权变化 |

3. 采用TTL加随机抖动避免同批键同时失效，热点结果可在过期前异步刷新；仅允许短时陈旧时，可用stale-while-revalidate，但必须标注数据时间。负面结果、失败和低置信度答案应更短或不缓存。通过命中率、节省成本、陈旧命中率、错误放大范围和权限泄漏事件共同调参，而非只追求命中率。

**相关知识点：** TTL、最大陈旧时间、缓存键、版本化缓存、事件驱动失效、随机抖动、缓存击穿、异步刷新、stale-while-revalidate、负缓存。
