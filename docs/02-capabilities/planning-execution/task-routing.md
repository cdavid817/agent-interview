### Agent如何做任务识别，比如判断一个任务是简单问答、代码解释、代码修改，还是复杂开发任务？（DeepSeek一面）

**Agent任务识别应采用“结构化解析、分层分类、复杂度评分、风险校验”的混合路由机制，不能只依赖关键词或让LLM直接决定。**

1. 首先提取**目标、操作对象、期望产物、约束、上下文依赖和潜在副作用**，形成Task Spec。“解释函数”属于只读分析；“修复并提交代码”还包含文件写入、测试和版本控制，应进入不同执行路径。

2. 采用Rule、轻量模型和LLM分层协作：规则处理固定命令与安全边界；分类模型处理高频类别；LLM负责长尾语义、多意图和隐含目标。输出包含标签、置信度、证据及候选类别。

| 任务类型 | 判定特征 | 推荐执行方式 |
| --- | --- | --- |
| 简单问答 | 单步骤、无外部状态变化 | LLM直接回答 |
| 代码解释 | 只读代码上下文 | 检索后解释 |
| 代码修改 | 涉及文件写入和验证 | 定位、修改、测试 |
| 复杂开发 | 多文件、多依赖、多阶段 | Planner生成DAG |

3. 复杂度评分综合步骤数、依赖深度、文件跨度、工具数量、上下文规模和不可逆风险。低复杂度任务进入Executor；跨模块或高风险任务进入Planner；固定流程优先路由到Workflow。

4. 当置信度低、候选解释会产生不同副作用或关键参数缺失时，应请求澄清。线上通过**路由准确率、宏平均F1、误执行率和任务完成率**持续校准，并用失败样本更新规则与分类器。

**相关知识点：** Intent Classification、Task Spec、多标签分类、复杂度评分、Rule+LLM、Skill Router、置信度校准。

### 用户输入一个需求以后，Agent如何理解用户意图，并进行任务拆解？（DeepSeek二面）

**Agent应先把自然语言需求转换为可验证的Task Spec，再从验收目标反推子任务和依赖关系。**

1. 意图理解不能只看当前句子，需要结合历史对话、用户身份、权限、工作区状态和领域知识，抽取**最终目标、操作对象、期望交付物、范围、约束、优先级及禁止事项**，同时区分显式要求与合理隐含要求。

2. 解析结果写入Task Spec，包括输入输出、成功标准、风险、成本预算、可用工具和待澄清项。对象不唯一、验收标准冲突或不可逆操作范围不明时应先澄清；低风险细节可以采用默认值，但必须记录假设。

| 层级 | 核心问题 | 结构化产物 |
| --- | --- | --- |
| 意图 | 用户真正要解决什么 | Goal |
| 规格 | 有哪些约束和验收条件 | Task Spec |
| 规划 | 需要哪些中间产物 | Task DAG |
| 执行 | 谁在何时完成步骤 | Execution Plan |

3. 拆解采用**目标反推**：先确定最终验收条件，再识别必须产生的中间结果，将其划分为单一责任、输入输出明确、可独立验证和可安全重试的节点。随后建立数据依赖、控制依赖和资源冲突边，无依赖节点才允许并行。

4. Planner生成计划后由Validator检查依赖闭包、工具可用性、权限和成功标准。Executor逐步写回结果；只有关键假设失效或路径不可达时才局部重规划，已经成功且仍有效的节点不得重复执行。

**相关知识点：** 意图识别、Task Spec、目标反推、任务DAG、依赖分析、Validator、局部重规划。

### 对于复杂任务，Agent应该如何进行任务拆解和执行计划生成？（DeepSeek一面）

**复杂任务应被规划为具有明确输入输出、依赖关系、执行器和成功标准的任务DAG，而不是自然语言步骤列表。**

1. Planner先建立Task Spec，明确目标、范围、约束、预算、风险和验收条件；再采用目标反推或分层任务网络识别中间产物。每个子任务必须具备单一职责，能够独立调度、验证和重试，避免同时承担分析、修改与发布。

2. 根据子任务的**数据依赖、控制依赖和资源冲突**建立有向边。无依赖且资源不冲突的节点可以并行；涉及共享文件、独占资源或不可逆外部操作的节点应串行，并设置权限确认、幂等键或补偿动作。

| 规划结构 | 优势 | 适用场景 |
| --- | --- | --- |
| 顺序列表 | 实现简单 | 短链路任务 |
| Task Tree | 便于层级分解 | 目标探索 |
| DAG | 支持共享依赖与并行 | 复杂工程任务 |
| Workflow | 稳定、可审计 | 标准业务流程 |

3. Execution Plan至少包含Task ID、节点输入输出、前置条件、工具或Skill、优先级、超时、重试策略、幂等属性、成功判据、失败分支和成本预算。生成后由**Plan Validator**检查环路、依赖闭包、权限、工具可用性及预算可行性。

4. Executor按就绪节点调度并持久化结果。瞬时故障有限重试；单节点路径失效时局部修补DAG；只有目标、核心约束或整体依赖改变时才全局重规划。已完成且仍有效的节点必须复用。

**相关知识点：** Planner、Task Spec、HTN、任务DAG、Plan Validator、关键路径、局部重规划。

### Agent执行复杂任务时，如何支持暂停、恢复、重试、回滚、人工干预和任务回放？（腾讯二面）

**复杂任务必须建立持久化状态机、Checkpoint和事件日志，才能统一支持暂停恢复、失败处理、人工接管及任务回放。**

1. 状态机至少包含PENDING、RUNNING、PAUSED、SUCCEEDED、FAILED、COMPENSATING和CANCELLED。Task、Step、Attempt状态通过CAS迁移并持久化，不能依赖Worker内存。

2. **Checkpoint**保存计划版本、节点状态、输入输出引用、上下文摘要、工具回执、幂等键和待执行队列，并写在副作用提交后的稳定边界。暂停时停止领取新节点，让运行中操作到达安全点。

| 能力 | 实现基础 | 关键风险 |
| --- | --- | --- |
| 恢复 | Checkpoint、状态机 | 重复副作用 |
| 重试 | 错误分类、幂等键 | 无限循环 |
| 回滚 | 快照、逆操作、Saga | 补偿失败 |
| 回放 | 事件日志、版本快照 | 环境不一致 |

3. 恢复时加载最近快照，校验权限和依赖版本，并查询外部副作用。瞬时错误有限重试；可逆变更使用Rollback；已提交操作使用**Saga补偿**，重试前验证幂等性。

4. 人工可审批高风险动作、修改参数、跳过节点或接管任务，但须转移租约并记录原因。审计回放只还原轨迹；真实重执行需固定模型、Prompt、工具版本和输入快照，并在隔离环境运行。

**相关知识点：** 持久化状态机、Checkpoint、Durable Execution、Event Sourcing、Saga、Human-in-the-loop、任务回放。

### Agent 如何识别用户意图？

**用户意图识别应从“字面请求”上升为对真实目标、对象、约束和期望结果的结构化推断，并保留置信度与证据。**

1. 解析输入时，结合多轮对话、用户角色、工作区状态和时间信息解决指代、省略与隐含目标。例如“把它修好”必须确定对象、预期行为和修改范围，不能只按“修复”关键词路由。

2. 将结果表示为**Intent、Entity、Slot、Constraint、Expected Output和Risk**。请求可能同时包含查询、修改、测试和文档生成，因此采用多标签与槽位抽取，并区分明确要求与系统假设。

| 识别层 | 输入证据 | 主要职责 |
| --- | --- | --- |
| Rule | 关键词、命令、权限 | 硬边界和高精度路由 |
| 分类模型 | 标注样本 | 高频意图分类 |
| LLM | 完整上下文 | 长尾语义与隐含目标 |
| Calibrator | 多源分数 | 置信度与决策阈值 |

3. 决策层融合规则命中、分类概率、LLM一致度和历史先验。置信度不足、候选解释产生不同副作用或关键槽位缺失时请求澄清；低风险默认项记录假设后继续。

4. 线上保存输入、上下文版本、候选意图、证据和执行结果，通过**Intent Accuracy、Macro-F1、槽位F1、澄清率、误执行率和任务完成率**评估，并回流纠错样本。

**相关知识点：** Intent Classification、Entity、Slot Filling、多标签分类、上下文消歧、置信度校准、Clarification。

### 如何进行任务分类？

**任务分类应采用分层、多标签、可校准的体系，并让分类结果直接决定执行路径、权限边界与资源预算。**

1. 先建立标签空间。一级标签描述**任务意图**，如问答、解释、生成、修改与执行；二级标签描述领域和交付物；同时标注复杂度、风险、时效性及工具需求。复合请求不能被强行压缩成单标签，应拆出主任务、子任务与依赖关系，并为每个标签定义正例、反例和决策边界。

| 分类维度 | 典型取值 | 路由作用 |
| --- | --- | --- |
| 意图 | 查询、分析、修改、执行 | 选择处理流程 |
| 复杂度 | 简单、复合、长期 | 分配规划深度 |
| 风险 | 只读、可逆、高影响 | 决定审批与隔离 |
| 能力 | 纯推理、检索、代码、工具 | 选择模型与工具 |

2. 识别阶段抽取**目标、对象、交付物、约束、副作用和上下文指代**，再采用级联方案：确定性格式与安全边界由规则判定，常见意图由轻量分类器处理，长尾语义和多意图交给LLM。分类器应输出候选标签、置信度和依据，而不是只返回最终类别。

3. 路由层根据置信度和错误成本决策。高置信度直接执行；中置信度采用受限方案或补充检索；当不同分类会导致不可逆操作时必须澄清。执行中若发现工具需求、步骤数量或风险上升，还应支持**动态升类与重新规划**。

4. 评估不能只看分类准确率，还应观察宏平均F1、混淆矩阵、置信度校准误差、澄清率、误路由率和端到端完成率。日志需保留输入证据、标签版本、路由决策及结果，通过失败样本调整标签定义和阈值。

**相关知识点：** 层次分类、多标签分类、意图识别、置信度校准、任务路由、风险分级、动态规划。

### 如何判断一个任务是否属于复杂任务？

**复杂任务不是单纯“步骤多”，而是目标、依赖、状态和风险共同导致一次推理无法可靠完成的任务。**

1. 判断时应建立可量化特征：目标是否模糊或相互制约，是否需要拆分子目标，步骤间是否存在依赖，是否调用异构工具，结果是否改变外部状态，是否需要跨轮记忆、重规划与人工审批。任一特征很强或多项叠加，都意味着复杂度上升。

| 维度 | 简单任务 | 复杂任务 |
| --- | --- | --- |
| 目标 | 单一且明确 | 多目标、约束冲突 |
| 路径 | 一次生成或单次调用 | 多阶段、存在依赖 |
| 状态 | 无状态或短上下文 | 长期状态、外部环境变化 |
| 风险 | 只读、易撤销 | 高影响或不可逆 |
| 验证 | 结果容易判断 | 需多指标、交叉验证 |

2. 工程上可为各维度设置0—2分，形成**复杂度评分**。对目标不确定性、步骤数、工具数量、依赖深度、运行时长、失败代价和验证难度计分；低分直接回答，中等采用轻量计划，高分启用Planner、检查点、持久化状态和人工门控。阈值须由真实任务数据校准。

3. 复杂度应动态更新。初始简单的请求若出现工具失败、信息冲突、上下文不足或风险升级，应立即**升类并重新规划**；若子任务相互独立且路径明确，可降级为并行工作流，以减少调用和延迟。

4. 还需区分任务复杂度与语言难度。专业术语密集的问题可能只需一次准确回答，而文字简短的“发布这个版本”可能涉及测试、审批、部署和回滚。最终判断依据应是完成任务所需的控制闭环，而不是输入长度。

**相关知识点：** 任务分解、依赖图、复杂度评分、动态路由、重规划、检查点、风险分级、人工审批。

### DAG 为什么适合复杂任务？

**DAG能显式表达复杂任务的依赖关系，并在保证执行顺序的同时释放安全并行度，因此适合多阶段任务调度。**

1. DAG节点表示可独立执行和验证的子任务，边表示数据或控制依赖；无环约束保证任务能按拓扑顺序结束。它能表达一对多、多对一和共享产物，避免重复计算，并把失败范围限定到节点及下游。

| 结构 | 依赖表达 | 并行能力 | 典型场景 |
| --- | --- | --- | --- |
| 顺序列表 | 仅前后顺序 | 低 | 短流程 |
| Task Tree | 父子层级 | 中 | 递归分解 |
| DAG | 数据与控制依赖 | 高 | 复杂工程任务 |
| 状态机 | 状态迁移与循环 | 按规则 | 业务审批流程 |

2. 节点应声明**输入输出Schema、前置条件、执行器、资源、副作用、超时和成功标准**。构图后执行环检测、可达性及依赖校验；仅当前驱成功且产物已持久化时，后继才进入Ready Queue。Scheduler按关键路径、截止时间和资源配额分配Worker。

3. 节点失败时可按错误类型重试、补偿或局部重规划，有效节点无需重做；系统通过检查点恢复未完成部分。幂等节点可重放，外部写操作则需幂等键、事务或补偿机制。

4. 无依赖不等于可并行：节点若写入同一资源，仍需锁、资源边或串行化。动态增删节点后须重算就绪集合、更新计划版本并检测环。评估关键路径耗时、并行加速比、资源利用率、重试率和完成率。

**相关知识点：** DAG、拓扑排序、关键路径、Ready Queue、并行调度、幂等、检查点、补偿事务。

### 上下文多轮对话下，如何避免任务识别偏差

**多轮任务识别应以当前有效任务状态为依据，并通过指代解析、意图变更检测和关键歧义澄清防止旧上下文错误渗透。**

1. 系统不应等权拼接历史，而应维护Task State：目标、对象、交付物、约束、确认事实、未决问题和计划版本。每轮先判断补充、纠正、取消、切换或新任务，再更新字段；**用户最新明确指令优先于旧假设**，但安全约束不变。

| 上下文信息 | 处理方式 | 主要风险 |
| --- | --- | --- |
| 当前轮明确指令 | 直接进入任务状态 | 误识别否定或修正 |
| 近期相关消息 | 保留原文与来源 | 指代解析错误 |
| 长期历史 | 摘要后按需检索 | 摘要丢失限定条件 |
| 工具结果 | 结构化保存并标注时效 | 使用过期外部状态 |

2. 对“它、继续、按刚才的方式”等表达进行指代解析，候选对象来自活跃任务。摘要区分用户事实、模型推测与工具证据，并携带来源和时间；价格、权限、文件状态等动态信息须重新验证。

3. 识别器输出候选意图、任务ID、置信度和证据。当意图分差小，或不同解释会修改不同资源时，应最小化澄清；低风险偏好可记录假设后继续。任务切换时冻结旧计划，禁止旧异步结果写入新上下文。

4. 使用包含纠正、插话、指代和任务切换的测试集，评估意图准确率、任务串扰率、指代正确率、无效澄清率和误执行率。日志保留状态差异、证据和版本，并用真实样本更新策略。

**相关知识点：** Task State、对话状态跟踪、指代消解、意图漂移、上下文摘要、任务隔离、置信度校准。
<a id="plan-040"></a>
### 任务识别置信度低时，反思 Agent 具体执行逻辑

**低置信度时，反思Agent应查明不确定性来源、补充证据并重新判定；只有证据仍不足且决策影响显著时才向用户澄清。**

1. 识别器输出Top-K候选意图、对象、置信度、证据与缺失字段。反思器不重复原Prompt，而是检查候选覆盖、指代、标签边界及规则冲突，并将原因归为信息缺失、语义歧义、上下文污染或模型波动。

| 不确定性来源 | 反思动作 | 后续处理 |
| --- | --- | --- |
| 信息缺失 | 抽取必填槽位 | 定向询问 |
| 指代不清 | 检索活跃任务状态 | 确认对象 |
| 标签重叠 | 对比正反例和边界 | 重新排序 |
| 模型波动 | 独立复核或规则验证 | 聚合结果 |

2. 反思器依据原请求、Task State、标签定义和工具状态补充证据，必要时用不同Prompt或验证器独立复核，避免自我确认。随后重算**校准置信度**，综合候选分差、规则强度和历史先验。

3. 按置信度与错误成本门控：高置信度直接路由；中置信度选择只读、可逆动作并记录假设；低置信度且候选会访问不同资源或改变状态时，提出信息增益最高的问题。无法澄清时拒绝或转人工。

4. 反思受轮次、Token、延迟和费用预算约束；无新证据、排序不变或置信度未改善时停止。日志保存候选、依据、分数变化和结果，评估修复率、误路由率、澄清有效率、额外成本及完成率。

**相关知识点：** Reflection、Top-K分类、Task State、置信度校准、信息增益、澄清策略、错误成本、人工接管。
<a id="plan-041"></a>
### 复杂开发任务如何拆解为子任务并分配对应子 Agent

**复杂开发任务应按可独立交付和验证的工程边界拆解，再依据能力、依赖、权限与负载将节点分配给专业子Agent。**

1. 主Agent建立Task Spec，明确需求、架构约束、仓库状态和验收标准，再按设计、实现、测试和文档反向拆解。子任务应满足**输入明确、输出可合并、可独立验证、失败可隔离**；修改同一文件的工作不宜并行。

| 拆分方式 | 适合场景 | 主要风险 |
| --- | --- | --- |
| 按模块 | 边界清晰的前后端或服务 | 接口漂移 |
| 按阶段 | 设计、实现、测试、评审 | 串行等待 |
| 按能力 | 安全、数据库、性能专项 | 上下文割裂 |
| 按文件 | 低耦合批量修改 | 语义一致性不足 |

2. Orchestrator按能力、权限、历史成功率、负载、成本和期限选择执行者。委派契约包含目标、修改范围、必读文件、输入版本、输出Schema、测试命令和完成条件；子Agent只获得最小上下文与权限，不得扩大范围。

3. 构建DAG：无依赖节点并行，有依赖节点拓扑推进；写同一文件的节点需串行、分支隔离或明确所有权。子Agent提交补丁、测试证据、假设和风险，不覆盖他人结果。主Agent在汇合点检查接口、冲突、回归测试和一致性。

4. 失败时判断实现错误、契约缺失或上游假设失效，再选择修复、替换Agent或局部重规划。限制并发数、委派深度和预算，以完成率、冲突率、返工率、并行加速比及单位成本评估收益。

**相关知识点：** Task Spec、Orchestrator、任务DAG、能力路由、任务契约、代码所有权、结果聚合、局部重规划。
<a id="plan-042"></a>
### 如何设计量化指标评估任务识别准确率

**任务识别评估不能只看总体准确率，应同时衡量分类质量、置信度可靠性、业务错误成本和端到端路由效果。**

1. 建立标签边界清晰的标准集，覆盖高频、长尾、多意图、否定、指代和任务切换，并按用户或会话隔离训练集与测试集。样本由多人标注，用Cohen’s Kappa衡量一致性，争议由专家仲裁。

| 指标 | 主要含义 | 适用重点 |
| --- | --- | --- |
| Accuracy | 全部样本正确比例 | 类别均衡场景 |
| Macro-F1 | 各类别等权平均 | 关注长尾类别 |
| Micro-F1 | 按全部实例统计 | 关注总体表现 |
| Top-K Recall | 正确标签是否在候选集 | 两阶段路由 |
| ECE/Brier | 置信度是否可信 | 阈值与澄清策略 |

2. 多标签任务还应报告Exact Match、Hamming Loss和每类Precision/Recall，并用混淆矩阵定位易混类别。应建立**成本加权错误率**，对越权、误写入和错误工具调用提高权重，避免高频低风险类别掩盖严重错误。

3. 线上还要监控路由准确率、澄清率、误执行率、人工接管率和任务完成率。按领域、语言、输入长度和模型版本切片，观察最差分组表现及数据漂移。

4. 阈值通过验证集在准确率、覆盖率与错误成本间优化，不能用测试集调参。上线采用影子流量或A/B实验，记录候选标签、置信度、路由与结果，并用Bootstrap置信区间判断差异；失败样本回流前重新标注。

**相关知识点：** Macro-F1、混淆矩阵、Top-K Recall、ECE、Brier Score、成本敏感分类、数据漂移、A/B测试。
<a id="plan-043"></a>
### 短模糊 Prompt、需求不完整场景下优化识别方案

**短而模糊的Prompt应先形成候选意图和缺失槽位，再依据风险选择推断、检索或最小化澄清，不能直接猜测并执行。**

1. 识别层结合当前消息、活跃任务和近期上下文，抽取目标、对象、动作、交付物、约束与副作用。对“处理一下”“继续”“优化它”等请求，先解析指代并生成Top-K意图，标注证据、置信度和**关键缺失字段**。

| 处理策略 | 适用条件 | 示例 |
| --- | --- | --- |
| 默认推断 | 低风险且偏好稳定 | 输出格式与语言 |
| 上下文检索 | 指代可由历史唯一确定 | “继续上一题” |
| 预览确认 | 可逆但方案差异明显 | 修改草稿 |
| 直接澄清 | 高风险或对象不唯一 | 删除、发布、付款 |

2. 澄清问题追求最大信息增益，只询问会改变路径或验收结果的字段，并提供互斥选项。例如不问“请补充需求”，而问“需要解释代码、修改代码，还是运行测试”。一次只问关键问题，不重复已知内容。

3. 低风险缺失信息可采用显式假设，例如默认输出Markdown并先预览；可逆修改在草稿、分支或沙箱执行；涉及权限、真实写入和不可逆副作用时必须确认。用户不回应时可提供只读分析，不能升级范围。

4. 维护槽位Schema、标签正反例、领域词典与默认策略，并校准置信度。日志记录候选、缺失槽位、澄清和用户修正，评估意图准确率、澄清轮数、无效澄清率、误执行率与完成率。

**相关知识点：** 槽位填充、Top-K意图、指代消解、信息增益、澄清策略、显式假设、可逆执行、置信度校准。
<a id="plan-045"></a>
### 任务识别模块如何做迭代优化与冷启动设计

**任务识别冷启动应先以清晰标签、规则和LLM少样本分类建立可用基线，再通过高质量反馈闭环逐步数据化和模型化。**

1. 冷启动先定义分层标签、正反例、易混边界、槽位和错误成本，优先覆盖高频与高风险意图。格式和安全边界用规则处理，长尾由LLM少样本分类；低置信度请求进入澄清或人工队列，避免过早训练分类器。

| 阶段 | 核心方案 | 主要目标 |
| --- | --- | --- |
| 冷启动 | 规则、LLM少样本、人工兜底 | 快速可用 |
| 数据积累 | 日志、主动学习、专家标注 | 提升样本质量 |
| 稳定期 | 小模型粗分、LLM处理长尾 | 降低成本延迟 |
| 持续迭代 | 漂移监控、灰度与回滚 | 保持线上效果 |

2. 线上记录规则命中、Top-K候选、置信度、澄清、路由和结果，但不能把用户未纠正视为正确标签。优先抽样分差小、损失高、模型分歧大和新分布样本，由多人审核；使用**主动学习**提高标注收益。

3. 数据积累后训练轻量分类器承担高频意图，LLM处理长尾与多意图。固定测试集并按领域、语言和时间切片，评估Macro-F1、长尾召回、校准误差、误执行率和完成率；标签变更时建立映射。

4. 规则、Prompt、模型和阈值分别版本化，经离线回放、影子流量与灰度上线，回归时回滚。监控输入、标签和置信度漂移；新意图先进入Unknown类，达到频次和价值门槛后再新增标签。

**相关知识点：** 冷启动、少样本分类、主动学习、Unknown类、标签体系、置信度校准、数据漂移、灰度发布。
<a id="plan-046"></a>
### 为什么不能直接让LLM回答所有任务，而需要任务识别？

**任务识别是LLM进入执行系统前的控制平面，用于选择能力、权限、成本和验证策略；缺少这一层会把生成能力误当成可靠执行能力。**

1. 任务完成条件不同：问答需要事实依据，代码解释需读取仓库，代码修改需写权限与测试，发布还涉及审批和副作用。若让LLM统一回答，可能在缺工具时编造、意图不清时误操作，或对简单请求浪费资源。

| 控制维度 | 直接回答的风险 | 任务识别后的处理 |
| --- | --- | --- |
| 能力 | 不知道是否需检索、代码或工具 | 路由模型与Skill |
| 权限 | 可能越权访问或写入 | 最小权限与审批 |
| 成本 | 所有请求使用同一配置 | 模型级联与预算 |
| 验证 | 只判断文本是否流畅 | 按任务选择Validator |
| 状态 | 忽略多轮任务与副作用 | 绑定Task State |

2. 任务识别将语言解析成**Task Spec**，包括目标、对象、交付物、约束、风险、工具和验收标准，再决定直接回答、检索、调用工具、进入Workflow或澄清。规则控制安全边界，LLM处理开放语义。

3. 识别层隔离不确定性：高置信度低风险任务直接执行，中置信度采用只读或可逆方案，低置信度且解释影响资源时必须澄清。权限、合规和金额限制由宿主校验，模型不能覆盖硬规则。

4. 任务识别也有成本，简单场景用规则或小模型，高难度和长尾才升级LLM。评估准确率、误路由率、越权拦截率、完成率、P95延迟和单位成本，验证路由收益。

**相关知识点：** Task Spec、意图识别、能力路由、模型级联、最小权限、Validator、Task State、错误成本。
<a id="plan-047"></a>
### Agent如何区分简单任务和复杂任务？

**Agent应依据完成任务所需的决策闭环判断复杂度，而不是以输入长度、专业术语多少或表面步骤数作为标准。**

1. 简单任务目标单一、输入充分、路径确定且无外部状态变化，可一次生成或单次调用完成。复杂任务包含目标歧义、子任务依赖、异构工具、长期状态、动态反馈或不可逆副作用，需要Planner、Runtime和Validator控制。

| 判断维度 | 简单任务 | 复杂任务 |
| --- | --- | --- |
| 目标 | 单一明确 | 多目标或约束冲突 |
| 路径 | 一次回答或调用 | 多阶段且有依赖 |
| 状态 | 无状态、短上下文 | 跨轮或外部状态 |
| 风险 | 只读、易撤销 | 高影响或不可逆 |
| 验证 | 易判断正确性 | 多指标或需交叉验证 |

2. 建立**复杂度评分**，对目标不确定性、节点数、依赖深度、工具数量、时长、失败代价和验证难度赋分。低分直接回答，中分生成轻量步骤，高分启用DAG、检查点、预算和人工门控。阈值由真实数据校准。

3. 复杂度动态变化。执行中若工具失败、信息冲突、范围扩大或风险升级，应升类并局部重规划；若节点独立且路径固定，可降级为并行Workflow，减少调用和协调成本。

4. 区分认知难度与执行复杂度：专业数学问题可能只需一次推理，而“上线版本”虽短，却涉及测试、审批、部署和回滚。记录分类证据及等级变化，评估识别准确率、升降级率、误路由率、完成率和单位成本。

**相关知识点：** 复杂度评分、Task Spec、任务分解、DAG、动态路由、局部重规划、风险分级、Workflow。
<a id="plan-048"></a>
### 任务复杂度一般如何评估？有哪些指标？

**任务复杂度应通过可观测特征形成多维评分，并以真实执行成本和失败结果持续校准，而不是依赖LLM主观判断。**

1. 维度包括目标不确定性、子任务数、依赖深度、工具种类、上下文跨度、外部状态、时长、验证难度和失败代价。各项按0—2或0—5分，再按风险加权形成**Complexity Score**；高风险项可一票升档。

| 指标类别 | 典型指标 | 反映问题 |
| --- | --- | --- |
| 结构复杂度 | 节点数、依赖深度、分支数 | 计划与调度难度 |
| 能力复杂度 | 工具数、领域数、模型档位 | 能力组合难度 |
| 状态复杂度 | 会话跨度、外部写入数 | 恢复与一致性难度 |
| 风险复杂度 | 权限级别、不可逆操作数 | 治理与审批成本 |
| 验证复杂度 | 验证器数、人工判定比例 | 正确性确认难度 |

2. 评分映射策略：低分直接回答；中分生成轻量计划并验证；高分启用DAG、Checkpoint、异步Runtime和人工门控。还应根据工具失败、范围扩张、数据冲突和风险更新，支持运行时升降级。

3. 预估值要与真实节点数、工具调用数、Token、墙钟时间、重试、重规划、人工介入率和单位成本对照。预估低但实际开销高说明特征缺失；持续高估则会造成不必要的Planner和强模型成本。

4. 使用历史任务训练分档模型，并按领域校准阈值；测试集覆盖短文本复杂任务和长文本简单任务。监控分档准确率、过度规划率、漏判率、完成率及成本偏差，并检查数据漂移。

**相关知识点：** Complexity Score、任务DAG、关键路径、动态升降级、成本预测、风险分级、数据漂移。
<a id="plan-049"></a>
### 如何设计一套Task Classification体系？

**Task Classification体系应采用分层、多轴、多标签设计，并让每个标签对应明确的路由、权限、预算和验收策略。**

1. 从业务决策反推标签。一级轴描述查询、解释、生成、修改和执行等意图；二级轴描述领域与交付物；独立轴标注复杂度、风险、工具和敏感度。每个标签须有定义、正反例、易混项及Unknown边界。

| 设计方式 | 优势 | 主要问题 |
| --- | --- | --- |
| 单层单标签 | 简单、易实现 | 无法表达复合请求 |
| 层次分类 | 支持粗到细路由 | 父子标签需一致 |
| 多标签 | 表达多个并存意图 | 阈值与组合更复杂 |
| 多轴分类 | 解耦意图、风险和能力 | Schema治理要求高 |

2. 请求解析为**Task Spec**，包含目标、对象、动作、交付物、约束和副作用。规则处理格式与安全边界，轻量分类器召回高频标签，LLM处理长尾、多意图和指代。输出包括Top-K标签、置信度、证据和缺失字段。

3. 标签转成执行决策：意图决定Workflow，复杂度决定Planner，风险决定审批与沙箱，工具轴决定Skill，敏感度决定访问范围。父子标签和多轴组合须校验；低置信度且候选副作用不同时澄清，新请求进入Unknown类。

4. 标签、指南、规则、模型和阈值均需版本化。评估标注一致性、Macro-F1、长尾召回、混淆矩阵、校准误差、误路由率及完成率；新增标签前验证样本量、业务价值和可分性，避免标签膨胀。

**相关知识点：** 层次分类、多标签分类、多轴分类、Task Spec、Unknown类、标签治理、置信度校准、任务路由。
<a id="plan-050"></a>
### Rule Engine和LLM分类各有什么优缺点？

**Rule Engine以确定性、低成本和可审计见长，LLM分类以语义泛化和长尾覆盖见长，两者适用于不同的不确定性区间。**

1. Rule Engine把字段、正则和业务条件编码为显式逻辑，稳定、低延迟且可追溯，适合权限、合规、固定命令和高精度拦截。规则增多后易冲突、优先级复杂、维护成本上升，也难处理同义表达、隐含意图和指代。

| 维度 | Rule Engine | LLM分类 |
| --- | --- | --- |
| 确定性 | 高，可重复 | 受模型和Prompt影响 |
| 语义泛化 | 弱 | 强 |
| 延迟与费用 | 低 | 较高 |
| 可解释性 | 命中条件明确 | 需额外证据字段 |
| 变更方式 | 修改规则并回归测试 | 调整Prompt、样本或模型 |
| 典型失败 | 漏掉长尾、规则冲突 | 幻觉、漂移、格式不稳 |

2. LLM能理解长文本、多意图、否定和指代，通过少样本快速支持新标签。但它存在随机性、成本与延迟，模型升级可能导致漂移；自报置信度通常未校准，也不能承担权限和安全边界。

3. 生产系统采用**级联混合方案**：前置规则处理名单、格式和风险，未命中请求交给LLM输出Top-K标签、证据与缺失字段，后置规则检查兼容性、参数和权限。冲突时安全规则优先，低置信度且副作用不同时澄清。

4. 两套机制独立版本化。规则评估覆盖率、冲突率和误拦截率；LLM评估Macro-F1、长尾召回、格式遵从率和校准误差；端到端监控误路由率、完成率、P95延迟及单位成本。

**相关知识点：** Rule Engine、LLM分类、级联分类、规则优先级、长尾意图、置信度校准、Guardrail、灰度发布。
<a id="plan-051"></a>
### 为什么企业级Agent通常采用Rule + LLM的混合路由方案？

**企业级Agent采用Rule与LLM混合路由，是为了同时获得确定性治理、开放语义覆盖和可控的成本性能。**

1. 企业请求既有权限、合规、租户隔离等精确约束，也有同义表达、多轮指代和长尾意图。Rule适合前者，LLM适合后者；只用规则会覆盖不足，只用LLM则难保证稳定、安全与审计。

| 方案 | 优势 | 主要风险 |
| --- | --- | --- |
| 纯Rule | 低延迟、可解释、结果稳定 | 长尾召回弱、规则冲突 |
| 纯LLM | 泛化强、上线新意图快 | 随机、昂贵、难兜底 |
| Rule+LLM | 边界稳定且覆盖长尾 | 需要冲突与版本治理 |

2. 典型链路是**前置Rule—LLM语义路由—后置Rule**。前置规则处理名单、格式、权限和风险；LLM输出Top-K意图、槽位、证据与缺失字段；后置规则校验标签、Schema、权限和预算。冲突时安全及合规规则优先。

3. 混合路由可实施模型级联：规则或小模型处理高频请求，复杂长尾才升级强模型，降低延迟和Token成本。低置信度且副作用不同时澄清；低风险请求可记录假设后进入只读或可逆流程。

4. 分别版本化规则、标签、Prompt、模型与阈值，记录规则命中、候选、置信度、路由和结果。离线评估Macro-F1、长尾召回和校准误差，线上监控误拦截率、误路由率、完成率、风险事件及单位成本。

**相关知识点：** 混合路由、Rule Engine、LLM分类、模型级联、Guardrail、置信度校准、灰度发布、审计日志。
<a id="plan-055"></a>
### Agent什么时候应该向用户发起澄清（Clarification）？

**Agent应在关键歧义无法由可信上下文消除，且错误解释会显著改变结果、权限或副作用时发起澄清。**

1. 检查目标、对象、交付物、约束、权限和验收标准。对象不唯一、必填参数缺失、指令冲突、请求可能越权，或候选会修改不同资源时必须澄清。仅影响格式等低风险偏好的缺失项，可采用默认值。

| 处理方式 | 适用条件 | 示例 |
| --- | --- | --- |
| 直接执行 | 高置信度、低风险 | 解释一段已指定代码 |
| 显式假设 | 缺失项可逆且影响小 | 默认Markdown格式 |
| 预览确认 | 可逆但方案差异明显 | 先展示修改草稿 |
| 必须澄清 | 高风险、对象不唯一 | 删除、发布、付款 |

2. 澄清门控应结合**置信度与错误成本**，不能只设统一分数阈值。即使分类概率较高，只要操作不可逆或涉及敏感数据，也应确认关键参数；反之，低置信度但所有候选都导向相同只读动作时，可先收集信息再判断。

3. 问题应最小化并提高信息增益：一次询问最能区分候选路径的字段，提供少量互斥选项，并说明选择将影响什么。例如不问“请补充需求”，而问“需要解释代码、修改代码，还是执行测试”。已从上下文确定的信息不应重复询问。

4. Agent应限制澄清轮数，用户未回应时可提供只读分析、保存草稿或安全终止，不得扩大权限。记录触发原因、候选意图、提问、用户修正和结果，评估澄清有效率、平均轮数、误执行率及完成率。

**相关知识点：** Clarification、信息增益、槽位填充、置信度校准、错误成本、显式假设、预览确认、安全终止。
<a id="plan-056"></a>
### Skill Router通常如何设计？

**Skill Router应采用能力注册、硬约束过滤、混合召回、精排和结果验证的多阶段架构，确保选中的Skill既相关又可执行。**

1. Skill Registry保存描述、适用与禁用场景、输入输出Schema、工具、权限、成本、版本及成功标准。请求解析为Task Spec，包括目标、对象、交付物、约束和风险；两者使用统一Schema。

| 路由阶段 | 核心方法 | 主要目标 |
| --- | --- | --- |
| 硬过滤 | Schema、权限、环境规则 | 排除不可执行能力 |
| 候选召回 | 关键词与向量检索 | 覆盖精确及语义匹配 |
| 精排 | LLM或学习排序 | 判断上下文适配度 |
| 验证 | 前置条件与结果校验 | 控制错误与副作用 |

2. 硬过滤检查输入、权限、工具和禁用条件；召回层融合BM25与向量检索得到Top-K。精排综合语义相关度、参数完整度、历史成功率、延迟、费用和风险，并输出理由与**校准置信度**。

3. 最高分低于阈值，或前两名分差小且副作用不同时，应澄清；低风险可沙箱试运行。单个Skill不足时，由Planner组合候选能力并构建依赖图。Validator检查结果，失败时重选能力或局部重规划。

4. 新Skill经过冲突、Schema兼容、安全审查和离线回放后灰度注册。记录候选集、过滤原因、评分、版本和结果，评估Top-K召回率、匹配准确率、误调用率、完成率、P95延迟及单位成本。

**相关知识点：** Skill Registry、Task Spec、混合检索、学习排序、能力路由、置信度校准、Validator、灰度注册。
<a id="plan-059"></a>
### Planner在任务识别之后承担什么职责？

**任务识别回答“这是什么任务”，Planner随后回答“如何在约束内完成”，并产出可调度、可验证、可恢复的执行计划。**

1. Planner接收包含目标、交付物、风险、Skill、预算和验收标准的Task Spec。它检查信息：低风险缺失项记录假设，高影响歧义返回澄清；简单任务直接交给Executor。

| 模块 | 核心职责 | 主要产物 |
| --- | --- | --- |
| Classifier | 判断意图与风险 | 标签、Task Spec |
| Planner | 分解、选路与分配资源 | DAG、预算 |
| Scheduler | 选择节点与Worker | 调度决策 |
| Executor | 调用模型或工具 | 节点结果 |
| Validator | 检查完成条件 | 判定与证据 |

2. Planner从验收条件反推产物，将任务拆成可验证和重试的节点，并建立数据、控制依赖和资源冲突边。节点声明执行器、参数Schema、超时、重试、风险和成功条件，形成**结构化DAG**。

3. 它还负责资源与风险规划：选择模型和Skill，识别并行节点，估算费用和时限，把高风险操作安排在备份、验证和审批之后。稳定路径复用Workflow，只有开放部分动态规划。

4. 工具不可用、假设失效或结果不合格时，Planner保留有效节点并局部重规划。系统限制计划深度、节点数、重规划次数和预算；评估可执行率、依赖正确率、重规划收益、完成率及单位成本。

**相关知识点：** Task Spec、Planner、任务分解、DAG、Workflow、资源预算、Validator、局部重规划。
<a id="plan-061"></a>
### 如何判断一个任务需要任务拆解（Task Decomposition）？

**当任务无法通过一次可验证动作可靠完成，且存在多个中间产物、依赖、工具或风险边界时，就应进行任务拆解。**

1. 判断信号包括多个交付物、步骤依赖、异构工具、长时间执行、跨轮状态、中间验证、局部重试，以及审批或不可逆操作。命中任一高风险条件或多个一般条件，均应拆解。

| 判断维度 | 无需拆解 | 需要拆解 |
| --- | --- | --- |
| 目标 | 单一且明确 | 多目标或约束冲突 |
| 执行 | 一次生成或调用 | 多工具、多阶段 |
| 状态 | 无状态、短上下文 | 长期或外部状态 |
| 验证 | 结果一次判定 | 中间产物需验证 |
| 失败 | 可整体重试 | 需局部恢复或补偿 |

2. 对节点数、依赖深度、工具数、时长、失败代价和验证难度建立**拆解评分**。低分直接执行，中分生成轻量步骤，高分构建DAG与Checkpoint。阈值以完成率、延迟和成本校准，不能按Prompt长度判断。

3. 节点应满足输入输出明确、可验证、可重试和失败可定位。若子任务仍含多个目标，应继续递归；若过细导致通信和调度成本超过收益，则合并。稳定路径复用Workflow，开放部分由Planner生成。

4. 工具失败、范围扩大或风险升级时可动态拆解并局部重规划；若节点无独立价值，可合并执行。评估拆解触发准确率、过度拆解率、复杂任务漏判率、并行收益和完成率。

**相关知识点：** Task Decomposition、复杂度评分、任务粒度、DAG、Checkpoint、Workflow、局部重规划。
<a id="plan-064"></a>
### 如何设计企业级Agent的执行路由（Execution Routing）？

**企业级执行路由应将自然语言任务转换为受身份、权限、风险、能力、SLA和预算约束的确定执行路径。**

1. 入口完成认证、隔离、限流和检查，再解析Task Spec，包括意图、交付物、风险、工具和验收标准。规则处理命令，分类器覆盖高频，LLM处理长尾；输出Top-K路由和置信度。

| 路由层 | 决策内容 | 典型产物 |
| --- | --- | --- |
| 安全路由 | 权限、合规 | 允许或拒绝 |
| 能力路由 | 模型、Skill、工具 | 执行器 |
| 控制路由 | ReAct、Planner、Workflow | 执行模式 |
| 资源路由 | 配额、并发 | Worker与预算 |
| 恢复路由 | 重试、补偿、接管 | 失败策略 |

2. 过滤无权限、不可用或副作用不允许的路径，再按相关度、成功率、延迟、费用和风险精排。简单请求直答，短任务进入ReAct，长任务交给Planner，稳定流程复用**Workflow**。低置信度且副作用不同时澄清。

3. Runtime执行前校验Schema、凭证、幂等性和审批，设置超时、重试与并发。只读节点可并行，写同一资源须串行或加锁；Validator检查结果，失败按类型重试、换路、补偿或转人工。

4. 规则、Prompt、模型、Skill和策略版本化，经回放和灰度发布。记录Trace ID、候选、过滤原因、证据、版本、成本与结果，评估路由准确率、越权拦截率、完成率、P95延迟及单位成本。

**相关知识点：** Execution Routing、Task Spec、能力路由、Workflow、权限、幂等、Validator、灰度发布。
<a id="plan-066"></a>
### 如何评估任务识别模块的效果？常用指标有哪些？

**任务识别模块应从标签判断、槽位抽取、置信度、路由结果、业务风险和运行成本六个层面联合评估。**

1. 评测集覆盖高频、长尾、多意图、否定、指代、切换、模糊输入及Unknown。规范定义标签边界、槽位和错误成本，多人标注并以Kappa衡量一致性。

| 层面 | 常用指标 | 主要目的 |
| --- | --- | --- |
| 分类 | Accuracy、Macro-F1 | 标签正确性 |
| 多标签 | Exact Match、Hamming Loss | 组合标签 |
| 槽位 | Slot F1、完整率 | Task Spec质量 |
| 校准 | ECE、Brier Score | 分数可信度 |
| 路由 | 误路由率、Unknown召回率 | 执行选择 |
| 业务 | 误执行率、完成率 | 最终价值 |

2. 类别不均衡时不能只看Accuracy，应报告每类Precision、Recall、Macro-F1和混淆矩阵，重点检查高风险Recall。多标签同时评估标签与槽位；建立**成本加权错误率**，对越权和误写入提高权重。

3. 置信度在验证集校准，用可靠性图、ECE和Brier Score检查。阈值评估覆盖率、自动执行准确率、澄清率和拒答率。线上观察指代正确率、任务串扰率、人工接管率和完成率。

4. 工程指标包括P50/P95延迟、Token成本、规则命中率和可用性。按领域、语言、输入长度与版本切片，监控漂移和最差分组。采用影子流量或A/B实验，以置信区间判断差异。

**相关知识点：** Macro-F1、Slot F1、Top-K Recall、Hamming Loss、ECE、成本敏感评估、数据漂移、A/B测试。
<a id="plan-067"></a>
### 任务识别模块如何支持新增Skill和业务能力，保证系统具备良好的可扩展性？

**可扩展的任务识别模块应采用能力注册表、统一契约与分层路由，使新增Skill主要表现为配置和插件接入，而非修改核心判断逻辑。**

1. 建立**Skill Registry**，每项能力声明名称、版本、意图、输入输出Schema、前置条件、权限、副作用、成本和示例。识别模块依赖元数据生成候选能力，执行器通过稳定接口调用，避免硬编码Skill分支。

| 方案 | 扩展方式 | 主要问题 |
| --- | --- | --- |
| 条件分支 | 修改核心代码 | 耦合高、回归面大 |
| Prompt枚举 | 追加能力描述 | 长度增长、边界模糊 |
| 注册表+插件 | 注册契约并加载 | 需治理版本兼容 |

2. 路由采用“领域—意图—Skill”分层检索：先缩小业务域，再依据语义、规则和上下文召回Top-K能力，最后校验参数与权限。若多个Skill能力重叠，应设置优先级、互斥关系及消歧样例；低置信度或高风险冲突进入澄清，不直接执行。

3. 新增能力应经过离线样例、对抗样例、历史流量回放和契约测试，验证旧任务不被错误吸收。使用灰度发布、版本锁定和快速回滚控制影响，并监控**路由准确率、Unknown召回率、误调用率及端到端完成率**。

4. 业务扩展需治理标签生命周期：支持别名、父子意图、废弃标记和Schema迁移；能力目录与向量索引原子更新，日志记录注册表版本。这样能够定位路由漂移，并允许识别器、Skill和业务策略独立演进。

**相关知识点：** Skill Registry、插件架构、能力契约、分层路由、Schema校验、语义检索、灰度发布、版本治理。
<a id="plan-068"></a>
### 如果同一个用户请求同时包含问答、代码修改和文档生成等多种意图，Agent应如何进行多意图识别与编排执行？

**多意图请求应被拆成具有依赖关系的原子子任务，并以DAG统一编排，共享事实但隔离每个任务的状态与副作用。**

1. 识别阶段采用多标签分类并抽取每个意图的目标、对象、输入、交付物和约束。例如“解释报错、修改代码并生成说明文档”拆为诊断、改码、验证和写文档，而不是路由到单一标签。若对象或范围不明确且影响写操作，应先澄清。

2. 编排器根据数据依赖和副作用生成**任务DAG**：诊断结果是改码输入，测试通过是文档定稿的前置条件；互不依赖的检索和环境检查可以并行。每个节点声明执行器、输入Schema、完成条件、重试策略、权限及产物引用。

| 执行关系 | 适用条件 | 示例 |
| --- | --- | --- |
| 串行 | 后项依赖前项产物 | 改码后生成变更说明 |
| 并行 | 输入独立且无资源冲突 | 查文档与读取日志 |
| 条件 | 由检查结果决定分支 | 测试失败则修复 |
| 人工门控 | 高风险或不可逆操作 | 发布前确认 |

3. 上下文管理使用共享事实库保存需求和已验证证据，节点局部上下文仅保留必要材料，防止问答内容污染代码修改。产物通过ID和版本传递，禁止依赖自然语言中的隐式状态；写操作设置幂等键、检查点和补偿动作。

4. 执行中持续重规划：节点失败先判断可重试、可替代或必须终止，并只重跑受影响的下游。最终汇总各子任务状态、修改文件、验证证据和未完成项，避免部分成功被表达为整体完成。评估关注意图召回率、依赖正确率、误执行率及端到端完成率。

**相关知识点：** 多标签分类、任务分解、DAG编排、依赖分析、上下文隔离、幂等性、补偿事务、动态重规划。
<a id="plan-069"></a>
### Agent如何识别用户真实意图，而不是字面意思？

**识别真实意图的关键是结合会话目标、语用信号和可用环境形成候选假设，再以证据与风险决定执行或澄清，而非擅自猜测用户心理。**

1. 将输入解析为三层：字面行为、期望结果和隐含约束。例如“这个测试怎么又失败了”字面是询问原因，潜在目标可能是定位故障，也可能要求修复；Agent应结合前文是否已授权改码、当前工作区和交付约定判断，但不能把抱怨自动解释为写入授权。

| 证据来源 | 可推断内容 | 主要限制 |
| --- | --- | --- |
| 措辞 | 动作、对象、语气 | 省略和反讽较多 |
| 会话历史 | 指代、连续目标 | 旧意图可能失效 |
| 环境状态 | 文件、报错、页面 | 状态不代表授权 |
| 用户习惯 | 表达偏好 | 不可覆盖本轮指令 |

2. 构造**意图假设**，分别抽取目标、对象、交付物、权限和完成条件，并依据显式指令、上下文一致性、可执行性及历史先验排序。关键判断应附证据；对否定、条件句、反问、代词和“顺便”等复合语用进行解析。

3. 决策遵循风险门控：低风险且假设差异不影响结果时，声明合理假设后继续；高风险、不可逆或不同解释会产生不同交付物时，提出最小化澄清问题。即使推断出真实目标，也必须遵守**显式权限边界**，不得自行发布、删除或对外发送。

4. 执行后利用用户纠正、接受率和任务完成结果更新识别策略，但应区分短期会话状态与长期偏好，避免把一次行为固化为永久习惯。评估除意图准确率外，还要关注澄清有效率、误执行率、纠正次数和端到端完成率。

**相关知识点：** 语用学、会话状态、指代消解、意图假设、置信度校准、风险门控、最小澄清、权限边界。

### 为什么复杂任务不能一次性交给LLM完成？

**复杂任务不宜一次性交给LLM完成，因为长链路中的假设、状态和错误会累积，模型也无法在单次生成中获得真实执行反馈并修正后续决策。**

1. LLM生成的是概率性文本，不等于任务已执行。复杂任务依赖文件、接口、权限、测试和动态环境；若一次生成全部步骤，早期错误会被后续内容当作事实，形成**误差传播**。步骤正确率即使较高，整体成功率也会乘积下降。

| 维度 | 一次性生成 | 分步闭环 |
| --- | --- | --- |
| 状态依据 | 依赖预设和猜测 | 使用实时工具结果 |
| 错误处理 | 后续错误连锁 | 节点级定位与修复 |
| 上下文 | 全部材料相互干扰 | 按任务裁剪 |
| 验证 | 末端统一检查 | 每步设置检查点 |
| 副作用 | 难暂停和回滚 | 权限门控、可补偿 |

2. 单次提示受上下文窗口、注意力稀释和输出长度限制。需求、代码、日志与文档同时输入时，关键约束容易被忽略；长输出可能目标漂移、步骤遗漏和前后矛盾。将任务拆为明确输入输出的节点，可减少干扰并独立验证。

3. 采用“规划—执行—观察—校验—重规划”：Planner产生计划，Executor调用工具，Validator根据测试或Schema判断结果，失败时只重做受影响节点。写入、发布等操作还应设置幂等键、审批点和回滚策略。

4. 并非所有任务都需要拆解。问答、单文件解释或一次工具调用若低风险且能验证，直接完成更经济；只有依赖多、状态动态、耗时长或副作用高时，显式任务分解才具有净收益。

**相关知识点：** 误差传播、长程规划、上下文窗口、Agent Loop、检查点、局部重规划、幂等性、补偿事务。

### Agent如何处理用户需求存在歧义的情况？

**歧义处理应以“候选解释—证据排序—风险评估—最小澄清”为主线，在减少打断的同时防止错误执行。**

1. 先识别歧义类型：目标不清、对象指代不明、范围缺失、约束冲突、时间表达模糊或授权边界未知。将每种解释转为**Task Spec候选**，列出目标、对象、交付物、副作用和依据，再结合本轮措辞、会话历史、用户角色与环境状态排序。

| 条件 | 处理方式 | 示例 |
| --- | --- | --- |
| 差异不影响结果且低风险 | 记录假设后执行 | 输出格式未指定 |
| 可通过只读检查消除 | 先检查环境 | “这个文件”可由当前编辑文件确定 |
| 候选导致不同交付物 | 提出选择式澄清 | 解释代码还是修改代码 |
| 涉及不可逆或越权操作 | 明确确认权限与范围 | 删除、发布、对外发送 |

2. 澄清问题应具有最大信息增益，只询问会改变计划的变量，并提供互斥候选及影响。例如不笼统询问“请补充需求”，而应询问“仅修复模块，还是同步修改调用方？”能从可信上下文确定的信息不重复询问。

3. 置信度不是唯一标准，还要考虑**错误成本**。高置信度推断若涉及写入、付款或外发，也需要权限检查；低置信度但可安全回滚的细节可以先采用默认值。用户未及时回应时，只能继续不扩大副作用的工作。

4. 执行前将确认结果写回任务状态，避免后续节点再次误解；执行后记录候选解释、选择证据、澄清轮次和纠正结果。评估指标包括歧义识别召回率、有效澄清率、平均澄清轮次、误执行率和任务完成率。

**相关知识点：** 歧义消解、Task Spec、指代消解、候选假设、信息增益、风险门控、最小澄清、置信度校准。

### Agent如何利用Memory提升意图识别准确率？

**Memory应作为带来源、时效和置信度的辅助证据参与意图排序，用于补全指代与稳定偏好，但不能覆盖用户当前的显式指令。**

1. 会话记忆保存最近目标、对象、约束和未完成任务，可解析“继续处理它”等省略表达；长期记忆保存用户允许持久化的语言、格式和领域偏好；情节记忆记录相似任务及纠正结果，用于调整意图先验。

| 记忆类型 | 对识别的作用 | 主要风险 |
| --- | --- | --- |
| 工作记忆 | 维持本轮目标和指代 | 上下文污染 |
| 情节记忆 | 复用历史任务模式 | 过度类比 |
| 语义记忆 | 提供领域实体关系 | 知识过期 |
| 偏好记忆 | 补全稳定选择 | 将偶然行为永久化 |

2. 检索前根据用户、会话、时间、领域和权限过滤，再以相似度、时间衰减、来源可信度和历史有效性排序。仅注入支持或反驳候选的少量记录，并标记Memory ID；不能把整段历史塞入上下文。

3. 识别器先从本轮输入生成候选，再使用**Memory Evidence**重排，而非先读记忆后套用旧意图。证据冲突时遵循“当前显式指令＞本轮确认事实＞近期行为＞长期偏好”；若旧记忆会改变高风险操作，应向用户确认而不是自动执行。

4. 写入记忆需要抽取、去重、敏感信息过滤、用户授权和TTL；用户纠正后应失效或修订旧记录。通过带Memory与不带Memory的对照评测，观察意图准确率、指代正确率、澄清率和记忆误导率，防止表面命中提升而误执行增加。

**相关知识点：** 工作记忆、情节记忆、语义记忆、偏好记忆、Memory Retrieval、时间衰减、证据排序、TTL、记忆治理。

### Agent如何判断一个任务是否需要拆解？

**任务是否拆解应比较“复杂度与失败代价”和“规划与协调开销”，只有拆解能提高净成功率时才进入Planner。**

1. 识别模块先计算可解释的复杂度特征：目标数量、交付物数量、工具与数据源数量、依赖深度、预估时长、外部状态变化、风险级别和上下文规模。高风险不可逆动作应单独成节点，即使任务总体不复杂。

| 信号 | 倾向拆解 | 倾向直执行 |
| --- | --- | --- |
| 交付物 | 多个且验收标准不同 | 单一明确结果 |
| 依赖 | 跨工具、跨文件或需等待 | 一次调用完成 |
| 环境 | 动态且需反馈修正 | 输入信息充分 |
| 风险 | 写入、发布、付款、删除 | 只读且可回滚 |
| 恢复 | 失败需局部重试 | 可低成本整体重做 |

2. 可采用**复杂度评分+硬规则**：高风险、长时间或多阶段任务直接规划；其余按加权得分与阈值判断。阈值不能只靠经验，应使用历史任务的完成率、规划延迟、重试成本和误执行率校准，并按领域分别设置。

3. 决定拆解后，从最终验收条件反推中间产物，构建DAG。每个子任务须具备单一责任、明确输入输出、执行器和Validator，粒度以可独立验证、可安全重试且失败可定位为界；若协调成本超过执行成本，应合并相邻节点。

4. 决策可在执行中调整：直接任务发现新依赖时升级为规划任务；已拆解任务若节点过多可折叠为Workflow或复合Skill。系统记录拆解决策、特征和最终效果，监控过度规划率、漏规划率、端到端完成率与P95延迟。

**历史别名：** `PLAN-070`、`PLAN-206`。

**相关知识点：** 复杂度分类、硬规则、任务粒度、成本收益分析、Task Spec、DAG、过度规划、动态升级。

### Cursor Agent如何决定搜索代码还是生成代码？

**Cursor Agent由模型根据当前证据缺口动态选择搜索、读取、编辑或终端工具，官方并未公开固定的“搜索或生成”评分公式。**

1. 当问题涉及现有实现、符号定义、调用链、项目约定或错误位置时，Agent应先搜索代码库并读取相关文件；只有目标、修改范围和依赖证据充分时才生成补丁。搜索结果若相互矛盾，应扩大检索，而非凭局部片段直接改写。

2. 路由信号通常包括用户是否指定文件、上下文中是否已有完整定义、任务是解释还是修改、修改是否跨模块、编译与测试反馈。**搜索用于降低事实不确定性，生成用于实施已定位的变化**；二者不是互斥阶段，而是可多轮交替。

| 情形 | 优先动作 | 原因 |
| --- | --- | --- |
| 定位未知实现 | 语义搜索、Grep | 建立证据 |
| 已知文件但缺依赖 | 读取定义与引用 | 控制影响面 |
| 新建独立模块 | 生成后检索校验 | 遵循项目约定 |
| 测试失败 | 搜索错误链并修补 | 反馈驱动迭代 |

3. 修改后应运行格式化、类型检查或测试，并根据结果重新搜索。若工具预算受限，可先用符号或语义检索缩小范围，再读取最相关文件。面试中不能把这种可观察循环描述为Cursor已公开的确定性路由器或阈值模型。

**相关知识点：** Codebase Search、语义检索、Grep、信息增益、工具路由、上下文收集、生成补丁、测试反馈、公开能力边界。

### Agent 如何控制 Token 消耗？

**Token治理重点是减少无关输入与无效迭代：对历史和工具结果分层摘要，只检索当前步骤证据，复用Prompt前缀缓存，并为每个Step设置输入、输出与累计预算。**

1. 执行前依据任务复杂度分配总Token预算，再按Plan拆到Step、模型调用和反思轮次。Runtime实时累计input、output、reasoning及cached token，结合剩余节点预测完工消耗；达到软阈值时降级，硬阈值时保存状态并停止。

2. 针对“Agent 如何控制 Token 消耗”，输入侧通过**检索裁剪、历史摘要、工具结果句柄和Prompt去重**减少无关上下文；输出侧设置结构化格式、最大Token和停止条件。路由器按任务难度选择模型与推理档位，简单分类、抽取和格式化优先使用小模型或确定性代码。

| 手段 | 主要收益 | 风险控制 |
| --- | --- | --- |
| 上下文裁剪 | 降低输入Token | 保留目标与约束 |
| 模型分级 | 降低单次单价 | 按难度与风险路由 |
| 结果缓存 | 减少重复推理 | 版本键、TTL、权限隔离 |
| 预算终止 | 控制最坏成本 | 返回明确未完成状态 |

3. 系统为租户、任务和步骤设置Token与费用预算，记录缓存命中、**重试**、反思和工具等待成本。稳定只读结果可按版本缓存，实时或权限敏感数据缩短TTL；超预算时优先关闭非关键反思、降低候选数量或转人工，不能静默牺牲高风险任务的正确性。

**相关知识点：** Token预算、上下文压缩、模型路由、语义缓存、Prompt缓存、提前终止、成本归因。

### Intent Classification 具体用什么模型/方法实现？规则、传统机器学习模型、还是 LLM 分类，各自的优劣是什么？

**生产级Intent Classification通常采用规则、传统分类器与LLM级联：规则处理确定命令，分类器覆盖高频标签，LLM负责长尾与复合语义。**

1. 先建立互斥或多标签Taxonomy、Unknown类别和误分类成本。规则基于关键词、正则与状态，确定且可审计；传统模型可用TF-IDF+线性分类器或小型Encoder，延迟低且概率易校准；LLM以结构化输出理解上下文、指代和零样本意图，但成本与波动更高。

2. 识别层应抽取**目标、对象、交付物、约束、副作用和上下文指代**，并采用多标签表示复合意图。高确定性命令由规则处理，传统分类器承担低延迟粗分，LLM负责长尾语义；最终由校准器综合模型分数、规则证据和历史先验形成置信度。

| 方法 | 优势 | 主要边界 |
| --- | --- | --- |
| 规则 | 稳定、低成本、可审计 | 泛化能力弱 |
| 分类模型 | 延迟低、便于校准 | 依赖标注数据 |
| LLM | 理解长尾和多意图 | 成本与波动较高 |

3. **线上必须**保存输入、候选标签、路由证据和最终结果，以路由准确率、宏平均F1、澄清率、误执行率及端到端完成率评估。低置信度且不同解释会造成明显不同副作用时才澄清；低风险细节可以记录假设后继续执行。

**相关知识点：** 意图识别、多标签分类、置信度校准、Task Spec、Rule+LLM、澄清策略。

### 如何控制大模型推理成本？

**推理成本除了Token，还包括模型单价、推理档位、重复调用和低命中缓存。**

1. 先建立请求级成本账本，记录输入、输出、缓存、重试、反思和评审调用，并归因到租户、任务、Step、模型与Prompt版本。核心指标不是单次均价，而是**每个成功任务成本**及质量约束下的成本分位数，避免低价失败导致更多返工。

2. 针对“如何控制大模型推理成本”，输入侧通过**检索裁剪、历史摘要、工具结果句柄和Prompt去重**减少无关上下文；输出侧设置结构化格式、最大Token和停止条件。路由器按任务难度选择模型与推理档位，简单分类、抽取和格式化优先使用小模型或确定性代码。

| 手段 | 主要收益 | 风险控制 |
| --- | --- | --- |
| 上下文裁剪 | 降低输入Token | 保留目标与约束 |
| 模型分级 | 降低单次单价 | 按难度与风险路由 |
| 结果缓存 | 减少重复推理 | 版本键、TTL、权限隔离 |
| 预算终止 | 控制最坏成本 | 返回明确未完成状态 |

3. 为租户、任务和步骤设置Token、调用次数与费用硬预算，Planner分配预算，Runtime逐步扣减。稳定只读结果按模型、Prompt、输入、数据版本和权限范围缓存；实时数据缩短TTL。接近上限时减少候选与非关键反思、延迟低优任务或转人工，不能静默牺牲高风险任务的正确性。策略通过评测集验证质量—成本前沿并灰度发布。

**相关知识点：** Token预算、上下文压缩、模型路由、语义缓存、Prompt缓存、提前终止、成本归因。
