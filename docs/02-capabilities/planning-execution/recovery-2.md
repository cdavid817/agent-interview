### PLAN-144 · 多Agent协作场景下如何进行失败恢复？

> 稳定 ID：`PLAN-144`｜原题号：144

**多Agent失败恢复应由中心Orchestrator维护权威状态，通过Lease、幂等消息和Checkpoint隔离局部故障。**

1. 任务表示为DAG，子任务记录task_id、agent_id、Attempt、Plan Version、产物和状态。Agent只持有局部副本，结果和Heartbeat写入事件流；聊天记录不是权威状态。

2. Orchestrator以**Lease与Heartbeat**识别失联Agent，过期后重分配节点；Fencing Token拒绝原Agent迟到提交，避免双写。消息携带唯一ID并去重。

| 故障类型 | 恢复动作 | 关键保护 |
| --- | --- | --- |
| Agent崩溃 | 从Checkpoint重分配 | Lease、幂等键 |
| 消息重复或乱序 | 按版本处理 | message_id |
| 分支失败 | 局部Retry或降级 | 隔离、预算 |
| 部分提交 | 执行补偿 | Saga、审计 |

3. Agent通过版本化产物交换数据，Reducer必须确定性。分支失败时保留其他分支；共享前提失效或结果无法合并时才Replan。Barrier明确All、Any或Quorum，避免永久等待。

4. 写操作使用幂等键，结果未知时先查状态；无法回滚的副作用由Saga补偿或转人工。监控重分配率、重复提交率、Lease过期、消息积压和恢复时延。

**相关知识点：** Orchestrator、Lease、Heartbeat、Fencing Token、幂等消息、Checkpoint、Reducer、Saga。

### PLAN-145 · Agent任务回滚和数据库事务回滚有什么区别？

> 稳定 ID：`PLAN-145`｜原题号：145

**数据库事务回滚撤销单一事务域内尚未提交的变更，Agent任务回滚则协调跨工具、跨系统且可能已经可见的副作用。**

1. 数据库依赖ACID和事务日志，异常时撤销写集，其他事务通常看不到未提交状态。其边界由事务管理器控制，无法撤销已发送邮件、支付调用或其他系统的写入。

2. Agent任务跨数据库、文件、API和人工步骤，不能长期持有全局锁。因此回滚通常是**状态恢复加业务补偿**：停止后继节点、恢复本地状态，对已提交动作执行取消、退款或删除。

| 维度 | 数据库事务回滚 | Agent任务回滚 |
| --- | --- | --- |
| 范围 | 单一事务域 | 多工具、多系统 |
| 可见性 | 未提交变更通常不可见 | 副作用可能已对外可见 |
| 机制 | WAL、MVCC、Undo | Checkpoint、Saga、补偿 |
| 保证 | 原子性与隔离性 | 业务最终一致 |
| 失败处理 | 自动恢复 | 补偿或人工介入 |

3. 每个副作用节点声明事务边界、幂等键、业务回执和补偿动作，以Saga规定正向与逆向顺序。数据库状态与消息发布可用Outbox保持一致；外部调用结果未知时先查询或对账，不能直接补偿或重放。

4. 补偿是新业务操作，可能失败，也未必恢复原状。不可逆操作应事前确认并设置人工兜底。系统记录原动作、补偿Attempt和最终状态，以业务不变量验证收敛，不能仅凭“已回滚”状态认定成功。

**相关知识点：** ACID、WAL、MVCC、事务边界、Saga、补偿事务、Transactional Outbox、最终一致性。

### PLAN-146 · Checkpoint机制如何设计才能支持断点续跑？

> 稳定 ID：`PLAN-146`｜原题号：146

**可断点续跑的Checkpoint必须是版本化、原子提交且与外部副作用边界一致的完整执行快照。**

1. 快照保存task_id、Plan Version、节点、Ready Queue、Attempt、产物引用、工具回执、幂等键、预算及模型版本。大产物存对象存储，Checkpoint仅保存URI与哈希。

2. 写入采用**生成新快照、校验完整性、原子切换current指针**，不覆盖旧快照。快照带递增版本、Schema Version和校验和；状态迁移使用CAS，保证并发Worker仅一个提交成功。

| 设计方式 | 优势 | 局限 |
| --- | --- | --- |
| 全量快照 | 恢复简单、读取快 | 写入与存储成本高 |
| 增量快照 | 写入量小 | 恢复需合并多个版本 |
| Event Log | 审计完整、可重建 | 全量回放较慢 |
| 快照加事件 | 恢复与审计平衡 | 实现较复杂 |

3. Checkpoint在节点完成、工具结果确认及副作用提交后的安全点创建。写操作结果未知时保存UNKNOWN而非SUCCEEDED；恢复时先查外部状态，确认未生效且具备幂等性才重做，实现等效Exactly-Once。

4. Worker获取Lease，读取快照、回放事件并重建队列，再复核权限、版本、输入有效期和外部状态。损坏时回退前一快照，Schema升级通过迁移器转换。系统定期清理并演练，监控失败率、恢复时长和重复执行率。

**相关知识点：** Checkpoint、原子快照、CAS、Event Sourcing、Lease、幂等键、安全点、Exactly-Once。

### PLAN-147 · Agent如何实现任务暂停、恢复和回放？

> 稳定 ID：`PLAN-147`｜原题号：147

**暂停、恢复和回放应建立在同一套持久化状态机上，但分别解决安全停机、继续执行和历史重建三个问题。**

1. 暂停时以CAS将RUNNING切为PAUSING并停止新节点；进行中动作在取消点停止，或完成至副作用提交边界后记录回执。随后写Checkpoint并进入PAUSED，保存计划、节点、队列、产物、幂等键和预算。

2. Worker获取Lease，加载Checkpoint并回放后续事件，重建Ready Queue。执行前复核权限、版本、输入有效期和外部状态；成功节点复用，UNKNOWN写操作先查询，确认未生效且幂等时才重做。

| 操作 | 核心目的 | 是否产生新副作用 |
| --- | --- | --- |
| 暂停 | 到达安全点并冻结调度 | 不应新增 |
| 恢复 | 从稳定状态继续任务 | 可能 |
| 审计回放 | 重建历史状态与轨迹 | 否 |
| 重执行回放 | 复现执行过程 | 可能，需隔离 |

3. Event Log记录节点迁移、模型摘要、工具调用、版本和回执。**审计回放只读事件并还原状态；重执行回放会重新运行模型和工具**，需固定Prompt、模型、随机种子、工具版本及输入。

4. 重执行默认在Sandbox使用Mock工具或录制响应，禁止生产写入；真实集成使用测试账户和幂等键。记录回放起点、版本差异和结果Diff，并实施访问控制与脱敏。回放不得修改原任务事件，必须形成新的Replay Run。

**相关知识点：** 持久化状态机、Checkpoint、Event Log、Lease、审计回放、确定性重放、Sandbox、Replay Run。

### PLAN-148 · 如何设计补偿事务（Compensation）机制？

> 稳定 ID：`PLAN-148`｜原题号：148

**补偿事务应把长任务拆成可独立提交的本地事务，并为每个已提交副作用定义可幂等执行的业务逆操作。**

1. 每个正向动作Ti声明事务边界、前置条件、回执、幂等键、补偿动作Ci及不可补偿条件。补偿不是数据库Undo，而是新业务操作，可能保留审计痕迹，也未必恢复原状，因此以业务不变量验收。

2. 正向动作将状态与**Outbox事件**在本地事务中保存；调用外部服务前登记意图，返回后保存资源ID和回执。结果未知时先查询或对账，已生效才补偿，未生效才重试，避免两者同时执行。

| Saga模式 | 优势 | 局限 |
| --- | --- | --- |
| Orchestration | 流程集中、状态清晰 | 编排器复杂且关键 |
| Choreography | 服务自治、耦合较低 | 链路难追踪、易成环 |
| TCC | 资源预留、确定性较强 | 参与方改造成本高 |

3. 通常按提交逆序补偿，存在依赖时按补偿DAG调度。Ci必须支持重复调用和状态查询，并设置退避、次数、Deadline及Attempt；失败进入死信队列和人工工单，不能提前标记为已恢复。

4. 不可逆动作尽量后置，并在执行前确认；可采用预留、延迟发布或软删除提高可补偿性。记录Saga ID、Ti/Ci状态、版本和回执，监控补偿成功率、收敛时间、悬挂事务和人工介入率。

**相关知识点：** Compensation、Saga、Orchestration、Choreography、TCC、Outbox、幂等性、最终一致性。

### PLAN-149 · Planner和RePlanner的职责边界是什么？

> 稳定 ID：`PLAN-149`｜原题号：149

**Planner负责从目标构造首版可执行计划，RePlanner负责在执行证据表明原计划失效时生成受约束的新版本。**

1. Planner解析目标、约束和成功条件，完成任务分解、依赖建模、工具选择、预算及风险门控，输出Plan Version 1。它回答如何完成，但不直接执行节点。

2. RePlanner接收**原计划、已完成产物、轨迹、错误证据、外部状态和剩余预算**，判断失效范围，仅修改相关节点及下游。已验证节点默认冻结，除非前提被推翻；外部副作用需继承或补偿。

| 维度 | Planner | RePlanner |
| --- | --- | --- |
| 触发时机 | 任务开始或目标重定义 | 路径、前提或约束失效 |
| 主要输入 | 目标与环境能力 | 原计划与Observation |
| 输出 | 首版DAG和验收条件 | 新Plan Version与变更集 |
| 变更范围 | 全局构造 | 优先局部修补 |

3. 瞬时超时、限流由Retry处理，参数或Schema错误由Repair修正；工具不匹配、依赖不可达、关键假设被否定或预算结构变化时才Replan，以避免计划抖动。

4. RePlanner输出变更理由、复用产物、废弃节点、新依赖和预算影响，并重验依赖、权限及成功条件。Scheduler只接受版本递增且通过校验的计划，以CAS切换；无新证据、频繁重规划或涉及不可逆动作时转人工。

**相关知识点：** Planner、RePlanner、Plan Version、局部重规划、DAG、Observation、Retry、Repair、计划抖动。

### PLAN-150 · Agent如何定位失败原因来自模型还是工具？

> 稳定 ID：`PLAN-150`｜原题号：150

**定位模型或工具故障的关键是保存调用边界证据，并通过分层验证与可控重放确定最早出现偏差的环节。**

1. 记录目标、Prompt版本、模型输出、arguments、Schema结果、请求ID、工具响应和Validator报告。定位第一处不满足契约的位置，不能因最终答案错误就归因模型。

2. 选错工具、遗漏调用、非法参数或误解Observation，属于模型或路由问题；合法输入下工具超时、违背Schema或未改变状态，属于工具问题。鉴权映射、序列化和版本冲突属于**集成层故障**。

| 证据表现 | 优先归因 | 验证方式 |
| --- | --- | --- |
| 工具选择不匹配 | 模型/Router | 检查候选与轨迹 |
| 参数未通过Schema | 模型或适配器 | 检查原始输出 |
| 合法输入稳定返回5xx | 工具 | 独立调用与日志 |
| 响应正确但解析错误 | 适配器 | 对比解析前后 |

3. 用Counterfactual Replay隔离变量：固定工具响应重跑模型，仍失败则偏向模型；固定合法参数调用工具，稳定失败则偏向工具。写操作使用录制响应或Sandbox，禁止重复真实副作用。

4. 根因标签包括MODEL、TOOL、ROUTER、ADAPTER、DATA和UNKNOWN，并记录证据与置信度。随机性或间歇故障需多样本对照，单次成功不能证明归因。按标签修复Prompt、路由、工具、适配器或数据。

**相关知识点：** 故障归因、分布式追踪、Schema校验、Counterfactual Replay、Adapter、根因分析、Sandbox。

### PLAN-151 · 长链路Agent任务如何保证最终一致性？

> 稳定 ID：`PLAN-151`｜原题号：151

**长链路任务无法依赖单一ACID事务，应通过本地原子提交、幂等消息、Saga补偿和周期对账使状态最终收敛。**

1. 先定义业务不变量和允许的中间状态，例如订单成功必须对应一次有效支付。任务采用持久化状态机，每个节点只负责一个事务域，状态变更带task_id、Attempt和业务版本，聊天上下文不是权威状态。

2. 节点在本地事务中提交业务数据与**Transactional Outbox**，异步发布事件；消费者按message_id和唯一键去重，以版本号拒绝旧消息。外部调用前登记意图，返回后保存回执，结果未知时先查询。

| 机制 | 解决问题 | 主要边界 |
| --- | --- | --- |
| 本地事务 | 单服务原子性 | 不覆盖外部系统 |
| Outbox | 状态与消息一致 | 仍可能重复投递 |
| 幂等消费 | 重复消息安全 | 不自动解决乱序 |
| Saga | 跨系统状态收敛 | 补偿可能失败 |
| 对账 | 修复遗漏与未知状态 | 有检测延迟 |

3. Saga正向推进，失败时依据补偿DAG执行反向动作；不可逆操作尽量后置并人工确认。Retry只用于瞬时错误，写操作需幂等键；补偿失败进入死信队列和人工工单，不能提前标记成功。

4. 最终一致不表示无限等待。每个Saga设置Deadline、收敛SLO和终态，以源系统回执对账，修复悬挂、重复或部分提交。监控消息积压、未知状态年龄、补偿成功率和收敛时间，并以审计链证明不变量成立。

**相关知识点：** 最终一致性、业务不变量、Transactional Outbox、幂等消费、Saga、补偿DAG、对账、死信队列。

### PLAN-154 · 企业级Agent如何实现高可用和故障恢复？

> 稳定 ID：`PLAN-154`｜原题号：154

**企业级Agent应通过无状态计算、多副本持久化、故障隔离和跨区域灾备，实现服务可用与任务可恢复。**

1. API、Planner、Scheduler和Worker无状态化并跨可用区部署，由健康检查摘除故障实例。任务状态、事件、队列及产物进入高可用存储，采用副本与备份；进程内Memory不是恢复依据。

2. Worker以**Lease、Heartbeat和Fencing Token**领取任务，故障后由其他Worker接管，CAS拒绝迟到提交。节点需幂等，消息至少一次投递并去重；Checkpoint支持从安全点继续。

| 能力 | 目标 | 典型机制 |
| --- | --- | --- |
| 高可用 | 单实例故障不中断服务 | 多副本、自动摘除 |
| 韧性 | 依赖故障时降级运行 | 熔断、隔舱、限流 |
| 故障恢复 | 恢复未完成任务 | Checkpoint、Lease |
| 灾难恢复 | 区域级故障后重建 | 异地备份、切流 |

3. 模型、向量库和工具设置超时、熔断、Bulkhead及Fallback；备用能力在权限和输出语义等价时切换。写操作结果未知先对账，跨系统部分提交由Saga补偿，避免放大副作用。

4. 依据业务等级定义SLO、RTO和RPO，关键控制面跨区部署，备份定期验证。监控可用率、队列积压、Lease过期、恢复时长和重复执行，并演练实例宕机、网络分区、存储故障及区域切换；未经演练的冗余不能证明高可用。

**相关知识点：** 高可用、故障恢复、灾难恢复、RTO、RPO、Lease、Fencing Token、熔断器、Bulkhead。

### PLAN-156 · 如何评估RePlanning是否有效？

> 稳定 ID：`PLAN-156`｜原题号：156

**RePlanning是否有效，应以故障后的增量任务成功率为核心，并同时衡量恢复成本、计划稳定性和安全性。**

1. 建立可复现失败集，覆盖工具不可用、前提错误、依赖变化、预算不足和结果冲突。冻结目标、初始计划、轨迹和故障点，比较Replan、继续Retry及直接失败，避免只看成功案例。

2. 核心指标是**Recovery Success Rate＝重规划后成功任务数÷触发重规划任务数**。同时统计首次成功率、Replan次数、恢复时延、额外Token与工具成本、产物复用率、新增副作用和人工介入率。

| 维度 | 指标 | 判定方向 |
| --- | --- | --- |
| 有效性 | 恢复成功率、约束满足率 | 越高越好 |
| 效率 | 恢复时延、增量成本 | 越低越好 |
| 稳定性 | Replan次数、计划编辑距离 | 适度且收敛 |
| 保留性 | 已验证产物复用率 | 越高越好 |
| 安全性 | 越权、重复副作用率 | 越低越好 |

3. 验证触发是否正确：本应Retry却Replan属于过度触发，路径失效却不Replan属于漏触发。新计划需修复根因、保持无关节点稳定，并通过依赖、权限、预算和成功条件校验；仅改措辞不算有效。

4. 离线用配对样本和置信区间比较，线上灰度或A/B，并按故障、难度、模型和工具切片。若成功率上升但成本、时延或风险恶化，应计算单位恢复成本和净效用。无新证据的重复Replan计为计划抖动并终止。

**相关知识点：** RePlanning、恢复成功率、故障注入、反事实基线、计划编辑距离、产物复用率、净效用、A/B测试。

### PLAN-157 · LangGraph、AutoGen、CrewAI分别如何实现失败恢复机制？

> 稳定 ID：`PLAN-157`｜原题号：157

**LangGraph以内建Checkpoint恢复，AutoGen保存团队状态，CrewAI主要通过Flows持久化和续跑。**

1. LangGraph配置Checkpointer后按Super-step保存状态；失败从成功边界恢复，并保留其他节点的Pending Writes。另有RetryPolicy、超时、错误处理、中断和回放。

2. AutoGen以save_state/load_state保存Team及参与者状态，可在回合结束后停止并恢复。**应用负责持久化时机和存储**；运行中保存可能不一致，自定义Agent需处理on_resume、幂等和失败路由。

| 框架 | 恢复核心 | 主要边界 |
| --- | --- | --- |
| LangGraph | 图Checkpoint与重放 | 副作用需幂等 |
| AutoGen | Team状态保存与加载 | 应用保证一致快照 |
| CrewAI | Flow持久化与续跑 | Crew恢复需编排 |

3. CrewAI以Crews负责协作，以Flows负责事件编排；Flows维护状态并恢复长任务，通过start、listen、router组织分支。Guardrail可验证结果，但重试、补偿与幂等仍需业务代码。

4. 选型以相同故障集验证崩溃、分支失败、中断和未知写状态，比较恢复粒度、重复执行、状态兼容性、可观测性与成本，并固定版本。

**相关知识点：** LangGraph Checkpointer、Super-step、AutoGen Team State、CrewAI Flows、幂等恢复。

### PLAN-159 · 为什么不能仅根据HTTP 200判断任务成功？

> 稳定 ID：`PLAN-159`｜原题号：159

**HTTP 200仅表示服务器成功处理了HTTP请求，不证明响应语义正确、业务状态已提交或用户目标已经完成。**

1. 状态码属于协议层。服务可能返回200但响应含业务错误码、空数据、降级结果或任务ID；也可能请求已接受而后台失败。反之，重试返回冲突码时目标可能已达成。

2. Agent按**协议、结构、业务、外部状态、最终目标**逐层验证。先查状态码，再用Schema验字段，随后检查业务码、资源ID、权限和不变量。写操作必须回读，不能只信success字段。

| 验证层 | 要回答的问题 | 典型证据 |
| --- | --- | --- |
| HTTP层 | 请求是否返回 | 状态码、响应头 |
| 结构层 | 数据是否可解析 | Schema、必填字段 |
| 业务层 | 业务规则是否成立 | 业务码、不变量 |
| 状态层 | 副作用是否真实提交 | 回读、回执、版本 |
| 目标层 | 用户需求是否完成 | Success Criteria |

3. 创建订单返回200但order_id为空是结构失败；有订单ID但库存未锁定是业务失败；订单正确但目标是付款，则任务仍未完成。适配器应标准化错误，供Retry、Repair或Replan处理。

4. 写操作结果未知时以幂等键查询，禁止重放。Validator输出PASS、FAIL或UNCERTAIN并附证据。监控HTTP成功但业务失败比例，发现契约漂移和静默降级；所有Must条件满足后才能成功。

**相关知识点：** HTTP语义、业务状态码、JSON Schema、业务不变量、回读验证、幂等键、Success Criteria、静默失败。

### PLAN-160 · Retry应该在哪一层实现，Tool层还是Agent层？

> 稳定 ID：`PLAN-160`｜原题号：160

**Retry应分层但不能重复负责：Tool层处理短暂技术故障，Agent层处理语义失败，并由Runtime统一控制总预算。**

1. Tool SDK或Adapter重试连接中断、429和暂时性5xx。它保持工具、参数和意图不变，采用超时、退避与抖动，并将错误标准化后上抛。

2. Agent层理解目标与Observation，负责Repair、Fallback或Replan。Schema、权限、业务校验和能力不匹配错误不能原样重试，因为等待不会修复。

| 责任层 | 适用问题 | 是否改变语义 |
| --- | --- | --- |
| HTTP/SDK | 连接、429、偶发5xx | 否 |
| Tool Adapter | 协议解析、错误归一 | 否 |
| Agent | 修参、换工具、补证 | 可能 |
| Orchestrator | 节点Retry与Replan | 可能改变计划 |

3. **同一调用链只能有一个主要自动重试责任层**。若SDK、网关、Tool和Agent各自重试，请求量会乘法放大。Runtime传递Deadline、Attempt和Retry Budget，禁止隐藏重试。

4. 只读操作可重试；写操作必须带幂等键。结果未知时先查外部状态，Tool不能重放。预算耗尽、指纹重复或熔断后，Tool返回结构化失败，由Agent决定Fallback、Replan或人工处理，并监控重试放大与副作用。

**相关知识点：** 分层Retry、Tool Adapter、Retry Budget、Deadline传播、指数退避、幂等键、重试放大、熔断器。

### PLAN-161 · 什么情况下应该Retry，什么情况下应该直接Replan？

> 稳定 ID：`PLAN-161`｜原题号：161

**选择Retry还是Replan取决于原路径是否仍可达、故障是否随时间恢复，以及再次执行是否安全。**

1. Retry要求三个条件：节点仍正确；错误具有瞬时性，如429或偶发5xx；操作有幂等性。此时保持工具、参数和Plan Version不变，只增加Attempt，并设置退避、Deadline及预算。

2. 工具能力不足、依赖不可用、假设被否定、约束变化或预算不足时，应Replan。参数或Schema错误先Repair；权限或合规拒绝应停止，**不能通过Replan绕过策略**。

| 诊断信号 | 处理 | 判断依据 |
| --- | --- | --- |
| Retry-After、偶发超时 | Retry | 成功率会随时间恢复 |
| 参数校验错误 | Repair | 路径正确、动作有误 |
| 工具能力不匹配 | Replan | 原节点不可达 |
| 相同错误连续出现 | Replan或终止 | 边际收益接近零 |
| 写操作结果未知 | 先查询状态 | 防止重复副作用 |

3. 重试净效用＝成功概率×剩余价值－等待、费用和副作用风险。净效用为正且预算充足则Retry，否则Replan。错误指纹重复、Validator判定无新证据或熔断器开启时应提前停止。

4. Replan生成新版本，复用已验证产物，重验依赖、权限、预算和Success Criteria。替代路径低置信、状态不明或涉及不可逆操作时转人工。统计Retry成功率、Replan恢复率和单位恢复成本。

**相关知识点：** Retry、Repair、Replan、路径可达性、期望效用、错误指纹、幂等键、计划版本。

### PLAN-162 · Exponential Backoff为什么比固定间隔重试更合适？

> 稳定 ID：`PLAN-162`｜原题号：162

**指数退避会随连续失败降低请求频率，为下游恢复留出时间；固定间隔则容易持续施压并形成同步重试峰值。**

1. 大量客户端收到429或5xx后，固定间隔会让其同时再请求，形成Thundering Herd，使服务再次过载。指数退避按attempt增长等待，公式为min(cap, base×2^attempt)，减少流量。

2. 纯指数增长仍可能同步，因此加入**Jitter随机抖动**。Full Jitter在0到上界间随机，Equal Jitter保留一半再随机，Decorrelated Jitter依据上次等待生成区间；生产通常采用抖动。

| 策略 | 请求分布 | 主要问题 |
| --- | --- | --- |
| 固定间隔 | 周期性集中 | 易形成重试风暴 |
| 纯指数退避 | 间隔增大但仍同步 | 客户端可能同相位 |
| 指数退避加Jitter | 峰值被打散 | 恢复时间略不确定 |
| Retry-After | 服从服务端建议 | 依赖服务正确返回 |

3. 指数退避适合网络抖动、限流和暂时不可用，不适合参数、权限、配额或业务错误。错误分类必须先于退避，否则只是更慢重复必然失败的请求。

4. 设置初始间隔、cap、次数、Deadline和Retry Budget，并遵守Retry-After。写操作需幂等键，结果未知先查询。监控重试成功率、请求放大和下游饱和度；熔断或Deadline不足时停止。

**相关知识点：** Exponential Backoff、Jitter、Thundering Herd、Retry-After、Retry Budget、幂等性、熔断器。

### PLAN-163 · 如何避免Agent进入无限重试循环？

> 稳定 ID：`PLAN-163`｜原题号：163

**无限重试应由确定性的Loop Guard阻断，模型只能建议再次尝试，不能控制计数器、预算或终止状态。**

1. Runtime为节点设置max_attempts、Deadline、Token、费用和等待上限，任务层设置全局Retry Budget。进入RUNNING前原子扣减预算并增加Attempt；耗尽后只能失败、Replan或转人工。

2. 生成**错误指纹＝节点＋工具＋规范化参数＋错误码＋结果摘要**并维护窗口。相同指纹达到阈值，或参数变化但约束、外部状态和证据量不变时，判定无进展并禁止原动作。

| 终止信号 | 系统动作 | 后续路径 |
| --- | --- | --- |
| 达到Attempt上限 | 停止Retry | Replan或失败 |
| 相同错误重复 | 打开节点熔断 | 换工具或人工 |
| Deadline或费用耗尽 | 取消后续尝试 | 返回部分结果 |
| 权限或策略拒绝 | 立即终止 | 申请授权 |
| 写操作状态未知 | 冻结重放 | 查询与对账 |

3. Retry前确认错误具有瞬时性，并采用抖动退避；参数错误进入Repair，路径失效进入Replan。SDK、网关和Agent共享Retry Budget，指定唯一主要重试层，防止乘法放大。

4. 写操作携带幂等键。终止时保存已尝试动作、最后错误、回执和缺口，进入死信队列或人工处理。监控预算耗尽率、重试放大率、重复指纹率和成功率，长期低收益规则应删除。

**相关知识点：** Loop Guard、Retry Budget、错误指纹、进展检测、熔断器、幂等键、死信队列、终止条件。

### PLAN-164 · Rollback与Compensation Transaction有什么区别？

> 稳定 ID：`PLAN-164`｜原题号：164

**Rollback撤销同一事务边界内尚未最终生效的变更，Compensation Transaction则用新的业务动作抵消已经提交的副作用。**

1. Rollback依赖事务日志、MVCC、Undo或快照，在提交前恢复旧状态，对外通常不可见，由事务系统提供原子性。它适用于单库事务或未越过提交点的修改。

2. Compensation发生在提交后，例如退款抵消扣款。它不是技术层Undo，而是**具有独立业务语义的新事务**；会产生审计记录，受时间窗口和外部规则限制，也可能失败。

| 维度 | Rollback | Compensation |
| --- | --- | --- |
| 执行时机 | 原事务提交前 | 原动作提交后 |
| 作用范围 | 单一事务域 | 跨服务或长流程 |
| 状态可见性 | 通常尚未对外可见 | 原副作用已经可见 |
| 恢复保证 | 可还原事务状态 | 只保证业务等价收敛 |
| 失败处理 | 事务系统处理 | 重试、对账或人工 |

3. 长链路Agent跨数据库、文件、支付和消息系统，不能持有全局事务，因此以Saga组织Ti和Ci。补偿按逆序或DAG执行，每个Ci需幂等键、状态查询、Deadline、重试预算和人工兜底。

4. 结果未知时不能立即回滚或补偿，应先查状态：未生效才重试，已生效才补偿。不可逆动作应后置并确认。系统以业务不变量验收，只有补偿完成或人工关闭后才能标记恢复，不能把已发起补偿视为成功。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** Rollback、Compensation Transaction、ACID、MVCC、Saga、补偿DAG、幂等性、最终一致性。

### PLAN-165 · Agent如何保证外部资源操作的幂等性？

> 稳定 ID：`PLAN-165`｜原题号：165

**外部操作幂等性的核心是用稳定业务键标识同一意图，并以原子去重记录保证重复执行返回同一结果。**

1. Task ID表示运行，Attempt表示尝试，Idempotency Key表示业务意图。键由tenant、操作、资源和规范化参数生成，首次请求及Retry必须复用；新键会把重试变成新操作。

2. 工具网关以**唯一约束或条件写**创建PENDING记录，保存参数哈希、状态和结果。并发请求仅一个执行；命中RUNNING返回状态句柄，命中SUCCEEDED返回原结果，参数哈希不同则拒绝。

| 机制 | 主要作用 | 不能替代什么 |
| --- | --- | --- |
| Idempotency Key | 识别同一业务意图 | 权限校验 |
| 唯一约束 | 原子阻止重复写入 | 外部结果查询 |
| 分布式锁 | 限制并发执行 | 永久去重事实 |
| 业务版本号 | 防止旧写覆盖新状态 | 请求去重 |

3. 优先调用支持幂等键的API，并保存request_id和资源ID。不支持幂等的邮件、文件或工单采用唯一字段、调用前登记、调用后回读和对账；结果未知时先查询，禁止重放。

4. TTL需覆盖重试与回放窗口，高风险交易长期保留。失败需区分未执行与结果未知，只有前者可新建Attempt。幂等不等于Exactly-Once，通常以At-Least-Once、幂等消费和对账获得等效一次结果，并监控键冲突和重复副作用。

**相关知识点：** Idempotency Key、Task ID、Attempt、唯一约束、条件写、At-Least-Once、等效Exactly-Once、对账。

### PLAN-166 · 什么情况下需要Checkpoint机制？

> 稳定 ID：`PLAN-166`｜原题号：166

**当任务重算成本、失败概率或副作用风险高于状态持久化开销时，应引入Checkpoint机制。**

1. 典型场景包括长任务、多步工具链、高成本模型调用、并行分支、人工审批、Worker迁移和跨系统写操作。从头重跑会浪费已验证产物，甚至重复付款或创建资源。

2. 短小、无副作用且可廉价重放的任务无需频繁Checkpoint。若失败概率×重算成本大于快照写入、存储和恢复成本，则持久化有价值；节点越昂贵、恢复目标越严格，快照应越密。

| 场景 | 是否需要 | 建议边界 |
| --- | --- | --- |
| 单次简单问答 | 通常不需要 | 任务结束 |
| 长链路检索与生成 | 需要 | 高成本节点后 |
| 外部写操作 | 强烈需要 | 副作用确认后 |
| 人工审批等待 | 必须需要 | 进入等待态前 |
| 可廉价重算的批处理 | 视成本决定 | 按批次或时间 |

3. Checkpoint保存**Plan Version、节点、队列、Attempt、产物引用、回执、幂等键、预算和版本**。必须在稳定边界创建：写操作结果未知时保存UNKNOWN；大产物放对象存储，仅保存URI与哈希。

4. 快照频率需平衡恢复点目标和写放大，可用全量、增量或快照加Event Log。恢复时核对权限、版本及外部状态；Checkpoint只恢复执行位置，不回滚副作用。以恢复时长、重算量、快照成本和重复率验证收益。

**相关知识点：** Checkpoint、重算成本、稳定边界、恢复点目标、增量快照、Event Log、幂等性、Durable Execution。

### PLAN-167 · Durable Execution如何支持任务恢复？

> 稳定 ID：`PLAN-167`｜原题号：167

**Durable Execution通过持久化执行历史与步骤结果，使进程崩溃后能重建控制流，并从未完成边界继续。**

1. 工作流把节点、定时器、消息和工具回执写入持久化存储。Worker可替换；崩溃后新Worker读取历史或Checkpoint，恢复节点、队列和预算。

2. 编排逻辑保持**确定性重放**：同一历史得到相同下一步。模型、时间、随机数和网络等非确定操作封装为Activity；结果记录后在重放中复用，避免重复副作用。

| 组件 | 保存或执行内容 | 恢复作用 |
| --- | --- | --- |
| Event History | 状态迁移与事件 | 重建控制流 |
| Checkpoint | 完整状态 | 缩短回放时间 |
| Activity | 模型、工具和副作用 | 隔离非确定性 |
| Durable Timer | 等待与Deadline | 重启后继续计时 |
| Task Queue | 待执行工作 | Worker接管 |

3. Activity采用At-Least-Once时必须幂等，记录Attempt、幂等键和回执。Worker通过Lease领任务，超时后重分配；迟到结果按版本拒绝。写操作未知时先查询。

4. 恢复不等于回滚：已提交副作用需Saga补偿，不可逆动作转人工。工作流代码和Schema需版本化，以兼容分支或迁移器处理旧历史。监控恢复时长、回放量和重复Activity。

**相关知识点：** Durable Execution、确定性重放、Event History、Activity、Checkpoint、Durable Timer、Lease、幂等性。

### PLAN-168 · Agent如何判断失败原因是模型问题还是工具问题？

> 稳定 ID：`PLAN-168`｜原题号：168

**模型与工具故障应按调用边界逐层归因，以最早违反契约的位置为根因，而不是根据最终答案猜测。**

1. Trace保存目标、模型tool call、Schema结果、工具请求、响应和Validator报告。先查工具与参数，再查请求是否返回合约结果，最后检查模型是否正确使用Observation。

2. 选错或漏调工具、参数错误、误读返回值，属于模型或Router；合法输入下持续超时、5xx或状态未改变，属于工具。序列化、鉴权、版本和解析错误属于**Adapter或集成层**。

| 现象 | 优先归因 | 验证方法 |
| --- | --- | --- |
| tool call未通过Schema | 模型/Adapter | 检查原始输出 |
| 合法参数稳定返回5xx | 工具 | 独立调用、服务日志 |
| 原始响应正确但解析错误 | Adapter | 对比解析前后 |
| 工具结果正确但答案误用 | 模型 | 固定Observation重放 |
| 相同请求偶发失败 | 环境/工具 | 多次采样 |

3. 反事实重放隔离变量：固定工具响应重跑模型，仍失败则偏向模型；固定参数调用工具，仍失败则偏向工具。写操作使用Mock、Sandbox或录制响应，避免产生副作用。

4. 根因标签包括MODEL、ROUTER、TOOL、ADAPTER、DATA和UNKNOWN，并附证据与置信度。随机或间歇故障需多样本对照，单次成功不能证明归因。按标签修复对应层。

**相关知识点：** 故障归因、调用边界、分布式追踪、Schema校验、反事实重放、Adapter、根因标签、Sandbox。

### PLAN-170 · Replanning需要重新调用Planner还是局部修改计划？

> 稳定 ID：`PLAN-170`｜原题号：170

**Replanning应默认局部修改受影响子图，只有目标、全局约束或大范围前提失效时才重新调用完整Planner。**

1. RePlanner从失败节点沿DAG定位下游，冻结前提未变的节点，只替换失效节点、相关边和下游计划。这样可保留产物，降低Token、时延和风险。

2. 若目标改变、核心假设被推翻、多个关键分支失效或全局约束变化，局部补丁可能不一致，应调用Planner重建。**全量重规划也必须继承执行事实和外部副作用**。

| 情形 | 推荐方式 | 主要原因 |
| --- | --- | --- |
| 单工具不可用 | 局部换工具 | 影响范围有限 |
| 单节点输入变化 | 修改局部子图 | 可复用产物 |
| 关键假设被否定 | 全量Planner | 多条路径同时失效 |
| 用户目标重新定义 | 全量Planner | Success Criteria变化 |
| 预算局部不足 | 局部降级 | 不必重建全部计划 |

3. 依据受影响节点比例、关键路径覆盖率、约束变化数和修补置信度设阈值。影响小且边界明确则Patch Plan；超过阈值或无法证明一致性则Full Replan。瞬时故障Retry，参数错误Repair。

4. 两种方式都生成Plan Version和Diff，说明复用、废弃、新增节点及预算，并重验DAG、依赖和Success Criteria。以CAS切换；副作用需复用或补偿，无进展时升级为全量规划或人工处理。

**相关知识点：** RePlanner、局部子图、全量Planner、影响分析、Plan Patch、Plan Version、结构化Diff、计划一致性。

### PLAN-171 · 多Agent执行过程中，一个Agent失败如何影响整个Workflow？

> 稳定 ID：`PLAN-171`｜原题号：171

**单个Agent失败不应直接终止整个Workflow，其影响取决于依赖关系、任务关键性、副作用状态以及系统是否具备故障隔离与降级路径。**

1. 编排器依据DAG计算传播范围：失败节点的下游进入Blocked，无依赖分支继续执行，可选依赖可使用默认值或降级产物；只有关键路径无替代节点时才可能使任务整体失败。**传播单位应是受影响子图，而非整个流程**。

2. 区分Agent进程、工具调用、输出校验和业务语义失败。前两类可重试，格式问题适合Repair，能力不匹配可切换Agent，目标前提失效才触发Replan；若已写入外部系统，还需确认幂等状态或执行补偿。

| 故障位置 | 影响 | 处置 |
| --- | --- | --- |
| 非关键叶子 | 局部缺失 | 跳过或降级 |
| 可替代节点 | 短暂阻塞 | 重试或切换 |
| 关键路径 | 下游阻塞 | 修复或重规划 |
| 已有副作用 | 状态不一致 | 幂等确认或补偿 |

3. 每个节点声明Criticality、Timeout、Retry Budget、Fallback和Compensation，并记录Pending、Failed、Blocked等状态。编排器采用并发隔离和熔断，防止故障耗尽共享资源。Workflow区分成功、部分成功、失败与待人工；恢复后重验受影响节点，连续失败且无新证据时停止循环，保留Checkpoint和Trace。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** 故障传播、DAG、关键路径、故障隔离、Fallback、熔断、幂等、Saga补偿、部分成功、Checkpoint。

### PLAN-173 · Human-in-the-loop通常在什么场景介入？

> 稳定 ID：`PLAN-173`｜原题号：173

**Human-in-the-loop应部署在风险、歧义或责任超过自动化边界的位置，而不是把人工审核机械地添加到每个Agent步骤。**

1. 典型介入场景包括不可逆写操作、高金额交易、敏感数据访问、权限或合规判断、目标存在重大歧义、模型置信度低且错误代价高、连续恢复失败，以及法律或伦理责任必须由人承担的决策。介入阈值应综合**影响范围、可逆性、资源敏感度和异常程度**。

2. 人工可在执行前审批、执行中处理例外或执行后复核。高风险动作必须事前批准；长流程遇到未知状态时暂停；低风险结果适合事后抽检，避免审批成为瓶颈。

| 模式 | 触发条件 | 系统动作 |
| --- | --- | --- |
| Allow | 低风险且已授权 | 执行并记录 |
| Ask | 高影响或信息不足 | 暂停并请求审批 |
| Deny | 越权或违反策略 | 拒绝并审计 |
| Review | 低风险质量抽检 | 执行后采样 |

3. 审批请求必须显示具体动作、对象、参数、证据、预期副作用和可撤销性，不能只询问“是否继续”。系统在Checkpoint持久化状态，使用一次性审批令牌绑定Plan Version与参数，防止批准后发生TOCTOU或被扩大执行范围。

4. 人工决定、策略版本和结果写入审计日志；超时应终止或转交，不得批准。**模型只能提供建议，不能成为授权主体**。统计拦截率、误报率、审批时延和人工推翻率，以校准阈值并减少无效介入。

**相关知识点：** Human-in-the-loop、风险分级、Allow/Ask/Deny、审批令牌、Checkpoint、TOCTOU、最小权限、审计日志。

### PLAN-174 · 如何设计Agent的错误分类体系？

> 稳定 ID：`PLAN-174`｜原题号：174

**Agent错误分类应采用“故障来源、可恢复性、影响范围、副作用状态”四维模型，使错误类型能够直接映射恢复策略和告警等级。**

1. 来源维度区分模型、工具、数据、编排、基础设施、权限和业务规则。例如模型可能产生语义错误，工具可能超时，数据可能缺失，编排可能死锁；若只使用“执行失败”，系统无法选择正确动作。

2. 错误对象应包含**稳定错误码、类别、严重度、可重试性、作用域、根因、Trace ID和副作用标记**。错误码面向程序保持稳定，消息面向人员提供上下文；同一根因生成错误指纹以便聚合。

| 分类 | 典型错误 | 默认动作 |
| --- | --- | --- |
| Transient | 超时、限流、抖动 | 退避重试 |
| Correctable | 参数、格式错误 | Repair |
| Permanent | 权限、资源不存在 | 停止或人工处理 |
| Semantic | 结果不满足约束 | 换策略或Replan |
| Side-effect | 写入结果未知 | 查询、补偿 |

3. 可恢复性还要结合幂等性、重试预算与外部状态。超时写操作可能已成功，应先查询；权限错误通常不可重试；参数错误只有修正后才值得重试。父节点汇总时保留根因链，不能因包装丢失证据。

4. 分类规则需版本化，并用失败样本校准误分率和无效重试率。未知错误进入Unknown，重复出现后再补充规则；安全与合规错误必须Fail Closed并审计。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** Error Taxonomy、错误码、可恢复性、错误指纹、根因链、幂等性、重试预算、Fail Closed、可观测性。

### PLAN-176 · 如何统计Agent任务成功率、重试率和恢复率等指标？

> 稳定 ID：`PLAN-176`｜原题号：176

**Agent指标统计的关键是先统一Task、Step与Attempt口径，再用事件事实计算，避免因重试、重复上报或任务难度差异产生失真。**

1. 成功率＝满足Success Criteria的终态任务数÷已结束任务数；重试率可定义为发生重试的任务占比，或额外Attempt数÷首次Attempt数；恢复率＝失败后最终成功任务数÷可恢复失败任务数。**取消、进行中和测试流量是否进入分母必须明确**。

2. 每次执行上报Task、Step、Attempt ID、终态、错误码、重试原因、恢复策略、时间、成本和版本。采集端按事件ID去重，以状态机处理迟到与乱序；超出观察窗口后再判定未恢复。

| 指标 | 分子 | 分母 |
| --- | --- | --- |
| 任务成功率 | 成功终态任务 | 已结束任务 |
| 任务重试率 | 有额外Attempt的任务 | 已执行任务 |
| 恢复率 | 失败后转成功任务 | 可恢复失败任务 |
| 一次通过率 | 首次Attempt成功任务 | 已结束任务 |

3. 指标按任务类型、复杂度、模型、工具、租户和版本切片，并展示样本量、时间窗与置信区间。总体成功率上升可能只是简单任务增多，版本对比应使用固定评测集或难度加权，并区分用户成功、Validator成功与调用成功。结合P95延迟、成本、无效重试率和接管率解释结果；指标定义须版本化。

**相关知识点：** Success Rate、Retry Rate、Recovery Rate、First-pass Yield、指标口径、事件去重、状态机、观察窗口、SLO、置信区间。

### PLAN-177 · Agent任务状态机应该如何设计？

> 稳定 ID：`PLAN-177`｜原题号：177

**Agent任务状态机应把执行生命周期、失败语义和人工介入显式化，并以受约束的状态迁移保证并发、恢复和审计的一致性。**

1. 任务状态设为已创建、已规划、运行、等待、成功、失败、取消；步骤再分待执行、就绪、重试、阻塞和完成。终态不可直接转回运行，恢复应创建新Attempt或Plan版本，保留历史链。

2. 迁移须定义事件、前置条件、动作和不变量：依赖完成才能就绪，持有Lease才能执行；写操作超时先确认状态，不能直接重试。**状态与事件应原子持久化**，用CAS防止重复领取。

| 状态 | 含义 | 允许去向 |
| --- | --- | --- |
| 就绪 | 依赖满足 | 运行、取消 |
| 运行 | 正在执行 | 完成、重试、失败 |
| 等待 | 审批或外部事件 | 运行、取消 |
| 阻塞 | 上游失败 | 就绪、失败 |
| 完成 | 步骤成功 | 不可变 |

3. Checkpoint保存Plan版本、节点状态、输入输出引用、工具回执、幂等键和待执行队列。恢复时加载稳定快照，复核Lease、权限及副作用，再决定继续、补偿或Replan；聊天记录不足以恢复业务状态。

4. Task与Step分层聚合，非关键失败可标记部分成功，关键路径失败才使任务失败。迁移记录Trace ID、原因与操作者；以故障注入验证崩溃、重复消息和并发恢复。

**相关知识点：** 有限状态机、状态迁移表、CAS、Lease、Checkpoint、Attempt、幂等、事件溯源、故障注入。

| --- | --- | --- |
| 对话与约束 | 消息、结构化摘要 | 摘要完整性 |

| 外部写入 | 回执、幂等键 | 查询真实状态 |

### PLAN-179 · 重试时如何避免重复执行有副作用的操作？

> 稳定 ID：`PLAN-179`｜原题号：179

**副作用操作的安全重试必须由端到端幂等协议保证，不能依赖Agent记忆或假设上一次超时等于执行失败。**

1. 首先区分“确定失败”与“结果未知”：连接超时可能发生在服务端提交之后，因此重试前应查询外部状态。系统需定义业务上的同一次意图，使重复请求命中原执行记录，而不是再次创建订单、付款、邮件或工单。

2. 针对“重试时如何避免重复执行有副作用的操作”，Task ID标识执行实例，**Idempotency Key**标识业务意图。幂等键通常由租户、用户、操作类型、规范化参数和时间窗组成，并贯穿网关、调度与工具层；服务端以唯一约束原子写入执行记录和结果引用，不能只依赖会过期的分布式锁。

| 概念 | 标识对象 | 主要作用 |
| --- | --- | --- |
| Task ID | 一次执行实例 | 追踪状态 |
| Idempotency Key | 一次业务意图 | 去重副作用 |
| 分布式锁 | 临界区执行权 | 降低并发冲突 |
| 唯一约束 | 最终写入事实 | 原子去重 |

3. 针对“重试时如何避免重复执行有副作用的操作”，重复请求命中成功记录时返回原结果，命中运行中记录时返回同一状态句柄；失败记录依据错误类型创建新Attempt。对于邮件、工单等外部副作用，优先使用对方**幂等**接口，否则采用业务唯一键、调用前登记、调用后查询和周期对账。

**相关知识点：** Task ID、Idempotency Key、唯一约束、幂等消费、At-Least-Once、Exactly-Once、对账。

### PLAN-181 · Agent回滚和传统数据库事务回滚有什么区别？

> 稳定 ID：`PLAN-181`｜原题号：181

**数据库事务回滚依赖单一事务管理器和隔离日志，能够撤销未提交写入；Agent回滚跨越模型、文件、API和人工动作，只能组合版本恢复与业务补偿，并接受最终一致而非瞬时原子性。**

1. 数据库事务拥有明确的Begin、Commit和Rollback边界，由日志、锁或MVCC维持ACID；失败可使事务内写入对外不可见。Agent步骤通常跨多个自治系统，外部邮件、支付或发布一旦提交，原编排器无权将其原子撤销。

2. 每一步使用本地事务同时提交业务状态与**Outbox事件**，消费者至少一次处理并以唯一约束去重。调用外部系统前登记操作意图，返回后保存业务回执；遇到超时未知状态时先查询或对账，不能直接再次执行。

| 维度 | Rollback | Compensation |
| --- | --- | --- |
| 事务状态 | 通常尚未最终提交 | 副作用已经提交 |
| 实现 | 恢复旧状态 | 执行反向业务动作 |
| 失败可能 | 较低 | 补偿也可能失败 |

3. 针对“Agent回滚和传统数据库事务回滚有什么区别”，**Rollback**适合同一事务域内可逆状态，Compensation通过新的业务动作抵消已提交结果，可能失败且不保证恢复到字节级原状。Saga把长事务拆成一组本地事务与补偿，并声明补偿顺序、超时、重试和人工兜底。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** 最终一致性、Outbox、Saga、补偿事务、业务不变量、对账、CAS。

### PLAN-182 · 如果工具调用已经成功但模型认为失败，如何处理？

> 稳定 ID：`PLAN-182`｜原题号：182

**工具或外部系统的已提交事实高于模型判断；出现认知分歧时应先对账并修正执行状态，禁止依据模型猜测重复调用。**

1. 编排器以Tool Call ID、幂等键、业务回执和资源版本查询真实状态。若工具返回成功且Validator确认副作用存在，将步骤标记Completed，并向模型注入结构化事实；若响应丢失，则先调用只读查询接口，不能把超时直接解释为失败。

2. 分歧可能来自工具响应Schema不明确、模型误读状态码、旧上下文覆盖新结果或观测延迟。工具应返回**机器可判定的状态、结果引用、副作用标识和可重试性**，由确定性状态机解析，模型只负责选择后续动作。

| 观测结果 | 状态判定 | 后续动作 |

### PLAN-184 · 如何区分可重试错误和不可重试错误？

| 策略 | 适用错误 | 是否改计划 |
| --- | --- | --- |
| Retry | 超时、限流、网络抖动 | 否 |
| Repair | 参数或格式错误 | 调整动作 |
| Compensation | 已产生外部副作用 | 恢复业务状态 |
| Replan | 路径或前提失效 | 是 |

### PLAN-220 · 如何避免 Agent 陷入无限循环执行？

> 稳定 ID：`PLAN-220`｜原题号：220

**防止Agent无限循环需要同时设置硬预算和语义进展检测；仅限制单次重试次数无法识别换一种表述重复同一路径。**

1. 在Task、Step和Tool层分别配置max_turns、最大调用数、Token、费用、时长及Retry Budget，任何上层预算耗尽都进入明确终态。每个循环必须声明Success Criteria与停止条件，不能由模型自行判断“继续可能有用”。

2. 对最近N步生成**进展指纹**，包含目标子状态、工具名、规范化参数、错误码、产物哈希和Validator分数。相同指纹重复、状态无变化、建议与已尝试方案相似或评价分数长期不提升时，触发Stuck Detector。

| 防护 | 检测对象 | 触发动作 |
| --- | --- | --- |
| 硬预算 | 次数、时间、成本 | 强制终止 |
| 指纹去重 | 重复动作与错误 | 禁止重试 |
| 进展评分 | 状态或质量停滞 | Replan |
| 熔断器 | 工具持续故障 | 隔离依赖 |

3. 首次停滞可要求反思并提供新证据，局部路径失效可Replan；无新增证据或跨计划重复时必须停止并转人工。副作用工具还需幂等键与熔断，避免循环产生重复写入。所有终止原因进入Trace，用离线样本校准阈值，防止过早终止正常长任务。

**相关知识点：** Stuck Detector、Retry Budget、进展指纹、循环检测、熔断器、Replan、幂等、终止条件。
