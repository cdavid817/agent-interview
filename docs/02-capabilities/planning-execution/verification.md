# 完成判定与执行评测

> 所属章节：[任务规划与执行](README.md)｜本文件共 **20** 题。

<a id="plan-063"></a>
### 1. Agent如何判断是否需要调用RAG或外部工具？

**当答案依赖模型参数之外的私有、实时、精确或可执行信息时，Agent应调用RAG或外部工具，而不是凭记忆生成。**

1. 需要私有文档、代码、用户数据、最新事实或引用时使用RAG；需要计算、查库、运行代码或改变状态时调用工具。纯创作、稳定常识可直接完成，但高风险事实仍须验证。

| 方式 | 适用需求 | 主要边界 |
| --- | --- | --- |
| 参数知识 | 稳定通用知识 | 可能过时或不可追溯 |
| RAG | 私有文档、证据引用 | 只读取，不负责执行 |
| 查询工具 | 结构化实时数据 | 依赖Schema与权限 |
| 执行工具 | 计算、代码、外部写入 | 需副作用治理 |

2. Router抽取**实体、时效、精度、来源、动作和权限**。出现“最新、这个仓库、我的订单、精确计算、执行修改”等表达时提高工具需求；模型置信度低、答案可验证或错误成本高时也应检索。范围不清时先澄清。

3. RAG采用关键词、向量和结构化过滤召回，再重排、去重并保留来源；代码还使用路径、符号索引和调用图。工具执行前校验Schema、权限、参数和副作用，Runtime负责执行与验证。

4. 工具返回不等于任务成功：RAG检查证据与引用，API验证业务状态。记录调用理由、候选工具、版本、证据和结果，评估选择准确率、无效调用率、Recall@K、引用正确率、完成率、延迟及成本。

**相关知识点：** RAG、Tool Routing、Hybrid Search、结构化查询、Function Calling、权限校验、证据引用、结果验证。

### 2. Tool Selection通常依据哪些信息？

**Tool Selection应综合任务需求、工具契约、运行环境、治理约束和历史表现，先排除不可用候选，再进行多目标排序。**

1. 任务侧信息包括目标、对象、输入类型、输出格式、时效性、数据敏感度、风险和预算；环境侧包括当前身份、网络、地域、已连接服务及资源状态。两类信息共同确定“能否调用”，不能仅依据用户措辞或工具名称。

2. 针对“Tool Selection通常依据哪些信息”，Tool Registry应保存**语义描述、输入输出Schema、权限、幂等属性、版本、费用、延迟和错误码**。Router先用规则或检索召回候选，再由模型基于当前目标排序；真正执行前由宿主校验参数、授权范围和风险，模型只生成调用意图。

> 本题视角：Tool Selection通常依据哪些信息
| 机制 | 解决问题 | 不负责什么 |
| --- | --- | --- |
| Function Calling | 生成结构化调用 | 实际执行 |
| MCP | 统一能力发现与交互 | 业务授权 |
| Tool Registry | 管理能力元数据 | 执行编排 |
| Workflow | 组织多次调用 | 开放式推理 |

3. 针对“Tool Selection通常依据哪些信息”，调用返回后要验证**业务效果**，HTTP 200只能证明协议成功。瞬时错误可退避重试，参数错误先修复，权限错误停止并申请授权，能力不匹配则重新选工具。成本可通过候选裁剪、结果缓存、批处理、并行无依赖调用和模型分级控制。

**相关知识点：** Tool Selection、Tool Registry、Function Calling、MCP、Schema、权限校验、结果验证。

### 3. Agent如何判断某一步执行成功？

**单步执行成功必须同时满足调用完成、产物合规、业务状态正确和副作用受控，不能以工具无报错或模型自评作为充分证据。**

1. Planner在执行前为节点声明成功标准、验证器和证据来源，Executor只负责返回结果。验证应独立于执行动作：写文件后重新读取并检查差异，调用接口后查询真实资源状态，避免把请求已提交误判为业务已完成。

2. 针对“Agent如何判断某一步执行成功”，每一步应定义**输出Schema、业务不变量、允许误差、预期状态变化和禁止副作用**。验证顺序包括协议状态、结构格式、业务规则、外部真实状态和用户最终目标；代码任务还要结合编译、测试、静态分析与差异审查。

| 验证层 | 检查对象 | 示例 |
| --- | --- | --- |
| 协议层 | 调用是否返回 | 状态码、异常 |
| 结构层 | 格式是否合规 | JSON Schema |
| 业务层 | 不变量是否满足 | 数量、权限 |
| 目标层 | 用户问题是否解决 | 验收测试 |

3. 针对“Agent如何判断某一步执行成功”，没有唯一答案时使用Rubric、成对比较、多评审器、事实证据和用户反馈，并分别评价正确性、完整性、安全性、成本与延迟。结果宜分为通过、可恢复失败、不可恢复失败和不确定；不确定时补证或**人工**复核，不强行二分类。

4. 节点只有在证据持久化且验证器通过后才能释放下游依赖。验证失败时保存原始输出、错误类型和计划版本，再决定重试、补偿或重规划；禁止为通过验收而降低既定阈值。

**相关知识点：** Success Criteria、Validator、业务不变量、LLM-as-a-Judge、Rubric、幻觉检测。

### 4. 如何评估任务拆解质量和执行计划的合理性？

**任务拆解质量应从目标覆盖、节点可执行性、依赖正确性、粒度、效率、安全性和失败恢复能力联合评估。**

1. 用Task Spec建立验收项，检查需求是否映射到计划节点，节点是否具有输入来源、执行器、输出Schema和成功标准。计划必须能被Executor消费；出现虚构工具、无生产者输入、循环依赖或无验证节点即不可执行。

| 维度 | 代表指标 | 典型问题 |
| --- | --- | --- |
| 完整性 | 目标覆盖率、约束遗漏率 | 漏掉交付物 |
| 正确性 | 依赖准确率、可执行率 | 顺序错误 |
| 粒度 | 平均节点规模、局部重试率 | 过粗或过细 |
| 效率 | 关键路径、并行度、成本 | 重复步骤 |
| 鲁棒性 | 恢复成功率、重规划次数 | 单点失败 |
| 安全性 | 越权率、高风险漏拦率 | 副作用失控 |

2. **任务粒度**不能用节点数量判断。合格节点应单一责任、可独立验证、可安全重试且失败可定位；协调耗时超过执行收益说明过细，一次失败迫使大范围重做则说明过粗。DAG还需检查共享前置去重和资源冲突串行。

3. 采用静态校验、仿真、历史回放、对抗样例和人工Rubric。人工判断计划是否符合领域常识、是否存在更短安全路径；LLM Judge可辅助语义评价，但不能替代Schema、权限和工具验证。

4. 线上以端到端完成率为最终指标，并监控首计划成功率、修改率、步骤失败率、P95时延、成本和人工接管率。按领域与复杂度切片并与基线比较，避免总体平均掩盖高风险长尾失败。

**相关知识点：** 目标覆盖率、计划可执行率、依赖准确率、任务粒度、关键路径、仿真执行、Rubric、A/B测试。

### 5. Agent如何根据任务自动选择工具（Tool Selection）？

**自动Tool Selection应采用候选召回、硬约束过滤、多目标排序、参数绑定和结果反馈五阶段路由。**

1. 将任务节点结构化为目标、输入、输出、时效、数据敏感度、风险和预算，再从Tool Registry召回候选。规则处理精确命令，关键词与向量检索负责初筛，模型只在Top-K中比较，不得编造工具。

2. Tool Registry保存**语义描述、输入输出Schema、适用与禁用场景、权限、幂等、版本、费用、延迟和错误码**。剔除参数不兼容、权限不足、服务不可用或副作用超授权的候选，再按匹配度、成功率、成本和延迟排序。

> 本题视角：Agent如何根据任务自动选择工具（Tool Selection）
| 机制 | 解决问题 | 不负责什么 |
| --- | --- | --- |
| Function Calling | 生成结构化调用 | 实际执行 |
| MCP | 统一能力发现与交互 | 业务授权 |
| Tool Registry | 管理能力元数据 | 执行编排 |
| Workflow | 组织多次调用 | 开放式推理 |

3. 选中后执行Schema Binding，将任务字段映射为参数并检查来源、类型和必填项。高风险调用由宿主校验权限并审批；候选接近且后果不同则澄清，低风险任务可试用低成本候选并保留备选。

4. 返回后验证**业务效果**，HTTP 200只表示协议成功。瞬时错误重试，参数错误修复，权限错误停止，能力不匹配则重新选择。记录候选集、选择理由、版本、耗时、成本和最终结果，用反馈更新排序。

**相关知识点：** Tool Selection、Tool Registry、Function Calling、MCP、Schema、权限校验、结果验证。

### 6. Agent如何评估每一步执行结果是否成功？

**每一步是否成功必须由Validator依据证据判定，不能把调用完成、HTTP 200或模型自信等同于业务成功。**

1. 节点契约定义输出Schema、成功条件、不变量、误差、预期状态和禁止副作用，并指定证据来源。Executor返回结果和回执，Validator读取产物或外部状态，避免执行者自证。

| 验证层 | 检查内容 | 示例 |
| --- | --- | --- |
| 传输层 | 是否送达、超时 | 状态码、异常 |
| 结构层 | 格式与类型 | JSON Schema |
| 语义层 | 是否满足要求 | Rubric、证据 |
| 业务层 | 不变量与外部状态 | 资源、数量 |
| 安全层 | 权限和副作用 | 无越权写入 |

2. 确定性任务优先用规则、查询、编译、测试和哈希比对；开放文本采用Rubric、事实引用或多评审器。**LLM-as-a-Judge**只适合语义维度，不得替代权限、金额或资源状态检查。

3. 结果分为Succeeded、Retryable Failure、Non-retryable Failure和Uncertain，包含错误类型、证据及建议。Uncertain补证或人工复核；可恢复失败才重试，前提失效则交给Replanner。

4. 证据持久化且版本一致时，节点才能标记成功并释放后继。监控假阳性率、假阴性率、覆盖率、人工推翻率和成本；通过失败样本更新Validator，但不得在执行中降低阈值。

**相关知识点：** Validator、Success Criteria、业务不变量、JSON Schema、LLM-as-a-Judge、Rubric、假阳性、证据链。

### 7. Agent如何判断当前步骤执行成功？

**当前步骤只有在输出契约、业务后置条件和副作用约束均被可信证据满足时，才能标记为成功。**

1. Planner预先定义节点的前置条件、输出Schema、业务不变量、允许误差、预期状态、禁止副作用及证据源。Validator据此验收，不能让执行模型凭自然语言自评成功。

2. 验证从低成本确定性检查逐层进行：先查异常和协议状态，再校验结构与类型，然后验证业务规则和外部状态，最后判断是否推动上层目标。HTTP 200、函数无异常或生成文本仅证明动作完成，**不等于业务目标达成**。

| 验证层 | 核心问题 | 典型证据 |
| --- | --- | --- |
| 协议层 | 调用是否正常结束 | 状态码、错误码 |
| 结构层 | 输出是否可消费 | JSON Schema |
| 业务层 | 后置条件是否成立 | 数据查询、不变量 |
| 目标层 | 子目标是否真正完成 | 测试、验收规则 |

3. 代码修改检查编译、测试、静态分析和Diff；检索验证来源、时效及交叉证据；写操作回读外部状态，核对资源ID、版本和幂等回执。确定性证据优先于LLM Judge，避免将表达流畅误判为正确。

4. 开放式结果用Rubric评价正确性、完整性、安全性和相关性，结合多评审器或人工复核。状态分为通过、可恢复失败、不可恢复失败和不确定；失败进入修复，不确定则补证，只有通过才解锁后继节点，并以误判率和漏判率校准阈值。

**相关知识点：** 前置条件、后置条件、输出契约、Validator、业务不变量、验收测试、LLM-as-a-Judge、证据链。

### 8. Agent如何设计Validator模块？

**Validator应是独立于Executor的分层验收模块，以任务契约和可追溯证据输出结构化判定。**

1. 输入包括目标、Success Criteria、产物、工具结果和风险。契约声明Schema、业务不变量、容差、预期状态和禁止副作用；Validator不可只读Executor总结，以免继承幻觉。

2. 流水线先查协议、格式和类型，再运行规则、测试或外部查询，最后用LLM Judge评估语义。前层失败可短路，评审按风险触发；写操作必须回读。

| 验证器 | 适用对象 | 证据 |
| --- | --- | --- |
| Schema Validator | 结构化输出 | 类型、必填项 |
| Rule Validator | 业务约束 | 不变量 |
| Test Validator | 代码与流程 | 编译、测试结果 |
| LLM Judge | 开放式文本 | Rubric与引用 |

3. 输出为**PASS、RETRYABLE_FAIL、FATAL_FAIL、UNCERTAIN**，携带错误码、证据、建议和置信度。Scheduler据此放行、Retry、Repair、Replan或转人工；Validator只判定，不改产物。

4. LLM Judge使用固定Rubric和隔离提示，防御提示注入；高风险场景采用多评审器或人工抽检。规则需版本化，用标注样本评估误报率、漏报率、校准度和延迟，并灰度发布。

**相关知识点：** Validator、Success Criteria、业务不变量、JSON Schema、Rubric、LLM-as-a-Judge、校准、职责分离。

### 9. Agent任务成功率如何量化评估？

**任务成功率应以预先定义的端到端验收条件计算，并按任务难度、风险和业务价值分层报告。**

1. TSR＝成功任务数÷有效任务数。成功需同时满足目标正确、关键约束完整、无禁止副作用且在时限内；取消、环境故障和无效输入是否进入分母须预先固定，不能事后剔除。一次尝试成功用Pass@1，多次尝试内成功记Pass@K。

2. 测试集应覆盖真实任务分布、长尾和对抗样本，并按类型、复杂度、工具、语言和风险切片。高价值任务可计算**加权成功率＝Σ权重×成功标记÷Σ权重**，同时报告宏平均，防止大量简单任务掩盖复杂任务失败。

| 指标层级 | 典型指标 | 反映问题 |
| --- | --- | --- |
| 端到端 | TSR、Pass@1 | 用户目标是否完成 |
| 步骤级 | 规划、工具、验证成功率 | 故障位置 |
| 效率级 | 时延、Token、调用成本 | 完成代价 |
| 安全级 | 越权率、重复副作用率 | 生产风险 |

3. 确定性任务用测试、规则和外部状态判定；开放式任务使用固定Rubric与独立Judge，并人工抽检一致性。部分完成可单列Partial Credit，但不得与完全成功混算；用户点赞只是辅助信号。

4. 报告样本量和置信区间，版本变更使用同一冻结集回归、配对比较及线上A/B。还要分析失败类型、重试后成功率和单位成功成本，防止Agent通过拒答、缩小范围或重复尝试投机指标。线上分布漂移后更新样本，同时保留历史集确保可比。

**相关知识点：** TSR、Pass@K、加权成功率、宏平均、Rubric、置信区间、回归评测、A/B测试。

### 10. Agent如何设计Success Criteria（成功判定标准）？

**Success Criteria应在执行前定义为可观察、可验证且与用户目标直接对应的验收契约。**

1. 将目标转为对象、期望状态、约束、时限和证据。标准应可由Validator判定，例如“测试通过且无新增高危告警”，而非“质量良好”。关键歧义需用户确认，Agent不能降低范围。

2. 建立任务级和步骤级标准：步骤成功保证产物可消费，任务成功证明目标达成。每项声明**Must/Should、规则、阈值、证据、误差和失败动作**；Must全部满足才完成，Should用于评分。

| 标准类型 | 检查内容 | 典型证据 |
| --- | --- | --- |
| 结构标准 | 格式、字段、类型 | JSON Schema |
| 功能标准 | 行为和输出正确 | 测试、业务查询 |
| 质量标准 | 完整性、相关性 | Rubric |
| 安全标准 | 权限与禁止副作用 | 策略、审计日志 |
| 效率标准 | 时延、Token、费用 | Runtime Metric |

3. 同时定义正向条件和负向约束。HTTP 200或生成文件仅证明动作结束，不代表成功；写操作需回读状态，事实回答核对来源与时效，代码任务运行编译、测试和Diff检查。

4. Validator优先用确定性规则，开放语义再用Rubric、Judge或人工复核。结果分为PASS、FAIL和UNCERTAIN并附证据。标准需版本化，以样本评估误报与漏报，防止虚假成功或无效重试。

**相关知识点：** Success Criteria、验收契约、Must/Should、业务不变量、Validator、Rubric、负向约束、证据链。

### 11. 如何设计统一的Validator框架？

**统一Validator框架应以标准契约、插件注册表和统一判定协议覆盖不同任务。**

1. 请求包含目标、Success Criteria、产物、工具结果和风险；结果输出PASS、RETRYABLE_FAIL、FATAL_FAIL或UNCERTAIN，并附错误码、证据和建议。

2. Registry按产物、任务域和风险选插件，形成**确定性优先、语义评审后置**的流水线。先查协议、Schema和安全策略，再运行规则、测试或外部查询，最后用LLM Judge；前层失败可短路。

| 验证器类型 | 适用对象 | 典型证据 |
| --- | --- | --- |
| Schema | JSON、表单、工具结果 | 类型与必填项 |
| Rule | 权限、金额、业务约束 | 不变量与阈值 |
| Test | 代码、工作流 | 编译与测试报告 |
| LLM Judge | 开放文本 | 固定Rubric |

3. Orchestrator据结果决定放行、Repair、Retry、Replan或转人工，Validator不改产物。插件声明Schema、成本、超时、版本和范围，支持串行、并行及Quorum；高风险任务需确定性证据。

4. 框架隔离不可信产物，防止提示注入，并实施权限与脱敏。用标注集评估误报率、漏报率、校准度、延迟和费用，升级先Shadow再灰度。缓存仅复用相同产物哈希、契约和验证器版本的结果。

**相关知识点：** Validator Registry、Validation Contract、插件化、短路、Quorum、LLM-as-a-Judge、校准、Shadow验证。
<a id="plan-209"></a>
### 12. Agent 如何构建高质量上下文（Context）？

**高质量Context不是信息堆积，而是为当前决策提供最小充分、来源明确、权限合规且内部一致的工作集。**

1. 上下文按优先级组织：系统与安全规则、当前Task Spec、Plan和Step状态、工具Schema、相关证据、近期观察、长期记忆摘要及未决问题。每块附来源、时间、版本、权限和置信度，避免模型把旧记忆或不可信工具输出当成指令。

2. 检索阶段先从目标抽取实体、范围、时效和访问约束，再使用关键词、向量及结构化过滤召回，经过重排、去重和证据覆盖检查。**选择标准是对下一动作的信息增益，而非单纯相似度**；关键事实保留原文片段及引用。

| 内容层 | 保留方式 | 主要风险 |
| --- | --- | --- |
| 指令 | 原文、分级 | 冲突与注入 |
| 执行状态 | 结构化字段 | 版本过期 |
| 证据 | 片段与引用 | 召回噪声 |
| 工具结果 | 摘要与Artifact | 输出过长 |

3. 长任务将完整产物存外部存储，只注入摘要、URI和哈希；接近窗口上限时按重要性压缩，必须保留目标、约束、已完成事实、错误和下一步。上下文组装后检查Token预算、重复、矛盾、敏感数据与Prompt Injection。通过任务成功率和引用正确率评估，而非只看召回率。

**相关知识点：** Context Engineering、最小充分上下文、信息增益、Hybrid Retrieval、重排、Artifact、上下文压缩、Prompt Injection。

### 13. Agent 如何选择最合适的 Tool？

**Agent应先按能力与权限过滤工具，再按成功概率、证据质量、时延、成本和副作用风险排序，而不是仅依据工具名称做语义匹配。**

1. Router先从当前Step提取所需能力、输入类型、输出契约、数据范围和是否允许写操作。硬约束不满足的工具直接淘汰；对剩余候选计算历史成功率、P95延迟、价格、数据新鲜度和风险分数，必要时选择只读工具先补证。

2. 针对“Agent 如何选择最合适的 Tool”，Tool Registry应保存**语义描述、输入输出Schema、权限、幂等属性、版本、费用、延迟和错误码**。Router先用规则或检索召回候选，再由模型基于当前目标排序；真正执行前由宿主校验参数、授权范围和风险，模型只生成调用意图。

> 本题视角：Agent 如何选择最合适的 Tool
| 机制 | 解决问题 | 不负责什么 |
| --- | --- | --- |
| Function Calling | 生成结构化调用 | 实际执行 |
| MCP | 统一能力发现与交互 | 业务授权 |
| Tool Registry | 管理能力元数据 | 执行编排 |
| Workflow | 组织多次调用 | 开放式推理 |

3. 针对“Agent 如何选择最合适的 Tool”，调用返回后要验证**业务效果**，HTTP 200只能证明协议成功。瞬时错误可退避重试，参数错误先修复，权限错误停止并申请授权，能力不匹配则重新选工具。成本可通过候选裁剪、结果缓存、批处理、并行无依赖调用和模型分级控制。

**相关知识点：** Tool Selection、Tool Registry、Function Calling、MCP、Schema、权限校验、结果验证。

### 14. Tool Calling 的整体架构如何设计？

### 15. Agent 如何判断工具调用是否成功？

**工具调用成功必须同时满足协议返回、输出契约、业务不变量和预期外部状态，HTTP 200或无异常都不足以单独证明成功。**

1. 调用前为每个Tool定义Success Contract，包括允许状态码、输出Schema、错误字段、预期资源变化、唯一标识和禁止副作用。调用后Runtime先解析传输与协议状态，再验证结构；超时或连接中断应标记Unknown，而不是直接判定失败。

2. 针对“Agent 如何判断工具调用是否成功”，每一步应定义**输出Schema、业务不变量、允许误差、预期状态变化和禁止副作用**。验证顺序包括协议状态、结构格式、业务规则、外部真实状态和用户最终目标；代码任务还要结合编译、测试、静态分析与差异审查。

| 验证层 | 检查对象 | 示例 |
| --- | --- | --- |
| 协议层 | 调用是否返回 | 状态码、异常 |
| 结构层 | 格式是否合规 | JSON Schema |
| 业务层 | 不变量是否满足 | 数量、权限 |
| 目标层 | 用户问题是否解决 | 验收测试 |

3. 针对“Agent 如何判断工具调用是否成功”，没有唯一答案时使用Rubric、成对比较、多评审器、事实证据和用户反馈，并分别评价正确性、完整性、安全性、成本与延迟。结果宜分为通过、可恢复失败、不可恢复失败和不确定；不确定时补证或**人工**复核，不强行二分类。

**相关知识点：** Success Criteria、Validator、业务不变量、LLM-as-a-Judge、Rubric、幻觉检测。

### 17. 如果工具调用返回结果不可信或格式错误，系统如何兜底？

**工具结果必须先经过Schema、来源、业务规则和交叉证据验证；格式错误可Repair，事实不可信则隔离结果并切换证据路径。**

1. Runtime把工具原始响应保留为不可变Artifact，记录tool_id、版本、call_id、时间和哈希，再按outputSchema解析。缺字段、类型错误或包裹文本可用确定性Parser修复；修复后必须重新校验，禁止让模型凭猜测补造关键值。

2. 可信度检查包括来源身份与签名、数据时效、权限范围、业务不变量、内容注入和外部状态。**协议成功与业务可信必须分离**：HTTP 200只表示传输完成，不能证明价格、库存、文件写入或查询结果正确。

| 异常 | 首选动作 | 升级条件 |
| --- | --- | --- |
| 格式可修 | Parser/Repair | 仍不合Schema |
| 数据过期 | 重新查询 | 无新版本 |
| 来源不可信 | 换权威工具 | 无替代证据 |
| 结果冲突 | 交叉验证 | 高风险未决 |

3. 结果无效时不进入Memory和下游节点，状态标为Untrusted或Unknown，并携带证据原因。可更换工具、缩小查询或要求人工确认；高风险操作Fail Closed。持续统计Schema失败率、冲突率与人工推翻率，异常版本自动熔断并回滚。

**相关知识点：** Output Schema、Artifact、Parser Repair、业务不变量、来源验证、交叉验证、Fail Closed、熔断。

### 18. 如何评估整个 Agent 系统的效果（准确率、任务完成率、延迟等指标）？

**Agent系统评估必须同时覆盖任务质量、可靠性、安全、效率和业务价值，并区分离线基准、在线实验与生产监控。**

1. 先按真实任务分布建立分层评测集，包含常规、长尾、失败恢复、权限和对抗样本；每题定义Success Criteria、允许误差与证据。确定性任务用单元测试、Schema和外部状态验证，开放答案用Rubric、多评审器及人工抽检。

2. 核心指标包括**端到端任务完成率、一次通过率、步骤成功率、恢复率、人工接管率、安全违规率、P50/P95延迟、Token和每次成功成本**。准确率只适合有明确标签的子任务，不能替代任务完成率。

| 评估层 | 方法 | 主要目的 |
| --- | --- | --- |
| 离线 | 固定基准与回放 | 版本门禁 |
| Shadow | 生产流量旁路 | 无风险对比 |
| A/B | 随机在线实验 | 因果评估 |
| 监控 | SLI/SLO和告警 | 发现退化 |

3. 比较版本时固定任务集或按难度加权，报告样本量、置信区间和失败类型，避免简单任务占比变化制造提升。上线使用Canary与回滚阈值，持续抽样人工复核；将线上失败脱敏后回灌评测集。最终以质量—延迟—成本Pareto前沿选型。

**相关知识点：** Agent Evaluation、Success Criteria、任务完成率、Rubric、Shadow、A/B测试、SLI/SLO、置信区间、Pareto前沿。

### 19. 没有标准答案时如何做结果评估？

**没有唯一标准答案时，应使用维度化Rubric、证据约束、相对比较和人工校准评估，而不是要求评审器猜测唯一参考文本。**

1. 先与业务方定义正确性、完整性、相关性、可执行性、安全性、风格和成本等维度，为每档提供行为锚点及权重。即使答案开放，引用真实性、格式、禁用内容、事实一致性和任务约束仍可由确定性规则检查。

2. 语义评价可由LLM-as-a-Judge按Rubric打分，并要求逐项证据；为降低位置偏差和自偏好，采用随机顺序的成对比较、多个异构Judge或人工抽样。**Judge分数必须用专家标注集做相关性与阈值校准**。

| 方法 | 优势 | 主要风险 |
| --- | --- | --- |
| Rubric评分 | 维度透明 | 锚点设计困难 |
| 成对比较 | 易判断相对优劣 | 位置偏差 |
| 多Judge | 降低单点偏差 | 成本增加 |
| 人工评审 | 业务可信 | 慢且一致性有限 |

3. 结果输出分项分数、证据、置信度和不确定原因，不只给总分。低置信度或高风险分歧转人工；定期计算评审者间一致性，定位Rubric歧义并更新行为锚点。线上结合用户采纳率、返工率与任务完成率验证离线分数。评测集覆盖长尾和反例，并防止模型针对固定Judge过拟合。

**相关知识点：** Rubric、行为锚点、LLM-as-a-Judge、成对比较、多评审器、人工校准、位置偏差、评测过拟合。

### 20. 如何检测模型幻觉？

**模型幻觉检测的核心是把回答中的可验证声明拆成原子事实，并逐项检查其证据支持、逻辑一致性与来源可靠性。**

1. 先识别答案中的实体、数字、时间、因果、引用和工具执行结果，将每个声明与检索文档、数据库、知识图谱或真实环境状态对齐。**存在来源不等于获得支持**：还要判断证据是否蕴含该声明、是否过期、是否被断章取义，以及多个来源是否相互冲突。

2. 检测应组合确定性校验与语义校验。数字、格式、引用链接、API返回值优先使用规则和外部查询；开放文本可用自然语言推断模型或LLM-as-a-Judge判断证据一致性，但评审器也可能产生幻觉，必须用标注集校准，并对高风险判断执行人工复核。

| 检测方法 | 适用对象 | 局限 |
| --- | --- | --- |
| 规则与数据库核验 | 数字、实体、状态 | 难覆盖开放知识 |
| 检索证据对齐 | 事实性陈述 | 受召回质量影响 |
| 多次采样一致性 | 模型内部不确定性 | 一致也可能共同错误 |
| Judge或NLI | 语义蕴含关系 | 存在模型偏差 |

3. 在线系统不应只输出“有或无幻觉”，而应记录声明级支持度、来源质量、冲突情况和置信区间。低支持或高影响声明触发二次检索、要求模型引用证据、降级为保守回答或转人工。离线评测需覆盖无答案问题、诱导性前提、时效知识与伪造引用，并分别统计事实精确率、声明召回率和严重幻觉率。

**相关知识点：** 原子事实、事实核验、证据蕴含、检索增强生成、自一致性、NLI、LLM-as-a-Judge、声明级置信度、幻觉评测。
