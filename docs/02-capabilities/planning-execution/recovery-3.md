### PLAN-250 · Agent如何判断当前步骤成功还是失败？

> 稳定 ID：`PLAN-250`｜原题号：250

**当前步骤的成败应由预先声明的Step Contract和独立Validator判定，不能由执行该步骤的模型自行宣布。**

1. Planner为节点定义输入版本、输出Schema、Success Criteria、业务不变量、允许误差、预期副作用和禁止动作。Executor返回产物、工具回执、错误与Trace引用；Validator依据同一契约版本检查，避免计划更新后用新标准误判旧Attempt。

2. 针对“Agent如何判断当前步骤成功还是失败”，每一步应定义**输出Schema、业务不变量、允许误差、预期状态变化和禁止副作用**。验证顺序包括协议状态、结构格式、业务规则、外部真实状态和用户最终目标；代码任务还要结合编译、测试、静态分析与差异审查。

| 验证层 | 检查对象 | 示例 |
| --- | --- | --- |
| 协议层 | 调用是否返回 | 状态码、异常 |
| 结构层 | 格式是否合规 | JSON Schema |
| 业务层 | 不变量是否满足 | 数量、权限 |
| 目标层 | 用户问题是否解决 | 验收测试 |

3. 针对“Agent如何判断当前步骤成功还是失败”，没有唯一答案时使用Rubric、成对比较、多评审器、事实证据和用户反馈，并分别评价正确性、完整性、安全性、成本与延迟。结果宜分为通过、可恢复失败、不可恢复失败和不确定；不确定时补证或**人工**复核，不强行二分类。

**相关知识点：** Success Criteria、Validator、业务不变量、LLM-as-a-Judge、Rubric、幻觉检测。

### PLAN-254 · Task ID 和 Idempotency Key 有什么区别？

> 稳定 ID：`PLAN-254`｜原题号：254

**Task ID唯一标识某次执行实例，用于追踪状态；Idempotency Key标识业务意图，用于跨重试和重复提交去重。**

1. Task ID由任务系统创建，回答“哪一个任务正在运行”，用于状态查询、暂停恢复和审计。调用方因超时重新提交时，系统可能创建新的Task ID；因此它无法判断两次请求是否属于同一业务操作。

2. Idempotency Key通常由调用方生成，在同一业务请求的全部重试中保持不变。服务端应以租户、操作类型和幂等键建立唯一约束，原子保存请求摘要、处理状态与结果引用。**相同键却携带不同参数时必须拒绝**，否则会把不同业务意图错误合并。

| 标识 | 代表对象 | 重试时变化 | 主要用途 |
| --- | --- | --- | --- |
| Task ID | 一次任务实例 | 可变化 | 追踪生命周期 |
| Idempotency Key | 一次业务意图 | 不变化 | 防止重复副作用 |
| Attempt ID | 一次执行尝试 | 每次变化 | 分析重试过程 |

3. 重复请求命中成功记录时返回原结果，命中处理中记录时返回同一状态句柄，可重试失败则创建新Attempt但沿用幂等键。记录保留时间必须覆盖最大重试窗口；对支付、发信等外部副作用，还要向下游透传幂等键，或采用业务唯一键、事务发件箱、结果查询和对账。三类标识应同时进入链路日志，以区分重复提交、系统重试和独立任务。

**相关知识点：** Task ID、Attempt ID、Idempotency Key、请求摘要、唯一约束、幂等消费、事务发件箱、At-Least-Once、对账。

### PLAN-255 · Agent 为什么比普通 Web 服务更需要幂等性？

> 稳定 ID：`PLAN-255`｜原题号：255

**Agent比普通Web服务更依赖幂等性，因为其执行链更长、重试主体更多、状态恢复更复杂，且同一意图可能触发多个真实副作用。**

1. 普通Web请求通常是短事务，调用入口和写入点相对明确；Agent则经历规划、工具调用、观察、反思和重规划，任一阶段的超时、进程重启或消息重复投递都可能触发重放。模型还可能生成语义相同但文本不同的动作，单纯按请求体去重并不可靠。

2. Agent经常调用发邮件、创建工单、付款和修改配置等非幂等工具；一次重复执行可能造成业务损失。并且任务可跨分钟甚至数天恢复，内存中的锁和短期缓存无法覆盖完整生命周期。**幂等边界必须从用户意图延伸至每个有副作用的步骤**。

| 特征 | 普通Web服务 | Agent系统 |
| --- | --- | --- |
| 执行时长 | 多为短请求 | 长任务、可暂停恢复 |
| 重试位置 | 网关或客户端 | 编排器、步骤、工具多层 |
| 动作确定性 | 参数相对稳定 | 模型输出具有随机性 |
| 副作用数量 | 通常集中 | 跨多个外部系统 |

3. 落地时为任务意图、计划步骤和执行尝试分别建立标识，持久化动作规范化参数、状态与结果摘要；写入侧使用唯一约束或事务发件箱，外部工具优先透传幂等键。恢复时先查询既有结果，再决定重试、补偿或转人工。这样保证的是“可观测的有效副作用至多一次”，而非宣称分布式环境中天然实现Exactly-Once。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** 幂等性、任务重放、语义去重、长事务、事务发件箱、唯一约束、补偿事务、At-Least-Once、Exactly-Once语义。

### PLAN-256 · 幂等性和一致性是什么关系？

> 稳定 ID：`PLAN-256`｜原题号：256

**幂等性解决重复执行不产生额外效果的问题，一致性约束多个状态副本或业务对象保持规则成立；前者是实现后者的重要手段，但不能替代后者。**

1. 幂等性关注同一操作执行一次或多次后的可观察结果是否等价，例如重复创建任务只产生一个任务。一致性关注系统状态是否满足约束，例如任务记录、额度扣减和外部工单最终对应。一个接口可以幂等却读取旧副本，也可以强一致却因重复请求产生两次扣款。

2. 在至少一次投递和网络超时环境中，消费者必须重试；幂等键、唯一约束和已处理消息表防止重放扩大副作用，从而帮助维持业务不变量。然而跨服务更新仍可能出现部分成功，需要事务、Saga补偿、Outbox与对账保证最终一致。**幂等只消除重复，不会自动修复遗漏、乱序或并发写冲突**。

| 机制 | 主要问题 | 典型保障 |
| --- | --- | --- |
| 幂等性 | 重复执行 | 副作用至多一次 |
| 强一致性 | 读写时序 | 立即观察最新状态 |
| 最终一致性 | 跨服务收敛 | 延迟后满足不变量 |
| 事务原子性 | 部分提交 | 全部成功或回滚 |

3. 设计时先定义业务不变量和一致性边界，再为每个可能重放的命令设置稳定幂等键。数据库内用事务和唯一约束原子落库；跨系统携带事件ID、版本号和因果顺序，失败后补偿并定期对账。验证既要注入重复消息，也要覆盖丢失、乱序、并发和恢复场景，不能以“没有重复记录”代替一致性验收。

**相关知识点：** 幂等性、强一致性、最终一致性、业务不变量、唯一约束、乐观并发控制、Saga、事务发件箱、消息去重、对账。

### PLAN-257 · 幂等性和事务有什么区别？

> 稳定 ID：`PLAN-257`｜原题号：257

**幂等性保证同一意图重复执行不会叠加副作用，事务保证一组操作满足原子性、一致性、隔离性和持久性；两者解决的故障维度不同。**

1. 幂等性面向重试和重复投递，比较一次与多次执行后的可观察状态；事务面向执行过程中的部分失败和并发干扰，规定一组读写如何提交或回滚。幂等接口内部不一定有事务，例如按固定值更新配置；事务操作也不一定幂等，例如每次事务都将余额减一。

2. 在单数据库内，可把幂等记录、业务更新和结果写入同一事务，并通过唯一约束阻止并发重复执行，这是二者最可靠的组合。**事务只保护其资源边界**；一旦涉及消息队列、邮件或第三方API，本地事务无法回滚外部副作用，需要Outbox、幂等消费者、Saga补偿和对账。

| 维度 | 幂等性 | 事务 |
| --- | --- | --- |
| 主要故障 | 重复请求、重放 | 部分失败、并发冲突 |
| 核心目标 | 多次效果等价 | 一组操作可靠提交 |
| 常用机制 | 幂等键、去重表 | ACID、锁、MVCC |
| 跨系统能力 | 可逐层传递 | 通常受资源边界限制 |

3. Agent任务中，应先确定业务意图的幂等键，再划分每一步的事务边界。数据库提交成功但响应丢失时，重试通过幂等记录返回原结果；外部调用状态不明时，先查询对方状态，不能直接重放。测试需分别注入重复消息、提交前崩溃、提交后超时和跨服务部分成功，验证去重与恢复逻辑。

**相关知识点：** 幂等性、ACID、事务边界、唯一约束、MVCC、事务发件箱、幂等消费者、Saga、补偿事务、状态不明。

### PLAN-259 · 如何保证发送邮件操作的幂等性？

> 稳定 ID：`PLAN-259`｜原题号：259

**邮件发送前以业务键登记PENDING记录，并把幂等键写入邮件元数据；超时后先查询供应商回执或发送日志，再决定重试。**

1. 幂等键应表达一次业务通知，而非一次HTTP调用，可由租户、事件类型、对象ID、收件人和模板版本生成。数据库以该键建立唯一约束；相同键但关键参数不同必须拒绝。周期性营销邮件还需纳入活动批次或时间窗。

2. 业务事务内同时写入发送意图与Outbox记录，由异步Worker领取并标记SENDING；调用邮件供应商时透传幂等键，成功后保存Message ID和回执。**数据库状态与Outbox必须原子提交**，否则可能出现业务已完成但邮件任务丢失，或事务回滚后仍发送。

| 机制 | 解决问题 | 注意事项 |
| --- | --- | --- |
| 唯一业务键 | 应用内重复请求 | 需校验参数摘要 |
| Outbox | 事务与消息一致性 | Worker仍需幂等 |
| 供应商幂等键 | 外部重复调用 | 受保留期限限制 |
| Message ID查询 | 超时状态不明 | 依赖供应商能力 |

3. 超时不等同于发送失败：优先按幂等键或Message ID查询，确认未接收后才能重试。供应商不支持查询或去重时，只能实现业务侧“尽量不重复”，可增加发送前登记、租约领取、状态对账及人工处理。退信和投递回执也要按事件ID去重，并区分“已接受”“已投递”与“已阅读”。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** Idempotency Key、事务发件箱、唯一约束、Message ID、状态不明、幂等消费者、投递回执、At-Least-Once、周期对账。

### PLAN-260 · 如何保证 Git Commit 的幂等性？

> 稳定 ID：`PLAN-260`｜原题号：260

**Git Commit幂等性的目标不是强行生成相同哈希，而是让同一变更意图重复执行时复用既有提交，不产生新的等价提交或重复修改。**

1. Commit哈希由tree、父提交、作者、时间和消息共同决定，因此内容相同也可能得到不同哈希。执行前固定目标仓库、基线和变更标识，检查工作树是否已有预期diff，并在分支历史中查询任务ID或Commit Trailer。

2. Agent应用补丁后重新计算规范化diff或目标tree：若HEAD已包含该变更，直接返回已有Commit；若工作树无变化，不创建空提交；若标记存在但内容不一致，则报告冲突而不是覆盖。**tree相同只说明快照相同，不能单独证明业务意图相同**。

| 判定依据 | 能确认什么 | 局限 |
| --- | --- | --- |
| Commit哈希 | 完整提交对象相同 | 元数据变化即不同 |
| Tree哈希 | 文件快照相同 | 不含父提交与意图 |
| Patch-ID | 补丁语义近似相同 | 合并提交处理有限 |
| 任务Trailer | 业务意图相同 | 需校验实际内容 |

3. 并发执行时按仓库和分支加锁，提交前确认HEAD未变化；推送使用快进检查，确需更新时采用带租约推送，不能盲目强推。持久化任务键、基线、目标tree、Commit哈希和推送结果；超时恢复时先查询提交图与远端引用，再决定复用、变基或人工处理。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** Git对象模型、Commit哈希、Tree哈希、Patch-ID、Commit Trailer、快进、乐观并发、带租约推送、幂等恢复。

### PLAN-261 · 如何保证 Jira 工单创建不重复？

> 稳定 ID：`PLAN-261`｜原题号：261

**以租户、项目、工单类型和业务实体ID构造唯一键，创建前后都查询Jira自定义字段或本地映射表。**

1. 先按租户、Jira项目、工单类型、业务实体ID和批次定义稳定Idempotency Key。不要使用摘要、描述等可变文本去重；应把该键写入受控的Jira自定义字段或Issue Property，并在本地建立唯一索引。

2. 创建前，在本地事务中插入PENDING记录；唯一键冲突时返回已有Issue Key或进行中状态。Worker先按远端字段查询，确认不存在后调用创建接口，随后保存Issue ID、响应摘要和状态。**分布式锁只能降低并发概率，最终去重仍依赖持久化唯一约束与远端标记**。

| 方案 | 优势 | 风险 |
| --- | --- | --- |
| 本地唯一映射 | 原子防并发 | 无法单独确认远端结果 |
| Jira自定义字段 | 可跨系统查询 | 需配置字段与权限 |
| 标签或属性 | 接入简单 | 可能被修改或不唯一 |
| 标题模糊匹配 | 无需改Schema | 易误判，不宜主用 |

3. 创建请求超时时结果未知，必须先按幂等字段查询Jira，再决定补写本地映射或重试；不能直接再次创建。若远端查询有索引延迟，可进入UNKNOWN状态并延迟复查。定时对账应发现一键多单及本地、远端记录不一致；重复单按策略关联、关闭或人工合并，并保留审计记录。

**相关知识点：** Idempotency Key、Jira自定义字段、Issue Property、唯一索引、状态不明、索引延迟、幂等消费、周期对账、重复工单治理。

### PLAN-262 · Tool 调用失败后如何重试？

> 稳定 ID：`PLAN-262`｜原题号：262

**Tool调用失败后不能立即盲目重试，必须先分类错误、确认上次副作用状态，再选择退避重试、修参、补偿、重规划或终止。**

1. 将工具返回统一为成功、可重试失败、调用方错误、权限错误、业务冲突和状态未知，并保存状态码、异常类型、Retry-After及原始响应。网络超时不代表工具未执行；有副作用的调用应先凭幂等键或业务ID查询真实状态。

2. **瞬时网络故障和服务过载**采用有抖动的指数退避，并尊重服务端Retry-After；参数或Schema错误先由Validator修复，不能用原参数重放；鉴权、权限、配额耗尽和确定性业务拒绝通常直接终止或转人工；工具能力与计划前提失效时才触发Replan。

| 策略 | 适用错误 | 是否改计划 |
| --- | --- | --- |
| Retry | 超时、限流、网络抖动 | 否 |
| Repair | 参数或格式错误 | 调整动作 |
| Compensation | 已产生外部副作用 | 恢复业务状态 |
| Replan | 路径或前提失效 | 是 |

3. 每次调用携带稳定Idempotency Key和新的Attempt ID，设置单次超时、最大次数、累计时长及费用预算。失败率升高时配合熔断和并发限制，避免重试风暴。跨系统部分成功使用Saga补偿；相同错误重复、无新证据或预算不足时安全终止，并把轨迹交给人工。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** 错误分类、状态未知、指数退避、随机抖动、Retry-After、Idempotency Key、Attempt ID、熔断器、重试风暴、Saga、Replan。

### PLAN-263 · Tool 超时但实际执行成功怎么办？

> 稳定 ID：`PLAN-263`｜原题号：263

**Tool超时后应进入“结果未知”状态，先通过幂等键、业务ID或查询接口确认真实副作用，再决定复用结果、重试、补偿或人工处理。**

1. 超时仅表示调用方未在期限内收到响应，可能发生在服务端执行前、执行中或执行成功后的响应链路。若直接重试支付、发信、建单等操作，可能产生重复副作用。因此状态机不能把超时简单记为FAILED，而应记录UNKNOWN及原请求标识。

2. 调用前生成稳定Idempotency Key，并预写PENDING记录；下游若支持幂等接口，重试时继续使用原键，服务端应返回首次结果。若支持按Request ID或业务ID查询，则轮询确认成功、失败或仍处理中。**新的Attempt ID用于追踪重试，但不能替换原幂等键**。

| 查询结果 | 后续动作 | 原因 |
| --- | --- | --- |
| 已成功 | 保存回执并继续 | 避免重复执行 |
| 明确失败且无副作用 | 按策略重试 | 可安全重放 |
| 仍处理中 | 延迟查询 | 防止并发重复 |
| 无法确认 | 转人工或对账 | 不可证明安全 |

3. 下游既不支持幂等也不能查询时，Exactly-Once无法由调用方单独保证；应使用业务唯一约束、事务发件箱、回调事件、周期对账或补偿操作降低风险。未知状态必须设置最长观察期限和升级路径，且后续步骤不得假设该动作失败。监控应单独统计超时率、未知状态滞留时间和重复副作用率。

**相关知识点：** 状态未知、Idempotency Key、Attempt ID、请求回执、轮询查询、事务发件箱、Exactly-Once边界、补偿事务、周期对账。

### PLAN-264 · Checkpoint 如何设计？

> 稳定 ID：`PLAN-264`｜原题号：264

**Checkpoint应保存足以确定性恢复任务的最小完整状态，并建立在副作用边界上，而不是简单序列化全部内存或聊天记录。**

1. 快照包含Task ID、状态机位置、计划版本、节点状态、输入输出引用、上下文摘要、预算、幂等键及外部回执。还要记录模型、Prompt、工具Schema和策略版本，否则恢复后行为可能漂移。

2. 生成时机选择稳定边界：节点完成、外部副作用确认或等待人工前。工具调用中途崩溃不能假定失败，应保留PENDING或UNKNOWN，并在恢复时查询真实状态。**Checkpoint写入与状态迁移必须原子化或具有明确提交协议**。

| 机制 | 内容 | 主要用途 |
| --- | --- | --- |
| Checkpoint | 某时刻完整恢复状态 | 快速续跑 |
| Event Log | 不可变迁移事件 | 审计与重建 |
| Tool Receipt | 外部执行回执 | 判断副作用 |
| Artifact Store | 大型输入输出 | 避免快照膨胀 |

3. 采用版本号、校验和与CAS防止并发覆盖，大对象放Artifact Store，快照只存引用；敏感字段加密并设保留期限。恢复时验证完整性、租约、权限和依赖兼容性，再从首个未确认节点继续。测试覆盖写入中断、版本迁移、重复恢复、状态未知及快照损坏。

**历史别名：** `PLAN-036`。

**相关知识点：** Checkpoint、稳定恢复点、持久化状态机、CAS、Tool Receipt、Artifact Store、Durable Execution、Event Sourcing、版本迁移。

### PLAN-265 · Workflow 如何断点续跑？

> 稳定 ID：`PLAN-265`｜原题号：265

**Workflow断点续跑依赖持久化状态机、稳定Checkpoint和幂等节点，恢复时从首个“未被确认完成”的节点继续，而非从进程中断位置机械重放。**

1. 每个节点具有PENDING、RUNNING、SUCCEEDED、FAILED、UNKNOWN等状态，完成后原子保存输出引用、Attempt ID、幂等键和工具回执。实例还需保存图版本、变量、分支选择、循环计数、等待条件和预算，才能重建控制流。

2. Worker通过租约领取任务，以版本号或CAS提交迁移；崩溃后由新Worker加载Checkpoint。**RUNNING节点不能直接视为失败**：纯计算节点可重算，有副作用节点必须查询外部状态，确认未执行才重试，已执行则补写结果。

| 节点状态 | 恢复动作 | 关键条件 |
| --- | --- | --- |
| SUCCEEDED | 跳过并复用输出 | 回执完整 |
| FAILED | 按错误策略重试 | 仍有预算 |
| RUNNING/UNKNOWN | 先查外部状态 | 禁止盲目重放 |
| WAITING | 重新注册等待条件 | 期限未失效 |

3. 恢复前校验工作流、Prompt、工具Schema、权限和Artifact版本；不兼容时显式迁移或转人工。恢复后重新计算就绪节点，避免调度已完成分支。测试注入节点前后崩溃、重复消息、租约争抢和状态损坏，并验证结果与副作用不重复。

**历史别名：** `TOOL-173`。

**相关知识点：** Workflow、断点续跑、Checkpoint、节点状态、租约、CAS、幂等节点、Durable Execution、状态迁移、故障注入。

<a id="plan-266"></a>
### PLAN-266 · Step 粒度应该如何划分？

> 稳定 ID：`PLAN-266`｜原题号：266

**Step是运行时恢复和幂等控制的最小单位，应按照一次可提交的状态变化划分。**

1. 一个Step应具有单一目标、明确输入输出、独立验证器、超时与重试策略，并能在失败后确定是否安全重放。划分边界通常位于外部副作用、权限变化、人工审批、长时间等待和高成本调用前后；多个无副作用且不可独立验收的推理动作可以合并。

2. 粒度过粗会导致失败定位困难、重试成本高、上下文膨胀，且无法复用部分成果；粒度过细会增加调度、序列化、模型调用和状态持久化开销，也容易丢失整体语义。**判断标准不是代码行数或Token数，而是是否形成可验证、可提交的业务结果**。

| 粒度 | 优势 | 主要问题 |
| --- | --- | --- |
| 粗粒度 | 编排简单、调用少 | 恢复与定位困难 |
| 细粒度 | 易并行、易观测 | 协调成本和延迟高 |
| 适中粒度 | 可验收、可重试 | 需按场景设计 |

3. 设计时从最终验收条件反推中间产物，再按数据依赖形成DAG；能够独立执行、缓存、验证或补偿的产物通常值得成为Step。对批量同构小任务可合并处理，对长耗时任务可继续分片。上线后以单步成功率、平均重试成本、调度开销、关键路径时长和故障定位时间校准粒度，而不是一次性固定。

**相关知识点：** Step、任务粒度、单一职责、验收条件、幂等重试、Checkpoint、DAG、关键路径、批处理、调度开销。
<a id="plan-267"></a>
### PLAN-267 · Saga 和 Checkpoint 有什么区别？

> 稳定 ID：`PLAN-267`｜原题号：267

**Checkpoint保存执行位置和上下文，用于故障后继续；Saga协调跨系统副作用及补偿，用于业务一致性。**

1. Checkpoint回答“任务执行到哪里、恢复后从哪里继续”，保存状态机位置、节点结果、计划版本、幂等键和工具回执。它主要处理进程崩溃、Worker迁移和长任务暂停，不定义跨服务失败后如何恢复业务不变量。

2. Saga回答“部分步骤已提交而后续失败时如何收敛”，将长事务拆成多个本地事务，并为可逆步骤设计补偿动作。补偿不是数据库回滚，而是新的业务操作，可能失败、需要重试，也未必能完全还原原状态。**Saga必须持久化每个正向动作与补偿动作的执行状态**。

| 维度 | Checkpoint | Saga |
| --- | --- | --- |
| 核心目标 | 执行连续性 | 跨服务业务一致性 |
| 主要产物 | 状态快照、回执 | 本地事务、补偿链 |
| 失败动作 | 恢复并续跑 | 前向恢复或反向补偿 |
| 是否撤销副作用 | 否 | 通过补偿尝试修复 |

3. 二者通常组合使用：Checkpoint记录Saga编排器当前步骤、外部回执和补偿进度；崩溃恢复后先确认状态，再继续正向步骤或补偿，避免重复执行。对于发邮件这类不可撤销动作，应采用幂等、延迟提交或人工确认，而不能假设存在完美补偿。设计时还要设置补偿顺序、重试策略、超时和人工升级路径。

**相关知识点：** Checkpoint、Saga、长事务、本地事务、补偿事务、前向恢复、反向补偿、业务不变量、Durable Execution、幂等恢复。

### PLAN-268 · Agent 如何实现任务恢复？

> 稳定 ID：`PLAN-268`｜原题号：268

**Agent恢复不仅要加载聊天历史，还要恢复Task、Step和Attempt状态、工具回执、权限及待执行依赖。**

1. 正常执行期间持续把状态迁移写入持久化存储，并在稳定边界生成Checkpoint。快照包含计划版本、节点状态、上下文摘要、输入输出引用、预算、幂等键、工具回执，以及模型、Prompt与工具Schema版本；大对象只保存不可变引用。

2. 恢复进程先获取任务租约并校验快照完整性，防止多个Worker同时续跑；随后重建DAG就绪队列，跳过已确认成功节点。对于RUNNING或UNKNOWN节点，纯计算可重算，有副作用的工具必须查询外部状态。**未收到响应不能作为再次执行的充分依据**。

| 恢复对象 | 必要信息 | 恢复动作 |
| --- | --- | --- |
| 已完成节点 | 输出与验证结果 | 直接复用 |
| 纯计算运行中节点 | 输入与版本 | 安全重算 |
| 副作用未知节点 | 幂等键与回执 | 先查后重试 |
| 等待节点 | 等待对象与期限 | 重建订阅或定时器 |

3. 续跑前重新校验凭证、权限、依赖资源和版本兼容性；条件变化时局部重规划、执行状态迁移或转人工，不静默沿用失效假设。恢复操作本身也须幂等，并受重试、时间与费用预算约束。通过进程崩溃、网络分区、重复恢复和外部调用状态未知等故障注入验证任务最终收敛。

**相关知识点：** 任务恢复、Checkpoint、持久化状态机、租约、DAG重建、状态未知、幂等恢复、版本兼容、Durable Execution、故障注入。

### PLAN-269 · 多个 Agent Worker 同时执行同一个任务怎么办？

> 稳定 ID：`PLAN-269`｜原题号：269

**多个Worker争抢同一任务时，应通过持久化租约、版本化状态迁移和幂等副作用实现单一有效执行，而不能依赖进程内锁。**

1. 调度器采用数据库条件更新或分布式租约领取任务，记录Owner、Lease ID和过期时间。Worker定期续租，只有有效持有者可推进状态。租约只能协调执行权，不能证明旧Worker已经停止，因此仍需防范“僵尸Worker”。

2. 状态更新携带版本号或Fencing Token，存储层以CAS拒绝旧写入；步骤和业务写入同时携带Idempotency Key。**租约协调执行权，Fencing Token阻止过期Worker提交，幂等性兜住重复副作用**，三者不可替代。

| 机制 | 解决问题 | 局限 |
| --- | --- | --- |
| 进程内锁 | 单进程互斥 | 跨机器无效 |
| 分布式租约 | 协调任务所有权 | 过期Worker仍可能运行 |
| CAS/版本号 | 防止旧状态覆盖 | 不直接保护外部系统 |
| 幂等键 | 去重业务副作用 | 需下游配合 |

3. Worker失联后由新Worker在租约过期后接管，从Checkpoint确认节点状态；未知外部调用先查询后重试。监控重复领取、续租失败、CAS冲突和重复副作用率。测试模拟网络分区、长暂停、时钟偏差与消息重复，验证只有一个Worker能形成有效提交。

**相关知识点：** Worker竞争、分布式租约、Lease ID、Fencing Token、CAS、乐观并发、Idempotency Key、僵尸Worker、Checkpoint、网络分区。

### PLAN-271 · Kafka 如何实现幂等消费？

> 稳定 ID：`PLAN-271`｜原题号：271

**Kafka幂等消费的核心是在业务提交边界原子记录消息已处理事实，使同一消息被重复拉取、重平衡或重放时不会再次产生业务副作用。**

1. 消息携带稳定Event ID或业务幂等键；消费者建立唯一索引或Inbox表。在同一数据库事务内插入去重记录并更新业务，唯一键冲突即视为已处理。只有事务成功后才提交Kafka Offset，避免先确认后落库造成丢失。

2. 若结果仍需发送Kafka消息，可用Kafka事务原子提交消费Offset与新消息，实现Kafka内部Exactly-Once语义；外部数据库、HTTP和邮件不在该事务内。**端到端幂等仍需唯一约束、Outbox、下游幂等键或补偿机制**。

| 方案 | 适用边界 | 注意事项 |
| --- | --- | --- |
| Inbox/去重表 | Kafka到数据库 | 与业务更新同事务 |
| 业务唯一约束 | 创建型操作 | 业务键必须稳定 |
| Kafka事务 | consume-process-produce | 主要限于Kafka内部 |
| 下游幂等键 | 外部API | 依赖对方支持 |

3. 去重记录期限应覆盖Topic保留期与最大重放窗口。并发消费者必须依赖原子约束，不能仅“先查再写”；失败消息进入有限重试和死信流程，人工重放仍沿用原Event ID。监控重复命中、事务失败、消费延迟和死信量，并用崩溃及重平衡测试验证。

**相关知识点：** Kafka、幂等消费、Event ID、Inbox、唯一约束、Offset提交、Kafka事务、Exactly-Once语义、Outbox、死信队列、重平衡。

### PLAN-272 · Exactly Once 在 Agent 中如何落地？

> 稳定 ID：`PLAN-272`｜原题号：272

**Agent端到端Exactly-Once通常不是单一中间件能力，而是至少一次投递、消费者幂等、唯一约束、原子状态提交和外部对账的组合效果。**

1. 先定义“Once”的边界：是任务、Step，还是付款、发信等副作用一次。Task ID标识执行实例，Attempt ID标识尝试，稳定Idempotency Key标识业务意图；重试可产生新Attempt，但不能产生第二次有效副作用。

2. 数据库内将幂等记录、业务更新和结果引用放入同一事务，以唯一约束抵抗并发；消息链路采用Outbox、至少一次投递和Inbox去重。**消息系统的Exactly-Once不等于外部副作用Exactly-Once**，第三方API通常不参与该事务。

| 层级 | 主要机制 | 保障目标 |
| --- | --- | --- |
| 存储层 | 事务、唯一约束 | 单库原子提交 |
| 消息层 | Outbox、Inbox | 重复投递不重复消费 |
| 工具层 | 下游幂等键、状态查询 | 外部动作去重 |
| 业务层 | 对账、补偿 | 异常状态最终收敛 |

3. 外部调用超时后进入UNKNOWN，先按业务键查询；未执行才重试，已执行则补写回执。下游不支持幂等或查询时，只能通过预登记、补偿和对账逼近业务语义恰好一次，不能绝对承诺。测试覆盖重复消息、响应丢失、进程崩溃与网络分区，并以重复副作用率验收。

**相关知识点：** Exactly-Once语义、At-Least-Once、Idempotency Key、Attempt ID、唯一约束、Outbox、Inbox、状态未知、补偿、对账。

### PLAN-273 · Event Sourcing 如何帮助实现幂等性？

> 稳定 ID：`PLAN-273`｜原题号：273

**Event Sourcing通过不可变事件、唯一事件标识和版本化追加，使重复命令可以被识别、状态可以重建，但幂等性仍需命令端与投影端共同实现。**

1. 业务命令携带Command ID，聚合处理后生成具有Event ID和Aggregate Version的事件。事件存储对标识建立唯一约束并按期望版本追加；同一命令重放时返回既有结果，并发版本冲突则重新加载后决策。

2. 状态由事件序列折叠得到，崩溃后可判断动作是否形成业务事实；Outbox可与事件追加原子提交。**事件不可变不等于消费天然幂等**：投影、通知和外部工具仍可能重复接收事件，必须按Event ID去重。

| 机制 | 对幂等性的贡献 | 不能解决 |
| --- | --- | --- |
| Command ID | 去重业务意图 | 投影重复消费 |
| Event ID | 去重事件处理 | 外部调用状态未知 |
| Aggregate Version | 防并发覆盖 | 跨聚合原子性 |
| 事件回放 | 重建和审计状态 | 自动撤销副作用 |

3. 投影应在事务内记录已处理Event ID与读模型变化，或用单调Offset保证顺序。回放时隔离邮件、支付等真实副作用，只重建内部状态；重驱外部系统须使用专用流程。还要设计Schema演进、快照校验及去重记录保留期，防止历史重放绕过去重窗口。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** Event Sourcing、Command ID、Event ID、聚合版本、乐观并发、事件存储、投影、Outbox、事件回放、Schema演进。

### PLAN-274 · 为什么Agent系统必须采用异步队列架构？

> 稳定 ID：`PLAN-274`｜原题号：274

**生产级长任务Agent通常需要异步队列解耦请求、调度与执行，但简单低延迟问答并非必须异步，关键取决于任务时长、可靠性和并发需求。**

1. Agent任务可能持续数分钟至数天，包含模型推理、工具调用、限流等待、人工审批和断点恢复，无法依赖一个HTTP连接存活。接入层应快速返回Task ID，由队列缓冲任务并让Worker异步推进，客户端通过轮询、SSE、WebSocket或回调获取状态。

2. 队列吸收流量峰值，支持限速、优先级、延迟重试、负载均衡和Worker水平扩展；消费者崩溃后消息可重新投递。**队列提供的是解耦和至少一次投递，不自动保证任务正确完成**，仍需持久化状态机、Checkpoint、幂等消费、死信与可观测性。

| 架构 | 优势 | 适用场景 |
| --- | --- | --- |
| 同步调用 | 实现简单、即时返回 | 短问答、无副作用 |
| 异步队列 | 削峰、恢复、弹性扩展 | 长任务和批处理 |
| 工作流引擎 | 状态持久、等待与补偿 | 复杂可靠执行 |

3. 设计消息时仅传Task ID、Step ID、版本和上下文引用，避免大Prompt进入队列；按租户或任务设置分区与公平调度，防止热点和饥饿。设置可见性超时、最大重试、退避和DLQ，并监控积压量、最老消息年龄、处理延迟及重复率。对强交互环节可同步流式响应，后台步骤继续异步执行。

**相关知识点：** 异步队列、削峰填谷、Task ID、至少一次投递、Checkpoint、幂等消费、可见性超时、死信队列、公平调度、背压。

| 弹性扩缩容 | 匹配供需 | 利用率、扩容延迟 |

**相关知识点：** 分区队列、无状态调度、加权公平队列、优先级老化、租约、Checkpoint、多级限流、背压、弹性扩缩容、分区倾斜。

### PLAN-277 · 多Agent协作场景如何避免任务堆积？

> 稳定 ID：`PLAN-277`｜原题号：277

**多Agent协作避免任务堆积的关键是限制任务生成速率、实施端到端背压，并按关键路径和资源瓶颈调度，而非无限增加Worker。**

1. Orchestrator为每个父任务设置最大子任务数、最大扇出、并行度、队列长度、Token和费用预算；Agent创建子任务前必须经过准入控制。对语义相同的任务按规范化目标与输入指纹合并，避免多个Agent重复检索、分析或调用同一工具。

2. 队列按角色、租户和资源类型隔离，使用有界队列、信号量与令牌桶把下游容量反向传递给上游。调度优先处理能解除最多依赖的关键路径节点，并采用公平队列与优先级老化。**扩容只对可并行且下游尚有配额的瓶颈有效**。

| --- | --- | --- |
| 有界队列 | 限制在途任务 | 内存和延迟失控 |
| 背压 | 抑制上游生产 | 越忙越生成 |
| 任务合并 | 消除重复工作 | 协作冗余 |
| 关键路径调度 | 优先解除依赖 | 下游空等 |

3. 当最老任务年龄或预计等待时间超过SLO时，依次暂停非关键扇出、批量合并调用、降级模型、延迟低优先级任务并拒绝新任务；同时防止失败重试形成二次洪峰。监控到达率、完成率、队列年龄、在途数量、Agent空闲等待和依赖阻塞时间，以Little定律定位是生产过快、服务过慢还是依赖失衡。

**相关知识点：** 多Agent编排、有界队列、背压、任务扇出、准入控制、任务去重、关键路径、公平调度、Little定律、重试风暴。

### PLAN-283 · 如何解决任务饥饿问题？

> 稳定 ID：`PLAN-283`｜原题号：283

**避免饥饿可采用优先级老化、加权公平队列、每租户最小资源份额和最大连续执行配额。**

1. 先区分饥饿与正常排队：任务在系统仍有处理能力时长期得不到服务，通常源于持续高优流量、短任务偏置、租户垄断或所需资源稀缺。应设置最大等待时间和“在该优先级下的理论服务份额”，以指标判断，而不是只看队列长度。

2. 优先级老化随等待时间提高有效优先级；加权公平队列或Deficit Round Robin为租户、队列分配稳定份额；每个等级保留最小执行槽，并限制同一租户连续占用次数。**高优先级影响服务顺序，但不应永久取消低优先级的可达性**。

| 机制 | 作用 | 代价 |
| --- | --- | --- |
| 优先级老化 | 等待越久越优先 | 可能影响高优SLA |
| 最小资源份额 | 保证持续进展 | 峰值利用率略降 |
| 公平队列 | 隔离租户竞争 | 参数配置复杂 |
| 协作式抢占 | 释放稀缺资源 | 要求安全Checkpoint |

3. 对持有GPU、连接或锁的长任务设置时间片、租约和安全Checkpoint，允许到达边界后让出资源；无法满足所需能力的任务应标记资源不可用并升级，而非无限等待。监控最大与P99等待时间、各等级服务份额、零进展任务数及抢占失败率，使用持续高优流量和稀缺资源场景验证调度器。

**相关知识点：** 任务饥饿、优先级老化、加权公平队列、Deficit Round Robin、最小资源份额、时间片、协作式抢占、Checkpoint。

### PLAN-284 · 长任务和短任务如何隔离？

> 稳定 ID：`PLAN-284`｜原题号：284

**长短任务应在队列、Worker池、并发配额和SLO上隔离，防止长任务占满执行槽形成队头阻塞，同时保留可控的资源借用。**

1. 入队前根据历史分位数、任务类型、预计Token、工具次数和输入规模估算服务时间，将交互式短任务与批量长任务路由到不同逻辑队列。估算不确定时采用多级反馈队列：任务消耗完时间片仍未完成，则逐步降到长任务队列。

2. 短任务池配置较高优先级、较短超时和严格尾延迟SLO；长任务池配置较长租约、Checkpoint、暂停恢复及成本预算。两者分别限制并发、连接和模型配额，必要时部署独立Worker。**仅分队列而共享无上限资源池，仍会发生资源争用**。

| 维度 | 短任务 | 长任务 |
| --- | --- | --- |
| 核心目标 | 低尾延迟 | 吞吐与可恢复 |
| 调度方式 | 优先、短时间片 | 分片、可暂停 |
| 状态策略 | 轻量持久化 | 频繁Checkpoint |
| 资源配额 | 预留最小容量 | 限制最大占用 |

3. 允许空闲容量跨池借用，但本池需求恢复时应通过新任务不再借出或在安全点协作式抢占来回收，不能强杀有副作用的步骤。监控各类到达率、服务时间、排队P95、队头阻塞和资源份额，定期根据真实耗时校准分类器；误分类的超长任务应迁移队列，而不是持续占用短任务槽。

**相关知识点：** 长短任务隔离、队头阻塞、多级反馈队列、服务时间估计、资源池隔离、时间片、Checkpoint、协作式抢占、尾延迟。

### PLAN-287 · OpenAI接口限流后如何处理？

> 稳定 ID：`PLAN-287`｜原题号：287

**OpenAI接口出现限流后，应识别触发的请求或Token配额，采用带随机抖动的指数退避和有限重试，同时从入口降低发送速率。**

1. 捕获429与RateLimitError，记录模型、项目、请求Token估算、并发、错误信息和请求标识，判断是RPM、TPM、并发或可用额度问题。鉴权、参数错误不能按限流重试；持续429还需检查项目用量、配额层级和组织配置，而不是无限等待。

2. 官方建议使用随机指数退避：首次短暂等待，失败后逐步增大延迟并加入Jitter，设置最大次数和总时限。**失败请求也会计入每分钟限额，立即连续重发只会加重限流**。多个Worker应共享限流状态，避免各自重试形成同步洪峰。

| 场景 | 处理方式 | 禁止做法 |
| --- | --- | --- |
| 短暂429 | 指数退避加抖动 | 立即循环重试 |
| RPM受限 | 降低请求频率或批处理 | 仅缩短Prompt |
| TPM受限 | 压缩上下文、限制输出 | 只减少请求数 |
| 持续超限 | 排队、降级或申请更高额度 | 无上限重试 |

3. 调用前用共享令牌桶预留RPM和预计TPM，实际返回后校正余额；队列按租户公平调度，并设置最大等待时间。可延迟任务进入异步队列，低价值任务可降级模型或缩减上下文，但需重新验证质量。监控429率、重试成功率、额外Token消耗和P95等待时间，防止恢复后瞬间放量。

**相关知识点：** OpenAI RateLimitError、HTTP 429、RPM、TPM、指数退避、随机抖动、令牌桶、重试风暴、上下文压缩、配额治理。

### PLAN-288 · 模型服务过载时有哪些降级方案？

> 稳定 ID：`PLAN-288`｜原题号：288

**过载时按顺序启用并发收缩、排队与背压、小模型或低推理档位、缩短上下文、关闭非关键反思、返回缓存结果和拒绝低优请求。**

1. 先用超时率、429/5xx、P95延迟、队列年龄和GPU利用率确认过载，再按任务风险与SLO分级。交互请求优先保障尾延迟，批处理允许排队；支付、权限变更等高风险任务只能延迟或转人工，不能为了吞吐降低安全校验。

2. 第一层收紧自适应并发、入口限流并通过有界队列背压，防止重试风暴；第二层减少非关键调用，如压缩上下文、降低最大输出、关闭额外采样与反思；第三层切换经过评测的小模型、缓存或规则结果。**任何模型降级都必须满足任务能力与质量阈值**。

| 降级方式 | 收益 | 主要风险 |
| --- | --- | --- |
| 排队与背压 | 保护服务稳定 | 等待时间增加 |
| 缩短上下文/输出 | 减少Token消耗 | 信息或答案不完整 |
| 小模型或低档位 | 降低成本与延迟 | 质量下降 |
| 缓存或规则结果 | 快速返回 | 时效性和覆盖有限 |

3. 容量仍不足时暂停后台任务、拒绝低优先级请求并返回明确可重试状态，不能让所有请求超时。降级策略需版本化、灰度、设触发与恢复迟滞，并标记响应的质量级别；恢复时逐步放量，避免瞬时回潮。监控降级命中率、任务成功率、质量回归、用户重试率和节省Token，以评估真实收益。

**相关知识点：** 过载保护、背压、自适应并发、模型降级、上下文压缩、缓存、质量门禁、负载脱落、恢复迟滞、重试风暴。

### PLAN-291 · Worker宕机后任务如何恢复？

> 稳定 ID：`PLAN-291`｜原题号：291

**Worker宕机后应依靠租约过期触发接管，由新Worker从持久化Checkpoint恢复，并先确认运行中副作用的真实状态再继续。**

1. Worker领取任务时获得Lease ID并持续心跳，状态保存Owner、期限与Fencing Token。心跳中断后不能立即并发接管；应等租约失效，再以CAS转移所有权，旧Worker的迟到写入由Token拒绝。

2. 新Worker加载Task、Step、Attempt、计划、上下文、输入输出引用、预算、幂等键和工具回执，重建就绪节点。**SUCCEEDED直接复用，纯计算RUNNING可重算，有副作用的RUNNING或UNKNOWN必须先查询外部系统**。

| 节点状态 | 恢复动作 | 安全条件 |
| --- | --- | --- |
| SUCCEEDED | 跳过并复用 | 回执和输出完整 |
| PENDING | 重新调度 | 依赖已满足 |
| RUNNING | 按类型查证或重算 | 原租约已失效 |
| UNKNOWN | 查询、补偿或人工处理 | 禁止盲目重试 |

3. 恢复前校验权限及模型、Prompt、工具Schema版本，失效时迁移或转人工。消息会重复投递，因此Step与外部调用必须幂等；重试沿用业务键但创建新Attempt ID。通过进程强杀、长暂停、网络分区及响应丢失测试，验证只形成一次有效副作用。

**相关知识点：** Worker恢复、租约、心跳、Fencing Token、CAS、Checkpoint、状态未知、幂等恢复、Attempt ID、故障接管、网络分区。

### PLAN-292 · 如何保证任务至少执行一次（At-Least-Once）？

> 稳定 ID：`PLAN-292`｜原题号：292

**At-Least-Once通过消息持久化、消费确认、可见性超时和失败重投保证任务不会静默丢失，代价是可能重复。**

1. 生产端在业务事务中写Outbox，由Relay发送直至收到Broker确认；Broker启用持久化、复制和足够保留期。消息包含Task ID、Step ID与Event ID。只有调用返回成功而没有持久化交付证据，不能证明任务进入可靠链路。

2. Worker领取后消息进入不可见或未确认状态，定期续租；任务业务状态与Checkpoint成功提交后才ACK或提交Offset。Worker崩溃、租约到期或确认丢失时，Broker重新投递。**确认必须晚于业务提交，否则会形成已确认但未执行的永久缺口**。

| 环节 | 保障机制 | 失败后的动作 |
| --- | --- | --- |
| 生产 | Outbox、Broker确认 | 重发原消息 |
| 存储 | 持久化、多副本 | 副本恢复 |
| 消费 | 晚确认、可见性超时 | 重新投递 |
| 业务 | 幂等键、唯一约束 | 吸收重复 |

3. 提交成功后ACK可能丢失，因此重复不可避免；消费者以Idempotency Key、Inbox和唯一约束原子去重，外部工具继续透传该键。永久失败进入DLQ并告警，必须有修复与受控重放流程，不能视为已完成。定期对账Outbox、Broker水位和业务终态，并以宕机及网络分区测试验证。

**相关知识点：** At-Least-Once、事务发件箱、Broker确认、晚确认、可见性超时、消息重投、Inbox、幂等消费、死信队列、对账。

### PLAN-293 · 如何保证任务恰好执行一次（Exactly-Once）？

> 稳定 ID：`PLAN-293`｜原题号：293

**分布式Agent难以保证物理执行仅发生一次，工程上应保证同一业务意图即使被重复调度，也只产生一次可观察的有效提交。**

1. 先定义Exactly-Once的业务边界与唯一键，如租户、操作、对象ID和版本。Task ID表示任务实例，Attempt ID表示尝试，Idempotency Key表示业务意图；重试可创建多个Attempt，但必须共享幂等键并返回同一结果。

2. 单库内将幂等记录、状态迁移和副作用放入同一事务，以唯一约束解决并发。消息采用至少一次投递与Inbox去重，跨消息和数据库使用Outbox。**分布式锁只能减少并发，锁过期后旧Worker仍可能写入，不能作为最终保证**。

| 层级 | 关键机制 | 达成效果 |
| --- | --- | --- |
| 调度层 | 租约、Fencing Token | 单一有效Worker |
| 存储层 | 事务、唯一约束 | 单次业务提交 |
| 消息层 | Inbox、Outbox | 重投不重复处理 |
| 工具层 | 幂等键、状态查询 | 外部副作用去重 |

3. 外部调用超时后进入UNKNOWN，先按业务键查询；已成功则补写回执，明确未执行才重试。下游无幂等接口且不能查询时，无法严格承诺Exactly-Once，只能以预登记、补偿和对账降低重复。通过重复消息、提交后崩溃、租约过期与网络分区测试，以重复副作用率验收。

**相关知识点：** Exactly-Once语义、业务幂等、Task ID、Attempt ID、唯一约束、Inbox、Outbox、Fencing Token、状态未知、补偿与对账。

### PLAN-296 · 如何实现Agent平台的弹性扩缩容？

> 稳定 ID：`PLAN-296`｜原题号：296

**Agent平台应按接入、编排、CPU Worker、GPU推理和外部工具分别扩缩容，并以队列需求和SLO预测容量，而不是只看CPU利用率。**

1. 接入与无状态编排器可按QPS、并发和延迟水平扩展；Worker按队列长度、最老任务年龄、到达率与平均服务时间计算所需副本；GPU池还要观察显存、Token吞吐、模型驻留和批处理效率。不同资源池独立伸缩，避免一个平均指标掩盖局部瓶颈。

2. 扩容策略结合反应式与预测式控制：突发时按队列SLO快速扩容，周期流量提前预热模型和实例；设置最小、最大副本、冷却时间与迟滞区间。**扩容必须受下游RPM、TPM和数据库容量约束**，否则增加Worker只会扩大429与重试风暴。

| 资源层 | 主要伸缩信号 | 特殊约束 |
| --- | --- | --- |
| API/编排器 | QPS、延迟、并发 | 保持无状态 |
| CPU Worker | 队列年龄、服务时间 | 租约与幂等 |
| GPU推理 | 显存、TPS、批效率 | 预热和模型驻留 |
| 工具调用池 | 429、连接与配额 | 下游限额 |

3. 缩容前停止领取新任务，让运行中步骤到Checkpoint后排空，再释放租约；有副作用的调用不能强杀。保留暖池减少冷启动，低峰期再逐步缩容。监控扩容启动时间、SLO违约、空闲成本、队列清空时间和缩容中断率，并用流量突增、节点故障与下游限流场景验证伸缩策略。

**相关知识点：** 弹性扩缩容、队列驱动伸缩、预测式扩容、冷却时间、迟滞、模型预热、暖池、优雅缩容、Checkpoint、下游配额。

### PLAN-297 · 高峰流量突然增长10倍时系统如何自适应处理？

> 稳定 ID：`PLAN-297`｜原题号：297

**系统先由队列吸收突发并触发背压，再依据排队时长和资源利用率快速扩容Worker；同时收紧租户配额、启用缓存和模型降级。**

1. 入口先鉴权、去重并按全局、租户、用户执行令牌桶限流；有界队列只吸收可控突发，超过最大等待时间则返回Retry-After或转异步。优先保障高价值交互与安全任务，暂停离线批处理，防止十倍流量直接传播到模型、数据库和外部工具。

2. 根据到达率、最老任务年龄、平均服务时间和启动延迟预测副本需求，快速扩展无状态接入与Worker，并预热模型；但必须受GPU、RPM、TPM和数据库连接容量约束。**扩容下游没有余量的Worker只会放大429、超时和重试风暴**。

| 阶段 | 主要动作 | 目标 |
| --- | --- | --- |
| 数秒内 | 限流、背压、隔离 | 阻止级联故障 |
| 数分钟内 | 扩容、预热、批处理 | 提高有效容量 |
| 持续过载 | 降级、负载脱落 | 保住核心SLO |
| 恢复阶段 | 渐进放量、清理积压 | 防止二次冲击 |

3. 容量仍不足时命中缓存、压缩上下文、关闭非关键反思、切换经评测的小模型，并明确标注降级；高风险任务不得降低验证标准。恢复时设置迟滞与冷却，逐步开放流量并优先清理临近截止任务。监控丢弃率、队列P95、SLO、429、成本和公平份额，事后用峰值回放校准预案。

**相关知识点：** 流量突增、背压、有界队列、负载脱落、弹性扩容、模型预热、重试风暴、服务降级、Retry-After、恢复迟滞。

### PLAN-298 · taskKey应该由哪些字段组成？

> 稳定 ID：`PLAN-298`｜原题号：298

**taskKey应稳定标识一次业务任务意图，通常由租户、任务类型、业务对象、规范化输入版本和必要时间域组成，而不是使用随机Task ID。**

1. 推荐结构为tenantId + namespace + taskType + objectId + operationVersion + inputDigest；周期任务加入timeWindow或batchId。哈希前统一大小写、Unicode、时间和JSON键顺序。

2. 不应纳入请求时间、随机数、Attempt ID、链路ID等易变字段，也不能只用标题或自然语言摘要。**taskKey表示业务等价性，Task ID表示执行实例，Attempt ID表示一次尝试**。

| 字段 | 是否常用 | 作用 |
| --- | --- | --- |
| tenantId/namespace | 必需 | 隔离键空间 |
| taskType/objectId | 必需 | 标识操作对象 |
| operationVersion | 建议 | 区分语义版本 |
| inputDigest | 按需 | 校验关键参数 |
| timeWindow/batchId | 周期任务 | 区分合法批次 |

3. 数据库存储组成字段、参数摘要和哈希，并建立唯一约束；相同taskKey但摘要不同应返回冲突，不得复用旧结果。保留期覆盖重试与重放窗口，隐私内容只存摘要。以并发、版本升级和周期边界样本验证误合并与漏合并率。

**相关知识点：** taskKey、业务幂等键、Task ID、Attempt ID、输入规范化、哈希摘要、命名空间、唯一约束、时间窗口、键冲突。

### PLAN-300 · Redis分布式锁失效会带来什么问题？

> 稳定 ID：`PLAN-300`｜原题号：300

**Redis分布式锁失效会使多个Worker同时认为自己持有执行权，导致重复副作用、旧状态覆盖、额度超扣和任务状态机错乱。**

1. 常见原因包括TTL短于执行时间、续租因长暂停或网络故障失败、主从切换丢失未复制的锁，以及释放时未校验Owner Token。锁过期后新Worker进入，而旧Worker恢复后继续写，形成僵尸持有者。

2. 后果不只是“执行两次”：两个Planner可能产生不同计划，工具重复调用，旧Attempt覆盖新状态，锁误删后第三个Worker也能进入。**互斥锁不能阻止已过期持有者提交写入**，因此不能作为唯一防线。

| 失效场景 | 直接风险 | 防护 |
| --- | --- | --- |
| TTL过期 | 并发进入临界区 | 续租、合理租期 |
| 主从切换 | 多持有者 | 评估一致性模型 |
| 误释放他人锁 | 互斥失效 | 随机Token原子校验 |
| 旧持有者恢复 | 迟到写覆盖 | Fencing Token |

3. 获取锁使用原子SET NX PX，释放与续租须校验随机Token；每次获取分配递增Fencing Token，由资源端拒绝旧Token。同时以CAS、唯一约束和Idempotency Key保护写入，外部副作用前后查询状态。测试覆盖长暂停、网络分区和故障切换，并监控续租失败与重复执行率。

**相关知识点：** Redis分布式锁、SET NX PX、锁续租、Owner Token、Fencing Token、僵尸持有者、主从切换、CAS、唯一约束、幂等副作用。

### PLAN-301 · 如何避免锁过期后任务被重复执行？

> 稳定 ID：`PLAN-301`｜原题号：301

**锁过期后旧Worker可能仍在运行，新Worker又取得锁，形成双执行。**

1. 将锁设计为有Owner、Lease ID和TTL的租约，Worker仅在仍持有时续期；租期依据P99步骤耗时设置。长任务拆成可提交Step，完成后写Checkpoint，避免一把锁覆盖整个生命周期。

2. 每次获取租约生成单调递增Fencing Token，所有状态写入携带Token，数据库以CAS或条件更新拒绝小于当前版本的提交。**续租只能降低过期概率，Fencing Token才负责阻止旧Worker恢复后的迟到写入**；资源端不校验Token时仍需唯一约束兜底。

| 机制 | 解决问题 | 局限 |
| --- | --- | --- |
| 租约续期 | 减少正常任务误过期 | 无法阻止长暂停 |
| Fencing Token | 拒绝过期持有者写入 | 资源端须配合 |
| CAS状态迁移 | 防止旧状态覆盖 | 只保护该存储 |
| 幂等键 | 去重业务副作用 | 需稳定业务语义 |

3. 工具调用使用稳定Idempotency Key；超时或接管后先查外部状态，未执行才重试。旧Worker续租失败后应停止领取新Step，但不能依赖其自觉退出。测试模拟长暂停、网络分区、续租丢失和主从切换，验证旧Token无法写入、重复Attempt只返回同一结果。

**相关知识点：** 租约、TTL、Lease ID、Fencing Token、CAS、Checkpoint、僵尸Worker、Idempotency Key、状态查询、迟到写入。

### PLAN-302 · RUNNING状态任务长时间不结束怎么处理？

> 稳定 ID：`PLAN-302`｜原题号：302

**RUNNING任务需要心跳、租约到期时间和步骤级Deadline。**

1. 状态中保存Owner、Lease ID、最后心跳、当前Step、开始时间、Deadline、进度和最近工具调用。监控同时判断心跳超时、无进展时长与总执行时长；长任务只要持续产生可信进度，不应因固定墙钟阈值被误杀。

2. 超时后先分类：Worker失联则等待租约过期并接管；工具仍运行则查询或取消工具；模型调用卡住则按超时策略重试；业务死锁或计划循环则停止并诊断；状态回写失败则依据外部回执补写。**RUNNING超时是状态未知，不等于任务失败**。

| 原因 | 识别信号 | 处理 |
| --- | --- | --- |
| Worker失联 | 心跳和租约过期 | 新Worker接管 |
| 工具执行慢 | 有远端运行记录 | 等待、查询或取消 |
| 计划死循环 | 重复动作且无新证据 | 终止或Replan |
| 回写失败 | 外部成功但本地未完成 | 补写回执 |

3. 接管时使用Fencing Token阻止旧Worker迟到提交，并从Checkpoint恢复；有副作用的UNKNOWN步骤先按幂等键查证，不能盲目重试。设置软超时触发告警与诊断，硬超时触发取消或人工升级，同时限制最大运行时间和费用。监控RUNNING年龄分布、无进展任务数、误接管率和重复副作用率。

**相关知识点：** RUNNING超时、心跳、租约、Deadline、进度检测、状态未知、Fencing Token、Checkpoint、任务接管、软硬超时、Replan。

### PLAN-303 · Agent中间步骤失败后如何保证不重复执行副作用操作？

> 稳定 ID：`PLAN-303`｜原题号：303

**中间步骤失败后，应通过副作用写前登记、稳定幂等键、执行回执和恢复查证，确保重试复用既有结果而不重复改变外部状态。**

1. 为副作用Step生成由Task业务键、Step版本和目标对象组成的Idempotency Key。调用前以唯一约束写入PENDING、参数摘要和Attempt ID；重复进入时读取原记录，相同键但参数不同则报冲突。

2. 调用下游时透传幂等键，成功后保存对象ID和回执，再将Step置为SUCCEEDED。若响应前崩溃或超时，记为UNKNOWN。**UNKNOWN不能直接重放，必须先通过查询接口或业务唯一键确认是否生效**。

| 状态 | 恢复动作 | 是否可重试 |
| --- | --- | --- |
| PENDING | 判断是否已发起 | 满足条件后 |
| SUCCEEDED | 复用结果 | 否 |
| FAILED且无副作用 | 修复后重试 | 是 |
| UNKNOWN | 查询、对账或人工处理 | 未确认前否 |

3. 后续失败时只重试失败节点及下游，SUCCEEDED副作用节点从Checkpoint复用；撤销时执行Saga补偿，不能再运行原动作。下游不支持幂等或查询时，采用Outbox、预登记、延迟复查和人工对账。故障注入覆盖提交后崩溃、响应丢失和重复消息。

**相关知识点：** 副作用治理、写前登记、Idempotency Key、参数摘要、Tool Receipt、UNKNOWN状态、Checkpoint、局部重试、Saga补偿、对账。

### PLAN-304 · 幂等机制放在网关层、调度层还是执行层？

> 稳定 ID：`PLAN-304`｜原题号：304

**幂等机制不应三选一，而应让同一业务键贯穿网关、调度和执行层，并由最接近业务副作用的存储承担最终去重。**

1. 网关层校验Idempotency Key格式、租户作用域和请求摘要，短路客户端重复提交：命中成功返回原Task ID与结果引用，命中处理中返回同一状态句柄。但网关缓存会过期，也看不到内部重试，因此只能减少入口重复，不能保证业务结果。

2. 调度层以Task、Step和Attempt模型吸收重复消息，使用唯一约束、租约和CAS避免同一Step产生多个有效状态迁移。执行层为每个副作用动作派生稳定子键，写前登记并向下游透传。**执行层最了解业务语义，因此必须承担最后一道去重责任**。

| 层级 | 幂等职责 | 无法单独解决 |
| --- | --- | --- |
| 网关层 | 去重外部重复请求 | 内部重试 |
| 调度层 | 去重任务与Step调度 | 下游真实副作用 |
| 执行层 | 去重工具和业务写入 | 跨系统状态未知 |
| 对账层 | 发现并修复异常 | 实时阻止重复 |

3. 各层保存键、参数摘要、状态、结果引用和保留期；相同键参数不同必须报冲突。调用超时进入UNKNOWN并先查询外部状态，不能依靠上层认为失败而重放。指标应能关联入口键、Task ID、Step ID和Attempt ID，并通过客户端重试、消息重复及Worker接管测试验证端到端仅有一次有效副作用。

**相关知识点：** 分层幂等、Idempotency Key、请求摘要、Task ID、Step ID、Attempt ID、唯一约束、CAS、写前登记、状态未知、对账。

### PLAN-307 · 如何设计任务重试和补偿机制？

> 稳定 ID：`PLAN-307`｜原题号：307

**任务重试处理尚未完成的可恢复失败，补偿修复已经提交的业务副作用；二者必须基于错误分类、幂等状态和明确预算协同设计。**

1. 统一错误模型至少区分瞬时故障、限流、参数错误、权限错误、业务冲突、状态未知和计划失效。网络抖动、过载可重试；参数错误先修复；权限和合规错误停止；UNKNOWN先查询外部状态。**只有重复执行安全时才允许Retry**。

2. 每个Step定义最大次数、单次超时、累计时长、费用、退避策略和可重试错误集合；使用随机指数退避并尊重Retry-After，稳定Idempotency Key贯穿重试，新Attempt ID记录每次尝试。相同错误无新证据、熔断开启或预算耗尽时安全终止。

| 机制 | 适用情况 | 核心要求 |
| --- | --- | --- |
| Retry | 瞬时失败且未完成 | 幂等、有限预算 |
| Repair | 参数或格式错误 | 修改后再尝试 |
| Replan | 路径或前提失效 | 保留有效成果 |
| Compensation | 已提交部分副作用 | 独立、可重试、可审计 |

3. 跨系统流程以Saga记录正向步骤与逆序补偿；补偿是新的业务操作，不是数据库回滚，也可能失败，因此需要自己的幂等键、重试与人工升级。不可逆动作应延迟到验证后执行或要求审批。通过失败矩阵注入每个提交边界的崩溃，验证最终业务不变量、无重复副作用和可审计轨迹。

**相关知识点：** Retry、错误分类、状态未知、指数退避、Retry-After、Idempotency Key、Attempt ID、Saga、补偿事务、业务不变量、故障注入。
