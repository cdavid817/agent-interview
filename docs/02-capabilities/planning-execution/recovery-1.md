### PLAN-005 · 如何设计Agent规划器，避免频繁重新规划？（千问二面）

> 稳定 ID：`PLAN-005`｜原题号：5

**避免频繁重新规划的关键，是提高初始计划稳定性，并把执行故障、动作错误与计划失效分层处理。**

1. 初始计划必须包含目标、节点输入输出、依赖、成功标准、预算、风险假设和备用路径。生成后由Plan Validator检查遗漏任务、循环依赖、工具可用性、权限和资源约束，从源头减少因计划质量不足造成的重复规划。

2. 执行阶段先进行**失败分类**：网络抖动、限流和暂时性超时属于执行故障；Schema或参数错误属于动作错误；关键前提失效、依赖改变、工具能力不足或目标不可达才属于计划失效。前两类不能直接触发Planner。

| 恢复机制 | 适用情况 | 计划变化 |
| --- | --- | --- |
| Retry | 瞬时故障 | 不变 |
| Repair | 参数或格式错误 | 仅修改动作 |
| Local Replan | 单个路径失效 | 修改局部DAG |
| Global Replan | 目标或核心约束变化 | 重建整体计划 |

3. 重规划时优先替换失败节点及其下游，保留已成功且仍有效的结果。RePlanner必须接收错误证据、已尝试方案、外部状态和剩余预算，禁止忽略执行历史重新生成相同路径；稳定流程还可使用计划模板或历史成功计划缓存。

4. 设置**计划版本、触发阈值、错误指纹、冷却窗口、最大重规划次数和成本上限**。冷却期内不重复触发；连续计划无实质差异或没有新增证据时，应停止自动规划并进入降级或人工处理。

**相关知识点：** Plan Validator、Failure Classification、Local Replan、计划缓存、冷却窗口、规划预算。

### PLAN-006 · Agent在执行任务过程中，如何判断当前步骤是否成功？失败后如何重试、回滚或重新规划？（DeepSeek一面）

> 稳定 ID：`PLAN-006`｜原题号：6

**步骤是否成功必须依据预先声明的Success Criteria和外部证据判断；失败后再按根因选择重试、回滚、补偿或重规划。**

1. 每个Step执行前声明输入输出Schema、业务不变量、允许误差、预期状态、禁止副作用和验收方式。代码修改除写入成功外，还要检查编译、测试、变更范围及目标行为。

2. Validator进行**分层验证**：协议层检查异常，结构层校验字段，业务层检查不变量，状态层查询外部系统，目标层判断用户问题是否解决。HTTP 200或模型声称完成都不能单独作为依据。

| 恢复方式 | 适用失败 | 处理边界 |
| --- | --- | --- |
| Retry | 超时、限流、网络抖动 | 原计划不变 |
| Repair | 参数、格式错误 | 修改当前动作 |
| Rollback/补偿 | 已产生副作用 | 恢复业务状态 |
| Replan | 路径或前提失效 | 修改计划 |

3. Failure Analyzer区分瞬时故障、参数错误、权限问题、业务冲突、能力不足和计划失效。瞬时故障采用指数退避；确定性错误不能原样重试；副作用操作重试前必须使用**Idempotency Key**并查询上次结果。

4. 可逆变更使用Rollback，已提交的跨系统操作使用Saga补偿。只有关键假设失效或路径不可达时才局部Replan。验证证据、错误分类、尝试次数和计划版本均写入Trace。

**相关知识点：** Success Criteria、Validator、Failure Analyzer、幂等重试、Rollback、Saga、Local Replan。

### PLAN-011 · Agent反复循环调用同一个工具、重复执行任务，怎么排查根源并优化（Agent初级）

> 稳定 ID：`PLAN-011`｜原题号：11

**工具循环通常不是模型单点问题，而是终止条件、观察回填、状态提交、错误分类或幂等控制共同失效的结果。**

1. 按Trace还原每轮模型输入、tool call ID、参数、工具输出、Validator结果和状态版本。确认结果是否写回上下文、模型是否误读成功状态，以及持久化失败是否让任务停在RUNNING。

2. 检查Prompt和状态机是否定义**Success Criteria**、停止动作、最大步数和失败出口。工具结果非结构化或错误码未标准化时，模型可能把成功识别为失败；Retry与Replan边界不清也会重复调用。

| 根因 | 典型信号 | 优化措施 |
| --- | --- | --- |
| 观察未回填 | 每轮上下文相同 | 结构化Tool Result |
| 终止条件缺失 | 成功后仍调用 | Success Criteria |
| 重试无上限 | 错误指纹重复 | 次数与成本预算 |
| 状态竞争 | 多Worker重复执行 | CAS、租约、幂等键 |

3. Runtime计算**动作指纹**，由工具名、规范化参数和前置状态组成；指纹连续重复时触发循环检测。副作用操作使用Idempotency Key，重试前查询外部状态，避免业务已成功却再次调用。

4. 设置最大轮数、工具调用次数、Token、费用和Deadline。重复错误且无新证据时停止执行，转为换工具、局部Replan或人工介入。监控循环率、重复调用率和幂等命中率。

**相关知识点：** Tool Loop、Execution Trace、动作指纹、Success Criteria、幂等键、循环检测、终止条件。

### PLAN-012 · Agent幂等性怎么设计？（豆包一面）

> 稳定 ID：`PLAN-012`｜原题号：12

**Agent幂等性的核心，是让同一业务意图被重复提交、重试或消费时只产生一次有效副作用，并能返回一致结果。**

1. Task ID标识一次执行实例，用于追踪状态；Idempotency Key标识业务意图，需跨请求、消息重投和Attempt保持稳定。同一幂等键可以对应多次尝试，但只能产生一次有效结果。

2. **Idempotency Key**由租户、用户、操作类型、目标资源、规范化参数和时间窗组成。服务端以唯一索引原子写入请求摘要、任务状态和结果引用；参数不同却复用同一键时必须拒绝。

| 记录状态 | 重复请求处理 | 是否执行 |
| --- | --- | --- |
| PENDING/RUNNING | 返回同一任务句柄 | 否 |
| SUCCEEDED | 返回原结果 | 否 |
| FAILED可重试 | 创建新Attempt | 条件执行 |
| FAILED不可重试 | 返回原错误 | 否 |

3. 幂等控制贯穿网关、队列、Scheduler和Tool Adapter。分布式锁只能减少并发，不能替代**数据库唯一约束、状态条件更新和fencing token**。At-Least-Once投递要求消费端幂等。

4. 邮件、工单等副作用优先使用对方幂等接口；否则采用业务唯一键、调用前登记、调用后查询和周期对账。超时且状态未知时，必须先查外部结果再决定重试。

**相关知识点：** Task ID、Idempotency Key、唯一约束、状态机、fencing token、At-Least-Once、对账。

### PLAN-013 · 多个用户同时触发同一个Agent任务时，如何设计幂等机制，避免任务重复执行？（腾讯一面）

> 稳定 ID：`PLAN-013`｜原题号：13

**并发用户触发同一任务时，应以规范化业务意图生成全局Task Key，通过原子去重和共享执行避免重复计算，同时保持权限隔离。**

1. Task Key由租户、操作类型、目标资源、规范化参数、数据版本和时间窗组成。结果允许跨用户共享时可去掉User ID；涉及私有数据或个性化权限时必须纳入用户维度。

2. 网关以数据库唯一索引或Redis原子脚本创建记录。首个请求成为Owner并入队，其余请求作为Follower绑定同一Task ID，订阅状态和结果，形成**Singleflight**；禁止先查询再插入。

| 任务状态 | 后续请求处理 | 是否新建执行 |
| --- | --- | --- |
| PENDING/RUNNING | 返回原Task ID并订阅 | 否 |
| SUCCEEDED | 返回缓存结果 | 否 |
| FAILED可重试 | 创建新Attempt | 条件执行 |
| 已过有效期 | 生成新任务 | 是 |

3. Scheduler使用CAS、租约和fencing token防止多个Worker成为Owner；Tool Adapter继续传递**Idempotency Key**，因为调度去重不能防止外部副作用重复。超时后先查询外部状态再重试。

4. 共享执行不等于共享权限。结果返回前按请求者鉴权和字段过滤，缓存按租户隔离，并记录Owner与Follower。监控Task Key冲突率、去重命中率和重复副作用率。

**相关知识点：** Task Key、Singleflight、CAS、fencing token、Idempotency Key、租户隔离、权限复核。

### PLAN-015 · Agent任务分布式调度，海量异步任务如何分片、负载均衡，如何避免分布式重复任务、死任务堆积（Agent高级）

> 稳定 ID：`PLAN-015`｜原题号：15

**海量Agent任务应通过分区队列、资源感知调度、Worker租约和端到端幂等构建可扩展的分布式执行体系。**

1. 分片键由租户、任务类型、目标资源或Task ID哈希组成，兼顾顺序性与热点。在线、离线、GPU及长短任务使用不同队列；热点分区通过虚拟节点或二级分片动态拆分。

2. Scheduler根据**优先级、截止时间、等待时长、GPU需求、Worker负载和租户配额**选择节点。负载均衡还要估算Token、显存和预计时长，采用加权最少负载或资源装箱策略。

| 异常 | 检测依据 | 恢复手段 |
| --- | --- | --- |
| 重复任务 | Task Key冲突 | 唯一约束、幂等消费 |
| Worker宕机 | 心跳和租约过期 | 重新投递 |
| 死任务 | 超过Deadline | 终止、补偿或人工 |
| 队列积压 | 积压年龄超阈值 | 扩容、降级、限流 |

3. Worker通过租约和**fencing token**领取任务，过期Worker不能提交；At-Least-Once消息由Task Key、Idempotency Key和唯一约束吸收重复。外部副作用仍需在Tool Adapter层去重。

4. RUNNING任务设置心跳、Step Deadline和最大时长；超时后先核验外部状态，再接管、补偿或进入DLQ。监控分区倾斜、积压年龄、重复率、死信率和恢复率。

**相关知识点：** 分区队列、资源感知调度、Worker租约、fencing token、幂等消费、DLQ、弹性扩缩容。

### PLAN-022 · 为什么需要 Planner？

> 稳定 ID：`PLAN-022`｜原题号：22

**Planner的价值是把开放目标转化为可调度、可验证、可恢复的执行结构，从而控制长链路任务的不确定性。**

1. LLM直接执行复杂任务容易遗漏约束、重复调用工具，并在局部失败后从头尝试。Planner解析目标、交付物、预算和验收标准，再拆成具有输入输出、依赖、执行器与验证器的节点，使Executor只处理当前动作。

| 机制 | 是否动态决策 | 适用场景 |
| --- | --- | --- |
| Prompt步骤清单 | 弱 | 短且无状态任务 |
| Planner | 强 | 开放目标与动态环境 |
| Workflow | 低 | 路径稳定的标准流程 |
| DAG调度器 | 按既定依赖执行 | 大量并行任务 |

2. 计划应是**结构化执行契约**：节点包含前置条件、参数Schema、产物、超时、重试、风险和完成条件；边表达数据或控制依赖。系统据此并行无依赖节点、阻断条件未满足的动作并定位失败范围。

3. Planner还承担资源与风险治理：根据成本、时限和工具配额选择路径，对高风险节点设置审批，将不可逆操作安排在验证之后。简单问答或固定流程不必动态规划，否则会增加延迟、费用和失败面。

4. 工具不可用、环境变化或结果不达标时，应进行**局部重规划**：保留有效节点，只替换失败节点及其下游；同时限制次数、预算和触发条件，防止计划振荡。评估计划可执行率、依赖正确率、重规划收益、完成率及单位成功成本。

**相关知识点：** 任务分解、Task Spec、DAG、Workflow、Executor、检查点、局部重规划、预算控制。

### PLAN-023 · Planner 如何进行任务拆解？

> 稳定 ID：`PLAN-023`｜原题号：23

**Planner应从验收条件反向推导中间产物，再把产物映射为有依赖、可验证、可恢复的原子任务。**

1. 首先将请求规范化为Task Spec，明确目标、交付物、约束、工具、预算和完成标准。低风险缺失信息可记录假设；会改变方案或产生高影响操作的歧义必须澄清。随后采用**目标反推**，从最终交付物确定中间产物，再推导所需动作。

2. 子任务粒度以“可独立调度、验证、重试和定位失败”为准。节点包含标识、输入输出Schema、执行器、前置条件、超时、重试、风险和验证器；节点间用数据或控制依赖连接，不能只生成自然语言步骤。

| 结构 | 优势 | 适用场景 |
| --- | --- | --- |
| 顺序计划 | 简单、开销低 | 短链路任务 |
| Task Tree | 层次清晰 | 探索与递归分解 |
| DAG | 支持共享依赖和并行 | 多工具复杂任务 |
| Workflow | 稳定、可审计 | 固定业务流程 |

3. 拆解时识别关键路径、并行节点与汇合点。读取任务可并发，写入同一资源应串行或加锁；不可逆节点必须置于验证、备份或审批之后。公共输入应复用，避免重复调用。

4. 执行过程中根据反馈做**局部重规划**：保留已完成且仍有效的节点，只替换失败节点及受影响下游，并更新计划版本。系统还需限制最大深度、节点数、重规划次数和总预算，防止过度拆分或循环规划；最终以依赖正确率、节点成功率、并行收益和端到端完成率评估。

**相关知识点：** Task Spec、目标反推、任务粒度、DAG、关键路径、并发控制、Validator、局部重规划。

### PLAN-027 · Runtime 如何调度 Tool？

> 稳定 ID：`PLAN-027`｜原题号：27

**Runtime应将模型产生的工具意图转化为受权限、Schema、状态和预算约束的可靠调用，而不能让模型直接操作外部系统。**

1. Tool Registry保存**能力描述、输入输出Schema、权限、版本、幂等性、费用和错误码**。Runtime按任务、参数完整度和历史成功率排序候选；执行前由宿主校验参数、授权、资源状态和风险，模型只提出调用意图。

| 机制 | 解决问题 | 不负责什么 |
| --- | --- | --- |
| Function Calling | 生成结构化调用 | 实际执行 |
| MCP | 统一能力发现与交互 | 业务授权 |
| Tool Registry | 管理能力元数据 | 执行编排 |
| Runtime | 调度、隔离与状态管理 | 定义业务目标 |

2. 调度器生成调用ID和幂等键，设置超时、并发上限与重试预算。无依赖只读调用可并行；写入同一资源需串行或加锁。长任务采用异步队列和租约，持久化结果以便恢复。

3. 返回后必须验证**业务效果**，HTTP 200只代表协议成功。网络错误退避重试；参数错误进入修复；权限错误停止；能力不匹配则重选工具；外部写入部分成功时执行补偿或转人工，不能统一重试。

4. Runtime记录选择依据、参数摘要、版本、耗时、费用、结果与副作用。通过候选裁剪和缓存控成本，以凭证隔离、最小权限和审计保障安全。指标包括调用成功率、业务成功率、重复副作用率、P95延迟及单位成本。

**相关知识点：** Tool Registry、Function Calling、MCP、幂等键、异步调度、权限隔离、结果验证、补偿机制。

### PLAN-028 · Runtime 如何支持异步任务？

> 稳定 ID：`PLAN-028`｜原题号：28

**Runtime支持异步任务的核心是将执行状态持久化，并用队列、租约和事件机制解耦任务提交、实际执行与结果消费。**

1. 运行时建立Task、Step、Attempt三级状态机，覆盖等待、运行、成功、失败、取消和超时。迁移携带版本号并持久化，通过**乐观锁**防止Worker重复提交。

| 组件 | 主要职责 | 核心状态 |
| --- | --- | --- |
| 消息队列 | 分发任务 | 偏移量、确认 |
| Scheduler | 配额调度 | Ready、Running |
| State Store | 保存进度 | 版本、Checkpoint |
| Event Bus | 推送结果 | 序号、游标 |

2. Scheduler投递就绪步骤，Worker领取租约并续期；异常退出后由其他Worker接管。队列通常至少投递一次，因此工具调用须用幂等键，结果也要去重。大结果写入对象存储，状态库只存引用。

3. Runtime统一控制超时、重试、熔断、背压和并发配额。瞬时故障退避重试，参数错误立即失败；队列积压时降低并发。取消信号沿父子任务传播，但有副作用的步骤须到安全点或补偿，客户端断线不应取消任务。

4. 流式事件携带Task ID、Attempt ID、序号和游标，支持断线续传与去重。系统记录Trace ID、版本、耗时和成本，并评估排队时延、恢复率、重复执行率和积压量。

**相关知识点：** 状态机、异步队列、Worker租约、幂等、Checkpoint、CancelScope、背压、流式事件。

### PLAN-030 · Runtime 如何实现状态管理？

> 稳定 ID：`PLAN-030`｜原题号：30

**Runtime状态管理应以持久化状态机为核心，确保任务在并发、重试和进程故障下仍能恢复且不会重复产生副作用。**

1. 状态分为Task、Step、Attempt三级：Task表示整体生命周期，Step对应计划节点，Attempt记录每次执行。状态从Pending进入Running，再进入成功、失败、取消或超时；迁移由事件驱动，并通过**状态转移表**拒绝非法跳转。

| 状态类型 | 保存内容 | 推荐存储 |
| --- | --- | --- |
| 控制状态 | 阶段、版本、租约 | 关系库或KV |
| 业务产物 | 中间结果、最终结果 | 对象存储 |
| 对话上下文 | 消息与摘要 | 文档库或关系库 |
| 事件轨迹 | 调度和工具事件 | 日志或事件流 |

2. 状态写入采用版本号或Compare-and-Set，保证Attempt只提交一次终态。Worker领取租约，崩溃后由调度器回收；重试创建新Attempt，不覆盖历史。工具调用配合幂等键，外部写操作使用事务或补偿。

3. 关键节点保存**Checkpoint**，包含计划版本、完成节点、产物引用、剩余预算和上下文摘要。重启后从一致检查点恢复，并验证外部资源；大对象只保存URI与校验和。

4. 状态变化与业务事件采用事务性发件箱或事件溯源，防止数据库已更新但消息未发送。数据需租户隔离、加密、审计和保留周期。评估非法迁移率、重复执行率、恢复率、写入延迟和孤儿任务数。

**相关知识点：** 状态机、Task-Step-Attempt、乐观锁、租约、幂等、Checkpoint、事件溯源、事务性发件箱。

### PLAN-031 · CancelScope 为什么重要？

> 稳定 ID：`PLAN-031`｜原题号：31

**CancelScope为一组并发子任务建立结构化取消边界，使超时、用户终止和父任务失败能够一致传播并完成资源清理。**

1. Agent常并发运行模型、检索、工具和Worker；若只取消外层Future，子任务可能继续耗费资源或修改状态。CancelScope把父子任务绑定到同一生命周期，父级取消时向范围内操作发送信号并等待终态，避免**孤儿任务**。

| 机制 | 作用范围 | 典型用途 |
| --- | --- | --- |
| Timeout | 单个操作或作用域 | 限制最长执行时间 |
| CancelScope | 一组父子任务 | 传播取消与清理 |
| Circuit Breaker | 某类下游调用 | 故障时快速失败 |
| Process Kill | 整个进程 | 最后手段的强制终止 |

2. 取消是协作式控制。Runtime在等待点检查令牌，停止新任务，并关闭流、释放租约、连接和临时文件。数据库提交、支付等原子操作应使用**屏蔽区或安全点**：完成原子段后，再返回已完成、已补偿或需人工处理。

3. 作用域支持层级传播和局部隔离。父级取消通常传播到子级；审计、补偿和状态落库可短暂shield，但要有独立超时。并行竞速可在首个成功后取消其余任务，批量任务则可保留其他分支。

4. 状态库记录取消来源、传播路径、终态与残留副作用。取消接口必须幂等，多次请求只能产生一次迁移。评估取消时延、孤儿任务数、资源泄漏率、副作用率和清理成功率。

**相关知识点：** 结构化并发、CancelScope、取消令牌、Timeout、Shield、安全点、资源清理、幂等取消。

### PLAN-032 · Retry 应该如何设计？

> 稳定 ID：`PLAN-032`｜原题号：32

**Retry必须建立在错误可恢复、操作可安全重放且仍有预算的前提上，不能把所有失败都转化为重复调用。**

1. 先依据错误码、轨迹和外部状态分类。网络抖动、过载和超时属于瞬时故障；参数、权限、业务规则和能力不匹配属于确定性故障。前者可重试，后者须先修复、换工具或终止。

| 策略 | 适用故障 | 核心动作 |
| --- | --- | --- |
| Retry | 超时、限流、网络抖动 | 原动作再次执行 |
| Repair | 参数或格式错误 | 修正输入后执行 |
| Compensation | 已产生外部副作用 | 恢复业务状态 |
| Replan | 路径或前提失效 | 修改后续计划 |

2. 可重试错误采用**指数退避加随机抖动**，并尊重Retry-After，避免惊群。每步设置最大次数、总时长和成本预算；单次超时不能让多次尝试突破整体截止时间。下游持续故障时由熔断器快速失败。

3. 安全重试依赖幂等性。写操作携带Idempotency Key，并通过唯一约束或状态查询确认是否生效；结果未知时不能再次扣款或发布。本地事务使用Rollback，跨系统动作使用Saga补偿，状态不明时转人工。

4. Attempt记录错误指纹、参数摘要、延迟、退避和结果。若错误不变、没有新证据、成功概率低或预算耗尽，应终止。评估重试成功率、放大系数、额外延迟、重复副作用率和熔断命中率。

**相关知识点：** 错误分类、指数退避、随机抖动、Retry-After、幂等键、熔断器、Rollback、Saga。

### PLAN-033 · Workflow 与 Planner 有什么关系？

> 稳定 ID：`PLAN-033`｜原题号：33

**Workflow提供稳定、可审计的控制骨架，Planner负责在开放目标和环境变化中动态补全路径，两者是确定性与适应性的分工。**

1. Workflow预定义节点、依赖、分支、重试和补偿，按状态机推进，适合审批、发布等稳定流程。Planner根据目标和上下文生成或修改计划，适合路径无法提前穷举的任务，但必须受Schema、权限和Validator约束。

| 维度 | Workflow | Planner |
| --- | --- | --- |
| 控制方式 | 预定义流程 | 动态生成计划 |
| 确定性 | 高 | 较低 |
| 变化方式 | 发布时更新 | 运行时重规划 |
| 场景 | 稳定、高风险路径 | 开放复杂任务 |
| 风险 | 僵化 | 漂移、不可执行 |

2. 企业系统常采用**Workflow包裹Planner**。外层固定鉴权、预算、审批、验证和补偿；在信息收集、方案生成等不确定节点内调用Planner。Planner只选白名单工具并输出结构化子图，通过环检测、权限和预算校验后执行。

3. Planner也可选择已有Workflow并填参，而不生成底层步骤。例如选择代码修复或数据分析流程，复用异常处理；只有能力库无法覆盖的部分才临时规划。

4. 执行反馈可触发局部重规划，但不得改写外层控制节点。系统保留版本、变更原因和失败轨迹，并限制重规划次数与成本。评估流程成功率、Planner节点成功率、人工接管率和端到端成本。

**相关知识点：** Workflow、Planner、状态机、结构化计划、能力编排、Validator、局部重规划、版本治理。

### PLAN-035 · 如何设计长任务执行流程？

> 稳定 ID：`PLAN-035`｜原题号：35

**长任务应设计为可持久化、可暂停、可恢复、可重规划的分段执行系统，而不是依赖单次会话持续运行。**

1. 将目标拆成有依赖的里程碑和节点，声明输入输出、完成条件、超时、重试和风险。Runtime维护Task、Step、Attempt状态，只调度依赖满足的节点；等待审批时进入Suspended状态。

| 机制 | 保存内容 | 主要用途 |
| --- | --- | --- |
| Checkpoint | 稳定时刻快照 | 断点恢复 |
| Event Log | 不可变事件序列 | 审计与重建 |
| Heartbeat | Worker存活与进度 | 故障接管 |
| Compensation | 反向业务动作 | 跨系统修复 |

2. 在里程碑、副作用提交后和长等待前写入**Checkpoint**，保存计划版本、节点状态、产物引用、上下文摘要、工具回执、幂等键及预算。大文件存入对象存储；状态更新使用乐观锁。

3. Worker通过租约和心跳执行节点，失联后由调度器接管。暂停时停止领取节点，让写操作到达安全点；恢复时加载快照，验证权限、依赖和外部状态，再决定继续、重试、补偿或局部重规划。写操作须幂等，跨系统部分成功使用Saga补偿。

4. 设置总时限、费用预算、重规划次数、审批点和取消传播。事件日志记录状态、版本、证据和副作用。评估完成率、恢复率、恢复时间、孤儿任务数、重复副作用率和单位成功成本。

**相关知识点：** Durable Execution、Checkpoint、状态机、租约、心跳、幂等、Saga、局部重规划、人工接管。

### PLAN-037 · 如何实现任务恢复？

> 稳定 ID：`PLAN-037`｜原题号：37

**任务恢复应从最近一致检查点重建执行状态，核实外部副作用后仅重新调度未完成且可安全重放的节点。**

1. Runtime先取得租约，冻结旧Worker写权限，再加载Checkpoint与后续Event Log。系统校验Schema、校验和及版本，恢复节点状态、产物引用、上下文、预算和队列；失败时回退检查点。

| 节点状态 | 恢复动作 | 关键校验 |
| --- | --- | --- |
| Succeeded | 保留结果 | 产物与副作用仍有效 |
| Running | 判定为未知 | 租约与外部回执 |
| Failed | 按策略重试 | 错误是否可恢复 |
| Pending | 重新入队 | 前置依赖已满足 |

2. 难点是崩溃前处于Running的节点：本地状态无法判断工具是否完成。应根据**幂等键、事务ID或工具回执**查询外部系统；已生效则补记成功，未生效才重试，部分成功则补偿或转人工。高风险写操作状态不明时禁止重放。

3. 调度前验证权限、工具版本、输入和资源锁。Succeeded节点不动；Pending节点在依赖满足后入队；Failed节点创建新Attempt，不覆盖旧轨迹。计划前提变化时局部重规划。

4. 恢复流程须幂等，使用租约、Fence Token和CAS防止新旧Worker并发。记录来源检查点、状态修正和重放节点。通过故障注入验证崩溃、重复投递和网络分区，评估恢复率、恢复时间、重复副作用率和数据丢失率。

**相关知识点：** Checkpoint、Event Log、Fence Token、CAS、幂等键、故障注入、局部重规划、补偿事务。

### PLAN-054 · 当任务分类错误时，Agent如何进行纠错？

> 稳定 ID：`PLAN-054`｜原题号：54

**任务分类纠错应先阻断错误路径和控制副作用，再依据新证据重新分类、修复状态并恢复后续执行。**

1. 错误可由用户纠正、Validator失败、工具不匹配或权限冲突触发。Runtime立即暂停下游节点，保存计划、原分类、证据和已发生副作用；只读错误可重路由，写操作先确认外部状态，避免扩大影响。

| 错误阶段 | 纠错动作 | 关键保护 |
| --- | --- | --- |
| 执行前 | 重新分类并替换路由 | 清除旧计划 |
| 只读执行中 | 取消错误工具并重试 | 保留有效结果 |
| 可逆写入后 | 回滚再重路由 | 幂等与快照 |
| 跨系统提交后 | Saga补偿或人工处理 | 审计与审批 |

2. 纠错器读取原请求、最新指令、Task State、工具回执和Validator报告，将原因归为指代、标签边界、信息缺失或规则冲突。随后生成Top-K候选和**修正后置信度**；若副作用仍不同，则提出信息增益最高的问题。

3. 新分类确定后创建计划版本，只替换错误节点及下游，仍有效结果继续复用。写入通过幂等键查询是否生效；本地事务可Rollback，跨系统部分成功使用补偿。高风险状态不明时转人工。

4. 记录原标签、新标签、触发信号、根因、副作用与恢复结果。用户纠正可作为候选样本，但须脱敏、去重和审核，不能直接在线学习。评估纠错成功率、发现时延、错误扩散节点数、补偿成功率及完成率。

**相关知识点：** Error Recovery、Task State、Validator、局部重规划、幂等键、Rollback、Saga补偿、反馈学习。

### PLAN-057 · 一个Skill需要包含哪些信息？

> 稳定 ID：`PLAN-057`｜原题号：57

**一个可生产使用的Skill应同时描述能力语义、机器接口、执行依赖、安全边界、失败处理和可验证的成功标准。**

1. 路由元数据包括名称、版本、能力摘要、标签、适用与禁用场景、正反例和负责人。描述应明确“能做什么”和“不能做什么”，避免与其他Skill使用宽泛措辞。

| 信息类别 | 必备字段 | 主要作用 |
| --- | --- | --- |
| 语义 | 描述、场景、标签、示例 | 支持能力匹配 |
| 接口 | 输入输出Schema、默认值 | 保证调用契约 |
| 依赖 | 工具、模型、数据与环境 | 判断是否可执行 |
| 安全 | 权限、敏感数据、副作用 | 限制风险 |
| 运行 | 超时、重试、成本、并发 | 资源治理 |
| 验收 | Validator、成功与失败条件 | 判断业务完成 |

2. 接口采用**结构化Schema**，说明必填字段、类型、约束、输出和错误码；依赖声明工具版本、模型、凭证和环境。若写入外部系统，还需标注幂等性、可逆性、审批和补偿动作，不能只把Prompt当Skill。

3. 执行策略包括前置条件、脚本入口、超时、重试、并发、预算、缓存和取消。失败区分瞬时故障、参数错误、权限错误和业务失败，并定义重试、修复、降级或人工接管。

4. 验收信息包含结果Schema、业务断言、样例、阈值和Validator。还要有变更日志、兼容范围、弃用状态和观测字段。发布前进行兼容、安全与离线评测，线上记录版本、延迟、成本、错误码和成功率。

**相关知识点：** Skill Manifest、能力注册表、JSON Schema、最小权限、幂等、Validator、版本治理、可观测性。

### PLAN-058 · Workflow与Skill之间是什么关系？

> 稳定 ID：`PLAN-058`｜原题号：58

**Skill封装单项可复用能力，Workflow编排能力之间的顺序、条件、状态与异常处理，两者分别解决“做什么”和“如何持续完成”。**

1. Skill暴露输入输出Schema、边界、权限、依赖和成功标准，内部可由Prompt、代码或工具实现。它应高内聚、可独立验证，但不负责跨步骤状态、事务和审批。

| 维度 | Skill | Workflow |
| --- | --- | --- |
| 抽象层级 | 单项能力 | 多节点业务过程 |
| 核心接口 | 输入、输出、错误 | 节点、边、状态 |
| 复用方式 | 被多个流程调用 | 复用流程模板 |
| 失败处理 | 本次调用重试或失败 | 重试、回滚、补偿、接管 |
| 变化方式 | 能力版本升级 | 流程版本与迁移 |

2. Workflow将Skill、代码、工具及人工节点组成DAG或状态机，负责前置条件、串并行、分支、重试、补偿和Checkpoint。例如发布流程调用检查、测试、部署和通知Skill，并插入审批。

3. 二者通过**版本化契约**解耦。Workflow只依赖Skill的Schema、版本和错误码；兼容升级可复用，破坏性变更发布新主版本。Runtime执行前校验权限、工具和版本。

4. 稳定、高风险业务固化为Workflow；开放目标由Planner选择Skill，但安全、审批和预算仍由外层控制。Skill评估成功率、质量与成本，Workflow评估完成率、恢复率、补偿率和关键路径时延。

**相关知识点：** Skill、Workflow、DAG、状态机、Schema契约、语义版本、补偿事务、Planner。

### PLAN-075 · Planner通常由哪些模块组成？

> 稳定 ID：`PLAN-075`｜原题号：75

**Planner应将需求解析、任务分解、依赖构图、能力绑定、计划校验和重规划组成结构化流水线。**

1. 输入解析器将请求、会话和环境事实转为**Task Spec**，定义目标、交付物、约束、权限与验收条件；复杂度分类器选择直接执行、复用工作流或动态规划。

4. 反馈触发RePlanner替换失败节点及下游，并保留有效产物。设置重规划阈值、次数预算、冷却时间和升级条件，防止计划振荡。

### PLAN-076 · Workflow与Planner分别负责什么？

> 稳定 ID：`PLAN-076`｜原题号：76

**Workflow负责按照预定义状态与规则稳定执行，Planner负责面对开放目标动态生成或调整计划，二者应组合而非相互替代。**

1. **Workflow**由节点、流转条件、异常分支、超时、重试和补偿构成，适合审批、工单等路径稳定且需审计的业务。相同状态和输入应产生可预期的下一步。

| 维度 | Workflow | Planner |
| --- | --- | --- |
| 控制方式 | 预定义状态流转 | 动态生成与修订 |
| 确定性 | 较高 | 较低 |
| 适用场景 | 稳定业务 | 开放复杂任务 |
| 变化方式 | 修改流程定义 | 根据反馈重规划 |
| 风险控制 | 节点级规则 | Schema、验证器和预算 |

2. **Planner**解析目标与环境，拆分任务、建立依赖、选择能力，并在结果偏离预期时局部重规划。它适合路径无法预先枚举或信息需逐步获取的任务，但计划必须通过权限、完整性和可执行性校验。

3. 生产系统多采用混合模式：Planner选择并参数化Workflow，或将稳定子流程封装为计划节点；Workflow控制支付、发布等关键路径，Planner处理检索、诊断等不确定环节，从而限制模型直接控制高风险状态。

4. 边界依据变化频率、错误成本和可枚举性划分。规则稳定、合规要求高的部分归Workflow；目标开放、分支依赖运行时证据的部分归Planner。两者通过Plan Schema交接，记录节点状态、产物、证据和失败原因。

**相关知识点：** Workflow、Planner、状态机、DAG、动态规划、局部重规划、补偿事务、Plan Schema、混合编排。

### PLAN-079 · Skill和Workflow有什么区别？

> 稳定 ID：`PLAN-079`｜原题号：79

**Skill是可复用的能力单元，Workflow是跨步骤的控制与状态编排；二者分别解决能力复用和过程确定性问题。**

1. **Skill**封装专业指令、领域资料、脚本、工具用法和验证方法，以输入输出契约提供能力。例如“生成数据库迁移脚本”可作为Skill被不同任务选择；内部可以有多个动作，对外仍是一个能力边界。

2. **Workflow**定义节点顺序、条件分支、等待、超时、重试、审批和补偿，使业务实例可靠迁移状态。例如代码发布流程固定检查、构建、审批、发布与回滚阶段。

| 维度 | Skill | Workflow |
| --- | --- | --- |
| 核心关注 | 能做什么、如何做好 | 何时做、按何顺序 |
| 调用方式 | 动态选择 | 由事件或入口启动 |
| 状态范围 | 局部上下文 | 持久化流程状态 |
| 变化能力 | 可根据语义适配输入 | 路径由定义和条件约束 |
| 失败处理 | 返回错误或验证结果 | 重试、补偿、人工节点 |

3. 两者可以嵌套：Workflow节点调用Skill，Planner也可把整个Workflow视为稳定能力。Skill不得绕过Workflow的审批和权限；Workflow不应复制Skill内部逻辑，否则会产生耦合和版本分叉。

4. 若变化集中在处理方法、知识或工具，封装为Skill；若需跨时段保存状态、协调多角色并保证合规顺序，则使用Workflow。两者都应具备版本、Schema、审计和回归测试。

**相关知识点：** Skill、Workflow、能力封装、状态机、控制流、能力注册表、补偿事务、版本治理。

### PLAN-085 · Agent执行失败后如何进行重试或重新规划？

> 稳定 ID：`PLAN-085`｜原题号：85

**失败恢复应先判断错误是否可恢复、原计划是否仍有效以及副作用是否已发生，再选择重试、修复、补偿或重新规划。**

1. 收集错误码、调用参数、执行轨迹、外部真实状态和验证器结果，生成错误指纹并定位失败节点。相同输入下重复出现确定性错误时不得盲目重试；只有错误可能随时间消失且原动作安全时，重试才有意义。

2. 针对“Agent执行失败后如何进行重试或重新规划”，错误至少分为**瞬时故障、限流、参数错误、权限错误、业务冲突、能力不匹配、模型推理错误和计划失效**。瞬时故障采用带抖动的指数退避；参数错误先修复；权限和合规错误停止；只有路径或核心前提失效时才修改计划。

| 策略 | 适用错误 | 是否改计划 |
| --- | --- | --- |
| Retry | 超时、限流、网络抖动 | 否 |
| Repair | 参数或格式错误 | 调整动作 |
| Compensation | 已产生外部副作用 | 恢复业务状态 |
| Replan | 路径或前提失效 | 是 |

3. 针对“Agent执行失败后如何进行重试或重新规划”，重试前检查副作用和幂等性，通过Idempotency Key、唯一约束或外部状态查询确认上次调用是否已生效。可逆本地状态使用**Rollback**，跨系统已提交动作使用Saga补偿。每步设置次数、时长、成本预算和错误指纹，重复失败且无新证据时转人工或安全终止。

4. Replanner只替换失败节点及其受影响下游，保留已验证且仍有效的产物，并记录新计划版本和变更原因。若目标、权限或关键前提已经失效，应停止执行并请求新信息，不能通过改写计划绕过约束。

**相关知识点：** 错误分类、指数退避、随机抖动、幂等键、Rollback、Saga、局部Replan。

### PLAN-089 · 如何设计一个可扩展的Planner模块？

> 稳定 ID：`PLAN-089`｜原题号：89

**可扩展Planner应以Task Spec和Plan Schema为核心，通过接口插拔分解、构图、能力选择与校验策略。**

1. 隔离输入、规划和执行：Normalizer把请求转为**Task Spec**；Planner输出计划；Executor消费计划并回传观察。替换模型、规则或模板时无需改造运行时。

| 扩展点 | 接口输入 | 接口输出 |
| --- | --- | --- |
| Decomposer | 目标与约束 | 子任务 |
| Dependency Builder | 子任务及资源 | DAG |
| Capability Resolver | 节点与能力目录 | 执行器 |
| Plan Validator | 计划与权限 | 校验报告 |
| Replanner | 轨迹与失败证据 | 新版本 |

2. Plan Schema定义节点ID、输入输出、依赖、执行器、成功标准、超时、重试、副作用和验证器，并支持兼容演进。插件通过接口访问上下文，不得修改共享状态；第三方策略受权限、超时和配额限制。

3. 采用**规则+模板+LLM**分层：简单任务直执行，业务复用Workflow，长尾任务由LLM规划。领域可注册分解模板、约束和成本函数，但必须经过统一Validator。

4. 计划、策略和能力目录版本化，支持依赖注入、开关、影子评测和回滚。测试覆盖契约、黄金任务、对抗输入、计划回放及重规划；监控可执行率、成功率、延迟和成本。

**相关知识点：** Task Spec、Plan Schema、策略模式、插件架构、依赖注入、能力注册表、Plan Validator、Replanner、契约测试。

### PLAN-090 · 企业级Agent如何管理超长任务和长时间运行任务？

> 稳定 ID：`PLAN-090`｜原题号：90

**企业级长任务应运行在持久化工作流之上，以检查点、事件日志、租约和幂等机制实现可暂停、可恢复、可审计执行。**

1. 将长任务拆成可安全重试的节点，由Durable Scheduler管理Ready、Running、Waiting和Done状态。Worker通过租约领取节点并心跳，宕机或租约过期后由其他Worker接管，不能依赖进程内存。

2. Checkpoint保存**计划版本、节点状态、输入输出引用、上下文摘要、工具回执、幂等键、模型与Prompt版本及待执行队列**，并写在副作用提交后的稳定边界。状态迁移采用CAS，防止多个Worker同时恢复。

> 本题视角：企业级Agent如何管理超长任务和长时间运行任务
| 机制 | 保存内容 | 主要用途 |
| --- | --- | --- |
| Checkpoint | 稳定时刻快照 | 断点恢复 |
| Event Log | 不可变事件序列 | 审计与重建 |
| Rollback | 旧状态或逆操作 | 撤销可逆变更 |
| Compensation | 反向业务动作 | 跨系统修复 |

3. 暂停时停止领取新步骤并让操作到达安全点；恢复时加载快照，复核权限、依赖版本及外部副作用，再决定继续、**补偿**或重做。审计回放只重建事件，真实重执行须固定版本并置于隔离环境。

4. 等待审批、外部回调或定时条件时，挂起任务并释放资源，由事件唤醒。上下文采用摘要加产物引用，原文件存对象存储；设置总截止时间、步骤预算、取消信号和人工接管接口，避免无限运行。

**验证指标：** 任务完成率、步骤成功率、重规划率、无效调用率和单任务成本。

**相关知识点：** Checkpoint、持久化状态机、Durable Execution、Event Sourcing、回放、人工接管。

### PLAN-093 · 从用户输入到最终完成任务，Agent整体执行链路是怎样的？

> 稳定 ID：`PLAN-093`｜原题号：93

**Agent的完整链路是“接入与安全检查—任务理解—检索与规划—计划校验—执行反馈循环—最终验收与交付”。**

1. 接入层完成身份、权限、安全和限流，并分配Trace ID。理解层结合会话与Memory解析目标、对象、约束、交付物和副作用，形成**Task Spec**；歧义影响结果或风险时先澄清。

| 阶段 | 核心产物 | 失败处理 |
| --- | --- | --- |
| 理解 | Task Spec | 澄清或拒绝 |
| 检索 | 来源化事实 | 扩展查询 |
| 规划 | DAG、能力绑定 | 修复计划 |
| 执行 | 产物与回执 | 重试、补偿 |
| 验收 | Validator证据 | 返工或人工复核 |

2. Planner依据验收条件分解任务、建立依赖并选择能力。Plan Validator检查目标覆盖、输入来源、Schema、权限、环、成本和副作用；不合格计划不得执行，高风险节点插入审批。

3. Runtime维护**Task—Step—Attempt**状态并调度节点。Executor调用能力，Validator检查结构、业务状态和目标；失败按类型重试、修复、补偿或局部重规划。观察更新事实与版本，有效产物不重复执行。

4. 节点通过后全局验收，生成交付物、证据和未完成项，再按授权更新Memory。系统持久化计划、回执、审计与成本；客户端断线不终止持久任务，取消信号沿任务树传播并在安全点生效。

**相关知识点：** Agent Loop、Task Spec、RAG、Planner、Plan Validator、Runtime、Tool Calling、局部重规划、审计追踪。

### PLAN-094 · Agent为什么需要任务拆解，而不是一次性生成最终答案？

> 稳定 ID：`PLAN-094`｜原题号：94

**任务拆解把不可控的长链生成转化为可执行、可验证和可恢复的节点，是复杂Agent获得可靠性的基础。**

1. 一次性生成默认所有信息已知且执行环境不变，模型会在没有工具反馈时推测中间结果；任何早期假设错误都会传递到最终答案。拆解后，每个节点先获取事实或产物，再据此推进，使计划能够随外部状态更新。

| 维度 | 一次性生成 | 任务拆解 |
| --- | --- | --- |
| 事实获取 | 依赖输入和假设 | 分步调用工具取证 |
| 错误定位 | 只能检查整体 | 定位到具体节点 |
| 恢复成本 | 通常整体重做 | 局部重试或重规划 |
| 上下文 | 多类材料混杂 | 按节点裁剪 |
| 并行能力 | 难识别独立工作 | DAG并行调度 |
| 风险控制 | 末端发现副作用 | 节点级权限与审批 |

2. Planner从验收条件反推中间产物，建立**Task Spec与DAG**。每个节点声明输入、输出、执行器、成功标准、超时和副作用，粒度以可独立验证、可安全重试且失败可定位为界；过细会增加通信成本，过粗则失去恢复价值。

3. 执行阶段形成“行动—观察—验证”闭环。验证通过才释放下游；瞬时错误重试，参数错误修复，关键前提变化则局部重规划。已成功节点及其产物被保留，避免因单点失败重新消耗全部Token和工具成本。

4. 拆解也不是默认答案。简单问答、低风险转换或一次工具调用若可立即验证，直接生成更经济；只有任务具有多目标、外部状态、长依赖、并行机会或高风险副作用时，拆解收益才超过规划开销。

**相关知识点：** 任务分解、Task Spec、DAG、误差传播、节点验证、局部重试、动态重规划、上下文隔离。

### PLAN-096 · Planner模块通常如何设计？

> 稳定 ID：`PLAN-096`｜原题号：96

### PLAN-097 · Execution Plan一般包含哪些核心内容？

> 稳定 ID：`PLAN-097`｜原题号：97

### PLAN-099 · 如何确定任务拆解的粒度？

> 稳定 ID：`PLAN-099`｜原题号：99

**合适的任务粒度应使每个节点具备单一责任、明确契约、独立验证和有限失败影响，同时不引入过高协调成本。**

1. 从最终验收条件反推中间产物，每个产物对应一个候选节点，再检查动作是否共享相同执行器、权限、事务和上下文。若多个动作必须原子提交且无法分别验收，应合并；若包含不同副作用、不同失败原因或可并行部分，应拆分。

| 粒度 | 典型特征 | 主要后果 |
| --- | --- | --- |
| 过粗 | 多目标、多工具、验证滞后 | 失败难定位、整体重做 |
| 合适 | 单一产物、契约明确、可重试 | 易调度、易恢复 |
| 过细 | 节点只做微小转换、频繁传上下文 | 通信和Token成本高 |

2. 节点至少声明**输入、输出Schema、执行器、成功标准、超时、副作用和Validator**。经验边界是一次执行能在可控时间内完成，输出可持久化供下游使用，失败可在不重做无关步骤的情况下恢复。

3. 使用成本模型平衡收益：拆分收益包括并行度、上下文隔离、缓存复用和局部重试；成本包括规划、序列化、调度、通信和验证。可合并连续、低风险、同工具且共享上下文的节点；独占资源或高风险写操作即使很短也应单列。

4. 粒度需要运行时校准。若节点经常同时失败、共享大量重复上下文，可合并为复合Skill或Workflow；若单节点P95过长、重试昂贵或错误类型分散，应继续拆分。监控节点完成率、平均上下文量、协调耗时、重试范围和关键路径时长。

**相关知识点：** 任务粒度、单一职责、原子性、输入输出契约、局部重试、协调成本、复合Skill、关键路径。

### PLAN-102 · 什么情况下需要重新规划（Replanning）？

> 稳定 ID：`PLAN-102`｜原题号：102

**只有原计划的关键前提、目标、能力路径或资源约束失效时才需要Replanning；可恢复的单步错误应优先局部处理。**

1. 触发信号包括用户修改目标、外部状态与假设冲突、产物不符合下游契约、能力不可用、权限变化、预算或截止时间无法满足，以及同一错误经合理重试仍出现。Validator应提供证据，不能由Planner主观改写计划。

| 策略 | 适用错误 | 是否改计划 |
| --- | --- | --- |
| Retry | 超时、限流、网络抖动 | 否 |
| Repair | 参数或格式错误 | 调整动作 |
| Compensation | 已产生外部副作用 | 恢复业务状态 |
| Replan | 路径或前提失效 | 是 |

2. 网络故障、限流和偶发超时采用带抖动退避，不触发Replan；参数错误先Repair；权限或合规错误应停止，不能换路径绕过。仅当重试无法改变结果，或能力、依赖顺序和完成路径需要变化时才重规划。

3. Replanner以**当前Task Spec、计划版本、已验证产物、失败证据、外部状态和剩余预算**为输入，定位最小失效切面，仅替换失败节点及其受影响下游。仍满足版本、时效和契约的成功节点保留，避免全量重做。

4. 重规划前检查副作用，必要时先回滚或Saga补偿；新计划重新经过依赖、权限、预算和风险校验。设置触发阈值、次数上限、冷却时间和相似度检测，连续生成近似路径或无新证据时转人工，防止计划振荡。

**相关知识点：** 错误分类、指数退避、随机抖动、幂等键、Rollback、Saga、局部Replan。

### PLAN-108 · 如何设计一个支持断点续跑（Checkpoint）的Agent？

> 稳定 ID：`PLAN-108`｜原题号：108

**支持断点续跑的Agent应采用持久化状态机，将计划、节点产物和副作用回执写入一致性检查点，并以幂等语义恢复执行。**

1. Runtime将任务建模为Task—Step—Attempt状态，迁移写入数据库并带版本号。Checkpoint位于节点验证通过、产物已持久化且副作用明确的安全边界；聊天历史无法还原待执行队列和外部状态。

2. Checkpoint保存**计划版本、节点状态、输入输出引用、上下文摘要、工具回执、幂等键、模型与Prompt版本及待执行队列**。状态迁移采用CAS，防止多个Worker同时恢复。

> 本题视角：如何设计一个支持断点续跑（Checkpoint）的Agent
| 机制 | 保存内容 | 主要用途 |
| --- | --- | --- |
| Checkpoint | 稳定时刻快照 | 断点恢复 |
| Event Log | 不可变事件序列 | 审计与重建 |
| Rollback | 旧状态或逆操作 | 撤销可逆变更 |
| Compensation | 反向业务动作 | 跨系统修复 |

3. 暂停时停止领取新步骤并让操作到达安全点；恢复时加载快照，复核权限、依赖版本及副作用，再决定继续、**补偿**或重做。不能假设进程崩溃等于工具未执行，超时调用先查询外部状态。

4. 多Worker恢复采用租约或CAS，保证同一节点只有一个有效Attempt提交。执行器携带Idempotency Key，提交时校验计划与Attempt版本；版本不兼容或副作用无法确认时转人工。

### PLAN-109 · Agent如何管理长时间运行任务的状态？

> 稳定 ID：`PLAN-109`｜原题号：109

**长任务必须将控制状态、业务状态、产物和回执持久化，使Worker重启或客户端断线时不丢进度。**

1. 采用**Task—Step—Attempt**状态机：Task记录目标、计划版本和期限；Step记录依赖、输入输出、状态和重试；Attempt记录执行者、租约、回执与错误。状态迁移通过事务或CAS完成，不能仅存于进程内存。

| 状态类别 | 保存内容 | 推荐存储 |
| --- | --- | --- |
| 控制状态 | DAG、队列、计时器、版本 | 关系库或工作流引擎 |
| 大型产物 | 文件、日志、长输出 | 对象存储 |
| 事件轨迹 | 状态变更、审批、回调 | Event Log |
| 临时锁定 | 租约、心跳、配额 | TTL协调存储 |

2. 节点完成后原子保存产物、验证结果和后继状态，并形成Checkpoint。副作用调用记录**Idempotency Key**和资源ID；恢复时查询真实状态，不能因Attempt停在Running就判断操作未完成。

3. 等待审批、回调或定时时，将Step置为Waiting，持久化唤醒条件并释放Worker。回调携带关联ID和去重键，计时器到期生成事件；客户端仅负责展示，断线后任务运行。

4. 记录模型、Prompt、Tool和Schema版本，升级时迁移或锁定旧环境；设置保留期、加密、访问控制和敏感信息清理。监控心跳超时、卡住任务、迁移失败、积压时长和恢复成功率。

**相关知识点：** Durable Execution、持久化状态机、Checkpoint、Event Log、租约、TTL、幂等键、外部回调、状态迁移。

### PLAN-111 · 如何设计Agent的任务队列（Task Queue）？

> 稳定 ID：`PLAN-111`｜原题号：111

**Agent任务队列需提供持久投递、可见性超时、优先级与公平性、延迟重试、死信隔离和幂等消费能力。**

1. 消息承载Task ID、Step ID、Attempt、版本、租户、优先级、截止时间、能力、产物引用和Trace ID；上下文存对象存储。只有依赖满足且Validator通过的节点进入Ready Queue。

| 队列 | 保存对象 | 处理方式 |
| --- | --- | --- |
| Ready Queue | 可执行节点 | Worker领取 |
| Delay Queue | 等待退避节点 | 到期转Ready |
| Retry Queue | 可恢复失败 | 按策略重投 |
| DLQ | 超预算或毒消息 | 告警、人工 |

2. Worker通过**Lease或Visibility Timeout**领取消息并续期；成功后先原子提交产物与状态，再确认。Worker宕机则消息重新可见，因此只保证至少一次投递；业务“恰好一次”依赖Idempotency Key、唯一约束和去重。

3. 优先级综合业务等级、截止时间、关键路径和等待时长，并用老化与租户加权防止饥饿。按模型、Tool和租户设置配额；消费变慢时启用背压、暂停低优入口或降级。

4. 重试区分瞬时、限流、参数和权限错误，采用抖动退避并设置次数、时长与成本上限；毒消息进入DLQ。监控队列深度、最老消息年龄、领取延迟、租约超时、重投率和吞吐量。

**相关知识点：** Task Queue、Ready Queue、Delay Queue、DLQ、Visibility Timeout、至少一次投递、幂等消费、背压、公平调度。

### PLAN-115 · 当工具调用失败时，Agent如何自动恢复？

> 稳定 ID：`PLAN-115`｜原题号：115

**工具调用失败后的自动恢复必须先分类错误并确认副作用，再选择重试、修参、降级、补偿或局部重规划。**

1. Executor保存工具版本、参数摘要、错误码、响应、Attempt和资源ID，分类网络故障、限流、参数错误、权限错误、业务冲突、工具不可用和未知结果。不同类别不得使用同一重试策略。

| 失败类型 | 自动恢复动作 | 禁止行为 |
| --- | --- | --- |
| 超时、网络抖动 | 退避重试 | 高频重放 |
| 限流 | 遵循Retry-After并降并发 | 并发放大 |
| 参数错误 | 修参后再试 | 原参数重放 |
| 权限错误 | 停止并申请授权 | 绕过权限 |
| 工具不可用 | 熔断并选备选 | 永久循环 |
| 结果未知 | 查询外部状态 | 默认失败 |

2. 副作用调用携带**Idempotency Key**。超时或中断时，先通过查询、唯一约束或回执确认是否生效；已成功则补录结果，部分成功则补偿，只有确认未执行才能重试。

3. 重试设置次数、总时长与费用预算，并使用指数退避和抖动。连续同类错误触发Circuit Breaker；存在等价且权限相同的备选工具时可降级，否则把证据交给Replanner修改局部路径。

4. 恢复结果仍需Validator验收，不因“重试成功”释放下游。记录每次Attempt、策略和最终状态，监控工具成功率、重试放大率、恢复率、重复副作用和熔断次数；未知或高风险状态转人工。

**相关知识点：** 错误分类、指数退避、Retry-After、幂等键、Circuit Breaker、工具降级、补偿事务、局部重规划。

### PLAN-120 · DAG和Workflow有什么区别？

> 稳定 ID：`PLAN-120`｜原题号：120

**DAG是描述任务依赖的无环图结构，Workflow是可运行、可持久化和可治理的业务流程定义，二者处于不同抽象层。**

1. DAG由节点与有向边组成，回答“哪些任务先完成、哪些可并行”，通过拓扑排序、入度和关键路径调度。它不规定权限、重试、等待事件、人工审批、版本升级或补偿。

| 维度 | DAG | Workflow |
| --- | --- | --- |
| 核心对象 | 节点与依赖边 | 活动、状态、流转规则 |
| 是否允许循环 | 不允许 | 可通过状态或迭代表达 |
| 运行状态 | 外部维护 | 通常内建持久化 |
| 异常处理 | 额外定义 | 重试、补偿、超时 |
| 人工与事件 | 非固有能力 | 等待、审批、回调 |
| 复用方式 | 单次计划实例 | 版本化流程模板 |

2. **Workflow**除控制流外，还包含Schema、不变量、权限、SLA、幂等、取消和审计，由引擎保证长任务恢复。审批、支付、发布等稳定流程适合Workflow；一次任务的并行依赖适合DAG。

3. 二者可组合：Workflow阶段内部用DAG并行，或Planner生成DAG后交给Durable Workflow。DAG负责依赖优化，Workflow负责生命周期和一致性，不能因有DAG就省略状态机与补偿。

4. 需计算拓扑顺序、并行度和关键路径时使用DAG；需跨时段等待、人工介入、审计和版本迁移时使用Workflow。循环应封装为带退出条件的活动，不能向DAG加入回边。

**相关知识点：** DAG、Workflow、拓扑排序、关键路径、持久化状态机、人工审批、补偿事务、Durable Execution。

### PLAN-121 · Agent如何实现动态重规划（Replan）？

> 稳定 ID：`PLAN-121`｜原题号：121

**动态Replan应采用事件触发、影响分析、局部DAG改写、校验和原子版本切换的闭环。**

1. Runtime将验证失败、外部状态变化、目标修改、能力不可用或预算告急转为Replan Event，并附错误码、轨迹、回执和Plan Version。网络抖动、限流和格式错误先Retry或Repair。

| 阶段 | 核心动作 | 输出 |
| --- | --- | --- |
| Detect | 判断前提是否失效 | 触发事件 |
| Diagnose | 识别根因与范围 | 失效节点集 |
| Rewrite | 替换节点、边或能力 | 候选子图 |
| Validate | 检查依赖、权限和风险 | 校验报告 |
| Commit | CAS切换版本 | 新计划 |

2. Replanner读取**Task Spec、旧DAG、有效产物、失败证据、外部状态和预算**，计算影响闭包。满足Schema、版本和时效的成功节点保持Immutable，只生成失效节点及下游。

4. Scheduler暂停受影响节点，用CAS提交新Plan Version并重算Ready Queue；Attempt不能覆盖新版本。限制重规划次数、Token、时间和相似度，无新证据或振荡时转人工，并记录图差异与理由。

### PLAN-125 · Agent如何决定是否调用工具？

> 稳定 ID：`PLAN-125`｜原题号：125

**Agent只有在内部知识无法可靠完成目标，且某个工具的预期收益高于调用成本与风险时，才应发起工具调用。**

1. 先判断是否需要外部能力：实时事实、私有数据、精确计算、代码执行和业务写入通常需调用工具；稳定常识或已有信息可直接回答。关键参数缺失时应向用户澄清。

2. Tool Registry记录**能力、Schema、权限、时延、费用、可靠性、幂等性和副作用**。路由器先召回参数可满足的候选，再按匹配度、成功率、信息增益、成本和风险评分；无候选达到阈值时不调用。

| 决策方式 | 适用条件 | 主要边界 |
| --- | --- | --- |
| 直接回答 | 上下文充分且事实稳定 | 不得虚构实时信息 |
| 检索或只读工具 | 需要外部证据或私有数据 | 验证来源与新鲜度 |
| 写操作工具 | 必须改变外部状态 | 授权、确认与审计 |
| 向用户澄清 | 目标或关键参数缺失 | 避免错误执行 |

3. 模型生成结构化调用意图，宿主执行前校验Schema、参数、权限、预算和策略。转账、删除、发布等高风险动作需要**最小权限和人工确认**；能以只读或可逆方式实现时优先选择低风险路径。

4. 返回后需验证完整性、可信度和目标达成度，不能只检查HTTP状态。瞬时故障可限次退避重试，参数错误应修正，权限错误停止，能力不匹配则重新路由；记录理由、参数、结果和耗时，以成功率和反馈校准阈值，防止过度调用或漏调用。

**历史别名：** `CTX-201`。

**相关知识点：** Tool Selection、Tool Registry、Function Calling、Schema校验、信息增益、最小权限、幂等性、结果验证。

### PLAN-127 · Function Calling底层机制是什么？

> 稳定 ID：`PLAN-127`｜原题号：127

**Function Calling本质是模型生成受Schema约束的调用意图，由宿主完成校验、执行和结果回填，模型自身并不直接运行函数。**

1. 宿主把工具名称、用途、JSON Schema和策略发给模型。模型输出文本或tool call；服务端通过结构化训练、语法约束或受限解码，使工具名与参数符合Schema，但业务合法性仍由宿主校验。

2. 响应包含**tool name、arguments和call_id**。宿主解析JSON，验证字段、类型、范围、权限及预算，再映射到本地函数或远程接口。结果以对应call_id的tool message回填会话，模型据此继续调用或生成答案。

| 机制 | 核心作用 | 是否执行工具 |
| --- | --- | --- |
| Function Calling | 结构化表达调用意图 | 否 |
| JSON Mode | 保证输出为合法JSON | 否 |
| MCP | 标准化连接外部能力 | 由客户端执行 |
| 普通API调用 | 直接请求确定端点 | 是 |

3. 并行调用可含多个call_id，宿主分别执行并按ID回填，避免错配。流式参数可能分片到达，必须聚合后解析；调用循环需设置最大轮数、超时和费用上限。

4. Schema合法不等于操作安全。写操作应采用**最小权限、幂等键、人工确认和审计日志**；瞬时故障可重试，参数错误可回填供模型修正，权限或策略拒绝不得绕过。函数正常返回后仍需验证业务目标。

**相关知识点：** JSON Schema、受限解码、tool call、call_id、宿主执行、结果回填、幂等键、调用循环。

### PLAN-130 · 工具调用失败如何恢复？

> 稳定 ID：`PLAN-130`｜原题号：130

**工具失败恢复应先分类错误，再选择重试、修参、降级、重规划或补偿，不能对所有异常统一重试。**

1. 每次调用记录tool、参数、call_id、Attempt、幂等键和状态，将响应标准化为错误码、可重试性及副作用状态。恢复前判断操作未执行、已执行或结果未知；未知写操作先查询业务状态，避免重复提交。

| 错误类型 | 典型原因 | 恢复策略 |
| --- | --- | --- |
| 瞬时错误 | 超时、限流、网络抖动 | 退避重试 |
| 参数错误 | Schema或业务校验失败 | 修参后新Attempt |
| 权限错误 | 凭证失效、范围不足 | 停止并申请授权 |
| 能力错误 | 工具不匹配或下线 | 备用工具或Replan |
| 部分成功 | 外部状态已改变 | 查询、补偿或人工处理 |

2. **自动重试只适用于幂等操作或带幂等键的安全写操作**，并设置次数、指数退避、抖动和总时限。错误指纹连续相同时应转入修参或重规划；服务持续异常时由熔断器阻止请求风暴。

3. 参数可修复时，将错误回填模型；主工具不可用时按能力、权限和结果等价性选择备用工具。替代工具改变语义、费用或副作用时需重验计划。非关键步骤可返回缓存或降级结果，并标明新鲜度。

4. 工作流从Checkpoint恢复并复核副作用。跨系统事务无法原子回滚时执行Saga补偿；删除、付款等不可逆或状态不明操作应转人工。最终由Validator确认目标，并监控恢复成功率、重试放大率和重复副作用率。

**相关知识点：** 错误分类、指数退避、幂等键、熔断器、Fallback、Replan、Checkpoint、Saga补偿。

### PLAN-131 · 如何避免工具调用循环？

> 稳定 ID：`PLAN-131`｜原题号：131

**避免工具调用循环需要同时设置硬预算、检测重复状态，并要求每次继续调用都能产生可验证的新进展。**

1. Runtime设置最大调用轮数、单工具重试次数、时长、Token和费用上限，任一预算耗尽即停止。Planner定义成功、失败条件及工具白名单，避免模型自行延长流程。

2. 每次调用生成**目标、节点、工具、规范化参数、结果摘要和错误类型**组成的状态指纹。相同指纹重现或窗口内形成A→B→A时判定无进展；参数不同但结果与计划状态不变，也属于语义循环。

| 行为 | 是否属于循环 | 处理方式 |
| --- | --- | --- |
| 瞬时错误后限次重试 | 否 | 退避并累计Attempt |
| 长任务按状态轮询 | 否 | 设间隔与截止时间 |
| 相同输入得到相同错误 | 是 | 停止重试并诊断 |
| 工具互相触发且状态不变 | 是 | 断开调用链并Replan |

3. Validator计算子目标完成数、未满足约束、测试通过率或新增证据量。只有进展超过阈值才允许继续，“再试一次”不构成证据。参数错误可修复，能力不匹配应换工具，前提失效则局部Replan。

4. 调用由中心调度器控制，不允许工具结果直接触发下一工具；嵌套调用设置深度限制和调用图环检测。写操作使用幂等键。终止时返回已完成内容、循环证据、剩余缺口和建议，高风险任务转人工。

**相关知识点：** 循环检测、状态指纹、进展度量、调用预算、终止条件、幂等键、轮询、局部Replan。

### PLAN-133 · Retry策略如何设计？

> 稳定 ID：`PLAN-133`｜原题号：133

**Retry应只用于预计再次执行可能成功的瞬时故障，并由幂等性、退避算法和总预算共同约束。**

1. 先按错误码和业务语义分类。网络抖动、超时、暂不可用及限流通常可重试；参数、认证、权限和业务校验错误应停止或修复，不能原样重试。超时且结果未知时先查询服务端状态。

2. 只读操作通常可重试；写操作必须具有**幂等键、唯一约束或可查询的业务请求号**。每次Retry沿用幂等键并增加Attempt，防止付款、创建订单等副作用重复。无法确认幂等性的高风险操作应转人工。

| 退避方式 | 特点 | 适用场景 |
| --- | --- | --- |
| 固定间隔 | 简单但易同步冲击 | 低并发内部任务 |
| 线性退避 | 等量增加等待 | 恢复时间较稳定 |
| 指数退避 | 快速降低请求频率 | 服务异常或限流 |
| 指数退避加抖动 | 打散重试峰值 | 分布式生产系统 |

3. 等待时间可按min(cap, base×2^attempt)计算并加入随机抖动；服务返回Retry-After时优先遵守。策略同时设置最大次数、单次超时、总截止时间和费用预算，且不能让各层SDK、网关和业务服务叠加重试造成指数放大。

4. 连续相同错误、超过截止时间或熔断器开启时停止Retry，转为Fallback、修参、Replan或人工处理。监控重试成功率、请求倍数、恢复时延和重复副作用率，并按工具和错误类型配置；成功率长期过低的规则应下线。

**相关知识点：** Retry、错误分类、指数退避、随机抖动、Retry-After、幂等键、重试预算、熔断器。

### PLAN-134 · Replan和Retry有什么区别？

> 稳定 ID：`PLAN-134`｜原题号：134

**Retry是在计划仍然有效时重新尝试同一动作，Replan是在原路径或前提失效时修改任务计划。**

1. Retry假设目标、依赖和工具正确，失败来自超时、限流等瞬时因素，因此不改计划，只创建新Attempt。它需要幂等保护、退避、次数和截止时间。

2. Replan表示原动作已无价值，例如工具不匹配、资源不可用、依赖结果推翻假设或约束变化。Planner依据最新Observation更换工具、调整依赖、拆分节点或改变路径，并生成**新Plan Version**。

| 维度 | Retry | Replan |
| --- | --- | --- |
| 核心假设 | 路径正确，执行偶发失败 | 路径或前提已失效 |
| 变更范围 | 新Attempt，不改节点 | 修改节点、依赖或工具 |
| 典型触发 | 超时、限流、暂时不可用 | 能力不匹配、约束变化 |
| 主要风险 | 请求放大、重复副作用 | 规划漂移、工作作废 |

3. 两者之间还有Repair：Schema或参数错误时修正动作，不改完整计划。先分类错误，再判断原节点是否仍可达成目标；可达且成功率会随时间恢复则Retry，参数有误则Repair，不可达才Replan。

4. Runtime记录错误指纹、Attempt、Plan Version和副作用。相同错误持续、预算耗尽或无进展时升级为Replan；新计划不得重放旧节点，应复核已有产物和补偿需求。不可逆操作或关键事实不确定时转人工。

**相关知识点：** Retry、Replan、Repair、Attempt、计划版本、错误分类、幂等性、局部重规划。

### PLAN-135 · 如何实现任务暂停与恢复？

> 稳定 ID：`PLAN-135`｜原题号：135

**任务暂停与恢复应基于持久化状态机和稳定Checkpoint实现，恢复的是可验证执行状态，而不只是聊天记录。**

1. 状态机包含RUNNING、PAUSING、PAUSED、RESUMING。暂停时以CAS置为PAUSING并停止领取新节点；进行中调用可安全取消则取消，否则等待提交边界并记录结果。

2. Checkpoint保存**Plan Version、节点状态、产物引用、上下文摘要、队列、Attempt、工具回执、幂等键及模型版本**。快照与状态转换原子提交，大产物保存不可变引用，敏感数据隔离。

| 机制 | 保存形式 | 主要作用 |
| --- | --- | --- |
| Checkpoint | 某时刻完整快照 | 快速恢复 |
| Event Log | 不可变状态事件 | 审计与重建 |
| Lease | Worker持有权与期限 | 防止重复恢复 |
| Compensation | 反向业务动作 | 修复已提交副作用 |

3. Worker获取Lease后加载快照、回放事件并重建Ready Queue。再核对权限、工具版本、输入有效期和外部状态；成功节点复用，未知写操作先查询，只有幂等且未生效的动作可重做。

4. 外部依赖或前提变化时应局部Replan或人工确认。恢复后以CAS切回RUNNING，监控恢复耗时、快照失败率、重复执行率和状态不一致率。Checkpoint需定期演练。

**相关知识点：** 持久化状态机、Checkpoint、Event Sourcing、CAS、Lease、安全点、幂等恢复、Durable Execution。

### PLAN-137 · Agent如何处理中断和超时？

> 稳定 ID：`PLAN-137`｜原题号：137

**中断与超时应通过可传播的取消信号、分层Deadline和安全清理机制处理，并把最终状态持久化为可恢复事实。**

1. 区分用户取消、系统关闭、节点超时和总Deadline。Runtime把剩余时间分配给子步骤，子步骤不得越过父级Deadline；取消信号沿调用树传播，已完成节点仍保留。

2. 工具和Worker采用**协作式取消**：在等待和提交前检查Token，停止新工作并释放资源。无响应时等待Grace Period再强制终止；外部API不可取消时，停止等待但继续跟踪状态。

| 情形 | 立即动作 | 后续处理 |
| --- | --- | --- |
| 用户中断 | 停止新节点 | 保存进度并返回摘要 |
| 单步超时 | 取消当前Attempt | 判断Retry或Fallback |
| 总Deadline到期 | 终止调用树 | 输出部分结果 |
| 结果未知的写操作 | 禁止直接重放 | 查询外部状态 |

3. 状态机使用RUNNING、CANCELLING、CANCELLED、TIMED_OUT。终止前写Checkpoint，保存计划、节点、回执、幂等键和未完成项；使用CAS防止迟到结果把已取消任务改回成功。

4. 已提交副作用不能靠取消撤销，应执行补偿；不可逆操作转人工。超时是否Retry取决于幂等性、预算和错误类型，结果未知时先对账。监控超时率、取消延迟、资源泄漏和重复副作用率。

**相关知识点：** Deadline、Timeout、Cancellation Token、协作式取消、Grace Period、Checkpoint、幂等性、补偿事务。

### PLAN-141 · 什么情况下应该重试，什么情况下应该直接重新规划？

> 稳定 ID：`PLAN-141`｜原题号：141

**原路径仍可达且失败具有瞬时性时重试；路径、能力或关键前提已失效时应直接重新规划。**

1. 先判断后置条件能否由同一工具和动作达成。网络抖动、限流、暂不可用不改变路径有效性，且成功率随时间恢复，适合Retry；Schema或参数错误先Repair，不应原样重试。

2. 工具能力不足、依赖结果推翻假设、资源下线、约束变化或节点无法满足目标时，应Replan。权限缺失应停止并申请授权；**Replan不能用于绕过权限和安全策略**。

| 观察信号 | 决策 | 原因 |
| --- | --- | --- |
| Retry-After、偶发5xx | Retry | 环境可能自行恢复 |
| 参数校验失败 | Repair | 路径有效、动作有误 |
| 重复相同错误且无新证据 | Replan | 再试收益接近零 |
| 工具能力不匹配 | Replan | 原节点不可达 |
| 写操作结果未知 | 先查询状态 | 避免重复副作用 |

3. 若重试成功概率×剩余价值大于等待、费用和风险，则在预算内重试；否则切换路径。每个节点设置次数、时限和费用上限，错误指纹重复、无进展或熔断器开启时终止Retry。

4. Replan前保留已验证产物，核对副作用并决定复用、补偿或废弃；新Plan Version需重查依赖和成功条件。不可逆写操作、状态不明或替代路径均低置信时应转人工。

**相关知识点：** Retry、Repair、Replan、路径可达性、错误指纹、预期效用、幂等性、计划版本。

### PLAN-142 · 如何避免Agent陷入无限重试循环？

> 稳定 ID：`PLAN-142`｜原题号：142

**防止无限重试必须由Runtime实施硬性重试预算，并在重复错误、无进展或路径失效时强制终止或升级策略。**

1. 节点设置max_attempts、Deadline、费用和等待上限，任务层设置全局Retry Budget；任一阈值达到即禁止重试。SDK、网关、Worker和Agent只指定一个主要重试层，避免多层重试形成指数放大。

2. 每次失败生成**错误指纹＝工具＋规范化参数＋错误码＋结果摘要**。同一指纹连续出现即无新增信息；即使参数改变，若外部状态、约束和证据量未变化，也属于语义无进展。

| 触发信号 | 处理动作 | 不应继续Retry的原因 |
| --- | --- | --- |
| 参数或权限错误 | Repair或申请授权 | 时间不会自动修复 |
| 相同错误达到阈值 | Replan | 边际成功率过低 |
| 服务持续异常 | 打开熔断器 | 防止请求风暴 |
| 写操作结果未知 | 先查询状态 | 可能重复副作用 |
| 无替代路径 | 转人工或终止 | 自动执行无进展 |

3. 瞬时错误采用抖动指数退避并遵守Retry-After；写操作使用幂等键。Validator在每个Attempt后计算进展，只有出现新证据或错误条件改变才允许继续；模型不能修改计数器或绕过预算。

4. 预算耗尽后记录已尝试动作、最后错误和剩余缺口，进入Replan、Fallback、死信队列或人工处理。监控重试放大率、预算耗尽率、重复错误率和副作用率，下线成功率过低的规则。

**相关知识点：** Retry Budget、错误指纹、指数退避、随机抖动、熔断器、幂等键、无进展检测、死信队列。
