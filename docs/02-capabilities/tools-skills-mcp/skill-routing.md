# Skill 发现、检索与路由

> 所属章节：[工具、Skills 与 MCP](README.md)｜本文件共 **24** 题。

<a id="tool-003"></a>
### 1. MCP和Skills有什么区别？（豆包一面）

**MCP 解决能力的标准化接入，Skill 解决任务经验的封装复用**。二者层级不同，通常组合使用。

| 维度 | MCP | Skill |
|---|---|---|
| 定位 | 模型与外部系统的连接协议 | 可复用的任务级能力 |
| 核心内容 | Tools、Resources、Prompts及通信规范 | 指令、流程、约束、知识和工具组合 |
| 粒度 | 偏原子操作与数据访问 | 偏完整任务或工作流 |
| 发现方式 | Client从Server枚举能力 | Router按意图检索和选择 |
| 标准程度 | 有统一协议规范 | 依赖平台实现 |

1. **MCP属于接入层**：Server 暴露工具、资源和提示模板，Client 负责连接、能力发现、参数传输和结果接收，减少为每种数据源重复开发连接器。
2. **Skill属于编排层**：Skill 描述任务步骤、输入输出、质量标准、异常处理及适用边界，可以调用一个或多个本地 Tool 或 MCP Tool。
3. **职责边界**：MCP 不宜承载复杂业务流程，Skill 不应重复实现认证和协议适配。企业可将稳定原子能力封装为 MCP Tool，将高频、步骤稳定、结果可评价的任务沉淀为 Skill。

例如，MCP 提供读取代码和查询缺陷，Code Review Skill 规定检查顺序、风险规则、报告结构及失败降级：前者描述“能连接什么”，后者描述“怎样完成任务”。

**验证指标：** 工具选择准确率、调用成功率、参数错误率、P95 延迟和失败恢复率。

**相关知识点：** MCP Client、MCP Server、Tools、Resources、Tool Discovery、Skill Router、Workflow、能力编排。

### 2. 用户输入进来以后，系统如何匹配相关Skill？（DeepSeek二面）

Skill 匹配应采用 **规则过滤、混合召回、语义重排、约束校验、置信度决策** 的多阶段路由，不能把全部 Skill 描述直接交给大模型选择。

1. **请求理解**：提取意图、实体、目标、上下文、仓库类型和风险等级，将多轮对话改写为独立查询，并识别缺失的必填参数。
2. **候选过滤与召回**：按租户、权限、环境、版本过滤不可用 Skill，再融合 BM25 关键词召回与 Embedding 语义召回，通过 RRF 合并排名，将候选缩小到十几个。
3. **精排与决策**：Reranker 综合语义相关度、输入 Schema 匹配度、历史成功率、延迟、成本、用户偏好和风险分数。Top1 超过阈值且与 Top2 分差足够时直接选择；置信度不足则澄清、返回 Planner，或退化为通用推理。
4. **执行反馈**：执行前校验适用边界和依赖 Tool；执行后将成功、失败、人工改选记录为评测样本，线上反馈需审核，避免错误经验强化。

| 路由方式 | 优势 | 局限 |
|---|---|---|
| 规则 | 确定、快速、可审计 | 难覆盖语义表达 |
| 向量检索 | 语义召回能力强 | 相似能力容易混淆 |
| LLM路由 | 能理解复杂上下文 | 成本高、稳定性较弱 |
| 混合路由 | 兼顾召回与精度 | 工程和评测复杂 |

评估需使用真实标注集，关注 **Recall@K、Top1准确率、MRR、误路由率、拒识准确率和端到端成功率**；其中高风险 Skill 应提高选择阈值。

**相关知识点：** BM25、Embedding、RRF、Reranker、Skill Router、置信度阈值、拒识、在线反馈。

### 3. 如何自动发现可沉淀的Skill？

自动发现应从执行轨迹中**识别重复且成功的任务模式，生成候选而非自动发布Skill**；最终仍需领域审核、脱敏、评测与安全审查。

1. **数据准备**：采集脱敏后的用户意图、计划步骤、工具序列、参数形态、结果、耗时、成本、人工修正和满意度；剔除失败、越权、偶然捷径及包含敏感信息的轨迹，并保留来源与版本。
2. **模式挖掘**：对意图和目标做语义聚类，对工具调用序列做频繁模式或流程挖掘；结合输入输出Schema抽取可参数化变量，识别共同前置条件、分支和终止状态。
3. **候选评分**：依据频率、覆盖用户、成功率、步骤稳定度、人工节省、风险与维护成本排序。高频但成功率低的模式应进入问题诊断，而非直接沉淀。
4. **生成验证**：由系统生成候选契约、流程草案和评测样例，领域专家确认语义与边界；在沙箱中重放历史案例并加入反例、权限和故障测试，通过后灰度发布。

| 方法 | 发现对象 | 局限 |
|---|---|---|
| 语义聚类 | 相似目标 | 可能混合不同业务语义 |
| 序列挖掘 | 重复工具路径 | 忽略上下文条件 |
| 流程挖掘 | 分支与瓶颈 | 依赖高质量事件日志 |
| 人工标注 | 高价值经验 | 成本高、覆盖有限 |

上线后监控候选命中率、复用率和相对无Skill基线的增益，防止将历史偏差固化为标准能力。

**相关知识点：** 轨迹挖掘、语义聚类、频繁序列、流程挖掘、参数抽取、候选评分、离线重放、基线评测、人机协同。

### 4. Planner如何决定调用Skill还是重新规划？

Planner应先判断现有Skill是否对当前目标形成**高覆盖、前置条件满足、风险可接受且质量达标**的执行路径；满足则调用，否则重新规划或组合多个Skill。

1. **候选检索**：结构化目标、输入、约束和结果，先按权限、环境、Schema、依赖和风险过滤，再以语义、成功率、成本和延迟排序。
2. **适配判断**：比较Skill的前置条件、能力边界和输出能否覆盖计划中的子目标。完全覆盖且置信高时直接调用；部分覆盖时把Skill作为子计划；无合适候选或关键参数缺失时重新规划或澄清。
3. **执行中决策**：Skill运行后由验证器检查后置条件和证据。可恢复失败按Skill定义重试或降级；前置条件变化、连续无进展或输出不满足目标时返回Planner，但应携带已完成状态，避免从头重复。
4. **防止振荡**：记录计划和Skill调用指纹，限制重规划次数、总步骤、Token与费用；同一失败原因未变化时不得重复选择原Skill。高风险写入后仅能走补偿或人工路径。

| 情况 | 推荐动作 | 原因 |
|---|---|---|
| 完全匹配且已验证 | 调用Skill | 复用稳定能力 |
| 部分目标匹配 | Skill作为子计划 | 减少重复规划 |
| 权限/前置条件不满足 | 排除或澄清 | 当前不可执行 |
| 执行后目标未满足 | 带状态重规划 | 保留已有进展 |

评测需观察Skill命中准确率、无效重规划率、循环率、端到端成功率及相对从零规划的成本收益。

**相关知识点：** 能力匹配、前置条件、后置条件、混合检索、计划修复、状态继承、调用指纹、预算控制、拒选机制。

### 5. Skill如何避免能力重叠？

避免重叠需要在设计与运行两端建立**清晰能力边界、发布前重复检测、冲突路由和持续合并机制**，而不是仅依赖命名不同。

1. **契约化边界**：每个Skill必须声明目标、领域、适用与禁用条件、输入输出、前后置条件、风险和示例反例。描述“何时不能用”通常比增加宽泛关键词更能区分能力。
2. **发布前检测**：将新Skill与Registry中的描述、Schema、工具序列和评测样例做关键词及向量相似度比较；对高相似候选执行交叉测试，判断是同一能力的版本、参数变体，还是确有不同业务语义。
3. **优先复用扩展**：核心流程一致时使用参数、策略表、领域配置或子Skill组合；只有权限边界、成功标准或流程本质不同才新建。禁止复制既有Skill后仅修改Prompt名称。
4. **运行冲突处理**：Router先按权限和前置条件过滤，再按专用度、成功率、成本与版本状态排序；多个候选接近时澄清或使用显式优先级，避免随机选择。

| 重叠类型 | 推荐处理 | 示例 |
|---|---|---|
| 同义能力 | 合并并保留别名 | “邮件总结/总结邮件” |
| 参数差异 | 配置化 | 不同语言输出 |
| 领域差异 | 公共基类+领域策略 | 法务与财务审阅 |
| 风险差异 | 独立Skill | 草稿与生产写入 |

持续监控候选同时命中率、用户改选率和结果差异；对长期竞争且无显著差异的Skill合并、弃用并提供迁移映射。

**相关知识点：** 能力边界、重复检测、向量相似度、交叉评测、专用度、Router冲突、别名、Skill合并、迁移映射。

### 6. Skill Router应该如何设计？

Skill Router应采用**规则硬过滤、混合召回、学习重排、低置信拒选**的分层架构，使正确性、安全性和成本分别由适合的机制负责。

1. **意图表示**：将请求转成目标、领域、实体、输入类型、期望输出、风险、时限和会话状态；用户明确指定Skill时仍需做权限及前置条件校验，不可直接放行。
2. **候选过滤**：依据租户、身份、环境、生命周期、Schema兼容、依赖可用、风险和预算剔除不可执行项。硬约束由规则或Policy Engine处理，禁止交给LLM自行遵守。
3. **召回与重排**：用关键词、标签、向量召回Top-K，再按语义、专用度、成功率、成本和延迟重排；可让LLM判别，但只输出受限ID。
4. **决策门控**：分数超过阈值且领先明显时执行；多候选接近则澄清或选择低风险方案；无匹配时返回Planner重新拆解，不能强行选择。路由结果固定Skill版本并记录理由。

| 层次 | 技术 | 主要作用 |
|---|---|---|
| 硬过滤 | 规则/策略 | 安全与可执行性 |
| 召回 | BM25+向量 | 保证覆盖 |
| 重排 | 模型/统计评分 | 提高Top-1精度 |
| 门控 | 阈值与差值 | 拒选和澄清 |

离线评估Top-1准确率、Recall@K、拒选准确率，线上跟踪改选率、端到端成功率、延迟和成本，并按版本和任务类型切片。

**相关知识点：** Intent Routing、Hybrid Retrieval、Metadata Filter、Reranker、置信阈值、Margin、拒选机制、Policy Engine、路由评测。

### 7. 多个Skill都匹配时如何决策？

多个Skill匹配时应先**淘汰不可执行项，再按专用度、质量、风险和成本重排；差异不足时澄清或拒选**，不应随机或只按向量分数最高者执行。

1. **硬过滤**：移除权限不足、环境不符、已弃用、输入Schema不兼容、依赖不可用及风险超预算的Skill。用户指定某项也必须通过这些检查。
2. **适配评分**：比较目标覆盖、前置条件、实体与领域匹配、输出可用性；在同等质量下优先边界更窄的专用Skill，避免宽泛描述长期压制专业能力。
3. **运行指标**：综合同类任务历史成功率、人工纠正、延迟、一次成功成本、时效和风险。评分应按任务类型切片并设置最低样本量，防止新Skill因数据少被永久冷启动。
4. **决策门控**：Top-1超过阈值且与Top-2差距足够才自动执行；差距小则提出能区分候选的最少问题。若任务包含多个独立子目标，由Planner组合Skill而非强选一个。

| 冲突情况 | 推荐动作 | 原因 |
|---|---|---|
| 通用与专用同时匹配 | 选满足条件的专用项 | 边界更明确 |
| 分数接近且高风险 | 澄清/审批 | 降低误执行 |
| 各覆盖部分目标 | 组合或重新规划 | 单项不完整 |
| 均低于阈值 | 拒选 | 避免强行匹配 |

记录候选列表、各项得分、过滤理由和最终选择，通过用户改选率、严重误路由率及端到端成功率持续校准。

**相关知识点：** 候选过滤、专用度、Reranking、置信阈值、Margin、澄清问题、Skill组合、冷启动、拒选机制。

### 8. Skill匹配准确率如何评估？

Skill匹配评估应覆盖**正确选择、正确拒选、候选排序和最终任务效果**，并对高风险误匹配单独计量；单一总体准确率容易掩盖长尾与类别不均衡。

1. **构建数据集**：从真实请求抽样脱敏，由专家标注可接受Skill、需澄清和无匹配场景；加入同义表达、信息缺失、相似能力与对抗输入。
2. **离线指标**：单标签看Top-1 Accuracy，多答案看Precision、Recall、F1；召回看Recall@K，排序看MRR/NDCG；拒选测识别率与误拒率。
3. **风险加权**：把高风险Skill误选、跨权限选择和低风险漏选赋予不同损失，计算Cost-weighted Error；按领域、语言、租户、请求长度和新旧Skill切片，输出混淆矩阵。
4. **线上验证**：灰度记录用户改选、澄清率、执行前拦截、端到端成功、人工接管和严重事件；使用A/B或影子流量与旧Router比较，避免离线标签无法反映业务结果。

| 指标 | 衡量内容 | 适用阶段 |
|---|---|---|
| Top-1 Accuracy | 首选是否正确 | 最终路由 |
| Recall@K | 候选是否召回 | 召回层 |
| MRR/NDCG | 正确项排序位置 | 重排层 |
| 拒选准确率 | 无合适Skill识别 | 门控层 |

数据集定期更新并保留稳定回归集；Router、Skill描述或Embedding变化均需重测。

**相关知识点：** Top-1 Accuracy、Precision、Recall、F1、Recall@K、MRR、NDCG、混淆矩阵、风险加权错误、校准。

### 9. Skill召回率和精确率如何平衡？

平衡策略是**召回层适度放宽保证候选覆盖，重排与门控层提高最终精确率，并按误选风险动态设置阈值**，不必用一个模型同时完成所有目标。

1. **分层优化**：关键词、标签与向量多路召回较大的Top-K，去重后再按语义、前置条件、专用度、质量、成本和风险重排；执行前用Schema与权限硬校验，降低宽召回带来的误调用。
2. **风险差异化**：高风险Skill提高相似度阈值、要求更大Top-1与Top-2差值，并在不确定时澄清或审批，优先精确率；低风险只读能力可降低阈值，优先召回率并允许用户纠正。
3. **数据与描述**：补充容易漏召回的同义表达和长尾样例；为经常误召回的Skill增加禁用条件、反例和领域标签。合并语义重复Skill，减少系统性竞争。
4. **阈值选择**：在验证集绘制Precision-Recall曲线，以业务错误成本选择Top-K、阈值和Margin，而非追求最高F1；线上按领域、语言和风险分别校准。

| 侧重点 | 适用场景 | 代价 |
|---|---|---|
| 高召回 | 低风险发现、候选生成 | 候选多、重排成本高 |
| 高精确 | 高风险自动执行 | 漏选与澄清增加 |
| 混合分层 | 大多数生产系统 | 架构与评测更复杂 |

最终同时监控Recall@K、Top-1 Precision、拒选率、澄清率、严重误路由和端到端成功率，防止局部指标改善而业务效果下降。

**相关知识点：** Precision-Recall曲线、Top-K、Reranker、置信阈值、Margin、风险分层、拒选、校准、错误成本。

### 10. 为什么不能直接让 Agent 调用 Tool，而要增加 Skill 层？

简单、低风险、少工具任务可直接调用Tool。复杂场景引入Skill，是为了把**领域方法、稳定流程和治理策略**从临时推理中抽离。

1. **降低规划不确定性**：Tool数量增加后，模型需每次重新选择顺序、参数和终止条件，容易误选、循环与漏步骤；Skill把验证过的组合路径作为候选能力，缩小搜索空间。
2. **沉淀领域经验**：SOP、规则、样例、前后置条件和失败处理无法仅靠原子Tool表达。Skill使这些程序性知识可版本化、复用和评测，避免散落在系统Prompt中。
3. **强化治理**：Skill可声明所需权限、风险、预算、审批与依赖，并提供端到端审计；平台能对“完成退款处理”做整体门禁，而不只是分别控制查询和写入接口。
4. **提升演进能力**：底层Tool替换时调整Skill实现，Planner继续依赖稳定目标契约；相同Tool也能组合不同能力。

| 架构 | 优点 | 适用范围 |
|---|---|---|
| Agent直接调用Tool | 简单、开销低 | 少量低风险工具 |
| Agent→Skill→Tool | 复用、可控、易评测 | 复杂稳定业务 |
| 固定Workflow→Tool | 确定性最高 | 强监管固定流程 |

Skill层有目录、版本和路由成本，只有收益超过成本时才引入；它也不能替代Tool侧鉴权与幂等。

**相关知识点：** 抽象分层、搜索空间、程序性知识、SOP、目标级契约、Skill Router、端到端治理、Tool鉴权、Build vs Buy。
<a id="tool-166"></a>
### 11. Skill Router 应该基于规则还是基于 LLM？

生产级Skill Router应采用**规则确定边界，检索与LLM理解语义，门控决定是否执行**的混合方案；不存在所有场景通用的单一路由器。

1. **规则承担硬约束**：权限、租户、环境、风险、额度、数据等级、Skill状态和明确命令都应由规则处理，特点是确定、快速、可审计。高风险能力不能因LLM判断“合适”而绕过规则。
2. **LLM处理语义歧义**：当用户表达多样、上下文较长、类别边界难写成条件时，LLM可在已过滤的候选集中判别目标、所需输入与缺失信息；输出必须是受限Skill ID或澄清，不允许生成新能力名称。
3. **检索控制规模**：先以关键词、标签和向量召回Top-K，再交给轻量模型或LLM重排，避免把完整Skill目录塞入上下文，降低Token、延迟和错误竞争。
4. **选择依据**：类别少且边界稳定时规则优先；长尾多、变化快时增加LLM；安全等级越高，自动执行阈值越严。高频稳定语义可逐步下沉为规则。

| 路由方式 | 最强能力 | 主要短板 |
|---|---|---|
| 规则 | 确定性与合规 | 泛化差、维护膨胀 |
| LLM | 语义与上下文理解 | 概率性、成本与漂移 |
| 混合 | 兼顾边界和泛化 | 工程复杂度较高 |

用严重误路由、拒选、准确率、P95延迟、单次成本和规则维护工时联合评估，并对模型及目录变更执行回归。

**相关知识点：** Rule Routing、LLM Routing、Hybrid Routing、候选集约束、硬策略、置信阈值、规则下沉、模型漂移。
<a id="tool-167"></a>
### 12. 多个 Skill 同时匹配时如何排序？

排序应采用**硬约束先行、任务适配为主、线上质量校正、风险成本约束**的多目标评分，而不是单独依赖语义相似度或历史调用量。

1. **先过滤后排序**：先剔除未授权、状态不可用、环境不符、前置条件失败、Schema不兼容和依赖缺失项。硬约束不参与加权，任何一项失败即淘汰。
2. **核心相关性**：评分任务目标覆盖、领域与实体匹配、输入可满足度、输出可用性、专用度及反例冲突；对明确领域优先专用Skill，防止通用描述因词汇丰富得分过高。
3. **运营质量**：加入同类任务成功率、人工纠正、稳定性、数据新鲜度、版本状态和样本置信区间；新Skill使用离线评测与小流量探索，避免冷启动无曝光，也防止下载量形成马太效应。
4. **代价与风险**：质量接近时优先低风险、低成本、低延迟版本；高风险候选提高阈值。最终分数需校准，Top-1与Top-2差距不足时澄清。

| 特征组 | 作用 | 是否可否决 |
|---|---|---|
| 权限/前置条件 | 判断可执行 | 是 |
| 语义与专用度 | 判断适配 | 否 |
| 成功率与时效 | 判断质量 | 否 |
| 风险与成本 | 控制代价 | 高风险可否决 |

权重应按领域和风险分层，通过NDCG、MRR、Top-1准确率、改选率及端到端收益调优，并记录每次排序的特征与理由。

**相关知识点：** Learning to Rank、多目标排序、硬过滤、专用度、置信区间、冷启动、Margin、分数校准、NDCG、MRR。
<a id="tool-168"></a>
### 13. 如何提高 Skill 召回率和准确率？

提升效果需要同时优化**Skill语义资产、混合检索、重排门控和高质量反馈数据**，并分阶段诊断“没召回”还是“召回后排错”。

1. **改进语义资产**：为Skill补充清晰目标、适用与禁用条件、领域标签、同义词、正反例及输入输出Schema；拆分过宽能力、合并同义能力，减少描述重叠和索引噪声。
2. **混合召回**：并行使用名称/别名精确匹配、BM25、标签层级、向量和历史案例，合并去重；按语言、领域选择合适Embedding和切分方式，利用查询改写扩展简称，但保留原意。
3. **过滤与重排**：权限、环境、状态和Schema先硬过滤；Reranker综合语义、专用度、质量、成本与风险。按任务类型校准阈值、Top-K和Top-1差值，低置信时澄清或拒选。
4. **数据闭环**：收集用户改选、人工标注、无匹配请求和困难负样本，定期训练或调整排序；对新Skill提供受控探索。模型、描述和索引变化都运行稳定回归集。

| 问题表现 | 优先改进 | 对应指标 |
|---|---|---|
| 正确项不在候选 | 描述、查询、召回通道 | Recall@K |
| 正确项排名靠后 | Reranker与困难负样本 | MRR/NDCG |
| 错误项被自动执行 | 阈值、反例、门控 | Top-1 Precision |
| 经常无合适项 | 拒选数据与目录建设 | 拒选准确率 |

最终以任务成功率和严重误选率验收，避免只提高相似度分数。

**相关知识点：** 混合检索、Query Rewrite、Embedding、BM25、困难负样本、Reranker、阈值校准、Recall@K、回归集。
<a id="tool-181"></a>
### 14. Coding Agent 的核心 Skill 应该有哪些？

Coding Agent核心Skill应覆盖**理解代码库、计划变更、可靠编辑、质量验证和安全交付**，而非只生成代码。

1. **仓库理解**：目录与符号检索、依赖和调用图分析、构建系统识别、规范与历史变更读取、相关测试定位；输出证据化上下文，避免把整个仓库塞入模型。
2. **任务规划**：需求澄清、影响范围分析、风险分级、文件与步骤计划、验收条件生成；小改动可直接执行，跨模块或高风险任务先展示计划。
3. **代码变更**：局部补丁、重构、接口适配、依赖升级、测试与文档同步；使用结构化编辑或补丁，保护用户未提交修改，并限制可写路径和命令。
4. **质量验证**：运行格式化、静态检查、类型检查、单元与集成测试，分析失败根因并有限修复；比较变更前后行为，防止只让测试“变绿”而改变需求。
5. **安全交付**：密钥检测、依赖与漏洞检查、危险命令审批、diff审查、提交说明和回滚建议；所有命令与文件修改可追踪。

| Skill层 | 代表能力 | 核心约束 |
|---|---|---|
| 理解 | 搜索、符号、依赖分析 | 来源可追溯 |
| 变更 | 编辑、重构、生成测试 | 最小补丁 |
| 验证 | lint、类型、测试 | 失败可解释 |
| 交付 | diff、提交、PR摘要 | 人工确认高风险动作 |

进阶能力可加入Bug定位、性能分析、迁移和Code Review，但应建立在可靠工具执行、检查点与沙箱隔离之上。

**相关知识点：** Repository Understanding、代码检索、影响分析、结构化编辑、最小补丁、测试金字塔、静态分析、Diff Review、安全交付。

### 15. Agent 如何发现高频任务？

Agent发现高频任务应基于**脱敏事件数据、统一任务归一化和语义聚类**，同时区分真实业务需求、失败重试与系统循环，不能直接按原始Prompt计数。

1. **采集事件**：记录租户、用户、时间、目标摘要、输入输出类型、工具序列、结果、耗时、成本、人工修正与满意度；正文按最小原则脱敏或仅存特征，明确用途、留存周期和访问权限。
2. **任务归一化**：去除日期、ID、姓名等实例变量，将请求映射为意图、领域、实体槽位和期望结果；合并同义表达，拆分一个请求中的多个独立目标，避免表述差异稀释频率。
3. **聚类与序列分析**：结合关键词、Embedding聚类、主题模型和工具调用序列形成任务簇；用时间窗统计独立用户数、重复使用率、周期性、成功率和人工耗时，而非仅看调用次数。
4. **质量过滤**：排除测试流量、机器人流量、重试风暴和循环调用；高频失败簇先定位产品缺陷，高频成功且轨迹稳定簇才作为Skill候选。低频高风险任务另行纳入。
5. **人工确认**：领域专家审阅簇的共同目标、边界和价值，抽样验证聚类纯度，再进入候选Workflow或Skill评测。

| 信号 | 含义 | 处理 |
|---|---|---|
| 高频+高成功+稳定轨迹 | 可复用模式 | 候选Skill |
| 高频+高失败 | 系统或流程问题 | 优先修复 |
| 高频+低独立用户 | 个别用户循环 | 排查异常 |
| 低频+高风险 | 治理需求 | 候选受控Workflow |

**相关知识点：** 任务归一化、语义聚类、Embedding、序列挖掘、独立用户、聚类纯度、重试去重、隐私治理、候选Skill。
<a id="tool-199"></a>
### 16. 经验库如何设计？

经验库应设计为**带来源、时效、置信、作用域和验证状态的经验资产层**，支持检索与Skill发现，但不能成为未经治理的对话堆积。

1. **数据模型**：每条经验包含目标、情境、采取的动作、结果、证据、来源事件、主体与租户、时间、环境、模型/工具版本、置信度、敏感等级、有效期和审核状态；成功与失败经验都保存。
2. **分层存储**：原始轨迹进入受限事件仓，结构化经验进入关系或文档库，语义字段建立向量与关键词索引，大文件存对象仓；权威元数据与检索索引分离，索引可重建。
3. **写入治理**：从轨迹抽取候选后做脱敏、去重、结果验证、冲突检测和质量评分；模型自评只作弱信号。高风险经验需专家审核，任何更正采用新版本而非静默覆盖。
4. **检索应用**：先按租户、身份、领域、环境、时效和验证状态过滤，再混合召回与重排；返回来源、适用条件和不确定性。经验可辅助规划、故障诊断和候选Skill生成。
5. **生命周期**：支持合并、降权、过期、撤销、用户查看和删除；维护经验—轨迹—Skill血缘，来源删除或规则变化时进行影响分析。

| 层次 | 内容 | 可信度 |
|---|---|---|
| 原始轨迹 | 完整执行事件 | 未归纳 |
| 候选经验 | 抽取的模式 | 待验证 |
| 已验证经验 | 有证据与适用范围 | 可检索使用 |
| Skill | 契约化程序性知识 | 经评测发布 |

监控经验命中后的任务增益、错误引用、过期命中和隐私删除完成率，定期清理低价值条目。

**相关知识点：** 经验库、数据血缘、混合检索、来源可信度、时间衰减、冲突检测、隐私删除、候选经验、Skill蒸馏。
<a id="tool-211"></a>
### 17. Coding Agent如何匹配代码相关Skill？

Coding Agent匹配Skill应结合**用户意图、仓库事实、变更阶段、技术栈和权限风险**，代码上下文的重要性不低于自然语言相似度。

1. **任务解析**：识别解释、Review、修复、重构、测试、迁移或发布，提取目标符号、错误、期望与变更范围；不足时先只读探索。
2. **仓库画像**：从清单、锁文件、构建配置、扩展名、CI和Git状态识别语言、框架、包管理器及测试工具；事实由工具获取。
3. **候选过滤**：按Skill支持的语言、框架、任务阶段、输入Schema、所需工具、环境、读写权限和风险过滤；不兼容、已撤销或会覆盖未提交修改的能力排除。
4. **混合排序**：结合请求与Skill描述的关键词/向量相似度、仓库标签精确匹配、目标符号类型、历史同仓成功率、成本和专用度重排；专用Skill在前置条件满足时优先。
5. **验证与反馈**：低置信或候选接近时先澄清或生成只读计划；选定后固定版本，用测试与开发者改选更新评测。

| 信号 | 示例 | 权重特点 |
|---|---|---|
| 用户意图 | “修复空指针” | 决定任务类型 |
| 仓库事实 | Maven、Spring | 强过滤 |
| 当前阶段 | 规划/实现/Review | 避免错用 |
| 权限风险 | 只读/可写/发布 | 可一票否决 |

**相关知识点：** Repository Profiling、意图识别、技术栈检测、Metadata Filter、混合检索、专用度、只读探索、Skill Router。
<a id="tool-213"></a>
### 18. Code Review Skill如何设计？

Code Review Skill应采用**确定性检查打底、LLM语义审查补充、证据化输出和风险门控**，目标是发现高价值问题而非生成大量风格意见。

1. **审查范围**：输入基线、目标提交、需求和范围，解析Diff及受影响符号；忽略生成文件，识别API、数据模型、调用者与测试变化，保护敏感信息。
2. **检查流水线**：先运行格式、lint、类型、编译、测试、依赖和安全扫描，再由模型检查逻辑正确性、边界条件、并发、事务、错误处理、资源释放、兼容性和需求一致性。
3. **证据与去重**：每条意见必须指向文件与行、给出触发场景、影响、严重度和最小修复建议；合并工具与模型重复发现。无法由代码证实的意见标为疑问，不得表述为事实。
4. **风险门控**：安全、资金、权限、数据库迁移和公共API变更提高审查级别，并要求Code Owner批准；Skill不能自动合并。低风险Suggestion不阻塞交付。
5. **评测反馈**：用真实缺陷和干净变更计算Precision、Recall、严重漏检、误报及采纳率；拒绝意见作为困难负样本。

| 级别 | 含义 | 处理 |
|---|---|---|
| Blocking | 高概率严重缺陷 | 修复或责任人豁免 |
| Warning | 有风险需确认 | 解释或修复 |
| Suggestion | 可维护性改进 | 非阻塞 |
| Question | 证据不足 | 补充上下文 |

**历史别名：** `TOOL-182`。

**相关知识点：** Diff Analysis、静态分析、语义审查、证据定位、风险分级、Code Owner、误报率、严重漏检、困难负样本。
<a id="tool-215"></a>
### 19. 如何根据代码上下文提升Skill匹配准确率？

提升准确率的关键是把请求与**仓库、符号、变更、错误和开发阶段**联合表示，并用结构化代码特征做硬过滤，文本向量只承担语义召回。

1. **选择有效上下文**：提取当前文件、符号、Diff、诊断、堆栈、测试失败和用户实体；通过符号图补充定义、引用、调用者和测试，避免加载整个仓库。
2. **仓库与阶段画像**：识别语言、框架、依赖、构建器、模块、Git状态以及当前处于理解、实现、Review、修复或发布阶段。相同请求在不同阶段应匹配不同Skill。
3. **Skill元数据增强**：声明支持语言/框架版本、任务类型、文件模式、符号类型、错误类别、所需上下文、读写权限和反例；用结构化字段先过滤，再做关键词与Embedding召回。
4. **上下文重排**：Reranker输入目标、代码摘要、仓库标签和候选Skill，综合专用度、同仓成功率、成本与风险；代码使用AST/符号表示。
5. **置信门控**：候选接近时先只读探测或澄清；记录改选和测试结果，形成按技术栈切片的困难负样本。

| 上下文 | 主要作用 | 风险 |
|---|---|---|
| 仓库画像 | 强过滤 | 多技术栈误判 |
| 符号/调用图 | 精确任务范围 | 索引过期 |
| Diff与诊断 | 判断当前意图 | 临时噪声 |
| 历史成功 | 排序校正 | 反馈偏差 |

**相关知识点：** Code Context、AST、Symbol Graph、Repository Profiling、Metadata Filter、Reranker、困难负样本、置信门控。
<a id="tool-216"></a>
### 20. 为什么Skill匹配需要向量检索？

Skill匹配需要向量检索，因为用户意图与Skill描述常有**同义表达、跨语言和词汇不重合**；Embedding能召回语义候选，但不能单独决定执行。

1. **解决词面差异**：用户说“排查接口变慢”，Skill可能叫“API性能诊断”，关键词交集很少；向量将目标语义映射到相近空间，提升长尾和自然表达的召回率。
2. **适合能力描述**：Skill包含目标、场景、示例和领域语义；向量可比较请求与这些字段，也可用历史案例召回。
3. **固有限制**：相似不等于可执行。向量难严格判断权限、版本、输入Schema、环境和否定条件，也可能把“创建用户”与“删除用户”因主题相似而混淆，存在模型与索引漂移。
4. **正确架构**：先按租户、权限、状态、风险和兼容性做Metadata Filter，再融合BM25与向量召回，使用Reranker综合专用度和质量；低置信或候选接近时澄清或拒选。

| 方法 | 优势 | 短板 |
|---|---|---|
| 精确/关键词 | 名称、术语、ID准确 | 同义表达召回弱 |
| 向量检索 | 语义泛化强 | 边界和否定易混淆 |
| 规则过滤 | 约束确定 | 不理解开放语义 |
| 混合检索 | 兼顾覆盖与精度 | 需调权与评测 |

评估看Recall@K、Top-1精度、拒选和严重误匹配，并分领域选择Embedding、Top-K与阈值。

**相关知识点：** Embedding、语义检索、Metadata Filter、Hybrid Search、BM25、Reranker、Recall@K、向量漂移、拒选机制。
<a id="tool-219"></a>
### 21. 如何解决Skill语义重叠问题？

Skill语义重叠应从**资产边界、索引表示、排序门控和目录治理**四处同时处理；仅调整向量阈值无法解决能力本身定义模糊。

1. **澄清边界**：为每个Skill补齐目标、适用与禁用条件、前后置条件、输入输出、领域、风险和正反例；把“查询订单”和“取消订单”等相近主题但不同动作显式区分。
2. **检测重叠**：发布前比较名称、描述、Schema、工具序列和评测样例的关键词与向量相似度；对高相似候选做交叉评测和候选同时命中分析，识别同义、包含、部分交叉或仅主题相近。
3. **选择治理动作**：同义Skill合并并保留别名；核心流程相同、参数不同则配置化；存在包含关系时建立通用与专用层级；权限、风险或成功标准本质不同则独立保留。
4. **路由消歧**：先按权限、环境、Schema和前置条件过滤，再用Reranker关注动作、对象、阶段、专用度与反例；Top候选差距不足时提出最少澄清问题，不随机执行。
5. **持续清理**：监控候选共现率、用户改选率、混淆矩阵和结果差异，定期合并低价值项；更新描述后重建索引并运行稳定回归集。

| 重叠类型 | 处理方式 | 示例 |
|---|---|---|
| 完全同义 | 合并+别名 | “评审代码/代码审查” |
| 参数差异 | 单Skill参数化 | 输出语言不同 |
| 通用与专用 | 层级+专用优先 | 通用测试/Java测试 |
| 高低风险 | 分开并强过滤 | 草稿/生产写入 |

**相关知识点：** 语义重叠、反例、交叉评测、能力包含、Skill合并、专用度、混淆矩阵、澄清问题、索引重建。

### 22. Tool Calling与Skill Routing如何协同？

**Skill Routing先选完成目标的方法，Tool Calling再表达具体原子动作**；Runtime统一状态、权限和验证。

1. **路由**：将请求转为目标、约束和风险，按权限、环境及Schema过滤Skill，再召回、重排、门控并固定版本；不产生副作用。
2. **执行**：Skill按流程向模型提供有限Tool Schema；模型输出工具与参数，Runtime校验结构、语义、权限、预算和审批后才执行。
3. **回流**：Tool返回标准结果，截断、脱敏并标为不可信；Validator更新状态，必要时触发下一Tool、降级或人工接管。
4. **控制**：Router定能力白名单，Skill定工具候选，Policy Engine决定能否调用，业务服务最终鉴权；上层不能替代下层。
5. **观测**：Trace关联路由、Skill版本、Tool参数摘要和结果；限制步骤、重复指纹、Token、时间与成本。

| 阶段 | 核心决策 | 输出 |
|---|---|---|
| Skill Routing | 用哪种能力 | Skill ID与版本 |
| Planning | 执行哪些步骤 | 有界计划 |
| Tool Calling | 当前调用什么 | Tool与参数 |
| Policy/Executor | 是否执行 | 授权与结果 |

**相关知识点：** Skill Router、Tool Calling、Runtime、Tool Schema、Policy Engine、Validator、能力白名单、调用指纹、端到端Trace。

### 23. 如何设计百万级Skill检索系统？

百万级Skill检索应采用**分域路由、权限前置过滤、稀疏与向量分片召回、多级重排和分层缓存**，把全库问题缩小为可控候选集。

1. **数据与索引**：权威库保存租户、领域、版本、Schema、权限和状态；名称/标签建倒排，目标/场景/反例建向量，依赖建图。索引按租户或领域分片。
2. **查询路由**：解析身份、领域、语言、任务和环境，以ACL、状态与兼容性过滤少量分片；超大租户使用位图，禁止全局召回后鉴权。
3. **多阶段召回**：精确ID/别名、BM25与ANN并行取候选，以RRF或学习融合去重；轻量特征模型先粗排，Cross-Encoder或LLM只重排很小Top-K，最后进行置信门控。
4. **性能可靠性**：缓存热门查询、Skill向量和租户过滤结果，键包含版本与权限摘要；发布增量更新，撤销高优先级失效。设置超时、降级到关键词检索和跨分片熔断。
5. **质量运维**：以Recall@K、Top-1、P99、索引新鲜度、过滤正确率和成本验收；用影子索引评估调整，支持重建和双写切换。

| 层级 | 候选规模 | 目标 |
|---|---|---|
| 分域/权限过滤 | 百万→局部 | 安全、缩小空间 |
| 多路召回 | 局部→数百 | 保证Recall |
| 粗排 | 数百→几十 | 控制延迟 |
| 精排门控 | 几十→1/拒选 | 提高准确率 |

**相关知识点：** 倒排索引、ANN、索引分片、ACL Bitmap、RRF、Cross-Encoder、多级检索、增量索引、影子索引、双写切换。

### 24. 如何构建自学习的Skill推荐系统？

自学习推荐系统应采用**离线训练、在线受控探索、因果评估和安全门控**，学习排序偏好而不是让线上反馈直接修改Skill或权限。

1. **反馈定义**：记录曝光、位置、候选、分数、采用、改选、任务成功、接管、成本和风险；点击是弱反馈，经验证结果才是强标签。数据按租户脱敏隔离。
2. **召回排序**：规则过滤权限与环境，BM25和Embedding召回；Reranker使用任务语义、上下文、Skill质量、时效和团队偏好。个性化只能重排授权候选，不能扩大能力范围。
3. **学习机制**：离线用pointwise、pairwise或listwise方法训练，困难负样本来自相似误选；新Skill通过Bandit受控探索获得曝光，设置风险、流量和成本上限，高风险能力不自动探索。
4. **纠正偏差**：保存展示概率，使用倾向评分、反事实评估或随机小流量减少位置、流行度和选择偏差；按时间切分验证，防止用未来信息训练过去。
5. **发布防护**：新模型先离线回归、Shadow和A/B，监控NDCG、Top-1、任务增益、严重误选、ECE与成本；越界回滚。反馈进入版本化数据集。

| 信号 | 可信度 | 用法 |
|---|---|---|
| 点击/查看 | 低 | 兴趣弱信号 |
| 采用与改选 | 中 | 排序偏好 |
| 验证成功 | 高 | 主要质量标签 |
| 安全事件 | 极高负向 | 一票否决 |

**相关知识点：** Learning to Rank、Contextual Bandit、受控探索、倾向评分、反事实评估、曝光偏差、A/B测试、模型校准、安全门控。
