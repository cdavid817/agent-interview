### Agent工具调用系统应该怎么设计？工具如何注册、调用、鉴权、限流和追踪？（DeepSeek一面）

Agent 工具调用系统应采用 **注册、路由、策略、执行、观测** 五层架构，使模型负责选择工具和生成参数，确定性系统负责安全执行。

1. **注册**：Tool Registry 保存名称、用途、输入输出 JSON Schema、版本、地址、超时、幂等属性和风险等级；注册时检查 Schema、连通性及版本兼容性。
2. **调用**：Router 根据意图、权限、成本和可用性筛选工具，Executor 负责参数校验、协议适配、超时、重试及结果标准化。写操作必须携带幂等键，避免重复执行。
3. **鉴权**：OAuth2 或 JWT 负责认证，RBAC 与 ABAC 组合授权，依据用户、租户、资源、环境和风险动态决策；密钥应在运行时安全注入，不能进入提示词。
4. **限流与追踪**：按用户、租户、工具和供应商限制 QPS、并发、Token 与费用，配合熔断、降级和备用工具；用 OpenTelemetry 将 `trace_id` 贯穿推理与执行。

| 阶段 | 核心控制 |
|---|---|
| 调用前 | 参数、权限、预算、风险检查 |
| 调用中 | 限流、超时、隔离、熔断 |
| 调用后 | 结果校验、脱敏、审计、指标统计 |

日志记录工具版本、耗时、状态、重试次数和参数摘要，并对敏感信息脱敏；高风险调用还需审批。核心指标包括 **选择准确率、业务成功率、P95延迟和单位任务成本**。

**相关知识点：** Tool Registry、JSON Schema、RBAC、ABAC、幂等性、限流、熔断降级、OpenTelemetry、审计日志。

### Agent生成SQL、代码或Shell命令时如何设计沙箱，了解如何确认机制？（腾讯一面）

Agent 生成的 SQL、代码和 Shell 必须经过 **风险评估、隔离执行、最小权限、人工确认、审计恢复**，用户确认不能替代安全策略。

| 对象 | 主要风险 | 核心隔离措施 |
|---|---|---|
| SQL | 全表更新、删表、数据泄露 | 只读副本、事务、行数上限 |
| 代码 | 恶意依赖、资源耗尽、逃逸 | 容器或微虚机、资源配额 |
| Shell | 删除文件、提权、外连 | 工作区挂载、命令策略、网络隔离 |

1. **执行前**：基于 AST 静态分析 DDL、DML、递归删除、提权等行为，结合资源范围、可逆性、数据敏感度计算风险；默认拒绝未知命令，凭据按任务临时注入。
2. **沙箱隔离**：任务使用独立容器或微虚机，以非 root 用户运行；文件系统默认只读，仅挂载工作目录；用 cgroups 限制 CPU、内存、进程和时间，用网络策略限制外连。
3. **确认机制**：低风险只读操作可自动执行；中风险操作展示规范化命令、目标资源和影响范围后确认；生产写入、批量删除及权限变更实行双人审批。即使用户确认，命中禁止策略的操作仍须拦截。
4. **执行后**：SQL 写入使用事务或补偿日志；文件修改保留 diff、快照或 Git 分支；超时终止并回收资源。审计记录输入、审批人、策略版本、输出摘要和 `trace_id`。

确认页面必须展示 **执行什么、影响哪里、能否回滚、使用何种权限**，避免只有“是否继续”的无信息确认。

**历史别名：** `TOOL-012`。

**相关知识点：** 容器隔离、Firecracker、cgroups、seccomp、AST分析、最小权限、HITL、事务回滚、审计日志。

### Agent沙箱设计方案（附加专题）

Agent 沙箱应采用 **计算隔离、最小权限、文件与网络约束、资源配额、审计恢复** 的纵深防御，不能仅依赖危险命令黑名单。

1. **隔离运行时**：普通任务可使用容器；未知代码或多租户高风险任务采用 gVisor 或 Firecracker。进程以非 root 用户运行，启用 namespace、seccomp、能力裁剪和只读根文件系统。
2. **资源与文件控制**：通过 cgroups 限制 CPU、内存、进程、磁盘和时间；只挂载任务工作目录。宿主侧规范化真实路径，阻止符号链接和目录穿越。
3. **网络与凭据控制**：网络默认拒绝，仅按域名、端口放行；外部调用经过受控 Gateway。密钥由密钥系统签发最小作用域的短期令牌，任务结束立即吊销。
4. **生命周期与恢复**：执行前静态检查，运行中采集系统调用与资源事件；超时先优雅终止，再强制回收卷、网络和凭据。文件保留快照或 diff，数据库写入使用事务或补偿。

| 隔离方式 | 安全性 | 性能与适用场景 |
|---|---|---|
| 容器 | 中等，共享宿主内核 | 启动快，适合低风险任务 |
| gVisor | 较高，拦截系统调用 | 安全与兼容性的折中 |
| Firecracker | 高，独立内核 | 适合任意代码和强多租户 |

高风险任务运行在独立节点池，镜像需最小化、签名并持续修补；审计记录镜像版本、策略、输入摘要和 `trace_id`。

**验证指标：** 工具选择准确率、调用成功率、参数错误率、P95 延迟和失败恢复率。

**相关知识点：** 容器、gVisor、Firecracker、cgroups、seccomp、网络隔离、短期凭据、沙箱逃逸。

### Tool Registry 如何设计？

Tool Registry 应是 **工具元数据、版本、权限策略和运行状态的统一控制面**，不能只是保存工具名称与调用地址的静态配置表。

1. **元数据模型**：记录名称、描述、输入输出 JSON Schema、协议、版本、负责人、端点、超时、幂等属性、风险、权限、依赖和标签，并写明适用与禁用场景。
2. **注册流程**：工具提交后依次进行命名冲突、Schema、连通性、安全、权限和兼容性检查，通过审批后灰度发布。下线时先停止新流量，等待在途任务完成，再撤销端点与凭据。
3. **检索解析**：支持按租户、能力域、标签、关键词、语义向量、版本和健康状态查询；先过滤无权限或不可用工具，再把少量候选暴露给模型。调用侧使用逻辑工具名，由 Registry 解析实际版本。
4. **运行治理**：同步健康、业务成功率、P95 延迟、限流和熔断状态；保存废弃日期和替代工具。多租户隔离命名空间、凭据、配额和审计。

| 模块 | 核心职责 | 关键数据 |
|---|---|---|
| Catalog | 能力描述与检索 | Schema、标签、版本 |
| Policy | 权限和风险控制 | 租户、角色、审批 |
| Runtime | 流量与健康治理 | 指标、限流、熔断 |

Registry 只负责控制面，实际执行由 Tool Executor 完成；两者通过不可变版本和缓存失效事件协同，避免工具升级导致调用结果漂移。

**相关知识点：** Tool Registry、JSON Schema、语义版本、健康检查、灰度发布、权限过滤、Tool Executor。

### Agent 如何从数百个工具中快速选择最合适的工具？

数百个工具不能全部注入模型上下文，应采用 **硬过滤、混合召回、语义精排、置信度决策** 的多阶段选择，把候选压缩到少量高相关工具。

1. **请求理解**：从多轮对话中提取意图、实体、目标资源、环境、风险和缺失参数，改写为独立检索查询；明确不需要工具的纯推理请求，避免强制调用。
2. **硬过滤**：依据租户、用户权限、工具状态、版本兼容、风险等级和能力域排除不可调用项。此阶段由确定性规则完成，不能依靠模型自行遵守。
3. **混合召回**：BM25 负责工具名、错误码等精确匹配，Embedding 负责同义表达和语义召回，通过 RRF 合并排名，通常从数百个工具缩小到十至二十个。
4. **精排决策**：Reranker 综合语义相关度、输入 Schema 匹配度、历史成功率、P95 延迟、成本和风险。Top1 低于阈值或与 Top2 分差过小时，进行澄清或交给 Planner，而不是冒险调用。

| 阶段 | 目标 | 典型技术 |
|---|---|---|
| 过滤 | 排除无权限和不可用项 | RBAC、ABAC、状态规则 |
| 召回 | 保证正确工具进入候选 | BM25、Embedding、RRF |
| 精排 | 从候选中选出最优项 | Reranker、业务特征 |

执行后记录正确选择、人工改选和失败原因，经审核后进入离线评测集。核心指标包括 **Recall@K、Top1准确率、MRR、误调用率、拒识准确率和任务成功率**。

**相关知识点：** 工具检索、BM25、Embedding、RRF、Reranker、权限过滤、置信度阈值、Recall@K。

### OAuth2、JWT、RBAC、ABAC 在 Agent 中分别适用于哪些场景？

四者解决的问题不同：**OAuth2 负责委托授权，JWT 负责携带身份声明，RBAC 负责角色权限，ABAC 负责上下文条件决策**，企业 Agent 通常组合使用。

| 机制 | 核心作用 | Agent典型场景 |
|---|---|---|
| OAuth2 | 用户授权应用访问资源 | 代表用户访问邮箱、云盘 |
| JWT | 传递短期身份与声明 | Agent到Tool Gateway身份传递 |
| RBAC | 按岗位分配稳定权限 | 开发者、审核员、管理员 |
| ABAC | 按属性动态授权 | 租户、环境、时间、风险控制 |

1. **OAuth2**：适合用户委托和第三方 API，通过 scope 限定能力；使用短期 Access Token 和 PKCE，令牌不能交给模型。
2. **JWT**：是令牌格式而非授权模型，用于传递用户、租户、角色和过期时间。服务端校验签名、issuer、audience 与时间，并支持吊销。
3. **RBAC**：适合稳定组织岗位，管理成本低、便于审计；但角色过多会造成角色爆炸，难表达动态条件。
4. **ABAC**：依据主体、资源、操作和环境属性决策，适合多租户与高风险工具；需要统一属性源和可解释日志。

常用组合是 OAuth2 完成委托，JWT 承载身份，RBAC 给出基线，ABAC 根据资源、环境和风险收紧，服务端仍做资源级校验。

**相关知识点：** OAuth2、JWT、RBAC、ABAC、Scope、PKCE、Policy Engine、最小权限。

### 如何设计企业级工具权限模型？

企业工具权限应采用 **身份、能力、资源、环境、风险五维模型**，以 RBAC 提供基线、ABAC 动态收紧，坚持最小权限和默认拒绝。

1. **主体身份**：区分最终用户、Agent、服务账号和审批人，接入企业 IAM/SSO；每次 Tool Call 同时携带用户身份与工作负载身份，避免所有调用共用高权限账号。
2. **能力授权**：按工具及操作拆分 `read、create、update、delete、approve` 等权限，Registry 只向模型暴露已授权能力。工具版本或风险等级变化后必须重新评估授权。
3. **资源与环境授权**：ABAC 根据租户、项目、数据级别、资源所有者、测试或生产环境、时间和来源网络判断。即使拥有工具权限，也不代表可以访问全部数据。
4. **风险与审批**：低风险只读操作自动执行；有限范围写入需影响预览和确认；生产删除、发布、转账及提权采用双人审批；合规禁止项不能被用户确认覆盖。

| 层级 | 回答的问题 | 示例 |
|---|---|---|
| RBAC | 该岗位能用哪些能力 | 开发者可读测试日志 |
| ABAC | 当前条件下能否操作 | 仅本人项目、非生产 |
| Policy | 如何执行该操作 | 自动、确认、双审、拒绝 |

Policy Engine 在候选筛选和执行前至少校验两次，最终服务还要做资源级鉴权。临时提权使用有范围、有期限、可撤销的凭据，并记录申请原因、审批人、策略版本和 `trace_id`。

**相关知识点：** IAM、SSO、RBAC、ABAC、Policy Engine、最小权限、默认拒绝、临时提权、双人审批。

### 工具调用如何实现限流、配额和调用预算控制？

工具流量治理应同时控制 **瞬时速率、并发资源、周期配额和单任务预算**，并按用户、租户、Agent、工具及供应商多维度实施。

1. **限流与并发**：入口使用令牌桶限制 QPS 和突发量，Executor 使用信号量或隔离线程池控制并发；写操作还需按资源键串行化，防止并发副作用。超过容量时快速拒绝或进入有界队列。
2. **周期配额**：按小时、日或月统计调用次数、Token、外部 API 费用和数据量。配额采用分层账户，组织向团队、团队向用户分配，并为生产关键任务预留容量。
3. **任务预算**：任务开始时下发最大工具步数、单工具次数、总时长、Token 和费用。Planner 每次扩展计划前检查剩余额度，接近上限时禁止新分支，选择缓存、低成本工具或简化结果。
4. **超限处置**：返回明确的限制维度、恢复时间和剩余额度；对 429 遵循 `Retry-After`，禁止立即重试形成流量风暴。高优先级任务可使用审批后的临时额度，但必须设范围和有效期。

| 机制 | 控制对象 | 典型算法 |
|---|---|---|
| 限流 | 单位时间请求 | 令牌桶、滑动窗口 |
| 并发控制 | 同时运行任务 | 信号量、有界队列 |
| 配额 | 周期累计用量 | 分层计量账户 |
| 预算 | 单次Agent任务 | 步数、时间、费用上限 |

监控应包含拒绝率、排队时长、配额利用率、预算终止率和单位任务成本，并通过压测确定容量与降级阈值。

**相关知识点：** 令牌桶、滑动窗口、并发隔离、分层配额、调用预算、Retry-After、成本治理。
<a id="tool-036"></a>
### 如何设计熔断、降级和备用工具切换策略？

熔断、降级与备用切换应形成 **检测故障、隔离依赖、选择替代、验证恢复** 的状态机，目标是限制故障传播，而不是掩盖业务失败。

1. **熔断判定**：按工具版本和端点维护滑动窗口，综合错误率、慢调用率、连续失败及最小请求量触发熔断。`CLOSED` 正常放行，`OPEN` 快速失败，冷却后进入 `HALF_OPEN` 并仅允许少量探测流量。
2. **降级分层**：优先切换等价备用工具，其次使用满足时效要求的缓存、只读模式或简化功能，最后转人工。涉及资金、权限和生产写入时，无法证明等价则宁可停止，不能返回伪成功。
3. **备用选择**：Registry 记录能力、Schema、数据新鲜度、权限、成本、区域和历史质量。切换前重新做参数映射、授权与风险校验，禁止因主工具故障自动切换到权限更高的工具。
4. **恢复控制**：半开探测成功达到阈值后逐步放量，失败则重新打开；恢复期间采用滞后窗口，避免频繁抖动。写操作状态未知时先按幂等键查询，不直接在备用工具重放。

| 机制 | 触发条件 | 主要作用 |
|---|---|---|
| 熔断 | 错误率或慢调用超阈值 | 快速隔离故障 |
| 降级 | 主能力不可满足SLA | 保留有限服务 |
| 备用切换 | 存在等价健康能力 | 恢复完整能力 |

指标包括熔断次数、误熔断率、降级成功率、备用一致性、恢复时间和业务损失；策略需通过故障注入和灰度演练验证。

**相关知识点：** Circuit Breaker、滑动窗口、半开探测、降级、备用工具、幂等查询、故障注入。

### 如何防止第三方工具调用拖垮整个 Agent 系统？

第三方工具必须被视为 **不稳定且不完全可信的外部依赖**，通过舱壁隔离、超时预算、流量控制、熔断和结果边界限制爆炸半径。

1. **资源舱壁**：每个供应商或高风险工具使用独立连接池、线程池、队列和并发信号量，禁止共享无上限资源。单个池耗尽只能影响对应工具，不能阻塞 Agent 主线程和其他工具。
2. **时间与流量边界**：设置连接、读取、单次调用和任务总 Deadline；限制 QPS、并发、重试次数及排队长度。请求超限快速失败，重试采用指数退避与随机抖动，并计入任务预算。
3. **故障隔离**：持续统计错误率和慢调用率，触发熔断后快速拒绝；根据业务要求切换备用工具、缓存、只读或简化模式。探测恢复时逐步放量，避免依赖刚恢复就再次过载。
4. **数据与安全边界**：限制请求和响应大小、分页数量及流式持续时间；返回内容先做 Schema、业务码、敏感信息和提示注入检查。第三方凭据使用独立短期令牌，网络仅允许指定域名。

| 风险 | 保护机制 | 防止的影响 |
|---|---|---|
| 慢调用 | Deadline、取消 | 工作线程耗尽 |
| 流量过载 | 限流、有界队列 | 级联拥塞 |
| 连续失败 | 熔断、备用工具 | 重试风暴 |
| 超大或恶意响应 | 大小限制、内容检测 | 内存与上下文污染 |

还需按供应商监控 P95、失败率、队列利用率、熔断次数和成本，定期开展慢依赖、断网、错误响应和限流故障注入。

**相关知识点：** Bulkhead、连接池隔离、有界队列、Deadline、熔断、重试预算、响应限制、故障注入。
<a id="tool-041"></a>
### Tool Call 的结果如何写入 Memory 并参与后续推理？

工具结果应经过 **校验、提取、分层存储、权限过滤和检索注入**，只有可信且可复用的信息进入长期记忆。

1. **校验与归一化**：确认 HTTP、业务码和后置条件成功，记录来源、版本、时间、参数摘要和置信度；状态未知的结果只保存为轨迹。
2. **分层写入**：当前结果进入工作记忆，事件进入 Episodic Memory，稳定事实进入 Semantic Memory。大结果存对象存储，Memory 只保存摘要和引用。
3. **写入治理**：执行去重、敏感信息脱敏、权限标签、保留期和冲突检测。用户偏好与共享业务事实分开存储；低置信、过期或可变数据设置较短 TTL，防止长期污染。
4. **参与推理**：后续请求先按用户、租户和权限过滤，再按关键词、向量、时间和重要度排序；注入时携带来源与时间。

| 记忆层 | 适合内容 | 生命周期 |
|---|---|---|
| Working Memory | 当前工具结果和计划状态 | 单次任务 |
| Episodic Memory | 执行事件、成功经验 | 可衰减 |
| Semantic Memory | 经验证的稳定事实 | 长期并可更新 |

高风险决策不能只依赖历史 Memory，应重新查询权威工具。记忆的命中、采用、纠错和删除都需审计，并支持用户查看与更正。

**相关知识点：** Working Memory、Episodic Memory、Semantic Memory、来源追踪、TTL、权限过滤、向量检索。
<a id="tool-044"></a>
### 如何对 Tool Calling 系统进行性能优化和压测？

Tool Calling 性能优化应先定位 **模型选择、Executor 排队、网络调用和多步关键路径** 的耗时占比，再按瓶颈优化，不能只提高单接口 QPS。

1. **链路拆解**：用 Trace 记录候选检索、模型推理、参数校验、排队、连接、下游执行、重试和结果处理时间，按工具、版本与租户统计 P50/P95/P99，识别关键路径。
2. **优化手段**：裁剪模型候选工具，缓存稳定描述和 Registry 元数据；复用 HTTP/数据库连接；独立只读节点并发执行；对大结果分页、压缩和摘要。写操作仍需幂等、顺序及冲突控制。
3. **压测模型**：分别进行单工具基准、真实混合流量、突发流量和长稳测试，覆盖读写比例、参数大小、工具链长度及多租户配额；逐级提高并发直至延迟拐点和错误预算耗尽。
4. **故障压测**：注入慢依赖、超时、429、5xx、断网、超大响应和部分写入，验证限流、队列、熔断、降级、取消与资源回收，防止重试风暴。

| 测试类型 | 主要目标 | 核心指标 |
|---|---|---|
| 基准测试 | 单组件能力 | QPS、服务时间 |
| 负载测试 | 目标容量 | P95、成功率 |
| 压力测试 | 查找系统极限 | 拐点、降级行为 |
| 稳定性测试 | 发现泄漏与累积故障 | 内存、连接、队列 |

最终关注端到端任务成功率、关键路径延迟、单位任务成本和重复副作用率。容量评估应包含硬件、版本、数据规模与流量模型，确保可复现。

**相关知识点：** 性能剖析、关键路径、连接复用、并发DAG、负载测试、故障注入、P95、错误预算。
<a id="tool-056"></a>
### Agent如何判断一个工具是否属于高风险工具？

工具风险不能只由名称决定，应综合 **操作副作用、目标环境、影响范围、数据敏感度、权限级别、可逆性和输入确定性** 计算 Risk Score，并设置强制禁止规则。

1. **静态风险**：在 Registry 为工具标注只读、写入、删除、转账、发布、提权等操作类型，以及所需权限、是否外连、是否执行代码、是否幂等和能否回滚，形成基础风险分。
2. **动态风险**：同一工具在测试与生产、单条与批量、普通与敏感数据、本人资源与跨租户资源上的风险不同。Executor 根据实际参数、目标和用户身份实时调整评分。
3. **不确定性风险**：参数含通配符、自然语言路径、未限定 SQL 条件或模型置信度低时，应提高风险；无法解析影响范围的操作按较高等级处理，不能默认安全。
4. **策略映射**：低风险只读操作自动执行；中风险有限写入展示影响预览并确认；生产删除、发布、权限变更采用双人审批；破坏审计、越权和不可控递归删除直接禁止。

| 维度 | 低风险示例 | 高风险示例 |
|---|---|---|
| 副作用 | 读取公开信息 | 删除、转账、提权 |
| 环境 | 本地或测试 | 生产核心系统 |
| 范围 | 单资源、明确条件 | 批量、通配符、跨租户 |
| 可逆性 | 可自动回滚 | 不可逆或恢复困难 |

风险等级还应决定沙箱强度、凭据 Scope、网络权限、超时和审计保留期，并依据事故与误拦截数据持续校准。

**历史别名：** `GOV-152`。

**相关知识点：** Risk Score、动态风险、可逆性、影响范围、HITL、双人审批、默认拒绝、风险校准。
<a id="tool-057"></a>
### 如何设计Tool的权限模型？

Tool 权限应把 **主体、工具、操作、资源和环境** 分开，以 RBAC 设置基线、ABAC 判断条件，由 Policy Engine 执行。

1. **主体建模**：识别用户、Agent、服务账号和审批人。Tool Call 携带用户委托与 Agent 身份，禁止共用高权限账号。
2. **能力操作拆分**：权限应拆为 `read、create、update、delete、execute、approve`，并绑定版本与风险；Registry 只返回已授权候选。
3. **资源与上下文约束**：ABAC 根据租户、项目、资源所有者、数据级别、测试或生产环境、时间、来源网络和影响范围决定是否允许。拥有查询工具不代表能够读取所有数据。
4. **执行与提权**：Executor 调用前求值，最终服务再鉴权。临时提权使用限定 Scope 和期限的凭据，高风险操作需预览与审批。

| 权限层 | 管理内容 | 示例 |
|---|---|---|
| RBAC | 稳定岗位权限 | 开发者可读取测试日志 |
| ABAC | 动态资源与环境条件 | 仅本人项目、非生产 |
| Risk Policy | 执行方式 | 自动、确认、双审、拒绝 |

策略采用默认拒绝，并在候选暴露、Executor 执行和服务端至少三处校验。审计记录主体、资源、决策、审批、策略版本和 `trace_id`。

**历史别名：** `GOV-153`。

**相关知识点：** RBAC、ABAC、Policy Engine、资源级授权、工作负载身份、临时提权、默认拒绝、审计。
<a id="tool-058"></a>
### RBAC与ABAC分别适用于哪些场景？

**RBAC 适合稳定岗位，ABAC 适合按主体、资源和环境动态判断**。企业 Agent 通常以 RBAC 定基线、ABAC 收紧调用。

| 维度 | RBAC | ABAC |
|---|---|---|
| 决策依据 | 用户所属角色 | 主体、资源、操作、环境属性 |
| 优势 | 简单、易审计、易复用 | 细粒度、上下文感知 |
| 局限 | 易角色爆炸，难表达动态条件 | 策略复杂，依赖可靠属性 |
| 典型场景 | 岗位工具菜单、管理权限 | 多租户、生产、敏感数据 |

1. **RBAC 场景**：组织结构稳定、权限能按开发者、审核员、运维和管理员等岗位归类时使用。例如开发者可以查询测试日志，发布管理员可以发起部署。它适合定义“通常能做什么”。
2. **ABAC 场景**：授权依赖租户、项目归属、数据级别、目标环境、时间、来源网络、影响范围或风险分时使用。例如开发者只能修改本人项目且不能写生产库。
3. **组合策略**：先判断角色是否拥有工具和操作权限，再根据请求参数与环境属性求值；任一层拒绝即终止。高风险操作还需审批，最终服务再次做资源级鉴权。
4. **治理要求**：RBAC 需控制角色数量并定期复核；ABAC 需统一属性来源、策略版本、冲突优先级和解释日志。属性缺失或不可验证时采用默认拒绝。

策略决策应集中在 Policy Engine，Registry 负责候选过滤，Executor 负责调用前校验，避免权限逻辑散落在 Prompt 和各工具中。

**历史别名：** `GOV-154`。

**相关知识点：** RBAC、ABAC、角色爆炸、属性源、Policy Engine、默认拒绝、资源级鉴权、审批。

<a id="tool-061"></a>
### 风险评分如何影响Agent的执行策略？

风险评分不应只是展示字段，而应直接控制 **是否执行、审批级别、沙箱强度、凭据范围、网络权限、回滚要求和审计粒度**。

1. **执行分级**：低风险只读、范围明确且可验证的操作自动执行；中风险有限写入先展示影响预览并由用户确认；高风险生产删除、发布、转账或提权采用双人审批；命中禁止规则直接拒绝。
2. **运行约束**：风险越高，使用越强的隔离环境、更短的 Deadline、更低的并发和更严格的资源上限。高风险代码优先使用微虚机，网络默认关闭，仅放行必要 Tool Gateway。
3. **权限与数据**：低风险使用常规最小角色，高风险由 Vault 签发更窄 Scope、更短期限的一次性凭据；敏感字段减少进入模型上下文，输出加强脱敏和内容检查。
4. **恢复与审计**：中高风险操作执行前必须具备事务、快照、补偿或明确人工恢复方案；日志提高采样率并记录参数摘要、影响范围、审批人、策略版本、结果和 Trace。

| 风险级别 | 执行方式 | 附加控制 |
|---|---|---|
| 低 | 自动执行 | 基础审计 |
| 中 | 影响预览、单人确认 | 快照、限额 |
| 高 | 双人审批或专人执行 | 强沙箱、短期凭据 |
| 禁止 | 拒绝 | 告警与安全事件 |

评分还应影响 Planner：高风险路径优先选择只读验证、最小变更和可逆工具。评分变化需重新求值，用户确认不能覆盖硬性红线。

**历史别名：** `GOV-157`。

**相关知识点：** 风险分级、HITL、强沙箱、短期凭据、影响预览、补偿、双人审批、Policy Engine。
<a id="tool-062"></a>
### Human-in-the-Loop应该在哪些场景下介入？

Human-in-the-Loop 应介入 **高影响、不可逆、低置信、规则冲突或需要责任确认** 的节点，而不是对每次 Tool Call 都弹出确认。

1. **高风险副作用**：生产删除、批量数据修改、资金交易、权限变更、对外发送、代码合并和部署发布需要人工确认；影响跨租户、敏感数据或核心服务时采用双人审批。
2. **不确定性过高**：目标含糊、关键参数缺失、多个工具得分接近、影响范围无法计算、数据源冲突或模型置信度低时，应先澄清或由专家选择，不能猜测执行。
3. **异常与恢复**：写入状态未知、补偿失败、自动回滚不可用、连续重规划仍无进展时，人工决定继续、回退或终止，并接收已完成步骤和现场证据。
4. **合规与责任节点**：法律、医疗、财务、人事等受监管决策，以及需要明确业务责任人的例外授权，即使技术风险分不高，也必须由具备资格的人员批准。

| 场景 | 人工动作 | 系统需展示 |
|---|---|---|
| 中风险写入 | 单人确认 | 命令、目标、影响、回滚 |
| 高风险生产操作 | 双人审批 | 风险、权限、证据 |
| 低置信或冲突 | 澄清或选择 | 候选方案与差异 |
| 自动恢复失败 | 接管处置 | 现场、日志、已完成步骤 |

低风险、可逆、范围明确且已验证的操作可自动执行。审批必须绑定规范化参数、具体版本和有效期；参数变化后原审批失效。

**历史别名：** `GOV-158`。

**相关知识点：** HITL、风险分级、双人审批、低置信度、影响预览、人工接管、审批绑定、职责分离。
<a id="tool-063"></a>
### 如何避免Agent误删代码或误删文件？

避免误删应采用 **工作区限制、路径规范化、删除策略、影响预览和可恢复存储**，禁止 Agent 直接对宿主文件系统执行任意递归删除。

1. **限制可见范围**：Agent 以非特权身份运行，只挂载指定仓库或临时工作区；宿主目录、根目录、凭据目录和其他租户目录不可见。文件系统默认只读，仅授权子目录可写。
2. **确定目标路径**：Executor 在宿主侧解析绝对真实路径，验证位于允许根目录内，并拒绝空路径、根目录、`..`、未解析变量、通配符和符号链接逃逸。路径校验应在每次操作前完成。
3. **控制删除操作**：优先把文件移动到回收区或创建 Git 提交、快照，再执行逻辑删除；递归删除、批量范围超过阈值、删除未跟踪文件或修改仓库外内容必须展示列表并审批。
4. **执行后验证**：记录删除前后的文件清单、哈希和 diff，运行构建或测试验证仓库完整性；异常时通过回收区、Git revert 或快照恢复。审计记录用户、命令、路径、审批和 Trace。

| 保护层 | 机制 | 防护目标 |
|---|---|---|
| 运行隔离 | 只挂载工作区 | 看不到宿主文件 |
| 路径策略 | realpath、根目录校验 | 防目录穿越 |
| 操作策略 | 禁止直接递归删除 | 限制影响范围 |
| 恢复机制 | 回收区、Git、快照 | 可撤销误删 |

即使用户确认，命中根目录、宿主目录或不可恢复范围等禁止策略也必须拦截；确认页面需显示规范化路径和文件数量。

**历史别名：** `GOV-159`。

**相关知识点：** 工作区隔离、realpath、符号链接逃逸、回收区、Git revert、快照、影响预览、审计。

<a id="tool-065"></a>
### 如何防止Prompt Injection诱导Agent执行恶意工具？

防止 Prompt Injection 的核心是 **把外部内容视为不可信数据，让权限与执行决策脱离模型**；系统提示不是安全边界。

1. **指令与数据隔离**：系统策略、用户目标和网页、邮件、代码注释、MCP Resource 使用不同通道与来源标签。外部命令不能升级为指令。
2. **最小工具暴露**：根据当前子任务、用户权限和环境动态筛选工具。读取文档的步骤不应同时拥有删除、转账或部署权限；敏感工具使用独立 Agent、短期凭据和更高审批阈值。
3. **确定性执行门禁**：Executor 对工具、参数、目标资源、数据流和风险重新校验，实施 allowlist、ABAC、影响预览与人工审批。模型无权修改 Policy，也不能通过自然语言结果声明已获授权。
4. **输入输出防护**：限制外部内容长度和可引用范围，检测诱导调用、凭据索取与数据外传；工具结果做脱敏和来源标记。高风险操作检查参数是否源自不可信内容，并阻断异常外连。

| 防护层 | 主要作用 | 不能替代 |
|---|---|---|
| 提示隔离 | 降低指令混淆 | 权限校验 |
| 工具最小化 | 缩小攻击面 | 参数校验 |
| Policy Engine | 确定性拦截 | 高风险人工审批 |
| 沙箱与网络策略 | 限制突破后影响 | 上层身份控制 |

使用间接注入、越权调用和数据外传红队集持续评测，重点监控攻击成功率、高风险误放行率和敏感数据泄露率。

**历史别名：** `GOV-161`。

**相关知识点：** Prompt Injection、指令数据隔离、工具最小化、ABAC、Policy Engine、数据流控制、红队评测。
<a id="tool-067"></a>
### Tool调用前、中、后分别需要做哪些安全检查？

Tool 安全应覆盖 **调用前阻止、调用中隔离、调用后验证与留痕**，三阶段缺一不可。

1. **调用前**：确认用户与 Agent 身份，按 RBAC/ABAC 校验工具、操作和目标资源；执行 JSON Schema、业务参数、路径或 SQL AST 校验；计算 Risk Score，检查审批、配额、工具健康、版本与幂等条件。凭据由密钥系统按任务临时签发。
2. **调用中**：在隔离的 Executor 或沙箱中运行，限制 CPU、内存、进程、网络、文件和执行时间；传播 Deadline 与取消信号，实施限流、舱壁和熔断。监控异常系统调用、外连、输出大小和资源增长，禁止工具绕过 Gateway。
3. **调用后**：同时校验传输状态、业务码与后置条件；查询写操作真实状态，确认影响范围符合审批。结果进行 Schema 检查、脱敏、内容安全与 Prompt Injection 检测，再决定是否写入 Memory。
4. **恢复和审计**：失败时按类型重试、降级或补偿，状态未知先查询。记录主体、版本、参数摘要、策略、审批、结果、影响及 `trace_id`。

| 阶段 | 核心目标 | 典型控制 |
|---|---|---|
| 调用前 | 防止不该执行 | 鉴权、校验、审批 |
| 调用中 | 限制执行影响 | 沙箱、配额、监控 |
| 调用后 | 确认结果可信 | 后置条件、脱敏、审计 |

高风险操作即使前置审批通过，运行中越过范围或调用后状态异常也必须终止后续计划并进入人工恢复。

**历史别名：** `GOV-163`。

**相关知识点：** 纵深防御、参数校验、Risk Score、沙箱、Deadline、后置条件、补偿、审计日志。
<a id="tool-068"></a>
### Agent如何实现命令沙箱隔离？

命令沙箱以 **独立运行时、非特权身份、最小挂载、网络拒绝和资源配额** 构成边界，命令过滤仅作辅助。

1. **隔离级别**：低风险命令用容器；未知代码或高风险命令采用 gVisor 或 Firecracker。宿主与业务节点分离，禁止特权模式、宿主网络及 Docker Socket。
2. **进程与内核**：使用非 root，裁剪 capabilities，启用 namespace、seccomp 和只读根文件系统；镜像最小化、签名并修补。
3. **文件与网络**：只挂载指定工作区，宿主侧校验 realpath，阻止符号链接和目录穿越。网络默认关闭，必要外连经 Tool Gateway 按域名、端口和协议放行，沙箱不持有长期凭据。
4. **资源与回收**：cgroups 限制 CPU、内存、进程、磁盘和 I/O，设置总 Deadline。超时先发送终止信号，宽限期后结束整个进程组，再卸载卷、撤销网络与令牌并清理临时数据。

| 隔离技术 | 安全性 | 适用场景 |
|---|---|---|
| 容器 | 中等，共享内核 | 低风险、短任务 |
| gVisor | 较高，系统调用拦截 | 多租户通用代码 |
| Firecracker | 高，独立内核 | 任意代码、高风险任务 |

沙箱还需记录镜像、命令摘要、系统调用异常、网络连接、资源峰值和 Trace，并通过逃逸测试与故障注入验证。

**历史别名：** `GOV-164`。

**相关知识点：** 容器、gVisor、Firecracker、namespace、seccomp、cgroups、网络隔离、资源回收。

<a id="tool-070"></a>
### Git Push为什么通常需要审批？

Git Push 将本地变更扩散到远端，可能触发 **协作、CI/CD、制品和部署**，影响超出 Agent 工作区，因此需要审批。

1. **共享副作用**：Push 会修改远端、触发流水线，强推还可能改写历史；错误提交可能包含缺陷、密钥或无关文件。
2. **职责分离**：Agent 可生成代码、运行测试和创建本地提交，但远端写入应由独立身份与策略控制。开发者、评审者和发布者权限分离，避免一个 Agent 同时完成修改、批准和发布。
3. **审批内容**：确认页面展示仓库、远端、目标分支、提交范围、diff 摘要、测试与扫描结果、是否强推及可能触发的流水线。审批绑定具体 commit SHA；提交变化后必须重新审批。
4. **技术门禁**：使用短期 Git 凭据，只允许推送临时分支；主分支开启保护、必需评审、状态检查、签名提交和禁止强推。敏感信息扫描或测试失败时，即使人工确认也应拦截。

| 操作 | 风险 | 推荐策略 |
|---|---|---|
| 本地提交 | 影响仅在工作区 | 可自动并保留diff |
| 推送临时分支 | 影响团队与CI | 单人确认 |
| 合并主分支 | 影响共享基线 | 评审与状态检查 |
| 强推受保护分支 | 历史破坏 | 默认禁止 |

审计应关联需求、Agent、commit SHA、审批人、扫描结果和 Trace；错误 Push 通过 revert 或关闭分支恢复，不自动改写公共历史。

**历史别名：** `GOV-166`。

**相关知识点：** Git Push、分支保护、职责分离、Commit SHA、短期凭据、状态检查、Secret Scan、revert。
<a id="tool-071"></a>
### 如何防止Agent直接向主分支提交代码？

应通过 **分支保护、低权限身份和受控合并** 强制限制，而不是仅靠 Prompt。

1. **权限隔离**：Agent 使用独立身份和短期令牌，只能更新指定前缀的临时分支，无主分支写入、强推和绕过规则权限。
2. **远端保护**：在 Git 服务端为主分支设置禁止直接 Push、禁止 Force Push、必需 Pull Request、代码所有者评审、状态检查、签名提交和线性历史。管理员绕过权限也应最小化并审计。
3. **Agent 工作流**：从基线创建任务分支，运行测试、静态检查与密钥扫描，生成提交和 PR；PR 包含 diff、证据、风险与回滚。
4. **合并控制**：合并由人工或独立 Merge Bot 完成，审批绑定 commit SHA。提交更新、测试状态变化或基线冲突后重新评审；高风险仓库采用双人审批和部署门禁。

| 控制位置 | 机制 | 防止绕过 |
|---|---|---|
| Agent凭据 | 仅临时分支写权限 | 无主分支权限 |
| Git服务端 | Branch Protection | 拒绝直接Push |
| CI | 必需测试与扫描 | 阻止不合格变更 |
| 合并流程 | PR评审、SHA绑定 | 防审批后换包 |

即使 Agent 获得本地 Git 权限，服务端仍是最终边界。审计应关联任务、分支、提交、评审、状态检查和 Trace。

**历史别名：** `GOV-167`。

**相关知识点：** Branch Protection、Pull Request、最小权限、短期令牌、CODEOWNERS、Commit SHA、Merge Bot。

### 如何设计统一的Policy Engine管理所有工具权限？

Policy Engine 是 **独立于模型和工具的确定性决策点**，接收授权上下文，返回允许、拒绝、审批及约束。

1. **策略输入**：描述主体、租户、Agent、工具版本、操作、资源、参数摘要、环境、数据级别、风险和审批；属性来自 IAM、Registry 与资源目录。
2. **策略模型**：RBAC 定义岗位基线，ABAC 表达资源和环境条件，强制规则处理禁止项，Risk Policy 决定自动、确认或双审。冲突时采用显式拒绝优先，属性缺失默认拒绝。
3. **执行架构**：Registry、Executor 和服务端向 PDP 求值；各 PEP 执行限额、沙箱、凭据 Scope 和结果脱敏等约束。
4. **版本解释**：策略作为签名制品，经测试、评审和灰度；决策返回命中规则、版本与原因码，支持模拟和回放。

| 组件 | 职责 | 示例 |
|---|---|---|
| PDP | 计算授权决策 | allow、deny、approve |
| PEP | 执行决策和约束 | Executor、Gateway |
| PIP | 提供可信属性 | IAM、资源目录 |
| PAP | 策略编写与发布 | 评审、版本、灰度 |

决策缓存必须包含主体、资源、操作和策略版本，并使用短 TTL；权限撤销时主动失效。审计记录输入摘要、决策、原因和 Trace。

**历史别名：** `GOV-174`。

**相关知识点：** Policy Engine、PDP、PEP、PIP、PAP、RBAC、ABAC、拒绝优先、策略即代码。

### Agent执行数据库DDL或DML操作应有哪些额外保护机制？

Agent 执行 DDL/DML 必须增加 **SQL AST 审查、最小数据库权限、影响评估、事务或迁移保护、审批和执行后验证**，生产库禁止直接执行未验证 SQL。

1. **静态检查**：使用数据库方言 Parser 构建 AST，禁止多语句、注释绕过、危险函数、无条件 UPDATE/DELETE、跨租户访问和未授权 DDL；所有值使用参数绑定，表名等标识符通过允许列表。
2. **影响评估**：执行 EXPLAIN 和等价只读预查询，估算扫描量、影响行数、锁范围、索引变化、执行时间及复制延迟。超过阈值或无法估算时停止并审批。
3. **执行保护**：DML 在事务中设置行数上限、超时、锁等待和资源组；写入使用幂等键与条件版本。DDL 采用在线变更、影子表或分阶段迁移，避免长时间锁表。
4. **恢复验证**：DML 保存变更前镜像或补偿记录，DDL 具备备份与向前兼容回退方案。执行后核对影响行数、约束、业务不变量和副本状态；状态未知时先查询。

| 操作 | 主要风险 | 额外保护 |
|---|---|---|
| UPDATE/DELETE | 全表误改 | WHERE校验、行数上限 |
| INSERT | 重复数据 | 唯一约束、幂等键 |
| DDL | 锁表、结构破坏 | 在线变更、双审 |
| 数据迁移 | 新旧版本不兼容 | 分阶段、可回退 |

生产写入使用独立短期账号并限制库表范围，审计记录规范化 SQL、参数摘要、执行计划、审批、影响和事务结果。

**历史别名：** `GOV-179`。

**相关知识点：** SQL AST、EXPLAIN、参数绑定、事务、行数上限、在线DDL、变更前镜像、业务不变量。
<a id="tool-084"></a>
### 如何平衡Agent自动化效率与人工审批带来的成本？

平衡点不是减少审批数量本身，而是采用 **风险分级、信息充分的审批、策略自动化和效果度量**，让人工只介入高影响或高不确定节点。

1. **风险分层**：低风险、只读、范围明确且可逆的操作自动执行；中风险有限写入采用一次确认；生产删除、转账、发布和提权采用双审；命中合规禁止项直接拒绝。风险按实际参数动态计算。
2. **减少无效审批**：审批页面展示规范化命令、目标环境、影响范围、权限、证据和回滚方式，绑定具体请求哈希与有效期；同一计划中可批量审批边界明确的步骤，参数变化则重新审批。
3. **自动化门禁**：使用 Schema、静态分析、测试、影响评估、Policy Engine 和后置验证替代低价值人工检查。对稳定高成功率的操作逐步提高自动化等级，对异常或新工具降低等级。
4. **运营优化**：度量审批量、等待时长、拒绝率、修改率、事故率、误放行与误拦截。通过历史数据校准阈值和审批路由，设置值班与超时转派，避免任务无限等待。

| 策略 | 效率 | 风险 |
|---|---|---|
| 全量审批 | 低 | 人员疲劳、形式化确认 |
| 全自动 | 高 | 高风险误执行 |
| 风险分级 | 较高 | 依赖准确评分与治理 |
| 渐进授权 | 持续提升 | 需效果监控和回退 |

安全红线不因效率目标放宽；优化方向应是减少低价值审批、提高审批信息质量，而不是取消高风险责任节点。

**历史别名：** `GOV-180`。

**相关知识点：** 风险分级、HITL、审批疲劳、请求哈希、渐进授权、误放行、误拦截、审批SLA。

<a id="tool-086"></a>
### 容器隔离和虚拟机隔离（如Firecracker）在安全性和性能上的具体权衡是什么？

容器以 **共享内核换取低延迟和高密度**，Firecracker 以独立内核换取强隔离，但增加内存和运维成本。

| 维度 | 容器 | Firecracker微虚机 |
|---|---|---|
| 隔离边界 | namespace/cgroup，共享内核 | 硬件虚拟化、独立内核 |
| 逃逸影响 | 内核漏洞可能影响宿主 | 虚拟机边界缩小影响 |
| 启动与密度 | 毫秒级、密度高 | 较慢、单实例开销更高 |
| 兼容性 | 接近宿主Linux | 需维护内核与根文件系统 |
| 适用任务 | 受信代码、短任务 | 任意代码、强多租户 |

1. **安全性**：容器的 seccomp、capabilities 和只读文件系统能显著收缩攻击面，但不能消除共享内核风险；微虚机隔离内核，即使 Guest 被攻破，仍需跨越虚拟化边界。
2. **性能**：容器创建快、镜像生态成熟、I/O 接近原生，适合高并发短任务；微虚机需要启动内核并预留内存，网络与存储路径更复杂，但可通过快照与预热池优化。
3. **运营成本**：容器易与 Kubernetes 等平台集成；微虚机需管理内核、镜像、快照、Guest Agent 和调度，监控与故障排查也更复杂。
4. **选型原则**：按代码可信度、租户敏感度和宿主价值分级。低风险用加固容器，中风险可用 gVisor，高风险用户上传代码使用微虚机与独立节点池。

无论选择哪种方式，都需最小权限、网络默认拒绝、资源配额、镜像签名和及时修补，不能把虚拟化当作唯一防线。

**相关知识点：** 容器、Firecracker、共享内核、硬件虚拟化、gVisor、预热池、纵深防御、节点隔离。
<a id="tool-087"></a>
### 如何设计沙箱的冷启动优化方案，降低池化管理的资源浪费？

沙箱冷启动优化应采用 **分层预热池、镜像与快照缓存、需求预测和租约回收**，在延迟、空闲成本和隔离强度之间动态平衡。

1. **分级池化**：按运行时语言、镜像版本和风险等级建立池。低风险容器维持较小热池，高风险微虚机使用快照恢复池；长尾镜像不常驻，按需启动。不同租户敏感级别不可混用实例。
2. **减少启动工作**：节点预拉并校验镜像，复用只读基础层、语言运行时与依赖缓存；Firecracker 在初始化完成且无租户数据时制作签名快照。每次分配创建全新可写层、网络与短期身份。
3. **动态容量**：根据历史到达率、时段、排队长度、冷启动 P95 和池命中率预测最小热池，设置上下限、扩缩容冷却窗口和突发缓冲。高优先级任务预留容量。
4. **安全回收**：实例使用带 TTL 的租约，任务结束清理进程、内存、临时卷、网络和凭据，通过残留检测后才回池；无法证明清洁则销毁。长期空闲实例按水位回收。

| 优化方式 | 收益 | 主要风险 |
|---|---|---|
| 预拉镜像 | 减少下载时间 | 缓存占用磁盘 |
| 热池 | 启动最快 | 空闲资源浪费 |
| 微虚机快照 | 兼顾隔离与速度 | 快照污染与版本管理 |
| 预测扩缩容 | 提高命中率 | 预测误差 |

核心指标包括冷启动 P95、热池命中率、空闲成本、排队时间、回收失败率和残留检测失败率，并按任务类型分别调优。

**相关知识点：** 预热池、镜像缓存、微虚机快照、需求预测、租约、扩缩容、残留检测、冷启动P95。
<a id="tool-088"></a>
### seccomp的系统调用过滤策略具体如何配置，有哪些常见的危险syscall需要屏蔽？

seccomp 应采用 **默认拒绝、按任务建立允许列表、参数约束和观测上线**，不能照搬通用黑名单。

1. **配置方法**：采集不同任务的 syscall，建立最小允许集；默认返回 `ERRNO` 或终止，仅放行必需调用。按架构和内核版本维护，镜像升级需回归。
2. **高危类别**：屏蔽模块与系统控制的 `init_module、delete_module、kexec_load、reboot`；跨进程访问的 `ptrace`；内核攻击面的 `bpf、userfaultfd、perf_event_open`。
3. **逃逸相关**：普通任务禁用 `mount、pivot_root、setns、unshare`，限制 `clone/clone3` 参数；屏蔽 `open_by_handle_at` 等宿主访问能力。
4. **上线响应**：测试环境先记录违规再阻断；告警包含 syscall、镜像、任务和 Trace。还需配合非 root、能力裁剪和只读文件系统。

| 策略 | 优点 | 风险 |
|---|---|---|
| 黑名单 | 兼容性较好 | 容易漏掉新攻击面 |
| 允许列表 | 攻击面最小 | 维护与兼容成本高 |

禁止项需按内核、运行时和业务验证，避免破坏 DNS、线程或语言运行时。

**相关知识点：** seccomp、syscall allowlist、ptrace、bpf、mount、clone3、capabilities、纵深防御。
<a id="tool-090"></a>
### 如果Agent需要执行任意用户上传的代码，沙箱逃逸（sandbox escape）风险如何防范？

任意代码按 **完全不可信负载** 处理，采用微虚机、最小宿主、无长期凭据、默认断网和快速销毁。

1. **强隔离边界**：优先使用 Firecracker 或独立虚拟机，不以共享内核容器作为唯一边界；禁止特权模式、宿主网络、设备和宿主目录挂载。
2. **收缩攻击面**：Guest 使用最小只读镜像、非 root、能力裁剪和 seccomp；宿主运行最少服务，持续更新 CPU 微码、内核、虚拟化层和运行时。镜像签名并锁定版本。
3. **限制可达资源**：网络默认关闭，必要请求仅经 Tool Gateway 按域名和协议放行；沙箱不持有云元数据凭据和长期密钥，使用单任务短期令牌。限制 CPU、内存、进程、磁盘和时间。
4. **检测响应**：监控异常 syscall、提权、内核探测和网络扫描；命中后冻结证据、终止实例、隔离宿主并轮换凭据。

| 控制层 | 主要措施 | 逃逸后的作用 |
|---|---|---|
| Guest | seccomp、非root、只读镜像 | 降低利用面 |
| 虚拟化 | 独立内核、最小设备 | 增加隔离边界 |
| Host | 专用节点、及时修补 | 缩小宿主暴露 |
| 网络身份 | 默认拒绝、短期令牌 | 限制横向移动 |

还需定期进行逃逸红队测试、模糊测试和事件演练。无法保证绝对安全，设计目标是纵深防御与最小爆炸半径。

**相关知识点：** Sandbox Escape、Firecracker、最小镜像、seccomp、网络默认拒绝、短期令牌、红队测试、节点隔离。
<a id="tool-091"></a>
### 沙箱执行超时后如何优雅终止任务并保证资源正确回收？

沙箱超时处理应采用 **截止时间传播、分阶段终止、进程树清理、外部副作用确认和租约回收**，不能只结束入口进程。

1. **统一 Deadline**：任务入口生成绝对截止时间并传给沙箱、子进程和外部工具；到期前进入取消阶段，停止接收新步骤，向运行进程和协程发送可处理的终止信号。
2. **分阶段终止**：先给任务短暂宽限期保存日志、刷新缓冲区和写检查点；超时后结束整个进程组或 cgroup，而非单个 PID。仍无法停止时由运行时销毁容器或微虚机。
3. **资源回收**：撤销网络规则、短期令牌、文件锁和分布式租约，关闭连接，卸载临时卷并删除可写层；回收动作设计为幂等，并由独立 Reaper 处理主进程崩溃后的遗留资源。
4. **副作用处理**：对数据库、消息和外部 Tool Call 查询真实状态；状态未知不能直接重试。根据幂等键、事务或补偿计划恢复，并保留工作区快照与审计证据。

| 阶段 | 动作 | 目标 |
|---|---|---|
| 取消 | 停止新步骤、发送信号 | 允许正常收尾 |
| 强制终止 | 杀进程组或销毁实例 | 确保计算停止 |
| 回收 | 撤销凭据、网络、卷、租约 | 消除资源泄漏 |
| 核验 | 检查副作用与残留 | 保证一致性 |

监控僵尸进程、租约残留、回收失败、实例销毁时长和未知状态操作；回收失败应隔离节点并触发告警。

**相关知识点：** Deadline、优雅终止、进程组、cgroup、Reaper、租约、幂等回收、补偿事务。
<a id="tool-093"></a>
### 沙箱的审计日志系统如何设计，以支持安全事件的快速定位与回溯？

沙箱审计应采用**全链路、不可抵赖、可关联、分级留存**的设计，使一次执行能够从用户请求追溯到进程、文件、网络和资源变化。

1. **统一事件模型**：为任务生成全局 Trace ID，并关联租户、用户、会话、镜像摘要、策略版本、节点、容器及父子进程。日志记录主体、动作、对象、结果、时间、来源和风险等级，时间统一同步。
2. **覆盖关键证据**：采集控制面操作、鉴权与授权结果、命令及参数、系统调用摘要、文件读写、网络连接、工具调用、资源超限、异常退出和人工审批。敏感内容只存哈希、脱敏值或受控密文。
3. **可信存储**：日志实时发送到沙箱外部，经签名、哈希链或 WORM 存储防篡改；传输失败时使用限额缓冲，禁止任务删除审计记录。热数据支持检索，冷数据按合规周期归档。
4. **定位与回溯**：建立 Trace ID、主体、对象、时间窗和规则命中索引，将事件汇入 SIEM；高风险行为实时告警，并保留镜像、策略、输入输出摘要及必要快照，以便重放环境而非盲目重执行恶意载荷。

| 机制 | 主要价值 | 局限 |
|---|---|---|
| 普通应用日志 | 解释业务流程 | 缺少内核级证据 |
| 审计事件 | 还原安全行为 | 数据量较大 |
| 快照/取证包 | 深度复盘 | 成本高、需严格授权 |

应通过字段完整率、日志丢失率、告警时延和平均定位时间持续验收，并实施访问分权与查询留痕，避免审计系统本身成为敏感信息泄露源。

**相关知识点：** Trace ID、结构化日志、WORM、哈希链、SIEM、时间同步、证据链、分级留存、取证快照。
<a id="tool-094"></a>
### 在大规模并发场景下，沙箱集群如何做弹性伸缩与调度？

大规模沙箱集群应以**分层队列、资源感知调度、预测与响应式扩缩容结合**为核心，在隔离强度、启动时延、吞吐量和成本之间取得平衡。

1. **任务分级**：按租户、优先级、CPU、内存、GPU、时限及风险等级进入不同队列；采用配额、加权公平队列和背压，避免大租户或长任务挤占集群。
2. **调度决策**：根据资源请求、节点剩余量、镜像缓存、数据位置、隔离等级、亲和与反亲和约束进行装箱；高风险任务进入专用节点池，禁止仅依据平均利用率调度。
3. **弹性策略**：Pod/实例层依据队列深度、等待时间和资源使用率扩缩，节点层依据未调度任务扩容。结合历史到达率预测预热容量，突发流量使用 warm pool；缩容前排空节点并设置冷却期。
4. **可靠执行**：调度与执行解耦，任务使用幂等标识和租约；节点失联后租约到期重调度，是否重试取决于副作用语义。设置超时、熔断、最大重试和降级策略。

| 策略 | 优点 | 适用场景 |
|---|---|---|
| Bin Packing | 提高利用率、便于缩容 | 通用计算任务 |
| Spread | 降低故障域风险 | 高可用任务 |
| 预热池 | 启动快 | 突发、低时延任务 |

核心指标包括排队时延P95/P99、调度成功率、冷启动时长、节点利用率和单位任务成本。容量规划还应预留故障冗余，并通过优先级抢占与准入控制保护关键任务。

**相关知识点：** 多级队列、加权公平、Bin Packing、Warm Pool、背压、租约、幂等、节点池、预测扩容、故障域。
<a id="tool-097"></a>
### 企业级 Agent 为什么更强调可控性？

企业级Agent连接真实数据、系统权限和业务动作，模型的概率性输出会被放大为资金、合规或生产风险，因此必须做到**权限可约束、过程可观测、结果可验证、异常可恢复、责任可追溯**。

1. **风险边界更大**：Agent可能读取客户数据、修改订单、发送消息或执行代码；一次幻觉、提示词注入或工具参数错误，不再只是文本质量问题，而可能形成越权、泄密和不可逆副作用。
2. **治理要求更严**：企业需要满足最小权限、职责分离、数据分级、审批、审计与留存要求，还要说明某次决策使用了何种模型、提示词、知识版本及工具结果。
3. **服务目标明确**：生产系统需承诺可用性、延迟、成本和恢复目标。应限制最大步数、Token、时间、并发和预算，设置超时、熔断、幂等、补偿与人工接管。
4. **质量必须可验收**：通过离线基准集、对抗测试、灰度发布和线上指标，持续监控任务成功率、误调用率、拒答率与安全事件。

| 能力 | 普通聊天助手 | 企业级Agent |
|---|---|---|
| 输出影响 | 多为建议 | 可产生业务副作用 |
| 权限模型 | 较简单 | 细粒度、动态授权 |
| 失败处理 | 重新提问 | 回滚、补偿、接管 |
| 审计要求 | 可选 | 通常必需 |

可控性不等于把流程完全固定，而是将不确定性限制在可接受边界：确定性系统负责策略与授权，模型负责语义理解和候选方案，高风险动作必须经过验证或审批。

**相关知识点：** 最小权限、职责分离、Human-in-the-loop、幂等、补偿事务、策略引擎、审计追踪、红队测试、灰度发布。
<a id="tool-106"></a>
### 如何设计高风险工具的审批机制？

高风险工具审批应采用**风险分级、执行前冻结、审批后再校验、授权一次一用**的机制；审批不是提示框，而是一项可审计的安全控制。

1. **风险分类**：依据数据敏感度、权限范围、影响对象、可逆性和金额划分等级。只读低风险可自动执行；外部发送、批量修改、删除、转账和提权必须审批，极高风险还需双人复核或禁止自动化。
2. **审批对象**：冻结规范化后的工具名、版本、参数、目标、影响预览、调用身份、依据和有效期，生成不可变请求摘要。审批人看到的是实际动作与差异，而非模型的模糊描述。
3. **授权语义**：审批服务签发绑定请求哈希、审批人、范围、次数和短有效期的令牌；Executor执行前重新鉴权，并检查资源版本和环境是否变化。任何参数改变都使审批失效。
4. **执行保障**：写操作使用幂等键，优先提供dry-run、备份和补偿；超时未批自动取消，拒绝后不得由Agent绕路重试。申请、查看、批准、执行和结果全部写入审计链。

| 模式 | 适用风险 | 控制强度 |
|---|---|---|
| 用户确认 | 个人低至中风险 | 单人、单次 |
| 业务审批 | 跨资源高风险 | 指定角色 |
| 双人复核 | 资金、生产核心操作 | 职责分离 |
| 自动拒绝 | 越权或不可接受风险 | 不允许审批豁免 |

需监控审批绕过率、误批率、等待时长和执行偏差，定期复核审批策略与人员权限。

**相关知识点：** 风险分级、职责分离、四眼原则、请求哈希、一次性授权、TOCTOU、dry-run、幂等、补偿、审计链。
<a id="tool-111"></a>
### 如何保证工具调用的安全性？

工具调用安全依赖**模型与执行权分离、最小权限、全程校验和可审计执行**。模型只能提出调用意图，可信控制面决定能否执行。

1. **可信注册**：工具通过Registry发布名称、版本、Schema、权限和副作用等级；来源需签名，变更经过评审，防止同名替换。
2. **调用前控制**：依据用户、租户、任务和资源执行鉴权与策略授权；参数进行类型、范围、路径、域名和业务规则校验。高风险动作展示实际参数并审批，批准后任何变更必须重新审批。
3. **执行隔离**：Executor使用短期、最小范围凭证，在沙箱或专用服务账户中运行；限制文件、网络、CPU、时间、响应大小和并发。外部返回值视为不可信数据，不得覆盖系统指令。
4. **副作用保护**：写操作使用幂等键、dry-run、事务或补偿；设置超时、有限重试、熔断和紧急停止。密钥由Secrets Manager按需注入，禁止进入提示词和日志。

| 威胁 | 关键控制 |
|---|---|
| 越权调用 | RBAC/ABAC、最小权限 |
| 参数注入 | Schema与语义校验 |
| 提示词注入 | 数据/指令隔离、工具白名单 |
| 重复副作用 | 幂等、状态查询、补偿 |
| 数据外泄 | 出站白名单、脱敏、DLP |

全链路记录Trace、授权、参数摘要、版本和结果，并通过权限矩阵、对抗样例与故障注入验证防线。

**历史别名：** `ARC-086`。

**相关知识点：** Tool Registry、RBAC、ABAC、Policy Engine、短期凭证、沙箱、提示词注入、DLP、幂等、Secrets Manager。
<a id="tool-113"></a>
### 工具调用失败如何自动恢复？

自动恢复的目标不是反复重试，而是借助**持久化状态、错误分类、幂等执行和替代路径**，从最近安全点继续，并确保业务状态不重复、不丢失。

1. **保存检查点**：每次调用前持久化任务状态、工具版本、规范化参数、幂等键和预期副作用；调用后记录结果与外部资源版本。进程崩溃后可判断尚未执行、执行成功或结果未知。
2. **分类恢复**：瞬时错误采用有限退避重试；参数错误让模型在Schema和错误码约束下有限修正；服务不可用可切换等价工具、缓存或异步队列；权限和业务拒绝直接终止或转人工。
3. **处理结果未知**：写操作先通过幂等键查询服务端状态，不得直接重放；若无法去重，使用事务、Outbox、Saga补偿或人工核对。补偿必须独立审计，并允许补偿失败再次处理。
4. **恢复编排**：状态机明确Retry、Fallback、Compensate、Pause和Fail终态，设置总时限、最大恢复次数与熔断；恢复后从检查点重建最小上下文，而非重新执行整条链。

| 故障状态 | 判断依据 | 恢复策略 |
|---|---|---|
| 未执行 | 无受理记录 | 安全重试 |
| 已成功 | 查询到相同幂等键 | 复用结果 |
| 结果未知 | 超时且无状态接口 | 暂停核对 |
| 部分完成 | 子步骤状态不一致 | Saga补偿/续作 |

应通过故障注入验证进程退出、网络分区、重复消息和补偿失败，监控恢复成功率、重复副作用率及平均恢复时间。

**历史别名：** `GOV-050`、`GOV-133`。

**相关知识点：** Checkpoint、幂等键、状态查询、Saga、Outbox、补偿事务、错误分类、Fallback、故障注入、恢复点目标。
<a id="tool-115"></a>
### Tool参数生成错误如何治理？

Tool参数错误应通过**契约前移、分层校验、有限修复和反馈评测**治理，不能把业务API报错原样交给模型无限尝试。

1. **优化Schema**：使用明确类型、必填项、枚举、格式、范围、互斥条件和示例；字段名表达业务含义，避免多个相似参数。工具描述说明适用与禁用场景，并对Schema和工具版本绑定。
2. **分层校验**：模型侧启用结构化输出；Gateway先做JSON Schema校验，再做日期关系、资源存在性、权限、额度和状态机等语义校验。字符串还需路径、域名、SQL片段等安全检查。
3. **受控修复**：返回错误码、字段路径、约束和候选值，让模型仅修改错误字段；限制次数，连续失败转为追问或人工处理。禁止删除安全字段绕过校验。
4. **高风险确认**：对金额、收件人、删除范围等关键参数，先标准化并展示差异，审批令牌绑定完整参数哈希；执行前再次验证资源版本，防止检查与使用间状态变化。

| 错误层次 | 示例 | 处理方 |
|---|---|---|
| 语法/类型 | 日期格式错误 | Schema Validator |
| 业务语义 | 结束时间早于开始 | 规则引擎 |
| 权限 | 访问其他租户资源 | Policy Engine |
| 信息缺失 | 用户未提供目标 | 追问用户 |

将参数一次通过率、字段错误分布、修复成功率和误执行率纳入评测，反向改进工具描述、Schema与训练样例。

**历史别名：** `GOV-052`。

**相关知识点：** JSON Schema、Structured Output、语义校验、Policy Engine、参数规范化、错误码、TOCTOU、审批哈希、契约测试。
<a id="tool-118"></a>
### 如何设计Agent工具调用白名单？

工具白名单应是**基于身份、任务、环境、资源和风险动态计算的最小能力集合**，不是一份对所有用户永久开放的工具名称列表。

1. **分层准入**：工具先经过平台级安全评审进入Registry；再按租户、角色、Agent类型和环境配置静态许可；每次任务依据用户身份、目标、数据等级及当前状态生成会话级候选集。
2. **细化到动作与资源**：不仅限制工具名，还限制版本、操作类型、资源范围、参数区间、目标域名、调用次数和有效期。例如允许查询本人订单，不等于允许查询任意订单。
3. **风险控制**：读写分离，高风险工具默认不进入模型上下文；确需使用时由策略引擎触发审批，签发绑定参数哈希的一次性令牌。禁止模型通过别名、通用HTTP工具或代码执行间接绕过。
4. **执行时复核**：Gateway与最终业务服务都要重新鉴权，工具返回内容按不可信数据处理；权限变化应即时撤销会话能力，所有拒绝和调用均写审计。

| 白名单层级 | 约束对象 | 更新频率 |
|---|---|---|
| 平台级 | 是否允许接入工具 | 发布时 |
| 租户/角色级 | 哪类主体可见 | 策略变更时 |
| 会话级 | 当前任务可调用项 | 每次任务 |
| 调用级 | 参数与具体资源 | 每次执行 |

治理上应设置负责人、版本、到期时间和定期复核，监控未使用权限、拒绝率与绕过尝试；工具下线采用先隐藏、再拒绝、最终移除的兼容流程。

**相关知识点：** Allowlist、最小权限、RBAC、ABAC、Capability Token、Policy Engine、参数级授权、权限撤销、工具注册表。
<a id="tool-119"></a>
### 如果用户确认了高危命令，系统还要不要拦截？

**仍然要拦截不可接受或越权的命令**。用户确认只能证明其知晓某个具体风险，不能替代身份授权、组织策略、法律合规和系统安全边界。

1. **不可豁免项**：越权访问、跨租户操作、泄露密钥、破坏审计、绕过安全控制、违反法规及可能影响无关主体的命令，应由策略引擎硬拒绝，即使用户重复确认也不得执行。
2. **可确认项**：用户确有权限、影响范围明确且风险可接受的删除、覆盖、发布等操作，可在展示规范化命令、目标、影响预览和恢复方案后确认。确认必须绑定参数哈希、身份、环境、有效期和单次执行。
3. **分级审批**：个人资源可由本人确认；生产、资金或批量数据操作需要指定角色审批或双人复核；系统级极高风险操作应改用受控运维流程，不交给通用Agent。
4. **执行前复检**：确认后仍重新检查权限、资源版本、环境与策略，参数变化即失效；优先dry-run、备份、限速、幂等和可回滚执行，并设置紧急停止。

| 控制 | 回答的问题 | 能否被确认替代 |
|---|---|---|
| 身份授权 | 用户有没有权力 | 否 |
| 硬性策略 | 组织是否允许 | 否 |
| 风险确认 | 用户是否理解后果 | 仅适用于可接受风险 |
| 双人审批 | 是否满足职责分离 | 否 |

全过程记录请求、警告、确认、策略决策和执行结果，防止“用户已确认”成为系统转移安全责任的依据。

**验证指标：** 工具选择准确率、调用成功率、参数错误率、P95 延迟和失败恢复率。

**相关知识点：** 知情确认、硬策略、最小权限、职责分离、参数绑定、TOCTOU、dry-run、可回滚执行、审计责任。

### Agent生成的SQL如何做影响范围评估？

Agent生成的SQL执行前须经过**语法树解析、权限校验、计划分析、数据量预估和受控试运行**，禁止仅靠字符串匹配或模型自检。

1. **静态分析**：解析AST，识别语句类型、库表、列、JOIN、子查询、函数及WHERE条件；拒绝多语句、动态SQL、危险DDL、系统表访问和无法解析的方言。将逻辑对象映射到用户实际可访问资源。
2. **范围估算**：使用EXPLAIN获取扫描方式、估算行数、成本、索引命中和锁范围；结合表规模、分区裁剪、谓词选择性及历史统计，计算扫描行、返回行、影响行、执行时间和资源消耗上界。
3. **环境验证**：只读查询先在只读副本设置行数、时间、内存和并发限制；写语句在脱敏影子库或事务中dry-run，展示目标表、预计行数、样例主键和前后差异。统计信息过旧时提高风险等级。
4. **决策执行**：按阈值自动放行、限流、审批或拒绝；生产写入必须带主键范围、幂等标识和回滚方案，执行时监控实际影响，一旦超过批准阈值立即中止。

| 检查方式 | 能判断 | 局限 |
|---|---|---|
| AST分析 | 对象与语义风险 | 不知道实际数据量 |
| EXPLAIN | 计划与估算成本 | 依赖统计信息 |
| dry-run/影子库 | 结果与影响样例 | 数据可能不完全一致 |
| 在线护栏 | 实际行数与时长 | 已进入执行阶段 |

审计需保存原SQL、规范化SQL、计划摘要、评估版本、审批阈值及实际影响，并持续校准估算误差。

**相关知识点：** SQL AST、EXPLAIN、基数估计、谓词选择性、分区裁剪、只读副本、dry-run、查询护栏、影响行数。
