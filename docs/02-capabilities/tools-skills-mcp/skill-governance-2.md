### 1. Skill 如何跨团队复用？

跨团队复用的关键是把Skill从“团队脚本”升级为**稳定契约、明确Owner、可配置实现和受治理服务**，同时保留领域差异与数据边界。

1. **抽取公共内核**：识别各团队共同目标、输入输出和关键步骤，把差异项参数化或放入策略插件；权限、成功标准或流程本质不同的场景保留独立Skill，避免过度抽象。
2. **标准与文档**：统一Metadata、Schema、版本、错误码、依赖和评测规范；提供适用/禁用条件、正反例、快速试用和迁移说明。契约向后兼容，已发布制品不可变。
3. **组织分发**：内部Registry或Marketplace支持发现、比较、安装、灰度、反馈与弃用；按团队、租户和敏感等级控制可见性。共享只表示能力可用，真实调用仍按用户与资源鉴权。
4. **质量分层**：公共评测集验证通用行为，各团队使用本地数据补充兼容测试；指标按团队、任务和版本切片，防止一个团队的高成功率掩盖其他团队退化。
5. **运营责任**：设主Owner、贡献者和支持SLA，明确变更提案、评审、成本分摊与漏洞响应；重复实现通过语义检测和委员会评审合并。

| 共享模式 | 适用情况 | 风险 |
|---|---|---|
| 直接复用 | 契约完全一致 | 本地差异被忽略 |
| 参数化复用 | 流程一致、策略不同 | 配置膨胀 |
| 公共子Skill | 局部能力一致 | 依赖过深 |
| 独立Skill | 权限或语义本质不同 | 重复维护 |

**相关知识点：** 公共内核、策略插件、内部Marketplace、契约兼容、分级共享、本地评测、Owner、成本分摊、重复治理。

### 2. Skill Marketplace 应该如何设计？

Skill Marketplace应按**供给审核、目录发现、受控消费、运行反馈和生命周期退出**设计，既是产品门户，也是安全与质量控制面。

1. **供给流程**：发布者提交身份、Owner、Metadata、版本、许可证、SBOM、依赖、权限、风险和评测；平台完成Schema校验、签名、漏洞与恶意行为扫描，高风险项人工共审。
2. **目录与推荐**：支持领域树、标签、关键词、向量和场景导航；展示契约、适用/禁用条件、质量、成本、维护状态、已知限制及依赖。检索前按租户、环境和权限过滤。
3. **试用与安装**：提供样例、沙箱试跑、权限影响预览和管理员审批；安装只将Skill加入租户候选集，运行时仍以用户身份鉴权。支持固定版本、自动更新策略、配额和成本预算。
4. **运行治理**：采集成功率、人工改选、延迟、一次成功成本、事故和反馈，按版本与场景切片；评分结合客观指标和可信评价，防止下载量及刷分主导排序。
5. **退出机制**：安全问题可紧急撤销并使缓存失效；普通弃用提供替代、迁移窗口和反向依赖通知。无Owner、长期过期或低价值项归档。

| 平面 | 核心能力 | 安全重点 |
|---|---|---|
| 发布者门户 | 创建、评测、发布 | 身份与供应链 |
| 消费者门户 | 搜索、比较、试用 | 权限过滤 |
| 管理控制台 | 审批、配额、策略 | 租户治理 |
| 运营平台 | 指标、反馈、退出 | 持续复评 |

**相关知识点：** Marketplace、SBOM、制品签名、沙箱试用、权限预览、信誉体系、成本预算、反向依赖、紧急撤销。

### 3. 如何构建一个可持续进化的 Skill 沉淀体系？

可持续进化依赖**数据反馈飞轮与严格发布门禁并存**：运行产生候选经验，评测筛选有效改进，版本化发布验证收益，低价值资产持续退出。

1. **统一可观测数据**：用结构化事件记录目标、步骤、Tool、结果、人工修正、成本、风险和版本，建立稳定评测集与数据血缘；日志脱敏，模型自评不作为成功真值。
2. **双通道沉淀**：专家从SOP和政策主动建设，平台从高频成功轨迹、失败热点与用户改选中发现候选；自动抽取只形成草稿，不直接改变线上Skill。
3. **工程化门禁**：候选必须完成契约、重复、权限、安全、独立质量和成本评测，经Owner与领域审核，再通过Shadow、Canary和渐进发布；严重错误一票否决。
4. **在线学习闭环**：按任务、版本和租户观察成功增量、人工接管、一次成功成本及风险事件；反馈进入离线数据集，经去偏、去重和复核后用于下一版本，避免实时自我修改。
5. **组织与退出**：明确Owner、SLA、维护预算和贡献机制；定期检查过期知识、依赖漏洞、重复和使用价值，执行合并、弃用、归档与迁移。

| 环节 | 自动化边界 | 人工责任 |
|---|---|---|
| 发现 | 聚类、候选生成 | 确认业务价值 |
| 验证 | 批量评测 | 定义门槛与反例 |
| 发布 | 灰度与回滚 | 高风险审批 |
| 运营 | 指标告警 | 归因与取舍 |

体系目标应是持续提升业务成功率和治理质量，而非持续增加Skill数量。

**相关知识点：** 反馈飞轮、数据血缘、候选Skill、独立评测、Shadow、Canary、离线学习、Owner机制、生命周期清退。

### 4. 如何根据仓库类型动态选择Skill？

动态选择应先构建**可验证的仓库画像**，再用Metadata硬过滤与质量排序选择Skill；仓库类型不是单一语言标签，而是技术栈、结构、构建和风险的组合。

1. **仓库探测**：只读扫描清单、锁文件、构建配置、扩展名、CI和部署文件，识别语言、框架、包管理器、测试工具、应用类型与monorepo；冲突信号保留置信度。
2. **子项目划分**：monorepo按工作区与依赖图建立模块画像，不用根标签覆盖子项目；变更文件决定局部技术栈，并保留跨模块依赖。
3. **Skill声明**：Metadata标注支持的语言、框架版本、构建器、任务类型、目录模式、所需工具、环境、权限与互斥条件；通用Skill作为兜底，专用Skill只有前置条件满足才优先。
4. **选择流程**：先按画像、兼容版本和权限过滤，再结合用户目标、受影响模块、历史同类成功率、成本与风险重排；置信不足时运行安全探测命令或向用户澄清。
5. **缓存更新**：画像以提交、分支和配置摘要为键；构建文件变化即失效。记录选择证据，避免任务中途漂移。

| 仓库信号 | 推断内容 | 注意点 |
|---|---|---|
| manifest/lockfile | 语言与依赖 | 多文件可能冲突 |
| 构建配置 | 命令与模块 | 版本兼容 |
| CI配置 | 真实验证流程 | 可能含密钥引用 |
| 目录与扩展名 | 子项目边界 | 生成代码需排除 |

**相关知识点：** Repository Profiling、Monorepo、依赖图、Metadata Filter、置信度、通用兜底、缓存失效、版本兼容。

### 5. 如何构建Skill知识库？

Skill知识库应以**权威Metadata与制品为源，构建面向发现、理解和治理的多索引视图**，而不是把所有SKILL.md简单写入向量库。

1. **内容建模**：保存ID、版本、目标、条件、契约、领域、示例、依赖、权限、风险、质量、Owner和状态；Prompt、代码、Workflow作为签名制品存储。
2. **索引策略**：名称、标签、术语进入BM25；目标、场景、正反例生成向量；Schema、权限、环境和版本用于结构化过滤，依赖进入图索引。字段分别加权。
3. **构建流水线**：发布触发Schema校验、脱敏、去重、Embedding和索引更新；记录模型与索引版本。撤销先移出可见集，再异步清理。
4. **检索服务**：先做租户、权限、状态、风险和兼容过滤，再BM25与向量多路召回、去重、Rerank和置信门控；返回候选、来源字段、得分、版本及选择理由。
5. **治理运维**：监控新鲜度、索引延迟、重复率、Recall@K与漂移，支持增量更新、恢复、审计和清理。

| 存储 | 内容 | 角色 |
|---|---|---|
| 元数据仓 | 契约、权限、版本 | 权威源 |
| 制品仓 | Skill实现与附件 | 不可变内容 |
| 搜索/向量索引 | 语义发现 | 可重建 |
| 图存储 | 依赖与血缘 | 影响分析 |

**相关知识点：** Skill知识库、BM25、向量索引、Metadata Filter、图索引、Embedding版本、Rerank、增量索引、权威数据源。

### 6. Skill之间如何传递上下文？

Skill之间应通过**版本化的结构化状态和最小化数据引用**传递上下文，避免直接拼接完整对话、隐藏Scratchpad或共享可变全局内存。

1. **定义Schema**：区分目标、确认事实、中间结果、证据、决策、待办、错误和预算；字段标注类型、来源、时间、置信、敏感等级与范围。Skill只读所需字段。
2. **传值与引用**：小型结果直接传；文档、日志和代码存对象仓，只传URI、摘要、版本及短期令牌，令牌绑定接收Skill。
3. **状态一致性**：Workflow Runtime作为权威源，节点以乐观锁原子更新；每步产生不可变事件和新版本，禁止同时覆盖同一字段。
4. **压缩与隔离**：历史对话转为事实、决策和未完成项摘要，关键原文保留引用；敏感字段按权限过滤或脱敏，模型推理草稿不作为跨Skill事实。外部Tool结果标记为不可信数据。
5. **传播控制**：Trace、Deadline、取消、预算和幂等域向下传播，但权限重新计算；子Skill结果由父级验证后合并。

| 方式 | 适用内容 | 风险 |
|---|---|---|
| 结构化传值 | 状态、参数、小结果 | Schema演进 |
| 受控引用 | 大文件、原始证据 | 引用失效与权限 |
| 对话全文 | 极少使用 | Token、隐私、注入 |
| 全局共享内存 | 不推荐 | 串扰与竞态 |

**相关知识点：** Context Schema、结构化状态、对象引用、乐观锁、事件溯源、数据最小化、Trace Context、权限再计算、Schema迁移。

### 7. Planner和Skill Router的边界是什么？

**Planner把目标分解成子目标及依赖，Skill Router为明确子目标选择已注册能力**。前者决定做哪些事，后者决定用哪个Skill。

1. **Planner**：输入目标、约束和状态，输出子目标、依赖、成功判据、预算与终止；可修改计划，但不能绕权调用Tool。
2. **Router**：输入单个子目标、上下文和身份，对Registry候选过滤、召回、重排与门控，返回固定版本或无匹配。
3. **交互闭环**：Planner提出子目标，Router匹配；无匹配时重新分解、组合或澄清。执行后更新状态，仅在目标未满足时重规划。
4. **控制边界**：权限、风险、审批、预算和兼容由确定性控制面强制，不能被评分覆盖；两者不持有执行凭证。
5. **防止循环**：记录计划、路由指纹、失败和完成状态，限制重规划；条件未变时不得改写目标绕过拒绝。

| 组件 | 优化目标 | 主要失败 |
|---|---|---|
| Planner | 全局任务可完成 | 分解错误、循环 |
| Skill Router | 局部能力匹配准确 | 误选、漏选 |
| Runtime/Policy | 安全可靠执行 | 状态或授权错误 |

**验证指标：** 工具选择准确率、调用成功率、参数错误率、P95 延迟和失败恢复率。

**相关知识点：** Task Planning、Skill Routing、子目标、Registry、计划修复、置信门控、Policy Engine、循环检测、全局与局部优化。

### 8. 多Agent协作时如何共享Skill？

多Agent协作应共享**Skill定义、契约和受控制品**，并隔离会话、Memory、权限与预算；协调器分配，Registry统一版本。

1. **能力目录**：Agent从统一Registry发现Skill，标注适用角色、契约、依赖、风险与版本；协调器过滤后随子任务分配具体版本。
2. **契约通信**：Agent以任务ID、结构化结果、证据引用和错误码交接，不复制完整对话。大对象放受控存储，用短期令牌访问。
3. **身份与权限**：每个Agent以独立身份和用户上下文调用，重新授权；主Agent有权不代表子Agent有权。高风险动作集中审批。
4. **状态协调**：权威Store维护Workflow状态，Agent以租约领任务、幂等更新和检查点防重复；子Agent只获分配预算。
5. **版本与反馈**：同一任务固定依赖锁；指标按Agent角色、模型和Skill版本切片，兼容问题局部回退。

| 共享内容 | 方式 | 是否可修改 |
|---|---|---|
| Skill制品 | Registry固定版本 | 否 |
| 任务状态 | 状态库+版本控制 | 受控 |
| 证据数据 | URI+短期令牌 | 按权限 |
| 用户Memory | 默认不共享 | 明确授权例外 |
| 凭证 | 按Agent动态签发 | 不共享 |

**相关知识点：** 多Agent协作、能力目录、结构化交接、租约、状态权威源、依赖锁、预算分配、身份隔离、Trace。

### 9. 企业级Agent一般有多少个Skill？

企业级Agent**没有合理的固定Skill数量**。单个Agent应只暴露完成职责所需的最小活跃集合，组织可以拥有数百或更多资产，但不能全部同时注入模型。

1. **决定因素**：业务领域宽度、任务复杂度、Skill粒度、风险、团队规模和Router能力共同决定数量。按单个案例拆分会数量爆炸，过度合并又会使边界模糊、评测困难。
2. **分层规模观**：面向单一岗位的Agent常见是少量到几十个高频Skill；跨部门平台的Registry可能有数百至数千个，但应按租户、角色、场景和环境裁剪为小候选集。百万级更像生态目录，不是单Agent工具箱。
3. **控制上下文**：模型初始只看到名称、短描述或检索接口，Router经权限过滤和召回得到Top-K，再加载少数Skill全文；避免Token膨胀、选择混淆和不必要权限暴露。
4. **以指标定规模**：监控候选共现、Top-1准确率、无用权限、复用率、维护成本和改选。新增Skill须有复用证据，低使用或重叠项合并、弃用。

| 视角 | 关注数量 | 管理方式 |
|---|---|---|
| 单次模型上下文 | 极少数候选 | Top-K按需加载 |
| 单个Agent活跃集 | 少量至几十 | 角色与场景过滤 |
| 企业Registry | 数百/数千可存在 | 分域与生命周期 |
| 外部生态目录 | 可达更大规模 | 分片检索与信任分级 |

因此，衡量成熟度应看匹配质量和业务覆盖，不看Skill总数。

**相关知识点：** 最小能力集、活跃集合、Top-K、按需加载、目录分域、能力粒度、维护成本、Skill清退、权限暴露。

### 10. Skill注册中心如何设计？

Skill注册中心应成为**版本、契约、权限、依赖和生命周期的权威控制面**；检索索引和制品仓是配套组件，不能反向成为事实来源。

1. **核心模型**：以稳定Skill ID和不可变版本为主键，保存Metadata、输入输出Schema、适用条件、Owner、风险、权限、依赖、评测、渠道和状态；制品仅保存摘要与仓库地址。
2. **状态机与API**：提供Draft、Review、Canary、Active、Deprecated、Revoked状态，以及注册、校验、评审、发布、解析、查询、弃用、撤销和订阅接口。每次变更做鉴权、审批和追加审计。
3. **存储架构**：关系库承担强一致元数据，对象仓保存签名制品，搜索/向量索引承担发现，图存储维护依赖与血缘；通过事务Outbox驱动索引和事件更新，所有派生数据可重建。
4. **运行时一致性**：任务把渠道别名解析为具体版本并固定；读缓存按租户和版本隔离。撤销通过高优先级事件推送，节点收到后立即隐藏并失效缓存，未知状态默认拒绝。
5. **可靠治理**：多可用区、备份恢复、幂等写入、Schema版本化和灾难演练；Dashboard展示采用、质量、漏洞、过期和依赖影响。

| 组件 | 权威性 | 主要职责 |
|---|---|---|
| 元数据仓 | 权威 | 契约与治理 |
| 制品仓 | 内容权威 | 不可变实现 |
| 检索索引 | 派生 | 召回 |
| 事件流 | 派生可重放 | 变更传播 |

**相关知识点：** Registry、生命周期状态机、Outbox、制品签名、版本解析、缓存失效、依赖图、可重建索引、多租户。

### 11. 如何评估一个Skill是否值得沉淀？

评估应建立**价值、可复用性、可工程化、风险和维护成本**五维门槛；满足业务收益但无法可靠验证的任务，不应直接沉淀为自动执行Skill。

1. **业务价值**：统计频率、覆盖用户、人工耗时、周期、错误损失和合规风险；高频任务看效率，低频高风险任务看控制价值。明确相对现状的目标增益。
2. **模式复用**：分析多条轨迹是否共享目标、输入输出、关键步骤和成功判据，差异能否参数化；一次成功或依赖某位专家临场判断的案例，先保留为经验。
3. **工程可行**：所需Tool、数据与权限稳定，失败可观察，副作用可幂等、回滚或补偿；存在代表性评测集、Owner、SLA和升级路径。
4. **成本收益**：估算开发、标注、评测、审批、运行、依赖升级和清退成本，对比节省工时、业务增量与风险损失减少，计算净价值与回收期。
5. **试运行决策**：先模板化或半自动运行，在独立样例上比较成功率、人工接管、一次成功成本和安全；达到阈值再进入Registry。

| 维度 | 通过信号 | 否决信号 |
|---|---|---|
| 复用 | 多案例稳定模式 | 一次性需求 |
| 验证 | 明确成功判据 | 结果不可判断 |
| 依赖 | 可版本化、可授权 | 不稳定或越权 |
| 经济 | 正净价值 | 维护成本过高 |
| 治理 | 有Owner与退出机制 | 无人负责 |

沉淀后仍需周期复评，使用低、无增益或规则过期时应合并、降级为模板或下线。

**相关知识点：** Skill准入、复用性、可工程化、净价值、回收期、一次成功成本、试运行、Owner、生命周期复评。
<a id="tool-231"></a>
### 12. 如何建立Skill运营体系？

Skill运营体系应围绕**供给质量、分发效率、使用效果、风险治理和生命周期**建立责任、流程、指标与节奏，把Skill当作持续运营的产品资产。

1. **角色机制**：明确平台、领域、发布、安全、运营和使用团队职责；每个Skill配置Owner、SLA、风险、维护预算及替补。
2. **供给运营**：提供需求池、评审、模板、评测、签名、灰度和发布日历；从SOP与日志发现候选，用重复检测和准入控制数量。
3. **分发与采用**：Marketplace按领域、场景和角色展示，提供沙箱、权限预览、案例与迁移指南；推荐先做权限过滤。
4. **指标体系**：监控活跃用户、复用率、Top-1匹配、任务成功、人工接管、一次成功成本、P95延迟、风险事件、版本采用和用户反馈；按版本、团队和场景切片。
5. **生命周期运营**：定期健康评审，低采用、重叠、过期或有漏洞的Skill优化、合并、弃用或撤销，并提供迁移窗口。

| 运营阶段 | 核心指标 | 决策 |
|---|---|---|
| 引入 | 试用转化、评测通过 | 是否发布 |
| 成长 | 活跃、复用、成功率 | 是否扩展 |
| 稳定 | SLA、成本、风险 | 持续优化 |
| 衰退 | 使用下降、维护状态 | 合并或退出 |

定期资产盘点结合实时告警，激励基于业务增益和维护质量，而非数量。

**相关知识点：** Skill运营、Owner机制、Marketplace、健康度、采用率、一次成功成本、SLA、生命周期、资产盘点、激励机制。

### 13. 如何实现Skill自动发现与推荐？

Skill自动发现与推荐应分为**候选资产发现**和**在线能力推荐**两条链路：前者从行为中挖掘新Skill，后者为当前任务选择已有Skill，两者都需权限与质量门控。

1. **候选发现**：对脱敏意图、工具序列、结果和修正做归一化、聚类及流程挖掘，识别高频、高成功、轨迹稳定的模式；生成契约草案，专家审核后进入Registry。
2. **在线召回**：请求先提取目标、实体、场景和风险，按租户、身份、状态、环境和Schema过滤；使用名称/标签、BM25、Embedding和历史案例多路召回并去重。
3. **个性化重排**：Reranker综合语义、专用度、质量、成本、时效和偏好；只能在授权候选内调整。新Skill以受控探索获得曝光。
4. **置信与体验**：高分且领先明显时推荐或自动路由，候选接近时解释差异并澄清，无匹配时拒选；高风险Skill默认不做无确认自动执行。
5. **反馈闭环**：记录曝光、采用、改选、任务成功和接管，以A/B评估增益；去除位置与流行度偏差，离线验证后更新。

| 环节 | 核心指标 | 主要风险 |
|---|---|---|
| 新Skill发现 | 候选转化、复用增益 | 固化错误经验 |
| 召回 | Recall@K | 漏掉正确项 |
| 推荐排序 | NDCG、采用率 | 流行度偏差 |
| 执行 | 任务成功、严重误选 | 权限与副作用 |

**相关知识点：** 语义聚类、Workflow Mining、Hybrid Retrieval、Reranker、受控探索、反馈偏差、A/B测试、拒选、权限过滤。

### 14. 如何实现分层Skill架构？

分层Skill架构应按**执行原语、通用能力、领域能力、业务流程和治理控制**分离变化速度与责任边界，避免所有逻辑堆在一个Agent Prompt中。

1. **Tool层**：封装搜索、数据库、文件和业务API等原子动作，提供Schema、鉴权、幂等、超时和审计，不含跨步骤判断。
2. **基础Skill层**：沉淀检索、摘要、分类、验证、计划、Review等跨领域能力，以稳定契约复用Tool并独立评测。
3. **领域Skill层**：加入法务、财务、研发等规则、知识与技术栈，通过参数和策略扩展基础Skill；权限按领域定义。
4. **业务Workflow层**：将Skill组织为状态机或DAG，处理审批、补偿、检查点和SLA；Planner只在受限节点参与。
5. **控制治理层**：Registry、Router、Policy、Runtime、评测和追踪横切各层，统一版本、预算、灰度与退出。

| 层级 | 复用范围 | 变化频率 |
|---|---|---|
| Tool | 全平台 | 接口驱动 |
| 基础Skill | 跨业务 | 较低 |
| 领域Skill | 领域内部 | 中 |
| Workflow | 具体业务 | 较高 |
| 治理控制 | 全组织 | 策略驱动 |

依赖自上向下且显式，禁止底层反向依赖业务层；契约稳定、实现可替换，任务固定版本和依赖锁。只有职责与演进速度不同才拆层。

**相关知识点：** 分层架构、Tool层、基础Skill、领域Skill、Workflow、控制面、依赖倒置、稳定契约、依赖锁。
