# Workflow Skill 与能力编排

<a id="tool-139"></a>
### 一个Skill内部应该如何调用多个Tool？

多Tool Skill应以**显式状态、依赖关系、统一契约和受控副作用**组织调用；模型负责有限决策，运行时负责调度、授权、恢复和终止。

1. **先定义计划**：把目标拆成原子步骤，声明每步输入、输出、前置条件、成功判据和依赖。固定流程用状态机或DAG；路径未知时由Planner生成候选计划，再做工具白名单、参数和可执行性校验。
2. **管理数据流**：使用类型化共享状态传递结果，不拼接冗长自然语言；每个Tool返回标准状态、错误码、结构化数据和证据。只向下游提供必要字段，敏感数据按权限过滤。
3. **可靠调度**：无依赖且只读的调用可并行；写操作明确顺序、幂等键、事务边界和补偿。为每步设置超时、有限重试与熔断，失败按错误类型选择重试、替代、跳过、补偿或人工接管。
4. **安全与观测**：执行每个Tool前重新授权，高风险动作审批；统一Trace关联步骤、版本、参数摘要、耗时和费用。总步骤、Token、并发、时长和预算均设置硬上限。

| 编排方式 | 适用场景 | 注意点 |
|---|---|---|
| 顺序 | 强依赖步骤 | 延迟累加 |
| 并行 | 独立只读查询 | 汇总与部分失败 |
| 条件分支 | 规则明确 | 分支覆盖测试 |
| 动态规划 | 路径未知 | 必须预算和验证 |

最终结果需由验证节点检查完整性、一致性和来源；不能因单个Tool成功就认定Skill完成。

**相关知识点：** 状态机、DAG、Planner、类型化状态、并行调用、幂等、Saga补偿、错误分类、Trace、结果验证。
<a id="tool-149"></a>
### Skill和Tool有什么区别？

从系统架构看，**Tool属于执行层的原子接口，Skill属于能力层的任务策略**：Agent选择Skill完成目标，Skill再编排一个或多个Tool实施动作。

1. **职责**：Tool封装查询、HTTP调用、代码执行等确定动作；Skill封装领域方法、步骤、分支、验证和失败处理，目标粒度更高。
2. **状态**：Tool通常无状态，调用后即返回；Skill可维护任务状态、检查点与证据，支持暂停、恢复和人工介入。
3. **安全**：Tool声明资源权限、副作用、幂等和网络边界，最终服务做资源级鉴权；Skill声明完成任务所需的能力范围与风险策略，但不能替代每次Tool授权。
4. **评测**：Tool关注可用率、延迟、参数正确率和副作用一致性；Skill关注端到端任务成功率、适用性、成本、人工接管与业务收益。

| 比较项 | Tool | Skill |
|---|---|---|
| 抽象层 | 执行接口 | 任务能力 |
| 典型内容 | API、函数、命令 | Prompt、规则、Workflow |
| 复用方式 | 被多个Skill调用 | 被Planner按目标选择 |
| 版本重点 | 契约兼容 | 行为质量与依赖兼容 |

例如“发送邮件”是Tool；“处理客户投诉”是Skill，需检索订单、判断政策、审批补偿并调用发送Tool。分层可避免Tool隐藏业务决策。

**历史别名：** `TOOL-128`。

**相关知识点：** 执行层、能力层、Tool Contract、Skill Contract、状态管理、资源级鉴权、端到端评测、能力编排。
<a id="tool-158"></a>
### Skill 和 Tool 的本质区别是什么？

本质上，**Tool是能力的“执行原语”，Skill是经验的“程序性抽象”**：Tool把外部世界的一个动作暴露给系统，Skill把完成一类目标的方法沉淀为可复用策略。

1. **语义层级**：Tool描述函数契约，即输入、动作和返回；Skill描述任务契约，还包含适用条件、步骤、验证、异常和完成标准。
2. **确定性边界**：Tool应尽量确定、幂等且可独立测试；Skill可组合模型、规则、Workflow与Tool，具有上下文和概率性，需端到端评测。
3. **控制责任**：Tool承担资源级权限、参数校验、限流、超时和副作用一致性；Skill承担计划级风险、预算、审批节点和失败恢复。Skill选择合法不代表其中每个Tool自动获权。
4. **演进方式**：Tool按接口兼容和服务SLA演进；Skill按业务目标、知识有效性、行为质量和依赖版本演进。把两者分开，可替换底层工具而保持能力契约，也可复用工具构建新能力。

| 本质维度 | Tool | Skill |
|---|---|---|
| 抽象对象 | 动作 | 完成目标的方法 |
| 知识类型 | 接口知识 | 程序性/领域知识 |
| 组合位置 | 叶子执行节点 | 编排与决策节点 |
| 主要失败 | 调用或副作用失败 | 目标未完成 |

例如“查汇率”是Tool，“制定差旅预算”是Skill；后者还需应用政策、计算并验证结果。

**相关知识点：** 执行原语、程序性知识、任务契约、Tool Contract、Skill Contract、能力编排、资源级授权、端到端验证。

### 什么样的任务适合沉淀为 Skill？

适合沉淀为Skill的任务，应满足**有重复价值、有稳定模式、有明确边界、有可验证结果、有可维护责任人**；不应把每次成功对话都直接资产化。

1. **价值充分**：任务高频、覆盖多人、人工成本高，或虽低频但错误损失与合规风险高。沉淀后能显著提升成功率、缩短时长、统一治理或降低事故概率。
2. **模式稳定**：目标、关键输入输出、步骤和成功判据在多个案例中重复，差异可以参数、策略或有限分支表达；依赖的Tool、数据和规则具有可预期生命周期。
3. **边界清晰**：能够写出适用与禁用条件、所需权限、风险等级、失败语义和人工兜底；无法确定什么时候停止、结果是否正确的任务不宜自动执行。
4. **可工程化**：存在代表性评测集，能版本化、灰度、监控和回滚，并有Owner维护知识、依赖及SLA。缺少维护主体的Skill会快速过期。

| 任务类型 | 适合度 | 推荐形态 |
|---|---|---|
| 高频稳定文本任务 | 高 | Prompt型Skill |
| 固定多工具业务流程 | 高 | Workflow Skill |
| 低频高风险SOP | 高 | 强审批Workflow |
| 一次性开放研究 | 低 | 临时Planner |
| 纯主观创作 | 中低 | 模板或人工协作 |

可先进行若干次受控试运行，以复现率、轨迹稳定度、收益和维护成本打分；通过门槛后进入Registry，否则保留为模板或案例。

**历史别名：** `PLAN-225`、`TOOL-148`。

**相关知识点：** Skill准入、重复价值、轨迹稳定度、成功判据、风险边界、评测集、Owner、Workflow Skill、维护成本。

### MCP Tool 和 Skill 的边界是什么？

**MCP Tool是标准协议暴露的操作，Skill是面向目标的知识与流程抽象**。MCP解决连接，Skill解决何时及如何组合能力。

1. **MCP Tool边界**：Server声明名称、描述和Schema，Client发现调用；它应完成单一动作，不承载跨工具的隐式决策。
2. **Skill边界**：定义目标、条件、契约、步骤、验证、权限和失败处理，可调用本地或MCP Tool，也可只含知识或Prompt。
3. **组合方式**：Host发现工具并做权限、风险过滤；Skill选择Tool后，Host再校验参数、授权、审批并发送tools/call，结果按不可信数据验证。
4. **治理差异**：MCP Tool关注身份、协议、可用性、参数和资源鉴权；Skill关注任务成功、路由、依赖、版本和端到端风险。

| 维度 | MCP Tool | Skill |
|---|---|---|
| 抽象层 | 原子执行接口 | 目标级能力 |
| 标准重点 | 发现与调用协议 | 能力契约与流程 |
| 运行位置 | MCP Server | Agent Host/Runtime |
| 主要评价 | 调用可靠性 | 任务完成与业务价值 |

简单场景可直接调用MCP Tool；需要SOP、多工具组合、验证和恢复时引入Skill。

**相关知识点：** MCP Server、MCP Client、tools/list、tools/call、JSON Schema、Skill Contract、Host安全边界、能力编排、零信任。

### 一个复杂任务如何拆分多个Skill？

复杂任务拆分应按**可独立验证的子目标、清晰数据契约和最小副作用边界**进行，而不是按自然语言段落或工具数量机械切分。

1. **明确全局目标**：定义最终产物、成功判据、约束、时限、预算和不可接受风险，区分必须完成、可选与人工节点；缺少这些信息时先澄清。
2. **建立子目标图**：把任务分解为输入可获得、输出可验证的能力，如收集、分析、决策、执行和验证；识别依赖、可并行项、共享资源及事务边界，形成DAG或状态机。
3. **映射现有Skill**：对每个子目标检索Registry，按权限、前置条件、Schema和质量筛选；完整覆盖则复用，部分覆盖则组合，真正缺口才由Planner临时处理或形成候选Skill。
4. **定义接口与状态**：每个Skill声明输入输出、证据、错误、超时和幂等性，使用结构化共享状态；只传必要信息，避免长对话直接级联。写操作明确顺序、审批与补偿。
5. **运行控制**：外层Workflow管理版本、预算、检查点、失败传播、重试、降级和终止；最终验证节点检查全局目标，防止子Skill均成功但整体结果不一致。

| 拆分原则 | 好的边界 | 反模式 |
|---|---|---|
| 可验证 | 有独立成功判据 | 输出无法判断 |
| 低耦合 | 结构化契约 | 共享隐式上下文 |
| 副作用内聚 | 单一事务责任 | 多Skill共同改同一资源 |
| 可复用 | 跨任务稳定 | 仅服务单个实例 |

**相关知识点：** 任务分解、子目标、DAG、状态机、能力映射、结构化状态、事务边界、补偿、全局验证。
<a id="tool-233"></a>
### MCP和Skill体系是什么关系？

MCP与Skill是**连接协议层和能力抽象层**的关系：MCP标准化外部能力访问，Skill把知识、流程和工具组织成任务能力。

1. **MCP职责**：定义Host、Client、Server协议与协商，Server暴露Tools、Resources和Prompts；以Schema描述工具，解决互操作。
2. **Skill职责**：声明目标、条件、契约、步骤、依赖、权限、验证和失败；可调用MCP Tool、读取Resource，也可使用本地Tool。
3. **融合流程**：Host发现MCP能力后做权限、风险和兼容过滤，注册为Skill依赖；Router选择Skill，Runtime再校验、审批、调用并验证返回。
4. **治理边界**：MCP不解决Tool选择、业务流程、端到端评测和Skill版本；Skill不负责传输与Server发现。两者不替代资源鉴权。
5. **安全原则**：验证Server身份、传输、目标和变更；返回与注解视为不可信数据，凭证最小下传。

| 层次 | MCP | Skill体系 |
|---|---|---|
| 核心问题 | 如何连接与调用 | 如何完成任务 |
| 主要对象 | Tool/Resource/Prompt | 目标、流程、依赖 |
| 复用范围 | 跨客户端互操作 | 跨任务经验复用 |
| 质量 | 协议与调用可靠性 | 任务成功与业务价值 |

**相关知识点：** MCP Host、Client、Server、Tools、Resources、Skill Contract、能力编排、零信任、资源鉴权。
