### TOOL-007 · Skill沉淀体系应该怎么设计？什么样的任务适合沉淀成Skill？（DeepSeek一面）

> 稳定 ID：`TOOL-007`｜原题号：7

Skill 沉淀体系应形成 **发现、评审、封装、发布、评估、淘汰** 的闭环，把稳定经验转为可复用能力，而非保存 Prompt。

1. **资产模型**：每个 Skill 应包含名称、用途、适用边界、输入输出 Schema、步骤、依赖 Tool、权限、风险等级、示例、质量指标、负责人和版本。执行过程需支持状态持久化、失败恢复和审计。
2. **沉淀来源**：从高频请求、成功执行轨迹、人工最佳实践和故障复盘中发现候选；先聚类相似任务，再由专家提炼稳定步骤，使用离线数据集验证后进入 Registry。自动挖掘只负责推荐，不能未经审核直接发布。
3. **生命周期**：采用语义版本、依赖锁定、灰度发布和快速回滚；持续统计调用量、成功率、节省时间、人工接管率与成本。低使用、低收益、重复或长期失败的 Skill 应合并、修复或下线。

| 适合沉淀 | 不适合直接沉淀 |
|---|---|
| 高频重复、步骤相对稳定 | 一次性、目标持续变化 |
| 输入输出可结构化 | 无法定义验收标准 |
| 结果可评测、失败可恢复 | 高度依赖临场主观判断 |
| 能组合稳定Tool完成 | 仍处于探索验证阶段 |

判断公式可概括为：**沉淀价值≈调用频率×单次节省成本×成功率－开发维护成本－风险成本**。代码审查、日报生成、标准化故障排查适合沉淀；开放式战略咨询不宜过早固化。为避免数量爆炸，还需相似度检测、能力域分类和负责人制度。

**相关知识点：** Skill Registry、Workflow Mining、执行轨迹、语义版本、灰度发布、离线评测、ROI、生命周期治理。

### TOOL-009 · Skill分层体系是怎么设计的？为什么要这样分层？不同层级Skill的职责边界是什么？（DeepSeek二面）

> 稳定 ID：`TOOL-009`｜原题号：9

Skill 可分为 **原子能力层、任务技能层、工作流层、领域方案层**，以下层稳定复用、上层表达业务的方式控制复杂度。

| 层级 | 主要职责 | 边界与示例 |
|---|---|---|
| 原子能力层 | 封装单一确定性操作 | 查数据库、读文件；不做任务规划 |
| 任务技能层 | 完成可独立验收的任务 | 生成单测、分析日志；流程较短 |
| 工作流层 | 编排多个Skill和Tool | 代码审查流程；负责状态与恢复 |
| 领域方案层 | 结合业务规则完成端到端目标 | 发布治理；负责策略，不实现连接 |

1. **分层原因**：原子能力变化慢、复用率高，业务流程变化快。分层后可独立版本化、测试和授权，底层替换不迫使上层重写，也能缩小模型候选空间。
2. **依赖方向**：上层依赖同层接口或下层能力，禁止底层反向依赖业务 Skill；跨层通过 Schema 化输入输出传递数据。嵌套深度应设上限，防止循环依赖。
3. **责任划分**：原子层保证可靠与幂等，任务层保证单项质量，工作流层负责顺序、并发、补偿和续跑，领域层负责策略、权限及最终验收。指标需分层归因。

分层不是按 Prompt 长度划分，而是依据 **职责、复用范围、状态复杂度和变更频率**。Registry 需记录层级、依赖、版本与负责人，并在发布时检查循环依赖和兼容性。

**相关知识点：** 原子Skill、Workflow Skill、领域Skill、依赖倒置、Schema契约、DAG、断点续跑、版本治理。

### TOOL-010 · 有没有Skill沉淀机制？Skill是系统自动沉淀，还是只能用户手动构造？（DeepSeek二面）

> 稳定 ID：`TOOL-010`｜原题号：10

Skill 应采用 **系统自动发现候选、专家审核定型、平台持续评估** 的半自动沉淀机制。完全依赖人工会遗漏高频经验，完全自动发布又容易把偶然路径和错误经验固化。

1. **候选发现**：系统从请求日志、成功执行轨迹、人工改选和故障复盘中提取任务目标、工具序列、参数模式及验收结果，对相似轨迹聚类，识别高频且流程稳定的任务。
2. **自动提炼**：对候选轨迹生成 Skill 草案，包括用途、适用边界、输入输出 Schema、步骤、依赖 Tool、异常处理、权限和评价指标；具体资源名应参数化，敏感数据必须去除。
3. **人工评审**：领域专家验证业务规则、安全边界和失败路径，平台执行重复度检测、历史回放、对抗测试与权限审查。自动生成的草案未经审核不能直接进入生产。
4. **发布演进**：通过版本化和灰度流量发布，持续统计成功率、人工接管率、节省时间和风险事件；效果下降时回滚，长期低价值或能力重叠时合并、修订或下线。

| 方式 | 优势 | 主要风险 |
|---|---|---|
| 人工构造 | 边界清晰、质量可控 | 成本高、覆盖慢 |
| 自动沉淀 | 能发现真实高频模式 | 噪声和错误经验固化 |
| 半自动机制 | 兼顾规模与质量 | 需要评测和治理平台 |

准入标准应是 **高频重复、步骤相对稳定、输入输出可结构化、结果可评价、失败可恢复**。一次性探索任务和高度依赖主观判断的任务不宜沉淀。

**相关知识点：** Workflow Mining、轨迹聚类、Skill草案、人工评审、离线回放、灰度发布、生命周期治理。

### TOOL-013 · Tool 与 Skill 有什么区别？

> 稳定 ID：`TOOL-013`｜原题号：13

**Tool 是可直接执行的原子能力，Skill 是完成某类任务的可复用方法**。Tool 解决“系统能做什么”，Skill 解决“如何稳定完成一个目标”，二者属于不同抽象层。

| 维度 | Tool | Skill |
|---|---|---|
| 粒度 | 单一查询、计算或写入 | 完整任务或可复用子任务 |
| 内容 | 接口、Schema、执行逻辑 | 指令、流程、知识、约束和验收 |
| 选择 | Function Calling直接选择 | Skill Router按意图匹配 |

1. **职责边界**：Tool 封装数据库查询、文件读取等确定性操作，定义输入输出、权限、副作用和错误模型，不理解完整业务目标。
2. **任务封装**：Skill 规定场景、步骤、依赖、异常处理和质量标准。例如“读取代码”是 Tool，“完成代码审查”是组合搜索、分析和测试 Tool 的 Skill。
3. **治理方式**：Tool Registry 关注注册、鉴权、限流、健康和版本；Skill Registry 还需治理语义检索、依赖、灰度、效果和生命周期。两者应分别观测。
4. **沉淀原则**：稳定单步能力封装为 Tool；高频、步骤稳定、输入输出可结构化且结果可评价的任务沉淀为 Skill。

Skill 可调用多个 Tool 或受控调用其他 Skill；认证、连接和协议适配应保留在 Tool 或 Executor 层。

**相关知识点：** Tool、Skill、Function Calling、Skill Router、Tool Registry、Workflow、任务成功率、ROI。

### TOOL-018 · Skill Registry 如何设计？

> 稳定 ID：`TOOL-018`｜原题号：18

Skill Registry 应统一管理 **能力目录、可执行制品、依赖权限、版本和效果数据**，覆盖 Skill 从注册、检索、发布到淘汰的完整生命周期。

1. **元数据与制品**：记录名称、描述、能力域、适用与禁用场景、输入输出 Schema、依赖 Tool/Skill、权限、风险、负责人、版本、示例和指标。Prompt、流程、代码与配置打包为签名的不可变制品。
2. **注册发布**：提交后完成命名与语义重复检测、依赖解析、安全扫描、权限审查和离线评测；通过后按租户、用户或流量灰度，指标异常时回滚上一稳定版本。
3. **检索路由**：先按租户、权限、环境、状态和兼容版本过滤，再融合标签、BM25 和向量召回，由 Reranker 根据相关度、Schema 匹配、成功率、延迟和风险精排。
4. **运营治理**：持续统计调用量、路由准确率、任务成功率、人工接管率、成本和节省时间。低使用、低收益、能力重叠或长期失败的 Skill 应合并、修订或下线。

| 模块 | 职责 | 核心能力 |
|---|---|---|
| Catalog | 发现与检索 | 标签、全文、向量索引 |
| Artifact | 制品与依赖 | 签名、版本、依赖图 |
| Governance | 质量与生命周期 | 评测、灰度、回滚、淘汰 |

多租户环境需隔离命名空间、制品、配置、权限和使用数据。执行实例必须固定具体版本，避免热更新导致同一工作流中途行为漂移。

**相关知识点：** Skill Registry、Metadata、不可变制品、依赖图、混合检索、灰度发布、生命周期治理。

### TOOL-102 · 如何设计 Agent 的 Skill 沉淀机制？

> 稳定 ID：`TOOL-102`｜原题号：102

Skill沉淀应将成功经验转化为**可版本化、可评测、可授权、可组合的执行资产**，而不是直接保存模型生成的提示词或完整轨迹。

1. **统一契约**：每个Skill定义名称、目标、适用条件、输入输出Schema、所需工具与权限、前后置条件、成本、超时、失败语义和示例；实现可由提示词、代码、工作流或其组合构成。
2. **候选产生**：从高质量执行轨迹、人工SOP和故障复盘中识别重复模式，抽取可参数化步骤；先脱敏、去除偶然路径和无关上下文，再由领域专家审核，禁止自动发布。
3. **验证发布**：使用固定基准集、对抗样例和权限测试评估成功率、稳定性、成本及副作用；通过后签名、版本化并进入Registry，采用灰度、回滚和弃用周期。
4. **运行选择**：先按任务、领域、权限和环境过滤，再做语义召回与重排序；模型只在授权集合中选择。执行结果和用户修正回流为评测数据，而非立即覆盖Skill。

| 资产 | 特征 | 沉淀方式 |
|---|---|---|
| Prompt模板 | 轻量、概率性强 | 版本库+评测 |
| Workflow | 路径明确、可恢复 | 状态机/DAG |
| Tool | 原子能力、有权限边界 | Registry+契约 |
| Skill | 面向目标的组合能力 | 以上资产编排 |

应持续监控调用量、成功率、人工接管率、版本退化和复用收益，长期低效或与策略冲突的Skill及时下线。

**相关知识点：** Skill Registry、程序性记忆、Schema、SOP、轨迹蒸馏、基准评测、灰度发布、版本治理、能力组合。

### TOOL-129 · Skill与Workflow有什么区别？

> 稳定 ID：`TOOL-129`｜原题号：129

**Skill是可复用的目标级能力描述，Workflow是显式定义步骤、依赖和状态转移的执行结构**。一个Skill可由Workflow实现，也可由提示词、代码或动态规划实现。

1. **关注点**：Skill强调能力、适用条件、权限和质量；Workflow强调步骤、分支、重试、审批与终止。
2. **确定性**：Workflow具有可见节点与边，便于审计、恢复和SLA管理；Skill允许内部策略变化，调用者依赖输入输出契约。
3. **复用边界**：Skill面向Planner，可按语义检索组合；Workflow面向调度运行时，可被Skill或业务服务复用。
4. **治理重点**：Skill管理评测、依赖与版本；Workflow管理状态Schema、幂等、检查点、补偿和并发控制。

| 维度 | Skill | Workflow |
|---|---|---|
| 核心对象 | 可复用能力 | 执行拓扑 |
| 面向使用者 | Planner/Agent | 调度运行时 |
| 路径 | 可动态选择 | 多为显式定义 |
| 主要指标 | 任务成功率、适配度 | 节点成功率、恢复时间 |

受监管、含副作用且需恢复的任务，应以Workflow承载Skill；开放任务可动态规划，但外层仍需预算和终止护栏。

**相关知识点：** 能力契约、状态机、DAG、Planner、检查点、补偿、动态规划、Skill Registry、Workflow Runtime。

### TOOL-130 · Prompt什么时候应该升级成Skill？

> 稳定 ID：`TOOL-130`｜原题号：130

当Prompt从一次性表达变为**反复承担稳定任务目标，并需要明确契约、工具、验证、权限和生命周期治理**时，应升级为Skill；仅因Prompt变长并不足以升级。

1. **升级信号**：同类请求频繁出现；Prompt包含多步骤、条件分支、工具选择或失败处理；不同团队反复复制修改；输出必须满足业务指标；变更需要评测、审批、灰度和回滚。
2. **Skill化内容**：定义目标、适用条件、输入输出Schema、依赖Tool、权限、步骤、成功判据、异常、成本和超时；将示例转化为评测集。
3. **不宜升级**：临时探索、低复用的个性化写作、尚未稳定的需求，以及只需简单模板替换的场景，可继续保留Prompt模板，避免目录膨胀和维护负担。
4. **渐进迁移**：先版本化Prompt并收集轨迹，识别稳定部分；再加入结构化契约、工具和验证器，注册为候选Skill；通过离线评测和小流量灰度后发布，保留旧版本回滚。

| 形态 | 适用阶段 | 治理强度 |
|---|---|---|
| 临时Prompt | 探索和一次性任务 | 低 |
| Prompt模板 | 稳定文本生成 | 版本+基础评测 |
| Skill | 可复用目标级能力 | 契约、权限、全量评测 |
| Workflow Skill | 高风险固定流程 | 状态、审批、恢复 |

判断收益应比较复用次数、成功率提升、人工节省与维护成本；Skill化后若仍高度依赖隐式上下文，说明契约尚未完成。

**相关知识点：** Prompt模板、Skill契约、Schema、评测集、程序性知识、灰度发布、版本管理、隐式上下文、复用收益。
<a id="tool-131"></a>
### TOOL-131 · 如何判断一个任务值得沉淀为Skill？

> 稳定 ID：`TOOL-131`｜原题号：131

值得沉淀的任务应同时具备**重复发生、流程可抽象、质量可验证、复用收益大于治理成本**；频繁出现但每次目标完全不同的任务未必适合Skill化。

1. **需求价值**：统计出现频率、覆盖用户数、人工耗时、业务重要度和错误损失。高频低价值任务与低频高风险任务都可能值得沉淀，但评价依据分别是效率和风险控制。
2. **可抽象性**：不同案例应共享稳定目标、输入输出、关键步骤和成功标准，差异可通过参数、策略或少量分支表达；若主要依赖个人隐性判断且无法评测，应先补充SOP和领域规则。
3. **可执行性**：所需数据和Tool稳定可用，权限边界明确，失败可检测，副作用可控制或补偿；否则Skill只会把不稳定流程包装起来。
4. **经济性验证**：以候选Skill的开发、评测、审批、维护和升级成本，对比节省工时、成功率提升、风险下降和复用规模；设定最小收益阈值及观察周期。

| 信号 | 值得沉淀 | 暂不沉淀 |
|---|---|---|
| 复现性 | 多次出现相似轨迹 | 一次性需求 |
| 稳定性 | 契约与工具较稳定 | 规则频繁变化 |
| 可评测性 | 有明确成功判据 | 结果完全主观 |
| 治理收益 | 可统一权限与审计 | 维护成本超过复用 |

先将候选流程模板化并小范围试运行，达到调用量、成功率和复用率门槛后再进入Registry；长期低使用或无增益的Skill应合并或下线。

**相关知识点：** 复用价值、可抽象性、SOP、成功判据、总拥有成本、候选Skill、ROI、Skill Registry、生命周期治理。
<a id="tool-133"></a>
### TOOL-133 · Skill Registry应该如何设计？

> 稳定 ID：`TOOL-133`｜原题号：133

Skill Registry应是**能力目录、版本仓库、治理控制面和检索索引**的组合，既让Planner找到合适Skill，也保证只有经过评测与授权的版本能够执行。

1. **数据模型**：以不可变Skill ID和语义版本标识实体，保存目标、领域、Schema、适用条件、权限、风险、成本、SLA、依赖、负责人及评测结果；制品使用摘要和签名。
2. **生命周期**：状态至少包含Draft、Review、Canary、Active、Deprecated和Revoked。发布需经过契约、安全、离线评测及审批；弃用提供迁移期限，撤销则立即阻断新调用并告警存量任务。
3. **发现与选择**：同时提供标签、关键词、结构化过滤和向量检索；先按租户、权限、环境、风险和兼容版本过滤，再语义召回与重排序，返回选择理由及版本。
4. **运行集成**：执行时按固定版本解析依赖，校验Tool、模型和策略兼容性；记录调用、成功率、延迟、成本与用户反馈。缓存必须支持版本失效，不能让已撤销Skill继续可见。

| 组件 | 职责 | 关键要求 |
|---|---|---|
| 元数据仓库 | 契约与治理信息 | 强一致、可审计 |
| 制品仓库 | Prompt/代码/流程 | 不可变、签名 |
| 检索索引 | 候选召回 | 权限过滤前置 |
| 发布控制器 | 灰度与回滚 | 指标门禁 |

平台还需提供依赖图、重复检测、过期提醒和使用分析，定期合并低价值Skill。

**相关知识点：** Skill Registry、语义版本、制品签名、生命周期状态机、向量检索、依赖图、灰度发布、撤销、能力血缘。
<a id="tool-134"></a>
### TOOL-134 · Skill元数据通常包含哪些字段？

> 稳定 ID：`TOOL-134`｜原题号：134

Skill元数据应覆盖**可发现、可执行、可治理、可评测和可追溯**五类信息，字段既服务Planner检索，也服务运行时授权与平台治理。

1. **身份与描述**：不可变Skill ID、名称、语义版本、摘要、详细目标、领域、标签、负责人、所属团队、创建与更新时间、生命周期状态，以及适用和禁用场景。
2. **执行契约**：输入输出Schema、前置条件、后置条件、状态Schema、实现类型、入口、超时、最大步骤、成本等级、并发限制、幂等性、失败码、重试与补偿策略。
3. **依赖与权限**：依赖Tool、模型、知识库、子Skill及其版本范围；所需RBAC/ABAC权限、数据等级、网络范围、环境、风险级别、审批规则和凭证要求。
4. **质量与运维**：评测集版本、成功率、延迟、成本、安全测试结果、发布渠道、灰度比例、兼容性、弃用日期、替代Skill、变更记录、制品摘要与签名。

| 元数据类别 | 主要消费者 | 作用 |
|---|---|---|
| 语义描述 | Planner/检索器 | 召回与选型 |
| 契约 | Executor | 校验和执行 |
| 权限风险 | Policy Engine | 授权与审批 |
| 质量指标 | 排序器/运营 | 门禁与优化 |
| 版本血缘 | 发布系统 | 回滚与追溯 |

必填字段应保持精简，扩展字段使用命名空间；任何影响执行语义的元数据变化都要生成新版本，不得静默修改已发布版本。

**相关知识点：** 元数据Schema、语义版本、输入输出契约、依赖范围、RBAC、ABAC、质量门禁、制品签名、能力血缘。
<a id="tool-135"></a>
### TOOL-135 · Agent如何检索最合适的Skill？

> 稳定 ID：`TOOL-135`｜原题号：135

Skill检索应采用**硬条件过滤、混合召回、风险与质量重排序、执行前适配验证**，不能仅按描述做向量相似度匹配。

1. **任务结构化**：从请求提取目标、领域、输入类型、期望输出、环境、时限和风险，并保留用户明确约束；信息不足时先澄清，不应凭相似文本猜测高风险Skill。
2. **硬过滤**：依据租户、身份、权限、生命周期、环境、数据等级、输入Schema、依赖可用性和版本兼容性筛选。已撤销、未授权或前置条件不满足的Skill不得进入模型候选。
3. **混合召回**：结合关键词、标签、领域层级、向量语义和历史成功案例召回；对名称精确匹配、任务语义和输入输出兼容分别打分，避免通用Skill因描述宽泛占据前列。
4. **重排序选择**：综合适配度、成功率、成本、延迟、风险、时效性和用户偏好排序；Top候选差距小或风险较高时要求澄清。执行前验证前置条件，并将选中版本固定到任务。

| 阶段 | 主要方法 | 目标 |
|---|---|---|
| 过滤 | 权限与Schema规则 | 去除不可执行项 |
| 召回 | BM25+向量+标签 | 提高覆盖率 |
| 重排 | 质量、成本、风险模型 | 提高精度 |
| 验证 | 前置条件检查 | 防止误执行 |

评估采用Recall@K、Top-1准确率、误选率、无合适Skill时的拒选率和端到端成功率；用户纠正用于离线优化，不应直接污染线上排序。

**相关知识点：** 混合检索、BM25、向量召回、Metadata Filter、Reranker、Recall@K、拒选机制、版本固定、权限前置过滤。
<a id="tool-136"></a>
### TOOL-136 · 如何避免Skill数量越来越多导致维护困难？

> 稳定 ID：`TOOL-136`｜原题号：136

控制Skill规模的关键是**准入有门槛、能力有分类、重复可检测、生命周期可退出**，目标不是限制数量本身，而是降低语义重叠和治理成本。

1. **严格准入**：新增前提交目标、复用证据、契约、负责人、评测集和维护预算；检索Registry检查同义或可扩展Skill。优先给既有Skill增加参数、策略或组合层，避免为单个案例复制。
2. **分层组织**：建立领域分类、稳定标签和能力层级，区分原子Tool、基础Skill与业务组合Skill；公共内核与领域配置分离，减少相似实现。每个Skill限定清晰适用与禁用边界。
3. **度量治理**：持续统计调用量、独立用户、成功率、复用率、成本、人工接管和重叠命中。低使用、低增益或长期无负责人项进入观察名单，先合并或弃用，再按兼容周期下线。
4. **依赖与版本控制**：维护Skill—Tool—模型—知识库依赖图，自动提示过期依赖和破坏性变更；限制分叉版本长期并存，设定主版本支持窗口与升级负责人。

| 问题 | 治理动作 | 判断依据 |
|---|---|---|
| 语义重复 | 合并、增加路由条件 | 候选同时命中率 |
| 参数轻微差异 | 模板化/配置化 | 核心流程一致 |
| 长期不用 | 弃用与归档 | 调用量、业务价值 |
| 质量持续偏低 | 修复或撤销 | 回归指标与事故 |

建立定期目录评审和自动健康报告，并保留弃用别名到替代Skill的映射，避免清理过程破坏存量调用。

**相关知识点：** 能力分类、重复检测、Skill合并、生命周期、依赖图、弃用策略、支持窗口、健康度评分、目录治理。
<a id="tool-137"></a>
### TOOL-137 · 如何设计Skill的版本管理机制？

> 稳定 ID：`TOOL-137`｜原题号：137

Skill版本管理应采用**不可变制品、语义版本、依赖锁定和可复现实验**，确保任一历史任务都能说明并重建当时使用的能力。

1. **版本规则**：以MAJOR.MINOR.PATCH表达兼容性。输入输出、权限或执行语义发生破坏性变化升主版本；向后兼容能力新增升次版本；不改变契约的修复升补丁版本。模型或知识更新若影响行为，也应产生新版本。
2. **不可变发布**：已发布版本禁止覆盖，Prompt、代码、Workflow、配置及评测集打包为制品，保存摘要、签名、构建信息和变更记录；别名只指向具体版本，解析结果写入任务。
3. **依赖管理**：声明Tool、子Skill、模型、知识库和策略的兼容范围；发布时解析并生成Lockfile，执行时校验依赖未撤销。依赖升级通过回归测试，不能静默漂移。
4. **兼容与迁移**：为状态Schema和长期任务提供迁移器；同时维护支持窗口、弃用日期、替代版本和回滚条件。主版本并存时按租户或流量路由，不改变运行中任务。

| 变化 | 推荐版本 | 示例 |
|---|---|---|
| 文案修正、行为不变 | PATCH | 错别字、日志修复 |
| 兼容新增能力 | MINOR | 新增可选参数 |
| 破坏契约或权限 | MAJOR | 删除字段、扩大写权限 |

发布流水线需执行契约、安全、质量和成本回归，并记录版本采用率、失败率及迁移进度，及时撤销存在安全问题的制品。

**相关知识点：** Semantic Versioning、不可变制品、Lockfile、依赖解析、制品签名、状态迁移、支持窗口、版本别名、可复现执行。
<a id="tool-138"></a>
### TOOL-138 · Skill如何支持灰度发布和回滚？

> 稳定 ID：`TOOL-138`｜原题号：138

Skill灰度应做到**版本不可变、路由稳定、指标可比较、触发条件可自动回滚**；回滚必须同时考虑新旧状态与外部副作用，而非只切换Prompt。

1. **发布准备**：新版本通过契约、安全、离线质量和成本回归，制品签名并锁定依赖；定义成功率、严重错误、延迟、成本和人工接管等门禁，以及明确观察窗口和停止线。
2. **流量路由**：先内部与影子测试，再按租户、用户哈希或任务类型分配1%至更高比例，保证同一会话固定版本。高风险场景先限制为只读或需要审批，避免随机分流破坏体验。
3. **效果判断**：将新旧版本在相同任务分布上比较，分层观察质量、安全与成本；严重安全事件立即停止，不等待统计显著。模型、Tool和知识版本需一并记录，避免错误归因。
4. **回滚机制**：Registry别名原子切回稳定版本，阻止新任务进入；运行中任务通常继续固定版本，若存在安全缺陷则安全暂停并迁移。已经产生的写入依据幂等记录和补偿流程处理。

| 阶段 | 流量 | 主要目的 |
|---|---|---|
| Shadow | 0%真实执行 | 对比决策、无副作用 |
| Canary | 小比例 | 发现线上兼容问题 |
| Progressive | 逐步扩大 | 验证稳定性 |
| Rollback | 切回旧版 | 控制损失 |

灰度控制面还应支持紧急撤销、状态Schema迁移、版本采用率追踪和回滚演练，确保操作在分钟级完成。

**相关知识点：** Canary、Shadow Traffic、稳定哈希、指标门禁、原子路由、紧急撤销、状态迁移、补偿、回滚演练。
<a id="tool-142"></a>
### TOOL-142 · 如何设计Skill之间的依赖关系？

> 稳定 ID：`TOOL-142`｜原题号：142

Skill依赖应设计成**显式、有向、版本受约束且可在发布前解析的能力图**，避免运行时临时寻找下游Skill造成行为漂移和循环。

1. **声明契约**：每项依赖记录Skill ID、兼容版本范围、必需或可选、调用目的、输入输出映射、权限继承规则、超时和失败策略；发布时解析为Lockfile，任务固定具体版本。
2. **限制拓扑**：依赖图默认要求无环，并限制最大深度与扇出；Registry在发布时检测直接和间接循环。确需迭代的业务过程应在同一Workflow中显式建环，而非通过Skill互调形成隐式递归。
3. **隔离演进**：下游遵循语义版本，破坏性变更升主版本；上游通过契约测试和集成回归后升级。依赖撤销、弃用或安全事件需要沿反向依赖图通知、阻断或切换替代版本。
4. **运行治理**：父Skill不自动把全部用户上下文和权限传给子Skill，运行时按子能力重新授权并最小化数据；Trace记录父子关系，预算、步骤和取消信号向下传播。

| 依赖方式 | 优点 | 风险 |
|---|---|---|
| 固定版本 | 可复现 | 升级较慢 |
| 兼容范围+锁定 | 灵活且可复现 | 需解析与回归 |
| 运行时最新版 | 更新快 | 行为不可预测 |
| 可选依赖 | 支持降级 | 分支测试增加 |

平台应展示依赖健康度、关键路径、单点依赖和升级影响范围，并定期减少过深嵌套与重复中间层。

**相关知识点：** 依赖图、DAG、Semantic Versioning、Lockfile、循环检测、反向依赖、契约测试、权限再校验、预算传播。
<a id="tool-143"></a>
### TOOL-143 · Skill是否支持嵌套调用（Skill调用Skill）？

> 稳定 ID：`TOOL-143`｜原题号：143

Skill可以嵌套调用，但应视为**受治理的能力组合**：依赖显式、深度有限、权限重新校验、状态与预算可传播，不能形成自由递归。

1. **适用价值**：组合Skill可复用成熟的领域能力，例如“处理差旅行程”调用“查询航班”“校验政策”和“生成报销草稿”，减少重复流程并统一质量。
2. **契约边界**：父Skill只通过子Skill公开的输入输出Schema交互，不依赖其内部Prompt和步骤；Registry记录版本范围、数据映射和失败语义，发布时解析并锁定实际版本。
3. **运行控制**：限制最大嵌套深度、总步骤、扇出、Token、时间和费用；通过依赖图与调用栈检测直接、间接循环。相互迭代应改为同一状态机中的显式循环。
4. **安全可靠性**：子Skill按当前用户与资源重新授权，父Skill不能放大权限；Trace、取消、Deadline和预算向下传播。子Skill失败时依据契约选择重试、替代、部分结果、补偿或人工接管。

| 方式 | 适用场景 | 主要风险 |
|---|---|---|
| 顺序嵌套 | 明确依赖 | 延迟累积 |
| 并行嵌套 | 独立子目标 | 成本与汇总冲突 |
| 动态选择 | 开放任务 | 不可预测性 |
| 递归调用 | 极少数分治任务 | 循环和预算失控 |

嵌套层级过深会降低可解释性和故障定位效率；当组合关系稳定且关键时，应提升为显式Workflow并单独评测端到端效果。

**相关知识点：** Skill Composition、依赖图、调用栈、循环检测、预算传播、权限再授权、Trace Context、显式Workflow、契约隔离。

### TOOL-146 · 如何设计企业级Skill市场（Skill Marketplace）？

> 稳定 ID：`TOOL-146`｜原题号：146

企业级Skill市场应是**受治理的能力供应链与分发平台**，不仅提供搜索和安装，还必须覆盖身份、评审、权限、版本、质量、计量及退出机制。

1. **发布准入**：发布者需实名与归属团队，提交契约、负责人、许可证、数据分类、依赖清单、权限、风险、评测集和支持周期；平台执行制品签名、漏洞扫描、恶意行为检测及人工评审。
2. **目录发现**：按领域、目标、输入输出、风险、成本和环境分类，支持关键词、语义与标签检索；先按租户权限和兼容性过滤，再展示质量、采用率、最近更新、依赖与已知限制。
3. **安装运行**：安装不是授予全部权限。管理员批准可用范围，运行时仍按用户身份最小授权；版本固定、依赖锁定，支持沙箱试用、灰度、配额、计费或成本分摊，并记录完整审计。
4. **生命周期**：监控成功率、事故、维护活跃度和用户反馈；安全缺陷可紧急撤销，弃用提供替代项与迁移窗口。无负责人、长期未更新或低质量Skill进入清退。

| 角色 | 主要职责 | 关键控制 |
|---|---|---|
| 发布者 | 开发与维护 | 身份、SLA |
| 平台方 | 评审与分发 | 签名、扫描、门禁 |
| 管理员 | 租户准入 | 权限与配额 |
| 使用者 | 选择与反馈 | 最小授权、审计 |

评分应区分客观质量指标和主观评价，防止下载量主导排序；内部与第三方Skill采用不同信任等级和隔离策略。

**相关知识点：** Skill Marketplace、软件供应链、制品签名、SBOM、权限审批、依赖锁定、信誉体系、紧急撤销、成本分摊。

### TOOL-147 · 如何构建可持续演进的Skill沉淀体系？

> 稳定 ID：`TOOL-147`｜原题号：147

可持续的Skill体系需要形成**发现—设计—评测—发布—观测—迭代—退出**闭环，并把所有权、质量门禁和收益度量纳入日常工程流程。

1. **统一标准**：定义Skill契约、元数据、版本、权限、风险、评测和审计规范，提供模板、SDK与示例；将Tool、Prompt、Workflow和知识依赖显式化，避免个人脚本成为隐性关键资产。
2. **双向来源**：专家从SOP主动建设，平台从脱敏轨迹挖掘高频模式；自动化只生成候选，需经负责人确认、权限评审和回归测试。
3. **发布运营**：Registry管理不可变制品、依赖、灰度、回滚和撤销；线上持续采集成功率、成本、人工接管、风险事件和复用率，异常自动收紧流量或回滚。
4. **组织机制**：每个Skill有明确Owner、SLA和维护预算；设领域评审委员会处理重复、跨域共享及高风险能力。贡献者获得可量化收益反馈，使用团队承担合理成本。
5. **生命周期**：定期检查知识过期、依赖漏洞、模型变化和业务规则变更；低使用、低增益、重复或无人维护的Skill合并、弃用或下线，并提供迁移路径。

| 阶段 | 核心产物 | 质量门禁 |
|---|---|---|
| 设计 | 契约、风险说明 | 可复用性评审 |
| 验证 | 评测集、测试报告 | 质量与安全阈值 |
| 发布 | 签名制品、版本 | 灰度指标 |
| 运营 | 真实指标、反馈 | 持续复评 |

最终以业务增益和总成本衡量，而非Skill数量。

**相关知识点：** 能力生命周期、Skill Registry、Owner机制、质量门禁、轨迹挖掘、灰度发布、持续评测、总拥有成本、目录清退。

### TOOL-150 · Skill如何进行版本管理？

> 稳定 ID：`TOOL-150`｜原题号：150

Skill版本管理应保证**已发布版本不可变、运行任务可复现、升级影响可评估、异常可快速回退**，并将行为依赖纳入同一版本视图。

1. **版本对象**：包含Prompt、Schema、Workflow、配置、依赖Tool、模型、知识库、评测集及权限。制品生成摘要并签名，禁止覆盖同一版本。
2. **编号规则**：使用语义版本。破坏输入输出或权限语义时升MAJOR；兼容新增参数、路径或能力升MINOR；行为不变的缺陷修复升PATCH。任何可能显著改变结果的模型或知识更新都需形成可追踪版本。
3. **发布流程**：分支变更经代码审查、契约测试、安全扫描、离线质量与成本回归，再进入Canary；注册表记录作者、时间、变更说明、评测报告、依赖锁和审批。
4. **运行与迁移**：任务启动时把别名解析为具体版本并固定，长任务同时固定配置快照；状态Schema变化提供迁移器。旧版本设置支持窗口、弃用日期和替代版本，安全漏洞可立即撤销。

| 标识 | 用途 | 是否可变 |
|---|---|---|
| Skill ID | 标识能力实体 | 否 |
| 具体版本 | 指向制品 | 否 |
| stable/canary别名 | 流量路由 | 是 |
| Lockfile | 固定依赖解析 | 随新版本生成 |

监控各版本采用率、成功率、成本和故障分布，回滚通过原子切换别名完成；已产生副作用的任务仍需按补偿流程处理。

**历史别名：** `TOOL-161`。

**相关知识点：** Semantic Versioning、不可变制品、内容摘要、版本别名、Lockfile、状态迁移、Canary、支持窗口、紧急撤销。

### TOOL-151 · Skill如何实现热更新？

> 稳定 ID：`TOOL-151`｜原题号：151

Skill热更新应采用**发布新不可变版本、原子切换路由、任务级版本固定**，而不是在运行节点上覆盖文件；这样既不中断服务，又保持执行可复现。

1. **构建发布**：新版本打包Prompt、Workflow、Schema、配置和依赖锁，完成签名、评测与安全门禁后上传Registry。运行节点监听版本事件或短轮询拉取，先下载、验签、预加载并健康检查。
2. **原子生效**：通过stable或canary别名、配置中心或路由表一次性切换新任务流量；旧版本仍在内存中服务已开始的任务。使用租户或会话稳定哈希，避免同一会话中途改变行为。
3. **兼容处理**：新旧版本需在支持窗口内兼容公共输入输出；状态Schema变化提供迁移器。若依赖Tool或模型不兼容，发布控制器拒绝激活，不把错误留到调用时暴露。
4. **监控回退**：比较成功率、严重错误、延迟、成本和人工接管，超过阈值立即把别名切回旧版；节点保留最近稳定制品。安全撤销可强制暂停受影响任务并吊销缓存。

| 更新方式 | 对新任务 | 对运行中任务 |
|---|---|---|
| 原子别名切换 | 使用新版本 | 保持旧版本 |
| 进程内覆盖 | 行为不可预测 | 可能前后不一致 |
| 滚动重启 | 逐节点更新 | 需排空与恢复 |

缓存键必须包含具体版本，审计记录解析结果和配置快照；热更新只缩短发布中断，不减少回归、灰度和回滚要求。

**相关知识点：** 热更新、不可变制品、原子路由、版本固定、稳定哈希、预加载、状态迁移、缓存失效、紧急撤销。

### TOOL-160 · Skill 应该如何定义元数据（Metadata）？

> 稳定 ID：`TOOL-160`｜原题号：160

Skill Metadata应设计为**机器可校验的统一Schema**，既描述语义，又承载运行和治理约束；关键决策字段必须结构化。

1. **基本标识**：ID、名称、版本、摘要、领域、标签、负责人、状态与更新时间；ID永久稳定，版本指向不可变制品。
2. **能力契约**：目标、适用与禁用条件、输入输出Schema、前后置条件、正反例，供Router召回与执行前验证。
3. **运行声明**：实现入口、依赖及版本、超时、最大步骤、并发、Token与成本预算、幂等、重试和降级策略。
4. **安全质量**：权限范围、数据等级、风险、审批、网络和审计策略，以及评测集、质量、延迟、已知限制、弃用日期与制品摘要。

| 字段组 | 是否参与自动决策 | 典型消费者 |
|---|---|---|
| 语义与边界 | 是 | Router/Planner |
| 输入输出契约 | 是 | Validator/Executor |
| 权限与风险 | 是 | Policy Engine |
| 质量与成本 | 是 | Reranker/运营 |
| 负责人和说明 | 部分 | 治理与人工 |

Schema本身需版本化，定义必填、默认值、枚举和扩展命名空间；影响执行或授权的变更必须发布新Skill版本并重测，禁止静默覆盖。

**相关知识点：** Metadata Schema、机器可读契约、正反例、依赖锁定、风险元数据、制品摘要、Schema版本化。

### TOOL-162 · Skill 如何实现动态加载和热更新？

> 稳定 ID：`TOOL-162`｜原题号：162

动态加载应通过**注册中心发现、可信制品拉取、隔离初始化和原子路由切换**实现；热更新只接管新任务，运行中任务保持版本一致。

1. **发现机制**：运行时订阅Registry事件或按版本游标轮询，获取新增、灰度、稳定、弃用和撤销信息；事件只携带元数据与制品地址，避免直接执行远端内容。
2. **安全加载**：从可信仓库下载固定摘要制品，校验签名、来源、Schema和依赖；在隔离区解包，预编译Prompt或Workflow，执行健康检查与最小测试，失败时不进入候选池。
3. **并存与切换**：以Skill ID和具体版本作为缓存键，多版本并存；路由表通过原子快照更新，并使用会话稳定哈希。旧版本待任务排空后卸载，引用计数防止仍在使用时回收。
4. **故障处理**：新版本指标越界时原子切回旧路由；撤销事件立即禁止新调用，并对运行任务按风险决定完成、暂停或终止。缓存和节点离线时采用最近已验证版本，未知版本默认拒绝。

| 机制 | 解决问题 | 关键约束 |
|---|---|---|
| 事件订阅 | 快速发现版本 | 去重、有序或可重放 |
| 制品验签 | 防供应链篡改 | 固定摘要 |
| 原子快照 | 无中间状态切换 | 任务版本固定 |
| 引用计数 | 安全卸载旧版 | 排空运行任务 |

审计记录加载、验签、激活、路由、回滚和卸载事件，并用并发切换、节点断网及撤销演练验证一致性。

**相关知识点：** 动态加载、Registry事件、制品验签、固定摘要、原子快照、稳定哈希、引用计数、缓存降级、版本撤销。

### TOOL-163 · Skill 注册中心应该如何设计？

> 稳定 ID：`TOOL-163`｜原题号：163

Skill注册中心应采用**控制面与制品面分离、强治理元数据与高性能检索索引分离**的架构，兼顾发布一致性、运行发现和安全撤销。

1. **核心存储**：关系型元数据仓保存ID、版本、契约、权限、状态、负责人和审批记录，保证事务与审计；对象仓保存签名制品；搜索与向量索引提供发现，但不作为权限和版本的权威数据源。
2. **服务接口**：提供注册、评审、发布、查询、版本解析、依赖分析、弃用、撤销和事件订阅API。写路径校验Metadata Schema、语义版本、所有权及签名；读路径必须携带租户和主体上下文。
3. **状态与一致性**：以状态机管理Draft、Review、Canary、Active、Deprecated、Revoked；发布先写权威库，再通过Outbox更新索引与事件流。索引延迟时宁可少召回，也不能显示未授权或已撤销版本。
4. **运行保障**：多可用区部署，读缓存按租户和具体版本隔离；撤销走高优先级推送并使缓存失效。所有变更追加审计，支持按版本重建索引和回放事件。

| 数据面 | 内容 | 一致性要求 |
|---|---|---|
| 元数据仓 | 契约、权限、状态 | 强一致 |
| 制品仓 | Prompt/代码/流程 | 不可变、验签 |
| 检索索引 | 文本、向量、标签 | 最终一致 |
| 事件流 | 发布与撤销通知 | 可重放、幂等 |

还需提供依赖图、健康度、重复检测和过期提醒，并设置备份恢复、灾难演练与细粒度管理员权限。

**相关知识点：** 控制面、制品仓、权威数据源、Outbox、生命周期状态机、缓存失效、可重放事件、依赖图、多租户隔离。

### TOOL-164 · Skill Marketplace 应该具备哪些能力？

> 稳定 ID：`TOOL-164`｜原题号：164

Skill Marketplace应具备**可信发布、精准发现、安全试用、受控安装、运行治理和完整退出**能力，本质是企业能力资产的供应链平台。

1. **供给侧**：支持开发模板、Metadata校验、版本与依赖管理、制品签名、许可证和SBOM、安全扫描、评测报告、人工评审、灰度及发布者身份认证。
2. **消费侧**：提供分类、关键词、语义、标签和场景导航，展示输入输出、权限、风险、成本、质量、兼容性、负责人、支持周期和已知限制；推荐结果先做租户与权限过滤。
3. **安装试用**：支持沙箱演示、样例任务、权限影响预览、管理员审批、租户级配置和配额。安装只代表可发现，真实调用仍按用户与资源重新鉴权。
4. **运营治理**：统计采用率、独立用户、成功率、成本、事故与评分；支持计量、成本分摊、SLA、问题反馈、维护通知、自动更新策略和版本锁定。
5. **生命周期**：提供弃用提示、替代推荐、迁移向导、紧急撤销、依赖影响分析和审计。第三方Skill使用更严格的隔离与信任等级。

| 能力域 | 关键功能 | 主要目标 |
|---|---|---|
| 发布 | 评审、签名、评测 | 可信供给 |
| 发现 | 检索、推荐、比较 | 正确选择 |
| 使用 | 试用、审批、配置 | 安全落地 |
| 运营 | 指标、计量、SLA | 持续价值 |
| 退出 | 弃用、撤销、迁移 | 控制风险 |

市场排序不能只依赖下载量，应综合任务适配度、质量、风险、时效和维护状态，并防止评分操纵。

**相关知识点：** Skill Marketplace、SBOM、制品签名、权限预览、沙箱试用、成本分摊、信誉体系、依赖影响、紧急撤销。

### TOOL-165 · 用户请求进来后如何匹配对应 Skill？

> 稳定 ID：`TOOL-165`｜原题号：165

匹配流程应为**请求理解—安全过滤—多路召回—质量重排—置信门控—执行验证**，并允许“无合适Skill”作为正常结果。

1. **理解请求**：结合当前会话提取目标、实体、领域、输入类型、输出要求、时限和风险；明确区分用户原始事实与模型推断。关键参数缺失时先生成澄清问题。
2. **安全过滤**：按用户、租户、角色、环境、数据等级、Skill状态、输入Schema、依赖和预算过滤；已撤销、未授权或前置条件不满足的能力不得进入候选，即使语义高度匹配。
3. **多路召回**：使用名称与别名精确匹配、BM25关键词、领域标签、向量语义和历史案例分别召回，合并去重形成Top-K，提升对同义表达和长尾请求的覆盖。
4. **重排决策**：综合目标覆盖、专用度、成功率、成本、延迟、风险和用户偏好排序；Top-1超过阈值且领先明显才自动选择，否则澄清、交给Planner拆解或拒选。
5. **执行反馈**：固定具体Skill版本，验证输入和前置条件；记录候选、得分、选择理由及最终效果，用人工改选和任务结果更新离线模型。

| 阶段 | 失败风险 | 保护措施 |
|---|---|---|
| 理解 | 意图抽取错误 | 澄清与结构化字段 |
| 召回 | 漏掉正确Skill | 多路召回 |
| 排序 | 相似Skill误选 | 专用度与质量特征 |
| 门控 | 低置信强行执行 | 阈值、拒选 |

评估同时观察Recall@K、Top-1准确率、澄清率、严重误选率和端到端成功率。

**相关知识点：** 意图理解、权限过滤、BM25、向量召回、Reranker、置信门控、拒选、版本固定、反馈闭环。

### TOOL-170 · Workflow Skill 如何实现任务编排？

> 稳定 ID：`TOOL-170`｜原题号：170

Workflow Skill应以**显式状态模型和节点契约**实现编排：确定性运行时控制依赖、并发、重试与恢复，LLM只在需要语义判断的节点参与。

1. **建模**：任务定义为状态机或DAG，节点声明输入输出、成功判据、超时、幂等、副作用和补偿；边声明顺序、条件、并行与终止。共享状态使用Schema。
2. **执行**：调度器运行就绪节点，独立只读节点并行，写节点按资源冲突排序；每步先鉴权与预算检查，结果验证后写入状态。
3. **可靠性**：节点完成后建立检查点，使用幂等键防重复；瞬时故障有限重试，业务失败走条件分支，部分完成按Saga补偿。任务暂停、取消和Deadline向所有子节点传播。
4. **智能节点**：LLM用于分类、信息抽取、候选生成或受限规划，其输出须Schema校验和业务验证；高风险Tool节点必须审批，禁止模型动态添加未注册节点。
5. **观测**：Trace记录节点、版本、Tool、耗时、成本、重试和审批；最终节点验证任务目标。

| 编排元素 | 主要职责 | 关键保障 |
|---|---|---|
| Node | 原子步骤 | 幂等、超时 |
| Edge | 依赖与条件 | 可验证表达式 |
| State | 传递事实与进度 | 版本化、持久化 |
| Checkpoint | 恢复位置 | 原子写入 |

运行中实例固定Workflow版本，状态Schema提供迁移策略。

**相关知识点：** 状态机、DAG、节点契约、结构化状态、检查点、幂等、Saga、Validator、Deadline、Workflow版本。

### TOOL-175 · 如何设计一个企业级 Skill 沉淀体系？

> 稳定 ID：`TOOL-175`｜原题号：175

企业级Skill体系应把**资产标准、生产流水线、运行平台和组织治理**连成闭环，使经验可复用且责任清晰。

1. **标准层**：统一定义、Metadata、Schema、版本、依赖、风险、评测和审计；区分Prompt、Tool、基础Skill和Workflow Skill。
2. **生产层**：从SOP建设或轨迹发现候选；提供模板、沙箱、评测、契约测试、安全扫描、签名、评审、灰度和回滚。
3. **平台层**：Registry保存元数据与制品，Router负责过滤与选择，Runtime负责状态、审批、恢复和追踪，Marketplace负责分发。
4. **治理层**：每项设Owner、SLA、风险和维护周期；委员会处理重复、共享与高风险准入，低价值或无人维护项退出。
5. **度量层**：持续衡量复用率、端到端成功、人工节省、一次成功成本、安全事件和ROI，以业务增益而非资产数量作为目标。

| 层次 | 核心产物 | 责任主体 |
|---|---|---|
| 标准 | 契约与规范 | 平台架构组 |
| 生产 | 签名制品与评测 | Skill团队 |
| 运行 | 路由、状态、审计 | 平台团队 |
| 治理 | 准入、复评、退出 | 领域委员会 |

从高价值场景和最小规范开始，形成闭环后再扩展Marketplace和自动发现。

**相关知识点：** Skill生命周期、Registry、Router、Runtime、Marketplace、Owner机制、质量门禁、制品签名、ROI、目录治理。

### TOOL-178 · Skill 之间如何管理依赖关系？

> 稳定 ID：`TOOL-178`｜原题号：178

Skill依赖管理类似软件包管理，但还需考虑**行为质量、权限传播、状态兼容和运行预算**；依赖必须声明、锁定和验证。

1. **声明方式**：父Skill记录子Skill ID、版本范围、用途、输入输出映射、失败策略、权限与数据范围；禁止运行时按名称模糊解析。
2. **解析与锁定**：发布控制器构建依赖DAG，检查循环、最大深度、版本冲突和已撤销项，解析出具体版本写入Lockfile。运行实例固定该锁文件，避免子Skill热更新导致行为变化。
3. **兼容验证**：下游变更除契约测试外，还要对上游评测集做行为回归；主版本由上游显式采用，状态变化提供迁移器。
4. **权限与资源**：调用子Skill时按当前用户重新授权，只传完成任务所需数据；Deadline、取消、Token、费用和最大深度向下传播，父子调用统一Trace。
5. **生命周期联动**：Registry维护正向和反向依赖图，下游弃用、漏洞或SLA退化时通知Owner并分析影响；关键单点依赖准备替代或降级路径。

| 依赖风险 | 检测时机 | 处理 |
|---|---|---|
| 循环 | 发布前 | 拒绝发布 |
| 版本冲突 | 解析时 | 升级或拆分 |
| 权限放大 | 每次调用 | 重新授权 |
| 下游撤销 | 实时事件 | 阻断/切换替代 |

依赖图纳入发布评审与故障演练，减少过深嵌套，防止失败扩散。

**相关知识点：** 依赖DAG、Lockfile、Semantic Versioning、契约测试、行为回归、反向依赖、预算传播、权限再授权、单点依赖。

### TOOL-180 · 如何建设组织级 Skill 资产库？

> 稳定 ID：`TOOL-180`｜原题号：180

1. **资产模型**：统一ID、Metadata、版本、契约、依赖、权限、风险、评测和SLA；建立领域树与标签，使能力可检索比较。

3. **共享分级**：按个人、团队、事业部、全组织和敏感等级发布；扩大范围前检查通用性、数据隔离和支持能力。共享不等于授权。

5. **生命周期**：定期复核知识时效、漏洞、负责人、使用价值与合规要求；过期、低价值或无人维护项先弃用、提供替代映射，再归档或撤销。

| 层级 | 责任 | 关键产物 |
|---|---|---|
| 平台层 | 标准与基础设施 | Registry、运行时 |
| 领域层 | 语义与质量 | Skill、评测集 |
| 治理层 | 准入与风险 | 策略、审计 |
| 运营层 | 推广与价值 | 指标、成本分摊 |

从少数跨团队高价值能力试点，验证闭环后再扩展，避免成为无人维护的目录。

**相关知识点：** 组织级资产、领域治理、分级共享、Owner机制、Metadata标准、能力目录、成本分摊、支持窗口、资产清退。

### TOOL-183 · Bug Fix Skill 如何设计？

> 稳定 ID：`TOOL-183`｜原题号：183

Bug Fix Skill应遵循**先复现、再定位、最小修复、回归验证**的证据链，禁止在未理解失败机制时大范围改写或仅修改测试绕过问题。

1. **问题规范化**：收集期望与实际行为、复现步骤、环境、日志、堆栈、版本和最近变更；去除密钥与个人信息，区分缺陷、配置错误、环境故障和需求歧义。
2. **建立复现**：在隔离分支与沙箱运行现有测试，必要时创建最小失败测试；记录失败信号、频率和前置数据。无法复现时先增加观测或提出假设，不声称已修复。
3. **根因定位**：结合调用图、日志、二分、静态分析、数据流和历史提交缩小范围；形成多个假设，用可证伪实验排序，明确根因与表面症状。
4. **最小变更**：只修改解决根因所需代码，同步边界测试、类型和文档；保护未提交修改，不随意升级依赖或重构无关模块。高风险文件与命令需审批。
5. **验证交付**：确认失败测试转绿，运行相关回归、静态检查和必要集成测试；审查Diff、性能、安全与兼容影响，输出根因、修复、证据、剩余风险和回滚方式。

| 阶段 | 核心产物 | 失败判据 |
|---|---|---|
| 复现 | 稳定失败样例 | 无法观察原问题 |
| 定位 | 可证伪根因 | 只有猜测 |
| 修复 | 最小补丁 | 无关改动过多 |
| 验证 | 回归证据 | 仅单测通过 |

评测可使用真实缺陷仓库，衡量修复成功率、补丁最小性、回归率、测试作弊率与平均工具调用成本。

**历史别名：** `TOOL-214`。

**相关知识点：** 最小复现、根因分析、假设驱动、回归测试、最小补丁、Git Bisect、数据流分析、测试作弊、回滚。

### TOOL-184 · 自动开发 Agent 的 Skill 体系如何规划？

> 稳定 ID：`TOOL-184`｜原题号：184

自动开发Agent的Skill体系应按**生命周期分层、风险逐级授权、通用与技术栈能力解耦**，先建立可靠闭环。

1. **基础工具层**：文件与符号检索、编辑、Git、构建、测试和终端；统一Schema、沙箱、超时、权限和审计，不嵌入业务决策。
2. **工程基础Skill**：仓库理解、需求澄清、影响分析、规划、局部修改、测试生成、静态检查和Diff审查，适用于多数仓库。
3. **专业Skill**：Bug修复、重构、依赖升级、迁移、性能和安全修复，以及语言、框架专用能力；按项目动态加载。
4. **交付Workflow**：将规划、实现、验证、Review、审批和发布组织为可恢复状态机；生产发布、密钥、基础设施和破坏性迁移设置强审批，Agent不得自行扩大范围。
5. **治理评测**：Registry管理版本与Owner；用真实任务衡量解决率、补丁质量、回归、成本和接管，淘汰低价值Skill。

| 层次 | 复用范围 | 主要风险 |
|---|---|---|
| Tool | 全平台 | 执行权限 |
| 基础Skill | 跨语言 | 上下文与规划错误 |
| 专业Skill | 特定技术栈 | 兼容性 |
| 交付Workflow | 业务流程 | 生产副作用 |

先开放只读理解，再开放沙箱编辑和测试，最后开放受审批的发布。

**相关知识点：** 软件生命周期、能力分层、Coding Tool、专业Skill、交付Workflow、沙箱、风险授权、Skill Registry、真实任务评测。

### TOOL-185 · 企业级 Coding Agent 如何实现 Skill 复用与共享？

> 稳定 ID：`TOOL-185`｜原题号：185

企业级Coding Skill复用应采用**通用内核、技术栈插件、仓库配置和组织Registry**四层设计，同时隔离代码、权限与密钥。

1. **分层资产**：检索、编辑、测试、Review做成通用Skill；语言、框架和构建系统做插件；规范、目录及命令放仓库配置。
2. **统一契约**：声明输入输出、条件、工具、权限、风险和评测；使用语义版本与不可变制品。仓库差异通过参数和策略注入。
3. **集中分发**：Registry提供检索、评审、签名、灰度、弃用和撤销；按个人、团队、组织管理可见性，项目固定版本或跟随稳定通道。
4. **安全隔离**：Skill可共享，项目源码和执行凭证不得随资产上传；运行时按用户与仓库重新授权，在沙箱执行，限制目录、网络和命令。敏感仓库只能使用批准的模型与Skill。
5. **质量治理**：公共评测验证基础能力，项目评测验证本地兼容；按版本追踪成功率、回归与成本，由Owner维护。

| 共享层 | 内容 | 变化频率 |
|---|---|---|
| 组织通用 | Review、测试、Git流程 | 低 |
| 技术栈 | Java/React等规范 | 中 |
| 仓库级 | 命令、架构、约定 | 较高 |
| 会话级 | 当前任务与临时约束 | 最高 |

优先共享方法与契约，不共享未经审查的历史轨迹；重复Skill及时合并。

**相关知识点：** 组织Registry、技术栈插件、仓库配置、作用域、语义版本、制品签名、沙箱、项目评测、Owner机制。

### TOOL-186 · 什么样的任务适合沉淀成 Skill？

> 稳定 ID：`TOOL-186`｜原题号：186

任务适合沉淀成Skill的核心判断是：**稳定经验能否跨案例复用，并通过契约和评测获得可证明的增益**。频率、风险和维护成本需要共同衡量。

1. **重复性**：同类意图在多个用户或周期出现，成功轨迹具有共同步骤；差异主要是参数、数据或少量规则，而非每次都要重新定义目标。
2. **稳定性**：输入输出、前置条件、工具依赖和完成标准能够明确描述，领域知识和外部接口不会短期频繁失效；失败可检测，必要时可降级或人工接管。
3. **价值性**：高频任务可节省工时，低频高风险任务可固化权限、审批、验证和审计；预计收益需覆盖开发、评测、运行、升级和清退成本。
4. **可治理性**：存在可靠数据与评测集，有Owner维护版本、依赖和SLA，敏感数据能够隔离，副作用可以幂等、回滚或补偿。

| 判断信号 | 适合沉淀 | 不适合沉淀 |
|---|---|---|
| 目标 | 稳定可复述 | 持续变化 |
| 轨迹 | 多次相似成功 | 偶然成功 |
| 结果 | 可验证 | 纯主观且无标准 |
| 依赖 | 可控、可版本化 | 不稳定或无权限 |
| 责任 | 有Owner与预算 | 无人维护 |

先将候选任务模板化并进行受控试运行，用复现率、任务成功增量、人工节省和风险下降验收；未达门槛时保留为案例或Prompt模板。

**相关知识点：** Skill准入、可复用性、轨迹稳定度、契约化、成功判据、风险治理、Owner、TCO、候选试运行。

### TOOL-188 · Skill 与 Prompt Template 的区别是什么？

> 稳定 ID：`TOOL-188`｜原题号：188

**Prompt Template是可参数化的模型输入文本，Skill是可发现、可执行、可治理的目标级能力**。Prompt可以是Skill的一部分，但不能代表完整Skill。

1. **范围**：Prompt规定角色、任务、上下文槽位和格式；Skill还包含适用条件、Schema、Tool依赖、权限、流程、验证、错误与版本。
2. **执行**：Prompt通常对应一次模型调用；Skill可运行多轮推理、多个Tool、分支、审批和检查点，并返回任务结果。
3. **治理**：Prompt关注文本版本、Token、模型兼容和输出；Skill还管理端到端成功、依赖、风险、SLA、灰度、回滚和Owner。
4. **复用**：Prompt按模板引用；Skill由Router按语义、权限和环境发现，并通过契约被Planner组合。依赖隐式上下文的模板难复用。

| 维度 | Prompt Template | Skill |
|---|---|---|
| 核心对象 | 一次模型输入 | 一类任务能力 |
| 组成 | 文本+变量 | Prompt/规则/Tool/Workflow |
| 状态 | 通常无状态 | 可持久化和恢复 |
| 风险控制 | 主要靠调用方 | 声明并编排控制 |
| 评测 | 输出级 | 端到端任务级 |

简单无副作用的生成任务用Prompt即可；需要Tool、验证、权限、恢复或跨团队复用时升级为Skill。

**相关知识点：** Prompt Template、Skill Contract、Schema、Tool依赖、Workflow、端到端评测、灰度发布、程序性知识、隐式上下文。

### TOOL-189 · Skill 与 Workflow 的关系是什么？

> 稳定 ID：`TOOL-189`｜原题号：189

Skill与Workflow是**能力契约与实现方式**的关系：Skill声明目标，Workflow规定步骤。两者可一对多，也不必绑定。

1. **Skill对外**：包含目标、契约、条件、权限、风险和版本，供Router发现、Planner组合；内部实现可替换。
2. **Workflow对内**：定义节点、依赖、分支、状态、审批、重试、补偿和终止；同一模板可被多个Skill参数化复用。
3. **组合形态**：简单Skill可只含Prompt或函数；多步骤、有副作用、需恢复的Skill适合状态机或DAG；Workflow也可不暴露为Skill。
4. **版本治理**：Skill锁定Workflow和Tool版本；破坏状态或行为的变化升主版本并迁移，运行实例固定版本。

| 关系 | 示例 | 设计重点 |
|---|---|---|
| Skill无Workflow | 文本分类 | 契约与评测 |
| Skill由Workflow实现 | 退款处理 | 状态、审批、补偿 |
| 多Skill共享Workflow | 多语言报告 | 参数与策略隔离 |
| Workflow非Skill | 内部定时ETL | 调度与运维 |

Skill看目标完成与收益，Workflow看节点可靠性、恢复时间和状态一致性。

**相关知识点：** 能力契约、实现封装、状态机、DAG、Workflow Runtime、版本锁定、状态迁移、端到端评测、节点可靠性。

### TOOL-190 · Skill 是否支持嵌套调用？

> 稳定 ID：`TOOL-190`｜原题号：190

Skill可以嵌套，但须限制为**显式依赖的有界组合**，不能任意递归。其价值是复用，代价是链路、权限和故障复杂度上升。

1. **依赖声明**：父Skill在发布时声明子Skill ID、兼容版本、输入输出映射、必需性和失败策略；Registry解析依赖DAG并锁定版本，禁止运行时按名称选择“最新版”。
2. **循环控制**：发布阶段检测直接与间接环，运行时维护调用栈和指纹，限制最大深度、扇出、步骤、Token、时间和费用。需要循环的过程应在单一Workflow内显式表达终止条件。
3. **权限隔离**：父Skill只传必要数据，子Skill按当前用户、租户和资源重新鉴权；父级权限不能自动继承或放大。高风险子能力仍需独立审批。
4. **状态与故障**：父子之间使用结构化契约，Trace、Deadline、取消和预算向下传播；子Skill失败按约定返回可重试、可降级、部分结果或不可恢复状态，由父Skill决定续作、补偿或人工接管。

| 嵌套类型 | 是否推荐 | 原因 |
|---|---|---|
| 共享基础能力 | 推荐 | 提高复用 |
| 独立子目标并行 | 条件推荐 | 需控制成本与汇聚 |
| 深层多级包装 | 不推荐 | 难观测和维护 |
| 相互递归 | 禁止 | 容易循环失控 |

当嵌套关系长期稳定且含关键副作用时，应将组合提升为显式Workflow，单独做端到端评测与恢复演练。

**相关知识点：** Skill Composition、依赖DAG、调用栈、循环检测、预算传播、权限再授权、Trace Context、显式Workflow、端到端评测。

### TOOL-193 · 如何从执行日志中抽取 Skill？

> 稳定 ID：`TOOL-193`｜原题号：193

从日志抽取Skill应遵循**轨迹筛选—模式归纳—契约生成—离线验证—人工发布**，日志是经验样本，不是可以直接执行的可信指令。

1. **构造高质量轨迹**：关联任务目标、步骤、Tool、参数形态、结果、用户修正、耗时与成本；脱敏后排除失败、越权、循环、人工暗中补救和偶然成功轨迹，并保留来源与版本。
2. **聚类与归一化**：按目标语义和输出类型聚类，对Tool序列做频繁模式挖掘；把订单号、日期等实例值抽取为参数，合并同义动作，识别稳定前置条件、分支、终止和失败处理。
3. **生成候选契约**：输出目标、适用与禁用条件、输入输出Schema、步骤、依赖、权限、风险、成功判据、预算和示例；不将日志中的用户数据、密钥或具体资源硬编码。
4. **验证泛化**：在独立历史样本、反例和边界案例上重放，与无Skill基线比较成功率、成本和安全；加入Tool失败、权限拒绝和提示词注入测试，防止只复现训练轨迹。
5. **审核发布**：领域专家确认业务正确性，安全人员审核权限与数据流，经签名、版本化和灰度进入Registry。线上反馈只回流为候选数据。

| 日志内容 | 抽取结果 | 处理原则 |
|---|---|---|
| 实例参数 | Schema变量 | 泛化、脱敏 |
| 重复步骤 | Workflow节点 | 去除偶然动作 |
| 人工修正 | 规则/评测样例 | 专家确认 |
| 失败轨迹 | 反例和异常路径 | 不作为成功模板 |

**相关知识点：** 轨迹蒸馏、序列挖掘、参数抽取、Schema归纳、数据脱敏、反例、历史重放、人工审核、Skill Registry。

### TOOL-194 · 自动生成 Skill 的质量如何评估？

> 稳定 ID：`TOOL-194`｜原题号：194

自动生成Skill必须从**契约正确、任务有效、泛化稳定、安全可控和维护可行**五方面评估，且只能作为候选，通过门禁后才能发布。

1. **契约检查**：验证目标、适用与禁用条件、Schema、前后置条件、依赖版本、错误语义和成功判据是否完整一致；静态检测未声明变量、循环依赖、不可达节点和权限放大。
2. **离线效果**：在来源轨迹之外的独立任务集上测试端到端成功、输出正确、Tool参数一次通过、步骤数、延迟和成本；与无Skill、人工SOP及既有Skill基线比较，防止只记忆训练样例。
3. **稳健安全**：加入信息缺失、歧义、长尾、Tool超时、重复消息、权限拒绝、提示词注入和恶意数据，检查拒答、降级、幂等、补偿和人工接管；高风险错误设置一票否决。
4. **可维护性**：评审流程复杂度、依赖深度、文档、可观测字段、Owner和升级成本；与现有能力做重复检测，避免生成大量近义Skill。
5. **线上验证**：签名、固定版本后进行影子和小流量灰度，监控严重错误、成功率、人工纠正、成本与漂移，越界自动回滚。

| 维度 | 代表指标 | 门禁 |
|---|---|---|
| 正确性 | 成功率、参数准确率 | 不低于基线 |
| 泛化 | 独立集与长尾表现 | 无显著退化 |
| 安全 | 越权、误执行 | 高风险错误为零 |
| 效率 | 一次成功成本 | 在预算内 |
| 维护 | 复杂度、重复度 | 有Owner、可演进 |

**相关知识点：** 契约验证、独立测试集、基线比较、对抗评测、风险门禁、影子测试、灰度、自动回滚、重复检测。
<a id="tool-196"></a>
### TOOL-196 · Memory 和 Skill 的区别是什么？

> 稳定 ID：`TOOL-196`｜原题号：196

**Memory保存“过去发生了什么和已知什么”，Skill定义“遇到一类目标应如何做”**。Memory提供上下文和事实，Skill提供可复用的程序性方法。

1. **内容形态**：Memory含任务状态、事件、偏好和事实，按用户或租户隔离；Skill含目标、条件、步骤、Tool、验证、权限和失败处理，跨任务复用。
2. **获取方式**：Memory按主体、时间、相似度和重要度检索，仍需判断时效与可信度；Skill由Router按目标、权限和环境选择，固定版本执行。
3. **生命周期**：Memory管理写入、冲突、衰减、TTL和删除；Skill管理评测、版本、灰度、回滚、弃用与Owner。对话不能直接升级为Skill。
4. **安全边界**：Memory更容易包含个人和敏感信息，必须最小化存储与权限过滤；Skill应尽量不内嵌实例数据，只引用授权的数据源。两者访问均需审计。

| 维度 | Memory | Skill |
|---|---|---|
| 核心问题 | 记住什么 | 如何完成任务 |
| 典型作用域 | 用户/会话/租户 | 团队/组织/领域 |
| 主要检索 | 时间与相关性 | 能力匹配 |
| 主要治理 | 隐私、时效、冲突 | 质量、版本、依赖 |
| 输出 | 上下文事实 | 执行结果 |

Episodic Memory可作为Skill数据源，但需跨案例归纳、脱敏、验证和人工审核。

**相关知识点：** 工作记忆、情景记忆、语义记忆、程序性知识、Skill Router、时间衰减、隐私删除、经验抽象、版本治理。

### TOOL-200 · Skill 如何做版本管理？

> 稳定 ID：`TOOL-200`｜原题号：200

Skill版本管理应把**契约版本、行为制品、运行依赖和发布渠道**统一管理，确保修改有边界、任务可复现、线上可比较。

1. **完整制品**：版本包含Prompt、代码、Workflow、Schema、策略、Tool与模型依赖、知识快照和评测集；生成不可变摘要、签名和变更说明。禁止覆盖已发布版本或只记录文件名。
2. **变更分类**：输入输出、权限、状态或业务语义不兼容时升主版本；兼容新增参数与分支升次版本；行为不变的修复升补丁版本。模型、Embedding或知识更新若影响结果，也作为可追踪变更。
3. **分支与渠道**：开发版本经评审、契约、安全、质量和成本回归，依次进入候选、灰度和稳定渠道；stable/canary是可变指针，具体版本不可变，任务启动后固定解析结果。
4. **依赖与状态**：发布时解析依赖并生成Lockfile；运行中任务保存Skill、配置和依赖版本。状态Schema变化提供迁移器，旧主版本设置支持期、弃用日期和替代项。
5. **审计运营**：记录作者、审批、发布时间、采用率、指标和回滚事件；严重漏洞可撤销版本并沿反向依赖图通知调用方。

| 版本对象 | 是否可变 | 用途 |
|---|---|---|
| Skill ID | 否 | 稳定身份 |
| 具体版本 | 否 | 可复现执行 |
| 渠道别名 | 是 | 灰度与切流 |
| Lockfile | 随版本生成 | 固定依赖 |

**相关知识点：** 语义版本、不可变制品、版本渠道、Lockfile、状态迁移、支持周期、反向依赖、行为版本、制品签名。
<a id="tool-201"></a>
### TOOL-201 · Skill 如何回滚？

> 稳定 ID：`TOOL-201`｜原题号：201

Skill回滚应区分**能力版本回切、运行状态恢复和外部副作用补偿**。路由切回旧版本只解决后续调用，不能自动撤销已经完成的业务动作。

1. **回滚准备**：发布前保留最近稳定的不可变版本、依赖锁、配置快照和状态Schema，定义指标阈值、回滚负责人、兼容范围及补偿流程；定期演练，不把回滚当临时脚本。
2. **触发与切流**：严重安全错误立即人工或自动熔断，普通质量、延迟和成本退化在观察窗口内达到阈值后触发；Registry原子将stable别名切回旧版并停止新任务进入问题版本。
3. **运行中任务**：原则上继续固定原版本，避免中途语义变化；若版本存在安全缺陷，则暂停任务，在检查点验证状态后迁移或转人工。迁移器必须可重试并保留原状态。
4. **副作用处置**：依据幂等键和业务操作ID查询真实状态；已写入数据使用Undo、Saga补偿或人工核对，结果未知时禁止盲目重放。回滚Skill本身不等于数据库回滚。
5. **后续治理**：清理缓存、撤销制品、通知反向依赖方，记录影响范围、恢复时间和根因；修复版本重新走完整门禁。

| 对象 | 回滚方式 | 关键限制 |
|---|---|---|
| 新任务路由 | 别名切回 | 只影响新任务 |
| 运行状态 | 检查点迁移 | 需Schema兼容 |
| 外部写入 | 补偿/Undo | 可能再次失败 |
| 安全版本 | 撤销与阻断 | 优先于可用性 |

**相关知识点：** 原子切流、检查点、状态迁移、Saga补偿、Undo、幂等键、紧急撤销、反向依赖、回滚演练。
<a id="tool-202"></a>
### TOOL-202 · Skill 如何做灰度发布？

> 稳定 ID：`TOOL-202`｜原题号：202

Skill灰度发布应实现**版本隔离、稳定分流、同分布比较、指标门禁和自动回退**，逐步验证真实流量下的质量、安全、延迟与成本。

1. **发布前基线**：新制品完成契约、安全、离线质量和成本回归，固定模型、Tool、知识与配置版本；定义严重错误、成功率、人工接管、P95延迟和一次成功成本阈值。
2. **分阶段流量**：先离线重放与Shadow，仅比较决策且不产生副作用；再对内部用户或低风险只读任务Canary，按用户、租户或会话稳定哈希从1%逐级扩大，避免同一会话版本跳变。
3. **风险分层**：高风险Skill先限制目标资源、额度和审批，不能与普通流量同速扩大；新旧版本同时保留，运行任务固定具体版本。样本需按任务难度和领域分层，防止分布偏差。
4. **门禁判断**：比较新旧版本的任务完成、安全事件、拒答、重试、成本和满意度；严重安全错误立即停流，普通指标需满足样本量与观察窗口。不能只看总体平均。
5. **扩容或回退**：通过门禁后逐步增加流量直至stable；越界原子切回旧别名，暂停问题版本并保全Trace，修复后重新灰度。

| 阶段 | 副作用 | 主要目标 |
|---|---|---|
| 离线重放 | 无 | 基础质量 |
| Shadow | 无真实写入 | 线上分布比较 |
| Canary | 受限 | 发现兼容问题 |
| Progressive | 逐步开放 | 验证稳定性 |

**相关知识点：** Shadow、Canary、稳定哈希、指标门禁、风险分层、观察窗口、原子回退、版本固定、一次成功成本。
<a id="tool-203"></a>
### TOOL-203 · Skill 如何做权限隔离？

> 稳定 ID：`TOOL-203`｜原题号：203

Skill权限隔离应遵循**能力可见性、调用授权、数据访问和执行身份四层分离**；发现某个Skill不等于获得其底层资源权限。

1. **目录隔离**：Registry按租户、团队、环境和敏感等级控制可见性；Router在召回前过滤未授权项，避免描述泄露。
2. **声明最小权限**：Metadata列出Scope、资源、数据等级、网络和副作用；禁止全能账号。安装只授予候选资格，不分配长期凭证。
3. **运行时授权**：每次调用按用户、任务、资源和风险做RBAC/ABAC判断，签发短期、限范围令牌；父Skill调用子Skill和Tool时重新鉴权。
4. **数据与执行隔离**：状态、Memory、索引、日志和缓存按租户分区；沙箱使用独立身份与网络策略，密钥按需注入。高风险动作参数级审批。
5. **撤销审计**：权限变化即时使令牌和缓存失效，拒绝与成功调用均记录主体、策略版本、参数摘要和资源；最终业务服务仍执行资源级校验。

| 层次 | 控制对象 | 典型机制 |
|---|---|---|
| 可见性 | Skill元数据 | 租户/团队ACL |
| 调用权 | 当前任务 | RBAC/ABAC |
| 资源权 | 具体数据对象 | 服务端鉴权 |
| 执行域 | 文件、网络、密钥 | 沙箱+短期令牌 |

通过跨租户、嵌套、缓存污染和撤销测试，验证默认拒绝且无间接绕过。

**相关知识点：** 最小权限、RBAC、ABAC、Capability Token、多租户隔离、参数级授权、沙箱、权限撤销、资源级鉴权。

### TOOL-204 · Skill 如何做依赖管理？

> 稳定 ID：`TOOL-204`｜原题号：204

Skill依赖管理应实现**声明、解析、锁定、验证、观测和退出**闭环，依赖对象不仅包括子Skill，也包括Tool、模型、知识、运行时和策略。

1. **依赖清单**：Metadata记录依赖ID、类型、兼容版本范围、必需或可选、用途、输入输出映射、权限与失败策略；外部服务还需声明SLA、区域和数据边界。
2. **发布解析**：构建依赖图，检测循环、版本冲突、最大深度、许可证和已撤销项；解析具体版本写入Lockfile和制品清单，任务启动后固定，禁止隐式跟随latest。
3. **兼容门禁**：Schema契约测试验证接口，行为回归验证质量，安全测试验证权限没有扩大；下游主版本升级由上游显式采用，知识或模型变化同样执行关键评测。
4. **运行时治理**：启动前检查依赖健康和权限，调用时传播Trace、Deadline、取消和预算；可选依赖失败走降级，关键依赖失败快速终止或转人工，防止无限重试。
5. **生命周期联动**：Registry维护反向依赖图，下游弃用、漏洞或SLA下降时计算影响、通知Owner并触发升级；关键单点依赖准备替代实现。

| 依赖类型 | 主要兼容性 | 典型风险 |
|---|---|---|
| 子Skill/Tool | Schema与行为 | 破坏契约 |
| 模型 | 输出与工具能力 | 行为漂移 |
| 知识库 | 数据版本与权限 | 过期、越权 |
| 运行时 | API与状态Schema | 无法恢复 |

**相关知识点：** 依赖图、Lockfile、制品清单、Semantic Versioning、契约测试、行为回归、反向依赖、单点依赖、预算传播。

### TOOL-205 · 企业 Agent 的 Skill Store 应该如何设计？

> 稳定 ID：`TOOL-205`｜原题号：205

企业Skill Store应是**权威元数据仓、不可变制品仓、检索索引和治理服务**的组合，既支持运行时低延迟发现，也保证权限与版本一致。

1. **数据分层**：关系库保存Skill ID、版本、契约、状态、权限、风险、Owner和审批，作为权威源；对象仓保存签名后的Prompt、代码、Workflow与附件；关键词和向量索引只服务检索，可从权威数据重建。
2. **核心接口**：提供注册、评审、发布、版本解析、搜索、依赖查询、下载、弃用、撤销和事件订阅；所有写操作校验Metadata Schema、所有权、签名及审计，所有读请求携带租户与身份。
3. **一致性与缓存**：发布使用事务与Outbox同步事件，运行端缓存按租户和具体版本隔离；任务解析版本后固定。撤销走高优先级通知并强制失效缓存，网络分区时未知版本默认拒绝。
4. **安全供应链**：制品固定摘要、签名和SBOM，下载使用短期授权；敏感Skill加密并限制区域，第三方内容先沙箱扫描。Store不保存运行时长期密钥。
5. **运营能力**：维护依赖与血缘图、使用率、成功率、成本、过期和漏洞状态，支持灰度通道、回滚、备份恢复和目录清退。

| 组件 | 职责 | 一致性 |
|---|---|---|
| 元数据仓 | 契约与治理 | 强一致 |
| 制品仓 | 能力内容 | 不可变 |
| 检索索引 | 关键词与向量召回 | 最终一致 |
| 事件总线 | 发布与撤销传播 | 可重放 |

**相关知识点：** Skill Store、权威数据源、对象存储、向量索引、Outbox、制品签名、SBOM、缓存失效、多租户、可重放事件。

### TOOL-206 · 多 Agent 如何共享 Skill？

> 稳定 ID：`TOOL-206`｜原题号：206

多Agent应通过**统一Registry和稳定契约共享Skill，以各自上下文与身份独立执行**，不能共享可变状态和长期凭证。

1. **统一发现**：Registry发布ID、版本、Schema、依赖、风险和适用Agent；各Agent按权限、环境和兼容性过滤，任务固定版本。
2. **标准调用**：Skill使用结构化契约，隐藏内部实现；不同Agent通过同一Runtime调用。上下文只传必要字段，大对象用受控引用。
3. **身份与状态隔离**：按用户和Agent重新授权，子Agent不继承全部权限；每个任务独立状态、预算、Trace和幂等域，敏感Memory不自动传播。
4. **版本与兼容**：Agent声明兼容版本；灰度按Agent类型分层，依赖锁保证可复现。撤销事件同步所有缓存。
5. **共享反馈**：指标回传平台并按Agent、模型和任务切片，分别评估质量；轨迹脱敏后才能改进。

| 共享对象 | 是否共享 | 原因 |
|---|---|---|
| Skill定义与制品 | 是 | 复用能力 |
| 评测与质量指标 | 是，需切片 | 统一治理 |
| 运行状态 | 否 | 防串扰 |
| 用户Memory | 默认否 | 隐私与权限 |
| 长期凭证 | 否 | 最小权限 |

**相关知识点：** 多Agent、统一Registry、能力契约、身份传递、状态隔离、版本锁定、Trace、幂等域、反馈切片。
