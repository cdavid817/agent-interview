### 工具调用过程中各类异常怎么捕获、兜底处理（Agent初级）

工具异常治理应遵循 **分类识别、分层捕获、有限重试、明确降级、全程追踪**，统一重试会放大故障或重复执行写操作。

| 异常类型 | 典型表现 | 处理方式 |
|---|---|---|
| 参数异常 | 缺字段、类型或范围错误 | Schema拦截并让模型修正 |
| 鉴权异常 | 凭据失效、权限不足 | 刷新凭据或终止调用 |
| 瞬时异常 | 超时、断连、HTTP 5xx | 指数退避和有限重试 |
| 限流异常 | HTTP 429、配额耗尽 | 遵循Retry-After或切换服务 |
| 业务异常 | 库存不足、状态冲突 | 返回原因并重新规划 |
| 系统异常 | 服务崩溃、资源耗尽 | 熔断、隔离、告警、降级 |

1. **调用前**：检查参数、权限、预算、工具健康度和风险等级，从源头减少无效调用。
2. **调用中**：分别设置连接超时、读取超时和任务总截止时间；在 Executor 统一捕获底层异常，转换为 `code、message、retryable、fallback、trace_id`，避免模型解析不同供应商的错误格式。
3. **重试与兜底**：仅对网络抖动等可恢复错误重试，并采用指数退避加随机抖动。查询操作可安全重试；写操作只有具备幂等键、事务或补偿机制时才允许重试。失败后依次选择备用工具、缓存数据、只读模式、简化结果或人工接管。
4. **调用后**：校验业务结果，记录耗时、错误码、重试次数和状态。兜底不能伪造成功；无法完成时，应明确失败范围和恢复建议。连续失败触发熔断，防止工具拖垮 Agent。

**相关知识点：** 异常分类、超时控制、指数退避、幂等性、熔断、降级、补偿事务、人工接管、链路追踪。

### 工具调用返回200，但业务逻辑错误怎么办？（千问二面）

HTTP 200 只表示协议层正常响应，**不代表业务执行成功**。执行器必须校验传输状态、业务状态和结果语义。

| 层级 | 成功依据 | 错误示例 |
|---|---|---|
| 传输层 | HTTP状态、连接完整 | 超时、5xx、响应截断 |
| 业务层 | `success`、业务码、状态字段 | 余额不足、库存冲突 |
| 语义层 | 数据满足任务目标和约束 | 空结果、字段缺失、状态不一致 |

1. **统一返回契约**：将第三方响应适配为 `success、code、message、data、retryable、trace_id`。只有业务码进入成功集合，且关键字段通过 Schema 校验，Executor 才能将调用标记为成功。
2. **语义校验**：针对金额、数量、资源状态设置不变量和后置条件。例如转账后核对状态与金额，创建工单后校验编号，避免接口成功但目标未达成。
3. **分类处置**：参数或业务规则错误应反馈 Planner 修正方案，不应盲目重试；瞬时依赖异常可有限重试；状态未知的写操作先用幂等键查询执行结果，再决定重试或补偿。
4. **监控与治理**：分别统计 HTTP 成功率、业务成功率和任务完成率，记录原始业务码、工具版本及校验失败原因。高风险写操作需事务、补偿或人工复核，禁止模型依据自然语言消息自行判断成功。

这类问题的关键是将 **技术成功、业务成功、任务成功** 分开建模；只有三层检查均通过，才能向 Agent 返回可继续推理的成功结果。

**相关知识点：** 业务状态码、统一响应模型、Schema校验、后置条件、幂等查询、补偿事务、任务完成率。

### Tool 调用失败如何恢复？

Tool 调用失败后应先区分错误类型，再选择 **修正参数、有限重试、备用工具、补偿恢复或人工接管**；对所有错误统一重试会放大故障和写入副作用。

1. **错误分类**：参数、权限和业务规则错误不可原样重试，应返回结构化原因供 Planner 修正；网络抖动、限流及部分 5xx 属于瞬时错误，可在任务截止时间内重试；写入状态未知时必须先查询执行结果。
2. **重试控制**：采用指数退避、随机抖动、最大次数和总时间预算。读操作通常可以重试；写操作只有具备幂等键、唯一约束、事务或服务端去重记录时才允许自动重试。
3. **降级回退**：主工具不可用时，根据能力、数据新鲜度和风险选择备用工具、缓存、只读模式或简化结果。切换工具后仍需重新校验参数 Schema 和权限，不能假设接口完全兼容。
4. **状态恢复**：多步工作流持久化节点状态和输出，从最近成功检查点续跑；已产生部分副作用时执行补偿事务。无法保证一致性时冻结后续步骤并转人工，同时保留完整现场。

| 失败类型 | 是否重试 | 恢复方式 |
|---|---|---|
| 参数或权限错误 | 否 | 修正参数或重新授权 |
| 超时、限流、5xx | 有限重试 | 退避、备用工具 |
| 写入状态未知 | 先查询 | 幂等确认或补偿 |

连续失败应触发熔断，半开状态只放少量探测请求。恢复效果通过最终任务成功率、重复副作用率、恢复时长和人工接管率衡量。

**相关知识点：** 错误分类、指数退避、幂等性、熔断、备用工具、补偿事务、检查点、人工接管。

### 工具调用失败后如何进行重试和回退？

重试和回退必须由 **错误分类、幂等保障、截止时间与降级策略** 共同决定；只有短暂且可恢复的错误可以自动重试，业务错误应修正计划。

1. **判定可重试性**：连接重置、短时超时、429 和部分 5xx 可重试；参数错误、权限不足、资源不存在和业务规则冲突不可原样重试。统一错误对象应包含 `code、retryable、retry_after、trace_id`。
2. **设计重试策略**：采用指数退避加随机抖动，设置单次超时、最大次数和任务总截止时间，并遵循服务端 `Retry-After`。重试应计入调用、Token 和费用预算，避免故障期间请求风暴。
3. **保护写操作**：读操作通常可安全重试；写操作必须使用稳定幂等键、唯一约束或事务。若调用超时但服务端状态未知，应先查询原操作结果，确认未执行后才能重试。
4. **执行回退策略**：按优先级切换等价备用工具、可信缓存、只读模式、简化结果或人工接管。备用工具需重新做 Schema、权限、数据新鲜度和风险校验，不能把降级伪装为完整成功。

| 错误类型 | 重试策略 | 回退方式 |
|---|---|---|
| 网络抖动、5xx | 有限退避重试 | 备用端点 |
| 429、配额不足 | 等待指定时间 | 备用供应商或降级 |
| 参数、权限错误 | 不重试 | 修正参数或授权 |
| 写入状态未知 | 先查询 | 幂等确认或补偿 |

连续失败触发熔断，半开阶段仅允许探测流量。监控重试成功率、额外延迟、重复副作用率、降级成功率和人工接管率。

**相关知识点：** 可重试错误、指数退避、随机抖动、Retry-After、幂等键、熔断、降级、补偿。

### 如何设计工具调用的超时机制？

工具超时应采用 **分层超时、绝对截止时间、可传播取消和资源回收**，而不是只在最外层设置一个固定等待时间。

1. **分层设置**：分别定义连接超时、读取超时、单次调用超时和任务总截止时间。单工具超时必须小于剩余任务预算，并为重试、降级和最终回答预留时间。
2. **动态预算**：根据工具历史 P95/P99、操作类型、用户 SLA 和下游依赖动态配置。查询与写入使用不同阈值；长任务应返回任务标识并转为异步轮询或回调，不能长期占用同步连接。
3. **截止时间传播**：入口生成绝对 `deadline`，Planner、Executor、Adapter 和下游服务继续传递；每层以剩余时间为准，避免各层重新计时导致总耗时叠加。用户取消时同步传播取消信号。
4. **超时处置**：读操作可在预算内有限重试；写操作超时后状态可能未知，必须用幂等键查询结果，禁止直接重放。进程类工具先发送优雅终止信号，宽限期后结束进程组，并回收连接、锁、临时文件和凭据。

| 超时层级 | 控制对象 | 主要目的 |
|---|---|---|
| 连接超时 | 建连、DNS、握手 | 快速识别不可达 |
| 调用超时 | 单次工具执行 | 限制局部阻塞 |
| 总截止时间 | 完整Agent任务 | 控制端到端SLA |

超时应返回 `timeout_stage、elapsed、retryable、trace_id`，并统计超时率、取消成功率、僵尸任务数和资源回收失败率。熔断器可隔离持续慢调用。

**相关知识点：** 连接超时、Deadline、取消传播、异步任务、幂等查询、资源回收、熔断、SLA。

### 工具执行如何支持并发和 DAG 调度？

工具执行应把任务表示为 **带依赖、状态和资源约束的 DAG**，调度器只并发运行依赖已满足且互不冲突的节点，保证效率的同时维持确定性。

1. **图模型**：节点声明工具版本、输入输出 Schema、前置条件、超时、重试、幂等性、资源需求和失败策略；边表示数据依赖或控制依赖。提交前必须检测环路、缺失依赖和不兼容类型。
2. **就绪调度**：入度为零或所有上游成功的节点进入就绪队列，调度器根据优先级、截止时间、租户配额和资源容量分配执行槽。无依赖只读节点可并发，汇聚节点等待所需结果齐备。
3. **冲突控制**：共享数据库记录、文件或部署环境的写操作需使用资源锁、租约或乐观版本控制；同一业务操作携带幂等键。并发失败不能通过无条件重放解决。
4. **状态与恢复**：持久化节点的等待、运行、成功、失败和跳过状态以及输出引用。瞬时错误仅重试当前节点，业务失败触发补偿或重规划；进程重启后从检查点恢复，不重复已成功副作用。

| 调度方式 | 适用关系 | 关键控制 |
|---|---|---|
| 串行 | 强数据依赖、共享写资源 | 顺序、事务 |
| 并行 | 相互独立的只读任务 | 并发上限、配额 |
| DAG汇聚 | 多源数据加工 | 依赖计数、部分失败策略 |

调度器还需设置最大并发、关键路径 Deadline 和费用预算。核心指标包括 DAG 完成率、关键路径延迟、队列等待、并发利用率和重复副作用率。

**相关知识点：** DAG、拓扑排序、就绪队列、资源锁、乐观锁、幂等性、检查点、补偿事务。

### 如何避免 Agent 无限循环调用工具？

避免工具循环需要同时设置 **语义终止条件、进展检测和硬资源预算**；不能只依赖模型自行判断任务是否已经完成。

1. **显式任务状态**：Planner 为每个子目标定义完成条件、预期工具输出和后置校验。工具结果满足条件后将节点标记为完成，后续规划不得无理由重新打开该节点。
2. **循环指纹检测**：记录最近若干次的工具名、规范化参数、结果摘要和计划状态。相同调用重复、A→B→A 周期出现，或结果长期无新增信息时，判定为确定性循环或停滞。
3. **硬性预算约束**：限制最大步骤、单工具调用次数、连续失败次数、总时间、Token 和费用。预算接近阈值时禁止扩展新分支，只允许完成当前路径、降级或生成部分结果。
4. **受控退出机制**：首次检测停滞时允许一次重新规划，并要求说明新计划的信息增益；仍无进展则终止执行，返回已完成步骤、失败原因和所需人工输入。写操作依靠幂等键防止循环产生重复副作用。

| 检测信号 | 问题类型 | 处理方式 |
|---|---|---|
| 工具、参数、结果均重复 | 确定性循环 | 立即终止 |
| 工具变化但状态不变 | 计划停滞 | 限次重规划 |
| 步骤或费用达到上限 | 预算越界 | 降级或转人工 |

生产监控应关注平均工具步数、重复调用率、无效调用率、预算终止率和循环误判率，并通过轨迹回放调整窗口及阈值。

**相关知识点：** 终止条件、循环指纹、信息增益、步骤预算、动态重规划、幂等键、轨迹回放。

### 如何实现 Tool Call 的幂等性？

Tool Call 幂等性的目标是：同一业务意图被重复提交时，**只产生一次有效副作用，并稳定返回同一业务结果**。客户端去重只能减少请求，最终保证必须由执行副作用的服务实现。

1. **生成稳定幂等键**：由租户、业务操作、目标资源和任务请求标识组成，同一次调用的重试必须复用原键；不能使用每次重试都会变化的随机值。服务端同时保存参数摘要，防止不同请求误用同一键。
2. **保证原子执行**：幂等记录与业务写入放在同一数据库事务中，或使用唯一约束、条件更新和 Outbox。先写业务后写幂等表会产生成功但无记录的窗口，先写幂等表也可能留下虚假成功状态。
3. **管理执行状态**：首次请求创建 `PROCESSING` 状态，完成后保存 `SUCCESS/FAILED` 与标准结果；重复请求在处理中返回查询标识或等待，在完成后直接返回原结果。状态未知时不得再次执行。
4. **控制生命周期**：根据最大重试和消息重投窗口设置 TTL；资金、订单等长期一致性操作需更长保留期。超时或故障后先通过幂等键查询状态，再决定重试、补偿或人工处理。

| 实现方式 | 适用场景 | 关键约束 |
|---|---|---|
| 唯一索引 | 创建订单等写入 | 冲突后返回原记录 |
| 幂等记录表 | 跨服务调用 | 与业务事务一致 |
| 版本号/CAS | 状态更新 | 检测并发修改 |

删除、扣款和消息发送等工具应声明是否幂等；不具备服务端幂等保障的写工具，Executor 不得自动重试。

**验证指标：** 工具选择准确率、调用成功率、参数错误率、P95 延迟和失败恢复率。

**相关知识点：** 幂等键、唯一约束、幂等表、CAS、Outbox、事务、状态机、重复提交。
<a id="tool-030"></a>
### 如何设计统一的 Tool Executor？

统一 Tool Executor 是 **模型决策与真实副作用之间的确定性执行层**，通过统一契约、策略管道和适配器治理工具。

1. **统一契约**：输入包含工具标识、版本、参数、身份、截止时间、幂等键和 `trace_id`；输出统一为 `success、code、data、message、retryable`。
2. **调用前管道**：完成 Registry 解析、Schema 与业务校验、认证、Policy 授权、风险审批、预算和限流检查；失败即终止。
3. **适配执行层**：HTTP、本地函数、数据库、Shell、Python 和 MCP 由 Adapter 处理连接，但共用超时、重试、熔断、沙箱和取消机制。
4. **调用后管道**：检查 HTTP 状态、业务码和任务后置条件，执行结果脱敏、审计、指标上报及 Trace 结束；写操作保存幂等结果，工作流记录节点状态和补偿信息。

| 层次 | 核心职责 | 禁止事项 |
|---|---|---|
| Planner | 选择工具、生成计划 | 直接持有凭据 |
| Executor | 策略校验、可靠执行 | 相信未校验参数 |
| Adapter | 协议转换、连接管理 | 绕过统一策略 |

Executor 核心与业务解耦，领域规则通过 Validator 或 Policy 扩展。指标包括业务成功率、P95 延迟、重试率、拒绝率和单位成本。

**相关知识点：** Tool Executor、Adapter、统一调用契约、Policy Engine、幂等性、熔断、后置条件、OpenTelemetry。

### Agent 如何管理 API Key 和敏感凭据？

Agent 不应读取或长期保存明文凭据，应采用 **集中密钥管理、短期凭据、最小作用域、运行时注入和全程脱敏** 的机制。

1. **集中存储**：API Key、密码和证书保存在 Vault、KMS 或 Secrets Manager 中；禁止写入 Prompt、代码、仓库、镜像和 Memory。
2. **身份换取凭据**：Agent 使用工作负载身份向密钥系统认证，根据用户、租户、工具、环境和任务申请短期令牌。优先使用 OAuth2、STS 或动态数据库账号，避免共享长期 API Key。
3. **运行时注入**：Executor 在调用最后一刻把凭据注入 Adapter 的受保护内存或文件描述符，模型只看到逻辑凭据引用。凭据限定 audience、scope、资源、有效期和来源网络，任务结束立即撤销。
4. **轮换与泄露防护**：自动轮换长期密钥并支持紧急吊销；日志、Trace 和工具结果字段级脱敏，检测高熵字符串和密钥格式。

| 方式 | 风险 | 推荐控制 |
|---|---|---|
| 长期共享Key | 难追责、泄露面大 | 仅用于受控遗留系统 |
| 短期Token | 生命周期短 | 按任务签发与撤销 |
| 动态账号 | 权限可细分 | 自动创建、过期回收 |

审计应记录凭据引用、申请身份、作用域、使用工具和 `trace_id`，但不得记录密钥值。发现泄露时立即吊销、轮换，并追踪所有使用记录和潜在影响。

**相关知识点：** Vault、KMS、Secrets Manager、工作负载身份、STS、短期令牌、密钥轮换、日志脱敏。
<a id="tool-038"></a>
### 如何设计 Tool Call 的日志、指标和链路追踪？

Tool Call 可观测体系应统一 **结构化日志、指标和分布式 Trace**，关联模型、Planner、Executor 与下游服务。

1. **日志设计**：记录租户、身份、工具版本、参数摘要、授权、耗时、业务码、重试、降级和结果大小。敏感字段必须脱敏，原始数据按级别采样和保留。
2. **指标设计**：系统指标包括 QPS、并发、P95、超时、错误、队列和熔断；质量指标包括选择准确率、参数正确率、业务成功率和人工接管率；成本指标包括 Token 与外部费用。
3. **Trace 设计**：入口建立根 Span，模型调用、规划节点、每次 Tool Call 和下游请求建立子 Span，传播 `trace_id、span_id、deadline`。异步任务使用 Span Link 或持久化父任务标识关联。
4. **告警与分析**：按 SLO 设置错误预算和多窗口告警，通过 Trace 定位关键路径，再用日志查看原因；指标按工具、版本、租户和错误类型分桶。

| 信号 | 主要回答 | 典型内容 |
|---|---|---|
| Logs | 具体发生了什么 | 参数摘要、业务码 |
| Metrics | 系统是否异常 | 延迟、成功率、成本 |
| Traces | 故障位于哪里 | 调用依赖、关键路径 |

审计日志与调试日志应分离：前者完整、不可篡改，后者可采样。所有记录都需包含 Schema 与策略版本，支持轨迹回放和版本对比。

**相关知识点：** 结构化日志、Metrics、Trace、Span、SLO、错误预算、轨迹回放、审计日志。
<a id="tool-073"></a>
### Agent如何支持灰度发布和自动回滚？

Agent 应负责生成发布计划和观察信号，确定性发布控制器负责 **分批放量、指标判定、暂停和回滚**，避免模型直接控制生产流量。

1. **发布准备**：固定签名制品、配置版本和数据库迁移方案，定义目标环境、灰度单元、每阶段流量、观察窗口、成功阈值与回滚条件。计划经过 Policy 和审批后不可由 Agent 临时扩大范围。
2. **渐进策略**：先部署预生产，再按实例、租户、地域或百分比进行金丝雀；每阶段只在上一阶段通过后放量。高价值租户和核心区域最后进入，设置最大并发变更数。
3. **指标门禁**：同时观察技术指标、业务指标和安全指标，例如错误率、P95、资源、订单成功率、人工投诉与异常权限事件，并与稳定版本对照，避免只看服务存活。
4. **自动回滚**：任一硬阈值越界立即停止新流量，将路由和配置切回稳定版本，记录现场并告警。数据库变更必须向前兼容或使用独立补偿；不可逆数据操作转人工恢复。

| 策略 | 优点 | 适用场景 |
|---|---|---|
| 金丝雀 | 小流量快速验证 | 在线服务 |
| 蓝绿 | 切换和回滚快速 | 环境可双份部署 |
| 分租户/地域 | 精确控制影响 | 多租户全球系统 |

为防止指标抖动，使用最小样本量、连续窗口和冷却时间。审计记录计划、制品哈希、审批、每批结果、回滚原因及 Trace。

**历史别名：** `GOV-169`。

**相关知识点：** 灰度发布、金丝雀、蓝绿发布、指标门禁、对照组、自动回滚、向前兼容、冷却窗口。
<a id="tool-074"></a>
### Agent执行失败后如何恢复现场？

现场恢复需要在执行前建立 **可追溯状态、检查点、幂等与补偿方案**，失败后先冻结证据和阻止继续扩散，再按副作用类型恢复。

1. **保存执行状态**：每个任务记录计划版本、节点状态、工具与版本、参数摘要、输出引用、幂等键、审批和 Trace。关键节点完成后写检查点，避免进程重启后整条链路重新执行。
2. **失败隔离**：检测到异常立即停止受影响分支，取消在途调用，撤销临时凭据和租约；保留日志、工作目录快照、数据库事务状态、网络事件及资源版本，禁止清理关键证据。
3. **分类恢复**：无副作用的读操作可重试；文件修改通过快照、回收区或 Git revert 恢复；数据库使用事务回滚、变更前镜像或补偿；发布切回稳定制品。写入状态未知时先查询真实结果。
4. **断点续跑**：恢复完成后从最近一致检查点继续，只执行未完成节点；重放使用原幂等键。补偿失败、状态冲突或不可逆操作转人工，并展示已完成动作和剩余风险。

| 副作用 | 现场证据 | 恢复方式 |
|---|---|---|
| 文件 | diff、哈希、快照 | revert或恢复快照 |
| 数据库 | 事务、前镜像、行数 | 回滚或补偿 |
| 发布 | 制品、配置、流量版本 | 切回稳定版本 |
| 外部消息 | 消息ID、幂等键 | 查询、撤回或人工处理 |

恢复后必须验证业务后置条件，而非只看补偿接口成功。复盘指标包括恢复时间、补偿成功率、重复副作用和现场完整率。

**历史别名：** `GOV-170`。

**相关知识点：** 检查点、幂等键、补偿事务、现场冻结、Git revert、状态查询、断点续跑、MTTR。
<a id="tool-075"></a>
### 如何设计完整的Tool Audit Log？

完整 Tool Audit Log 必须回答 **谁基于什么授权，在何时调用了哪个版本的工具，影响了什么资源，结果与恢复情况如何**，并保证不可抵赖。

1. **身份与上下文**：记录用户、Agent 工作负载、租户、会话、任务、来源应用和网络区域；保存用户委托、角色、临时提权及审批人，但不记录令牌和密钥值。
2. **请求与策略**：记录工具逻辑名和版本、规范化参数摘要、目标资源、Risk Score、Policy 版本、鉴权结果、审批绑定的请求哈希、Deadline、幂等键和 `trace_id`。
3. **执行与结果**：记录开始结束时间、Executor 与 Adapter、重试、降级、业务码、结果摘要、影响行数或文件、后置条件、补偿和最终状态。状态未知必须明确标识。
4. **安全存储**：敏感字段脱敏或哈希，事件按统一 Schema 写入追加式存储并进行签名、时间戳和完整性校验；设置访问控制、保留期、归档及合法删除流程。

| 日志类型 | 主要目的 | 特性 |
|---|---|---|
| 运行日志 | 调试性能和错误 | 可采样、短期 |
| 审计日志 | 追责与合规 | 完整、不可篡改 |
| 安全事件 | 威胁响应 | 高优先级告警与归档 |

审计系统支持按用户、资源、工具、审批、时间和 Trace 构建时间线，并对越权尝试、异常批量操作、日志缺失和策略绕过实时告警。

**历史别名：** `GOV-171`。

**验证指标：** 工具选择准确率、调用成功率、参数错误率、P95 延迟和失败恢复率。

**相关知识点：** Audit Log、追加式存储、日志签名、请求哈希、数据脱敏、保留策略、Trace ID、事件时间线。
<a id="tool-080"></a>
### 如何防止多个Agent同时操作同一资源导致冲突？

多 Agent 并发应通过 **资源版本、条件写入、锁或租约、幂等和冲突恢复** 保证一致性，并尽量避免共享可变状态。

1. **资源版本控制**：文件、数据库记录和部署对象携带版本号、ETag 或 commit SHA。Agent 读取时保存版本，写入使用 If-Match 或 CAS；版本不一致立即拒绝，要求重新读取与规划。
2. **互斥机制**：短事务使用数据库行锁，长任务使用带 TTL 的分布式租约或资源所有权；锁粒度按资源而非全局设置，并支持续租、超时回收和持有者身份校验。
3. **幂等与排序**：每个业务操作使用稳定幂等键，消息按资源键分区保证顺序；重复请求返回原结果。多个 Agent 不能共享同一幂等键处理不同参数，参数摘要不一致应拒绝。
4. **冲突处理**：文本变更可基于共同基线进行三方合并，数据库或发布冲突通常不可自动覆盖，应重新验证业务条件或转人工。工作流保存检查点，并为已执行步骤定义补偿。

| 机制 | 适用场景 | 主要权衡 |
|---|---|---|
| 乐观锁/CAS | 冲突概率低 | 失败后需重试 |
| 悲观锁 | 强互斥短事务 | 降低并发 |
| 分布式租约 | 跨服务长任务 | 需处理过期与脑裂 |
| 资源队列 | 同资源顺序写 | 增加等待延迟 |

监控冲突率、锁等待、租约超时、重复副作用和人工合并率，据此调整锁粒度与调度策略。

**历史别名：** `GOV-176`。

**相关知识点：** 乐观锁、CAS、ETag、悲观锁、分布式租约、幂等键、三方合并、补偿事务。
<a id="tool-081"></a>
### Agent如何保证工具调用的幂等性？

Agent 只能协调幂等，真正保证必须落在 **产生副作用的工具或服务端**：同一业务意图重复提交时只执行一次，并返回可复用的原结果。

1. **稳定幂等键**：由租户、任务、业务操作和目标资源生成，所有超时重试与消息重投复用同一键；服务端保存请求参数摘要，若同键参数不同则拒绝，防止错误去重。
2. **原子记录与写入**：幂等状态和业务更新放在同一事务，或使用唯一约束、CAS、Outbox。执行前写入 `PROCESSING`，完成后保存 `SUCCESS/FAILED` 与标准结果，避免成功但无记录的窗口。
3. **重试与状态查询**：查询类工具通常天然幂等；创建、扣款、发送消息等必须显式声明保障方式。写调用超时后先按幂等键查询状态，只有确认未执行且策略允许时才重试。
4. **多步任务处理**：每个 Tool Call 使用独立幂等键，工作流节点另有任务与步骤标识；补偿操作也需幂等。Planner 重规划时复用已完成节点结果，禁止重新产生副作用。

| 机制 | 适用操作 | 关键要求 |
|---|---|---|
| 唯一约束 | 创建资源 | 冲突后返回原记录 |
| 幂等表 | 跨服务写入 | 与业务事务一致 |
| CAS/版本号 | 状态更新 | 检测并发修改 |
| Outbox | 消息与数据库一致性 | 可靠投递与去重 |

幂等记录 TTL 应覆盖最大重试窗口；订单、资金等长期一致性场景需更长保留。指标关注重复请求率、去重命中率和重复副作用率。

**历史别名：** `GOV-177`。

**相关知识点：** 幂等键、唯一约束、幂等表、CAS、Outbox、状态查询、补偿幂等、重复副作用。
<a id="tool-098"></a>
### 如果不用框架，Tool 调用系统怎么设计？

不用框架时，应把Tool调用实现为**模型提议、确定性系统校验并执行、结构化结果回传**的受控协议，模型不得直接访问业务接口或持有长期凭证。

1. **工具注册**：建立Registry，记录名称、版本、JSON Schema、权限、超时、幂等性和副作用等级；描述需明确边界，避免语义重叠。
2. **调用闭环**：提供候选工具Schema；解析结构化调用后，执行参数校验、身份鉴别、策略授权、限流和预算检查，再由Executor调用服务。结果统一为成功、可重试、业务拒绝或系统错误。
3. **安全控制**：按用户身份下传最小权限短期令牌；高风险操作采用确认或审批，写操作使用幂等键，外部内容按不可信数据处理，并限制网络目标、响应大小和重试次数。
4. **状态与观测**：每次调用关联Trace ID、会话、工具版本和策略版本，记录参数摘要、耗时、结果与费用；执行状态持久化，以支持恢复、补偿和人工接管。

| 模块 | 职责 | 禁止事项 |
|---|---|---|
| Planner/LLM | 选择工具、生成参数 | 直接执行业务动作 |
| Policy Engine | 鉴权与风险决策 | 依赖模型自我约束 |
| Executor | 隔离执行、超时重试 | 无限重试 |
| Registry | 契约与版本管理 | 静默破坏兼容性 |

测试覆盖Schema契约、权限矩阵、提示词注入、幂等与故障注入；工具版本需兼容演进。

**相关知识点：** Tool Registry、JSON Schema、Policy Engine、短期令牌、幂等键、Executor、结构化输出、补偿、契约测试。
<a id="tool-104"></a>
### 如何防止 Agent 工具循环调用？

防循环不能只靠提示词，应由运行时实施**硬预算、状态去重、进展检测和明确终止语义**，使任何异常轨迹都能在有限资源内停止。

1. **硬限制**：为任务设置最大步骤、单工具调用次数、连续失败次数、总时长、Token和费用上限；达到阈值立即转入结束、降级或人工接管状态。
2. **调用指纹**：将工具名、规范化参数、关键上下文和结果摘要生成指纹；若相同调用在状态未变化时重复，直接复用缓存或阻断。写工具还必须使用幂等键，防止重复副作用。
3. **进展判定**：每一步声明预期状态变化和成功条件。执行后比较任务状态、证据增量与错误类型；连续无新信息、目标距离未缩短或计划在若干状态间振荡，即判定停滞。
4. **错误治理**：区分瞬时、参数、权限和业务错误，仅瞬时错误指数退避重试；参数错误允许有限修正，权限错误禁止重试。工具返回机器可读错误码和可恢复建议。

| 机制 | 解决问题 | 注意点 |
|---|---|---|
| 步数/预算上限 | 保证最终停止 | 可能提前终止长任务 |
| 指纹去重 | 相同调用循环 | 需规范化动态字段 |
| 进展检测 | 不同调用的语义循环 | 需定义状态指标 |
| 状态机 | 限制转移路径 | 开放任务灵活性较低 |

监控循环终止率、重复调用率和人工接管率，并保存终止原因供离线评测；不可将“再试一次”作为通用恢复策略。

**相关知识点：** 调用指纹、幂等键、循环检测、进展函数、最大步数、指数退避、错误分类、终止条件、人工接管。
<a id="tool-105"></a>
### 如何做 Agent 执行链路追踪？

Agent链路追踪应以任务为根Trace，将**模型推理、规划、检索、工具、记忆、审批和状态转移**统一关联，既能定位性能故障，也能解释结果来源。

1. **统一标识**：生成Trace ID，每个步骤创建Span，记录父子关系、会话、租户、Agent版本、提示词版本、模型、工具版本和策略版本；异步队列通过Trace Context继续传播。
2. **结构化事件**：模型Span记录输入输出Token、延迟、采样参数、结束原因和费用；检索记录查询、文档ID与分数；工具记录参数摘要、授权结果、重试和返回码；状态节点记录进入、退出及检查点。
3. **安全分层**：默认采集元数据，正文按敏感等级脱敏、加密或仅存哈希；审计证据与调试数据分库、分权和分周期保留，避免追踪平台形成数据泄露面。
4. **分析闭环**：结合Metrics、Logs和Traces构建成功率、延迟、成本及调用图；支持按Trace回放状态，有副作用的工具只能模拟或经审批重放。

| 信号 | 回答的问题 | 典型粒度 |
|---|---|---|
| Trace | 时间花在哪里、路径如何 | 单次任务 |
| Log | 具体发生了什么 | 单个事件 |
| Metric | 系统是否整体异常 | 聚合趋势 |
| Audit | 谁以何权限做了什么 | 合规证据 |

采样应对普通成功链路按比例、对错误和高风险链路全量保留，并校验上下游关联率、数据完整率及追踪开销。

**相关知识点：** OpenTelemetry、Trace、Span、Context Propagation、结构化事件、日志脱敏、采样、调用图、状态回放。
<a id="tool-108"></a>
### LangChain 的 Agent Executor 有哪些局限？

Agent Executor适合“模型选择工具—观察结果—继续推理”的轻量循环，但对生产级复杂Agent而言，主要局限是**流程表达、持久化恢复、细粒度控制和可调试性不足**；复杂场景通常更适合显式图编排。

1. **控制粒度有限**：核心是通用循环，分支、并行、嵌套子流程、审批、补偿和自定义终止条件表达不够直观；控制逻辑容易散落在提示词、回调与工具中。
2. **状态与恢复较弱**：长任务需要可靠检查点、暂停后恢复、故障重放和人工介入。若只依赖进程内循环，崩溃后难以从确定步骤继续，重复工具调用还可能产生副作用。
3. **调试困难**：模型决策具有不确定性，隐式Scratchpad和动态步骤使问题复现、Token归因、状态差异对比及单节点测试更困难。
4. **治理需外补**：权限、审批、预算、幂等、工具版本、审计和多租户隔离并非Executor自动提供，仍需独立控制面。

| 维度 | Agent Executor | 显式图/状态机 |
|---|---|---|
| 路径 | 动态循环 | 节点与边可见 |
| 恢复 | 需额外实现 | 可基于检查点 |
| 人工介入 | 集成成本较高 | 可建暂停节点 |
| 适用任务 | 简单工具Agent | 长流程、关键业务 |

这并不表示其不可用：低风险、短链路和快速验证中，它能减少样板代码。迁移前应先以步骤数、恢复要求和副作用风险判断，避免为简单任务引入过重编排。

**相关知识点：** Agent Executor、ReAct循环、LangGraph、检查点、持久化执行、Human-in-the-loop、幂等、显式状态。
<a id="tool-110"></a>
### 工具调用失败时如何重试和降级？

工具失败处理应先**识别错误是否可恢复，再实施有界重试、熔断与业务降级**；未经分类的统一重试会放大故障，并可能重复产生副作用。

1. **错误分类**：超时、限流、临时网络故障和部分5xx通常可重试；参数、认证、权限、资源不存在及业务规则拒绝应直接修正、终止或转人工。工具需返回稳定错误码、可重试标志与Retry-After。
2. **安全重试**：读操作可指数退避并加入抖动；写操作只有携带幂等键、服务端去重或事务状态可查询时才能自动重试。设置单次超时、最大次数、总时间和总成本预算。
3. **防故障扩散**：采用熔断器、并发隔离、限流和背压；熔断开启后快速失败，半开阶段仅放少量探测流量。重试应尽量在单一层执行，避免SDK、网关和Agent叠加形成重试风暴。
4. **分级降级**：可切换等价只读工具、缓存或稍旧数据，也可返回部分结果、排队稍后处理或人工接管；不得用低可信来源静默替代高可信结果。

| 错误 | 自动重试 | 推荐动作 |
|---|---|---|
| 限流/瞬时网络 | 是 | 退避、抖动 |
| 参数错误 | 否 | 有限修正参数 |
| 权限拒绝 | 否 | 终止并审计 |
| 写入结果未知 | 条件式 | 查状态或用幂等键 |

监控首次成功率、重试成功率、放大倍数、熔断次数及降级占比，并将最终状态明确回传给Planner，防止其换参数绕过策略。

**历史别名：** `ARC-081`。

**相关知识点：** 错误分类、指数退避、Jitter、幂等键、熔断器、Retry-After、背压、Bulkhead、部分结果、人工接管。
<a id="tool-114"></a>
### 工具超时如何处理？

工具超时必须被视为**结果未知而非执行失败**：先停止本地等待，再确认远端状态，依据幂等性决定重试、续查、补偿或人工介入。

1. **分层时限**：设置连接、首字节、读取、单次调用和任务总截止时间，子调用预算不得超过剩余总时限；超时值依据历史P95/P99、业务SLA和操作类型制定，禁止所有工具共用固定值。
2. **取消传播**：到期后发送Cancellation并释放线程、连接和沙箱资源；服务端应接收Deadline并主动终止无意义工作。客户端停止等待不代表服务端已停止，因此写操作仍需查询。
3. **后续决策**：无副作用读操作可有限退避重试；幂等写操作携带同一幂等键查询或重试；非幂等写操作若状态不明，禁止自动重放，应查业务状态、执行补偿或转人工。
4. **慢任务设计**：预计耗时较长的工具改为异步提交，返回Job ID，通过轮询、回调或事件获取进度；支持断点、心跳和用户取消，避免持有长连接。

| 类型 | 超时后策略 | 风险 |
|---|---|---|
| 只读查询 | 退避重试/缓存 | 数据稍旧 |
| 幂等写入 | 同键续查或重试 | 服务端需去重 |
| 非幂等写入 | 查状态/人工核对 | 重复副作用 |
| 长任务 | 异步Job | 状态管理复杂 |

监控超时率、超时后成功率、孤儿任务数和重复执行率，并用链路追踪定位排队、网络还是服务端处理造成的时延。

**历史别名：** `GOV-051`。

**相关知识点：** Deadline、Cancellation、P99、幂等键、结果未知、异步Job、心跳、退避重试、孤儿任务、超时预算。
<a id="tool-120"></a>
### 如何记录Agent执行审计日志？

Agent审计日志应形成**主体—意图—决策—动作—结果—证据**的完整链路，支持追责和事件回溯，同时遵循最小记录原则，避免日志反向泄密。

1. **统一关联**：每次任务生成Trace ID，并关联用户、租户、会话、Agent、模型、提示词、知识库、工具和策略版本；异步步骤、人工审批与外部任务继续传播该标识。
2. **记录关键事件**：保存请求目的与输入摘要、检索文档ID、模型决策摘要、工具名及规范化参数、鉴权结果、审批、重试、状态转移、最终结果和错误码。对写操作额外记录目标资源执行前后版本。
3. **可信与隐私**：日志在Agent沙箱外实时汇聚，使用时间同步、签名、哈希链或WORM防篡改；密钥、个人信息和业务正文应脱敏、加密或仅存哈希。审计与调试日志分权、分周期留存。
4. **检索告警**：按主体、资源、时间、Trace和风险规则建立索引；越权尝试、高危工具、策略绕过和异常批量操作实时告警，查询审计日志本身也需留痕。

| 日志类型 | 用途 | 内容策略 |
|---|---|---|
| 审计日志 | 合规与责任认定 | 精简、不可篡改 |
| 运行日志 | 故障定位 | 技术细节、限期保留 |
| Trace | 链路与性能分析 | Span及元数据 |
| 业务证据 | 还原资源变化 | 版本/摘要/受控快照 |

验收指标包括事件完整率、关联成功率、写入延迟、丢失率和检索时间，并定期执行模拟事件回溯验证。

**相关知识点：** 审计事件、Trace ID、WORM、哈希链、数据脱敏、证据链、SIEM、分级留存、资源版本。
<a id="tool-192"></a>
### Workflow Mining 如何实现？

Workflow Mining应从事件日志中**发现实际流程、比较规范并定位变体与瓶颈**，输出候选流程而非直接生成代码。

1. **事件模型**：事件含Case ID、动作、时间、主体、结果和资源；Agent还记录Tool、状态、审批与错误码。统一时钟、去重、处理乱序并脱敏。
2. **流程发现**：按Case ID重建轨迹，以直接跟随图或流程挖掘算法生成模型；先归一化动作，区分业务重做、系统重试和并行。
3. **一致性检查**：与SOP或既有Workflow比较，识别跳步、回退、绕过审批和循环；计算路径频率、等待时间、返工率与失败热点。
4. **候选提炼**：以高频、高成功、低变异路径为主流程，例外建分支；明确契约、权限、超时、补偿和人工节点。高频失败路径用于整改。
5. **验证发布**：专家确认语义，经历史回放、异常注入和灰度后注册。

| 方法 | 目的 | 输出 |
|---|---|---|
| 流程发现 | 发现真实路径 | 流程图 |
| 一致性检查 | 比较规范与实际 | 偏差列表 |
| 流程增强 | 分析性能与瓶颈 | 优化建议 |
| 序列聚类 | 分组流程变体 | 典型轨迹 |

评估需关注模型对日志的拟合度、简洁度、泛化能力和业务可解释性；过度拟合每个例外会得到难以维护的“意大利面流程”。

**相关知识点：** Process Mining、Case ID、事件日志、直接跟随图、流程发现、一致性检查、流程变体、瓶颈分析。
<a id="tool-224"></a>
### DAG任务编排如何实现？

DAG编排应将任务表示为**有向无环依赖图和版本化状态**，调度器只运行依赖满足的节点，并通过幂等、检查点和补偿保证可恢复。

1. **图定义**：节点声明输入输出Schema、资源、超时、重试、幂等性、副作用和成功判据；边表示数据或控制依赖。发布前执行环检测、拓扑排序、Schema兼容和不可达节点检查。
2. **调度执行**：实例创建后计算入度为零的就绪节点，Worker通过队列与租约领取；节点完成后原子写状态并减少下游依赖计数，新就绪节点入队。独立节点并行，资源冲突或写操作按约束串行。
3. **状态一致性**：节点输出、状态转移和Outbox事件在同一事务提交，消息采用至少一次投递并靠幂等键去重；大结果存对象仓，状态只保留引用和摘要。
4. **失败恢复**：瞬时错误有界重试，业务失败走条件分支，部分完成按Saga补偿；进程崩溃由租约过期接管，从最近检查点恢复。结果未知的写操作先查远端状态。
5. **控制观测**：支持Deadline、取消、优先级、并发和预算；Trace记录节点、依赖、尝试、耗时与成本。最终汇聚节点验证全局目标。

| 组件 | 职责 | 关键机制 |
|---|---|---|
| DAG定义 | 描述依赖 | 环检测、版本化 |
| Scheduler | 计算就绪节点 | 拓扑与资源约束 |
| Worker | 执行节点 | 租约、幂等 |
| State Store | 保存进度 | 事务、检查点 |

**相关知识点：** DAG、拓扑排序、就绪队列、租约、幂等键、Outbox、检查点、Saga、关键路径、状态存储。
