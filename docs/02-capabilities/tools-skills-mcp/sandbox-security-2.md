### 如何在自动化效率和人工审批安全之间做平衡？

平衡的关键是**按风险而非按功能决定自动化程度**：低风险自动执行，中风险在明确条件下确认，高风险审批，超过容忍边界的操作直接禁止。

1. **建立风险模型**：综合主体权限、数据敏感度、影响范围、金额、可逆性、环境、模型置信与历史异常评分；策略输出自动、确认、单人审批、双人审批或拒绝，并记录理由。
2. **减少无效审批**：对重复、低影响动作使用预授权额度和时间窗；把多个同质步骤聚合为一次审批，展示结构化差异、影响预览和恢复方案。禁止用频繁弹窗造成审批疲劳。
3. **保持执行绑定**：批准内容必须绑定工具版本、规范化参数、资源、环境、次数和有效期；执行前再次校验权限与资源版本，参数变化重新审批，防止“先批后改”。
4. **动态调节**：新工具、异常时段或高风险租户提高审批级别；稳定且指标良好的动作可逐步扩大自动化。发生安全事件时立即收紧或熔断，不能等待模型更新。

| 风险级别 | 默认方式 | 示例 |
|---|---|---|
| 低 | 自动+抽检 | 公开信息只读查询 |
| 中 | 用户确认/额度内自动 | 发送草稿、个人资源修改 |
| 高 | 指定角色审批 | 生产发布、批量写入 |
| 禁止 | 硬拦截 | 越权、破坏审计 |

用自动完成率、审批等待时间、误批率、绕过率、人工接管率和事故损失联合优化，不能只追求审批数量下降。

**相关知识点：** 风险分级、Policy Engine、Human-in-the-loop、预授权、审批疲劳、职责分离、参数绑定、动态风控、熔断。

### SQL写操作如何做到可回滚？

SQL写操作可回滚的前提是**在执行前设计恢复路径并保留足够证据**；数据库事务只解决未提交阶段，提交后的恢复需要备份、变更集或补偿机制。

1. **短事务回滚**：将相关写入放在事务中，先校验影响行数和业务约束，再提交；异常立即ROLLBACK。设置锁等待、执行时间和影响行数上限，避免长事务拖垮线上。
2. **提交后恢复**：更新与删除前捕获主键、旧值和版本号，形成受保护的Undo Log或反向SQL；大批量操作使用数据库时间点恢复、快照或备份。恢复数据需加密、限期保留并验证可用性。
3. **分批与可重入**：按稳定主键范围小批执行，每批携带变更ID和幂等键，记录成功边界；暂停后可从检查点续作。使用乐观锁防止回滚覆盖他人的后续合法修改。
4. **跨系统操作**：数据库与消息、搜索索引等无法用单库事务覆盖时，采用Outbox与Saga，为每个步骤定义补偿；补偿是新的业务动作，可能失败，必须可重试并审计。

| 机制 | 适用阶段 | 局限 |
|---|---|---|
| 数据库事务 | 提交前 | 不覆盖已提交结果 |
| Undo Log/反向SQL | 精确撤销少量变更 | 需处理并发冲突 |
| 快照/PITR | 大范围灾难恢复 | 恢复粒度和时间较大 |
| Saga补偿 | 跨服务流程 | 不是物理回滚 |

执行前必须dry-run并展示影响范围，执行后核对行数、校验和与业务指标；回滚方案应定期演练，而非只在文档中声明。

**相关知识点：** ACID事务、Undo Log、PITR、乐观锁、幂等键、分批执行、Outbox、Saga、补偿事务、恢复演练。

### Shell命令如何防止误删宿主机文件？

防误删的根本措施是**让执行环境在权限和挂载层面无法访问宿主机文件**，命令解析与黑名单只能作为补充，不能承担主防线。

1. **强隔离**：在容器或轻量虚拟机中以非特权用户运行，使用独立Mount Namespace；不挂载宿主根目录、Docker Socket和设备，禁用特权模式并移除多余capabilities。
2. **只读与限定写区**：根文件系统及输入数据只读挂载，仅开放任务专属临时目录；对写区设置磁盘配额，任务结束整体销毁。确需输出时由受控服务复制指定文件，而非允许Shell访问目标目录。
3. **命令护栏**：优先使用参数数组调用固定程序，避免拼接Shell字符串；解析AST并限制可执行文件、参数、重定向、通配符、符号链接和路径穿越。删除操作先解析规范化路径，验证其仍位于授权目录。
4. **执行与恢复**：高风险删除采用dry-run、影响清单和审批，优先移动到隔离回收区；设置进程、时间和文件数上限，并记录命令摘要、文件清单及结果。

| 防线 | 作用 | 局限 |
|---|---|---|
| 命令黑名单 | 阻挡已知危险文本 | 易被变形绕过 |
| 路径校验 | 限制目标目录 | 需防符号链接竞态 |
| Mount隔离 | 隐藏宿主文件 | 配置错误仍有风险 |
| 轻量虚拟机 | 独立内核边界 | 资源开销较高 |

还应测试软硬链接、挂载传播、路径竞态和子进程绕过，确保失败时默认拒绝而非扩大权限。

**相关知识点：** Mount Namespace、只读挂载、非特权容器、Capabilities、路径规范化、符号链接竞态、回收区、fail-closed。

### 沙箱逃逸风险如何防护？

沙箱逃逸无法靠单项配置消除，应采用**分层隔离、最小攻击面、快速修补、运行时检测和限制爆炸半径**的纵深防御；高风险代码优先使用独立内核边界。

1. **选择隔离级别**：低风险任务可用加固容器；不可信二进制或高价值任务采用microVM或独立节点池，避免与控制面共置。
2. **缩小权限**：非root运行、用户命名空间、只读根文件系统、最小Capabilities、seccomp与SELinux/AppArmor；禁止privileged、hostPID、hostNetwork、宿主设备、Docker Socket和宽泛挂载。
3. **供应链与内核治理**：使用最小签名镜像，扫描漏洞和恶意依赖，固定摘要；内核、运行时及基础镜像及时修补，高危漏洞出现时隔离节点、撤销镜像并重新创建实例。
4. **运行时防护**：监测异常系统调用、命名空间变更、敏感路径、提权、内核日志和异常网络行为；发现迹象立即终止任务、隔离节点、吊销凭证并保全取证证据。

| 边界 | 隔离强度 | 典型代价 |
|---|---|---|
| 语言沙箱 | 低 | 兼容好但依赖运行时 |
| 加固容器 | 中 | 共享宿主内核 |
| microVM/虚拟机 | 高 | 启动与资源成本较高 |
| 独立物理节点 | 最高 | 成本和调度复杂 |

网络默认拒绝、短期凭证和租户分区可降低逃逸影响；定期开展逃逸测试与应急演练。

**相关知识点：** 纵深防御、microVM、User Namespace、seccomp、SELinux、Capabilities、镜像签名、运行时检测、节点隔离。

### Workflow 失败后如何恢复执行？

Workflow恢复应以**持久化状态和节点幂等为基础，从最近一致检查点继续**；恢复前必须识别外部副作用的真实状态，不能简单重跑整条流程。

1. **错误与状态判定**：区分瞬时错误、业务拒绝、权限变化、数据冲突、结果未知和不可恢复错误；保存失败节点、尝试次数、错误码、状态版本及已完成节点。
2. **恢复策略**：瞬时错误指数退避重试；业务错误走修正或替代分支；权限错误暂停等待授权；依赖不可用可降级或排队；达到次数、时限或预算上限后转人工或终止。
3. **副作用一致性**：节点使用幂等键，恢复时先查询外部系统，区分未执行、已成功、部分完成和结果未知。已提交写入通过续作或Saga补偿处理，禁止无状态重放。
4. **检查点调度**：以原子事务保存节点输出、状态和Outbox事件，再确认节点完成；恢复器获取工作流租约，重建就绪节点，防止多个Worker同时恢复同一实例。
5. **版本安全**：默认使用失败时的Workflow、Skill和依赖版本；若必须升级，先执行状态Schema迁移并记录审计。

| 失败类型 | 默认动作 | 自动化条件 |
|---|---|---|
| 瞬时故障 | 有界重试 | 节点幂等 |
| 业务拒绝 | 分支/人工 | 有明确修正规则 |
| 结果未知 | 查询状态 | 外部系统可查 |
| 部分完成 | 续作/补偿 | 有检查点和补偿定义 |

通过进程崩溃、重复消息、网络分区和补偿失败测试恢复，监控成功率、重复副作用及恢复时间。

**相关知识点：** 检查点、节点幂等、租约、Outbox、Saga、补偿、错误分类、状态查询、故障注入、版本固定。

### Workflow 如何进行状态持久化？

Workflow状态持久化应采用**事件记录与当前快照结合、原子状态转移、版本化Schema和租户隔离**，同时满足恢复、审计与高并发访问。

1. **状态模型**：区分实例、变量、节点、尝试、审批、预算和外部引用；状态含实例ID、定义版本、递增版本号和时间。大文件放对象存储，状态库只存URI、摘要和权限。
2. **写入一致性**：节点完成时以事务写入输出摘要、状态转移、检查点及Outbox事件，再确认消息；使用乐观锁或条件更新防止多个Worker覆盖。状态转移必须可重复提交，防止网络重试产生分叉。
3. **存储分层**：关系库适合权威状态与事务，事件日志保存完整变更，缓存承载热点读取，对象仓保存大载荷。缓存不可作为恢复依据，搜索索引仅用于查询。
4. **恢复与迁移**：快照加后续事件重建实例，定期压缩事件控制恢复时间；Workflow升级提供Schema迁移器，运行中实例默认固定旧版本。迁移失败应保持原状态并可回退。
5. **安全治理**：按租户分区授权，敏感字段加密，设置审计、TTL、归档和删除策略；禁止保存密钥。

| 存储 | 适合内容 | 一致性定位 |
|---|---|---|
| 关系库 | 当前状态、检查点 | 权威强一致 |
| 事件日志 | 状态变更历史 | 追加、可重放 |
| 对象存储 | 大文件与模型载荷 | 摘要校验 |
| 缓存 | 热点读取 | 可丢弃 |

通过并发、重复消息、故障恢复和版本迁移测试验证。

**相关知识点：** 事件溯源、状态快照、Outbox、乐观锁、Schema迁移、对象存储、租户隔离、TTL、可重放事件。

### 如何判断一个 Workflow 是否值得沉淀？

值得沉淀的Workflow应满足**流程重复、依赖相对稳定、状态与异常可建模、沉淀收益高于编排成本**，不能只因步骤较多就固化。

1. **观察重复模式**：从SOP和执行日志统计同类目标的步骤序列、分支、工具与人工节点；若多数成功案例共享关键路径，且变化能通过参数或有限分支表达，具备沉淀基础。
2. **评估确定性**：输入输出、前后置条件、成功判据、超时、重试、审批和补偿能够明确；外部系统有稳定接口，副作用可幂等或追踪。路径高度开放且每次重规划的任务不宜强行DAG化。
3. **衡量价值**：比较人工耗时、错误率、等待时间、合规风险和业务损失，估算自动化后节省；扣除设计、评测、运行、监控、依赖升级及状态迁移成本，计算回收期。
4. **验证再固化**：先以模板或半自动流程运行，收集足够样本；通过历史重放、异常注入和小流量灰度，确认成功率、恢复能力与人工接管优于基线，再进入Registry。

| 特征 | 值得沉淀 | 暂缓 |
|---|---|---|
| 路径 | 主路径稳定 | 每次完全不同 |
| 异常 | 可分类与处理 | 失败不可观察 |
| 副作用 | 可幂等/补偿 | 状态无法确认 |
| 价值 | 高频或高风险 | 一次性低价值 |
| 维护 | 有Owner | 依赖频繁失控 |

沉淀后仍要定期复评；业务规则改变导致分支持续膨胀时，应拆分、重构或退回Planner。

**相关知识点：** 流程挖掘、关键路径、状态机、DAG、幂等、补偿、异常注入、ROI、Workflow Registry、Planner。
