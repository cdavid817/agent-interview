### 1. 工具注册中心（Tool Registry）应该如何设计？

企业级 Tool Registry 应按照 **Catalog、Policy、Version、Runtime** 四个域设计，统一管理工具定义、访问策略、版本流量和运行状态，并与真正执行工具的 Executor 解耦。

1. **Catalog 域**：保存标识、描述、能力域、输入输出 JSON Schema、协议、负责人、依赖、风险及适用边界；建立标签、全文和向量索引。
2. **Policy 域**：记录租户、角色、资源范围、数据级别和审批策略。Registry 返回候选前做权限过滤，Executor 调用前再次求值，防止缓存、版本切换或模型参数绕过授权。
3. **Version 域**：使用语义版本管理 Schema 与实现，通过契约测试判断兼容性；支持按租户、用户或流量权重灰度。下线先停止新请求，等待在途任务结束，并提供替代版本和废弃期限。
4. **Runtime 域**：聚合健康、业务成功率、P95 延迟、限流、熔断和成本。路由器只选择健康版本，异常时切换备用工具，但不得提升权限。

| 平面 | 管理内容 | 更新特点 |
|---|---|---|
| 控制面 | 元数据、权限、版本 | 低频、强一致 |
| 数据面 | 调用、限流、熔断 | 高频、低延迟 |
| 观测面 | 日志、指标、Trace | 异步汇聚 |

多租户环境必须隔离命名空间、凭据、配额和审计数据。调用方使用逻辑工具名，由 Registry 解析实际版本，避免模型绑定具体地址。

**相关知识点：** Tool Registry、Catalog、Policy、语义版本、契约测试、灰度发布、健康检查、多租户。

### 2. 为什么工具需要使用 JSON Schema 描述？

工具使用 JSON Schema，是为了把自然语言说明转化为 **模型可生成、程序可校验、平台可治理** 的结构化契约，从而降低参数幻觉和接口歧义。

1. **约束模型输出**：Schema 可定义对象结构、字段类型、必填项、枚举、数值范围、字符串格式、数组长度和条件规则。清晰的字段描述与示例还能帮助模型判断参数的业务含义和单位。
2. **执行前校验**：Executor 在真实调用前验证模型参数，使缺字段、类型错误和越界值停留在 Agent 层，不进入数据库或外部服务。校验失败应返回字段级错误，供模型定向修正。
3. **统一工程契约**：同一份 Schema 可用于运行时校验、客户端生成、文档、测试数据、Mock、版本兼容检查和审计，避免模型描述、代码类型与接口文档各自维护后发生漂移。
4. **支持工具治理**：Registry 可根据 Schema 判断工具兼容性，Router 可比较用户实体与工具必填参数，安全层可识别敏感字段并执行脱敏、审批和取值范围限制。

| 校验层 | 检查内容 | 示例 |
|---|---|---|
| JSON Schema | 结构与格式 | 类型、枚举、范围 |
| 业务校验 | 真实语义与状态 | 余额、资源是否存在 |
| 权限校验 | 身份与资源范围 | 租户、环境、角色 |

Schema 不能替代业务和权限校验，也不能保证模型一定选对工具。新增可选字段通常向后兼容；删除字段、改变类型或收紧约束应升级版本并灰度迁移。

**相关知识点：** JSON Schema、结构化输出、参数校验、业务校验、Schema演进、契约测试、Tool Registry。

### 3. Planner 如何决定调用一个工具还是多个工具？

Planner 应依据 **目标覆盖度、信息依赖、验证要求、可并行性和风险成本**，选择能够完成任务的最小工具集合，而不是工具越多越好。

1. **单工具条件**：一个工具能直接产生满足验收条件的结果，输入已齐全、无前置依赖且结果可验证时，应采用单工具调用，以减少延迟、成本和故障点。例如根据订单号查询确定状态。
2. **多工具条件**：目标跨数据源、需要先查后写、交叉验证或分阶段产生结果时，Planner 将任务拆为子目标，明确每步输入、输出、前置条件和后置条件，再建立依赖关系。
3. **调度策略**：无依赖的只读步骤并行执行；存在数据依赖、共享写资源或事务关系的步骤按 DAG 串行或汇聚执行。高风险写操作设置审批节点，并预先定义补偿路径。
4. **动态调整**：工具返回缺失信息、冲突或不可用状态时，只重规划受影响分支。系统设置最大步骤、工具次数、总时间、Token 和费用预算，防止计划无限扩张。

| 场景 | 调用策略 | 主要依据 |
|---|---|---|
| 单系统直接查询 | 单工具 | 结果可直接验收 |
| 多源信息汇总 | 并行多工具 | 步骤相互独立 |
| 先查询后写入 | 串行多工具 | 存在状态依赖 |
| 关键事实核验 | 多工具交叉验证 | 降低单源错误 |

Planner 每次增加工具都应说明其预期信息增益。计划质量通过 **任务成功率、无效调用率、关键路径延迟、重规划次数和单位任务成本** 评价。

**相关知识点：** Planner、任务分解、信息增益、DAG、并发调度、动态重规划、调用预算。

### 4. 工具参数校验应该放在哪一层完成？

参数校验应采用 **模型约束、Executor校验、工具业务校验、服务端校验** 的纵深结构；越靠近副作用，权威性越高。

1. **模型层**：通过工具描述和 JSON Schema 提高参数生成正确率，使用类型、枚举、范围和必填项减少格式错误。但模型约束属于概率性引导，不能作为安全边界。
2. **Executor 层**：调用前执行 Schema、格式、长度、敏感字段和基础跨字段校验，返回字段级错误供模型修正，确保各适配器入口一致。
3. **工具业务层**：校验资源是否存在、状态是否允许、金额与数量关系、时间窗口等领域不变量；只有工具拥有足够业务上下文，不能把复杂业务规则全部塞入通用 Executor。
4. **服务与策略层**：最终服务重新验证权限、租户、并发版本和业务状态；Policy Engine 独立判断风险、环境、数据级别和审批。

| 层级 | 主要校验 | 是否可替代下层 |
|---|---|---|
| 模型 | 参数生成格式 | 否 |
| Executor | Schema与通用安全规则 | 否 |
| 工具/服务 | 业务语义与真实状态 | 否 |
| Policy | 权限与风险 | 与业务校验并行 |

校验错误应统一返回 `field、code、message、retryable`，区分可由模型修正的参数错误和必须终止的权限错误。日志保留脱敏摘要与 Schema 版本。

**相关知识点：** JSON Schema、纵深校验、Tool Executor、业务不变量、Policy Engine、字段级错误、服务端校验。

### 5. 如何利用 OpenTelemetry 构建 Agent 的可观测体系？

OpenTelemetry 是 Agent 的 **统一遥测与上下文传播标准**，覆盖模型、规划、Tool、Memory 和下游服务。

1. **Trace 模型**：用户任务创建根 Span，模型、Router、Planner、Executor、Memory 和外部请求建立子 Span；异步队列用 Context 与 Span Link 保留因果关系。
2. **语义属性**：记录模型、Prompt、工具版本、节点状态、Token、费用、业务码、租户和风险。原始 Prompt 不作为 Metric Label，敏感内容需脱敏。
3. **信号采集**：SDK 采集 Trace、Metrics 和 Logs，经 Collector 批处理、采样、过滤和转发，再输出到可观测后端。
4. **采样告警**：正常流量概率采样，错误、高延迟、高风险轨迹强制保留；基于成功率、P95、成本和错误预算告警。

| 组件 | 主要职责 | 设计要点 |
|---|---|---|
| SDK/Instrumentation | 生成遥测数据 | 统一语义约定 |
| Collector | 处理与转发 | 脱敏、采样、批处理 |
| Backend | 查询和展示 | Trace、指标、日志关联 |

OpenTelemetry 解决采集与关联，不能替代业务评测；后置条件和用户评价仍需写入 Trace。

**相关知识点：** OpenTelemetry、Context、Span Link、Collector、Tail Sampling、Semantic Conventions、SLO。

### 6. Langfuse、Phoenix 等平台在 Agent 调试中的作用是什么？

Langfuse、Phoenix 提供 **轨迹回放、数据集评测、版本对比和错误分析**，定位路由、规划、工具或生成阶段的问题。

1. **执行轨迹分析**：展示模型、Planner、Tool、Memory、Token、费用和延迟，从失败结果回溯到具体 Span，并比较任务的多次运行。
2. **提示与版本管理**：关联 Prompt、模型、Skill 和工具版本，通过标签或实验分组比较成功率、延迟与成本，避免版本升级后只凭主观样例判断效果。
3. **评测体系**：将真实失败轨迹沉淀为数据集，运行规则、模型评分或人工标注，衡量工具选择准确率、参数正确率、任务完成率、事实性和用户满意度。
4. **运营诊断**：按错误、工具、租户、模型和版本聚类，发现高频失败与回归；将人工改选关联到轨迹，改进 Router 与 Prompt。

| 能力 | OpenTelemetry | Agent调试平台 |
|---|---|---|
| 遥测采集与传播 | 核心能力 | 通常接收或自行采集 |
| 轨迹可视化 | 依赖后端 | 面向LLM/Agent语义 |
| 数据集与评测 | 不负责 | 核心能力 |
| Prompt实验 | 不负责 | 版本对比和评测 |

此类平台不能替代业务审计和安全控制。Prompt 与工具结果需脱敏、控制采样和保留期；高风险任务仍以确定性后置条件及人工审核为准。

**相关知识点：** Langfuse、Phoenix、Trace Replay、Dataset、Evaluation、Prompt版本、错误聚类、OpenTelemetry。

### 7. 如何设计企业级、多租户、多版本的工具管理平台？

企业工具平台应采用 **全局控制面、租户隔离的数据面和不可变版本制品**，统一覆盖注册、权限、发布、运行、观测与运营。

1. **多租户模型**：每个租户拥有独立命名空间、工具可见性、凭据、配额、策略和审计索引；共享工具只共享签名制品，不共享身份与运行数据。所有表和缓存键必须包含租户标识。
2. **多版本管理**：工具定义、Schema、Adapter 和配置打包为不可变版本，使用语义版本与制品哈希。契约测试判断兼容性，在途任务固定版本，新任务按租户或流量权重灰度。
3. **统一控制面**：Catalog 管理元数据和检索，Policy 对接 IAM/SSO，Release 管理审批、灰度和回滚，Runtime 汇聚健康、限流、熔断与成本；Executor 负责真实调用。
4. **治理与运营**：工具注册需经过来源验证、安全扫描、权限审查和负责人确认；持续统计使用量、业务成功率、P95、成本和风险事件。无主、低价值或长期故障工具应下线。

| 隔离对象 | 实现方式 | 防止的问题 |
|---|---|---|
| 元数据 | 租户命名空间与行级策略 | 工具越权发现 |
| 凭据 | 独立密钥路径与短期令牌 | 身份串用 |
| 流量 | 独立配额、队列和熔断 | 邻居干扰 |
| 版本 | 租户级路由权重 | 升级同时影响全部租户 |

平台 API、事件和审计需带租户、工具逻辑名、具体版本及 `trace_id`。回滚只恢复制品，外部副作用仍依赖幂等与补偿。

**相关知识点：** 多租户、命名空间、不可变制品、语义版本、契约测试、灰度发布、Policy、租户配额。

### 8. 如何评估 Agent 工具调用的准确率、成功率和整体执行效率？

工具调用评估应分为 **选得对、参数对、执行成、任务成、成本合理** 五层，避免用 HTTP 200 或单次工具成功率代替端到端质量。

1. **离线准确率**：构建包含用户请求、正确工具、允许替代工具、参数及期望结果的标注集，评估 Recall@K、Top1、MRR、无工具请求拒识率、工具误调用率和参数字段准确率。
2. **执行成功率**：分别统计传输成功、业务码成功和后置条件成功。写操作还需检查目标资源是否处于期望状态、是否重复产生副作用；失败按参数、权限、依赖和业务规则分类。
3. **任务成功率**：多步任务以最终目标和验收条件为准，计算端到端完成率、首次完成率、重规划率、人工接管率及部分完成率。单个 Tool 成功但最终目标失败，仍算任务失败。
4. **执行效率**：统计工具调用数、无效调用率、关键路径 P95、排队时间、Token、外部费用、重试和单位成功任务成本，并与无工具或旧版本基线比较。

| 层级 | 代表指标 | 回答的问题 |
|---|---|---|
| 选择 | Top1、Recall@K | 是否选对工具 |
| 参数 | 字段准确率 | 是否传对数据 |
| 执行 | 业务成功率 | 工具是否做成 |
| 任务 | 端到端完成率 | 用户目标是否完成 |
| 效率 | P95、单位成本 | 是否高效完成 |

评测需按工具类型、风险、租户和版本分桶，并同时使用离线回放、线上灰度与人工抽检；高风险误执行应单独设为零容忍指标。

**相关知识点：** Recall@K、Top1、MRR、业务成功率、后置条件、任务完成率、单位任务成本、回归评测。

### 9. Risk Score应该包含哪些评估维度？

Risk Score 应同时覆盖 **操作危险性、目标价值、影响范围、权限强度、可逆性、输入确定性和运行上下文**，并设置不能被分数抵消的强制禁止规则。

1. **操作与副作用**：只读、创建、修改、删除、转账、发布、提权和任意代码执行具有不同基础分；是否幂等、是否外连、是否改变访问控制也应纳入。
2. **资源与范围**：评估测试或生产环境、数据敏感级别、资源关键度、单条或批量、跨租户范围及预计影响行数。范围无法计算、存在通配符或无条件 SQL 时提高风险。
3. **可逆与权限**：衡量是否有事务、快照、补偿或自动回滚，以及恢复时间和数据损失。所需凭据 Scope、是否临时提权和是否绕过职责分离也影响评分。
4. **上下文与不确定性**：考虑用户身份、来源网络、时间窗口、历史行为、模型选择置信度、参数完整性、外部内容是否可能提示注入，以及工具当前异常率。

| 维度 | 低风险特征 | 高风险特征 |
|---|---|---|
| 操作 | 只读、幂等 | 删除、提权、任意代码 |
| 范围 | 单资源、明确条件 | 批量、通配符、跨租户 |
| 环境 | 本地、测试 | 生产核心资源 |
| 可逆性 | 自动回滚 | 不可逆、恢复困难 |
| 确定性 | 参数完整可验证 | 目标模糊、状态未知 |

评分映射为自动执行、确认、双人审批或拒绝，并决定沙箱、凭据与审计强度。阈值需通过事故、误拦截和演练数据校准。

**历史别名：** `GOV-156`。

**相关知识点：** Risk Score、副作用、影响范围、可逆性、数据分级、模型置信度、强制策略、阈值校准。

### 10. Trace ID如何贯穿整个Agent执行链路？

Trace ID 在入口生成，通过 **上下文传播、Span 层级和异步关联** 贯穿模型、Planner、Tool、Memory 与下游服务。

1. **入口创建**：Gateway 或 Host 创建根 Trace、根 Span 和任务 ID。Trace ID 标识一次执行，任务 ID 用于跨重试与续跑。
2. **同步传播**：模型、Router、Planner、Executor、HTTP、数据库和 MCP 创建子 Span，传递 `traceparent`、Deadline 与租户，禁止重新生成孤立 Trace。
3. **异步传播**：队列和回调将 Trace Context 写入消息头；消费者创建子 Span，无法保持父子关系时用 Span Link，并保存任务与 Trace 映射。
4. **日志审计**：日志、指标 Exemplars、审批、幂等记录和错误包含 Trace ID；敏感参数脱敏，高风险与错误轨迹强制保留。

| 标识 | 作用范围 | 主要用途 |
|---|---|---|
| Trace ID | 一次端到端执行 | 链路关联 |
| Span ID | 单个步骤 | 父子与耗时分析 |
| Task ID | 逻辑任务及重试 | 断点续跑 |
| Idempotency Key | 单个业务操作 | 防重复副作用 |

监控链路完整率、孤立 Span 和上下文丢失率，并通过 HTTP、队列和 MCP 集成测试验证。

**历史别名：** `GOV-172`。

**相关知识点：** Trace ID、Span ID、Task ID、traceparent、Context Propagation、Span Link、Exemplar、采样。

### 11. 多租户场景下如何防止侧信道攻击（side-channel attack）？

多租户侧信道防护应减少 **CPU 缓存、内存、计时器、共享存储和资源竞争** 的可观测性，并对高敏租户采用更强物理或虚拟隔离。

1. **租户分级调度**：普通任务可共享加固节点，高敏、竞争对手或包含密钥的任务进入独立节点池、核心或微虚机；避免将高低信任租户调度到同一宿主，节点标签与策略不可由用户伪造。
2. **计算与计时隔离**：限制高精度计时器、性能计数器和硬件调试接口，禁用不必要的共享内存；对敏感工作负载使用 CPU pinning、核心独占或禁用 SMT，降低缓存与分支预测侧信道。
3. **资源与存储隔离**：使用独立 cgroup、配额、I/O 队列和网络限速，防止通过资源争抢推断其他租户负载；临时卷、内存页、快照与镜像可写层在复用前安全清理，缓存键包含租户。
4. **更新与检测**：及时修补 CPU 微码、内核和虚拟化层，启用可用的推测执行缓解措施；监控异常高频计时、缓存探测、性能计数器访问和资源抖动，发现后隔离宿主。

| 防护方式 | 安全性 | 成本 |
|---|---|---|
| 共享容器加固 | 中等 | 密度高 |
| 微虚机+调度隔离 | 较高 | 内存与运维增加 |
| 独占节点/核心 | 高 | 利用率低 |
| 禁用SMT | 降低同核攻击 | 吞吐下降 |

侧信道无法仅靠应用权限完全消除，应根据数据敏感度权衡隔离成本，并通过跨租户残留与泄漏测试持续验证。

**相关知识点：** 侧信道、CPU Cache、SMT、CPU Pinning、微码、独占节点、资源竞争、残留清理。
<a id="tool-096"></a>
### 12. 什么场景适合用 LangChain，什么场景适合自研 Agent 框架？

选择标准不是功能多寡，而是**业务差异化程度、控制要求、团队能力与全生命周期成本**：通用能力和快速验证优先LangChain，关键链路需要精确语义与长期治理时才考虑自研。

1. **适合LangChain**：原型验证、RAG、常规工具调用、多模型试验及连接器密集的应用。它能缩短集成周期，并借助LangGraph表达有状态流程，适合需求仍在探索且可接受框架抽象的团队。
2. **适合自研**：核心Agent平台、强监管业务、极致低延迟或高吞吐场景，以及需要确定性调度、自定义权限、精细成本核算、特殊记忆语义和跨语言运行时的系统。此时框架默认行为可能难以审计或优化。
3. **推荐路径**：先用成熟组件验证业务闭环，稳定后识别真正的差异化模块；保留模型、工具、记忆和追踪的内部接口，逐步替换编排内核，不应一次性重写所有连接器。

| 维度 | LangChain | 自研框架 |
|---|---|---|
| 上线速度 | 快 | 慢 |
| 控制与定制 | 受抽象约束 | 高 |
| 初期成本 | 低 | 高 |
| 长期风险 | 版本与框架耦合 | 维护与人才风险 |

决策前应以同一任务集比较成功率、P95延迟、Token成本、可观测性、故障恢复和升级工作量。若只是封装模型API或改写已有通用组件，自研通常没有收益；若关键策略长期被框架限制，则应采用“通用组件复用、核心编排自持”的混合模式。

**相关知识点：** Build vs Buy、LangGraph、适配器层、RAG、确定性编排、可观测性、总拥有成本、渐进式替换。
<a id="tool-099"></a>
### 13. Agent 的任务编排是用状态机、DAG 还是 Planner？

三者不是互斥选项。企业Agent通常采用**状态机控制生命周期、DAG承载可预测依赖、Planner处理开放式分解**的分层混合架构，并以确定性控制层约束Planner。

1. **状态机**适合步骤有限、转移规则清晰、需要审批、暂停、恢复和补偿的流程。它可验证、易审计，但面对动态任务时状态数量容易膨胀。
2. **DAG**适合依赖明确、可并行的批处理、检索、分析和多模型流水线。其调度与重试高效，但原生不擅长循环、长期交互和运行时改变拓扑。
3. **Planner**适合目标开放、路径事先未知的研究、诊断和复杂工具选择。灵活性最高，但存在幻觉步骤、循环、成本失控及不可复现问题。
4. **落地方式**：外层状态机定义接收、规划、执行、验证、审批和结束；单阶段内用DAG并行；仅在受限节点调用Planner。每一步设置工具白名单、预算、最大深度、终止条件和结果验证。

| 方案 | 确定性 | 动态性 | 典型用途 |
|---|---|---|---|
| 状态机 | 高 | 低 | 业务事务、审批 |
| DAG | 高 | 中 | 并行依赖任务 |
| Planner | 低 | 高 | 开放目标探索 |

选型应依据流程可预知度、副作用风险、并行需求与恢复要求，而非追求“智能”。涉及资金、权限或外部写入时，应优先固定路径和人工确认；Planner输出只作为计划提案，必须经过策略与可执行性校验。

**相关知识点：** 有限状态机、DAG、Planner、Workflow、Human-in-the-loop、检查点、补偿、预算控制、计划验证。
<a id="tool-101"></a>
### 14. 如何设计 Agent 的 Memory 模块？

Agent Memory应是**按作用域分层、可检索、可更新、可遗忘且受权限控制的状态系统**，不能简单等同于把全部历史对话写入向量库。

1. **分层建模**：工作记忆保存当前任务状态和最近交互；情景记忆记录带时间的事件与执行结果；语义记忆沉淀稳定事实、偏好和规则；程序性记忆保存可复用Skill。不同层采用不同生命周期。
2. **写入治理**：先抽取候选事实，再进行来源校验、去重、冲突检测、敏感分类和置信度评估；记录主体、来源、时间、有效期与版本。重要事实需用户确认，禁止模型任意写入长期记忆。
3. **检索策略**：依据用户、租户、任务和权限过滤后，结合关键词、向量相似度、时间衰减、重要度及重排序选取内容，并控制注入Token预算；检索结果仍按不可信上下文处理。
4. **更新与删除**：采用追加事件加物化视图，支持更正、过期、合并、用户查看与删除；多租户必须物理或逻辑隔离，并对访问全程审计。

| 类型 | 内容 | 典型存储 |
|---|---|---|
| 工作记忆 | 当前步骤、临时变量 | 状态库/缓存 |
| 情景记忆 | 历史事件与结果 | 事件库 |
| 语义记忆 | 事实、偏好、规则 | 关系库+向量索引 |
| 程序性记忆 | 流程与Skill | 版本化仓库 |

验收指标包括记忆命中率、事实正确率、冲突率、过期命中率、检索延迟和隐私删除完成率；还需通过“无记忆基线”确认记忆确实提升任务效果。

**相关知识点：** 工作记忆、情景记忆、语义记忆、程序性记忆、时间衰减、重排序、TTL、事件溯源、隐私删除。
<a id="tool-103"></a>
### 15. 如何做上下文窗口和 Token 成本控制？

控制上下文与Token成本的核心是**按任务价值分配预算，只注入完成当前决策所需的最小高质量信息**，同时保证关键约束不因压缩而丢失。

1. **预算前置**：按租户、任务和阶段设置输入、输出、工具返回、重试与总成本上限；调用前用Tokenizer估算，超限时拒绝、降级模型或缩小任务，而不是依赖模型自行节省。
2. **上下文分层**：系统规则与安全约束固定保留；近期对话使用滑动窗口；较早内容结构化摘要；知识通过RAG按需检索；大工具结果先过滤、聚合或保存为引用，不直接回填全文。
3. **提升有效密度**：对文档合理切块、去重并重排序，限制Top-K；使用结构化状态替代重复自然语言，缓存稳定前缀和检索结果，简单步骤路由到小模型，复杂步骤再升级。
4. **防止失真**：摘要保留事实、决策、未完成事项、来源和不确定性，关键字段单独持久化；压缩后执行一致性检查，重要任务可回查原文。

| 方法 | 节省来源 | 主要风险 |
|---|---|---|
| 滑动窗口 | 删除旧对话 | 丢失远期依赖 |
| 摘要 | 压缩历史 | 事实漂移 |
| RAG | 按需注入 | 召回遗漏 |
| 模型路由 | 降低单价 | 小模型能力不足 |

线上应按任务记录输入输出Token、缓存命中率、单次成功成本及超限率，并用“成本—质量”曲线选择预算；仅降低Token而导致重试增加，可能使总成本更高。

**相关知识点：** Context Engineering、Tokenizer、滑动窗口、结构化摘要、RAG、重排序、Prompt Caching、模型路由、Token预算。
<a id="tool-107"></a>
### 16. 如何保证 Agent 输出结果可靠？

Agent输出无法靠单次模型调用“保证”正确，可靠性来自**证据约束、分层验证、风险匹配和持续评测**；风险越高，越应由确定性系统或人工作最终裁决。

1. **输入与证据**：明确任务边界、时间范围和输出Schema；通过可信数据源检索，保留来源、版本和引用位置。检索内容视为不可信数据，防止提示词注入改变系统规则。
2. **生成约束**：要求区分事实、推断与未知，缺少证据时拒答或请求补充；使用结构化输出、枚举和范围限制降低格式及参数错误，但不把格式正确等同于事实正确。
3. **结果验证**：语法由Schema校验，数值由程序复算，业务规则由规则引擎检查，事实与引用进行一致性验证。可用独立模型做补充审阅，但不能把“模型互相同意”当作真值。
4. **风险处置**：低风险内容抽检，高风险建议展示证据并人工确认；写操作先dry-run，再鉴权、审批和幂等执行。失败时降级到搜索结果、模板或人工服务。

| 方法 | 能发现的问题 | 局限 |
|---|---|---|
| 结构化输出 | 格式、类型错误 | 不验证事实 |
| RAG与引用 | 无依据回答 | 依赖召回质量 |
| 规则/程序校验 | 明确约束错误 | 覆盖有限 |
| 人工复核 | 复杂高风险问题 | 成本与时延高 |

上线前建立带标准答案和风险标签的评测集，线上监控正确率、引用支持率、拒答率、工具误调用率及人工纠正率，并对模型、提示词和知识库版本做回归。

**相关知识点：** Grounding、RAG、Schema校验、引用一致性、规则引擎、Human-in-the-loop、校准、回归评测、拒答策略。
<a id="tool-116"></a>
### 17. 如何评估工具调用质量？

工具调用质量应分解为**选得对、参数对、执行对、结果被正确利用且代价可接受**，不能只统计接口是否返回成功。

1. **离线任务集**：从真实场景构造含标准工具、参数、调用顺序、期望结果和“不应调用”样例的基准集，覆盖歧义请求、缺失信息、权限拒绝、提示词注入及工具故障。
2. **分层指标**：工具选择计算准确率、召回率及误调用率；参数衡量Schema一次通过率、字段准确率；执行衡量成功率、超时率、重试率和副作用正确率；端到端衡量任务完成率与结果正确性。
3. **效率与安全**：记录平均调用数、重复调用率、P95延迟、Token和工具费用；安全侧统计越权拦截率、高危操作确认率、敏感数据外传和幂等冲突。成功但多次绕路也属于低质量。
4. **线上闭环**：按模型、提示词、工具版本和租户切片监控，以用户纠正、人工接管和业务结果作为反馈；版本升级先回归、影子和灰度，发现退化自动回滚。

| 层次 | 核心指标 | 典型问题 |
|---|---|---|
| 决策 | 选择准确率 | 选错或不该调用 |
| 参数 | 一次通过率 | 字段缺失、语义错误 |
| 执行 | 成功率、幂等性 | 超时、重复副作用 |
| 任务 | 完成率、成本 | 局部成功但目标失败 |

评测需同时包含确定性断言、规则评分和人工盲评，并对高风险错误赋予更高权重，避免总体平均分掩盖严重事故。

**历史别名：** `GOV-053`。

**相关知识点：** 工具选择准确率、参数通过率、端到端成功率、误调用率、成本质量比、影子测试、灰度发布、风险加权评测。

### 18. 如何限制代码执行的CPU、内存和网络访问？

代码执行必须放入**强隔离沙箱并实施资源硬配额与默认拒绝网络策略**，限制应由内核或虚拟化层强制，不能依赖代码自觉或语言运行时。

1. **CPU控制**：用cgroups设置CPU quota、shares和进程数，配置墙钟超时；到期先优雅终止，再强制杀死进程组，防止子进程遗留。
2. **内存控制**：设置memory.max、交换空间和OOM策略，限制文件描述符、线程及临时磁盘；任务退出后销毁环境并核对回收。
3. **网络控制**：独立Network Namespace，默认拒绝入站与出站，仅经代理放行目标；校验DNS，拦截私网和元数据地址，限制速率与响应大小。
4. **隔离加固**：非特权用户、只读根文件系统、最小capabilities、seccomp和临时目录；高风险代码使用轻量虚拟机或独立节点池。

| 层级 | 主要机制 | 防护目标 |
|---|---|---|
| 进程 | rlimit、进程组 | 线程/句柄耗尽 |
| 容器内核 | cgroups、seccomp | 资源滥用、危险系统调用 |
| 网络 | Namespace、Egress Proxy | 扫描与数据外传 |
| 虚拟机 | 独立内核 | 降低逃逸影响 |

记录超限与网络审计事件，并通过资源耗尽、fork bomb、DNS重绑定及逃逸样例验证。

**相关知识点：** cgroups、Network Namespace、seccomp、Capabilities、只读文件系统、Egress Proxy、OOM、轻量虚拟机、资源回收。
<a id="tool-124"></a>
### 19. 如何判断一个Agent操作属于低风险、中风险还是高风险？

风险等级应由**发生概率、影响严重度和控制可恢复性**共同决定，并以确定性规则计算；模型可提供语义标签，但不能自行决定是否放行。

1. **评估维度**：识别数据敏感度、读写类型、目标环境、影响人数或资源量、金额、权限提升、外部传播、可逆性及合规约束；再叠加用户身份、设备、时段、行为异常和工具可信度等上下文。
2. **分级标准**：低风险通常是授权范围内、影响小、可逆且无敏感数据的只读或草稿操作；中风险存在有限写入、外发或个人敏感信息，但可预览和恢复；高风险涉及生产、资金、批量删除、跨租户、密钥、不可逆动作或重大合规责任。
3. **风险合成**：可采用“严重度×可能性×暴露度”评分，但设置硬规则覆盖总分，例如越权和关闭审计直接判为禁止。多个低风险步骤组合可能形成高风险，应评估整条计划的累计影响。
4. **控制映射**：低风险自动执行并抽检；中风险要求确认、限额或二次校验；高风险需指定角色审批、双人复核、dry-run和回滚；不可接受风险硬拦截。

| 等级 | 典型特征 | 默认控制 |
|---|---|---|
| 低 | 小范围、可逆、非敏感 | 自动+审计 |
| 中 | 有限副作用或敏感性 | 确认+限额 |
| 高 | 大范围、不可逆、关键系统 | 审批+强护栏 |
| 禁止 | 越权或违反硬策略 | 直接拒绝 |

应基于事故、误报和审批数据定期校准阈值，所有评级保留特征、规则版本与决策理由。

**验证指标：** 工具选择准确率、调用成功率、参数错误率、P95 延迟和失败恢复率。

**相关知识点：** 风险矩阵、严重度、可能性、暴露度、硬规则、组合风险、动态风控、风险控制映射、可解释决策。

### 20. Rule Routing和LLM Routing如何选择？

选择原则是**确定性、合规和高风险约束用Rule Routing，语义复杂且边界难枚举的意图识别用LLM Routing**；生产系统通常采用规则前置、LLM补充的混合路由。

1. **Rule Routing**：基于用户、字段、关键词、权限、环境、额度和状态等显式条件，结果稳定、低延迟、可审计，适合硬策略、固定命令和少量清晰类别；缺点是规则随场景增长而膨胀，难处理表达多样性。
2. **LLM Routing**：利用语义理解在相似Skill间判断，可处理自然语言、上下文和新表达，适合开放入口与长尾意图；缺点是概率性、成本、延迟及版本漂移，需要候选约束和置信门控。
3. **混合架构**：先用规则完成权限、风险、环境和明确指令过滤；再以检索缩小候选，由LLM输出受限Skill ID及理由；最后规则验证输入Schema和前置条件。低置信或候选接近时澄清。
4. **演进方式**：初期类别少时规则优先；积累标注后引入语义路由。高频稳定意图可从LLM路径下沉为规则，长尾保留LLM，并通过线上反馈持续校准。

| 维度 | Rule Routing | LLM Routing |
|---|---|---|
| 确定性 | 高 | 较低 |
| 语义泛化 | 弱 | 强 |
| 延迟成本 | 低 | 较高 |
| 可审计性 | 强 | 需额外解释与记录 |

评估不能只看分类准确率，还要比较拒选率、严重误路由、延迟、成本和规则维护工时；安全硬规则不得被LLM结果覆盖。

**相关知识点：** 规则路由、语义路由、混合路由、候选约束、置信门控、拒选、规则下沉、模型漂移、Policy Engine。

### 21. DAG 编排和链式编排有什么区别？

**链式编排是单一路径的线性依赖，DAG编排是无环的多分支依赖图**。步骤少且严格顺序时选链式；需要并行、汇聚和复杂依赖时选DAG。

1. **结构**：链式流程中前一步输出直接成为后一步输入，理解与调试简单；DAG允许一个节点有多个上游或下游，可表达并行查询、条件分支和结果汇聚，但要求显式定义依赖。
2. **性能**：链式总时延近似各步骤累加，资源利用有限；DAG可并行执行无依赖节点，关键路径决定理论最短时间。并行也会增加并发、限流和成本压力。
3. **失败处理**：链式失败点明确，通常从该步骤重试；DAG需区分节点、分支和汇聚失败，维护就绪状态、部分结果与依赖传播，恢复调度更复杂。
4. **适用边界**：DAG不能天然表达无限循环和长期交互，需通过有界展开、子图或外层状态机补充；链式若大量使用条件跳转，实质已成为图，应显式建模。

| 维度 | 链式编排 | DAG编排 |
|---|---|---|
| 拓扑 | 线性 | 分支、并行、汇聚 |
| 调度复杂度 | 低 | 较高 |
| 执行时延 | 易累加 | 可缩短至关键路径 |
| 恢复粒度 | 单一步骤 | 节点与依赖状态 |
| 典型场景 | 提取→生成→校验 | 多源检索、并行分析 |

选型还需考虑副作用顺序、数据一致性和可观测性；即使采用DAG，写操作也可能因业务约束必须串行。

**相关知识点：** DAG、Pipeline、关键路径、拓扑排序、并行执行、汇聚节点、检查点、外层状态机、副作用顺序。

### 22. 如何避免错误经验被学习？

避免错误经验被学习，需要把**运行日志、候选经验和已发布Skill严格分层**，通过来源可信度、结果验证、反例测试与人工门禁阻断污染。

1. **数据分层**：原始轨迹进入只读数据湖，不能直接修改Memory或Skill；候选经验带来源、时间、模型、工具、结果、用户身份和置信度。未验证内容统一标记为观察数据。
2. **质量筛选**：仅采纳目标完成且通过外部验证的轨迹，排除模型自评成功、用户未确认、人工暗中补救、测试绕过、循环重试和越权结果；高风险领域要求权威系统或专家给出标签。
3. **去偏与冲突**：跨多个用户、时间和环境验证同一模式，降低单个异常样本权重；检测与SOP、政策、现有Skill和事实库的冲突。新证据不能静默覆盖高可信规则，应建立版本与人工裁决。
4. **验证发布**：从轨迹抽取候选后，在独立集、反例、边界和对抗样例上重放；执行安全、权限、幂等与故障测试，经领域及安全评审后灰度。
5. **持续纠错**：保留数据与Skill血缘，线上出现退化可定位来源、撤销版本和删除污染样本；用户反馈仅作为弱信号，需聚合验证。

| 信号来源 | 默认可信度 | 用途 |
|---|---|---|
| 模型自评 | 低 | 候选排序 |
| 用户反馈 | 中低 | 弱监督 |
| 确定性测试/业务结果 | 高 | 质量标签 |
| 专家和权威规则 | 高 | 高风险门禁 |

**相关知识点：** 数据血缘、弱监督、来源可信度、经验污染、冲突检测、独立评测、人工门禁、版本撤销、反例测试。

### 23. BM25和Embedding检索如何融合？

BM25与Embedding应采用**多路召回、分数归一或排名融合、统一重排**：前者擅长精确术语，后者擅长语义泛化，融合能降低单一路径漏召回。

1. **召回前过滤**：先按租户、权限、状态、环境和风险过滤，避免未授权候选进入索引；查询保留原文、规范化实体和必要同义词。
2. **并行召回**：BM25从名称、标签和描述取Top-N，Embedding从目标、条件与示例取Top-N；保留分数、命中字段与排名，合并去重。
3. **融合方法**：无法可靠比较不同分数尺度时使用RRF，按名次贡献合并；有标注数据时可对分数归一后加权，权重按查询类型动态调整，例如含精确错误码时提高BM25权重。
4. **精排与门控**：Reranker读取请求、仓库/会话上下文和候选契约，综合语义、专用度、质量、成本与风险输出排序；Top-1低于阈值或与Top-2接近则澄清或拒选。
5. **评测调优**：测各通道Recall@K、融合增益、MRR/NDCG、延迟和成本；按术语型、语义型及无匹配查询切片。

| 融合方式 | 优点 | 局限 |
|---|---|---|
| RRF | 无需校准分数 | 难利用分数幅度 |
| 归一化加权 | 可解释、灵活 | 需稳定校准 |
| 学习融合 | 可优化业务目标 | 依赖高质量标签 |

**相关知识点：** BM25、Embedding、Hybrid Search、RRF、Score Normalization、Query Routing、Reranker、Recall@K、NDCG。

### 24. Rerank模型如何设计？

Skill Reranker应在小候选集学习**请求—上下文—Skill的相关性与业务代价**，输出可校准分数；硬约束在重排前完成。

1. **输入表示**：包含用户目标、实体、代码/会话上下文、候选Skill的目标、条件、契约和示例；截断时优先契约与反例，不传完整实现。
2. **模型选择**：Cross-Encoder精度高，适合Top-K精排；特征模型延迟低；LLM Judge语义强但成本高，适合少量高价值候选。
3. **特征与目标**：融合BM25、向量分数、专用度、Schema兼容、成功率、成本和风险；可采用分类、成对偏好或列表排序，高风险误选提高权重。
4. **数据构建**：正样本来自专家和验证成功，困难负样本来自相似错误Skill、用户改选与误路由；按时间切分，纠正曝光偏差。
5. **门控与评测**：校准Top-1及Margin，低置信澄清或拒选；评估MRR、NDCG、准确率、严重误选、ECE、延迟与成本。

| 模型 | 优点 | 适用 |
|---|---|---|
| Cross-Encoder | 细粒度准确 | 常规精排 |
| 特征排序模型 | 快、可解释 | 大规模低延迟 |
| LLM Judge | 复杂推理强 | 高价值小候选集 |

线上以影子和A/B验证任务成功率，并监控数据与模型漂移。

**历史别名：** `CTX-138`。

**相关知识点：** Cross-Encoder、Pairwise Ranking、Listwise Ranking、困难负样本、曝光偏差、分数校准、Margin、NDCG、ECE。
