### 多源信息融合时，知识库、API和用户历史信息冲突怎么办？（千问二面）

**多源冲突不能用固定的“API永远优先”规则处理，应依据事实类型、来源权威性、时间、版本和用户确认状态进行可解释裁决。**

1. 融合前把知识库、API和用户历史标准化为claim，包含subject、value、source、observed_at、valid_time、version、confidence和权限。先区分版本差异、不同时间均成立、偏好变化、单位或口径不一致及真正互斥。经过单位换算、实体归一和有效期对齐，很多表面冲突可消除。

2. **优先级应按字段定义，而不是按数据源整体定义**。库存、价格和订单状态以授权API为准；制度及产品规则以已发布知识库为准；称呼、偏好和个人目标以用户最近确认的记录为准。权威性相同时优先时间更近、版本更高且证据完整者，但用户历史不得覆盖法律、安全或权限规则。

3. 无法裁决时，保留双方的值、来源、时间和不确定性，要求用户确认或人工审核，禁止静默选择。结果写入Conflict Log，记录采用值、规则版本、操作者和否决证据；用户纠正时追加新版本。监控冲突率、自动裁决率、纠错率、来源过期率和错误引用率，并用高风险样本回归。

**相关知识点：** Claim Normalization、Source Authority、Valid Time、Conflict Resolution、数据口径、用户确认、Conflict Log、版本化事实。

### 如何避免知识污染？

**避免知识污染需要在采集、解析、索引、检索和生成各层建立来源、版本、权限与可信度控制，未经验证的数据不能进入权威知识域。**

1. 采集只接收白名单源，校验签名、哈希、发布主体和时间；文档经过恶意指令、敏感信息、重复及格式检测后进入隔离区。审核或质量门通过后才发布。Chunk保存tenant、source、authority、version、valid_time、ACL和审核状态，禁止匿名内容覆盖正式制度。

2. **向量相似度不能作为可信度证明，检索排序必须同时考虑来源权威性、版本和时效**。被撤回、过期或superseded的文档退出默认召回；向量、BM25、缓存和对象存储使用一致ACL，避免索引串库。外部文档中的指令均视为数据，以明确边界注入，不能改变System规则或自动触发高风险工具。

3. 发布使用影子索引，验证数量、哈希、权限、重复率和检索效果后切换，异常回滚。用户反馈、模型输出和记忆不得直接回写知识库，必须进入候选队列。全链路记录写入者、来源、审核和索引版本，监控未授权写入、跨租户命中、过期命中、注入检出率及错误引用率，并定期红队测试。

**相关知识点：** Source Provenance、Quarantine、Content Hash、ACL、Prompt Injection、Supersedes、影子索引、审核工作流、知识审计。

### 双路召回架构应该如何设计？

**双路召回应并行使用稀疏与稠密检索，再经分数校准、候选融合与重排，兼顾精确词项和语义改写。**

| 通道 | 优势 | 典型弱点 |
| --- | --- | --- |
| BM25稀疏召回 | 编号、专名、精确词项 | 同义表达召回弱 |
| Embedding稠密召回 | 语义和改写匹配 | 可能发生语义漂移 |

1. Query Processor完成纠错、实体、时间和意图抽取，生成两路查询；服务端先按tenant、ACL、版本和有效期过滤，再并行请求倒排与ANN索引。两路设置独立Top-K、超时和熔断，任一路失败可用另一路降级；请求携带相同index_version，避免版本混读。

2. BM25分数与余弦相似度不可直接相加，可用RRF按名次融合，或按查询类型归一化并学习权重；以document_id、chunk_id及哈希去重。**双路召回解决候选覆盖问题，Reranker负责判断候选是否真正相关。**Cross Encoder结合实体、时效和来源权威性选出Top-N。

3. K值与权重依据查询类型、分数断层和Token预算调整，编号类提高稀疏权重，自然语言改写提高稠密权重。离线分别测两路Recall@K、合并增益、MRR与NDCG，线上监控去重率、单路超时、P95、重排成本和成功率；消融实验验证双路是否带来净收益。

**相关知识点：** BM25、Embedding、ANN、Hybrid Retrieval、RRF、Score Calibration、Cross Encoder、动态Top-K、熔断降级、消融实验。

### 向量检索和关键词检索如何结合？

**向量和关键词检索应并行召回、校准融合、统一重排，利用前者的语义泛化和后者的精确词项能力互补。**

| 方式 | 优势 | 局限 |
| --- | --- | --- |
| 关键词/BM25 | 编号、专名、错误码精确 | 同义改写召回弱 |
| 向量/Embedding | 语义、意图和近义表达 | 可能发生语义漂移 |

1. Query Processor执行纠错、实体、时间和意图抽取，保留关键词并生成Embedding查询；服务端先按tenant、ACL、版本和有效期过滤，再并行请求倒排与ANN索引。编号、产品名和代码词提高BM25配额，自然语言改写和描述性问题提高向量配额。

2. BM25分数和余弦相似度量纲不同，不能直接相加；可用RRF按名次融合，或按查询类型归一化并学习权重。候选按document_id、chunk_id和哈希去重，再由Cross Encoder结合实体、时效、来源和上下文重排。**混合召回负责找全，Reranker负责排准，二者职责不能互相替代。**

3. 两路设置独立Top-K、超时和熔断，单路故障可降级；Top-N受Token预算和阈值限制。离线评测单路Recall@K、融合增益、MRR及NDCG，线上监控重合率、边际贡献、无结果率、P95、成本和任务成功率，并用消融实验避免无效复杂度。

**历史别名：** `CTX-110`、`CTX-136`。

**相关知识点：** BM25、Embedding、ANN、Hybrid Retrieval、RRF、Score Normalization、Cross Encoder、动态权重、消融实验、NDCG。

### Skill 匹配是在 Prompt 组装之前还是之后？

**Skill匹配应在最终Prompt组装之前完成：先用最小上下文识别意图并选取Skill，再把命中的Skill指令、证据和预算注入最终Prompt；执行中可依据新状态二次匹配。**

1. 路由阶段使用System安全边界、当前问题、必要状态、权限和Skill元数据；根据名称、描述、触发规则、输入要求与能力约束生成候选，再以规则、Embedding或分类模型选择。若把所有Skill全文加入Prompt再匹配，会浪费Token、引入冲突并使无关Skill干扰识别。

2. 命中Skill后，系统读取完整指令与引用，确定工具、流程、格式和验证，再由Prompt Builder按优先级和预算组装最终消息。**“组装之前”指最终执行Prompt之前，不代表路由没有上下文；路由本身仍需小而稳定的识别输入。**未命中、低置信或多个Skill冲突时应回退、重排或澄清。

3. 工具结果改变任务类型时可二次匹配，但须保留状态、避免重复初始化，并记录skill_id、version、分数与切换原因。评测覆盖单Skill、多Skill、无Skill、错误触发和嵌套任务，指标包括匹配准确率、任务成功率、额外Token、路由P95与冲突率；Skill升级应做版本化回归和回滚发布。

**相关知识点：** Skill Router、意图识别、两阶段Prompt、候选召回、路由置信度、Prompt Builder、二次匹配、Skill版本、回退策略。
