### 介绍一下Harness Engineering（上下文工程）（附加专题）

**Harness Engineering通过运行环境、反馈机制和工程约束，使Agent在长周期任务中稳定执行、验证结果并从故障点恢复。**

1. 其核心是把模型置于可控闭环：状态机维护目标和计划；工具层通过Schema及沙箱限制动作；Checkpoint保存恢复点；Validator判断产物是否合格；Trace记录调用和结果。模型提出下一步，Harness执行并返回Observation。

2. **高质量Harness应遵循渐进式披露和证据驱动原则**。入口仅提供任务地图、关键规则和能力索引，按需读取代码或文档；工具返回结构化结果、来源与错误。代码Agent还应具备可复现环境、测试、差异审查和回滚机制。

| 技术 | 优化对象 | 典型产物 |
| --- | --- | --- |
| Prompt Engineering | 指令表达 | 模板、示例、输出格式 |
| Context Engineering | 本轮可见信息 | 历史、记忆、检索证据 |
| Harness Engineering | Agent运行闭环 | 工具、状态、验证、恢复 |

3. 落地时先定义成功标准和禁止动作，再建设结构化工具、状态持久化、超时重试、幂等执行与人工接管；用长任务、工具异常、权限拒绝及中断恢复做回归。指标包含任务成功率、无效调用率、恢复成功率、P95时延和单位成功任务成本。

**相关知识点：** Agent Runtime、Context Engineering、渐进式披露、状态机、Checkpoint、Validator、沙箱、幂等、可观测性、人工接管。

### 如何理解Agent中的状态和上下文？（千问二面）

**Agent状态是跨步骤持久存在的权威事实，上下文是某次模型调用从状态、指令和外部证据中投影出的有限输入，两者是数据源与派生视图的关系。**

1. 状态描述执行位置，包括任务、步骤、目标、计划、变量、预算、工具回执、授权和Checkpoint，存于状态机或数据库。它必须一致、幂等、可恢复、可审计，即使未注入窗口也不能丢失；易变事实保存引用和版本。

2. 上下文回答“本轮需要看到什么”，由Context Builder从System规则、用户目标、任务状态、必要历史、RAG、Memory和Tool Result中筛选，并受Token预算约束。**上下文可以随步骤重建，状态必须在步骤之间延续**；模型只看到裁剪后的状态片段。

| 维度 | 状态 | 上下文 |
| --- | --- | --- |
| 性质 | 权威、可持久化数据 | 单次调用的输入视图 |
| 更新方式 | 校验后事务提交 | 每轮动态组装 |
| 主要约束 | 一致性、恢复、审计 | 相关性、可信度、Token |

3. Runtime读取状态，Context Builder只注入必需字段；模型返回动作后，Validator校验Schema、权限、前置条件和业务不变量，再以CAS或事务提交迁移。恢复时加载Checkpoint并重查易变事实，既防止模型输出污染权威状态，也避免裁剪导致进度丢失。

**相关知识点：** Agent State、Context Window、状态机、Checkpoint、Context Builder、派生视图、Validator、CAS。

### 如何实现跨会话任务状态恢复？

**跨会话恢复应依赖持久化状态和可重放事件，而不是拼接聊天记录；恢复点必须明确、版本一致且能验证外部副作用。**

1. 为任务分配task_id，状态对象保存目标、确认约束、计划版本、当前步骤、已完成项、待办、关键变量、产物引用、工具结果、错误和审批状态。每次迁移以event_id追加事件，并周期生成checkpoint；大文件存对象存储，状态只保留URI、哈希和版本。

2. 新会话以用户身份加载有效checkpoint，再重放后续事件，并核对代码版本、文件哈希、工具配置、权限和外部资源状态。**恢复的是已经确认的状态，不是模型对历史对话的猜测**。付款、发布、发送消息等副作用动作必须查询幂等键和外部结果，不能因本地状态缺失而重做。

3. Context Builder仅注入目标、硬约束、下一步、必要证据和最近错误，其余按需展开；状态Schema和计划变更使用版本迁移。并发恢复用乐观锁或租约防止双写。测试覆盖进程崩溃、重复事件、部分工具成功、权限变化和Schema升级，监控恢复成功率、状态偏差率、重复副作用率、时延及纠错率。

**相关知识点：** Task State、Checkpoint、Event Sourcing、Replay、幂等键、乐观锁、Schema Migration、Context Builder、状态机、Exactly-once Effect。

### 如何实现任务执行过程中的状态快照？

**任务状态快照应保存可恢复的最小完整状态，并与增量事件、外部副作用和代码版本关联，使Agent能从一致检查点继续执行。**

1. 快照Schema包含task_id、snapshot_id、计划版本、当前节点、已完成节点、待办、关键变量、产物引用、工具结果摘要、错误、审批状态、重试计数和创建时间。大文件、日志及工具原始响应放对象存储，快照只保存URI、内容哈希与版本；密钥不进入快照，敏感字段按租户密钥加密并执行ACL。

2. 在步骤完成、调用高风险工具前后、用户批准后及固定事件数或时间间隔触发快照。写入采用snapshot_id幂等键和乐观锁，先持久化状态事件，再原子更新latest_snapshot指针。**快照描述的是已确认状态，不能把未执行计划或模型猜测标记为已完成。**并发执行需记录分支和汇合水位。

3. 恢复时加载最新有效快照，校验Schema、代码、配置、文件哈希和权限，再重放其后的事件；对付款、发布、消息发送等动作查询外部幂等键，避免重复副作用。快照采用全量加增量组合，定期合并并按保留策略清理。测试覆盖崩溃、部分写入、重复事件、版本升级和对象缺失，监控快照成功率、恢复点目标、恢复时延及状态偏差率。

**相关知识点：** Snapshot、Checkpoint、Event Sourcing、Write-ahead Log、乐观锁、幂等键、增量快照、RPO、状态恢复、外部副作用。

### Planner 如何决定保留哪些上下文？

**Planner应针对当前计划节点保留目标、前置依赖、最新状态、直接证据和未决风险，其他信息通过索引按需展开。**

1. Planner将任务表示为目标、子任务DAG、依赖变量、完成条件和当前节点。固定System约束、验收标准与不可逆操作规则；当前节点只加载父节点输出、工具Schema、相关Memory或RAG、最近错误和资源状态。无后续依赖的细节转为摘要，原始产物存工作区并保留引用。

2. 每个片段标记scope、source、version、trust、depends_on、valid_until和token_count；先执行权限、版本和有效期过滤，再按任务依赖、相关性、权威性和唯一性排序。**“以后可能有用”不能成为永久保留理由，只有存在明确依赖边或高回退价值的信息才进入工作上下文。**未知依赖可保留目录或检索句柄，需要时再展开原文。

3. 每步更新Checkpoint，记录状态差异、产物URI、事实、错误和下一步，不携带完整轨迹；计划变更时按新DAG重算上下文。评测约束保持率、状态恢复率、错误继承率、无效Token占比和成功率，并做片段消融。缺少关键依赖时应重新检索或澄清，不能用摘要猜测。

**相关知识点：** Planner、任务DAG、前置依赖、Checkpoint、工作上下文、产物URI、上下文句柄、状态差异、片段消融、约束保持率。

### 多 Agent 协作时上下文如何共享？

**多Agent协作应共享结构化任务状态、必要证据和产物引用，不应广播各自完整对话、Prompt或隐藏推理。**

1. 协调器维护Shared Task Board，记录task_id、目标、子任务、owner、依赖、状态、产物URI、事实、风险和version。分派时只给Agent职责、输入契约、证据、工具权限和输出Schema；大型文件放工作区，通过引用读取。共享摘要携带source_agent、timestamp和confidence，便于验证。

2. Agent完成步骤后提交状态差异与产物清单，以event_id幂等发布；协调器用expected_version防止旧结果覆盖新状态。冲突事实保留来源并裁决。**共享内容必须按最小必要原则和Agent能力授权，能读取任务状态不等于能读取用户全部记忆或其他任务。**撤权及时失效缓存与令牌。

3. Agent的Prompt由自身System/Skill、当前子任务及授权片段组装，工具日志只传摘要、错误码和引用；细节按需回读。监控传播延迟、版本冲突、重复工作、越权拒绝、共享Token和成功率。故障测试覆盖Agent离线、消息乱序、恶意产物和协调器恢复，确保能从Task Board重建状态。

**相关知识点：** Shared Task Board、任务契约、状态差异、产物引用、事件幂等、乐观锁、最小必要授权、冲突裁决、上下文传播、状态重建。

### 多 Agent 系统中 Prompt 如何共享和传递？

**多Agent不应直接复制完整Prompt，而应通过结构化任务信封传递目标、约束、证据、状态和权限，每个Agent再按自身职责组装本地Prompt。**

1. 共享消息包含task_id、目标、输入、约束、已完成、未决事项、证据、截止时间、发送方、接收方、ACL和version；大文件只传artifact_ref。接收Agent验证Schema、身份、权限和版本后，将必要字段与自身System、Skill和工具组合，避免上游覆盖安全策略。

2. 共享事实进入版本化Blackboard，消息只携带引用；并发Agent提交带基线版本的补丁，由协调器检测冲突、合并或重试。**共享的是可验证状态和证据，不是Agent未验证的内部推断。**保留来源、置信度与有效期，敏感信息按最小权限裁剪，禁止跨租户广播。

3. Coordinator负责拆分、路由、汇总和终止，Agent输出结构化result、status、evidence、error与next_action；汇总时去重并解决版本冲突。Trace用task_id串联因果链。评测传递准确率、状态丢失率、冲突率、越权率、消息Token、重复工作和成功率，并测试超时、乱序及失败恢复。

**相关知识点：** Task Envelope、Coordinator、Blackboard、事件存储、artifact_ref、ACL传播、版本冲突、结构化结果、因果Trace、状态丢失率。
