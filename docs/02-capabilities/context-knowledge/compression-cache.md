# 上下文压缩与缓存

> 所属章节：[上下文与知识系统](README.md)｜本文件共 **44** 题。

<a id="ctx-008"></a>
### 1. 上下文是怎么构建的？怎么避免上下文过长或者信息污染？（百度Agent）

**上下文不是历史信息的简单拼接，而是Context Builder依据当前目标、指令优先级、证据质量和Token预算生成的最小充分输入。**

1. 先固定System与安全规则，再加入用户目标、硬约束、任务状态和计划，随后选择必要对话、工具结果、检索证据及长期记忆。片段携带来源、时间、版本、权限和内容类型，并以角色及标签隔离，防止把用户文本、外部文档或工具数据误当成系统指令。

2. 先为模型输出、工具参数和异常修复预留Token，再对历史、RAG、Memory和Tool Result设置上限。历史使用滑动窗口与滚动摘要；检索结果经过权限过滤、去重、重排和压缩；大型结果存入Artifact Store，仅注入当前步骤需要的字段及引用。**上下文质量取决于有效证据密度，不取决于窗口填充率**。

3. 防污染需处理无关、重复、过期、冲突和恶意内容：先校验权限与来源，再检查版本和时效；矛盾证据显式标注，外部指令仅作为数据。调用前由Context Validator检查约束缺失、证据重复和Token超限。线上监控输入Token、证据利用率、错误引用率、冲突率及任务成功率，并将失败样本加入回归集。

**相关知识点：** Context Builder、Token Budget、Prompt分层、滚动摘要、Contextual Compression、Artifact Store、Context Validator、Prompt Injection。

### 2. 动态Prompt和静态Prompt有什么区别？上下文是如何动态组装的？（DeepSeek二面）

**静态Prompt定义行为边界与输出契约，动态Prompt依据本轮任务选择状态、记忆、知识和工具结果，两者由Prompt Builder组合。**

1. 静态部分包括System身份、安全规则、工具协议和输出Schema，适合版本、审计和前缀缓存；不写用户数据或易变知识。动态部分包含目标、任务状态、会话摘要、Memory、RAG、Tool Result和Skill，按意图、权限、时效及Token预算选择。

| 类型 | 典型内容 | 主要治理 |
| --- | --- | --- |
| 静态Prompt | 身份、规则、契约 | 版本、缓存 |
| 动态Prompt | 状态、记忆、证据 | 权限、预算 |

2. 先固定System和安全策略，再加入用户问题、约束及任务状态，随后检索Memory和Knowledge，最后附加工具结果。区块使用明确角色、XML或JSON，并记录来源和版本。**外部文档与工具数据只能作为证据，不能提升为System指令**，以降低注入风险。

3. Prompt版本与模型、索引、Skill及实验组写入Trace。超预算时保留规则、目标、状态和直接证据，删除重复历史、低相关记忆及冗长字段；长内容用摘要和Artifact引用。离线评估指令遵循、事实正确性和注入防护，线上观察成功率、Token、缓存命中及P95。

**相关知识点：** Static Prompt、Dynamic Prompt、Prompt Builder、Prompt分层、版本管理、Prompt Injection、Prefix Cache。

### 3. 上下文窗口总Token是多少？压缩机制（DeepSeek二面）

**上下文窗口没有统一Token数，必须以所选模型的官方限制为准；工程预算还要从总窗口中扣除预期输出、工具参数和安全余量。**

1. 总窗口计算System、Developer、用户消息、历史、RAG、Memory、Tool Call、Tool Result及模型输出。可用输入预算等于窗口上限减去最大输出、工具与结构化输出预留、重试和安全余量。不同模型和Tokenizer会改变中英文、代码及JSON消耗，上线前应使用对应Tokenizer计算，不能按字符估算。

2. **窗口容量大不等于所有历史都应保留**。优先级通常是系统与安全规则、当前问题、硬约束、最新状态、直接证据、必要工具结果、近期对话、长期记忆和背景材料。先删除低相关、重复、过期内容；数字、否定、截止时间、责任主体和错误信息应保留原文。

3. 压缩分四层：确定性裁剪删除重复日志；抽取式压缩保留Query相关证据；滚动摘要把旧对话转成目标、决策、待办和事实；Contextual Compression压缩检索文档并保留source_id。摘要应版本化，低置信或冲突时回退原文。监控输入Token、压缩率、保真度、首Token延迟和任务成功率，避免损失关键约束。

**相关知识点：** Context Window、Tokenizer、Token Budget、输出预留、滚动摘要、抽取式压缩、Contextual Compression、Lost in the Middle、保真度。

### 4. 长对话+大量检索文档，上下文过长送入模型出现超时、回答冗余，怎么优化处理（Agent中级）

**长对话叠加大量RAG文档时，应分别压缩历史和检索证据，再由统一Token预算选择最小充分上下文，避免把超时交给模型承担。**

1. 对话侧把旧消息转换为结构化摘要，保留目标、约束、事实、决策、待办和近期交互；原文外置并按需回溯。检索侧先执行ACL、版本和时间过滤，再用Reranker选候选，按文档、原文区间和哈希去重，相邻Chunk合并，避免重复占用窗口。

2. **历史摘要解决时间连续性，Contextual Compression解决证据冗余，两者不能混成无边界摘要**。候选文档只抽取相关句子、表格行或代码段，并保留source_id和引用；数字、否定、条件及冲突不得模糊改写。证据不足时重检或拒答，不能扩大Top-K并把噪声送入Prompt。

3. Prompt Builder先预留输出，再按System规则、问题、约束、状态、直接证据、必要历史和背景分配预算；每类设置上限，超限时按相关性和可信度裁剪。稳定前缀使用Prompt Cache，大结果改为Artifact引用。监控输入Token、重复率、压缩保真度、首Token延迟、超时率、冗余率、引用准确率和成功率。

**相关知识点：** Rolling Summary、Reranker、Contextual Compression、Token Budget、证据去重、Artifact Store、Prompt Cache、超时率。

### 5. 如果上下文窗口不够，优先保留哪些信息？为什么？（百度Agent）

**窗口不足时应优先保留决定模型行为和当前任务正确性的内容，历史背景与低相关材料只能在剩余预算中按需加入。**

1. 第一优先级是System与安全规则、当前问题、业务约束和输出契约，删除它们会改变任务或产生越权。第二优先级是最新状态、待办、工具错误和直接证据，它们决定下一步是否正确。关键数字、否定、截止时间、权限和用户更正应保留原文。

| 优先级 | 内容 | 保留原因 |
| --- | --- | --- |
| 最高 | 系统规则、当前目标、硬约束 | 定义行为边界 |
| 高 | 最新状态、直接证据、错误 | 决定当前决策 |
| 中 | 近期对话、已验证记忆 | 保持连续性 |
| 低 | 重复历史、背景材料、完整日志 | 可摘要或按需加载 |

2. **保留顺序由指令层级、任务相关性、可信度和时效共同决定，而不是简单选择最近消息**。旧但有效的合同约束高于最新寒暄，实时API通常高于过期记忆。冲突时保留双方来源和时间，不能静默删除证据。

3. Prompt Builder先预留输出和工具参数，再设置分区预算。重复内容去重，历史生成滚动摘要，检索文档抽取证据句，大结果改为Artifact引用；低置信摘要回退原文。评估压缩保真度、必需信息保留率、错误引用率、首Token延迟和成功率，以失败样本校准排序。

**相关知识点：** Instruction Hierarchy、Token Budget、Context Ranking、Rolling Summary、证据抽取、Artifact引用、冲突保留、压缩保真度。

### 6. Token成本怎么控制？（豆包一面）

**Token成本应以“单位成功任务的总Token与费用”为治理目标，通过精确计量、上下文裁剪、模型路由、缓存和调用预算联合控制。**

1. Trace记录输入、输出、缓存Token、模型、租户、Prompt版本、重试和任务结果，并归因Embedding、Rerank及工具成本。按任务设置Token、调用、工具和金额上限，超预算时压缩或降级。没有成功率维度的Token下降，可能只是减少有效推理。

2. 输入侧删除重复规则和完整历史，以滚动摘要保存状态；RAG动态Top-K，精排后只注入最小证据；大结果存Artifact。稳定前缀启用Prompt Cache，重复问法用Semantic Cache。**缓存键必须包含租户、权限、知识版本、模型和Prompt版本，命中后仍要校验新鲜度**。

3. 按复杂度路由模型：分类、抽取用小模型，复杂规划用强模型；限制无效ReAct循环，工具失败采用确定性重试和早停，输出设置max_tokens。批量Embedding和异步摘要降低开销。线上看每成功任务Token、缓存命中率、重试率、成功率、P95与费用，以质量门槛下的Pareto曲线选型。

**相关知识点：** Token Accounting、Budget Guard、模型路由、Rolling Summary、动态Top-K、Prompt Cache、Semantic Cache、Artifact Store、Pareto最优。

### 7. 为什么不能把所有聊天记录直接放进Prompt？

**全部聊天记录直接进入Prompt会放大成本、噪声、冲突、安全和隐私风险，长上下文不等于模型能无损利用所有历史。**

1. 历史长度会增加输入Token、延迟和费用，超过窗口时会截断。即使未超限，无关轮次也会稀释目标，使关键信息处于中部，并诱发模型沿用已失效计划、旧参数或误解。**上下文窗口是可容纳上限，不是有效注意力和可靠记忆的保证**；重复信息、相互矛盾的用户陈述也会降低输出稳定性。

2. 完整历史可能包含密码、个人信息、跨租户数据、已撤销授权和外部Prompt Injection；持续复制会扩大泄露面，并使低可信文本与系统指令竞争。工具输出通常体积大且具有时效性，旧搜索结果或旧文件内容若被重复注入，容易形成过期事实。聊天中模型生成的错误也可能被后续轮次当作已确认事实，造成误差累积。

3. 工程上应由Context Builder按优先级组装最小充分上下文：固定系统规则和当前请求，保留最近必要轮次，从历史中抽取目标、硬约束、用户确认事实与未决事项，再按需检索原文和长期记忆。摘要必须附来源与版本，数字、否定和决策不能模糊压缩；预算不足时先删除重复与低相关内容，并通过引用完整性、任务成功率、P95和Token成本验证裁剪策略。

**相关知识点：** Context Window、Token Budget、Lost in the Middle、注意力稀释、上下文污染、分层摘要、按需检索、Prompt Injection、最小充分上下文。

### 8. 静态知识如何进行权限隔离？

**知识权限隔离必须由服务端身份和数据层ACL强制执行，并贯穿原文、元数据、倒排索引、向量索引、缓存及生成引用。**

1. 接入时为文档及Chunk写入tenant_id、owner、classification、allowed_principals、allowed_roles、region和有效期，权限元数据来自IAM或源系统，不能由模型推断。租户使用独立命名空间或分区键，敏感域可采用独立索引和密钥；共享文档通过授权视图引用，避免复制后形成权限漂移。

2. 查询时先验证用户或服务主体，再以tenant和ACL做预过滤，之后才执行BM25、ANN和Reranker；向量相似度不得越过权限边界。**不能先全库召回再让LLM删除无权内容，因为候选、日志、缓存和Token都可能泄露数据。**缓存键包含主体或权限版本，引用展开和下载原文时再次授权，防止过期权限复用。

3. RBAC适合稳定岗位权限，ABAC适合结合部门、项目、地域、密级和时间动态决策，两者可组合；高敏数据执行最小权限和授权。权限变更通过事件驱动失效索引与缓存，并保存主体、资源、策略版本、决策和用途审计。测试覆盖跨租户、角色撤销、共享链接、缓存污染和批量导出，监控越权命中、拒绝率、权限同步延迟及审计缺失。

**相关知识点：** ACL、IAM、RBAC、ABAC、Tenant Isolation、Pre-filter、最小权限、缓存隔离、权限版本、审计日志、权限漂移。

### 9. 如何保证压缩后信息不丢失？

**压缩无法保证逐字无损，但可以通过强制字段、来源引用、自动校验和原文回溯，保证任务关键事实与约束不丢失。**

1. 压缩前先定义不可丢失Schema，包括目标、用户确认事实、数字、单位、否定、条件、截止时间、权限、审批、关键工具结果、错误、产物引用和未决事项；抽取式保留这些字段，生成模型只概括解释性文本。每个字段携带source_event_id和原文跨度，缺少来源时标为推断而非事实。

2. 发布前执行结构校验、字段级哈希或值比对、数字与实体一致性、否定检测、引用可达性和ACL交集检查；再用基于原文的问题集验证摘要能否回答关键问题。**摘要与原文冲突时必须以原文和权威事件为准，摘要只能作为可重建的派生视图。**低于事实保留阈值时拒绝发布并保留旧版本。

3. 原始事件按合规期限独立保存，摘要记录source_ids、覆盖区间、模型、Prompt版本和content_hash；高风险问题、低置信回答或用户追问时自动展开原文。更新原事件后反向标记相关摘要stale并重建。评测事实保留率、约束遗漏率、数字错误率、引用可达率、压缩前后任务成功差异和摘要漂移，并对关键场景持续回归。

**相关知识点：** Lossy Compression、强制槽位、Source Span、派生视图、事实一致性、引用可达性、Staleness、Progressive Retrieval、摘要漂移。

### 10. 如何处理已经失效的用户信息？

**失效的用户信息必须立即退出默认召回，并依据纠错、历史审计和隐私要求选择版本保留、归档或彻底删除。**

1. 用户明确更正、权威系统更新、有效期届满或授权撤销时，生成带event_id的变更事件。新值作为新版本写入，旧记录设置valid_to和superseded状态，并以supersedes关系关联；查询前按subject、status和有效时间硬过滤。当前请求中的明确陈述优先于历史记忆，但只在确认属于稳定变化后才长期更新。

2. **需要解释历史决策且允许保留时，旧值可进入审计域，但不得继续作为当前个性化依据。**地址、岗位等变化事实可保存有效区间；密码、令牌、撤销同意后的敏感数据和用户要求删除的内容不得以历史版本继续保存。存在来源冲突时保留并列候选并请求确认，不能静默选择最近写入值。

3. 状态变更通过Outbox同步向量、倒排、缓存和摘要；旧索引项先墓碑使其不可见，再异步清理并对账，关联摘要标记stale后重建。所有更新记录主体、来源、策略和时间，避免Agent自行推断失效。监控旧值命中率、更新传播延迟、缓存陈旧率、用户重复纠错率、删除完整性和历史域越权访问。

**相关知识点：** Valid Time、Supersedes、Bitemporal Data、用户纠错、审计域、Outbox、Staleness、墓碑删除、删除权、缓存失效。

### 11. Top-K参数应该如何设置？

**Top-K不应使用全局固定值，而应区分召回K、重排K和最终注入N，并根据查询难度、分数分布、Token预算及延迟动态调整。**

1. 初始召回K以保证Recall为目标，稀疏和稠密通道可分别设置候选数，融合去重后再送入Reranker；重排K受模型吞吐和P95约束，最终N受证据密度与Prompt预算约束。精确实体或编号查询通常需要较小K，多意图、多跳、短查询和长尾问题可提高K，但必须保留权限过滤。

2. 动态策略可利用查询分类、过滤后库规模、首尾分数、相邻分数断层、两路结果重合度和最低相关阈值决定早停；高风险任务提高可信阈值而不是盲目增加K。**K增大通常提高召回上限，也同步增加噪声、重排成本和上下文干扰，不能把“更多候选”视为更高准确率。**

3. 在按查询类型分层的Golden Dataset上扫描K组合，绘制Recall@K、NDCG、任务成功率、P95和成本曲线，选择满足质量SLO的最小值；再用A/B验证线上净收益。监控候选不足率、去重后数量、Rerank截断、最终证据采用率和Token浪费，索引、Embedding或数据分布变化后重新校准，禁止只沿用历史经验值。

**相关知识点：** Recall K、Rerank K、Top-N、动态Top-K、Score Gap、Early Stop、Golden Dataset、质量—延迟曲线、Token Budget、A/B测试。

### 12. 向量检索为什么会产生误召回？

**向量检索产生误召回，是因为Embedding压缩了语义细节，而近邻算法只优化几何相似，不验证事实、关系和业务约束。**

1. 模型可能把共享主题看得比关键差异更重要，例如“支持功能A”和“不支持功能A”向量仍很接近；数字、错误码、版本、实体和否定常被弱化。查询过短、多义或缺少会话实体时，表示会偏离真实意图；领域术语未进入模型训练分布也会造成空间失真。Chunk过大混入多主题，过小丢失限定条件，同样会使相似度不代表答案相关性。

2. ANN索引的近似搜索、量化和过低efSearch会带来邻居误差；只按固定Top-K返回会在低置信查询中强行给出无关结果。元数据过滤缺失则可能召回错误租户、时间或产品版本，索引未及时删除还会返回过期记忆。**向量分数不是可跨查询比较的真实性概率，不能仅凭阈值把候选直接作为事实注入。**

3. 定位时用标注集区分表示误差、切片误差、ANN误差、过滤错误和数据陈旧，比较精确KNN与ANN候选即可判断索引损失。优化包括查询补全、关键词与向量混合召回、结构化预过滤、领域Embedding、Cross-Encoder精排、动态阈值和无可靠结果拒答。评估Precision@K、困难负例误排率及分桶错误，而不能只看Recall。

**相关知识点：** Embedding、语义压缩、否定语义、Chunking、ANN、量化误差、元数据过滤、混合检索、Cross-Encoder、Precision@K、困难负例。
<a id="ctx-140"></a>
### 13. 什么是Context Pollution？

**Context Pollution是无关、过期、重复、冲突或不可信信息进入模型输入并干扰注意力与决策的现象。**

1. 污染来源包括旧对话、低相关RAG候选、失效Memory、重复Chunk、工具日志、矛盾规则及Prompt Injection。它不同于“上下文过长”：短Prompt也可能被一条错误指令污染，长Prompt若证据相关且结构清晰则未必污染。核心判断是信息是否降低任务信噪比、可信度或指令一致性。

2. 典型机制包括注意力被无关文本稀释、Lost in the Middle导致关键证据权重下降、旧状态覆盖新状态、冲突来源使模型随机选边，以及不可信数据被误当指令。**扩大上下文窗口只能提高容量，不能自动解决相关性排序、来源可信度和指令边界问题。**污染会表现为答非所问、事实混合、引用错误、工具参数偏离或安全策略被诱导绕过。

3. Prompt Builder按优先级和预算组装：固定系统约束与目标，只召回必要历史和证据；执行权限、版本、有效期过滤，再重排、去重和压缩。不可信文本以数据边界包裹，不能修改系统指令。监控证据密度、冲突率、错误引用率和任务成功率，通过消融定位污染来源。

**相关知识点：** Context Engineering、Token Budget、Prompt Builder、分层摘要、Contextual Compression、Lost in the Middle、证据密度、上下文污染。
<a id="ctx-141"></a>
### 14. 上下文污染会导致哪些问题？

**上下文污染会同时损害答案正确性、任务执行稳定性、安全边界、推理成本和问题可诊断性。**

1. 无关与重复内容会稀释关键证据，引发Lost in the Middle、答非所问和遗漏约束；过期Memory会产生错误事实，冲突内容使回答不一致。大量相似Chunk还会让模型误以为重复观点更可信，生成结果可能引用错误来源，表面流畅却无法追溯。

2. 对Agent执行而言，污染可能改变计划、误选工具、携带旧参数或重复执行有副作用的动作；不可信网页和工具输出若越过数据边界，还可能诱导泄露秘密或绕过策略。**污染不仅是质量问题，任何进入模型上下文的越权数据都已形成安全暴露，不能依赖生成后过滤补救。**因此授权和Prompt Injection防护必须发生在检索及组装阶段。

3. 冗余上下文增加输入Token、首Token延迟和费用，并降低缓存命中；多个来源混杂会让故障难以归因。应以消融实验分别移除历史、Memory、RAG和工具结果，观察正确率变化，配合trace定位污染层。监控证据密度、冲突率、过期内容命中、错误工具调用和单位成功任务成本；发现污染时重新检索或回退最小上下文，而不是继续追加说明。

**相关知识点：** Context Pollution、Lost in the Middle、注意力稀释、错误引用、Prompt Injection、越权暴露、工具误调用、证据密度、消融实验、单位成功任务成本。
<a id="ctx-142"></a>
### 15. 如何控制Prompt长度？

**控制Prompt长度应先建立分区Token预算，再通过按需检索、结构化裁剪、去重和保真压缩构造最小充分上下文。**

1. Prompt Builder为系统指令、当前问题、任务状态、历史、Memory、RAG证据、工具结果和输出预留独立预算；系统规则、用户当前目标、硬约束和直接证据优先。预算计算使用目标模型Tokenizer，并保留输出及工具调用余量，不能只按字符估算。每个片段记录来源、优先级、Token数、版本和截断策略，超限时按确定规则处理。

2. 历史对话只保留未决事项、用户确认事实与最近相关轮次，旧内容形成可回溯摘要；检索结果先做权限和有效期过滤，再精排、按来源与语义去重、合并邻接Chunk，仅抽取回答所需证据窗口。工具输出使用字段白名单和分页，日志仅保留错误摘要。**优先减少无关信息，而不是机械截断每段文本。**

3. 压缩采用抽取式优先：保留数字、实体、否定、条件、引用和工具错误；生成式摘要用于低风险叙述，并保存原文引用与摘要版本。运行时若超预算，按低相关候选、重复历史、工具明细的顺序剔除，必要时重新检索或分阶段执行。监控输入Token、证据密度、压缩保真度、P95、成本和任务成功率，用回归集防止缩短Prompt造成质量下降。

**相关知识点：** Prompt Builder、Token Budget、Tokenizer、最小充分上下文、结构化裁剪、语义去重、证据窗口、抽取式压缩、压缩保真度、分阶段执行。
<a id="ctx-143"></a>
### 16. Token Budget应该如何分配？

**Token Budget应先预留输出和安全余量，再按指令、当前任务、状态、证据、记忆与工具结果的优先级动态分配。**

1. 设模型窗口为W，先扣除期望输出、函数Schema及10%—20%安全余量，剩余才是输入预算。系统规则、当前问题和硬约束属于不可裁剪区；任务状态与直接证据次之，历史、记忆和工具明细按相关性竞争预算。使用目标模型Tokenizer计数，不能用字符长度代替，因为不同内容的Token密度差异明显。

2. 分配不应采用永久固定比例：知识问答提高RAG证据份额，长任务提高状态与工具结果份额，多轮个性化任务增加Memory份额。每个片段计算utility/token，可综合相关性、权威性、新鲜度和唯一性；先去除重复、过期及低可信内容，再压缩低密度片段。**预算目标是最大化单位Token的任务贡献，而不是把窗口填满。**

3. 超限时按低相关候选、旧历史、完整日志顺序剔除，必要时改为分阶段检索与执行；数字、否定、权限、错误信息和引用不可模糊摘要。建立不同预算档位的回归实验，比较任务成功率、证据忠实度、输入成本、首Token延迟与截断率，选择Pareto点。线上记录各分区实际用量和被裁剪原因，用失败样本持续校准策略。

**相关知识点：** 上下文窗口、输出预留、Tokenizer、不可裁剪区、动态预算、Utility per Token、证据密度、分阶段执行、Pareto最优、截断率。
<a id="ctx-145"></a>
### 17. Context Compression有哪些实现方式？

**Context Compression可分为确定性裁剪、抽取式压缩、生成式摘要、结构化状态化和分层按需展开五类方式。**

1. 确定性裁剪按优先级、时间窗、字段白名单和Token上限删除低价值内容，适合工具日志与重复历史；抽取式压缩从原文选择与查询相关的句子或证据窗口，事实保真度高；结构化状态化把长对话转换为目标、约束、已完成步骤、未决事项和错误等字段，适合Agent长期任务。这三类规则可审计，应优先用于数字、否定和权限信息。

2. 生成式摘要可采用滚动摘要、分层摘要或Map-Reduce，将低风险叙述压缩为更短文本，但必须保存source_ref、摘要版本和覆盖范围；摘要不能成为无来源的新事实。分层按需展开只在Prompt中放标题、摘要和索引，模型需要细节时再读取原文。**压缩不是一次性丢弃，关键内容应保持可回溯和可重新加载。**

3. 压缩流程先权限与有效期过滤，再去重、排序，随后按风险选择方法；超限时逐级降采样。评测比较压缩率、关键信息召回率、事实一致性、引用保持率、任务成功率和额外延迟，并构造数字、否定、冲突、代码错误及表格样本。若摘要失真或证据不足，应回退抽取片段或原文，而不是继续对摘要再摘要。

**相关知识点：** 确定性裁剪、抽取式压缩、结构化状态、滚动摘要、分层摘要、Map-Reduce、按需展开、压缩率、事实一致性、引用保持率。
<a id="ctx-149"></a>
### 18. Retrieval Pipeline应该如何设计？

**Retrieval Pipeline应按查询理解、强制过滤、多路召回、融合、精排、去重压缩和证据校验分阶段设计。**

1. 入口识别意图、实体、时间和是否需要检索，将追问改写为独立查询；认证上下文生成tenant_id、ACL、状态、有效期和版本过滤，禁止模型构造权限条件。按查询类型路由至BM25、Embedding、图或数据库，各通道保留候选来源、rank和trace_id，并设置上限及deadline。

2. 多路结果用RRF或学习融合，按document_id、memory_id和语义去重；Cross-Encoder再结合相关性、时效、权威性、重要性和冲突状态精排。**召回阶段追求正确证据进入候选，精排阶段控制最终精度，两者指标和故障不可混为一体。**最终按Token预算抽取最小证据窗口，保留标题、来源、版本及引用定位。

3. 全链路记录rewrite、过滤、各路候选、融合分数和精排结果；无高置信证据时拒答、澄清或扩大检索，通道超时可降级并标注风险。离线评估Recall@K、MRR、nDCG、Precision@N和引用完整率，线上监控正确率、零结果率、P95、成本及各通道边际贡献，并做版本回归。

**相关知识点：** Query Understanding、权限预过滤、多路召回、RRF、Cross-Encoder、语义去重、证据压缩、阶段Deadline、检索Trace、边际贡献。

### 19. 如何避免 Prompt 过长导致性能下降？

**避免Prompt过长应通过分区预算、按需检索、去重压缩和稳定前缀缓存，同时优化质量、延迟与费用。**

1. 为系统指令、当前任务、历史、Memory、RAG、工具结果和输出设置Token上限，使用目标模型Tokenizer计数并预留输出余量。系统规则、当前目标、硬约束和直接证据优先；历史只保留未决事项、确认事实和最近相关轮次，工具日志改为错误摘要与字段白名单。模板删除重复说明，将稳定公共前缀置前以提高缓存复用。

2. 检索先做权限、时效和版本过滤，再精排、按来源与语义去重、合并邻接Chunk，只抽取回答所需证据窗口；长期原文按需展开。压缩优先采用确定性裁剪和抽取式方法，生成摘要保存原文引用。**扩大上下文窗口不会消除注意力稀释和Lost in the Middle，信息选择仍是性能与正确性的核心。**

3. 超限时按低相关候选、旧历史、工具明细顺序剔除，复杂任务拆成检索、执行和汇总阶段。通过多档预算回归比较任务成功率、输入成本、首Token延迟、缓存命中与压缩保真度，选择Pareto点。线上记录各分区Token及裁剪原因，对突增告警；关键数字、否定、权限和错误信息禁止模糊摘要。

**相关知识点：** Token Budget、Tokenizer、Prompt Builder、前缀缓存、检索去重、证据窗口、抽取式压缩、Lost in the Middle、分阶段执行、Pareto最优。

### 20. 上下文窗口不足时如何选择保留哪些内容？

**上下文不足时应按指令优先级、任务必要性、证据可信度和单位Token价值保留最小充分信息，而不是简单保留最近文本。**

1. 第一优先级是System策略、当前问题、目标、硬约束和输出Schema；第二优先级是任务状态、依赖变量、未决事项及直接证据；第三优先级是相关偏好、历史摘要和背景。完整日志、重复候选、过期事实和无关闲聊优先删除，并为输出及工具调用预留空间。

2. Prompt Builder为片段计算相关性、权威性、新鲜度、唯一性和Token成本，执行权限与版本过滤后排序；同源相邻Chunk合并，证据抽取保留数字、否定、条件和引用。**“最近”只适用于会话连续性，不等于“最重要”；旧的系统约束或未完成任务依赖可能比最新闲聊更应保留。**摘要必须回指原文。

| 内容 | 优先级 | 处理方式 |
| --- | --- | --- |
| 指令与当前目标 | 最高 | 原文保留 |
| 最新状态与直接证据 | 高 | 去重、抽取 |
| 历史与工具明细 | 中低 | 摘要、按需读取 |

3. 若仍超限，将复杂任务拆为检索、局部推理和汇总阶段，或只放摘要索引并按需展开原文；不能裁剪关键权限和错误信息。通过不同预算档位回归，比较任务成功率、关键信息保留率、事实一致性、首Token延迟和成本。线上记录被剔除片段及原因，失败时重新检索或回退原文，持续校准策略。

**相关知识点：** 指令优先级、最小充分上下文、Utility per Token、证据可信度、抽取式压缩、历史摘要、按需展开、任务分阶段、保留率、回退原文。

### 21. 多轮会话摘要如何设计？

**多轮会话摘要应采用按主题分区的结构化增量摘要，区分确认事实、用户偏好、决策、待办与模型推断，并可回溯原始轮次。**

1. Schema包含summary_id、conversation_id、topic、time_range、goals、facts、preferences、decisions、constraints、open_items、source_turn_ids和version。字段标注来源、置信度与状态，用户原话和模型推断分开。并行主题分别维护摘要，任务状态独立保存Checkpoint，避免把闲聊、事实和工具结果混合。

2. 增量更新输入旧摘要与新增轮次，只变更受影响字段；用户更正通过新版本标记supersedes。达到Token阈值时，从原始事件重建摘要以校正漂移；数字、否定、承诺和未决事项采用抽取式保留。**摘要压缩表达而不创造事实，缺少证据的推断不得写成确定陈述。**

3. 组装时按主题取摘要、关键轮次和必要原文，旧主题只留索引并按需展开。评测字段覆盖率、事实一致性、未决事项保留率、压缩率和摘要漂移，构造话题切换、纠错与冲突样本。用户可修正摘要，异常时回退原文；模板、模型和Schema均应版本化。

**相关知识点：** 结构化摘要、主题分区、Source Turn、增量摘要、Checkpoint、版本链、摘要漂移、抽取式保留、按需展开、字段覆盖率。

### 22. 为什么上下文窗口越大不一定效果越好？

**更大的上下文窗口只提高可容纳信息量，不保证模型能正确定位、区分和使用信息，质量取决于信噪比与组织方式。**

1. 输入增长通常带来更多无关、重复、过期和冲突内容，稀释关键证据；模型对不同位置的利用并不均匀，重要信息位于中部时可能出现Lost in the Middle。相似段落重复还会造成虚假多数，旧状态可能覆盖新状态。窗口标称长度说明技术容量，不代表在全部长度上保持相同检索与推理精度。

2. 长输入增加预填充延迟、Token费用、显存或吞吐压力，并降低稳定前缀变化时的缓存收益；同时扩大敏感数据暴露面和Prompt Injection入口。**当新增Token的边际信息价值低于其噪声、成本与风险时，更长上下文会使端到端效果下降。**因此仍需权限过滤、检索、重排、去重、摘要和明确来源边界。

3. 应在相同任务集上比较不同长度与排列：固定关键证据，逐步加入干扰项并改变位置，测答案正确率、证据引用、约束遵循、P95和成本；再比较全量输入与检索压缩方案。生产中采用最小充分上下文，关键指令与当前目标优先，直接证据按相关性排序。需要全局综合时可分块推理后汇总，而非一次塞满窗口。

**相关知识点：** 上下文窗口、Lost in the Middle、注意力稀释、信噪比、预填充延迟、边际信息价值、Context Pollution、最小充分上下文、位置敏感、分块推理。
<a id="ctx-172"></a>
### 23. Lost in the Middle 问题是什么？

**Lost in the Middle是模型对长上下文中部信息利用率低于开头和结尾的现象，增加窗口并不能自动消除该注意力偏差。**

1. 典型实验将回答所需证据放在不同位置，并保持问题及其他内容不变；若证据位于中部时准确率明显下降，即说明模型存在位置敏感。该问题在多文档问答、长对话、代码仓库和长工具日志中都会出现：模型可能看到证据，却在生成时没有充分使用。它不同于截断，证据实际仍在窗口内，也不同于纯粹检索漏召回。

2. 成因包括训练数据的位置分布、位置编码外推、长距离注意力竞争及无关文本稀释；加入重复或冲突片段会进一步放大。**标称支持十万Token只说明输入容量，不保证每个位置的信息具有相同利用率。**因此把最相关证据机械拼在候选中部，或把关键系统约束埋入长模板，都可能降低指令遵循与事实正确率。

3. 缓解方式是减少无关上下文、Rerank后把关键证据靠近当前问题、用标题与结构标记分段、抽取证据窗口，并对长任务采用分块推理后汇总；不能简单复制证据到多处，以免产生偏权重。评测需绘制位置—准确率曲线，同时测不同长度和干扰强度。生产trace记录证据位置、Token区间与引用结果，持续校准排列策略。

**相关知识点：** Lost in the Middle、位置偏置、位置编码、注意力竞争、证据位置、位置—准确率曲线、Context Ranking、证据窗口、分块推理、上下文截断。
<a id="ctx-175"></a>
### 24. 如何设计 Context Ranking 机制？

**Context Ranking应先执行不可协商的优先级与权限规则，再对可选片段按任务相关性、可信度、新鲜度、唯一性和Token效率排序。**

1. System规则、当前问题与硬约束属于固定区，不参与软排序；History、Memory、RAG和Tool候选须通过tenant_id、ACL、有效期和版本过滤。候选保存source、type、timestamp、trust、token_count和引用。不同来源分别召回，避免分数未经校准直接比较。

2. 分数综合相关性、权威性、新鲜度、任务依赖和唯一性，再扣除冲突、冗余和Token成本；权重按查询类型变化。Cross-Encoder提供语义分，规则处理来源与时效。**Ranking目标不是选分数最高的片段，而是在预算内选择能覆盖任务所需事实且相互一致的最小集合。**因此加入MMR。

3. 排序后按来源和语义去重，冲突候选成组标注，再按预算选择片段：目标靠前，证据靠近问题，长材料只放证据窗口。训练数据来自引用采用和人工标注，困难负例包含过期、主体错误及相似反义内容。评估nDCG、Context Precision、覆盖率、任务增益、P95和单位Token价值。

**相关知识点：** Context Ranking、硬过滤、Cross-Encoder、来源校准、MMR、多样性、预算优化、Context Precision、困难负例、单位Token价值。
<a id="ctx-176"></a>
### 25. Agent 如何进行 Token Budget 分配？

**Agent应把Token预算分为输入上下文、规划推理、工具交互和最终输出四类，并根据任务阶段动态调整而非平均分配。**

1. 以窗口W为上限，先预留输出、工具Schema和安全余量，剩余输入按System、目标、状态、History、Memory、RAG与Tool分区。System规则、硬约束、Checkpoint和直接证据属于保护区；旧历史、低相关候选和日志竞争弹性预算。使用目标模型Tokenizer计数，并在工具返回后重算。

2. 预算随阶段变化：规划阶段保留目标、约束、可用工具和高层状态；执行阶段突出当前子任务、依赖变量和最近观察；汇总阶段保留结果、证据和未决风险。片段按相关性、可信度、唯一性、任务依赖和utility/token排序。**预算目标是最大化任务成功的单位Token贡献，而不是把窗口填满或让各来源平均占比。**

3. 超限时先过滤过期与重复内容，再删除低价值候选、压缩历史和工具结果；仍不足则分为多次调用，以Checkpoint传递状态。控制面设置每任务总Token、重试和金额上限，防止循环消耗。通过预算档位回归成功率、证据保留、P95与单位成功成本，选择Pareto点并记录裁剪原因。

**相关知识点：** Token Budget、Tokenizer、保护区、阶段预算、Utility per Token、Checkpoint、任务分解、重试预算、单位成功成本、Pareto最优。
<a id="ctx-179"></a>
### 26. Tool 调用结果如何压缩？

**工具结果压缩应保留完成下一步所需的结构化字段、错误、证据和产物引用，删除冗余日志但不改变执行事实。**

1. 为工具定义Result Adapter和最小Schema，如status、关键实体、变更数量、错误码、分页游标、artifact_uri和版本；数据库只返回所需列，搜索保留Top-N与引用，Shell日志保留退出码、stderr关键段和尾部，网页抽取正文与链接。大结果写工作区，Prompt只放引用及摘要。

2. 压缩顺序先字段白名单、过滤空值和重复行，再按当前子任务抽取相关片段，最后才对自然语言日志生成摘要。**任何会影响后续控制流的状态、数字、否定、错误、资源标识和副作用证明都必须原样保留。**敏感字段在进入模型前脱敏，分页与截断需显式标记，不能让模型误以为看到了完整数据。

3. 每次调用保留tool_call_id、参数哈希、结果哈希、压缩器版本和原始产物引用，使失败可重放与审计；后续Agent需要细节时按权限局部读取，而不重复整个结果。评测压缩率、关键字段保留率、下一步工具成功率、错误诊断率、额外延迟和Token成本，并构造超长日志、表格、二进制产物及部分失败样本。摘要不一致时回退原始片段。

**相关知识点：** Result Adapter、字段白名单、Artifact URI、分页游标、退出码、错误摘要、参数哈希、结果哈希、关键字段保留率、按需回读。
<a id="ctx-182"></a>
### 27. 上下文组装服务应该独立成微服务吗？

**当多个Agent或产品共享上下文策略、需要独立扩缩容与统一治理时应拆成微服务；早期单场景则优先保持模块化单体，避免无收益的网络边界。**

1. 独立服务的收益是统一执行指令优先级、历史摘要、记忆选择、检索证据、工具结果、Token预算、脱敏和引用格式，并集中管理模板版本、A/B实验与审计；调用方只提交结构化任务状态。若团队多、发布节奏不同或上下文组装计算较重，服务可独立扩容并复用缓存，减少各业务重复实现和策略漂移。

2. 代价是新增网络延迟、序列化、可用性依赖与跨服务调试复杂度，且上下文包含敏感数据，扩大传输和权限边界。**服务化的判断依据是复用、治理和扩缩容需求，不是Prompt Builder名称是否独立。**只有单一Agent、低QPS且策略频繁联调时，进程内模块通常更快；接口先抽象稳定，达到拆分阈值后再迁移。

3. 若拆分，API应输入结构化的system_policy_id、用户问题、状态、候选证据、权限上下文和token_budget，输出消息数组、引用映射、删减原因及版本，而非返回不可审计字符串。服务必须无状态或外置状态，配置可回滚，设置超时、熔断与本地降级。监控P95、Token利用率、压缩损失、缓存命中、失败率和Prompt质量回归。

**相关知识点：** 模块化单体、微服务边界、Prompt Builder、结构化API、策略版本、Token Budget、熔断降级、可观测性。
<a id="ctx-183"></a>
### 28. Prompt Builder 模块应该如何设计？

**Prompt Builder应是结构化、版本化且可审计的上下文编排器，负责按优先级和Token预算生成模型消息，而不是进行字符串拼接。**

1. 输入采用结构化对象，包括system_policy_id、任务目标、用户问题、会话状态、记忆、检索证据、工具结果、输出Schema、权限上下文和token_budget。内部按System、安全策略、业务流程、Skill、当前任务和不可信数据分层；动态内容使用清晰标签或消息角色，并保留来源、版本与可信级别，避免检索文本或工具结果被解释成高优先级指令。

2. 组装流程先解析模型上下文上限，预留输出与工具调用空间，再按硬规则、当前问题、任务状态和直接证据的顺序分配预算；随后完成相关性排序、去重、历史摘要和证据压缩。**Token预算裁剪必须遵守指令优先级，不能为了塞入更多资料删除安全策略、关键约束或工具错误。**

3. 输出为消息数组、引用映射、Token估算、模板版本与审计元数据。模板注册中心支持Schema校验、灰度、A/B和回滚；稳定前缀可缓存，动态证据不得跨权限复用。上线前回归指令遵循、注入防护、事实与格式，线上监控P95、Token利用率、裁剪率、缓存命中和任务成功率。

**相关知识点：** 消息分层、结构化输入、Token Budget、Prompt Registry、引用映射、Prompt Injection、前缀缓存、A/B测试、版本回滚。
<a id="ctx-185"></a>
### 29. 动态 Prompt 组装链路如何进行性能优化？

**动态Prompt组装应通过阶段并行、稳定前缀缓存、增量Token计算和有界压缩优化，优先消除串行等待与重复处理，而非盲目缩短内容。**

1. Trace拆分鉴权、意图、历史、记忆、RAG、工具、去重、压缩、渲染和Token计数耗时。互不依赖的记忆、知识库和工具预取并行执行，设置独立超时与取消传播；简单问答走快速路径。上游返回结构化片段及预估Token，避免重复解析全文。

2. System、政策、工具定义和模板骨架形成版本化稳定前缀，利用模型侧Prefix Cache；历史摘要、查询Embedding、授权后的检索结果可缓存，但键必须包含租户、ACL、知识与模板版本。**缓存不能绕过权限和新鲜度校验，动态用户数据也不能为了命中率放入跨用户公共前缀。**Token计数按组件增量缓存，最终只做一次精确校验。

3. 先用规则去重、字段裁剪和抽取式压缩，只有长文本再调用模型摘要；按剩余预算进行有界装箱，达到证据充分或边际收益阈值后早停。服务采用异步IO、连接池、批量压缩和预热，并在超时时回退到最近摘要或较小候选集。验收同时比较P95、首Token时间、Token数、缓存命中、Faithfulness与任务成功率，防止性能优化破坏证据。

**相关知识点：** 阶段Trace、异步并行、Prefix Cache、增量Token计数、快速路径、早停、抽取式压缩、Token装箱、取消传播。

### 30. 如何统计每轮请求的 Token 消耗？

**每轮Token消耗应以模型服务返回的Usage为权威值，并按Agent请求内的所有模型调用、重试、工具循环及缓存读写进行分项归集。**

1. 为轮次生成turn_id，每次调用生成call_id并关联请求、Agent、租户、模型和Prompt版本。记录input_tokens、output_tokens、cached_input_tokens、reasoning_tokens；流式结束时读取Usage，异常中断则保存Tokenizer估算并标注estimated，避免与权威值混合。

2. Agent一轮可包含规划、Query Rewrite、Rerank、工具反思与最终回答，应对所有LLM调用求和，并区分首次、重试、并行和取消。**一轮对话不等于一次模型调用，只统计最终回答会低估Token和成本。**Embedding按计费单位另列，不混入生成Token但纳入总成本。

3. 聚合层按turn_id计算总输入、输出、缓存节省、重试浪费和金额，并按租户、场景、模型及版本形成账单；价格表版本化。预算器在调用前估算额度，调用后用Usage校准。抽样对账供应商账单，检测Usage缺失和重复事件，监控每轮P50/P95、单位成功任务Token及异常突增。

**相关知识点：** turn_id、call_id、Usage、Input Token、Output Token、Cached Token、流式计量、价格版本、账单对账、预算控制。

### 31. 企业级 Agent 如何控制 Token 成本？

**企业级Agent应以单位成功任务Token和成本为目标，在预算控制、模型路由、上下文治理、循环终止与缓存复用五个层面联合降本。**

1. 请求进入时按租户、任务等级和SLA分配总Token、最大模型调用、工具轮次及金额预算，每次调用前预估剩余额度，超限则缩小候选、请求确认或终止。Usage按turn_id归集规划、Query Rewrite、工具后反思与最终回答，区分缓存Token、重试和无效分支；只有先建立分项账本，才能识别主要浪费来源。

2. 模型路由按任务复杂度选择最小可胜任模型，简单分类、抽取和格式化使用轻量模型，复杂推理再升级；Prompt Builder压缩历史、工具日志和RAG证据，只保留最小充分上下文。**上下文缩短不能删除安全规则、用户硬约束、工具错误和关键证据，否则节省Token会转化为重试与错误成本。**

3. 采用Prompt前缀缓存、查询Embedding缓存和经权限校验的Semantic Cache；ReAct循环设置完成条件、重复动作检测、无进展阈值和取消传播，防止无限反思。离线绘制任务成功率—Token—延迟曲线，线上监控每轮P50/P95、缓存节省、模型升级率、重试浪费和单位成功成本，并以质量、安全护栏做A/B验证。

**相关知识点：** Token Budget、Usage归集、模型路由、上下文压缩、Prompt Cache、Semantic Cache、循环终止、单位成功任务成本。

### 32. 如何控制Context Window和Token成本？

**控制Context Window应先分配硬预算，再按指令优先级和证据价值选择最小充分上下文，并通过模型路由、缓存和循环约束控制总Token成本。**

1. 每轮根据模型上限预留系统指令、输出、工具参数和安全余量，剩余预算分配给问题、状态、历史、记忆和RAG证据。保留顺序是不可变规则、用户约束、当前目标、最新状态、直接证据，再处理背景；Prompt Builder按组件计数并记录删减原因，不能静默截断句子或JSON。

2. 历史对话提炼未决事项、已确认事实和最近交互，完整原文外置；检索结果先Rerank、去重、合并相邻Chunk并抽取必要句段，工具结果只保留状态、关键字段和错误。**上下文压缩必须保留否定、数字、主体、来源及失败信息，否则节省Token会改变任务语义。**证据不足时二次检索，而非扩大所有候选。

3. 简单任务路由轻量模型，复杂任务才升级；稳定前缀使用Prompt Cache，语义缓存必须校验权限和版本。Agent设置最大调用、工具轮次、无进展阈值和取消传播，避免反复推理。监控每轮输入输出Token、各组件占比、裁剪率、缓存节省、重试浪费和单位成功成本，并用Golden Dataset验证正确性与Faithfulness未下降。

**历史别名：** `ARC-032`。

**相关知识点：** Context Window、Token Budget、Prompt Builder、历史摘要、Rerank、上下文压缩、模型路由、Prompt Cache、循环终止。

### 33. 长对话场景如何进行上下文压缩？

**长对话压缩应把原始消息转化为结构化任务状态、分层摘要和可检索历史，在保留约束与证据的前提下减少重复Token。**

1. 先将对话拆成不可压缩的System规则、用户硬约束、当前目标、已确认事实、未决事项、工具状态和普通闲聊。任务状态使用JSON等结构保存实体、参数、步骤、错误与版本，避免每轮从自然语言重新推断；最近若干轮保留原文，早期内容形成阶段摘要，完整消息存外部日志并以message_id回溯。

2. 摘要应采用增量合并并生成版本，重点保留否定、数字、主体、时间、用户更正、决策理由和工具失败；重复寒暄、已完成细节及完整工具日志可删除。**压缩的正确标准不是文本更短，而是后续任务所需状态能够无歧义恢复。**对高风险事实采用抽取式保留和引用，模型式摘要需做事实一致性校验。

3. Prompt Builder按优先级装入当前问题、状态、最近消息、相关摘要和检索历史；旧内容通过语义或实体索引按需取回，而非全部常驻。达到Token阈值再触发压缩，并保留上一摘要以便回滚。评估指代解析、约束保持、更正生效、事实丢失率、摘要压缩率和任务成功率，使用长对话回放定位首次丢失信息的轮次。

**历史别名：** `MODEL-074`。

**相关知识点：** 结构化任务状态、滑动窗口、分层摘要、增量摘要、抽取式压缩、历史检索、message_id、事实一致性、摘要回滚。
<a id="ctx-196"></a>
### 34. Token消耗主要集中在哪些部分？

**Agent的Token主要消耗在上下文的重复携带、多轮模型输出、工具循环与重试，以及RAG证据及工具结果的持续回填。**

1. 输入Token包括System规则、工具Schema、历史、记忆、RAG证据、工具结果和问题。这些内容会在规划、反思和回答时重复发送，累计成本高于单次Prompt；工具多、Chunk长、日志回填时明显。稳定前缀可缓存时，计费和延迟结构变化。

2. 输出Token来自计划、推理、Function Calling参数、摘要、修复和最终答案；ReAct每多一轮都会再次产生输入输出。**Agent一轮交互往往包含多次模型调用，重试、并行分支和无进展循环是易遗漏的Token放大器。**Embedding和Rerank可能按输入Token计费，应单列后纳入总成本。

3. 以turn_id聚合call_id，按system、tools、history、memory、retrieval、tool_result、reasoning和output分类，并记录cached与retry。按占比压缩历史和工具结果、减少RAG重复、按需加载工具、设置循环上限、路由轻量模型及使用Prefix Cache。最终比较单位成功任务Token。

**相关知识点：** Input Token、Output Token、Cached Token、工具Schema、RAG证据、ReAct循环、重试放大、turn_id、单位成功任务Token。
<a id="ctx-197"></a>
### 35. Agent系统中哪些内容最占上下文窗口？

**Agent上下文通常由长对话历史、RAG证据、工具Schema与工具结果占据大部分空间，具体占比取决于工具数量和任务迭代轮次。**

1. System与业务策略一般相对稳定，但复杂企业流程也可能较长；工具Schema会随工具数量、参数描述和枚举快速增长，并在每次允许调用时重复出现。多轮历史持续线性累积，若包含代码、表格或附件转写，往往成为最大项。应使用实际Tokenizer按system、tools、history等组件计量，不能凭字符数估算。

2. RAG为了高召回会注入多个Chunk，其中重复、邻接和长表格显著占用Token；工具返回的原始JSON、日志、网页和错误堆栈也会在ReAct循环反复回填。**最占空间的往往不是用户最后一句，而是系统为模型附带的历史、证据和能力描述。**模型输出与中间摘要在下一轮又变成输入，形成累计放大。

3. 优化按占比进行：工具按需注册或缩短描述，历史提炼为任务状态和分层摘要，RAG精排去重并抽取证据，工具结果只保留关键字段与引用；System规则仅去重，不删除安全约束。监控组件Token的P50/P95、窗口占用率、截断率和任务成功率，异常增长时由预算器限额并保留审计原因。

**相关知识点：** Tool Schema、Conversation History、RAG Chunk、Tool Result、Token Attribution、按需工具、历史摘要、证据压缩、窗口占用率。
<a id="ctx-198"></a>
### 36. 如果上下文窗口不足，应该优先保留哪些信息？

**上下文不足时应依次保留高优先级指令、当前问题、用户硬约束、最新任务状态和直接证据，再压缩辅助历史与低价值材料。**

1. 第一优先级是System安全策略、权限与不可变业务规则；第二是用户当前问题、明确格式、范围、截止时间等硬约束；第三是执行当前步骤必需的目标、已确认事实、工具状态、错误和未决事项。模型输出预算和工具调用空间要预先保留，不能先塞满输入再截断JSON或最终答案。

2. 事实型回答优先保留与问题直接相关、权威、最新且可引用的最小证据；多跳任务必须保证完整证据集合，而不是只留下最高分单块。**保留顺序由指令优先级和任务必要性决定，不能仅按向量相似度从高到低截断。**冲突证据需保留双方版本与生效时间，关键否定、数字、主体和工具失败不得被摘要抹去。

3. 可删除重复Chunk、已完成过程、闲聊、过期状态和完整原始日志；早期对话形成分层摘要，长证据做抽取式压缩，原文外置并保留引用。Prompt Builder为每类内容设置最小与最大预算，记录被裁剪项和原因；若仍缺关键证据，应二次检索、请求澄清或拒答。评测约束保持率、证据覆盖率、Faithfulness和截断错误率。

**相关知识点：** 指令优先级、Token Budget、最小充分证据、证据集合覆盖率、抽取式压缩、分层摘要、裁剪审计、拒答。
<a id="ctx-199"></a>
### 37. Prompt长度增加为什么会导致成本上升？

**Prompt变长会直接增加输入Token计费，并扩大注意力计算、KV Cache、传输和排队资源；在Agent循环中还会被多次重复放大。**

1. 模型服务按输入和输出Token计费，Prompt每增加历史、工具Schema或RAG证据，包含它的调用都会增加输入费用。ReAct中相同上下文可能用于规划、工具反思和最终回答，一轮交互的增量成本等于新增Token乘以调用次数，而不是只计算最后一次生成。

2. 计算侧需要为更多Token执行注意力预填充并保存KV Cache，消耗GPU时间与显存，降低可并发批次并增加首Token；虽然具体复杂度受模型架构和优化影响，但资源不会免费。**长Prompt的成本不仅是账单中的输入Token，还包括吞吐下降、尾延迟和扩容需求。**超长输入还可能挤压输出空间并提高重试概率。

3. 通过Token归因识别增长来源，采用历史摘要、RAG去重压缩、按需工具Schema、输出上限和循环终止；稳定前缀可使用Prompt Cache，但动态敏感内容不能共享。评估不同长度下的任务成功率、Faithfulness、首Token、P95、吞吐和单位成功成本，选择边际质量收益低于成本的位置，而非机械追求最短Prompt。

**相关知识点：** Input Token计费、Attention Prefill、KV Cache、首Token延迟、吞吐、ReAct放大、Token归因、Prompt Cache、边际成本。
<a id="ctx-202"></a>
### 38. Tool Result 应该如何组织到 Prompt 中？

**Tool Result应作为与call_id关联的结构化tool消息进入Prompt，明确状态、来源、时间和有效载荷，并只保留当前决策所需内容。**

1. 字段包括tool_name、call_id、status、source、schema_version、payload、error和artifact_ref；成功与失败须区分，空结果不能伪装成成功。消息使用tool角色与assistant调用配对，并行时按call_id归属，不应改成user文本或混入System指令。

2. Payload保留决策字段、数字、单位、错误码和引用，大JSON、日志、文件及网页外置并提供artifact_ref；长文本抽取压缩。**工具结果属于外部数据而非高优先级指令，即使包含“忽略规则”等文字，也不得改变System策略或触发危险动作。**

3. 执行器在入Prompt前进行Schema校验、脱敏、权限、注入检测和限长，并记录截断；Prompt Builder按当前步骤和Token预算选择结果，但须保留失败状态和来源。测试覆盖超时、部分成功、空值、恶意输出、超长结果及乱序，指标包括Schema通过率、引用准确率、压缩率、注入成功率和错误恢复率。

**相关知识点：** tool角色、call_id、Tool Result Schema、artifact_ref、结构化错误、抽取式压缩、Prompt Injection、脱敏、来源追踪。
<a id="ctx-203"></a>
### 39. ReAct Agent 的 Prompt 是如何动态变化的？

**ReAct Prompt在每轮保留稳定策略与任务目标，并追加动作、工具Observation和更新后的任务状态，直至满足终止条件或预算耗尽。**

1. 初始Prompt包含System规则、可用工具Schema、用户目标、已知状态和预算；模型先输出工具调用或最终回答。执行器将Action转换为真实调用，把带call_id、status、payload或error的Observation作为tool消息回填，下一轮模型依据新证据修订计划。工具集合也可随权限或任务阶段变化，但变更必须可审计。

2. 随轮次增长，原始Action/Observation会迅速占满窗口，因此只保留当前目标、已确认事实、未解决约束、关键错误和最近交互，完整轨迹进入外部Trace；旧步骤形成结构化状态或摘要。**压缩不能删除失败原因、已执行副作用和幂等键，否则Agent可能重复动作或沿错误路径循环。**

3. 每轮由状态机检查任务是否完成、证据是否充分、动作是否重复、预算和截止时间是否超限，再决定继续、澄清、降级或终止；相同失败禁止无界重试。评测不仅看答案，还统计任务成功率、平均轮次、无效动作、重复调用、Token、P95和误执行率。回放Trace可定位是哪次Observation导致计划偏移。

**相关知识点：** ReAct、Action、Observation、tool消息、任务状态机、轨迹摘要、幂等键、循环终止、Trace回放、无效动作率。
<a id="ctx-205"></a>
### 40. 如何控制 Prompt Token 成本？

**Prompt Token成本应通过分项计量、预算分配、上下文压缩、缓存与模型路由联合控制，并以单位成功任务成本而非单次Token数评价。**

1. 按指令、问题、历史、RAG、工具结果和输出预留量统计Token，并按场景和模型归因。为各区设置预算：安全规则与当前目标优先保留，历史转为状态或摘要，RAG执行动态Top-K、去重和抽取压缩，大型JSON与日志外置。超限时按优先级裁剪，不能删除权限、关键数字和失败状态。

2. **稳定前缀适合Prompt Cache，重复查询可在权限和新鲜度成立时使用Semantic Cache。**缓存键包含租户、ACL、知识版本和模型，命中后仍校验授权。分类、抽取和摘要可路由小模型，复杂推理再升级；限制Agent循环、工具返回、重试和最大输出，防止Token放大。

3. **优化必须守住任务质量、延迟和安全边界。**离线比较裁剪前后的成功率、事实一致性、引用准确率和压缩保真度；在线监控Token、缓存命中率、重试放大、P95延迟及每成功任务成本。通过A/B实验寻找Pareto前沿；若摘要失真、召回不足或失败率升高，应回退原文、增加预算或升级模型。

**相关知识点：** Token Accounting、Token Budget、Prompt Cache、Semantic Cache、模型路由、动态Top-K、Context Compression、重试放大、单位成功任务成本、Pareto前沿。
<a id="ctx-206"></a>
### 41. Context Compression 如何实现？

**Context Compression应按信息类型采用规则裁剪、抽取压缩、分层摘要和结构化状态化，在降低Token的同时保留约束、证据与可追溯性。**

1. 将上下文拆为规则、目标、历史、记忆、RAG和工具结果，并标注优先级、来源、权限及Token。安全规则、用户约束、未决事项、关键实体、数字与单位、否定条件、工具错误和引用必须保留；重复消息、已完成步骤、过期状态及低相关证据可裁剪。

2. **事实证据使用抽取式压缩，历史采用滚动摘要，长任务采用分层摘要与结构化Task State。**摘要Schema记录goal、constraints、decisions、completed、pending、open_questions，保存source_span或artifact_ref。模型压缩须检查事实一致性；冲突信息不能合并，应保留版本、时间和来源。

3. Prompt Builder依据预算选择摘要层级，优先加载最新状态和直接证据，需要细节时展开原文。**压缩过程必须可版本化、可回滚，并在更新后校验完整性。**离线比较任务成功率、事实召回率、引用准确率和压缩比；在线监控摘要漂移、状态遗漏、Token及恢复率，字段缺失时回退版本或读取原文。

**历史别名：** `CTX-167`。

**相关知识点：** Context Compression、抽取式压缩、滚动摘要、分层摘要、Task State、Prompt Builder、摘要漂移、压缩保真度、artifact_ref、可逆压缩。
