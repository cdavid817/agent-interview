## 一、既有题与新题的软冲突（5 处）

新增的源码级题目在细节上比既有的官方资料级题目更精确，两边可调和但都没有交叉说明。读者同时看到会困惑。**不建议用源码分析结论去改官方资料来源的既有题**——那会破坏本次刚建立的来源区分。合适的做法是在既有题上加一句「实现层面的细节见 X」。

| 议题 | 新题 | 既有题 | 说明 |
|---|---|---|---|
| Bash 能否并行 | `CC-106` | `CC-035`（「Bash 等有状态工具通常串行」） | 源码里 Bash 的并发安全性等同于本次命令是否只读，两条只读命令可并行 |
| Auto Memory 常驻 vs 召回最多 5 条 | `CC-126` | `CC-087` | 是两套机制（CLAUDE.md 指令加载 vs frontmatter 记忆召回），两边都没说明是两套 |
| 前缀精确匹配 vs 缓存编辑删除 | `CC-111`、`CC-122` | `CC-086` | 服务端 context editing 是「前部变化即失效」规则的例外 |
| PostToolUse 能否改写输出 | `CC-112`、`CC-135` | `CC-094`（「只能反馈」） | `CC-094` 表述过窄 |
| 子代理权限边界 | `CC-130` | `CC-068`、`CC-097` | `CC-130` 已加层级限定；既有两题未标层级，属既有不精确 |

## 二、两个产品章节的术语分裂

同机制异名，互不交叉引用。**不建议统一改名**（两个产品确实是不同实现），建议每处加一次括号对照。

| 概念 | OpenCode 章 | Claude Code internals |
|---|---|---|
| 压缩后存活标记 | 检查点 / 最新压缩序号 | 压缩边界 / 边界标记 |
| 读时重算历史 | 历史投影 | 读时投影 |
| 响应式压缩 | 溢出补救 | 响应式压缩 partialCompact |
| 缓存断点 | 缓存断点 | 动态边界 |
| 工具结果回填 | 工具结算 | 结果回填 |
| 大输出外置 | 有界化 / 受管文件 | 结果落盘 |
| epoch | 纪元（上下文基线周期） | 代际号（工作端互斥计数）—— **同词两义** |

另有 `fork` 一词撞车：`internals.md` 里指 forkedAgent 子代理，`claude-code-basics.md` 里指 `--fork-session` 会话分叉，全库无消歧。

本分支自造的三处大小写/用词分裂：`Schema 清理` vs `schema 清理`、`单写者全序` vs `单写者所有权`、`回放一致性测试` vs `重放一致性测试`。

## 三、缺失的守护

1. **每文件 `本文件共 **N** 题` 表头无校验。** 现状是既有惯例不统一：37 个含历史别名锚点的文件里，36 个的表头 = 题数 + 别名锚点数，本分支把 `tools-permissions.md` 改成了纯题数（方向对，但成了异类）。**加守护会立刻在 36 个既有文件上失败**，需要先统一口径再加。
2. **来源标签与 references.md 小节未绑定。** `validate.py` 接受「官方资料」与「源码分析」两个标签，但不检查该章 `references.md` 里是否真有对应小节。`openclaw/references.md` 目前只有官方小节，却可以合法声明「源码分析」。
3. **来源行无法带锚点。** 校验用的是字面子串 `来源：[X](references.md)`，写成 `references.md#源码分析资料非官方` 会直接判失败。代价是点「源码分析」落地在一个首节为「官方核验资料」的页面。

- `docs/00-guide/question-schema.md` 可补一句：**「可测口径」属仓库既定体裁（`METRIC_SIGNAL_RE` 强制），不在「来源」声明的覆盖范围内**。这是来源边界的一个真实缺口——60 道题结尾的验证口径都是作者构造的，源文档里没有。
- `scripts/build_glossary.ps1` 的 `$sourceDefaults` 缺 `"opencode"`。

## 六、既有设计脆弱性（非本分支引入）

术语索引的阈值机制：全库有 99 个术语恰好卡在 5 次阈值上（含 `健康检查`、`有界队列`）。任一「相关知识点」行的改动都可能让某个词掉出索引，触发约 200 行重编号 diff 甚至校验失败。改这类行前应先跑术语统计。
